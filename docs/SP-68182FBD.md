# 프로세스 모델(Process/AddressSpace) — 설계 제안 및 1차 구현

계획 PN-16CA347D("유저랜드 준비, 첫 프로세스 기동")의 첫 증분.
SP-8B6B8D25 §2-B(유저 프로세스 페이지 폴트 처리 정책)와 §5(가상
메모리 주소공간 관리)를 실제 구조로 옮기는 작업 - 이 문서는 이번
증분에서 **이미 구현/검증한 것**과, 다음 증분(ELF 로더/프로세스
생성-exec/ring3 진입)에 착수하기 전에 **먼저 확인해야 하는 것**을
같이 담는다.

## 1. 이번 증분에서 구현/검증 완료 (커밋 예정)

### 1.1 `Paging`에 "아직 CR3에 없는 주소공간"을 직접 구성하는 능력 추가

- `Paging::mapPage`/`unmapPage`에 선택적 `pml4Phys` 인자 추가(생략 시
  기존과 동일하게 현재 CR3) - 새 프로세스의 주소공간을 CR3 전환 없이
  direct map을 통해 직접 구성할 수 있다(구성 도중 인터럽트가 끼어들어도
  지금 실행 중인 주소공간을 전혀 안 건드림 - 기존 호출부는 전부 무변경
  동작).
- `Paging::currentPml4Phys()`(진단/재사용 공개) 추가.
- `Paging::createAddressSpace()`: 새 PML4 프레임을 확보해 0으로 초기화한
  뒤, **커널이 사는 canonical higher half(PML4 인덱스 256~511)만
  현재 PML4에서 엔트리째로 복사**한다 - `kDirectMapBase`
  (`0xFFFF800000000000`)가 정확히 이 경계(bit 47 부호 확장)라서,
  direct map/지연 매핑 구역/커널 이미지 자신까지 이 한 범위 복사로
  전부 커버된다. 엔트리(포인터+플래그)만 복사하므로 실제 하위 테이블은
  모든 프로세스가 물리적으로 공유한다(표준 기법 - "커널은 모든
  주소공간에서 항상 같다").
- `Paging::destroyAddressSpace()`: PML4 프레임 반납(하위 절반은 호출부가
  먼저 전부 unmap 했다는 전제).

### 1.2 `Process` 클래스 (신규, `minicore/kernel/process.h/.cpp`)

- `pml4Phys`(이 프로세스 전용 주소공간), `mainThread`(v1: 프로세스당
  스레드 1개), `FaultInfo lastFault`(§2-B가 요구하는 "폴트 정보를 그
  프로세스의 PCB에 매단다"의 자리 - 필드만, 아래 2.3 참고).
- `UserThread`(syscall.h)에 `Process* process` 백포인터 추가(전방
  선언, `async_task.h`의 `struct Task;`와 동일한 관례로 순환 include
  회피).

### 1.3 검증(QEMU)

임시 스모크 테스트(검증 후 제거) - `Process` 두 개를 만들어 확인:
PVH 단일 코어, GRUB(multiboot2) 단일 코어, GRUB+q35 `-smp 4`(4코어
SMP, AP 3개 정상 기동) 전부 통과:

- 두 프로세스 다 `init()` 성공.
- 두 PML4의 인덱스 256~511이 부트스트랩 PML4와 **완전히 동일**(공유
  확인).
- 두 PML4의 인덱스 0~255가 **전부 0**(유저 하위 절반이 비어 있는
  새 주소공간으로 시작함을 확인).
- 두 PML4가 **서로 다른 물리 프레임**(독립된 주소공간임을 확인).

## 2. 다음 증분(ELF 로더/프로세스 생성-exec/ring3 진입) 착수 전 확인 필요

RM-23F4B687 §4(명시되지 않은 설계는 임의로 결정하지 않는다) 원칙에
따라, 아래 네 가지는 이번 증분에 포함하지 않고 질의로 등록했다 -
**네 개 전부 설계자 답변으로 확정 완료(2026-09-14)** - 다음 증분
착수를 막는 설계 공백은 이제 없다.

- **QU-72108298 답변**: "128TB가 맞는데 오기한것." → SP-8B6B8D25 §5를
  128TiB로 정정 완료.
- **QU-7043EA6D 답변**: "코드 공간은 0x400000 번지(4MB) 부터 시작하고
  스택 공간은 유저 공간의 끝점에서 부터 맵핑. Stack-overflow 탐지를
  위한 guard 페이지 필요. 코드 공간 역시도 프로그래밍되지 않은 영역에
  대한 실행을 탐지하기 위한 guard 페이지가 필요해." → SP-8B6B8D25에
  §5-A로 반영 완료.
- **QU-0C4D25EF 답변**: "폴트 정보를 읽고 그걸 처리해서 프로세스를
  죽이는 비동기 작업이 프로세스를 죽이거나 swapfs에서 읽어서 페이지를
  갈아 끼워 줘야해. TaskState는 단순하게 블로킹 상태로 만들면 돼.
  어차피 얘를 블로킹 시킨 원인으로서 폴트 정보가 매달린건데, 그게
  처리되기 전까지 프로세스가 실행되지 않게만 막으면 돼." → 새
  TaskState 불필요, 기존 Blocked 재사용으로 확정 - Process.h에 반영
  완료(처리 주체인 비동기 작업/swapfs 자체는 아직 없어 그 인프라가
  생길 때 실제 연결).

### 2.1 §5 "유저랜드는 0~256TiB" 수치와 4레벨 페이징의 실제 상한 불일치

x86_64 4레벨 페이징에서 canonical 하위 절반(bit 47=0)은 PML4 인덱스
0~255(256개) × 512GiB = **128TiB**가 수학적 상한이다(5레벨 페이징을
쓰지 않는 한). §5는 "0번지부터 256TiB까지"라고 명시하는데, 이는 표준
4레벨 페이징 하위 절반의 정확히 2배다 - 오기(128TiB의 착오)인지,
아니면 5레벨 페이징(PML5, 57비트 가상주소)을 실제로 의도한 것인지
확인이 필요하다(후자면 부팅/CR4.LA57/CPU 지원 여부 등 훨씬 큰 파급
효과가 있다).

### 2.2 유저 주소공간 내부 레이아웃

§5는 "세그멘테이션으로 조회 속도 최적화", "라이브러리 로딩/재배치
최적화 가능"이라는 방향만 제시하고 구체 경계가 없다. ELF 로더가
실제로 어디에 텍스트/데이터를 얹을지 정하려면 최소한:

- ELF 로드 베이스(고정 주소 vs 이번 v1은 비-PIE라 ELF 자체의
  링크 주소를 그대로 쓰는지)
- 유저 스택 위치/기본 크기
- 힙(brk류)/향후 mmap 영역의 대략적 구획

정도는 확정이 필요하다 - 지금 단계에서 완전히 정밀할 필요는 없지만
(RM-23F4B687 §4 취지상 숫자 튜닝 수준은 구현 중 계측으로 판단 가능),
"구획을 어떻게 나눌지"의 큰 그림은 설계자 확인이 필요하다고 판단했다.

### 2.3 유저 모드 페이지 폴트 정책(§2-B)의 "그다음"

§2-B는 "그 프로세스만 블로킹시키고 스케줄러가 다음 작업으로 전환,
폴트 정보는 PCB에 매달아 둔다"까지는 확정했지만, **그 뒤 누가/언제
다시 그 프로세스를 깨우는지**는 아직 없다:

- 새 `TaskState`(예: `Faulted`)가 필요한가, 아니면 기존 `Blocked`를
  재사용하고 "왜 Blocked인지"는 `Process::lastFault.pending`으로만
  구분하는가?
- v1 범위에서는 "깨우는 주체" 자체가 없어(시그널/디버거 등 미착수)
  한 번 유저 폴트가 나면 그 스레드는 영구히 멈춘 채로 남는 것이
  의도된 v1 동작인지(추후 시그널/강제종료 인프라가 생기면 그때
  연결) 확인이 필요하다.

### 2.4 "첫 프로세스"의 정체와 유저랜드 빌드 체계 — 답변 확정 (2026-09-14, QU-FF3F0CAA)

> (1) 이 리포에서 작업하는 모든 유저 영역 서브 프로젝트들은 리포
> 루트의 `userland` 디렉터리에서 작업할텐데, 그 안에 `apps`, `libs`,
> `tests` 폴더를 만들고 각 유저 영역 서브 프로젝트 이름별로 하위
> 폴더를 만들어서 작업할거야. 일단 최초의 라이브러리는
> `userland/libs/libmc`(MiniCore 라이브러리, 커널 및 "커널 서비스"들의
> API를 노출하기 위한 라이브러리)이고, 테스트용 유저 런타임 라이브러리는
> `userland/tests/libuserlandtest`로, 테스트용 앱은
> `userland/tests/userlandtest`로 만들어. 추후에 동적 라이브러리도
> 되는지 테스트할 때 재활용할 수 있도록 `libuserlandtest`는 `shared`와
> `static` 양쪽으로 컴파일될 수 있어야 한다.
>
> (2) initrd(CPIO)의 구조는 그냥 모든 파일을 루트에 다 넣어버려.
> 일단 initrd 내에서 커널이 최초로 유저영역 용으로 구동할 앱은
> 하드코딩되어야 해. `init`이야. `init` 앱은 유저 영역의 일반 유저
> 앱과 커널 앱의 중간 지점에 있다고 생각하는데, 그러므로 예외적으로,
> `minicore/init`에 만들도록 해.

**정리**:

- 디렉터리: `userland/{apps,libs,tests}/<프로젝트명>` — 첫 라이브러리
  `userland/libs/libmc`(커널/커널 서비스 API 노출), 테스트용
  `userland/tests/libuserlandtest`(shared+static 둘 다 빌드),
  `userland/tests/userlandtest`.
- **`init`만 예외** - 일반 유저 앱이 아니라 유저 앱과 커널 앱의
  중간 지점이라 `userland/` 밖 `minicore/init`에 만든다. 커널이
  최초로 구동할 유저영역 프로그램은 이 `init` **하나로 하드코딩**.
- initrd(CPIO) 레이아웃: 서브디렉터리 없이 **전부 루트에 평면 배치**.

**추가 지시(같은 날, 메시지)** - ELF 로더 위치/컴파일 방식: `ELF`
로더는 `minicore/libs/libelf`에 두고 **커널/유저 영역 양쪽에서 링크
가능**해야 한다 - 매크로로 커널/유저 빌드를 구분하고, **기본값은
유저 영역용 컴파일**로 한다.

**남은 것(다음 증분에서 실제 착수)**: `userland/` 디렉터리 스캐폴딩
+ 별도 유저랜드 툴체인(비-PIE, 링크 베이스 0x400000 - §5-A), `libelf`
(`minicore/libs/libelf`), `libmc`, `minicore/init`, 프로세스 생성/exec,
ring3 진입(PN-124C105B) - 이제 전부 착수 가능(설계 질문 4건 모두 해소).

## 3. 참고

  (신규), `minicore/kernel/syscall.h`(`UserThread::process` 필드 추가).
