# 커널용 lock-free 공유/약한 포인터 템플릿 (`SharedPtr<T>`/`WeakPtr<T>`) — 설계 제안

설계자 메시지(2026-09-16): "lock-free 기반으로 커널용 공유 포인터
템플릿들을 설계해봐."

**이건 완전히 새로운 개념이 아니다** - `AsyncTaskWeakRef`(async_task.h/
.cpp, PN-D01B7D07, SP-F682B889 §3.7)가 이미 정확히 이 패턴을
AsyncTask 전용으로 한 번 구현해 뒀다(그때도 설계자 지시가 "lock-free
기반으로 약한 참조를 구현해"로 문구까지 거의 동일했다, 실측 확인). 이
문서는 **그 검증된 패턴을 임의 타입 `T`에 쓸 수 있는 범용 템플릿으로
일반화**한다 - `EventTopicRegistry`가 SP-71DA77B3의 검증된 구독자
슬롯 패턴을 일반화했던 것과 같은 종류의 작업이다.

**[확장, 2026-09-16, 설계자 지시("UniquePtr 같은 것들도 추가
설계")]** DC-21647E46(포인터 전면 교체 검토) 논의 중 설계자가
**배타적 소유**를 위한 `UniquePtr<T>`도 추가로 요청했다 - §2-A에서
다룬다. 문서 제목은 원래 발급받은 그대로 두지만(도구가 제목을
바꿀 수 없음), 이 문서는 이제 `SharedPtr`/`WeakPtr`/`UniquePtr`
세 템플릿을 함께 다룬다.

## 0. `Atomic<T>` - 기반 원자 연산 일반화 (2026-09-16, 설계자 메시지
"AtomicU32 이런 종류도 Atomic<T>로 일반화하는 것을 검토해봐")

위 §1-§2가 쓰는 `AtomicU32`/`AtomicPtr<T>`(둘 다 `libkenv/
spinlock.h`, 실측 확인)는 사실 같은 걸 서로 다른 타입에 대해
각각 손으로 짜 둔 것이다 - 연산 목록도 미묘하게 다르다
(`AtomicPtr<T>`엔 `exchange()`가 있는데 `AtomicU32`엔 없음, 실측
확인). 이 둘을 하나의 `Atomic<T>` 템플릿으로 합친다.

```cpp
// libkenv/spinlock.h 개정 - AtomicU32/AtomicPtr<T>를 Atomic<T>로 통합
namespace kernel {

template <typename T>
class Atomic {
public:
    Atomic() = default;
    explicit Atomic(T initial) : _value(initial) {}

    T load() const {
        return __atomic_load_n(&_value, __ATOMIC_ACQUIRE);
    }
    void store(T value) {
        __atomic_store_n(&_value, value, __ATOMIC_RELEASE);
    }
    // AtomicPtr<T>엔 있었지만 AtomicU32엔 없던 연산 - 통합하면서
    // 둘 다에 제공(빠져 있던 쪽엔 순증 - 기존 호출부는 안 건드림).
    T exchange(T value) {
        return __atomic_exchange_n(&_value, value, __ATOMIC_ACQ_REL);
    }
    // weak CAS(스퓨리어스 실패 가능) - 루프 안에서 재시도하는 용도로만.
    bool compareExchange(T& expected, T desired) {
        return __atomic_compare_exchange_n(&_value, &expected, desired, true, __ATOMIC_ACQ_REL, __ATOMIC_ACQUIRE);
    }

    // 정수 산술/비트 연산 - 정수 타입에서만 실제로 호출한다는 전제
    // (C++ 템플릿은 실제로 호출된 멤버 함수만 인스턴스화하므로,
    // Atomic<T*>에서 이 넷을 안 부르면 컴파일 자체가 안 된다 - 굳이
    // <type_traits>로 컴파일 타임에 막지 않는다, 이 프로젝트가 지금까지
    // 그런 SFINAE류 방어를 쓴 선례가 없고 RM-23F4B687 §4 - 실증된
    // 필요 없이 복잡도를 늘리지 않는다는 원칙과도 맞음. 포인터 타입에
    // 잘못 호출하면 컴파일 에러로 바로 드러나므로 런타임 위험은 없다).
    T fetchAdd(T delta) { return __atomic_fetch_add(&_value, delta, __ATOMIC_ACQ_REL); }
    T fetchSub(T delta) { return __atomic_fetch_sub(&_value, delta, __ATOMIC_ACQ_REL); }
    T fetchOr(T bits) { return __atomic_fetch_or(&_value, bits, __ATOMIC_ACQ_REL); }
    T fetchAnd(T bits) { return __atomic_fetch_and(&_value, bits, __ATOMIC_ACQ_REL); }

private:
    T _value{};
};

// 기존 호출부(scheduler.cpp/async_task.cpp/tlb_shootdown.cpp 등
// 수십 곳)가 전부 `AtomicU32`/`AtomicPtr<T>`라는 이름을 그대로 쓰고
// 있으므로, 타입 별칭으로 남겨 **기존 코드를 단 한 줄도 안 고치고**
// 새 템플릿으로 갈아탄다.
using AtomicU32 = Atomic<uint32_t>;
template <typename T>
using AtomicPtr = Atomic<T*>;

}  // namespace kernel
```

**왜 이렇게 통합하는가**: `SharedPtr`/`WeakPtr`/`UniquePtr`(§0 아래
전부)가 내부적으로 `AtomicPtr<T>`/`AtomicU32`를 쓰는데, 지금처럼
두 개의 별개 클래스로 있으면 앞으로 `Atomic<uint64_t>`나
`Atomic<bool>`류가 필요해질 때마다 또 손으로 짜야 한다 - 하나의
템플릿이면 즉시 재사용된다. **기존 호출부 무변경**이 핵심 제약이다
(타입 별칭으로 보장) - 이 통합 자체는 순수 내부 리팩터라 동작
변화가 없어야 한다(착수 시 기존 `AtomicU32`/`AtomicPtr<T>` 사용처
전부 QEMU 4개 표준 시나리오 무회귀로 확인).

## 1. 기존 패턴 실측(`AsyncTaskWeakRef`) - 이 설계의 출발점

```cpp
// async_task.cpp의 실제 코드(발췌, AsyncTask 전용)
class AsyncTaskWeakRef {
public:
    void init(AsyncTask* target) {
        _target.store(target);
        _refCount.store(2);  // AsyncTask 쪽 몫 1 + 타이머 콜백 쪽 몫 1
    }
    AsyncTask* lock() const { return _target.load(); }
    void invalidate() { _target.store(nullptr); }
    void release() {
        if (_refCount.fetchSub(1) == 1) {
            GenericSlabAllocator::free(this, sizeof(AsyncTaskWeakRef));
        }
    }
private:
    AtomicPtr<AsyncTask> _target;
    AtomicU32 _refCount;
};
```

핵심 통찰(기존 헤더 주석이 이미 정리해 둔 것, 이 문서가 그대로
계승): **대상(`T`)의 수명과 컨트롤 블록 자체의 수명을 분리**한다 -
대상이 죽어도(`invalidate()`) 컨트롤 블록은 아직 참여자가 남아 있으면
살아있고, 컨트롤 블록의 참조 카운트가 0이 될 때만 블록 자신이
반납된다. 두 원자 변수(`AtomicPtr<T>`/`AtomicU32`, 둘 다 이미
`libkenv/spinlock.h`에 존재) 만으로 락 없이 두 가지 질문("대상이
아직 살아있는가", "이 블록을 아직 누가 쓰고 있는가")에 안전하게
답한다 - 협조적 스케줄링(리액터 idle 경로/타이머 콜백이 서로 겹치지
않음, 인터럽트 컨텍스트 제외)이 이 안전성의 전제라는 점도 그대로
계승한다(§5).

## 2. 일반화 - `ControlBlock<T>` + `SharedPtr<T>`/`WeakPtr<T>`

`AsyncTaskWeakRef`는 "강한 참조"(대상을 살려 두는 쪽) 개념이 없다 -
AsyncTask 자신의 수명은 리액터가 별도로 관리하고, weakRef는 오직
"이미 죽었는지 아닌지 안전하게 물어보는" 용도였다. 범용 템플릿은
표준 `shared_ptr`/`weak_ptr` 관례대로 **강한 참조(`SharedPtr<T>`,
대상을 살아있게 유지)**와 **약한 참조(`WeakPtr<T>`, 대상 수명에
영향 없음)**를 함께 지원한다 - `strongCount`가 0이 되면 대상이
파괴되고, `weakCount`(강한 참조가 하나라도 있으면 암묵적으로 +1,
표준 `shared_ptr`와 동일 관례)가 0이 되면 컨트롤 블록 자신이
반납된다.

**[재설계, 2026-09-16, 설계자 Opinion "SharedPtr에도 커스텀
삭제자(deleter)의 템플릿 파라미터화도 설계해서 반영해"]** 직전
리비전은 삭제자를 `ControlBlock<T>`의 **런타임 필드**로만 뒀다
(표준 `shared_ptr`와 동일한 타입 소거 지점, `SharedPtr<T>`가 항상
같은 타입이라는 장점) - 그런데 설계자가 `UniquePtr<T>`처럼
`SharedPtr<T>` 자신도 `Deleter`를 **템플릿 파라미터**로 받도록
다시 요청했다. 아래는 그 요청대로 `ControlBlock`/`SharedPtr`/
`WeakPtr`/`kMakeShared`를 전부 `Deleter`로 파라미터화한 버전이다.
**알려진 트레이드오프(문서화된 제약, §2 끝의 "알려진 제약" 참고)**:
`SharedPtr<T, DeleterA>`와 `SharedPtr<T, DeleterB>`는 이제 서로
다른 타입이라 같은 컨테이너에 섞을 수 없고, `EnableSharedFromThis`
는 기본 삭제자 경로만 지원한다.

**[재설계 2차, 2026-09-16, QU-4E449C65 답변("(B) SharedPtr 별칭
생성자 추가")]** 아래는 별칭(aliasing) 생성자를 지원하도록 컨트롤
블록의 참조-카운팅 부분을 **타입 소거**한 버전이다(표준
`std::shared_ptr`의 실제 내부 구조와 동일한 접근 - 컨트롤 블록은
카운트만 알고, "이 핸들이 실제로 무엇을 가리키는지"는 `SharedPtr`/
`WeakPtr` 인스턴스 자신이 별도 필드로 들고 있다). 이 변경의 이유:
`Task::blockedOn` 같은 관찰자가 `WeakPtr<Waitable>`이 되려면, 실제
`Waitable` 구현체(`WaitQueue`)가 `Mutex`/`Semaphore`에 **임베디드**
멤버로 있어도(별도 `kMakeShared`할당 없이) 그 컨테이너의 컨트롤
블록을 공유하는 `WeakPtr`을 만들 수 있어야 한다 - 지금까지처럼
`ControlBlock<T,Deleter>`가 정확히 `T`한 가지 타입만 가리킬 수
있으면 이게 불가능하다(컨테이너는 `Mutex`, 별칭 대상은 `Waitable`로
서로 다른 타입).

**바뀌는 것(기존 대비 diff 요약)**:
- 참조 카운팅(`_strongCount`/`_weakCount`/`tryAddStrongRef`/
  `addStrongRefUnchecked`/`addWeakRef`)이 새 비템플릿 기반 클래스
  `ControlBlockBase`로 옮겨간다 - 더 이상 `T`를 몰라도 된다.
  `releaseStrong()`/`releaseWeak()`이 실제 소멸/반납을 수행할 때는
  `init()` 시점에 저장해 둔 **함수 포인터 트램폴린**(`_destroyOwned`/
  `_freeSelf`)을 통해 원래 타입으로 돌아간다(가상 함수 대신 - 이
  프로젝트가 `Deleter`에도 이미 쓰는 것과 같은 함수 포인터 타입
  소거 패턴, vtable 오버헤드 없음).
- `ControlBlock<T, Deleter>`는 `ControlBlockBase`를 상속하고,
  원래 소유 객체를 가리키는 `_target`/`_deleter`만 그대로 갖는다
  (소멸 시 무엇을 해제할지는 컨트롤 블록이 계속 안다 - 별칭은 "누가
  가리키는지"만 분리할 뿐 "누가 해제되는지"는 그대로 원래 소유
  객체다).
- `SharedPtr<T, Deleter>`/`WeakPtr<T, Deleter>`는 이제 **포인터
  2개**를 든다 - `ControlBlockBase* _block`(타입 소거된 컨트롤
  블록) + `T* _ptr`(이 핸들이 실제로 가리키는 대상, 별칭이면 컨트롤
  블록의 원래 타입과 다를 수 있음). `get()`은 이제 `_block->target()`
  간접 호출 없이 `_ptr`을 바로 반환한다(오히려 한 단계 빨라짐).
  **트레이드오프**: `SharedPtr`/`WeakPtr` 인스턴스 크기가 포인터
  1개(8바이트)에서 2개(16바이트, x86_64 기준)로 늘어난다.
- 새 별칭 생성자: `template <typename U, typename UDeleter>
  SharedPtr(const SharedPtr<U, UDeleter>& owner, T* aliasedPtr)`와
  `WeakPtr`의 동일한 짝 - `owner`의 컨트롤 블록을 공유(참조 카운트
  +1)하면서 `aliasedPtr`을 가리키는 새 핸들을 만든다. `owner`가
  살아있는 한(강한 참조를 하나 더 쥐고 있으므로) `aliasedPtr`도
  안전 - 이게 바로 "컨테이너가 살아있는 동안 그 멤버도 안전히
  관찰 가능"이라는, 이번 확장이 필요했던 이유 그 자체다.

```cpp
// minicore/libs/libkenv/shared_ptr.h (신규)
namespace kernel {

// 기본 삭제자 - GenericSlabAllocator로 만든 T를 반납한다(지금까지
// 모든 예시가 암묵적으로 전제해 온 경로).
template <typename T>
void kDestroyAndFree(T* ptr);  // T의 정리 로직(명시적 정리 메서드 호출 - 이 프로젝트는 소멸자 대신 이 관례를 씀) + GenericSlabAllocator::free

// [신규] 참조 카운팅만 아는 타입 소거된 기반 클래스 - `T`를 몰라도
// 카운트 증감/CAS 루프는 그대로 할 수 있다. 실제 소멸/반납은 파생
// 클래스가 init()에서 심어 둔 함수 포인터 트램폴린을 통해서만 한다
// (가상 함수 대신 - Deleter와 같은 함수 포인터 타입 소거 패턴).
class ControlBlockBase {
public:
    bool tryAddStrongRef() {
        uint32_t cur = _strongCount.load();
        while (cur != 0) {
            if (_strongCount.compareExchange(cur, cur + 1)) {
                return true;
            }
        }
        return false;  // 이미 0 - 대상이 파괴됨, 되살릴 수 없음
    }
    void addStrongRefUnchecked() { _strongCount.fetchAdd(1); }
    void addWeakRef() { _weakCount.fetchAdd(1); }

    void releaseStrong() {
        if (_strongCount.fetchSub(1) == 1) {
            _destroyOwned(this);  // 원래 소유 객체 소멸(파생 타입이 세팅한 트램폴린)
            releaseWeak();        // 강한 참조 전부 사라짐 - 암묵적 weak 1개도 해제
        }
    }
    void releaseWeak() {
        if (_weakCount.fetchSub(1) == 1) {
            _freeSelf(this);  // 컨트롤 블록 자신의 메모리 반납(파생 타입의 실제 크기를 아는 트램폴린)
        }
    }

protected:
    AtomicU32 _strongCount;
    AtomicU32 _weakCount;
    void (*_destroyOwned)(ControlBlockBase*) = nullptr;  // init()이 채움
    void (*_freeSelf)(ControlBlockBase*) = nullptr;      // init()이 채움
};

// `Deleter`를 템플릿 파라미터로 받는다(`UniquePtr<T, Deleter>`와
// 동일한 방식 - §2-A) - 함수 포인터 기본값을 쓰면 기존 호출부는
// 아무것도 안 바뀌고, 상태 없는 함수 객체(캡처 없는 람다 등)를
// 넘기면 그 타입 자체가 `_deleter` 필드 크기가 되어(대개 0바이트)
// 제로 오버헤드다. std::function류 타입 소거는 여전히 안 쓴다(힙
// 할당 요구, freestanding 환경에 새로 들이지 않음, RM-23F4B687 §4).
template <typename T, typename Deleter = void (*)(T*)>
class ControlBlock : public ControlBlockBase {
public:
    // AsyncTaskWeakRef::init()과 동일한 관례 - GenericSlabAllocator가
    // 준 raw 메모리 위에 앉힌 뒤 명시적으로 초기화(placement new 안 씀).
    void init(T* target, Deleter deleter = &kDestroyAndFree<T>) {
        _target.store(target);
        _strongCount.store(1);  // 최초 SharedPtr 생성자 몫
        _weakCount.store(1);    // 강한 참조가 하나라도 있는 동안의 암묵적 몫(표준 shared_ptr 관례)
        _deleter = deleter;
        _destroyOwned = &kDestroyOwnedTrampoline;
        _freeSelf = &kFreeSelfTrampoline;
    }

    // kMakeShared가 초기 SharedPtr::_ptr 값을 얻는 데만 쓴다 - 별칭
    // 생성자가 만든 SharedPtr은 이 값을 안 거치고 자기 _ptr을 직접 든다.
    T* target() const { return _target.load(); }

private:
    static void kDestroyOwnedTrampoline(ControlBlockBase* base) {
        auto* self = static_cast<ControlBlock<T, Deleter>*>(base);
        T* t = self->_target.load();
        if (t) {
            self->_deleter(t);
        }
        self->_target.store(nullptr);
    }
    static void kFreeSelfTrampoline(ControlBlockBase* base) {
        GenericSlabAllocator::free(base, sizeof(ControlBlock<T, Deleter>));
    }

    AtomicPtr<T> _target;
    Deleter _deleter = &kDestroyAndFree<T>;  // init()이 실제 값으로 덮어씀
};

template <typename T, typename Deleter>
class WeakPtr;

// RAII 강한 참조 - 대상을 살아있게 유지한다. `Deleter`는 기본값을
// 쓰면 기존 코드와 동일하게 `SharedPtr<T>`로만 써도 된다(템플릿
// 기본 인자라 명시할 필요 없음) - 커스텀 삭제자를 쓸 때만
// `SharedPtr<T, MyDeleter>`로 명시.
template <typename T, typename Deleter = void (*)(T*)>
class SharedPtr {
public:
    SharedPtr() = default;
    ~SharedPtr() { reset(); }

    SharedPtr(const SharedPtr& other) : _block(other._block), _ptr(other._ptr) {
        if (_block) _block->addStrongRefUnchecked();  // 이미 살아있는 SharedPtr에서 복사 - tryAddStrongRef의 CAS 불필요, 단순 fetchAdd로 충분(호출자가 이미 강한 참조 1개를 쥐고 있으므로 0에서 시작할 수 없음)
    }
    SharedPtr(SharedPtr&& other) noexcept : _block(other._block), _ptr(other._ptr) {
        other._block = nullptr;
        other._ptr = nullptr;
    }

    SharedPtr& operator=(const SharedPtr& other) {
        if (this != &other) {
            reset();
            _block = other._block;
            _ptr = other._ptr;
            if (_block) _block->addStrongRefUnchecked();
        }
        return *this;
    }
    SharedPtr& operator=(SharedPtr&& other) noexcept {
        if (this != &other) {
            reset();
            _block = other._block;
            _ptr = other._ptr;
            other._block = nullptr;
            other._ptr = nullptr;
        }
        return *this;
    }

    // [신규, 2026-09-16, QU-4E449C65 답변] 별칭(aliasing) 생성자 -
    // owner의 컨트롤 블록을 공유(강한 참조 +1)하면서, 그 컨트롤
    // 블록이 실제로 소유한 타입(U)과 무관한 대상(T*, 대개 U의 멤버
    // 하나)을 가리키는 SharedPtr을 만든다. owner가 살아있는 동안은
    // aliasedPtr도 안전하다(표준 std::shared_ptr 별칭 생성자와 동일한
    // 계약).
    template <typename U, typename UDeleter>
    SharedPtr(const SharedPtr<U, UDeleter>& owner, T* aliasedPtr) : _block(owner._block), _ptr(aliasedPtr) {
        if (_block) _block->addStrongRefUnchecked();
    }

    T* get() const { return _ptr; }
    T* operator->() const { return _ptr; }
    T& operator*() const { return *_ptr; }
    explicit operator bool() const { return _ptr != nullptr; }

    void reset() {
        if (_block) {
            _block->releaseStrong();  // 컨트롤 블록이 자기 몫 삭제자를 이미 알고 있다
            _block = nullptr;
        }
        _ptr = nullptr;
    }

private:
    // [신규] 별칭 생성자가 다른 SharedPtr<U,D>/WeakPtr<U,D>의 _block을
    // 읽을 수 있도록 - 타입이 다르면 서로 private 멤버에 접근 못 하는
    // C++ 기본 규칙을 이 템플릿 friend로 풀어 준다(표준 shared_ptr
    // 구현체들도 동일하게 이 패턴을 쓴다).
    template <typename U, typename D>
    friend class SharedPtr;
    template <typename U, typename D>
    friend class WeakPtr;
    // [버그 수정, 2026-09-16, PN-68871BC9 착수 2번째 증분 실측 컴파일 중
    // 발견] 이 friend 선언이 원안에 빠져 있었다 - kMakeShared가 이 아래
    // private 생성자를 직접 부르는데, EnableSharedFromThis<T> 쪽엔 같은
    // friend 선언이 있었으면서 SharedPtr 자신엔 없어 실제로 컴파일해
    // 보기 전까지 안 드러났다("private 생성자 호출" 컴파일 에러).
    template <typename U, typename D>
    friend SharedPtr<U, D> kMakeShared(U*, D);
    explicit SharedPtr(ControlBlockBase* block, T* ptr) : _block(block), _ptr(ptr) {}
    ControlBlockBase* _block = nullptr;
    T* _ptr = nullptr;  // [신규] 이 핸들이 실제로 가리키는 대상 - 별칭 지원을 위해 컨트롤 블록에서 분리
};

// 약한 참조 - AsyncTaskWeakRef와 동일한 역할이지만 임의 T에 대해.
// `SharedPtr<T, Deleter>`와 같은 `Deleter`로 맞춰야 같은 ControlBlock
// 을 가리킬 수 있다(lock()이 그 타입의 SharedPtr을 반환).
template <typename T, typename Deleter = void (*)(T*)>
class WeakPtr {
public:
    WeakPtr() = default;
    explicit WeakPtr(const SharedPtr<T, Deleter>& shared) : _block(shared._block), _ptr(shared._ptr) {
        if (_block) _block->addWeakRef();
    }
    ~WeakPtr() { if (_block) _block->releaseWeak(); }

    // [수정, 2026-09-16, `EnableSharedFromThis`용 `_weakThis = WeakPtr<T>
    // (result)` 대입 검토 중 발견] 복사/이동 생성자·대입 연산자가
    // 빠져 있었다 - 이대로면 컴파일러가 만든 기본 복사(얕은 포인터
    // 복사, `_weakCount` 조정 없음)가 쓰여 이중 해제/카운트 불일치로
    // 이어진다. `SharedPtr`와 동일한 패턴으로 채운다.
    WeakPtr(const WeakPtr& other) : _block(other._block), _ptr(other._ptr) {
        if (_block) _block->addWeakRef();
    }
    WeakPtr(WeakPtr&& other) noexcept : _block(other._block), _ptr(other._ptr) {
        other._block = nullptr;
        other._ptr = nullptr;
    }
    WeakPtr& operator=(const WeakPtr& other) {
        if (this != &other) {
            if (_block) _block->releaseWeak();
            _block = other._block;
            _ptr = other._ptr;
            if (_block) _block->addWeakRef();
        }
        return *this;
    }
    WeakPtr& operator=(WeakPtr&& other) noexcept {
        if (this != &other) {
            if (_block) _block->releaseWeak();
            _block = other._block;
            _ptr = other._ptr;
            other._block = nullptr;
            other._ptr = nullptr;
        }
        return *this;
    }

    // [신규, 2026-09-16, QU-4E449C65 답변] SharedPtr과 동일한 별칭
    // 생성자 - weak 쪽. Task::blockedOn처럼 "컨테이너가 살아있는 동안만
    // 그 임베디드 멤버를 관찰"하려는 용도가 바로 이 생성자를 쓴다.
    template <typename U, typename UDeleter>
    WeakPtr(const SharedPtr<U, UDeleter>& owner, T* aliasedPtr) : _block(owner._block), _ptr(aliasedPtr) {
        if (_block) _block->addWeakRef();
    }

    // AsyncTaskWeakRef::lock()과 동일한 역할이지만, "대상을 살려
    // 두는" SharedPtr을 반환한다(표준 weak_ptr::lock() 관례) - 대상이
    // 이미 파괴됐으면(strongCount==0) 빈 SharedPtr.
    SharedPtr<T, Deleter> lock() const {
        if (_block && _block->tryAddStrongRef()) {
            return SharedPtr<T, Deleter>(_block, _ptr);
        }
        return SharedPtr<T, Deleter>();
    }

private:
    template <typename U, typename D>
    friend class SharedPtr;
    template <typename U, typename D>
    friend class WeakPtr;
    ControlBlockBase* _block = nullptr;
    T* _ptr = nullptr;
};

// [신규, 2026-09-16, 설계자 지시("EnableFromSharedThis를 포함해서
// 착수해")] 표준 enable_shared_from_this와 같은 역할 - 어떤 타입 T가
// 이걸 상속해 두면, T의 멤버 함수 안에서(즉 이미 존재하는 T* this는
// 있지만 그걸 감싼 SharedPtr<T>는 손에 없는 상황 - 예: 콜백에 "나
// 자신"을 SharedPtr로 넘겨줘야 할 때) 새 컨트롤 블록을 만들지 않고
// **원래 그 객체를 소유하고 있던 바로 그 컨트롤 블록**을 가리키는
// SharedPtr<T>를 안전하게 재구성할 수 있다.
//
// **알려진 제약(2026-09-16, Deleter 템플릿 파라미터화의 부작용)**:
// `_weakThis`는 **기본 삭제자**(`WeakPtr<T>` = `WeakPtr<T, void(*)
// (T*)>`) 타입으로 고정돼 있다 - `kMakeShared<T>`를 커스텀 삭제자
// 없이 부른 경우에만 채워진다. `T`가 `EnableSharedFromThis<T>`를
// 상속하면서 동시에 커스텀 삭제자로 `kMakeShared<T>(ptr, myDeleter)`
// 를 부르면, 아래 `kMakeShared`의 `_weakThis = WeakPtr<T>(result)`
// 대입에서 `result`(타입 `SharedPtr<T, MyDeleter>`)가 `WeakPtr<T>`
// 생성자가 요구하는 `SharedPtr<T, void(*)(T*)>`와 타입이 안 맞아
// **컴파일 에러**가 난다 - 지금 이 프로젝트에 그런 조합(둘 다 필요한
// 실사용처)이 없으므로 RM-23F4B687 §4 원칙대로 지금은 그냥 이
// 제약을 문서화만 해 둔다(실제로 필요해지면 그때 `EnableSharedFromThis
// <T, Deleter>`로 확장 검토). **커스텀 삭제자가 필요한 타입에는
// `EnableSharedFromThis`를 쓰지 않는다.**
template <typename T>
class EnableSharedFromThis {
protected:
    // 이미 SharedPtr로 관리되는 객체 안에서만 안전하다 - kMakeShared로
    // 만들어지지 않은 T(스택/정적 변수 등)에서 부르면 _weakThis가
    // 비어 있어 빈 SharedPtr을 반환한다(전통적 enable_shared_from_this
    // 처럼 여기서 강제로 막지 않는다 - 예외를 못 쓰는 이 프로젝트
    // 관례상 "실패를 나타내는 빈 값 반환"이 일관된 선택).
    SharedPtr<T> sharedFromThis() { return _weakThis.lock(); }

private:
    template <typename U, typename D>
    friend SharedPtr<U, D> kMakeShared(U*, D);  // kMakeShared가 생성 직후 _weakThis를 채워준다(기본 인자는 정의부에만 - 선언에서 중복 지정 안 함, C++ 규칙).
    // _weakThis는 항상 기본 삭제자(void(*)(T*)) 타입으로 고정 - 바로
    // 아래 kMakeShared<T, Deleter>()가 D가 기본 삭제자가 아닐 때 이
    // 필드에 대입을 시도하면 타입 불일치로 컴파일 에러가 난다(의도된
    // 동작 - 위 "알려진 제약" 참고).
    WeakPtr<T> _weakThis;
};

// GenericSlabAllocator로 대상 T와 ControlBlock<T, Deleter>를 각각
// 따로 할당(AsyncTaskWeakRef와 동일하게 raw slab 메모리 위에 앉힘,
// placement new 없이 명시적 초기화 - T의 생성자를 어떻게 호출할지는
// T가 이미 이 프로젝트 관례대로 init()류 명시적 초기화 메서드를
// 갖는다는 전제. 인자 전달형 kMakeShared(Args&&...)는 T가 진짜
// 생성자를 쓰는 경우를 위한 옵션 - 착수 시 이 프로젝트에서 실제로
// 어느 쪽이 필요한지 첫 소비자 기준으로 확정).
// `Deleter`는 템플릿 파라미터라 `deleter` 인자의 타입에서 컴파일러가
// 추론한다(생략하면 기본값 `&kDestroyAndFree<T>`, 타입은
// `void(*)(T*)`로 추론) - 반환 타입이 `SharedPtr<T, Deleter>`이므로
// 커스텀 삭제자를 넘기면 호출부가 받는 타입도 자동으로 그에 맞춰진다.
template <typename T, typename Deleter = void (*)(T*)>
SharedPtr<T, Deleter> kMakeShared(T* preConstructed, Deleter deleter = &kDestroyAndFree<T>) {
    void* mem = GenericSlabAllocator::alloc(sizeof(ControlBlock<T, Deleter>));
    if (!mem) return SharedPtr<T, Deleter>();  // 할당 실패 - 빈 SharedPtr(예외 없음, 이 프로젝트 관례)
    auto* block = reinterpret_cast<ControlBlock<T, Deleter>*>(mem);
    block->init(preConstructed, deleter);
    // [버그 수정, 2026-09-16, PN-5FC484DF 실측 컴파일 중 발견] 이 줄은
    // 재설계(§2 "2차 재설계" 절) 이전 원안 `SharedPtr<T, Deleter>
    // result(block);`(1개 인자)를 그대로 남긴 오탈자였다 - 재설계로
    // SharedPtr의 private 생성자가 `(ControlBlockBase*, T*)` 2개
    // 인자로 바뀌었는데 이 호출부만 갱신이 안 됐다(문서 자체가 리팩터
    // 도중 스스로 낸 불일치 - 실제 컴파일 전까지는 안 드러남,
    // PN-68871BC9 2번째 증분의 friend 선언 누락과 같은 종류의 발견).
    SharedPtr<T, Deleter> result(block, preConstructed);
    // T가 EnableSharedFromThis<T>를 상속하면 _weakThis를 채운다 -
    // if constexpr로 컴파일 타임 분기(런타임 비용 0, T가 상속 안
    // 했으면 이 분기 자체가 인스턴스화되지 않는다). RTTI(dynamic_cast)
    // 없이 이 판정을 하려면 <type_traits>의 is_base_of가 사실상
    // 유일한 방법이다 - §0이 SFINAE류 방어적 사용은 피했지만, 이건
    // 방어가 아니라 핵심 기능이라 예외로 둔다. (기본 삭제자가 아닌
    // 경우 여기서 컴파일 에러가 날 수 있음 - 위 "알려진 제약" 참고.)
    if constexpr (std::is_base_of_v<EnableSharedFromThis<T>, T>) {
        preConstructed->_weakThis = WeakPtr<T>(result);
    }
    return result;
}

}  // namespace kernel
```

**[정정, 2026-09-16, PN-68871BC9 착수 2번째 증분 실측 컴파일 중 발견]**
위 `std::is_base_of_v` 사용은 이 프로젝트의 베어메탈 타겟
(`x86_64-unknown-none-elf`)에서 그대로 컴파일되지 않는다 -
`<type_traits>` 자체가 이 타겟에 없다(실측 확인: `clang++`로
`#include <type_traits>`만 컴파일 시도해도 "file not found") -
`libkenv/coroutine.h`가 `<coroutine>`에 대해 이미 남겨 둔 것과 정확히
같은 제약인데, 이 문서를 쓸 당시엔 검증하지 않고 표준 라이브러리가
쓸 수 있다고 가정했다. 실제 구현(`minicore/libs/libkenv/shared_ptr.h`)
은 `std::is_base_of_v<Base, Derived>` 대신 자체 구현한
`kIsBaseOf<Base, Derived>`(클래스 템플릿 정적 멤버 함수 오버로드 쌍 +
"B*→A* 변환이 B*→void* 변환보다 우선"이라는 표준의 오버로드 해석
tie-break 규칙을 이용한 C++11 이전부터 쓰인 표준 관용구)를 쓴다 -
의미상 완전히 동일하고 실측으로 정상 동작 확인(관계도 기록 참고).
앞으로 이 프로젝트에서 `<type_traits>`(또는 표준 라이브러리 헤더
일반)가 필요해 보이는 설계를 쓸 때는 착수 전에 반드시 실제로
`#include` 가능한지 먼저 확인할 것 - "표준 헤더니까 당연히 될 것"이라는
가정은 이 타겟에서 최소 두 번(`<coroutine>`, `<type_traits>`) 틀렸다.

```cpp
// minicore/libs/libkenv/type_traits.h (신규) - std:: 이름 그대로 써서
// 표준 관용구를 아는 사람이 그대로 읽을 수 있게 한다(단, 전부 이
// 프로젝트가 직접 구현 - <type_traits> include 없음).
namespace kernel {

// std::integral_constant/true_type/false_type과 동일한 최소 골격 -
// is_same/is_base_of 둘 다 이 위에 짓는다(나머지 표준 trait이 필요해지면
// 이미 이 기반 위에 자연스럽게 추가된다).
template <typename T, T Value>
struct IntegralConstant {
    static constexpr T value = Value;
    using ValueType = T;
    constexpr operator T() const { return value; }
};
using TrueType = IntegralConstant<bool, true>;
using FalseType = IntegralConstant<bool, false>;

template <typename A, typename B>
struct IsSame : FalseType {};
template <typename A>
struct IsSame<A, A> : TrueType {};
template <typename A, typename B>
inline constexpr bool kIsSame = IsSame<A, B>::value;

// SP-201238BB §2의 kIsBaseOf를 그대로 여기로 옮긴 것 - 클래스 템플릿
// 정적 멤버 함수 오버로드 쌍 + "B*→A*가 B*→void*보다 우선"이라는
// 표준 오버로드 해석 tie-break 규칙을 쓰는 C++11 이전부터 쓰인 관용구.
template <typename Base, typename Derived>
class IsBaseOf {
    static TrueType test(Base*);
    static FalseType test(void*);
public:
    static constexpr bool value = decltype(test(static_cast<Derived*>(nullptr)))::value;
};
template <typename Base, typename Derived>
inline constexpr bool kIsBaseOf = IsBaseOf<Base, Derived>::value;

}  // namespace kernel
```

`shared_ptr.h`는 자체 `kIsBaseOf`를 지우고 이 헤더의 `kernel::
kIsBaseOf`를 그대로 쓴다(동작 동일, 코드 중복만 제거). 이후 다른
설계가 `is_same`/`is_base_of` 외의 trait이 실제로 필요해지면 그때
이 헤더에 같은 패턴으로 추가한다 - 지금 미리 채워 넣지 않는다.

## 2-A. `UniquePtr<T>` - 배타적 소유 (2026-09-16, 설계자 지시("UniquePtr
같은 것들도 추가 설계") 반영)

`SharedPtr`/`WeakPtr`는 "런타임에 누가 마지막까지 살아남을지 정해지는"
**공유** 소유권 문제를 푸는 도구다 - DC-21647E46 조사에서 확인했듯,
이 코드베이스의 소유권 있는 포인터 중 상당수는 그런 문제가 아예
없다(`RingBuffer::data`, `Channel::pendingHead/pendingTail`처럼
**정확히 하나의 소유자가 명확히 정해져 있고**, 그 소유자가 없어질 때
같이 정리되면 끝나는 경우). 이런 **배타적 소유**에는 원자 연산도
컨트롤 블록도 필요 없다 - `UniquePtr<T>`는 소유권 이전(move)만
지원하고 복사는 금지해, 런타임 비용이 raw 포인터와 사실상 동일한
("zero-cost") RAII 래퍼다:

```cpp
// minicore/libs/libkenv/unique_ptr.h (신규, 또는 shared_ptr.h에 같이)
namespace kernel {

// (`kDestroyAndFree<T>`는 §2에서 이미 선언 - 여기서 다시 선언하지
// 않는다, 같은 헬퍼를 공유)

// [신규, 2026-09-16, 설계자 지시("커스텀 삭제자의 템플릿 파라미터화도
// 설계해서 반영")] `Deleter`를 **템플릿 파라미터**로 둔다(`SharedPtr`
// 와 다른 선택 - 표준 `unique_ptr<T, Deleter>`와 동일한 이유: 컨트롤
// 블록이 없어 타입 소거로 숨길 자리가 없고, 소유자가 정확히 하나뿐인
// 배타적 소유는 애초에 "다른 삭제자로 만들어진 UniquePtr과 같은
// 타입이어야 할" 이유도 없다 - 오히려 삭제자가 다르면 컴파일 타임에
// 다른 타입으로 구분되는 쪽이 실수를 더 잘 막는다).
template <typename T, typename Deleter = void (*)(T*)>
class UniquePtr {
public:
    UniquePtr() = default;
    explicit UniquePtr(T* ptr, Deleter deleter = &kDestroyAndFree<T>) : _ptr(ptr), _deleter(deleter) {}
    ~UniquePtr() { reset(); }

    // 배타적 소유 - 복사 금지(공유 소유권으로 새는 걸 컴파일 타임에 차단).
    UniquePtr(const UniquePtr&) = delete;
    UniquePtr& operator=(const UniquePtr&) = delete;

    // 이동만 허용 - 소유권이 한 곳에서 다른 곳으로 옮겨갈 뿐, 원자
    // 연산이 전혀 필요 없다(같은 순간 소유자가 정확히 하나뿐이므로
    // 경합 자체가 성립하지 않는다). 삭제자도 함께 옮긴다.
    UniquePtr(UniquePtr&& other) noexcept : _ptr(other._ptr), _deleter(other._deleter) { other._ptr = nullptr; }
    UniquePtr& operator=(UniquePtr&& other) noexcept {
        if (this != &other) {
            reset();
            _ptr = other._ptr;
            _deleter = other._deleter;
            other._ptr = nullptr;
        }
        return *this;
    }

    T* get() const { return _ptr; }
    T* operator->() const { return _ptr; }
    T& operator*() const { return *_ptr; }
    explicit operator bool() const { return _ptr != nullptr; }

    // 소유권을 포기하고 raw 포인터로 반환 - 이후 정리 책임은 호출자.
    T* release() {
        T* p = _ptr;
        _ptr = nullptr;
        return p;
    }

    void reset(T* newPtr = nullptr) {
        if (_ptr) {
            _deleter(_ptr);
        }
        _ptr = newPtr;
    }

private:
    T* _ptr = nullptr;
    // [버그 수정, 2026-09-17, PN-21C2D4E9 실측 사용 중 발견] 원래
    // `= &kDestroyAndFree<T>`였다 - 이 NSDMI는 기본 템플릿 인자
    // (`Deleter = void (*)(T*)`)를 그대로 쓰는 경우에만 유효한 값이라,
    // 위에서 이미 약속한 "상태 있는 함수 객체도 Deleter로 가능"(§2-A
    // 원문)을 실제 채택하면(예: RingBufferDeleter처럼 함수 포인터로
    // 변환 불가능한 구조체) 이 대입식 자체가 컴파일 에러가 났다 -
    // 실제 그런 타입을 처음 써 보기 전까지는 안 드러나는 종류의
    // 결함이었다. 값 초기화(`{}`)로 교체 - 함수 포인터 Deleter는
    // 여전히 nullptr로, 상태 있는 구조체 Deleter는 그 타입의 기본
    // 생성자로 초기화된다. 살아있는 포인터가 있는 인스턴스는 항상
    // 명시적 생성자/`initRaw()`가 `_deleter`도 함께 세팅하므로 동작
    // 변화 없음.
    Deleter _deleter{};

public:
    // [신규, 2026-09-17, PN-21C2D4E9 실측 중 발견] raw 슬랩 메모리
    // 위에 reinterpret_cast로 앉혀진 뒤 실제 생성자를 거치지 않은
    // 인스턴스(예: RingBuffer가 BridgePipe 슬랩 메모리 위에 놓이는
    // channel.h의 기존 관례) 전용 - `operator=`/`reset()`과 달리
    // **기존 `_ptr`을 절대 읽거나 해제하지 않는다**. 이 인스턴스가
    // 정말 raw 메모리에서 막 나왔다는 걸 호출부가 보장할 때만
    // 안전하다(진짜 살아있는 소유권을 덮어쓰면 그 옛 대상이 그대로
    // 샌다) - ChunkedList::ensureAllocator/AsyncTask::init()과 같은
    // "raw 메모리 재확립" 관례의 UniquePtr 버전.
    void initRaw(T* ptr, Deleter deleter) {
        _ptr = ptr;
        _deleter = deleter;
    }

    // [신규, 2026-09-17, PN-21C2D4E9] 버퍼(예: RingBuffer::data)를
    // 가리키는 UniquePtr<uint8_t>류 용도 - std::unique_ptr<T[]>처럼
    // 별도 배열 특수화를 두지 않고, 이 하나의 템플릿에 첨자 접근만
    // 더했다(포인터처럼 쓰는 기존 관례의 자연스러운 확장).
    T& operator[](uint64_t index) const { return _ptr[index]; }
};

template <typename T>
UniquePtr<T> kMakeUnique(T* preConstructed) {
    return UniquePtr<T>(preConstructed);
}

}  // namespace kernel
```

**"lock-free"가 애초에 해당 없는 이유**: 배타적 소유는 정의상 동시에
두 곳에서 같은 포인터의 소유권 상태를 바꿀 수 없다(소유자가 항상
정확히 하나) - `SharedPtr`/`WeakPtr`처럼 "여럿이 동시에 참조 카운트를
건드릴 수 있어 원자 연산이 필요한" 문제 자체가 성립하지 않는다.
설계자 지시의 "lock-free 기반"은 `SharedPtr`/`WeakPtr`(진짜 다자간
경합이 있는 대상)에 대한 요구였고, `UniquePtr`는 그 요구가 애초에
적용되지 않는 별개 범주로 이해했다 - 이 해석이 다르면 정정 바란다.

## 2-B. `IntrusiveControlBlock<T>` - 침습적(intrusive) 변형 (2026-09-16, 설계자 지시 "ControlBlock<T>의 Intrusive 버전도 고안해봐")

§2의 `ControlBlock<T, Deleter>`는 대상 `T`와 **별도로** 힙(Slab)에
할당된다 - `kMakeShared<T>()`가 `T`용 메모리 1번, `ControlBlock`용
메모리 1번, 총 2번 할당한다. **침습적(intrusive) 버전은 카운트를
`T` 자신의 메모리 안에 내장**시켜 이 2번째 할당을 없앤다 - 대신
`T`가 특정 기반 클래스를 상속해야 한다("침습적"이라는 이름의 유래 -
`T`의 정의 자체를 건드려야 함). Linux 커널의 `struct kref`, boost의
`intrusive_ptr`와 같은 계열의 절충이다: 할당 1회 감소 + 포인터
역참조 한 단계 감소(캐시 지역성 개선) 대신, `T`가 이 기반 클래스에
묶이고(비침습 버전처럼 "기존 아무 타입에나 나중에 붙이기"가 안 됨)
아래처럼 소멸 규약이 더 엄격해진다.

**핵심 위험 - 왜 비침습 버전처럼 단순히 "카운트 필드를 T 안으로
옮기기"만 하면 안 되는가**: §2의 `ControlBlock`이 `T`와 별도
할당인 덕분에, `strongCount`가 0이 돼 `T`가 파괴된 뒤에도
`WeakPtr::lock()`이 `weakCount`를 안전하게 건드릴 수 있다(그
메모리가 아직 살아있으므로). 카운트가 `T` 내부에 있으면, `T`를
파괴하면서 그 메모리까지 즉시 반납해버리면 그 시점 이후
`WeakPtr::lock()`이 이미 해제된 메모리의 카운트 필드를 건드리는
use-after-free가 된다. **따라서 침습적 버전은 "논리적 소멸"(T의
내용물 정리)과 "메모리 반납"(GenericSlabAllocator::free)을 반드시
분리해야 한다** - `strongCount`가 0이 되면 논리적 소멸만 하고,
`weakCount`(비침습 버전과 동일하게 강한 참조가 있는 동안 암묵적
+1)가 0이 될 때 비로소 메모리를 반납한다. 카운트 필드 자신은 그
사이에도 계속 유효해야 하므로, "논리적 소멸"을 수행하는 삭제자는
**절대로 자기 자신의 메모리를 반납해서는 안 된다**(이 제약이 §2의
`kDestroyAndFree<T>`와 침습 버전 기본 삭제자가 다른 이유).

```cpp
// minicore/libs/libkenv/shared_ptr.h (§2 이어서)
namespace kernel {

// 침습 버전 기본 삭제자 - "논리적 소멸"만 한다(GenericSlabAllocator::
// free는 IntrusiveControlBlock::releaseWeak()이 weakCount==0일 때만
// 별도로 호출 - 위 "핵심 위험" 참고). T의 정리 메서드만 호출하고
// 메모리는 그대로 둔다.
template <typename T>
void kDestroyOnly(T* ptr);  // T의 명시적 정리 메서드만 호출, free 없음

template <typename T, typename Deleter = void (*)(T*)>
class IntrusiveControlBlock {
public:
    void init(Deleter deleter = &kDestroyOnly<T>) {
        _strongCount.store(1);
        _weakCount.store(1);
        _deleter = deleter;
    }

    // §2의 ControlBlock<T>::tryAddStrongRef()와 완전히 동일한 CAS 루프.
    bool tryAddStrongRef() {
        uint32_t cur = _strongCount.load();
        while (cur != 0) {
            if (_strongCount.compareExchange(cur, cur + 1)) return true;
        }
        return false;
    }
    void addStrongRefUnchecked() { _strongCount.fetchAdd(1); }
    void addWeakRef() { _weakCount.fetchAdd(1); }

    // self는 이 블록을 내장한 T 인스턴스 자신(침습적이므로 별도
    // target 포인터가 필요 없다 - this가 곧 대상 안에 있다).
    void releaseStrong(T* self) {
        if (_strongCount.fetchSub(1) == 1) {
            _deleter(self);  // 논리적 소멸만 - free는 아직 안 함(!)
            releaseWeak(self);
        }
    }
    void releaseWeak(T* self) {
        if (_weakCount.fetchSub(1) == 1) {
            GenericSlabAllocator::free(self, sizeof(T));  // 이제 진짜 반납
        }
    }

private:
    AtomicU32 _strongCount;
    AtomicU32 _weakCount;
    Deleter _deleter = &kDestroyOnly<T>;
};

// T가 상속하는 기반 클래스 - EnableSharedFromThis<T>와 비슷한 위치지만
// "선택적 편의 기능"이 아니라 침습 포인터를 쓰려면 **반드시** 상속해야
// 하는 필수 요소라는 점이 다르다.
template <typename T, typename Deleter = void (*)(T*)>
class IntrusiveRefCounted {
public:
    IntrusiveControlBlock<T, Deleter>& refBlock() { return _block; }
private:
    IntrusiveControlBlock<T, Deleter> _block;
};

template <typename T, typename Deleter>
class IntrusiveWeakPtr;

// 비침습 SharedPtr<T,Deleter>와 인터페이스는 거의 동일하지만, 내부적으로
// `ControlBlock<T,Deleter>*`가 아니라 **T* 자신**을 들고 있다가
// `_ptr->refBlock()`으로 내장된 카운트에 접근한다 - 포인터 역참조
// 한 단계가 줄어든다(비침습 버전은 SharedPtr→ControlBlock→T 순인데
// 반해 여긴 SharedPtr→T이고 T 안에 카운트가 바로 있음).
template <typename T, typename Deleter = void (*)(T*)>
class IntrusiveSharedPtr {
public:
    IntrusiveSharedPtr() = default;
    ~IntrusiveSharedPtr() { reset(); }

    IntrusiveSharedPtr(const IntrusiveSharedPtr& other) : _ptr(other._ptr) {
        if (_ptr) _ptr->refBlock().addStrongRefUnchecked();
    }
    IntrusiveSharedPtr(IntrusiveSharedPtr&& other) noexcept : _ptr(other._ptr) { other._ptr = nullptr; }
    IntrusiveSharedPtr& operator=(const IntrusiveSharedPtr& other) {
        if (this != &other) {
            reset();
            _ptr = other._ptr;
            if (_ptr) _ptr->refBlock().addStrongRefUnchecked();
        }
        return *this;
    }
    IntrusiveSharedPtr& operator=(IntrusiveSharedPtr&& other) noexcept {
        if (this != &other) {
            reset();
            _ptr = other._ptr;
            other._ptr = nullptr;
        }
        return *this;
    }

    T* get() const { return _ptr; }
    T* operator->() const { return _ptr; }
    T& operator*() const { return *_ptr; }
    explicit operator bool() const { return _ptr != nullptr; }

    void reset() {
        if (_ptr) {
            _ptr->refBlock().releaseStrong(_ptr);
            _ptr = nullptr;
        }
    }

private:
    friend class IntrusiveWeakPtr<T, Deleter>;
    explicit IntrusiveSharedPtr(T* ptr) : _ptr(ptr) {}
    T* _ptr = nullptr;
};

template <typename T, typename Deleter = void (*)(T*)>
class IntrusiveWeakPtr {
public:
    IntrusiveWeakPtr() = default;
    explicit IntrusiveWeakPtr(const IntrusiveSharedPtr<T, Deleter>& shared) : _ptr(shared._ptr) {
        if (_ptr) _ptr->refBlock().addWeakRef();
    }
    ~IntrusiveWeakPtr() { if (_ptr) _ptr->refBlock().releaseWeak(_ptr); }

    IntrusiveWeakPtr(const IntrusiveWeakPtr& other) : _ptr(other._ptr) {
        if (_ptr) _ptr->refBlock().addWeakRef();
    }
    IntrusiveWeakPtr(IntrusiveWeakPtr&& other) noexcept : _ptr(other._ptr) { other._ptr = nullptr; }
    IntrusiveWeakPtr& operator=(const IntrusiveWeakPtr& other) {
        if (this != &other) {
            if (_ptr) _ptr->refBlock().releaseWeak(_ptr);
            _ptr = other._ptr;
            if (_ptr) _ptr->refBlock().addWeakRef();
        }
        return *this;
    }
    IntrusiveWeakPtr& operator=(IntrusiveWeakPtr&& other) noexcept {
        if (this != &other) {
            if (_ptr) _ptr->refBlock().releaseWeak(_ptr);
            _ptr = other._ptr;
            other._ptr = nullptr;
        }
        return *this;
    }

    // 대상이 이미 "논리적으로 소멸"됐으면(strongCount==0) 빈
    // IntrusiveSharedPtr - §2 WeakPtr::lock()과 동일한 계약.
    // **주의**: 이 시점에도 `_ptr` 메모리 자체는 아직 유효하다(위
    // "핵심 위험" 설명대로 releaseWeak가 아직 안 불렸다면 free 전) -
    // 다만 `T`의 다른 멤버는 이미 논리적으로 소멸된 상태라 `refBlock()`
    // 이외의 멤버 접근은 안전하지 않다.
    IntrusiveSharedPtr<T, Deleter> lock() const {
        if (_ptr && _ptr->refBlock().tryAddStrongRef()) {
            return IntrusiveSharedPtr<T, Deleter>(_ptr);
        }
        return IntrusiveSharedPtr<T, Deleter>();
    }

private:
    T* _ptr = nullptr;
};

// GenericSlabAllocator로 T 하나만 할당(비침습 kMakeShared와 달리
// ControlBlock을 따로 할당하지 않음 - 이게 침습 버전의 존재 이유).
template <typename T, typename Deleter = void (*)(T*)>
IntrusiveSharedPtr<T, Deleter> kMakeIntrusiveShared(T* preConstructed, Deleter deleter = &kDestroyOnly<T>) {
    preConstructed->refBlock().init(deleter);
    return IntrusiveSharedPtr<T, Deleter>(preConstructed);
}

}  // namespace kernel
```

**언제 침습 vs 비침습을 쓰는가**: 기본은 §2의 비침습
`SharedPtr<T>`(임의 타입에 나중에 붙일 수 있음, 구조가 더 단순).
침습 버전은 **할당 빈도가 높고 `T`를 새로 설계/수정할 수 있는
경우**(할당 1회 절약 + 캐시 지역성이 실측으로 의미 있다고 확인된
경우)에만 선택적으로 고려한다 - 예: PN-E2A114C1(정적 Process 인스턴스
SharedPtr 이관)처럼 자주 생성/소멸되는 커널 객체가 후보가 될 수
있으나, **v1에서 실제로 어느 타입에 침습 버전을 쓸지는 아직 미정**
(설계만 제공, 적용 대상은 실사용처가 나오면 그때 결정 - RM-23F4B687
§4 원칙).

## 3. `AsyncTaskWeakRef`와의 관계 - 당장 교체하지 않는다

`AsyncTaskWeakRef`는 **강한 참조 개념이 없는** 순수 약한 참조
전용(§1) - 이 문서의 `WeakPtr<T>`가 정확히 그 상위 호환이지만,
`AsyncTask`가 애초에 `SharedPtr<AsyncTask>`로 관리되는 대상이
아니다(리액터가 직접 스택풀/슬랩으로 수명 관리, §1의 "생성 시 2로
시작" 관례 자체가 `SharedPtr` 없이 참여자 두 곳이 수동으로 카운트를
나눠 가진 특수 사례). **`AsyncTaskWeakRef`를 `WeakPtr<AsyncTask>`로
교체하는 건 이 문서의 범위가 아니다** - 동작 중인 코드(PN-D01B7D07
구현 완료)를 검증되지 않은 리팩터로 건드릴 이유가 없다(RM-23F4B687
§4) - 향후 실제 필요가 생기면(예: 성능/코드 중복 문제가 실측으로
드러나면) 별도로 재검토한다.

## 4. 적용 범위 - 실사용처 후보 (2026-09-16, 설계자 지시로 확장)

**[확장, 2026-09-16, 설계자 지시 - "조금 더 완화해서 싱글톤을
제외하고 '소멸 경로 누락 방지, move-only로 실수로 복사돼 이중
해제되는 걸 컴파일 타임에 차단'라는 목적으로 WeakPtr, SharedPtr,
UniquePtr 도입 검토해봐"]** 원래 이 절은 후보를 몇 개만 참고로
제시했으나, 설계자가 **정적/전역 싱글턴(`gCurrentTask[]`류)만
제외하고 나머지 전반에 걸쳐 도입을 검토**하라고 지시해 범위를
넓힌다. 목적이 명확해졌다 - "소유권 모델을 바꾸자"가 아니라
**"지금 사람이 손으로 맞춰야 하는 안전 규약(널 체크/명시적 해제
호출 순서/복사 금지 관례)을 컴파일러가 강제하게 만들자"**는
RAII 안전성 목적이다.

### 4.1 적용 원칙

- **정적/전역 싱글턴**(`gCurrentTask[kMaxCores]`, `gHandlers[]`,
  `gForcedMigrationRequest` 등) - **제외**(설계자 지시 그대로).
  부팅 시 한 번 정해지고 다시는 옮기거나 해제하지 않는 슬롯이라
  RAII로 얻을 안전성이 없다.
- **배타적 소유**(`RingBuffer::data`, `Channel::pendingHead/
  pendingTail`) - §2-A대로 `UniquePtr<T>`.
- **비소유 관찰자**(`UserThread::process`, `Task::blockedOn`,
  `AsyncTask::waitingTask`, `BridgePipe::peer` 등) - **여기가
  이번 확장의 핵심.** `WeakPtr<T>`로 감싸면 "대상이 이미 없어졌는데
  모르고 역참조하는" 사고를 `get()`이 `nullptr`을 돌려주는 것으로
  안전하게 막을 수 있다 - **단, `WeakPtr<T>`가 기댈 컨트롤 블록이
  필요하므로 관찰 대상(예: `Process`, `Waitable`)의 실제 소유자도
  그 대상을 `SharedPtr<T>`로 들고 있어야 한다**(§2의 `ControlBlock<T>`
  구조상 `UniquePtr`가 소유한 대상은 컨트롤 블록이 없어 `WeakPtr`가
  붙을 수 없다). 즉 이 확장은 관찰자 쪽 필드 하나만 바꾸는 게
  아니라, **그 대상의 소유자 쪽도 함께 `SharedPtr<T>`로 옮겨야
  완성된다**(strong count가 사실상 평생 1로 유지되는 경우라도
  상관없다 - 목적이 "공유"가 아니라 "컨트롤 블록을 통한 안전한
  관찰"이므로).

### 4.2 예시로 본 실제 적용 모양 (`Process`/`UserThread` 쌍)

- **지금**: `Process::mainThread`(`UserThread*`, 비소유) /
  `UserThread::process`(`Process*`, 비소유 역참조) - 둘 다 raw
  포인터, 서로 상대가 언제 없어지는지 각자 다른 쪽의 정리 순서에
  의존한 채 수동으로 맞춰야 한다.
- **적용 후(예시)**: `Process`의 실제 소유자(지금은 `kmain.cpp`의
  정적 전역, 향후 PN-543C0CE9의 동적 Process 풀)가 `Process`를
  `SharedPtr<Process>`로 든다. `Process::mainThread`는 그대로
  `UserThread*`(또는 대칭적으로 `SharedPtr<UserThread>`) - 소유
  관계에 따라 결정. `UserThread::process`(역참조)는 `WeakPtr<Process>`
  로 바뀐다 - 이제 `process.lock()`이 `nullptr`이면 "이 스레드가
  가리키던 프로세스가 이미 정리됐다"는 걸 역참조 전에 **컴파일러가
  강제하는 API로**(호출자가 `lock()`의 반환값을 체크할 수밖에 없는
  타입) 알 수 있다 - 지금처럼 "이 시점엔 안 죽어 있을 것"이라는
  암묵적 가정에 기대지 않는다.
- 이 예시가 보여주듯, **정적 boot-time Process 인스턴스
  (`gInitProcess`/`gServiceProcess[4]`)도 이 패턴을 적용하려면
  `SharedPtr`로 옮겨야 한다** - 이것들은 "정적/전역 싱글턴"으로
  분류할 수도 있어(위 제외 범주와 모호하게 겹침) 실제로 이것까지
  포함할지는 명확한 확인이 필요하다(아래 열린 질문 참고).

### 4.3 구체적 후보 목록 (착수 시 개별 확인 필요, 이 문서가 강제하지 않음)

- `UserThread::process`(`Process*` → `WeakPtr<Process>`) - 위 예시.
- `Task::blockedOn`(`Waitable*` → `WeakPtr<Waitable>`) - 대기 구조체
  소유자도 `SharedPtr<Waitable>`로.
- `AsyncTask::waitingTask`(`Task*` → `WeakPtr<Task>`).
- `BridgePipe::peer`(상호 참조 → 양쪽 다 `WeakPtr`, "양쪽 다 닫혀야
  반납" 프로토콜을 컴파일 타임 안전성으로 보강).
- SP-9A6D579F(프로세스 디버깅) §3.1의 `DebugSession::debuggerProcess`/
  `debuggeeProcess`(`ProcessId` 대신 `WeakPtr<Process>`), `breakpoints`
  가 참조하는 대상 스레드도 동일.
- 향후 프로세스 트리(PN-543C0CE9/SP-6BEAE0C1)의 부모→자식 목록.

**이 문서는 이 후보들을 강제하지 않는다** - 템플릿 자체의 설계만
확정하고, 각 소비자(특히 `Process`/`Task`처럼 이미 존재하는 핵심
타입)를 실제로 `SharedPtr` 기반으로 옮길지는 그 소유자 쪽 구조체를
직접 다루는 문서/계획(PN-543C0CE9 등)에서 개별적으로 확정한다
(CLAUDE.md 규칙 4). DC-21647E46에 이 확장된 범위를 반영해 다시
정리했다 - 정적 boot-time Process 인스턴스까지 포함할지가 남은
핵심 열린 질문이다.

## 5. 동시성 계약 (기존 `AsyncTaskWeakRef` 주석의 일반화)

- `tryAddStrongRef()`/`releaseStrong()`/`releaseWeak()`은 CAS/원자
  연산만으로 구현되어 **스핀락이 전혀 필요 없다**(설계자 지시
  "lock-free 기반"의 핵심 - `AsyncTaskWeakRef`가 이미 증명한 성질을
  그대로 계승).
- 다만 `T` 자신의 소멸/정리 로직(`kDestroyAndFree<T>`)이 스레드
  안전한지는 **이 템플릿의 책임이 아니다** - `strongCount`가 정확히
  한 번만 0에 도달함을 원자적으로 보장하므로 소멸자가 정확히 한
  번만 호출됨은 보장되지만, 그 소멸자 본문 자체가 락이 필요한
  작업을 하면 그건 `T`가 알아서 할 일이다.
- `AsyncTaskWeakRef`와 달리 이 템플릿은 **범용**(어느 컨텍스트에서
  호출될지 모름)이므로 "협조적 스케줄링이라 진짜 동시 실행 경쟁이
  없다"는 그 문서의 전제를 그대로 가정하지 않는다 - 위 원자
  연산만으로 진짜 다중 코어 동시 접근에도 안전하다(그게 "lock-free"
  요구의 취지로 해석했다).

## 6. 범위 밖 (v1)

- `AtomicPtr<T>` 자체의 ABA 문제 완화(태그 포인터 등) - 이 프로젝트
  전반의 `AtomicPtr<T>` 사용처(예: TLB 샷다운 `AtomicU32::fetchOr`
  기반 pending mask, `AsyncTask::next` 침습적 리스트)가 지금까지
  ABA를 겪을 만한 재사용 패턴(같은 주소가 빠르게 재할당되는 free-list
  등)을 쓰지 않는다 - 필요해지면 별도 검토.
- 배열 특화(`SharedPtr<T[]>` 등) - 커널 내 실제 필요 사례가 아직
  없다.
- ~~`enable_shared_from_this`류 편의 기능~~ - [정정, 2026-09-16]
  실제로는 범위 밖이 아니라 §2에 `EnableSharedFromThis<T>`로 이미
  포함되어 구현됨(설계자 Opinion으로 반영) - 이 줄은 작성 당시
  기준이 이후 갱신과 어긋난 잔재라 취소선으로 남기고 정정한다.
- ~~커스텀 삭제자(deleter) 파라미터화 - v1은
  `GenericSlabAllocator::free` 고정~~ - [정정, 2026-09-16, 설계자
  Opinion 2건(`cmu4462eb001fow01e9ysif9n` "커스텀 삭제자의 템플릿
  파라미터화도 설계해서 반영해", 뒤이어 `cmu44g4cp00euow01ku1z4kno`
  "SharedPtr에도 커스텀 삭제자의 템플릿 파라미터화도 설계해서
  반영해")] 이 줄은 더 이상 사실이 아니다 - `ControlBlock<T, Deleter>`
  /`SharedPtr<T, Deleter>`/`WeakPtr<T, Deleter>`/`kMakeShared<T,
  Deleter>`(§2)와 `UniquePtr<T, Deleter>`(§2-A) 전부 `Deleter`를
  **템플릿 파라미터**로 받아 기본값(`&kDestroyAndFree<T>`)을
  오버라이드할 수 있도록 v1 범위에 포함됨. `EnableSharedFromThis<T>`
  는 이 확장의 부작용으로 기본 삭제자 경로만 지원하는 제약이 생김
  (§2 끝 "알려진 제약" 참고).

- [추가, 2026-09-16, 설계자 지시 "ControlBlock<T>의 Intrusive 버전도
  고안해봐"] `IntrusiveControlBlock<T>` 등 침습적 변형은 §2-B에 설계
  추가됨(`IntrusiveControlBlock`/`IntrusiveRefCounted`/
  `IntrusiveSharedPtr`/`IntrusiveWeakPtr`/`kMakeIntrusiveShared`) -
  다만 v1에서 실제로 **적용할 타입**은 아직 미정(설계만 제공, 실사용처
  나오면 그때 적용 여부 결정).

## 7. 착수 조건

없음 - `AtomicU32`/`AtomicPtr<T>`(둘 다 이미 구현 완료,
libkenv/spinlock.h)/`GenericSlabAllocator`(이미 구현 완료)만으로
바로 착수 가능. `AsyncTaskWeakRef`라는 실제로 동작 검증된 선례가
있어 설계 위험도 낮다.
