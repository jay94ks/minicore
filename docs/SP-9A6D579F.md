# 프로세스 디버깅(브레이크포인트/싱글스텝) 서브시스템 — 설계 제안

QU-3DB5F85C 답변(2026-09-16): "(B)에 필요한 기반 설계안들을 모두
작성해서 등록해봐." - SP-677210E6이 확정한 #DB ISR 라우팅(DR6
디코드 + 커널 내부 콜백 슬롯 `gDebugCallback`)의 **첫 실제
소비자**로, 한 유저 프로세스(디버거)가 다른 유저 프로세스(디버기)에
브레이크포인트/싱글스텝을 걸고 그 결과를 조회하는 크로스 프로세스
디버깅 지원을 설계한다.

**[개정, 2026-09-16, 설계자 Opinion]** 초안(아래 각 절에 "권장(확정
아님)"으로 표시했던 후보들)에 대해 설계자가 5가지 결정을 직접
내려줬다 - 이 리비전이 전부 반영한다:

1. 권한 모델은 **부모-자식 한정** + **"커널"과 "커널 서비스"는 모두
   [예외적으로 임의 대상] 가능**.
2. Attach/Detach 동작은 유지하되, **부모가 디버깅 대상으로 시작시킨
   프로세스는 정지 상태로 시작**한다.
3. 통지는 **커널 이벤트 발행/구독** 방식(원안 그대로) - 단, **디버그
   인터럽트는 디버깅 대상인 프로세스나 스레드를 정지시켜야 한다**.
4. **멀티 스레드 디버깅도 구현해야 함**(원안의 v1 범위 밖 항목을
   철회).
5. **복수 디버거의 동시 세션은 금지, 프로세스 1개당 세션 1개만
   허용**(원안과 동일 - 단 "추후 이걸 보안 메커니즘으로 채택한
   유저랜드 앱들이 출시될 수도 있도록"이라는 근거가 추가됨 - **v1
   임시 제약이 아니라 영구 설계 불변조건**으로 격상).

## 1. 실측 확인한 전제 (이 문서가 새로 짓는 것과 재사용하는 것)

- `kernel::TaskState`(task.h)는 `{Ready, Running, Blocked, Zombie}`
  4개뿐이다 - `Suspended`류 상태는 없다(AsyncTaskState와 혼동 주의 -
  그건 별개의 SP-F682B889 쪽 enum). 디버그 정지는 아래 §3.5에서
  기존 `Blocked`를 재사용한다.
- **`kernel::Process::mainThread`는 단일 `UserThread*` 필드다**
  (process.h, "v1: 프로세스당 스레드 하나"라고 명시적으로 주석돼
  있음) - **멀티스레드 유저 프로세스 자체가 이 코드베이스에 아직
  없다.** 이게 위 개정사항 4(멀티 스레드 디버깅)의 진짜 선행 조건 -
  아래 §1-A에서 별도로 다룬다.
- `kernel::Process`에는 부모 프로세스를 가리키는 필드가 아직 없다 -
  `ProcessRole{Normal, KernelService}` 두 값뿐이다. **다만
  PN-543C0CE9(일반 프로세스 생성 syscall)이 SP-6BEAE0C1로 설계
  중이고, 그 QU-52253384 답변(2026-09-16)이 "부모 자식 추적을 위해
  프로세스 트리 구조로 설계해, fire-and-forget 하면 안 돼"로
  확정됐다** - 즉 위 개정사항 1(부모-자식 권한 모델)이 요구하는
  실제 부모 추적 인프라가 SP-6BEAE0C1/PN-543C0CE9 쪽에서 곧 갖춰질
  예정이다. 이 문서는 그 프로세스 트리가 완성된다는 전제로 설계하고,
  실제 필드/API 이름은 착수 시 SP-6BEAE0C1 최종본을 따른다.

### 1-A. [신규 발견] 멀티스레드 유저 프로세스 지원 자체가 없다 - 별도 선행 계획 필요

개정사항 4가 요구하는 "멀티 스레드 디버깅"은 **디버깅 서브시스템만의
문제가 아니라, 애초에 한 `Process`가 여러 `UserThread`를 가질 수
있어야 한다는 훨씬 근본적인 선행 조건**을 필요로 한다 - 지금은
`Process::mainThread` 필드 하나뿐이라 "여러 스레드 중 하나가
브레이크포인트에 걸렸다"는 상황 자체가 원천적으로 발생할 수 없다.
이건 PN-543C0CE9(프로세스 생성)와도 별개의 축(프로세스가 여러
스레드를 담는 문제)이라 **새 계획 PN-2E4E9D79로 분리 등록**했다
(CLAUDE.md 규칙 4/7 - 임의로 이 문서 안에서 멀티스레딩 자체를
설계하지 않고, 별도 계획으로 그 필요성만 우선 기록). 이 문서의
멀티스레드 디버깅 관련 절(§3.1/§3.5/§4)은 **그 선행 계획이 완료된다는
전제로 설계**하되, 실제 착수는 그 전까지 보류한다(§8).

## 2. 범위/전제

- SP-677210E6의 #DB ISR 라우팅을 그대로 쓴다(재설계하지 않음) -
  `gDebugCallback`이 이 문서가 설계하는 로직으로 채워진다.
- 커널 자체 디버깅(이 문서는 유저 프로세스 대상만 - 커널 디버깅은
  SP-DABFCF9F의 QEMU gdb stub 워크플로가 이미 다룸, 완전히 별개
  메커니즘)은 범위 밖.
- 멀티스레드 디버깅은 범위 안이지만 §1-A의 선행 계획(PN-2E4E9D79)
  완료 전까지 착수 보류(§8).

## 3. 핵심 모델

### 3.1 `DebugSession`

```cpp
namespace kernel {

struct DebugBreakpoint {
    uintptr_t address = 0;
    enum class Condition : uint8_t { Execute, Write, ReadWrite } condition = Condition::Execute;
    bool enabled = false;
    // 개정사항 4 - 멀티스레드: 비워 두면(0) "이 프로세스의 어느
    // 스레드가 걸려도" 정지 대상이고, 특정 ThreadId를 지정하면 그
    // 스레드만 대상(§1-A 완료 후 ThreadId 타입 확정).
    ThreadId targetThread = kAnyThread;
};

struct DebugSession {
    ProcessId debuggerProcess;
    ProcessId debuggeeProcess;
    DebugBreakpoint breakpoints[4];  // DR0-3 하드웨어 슬롯 수와 동일 - 스레드마다 별도 슬롯이 아니라 프로세스당 4개 공유(코어 DR 레지스터 수 제약)
    bool singleStepPending = false;  // 개정 4 반영 시 스레드별 비트맵으로 확장 필요(§1-A 이후)
    bool active = false;
};

// 프로세스당(디버기 기준) 세션 하나만 - 설계자 지시(개정 5)로 영구
// 불변조건(§7 참고, v1 임시 제약이 아님).
DebugSession gDebugSessions[kAcpiAllProcessesMax];  // 실제 상한 상수명은 착수 시 기존 프로세스 테이블 상수 재사용

}  // namespace kernel
```

### 3.2 권한 모델 - 누가 누구를 디버깅할 수 있는가 (확정, 설계자 지시)

**부모-자식 한정 + "커널"/"커널 서비스" 예외**:

- **기본 규칙**: 디버거가 디버기의 **직접 부모**일 때만 `DebugAttach`
  가능(SP-6BEAE0C1/PN-543C0CE9의 프로세스 트리 완성이 전제 - §1
  참고).
- **예외 1 - "커널"**: 프로세스가 아닌 **커널 코드 자신**(예: 향후
  커널 내부 진단/복구 로직이 `EventTopicRegistry::subscribeKernel`
  처럼 직접 등록하는 소비자)은 부모-자식 여부와 무관하게 임의
  프로세스를 디버깅할 수 있다 - 이 경로는 syscall이 아니라 §3.5의
  `gDebugCallback` 슬롯에 커널 코드가 직접 등록하는 방식으로,
  Attach/Detach syscall 자체를 거치지 않는다(호출자가 유저 프로세스가
  아니므로).
- **예외 2 - `ProcessRole::KernelService`**: `ProcessRole::
  KernelService`로 스폰된 프로세스는 부모-자식 여부와 무관하게 임의
  프로세스를 `DebugAttach`할 수 있다(이미 존재하는 `Process::role`
  필드만으로 판정 가능, 추가 인프라 불필요).
- 판정 순서: `DebugAttach` 호출 시 (a) 호출자가 `ProcessRole::
  KernelService`면 즉시 허용 → (b) 아니면 호출자가 대상의 직접
  부모인지 확인(프로세스 트리 조회) → (c) 둘 다 아니면
  `PermissionDenied`.

## 3.3 Attach/Detach + 디버그 대상으로 스폰된 프로세스는 정지 상태로 시작(확정, 설계자 지시)

```
DebugAttach(pid: ProcessId) -> error    // §3.2 권한 모델 통과해야 성공
DebugDetach(pid: ProcessId) -> error
```

- 일반 `DebugAttach`(이미 실행 중인 프로세스에 사후 부착)는 원안
  그대로 - 디버기를 즉시 멈추지 않고 "관찰 대상으로 등록"만 한다.
- **[신규, 설계자 지시] 부모가 자식을 "디버깅 대상으로" 스폰하면 그
  자식은 첫 명령어를 실행하기 전에 정지 상태로 시작한다** -
  **[해소, 2026-09-16, QU-9585F6C4]** 처음엔 `SpawnProcess`(SP-6BEAE0C1
  §3)에 전용 `debugStart: bool` 파라미터가 필요하다고 봤으나, 실제로
  그 문서의 시그니처엔 반영이 안 돼 있던 게 뒤늦게 발견됐고(minicore-f8
  세션 리뷰 중), 설계자가 "일반화된 정수로 플래그 셋을 받는 형태로
  설계해놔(확장성)"로 확정했다 - SP-6BEAE0C1 §3에 `flags: uint32_t`
  (`SpawnProcessFlags::kSpawnDebugStart = 1u << 0`)로 반영 완료.
  이 문서에서 참조할 이름은 `kSpawnDebugStart` 비트다(단독
  `debugStart` 파라미터가 아님 - 위 표기 정정). 소급 반영 작업은
  PN-A6E01B8A로 추적한다. 정지 방식은 §3.5와 동일(`TaskState::Blocked`
  + 디버거에게 이벤트 통지) - 다만 트리거가 브레이크포인트가 아니라
  "스폰 시점 자체"라는 점만 다르다(구현상 `kAsyncTaskEntryWrapper`/
  `kTaskFallingToEnd`류 진입 지점이 아니라, 새 Task를 처음 Ready
  큐에 넣기 직전에 `flags & kSpawnDebugStart`면 곧장 `Blocked`로
  두는 방식이 될 것으로 보인다 - 착수 시 확정).

### 3.4 브레이크포인트/싱글스텝 설정

```
DebugSetBreakpoint(pid: ProcessId, slot: 0..3, address: uintptr_t,
                    condition: Execute|Write|ReadWrite, enable: bool,
                    targetThread: ThreadId = kAnyThread) -> error
DebugSetSingleStep(pid: ProcessId, enable: bool, targetThread: ThreadId) -> error
```

- `targetThread` 파라미터는 개정사항 4(멀티 스레드) 반영 - §1-A의
  멀티스레드 프로세스 지원이 갖춰지기 전까지는 `mainThread`
  (사실상 유일한 스레드) 고정으로 동작.
- `DR0`-`DR3`/`DR7`은 코어 레지스터이지 스레드별 저장 슬롯이
  아니다 - **이 syscall들은 대상 스레드의 저장된 컨텍스트에만
  쓴다**. 실제 하드웨어 `DR0`-`DR3`/`DR7` 로드는 그 스레드가 다음에
  디스패치될 때 이뤄져야 한다 - **SP-83A07867 §3.2의 세 디스패치
  훅(`kSyncCr3`/`kSyncRsp0ForDispatch`/`kSyncFpu`)에 네 번째
  `kSyncDebugRegs`를 추가**하는 것과 동형(그 문서가 이미 확립한
  "코어 소유가 아니라 Task 소유 레지스터는 디스패치 시점에 동기화"
  패턴을 그대로 재사용).

### 3.5 정지(Stop) / 재개(Continue) / 이벤트 통지

- **[확정, 설계자 지시] 브레이크포인트/싱글스텝이 실제로 걸리면
  디버깅 대상인 프로세스나 스레드를 반드시 정지시켜야 한다** -
  디버기의 #DB ISR(`gDebugCallback`)이 그 대상(멀티스레드 지원
  전까지는 프로세스 = 스레드 하나)의 상태를 **기존 `TaskState::
  Blocked`로 바꾼다**(§1 - 새 `DebugStopped` 상태를 추가하지 않는다,
  RM-23F4B687 §4 - 과설계 방지). 이 정지는 옵션이 아니다(설계자
  지시로 항상 발생).
- 디버거에게 이 사실을 알리는 방법 - **확정: SP-2602CAA6(커널 이벤트
  발행/구독) 재사용**(설계자 지시로 확정) - 이 디버기 전용 토픽을
  디버거가 구독(`SubscribeEvent`/`WaitEvent`). `EventTopicRegistry::
  registerTopic()`으로 디버그 세션마다 토픽 하나를 만들고,
  `EventPayload`에 디버기 pid(+개정 4 반영 시 ThreadId) + 정지
  사유(브레이크포인트 슬롯 번호 또는 싱글스텝)를 싣는다.
- `DebugContinue(pid, targetThread) -> error` - 정지된 대상을
  `Blocked`에서 다시 `Ready`로.
- `DebugGetRegisters(pid, targetThread, outRegs) -> error` /
  `DebugSetRegisters(pid, targetThread, inRegs) -> error` - 대상이
  `Blocked`(디버그 정지) 상태일 때만 성공, 아니면 `InvalidState`.
- `DebugReadMemory(pid, addr, len, out) -> error` / `DebugWriteMemory(pid,
  addr, len, in) -> error` - 프로세스 단위(주소공간은 스레드가 아니라
  프로세스 소유이므로 `targetThread` 불필요). 디버기의 주소공간을
  디버거 주소공간에 매핑하지 않고 **커널이 대행 복사**한다
  (`ProcessAddressSpaceManager`가 아는 PML4를 direct physical map
  경유로 - SP-2AAD7C8D 기존 인프라 재사용).

## 4. syscall 목록 (RM-48E1E610 번호 예약 필요 - 착수 시 먼저 등록, CLAUDE.md 규칙 10)

- `DebugAttach`
- `DebugDetach`
- `DebugSetBreakpoint`(§3.4 - `targetThread` 파라미터 포함)
- `DebugSetSingleStep`(§3.4 - `targetThread` 파라미터 포함)
- `DebugContinue`(§3.5 - `targetThread` 파라미터 포함)
- `DebugGetRegisters`(§3.5 - `targetThread` 파라미터 포함)
- `DebugSetRegisters`(§3.5 - `targetThread` 파라미터 포함)
- `DebugReadMemory`
- `DebugWriteMemory`

(이벤트 통지는 §3.5가 SP-2602CAA6의 기존 `SubscribeEvent`/
`WaitEvent`를 재사용하므로 별도 syscall 불필요. `SpawnProcess`의
`flags & kSpawnDebugStart` 비트는 SP-6BEAE0C1 쪽 번호 59 그대로 -
새 syscall 아님, 기존 `flags` 파라미터의 비트 하나일 뿐.)

## 5. 동시성/안전

- §1-A의 멀티스레드 프로세스 지원이 갖춰지기 전까지는 실질적으로
  프로세스당 스레드 하나이므로 "여러 스레드가 동시에 브레이크포인트에
  걸리는" 경합은 발생하지 않는다 - 그 지원이 들어온 뒤에는 같은
  프로세스의 서로 다른 스레드가 동시에 서로 다른 코어에서 각자
  걸릴 수 있다는 새 경합이 생긴다(§1-A 선행 계획 완료 시 이 절을
  다시 검토해야 함 - 지금은 명시만 해 둔다).
- `DebugReadMemory`/`WriteMemory` 도중 디버기가 동시에 스케줄돼 그
  메모리를 건드릴 가능성 - **[재검토 필요]** 이전 리비전은 "디버기가
  `Blocked`인 동안은 경합이 없다"고 했으나, 이는 프로세스의 **모든**
  스레드가 정지해 있어야 성립한다 - 멀티스레드 지원 후에는 한
  스레드만 브레이크포인트로 정지하고 나머지는 계속 실행 중일 수
  있어, `ReadMemory`/`WriteMemory` 중 다른(정지 안 된) 스레드가 같은
  메모리를 건드릴 여지가 생긴다. v1(사실상 단일 스레드)에서는 문제
  없지만, §1-A 완료 후 이 절을 다시 확정해야 한다.
- `DebugSetBreakpoint` 호출 시점에 대상 스레드가 마침 디스패치
  중이라면(`kSyncDebugRegs`가 아직 안 돈 순간) - 다음 디스패치에서
  반영되므로 최악의 경우 한 타임퀀텀 지연, 안전성 문제는 아니다.

## 6. 에러 케이스

- `DebugAttach`: 권한 모델(§3.2) 불통과 시 `PermissionDenied`, 이미
  다른 디버거가 세션을 갖고 있으면 `AlreadyExists`(§7 - 세션 1개
  한정은 영구 규칙).
- `DebugSetBreakpoint`/`SetSingleStep`/`Continue`/`GetRegisters`/
  `SetRegisters`/`ReadMemory`/`WriteMemory`: 호출자가 그 pid의 활성
  세션의 `debuggerProcess`가 아니면 `PermissionDenied`. 세션 자체가
  없으면 `InvalidState`.
- `GetRegisters`/`SetRegisters`: 대상 스레드가 `Blocked`(디버그
  정지)가 아니면 `InvalidState`(실행 중인 스레드의 레지스터를
  훔쳐보거나 덮어쓰는 건 허용 안 함).

## 7. 범위 밖 / 영구 설계 불변조건

- **커널 자체 디버깅**은 범위 밖(이 문서는 유저 프로세스 대상만 -
  커널 디버깅은 SP-DABFCF9F의 QEMU gdb stub 워크플로가 별개로 다룸).
- **Watchpoint 중 `Read` 단독 조건**은 범위 밖(§3.4는 Execute/Write/
  ReadWrite만 노출 - `DR7`은 Read 단독도 지원하지만 흔치 않은
  유스케이스라 생략).
- **[영구 불변조건, v1 제약 아님, 설계자 지시]** 복수 디버거의 동시
  세션 금지 - 디버기당 세션 1개만 허용한다. 이건 단순화를 위한
  임시 제약이 아니라 **의도적인 보안 메커니즘**이다 - 한 세션만
  허용되므로, 보안에 민감한 유저랜드 앱이 스스로를 자기 자신에게
  `DebugAttach`(또는 신뢰하는 부모가 대신)해 그 유일한 세션 슬롯을
  선점하면, 실제 악의적인 디버거가 나중에 `DebugAttach`를 시도해도
  `AlreadyExists`로 거부된다(안티 디버깅/안티 템퍼링 기법) - 이
  속성이 나중에 유저랜드 보안 라이브러리의 기반이 될 수 있으므로
  절대 완화하지 않는다.
- 멀티스레드 디버깅은 더 이상 범위 밖이 아니다(§1-A 선행 계획
  완료 후 §8 착수 조건 충족 시 구현).
