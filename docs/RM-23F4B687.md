# Minicore 작업 지침 — 코딩 컨벤션 및 문서화 원칙

설계자가 내린 지시로, 앞으로의 모든 작업(설계/구현 모두)에서 지켜야 한다.

## 1. 네이밍 컨벤션 (커널 코드, DC-79A2387A에서 확정)

- **함수(자유 함수/전역 함수만)**: 프리픽스 `k` + 파스칼 케이스. 예:
  `kMain`, `kOutB`(전역 함수/네임스페이스 스코프 함수 - 클래스 소속이
  아님).
- **클래스 멤버 메서드는 `k` 프리픽스 없이 camelCase다**(2026-09-14
  수정 - 처음엔 함수 규칙을 멤버 메서드에도 그대로 적용했다가 설계자
  지적으로 바로잡음). 예: `Serial::init()`, `Paging::mapPage(...)`,
  `Lapic::sendEoi()` — `Serial::kInit()`처럼 쓰지 않는다. 정적(static)
  메서드도 동일하게 camelCase.
- **타입**: 파스칼 케이스. 예: `PageFrame`.
- **상수**: `UPPER_CASE`.
- **네임스페이스**: 프리픽스 없음, **항상 snake_case**로만 쓴다(예:
  `kernel`, `page_alloc`). **커널 앱에만 적용**한다 — 유저랜드 앱은
  앱별로 완전히 별도 프로젝트로 간주하므로 이 규칙을 강제하지 않는다.
- **멤버 변수**:
  - public 멤버: 언더바 없는 `camelCase`.
  - private 멤버: 언더바 프리픽스 `_camelCase`.

## 2. 커널 C++ 런타임 정책 (DC-79A2387A에서 확정)

- **헤더 가드**: `#pragma once`가 아니라 전통적인 `#ifndef`/`#define`
  가드를 쓴다. 파일 확장자는 언어 디폴트를 그대로 사용한다(`.cpp`/`.h`
  등 표준 확장자, 별도 규칙 없음).
- **예외(Exception) 금지**: 커널 코드에서 C++ 예외(`try`/`catch`)를
  **절대 사용하지 않는다**. 대신 표준 `errno_t` 에러 체계를 정의해
  그것으로 에러를 전달한다.
- **RTTI/STL은 단계적으로 도입**: 부팅 초기(early boot) 단계에서는
  RTTI 지원이나 동적 메모리 할당 등 "운영체제가 준비되지 않아도 동작
  가능한 것"만 구현한다. 그 이상의 RTTI/STL 컨테이너 지원은 커널
  초기화가 진행되며 필요해질 때 단계적으로 확장한다 — 지금 전체 범위를
  미리 정하지 않는다.

## 3. 디렉터리 배치 원칙

- `minicore/arch/<arch_name>`: **순수 부팅 stub/bootstrap 코드만**
  (예: `boot.S`) — 부팅 이후에도 계속 쓰이는 코드를 여기 두지 않는다
  (2026-09-14 설계자 지적으로 바로잡음 - 처음에 ISR 스텁을 실수로
  여기 뒀었다).
- `minicore/libs/<arch_name>`: 부팅 이후에도 커널(및 나중에 커널
  서비스)이 재사용하는 **아키텍처 종속 라이브러리 코드**(예: ISR
  스텁 `isr.S`, 포트 I/O `io_port.h`) — 필요하면 직접 링크해 재사용할
  수 있도록 전처리기/추상화 계층을 갖춘다.
- `minicore/libs/libkenv`: **아키텍처 무관** early C/C++ 런타임(예:
  `memset`/`memcpy`/`memmove`/`memcmp`) — 이 넷은 우리 네이밍 규칙의
  예외로, 컴파일러가 암묵적으로 호출하는 표준 이름 그대로 정의해야
  한다(`kMemset`처럼 바꾸면 안 됨).
- ARM/RISC-V처럼 벤더별 차이가 큰 아키텍처는 해당 아키텍처 하위에서
  구현부를 추상화해 분리한다.

## 4. 개발 편의 요구사항

- 부팅 시 `--kernel`/`--initrd` 옵션으로 이미지를 직접 넘기는 방식을
  항상 지원한다(BIOS/PVH/multiboot2/EFI 각 경로 구현과 별개로 유지).
- 시리얼 포트를 구현해 커널 로그를 그것으로 수신할 수 있게 한다.
- QEMU 부팅 스모크 테스트(시리얼 로그 확인)는 지금부터 스크립트로
  자동화한다(DC-48565C0B에서 확정) — CI 자체는 아직 로컬 수동 검증
  단계이지만, 반복 확인은 스크립트로 한다.
- **부팅 경로별 회귀 테스트는 초기 확인 이후 매번 전부 돌리지
  않는다**(설계자 지시, 2026-09-13) — PVH/multiboot2(GRUB)/BIOS/EFI
  각 부팅 경로와 xAPIC/x2APIC, 단일코어/SMP 등 조합이 한 번씩 실측
  검증되고 나면, 이후 새 기능을 개발할 때마다 그 모든 조합을 매번
  다시 테스트할 필요는 없다 — **그 기능을 확인하기에 가장 적합한
  부팅 경로 하나만** 골라 테스트한다(예: 순수 커널 로직 변경은
  QEMU `-kernel` PVH 경로 하나로 충분, x2APIC 관련 변경만 KVM
  경로로, SMP 관련 변경만 `-smp`로). 부팅 경로 자체를 바꾸는 작업
  (예: 링커 스크립트, boot.S, multiboot2 파서)을 할 때만 관련
  경로들을 다시 교차 검증한다.

## 5. 문서화/의사결정 원칙 (CNW 사용 규칙)

- **명시되지 않은 설계 항목을 임의로 결정하지 않는다.** 설계자가 준
  범위에 없는 세부는 구현/설계 문서에 추측으로 채워 넣지 말고, DC(결정
  요구사항 및 요청) 문서로 등록하고 실제 질의(`docs question`)를 걸어
  답변을 기다린다.
- 기능/동작에 대한 검증 체크리스트는 QA 시나리오 문서로 남기고,
  실측 확인된 항목과 아직 검증 안 된 항목을 구분해 기록한다.
- 설계자가 내린 지시나 지켜야 할 지침(이 문서 같은 것)은 RM 문서로
  남기고, 필요 없어지면 보관 처리한다.
- 지금 만들고 있는 것의 명세는 SP 문서로 남긴다 — 구두로만 오간 설계
  내용이라도 빠뜨리지 않고 SP에 옮겨 적는다.
- 결정 요구사항(DC)에 대한 답이 오면, 그 결정과 근거를 DS(설계 결정)
  문서에 옮겨 적고 DC 문서 상태를 `approved`로 전이한다 — DC 자체를
  방치한 채 결정 내용만 기억에 의존하지 않는다.

## 6. `docs/` 폴더는 예외 — 공개용 사본(캐시)은 커밋한다

위 "로컬 스크래치 사본은 git 커밋 금지" 규칙은 `docs new`/`docs save`용
임시 편집 파일에 대한 것이지, 저장소 루트의 **`docs/` 폴더**에는
적용되지 않는다. `docs/`는 CNW 문서(SP/DC/DS/QA/RM 등)를 GitHub에서
코드 없이도 읽을 수 있도록 만든 **의도적인 공개용 사본(캐시)**이다.

- 정본은 항상 CNW DB다 — `docs/` 안의 파일을 직접 손으로 고치지 않는다.
- 최신화는 `node scripts/export-cnw-docs.mjs`를 실행해 다시 만든다
  (CNW의 모든 문서를 다시 조회해 덮어쓰고, 삭제된 문서의 캐시 파일은
  정리한다).
- **CNW 문서(SP/DC/DS/QA/RM/PL 등)를 하나라도 바꾼 뒤에는 매번 이
  스크립트를 다시 실행해 커밋한다**(설계자 지시, 2026-09-14 - 이전엔
  "명시적으로 요청했을 때만"이었으나 이 규칙으로 대체됨). `docs/`
  사본이 CNW DB보다 뒤처지지 않게 항상 같이 반영한다.

## 7. git 발행(publish) 시 반드시 CNW 파이프라인만 쓴다

이 저장소는 GitHub가 authoritative, Gitea 작업 저장소는 CNW가 커밋을
쌓는 중간 저장소다(`link-external`). **로컬 clone에서 직접
`git commit`/`git push`로 GitHub main에 커밋을 얹지 않는다** — Gitea
작업 저장소가 그 커밋을 모르는 채로 나중에 `docs git publish`를
실행하면, fast-forward가 아니게 된 GitHub main을 **조용히
force-push로 덮어써 그 커밋을 통째로 잃어버린다**(2026-09-13 실제
사고 - `.mcp.json` 커밋이 이렇게 사라졌다가 복구됨, 버그는
BR-3CAF6DBC로 신고). 저장소에 파일을 반영할 때는 항상 `docs git add`
→ `docs git commit` → `docs git publish` 순서로만 하고, 로컬
워킹 디렉터리는 발행 후 `git fetch`+fast-forward로만 따라간다.

**커밋/발행은 매번 확인받지 않고 자동으로 한다**(설계자 지시,
2026-09-13) — 위 파이프라인(add→commit→publish, 이후 로컬
fast-forward)을 그대로 따르는 한, 커밋하거나 GitHub에 발행하기 전에
"push해도 될까요?"처럼 매번 승인을 구하지 않는다. 단, 이 자동 승인은
정해진 파이프라인 안에서의 일반적인 반영에 한한다 — 강제 push, 히스토리
재작성(rebase/force), 다른 브랜치 삭제처럼 되돌리기 어려운 조작은
이 규칙과 무관하게 여전히 설계자에게 먼저 확인한다.

## 7-A. 세션 역할 분담 — 문서/계획 리뷰 세션은 git 파이프라인을 다루지 않는다
(신설, 2026-09-16, QU-92186A9B 답변 "역할별 분업 계획을 작성해봐" 반영)

§6/§7은 "CNW 문서를 다루는 세션은 git 동기화(`docs/` 캐시 재생성 +
add/commit/publish)까지 직접 한다"는 것을 암묵적 전제로 깔고 있다 -
그러나 실제로 이 프로젝트는 역할이 다른 여러 세션이 동시에 운영된다.
이 절은 그 역할 분담을 명시적으로 기록한다.

### 역할 정의

- **문서/계획 리뷰 세션** (`review`/`approved` 문서를 비판적으로
  검토하고, `PN-XXXXXXXX` 계획을 정리하고, `docs question`으로
  설계자에게 질의하는 세션 — CNW DB 상의 읽기/쓰기만 수행): **git
  관련 동작(§6의 `docs/` 캐시 재생성, §7의 `docs git add/commit/
  publish`, 로컬 `git fetch`/fast-forward 포함) 전체를 수행하지
  않는다.** 이 세션은 설계자로부터 구두 지시("파이프라인 중에서
  git관련 동작을 할 필요가 없다")로 이 범위에서 제외됐다.
- **커널 코드 구현 세션** (실제 `minicore/*`/`userland/*` 소스를
  작성·수정하는 세션): §6/§7을 문자 그대로 따른다 - CNW 문서를 하나
  라도 바꾸면 `docs/` 캐시를 재생성해 커밋하고, 코드 변경은
  `docs git add`→`commit`→`publish` 파이프라인으로 발행한다.

### 왜 "세션 이름"이 아니라 "역할"로 기술하는가

특정 세션 이름(예: 현재 떠 있는 세션 식별자)을 이 문서에 고정 기입하지
않는다 - 세션은 재시작/교체될 수 있어 이름을 못박으면 금방 낡은 정보가
된다. 대신 **"이 세션이 지금 무슨 작업을 하고 있는가"로 역할을
판별**한다: CNW 문서/계획만 다루고 있다면 위 "문서/계획 리뷰 세션"
역할을 따르고, 실제 소스 코드를 작성/수정하고 있다면 "커널 코드 구현
세션" 역할을 따른다. 한 세션이 두 역할을 겸하는 것 자체를 금지하지는
않는다 - 다만 겸할 경우엔 코드를 건드리는 순간부터 §6/§7이 적용된다.

### 새 세션이 시작할 때 판단 기준

세션 메모리가 없는 새 세션은 이 절을 읽고, 자신에게 주어진 작업
지시가 "문서/계획 검토·정리"인지 "실제 코드 구현"인지로 자신의 역할을
스스로 판단한다 - 구두로 별도 지시가 없다면 기본값은 §6/§7 그대로
(git 동기화까지 직접 수행)이며, "이 세션은 git 관련 동작을 하지
않는다"는 예외는 설계자가 명시적으로(구두든 문서든) 지시했을 때만
적용한다.

## 8. 구현 중 기억해야 할 설계 사항은 코드 관계도(relation)에도 남긴다

코드 작성을 시작하면, 나중에 다시 파악하려면 비용이 드는 설계
사실(예: "이 함수가 SP-8B6B8D25의 higher-half 레이아웃을 가정한다",
"이 구조체는 DS-D4E5C451의 buddy allocator 결정을 구현한다")을
`docs relation add <projectId> --file <path> --line <n> --purpose
<설명> --refs <관련 trackingCode>`로 기록한다. 단순 리팩터링이나
자명한 코드에는 걸지 않고, "이 코드를 보는 사람이 관련 설계 문서를
모르면 오해하거나 실수하기 쉬운 지점"에 건다. 새 파일을 만들기 전엔
`docs relation list`로 이미 기록된 관계가 있는지 먼저 확인한다.

## 9. QEMU gdb stub 기반 커널 디버깅 (SP-DABFCF9F, PN-1E7798AF, 2026-09-16)

같은 하룻밤 서로 무관한 세 조사(PN-584DB994/PN-57CF48DB/PN-6049A353,
전부 SMP/스케줄러 영역)가 전부 "코드 리뷰/정적 추론만으로는 한계에
도달했다"는 같은 결론에 막힌 뒤 설계자 승인(PN-1E7798AF Opinion)으로
SP-DABFCF9F가 설계하고 실제 구현까지 완료된 표준 절차다 - 재현되는
(또는 재현 시도 중인) 크래시/행(hang)의 실제 레지스터·스택·메모리
상태를 추측이 아니라 직접 봐야 할 때 쓴다.

- `scripts/run-qemu-gdb.sh`(PVH, run-qemu.sh 변형)/
  `scripts/run-grub-gdb.sh`(GRUB multiboot2, run-grub.sh 변형) -
  기존 두 스크립트와 동일한 빌드 절차를 재사용하되 `timeout` 대신
  `-s -S`(TCP 1234에 gdb stub, 첫 명령 실행 전 정지)로 QEMU를 띄운다.
  `MINICORE_QEMU_SMP=4` 환경변수로 SMP4 재현(PN-584DB994 등)을,
  `MINICORE_QEMU_INITRD=<경로>`로 initrd 포함 시나리오를 켠다.
- 다른 터미널(또는 백그라운드로 띄운 뒤)에서 프로젝트 루트에서
  `gdb -x scripts/kernel.gdb`로 붙는다 - ELF 심볼 로드 +
  `target remote localhost:1234` + 부팅 진입점(`kMain`)에 기본
  브레이크포인트를 건 상태로 시작한다. `continue`로 실행을 재개하고,
  특정 함수가 의심되면 `break <함수명>`을 추가로 건다 - 지금까지
  관찰된 크래시 패턴(Double Fault류)은 전부 `kPanic`으로 귀결됐다
  (PN-57CF48DB) - 그쪽을 조사할 땐 `break kPanic`이 유용하다.
- **gdb-multiarch 불필요(실측 확인)** - 이 WSL 환경엔 설치돼 있지
  않지만, 호스트/타겟이 둘 다 x86_64로 같아 평범한 `gdb`가 이미
  기본 지원한다 - gdb-multiarch는 아키텍처가 다를 때만 필요.
- **Triple Fault(kPanic까지 도달하지 못하고 CPU 자체가 리셋되는 경우,
  PN-6049A353처럼)는 `break kPanic`으로 못 잡는다** - 의심되는 함수에
  직접 브레이크포인트를 걸고 `stepi`로 좁혀 나가야 한다. 다만
  `-d cpu_reset,guest_errors -D <로그>`(두 스크립트 다 기본 포함)는
  Triple Fault 시에도 `CPU Reset (CPU N)` 항목을 남긴다(실측 확인,
  2026-09-16 PN-6049A353 재현 로그) - 리셋 직후의 영값(zeroed) 상태라
  원인 자체를 알려주진 않지만, "정말 리셋이 일어났는지"와 "어느
  코어(들)가 리셋됐는지"는 gdb 없이도 이 로그만으로 1차 확인 가능
  하다(예: SMP4에서 코어 4개 전부가 반복적으로 리셋된 사례처럼,
  범위가 특정 코어 하나로 국한된 문제인지 시스템 전역 손상인지
  가늠하는 단서가 된다).
- **[갱신, 2026-09-16, 설계자 Opinion]** "CPU 자체가 리셋되는 경우는
  QEMU가 리셋될 때 자동 재부팅을 에뮬레이션하지 말고, 그대로 죽으라는
  옵션을 주면 해결되는 문제야." - PN-6049A353에서 관찰된 "코어 여러
  개가 반복적으로 리셋되며 QEMU 프로세스는 타임아웃까지 계속 살아
  있는" 현상(원인은 `-no-reboot`가 이미 켜져 있어도, 개별 CPU 리셋이
  최상위 시스템 리부트 요청으로 반드시 이어지는 건 아니라서 그
  플래그가 발동하지 않는 것으로 추정)을 QEMU 자체 옵션으로 없애자는
  지시 - 반복 리셋 대신 그 시점에 QEMU 프로세스가 즉시 종료(die)되면
  "타임아웃까지 기다려야 트리플 폴트로 추정한다"는 지금의 간접 판정
  방식이 "프로세스가 그 즉시 죽었다"는 명확한 신호로 바뀐다.

  **[해소, 2026-09-16, PN-9C6EB9E1 실측 완료]** 네 스크립트에 이미
  적용돼 있던 `-no-reboot`가 그 자체로 이미 원하는 동작이었다 - 통제된
  두 재현(순수 real-mode 강제 Triple Fault, GRUB multiboot2 SMP4
  long-mode AP 코어 강제 Triple Fault)에서 전부 QEMU가 0.15~0.9초
  안에 `Triple fault` 로그 줄과 함께 exit code 0으로 즉시 종료됨을
  확인 - **스크립트 변경 불필요**. `-action reboot=shutdown`도
  교차 확인했으나 `-no-reboot`와 동등해 추가할 필요 없음.

  **부수 발견(PN-6049A353에도 반영됨)**: 정상적인 SMP4 부팅(크래시
  없음)도 baseline으로 `CPU Reset` 항목을 14건 남긴다(멀티스테이지
  핸드오프 과정에서 vCPU마다 발생하는 정상 노이즈) - 반면 진짜
  Triple Fault는 추가 `CPU Reset` 없이 곧장 `Triple fault` 텍스트로
  빠진다. 즉 **"CPU Reset 여러 건" 자체는 이상 징후 판정 근거로
  쓸 수 없다** - `Triple fault` 로그 줄의 유무 + QEMU 조기 종료
  여부만이 신뢰할 수 있는 신호다. 반대로 로그도 없고 조기 종료도
  없이 그냥 타임아웃까지 조용한 경우(PN-6049A353의 원래 사고처럼)는
  하드웨어 폴트가 아니라 **진짜 소프트웨어 행(hang)/데드락**일
  가능성이 높다 - 이런 경우는 reset/reboot 계열 QEMU 옵션으로는
  절대 감지되지 않으므로, 감지하려면 시리얼 로그를 외부에서 tail
  하며 "기대한 다음 줄이 일정 시간 안 찍히면 정체로 간주"하는 별도
  wrapper가 필요하다(바로 위 §9의 "낮은 재현율 버그 대응" 1단계와 결합
  가능 - 후속 과제, 이 문서가 지금 설계하지 않음).
- `-S`는 실제로 리셋 벡터(`0xfff0`)에서 정지한다(실측 확인) -
  higher-half 전환/페이징 이전의 `.boot` 저지대 코드까지 포함해
  부팅 전체를 처음부터 단일 스텝할 수 있다.
- 최상위 `CMakeLists.txt`가 전역으로 `-g`(DWARF 디버그 정보)를 켜
  둔다 - 런타임 코드 생성에는 영향이 없고(최적화 레벨 미지정 -> 기본
  `-O0`) ELF에 디버그 섹션만 추가한다. `objdump --dwarf=info` 또는
  `file build/minicore.elf`(`with debug_info`가 보이면 정상)로 확인
  가능.
- 재현율이 낮은 버그(PN-584DB994 ~4-6%) 대응 2단계 절차(SP-DABFCF9F
  §4) - **1단계**: 기존 `run-qemu.sh`/`run-grub.sh`(non-gdb)를
  반복 실행하며 로그에서 실패 시그니처(패닉 메시지, 또는 예상 로그
  줄이 안 찍히는 "침묵"도 실패로 간주)를 찾아 재현만 확인한다.
  **2단계**: 재현되면 그 자리에서 `run-*-gdb.sh`로 전환 - 다만 같은
  파라미터로 다시 실행해도 항상 같은 시점에 재현된다는 보장은
  없으므로(QEMU 자체의 벽시계 타이밍 비결정성), 조건부 브레이크포인트
  (`break <함수> if <조건>`)로 특정 상태에서만 멈추게 해 자연 재현을
  기다리며 그 시점을 놓치지 않는다.
- SMP 디버깅 - `-smp N`으로 띄우면 QEMU gdbstub이 vCPU마다 별도 gdb
  스레드로 노출한다 - `info threads`로 코어별 스레드 목록을,
  `thread N`으로 그 코어의 레지스터/스택 컨텍스트로 전환해 확인한다.
