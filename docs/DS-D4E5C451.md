# Minicore 초기 설계 결정 확정 (빌드/부팅/커널서비스/라이선스)

DC-48565C0B / DC-427BB6B2 / DC-5AB13FFC에서 제기된 질의(QU-*)에 대해
설계자가 확정한 결정과 근거를 기록한다. 코딩 컨벤션 세부(헤더 가드,
예외/RTTI, 네이밍)는 RM-23F4B687에 반영했으므로 여기서는 다루지 않는다.

## 빌드 시스템 / 툴체인 / CI (DC-48565C0B)

- **빌드 시스템: CMake** (QU-B14AEB6E).
- **컴파일러: WSL 환경의 clang** — 설치 여부를 먼저 확인하고 그것을
  쓴다(QU-BC00E475). **[교체, 2026-09-17, PN-22E5E9E7 lld PT_TLS
  다중 오브젝트 크기 합산 결함(QU-90A616DA) 대응, 설계자 직접 지시]**
  clang+lld(호스트 배포판이 제공하는 x86_64-unknown-none-elf 프리스탠딩
  타깃 흉내)에서 `/opt/cross`의 **x86_64-elf-gcc 13.2.0 + GNU Binutils
  2.42**(설계자가 이 프로젝트 커널 개발 전용으로 미리 준비해 둔, 실제
  이 타깃 전용 크로스컴파일 툴체인)로 전면 교체 완료(commit `e7943e0`) -
  같은 실제 오브젝트 세트로 lld가 계산 못 하던 `PT_TLS.p_memsz`를
  정확히 계산함을 실측 확인. `-fcoroutines`/`-fno-threadsafe-statics`
  플래그 추가 필요(GCC와 clang의 코드젠 차이), 링커 스크립트에
  `.init_array` 출력 섹션 신설 + 부팅 극초반 순회 호출 추가(방어적).
  cmake/toolchain-x86_64.cmake 참고.
- **CI: 처음엔 로컬 수동 검증만** — 초기 개발 속도 우선, 자동화는
  나중 단계로 미룬다(QU-C7B4B29F).
- **QEMU 부팅 스모크 테스트는 지금부터 스크립트로 자동화**한다 —
  CI 자체는 아직이지만, 로컬에서도 시리얼 로그 확인을 스크립트화해
  QA-26450C3E의 "부팅" 체크리스트를 반복 검증할 수 있게 한다
  (QU-A2D0CDE0).

## 부트 경로 착수 순서 및 부트로더 방식 (DC-427BB6B2)

- **첫 구현 대상: multiboot2**(QU-813EAEE7)였으나, **2026-09-14 설계자
  지시로 Xen PVH로 변경**했다. 실제 구현 중 QEMU의 `-kernel` 멀티부트
  로더가 (a) Multiboot2를 모르고(MB1만 지원, GRUB만 MB2 이해) (b)
  64비트 ELF 자체를 거부해서("give a 32bit one") higher-half 64비트
  커널을 실을 수 없다는 게 실측으로 확인됐다. 게다가 그 우회로
  QEMU의 멀티부트 fast-path를 계속 쓰면 SeaBIOS/펌웨어 단계를 아예
  건너뛰어 이후 ACPI/AHCI/PCIe 구현 때 실제 하드웨어와 다른 전제에서
  개발하게 될 위험도 지적됐다. PVH는 ELF 클래스를 가리지 않고
  QEMU/Xen이 네이티브로 직접 로드하므로 이 문제를 피한다 - SP-8B6B8D25
  §1에 이미 있던 4가지 목표 부팅 경로 중 하나를 먼저 앞당긴 것뿐이라
  범위 자체가 바뀐 건 아니다.
- **multiboot2/GRUB 경로 완료(PL-FC38956C, 2026-09-14, 계획 PN-F027A02D)** - PVH가
  검증해 둔 "GDT 적재/페이지 테이블 구성/long mode 전환/higher-half
  점프" 자산을 `common_32bit_entry`로 뽑아 `pvh_start`/`mb2_start`
  두 진입점이 공유한다. 실제 `grub-mkrescue`로 만든 ISO를 QEMU
  `-cdrom`으로 부팅해 PVH 경로와 100% 동일한 부팅 로그(메모리맵/
  ACPI/LAPIC/IOAPIC/HPET/PCI)로 완주함을 실측 확인 -
  `scripts/run-grub.sh` 신설(관련 코드 관계도 기록: boot.S 참고).
  **BIOS/UEFI 직접 부팅은 계획 PN-7FBF255A로 별도 등록**돼 있다.
- **부트로더는 직접 구현하지 않고 기존 부트로더를 체인로더로 활용**
  한다(QU-42F20587) — 초기 구현 속도 우선. (multiboot2/GRUB는 위처럼
  완료, PVH는 부트로더 자체가 필요 없음 - 하이퍼바이저가 ELF를
  직접 읽는다.)
- **EFI(UEFI)도 자체 .efi를 작성하지 않고 기존 UEFI 부트로더에
  의존**한다(QU-D579D739) — 위 결정과 일관된 선택. (UEFI 직접 부팅
  경로 자체는 아직 미구현 - 계획 PN-7FBF255A 참고.)
- **실측 확인(2026-09-14)**: PVH ELF Note(`Xen`/`XEN_ELFNOTE_PHYS32_ENTRY`)
  + higher-half long mode 부팅 + 시리얼 로그 출력까지 QEMU 8.2.2에서
  성공 검증(QA-26450C3E 갱신).
- **참고 - QEMU 자체 빌드 고려(설계자 언급, 2026-09-14)**: QEMU
  기본 빌드에는 일부 실제 물리 장치(ACPI/AHCI/PCIe 관련 등) 모델이
  없어서, 나중에 필요한 장치 모델을 켠 QEMU를 직접 빌드해야 할 수도
  있다 - 지금 결정한 건 아니고, 해당 장치를 실제로 구현할 시점에
  다시 판단한다.

## 커널 서비스 내부 알고리즘 (DC-5AB13FFC)

- **메모리 할당자**: 관리자(매니저) 본체는 커널에 구현하고, `libkmm`은
  재사용 가능한 알고리즘/자료구조만 제공하는 라이브러리로 둔다. 할당
  알고리즘은 **페이지 단위 + buddy allocator**를 기본으로 하고
  **NUMA**를 고려해 설계한다(QU-F34FF02C).
- **스케줄러**: 코어별 **개별 큐 구조** + **CPU affinity** +
  **CAS(compare-and-swap) 기반 동기화**. 코어간 로드밸런싱은
  **Push/Pull 방식**을 사용한다(QU-C3EC2C63, 계획 PN-7679813D).
- **IPC 메시지 포맷**: **raw binary**(별도 직렬화 포맷 없음)
  (QU-AB52C251).
- **프로세스간 "공개 인터페이스" registry / 제어 채널 프로토콜**:
  지금 확정하지 않고 **구현하면서 추가 설계로 계속 보강**한다
  (QU-6EEFDBEE) — 아직 열린 설계 영역이다(계획 PN-268F062B).
- **procfs 스키마**: 위와 동일하게 **구현하면서 추가 설계로 계속
  보강**한다(QU-4B14289E) — 아직 열린 설계 영역이다(계획 PN-48F0F90C).
- **devmgr 드라이버 모델**: devmgr은 "커널 서비스"로 분류되지만
  **실제로는 유저랜드에서 동작**한다. 커널은 devmgr에게 **필수적인
  IO 처리만 위임**하고 나머지 드라이버 로직은 유저랜드 devmgr이
  담당한다(QU-462F6D89).
- **"커널 서비스" 전체의 실행 특권 경계 (2026-09-13, 설계자 확정 —
  devmgr 답변의 일반화)**: 위 devmgr 원칙은 devmgr만의 예외가 아니라
  **모든 "커널 서비스"(devmgr/fs/net/tty)에 공통으로 적용되는
  원칙**이다. 커널 영역(ring 0)에서 구동되는 것은 `minicore/kernel`
  (커널 그 자체) 하나뿐이고, "커널 서비스"는 이름과 무관하게 전부
  유저랜드에서 구동되며 커널이 그 위에 대한 통제권만 쥔다. SP-8B6B8D25
  §2-A에 반영함.

## 인터럽트/타이머/SMP 대비 (2026-09-14, 설계자 지시 - "인터럽트 처리와 커널 타이머, SMP 부팅을 고려")

- **레거시 PIC(8259) 대신 처음부터 Local APIC를 쓴다.** SMP에서는
  코어마다 자기 LAPIC이 있어야 코어별 타이머/IPI(코어간 인터럽트)가
  가능하고, PIC은 애초에 코어를 지정해 인터럽트를 줄 수 없다 - PIC은
  전부 마스크해 완전히 죽여 둔다.
- **커널 타이머는 LAPIC 타이머**(코어 내장, PIC/IOAPIC 불필요)를
  PIT 채널2로 보정해 100Hz 주기로 프로그래밍한다. **IOAPIC 완료
  (PL-2D149D8F, 2026-09-14, 계획 PN-18810901)** - 외부 장치 IRQ 라우팅이 실제로
  동작함을 실측 확인(키보드 IRQ1 검증).
- **ACPI(RSDP→RSDT/XSDT→MADT)를 이 시점에 파싱한다**(설계자 지시 -
  "ACPI도 지금 단계에서 고려"). MADT에서 로컬 APIC 주소, 코어별
  APIC ID 목록, I/O APIC 주소까지 뽑아낸다 - SMP를 하려면 코어가
  몇 개고 APIC ID가 뭔지부터 알아야 하기 때문. QEMU 기본(코어 1개)
  환경에서 실측 확인(2026-09-14).
- **실제 AP(나머지 코어) 기동(INIT-SIPI-SIPI + 16비트 트램폴린)은
  아직 범위 밖이다** - 이번 마일스톤은 "SMP를 고려한 설계"(LAPIC
  선택, ACPI로 코어 목록 확보)까지이고, 실제 멀티코어 부팅은
  PL-65C20380으로 계획을 남겨뒀다(누락이 아니라 의도적 범위 구분,
  이후 계획 PN-BBF6CA37로 완료됨 - 동시(병렬) 기동만 PN-9CB69731로
  별도 남음). **그 계획의 0단계로 최소 스핀락/원자 연산 프리미티브를 먼저 만들기로
  확정**했다(QU-B97FDA44, 2026-09-14) - 지금 커널엔 동시성 제어가
  전혀 없어 코어가 2개 이상 돌면 공유 자료구조가 안전하지 않다.
- **libkenv/libs/x86_64의 네임스페이스는 `kernel::arch`로 확정**했다
  (QU-4606360C, 2026-09-14) - 유저랜드 프로세스가 커널과의 통신/권한
  처리 후 IO 권한을 얻으면 이 라이브러리를 그대로 링크해 직접 포트
  IO를 할 수 있게 하려는 의도.
- **MSI 완료(PL-2070E6EF, 2026-09-14, 계획 PN-4F901387)** - PCI 설정 공간 접근을
  0단계로 새로 구현(`pci.h/.cpp`, 레거시 포트 0xCF8/0xCFC)한 뒤,
  Capabilities List에서 MSI capability를 찾아 Message Address/Data를
  프로그래밍한다. IOAPIC이 만든 벡터-콜백 표(`Idt::registerHandler`)를
  그대로 재사용 - QEMU의 교육용 PCI 장치 `edu`로 실제 MSI 인터럽트가
  등록한 벡터로 들어옴을 실측 확인. **MSI-X는 이후 재작업으로 함께
  구현 완료됨**(PL-2070E6EF 참고).
- **x2APIC 완료(PL-D65F49CC, 2026-09-14, 계획 PN-B39C2E12)** - `Lapic`이 CPUID.01H:ECX
  비트21로 x2APIC 지원을 감지해 있으면 MSR 기반 접근으로, 없으면
  기존 xAPIC(MMIO)으로 폴백한다. `-accel kvm -cpu host`(실제
  하드웨어 가상화)로 x2APIC 모드 전환 자체가 정상 동작함을 실측
  확인 - 순수 소프트웨어 에뮬레이션(TCG)은 x2APIC을 아예 지원하지
  않는다는 것도 QEMU 자체 경고로 확인됨(코드 문제 아님, 관계도 기록).
- **레거시 PIC은 완전히 마스크하되, 반드시 리매핑도 해 둔다**(설계자
  지적, 2026-09-14) - 마스크만 하고 벡터를 그대로 두면(기본 IRQ0-7이
  0x08-0x0F, CPU 예외 벡터와 정확히 겹침) 드물게 새어 나오는 spurious
  PIC 인터럽트(레거시 IRQ7/15)가 진짜 CPU 예외로 오진될 수 있다.
  0xE0(마스터)/0xE8(슬레이브)로 리매핑해 우리 벡터(0-31 예외, 32
  타이머, 0xFF spurious) 전부와 안 겹치게 해 뒀다(실제로 수정 반영,
  2026-09-14).
- **HPET 완료(PL-E68894CD, 2026-09-14, 계획 PN-5DDCF618)** - 확정된 역할대로(QU-8E14D3D9)
  HPET을 스케줄러 기본 시간원으로, LAPIC 타이머(PIT 보정)는 fallback
  으로 유지한다. `Timer::init()`이 `Acpi::hasHpet() && Hpet::init()`
  성공 여부로 자동 분기 - HPET 있는 QEMU 기본 환경/강제 비활성화
  (`-machine pc,hpet=off`) 둘 다 실측 검증(회귀 없음). 멀티코어
  환경에서 전역 카운터인 HPET과 코어별 LAPIC 타이머가 스케줄러
  틱으로서 정확히 어떻게 공존하는지는 여전히 스케줄러 설계 시점에
  구체화하기로 미룸(PL-E68894CD §5, 코어별 독립 틱 연동은 계획
  PN-04258584로 별도 남음).
