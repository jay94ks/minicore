## 배경

설계자 지시(2026-09-14):

> "모든 Syscall은 커널이 받아서 그걸 각 `커널 서비스`에 연산을 위임하는
> 형태를 기본으로 하되, 커널 내에서 처리를 완료할 수 있는 것들은
> `커널`이 직접 처리하여 반환하라. 또한, Syscall 또한 비동기 방식으로
> 구현되어야 하며, 1) 유저랜드에서 정수 기반 syscall 엔드포인트 번호
> + args로 syscall. 2) 커널랜드에서 해당 Syscall을 비동기 작업자에게로
> push하며 해당 쓰레드 혹은 프로세스를 블로킹 처리한다. 예외 상황
> 처리: 1) 대상이 완료 전 종료되면 취소/폐기. 2) 완료 전 블로킹이
> 풀리면 push가 반환한 추적 토큰으로 다시 블로킹. 3) 추적 토큰은
> 쓰레드별로 관리된다."

이후 두 차례 후속 지시로 아래 설계가 확정/개정됐다(각 절에 반영):

- **[2026-09-14] Task ≠ 스레드 용어 정정**: "커널 Task와 쓰레드는
  다른 개념이다. 커널 Task는 커널 수준의 쓰레드이고, 그냥 `쓰레드`
  라고 함은, 유저 프로세스의 하위 개념인 `쓰레드`이므로 이부분을
  명확히 구분해야 한다. 내부적으로 Task를 상속받아 유저 쓰레드를
  구현해도 상관은 없다." - §"Task와 UserThread" 참고.
- **[2026-09-14, DC-D868D9EC/QU-EF643652 답변]**: 1) syscall 명령과
  레거시 `int 0x80`류 게이트 **둘 다** 계획. 2) `AsyncTaskHandler::
  onCancel` 추가 **승인**(SP-F682B889에 이미 반영 완료). 3) "syscall
  -> 추적코드 즉시 반환, waitForSyscall -> 추적코드의 완료를 대기"
  형태로 설계 - §"제출/대기 분리(submit/wait)" 이하 전면 개정.

이 요구사항은 전부 이미 확정된 다음 설계 위에 얹을 수 있다 - 새
병렬 메커니즘을 만들지 않고 기존 것을 재사용하는 것이 이 제안의
핵심이다:

- **SP-F682B889(비동기 프레임워크)** - `AsyncTask`/`AsyncTaskHandler`
  /`AsyncReactor`가 이미 "요청을 큐에 넣고, 완료되면 콜백"이라는
  정확히 필요한 형태를 갖추고 있다. "비동기 작업자에게 push"는 곧
  `AsyncReactor`의 실행 큐에 `AsyncTask`를 넣는 것이다.
- **PL-2D3184BC §6/8(스케줄러 블로킹/웨이크업)** - "범용 block API는
  비공개, 기능별 전용 API로 노출"이 이미 원칙으로 확정돼 있고, 8번
  항목이 "첫 소비자가 생길 때 노출"이라고 자리를 비워 뒀다 - **이
  Syscall 서브시스템이 바로 그 첫 소비자다.**
- **SP-8B6B8D25 §2-A/§3** - "커널 서비스"(devmgr/fs/net/tty)는 전부
  유저랜드에서 도는 별도 프로세스이고, 커널은 그 위의 통제권만 쥔다.
  따라서 "커널 서비스에게 위임"은 곧 **다른 프로세스와의 IPC**이고,
  본 제안과 짝을 이루는 **SP-1FBC0EEB(메시징 채널 IPC)**가 그 위임
  경로 자체를 구현한다.
- **DS-D4E5C451(IPC 포맷)** - "IPC 메시지 포맷: raw binary"가 이미
  확정돼 있다 - syscall args/결과 마샬링도 이 규칙을 따른다.

## Task와 UserThread (용어 정정, 2026-09-14)

`kernel::Task`(PL-2D3184BC)는 **커널 수준의 실행 단위**다 - 스케줄러
리액터 Task처럼 커널 자신의 내부 동시성에도 쓰이고, 유저 스레드의
커널 쪽 표현이기도 하다. 하지만 **"쓰레드"는 유저 프로세스의 하위
개념**이라 `Task`와 동일시하면 안 된다 - 이 문서가 이전 버전에서
"호출한 `kernel::Task`(스레드)"라고 쓴 표현은 부정확했다.

이 제안은 `Task`를 상속해 유저 스레드 전용 상태를 얹은
`kernel::UserThread`를 도입한다(설계자 지시 - "내부적으로 Task를
상속받아 유저 쓰레드를 구현해도 상관없다"):

```cpp
namespace kernel {

// 유저 프로세스에 속한 스레드의 커널 쪽 표현 - 스케줄링 가능 단위로는
// Task 그대로지만, syscall 진입/추적 토큰처럼 "유저 프로세스의
// 스레드"에게만 의미 있는 상태를 여기 추가한다. 커널 자신이 쓰는
// Task(리액터 Task 등)는 이 서브클래스가 아니다 - syscall을 낼 일이
// 없으므로 아래 필드가 필요 없다.
class UserThread : public Task {
public:
    // 대기 중인 syscall 하나(§"제출/대기 분리" 참고) - 한 스레드는
    // 한 번에 최대 하나만 가질 수 있다(동기적 모델 - 대기 중엔 그
    // 스레드 자체가 실행되지 않는다). 대기 중이 아니면 비어 있음.
    struct PendingSyscall {
        SyscallEndpointId endpoint;
        AsyncTaskManageCode token;
        bool valid = false;
    };
    PendingSyscall pendingSyscall;
};

}  // namespace kernel
```

아래 모든 절에서 "호출 스레드"는 전부 이 `UserThread`를 가리킨다.
(`UserThread`라는 이름 자체는 이 제안의 제안일 뿐 확정된 이름은
아니다 - 프로세스/스레드 모델을 실제로 설계할 때 최종 확정한다.)

## 설계 원칙

1. **모든 syscall은 예외 없이 커널을 거친다** - 유저랜드가 커널
   서비스와 직접 통신할 방법은 없다(SP-8B6B8D25 §2-A와 일관).
2. **완결 가능한 syscall은 커널이 직접 처리** - "커널이 직접 처리"와
   "커널 서비스에 위임"은 **같은 `AsyncTaskHandler::onExec` 안에서
   갈리는 구현 선택**일 뿐, 유저랜드나 스케줄러 입장에서는 완전히
   같은 경로(제출 → 완료 → 대기 중이던 스레드가 있으면 깨움)를
   탄다 - 프레임워크 차원에서 "직접 처리 syscall"과 "위임 syscall"을
   구분하는 별도 코드 경로를 두지 않는다.
3. **비동기 프레임워크를 그대로 재사용** - 새 "비동기 작업자" 개념을
   만들지 않는다. syscall 하나 = `AsyncTask` 하나, syscall 핸들러 =
   `AsyncTaskHandler` 하나.
4. **추적 토큰은 스레드(`UserThread`) 소유** - 전역 테이블이 아니라
   호출한 `UserThread` 자신의 `pendingSyscall` 필드에 저장한다 - 한
   스레드는 한 번에 최대 하나의 syscall만 대기할 수 있으므로 테이블
   검색이 필요 없다.

## 유저랜드 ABI - syscall 명령 + 레거시 int 게이트 둘 다 지원(확정)

```
submitId = syscall(endpointId: uint32_t, args: <레지스터 또는 포인터>) -> AsyncTaskManageCode
result   = waitForSyscall(token: AsyncTaskManageCode) -> result
```

- **트랩 경로 두 가지를 모두 구현한다**(설계자 지시, 2026-09-14 -
  "syscall과 legacy 호환으로 int 0x80류 둘다 계획하라"):
  1. x86_64 `syscall` 명령(빠른 시스템 콜, MSR `STAR`/`LSTAR`/`SFMASK`
     설정 필요) - 주 경로.
  2. 레거시 `int 0x80`류 소프트웨어 인터럽트 게이트 - 호환/폴백 경로.
     이 게이트는 **DPL=3**으로 설정해야 링3에서 `int`로 진입 가능하다
     - `idt.cpp`의 `kSetGate`가 지금은 모든 게이트에 DPL=0을 고정
     박아 두므로(`kInterruptGateTypeAttr = 0x8E`), 이 벡터 하나만
     DPL을 다르게 설정할 수 있는 경로가 구현 시 필요하다(설계
     수준의 메모, 정확한 구현은 PL에서).
  - 두 경로 모두 **같은 내부 디스패치**(아래 "커널 진입 흐름")로
    합류한다 - 레지스터 인자 규약도 두 경로가 동일하게 맞춘다.
- `endpointId`는 커널이 부팅 시 고정 배정하는 정수(§"SyscallRegistry"
  참고) - 동적 재배정 없음(공개 ABI이므로 커널 버전이 바뀌어도 같은
  번호가 같은 의미를 유지해야 한다).
- 어느 경로든 진입 시 링3→링0 전환이 일어나므로 **TSS.RSP0**
  (SP-677210E6에서 이미 자리만 잡아 두고 "유저랜드 syscall 진입점을
  만들 때 채운다"고 명시한 그 필드)를 이 시점에 채워야 한다 - 이
  제안이 바로 그 소비자다.
- 인자 전달은 이 프로젝트가 이미 확정한 "raw binary" 원칙(DS-D4E5C451)
  대로, 레지스터 몇 개 + 필요시 유저 메모리의 raw 바이트 블록을
  가리키는 포인터로 마샬링한다.

## 제출/대기 분리(submit/wait) - 확정 설계

**설계자 지시(2026-09-14, QU-EF643652)로 원래 제안("syscall 한 번에
제출+블로킹")을 다음과 같이 개정한다**: "syscall -> 추적코드 즉시
반환, waitForSyscall -> 추적코드의 완료를 대기." 즉 syscall 자체는
**블로킹하지 않는다** - `AsyncTask`를 만들어 제출하고 추적 토큰을
즉시 돌려준다. 실제 블로킹은 별도의 `waitForSyscall` 호출이 담당한다.

이 분리가 예외 상황 처리를 단순하게 만든다 - 원래 별도 설계가
필요할 것으로 예상했던 "재블로킹(rejoin)"이 **그냥 `waitForSyscall
(token)`을 다시 부르는 것**과 동일해진다(별도 `SYS_REJOIN` endpoint
불필요 - DC-D868D9EC 3번 항목이 이렇게 해소됨). 일반적인 "동기적으로
보이는" syscall을 원하는 유저랜드 라이브러리 스텁은 `syscall()` 직후
바로 `waitForSyscall()`을 호출하는 두 단계를 하나로 감싸면 된다 -
커널은 항상 이 두 단계만 제공하고, "동기처럼 보이게 감싸는 것"은
유저랜드 라이브러리의 몫이다.

## SyscallRegistry - `AsyncCallbackRegistry`와 분리된 고정 슬롯 테이블

`AsyncCallbackRegistry`(SP-F682B889 §3.1)는 `subjectCode`를 **동적
으로 할당**해 반환한다 - 내부 구현 세부이므로 부팅 순서가 바뀌면
값도 바뀔 수 있다. 반면 syscall `endpointId`는 **공개 ABI**라 고정
값이어야 한다. 그래서 별도의 고정 슬롯 테이블을 둔다:

```cpp
namespace kernel {

using SyscallEndpointId = uint32_t;

// endpointId는 스펙으로 미리 정해 둔 고정값 - 배열 인덱스로 그대로
// 쓴다(Idt의 벡터 배열과 같은 패턴). 등록 시 이미 채워진 슬롯에
// 다시 등록하면 실패(설계 실수 조기 발견용).
class SyscallRegistry {
public:
    static bool registerHandler(SyscallEndpointId id, AsyncTaskHandler* handler);
    static AsyncTaskHandler* resolve(SyscallEndpointId id);  // 없으면 nullptr
};

}  // namespace kernel
```

이 핸들러가 "커널이 직접 처리"하는 syscall이면 `onExec` 안에서 바로
연산을 끝내고 결과를 채운 뒤 반환한다(완료 즉시 대기 중이던
`waitForSyscall` 호출이 있으면 깨운다 - 아래 "완료/응답 흐름" 참고).
"커널 서비스에 위임"하는 syscall이면 `onExec`이 **SP-1FBC0EEB(메시징
채널 IPC)**로 그 서비스에게 요청을 보내고 즉시 `AsyncTask::yield()`
로 리액터에 제어를 돌려준다 - 나중에 서비스의 응답이 채널의 `read`
완료로 도착하면(그 자체가 또 하나의 `AsyncTask` 완료), 그 완료
콜백이 원래 syscall의 `AsyncTask`를 재개시켜 결과를 채우고 완료
처리한다.

## 커널 진입 흐름

### `syscall(endpointId, args) -> token`

1. 트랩 핸들러(§"유저랜드 ABI"의 두 경로 중 하나)가 `endpointId`+
   args를 읽는다.
2. `SyscallRegistry::resolve(endpointId)` - 없으면 즉시 실패 반환
   (블로킹 없음 - 잘못된 endpoint 번호는 그 자리에서 에러).
3. `AsyncTask`를 하나 만든다(Slab 할당, SP-D7013B26) -
   `subjectCode`=`endpointId`, `manageCode`=새로 발급한 추적 토큰,
   `args`=마샬링된 인자.
   - **Slab 고갈 시**: `AsyncTask` 자체를 못 만들었으므로 즉시
     "일시적으로 자원이 없음" 에러를 유저랜드에 돌려준다(재시도는
     유저랜드 몫 - 유저랜드가 아직 없어 정확한 에러 값 체계는
     이번 범위 밖).
4. 호출한 `UserThread` 자신의 `pendingSyscall`에 `{endpoint, token,
   valid=true}`를 기록한다.
5. `AsyncReactor`의 이 코어 실행 큐에 `AsyncTask`를 제출한다
   (SP-F682B889 §3.4의 `submitCompletion`을 그대로 쓴다).
6. **블로킹 없이** 토큰을 유저랜드에 즉시 반환한다.

### `waitForSyscall(token) -> result`

1. 호출한 `UserThread`의 `pendingSyscall`을 확인한다 - `valid`가
   `false`이거나 `token`이 일치하지 않으면 즉시 실패(자기 것이
   아니거나 이미 완료 처리된 토큰 - 전역 검색 없이 자기 자신의
   필드와만 비교하므로 위조/타인 토큰은 여기서 걸러진다).
2. 이미 완료돼 있으면(`AsyncTask::state`가 `Completed`/`Failed`)
   즉시 결과를 반환한다 - 블로킹하지 않는다.
3. 아직 완료 전이면 새 전용 API `Syscall::blockCurrentUntil(token)`
   으로 현재 스레드를 재운다 - 내부적으로 스케줄러의 비공개 block
   프리미티브를 쓴다(PL-2D3184BC §6 원칙 그대로, `Ipc::waitForReply`
   예시와 동일한 위치의 새 소비자). **이 호출이 어떤 이유로든
   완료 전에 풀려도**(설계자 지시 2번 - 이 프로젝트에 아직 설계
   되지 않은 시그널 등, SP-8B6B8D25 §2 11번 참고), 유저랜드는 그냥
   같은 `token`으로 `waitForSyscall`을 **다시 호출**하면 된다 - 1번
   단계가 여전히 유효한 토큰임을 확인해 주므로 별도 재합류 API가
   필요 없다.

## 완료/응답 흐름

`AsyncTask`가 완료(성공/실패 불문)되면, 그 결과를 `AsyncTask` 자신
(또는 그 `args`)에 보관해 둔다. 그 시점에 어떤 스레드가
`waitForSyscall(token)`으로 블로킹 중이었다면(대응하는 `UserThread::
pendingSyscall.token`이 일치) 스케줄러의 비공개 wake 프리미티브로
그 스레드를 깨운다 - 아직 아무도 기다리고 있지 않았다면(예: syscall만
하고 아직 `waitForSyscall`을 안 부른 경우) 그냥 완료 상태로 남아
있다가, 나중에 `waitForSyscall`이 호출되면 위 "이미 완료돼 있으면"
경로로 즉시 반환된다.

## 종료 시 취소 처리 (확정 - SP-F682B889 개정 완료)

대상 스레드(`UserThread`) 또는 그 프로세스 전체가 종료될 때,
`pendingSyscall.valid`가 `true`면 그 `AsyncTask`를 취소해야 한다.
**SP-F682B889에 `AsyncTaskHandler::onCancel`을 추가하는 개정이
승인·반영됐다**(DC-D868D9EC/QU-EF643652) - 각 syscall 핸들러는
`onExec`/`onFailure`와 마찬가지로 `onCancel`도 구현해야 하며, 서비스에
위임 중이었다면 그 채널 요청(SP-1FBC0EEB)도 여기서 함께 정리한다.

Task/프로세스 종료 경로(아직 미구현 - PL-2D3184BC에도 없음)가 이
`onCancel`을 호출하는 지점을 가져야 한다 - 정확한 종료 시퀀스는
프로세스 종료 자체를 설계할 때 확정한다(이번 제안은 "그 시점에
`onCancel`이 있어야 한다"는 요구사항만 명시).

## 기존 설계에 미치는 영향 (요약)

| 문서 | 영향 |
|---|---|
| SP-F682B889(비동기 프레임워크) | `AsyncTaskHandler`에 `onCancel` 추가 - **반영 완료**. |
| PL-2D3184BC(스케줄러) §2 | Task PCB의 "블로킹 사유" 자리는 `UserThread::pendingSyscall`로 구체화(단, 이 필드는 `Task` 자체가 아니라 `UserThread` 서브클래스에 있음 - 위 "Task와 UserThread" 참고). |
| PL-2D3184BC §6/8 | "블로킹/웨이크업 첫 소비자"가 이 Syscall 서브시스템으로 확정됨 - `Syscall::blockCurrentUntil`/wake 전용 API가 그 자리를 채운다. |
| SP-677210E6(TSS/IST) | RSP0 필드의 첫 실사용처가 이 syscall 트랩 진입 경로로 확정됨. |
| idt.cpp | 레거시 `int 0x80`류 게이트는 DPL=3이 필요 - 현재 `kSetGate`가 모든 게이트를 DPL=0으로 고정하므로 이 벡터만 예외 처리하는 경로가 구현 시 필요. |

## 남은 사항 (DC-D868D9EC 전부 해소됨 - 참고용 기록)

DC-D868D9EC의 세 항목은 위 답변으로 모두 결정됐다:
1. syscall 명령 + int 게이트 둘 다 구현.
2. `onCancel` 추가 승인, SP-F682B889에 반영 완료.
3. 별도 rejoin endpoint 불필요 - submit/wait 분리 자체가 재블로킹을
   흡수한다.

새로 열린 세부는 없음 - 남은 것은 전부 구현 단계(PL)에서 실측하며
확정할 수준(예: int 게이트의 정확한 벡터 번호, MSR 설정값).
