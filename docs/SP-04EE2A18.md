## 배경

설계자 지시(2026-09-14):

> "모든 Syscall은 커널이 받아서 그걸 각 `커널 서비스`에 연산을 위임하는
> 형태를 기본으로 하되, 커널 내에서 처리를 완료할 수 있는 것들은
> `커널`이 직접 처리하여 반환하라. 또한, Syscall 또한 비동기 방식으로
> 구현되어야 하며, 1) 유저랜드에서 정수 기반 syscall 엔드포인트 번호
> + args로 syscall. 2) 커널랜드에서 해당 Syscall을 비동기 작업자에게로
> push하며 해당 쓰레드 혹은 프로세스를 블로킹 처리한다. 예외 상황
> 처리: 1) 대상이 완료 전 종료되면 취소/폐기. 2) 완료 전 블로킹이
> 풀리면 push가 반환한 추적 토큰으로 다시 블로킹. 3) 추적 토큰은
> 쓰레드별로 관리된다."

이 요구사항은 전부 이미 확정된 다음 설계 위에 얹을 수 있다 - 새
병렬 메커니즘을 만들지 않고 기존 것을 재사용하는 것이 이 제안의
핵심이다:

- **SP-F682B889(비동기 프레임워크)** - `AsyncTask`/`AsyncTaskHandler`
  /`AsyncReactor`가 이미 "요청을 큐에 넣고, 완료되면 콜백"이라는
  정확히 필요한 형태를 갖추고 있다. "비동기 작업자에게 push"는 곧
  `AsyncReactor`의 실행 큐에 `AsyncTask`를 넣는 것이다.
- **PL-2D3184BC §6/8(스케줄러 블로킹/웨이크업)** - "범용 block API는
  비공개, 기능별 전용 API로 노출"이 이미 원칙으로 확정돼 있고, 8번
  항목이 "첫 소비자가 생길 때 노출"이라고 자리를 비워 뒀다 - **이
  Syscall 서브시스템이 바로 그 첫 소비자다.**
- **SP-8B6B8D25 §2-A/§3** - "커널 서비스"(devmgr/fs/net/tty)는 전부
  유저랜드에서 도는 별도 프로세스이고, 커널은 그 위의 통제권만 쥔다.
  따라서 "커널 서비스에게 위임"은 곧 **다른 프로세스와의 IPC**이고,
  본 제안과 짝을 이루는 **SP-1FBC0EEB(메시징 채널 IPC)**가 그 위임
  경로 자체를 구현한다.
- **DS-D4E5C451(IPC 포맷)** - "IPC 메시지 포맷: raw binary"가 이미
  확정돼 있다 - syscall args/결과 마샬링도 이 규칙을 따른다.

## 설계 원칙

1. **모든 syscall은 예외 없이 커널을 거친다** - 유저랜드가 커널
   서비스와 직접 통신할 방법은 없다(SP-8B6B8D25 §2-A와 일관).
2. **완결 가능한 syscall은 커널이 직접 처리** - "커널이 직접 처리"와
   "커널 서비스에 위임"은 **같은 `AsyncTaskHandler::onExec` 안에서
   갈리는 구현 선택**일 뿐, 유저랜드나 스케줄러 입장에서는 완전히
   같은 경로(push → block → 완료 → wake)를 탄다 - 프레임워크 차원에서
   "직접 처리 syscall"과 "위임 syscall"을 구분하는 별도 코드 경로를
   두지 않는다.
3. **비동기 프레임워크를 그대로 재사용** - 새 "비동기 작업자" 개념을
   만들지 않는다. syscall 하나 = `AsyncTask` 하나, syscall 핸들러 =
   `AsyncTaskHandler` 하나.
4. **추적 토큰은 스레드(Task) 소유** - 전역 테이블이 아니라 호출한
   `kernel::Task`(PL-2D3184BC 확정 용어) 자신의 PCB 필드에 저장한다
   - 한 스레드는 한 번에 최대 하나의 syscall만 대기할 수 있으므로
   (동기적 블로킹 syscall 모델 - 대기 중엔 그 스레드가 아예 실행되지
   않는다) 슬롯 하나면 충분하고, 테이블 검색이 필요 없다.

## 유저랜드 ABI (제안 - 확인 필요, §"결정이 필요한 사항" 참고)

```
syscall(endpointId: uint32_t, args: <레지스터 또는 포인터>) -> result
```

- `endpointId`는 커널이 부팅 시 고정 배정하는 정수(§"SyscallRegistry"
  참고) - 동적 재배정 없음(공개 ABI이므로 커널 버전이 바뀌어도 같은
  번호가 같은 의미를 유지해야 한다).
- x86_64에서는 `syscall` 명령(빠른 시스템 콜) 또는 `int 0x80`류 게이트
  둘 다 후보다 - 어느 쪽이든 진입 시 링3→링0 전환이 일어나므로
  **TSS.RSP0**(SP-677210E6에서 이미 자리만 잡아 두고 "유저랜드
  syscall 진입점을 만들 때 채운다"고 명시한 그 필드)를 이 시점에
  채워야 한다 - 이 제안이 바로 그 소비자다.
- 인자 전달은 이 프로젝트가 이미 확정한 "raw binary" 원칙(DS-D4E5C451)
  대로, 레지스터 몇 개 + 필요시 유저 메모리의 raw 바이트 블록을
  가리키는 포인터로 마샬링한다.

## SyscallRegistry - `AsyncCallbackRegistry`와 분리된 고정 슬롯 테이블

`AsyncCallbackRegistry`(SP-F682B889 §3.1)는 `subjectCode`를 **동적
으로 할당**해 반환한다 - 내부 구현 세부이므로 부팅 순서가 바뀌면
값도 바뀔 수 있다. 반면 syscall `endpointId`는 **공개 ABI**라 고정
값이어야 한다. 그래서 별도의 고정 슬롯 테이블을 둔다:

```cpp
namespace kernel {

using SyscallEndpointId = uint32_t;

// endpointId는 스펙으로 미리 정해 둔 고정값 - 배열 인덱스로 그대로
// 쓴다(Idt의 벡터 배열과 같은 패턴). 등록 시 이미 채워진 슬롯에
// 다시 등록하면 실패(설계 실수 조기 발견용).
class SyscallRegistry {
public:
    static bool registerHandler(SyscallEndpointId id, AsyncTaskHandler* handler);
    static AsyncTaskHandler* resolve(SyscallEndpointId id);  // 없으면 nullptr
};

}  // namespace kernel
```

이 핸들러가 "커널이 직접 처리"하는 syscall이면 `onExec` 안에서 바로
연산을 끝내고 결과를 채운 뒤 반환한다(반환 즉시 리액터가 이 `AsyncTask`
를 완료 처리 - 아래 "완료/응답 흐름" 참고). "커널 서비스에 위임"하는
syscall이면 `onExec`이 **SP-1FBC0EEB(메시징 채널 IPC)**로 그 서비스에게
요청을 보내고 즉시 `AsyncTask::yield()`로 리액터에 제어를 돌려준다 -
나중에 서비스의 응답이 채널의 `recv` 완료로 도착하면(그 자체가 또
하나의 `AsyncTask` 완료), 그 완료 콜백이 원래 syscall의 `AsyncTask`
를 재개시켜 결과를 채우고 완료 처리한다.

## 커널 진입 흐름

1. 트랩 핸들러가 `endpointId`+args를 읽는다.
2. `SyscallRegistry::resolve(endpointId)` - 없으면 즉시 실패 반환
   (블로킹 없음 - 잘못된 endpoint 번호는 그 자리에서 에러).
3. `AsyncTask`를 하나 만든다(Slab 할당, SP-D7013B26) -
   `subjectCode`=`endpointId`, `manageCode`=새로 발급한 추적 토큰,
   `args`=마샬링된 인자.
   - **Slab 고갈 시**: `AsyncTask` 자체를 못 만들었으므로 블로킹
     없이 즉시 "일시적으로 자원이 없음" 에러를 유저랜드에 돌려준다
     (재시도는 유저랜드 몫 - 유저랜드가 아직 없어 정확한 에러 값
     체계는 이번 범위 밖).
4. 호출한 `kernel::Task`(현재 스레드) 자신의 PCB에 추적 토큰을
   기록한다(§"추적 토큰과 재블로킹" 참고).
5. `AsyncReactor`의 이 코어 실행 큐에 `AsyncTask`를 제출한다(신규
   제출도 "완료 후 재개"와 같은 큐잉 경로 - SP-F682B889 §3.4의
   `submitCompletion`을 그대로 쓴다, 이름과 달리 "이 AsyncTask를
   실행 가능 상태로 큐에 넣는다"는 뜻이라 신규/재개 구분이 없다).
6. 새 전용 API `Syscall::blockCurrentUntil(token)`으로 현재 Task를
   재운다 - 내부적으로 스케줄러의 비공개 block 프리미티브를 쓴다
   (PL-2D3184BC §6 원칙 그대로, `Ipc::waitForReply` 예시와 동일한
   위치의 새 소비자).

## 완료/응답 흐름

`AsyncTask`가 완료(성공/실패 불문)되면, 그 `manageCode`(추적 토큰)로
원래 호출한 `kernel::Task`를 식별해(PCB에 저장해 둔 토큰과 대조)
결과를 그 Task가 볼 수 있는 곳(예: 유저 스택/레지스터 이미지)에
쓰고 스케줄러의 비공개 wake 프리미티브로 깨운다. 깨어난 Task는
`sysret`/`iretq`로 유저랜드에 결과와 함께 복귀한다.

## 추적 토큰과 재블로킹(rejoin)

- 토큰은 **`kernel::Task`(스레드) 스코프**로만 유일하면 된다(설계자
  지시 3번) - 전역 유일성 불필요. 가장 간단한 구현은 그 Task 안의
  단조 증가 카운터, 또는 `AsyncTask`의 `manageCode` 값을 그대로
  토큰으로 재사용(추가 매핑 테이블 없이 끝남 - 권장).
- `kernel::Task` PCB에 필드 추가 제안: `pendingSyscall`(옵션 타입 -
  `{ SyscallEndpointId endpoint; AsyncTaskManageCode token; }`,
  대기 중이 아니면 비어 있음) - PL-2D3184BC §2가 이미 "블로킹 사유"
  자리를 PCB에 예약해 뒀으므로, 그 필드를 이 구조체로 구체화하는
  것을 제안한다(아래 "기존 설계에 미치는 영향" 참고).
- **재블로킹 진입점**: 완료 전에 블로킹이 풀리는 원인(시그널 등,
  아직 이 프로젝트에 설계되지 않음 - SP-8B6B8D25 §2 11번 "시그널
  전파"가 아직 열린 영역)은 이번 제안 범위 밖으로 두고, "어떤 이유로든
  깨어났는데 아직 안 끝났으면"이라는 조건만 다룬다. 유저랜드는 일반
  `syscall` 진입점과는 **별도의 고정 endpoint**(`SYS_REJOIN`류, 정확한
  번호는 유저랜드 ABI 확정 시 배정)를 호출해 `pendingSyscall.token`을
  넘긴다 - 커널은 **현재 Task 자신의 PCB에 저장된 토큰과만 비교**
  하므로(전역 검색 없음) 위조된/남의 토큰을 넘겨도 그 Task 소유가
  아니면 즉시 거부된다. 일치하면 새 `AsyncTask`를 만들지 않고
  그대로 다시 블로킹만 한다.

## 종료 시 취소 처리

대상 스레드(`kernel::Task`) 또는 그 프로세스 전체가 종료될 때, PCB의
`pendingSyscall`이 비어 있지 않으면 그 `AsyncTask`를 취소해야 한다.
**이건 SP-F682B889가 다루지 않은 경우다** - 현재 `AsyncTaskHandler`
인터페이스는 `onExec`/`onFailure` 둘뿐이고, "이미 실행 중이거나
대기 중인 작업을 외부에서 강제 종료"하는 경로가 없다. 다음과 같은
확장을 제안한다(SP-F682B889에 대한 개정 - 설계자 확인 필요, §"결정이
필요한 사항" 참고):

```cpp
class AsyncTaskHandler {
public:
    virtual ~AsyncTaskHandler() = default;
    virtual void onExec(AsyncTask* task, void* args) = 0;
    virtual void onFailure(AsyncTask* task) = 0;
    // 신규 제안: 이 작업의 소유 스레드/프로세스가 완료 전에 종료돼
    // 강제로 취소될 때 호출 - args 해제 등 정리는 여전히 이 핸들러
    // 책임(3.1절 원칙 그대로). 서비스에 위임 중이었다면 그 채널
    // 요청도 여기서 함께 정리해야 한다(예: BridgePipe에 취소 통지).
    virtual void onCancel(AsyncTask* task, void* args) = 0;
};
```

Task/프로세스 종료 경로(아직 미구현 - PL-2D3184BC에도 없음)가 이
`onCancel`을 호출하는 지점을 가져야 한다 - 정확한 종료 시퀀스는
프로세스 종료 자체를 설계할 때 확정한다(이번 제안은 "그 시점에
`onCancel`이 있어야 한다"는 요구사항만 명시).

## 기존 설계에 미치는 영향 (요약)

| 문서 | 영향 |
|---|---|
| SP-F682B889(비동기 프레임워크) | `AsyncTaskHandler`에 `onCancel` 추가 제안 - **이미 approved 상태라 개정 확인 필요**. |
| PL-2D3184BC(스케줄러) §2 | Task PCB의 "블로킹 사유" 자리를 `pendingSyscall{endpoint, token}` 구조로 구체화. |
| PL-2D3184BC §6/8 | "블로킹/웨이크업 첫 소비자"가 이 Syscall 서브시스템으로 확정됨 - `Syscall::blockCurrentUntil`/wake 전용 API가 그 자리를 채운다. |
| SP-677210E6(TSS/IST) | RSP0 필드의 첫 실사용처가 이 syscall 트랩 진입 경로로 확정됨. |

## 결정이 필요한 사항 (DC로 등록)

아래 항목은 이 제안이 임의로 정하지 않고 별도 DC/질의로 확인받는다
(문서 등록 완료 - 참고 항목의 추적 코드 확인):

1. 유저랜드 syscall 트랩 명령(`syscall` vs `int 0x80`류)과 레지스터
   전달 규약의 구체적 확정.
2. `AsyncTaskHandler::onCancel` 추가(SP-F682B889 개정) 승인 여부.
3. 재블로킹(rejoin) 전용 endpoint의 정확한 설계(별도 고정 번호 vs
   기존 endpoint 재호출 시 플래그로 구분 등).

## 참고

- SP-F682B889 - 이 제안이 재사용하는 `AsyncTask`/`AsyncTaskHandler`/
  `AsyncReactor` 설계.
- PL-2D3184BC - 이 제안이 소비하는 스케줄러 블로킹/웨이크업 프리미티브.
- SP-677210E6 - RSP0 필드(이 제안의 트랩 진입점이 채움).
- DS-D4E5C451 - raw binary IPC 포맷 결정(이 제안의 args/결과 마샬링이
  따름).
- **SP-1FBC0EEB(메시징 채널 IPC)** - 커널 서비스 위임 경로의 실제
  구현체(짝을 이루는 제안).
