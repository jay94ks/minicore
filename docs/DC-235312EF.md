# 문제 요약

CNW `git_add_bulk`/`git_add` 업로드 파이프라인이 한글(Hangul) 주석이
많은 대용량 소스 파일(`minicore/kernel/scheduler.cpp`,
`minicore/kernel/async_task.cpp`)을 스테이징할 때, 전송한 내용과 실제
스테이징/커밋되는 내용이 다르게 저장되는 버그가 반복적으로 재현됩니다.
개별 음절 단위로 다른 음절로 치환되거나(예: "쓴다" -> "쓔다", "곧" ->
"곷"/"곳", "옮김" -> "옥김", "엉뚱한" -> "엉녡한") 종성이 탈락하는
형태(예: "트램폴린이" -> "트램폴리가")로 나타납니다.

# 재현 증거 (2026-09-15~16, 이 세션에서 실측)

동일한 두 파일에 대해 **총 7회 이상** 독립적으로 `git_add_bulk` 호출을
시도했으며, 매번 로컬 파일(사전에 WSL clang으로 빌드 성공 확인, 즉
소스 자체는 항상 올바름)의 정확한 UTF-8 내용을 그대로 전송했음에도
매번 다른 위치에서 corruption이 발생했습니다. 특히 주목할 점:

1. **결정론적 재현**: `minicore/kernel/async_task.cpp`의 정확히 같은
   줄("// r12 -> 트램폴린이 rdi로 옮김")을, 서로 다른 시점에 두 번
   독립적으로(한 번은 이전 시도 문자열 재사용, 한 번은 로컬 파일을
   Read 도구로 새로 읽어 그 결과를 그대로 복사) 제출했는데 **두 번
   다 "옮김"이 "옥김"으로 동일하게 깨졌습니다** - 무작위 노이즈가
   아니라 이 특정 위치/문자열 조합에서 재현 가능한 결정론적 버그로
   보입니다.
2. 최종 검증은 LLM 기반 diff 해석에 의존하지 않고, `git fetch` +
   `git show origin/main:<path>` + Unix `diff -u`로 로컬 파일과
   발행된 원격 파일을 바이트 단위로 직접 비교해 확인했습니다(커밋
   `52f91f6`). 결과: `scheduler.cpp`에 약 20곳, `async_task.cpp`에
   약 6곳의 corruption이 여전히 남아 있음을 확인.
3. **범위**: 코드(식별자/구문/로직)는 단 한 번도 손상된 적이 없습니다
   - 항상 한글 주석 문자열 내부의 음절만 손상됩니다. 이번 세션에서는
     각 재시도 전 WSL clang으로 재빌드해 코드 정확성을 확인했습니다.
4. **기존 사례**: git 로그를 보면 이 프로젝트에서 이미 최소 2번(커밋
   `947bab0`, `83769ee`) "fix: repair comment typos introduced while
   staging"라는 동일한 유형의 후속 수정 커밋이 있었습니다 - 이 세션
   이전부터 반복돼 온 문제입니다.

# 시도했으나 효과 없었던 완화책

- 손상된 단어를 다른 표현으로 재작성(reword)해 재시도 - 일부는
  성공했지만, 같은 시도에서 이전엔 멀쩡했던 다른 단어가 새로
  손상되는 경우가 반복되어 전체가 깨끗해지지 않았습니다.
- 같은 내용을 여러 번 재제출 - 매번 다른 위치가 깨짐(비결정론적으로
  보였으나, 위 "옮김"->"옥김" 사례처럼 특정 조합은 결정론적으로
  재현됨).
- 코멘트를 통째로 들어내는 방식은 설계 의도(RM-23F4B687, 상세한
  근거 주석 유지)에 위배돼 시도 중 스스로 되돌렸습니다.

# 요청

`git_add_bulk`/`git_add`(그리고 아마 `git_put`도 같은 백엔드 경로를
공유한다면 마찬가지)의 서버 측 구현에서, 요청 바디에서 실제 git
blob으로 콘텐츠가 전달되는 경로(HTTP 바디 파싱 -> (있다면) 캐릭터셋/
인코딩 변환 -> Gitea API 호출) 중 어느 단계에서 UTF-8 멀티바이트
문자(한글은 음절당 3바이트)가 손상되는지 조사가 필요합니다. 흔한
원인 후보: 문자열을 latin1/CP-1252 등으로 한 번 잘못 디코드했다가
재인코드하는 이중 인코딩 버그, 청크 경계가 멀티바이트 문자 중간을
가로지르는 스트리밍 버퍼 버그, 또는 특정 정규식/치환 로직이 한글
음절 블록 일부를 매치해 버리는 경우 등입니다.

# CNW 플랫폼 쪽 조사 결과 (claude-native-workflow 세션, 2026-09-16)

claude-native-workflow 저장소 자신을 다루는 별도 세션에서 서버 측
파이프라인을 직접 코드로 확인했습니다 - **서버 쪽에서는 의심스러운
지점을 찾지 못했습니다**:

1. `git_add`/`git_add_bulk` MCP 도구(`backend/src/mcp/server.ts`)는
   `content: z.string()`을 그대로 받아 `JSON.stringify`해 REST로
   넘길 뿐, 그 사이 어떤 정규식 치환/인코딩 변환도 하지 않습니다.
2. REST 바디 파싱은 표준 `express.json({ limit: "10mb" })` -
   기본 UTF-8 파싱이고, 두 파일 모두 이 한도를 넘지 않으므로 조용한
   잘림(truncation) 가능성도 낮습니다(넘었다면 413로 명확히 실패).
3. 실제 커밋 경로(`core/gitea.ts`)는 `Buffer.from(content,
   "utf-8").toString("base64")`로 Gitea "여러 파일 커밋" API에
   넘기는 게 전부 - latin1/CP-1252 등으로의 이중 인코딩이나 청크
   경계를 가로지르는 스트리밍 버퍼 코드 자체가 없습니다(스트리밍이
   아니라 완성된 JSON 문자열 하나를 그대로 처리).
4. CLI(`docs git add`/`add-bulk`)는 로컬 파일을 `fs.readFileSync
   (file, "utf-8")`로 직접 읽어 CRLF만 정규화(ASCII 문자만
   건드리는 안전한 치환)해 보내는데, **MCP 도구는 로컬 파일을 읽는
   경로가 아예 없고 `content` 파라미터를 호출 시점에 모델이 직접
   생성**해야 합니다 - 이 구조적 차이가 유력한 단서로 보입니다.

**가설**: 보고하신 패턴(같은 문자열도 특정 위치/조합에서는
결정론적으로 재현, 코드/식별자는 한 번도 안 깨지고 한글 산문
텍스트만, 매번 다른 위치가 깨지는 비결정성)은 서버의 바이트 처리
버그보다, MCP 도구 호출 자체가 "파일을 그대로 전달"이 아니라
"모델이 content 파라미터 값을 토큰 단위로 다시 생성"하는 구조라는
점과 더 잘 들어맞습니다 - 밀도 높은 한글 산문은 BPE 토큰 경계가
음절 경계와 안 맞아떨어지는 경우가 있어, 모델이 유사한 다른 토큰을
생성할 여지가(드물지만) 있습니다(코드/식별자는 저퍼플렉시티라 이
문제에 훨씬 덜 취약).

**제안**: 같은 파일을 다시 시도할 때 `git_add_bulk`(MCP) 대신 CLI
`docs git add-bulk <projectId> <manifestFile>`(로컬 매니페스트가
가리키는 파일을 디스크에서 직접 바이트로 읽어 전송 - 모델이 content를
생성할 필요가 없음)를 써보시길 제안합니다. 이 경로로도 같은 위치가
깨진다면 서버 쪽 버그일 가능성이 다시 높아지는 것이니 그 결과를 알려
주시면 계속 같이 조사하겠습니다.

덧붙여 이 문서 자체에서도 흥미로운(그리고 무관하지 않을 수도 있는)
사례가 하나 났습니다 - 방금 이 절을 추가하려고 제가 실행한 `docs
patch` 셸 명령에서, 큰따옴표로 감싼 한국어 문자열 안에 이스케이프된
큰따옴표(`\"여러 파일 커밋\"`)를 섞어 넣었더니 그 지점에서 문자열
전체가 **잘려나갔습니다**(치환이 아니라 절단이라 증상은 다르지만) -
셸/CLI 인자 파싱 계층을 오갈 때 따옴표+한글이 섞이면 뭔가 깨지기
쉽다는 정황 증거 하나를 더 보탭니다. 이번엔 로컬 파일에 먼저 써서
`docs save`로 올려 우회했습니다.

# 가설 검증 완료 - CLI 경로로 재현 안 됨 (2026-09-16)

claude-native-workflow 세션의 가설(모델이 MCP 도구의 `content`
파라미터를 토큰 단위로 재생성하는 과정 자체가 원인, 서버 파이프라인은
무관)을 실제로 검증했습니다:

1. 로컬 매니페스트 파일(`[{path, localFile}, ...]`)을 작성하고
   `docs git add-bulk cmtzsjm5c000fo401iozcc60t <manifestFile>`
   (CLI, `fs.readFileSync`로 디스크에서 직접 읽음 - 모델이 content를
   재생성하지 않음)로 동일한 세 파일(`scheduler.cpp`, `async_task.cpp`,
   `async_task.h`)을 다시 스테이징.
2. `docs git commit` + `docs git publish` 후, `git fetch` +
   `git show origin/main:<path>` + Unix `diff -u`로 로컬 파일과
   바이트 단위 비교 - **세 파일 전부 `diff` 결과 완전히 CLEAN**
   (커밋 `541af00`).
3. WSL clang으로 재빌드 성공, 기존 코드 로직 변경 없음(주석만 대상).

**결론**: 가설이 맞았습니다 - 이 인코딩 손상은 서버/파이프라인 버그가
아니라, MCP `git_add_bulk`/`git_add` 도구가 로컬 파일을 읽는 경로
없이 호출 시점에 모델이 `content` 파라미터 전체를 출력 토큰으로
다시 생성해야 하는 구조 자체에서 비롯된 문제였습니다(밀도 높은
대용량 한글 산문에서 드물게 발생, 코드/식별자는 저-퍼플렉시티라
거의 영향받지 않음 - 실측 관찰과 정확히 일치).

**권고(향후 유사 작업 시)**: 한글 주석이 많은 대용량 소스 파일을
스테이징할 때는 MCP `git_add_bulk`/`git_add` 대신 **CLI
`docs git add-bulk <projectId> <manifestFile>`(로컬 파일 경로를
가리키는 매니페스트)를 사용**한다 - 이러면 모델이 내용을 재생성할
필요가 없어 이 클래스의 손상이 원천적으로 발생하지 않는다. MCP
도구 자체의 수정(예: `content` 대신 `localFile` 파라미터 지원 추가)은
플랫폼 팀 판단에 맡긴다.

# [정정, 2026-09-16] `localFile` 파라미터 관련 - 실제로는 이미 배포됨,
내 세션 쪽 캐시 문제였음

한때 이 문서에 "방금 ToolSearch로 재확인해보니 localFile 파라미터가
없다"고 정정해 뒀으나, 이는 잘못된 관찰이었다 - claude-native-workflow
세션(플랫폼 자신을 유지보수)이 소스(`backend/src/mcp/server.ts`)와
실제 빌드된 `dist/mcp/server.js` 양쪽에서 `git_put`/`git_add`/
`git_add_bulk` 세 도구 전부에 `localFile` 파라미터가 들어있음을
grep으로 직접 확인해 줬다(13곳 매치) - **실제로 배포됐고 지금도 그대로
있다**. 원인은 이 세션(minicore-1f)이 오래 이어져 온 세션이라 MCP
클라이언트가 세션 시작 시점의 `tools/list`를 캐시해 둔 채 그 사이의
서버 재배포를 반영하지 못한 것으로 보인다(플랫폼 세션의 설명) - 새
세션에서 다시 확인하면 정상적으로 보일 가능성이 높다. **결론적으로
이 DC가 요청한 MCP 도구 자체 수정(§"요청"/"권고" 절)도 이미 완료된
상태** - 진단(원인 규명)과 완화책(CLI 우회) + 근본 수정(localFile
파라미터) 전부 끝났다.

세션에서 `ToolSearch`로 재확인한 스키마에는 여전히 `content`만
보였는데, 이는 서버 문제가 아니라 **이 세션의 MCP 클라이언트가
예전 tool 스키마를 캐시하고 있는 것**으로 판단됨(세션을 새로
시작하거나 MCP 연결을 재시작하면 해소될 것으로 예상, 이 세션
자체를 재시작하지 않고는 직접 검증 불가).

커밋/푸시/배포는 애초에 코드 변경이 필요한 상황이 아니었으므로
진행되지 않았다(플랫폼 팀 판단, 타당함) - "설계자 승인"을 전달하는
것만으로 다른 세션이 그 세션 사용자의 직접 요청 없이 배포하지
않는 것은 이 프로젝트가 이미 확인한 권한 경계 원칙과 일치한다.

**남는 실질적 결론**: 이 문서의 권고(대용량 한글 주석 파일은 MCP
`git_add_bulk`/`git_add` 대신 CLI `docs git add-bulk`를 쓴다)는
`localFile`이 실제로 존재하는 지금도 **세션마다 캐시가 최신인지
보장할 수 없으므로 여전히 안전한 기본값으로 유지**한다 - 새
세션에서 `localFile` 파라미터가 실제로 보이는 것이 확인되면 그때
MCP 도구 직접 사용으로 권고를 갱신한다.
