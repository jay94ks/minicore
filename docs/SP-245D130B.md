# ResourceGroup (cgroup류) 자원 제한/우선순위/제어/계정 체계

설계자 지시(2026-09-17, 메시지): "리눅스의 `cgroup`과 유사한 체계가
필요해. 주요 기능: (1) 자원 제한 - 메모리(fs 캐시 포함)/I/O 대역폭/
CPU 사용량 한도 강제, (2) 우선순위 부여 - 경쟁 시 특정 그룹에 더
큰 몫 배분, (3) 제어 - 그룹 전체 freeze 등, (4) 계정 - 그룹별 실제
자원 사용량 집계."

이 문서는 그 네 기능을 담을 **`ResourceGroup`**(Linux `cgroup`에
해당하는 이 프로젝트의 이름 - `ProcessRole`/`TaskClass`와 같은
PascalCase 관례) 체계를 제안한다.

## [분리, 2026-09-17, 설계자 opinion 2건] §0/§6이 지적한 CPU 가중치/
계정 공백이 별도 문서로 설계됨

설계자가 "가중치/지분(vruntime류), CPU 시간을 Task별로 집계하는
카운터 도입하자"/"어떤 프로세스가 얼마나 썼는지 추적하는 계정 계층도
설계해서 SP로 올려줘"라고 지시 - 아래 §0/§3/§5/§6이 "후속"으로
미뤄뒀던 CPU 가중 스케줄링(vruntime)/Task별 CPU 틱 카운터/프로세스별
메모리 coarse 계정을 `SP-B26CDBDD`(review)로 분리 설계했다. §3의
`ResourceGroupCpuControl`/§5의 `ResourceGroupAccounting`이 자리만
잡아 둔 필드들의 실제 갱신 로직이 그 문서 §5에 있다 - 이 문서는
트리/freeze/그룹 구조 자체를 계속 소유하고, CPU/메모리 계정의 실제
카운터 배선은 `SP-B26CDBDD`가 소유한다.

## 0. 먼저 확인한 것 - 이 커널이 지금 뭘 가졌고 뭘 안 가졌는가

실측(grep) 결과, 이 네 기능을 지금 당장 완전히 구현할 토대가 전부
있지는 않다:

- **CPU**: `Scheduler`가 코어별 FIFO 큐(`gRtQueues`/`gNormalQueues`)
  + 라운드로빈 + Push/Pull 로드밸런싱(SP-9525C4C0)을 갖고 있다 -
  **가중치/지분(vruntime류) 개념 자체가 없다**(TaskClass는 Normal/
  RealTime 이진값뿐). CPU 시간을 Task별로 집계하는 카운터도 없다.
- **메모리**: `PageFrameAllocator`/`GenericSlabAllocator`는 전역
  풀이고, 어떤 프로세스가 얼마나 썼는지 추적하는 계정 계층이 없다.
  fs 캐시는 fs 서비스 자체가 아직 코드로 없다(`SP-7CC5693A` 설계만,
  `minicore/fs` 디렉터리 0%).
- **I/O**: 블록 장치 드라이버가 하나도 구현돼 있지 않다(AHCI/USB
  둘 다 설계만, `PN-BD9AAE2F` devmgr 5번 항목 대기) - "I/O 대역폭"을
  제한할 실제 I/O 경로 자체가 없다.
- **제어(freeze)**: `TaskState`는 `{Ready, Running, Blocked, Zombie}`
  뿐이다 - 새 상태를 추가하지 않고 기존 `Blocked`를 재사용하는 게
  이 프로젝트의 확립된 관례다(`SP-9A6D579F` §3.5가 디버그 정지에
  이미 이 원칙을 씀, RM-23F4B687 §4 과설계 방지).

**결론**: 이 문서는 (a) 지금 바로 구현 가능한 것(트리 구조, freeze,
CPU 기초 계정+쿼터 스로틀)과 (b) 설계만 확정하고 구현은 선행
인프라를 기다리는 것(메모리/IO 제한, fs 캐시 연동, CPU 가중치
공정 스케줄링)을 명확히 나눈다 - 전부를 한 번에 만들려 하지 않는다
(RM-23F4B687 §4).

## 1. 핵심 모델 - `ResourceGroup` 트리

```cpp
// resource_group.h (신규 파일 제안, minicore/kernel)
class ResourceGroup : public EnableSharedFromThis<ResourceGroup> {
public:
    Spinlock lock;
    char name[kMaxNamedObjectNameLength] = {};  // named_object.h 기존 상수 재사용
    uint64_t nameLength = 0;

    // Process 트리(Process::parent/children)와 완전히 별개의 축이다 -
    // 실제 Linux cgroup처럼 "프로세스 트리 구조 != 그룹 트리 구조"를
    // 허용한다(프로세스는 부모와 다른 그룹에 속할 수 있음).
    WeakPtr<ResourceGroup> parent;
    ChunkedList<SharedPtr<ResourceGroup>, 8> children;  // Process::children과 동일 패턴 - 부모가 진짜 소유자

    // 이 그룹에 직접 속한 프로세스들 - 강한 참조 아님(Process가
    // 이미 다른 곳에서 소유됨, Process 쪽에서 group으로 WeakPtr류
    // "역참조 전용" 관계 - 실제 구현은 §6.1 DontDeref<T> 패턴 재사용
    // 검토, 그룹은 프로세스를 "소유"하지 않는다).
    ChunkedList<DontDeref<Process>, 8> memberProcesses;

    // §3 CPU 컨트롤러
    ResourceGroupCpuControl cpu;
    // §5 계정
    ResourceGroupAccounting accounting;
    // §4 freeze
    bool frozen = false;

    void init();  // 기존 관례(슬랩 할당+명시적 init, Channel과 동일)
};
```

- **가입은 프로세스 단위**(Linux cgroup v2와 동일 - 스레드 단위
  아님, 이 프로젝트가 어차피 "프로세스당 스레드 하나"라 자연히
  일치). 한 프로세스는 **정확히 하나의 그룹**에 속한다(Linux
  cgroup v2의 "unified hierarchy" 원칙 - v1처럼 컨트롤러마다 다른
  트리를 허용하지 않는다, 단순성 우선 RM-23F4B687 §4).
- **루트 그룹**: 부팅 시 `gRootResourceGroup` 하나가 미리 존재하고,
  그룹에 명시적으로 가입하지 않은 모든 프로세스(현재 전부)는 여기
  속한다 - 기존 동작 무변경 보장.
- **자식 그룹의 자원은 부모의 부분집합**(Linux cgroup 계층 제약과
  동일) - 자식의 CPU 쿼터 합이 부모의 쿼터를 넘을 수 없다는 정책은
  **[확정, 2026-09-18, QU-3356AD2B §9-3 답변("자식 합이 부모를 넘을 수 없다")]** 그 정책은 v1 범위 밖이 아니라 확정된 정책이다 - 구현은
  `PN-4190BBD3` 항목3(CPU 쿼터 카운터, 아직 미착수)이 맡는다.

## 2. Process ↔ ResourceGroup 연결

`Process`에 `DontDeref<ResourceGroup> group`(§6.1 `DontDeref<T>`
재사용 - 그룹은 프로세스를 관찰만, 소유는 그룹→멤버 방향이 아니라
`memberProcesses` 리스트가 짐) 필드를 추가한다(**[구현 차이, 2026-09-17, PN-4190BBD3 항목2]** 그룹이 전부 정적 전역(`gRootResourceGroup` 하나뿐)이라 실제로는 raw 포인터 `ResourceGroup* group = nullptr;`로 구현됨 - 동적 그룹 생성이 생기면 재검토). **[확정,
2026-09-17, QU-42C5D5BD §9-1 답변("상속 받는 구조로 하면 돼")]** 자식 프로세스는 `SpawnProcess`될 때 부모와 같은
그룹을 상속한다(Linux 기본 동작과 동일, 구현 완료) - 명시적
`ResourceGroupJoin` 없이도 이미 그렇게 동작한다.

## 3. CPU 컨트롤러 - v1은 가중 공정 스케줄링이 아니라 "쿼터 스로틀"

**[분리, 2026-09-18, 설계자 opinion("CPU 쿼터 카운터 설계안 별도
문서로 작성해줘")]** 이 절의 자료구조/정책을 실제 구현 가능한 수준
(스로틀 알고리즘/계층 강제 검증/syscall)으로 구체화한 문서가
`SP-6A563A8F`(review)로 분리됐다 - `SP-B26CDBDD`가 §0/§6의 CPU
가중치 공백을 분리했던 것과 같은 패턴. 아래 원문은 그대로 두되,
실제 구현은 `SP-6A563A8F`를 따른다.

Linux cgroup의 `cpu.weight`(상대 지분, 공정 스케줄러 전제)는 이
프로젝트의 단순 라운드로빈 스케줄러에 얹기엔 너무 큰 재설계다
(vruntime류 개념 자체를 새로 만들어야 함) - **v1은 그 대신 `cpu.max`
(Linux cgroup v2 용어, "주기당 최대 사용 시간") 스타일의 **쿼터
스로틀**만 구현한다:

```cpp
struct ResourceGroupCpuControl {
    // period/quota 둘 다 스케줄러 틱 단위(100Hz, PL-2D3184BC) -
    // "1000틱(10초)마다 최대 500틱(5초)까지만 실행 허용" 같은 정책.
    uint32_t periodTicks = 0;   // 0 = 무제한(기본값, 기존 동작 그대로)
    uint32_t quotaTicks = 0;
    uint32_t usedTicksInPeriod = 0;  // §5 계정과 공유하는 카운터
    uint64_t periodStartTick = 0;    // Timer::tickCount() 기준
};
```

- `Scheduler::onTick()`이 매 틱마다 현재 실행 중인 Task의
  `Process::group`을 따라가 `usedTicksInPeriod`를 1 증가시킨다(§5
  계정과 동일 지점 - 별도 훅 불필요, 이미 onTick을 도는 김에).
- `periodStartTick` 이후 `periodTicks`가 지나면 카운터/구간을
  리셋한다.
- **쿼터 초과 시**: `pickNext()`가 그 그룹 소속 Task를 이번 주기엔
  건너뛴다(다음 주기까지 유예 - Ready 상태 유지, 그냥 안 뽑힘) -
  새 TaskState 불필요, 기존 큐 순회 로직에 조건 하나만 추가.
- **우선순위(prioritization)**: v1은 "쿼터 없음(무제한) vs 쿼터
  있음(제한)"의 이진 구분만으로 충분히 실용적인 우선순위 부여가
  된다고 본다(무제한 그룹이 사실상 최우선) - Linux 수준의 세밀한
  상대 가중치(예: A그룹 200 vs B그룹 100 = 2배 몫)는 **후속 계획으로
  분리**(§7).

## 4. Freezer 컨트롤러 - 기존 `TaskState::Blocked` 재사용

```
ResourceGroupFreeze(name) -> error   // 그룹 소속 전체 프로세스의 Task를 Blocked로
ResourceGroupThaw(name) -> error     // 다시 Ready로(Scheduler::enqueue)
```

- `SP-9A6D579F` §3.5가 디버그 정지에 쓴 것과 동일한 원칙 - 새 상태
  추가 없이 `TaskState::Blocked` 재사용. 차이점: 디버그 정지는
  "그 Task 하나"만, freeze는 "그 그룹의 모든 멤버 프로세스의 모든
  Task"를 순회하며 일괄 적용.
- **디버그 정지와의 상호작용**(열린 질문): 이미 디버그 세션으로
  정지된 Task를 freeze/thaw가 건드리면 안 된다 - 정지 사유를
  구분하는 플래그가 필요할 수 있음(§7).
- Freeze 중인 Task는 `pickNext()`에 애초에 안 걸리므로(Blocked라
  Ready 큐에 없음) 스케줄러 쪽 추가 변경 불필요.

## 5. 계정(Accounting)

```cpp
struct ResourceGroupAccounting {
    uint64_t totalCpuTicks = 0;   // §3에서 누적, 무제한 그룹도 계속 집계(쿼터 없어도 통계는 냄)
    // 메모리/IO는 §6/§7이 먼저 필요한 인프라를 갖춘 뒤 추가 필드
};
```

- CPU 시간 계정은 §3의 카운터를 그대로 통계로도 노출 - 별도 작업
  없음.
- **조회 경로**: 새 syscall 대신 **읽기 전용 VFS 노출**을 제안한다
  - `/sys/live/resourcegroup/<name>/cpu.stat`류 파일(`ProcFs`/
  `LiveFs`가 이미 확립한 "고정 key: value 텍스트, 매 read마다
  스냅샷 재조립" 패턴, `SP-5D965B74`/`procfs.cpp` 그대로 재사용) -
  이 프로젝트가 상태 조회에 이미 쓰고 있는 관례와 일치하고, 새
  syscall 표면을 늘리지 않는다.

## 6. 메모리 컨트롤러 - 설계만, 구현은 후속(선행 인프라 없음)

메모리 사용량을 "어느 그룹 몫으로 계산할지" 판정하려면 **모든
할당 경로(`PageFrameAllocator`/`GenericSlabAllocator`/mmap)가 호출자
프로세스를 알아야 한다** - 지금은 그런 계정 계층 자체가 없다(할당
함수들이 "몇 바이트"만 받고 "누구 몫인지"는 모른다). 이건 이 문서
범위를 넘는 별도의 인프라 작업이다:

```cpp
// 제안 방향(구현은 후속 PN) - 각 할당 지점에 현재 Task의 그룹을
// 물어보는 게 아니라, Process 종료/mmap 시점에 이미 아는 크기만큼
// 그 프로세스가 속한 그룹의 accounting.memoryBytes에 가산/감산하는
// "coarse 계정"부터 시작하는 게 현실적이다(정확한 페이지 단위
// 실시간 추적보다 훨씬 저렴, RM-23F4B687 §4).
struct ResourceGroupMemoryControl {
    uint64_t limitBytes = 0;  // 0 = 무제한
    uint64_t usedBytes = 0;   // coarse - mmap/exec 시점에만 갱신
};
```

fs 캐시 몫은 fs 서비스 자체가 없어(§0) 전혀 설계할 게 없다 -
`SP-7CC5693A`가 실제로 캐시를 갖게 되는 시점에 재검토.

**후속 계획으로 분리**(§8) - 이 문서는 필드 모양만 스케치하고
enforcement는 만들지 않는다.

## 7. I/O 컨트롤러 - 전면 보류

블록 I/O 경로 자체가 없어(§0) 설계할 대상이 없다. `SP-C2670F69`
(AHCI)/`SP-E35FD36C`(USB)가 실제로 블록 장치를 노출하기 시작하면
그 인터페이스(`AhciBlockDevice`류) 위에 대역폭 제한 훅을 얹는
후속 설계가 필요하다 - **후속 계획으로 분리**(§8), 지금은 필드도
스케치하지 않는다(진짜로 아무 근거가 없음).

## 8. Syscall API (RM-48E1E610 번호 예약)

| 이름 | 설명 |
|---|---|
| `ResourceGroupCreate` | 이름 지정해 생성, 부모 그룹 지정(생략 시 루트 자식) |
| `ResourceGroupDestroy` | 자식/멤버가 없어야 성공(비어있음 강제 - Linux cgroup과 동일) |
| `ResourceGroupJoin` | 호출자(또는 지정 프로세스 - 권한은 §7 열린 질문) 프로세스를 그룹에 가입 |
| `ResourceGroupSetCpuQuota` | §3의 `periodTicks`/`quotaTicks` 설정, 0/0=무제한 |
| `ResourceGroupFreeze`/`ResourceGroupThaw` | §4 |

빈칸 36/37/46부터 채우고 나머지는 60부터 순서대로 배정(착수 시
`RM-48E1E610`에 실제로 기록).

**[추가, 2026-09-17, minicore-f8]** 거의 동시에 `RM-48E1E610`에도
다른 opinion이 올라와 있었다 - 설계자가 평평한 0-255 번호 체계를
그룹(상위 8비트)+call(하위 8비트) 2단계로 재편하라고 지시해
`SP-E9B44929`(review, 답변 대기)로 별도 설계를 등록해 뒀다. 이 표의
5개 새 syscall을 지금 구식 평평한 번호로 예약하면, `SP-E9B44929`가
승인되는 순간 다시 그룹+call 값으로 재배정해야 하는 이중 작업이
생긴다 - 착수 순서를 어떻게 할지 조율 필요(예: `SP-E9B44929`
승인을 기다렸다가 그 체계로 바로 배정하는 게 더 간단할 수 있음,
아니면 구식 번호로 먼저 예약 후 나중에 일괄 재인코딩).

## 9. [열린 확인 — 설계자] 이 설계에 대한 질문

1. **자식 프로세스의 기본 그룹**: `SpawnProcess`로 만든 자식이
   기본적으로 부모와 같은 그룹을 상속하는지(Linux 기본 동작), 항상
   루트에서 시작해 명시적 `ResourceGroupJoin`이 필요한지. **[확정,
   2026-09-17, QU-42C5D5BD §9-1 답변("상속 받는 구조로 하면 돼")]**
   부모와 같은 그룹을 상속한다 - 구현 완료(`PN-4190BBD3` 항목2).
2. **`ResourceGroupJoin`의 권한**: 임의 프로세스를 아무나 그룹에
   넣을 수 있는지, 아니면 그 프로세스의 조상만 가능한지(`Kill`/
   `DebugAttach`가 이미 쓰는 "조상-자손+커널 예외" 모델을 재사용할
   후보 - `PN-617F4E52`의 사용자/권한 체계가 먼저 필요할 수도 있음).
   **[확정, 2026-09-18, QU-3356AD2B §9-2 답변]** "호출자가 이미 그
   그룹의 조상 체인 안에 있을 때만 허용" - 제안된 가장 좁은 v1 그대로
   채택.
3. **자식 그룹 쿼터가 부모를 넘는 것을 강제로 막을지**(§1 "열린
   질문") - v1에서 검증 로직을 넣을지, 아니면 관례로만 두고 강제
   안 할지. **[확정, 2026-09-18, QU-3356AD2B §9-3 답변]** "자식 합이
   부모를 넘을 수 없다" - 계층적 강제 채택(§1 갱신 완료).
4. **freeze와 디버그 정지의 상호작용**(§4) - 정지 사유 구분 플래그
   필요 여부. **[확정, 2026-09-17, QU-42C5D5BD 답변("맞아. 사유
   구분 플래그를 둬야해")]** `DebugSession::pausedByDebugger`
   (debug_session.h, 신규) 도입 - `ResourceGroup::thaw()`가 그룹
   freeze를 풀 때 이 플래그가 서 있으면 `frozenByGroup`만 내리고
   실제로 깨우지는 않는다(구현 완료, resource_group.cpp). 반대
   방향(디버그 정지를 풀 때 그룹 freeze까지 실수로 풀지 않아야
   함)은 아직 미착수인 `DebugContinue`(SP-9A6D579F §3.5) 착수 시
   `!proc->group->frozen`을 먼저 확인해야 한다는 요구사항으로
   그 문서에 교차 기록해 뒀다 - `pausedByDebugger` 자신도 §3.4/
   §3.5/`kSpawnDebugStart` 소비 지점이 실제로 Blocked 전환할 때
   함께 세워야 하는데 그 지점들이 전부 아직 미착수라, 필드와
   thaw() 쪽 소비 로직만 먼저 준비해 뒀다(자리 확보, RM-23F4B687
   §4).
5. **CPU 우선순위 부여를 언제 "쿼터 이진 구분"에서 "상대 가중치"로
   격상할지** - 지금 당장 필요한지, 아니면 실사용처(여러 그룹이
   실제로 경쟁하는 워크로드)가 생길 때까지 미룰지. **[해소, 2026-09-18,
   `SP-B26CDBDD`(approved) §7]** `SetTaskWeight` syscall + vruntime
   기반 Task별 상대 가중치 스케줄링으로 이미 확정·설계 완료 - 이
   문서(ResourceGroup) §3의 쿼터 스로틀(그룹 단위 CPU *제한*)과는
   별개 축(Task 단위 CPU *우선순위*)이라 대체 관계가 아니라 병존한다.
