# 실행 계획: Syscall 디스패치 서브시스템

**[커널 내부 dispatch 로직 구현 완료, ring3 트랩 진입은 미착수,
2026-09-14 - 계획 PN-BF5F099D]** SP-04EE2A18의 `UserThread`/`SyscallRegistry`/제출-대기
(`Syscall::submit`/`Syscall::wait`) 모델을 구현했다. **착수
전제조건**이었던 AsyncTask 프레임워크(PL-1E247831, 완료)를 그대로
재사용했다.

## 배경

SP-04EE2A18 참고 - syscall 하나 = `AsyncTask` 하나, "제출(submit)은
즉시 반환, 실제 대기는 `waitForSyscall`" 모델(DC-D868D9EC/QU-EF643652
확정). 이 계획은 그 커널 내부 dispatch 로직만 다룬다 - **실제 유저랜드
(ring3) syscall 트랩 진입(syscall 명령/legacy int 0x80 게이트, MSR
STAR/LSTAR/SFMASK, GDT ring3 세그먼트, TSS.RSP0 배선)은 이번 범위에
없다**: 이 프로젝트에는 아직 ELF 로더/유저 페이지 테이블/프로세스
생성/ring3 진입 메커니즘 자체가 전혀 없어(SP-8B6B8D25가 그리는
유저랜드 인프라가 아직 없음), 트랩 진입부를 지금 구현해도 실제로
ring3에서 호출해 "실측 검증"할 방법이 없다 - 이 프로젝트가 지금까지
일관되게 지켜온 "QEMU 실측 검증" 원칙에 맞춰, **검증 가능한 커널
내부 dispatch 부분만** 이번에 완성하고, 트랩 진입부는 유저랜드
인프라(프로세스 모델)가 갖춰질 때 별도 계획으로 이어간다.

## 구현 (완료된 부분)

1. **`UserThread : public Task`**: `minicore/kernel/syscall.h` -
   설계 문서 그대로 `PendingSyscall{endpoint, token, valid}` 필드
   하나. 이름 자체는 제안일 뿐 확정이 아니다(설계 문서와 동일 각주).
2. **`SyscallRegistry`**: `endpointId`(공개 ABI, 고정 슬롯, v1 상한
   256) <-> `AsyncTaskHandler*` 매핑. **구현 판단 하나 기록**: 설계
   문서는 "`AsyncCallbackRegistry`와 분리된 고정 슬롯 테이블"이라고만
   했는데, 실제로는 `SyscallRegistry::registerHandler`가 내부적으로
   `AsyncCallbackRegistry::registerHandler`를 그대로 호출해 동적
   `subjectCode`를 얻은 뒤, 그 값을 `endpointId` 슬롯에 매핑해 두는
   **간접화 계층**으로 구현했다 - 이렇게 하면 기존 AsyncTask 디스패치
   경로(`kAsyncTaskEntryWrapper` -> `AsyncCallbackRegistry::resolve`)를
   전혀 건드리지 않고 그대로 재사용할 수 있고, `endpointId` 공간과
   내부 `subjectCode` 공간이 절대 섞이지 않는다(새 DC 불필요 수준의
   구현 세부).
3. **`Syscall::submit(endpointId, args)`**: `SyscallRegistry`로
   `subjectCode`를 찾아 `AsyncTask::submit(subjectCode, 0, args,
   autoFree=false)`를 호출하고, 호출한 `UserThread`의 `pendingSyscall`
   에 `{endpoint, token, valid=true}`를 기록한다. **토큰의 정체 =
   AsyncTask 포인터 그 자체**(설계 문서가 토큰의 내부 표현을 규정하지
   않아 - 별도 전역 토큰 테이블 없이, 포인터 값 자체를 불투명한
   식별자로 재사용하는 구현 판단, 새 DC 불필요 수준). `autoFree=false`
   가 필요해 `AsyncTask::submit`/`AsyncTask` 구조체에 `autoFree`
   플래그와, 완료 시 깨울 대상을 가리키는 범용 `waitingTask` 필드를
   추가했다(PL-1E247831 문서에도 교차 기록) - 둘 다 Syscall 전용이
   아니라 "특정 kernel::Task가 특정 AsyncTask의 완료를 기다린다"는
   범용 패턴으로 설계해, 앞으로 다른 소비자도 재사용할 수 있다.
4. **`Syscall::wait(token)`**: 자기 `pendingSyscall.token`과 다르면
   (위조/타인/이미 소비된 토큰) 즉시 `false` - 전역 검색 없이 자기
   스레드 필드와만 비교(설계 문서의 보안 속성 그대로). 이미 완료됐으면
   즉시 반환, 아니면 `task->waitingTask = self` 등록 후
   `Scheduler::parkCurrent()`로 블로킹 - **`PreemptionGuard`로 "완료
   여부 확인 + waitingTask 등록" 구간을 감싸야 한다**(실측 이전에
   코드 리뷰로 미리 피한 경쟁 - 이 구간 중간에 스케줄러 틱이 끼어들어
   리액터가 먼저 완료시켜 버리면, 그 시점엔 waitingTask가 아직
   비어 있어 아무도 못 깨우고 영원히 파킹된 채로 남는다). 완료 시
   `AsyncTask`/전용 스택 반납은 **`wait()` 자신이 직접** 한다(리액터의
   일반 자동 반납 경로는 `autoFree=false`라 건드리지 않음) - 재개
   시점에 안전하게 참조 가능함이 보장된 뒤에 반납하므로 use-after-free
   가 없다. 어떤 이유로든(설계자 지시 2번 - 아직 설계 안 된 시그널
   등) 파킹이 풀려도, 유저랜드가 그냥 같은 token으로 `wait()`을 다시
   부르면 되므로 별도 재합류 API가 필요 없다(이 함수 자체가 그
   재합류와 동일한 코드 경로 - 설계 확정 그대로).

   **[2026-09-14 추가, Channel IPC(PL-C8648D4D) 스트레스 테스트로
   실측 발견]** 위 `PreemptionGuard` 스코프는 "완료 확인 + waitingTask
   등록" 구간만 보호했는데, **그 스코프가 끝난 시점과 실제로
   `Scheduler::parkCurrent()`에 진입하는 시점 사이에 또 다른 틈**이
   있었다 - 그 틈에 스케줄러 틱이 끼어들면 이 Task를(아직
   `parkCurrent()`를 부르지 않았으니) 그냥 보통의 라운드로빈으로
   재큐잉해 버리고, `waitingTask`는 이미 세팅돼 있으므로 뒤이어
   리액터가 완료시키며 `scheduleImmediate`를 부르면 같은 Task가 두
   큐에 동시에 들어가는 이중 스케줄링이 된다(`reactorTaskEntry()`의
   `parkCurrent()` 호출부에서 이미 실측 발견한 것과 같은 근본 원인 -
   PL-2D3184BC "이중 스케줄링 버그 클래스의 구조적 방지책" 절 참고).
   **수정**: `PreemptionGuard` 스코프가 끝난 직후, `parkCurrent()`
   호출 직전에 `asm volatile("cli")`를 추가(`parkCurrent()` 자신의
   cli와 중복이라 무해) - `syscall.cpp`. 최종적으로는
   `Task::inRunQueue` 구조적 수정(PL-2D3184BC)으로 이 부류의 경쟁
   전체가 근본적으로 해결됐다 - 이 개별 수정은 그 전 단계의 기록으로
   남겨 둔다.

## 검증(QEMU, 완료)

임시 디버그 처리기 2종 + 드라이버 Task(검증 후 제거)로 다음을 확인
했다 - 단일 코어(PVH)와 4코어 SMP(GRUB+q35 `-smp 4`) 둘 다 회귀 없이
통과:

- **빠른 경로**: endpoint 등록 -> `submit` -> (리액터가 곧 처리) ->
  `wait`이 "이미 완료됨"을 발견해 즉시 반환, `args`를 통해 결과값이
  정확히 전달됨을 확인(`[FAST-PASS]`).
- **블로킹 경로**: `onExec`이 `AsyncTask::yield()`로 한 번 멈추는
  endpoint에 대해 `wait`을 호출하면 반드시 파킹되고, 별도 Task가
  (실제 I/O 완료 인터럽트를 흉내내) `AsyncReactor::submitCompletion`
  으로 다시 제출해야만 재개되어 최종 완료됨을 확인(`[SLOW-PASS]`) -
  `onExec`이 yield 직후 지점부터 정확히 이어짐(AsyncTask 수준 컨텍스트
  보존, PL-1E247831에서 이미 검증된 성질 재확인).
- **토큰 위조/재사용 거부**: 이미 `wait()`으로 소비(반납)된 토큰을
  다시 `wait()`하면 use-after-free 없이 즉시 `false`를 반환함을
  확인(`[REUSE-REJECT-PASS]`).
- 4코어 SMP 부팅(3개 AP 정상 기동) 및 실행 중 크래시 없음.

검증 후 임시 처리기/드라이버 코드는 제거 - 영구 코드는
`syscall.h/.cpp`, `async_task.h/.cpp`의 `waitingTask`/`autoFree` 확장
분만 남았다.

**[2026-09-14 추가]** 위 `Syscall::wait()`의 `cli` 수정은 Channel
IPC(PL-C8648D4D)의 4-Task 동시 동작 스트레스 테스트로 재검증됐다 -
진단 코드를 완전히 제거한 최종 빌드로 SMP4 연속 50회 무크래시(자세한
수치는 PL-C8648D4D 참고, `Task::inRunQueue` 구조적 수정과 함께
적용된 뒤의 결과).

## waitForMultipleSyscall/waitAnyForMultipleSyscall 구현 완료 (2026-09-14, 계획 PN-BCE6CFF3)

QU-31402585(`waitAnyForMultipleSyscall` 설계)/QU-F475C6C2(`UserThread`
필드 다중화) 설계자 답변을 반영해 구현/검증까지 완료했다(커밋
`8ba27e9`).

1. **`ChunkedList<T, ChunkCapacity>`**(신규, `minicore/libs/libkenv/chunked_list.h`):
   설계자 지시대로 "단순 배열 금지, 재사용 가능한 GENERIC 컨테이너"로
   만든 청크 기반 연결 리스트 - 원소가 꽉 찬 청크는 새 청크를 할당해
   앞에 붙이고, 빈 슬롯이 생기면(erase) 재사용한다. 할당자는 함수
   포인터 두 개(alloc/free)로 주입받아 `libkmm`(더 상위 계층)에
   의존하지 않는다.
2. **`UserThread::pendingSyscall`(단일 필드) → `pendingSyscalls`
   (`ChunkedList<PendingSyscall, 10>`)**: 청크 용량 10은
   `Slot(24B)*10+next(8B)=248B`가 `GenericSlabAllocator`의 256B
   버킷(SP-D7013B26)에 8B 낭비로 거의 꽉 차게 고른 값. `valid`
   플래그는 `ChunkedList::Slot::used`로 대체되어 제거됨.
3. **공용 내부 구현 `Syscall::waitForAnyOf(tokens[], count)`**: 주어진
   토큰 중 이미 끝났거나(Completed/Failed) 유효하지 않은 게 있으면
   즉시 그 하나를 반환(비블로킹), 전부 아직이면 그중 아무 하나가
   끝날 때까지 파킹한다(기존 `wait()`과 동일한 `PreemptionGuard`+
   `cli` 경쟁 방지 패턴을 그대로 적용). `wait(token)`/
   `waitForMultipleSyscall`/`waitAnyForMultipleSyscall` 셋 다 이
   구현을 공유한다 - **둘의 차이는 순수하게 호출부가 몇 번 부르는가**
   (AND: 캐리 호출부가 반복 호출해 N개를 드레인 / OR: 한 번만 호출해도
   충분)이지 커널 내부 메커니즘 자체는 완전히 동일하다(설계자 답변
   그대로).
4. **`Syscall::submit()` 경쟁 보강**: 기존엔 단일 필드 대입이라 실패할
   수 없었지만, 이제 `pendingSyscalls.insert()`가 목록 청크용 Slab
   고갈로 실패할 수 있다(AsyncTask 자체는 이미 확보돼 리액터 실행
   큐에 올라간 뒤) - `AsyncTask::submit()` 호출부터 `insert()` 실패
   판정까지 전체를 `PreemptionGuard`로 감싸, 그 사이 리액터가 끼어들어
   완료시켜 버리는(그러면 `autoFree=false`라 아무도 반납 못 함) 경쟁을
   막았다. 실패 시 `task->autoFree = true`로 되돌려 리액터가 대신
   정리하게 한다.
5. **검증**: WSL clang로 `minicore_kernel`/전체 빌드 성공, QEMU 부팅
   스모크 테스트로 회귀 없음을 확인(단, `UserThread`를 실제로 만드는
   호출부가 이 프로젝트에 아직 없어 - 프로세스 모델 미착수 - 이
   API들이 런타임에서 실제로 호출되는 경로는 없다. 컴파일/링크/기존
   경로 무회귀만 이번에 확인 가능한 범위).

## 다음 소비자

**Channel IPC(SP-1FBC0EEB)**가 이 Syscall dispatch의 다음 소비자였다
(`openChannel`/`connectChannel`/`acceptFromChannel`/`read`/`write`/
`closeBridge`/`destroyChannel` 전부 `SyscallRegistry`에 등록되는
`AsyncTaskHandler`로 구현 완료 - PL-C8648D4D) - ring3 트랩 진입이
없어도 API 계약과 상태 기계는 커널 내부에서 완전히 검증 가능함을
그대로 재확인했고, 그 스트레스 테스트가 위 `Syscall::wait()`의 경쟁
조건을 실측으로 드러냈다. 다음은 `waitForMultipleSyscall`/
`waitAnyForMultipleSyscall`(설계자 지시, 2026-09-14)이다.
