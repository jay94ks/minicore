# 실행 계획: 메시징 채널 IPC(Channel) 구현

**[커널 내부 구현 완료, 2026-09-14 - 계획 PN-A5C06B9B]** SP-1FBC0EEB의
`openChannel`/`connectChannel`/`acceptFromChannel`/`read`/`write`/
`closeBridge`/`destroyChannel` 전부를 Syscall endpoint(SP-04EE2A18,
PL-21344323)로 구현했다. **착수 전제조건**이었던 Syscall 디스패치
(PL-21344323, 완료)를 그대로 재사용했다. 구현 자체는 매끄러웠지만,
이 서브시스템을 검증하려고 만든 4-Task 동시 동작 스트레스 테스트가
**스케줄러/AsyncTask 프레임워크에 남아 있던 진짜 동시성 버그 넷**을
실측으로 드러냈다 - 이 문서 후반부에서 그 발견/수정 과정을 상세히
기록한다(각 버그의 정본 수정 위치는 PL-2D3184BC/PL-1E247831/
PL-21344323에도 교차 기록).

## 배경

SP-1FBC0EEB 참고 - Channel(랑데부 지점)/BridgePipe(연결된 반쪽,
전이중 raw binary 링버퍼) 모델, `/sys/live/named/` 이름 있는
오브젝트 네임스페이스(종류 은닉 보안 정책), 링버퍼 크기 정책(커널
고정값 + huge page 플래그), `read`/`write` 기본 비동기(제출/대기
분리) 전부 이미 승인된 설계 그대로 구현한다. 이번 구현 범위는
**커널 내부 dispatch만**이다 - ring3 syscall 트랩 진입 자체가 아직
없어(PL-21344323 "남은 것" 참고) 유저랜드에서 직접 호출하는 경로는
없고, 커널 내부에서 `Syscall::submit`/`wait`을 직접 불러 API 계약과
상태 기계를 완전히 검증했다(PL-21344323이 이미 확립한 "ring3 진입
없이도 dispatch 계층은 실측 검증 가능하다"는 원칙 그대로).

## 구현 (완료된 부분)

### 1. 이름 있는 오브젝트 테이블 - `minicore/kernel/named_object.h/.cpp`

설계 문서의 "`/sys/live/named/` 가상 파일" 절 그대로 - 실제 VFS/`fs`
서비스가 아직 없어(SP-8B6B8D25 §2-A, 그리고 2026-09-14 설계자 메시지
"VFS의 루트는 커널이 소유하고 관리하는데, 마운트 포인트에 대한
실질적인 처리를 커널 서비스인 `fs` 서비스가 처리한다" - 이 메시지
자체는 SP-8B6B8D25에 반영, 아래 "관련 설계 결정" 참고) 커널 자체
내부 테이블로 구현했다: `NamedObjectTable::reserve/resolve/release`,
고정 배열(`kMaxNamedObjects=128`, `kMaxNamedObjectNameLength=64`,
v1 상한), 이름 바이트를 슬롯에 직접 복사(`memcmp`로 비교). **종류
은닉 보안 정책 그대로**: `reserve()`는 이미 쓰이는 이름이면 그
오브젝트가 무슨 종류든 똑같이 `false`만 반환한다.

### 2. Channel/BridgePipe/RingBuffer - `minicore/kernel/channel.h/.cpp`

- **`Channel`**: `Spinlock lock`, `destroyed`/`hasName`/`name` 필드,
  `PendingConnectRequest`(연결 요청 하나 - `AsyncTask* task`,
  `done`/`rejected`/`resultBridge`) FIFO(단순 침습적 포인터 - 이미
  `channel->lock`으로 보호되므로 `TaskQueue`류의 락-프리 큐가
  불필요), `pendingAccepters`(대기 중인 accept 호출이 없을 때 자기
  자신을 등록해 두는 `AsyncTaskWaitQueue` - **[갱신, 2026-09-15,
  PN-C9625015]** 원래는 단일 슬롯이라 같은 채널에 동시에 진행 중인
  `acceptFromChannel`이 하나만 지원됐으나(두 번째부터는 슬롯을
  덮어써 첫 번째가 영구히 못 깨어나는 결함), `AsyncTask::next`를
  재사용하는 FIFO 큐로 교체해 여러 개가 동시에 대기해도 전부
  순서대로 처리되도록 확장). raw slab 메모리 위에 놓이므로(placement
  new 없음) `Channel::init()`에서 모든 필드를 명시적으로 리셋한다
  (AsyncTask::init()과 동일한 이유).
- **`RingBuffer`**: 한 방향 raw binary 링버퍼(`data`/`capacity`/
  `readPos`/`writePos`/`used`) + `pendingReaders`/`pendingWriters`
  (`AsyncTaskWaitQueue`, **[갱신, 2026-09-15, PN-C9625015]** 위와
  같은 이유로 방향당 단일 슬롯에서 FIFO 큐로 확장) - `read()`/
  `write()`가 빈 상태/가득 찬 상태를 만나면 이 큐에 자기 자신(현재
  실행 중인 AsyncTask)을 추가하고 `AsyncTask::yield()`로 리액터에
  양보한다.
- **`BridgePipe`**: `peer`(상대 반쪽 포인터) + `outbound`(이 반쪽이
  `write()`로 채우는 자기 소유 링버퍼 - 전이중은 두 `BridgePipe`가
  각자 `outbound`를 하나씩 가져서 자연히 성립: 내가 읽는 대상은
  `peer->outbound`) + `closedLocal`. **상대 쪽 닫힘 상태는 별도
  미러 필드 없이 `peer->closedLocal`을 직접 읽는다** - "양쪽 다
  닫혀야 반납"이 보장하는 수명 덕분에 항상 안전하게 역참조 가능하다
  (구현 판단, 새 DC 불필요 수준). `BridgePipe::createPair`가
  `GenericSlabAllocator`로 구조체 2개 + 링버퍼 데이터 2개를 확보해
  서로를 잇는다 - `useHugePage=true`면 즉시 실패(아래 4번 참고).
- **`kIsBridgeBroken(bridge)`**: `bridge->closedLocal ||
  bridge->peer->closedLocal` - 이 반쪽 또는 상대가 닫혔으면 무조건
  `true`(설계 문서의 "닫힌 파이프 처리" 그대로 - 0바이트로 EOF를
  표현하지 않고 항상 `BrokenPipe` 에러 코드).

### 3. ChannelId/BridgeHandle 표현 - 구현 판단(새 DC 불필요 수준)

설계 문서는 "ChannelId는 다른 프로세스에게 전달, BridgeHandle은
로컬 참조"로 구분하지만, 프로세스 모델 자체가 아직 없어(핸들
테이블/fd 개념 없음) 이 구분이 지금은 의미가 없다 - **Syscall
서브시스템의 토큰=포인터 관례**(PL-21344323)를 그대로 따라
`ChannelId`/`BridgeHandle` 둘 다 그 오브젝트 구조체 자신의 포인터
값으로 채운다(`openChannel`은 둘을 같은 값으로 반환). 프로세스
모델이 생기면 로컬 핸들 테이블을 끼워 넣는 계층을 추가하면 된다
(관련 계획: Channel ID 전달 메커니즘, PN-6D497EB0).

### 4. 링버퍼 크기 정책 - `kChannelRingBufferSize`(4K) 고정 + huge page 지원

`kChannelRingBufferSize = 4096`(v1 고정 상수, 커널 설정값 하나로
시작)이 기본이다. **[구현 완료, 2026-09-16, PN-34B34DB4, commit
2e183a7]** `useHugePage=true` 요청은 더 이상 즉시 실패하지 않는다 -
`PageFrameAllocator::allocOrder(9)`로 물리적으로 연속인 2MiB 블록을
확보해 `kPhysToVirt()`(paging.h)로 커널 가상주소를 바로 얻어 쓴다.
착수 전 이 절이 예상했던 `Paging::mapRange` 배선은 실제로는 필요
없었다 - 이 링버퍼는 커널만 접근하는 순수 커널 내부 메모리라(유저
주소공간에 매핑되지 않음) direct map(`kDirectMapBase`)이 이미 모든
usable 물리 메모리를 커널 가상주소공간에 1:1로 매핑해 두고 있어
새 페이지 테이블 엔트리 자체가 필요 없었다(`Paging::mapRange`는
이 물리 블록을 유저 프로세스 주소공간에도 노출해야 하는 시나리오 -
예: 미래 Tier A 공유메모리 - 에나 필요). `ChannelError::
HugePageUnsupported`는 이제 이 경로에서 반환되지 않는다(할당 실패는
`ResourceExhausted`로 통일) - enum 값 자체는 API 호환을 위해 유지.
아직 `connectChannel(useHugePage=true)`를 실제로 호출하는 유저랜드
소비자는 없다 - 아래 "남은 것"의 동시성 스트레스 테스트(PN-0367CDBA)
가 이 옵션까지 다루게 되거나 devmgr/fs 실코드가 생길 때 실제 syscall
왕복 경로로 재검증한다.

### 5. 7개 syscall endpoint - `minicore/kernel/channel.h`(상수)/`.cpp`(핸들러)

`kSyscallEndpointSelfTerminate`(0, PL-2D3184BC "Task 종료 프로토콜"
전용) 바로 다음부터 1~7번을 배정 - `OpenChannelHandler`/
`ConnectChannelHandler`/`AcceptFromChannelHandler`/
`ChannelReadHandler`/`ChannelWriteHandler`/`CloseBridgeHandler`/
`DestroyChannelHandler`, 각각 `AsyncTaskHandler`를 구현해
`Channel::registerSyscallEndpoints()`(부팅 시 1회 호출, `kmain.cpp`)
로 등록한다.

- **`OpenChannel`**: 이름 있으면 `NamedObjectTable::reserve` 먼저 -
  실패하면 방금 만든 `Channel`을 되돌리고 `NameInUse`. 블로킹 없음.
- **`ConnectChannel`**: 이름/ID로 채널을 찾고, `PendingConnectRequest`
  를 **스택(자기 AsyncTask 전용 스택) 지역 변수**로 만들어 채널 큐에
  넣는다 - AsyncTask 스택풀 컨텍스트 보존 덕분에(PL-1E247831에서 이미
  검증된 성질) `while (!req.done) AsyncTask::yield();` 루프로 안전하게
  대기할 수 있다(포인터가 스택 위에 살아 있는 동안 다른 AsyncTask가
  그 포인터로 결과를 채워 넣고 깨움).
- **`AcceptFromChannel`**: 대기 큐에 요청이 있으면 즉시
  `BridgePipe::createPair`로 handshake를 완료하고 양쪽을 깨운다 -
  없으면 `pendingAccepter`에 자기 자신을 등록하고 yield.
- **`ChannelRead`/`ChannelWrite`**: 위 "RingBuffer" 절의 대기/깨움
  패턴을 그대로 수행 - 성공하든 `BrokenPipe`로 끝나든 항상 상대편의
  대기자(있으면)를 `AsyncReactor::submitCompletion`으로 깨운 뒤 반환.
- **`CloseBridge`**: 멱등(이미 닫혔으면 그냥 성공) - `closedLocal`을
  세우고 `kWakeForClose`로 "내 outbound를 읽던 상대의 pendingReaders
  큐"와 "상대 outbound에 쓰려 대기하던 나의(또는 과거의)
  pendingWriters 큐"를 **전부(대기자가 여럿이어도 빠짐없이,
  PN-C9625015)** 깨운 뒤, 양쪽 다 닫혔으면 `BridgePipe::destroyPair`
  로 실제 반납.
- **`DestroyChannel`**: 멱등 - 대기 중이던 `pendingAccepters`
  큐 전체(여럿이어도 빠짐없이)/모든 `PendingConnectRequest`를 전부
  실패(`rejected=true`)로 깨우고,
  이름이 있으면 `NamedObjectTable::release`, 마지막으로 `Channel`
  구조체 반납.

## 실측 검증(QEMU) - 그리고 그 과정에서 발견한 스케줄러 버그 넷

echo(에코) 서버/클라이언트 2개 + "닫힌 파이프" accepter/connector
2개, 총 4개의 `UserThread` 임시 드라이버(검증 후 제거)로 다음을
확인했다:

- **이름 충돌**: 같은 이름으로 두 번째 `openChannel` 시도 →
  `NameInUse`.
- **정상 왕복**: server가 `openChannel`(이름 있음) → client가 이름
  으로 `connectChannel` → server `acceptFromChannel`로 handshake →
  양방향 `write`/`read`로 `"PING"`/`"PONG"` 정확히 교환 →
  `closeBridge` 양쪽 → `destroyChannel`.
- **이름 재사용**: `destroyChannel` 이후 같은 이름으로 다시
  `openChannel` → 성공(이름이 실제로 반납됐음을 확인).
- **닫힌 파이프**: accepter가 accept 직후 곧장 블로킹 `read`를
  걸어 두고(데이터 없음), connector는 아무것도 쓰지 않고 곧장
  `closeBridge`만 호출 - accepter의 블로킹 read가 `BrokenPipe`로
  정확히 깨어남을 확인(`kWakeForClose` 경로).

**단일 코어(PVH/GRUB)는 첫 시도부터 항상 깨끗하게 통과**했다. 문제는
**4코어 SMP(`q35 -smp 4`)**였다 - 처음엔 거의 매번(체감상 90% 이상)
`Double Fault`/`General Protection Fault` 또는 완전한 행업으로
실패했다. 아래는 그 원인을 하나씩 벗겨낸 실측 기록이다(전부
`Scheduler`/`AsyncReactor`/`Syscall`의 **기존** 코드에 있던 문제고
Channel IPC 자체의 버그는 아니었다 - Channel IPC가 그동안 다른
서브시스템이 겪어보지 못한 수준의 AsyncTask 제출/yield 밀도로
스트레스를 준 게 발견의 계기였을 뿐).

### 버그 1 - `AsyncReactor::submitCompletion`의 "리액터가 지금 도는 중인지" 오판

`Scheduler::currentTask() != &gReactorTasks[coreIndex]`로 "리액터가
안 돌고 있으니 깨워야 한다"를 판단했는데, 스케줄러 틱이 리액터
Task를(어떤 onExec 실행 도중이든) Task 수준에서 그냥 보통의
라운드로빈으로 선점해 버리면 `currentTask()`가 더 이상 리액터를
가리키지 않게 된다 - 그 순간 다른 Task가 `submitCompletion`을
부르면 "안 돌고 있다"고 오판해 `scheduleImmediate`로 리액터를 또
다른 큐에 넣어, 같은 Task가 두 큐에 동시에 들어가는 이중 스케줄링이
된다. **수정(1차)**: `gReactorParked[coreIndex]`라는 전용 플래그를
신설 - `reactorTaskEntry()`가 진짜로 `parkCurrent()`를 부르기
직전에만 `true`로 세우고, `submitCompletion()`이 그 값을 확인+
소비(`false`로 되돌림)하는 것으로 대체(`Scheduler::currentTask()`가
무엇이든 상관없이 정확하다). `async_task.cpp`.

### 버그 2 - 리액터가 AsyncTask 실행 중에 Task 수준으로 선점됨

버그 1의 플래그만으로는 부족했다 - 리액터가 어떤 AsyncTask의 onExec을
실행하는 도중에 Task 수준 틱으로 선점되면, `gCurrentTask[coreIndex]`
가 다른 Task로 바뀌는 동안 리액터는 "그냥 보통의 Ready Task"로
취급돼 여러 경로에서 상태 불일치가 생길 수 있다. **수정**:
`reactorTaskEntry()`가 AsyncTask 하나를 실제로 구동하는
`kContextSwitch` 호출 전체를 `PreemptionGuard`로 감싼다 - AsyncTask
프레임워크의 원래 설계 의도(SP-F682B889, "리액터가 AsyncTask를
실행하는 동안 바깥 Task 수준에서는 여전히 리액터가 실행 중이어야
한다")를 실제로 강제한다(이전에는 kContextSwitch의 기계적 안전성에만
기대고 있었을 뿐 이 불변조건 자체는 강제되지 않았다). `async_task.cpp`.

### 버그 3, 4 - `parkCurrent()` 호출 "직전" 틈

`reactorTaskEntry()`(popFront가 비어 있음을 확인한 시점과
`parkCurrent()` 진입 사이)와 `Syscall::wait()`(`PreemptionGuard`
스코프가 끝난 시점과 `parkCurrent()` 진입 사이) 둘 다 **"진짜로
블로킹하기로 결정한 시점"과 "실제로 blocked 상태가 되는 시점"
사이에 틈이 있었다** - 그 틈에 스케줄러 틱이 끼어들면 이 Task를
(아직 parkCurrent를 부르지 않았으니) 그냥 보통의 라운드로빈으로
재큐잉해 버리고, 뒤이어 다른 Task의 `scheduleImmediate` 호출이
(waitingTask/pendingAccepter 등은 이미 세팅돼 있으므로) 또 다른
큐에 넣어 이중 스케줄링이 된다 - **runLoop()/yieldCurrent()에서
PL-2D3184BC 8-부분 단계 때 이미 실측 발견했던 것과 정확히 같은
근본 원인이, `parkCurrent()`를 부르는 다른 두 지점에서 각각 다시
나타난 것**이다. **수정**: 두 곳 모두 `parkCurrent()` 호출 직전에
`asm volatile("cli")`를 추가(`parkCurrent()` 자신의 cli와 중복이라
무해) - `async_task.cpp`(`reactorTaskEntry`), `syscall.cpp`
(`Syscall::wait`).

### 버그 5(근본 수정) - `Task::inRunQueue` 구조적 방지책

버그 1~4를 전부 고친 뒤에도 SMP4에서 **약 1/20~1/30 확률로 여전히
같은 부류의 크래시/행업이 재현**됐다 - 위 네 지점을 개별적으로
찾아 막는 방식으로는 "스케줄러 틱이 끼어들 수 있는 모든 지점"을
전부 열거하는 게 원리상 불가능하다는 뜻이었다(같은 근본 원인이
아직 찾지 못한 다른 지점에서도 나타날 수 있음). **구조적으로
해결**: `Task`에 `bool inRunQueue`(기본 `false`) 필드를 신설 -
`Scheduler::enqueue()`/`scheduleImmediate()`가 push 직전에 `cli`로
보호된 구간에서 이 플래그를 확인하고, 이미 `true`면(=이미 세 큐 중
어딘가에 들어가 있음) **조용히 재삽입을 생략**한다. `pickNext()`가
실제로 큐에서 꺼내는 순간 다시 `false`로 내린다. **`state`
(Ready/Running/...)는 이 용도로 못 쓴다** - `Task::init()` 직후에도
이미 `state=Ready`라 "아직 한 번도 큐에 들어간 적 없음"과 "이미
큐에 있음"을 구분하지 못하기 때문에 별도 플래그가 필요했다(이
차이를 놓쳐 처음엔 `state==Ready` 체크로 잘못 구현했다가, 리액터의
"최초 1회 enqueue"가 조용히 무시돼 아예 실행되지 않는 회귀를 만들고
바로 잡음 - `Task::init()`이 `state`를 이미 `Ready`로 초기화해
두므로). `task.h`(필드), `scheduler.cpp`(`enqueue`/
`scheduleImmediate`/`pickNext`).

### 방법론적 발견 - 진단용 `Serial::write` 자체가 경쟁 창을 왜곡시켰다

버그 1~4만 고친 상태에서 진단용 추적 로그(각 단계마다 `Serial::write`
호출)를 잔뜩 심어 둔 채로 재현율을 쟀을 때는 여전히 거의 매번
실패했지만, **그 추적 로그를 전부 제거한 "실제 배포될 코드"로 다시
재보니 20번 중 19번 통과**로 급격히 좋아졌다 - 시리얼 폴링 I/O가
느려서 한 줄 출력에도 여러 스케줄러 틱 주기(10ms)가 걸릴 수 있고,
그만큼 "취약한 구간에 머무는 시간"을 인위적으로 늘려 버그 표출
확률을 왜곡시킨 것이다. **교훈**: 이런 종류의 타이밍 의존적 경쟁을
스트레스 테스트할 때는, 버그 5(구조적 수정) 적용 이후 **반드시
진단 코드를 걷어낸 최종 형태로 재검증**해야 한다 - 로그가 많을수록
"더 잘 재현되는" 것도, "덜 재현되는" 것도 아니고 근본 원인과 무관한
왜곡을 만들 수 있다.

### 최종 재검증 결과

버그 5까지 전부 적용하고 임시 코드를 완전히 제거한 배포용 빌드로:

- **SMP4(`q35 -smp 4`) 연속 50회 무크래시**(첫 30회 + 확인 20회,

임시 드라이버 Task/추적 로그는 전부 제거 - 영구 코드는
`named_object.h/.cpp`, `channel.h/.cpp`, `kmain.cpp`의
`Channel::registerSyscallEndpoints()` 호출 한 줄, 그리고 버그
수정으로 남은 `task.h`(`inRunQueue`)/`scheduler.cpp`(`enqueue`/
`scheduleImmediate`/`pickNext`)/`async_task.cpp`
(`gReactorParked`/`PreemptionGuard`/`cli`)/`syscall.cpp`(`cli`)뿐이다.

## 관련 설계 결정 - VFS 루트 소유권 (설계자 메시지, 2026-09-14)

> VFS의 루트는 커널이 소유하고 관리하는데, 마운트 포인트에 대한
> 실질적인 처리를 커널 서비스인 `fs` 서비스가 처리한다.

`/sys/live/named/`는 이 원칙과 일치한다 - **커널이 소유·관리하는
VFS 루트의 일부**(`sys/live/` 자체가 이미 SP-8B6B8D25 §4에서 "이
시스템을 지탱하는 커널과 커널 서비스들이 담당"으로 정의됨)로서,
실제 마운트/파일시스템 드라이버 처리(`fs` 서비스의 몫)와는 별개로
커널이 직접 관리하는 순수 이름 테이블이다 - 이번 v1 구현이 이미
그 구도를 그대로 따르고 있었다(설계자 확인 완료). 이 원칙 자체는
SP-8B6B8D25에 반영해 둔다(별도 참고).
