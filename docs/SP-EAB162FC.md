# 프로세스 신원 및 커널 서비스 권한(Capability) 체계 — 설계 제안

QU-E6D37232(SP-71DA77B3 §3 "미결" - exclusive 인터럽트 구독 자격
검증) 설계자 답변(2026-09-15)에 따라 새로 작성한다: "그러면 프로세스
신원/권한 체계 설계안을 작성해. 그리고 그 설계안을 해당 PnP 관련
문서에 태깅해놔."

## 0. 왜 필요한가 - 지금까지 드러난 두 개의 독립된 구멍

이 프로젝트에는 지금까지 "이 프로세스가 신뢰할 수 있는 커널
서비스인가"를 syscall 레벨에서 검증하는 메커니즘이 전혀 없다.
구체적으로 이미 두 곳에서 이 구멍이 확인됐다:

1. **SP-9DD4F3EA §3.3 `RequestIoPermission`** - 요청자가 누구인지
   전혀 확인하지 않는다. `DeviceOwnerTable`은 "이 BAR를 이미 누가
   점유했는지"만 확인할 뿐, "애초에 이 프로세스가 장치 IO 권한을
   요청할 자격이 있는 프로세스인지"는 확인하지 않는다 - 지금 설계
   그대로 구현하면 임의의 유저 프로세스가 아직 아무도 안 가져간
   장치의 MMIO/IRQ를 그냥 요청해서 가로챌 수 있다.
2. **SP-71DA77B3 §3 `SubscribeInterrupt(exclusive=true)`** - "커널
   서비스에게만 허용"이라는 요구사항(설계자 지시)은 있으나, 그
   자격을 판정할 근거 자체가 없어 QU-E6D37232로 질의했다.

두 구멍 다 같은 근본 원인(프로세스 신원/역할을 커널이 추적하지
않음)이므로 이 문서에서 한 번에 다룬다.

## 1. 설계 원칙 (v1 - 최소 범위)

이 프로젝트 전반의 관례(SP-71DA77B3 §9 등에서 반복 확인된 패턴 -
"동적 재구성 API는 만들지 않고, 필요하면 명시적으로 다시 등록한다")를
그대로 따른다:

- **역할(Role) 재조정 API를 두지 않는다** - 한 번 정해진
  `ProcessRole`은 그 프로세스가 살아있는 동안 절대 바뀌지 않는다.
- **위임/상속 체인을 두지 않는다** - "커널 서비스가 낳은 자식은
  자동으로 커널 서비스"같은 규칙은 v1에 없다(권한 상승 경로를
  최소화하기 위함). 커널 서비스가 될 수 있는 프로세스는 오직
  부팅 시 커널이 직접 만드는 고정된 집합뿐이다.
- **유저랜드가 스스로 "나는 커널 서비스다"라고 선언할 방법이
  없다** - 자기 선언 API는 아예 만들지 않는다(가장 흔한 공격
  표면이므로).

## 2. 메커니즘

### 2.1 ProcessRole - 부팅 시점에만 확정되는 불변 속성

```cpp
enum class ProcessRole : uint8_t {
    Normal = 0,        // 기본값 - 일반 유저 프로세스, exec()/fork()로 만들어진 모든 프로세스
    KernelService = 1, // devmgr/fs/net/tty/pubreg 등 - 오직 부팅 매니페스트로만 부여
};
```

`Process`(프로세스 제어 블록, process.h) 구조체에 `ProcessRole role`
필드를 추가한다 - 생성자에서 기본값 `Normal`로 초기화, 이 필드를
바꾸는 setter는 만들지 않는다(위 원칙).

### 2.2 부팅 매니페스트 - 누가 KernelService인가

`kmain.cpp`의 초기 부팅 시퀀스(SP-8B6B8D25 §2-A가 이미 "devmgr을
커널이 유저랜드 서비스로 직접 기동한다"고 전제한 지점)에서, 커널이
initrd/부트 모듈로부터 고정된 이름 목록(`devmgr`, `fs`, `net`,
`tty`, **`pubreg`**[추가, 2026-09-16, 설계자 지시 - SP-B071E628
"프로세스간 공개 인터페이스" 재설계로 5번째 커널 서비스 신설] -
SP-8B6B8D25 §3 디렉터리 규칙이 이 다섯 이름을 공식화해 둠)과
정확히 일치하는 실행 파일만 `ProcessRole::KernelService`로 스폰한다.
**[개정, QU-3AAAB5E9 답변, 2026-09-15]** devmgr이 PnP 드라이버
스폰 경로(SP-9DD4F3EA §3.2, `probe()` 성공 시 자식으로 띄우는
AHCI/USB 등)로 만든 자식 프로세스도 `KernelService`로 부여한다 -
당초 초안의 "devmgr 자식조차 Normal"은 철회한다. 그 외 모든
프로세스 생성 경로(`fork`/`exec` syscall 등 devmgr을 거치지 않는
일반 생성)는 여전히 예외 없이 `Normal`이다.

이것이 §1의 "위임/상속 체인 없음" 원칙을 깨는 게 아닌 이유:
devmgr(그 자신이 KernelService)이 도달할 수 있는 **단 하나의 고정
코드 경로**(PnP 드라이버 로더)로 태어난 프로세스만 해당한다 - 이건
"부모가 임의로 자식에게 역할을 위임"하는 일반 규칙이 아니라, §2.2
의 "부팅 매니페스트 이름 일치"와 완전히 같은 성격의 **두 번째 고정
인식 경로**일 뿐이다(둘 다 유저랜드가 스스로 선언할 수 없고, 커널이
자기 자신의 코드로만 확정한다는 점이 동일).

**신뢰 근거(설계자 지시)**: "드라이버들은 각 역할별로 별도의
프로세스로 분기되어야 한다. 그리고 이렇게 분기된 서비스들은 모두
`유저 랜드`에서 구동되는 `커널 프로세스`다. 드라이버들은 모두
신뢰되는 것으로 간주하며, 설치할 때 `사용자`에게 고지되어야 하는
부분이라 생각한다." - 즉 드라이버 프로세스는 서드파티 유저
프로그램이 아니라 OS/드라이버 설치 시점에 이미 사용자에게 고지된
신뢰 컴포넌트라는 정책적 전제다. 이 고지 자체(설치 관리자 UX)는
커널 구현 범위 밖이라 이 문서는 "커널이 role을 어떻게 부여하는가"
까지만 다루고, "사용자에게 어떻게 고지하는가"는 향후 설치
관리자/패키지 시스템 설계 시 별도로 다룬다.

### 2.3 검증 지점 - 두 소비자를 이 문서가 함께 고정한다

- **SP-71DA77B3 §3 `SubscribeInterrupt(exclusive=true)`**:
  QU-E6D37232가 만든 "미결"을 이 검증으로 대체한다 -
  `exclusive=true`인데 `role != KernelService`이면 §7의 자격 실패
  에러로 거부. (이 소비자는 §4의 미결과 무관 - exclusive 인터럽트
  구독은 애초에 devmgr 자식 드라이버가 아니라 devmgr/fs/net/tty
  자신이 쓸 용도로 설계됐으므로 바로 적용 가능.)
- **SP-9DD4F3EA §3.3 `RequestIoPermission`**: **[확정, QU-3AAAB5E9
  답변]** 이 syscall에는 role 검증을 적용하지 **않는다** - §0이
  지적한 구멍은 role 검증이 아니라 §2.2의 신뢰 확장(드라이버 자식도
  KernelService)으로 이미 막혀 있다(호출자가 KernelService가 아니면
  애초에 그 코드 경로 자체가 devmgr/드라이버 프로세스 바깥에서
  실행될 일이 없다는 전제). `DeviceOwnerTable`의 소유권 확인만으로
  충분하다.

두 소비자 모두 이미 존재하게 될 필드 하나를 읽기만 하므로, 이
문서가 확정되면 양쪽 SP는 "미결"/제안 문구를 이 문서로의 참조로
교체하기만 하면 된다(새 syscall도, 새 자료구조도 필요 없음 -
RM-48E1E610 갱신 대상 없음).

## 3. PN-268F062B("공개 인터페이스 registry")와의 관계

혼동하지 않도록 명확히 구분한다 - 이 문서는 "이 프로세스가
누구인가"(신원/역할)를 다루고, PN-268F062B는 "이 프로세스가 어떤
서비스를 제공하는가"(디스커버리)를 다룬다. 전자가 후자의
전제조건이 될 수 있다(예: 공개 인터페이스 registry에 자신을 등록할
수 있는 자격도 결국 `ProcessRole::KernelService`로 제한하고 싶을
수 있음) - 하지만 이 문서는 그 연결을 강제하지 않고 열어 둔다.

## 4. 아직 열려 있는 설계 영역

- **devmgr이 띄우는 드라이버 자식 프로세스의 역할**: [해결됨,
  QU-3AAAB5E9] - §2.2 개정 참고, 드라이버 자식도 `KernelService`로
  부여하는 것으로 확정됐다.
- **KernelService 프로세스가 죽었다가 재시작되면?**: [해결됨,
  QU-3AAAB5E9 - 같은 답변에서 `Resurrect` 시작 플래그로 확정] §6
  참고 - 재시작 시 role이 다시 부여되는지 여부는 §6의 재스폰
  메커니즘이 §2.2와 같은 스폰 경로(부팅 매니페스트 이름 일치 또는
  PnP 드라이버 로더)를 그대로 재사용하므로 자동으로 해결된다(role은
  "누가 스폰했는가"로 정해지지 "몇 번째 생애인가"로 정해지지
  않으므로 재스폰 때마다 자연스럽게 같은 role이 다시 부여된다).

## 5. 참고

PnP(SP-9DD4F3EA) §3.3 `RequestIoPermission`과 인터럽트 구독
(SP-71DA77B3) §3 `SubscribeInterrupt(exclusive)` 양쪽에 이 문서를
연관 문서로 링크해 둔다 - 두 소비자가 이 신원 체계에 의존한다는
사실을 추적한다.

## 6. 프로세스 시작 플래그 - Resurrect(즉시 자동 재시작) [신규,
설계자 지시, 2026-09-15]

"프로세스 Start flag로서 `죽으면 다시 되살림(Resurrect)`를 정의하고
이게 있으면 죽는 즉시 되살릴 수 있도록 설계하라"는 지시를 그대로
반영한다. `ProcessRole`과 마찬가지로 프로세스 생성 시점에 고정되는
불변 속성이라 이 문서(신원/권한 체계)의 자연스러운 확장으로 다룬다.

### 6.1 자료구조

```cpp
struct ProcessStartFlags {
    bool resurrect = false;  // true면 이 프로세스가 종료됐을 때 §6.4의 지연/백오프 일정에 따라 재생성한다(더 이상 "즉시"가 아님 - §6.3/§6.4 개정 참고)
    // [추가, 2026-09-15, 설계자 지시] 기존엔 "커널 서비스가 죽으면
    // 커널이 정상동작하지 않는다"고 암묵적으로 전제했으나, 이제
    // 그 전제를 명시적 플래그로 분리한다 - true(기본값, 기존 전제와
    // 동일)면 이 프로세스가 죽었을 때 즉시 커널 패닉(§6.4). false면
    // 패닉하지 않고 §6.4의 지연/백오프 일정으로만 재스폰을 시도한다.
    bool essential = true;
};
```

`Process`에 `ProcessStartFlags startFlags`를 추가한다(생성자에서
`{}`로 초기화, `role`과 마찬가지로 이 필드도 살아있는 동안 바꾸는
setter를 두지 않는다 - §1 원칙 확장).

### 6.2 재스폰에 필요한 것 - "같은 스폰 파라미터"란 무엇인가

v1에서 실제로 `Resurrect`가 걸릴 대상은 §2.2의 두 고정 스폰
경로(부팅 매니페스트 devmgr/fs/net/tty, PnP 드라이버 로더)뿐이다 -
이 둘은 이미 "무엇을 어떻게 다시 스폰하는가"에 필요한 정보(모듈
버퍼/경로, 인자)를 그 스폰 지점 자신이 들고 있으므로 별도의 범용
"스폰 파라미터 직렬화"가 필요 없다:

- 부팅 매니페스트 프로세스(devmgr 등): `kmain.cpp`의 각 스폰
  헬퍼(`kSpawnInitProcess`류)가 이미 참조하고 있는 모듈 버퍼를
  그대로 다시 `elf::Image::parse` + `Process::execImage`에 넘기면
  된다 - 부팅 시 딱 한 번 복사해 둔 버퍼(kmain.cpp의 `gInitImageBuffer`
  류 패턴)가 프로세스 생애와 무관하게 계속 살아있으므로 몇 번이든
  재사용 가능하다.
- PnP 드라이버 프로세스: devmgr 자신이 `probe()` 성공 시 이미 그
  드라이버 바이너리(경로/버퍼)를 알고 있는 상태에서 스폰하므로,
  같은 정보로 다시 스폰하는 것도 devmgr 쪽 책임이다.

**일반 `fork`/`exec` syscall로 만들어진 `Normal` 프로세스**의
`Resurrect`는 v1 범위 밖으로 명시한다 - 그런 syscall 자체가 이
프로젝트에 아직 없어(프로세스 생성은 지금까지 커널이 직접 부팅
시퀀스에서만 함) 재현할 "원래 스폰 파라미터"라는 개념 자체가 아직
성립하지 않는다. 그 syscall이 실제로 설계되는 시점에 이 플래그를
그 API의 인자로 노출할지 함께 확정한다.

### 6.3 트리거 지점 [개정, 2026-09-15, 설계자 지시 - "즉시" 전제 철회]

`Scheduler::retireTask(target)`을 호출하는 지점(현재
`SelfTerminateHandler::onExec`, scheduler.cpp) 직후 - 커널 스택
회수/`Process::destroy()`가 끝난 뒤 분기한다:

1. **`target->startFlags.essential == true`**: §6.2의 재스폰 경로를
   시도하지 않고 그 자리에서 곧바로 `kPanic("Essential service
   died: <프로세스명>")`류로 커널 패닉 - "커널 서비스가 죽으면
   커널이 정상동작하지 않는다"는 원래 전제가 `essential=true`인
   프로세스에는 여전히 그대로 적용된다(재시도해 봐야 소용없다고
   간주 - resurrect 플래그 값과 무관하게 우선한다).
2. **`target->startFlags.essential == false` && `resurrect == true`**:
   더 이상 "즉시" 재스폰하지 않는다 - §6.4의 지연/백오프 일정에
   따라 재스폰을 예약한다. 패닉하지 않는다(몇 번을 실패하든).
3. 그 외(`resurrect == false`): 기존과 동일하게 그냥 종료(재스폰
   없음, 패닉 없음).

### 6.4 비필수 서비스 재스폰 지연/백오프 [개정, 2026-09-15, 설계자
지시 - 무제한 즉시 재시작 폐기, 커널 패닉 조건이 §6.3의 "필수
서비스"로 이전됨]

**변경 배경**: 이전 초안(연속 5회까지 즉시 재시작 후 초과 시 커널
패닉)을 설계자가 다시 정정했다: "기존에 커널 서비스가 죽으면
커널이 정상동작 하지 않는다고 가정한다고 했었어. 그런데, 그걸
명시적인 플래그로 `필수 서비스`가 아님을 주고, 그걸 되살리는
간격을 조정할 수 있도록 만들며, `필수 서비스`가 죽었을 때만 `커널
패닉`하도록 변경해야해. 그걸 되살리는 간격의 기본값은 1분이고,
5회 실패시마다 1분씩 늘려서 최대 10분까지로 하자." - 커널 패닉의
방아쇠는 이제 "재시도 횟수 초과"가 아니라 §6.3의 "필수 서비스
여부" 하나뿐이다. `essential=false`인 서비스는 **패닉 없이
무한정** 재시도하되, 재시도 간격을 실패가 누적될수록 늦춘다(자원을
덜 태우면서 회복 가능성은 계속 열어 둠).

**카운터 배치**: `Process`(§2.1 `role`과 별개, 재스폰마다 이어지는
런타임 카운터라 `Process`에 직접 둔다)에 `uint32_t
consecutiveFailures = 0`(기존 `resurrectCount`에서 개명 - 더 이상
"패닉까지 남은 횟수"가 아니라 "백오프 계산용 연속 실패 횟수"이므로
이름을 그 의미에 맞춘다)을 추가한다. 재스폰 성공 시 옛 `Process`의
값을 그대로 이어받아 `+1`(§6.3의 옛 코드와 동일한 승계 방식).

```cpp
constexpr uint32_t kResurrectBaseIntervalMinutes = 1;    // 기본 간격
constexpr uint32_t kResurrectBackoffStepMinutes = 1;     // 5회마다 늘어나는 폭
constexpr uint32_t kResurrectBackoffEveryNFailures = 5;  // 이 실패 횟수마다 1단계씩
constexpr uint32_t kResurrectMaxIntervalMinutes = 10;    // 상한

uint32_t kResurrectIntervalMinutes(uint32_t consecutiveFailures) {
    uint32_t steps = consecutiveFailures / kResurrectBackoffEveryNFailures;
    uint32_t interval = kResurrectBaseIntervalMinutes + steps * kResurrectBackoffStepMinutes;
    return interval < kResurrectMaxIntervalMinutes ? interval : kResurrectMaxIntervalMinutes;
}
```

예: 실패 0~4회 → 1분 간격, 5~9회 → 2분, 10~14회 → 3분, ...,
45회 이상 → 10분(상한 고정, 그 이후로는 더 늘지 않고 영원히
10분 간격으로 계속 시도).
