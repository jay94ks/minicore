# 실행 계획: multiboot2 + GRUB 부팅 경로 추가

**[완료, 2026-09-14]** QA-26450C3E 체크됨. 아래는 완료 기록으로 남긴다.

DC-427BB6B2/DS-D4E5C451에서 미룬 항목. PVH가 이미 검증된 상태(boot.S,
QA-26450C3E)라 그 자산(GDT/페이지테이블/long mode 전환/higher-half
점프)을 재사용하고, "멀티부트2 헤더 + 32비트 진입점"만 새로 추가하는
방식으로 갔다.

## 선행 조건

- 없음(PVH 경로와 독립적으로 병행 가능).

## 한 것

1. **boot.S 리팩터링**: `pvh_start`에 있던 "GDT 적재 → 페이지 테이블
   구성 → long mode 전환 → higher-half 점프" 로직을
   `common_32bit_entry` 서브루틴으로 뽑았다 - `pvh_start`/`mb2_start`
   둘 다 자기 진입 상태(EBX/EAX)만 저장한 뒤 `jmp common_32bit_entry`
   로 합류한다. 파일 헤더 코멘트도 "PVH 전용"에서 "PVH/multiboot2
   공용"으로 갱신.
2. **부팅 정보 전달 방식**: `.boot.data`에 `saved_boot_protocol`(0=PVH,
   1=multiboot2)을 `saved_start_info` 옆에 추가 - 두 진입점이 각자
   써 두면 `higher_half_entry`가 `kMain`의 두 번째 인자(rsi)로 그대로
   넘긴다. `kMain` 시그니처가 `(startInfoAddr, bootProtocol)`로
   바뀌었다 - `Idt::init()` 이전에 프로토콜별로 memmap/rsdpPaddr를
   같은 형태(`HvmMemmapEntry` 배열 + 물리주소)로 통일해 두면, 그
   뒤(IDT/Paging/Acpi/PageFrameAllocator/Lapic/IoApic/Timer/PCI)는
   완전히 프로토콜 무관 공통 경로다(원래 PL이 제안한 두 옵션 중
   "부팅 프로토콜에 따라 다른 파서를 호출" 쪽을 택함).
3. **멀티부트2 헤더 복원**: `boot.S`의 `.boot.text` 맨 앞에 배치(magic
   0xE85250D6) - Entry Address 태그(type 3)로 `mb2_start`를 지정했다.
   링커 전역 `ENTRY()`/ELF `e_entry`는 여전히 `pvh_start`로 유지(Xen/
   QEMU의 PVH 로더는 `.note.pvh` ELF Note로 직접 점프하므로 영향
   없음) - GRUB만 이 태그로 `e_entry`를 재정의해서 쓴다. ELF 프로그램
   헤더가 이미 올바른 물리 적재 주소(`AT()`)를 담고 있어 GRUB의 ELF
   로더가 별도 Address 태그(type 2) 없이 그대로 로드할 수 있었다.
4. **멀티부트2 진입점 작성**: `mb2_start` - EAX 매직(0x36d76289) 확인
   (안 맞으면 시리얼도 없는 시점이라 로그 없이 `cli;hlt` 무한루프로
   방어), EBX(정보 구조체 물리주소) 보존 후 `common_32bit_entry`로
   합류.
5. **멀티부트2 정보 구조체 파싱**: `minicore/kernel/multiboot2.h/.cpp`
   신설. `Multiboot2Info::parse`가 태그 기반 가변 길이 구조를 훑어
   메모리맵 태그(type 6, entry_size만큼 건너뛰며 순회)를
   `HvmMemmapEntry` 정적 버퍼(최대 64개)로 변환하고, ACPI RSDP
   태그(신규=15 우선, 없으면 구형=14)에서 물리주소를 얻는다. MB2
   메모리 타입(1/3/4/5 + 그 외 전부 예약)을 `HvmMemmapType`으로
   직접 매핑(E820과 거의 동일한 규약이라 변환이 단순).
6. **GRUB ISO 빌드 스크립트**: `scripts/run-grub.sh` 신설 -
   `grub-mkrescue`로 ISO 생성(grub.cfg에 `multiboot2` 명령으로 커널
   로드), QEMU `-cdrom`으로 부팅. `scripts/run-qemu.sh`(PVH 전용)는
   그대로 두고 별도 스크립트로 분리했다.
7. **검증(실측, 2026-09-14, QEMU 8.2.2, grub-mkrescue/xorriso 2.12,
   WSL 환경에 이미 설치돼 있었음)**: `scripts/run-grub.sh`로 실제
   ISO를 만들어 GRUB 부트로더를 거쳐 부팅 - "minicore: booted via
   multiboot2 (GRUB, higher-half, long mode)" 배너로 시작해 메모리맵
   (PVH 경로와 완전히 동일한 7개 엔트리 - QEMU가 두 경로 모두 같은
   머신을 에뮬레이트하니 당연하지만, 파싱 결과가 바이트 단위로
   일치함을 실측 확인), ACPI MADT/SRAT(RSDP 태그를 거쳐 정상 접근,
   hpet=yes), PageFrameAllocator/LAPIC/IOAPIC/Timer(HPET)/PCI 열거
   까지 PVH 경로와 100% 동일한 로그로 완주함을 확인 - 이 프로젝트의
   모든 인터럽트 컨트롤러/타이머/PCI 서브시스템이 부팅 프로토콜과
   완전히 무관하게 동작함이 실측으로 증명됐다. `scripts/run-qemu.sh`
   (PVH)도 boot.S 리팩터 이후 회귀 없이 그대로 동작함을 재확인.
   ELF 파일의 첫 32768바이트 안(실제로는 오프셋 4096)에 멀티부트2
   매직이 들어있음도 별도로 바이트 스캔해 확인.

## 이번엔 안 한 것 (후속 과제로 남김)

- **BIOS/UEFI 직접 부팅**: multiboot2/GRUB은 여전히 BIOS 부트섹터
  (grub-mkrescow가 만든 하이브리드 ISO의 El Torito 부분)를 거친다 -
  UEFI 전용 부팅 경로(예: UEFI 애플리케이션으로 직접 실행)는 별도
  과제로 QA 체크리스트에 남겨 뒀다.
- **`Multiboot2Info`의 다른 태그(cmdline, 모듈, 부트로더 이름 등)
  파싱**: 지금은 메모리맵+RSDP 두 태그만 쓴다 - 커맨드라인 인자나
  initrd 모듈이 실제로 필요해지면 추가.

## 미결 사항

- 없음(원래 PL의 미결 사항 - grub.cfg 문법/타임아웃 - 은 구현 중
  `set timeout=0`으로 확정, 실사용에 문제없이 검증됨).
