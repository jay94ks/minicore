# ResourceGroup — cgroup 유사 자원 그룹 체계 설계 제안

**배경 지시(2026-09-17, 메시지)**:

> "새로운 설계 과제야: 리눅스의 cgroup과 유사한 체계가 필요해. 주요
> 기능으로 가져야 할 것은: 자원 제한(Resource limiting) - 그룹이
> 설정된 메모리 한도(파일시스템 캐시 포함)나 I/O 대역폭, CPU 사용량
> 한도를 넘지 못하도록 강제한다. 우선순위 부여(Prioritization) -
> 여러 그룹이 자원을 두고 경쟁할 때, 특정 그룹에 더 큰 몫을 배분할
> 수 있다. 제어(Control) - 프로세스 그룹 전체를 일시 정지(freeze)
> 시키는 등의 제어가 가능하다. 계정(Accounting) - 각 그룹이 실제로
> 얼마만큼의 자원을 사용했는지 집계한다."

## 0. 현재 상태 조사 — 이 위에 얹을 게 무엇인지

이 커널에 지금 없는 전제 조건들을 먼저 확인했다:

- **CPU 시간 계정 자체가 없다**: `Task`(task.h)는 `state`/`taskClass`/
  `affinityMask`/`numaNode`는 있지만 실행 시간을 누적하는 필드가
  없다 - 이 문서가 그 기반부터 추가해야 한다.
- **프로세스별 메모리 사용량 집계도 없다**: 물리 메모리 할당자는
  page+buddy+NUMA(DS-D4E5C451)지만 "이 페이지가 어느 Process 몫인지"
  역추적하는 메커니즘이 없다(MMIO 소유권을 추적하는 `DeviceOwnerTable`
  같은 선례는 있으나 일반 페이지 대상은 아님).
- **파일시스템 캐시 자체가 없다**: `fs` 서비스가 0% 구현(SP-7CC5693A
  approved, 코드 없음, AHCI/USB 드라이버 대기 중) - "메모리 한도(파일
  시스템 캐시 포함)"의 캐시 부분은 지금 강제할 대상 자체가 없다.
- **I/O 대역폭을 잴 실제 I/O 경로가 거의 없다**: 블록 장치 드라이버가
  전부 미구현이라 디스크 I/O 대역폭 제한은 당장 검증 불가 - Channel
  IPC(이미 구현됨)의 바이트 처리량은 지금도 잴 수 있다.
- **프로세스 트리는 이미 있다**: `Process::parent`(`WeakPtr`)/
  `children`(`ChunkedList<SharedPtr<Process>>`, process.h) - `fork()`
  계열 상속 모델의 기반은 이미 존재.
- **uid/gid 권한 체계가 없다**(`PN-617F4E52`, 아직 미설계) - 그룹
  이동/설정에 대한 권한 판정은 이 문서가 자체적으로 좁은 v1 스코프를
  두고, 완전한 판정은 `PN-617F4E52` 완료 후로 미룬다(procfs 자식
  pid 열람과 같은 패턴, `PN-85FA4992` 참고).

**결론**: 이 설계는 cgroup의 **구조(그룹 트리, 상속, 배치, 4대
기능의 훅 지점)**를 지금 확정하되, 실제로 강제할 자원 중 **CPU만
지금 온전히 동작 가능**하고 메모리/IO는 v1에서 회계 인프라부터
새로 놓아야 하며, "캐시 포함 메모리"/"디스크 IO 대역폭"은 그
대상(fs/AHCI)이 생기기 전까지는 훅만 마련해 두고 실제 강제는 유예된다
(RM-23F4B687 §4 "정당한 유예" 패턴, `SP-00CA7175`의 Tier A 사례와
동일).

## 1. 핵심 자료구조 — `ResourceGroup`

Linux cgroup v1(어느 노드에나 프로세스가 있을 수 있음)이 아니라
**cgroup v2 스타일(leaf-only)**을 채택한다 - 내부 노드(자식 그룹이
있는 그룹)는 프로세스를 직접 담지 않고, 프로세스는 항상 **말단
그룹**에만 속한다. 이유: 내부 노드에 프로세스와 자식 그룹이 동시에
있으면 "내 프로세스 몫"과 "자식 그룹에 위임한 몫"을 나누는 규칙이
따로 필요해져 v1 스타일보다 훨씬 복잡해진다 - cgroup v2가 실제로
이 문제 때문에 leaf-only로 갔다(업계 선례, 이 프로젝트가 처음부터
새로 설계하는 이점을 살려 v1의 레거시 복잡도를 피한다).

```cpp
// minicore/kernel/resource_group.h (제안)
class ResourceGroup : public EnableSharedFromThis<ResourceGroup> {
public:
    // 트리 구조 - Process와 완전히 같은 패턴(parent는 관찰만, children이
    // 실제 소유자, process.h의 parent/children 주석 그대로 재사용).
    WeakPtr<ResourceGroup> parent;
    static constexpr uint32_t kMaxChildGroupsChunkCapacity = 8;
    ChunkedList<SharedPtr<ResourceGroup>, kMaxChildGroupsChunkCapacity> children;

    // 이 그룹에 직접 속한 프로세스들(leaf 그룹만 실제로 채워짐 -
    // 내부 노드는 항상 비어 있다, §1 leaf-only 원칙).
    static constexpr uint32_t kMaxMemberProcessesChunkCapacity = 8;
    ChunkedList<WeakPtr<Process>, kMaxMemberProcessesChunkCapacity> members;
    // members가 WeakPtr인 이유: Process의 진짜 소유자는 여전히
    // Process::parent 트리(§6 "고아는 init이 입양")다 - ResourceGroup은
    // 소속만 관찰한다, 이중 소유권 금지(RM-23F4B687 §1/process.h 관례).

    // §2 - 자원 제한.
    ResourceLimits limits;
    // §3 - 우선순위.
    uint32_t weight = 100;  // cgroup v2 cpu.weight와 동일 관례(기본 100)
    // §4 - 제어.
    bool frozen = false;
    // §5 - 계정(누적값, 증분식 - 매 조회마다 트리 재순회 안 함).
    ResourceUsage usage;

    // 이름(진단/procfs 노출용 - §7).
    char name[64] = {};
};

struct ResourceLimits {
    uint64_t memoryLimitBytes = UINT64_MAX;      // UINT64_MAX = 무제한
    uint64_t ioBandwidthLimitBytesPerSec = UINT64_MAX;
    uint32_t cpuQuotaPercent = 100;   // 그룹 전체가 쓸 수 있는 CPU 비율
                                       // (코어 1개 환산 - cgroup cpu.max와
                                       // 동일 관례, 멀티코어는 quota*coreCount)
};

struct ResourceUsage {
    uint64_t cpuTimeConsumedNs = 0;   // §5.1
    uint64_t memoryBytesInUse = 0;    // §5.2
    uint64_t ioBytesTransferred = 0;  // §5.3
};
```

**계층적 제한의 의미**: 자식 그룹의 한도는 부모 한도를 넘을 수
없다(cgroup 관례 그대로) - 강제 시점(그룹 생성/한도 변경 syscall)에
"부모 한도 이하인지" 검사한다. 사용량 집계는 **위로 전파**한다(자식이
쓴 자원은 모든 조상 그룹의 `usage`에도 함께 더해짐 - 조상 그룹에서
"이 서브트리 전체가 얼마나 썼는지" 바로 조회 가능, 매번 트리 순회
불필요).

## 2. 자원 제한 (Resource Limiting)

- **CPU**: `cpuQuotaPercent`를 period(예: 100ms, cgroup 관례와 동일)
  단위 quota로 변환해 스케줄러가 강제 - §5.1의 계정과 결합, 한
  period 안에 그 그룹 소속 Task들이 quota를 다 쓰면 그 그룹의
  Task들을 `Scheduler::pickNext()`가 이번 period 남은 시간 동안
  건너뛴다(cgroup의 CFS bandwidth throttling과 동일 원리) - 실제
  타이머 period 경계는 기존 HPET 틱(PL-E68894CD)에 얹는다(새 타이머
  소스 불필요).
- **메모리**: `memoryLimitBytes` - `usage.memoryBytesInUse`가 한도에
  도달하면 그 그룹 소속 프로세스의 새 페이지 할당(온디맨드 매핑/
  mmap/brk)을 거부(`ResourceExhausted`류 에러, OOM kill은 v1 범위
  밖 - §6). **[유예]** "파일시스템 캐시 포함"은 캐시 자체가 없어
  v1은 프로세스 주소공간 페이지만 계정 - 캐시가 생기면(fs 서비스
  구현 이후) 같은 한도에 합산하도록 확장(새 설계 아님, §5.2 확장).
- **I/O 대역폭**: 토큰 버킷(token bucket) - 그룹마다
  `ioBandwidthLimitBytesPerSec`를 토큰 재충전률로 사용, Channel
  `ChannelRead`/`ChannelWrite`(지금 유일하게 실제로 동작하는 I/O
  경로) 핸들러가 처리 직전 그 프로세스가 속한 그룹의 버킷에서 토큰을
  소비 - 부족하면 그 자리에서 즉시 실패시키지 않고 AsyncTask 완료를
  다음 재충전 시점까지 지연(스로틀링, 거부 아님 - Linux io.max와
  동일 원칙). **[유예]** 디스크 I/O(AHCI/USB 경유)는 그 드라이버가
  생기면 같은 버킷을 공유하도록 확장.

## 3. 우선순위 부여 (Prioritization)

`weight`(cgroup v2 `cpu.weight`, 기본 100)를 `Scheduler::pickNext()`/
Push-Pull 로드밸런싱(`SP-9525C4C0`)에 반영한다 - 같은 코어에서 여러
그룹의 Task가 동시에 Ready 상태로 경쟁하면, 그룹 간 배분은 **가중치
비례**(weight가 2배면 대략 2배의 CPU 시간을 받음, stride scheduling
류 - 정확한 알고리즘은 §8 열린 질문)를 따르고, **같은 그룹 안에서는
기존 `TaskClass`(Immediate→RT→Normal) 순서를 그대로 유지**한다 -
이 문서는 그룹 "간" 배분만 새로 정의하고 그룹 "안"의 기존 정책
(RM-23F4B687에 이미 기록된 스케줄러 우선순위 규칙)을 대체하지 않는다.

## 4. 제어 (Control) — Freeze

```cpp
// TaskState에 새 상태 추가(제안)
enum class TaskState {
    Ready,
    Running,
    Blocked,
    Zombie,
    Frozen,  // [신규] ResourceGroup::freeze() 호출로 진입 - Scheduler가
             // pickNext()에서 건너뜀. 강제 시점은 Kill의 시그널 전달과
             // 같은 원칙 - 다음 안전한 전환점(preemption/syscall 복귀
             // 직전)에서 상태를 바꾼다, 명령어 중간에 즉시 멈추지 않음.
};
```

`ResourceGroup::freeze()`/`unfreeze()`는 그 그룹의 `members`뿐 아니라
**모든 자손 그룹의 멤버까지 재귀적으로** 상태를 바꾼다(leaf-only라
실제 멤버는 항상 leaf에만 있지만, 내부 노드에 freeze를 걸면 그
서브트리 전체가 대상). 해제(`unfreeze`)는 `Frozen`이던 Task를 원래
있던 상태(대개 `Ready`)로 되돌린다 - freeze 시점 상태를 별도로
기억해 뒀다가 복원(단순히 `Ready`로 되돌리면 `Blocked`이던 Task가
freeze/unfreeze만으로 깨어나 버리는 부작용이 생기므로, `Task`에
`preFreezeState` 필드 하나 추가 필요).

## 5. 계정 (Accounting)

### 5.1 CPU 시간

`Task`(task.h)에 `uint64_t cpuTimeConsumedNs` 신설 - 스케줄러가
컨텍스트 스위치 아웃 시점마다 그 슬라이스 동안 흐른 시간(rdtscp 또는
HPET, `QA-08F8C96F` 실측 기반으로 착수 시 확정)을 더한다. 그 Task가
속한 Process → `ResourceGroup`으로 매 슬라이스마다 증분 전파(§1의
"조상까지 누적" 관례) - 트리 깊이만큼의 포인터 순회, 매 컨텍스트
스위치마다 발생하므로 스케줄러 핫패스에 부담 - **[열린 질문]** 매
슬라이스 즉시 전파할지, Task 자신에게만 쌓아 뒀다가 주기적으로(예:
HPET 틱마다) 배치로 그룹까지 밀어 올릴지는 §8에서 확인.

### 5.2 메모리

Process가 소유한 페이지(주소공간 매핑, `SP-2AAD7C8D` Maple Tree)
총량을 그 Process가 속한 그룹의 `usage.memoryBytesInUse`에 반영 -
매핑/해제(mmap/munmap/brk/페이지 폴트 온디맨드 매핑) 시점마다 증분
갱신(전체 재계산 아님).

### 5.3 I/O

§2의 토큰 버킷 소비량 자체가 곧 계정값(소비=사용량, 별도 카운터
불필요 - 토큰 버킷을 "무제한"으로 설정한 그룹도 계정을 위해 항상
버킷을 두되 재충전을 막지 않는 방식으로 구현).

## 6. 그룹 배치/이동 — v1 권한 스코프

- **배치(생성 시 상속)**: `SpawnProcess`로 새 Process가 생기면
  기본적으로 **부모 Process와 같은 그룹**에 배치된다(Linux fork()가
  cgroup을 상속하는 것과 동일) - 새 syscall 불필요, 기존 스폰 경로에
  한 줄 추가.
- **이동(명시적)**: 새 syscall `MoveToResourceGroup`(번호는
  `SP-E9B44929`의 그룹+call 인코딩이 확정되면 그 체계로 예약 -
  이 문서 단독으로 먼저 번호를 예약하지 않는다, 두 설계가 서로
  의존하므로 순서 조율 필요, §8 참고) - **v1 권한 스코프**: 호출자
  자신이거나 호출자의 직계 자식만 이동 가능(Kill v1과 동일한 좁은
  스코프, `PN-617F4E52` 완료 전까지의 임시 조치 - 완료되면 그 결과의
  RWX 판정으로 교체).
- **그룹 생성/삭제/한도 설정**: v1은 `ProcessRole::KernelService`만
  가능(일반 프로세스는 자기 그룹을 벗어난 그룹을 새로 만들거나 한도를
  못 바꿈) - 이것도 `PN-617F4E52` 완료 후 root/특정 권한 사용자로
  교체될 잠정 스코프.

## 7. procfs 노출 (선택 - 별도 계획으로 분리 가능)

Linux의 `/sys/fs/cgroup/`처럼, `SP-5D965B74`(procfs)가 이미 확장
중인 `/sys/live/proc/`(현재 `self/status`만) 아래에
`/sys/live/proc/groups/<name>/status`류로 그룹별 한도/사용량을
노출할 수 있다 - 이 문서는 그 확장이 **필요하다는 것만 기록**하고,
실제 스키마는 `SP-5D965B74`가 이미 쓰고 있는 확장 패턴(§4의 v1
`meminfo`/`uptime` 추가와 같은 성격, `PN-0C282BB7`)에 맡긴다 -
별도 PN으로 분리 등록(§9).

## 8. 열린 질문 — 설계자 확인 필요

1. **§1 leaf-only(v2 스타일) 채택에 동의하는지** - 내부 노드에도
   프로세스를 직접 둘 수 있어야 하는(v1 스타일) 실제 필요가 있다면
   구조가 달라진다.
2. **§3 그룹 간 CPU 배분 알고리즘** - stride scheduling/weighted
   round-robin류 후보 중 어떤 걸 v1로 할지, 아니면 "가중치 비례"라는
   목표만 확정하고 구체 알고리즘은 착수 시 정할지(RM-23F4B687 §4).
3. **§5.1 CPU 계정 전파 시점** - 매 컨텍스트 스위치 즉시 vs 주기적
   배치.
4. **§6의 syscall 번호** - `SP-E9B44929`(syscall 그룹+call 인코딩)가
   먼저 승인돼야 이 문서의 새 syscall(`MoveToResourceGroup` 등,
   그룹 생성/삭제/한도 설정용 몇 개 더 필요)이 어느 체계로 번호를
   받을지 정해진다 - 두 설계 문서 순서를 어떻게 조율할지 확인
   필요(이 문서가 먼저 approve되면 구식 평평한 번호로 임시 예약
   후 나중에 재인코딩할지, `SP-E9B44929` 확정을 기다릴지).
5. **OOM 상황(그룹 메모리 한도 도달 시 정책)** - 단순 할당 거부
   (§2)만으로 충분한지, 아니면 Linux OOM killer처럼 그 그룹 안에서
   무언가를 강제 종료하는 정책까지 v1에 포함해야 하는지 - killer는
   상당히 복잡한 정책 공간이라 기본은 "거부만"으로 제안, 확장이
   필요하면 별도 후속.

## 9. 후속 계획 (승인 이후 등록 예정)

- 핵심 구조체(`ResourceGroup`) + §2/§3/§4/§5 구현.
- `Task::cpuTimeConsumedNs`/`preFreezeState` 필드 추가.
- §7 procfs 노출.
- §8이 해소되고 `SP-E9B44929`도 확정되면 syscall 실제 구현.
