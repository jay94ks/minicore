DC-6E2500A6(QU-43F6DD1D 답변, 2026-09-16)의 결정을 실제 설계로
구체화한다.

## 1. 설계자 답변 요약 (원문 근거)

> 1. 커널 서비스별 전용 공유메모리 링버퍼(부팅 시 커널이 미리
>    매핑해 둠) - syscall 왕복 자체를 생략.
> 2. 판단 기준은 대규모 IO가 예상되는가? Channel IPC가 페이지
>    크기(예: 4K, 혹은 2M)에 맞춰진 제한된 크기인데 감당을 할 수
>    있는가? <-- 이게 판단 기준이야.
> 3. 이미 일반 syscall로 설계/구현된 것은 이 답변의 2번 항목과
>    문맥에서 큰 차이가 없을 거야.
> 4. 현재 있는 것들 중에서 2번 항목을 넘어서는게 있었던가?
> 5. 전용 트랩 벡터는 로드밸런싱으로 확장되기 어렵고(코어별로
>    분산을 수동으로 해야 하므로).
> 6. 배타적 선점형 Channel IPC를 도입해서 고속이 필요치 않은 곳에
>    적용하는 것은 괜찮아 보인다.

정리하면: **"고속"의 기준은 지연시간이 아니라 처리량/크기**다 -
Channel IPC의 링버퍼가 이미 페이지 단위(4K/2M) 크기 제한을 갖고
있는데(SP-1FBC0EEB "링버퍼 크기 정책"), 그 한도를 감당 못 할
만큼 대규모 IO가 오가는 트래픽만 전용 공유메모리 링버퍼(Tier A)가
필요하다. 전용 트랩 벡터는 로드밸런싱 확장성 문제로 기각. 그
기준을 넘지 않는 나머지 커널서비스 트래픽(소용량이지만 여전히
우선순위가 필요한 제어 트래픽)은 **"배타적 선점형 Channel
IPC"**(Tier B, 신설)로 처리한다.

## 2. 두 계층 구조

**[갱신, 2026-09-16, 설계자 지시]** "Tier A는 실 사용처가 없어도
설계 진행해." / "Tier B는 기존에 존재하는 Channel에서 옵션을 받아
확장하는 형태로 설계하고, 배치 위치는 커널이 예약하고, 예약
지점은 `/sys/live/kernel/`아래에 둔다." - 아래 두 절을 이 지시에
맞춰 전면 재작성했다.

**[정합성 정정, 2026-09-16]** 이 절은 두 세션이 거의 동시에 독립적으로
개정하다 한쪽이 다른 쪽을 덮어쓴 것을 발견해 병합한 버전이다 - 아래
§2.0~§2.2는 `KernelReservedTable` + `LiveFs::open()` 권한 검사를
핵심으로 하는 개정(더 안전함 - 이유는 §2.0 끝 문단 참고)을 그대로
채택하고, 거기에 `kCreateNamedChannel` 팩터링 메모(§2.0a)만 추가로
포함시켰다. 문서형 저장소는 낙관적 동시성 잠금(버전 충돌 감지)이
없어 이런 일이 재발할 수 있다 - 큰 개정을 저장하기 전에는
`docs read`로 최신 상태를 다시 확인하는 습관이 필요하다.

### 2.0 공통 배치 지점 - `/sys/live/kernel/` (신설, 커널 예약)

Tier A/B 둘 다 **커널이 부팅 시 직접 예약**하는 엔드포인트라는
공통점이 있다 - 기존 `/sys/live/named/`(SP-1FBC0EEB)는 **어떤
프로세스든 `openChannel(name=...)`로 먼저 개설하는 쪽이 이름을
갖는 경쟁적 네임스페이스**라 이 용도에 맞지 않는다(커널서비스가
아직 스폰되지 않은 시점에 커널이 미리 자리를 잡아 둬야 하고, 그
자리를 다른 프로세스가 먼저 채가면 안 됨). 그래서 `livefs`
(SP-7CC5693A §2.4, `LiveFs : KernelFsDriver`)에 **세 번째 하위
경로**를 추가한다 - 기존 `/sys/live/named/`(경쟁적 사용자 네임스페이스)
/`/sys/live/initrd.cpio`(불투명 blob)와 나란히:

```cpp
// minicore/kernel/livefs.h - 신규 커널 전용 예약 테이블. NamedObjectTable
// 과 달리 reserve()는 syscall로 노출되지 않는다 - 커널 자신의 부팅
// 코드만 호출하는 내부 API(mountKernel()과 같은 성격, §2.0a 참고).
struct KernelReservedEntry {
    char name[kMaxKernelReservedNameLen];  // 예: "devmgr", "fs", "net", "tty"
    uint32_t nameLen;
    void* tierA;       // KernelServiceSharedRingBuffer* - §2.1 참고, 없으면 nullptr
    uint64_t tierBChannelId;  // Tier B Channel의 ChannelId(§2.2) - 0이면 미배정
    bool used = false;
};

class KernelReservedTable {
public:
    static bool init();
    // 커널 부팅 코드 전용(§2.2 부팅 매니페스트와 같은 지점에서 호출) -
    // devmgr/fs/net/tty 각각에 대해 Tier A 링버퍼 + Tier B Channel을
    // 미리 만들어 이 표에 등록한다. syscall 아님.
    static bool reserveForKernelService(const char* name, uint32_t nameLen);
    static KernelReservedEntry* find(const char* name, uint32_t nameLen);
};
```

- `LiveFs::open("kernel/<name>", ...)`가 이 경로를 처리한다 -
  **호출자의 `ProcessRole`이 `KernelService`이고 그 프로세스의
  스폰 이름(§2.2)이 요청한 `<name>`과 정확히 일치할 때만** 성공,
  그 외(role이 다르거나 이름이 다른 KernelService, 또는 임의의
  `Normal` 프로세스)는 전부 `NotAuthorized`로 거부한다 - "커널이
  예약한 자리는 그 자리의 정당한 소유자만 열 수 있다"는 의미를
  경로 자체에 부여한다(`LiveFs::open()`이 이미 호출자 컨텍스트를
  아는 위치이므로 새 검증 계층 불필요, SP-EAB162FC의 `ProcessRole`을
  그대로 재사용).
- 성공하면 그 항목의 `tierBChannelId`(있으면 `tierA` 포인터/핸들도
  함께)를 반환 - 호출한 커널서비스 프로세스는 이후 `connectChannel`
  (Tier B)로 실제 데이터 채널에 연결하거나, Tier A 핸들로 그
  공유메모리를 매핑한다(§2.1).
- **왜 이 방식이 `NamedObjectTable::reserve()`를 그대로 쓰는 것보다
  안전한가**: 만약 커널이 그냥 `NamedObjectTable::reserve("kernel/devmgr",
  ...)`만 호출하고 라우팅을 `named/`와 동일하게 뒀다면, 그 이름을
  아는 **어떤 프로세스든** `connectChannel(name="kernel/devmgr")`로
  연결을 시도할 수 있었을 것이다(Channel의 기존 "이름을 아는 사람은
  누구나 connect 가능" 정책, SP-0666DB3C §17.3의 Mutex와 동일 신뢰
  모델) - 이름이 `named/` 밖에 있다는 사실 자체는 권한 검사가 아니다.
  `LiveFs::open()` 단계에서 `ProcessRole`+스폰 이름 일치를 명시적으로
  검사해야 비로소 "이 이름을 아는 것"과 "이 이름을 실제로 열 수
  있는 것"이 분리되고, 그 넷(devmgr/fs/net/tty) 각자의 전용 채널을
  진짜 그 서비스만 열 수 있다는 보장이 성립한다.

#### 2.0a `Channel` 생성 로직 팩터링 (구현 메모)

`KernelReservedTable::reserveForKernelService()`가 부팅 시 syscall
없이 직접 Tier B `Channel`을 만들려면, 지금 `channel.cpp`의
`openChannel` syscall 핸들러 안에 인라인돼 있는 alloc+init+
`NamedObjectTable::reserve` 로직을 재사용 가능한 형태로 뽑아내야
한다(순수 리팩터링, 기존 syscall 핸들러 동작 무변경):

```cpp
// channel.cpp(또는 channel.h)
Channel* kCreateNamedChannel(const char* name, uint64_t nameLength, ChannelError* outError);
```

`openChannel` syscall 핸들러도 이 함수를 호출하도록 바꾸고,
`reserveForKernelService()`는 이 함수로 만든 `Channel*`에
`->exclusivePreemptive = true`(§2.2)를 추가로 설정한 뒤
`KernelReservedEntry::tierBChannelId`에 담는다.

### 2.1 Tier A - `KernelServiceSharedRingBuffer` (대용량, 설계는 지금
진행 - 설계자 지시)

부팅 시 커널이 각 커널 서비스(devmgr/fs/net/tty)마다 하나씩 만들어
두는 전용 공유메모리 링버퍼 - syscall submit/wait 왕복 자체를
생략한다. 실사용 소비자가 아직 없다는 사실과 무관하게 설계는
지금 확정한다(TLB 샷다운 IPI, SP-DE19BB1C가 이미 같은 패턴의
선례).

```cpp
// minicore/kernel/kernel_service_ring.h(가칭)
struct KernelServiceSharedRingBuffer {
    // 헤더 + 데이터 영역을 한 물리 프레임 묶음에 배치 - Channel의
    // RingBuffer(PL-C8648D4D)와 같은 SPSC 링 레이아웃이지만, syscall
    // read/write 대신 양쪽이 직접 메모리를 건드린다.
    AtomicU32 writePos;
    AtomicU32 readPos;
    uint32_t capacity;   // v1 고정값(구현 착수 시 확정 - RM-23F4B687 §4)
    uint8_t data[];       // 가변 길이, capacity 바이트
};

// 커널 쪽: 부팅 시 §2.0의 reserveForKernelService()가 물리 프레임을
// 확보해 커널 direct map(항상 접근 가능)에 둔다.
// 유저 쪽: 그 커널서비스 프로세스가 §2.0으로 `kernel/<name>`을 열면
// 응답에 담긴 물리 프레임을 자신의 주소공간에 findGap()+
// VmaBacking::FixedPhysical(SP-2AAD7C8D §2)로 매핑한다 - devmgr의
// RequestIoPermission(SP-9DD4F3EA §3.3)이 MMIO를 매핑하는 것과
// 정확히 같은 경로 재사용, 새 매핑 메커니즘 불필요.
```

- **소비 통지**: 어느 쪽이 쓰든 읽는 쪽은 폴링하거나, 경량 "데이터
  도착" 신호(작은 Tier B syscall 1개 또는 §2.0에서 미리 배선해 둔
  인터럽트)로 깨어난다 - 정확한 신호 방식은 실사용 소비자가 정해질
  때 확정(현재는 자리만).
- **v1 스코프**: 방향(커널→서비스 전용 / 서비스→커널 전용 / 양방향)
  과 `capacity` 크기는 지금 결정할 필요가 없는 구현 세부로 남긴다
  (RM-23F4B687 §4) - 이 절의 목적은 "커널이 예약해 둘 자리와 그
  자리가 어떤 모양인지"까지다.

### 2.2 Tier B - `ExclusivePreemptiveChannel` (소용량, 현재 전
트래픽 해당)

기존 Channel IPC(PL-C8648D4D) 위에 얹는 우선순위/전용성 계층 -
**"기존 Channel에서 옵션을 받아 확장"**(설계자 지시)하는 형태로,
새 IPC 오브젝트를 만들지 않고 `Channel`에 플래그 하나만 추가한다.

```cpp
// PL-C8648D4D의 Channel 구조체에 플래그 추가(신규 필드, 다른 동작은
// 무변경 - 기본값 false).
struct Channel {
    // ... 기존 필드 그대로 ...
    bool exclusivePreemptive = false;  // 신설
};
```

- **"배타적"(exclusive) + "배치는 커널이 예약"**: 이 Channel은
  `openChannel(name=...)`로 경쟁 개설되지 않는다 - §2.0의
  `KernelReservedTable::reserveForKernelService()`가 부팅 시
  커널 코드에서 직접 §2.0a의 `kCreateNamedChannel()`로 만들어
  `tierBChannelId`에 등록해 둔다. 해당 커널서비스 프로세스는
  §2.0의 `LiveFs::open("kernel/<name>")`을 통해서만(권한 검사 포함)
  그 ChannelId를 받아 `connectChannel()`할 수 있다 - 이름 충돌
  방지가 아니라 애초에 발급 경로 자체가 봉쇄돼 있는 강한 배타성.
- **"선점형"(preemptive)**: `exclusivePreemptive=true`인 Channel에서
  발생한 AsyncTask(그 Channel의 `read`/`write`/`acceptFromChannel`
  등에서 파생된 것)는 그 코어의 `AsyncReactor` 실행 큐에서 일반
  우선순위보다 앞서 처리된다.
- **[정정, 2026-09-15, 설계자 답변 QU-1D44FA84]** "배타적"의 정확한
  의미 - "해당 채널에 연결될 수 있는 접속자가 단 1명 뿐이라는거야."
  즉 "배타적"은 **연결(accept/connect) 시점에 1개 접속만 허용**하는
  제약이지, `read`/`write` 각 호출이 개별적으로 무언가를 배타적으로
  갖는다는 뜻이 아니다 - `acceptFromChannel`이 이미 정확히 1명만
  받도록 강제하면(`channel->exclusivePreemptive`를 그 자리에서 직접
  확인 가능, 구현 중 실측 확인됨 - PN-7AC01E6E) 그 이후의 `read`/
  `write`는 이미 그 유일한 연결 위에서만 일어나므로 **`BridgePipe`에
  별도 필드를 추가할 필요가 없다**(구현 질문 (A)/(B) 중 (A)가 정답 -
  `acceptFromChannel` 시점의 단일 접속 강제만으로 배타성이 완성되고,
  "선점형"(우선순위 큐 배치)은 이미 성립된 그 연결에서 파생된
  `read`/`write` AsyncTask에도 그대로 적용하면 된다 - 이는 원래
  서술 그대로 유효, 새 자료구조 불필요).

## 3. 현재 설계된 kernel↔service 트래픽 전수 검토 (설계자 질문 4번
답변)

| syscall/경로 | 출처 | payload 규모 | Tier A 필요? |
|---|---|---|---|
| `EnumerateDevices` | SP-9DD4F3EA §3.1 | `DeviceDescriptor`(~84B) 배열, 이미 페이지네이션(`capacity`)으로 호출자가 청크 크기를 직접 제어 - 한 호출의 응답이 페이지 크기를 넘을 이유가 없음 | 아니오 |
| `RequestIoPermission` | SP-9DD4F3EA §3.3 | 고정 크기 struct(~40B) | 아니오 |
| `Mount`/`Unmount` | SP-7CC5693A §2.2 | 경로 문자열(수백 B 이내) + channelId | 아니오 |
| `ResolvePath` | SP-7CC5693A §2.2 | 경로 in, 고정 struct out | 아니오 |
| `SignalUserlandReady`/`WaitForUserlandReady` | SP-7CC5693A §2.5 | payload 없음 | 아니오 |
| 인터럽트 라우팅 통지(PN-B3DD3D19, 미착수) | SP-71DA77B3 | 벡터 번호 등 수 바이트 | 아니오 |
| ~~`PublishInterface`/`QueryInterfaces`~~ | SP-B071E628 (2026-09-16 pubreg 재설계로 이 syscall 자체가 폐기됨 - RM-48E1E610 35-37번 참고. 후속 프로토콜은 `pubreg` 커널서비스와의 일반 Channel IPC이며 애초에 유저랜드간 트래픽이라 이 표/DC 범위 밖인 점은 그대로 유지) | 해당 없음(syscall 자체 폐기) |

**결론(설계자 질문 4번에 대한 답)**: 지금까지 설계된 것 중 Tier A
기준을 넘는 것은 없다. 실제 파일/블록 데이터처럼 대용량이 오갈 수
있는 트래픽(fs의 `Read`/`Write`, AHCI 블록 장치 read/write)은 애초에
커널을 거치지 않고 **요청자↔fs/드라이버 간 직접 Channel IPC**로
설계돼 있어(SP-2AAD7C8D §9, SP-B071E628 §4) 이 DC(커널↔커널서비스)의
대상이 아니다 - 커널↔커널서비스 트래픽 자체는 구조적으로 항상
제어/메타데이터 성격이라 Tier A가 실제로 필요해질 가능성이 낮다
(그래도 완전히 배제하지 않고 설계는 §2.1에 이미 확정해 뒀다 -
설계자 지시로 실사용처와 무관하게 미리 설계).

**따라서 위 표의 모든 syscall은 그대로 유지하되, 그 밑에 깔리는
Channel/syscall을 `exclusivePreemptive=true`로 표시하는 것으로
충분하다** - 새로운 재설계나 API 변경이 필요하지 않다.

## 4. 아직 열려 있는 설계 영역

- **`AsyncReactor` 우선순위 큐**: 지금 리액터는 단일 FIFO 실행
  큐(SP-F682B889)다. `exclusivePreemptive` AsyncTask를 "앞서
  처리"하려면 최소 2단 우선순위 큐(선점 큐/일반 큐)로 확장해야
  한다 - 구체 자료구조(단순 두 개의 FIFO? PL-2D3184BC의 즉시/RT/
  일반 3단과 통일?)는 실제 착수 시 확정(RM-23F4B687 §4 원칙,
  현재 소비자가 아직 코드로 존재하지 않아 지금 숫자/자료구조를
  확정할 필요 없음).
- **Tier A의 소비 통지 방식/`capacity` 크기**: §2.1이 자료구조/배치는
  확정했지만, "읽는 쪽이 새 데이터를 어떻게 아는지"(폴링 vs 경량
  신호)와 정확한 버퍼 크기는 실사용 소비자가 정해질 때 확정한다
  (§2.1 "v1 스코프" 참고) - 자료구조 자체는 이미 설계됨, 남은 건
  튜닝 파라미터 수준.
- **`KernelReservedTable`과 `DeviceOwnerTable`/`InterfaceRegistry`의
  관계**: 셋 다 "커널 내부 예약/등록 테이블"이라는 같은 패턴이지만
  용도가 다르다(§2.0은 커널서비스별 통신 엔드포인트 예약,
  `DeviceOwnerTable`은 MMIO/IRQ 소유권, `InterfaceRegistry`는
  유저랜드간 발견) - 혼동 방지 차원에서 RM-32D06563에 세 개를
  나란히 기록해 둘 것(착수 시).

## 5. 선행 조건 / 관련 계획

- Channel IPC(PL-C8648D4D, 완료) - `exclusivePreemptive` 플래그 및
  §2.0a의 `kCreateNamedChannel` 팩터링 대상.
- AsyncReactor(SP-F682B889, 완료) - 우선순위 큐 확장 대상.

  `/sys/live/kernel/`의 실제 라우팅 지점(착수 시 §2.4에 세 번째

  (PN-012E8C1A, 완료) - Tier A 링버퍼를 유저 프로세스 쪽에 매핑하는
