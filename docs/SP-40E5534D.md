PN-36E3164D("pubreg 커널 서비스 대행 릴레이 — 별도 설계안 작성")의
실제 설계 제안. SP-B071E628 §5-A가 정리한 제약을 구체화한다.

## 0. 설계자 지시 원문 (SP-B071E628 §5-A로 이미 인용, 재게재)

> 커널 서비스들이 pubreg에 뭔가를 등록하지 않아(성능문제, 프로토콜
> 유지보수 문제 등등). 유저 영역에서 `유저가 설치한 유저 서비스`가
> pubreg에 자신들의 동작을 등록해야해. 그러니까 결국, `유저 랜드`
> 에서 중계 패턴으로 구현된 무언가가 `대행`하는 방식이어야 하는거야.

## 1. 구성요소 정체성 - 전용 유저 프로세스 `pubreg-relay`

라이브러리가 아니라 **전용 프로세스**로 제안한다 - devmgr/fs 등에
`libjson`+pubreg 프로토콜 코드를 직접 링크시키면 "성능/프로토콜
유지보수 부담을 커널 서비스가 진다"는 지적을 그대로 재현하게 되므로,
그 부담을 완전히 분리된 별도 프로세스로 옮긴다.

- **`ProcessRole::Normal`** - `pubreg`(5번째 커널 서비스)와 달리
  이 릴레이는 커널 서비스가 아니다. "유저가 설치한 유저 서비스"라는
  설계자 표현과 일치시키기 위해 커널이 신뢰하는 부팅 매니페스트
  고정 5개 이름(devmgr/fs/net/tty/pubreg)에 포함시키지 않는다.
- 그럼에도 시스템이 부팅 직후부터 동작하려면(예: AHCI→fs 최초
  발견) 이 릴레이가 아주 이른 시점에 존재해야 한다 - **initrd에
  `pubreg-relay`라는 이름으로 동봉하고, init(또는 §2가 결정하는
  스폰 지점)이 최우선으로 기동**한다. "유저가 설치"라는 표현은
  "커널이 특권으로 신뢰하지 않는다"는 뜻으로 해석하고, 물리적으로는
  initrd에 사전 포함된 표준 구성요소로 제안한다(제안 - §5 열린
  질문 1 참고).
- `libjson`을 링크하는 것은 이제 **`pubreg` + `pubreg-relay` +
  (릴레이를 거치지 않고 스스로 pubreg에 등록하는 순수 유저 서비스)
  뿐** - devmgr/fs/net/tty는 더 이상 libjson을 링크할 필요가
  없어진다(PN-185406F6/PN-BD9AAE2F/PN-452FF696 선행 조건 갱신 필요).

## 2. 커널 서비스 → 릴레이 통신 경로 - 기존 "이름 있는 Channel" 재사용

devmgr(및 그 드라이버 자식)이 pubreg 프로토콜을 전혀 몰라도 되게
하려면, 이미 있는 가장 가벼운 메커니즘을 그대로 쓴다:

1. `pubreg-relay`는 부팅 시 고정 이름 Channel을 하나 연다(예:
   `openChannel(name="pubreg-relay-intake")`, SP-1FBC0EEB "이름
   있는 Channel" 패턴 그대로 - `/sys/live/named/`에 경쟁적으로
   등록, `pubreg` 자신의 `/sys/live/kernel/` 예약 경로와는 무관).
2. devmgr의 드라이버 자식(예: AHCI 포트)이 `probe()`에 성공하면,
   **JSON이 아니라 고정폭 raw binary struct**(DS-D4E5C451의 IPC
   원칙 그대로, §7 폐기된 구안이 원래 쓰려던 것과 동일한 형태)로
   최소 정보(processName, 자신의 실제 데이터 채널 `channelId`,
   장치 종류를 가리키는 짧은 코드)만 이 intake Channel에 `write`
   한다 - JSON 파싱/libjson 불필요, `struct`를 그대로 직렬화.
3. `pubreg-relay`가 이 raw binary 메시지를 읽어 **자신이** libjson으로
   MCP 스타일 tool 선언(JSON)을 구성하고, `pubreg`에 `register`
   (SP-B071E628 §3)한다 - 이때 `register`의 `channelId` 필드에는
   **devmgr 드라이버 자식의 실제 채널ID를 그대로 전달**한다(아래
   §3 참고, 릴레이 자신의 채널이 아님).

이 방향의 장점: devmgr/드라이버는 struct 하나를 채워 `write`만
하면 끝 - pubreg 프로토콜의 존재 자체를 몰라도 된다("프로토콜
유지보수 문제" 해소). tool 선언의 `description`/`inputSchema`
등 풍부한 메타데이터를 어떻게 채울지는 §5 열린 질문 2로 남긴다
(가장 단순한 안: 장치 종류 코드 → 고정 tool 선언 템플릿 매핑
테이블을 릴레이 자신이 들고 있는 것).

## 3. 릴레이 → pubreg 등록/조회 - "신원만 중개" 원칙 그대로 확장

**핵심 불변조건**: `pubreg`가 등록/조회에서 다루는 `channelId`는
항상 **실제 데이터가 오가는 그 채널의 소유자**를 가리켜야 한다 -
SP-B071E628 §3의 "제어 채널 중계 = 신원만 중개, 실제 데이터는
pubreg를 거치지 않는다"는 원칙이 이 릴레이의 존재로 깨지면 안 된다.

- `pubreg-relay`가 devmgr을 대신해 `register`할 때, `channelId`는
  **devmgr 드라이버 자식이 §2에서 직접 알려준 자신의 실제 채널**을
  그대로 전달한다 - 릴레이가 자기 자신의 채널을 대신 등록하지
  않는다.
- 따라서 소비자(fs)가 `query` 응답으로 받는 `channelId`로
  `connectChannel()`하면, **AHCI 드라이버 자식과 직접 연결**된다 -
  `pubreg-relay`는 등록 단계(제어 트래픽)에만 관여하고, 실제 블록
  IO 트래픽 경로에는 전혀 끼지 않는다(병목/프록시가 되지 않음 -
  §0가 지적한 "성능문제"의 핵심 우려가 이 구조로 해소된다).
- 등록 해제도 동일한 간접 구조를 따른다 - devmgr 드라이버 자식의
  실제 채널이 끊기면(SP-1FBC0EEB "닫힌 파이프") `pubreg`가 그
  등록을 지운다(SP-B071E628 §3 그대로, 이미 `channelId` 기준으로
  동작하므로 릴레이의 개입이 전혀 필요 없다) - **다만 릴레이 자신의
  intake Channel이 끊기는 것과는 별개 사건**이라는 점에 유의(§5
  열린 질문 3).

## 4. AHCI → fs 서비스 실사용 예 (SP-B071E628 §5 재작성)

1. devmgr이 부팅 시 PCI 장치를 찾아 AHCI 드라이버 자식을 스폰
   (SP-9DD4F3EA §3.2).
2. 그 자식이 `probe()`+포트 스캔에 성공하면, `openChannel(name=null)`
   로 실제 블록 IO 데이터 채널을 만들고, `pubreg-relay`의 intake
   Channel에 raw binary로 (processName="ahci-port0", channelId,
   deviceKind=AHCI_BLOCK) 알린다(§2).
3. `pubreg-relay`가 이를 받아 `pubreg`에 `register`(tool 이름
   `ahci.blockRead`/`ahci.blockWrite`, `channelId`=AHCI 드라이버
   자식의 실제 채널).
4. fs 서비스는 §2.5 `WaitForUserlandReady` 이후 `pubreg`에 `query`
   해 사용 가능한 블록 장치 tool 목록+`channelId`(AHCI 드라이버
   자식의 것)를 얻는다.
5. fs는 그 `channelId`로 `connectChannel()`해 **AHCI 드라이버
   자식과 직접** 연결 - 이후 실제 블록 IO 페이로드 형식(JSON인지
   raw binary인지)은 SP-C2670F69/SP-B071E628 §6-1(tool 명세가
   통신 방식 자체를 규정)에서 그 tool의 명세로 확정.

## 5. 아직 열려 있는 설계 영역

1. **`pubreg-relay`의 정확한 스폰 지점/시점**: init이 직접 스폰하는지
   (SP-68182FBD §2.4 "init이 최초 구동하는 유일한 유저 프로그램"과
   충돌 가능 - init이 다른 프로그램을 추가로 스폰하는 것 자체는
   막혀 있지 않지만 문서화 필요), 아니면 §1처럼 부팅 매니페스트에
   6번째 이름으로 추가하되 `ProcessRole::Normal`로만 스폰하는
   별도 경로를 새로 두는지 - 착수 시 확정.
2. **intake 메시지의 정확한 struct 레이아웃과 deviceKind→tool
   선언 매핑 테이블**: 이 문서 범위 밖, 착수 시 별도 확정(devmgr
   쪽 대상 장치 종류가 늘어날 때마다 이 매핑도 늘어나는 구조라
   RM-32D06563에 개념만 등재하고 세부는 코드 레벨에서 관리 제안).
3. **릴레이 자신의 크래시/재시작 시 재동기화**: `pubreg-relay`가
   죽었다 재시작하면 devmgr이 이미 보낸 §2 알림은 유실된다(릴레이가
   기억하지 못하므로 재등록도 안 일어남) - `pubreg` 자체의 크래시
   복구(SP-B071E628 §6-4, "등록자 자동 재등록"으로 확정)와 달리,
   릴레이의 크래시는 devmgr 쪽의 **재알림(재전송)** 없이는 스스로
   복구되지 않는다. devmgr이 intake Channel의 "닫힌 파이프"를
   감지해 재연결 시 이미 알린 장치를 다시 알리는 재전송 로직이
   필요할 수 있음 - 착수 시 확정.
4. **여러 커널 서비스(devmgr/net/tty)가 릴레이를 공유하는가, 서비스별로
   따로 두는가**: 이 문서는 단일 공용 `pubreg-relay` 하나를
   전제했다(가장 단순) - net/tty도 같은 패턴이 필요해지면 재검토.

## 선행 조건

- pubreg 서비스 자체(PN-185406F6, §3/§4 핵심 골격) - register/query
  프로토콜의 실제 구현체.
- Channel IPC(PL-C8648D4D, 완료) - intake Channel의 기반.
- `libjson`(신규, SP-B071E628 §4, 커널/유저 공용) - `pubreg-relay`가
  링크하는 유일한 JSON 소비자가 pubreg 자신 + 이 릴레이로 좁혀짐.

## 착수 조건

이 설계가 승인되면 PN-185406F6(pubreg 구현) 체크리스트 5/6번,
PN-BD9AAE2F(devmgr 구현) 항목 6, PN-452FF696(fs 구현) 항목 5를
이 설계에 맞춰 재작성하고 착수 가능 상태로 되돌린다.
