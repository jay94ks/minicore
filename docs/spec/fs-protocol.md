# FS 서버 공통 프로토콜 스펙 (M16 v2)

**관련 결정**: [filesystem.md](../design/filesystem.md) ADR-018(fd 라우팅),
ADR-047(synthetic FS 서버), ADR-101(공유 모드/잠금), ADR-128(`fs_node_id`),
[kernel-ipc-objects.md](../design/kernel-ipc-objects.md) ADR-151(IPC의
cross-address-space 확장), ADR-155/159/161(pages[]의 유저 프로세스
매핑 경로 — 이 문서 v2가 실제로 쓰는 경로)
**관련 스펙**: [ipc.md](ipc.md)(Call/Reply, message 구조), [procsrv.md](procsrv.md)
§4.1(`open_file_id`)

M13이 최소 버전(3개 오퍼레이션, `regs[]`만 사용)을 정의했다. 이
문서(v2, M16)는 OPEN-59가 ADR-159/161로 해소되어 실제로 구현됨에
따라 **`OP_READ`의 응답을 `pages[]` 기반으로 교체**하고, VFS에
**마운트 테이블**을 추가한다 — FAT32/ext4가 처음으로 이 프로토콜의
두 번째·세 번째 FS 서버가 되면서 필요해졌다.

## 1. 메시지 인코딩

- `OP_OPEN`(경로), `OP_WRITE`(memfs 전용, 쓰기 데이터)는 M13과 동일하게
  `regs[]`만 쓴다 — 경로 32바이트, 쓰기 payload 16바이트 상한
  그대로(M13의 제약, 이 문서가 다시 좁히지 않는다). FAT32/ext4는
  읽기전용이라 `OP_WRITE`를 구현하지 않는다(ADR-057/128/129가 이미
  정한 v1 범위).
- **`OP_READ`의 응답은 이제 `pages[]`를 쓴다**(ADR-155 §2/ADR-159/
  ADR-161) — 커널이 FS 서버가 보낸 프레임을 클라이언트의 고정 슬롯에
  참조카운트+읽기전용으로 매핑해 준다(`sys_recv`/`sys_call`의
  return 시점에 `msg.pages[0].vaddr`가 이미 그 위치를 가리킨다,
  클라이언트는 아무 사전 준비도 필요 없다). **한 번의 `OP_READ`는
  최대 1페이지(4096바이트)만 옮긴다**(ADR-159의 슬롯 예산 — 디스크립터
  당 정확히 1페이지, 슬롯 4개 중 1개만 씀) — 그보다 큰 파일을 읽는
  오프셋/seek 프로토콜은 이 문서의 범위 밖(§4).

## 2. 오퍼레이션

| `label` | 이름 | 방향 | 의미 |
|---|---|---|---|
| `1` | `OP_OPEN` | 클라이언트→VFS | 경로를 열거나(마운트 테이블로 대상 FS 서버 결정) 만든다 |
| `2` | `OP_WRITE` | 클라이언트→FS 서버(직접) | 열린 파일에 쓴다(memfs만 지원) |
| `3` | `OP_READ` | 클라이언트→FS 서버(직접) | 열린 파일에서 최대 1페이지를 읽는다 |

### 2.1. `OP_OPEN` (클라이언트 → VFS)

- 요청: `label=1`, `regs[0..3]` = 경로(ASCII, NUL 패딩, 최대
  32바이트). `page_count=0`, `handle_count=0`.
- 처리: VFS는 이제 **마운트 테이블**(고정 배열, M16 한정 정적
  등록 — 동적 마운트 syscall은 범위 밖)을 갖는다:
  | 경로 접두사 | 대상 |
  |---|---|
  | `/mnt/fat32/` | `servers/fs/fat32`(읽기전용) |
  | `/mnt/ext4/` | `servers/fs/ext4`(읽기전용) |
  | (그 외) | `servers/fs/memfs`(M13과 동일한 기본 경로, 하위 호환) |

  일치하는 접두사를 벗겨낸 **나머지 경로**를 대상 FS 서버에게
  `OP_OPEN`으로 그대로 전달한다(예: `/mnt/fat32/hello.txt` →
  fat32에게 `hello.txt`). memfs로 가는 기본 경로는 M13과 완전히
  동일하게 동작한다(선행 `/`만 벗김) — 이 변경으로 기존 동작이
  깨지지 않는다.
- 응답: `label=1`, `regs[0]`=대상 FS 서버가 발급한 `open_file_id`
  (0=실패), `regs[1]`=상태, `handle_count=1`, `handles[0]`=대상 FS
  서버 endpoint에 대한 프록시(`CAN_SEND`) — ADR-018 그대로. 이후
  클라이언트는 이 핸들로 그 FS 서버에게 직접 `OP_READ`/`OP_WRITE`를
  보낸다(VFS를 다시 거치지 않음, M13과 동일한 관례).

### 2.2. `OP_WRITE` (클라이언트 → FS 서버 직접, memfs만)

M13과 동일 — `regs[0]`=`open_file_id`, `regs[1]`=길이(0~16),
`regs[2..3]`=데이터. FAT32/ext4에게 이 label을 보내면
`k_status_not_found`(또는 그와 동등한 "지원 안 함")로 응답한다.

### 2.3. `OP_READ` (클라이언트 → FS 서버 직접) — v2: `pages[]` 응답

- 요청: `label=3`, `regs[0]`=`open_file_id`, `regs[1]`=요청 길이
  (내부적으로 4096바이트로 클램프됨 — 그보다 큰 값을 넣어도
  오류가 아니라 그냥 4096으로 잘린다).
- 응답: `label=3`, `regs[0]`=실제로 읽은 바이트 수(≤4096),
  `regs[1]`=상태, `page_count=1`, `pages[0]`=커널이 매핑해 준
  페이지(`vaddr`는 출력 — 클라이언트의 고정 슬롯 주소,
  `length=4096`, 실제 파일 내용은 앞 `regs[0]`바이트만 유효하고
  나머지는 0으로 채워져 있다).
- **알려진 제약**(ADR-155 §3이 이미 명시한 것과 같은 성격): FS
  서버가 응답을 준비하는 버퍼를 **다음 요청 전에 재사용**하면 그
  사이 클라이언트가 아직 다 읽지 않은 내용이 바뀔 수 있다 — 이
  문서의 모든 FS 서버는 "한 요청을 다 처리하고 회신한 뒤에야 다음
  요청을 받는" 단일 스레드 루프이므로(procsrv/vfs/memfs/devmgr와
  같은 구조) 실제로 부딫힐 상황이 아니다.

## 3. 상태 코드 (`regs[1]`, 모든 응답 공통)

```
0 = OK
1 = NOT_FOUND      (알 수 없는 open_file_id, 또는 그 FS 서버가 지원하지 않는 오퍼레이션)
2 = TOO_LARGE       (OP_WRITE 데이터 길이가 16바이트 초과 — OP_READ는 이제 내부 클램프라 이 코드를 안 씀)
3 = NO_SPACE        (memfs의 고정 파일 슬롯이 가득 참)
4 = MOUNT_ERROR      (FAT32/ext4가 마운트에 실패함 — 잘못된 시그니처, 지원 안 하는 feature 비트 등)
```

## 4. 이 문서가 명시적으로 다루지 않는 것

- `close`(fd 닫기), 공유 모드/잠금(ADR-101), `fs_node_id`(ADR-128)를
  응답에 싣는 것 — M13과 동일하게 이후 라운드.
- 디렉터리 나열, 하위 디렉터리 진입(FAT32/ext4 모두 v1은 **루트
  디렉터리 평평한 스캔만** — ADR-057/128/129가 정한 v1 범위, memfs
  와 같은 평평한 이름공간 전제).
- 4096바이트를 넘는 파일의 나머지 내용을 읽는 seek/offset
  프로토콜(`OP_READ`가 항상 파일 오프셋 0부터 최대 1페이지만
  읽는다) — 이 라운드의 검증 목표(마운트 후 파일을 열어 내용을
  읽어낸다)에 필요한 최소 크기의 테스트 파일만 다룬다.
- FAT32/ext4에 대한 쓰기(`OP_WRITE`) — 두 FS 모두 v1은 읽기전용
  (ADR-057/129).
- 동적 마운트/언마운트 syscall — §2.1의 마운트 테이블은 VFS 코드에
  정적으로 박혀 있다(cfgsrv 같은 동적 설정 소스가 아직 없다).
