# 빌드 시스템 / 툴체인 / CI — 요구분석

## 배경

SP-8B6B8D25에서 확정된 것은 "C++ 주 언어 + 어셈블러, x86-64 freestanding,
BIOS/PVH/multiboot2/EFI 4가지 부팅 경로 지원, `--kernel`/`--initrd` 개발
편의 옵션, 시리얼 포트 커널 로그"까지다. 이 범위를 실제로 컴파일하고
QEMU에서 부팅시켜 보려면, 소스를 어떤 도구로 빌드하고 어떤 크로스
컴파일러로 오브젝트를 만들지가 있어야 첫 커밋(빌드 스크립트 + "Hello from
kernel" 수준의 뼈대)조차 만들 수 없다. 즉 이 결정 없이는 구현 착수
자체가 불가능한 선결 조건이다.

또한 여러 부팅 경로(4종)와 여러 서비스(kernel/devmgr/fs/net/tty,
libkenv/libkern/libkmm)를 한 리포에서 관리해야 하므로, 빌드 시스템이
"타깃별/서비스별로 독립적으로 빌드되면서도 공용 라이브러리는
재사용"하는 구조를 지원해야 한다 — 이 요구를 만족하는 도구인지가
선택 기준이 된다.

## 결정이 필요한 항목과 각 선택의 영향

1. **빌드 시스템**: CMake / Meson / 수작업 Makefile / 기타.
   - CMake: 생태계가 크고 크로스컴파일 툴체인 파일 관례가 잘 갖춰짐.
   - Meson: 문법이 간결하지만 OS 개발 진영에서의 레퍼런스가 상대적으로 적음.
   - 수작업 Makefile: 완전한 제어가 가능하지만 서비스가 늘어날수록
     유지보수 비용이 커짐.
2. **크로스컴파일 툴체인**: 타깃 트리플(예: `x86_64-elf`)과 컴파일러
   (GCC/Clang) 및 버전 고정 여부 — 이후 모든 개발자/CI 환경의 재현성을
   좌우한다.
3. **CI 파이프라인 존재 여부**: 빌드/부팅 테스트를 GitHub Actions 등으로
   자동화할지, 처음엔 로컬 수동 검증만으로 시작할지 — 초기 개발 속도와
   회귀 방지 사이의 트레이드오프.
4. **QEMU 자동화 테스트**: 시리얼 로그에 특정 문자열이 찍히면 성공으로
   판정하는 부팅 스모크 테스트를 스크립트로 자동화할지, 처음엔 수동
   확인만 할지 — QA-26450C3E의 "부팅" 체크리스트를 자동 검증할 수
   있는지가 여기 달려 있다.
