# Minicore 범용 운영체제 — 초기 설계 명세

목표/범위 자체가 이전 시도(과거 브랜치)와 다른 새 프로젝트로 시작한다.
아래는 설계자가 확정해 준 범위이며, 여기 없는 세부는 임의로 정하지
않고 별도 DC 문서로 남긴다(DC-48565C0B, DC-427BB6B2, DC-79A2387A,
DC-5AB13FFC 참고).

## 0. 커널 형태와 개발 언어

- **하이브리드 커널**.
- 주 개발 언어: **C++**. 하드웨어 제어 및 로우레벨 대응은 **어셈블러**.
- 코딩 컨벤션: 프리픽스 + 파스칼 케이스 (예: `kMain`).
- **네임스페이스 부여 규칙은 "커널" 앱에만 적용된다.** 유저랜드 앱은
  앱별로 완전히 별도 프로젝트로 간주한다(커널과 같은 네임스페이스
  규칙을 따르지 않음).

## 1. 부팅 조건

타깃별로 다르다.

- **x86-64**: `BIOS`, `PVH`(QEMU), `multiboot2`, `EFI`(UEFI 포함)까지 지원.
  단, 개발 편의를 위해 `--kernel` 옵션 및 `--initrd` 옵션으로 이미지만
  바로 넘기는 방식을 사용한다. 그리고 시리얼 포트를 구현해 그것으로
  커널 로그를 수신한다.
- **ARM, RISC-V 등**: 고려 대상이지만 현 단계에서는 제외 — 설계상
  고려만 해 둔다(지금 구현 대상이 아님).

## 2. 커널이 담당하는 범위

1. 부팅 및 유저랜드를 준비하는 것.
2. 프로세스 및 권한 관리, 컨텍스트 스위칭 및 스케줄러, SMP, 인터럽트 처리.
3. IPC를 해석하여 메시징 채널로 커널 서비스들에게 전파.
4. 인터럽트를 적절한 커널 서비스들에게 라우팅.
5. 커널 서비스들에게 요청받은 IO 권한 부여(PCIe, USB, ...).
6. NUMA 및 메모리 관리, SWAP 스케줄링.
7. 페이지 단위 맵핑 및 페이지 소유권 관리.
8. 페이지 병합(예: x86-64에서 4K 페이지를 모아 2M 페이지로 병합).
9. CPU 캐시 관리, Fault 시 원인 조사, 적절한 커널 서비스로 라우팅.
10. 공유 메모리 및 프로세스간 메시징(IPC와 별도로 존재하는 채널).
11. 시그널 전파, 커널 logger(유저랜드가 준비되면 유저랜드에 존재하는
    데몬에게 역할 전환).
12. ~~프로세스간 "공개 인터페이스" registry 및 제어 채널 중계.~~
    **[정정, 2026-09-16, 설계자 지시로 재설계]** 커널 자신의 책임이
    아니게 됐다 - 5번째 커널 서비스 `pubreg`(유저랜드 구동, §3.1
    항목 7)가 전담하고, 커널은 기존 범용 `connectChannel()` syscall
    (§2 항목 3, Channel IPC) 이상의 registry 전용 로직을 전혀 갖지
    않는다(SP-B071E628 참고) - 이 항목은 "커널이 담당" 목록에는 더
    이상 해당하지 않지만, §3.1의 5번째 서비스 존재를 기억하기 위해
    역사적 참고로 남겨 둔다.
13. procfs 루트.

## 2-A. 커널과 "커널 서비스"의 실행 특권 경계 (중요 — 설계자 확정)

**"커널"만 커널 영역(ring 0/특권 모드)에서 구동된다.** §3에서 말하는
"커널 서비스"(devmgr, fs, net, tty 등)는 이름과 달리 전부 **유저랜드에서
구동**되며, 그 위에서 하는 일에 대한 통제권(권한 부여, 라우팅 등)을
커널이 쥐고 있을 뿐이다 — "커널이 모든 통제권을 쥔 유저랜드 서비스"라는
뜻이다. 예를 들어 devmgr은 필수적인 IO 처리만 커널에게 위임받아 처리하고
(DS-D4E5C451 참고), 나머지 로직은 유저랜드에서 실행된다. fs/net/tty도
동일한 원칙을 따른다 — 커널 영역 코드는 §2에 나열된 커널 자체의 책임
(스케줄링/인터럽트/IPC 라우팅/메모리 관리 등)에 한정된다.

**[정정, 2026-09-21] devmgr/fs는 이 원칙의 명시적 예외로 커널에
흡수됐다 - net/tty/pubreg/authmgr은 원칙 그대로 유효** - 설계자가
`QU-23B339AB`(2026-09-20, "devmgr과 fs를 커널이 흡수하자", 긴급도
최상)로 이 문서보다 나중에 이 원칙을 devmgr/fs 두 서비스에 한해
뒤집었다 - `DC-91ABD922`+`SP-43331889`(설계)+`PN-615C48D5`(구현,
completed)로 devmgr/fs는 이제 **`Process` 없는 순수 커널
`KernelThread`(ring 0, 커널과 완전히 같은 주소공간)**로 실제로
구동된다 - "유저랜드에서 구동되며 통제권만 커널이 쥔다"는 위 원칙이
더 이상 이 둘에는 적용되지 않는다. 뒤집은 이유(§1)와 무관하게
**net/tty/pubreg/authmgr(아직 미구현) 4개 서비스는 이 원칙 그대로
유저랜드 구동이 유효**하다 - devmgr/fs만의 특수 사례(devmgr/fs가
직접 하드웨어 블록 I/O를 다루는 저수준 서비스라는 점, §5의
"유저모드 드라이버" 신규 경로가 오히려 실제 하드웨어 드라이버
코드는 계속 ring3에 격리해 두는 것과 대비된다)로, 이 흡수가 다른
서비스에도 확대 적용된다는 결정은 없었다. §3의 각 서비스 배치
설명("유저랜드 구동, §2-A 참고")도 devmgr/fs 항목만 이 각주를
참고하도록 갱신이 필요하다(아래 §3 직접 각주 참고).

## 2-B. 유저 프로세스 페이지 폴트 처리 정책 (2026-09-14, 설계자 지시 — 유저랜드 준비 전 미리 기록)

유저랜드가 아직 없어 지금 당장 구현하지는 않지만, 프로세스/스케줄러를
만들 때 페이지 폴트 처리가 반드시 이 정책을 따라야 한다:

- 폴트가 **유저랜드 프로세스**에서 났으면(커널 자신의 폴트가 아니면),
  커널을 멈추지 않는다 — **그 프로세스만 블로킹(정지)시키고 스케줄러가
  다음 작업으로 전환**한다.
- 그 폴트 정보(폴트 주소, 에러 코드, 원인이 된 명령어 등)는 **그
  프로세스 자신의 자료구조(PCB)에 매달아 둔다** — 나중에 그 정보를
  보고 "이건 진짜 잘못된 접근(예외/강제 종료 대상)인지" 아니면
  "SWAP되어 있던 페이지라 다시 읽어와야 하는 것인지"를 판단한다.
- 즉 지금 §2-A의 `Paging::kHandlePageFault`(커널 자신의 지연 매핑
  전용, 실패하면 커널 패닉)와는 별도로, **유저 모드 폴트 전용 경로**가
  따로 필요하다 - CS의 CPL 비트나 에러코드의 U/S 비트로 유저 모드
  폴트인지 구분해서 분기해야 한다(관련 코드: `minicore/kernel/idt.cpp`,
  `minicore/kernel/paging.cpp`).

**[정정, 2026-09-17, minicore-f8 세션 - 실제 최종 구현과 대조해 발견]**
위 두 번째 항목("폴트 정보를 PCB에 매달아 두고 나중에 판단")은
**실제로 구현되지 않았다** - 이 커널에 SWAP 자체가 아직 없어(RM-
7C249618 "libswapfs 예정, 미구현") "진짜 잘못된 접근 vs SWAP 필요"
를 나중에 구분해 판단할 대상 자체가 없다는 게 실제 구현 시점에
확인됐다. **PN-71E50394**(Signal 전달 인프라)가 QU-04C420BF 답변
("그래 이렇게 해")으로 확정한 실제 정책은 **훨씬 단순하다** - 온디맨드
매핑/COW로도 못 고친 ring3(CPL 3) 폴트는 `Process::raiseSignal
(Segv)`(다만 `pendingSignals`에 기록만 하고 폴트 주소/에러코드
자체는 PCB에 별도 보관하지 않음)를 호출한 뒤 `kTerminateFaultingUserTask()`
로 그 즉시 Task를 종료시킨다(idt.cpp) - "블로킹 후 나중에 판단"이
아니라 **"블로킹 없이 즉시 종료"**다. 위 원문 두 항목 다 이 최종
정책과 어긋나므로(첫 항목 "블로킹시키고 스케줄러가 다음 작업으로
전환"도 실제로는 "종료시키고"에 가깝다 - Zombie 표시 후 리액터가
정리), 이 §2-B는 "유저랜드 준비 전 미리 기록"해 둔 **초안**이었고
실제 착수 시 더 단순한 방향으로 교체됐다는 기록으로 남긴다. 향후
SWAP이 실제로 설계/구현되면(현재 로드맵에 없음) 그때 폴트 정보
보관이 다시 필요해질 수 있다 - 그 시점에 별도 설계로 재검토.

## 3. 커널과 커널 서비스들의 디렉터리 배치

### 3.0 아키텍처 전용 코드

- 공통: `minicore/arch` 디렉터리.
- 아키텍처별 공통 코드 라이브러리는 `minicore/libs/<arch_name>` 디렉터리에
  배치한다. 커널 서비스들에서 필요한 경우 직접 링크해 재사용할 수 있도록
  전처리기와 추상화 계층을 구성한다.
- 부팅 stub 및 bootstrap, 초기 환경 구성 등 코드만 포함한다.
- ARM/RISC-V 등 벤더별 차이가 심한 경우, 해당 아키텍처 하에 구현부를
  추상화해 분리한다.

### 3.1 ~ 3.5 각 구성 요소의 위치

1. **kernel** (커널 영역/ring 0에서 구동되는 유일한 구성 요소):
   `minicore/kernel` 디렉터리.
2. **kernel library 루트**: `minicore/libs` 디렉터리.
   - `libkenv`: early 환경에서 동작하는 C/C++ 런타임 라이브러리.
   - `libkern`: 커널 및 유저랜드 양쪽에서 매크로로 구분되어 컴파일되며,
     구분된 구현들이 서로를 브릿징(IPC, 공유 메모리 등)할 수 있는 라이브러리.
   - `libkmm`: 메모리 관리자 구현 중 재사용 가능한 코드만 모은 라이브러리.
3. **devmgr 서비스**(2026-09-21부로 커널 KernelThread 구동 -
   §2-A 정정 각주 참고): `minicore/devmgr` 디렉터리.
4. **fs 서비스**(2026-09-21부로 커널 KernelThread 구동 -
   §2-A 정정 각주 참고): `minicore/fs` 디렉터리.
5. **net 서비스**(유저랜드 구동, §2-A 참고): `minicore/net` 디렉터리.
6. **tty 서비스**(유저랜드 구동, §2-A 참고): `minicore/tty` 디렉터리.
7. **[추가, 2026-09-16, 설계자 지시]** **pubreg 서비스**(유저랜드
   구동, §2-A 참고): `minicore/pubreg` 디렉터리 - 프로세스간 "공개
   인터페이스" 홍보/발견 디렉터리(MCP 스타일 tool 선언 레지스트리,
   SP-B071E628 참고).
8. **[추가, 2026-09-17, 설계자 지시]** **authmgr 서비스**(유저랜드
   구동, §2-A 참고): `minicore/authmgr` 디렉터리 - 사용자 신원
   (uid/gid 트리, 로그인/패스워드, sudo/su)의 전속 관리(`SP-30FCC8AE`
   §1-D 참고) - `pubreg`와 같은 층위의 6번째 커널 서비스.

## 4. 파일 시스템(fs) 구조

```
/
├── boot/                    # 부팅 루트
│   ├── (커널 이미지, initrd — Multiboot2 경로용, 일반 파일)
│   └── uefi/                # ESP(FAT32) 마운트 지점 — UEFI 경로 전용
│
├── sys/                     # OS를 구성하는 모든 것의 루트.
│   ├── live/                 # 이 시스템을 지탱하는 커널과 커널 서비스들이 담당.
│   │   ├── proc/              # 예: procfs.
│   │   ├── network/           # 예: netsrv 담당
│   │   ├── sched/              # 예: 스케줄러 노출용 서버 담당
│   │   └── ...                 # 서비스가 늘어날 때마다 하위 마운트 추가
│   ├── etc/                  # 전역 시스템 설정 (영속, 일반 FS)
│   ├── bin/                  # 전역 시스템 바이너리 (영속, 일반 FS)
│   ├── mnt/                  # 시스템 수준 외부 매체 마운트 루트
│   ├── dev/                  # devmgr가 dev별로 할당한 특수 파일 및 폴더들.
│   └── tmp/                  # memfs 마운트, 휘발성
│
├── apps/                     # 공용 설치 경로 — 사용자별 관리 불가
├── run/                      # apps + 사용자별 격리 루트 오버레이.
│
├── usr/                      # 사용자별 격리 루트
│   └── {사용자명}/
│       ├── bin/               # 이 사용자 전용 바이너리
│       ├── lib/               # 이 사용자 전용 라이브러리
│       ├── etc/               # 이 사용자 전용 설정
│       ├── mnt/                # 이 사용자가 마운트한 외부 매체들의 루트.
│       └── home/              # 기본 작업 디렉터리 (= /home/{사용자명})
│
└── home/                    # /usr/{사용자명}/home으로의 VFS 별칭.
    └── {사용자명}/            # → /usr/{사용자명}/home 으로 재작성되어 조회됨
```

## 4-A. VFS 루트 소유권과 마운트 포인트 처리 분담 (2026-09-14, 설계자 지시 — fs 서비스 준비 전 미리 기록)

> VFS의 루트는 커널이 소유하고 관리하는데, 마운트 포인트에 대한
> 실질적인 처리를 커널 서비스인 `fs` 서비스가 처리한다.

§2-A 원칙("커널이 모든 통제권을 쥔 유저랜드 서비스")을 VFS에 구체적으로
적용한 것이다 - **VFS 트리 구조 자체(루트, 경로 해석, 위 §4의 계층)는
커널이 소유·관리**하지만, 각 마운트 지점에서 실제로 파일시스템 드라이버를
구동하고 읽기/쓰기 요청을 처리하는 **실질적인 일은 `fs`
서비스**가 맡는다(§2-A가 원래 확정했던 "fs도 유저랜드 구동, 통제권만
커널" 원칙과 같은 결로 나눈 것 - 단 §2-A 정정 각주대로 `fs`는
2026-09-21부로 유저랜드가 아니라 커널 `KernelThread`로 구동된다,
**이 분담 원칙 자체(VFS 트리는 커널 소유, 마운트 지점 실질 처리는
fs 담당)는 fs의 실행 특권과 무관하게 그대로 유효**하다 - fs가 어느
특권 레벨에서 도는지와 "커널 vs fs가 어느 책임을 지는지"는 별개
질문이다) - 커널은 마운트 지점을 라우팅 대상으로만 알고 있고, 그
지점에서 무슨 파일시스템이 어떻게 동작하는지는 `fs` 서비스의 구현
세부다.

**이미 이 원칙을 따르고 있는 선례**: `sys/live/`(§4) 자체가 이미 "이
시스템을 지탱하는 커널과 커널 서비스들이 담당"으로 정의돼 있고, 그
하위의 `/sys/live/named/`(SP-1FBC0EEB, 메시징 채널 등 이름 있는
IPC 오브젝트 네임스페이스, PL-C8648D4D로 구현 완료)는 실제 VFS/`fs`
서비스가 아직 없는 지금 단계에서 **커널 자체 내부 이름 테이블**로
구현돼 있다 - 이는 "VFS 루트는 커널이 관리"라는 이번 원칙과 정확히
일치하는 배치다(설계자 확인 완료, PL-C8648D4D 참고). `fs` 서비스가
실제로 구축되면, 일반 마운트 지점(`sys/etc`, `sys/bin`, `mnt`,
`usr/*/mnt` 등)의 실질 처리는 그쪽으로 넘어가고, 커널은 계속 VFS
루트/경로 해석과 `sys/live/` 같은 커널 자체 서비스 하위 트리만
직접 관리하면 된다.

## 5. 가상 메모리 주소공간 관리

1. Higher half 커널.
2. 가상 주소의 상위 필드를 분할해 세그멘테이션함으로써 조회 속도를 최적화한다.
3. 유저랜드는 0번지부터 시작해 **128TiB**까지 사용한다(프로세스별 맵핑
   트리를 갖는다 — 4레벨 페이징 canonical 하위 절반의 수학적 상한과
   정확히 일치, 이전 판(256TiB)은 오기였음, QU-72108298 답변 확정,
   2026-09-14) — 주소 공간을 분할해 라이브러리 로딩 및 재배치 최적화가
   가능할 것으로 보인다.
4. On-demand 맵핑, page-fault 기반.

## 5-A. 유저 주소공간 내부 레이아웃 (2026-09-14, 설계자 답변 확정 — QU-7043EA6D)

  - 스택 쪽: 스택 오버플로우를 실제로 탐지하기 위한 가드 페이지.
  - 코드 쪽: 프로그래밍되지 않은(로드되지 않은) 영역에 대한 실행

- 힙(brk)/mmap 영역의 정확한 경계는 아직 미정 — RM-23F4B687 §4 취지상

- **로더는 ELF 파일 자신의 테이블을 항상 우선한다**(2026-09-14, 설계자
  지시 - "유저랜드의 주소가 0x400000부터 시작하는 것은 맞는데,
  컴파일된 ELF 파일을 로드할 때는 ELF 파일에 기록된 테이블들을
  우선시해야 해"): 0x400000은 **이 프로젝트 자체 유저랜드 툴체인의
  링커 스크립트가 선택한 관례값**(`userland/cmake/linker-userland-x86_64.ld`)
  일 뿐이다 - 커널의 ELF 로더(`minicore/libs/libelf`)는 이 값을 어디에도
  하드코딩하지 않고, 항상 로드하는 그 ELF 파일 자신의 프로그램 헤더
  (`p_vaddr`)와 `e_entry`를 그대로 따른다(이미 그렇게 구현돼 있음 -
  `elf::loadIntoAddressSpace`가 `seg.vaddr`만 보고 매핑, PN-58501EAA
  참고). 즉 0x400000은 "우리 툴체인이 만드는 바이너리의 관례적인 링크
  주소"이지 "로더가 강제하는 주소"가 아니다 - 다른 주소에 링크된
  ELF(예: 이식된 다른 툴체인 산출물)를 넘겨도 로더는 그 파일이 적힌
  그대로 로드해야 한다.
