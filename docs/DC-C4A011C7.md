## 배경

`PN-24A2B6F5`(authmgr E2E)가 CreateUser/LookupByUid, 이후 Ping-only로
축소 재현까지 시도하는 동안, "요청은 정확히 전달되는데 응답이 끝내
안 오는" 무응답 버그를 반복 재현했다 - 크래시 없음, `DC-2CB9DDA0`가
이미 해소한 캐스케이딩 gLock/gWriteLock/gPreemptiveQueues NMI
watchdog 계열과는 gdb로 무관함이 확인됐다(4코어 전부 정상 idle,
`Spinlock::lock()` 스핀 없음). Ping-only 10회 배치 - 8/10이
`ConnectChannel`(클라이언트)/`AcceptFromChannel`(서버) 핸드셰이크
자체에서 이미 실패.

코드 추적 결과, 이 세션 내내 안정적으로 성공해 온 Socket 계열
(`sockclient`/`socktest` 등)은 실제로 `SocketConnectHandler::onExec`
가 `kSubmitAndAwait()`로 `ConnectChannelHandler`를 **같은 AsyncTask
코루틴 안에서 중첩 호출**한다(`AsyncTaskAwaiter(nested).await()`) -
물리 UserThread의 raw syscall `wait()`가 직접 관여하지 않는다. 반면
`authtest`/`authmgr`(그리고 2026-09-23 pubreg-as-client 최초 시도)는
`ConnectChannel`/`AcceptFromChannel`을 **서로 다른 두 프로세스가 각자
유저랜드에서 raw `mc::submit()`+`mc::wait()`로 직접** 부른다 - 이
조합이 이번 세션 어디서도 안정적으로 성공한 적이 없다.

## 발견한 근본 원인 후보 - `AsyncTask::waitingTask`의 크로스코어 동기화 누락

`minicore/kernel/syscall.cpp`의 `kCheckPendingWaitOnce()`(raw syscall
`wait()`/`waitAnyForMultipleSyscall()`가 공유하는 "한 번 확인" 로직)가
대상 AsyncTask가 아직 안 끝났으면 그 AsyncTask에 대기자를 등록한다:

```cpp
// syscall.cpp:262-308, PreemptionGuard 스코프 안
reinterpret_cast<AsyncTask*>(slot->value.token)->waitingTask = self->weakAsTask();
```

이 대입은 `PreemptionGuard`(이 코어의 로컬 선점만 막는 장치 - cli와
동등한 단일 코어 보호)로만 감싸여 있다. 반대쪽, 해당 AsyncTask가
실제로 완료될 때(`minicore/kernel/async_task.cpp:1228-1241`,
`drainOnce()`가 어느 코어에서든 이 AsyncTask를 마저 실행해 `Completed`/
`Failed`에 도달한 시점) 대기자를 깨우는 코드:

```cpp
// async_task.cpp:1239-1241
if (SharedPtr<Task> waiter = task->waitingTask.lock()) {
    Scheduler::scheduleImmediate(coreIndex, waiter.get());
}
```

이 `task->waitingTask.lock()` 호출은 **완전히 다른 코어**(그 AsyncTask의
`homeCoreIndex`, 즉 최초 `submit()` 시점의 제출자 코어 - 반드시 대기자가
나중에 `wait()`를 부르는 코어와 같다는 보장이 없다)에서 일어날 수
있다. `WeakPtr<T>::operator=`(`libkenv/shared_ptr.h:350-358`)를
직접 확인했다:

```cpp
WeakPtr& operator=(const WeakPtr& other) {
    if (this != &other) {
        if (_block) _block->releaseWeak();
        _block = other._block;   // 평범한 포인터 대입, 원자적이지 않음
        _ptr = other._ptr;       // 마찬가지
        if (_block) _block->addWeakRef();
    }
    return *this;
}
```

**`_block`/`_ptr` 둘 다 원자적 연산도, 메모리 배리어도, 공유 락도
전혀 없는 평범한 포인터 대입이다.** 즉 `task->waitingTask = ...`
(코어 A, `PreemptionGuard`로 코어 A 자신의 선점만 방지)와
`task->waitingTask.lock()`(코어 B, 아무 보호 없음)가 **서로 다른
코어에서 동시에 일어나면 고전적인 동기화 없는 데이터 레이스**다 -
C++ 표준상 미정의 동작이고, 실제 x86 SMP에서는 코어 B가 코어 A의
쓰기를 아직 못 본 상태(캐시 일관성 전파 지연, 명시적 배리어 없음)로
읽어 `waitingTask`가 비어 있다고 판단해 **그 완료 통지를 조용히
영구 유실**할 수 있다 - 크래시 없이, 대기자만 영원히 깨어나지 못한다.
이 코드베이스가 이번 세션 내내(`DC-2CB9DDA0`) 정확히 이런 종류의
"크래시 없는 무응답"을 여러 번 다른 자료구조(전역 `Spinlock`들)에서
찾아 고쳐 온 것과 정확히 같은 패턴이 여기 또 있는 것으로 보인다 -
다만 이번엔 락이 아예 없는 필드다.

**왜 이 조합에서만 드러났는가(추정)**: `ConnectChannelHandler`/
`AcceptFromChannelHandler`의 핸드셰이크는 **서로 다른 두 프로세스**가
관여해 `homeCoreIndex`가 자연스럽게 갈릴 확률이 높다(각자 다른
타이밍에 다른 코어에서 실행 중이었을 수 있음). 반면 `kSubmitAndAwait`
중첩 경로(Socket 등)는 물리 UserThread의 raw `wait()`를 거치지
않아 이 `waitingTask` 필드 자체를 안 쓴다(`AsyncTaskAwaiter::await()`
가 완전히 다른, 같은 AsyncTask 실행 흐름 안에서의 관찰 메커니즘일
가능성 - 확인 필요, 아래 §미해결 참고). 단일 프로세스가 반복
`submit()`+`wait()`를 거는 패턴(예: authtest 자신의 `ChannelWrite`/
`ChannelRead` 반복)은 `homeCoreIndex`와 `wait()` 실행 코어가 우연히
일치할 확률이 높아(같은 짧은 코드 블록 안에서 연달아 실행) 이 레이스가
드물게만 드러났을 수 있다 - authtest 조사에서 CreateUser write+
authmgr의 read까지는 실제로 성공한 사례가 있었던 것과 결이 맞는다.

## 영향 범위

이 레이스가 실제 원인이라면 **authmgr에 국한되지 않는다** - `raw
ConnectChannel`/`AcceptFromChannel`을 유저랜드에서 직접(즉
`kSubmitAndAwait` 중첩 없이) 쓰는 모든 현재/미래 기능이 잠재적으로
영향을 받는다. 더 넓게는, **어떤 raw syscall이든 그 AsyncTask의 완료가
제출 코어와 다른 코어에서 일어날 수 있는 모든 경우**(Channel connect/
accept 핸드셰이크처럼 서로 다른 프로세스가 관여하는 비동기 완료)가
이론적으로 노출된다 - 단일 프로세스가 반복 제출하는 흔한 패턴은
우연히 갈릴 확률이 낮아 지금까지 드러나지 않았을 뿐일 수 있다.

## 미해결 - 확정을 위해 필요한 것

1. **gdb로 직접 확인 안 함** - 이 DC는 정적 코드 추적만으로 도출한
   가설이다. 재현 시 실패한 `ConnectChannelHandler`/
   `AcceptFromChannelHandler` AsyncTask의 `homeCoreIndex`와, 그
   완료를 처리한 실제 코어, 그리고 대기자 등록 시점의 코어를 gdb로
   직접 비교 확인해야 한다.
2. **`AsyncTaskAwaiter::await()`(kSubmitAndAwait 중첩 경로가 씀)가
   정말 `waitingTask`를 안 쓰는지** 확인 필요 - 이 문서 작성 세션은
   이 함수 내부까지는 못 읽었다.
3. 다른 필드(`waitingAsyncTask` 등, 코루틴 간 대기)도 같은 패턴(평범한
   대입, 크로스코어 잠재 노출)인지 함께 점검 필요 - 이 문서는
   `waitingTask`만 확인했다.

## 결정이 필요한 지점 - 고칠 방향

(A) `task->waitingTask`의 쓰기(코어 A)/읽기(코어 B) 양쪽을 감싸는
    전용 락 신설(`Spinlock` 또는 `IrqSpinlock` - 이 필드가 ISR
    인접 경로에서도 만져지는지 확인 필요) - `DC-2CB9DDA0`이 이번
    세션에 확립한 "짧은 임계구역 공유 상태는 락으로 보호" 원칙을
    그대로 적용. 가장 직접적이고 위험이 적은 수정으로 보이나, 매
    syscall 완료마다 락 오버헤드가 추가된다.
(B) `WeakPtr<T>`의 내부 포인터 필드 자체를 원자적으로 바꾼다 - 그러나
    `WeakPtr`는 프로젝트 전체에서 광범위하게 쓰이는 범용 타입이라
    (Task::blockedOn, EnableSharedFromThis 등) 영향 범위가 크고,
    "이 특정 크로스코어 공유 용도"에만 원자성이 필요한 다른 대다수
    사용처엔 불필요한 오버헤드가 된다 - RM-23F4B687 §4 과설계
    방지 원칙과 충돌 소지.
(C) `waitingTask`만 원자적 접근이 가능한 별도 전용 타입(예: 락 없는
    포인터 CAS 기반의 얇은 래퍼, 또는 그냥 `Atomic<AsyncTask*>`류
    raw 포인터 - `WeakPtr`의 강한/약한 참조 카운팅이 이 특정 용도엔
    애초에 필요 없을 수도 있음, 확인 필요)로 교체.
(D) 구조 자체를 바꿔 "대기자 등록"이 AsyncTask 완료 가능성이 생기기
    전에(예: `submit()` 시점 자체에, 아직 아무도 그 완료를 처리할 수
    없는 시점에) 미리 끝나도록 재설계 - 근본적으로 이 경쟁이 성립할
    타이밍 창 자체를 없앤다. 가장 근본적이지만 범위가 가장 크다.

이 프로젝트가 이번 세션 `DC-2CB9DDA0`에서 이미 (A)류 해법(전역 공유
상태를 IrqSpinlock으로 감싸는 체계적 감사)을 성공적으로 적용해 본
직접적 선례가 있어, 개인적으로는 (A)가 가장 안전해 보이지만 최종
결정은 설계자님께 맡긴다.
