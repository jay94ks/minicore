# 4K 페이지의 2M 페이지 병합 — 요구분석

## 배경

SP-8B6B8D25 §2 항목8은 "페이지 병합(예: x86-64에서 4K 페이지를 모아
2M 페이지로 병합)"을 커널이 담당하는 범위로 명시했고, QA-26450C3E도
"4K 페이지가 조건에 따라 2M 페이지로 병합된다"를 검증 시나리오로
남겨 뒀다. 그러나 "조건에 따라"가 구체적으로 어떤 조건인지, 언제
병합이 일어나는지는 어디에도 정해진 바가 없다 — 지금 코드 상태를
보면:

- `PageFrameAllocator`의 버디 할당자는 이미 order 0(4KiB)부터
  order 10(4MiB)까지 지원한다(`kMaxOrder = 10`, `page_frame_allocator.cpp:11`)
  - order 9가 정확히 2MiB라, "물리 프레임을 2MiB 단위로 통째로
    할당받는 것" 자체는 이미 가능하다.
- `Paging::mapPage`는 언제나 4KiB PT 리프 엔트리 하나만 만든다
  (`paging.cpp`) - PD 엔트리에 PS 비트를 세워 2M 대형 페이지로 직접
  매핑하는 경로가 아예 없다.
- `Paging::handlePageFault`(지연 매핑 구역, `kLazyZoneBase`, 1GiB)는
  폴트가 날 때마다 `PageFrameAllocator::allocPage()`(order 0)를
  불러 4KiB씩 독립적으로 매핑한다 - 같은 2M 정렬 구간 안의 512개
  가상페이지가 각각 다른 시점에, 서로 물리적으로 인접하지 않은
  프레임을 받을 수 있어 "나중에 되돌아보고 병합"하는 방식은 대부분의
  경우 애초에 병합 대상이 안 될 가능성이 높다.
- 이미 대형 페이지를 쓰는 유일한 곳(direct map, `Paging::init()`)은
  1GiB 페이지 4개를 **정적으로** 까는 방식이라 이번 "4K→2M 병합"
  범위와는 무관하다(이미 완료된 별개 메커니즘).
- 실제로 4K 매핑이 대량으로(그리고 종종 연속으로) 생기는 기존 코드는
  `Pci::init()`의 MMCONFIG(ECAM) 매핑 - bus 0 전체 1MiB를 256개
  개별 4KiB `Paging::mapPage` 호출로 채운다(`pci.cpp`). 이 영역은
  전부 캐시비활성(UC) + 같은 권한이라, 병합 조건을 논할 때 참고할
  실제 사례가 된다.

## 결정이 필요한 항목과 각 선택의 영향

1. **병합 시점(트리거)**: 다음 중 어느 방식으로 갈지가 구현 자체를
   완전히 다르게 만든다.
   - (a) **매핑 시점에 미리 큰 페이지로**: 처음부터 4K를 여러 개
     만들지 않고, 요청받은 범위가 2M 정렬+512개 연속 물리 프레임
     조건을 만족하면 `mapPage`(또는 별도 API)가 바로 PD에 PS 비트로
     매핑한다. 구현이 단순하고 TLB 항목도 즉시 줄지만, "기존에 이미
     4K로 매핑된 것을 나중에 합친다"는 문자 그대로의 "병합"은 아니다.
   - (b) **사후 병합(진짜 compaction)**: 이미 4K로 매핑된 영역을
     주기적으로(또는 명시적 호출 시점에) 스캔해서, 조건을 만족하면
     512개 PT 엔트리를 지우고 PD 엔트리 하나(PS 비트)로 교체한다.
     TLB 무효화 범위가 넓고(512개 엔트리 전부), 스캔 비용도 있지만
     "이미 흩어져 매핑된 것도 나중에 합쳐진다"는 QA 문구에 더 가깝다.
     이 경우 배경 스레드/타이머 기반 정기 컴팩션이 필요한지, 아니면
     특정 이벤트(예: 메모리 압박) 때만 도는지도 같이 정해야 한다.
   - (c) **명시적 API 호출 시에만**: 자동으로는 절대 안 하고, 호출부
     (예: 향후 유저 프로세스 ELF 로더가 큰 세그먼트를 한 번에 매핑할
     때)가 스스로 큰 페이지 매핑을 요청하는 API만 제공한다. 사실상
     "병합"이 아니라 "대형 페이지 매핑 지원"에 가깝다.
2. **분할(split)도 같이 필요한가**: 병합을 지원하면 그 반대(2M 매핑
   중 일부 4K만 권한을 바꾸거나 언맵해야 하는 상황, 예: 향후 스왑/
   데맨드페이징)도 언젠가 필요해진다 - 이번 범위에 분할까지 포함할지,
   아니면 "병합된 뒤엔 그 2M 영역 전체를 단위로만 다룬다"(부분 변경
   금지)는 제약을 둘지 미리 정해야 API 모양이 달라진다.
3. **적용 대상 범위**: 지금 커널 안에서 4K 매핑이 실제로 쌓이는 곳은
   지연 매핑 구역(`kLazyZoneBase`, 폴트마다 독립적으로 프레임을 받아
   자연 병합 대상이 거의 안 됨)과 PCI MMCONFIG(캐시비활성, 이미 연속
   물리 프레임+동일 권한이라 병합에 가장 적합) 정도뿐이다 - 유저
   프로세스 페이지 테이블(아직 없음)이 생기기 전까지는 이 기능을
   실제로 쓸 데가 마땅치 않을 수 있다. **지금 시점에 구현/검증까지
   할지, 아니면 유저랜드가 생겨 실제 수요가 명확해질 때(예: ELF
   세그먼트 매핑)로 미룰지** 결정이 필요하다.
4. **병합 조건의 정확한 정의**: (b)/(a) 어느 쪽이든 "이 2M 구간을
   합쳐도 되는지" 판정 기준을 명시해야 한다 - 예: 512개 항목 전부
   present, 물리주소가 연속(base+i*4K), PAGE_WRITABLE/PAGE_USER/
   PAGE_CACHE_DISABLE 등 플래그가 전부 동일. 이 중 하나라도 다르면
   병합 불가인데, "권한이 다른 인접 페이지가 하나라도 있으면 그 2M
   구간 전체가 영구히 병합 대상에서 빠지는 것"을 허용할지, 아니면
   재배치(다른 프레임으로 옮겨서라도 병합)까지 고려할지도 갈린다.
5. **버디 할당자와의 관계**: 이미 order 9(2MiB) 할당이 가능하므로,
   (a) 방식을 택하면 `PageFrameAllocator::allocOrder(9)`로 통째로
   프레임을 받아 한 번에 매핑하는 것만으로 충분할 수 있다 - 반대로
   (b) 방식(사후 병합)을 택하면 이미 독립적으로 흩어져 할당된
   4K 프레임들은 애초에 물리적으로 연속이 아닐 확률이 높아, "재배치
   없이는 병합이 거의 발생하지 않는" 구조적 한계를 그대로 받아들일지
   결정해야 한다.
