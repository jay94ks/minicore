# Slab 할당자(libkmm) — 설계 제안

**[제안, 검토 대기, 2026-09-14]** 비동기 프레임워크(SP-F682B889)의
`args` 할당에 쓸 Slab 할당자를 설계자 지시(QU-F86426D5 답변,
2026-09-14 - "libkmm에 Slab 할당자를 미리 구현하고... 코어 단위로
관리되는 유닛과, 커널 전역 단위로 관리되는 유닛으로 나뉘어야 한다.
추가 설계가 필요하다면 설계 제안서를 작성하도록 하라")에 따라
제안한다. `minicore/libs/libkmm`은 SP-8B6B8D25 §3.1에 이름만
예약돼 있고 아직 실제 코드가 없다 - 이 제안이 그 첫 구현이 된다.

## 1. 배경 / 동기

같은 크기 객체(비동기 프레임워크의 `args`, 향후 다른 고정 크기
커널 자료구조)를 반복적으로 할당/해제하는 경로에서 범용 할당자
(예: 향후 있을 `PageFrameAllocator` 기반 malloc류)를 매번 거치면
단편화와 오버헤드가 쌓인다. Slab 할당자(Bonwick 1994, "The Slab
Allocator")는 고정 크기 객체 전용 캐시를 둬서 이 비용을 없애는
표준 기법이고, 멀티코어 환경에서는 코어별 "매거진"(작은 로컬
프리스택)으로 락 경합 없이 빠른 경로를 만드는 확장(Bonwick & Adams
2001, "Magazines and Vmem")이 널리 쓰인다 - 설계자가 요구한
"코어 단위 유닛 + 전역 유닛" 구조가 정확히 이 매거진/디포 모델이다.

## 2. 핵심 구조

### 2.1 2단 구조 - 코어별 매거진(빠른 경로) + 전역 디포(재분배/슬랩 관리)

```
[코어 0 매거진] [코어 1 매거진] ... [코어 N 매거진]   <- 락 없음, 이 코어만 접근
        \            |                /
         \           |               /
          [전역 디포: 가득/빈 매거진 목록]              <- 코어 간 재분배
                     |
              [슬랩 페이지들](PageFrameAllocator에서 확보)
```

- **매거진(Magazine)**: 코어마다, 캐시(객체 종류)마다 하나씩 - 고정
  용량(예: 15개)의 포인터 스택. `alloc()`은 이 코어의 매거진에서
  pop, `free()`는 이 코어의 매거진에 push - **다른 코어와 전혀
  통신하지 않는 한 락이 필요 없다**(이 코어만 건드리므로).
- **디포(Depot)**: 캐시마다 전역으로 하나 - "가득 찬 매거진" 목록과
  "빈 매거진" 목록을 lock-free 스택(libkenv의 `AtomicPtr<T>`,
  스케줄러/비동기 프레임워크와 동일한 CAS 프리미티브 재사용)으로
  관리한다. 코어의 매거진이 비었는데 alloc해야 하면 디포에서 가득
  찬 매거진 하나를 통째로 교체해 온다(없으면 슬랩에서 직접 채움).
  코어의 매거진이 가득 찼는데 free해야 하면 디포에 그 매거진을
  통째로 넘기고 빈 매거진을 하나 받아 온다(없으면 새로 만듦).
  **디포를 건드리는 건 매거진 전체가 비거나 찰 때뿐**이라 개별
  alloc/free보다 훨씬 드물게 일어난다 - 코어 간 재분배 비용이
  객체 단위가 아니라 매거진(예: 15개) 단위로 상각된다.
- **슬랩(Slab)**: `PageFrameAllocator::allocOrder`로 확보한 물리
  페이지(direct map으로 접근) 하나를 고정 크기 객체 N개로 미리
  나눠 둔 것 - 빈 객체 안에 "다음 빈 객체" 포인터를 겹쳐 써서
  별도 메타데이터 없이 프리리스트를 구현한다(전통적 slab 기법).
  디포가 완전히 고갈되면(매거진도 없고 슬랩 프리리스트도 없음)
  새 슬랩 페이지를 `PageFrameAllocator`에서 하나 더 받아온다.

### 2.2 API

```cpp
namespace kernel {

// 객체 크기 하나를 전담하는 캐시 - 설계자 지시(2026-09-14)의
// "코어 단위 유닛 + 커널 전역 단위 유닛" 2단 구조.
class SlabCache {
public:
    // objectSize: 최소 sizeof(void*)(빈 객체에 free-list 포인터를
    // 겹쳐 씀 - 그보다 작은 요청은 GenericSlabAllocator가 올림).
    void init(unsigned long objectSize);

    void* alloc();
    void free(void* ptr);
};

// 임의 크기 객체를 위한 범용 래퍼(설계자 지시 - "이걸 또 wrapping
// 하여 generic한 slab 할당자를 구현") - 2의 거듭제곱 버킷(예: 32/
// 64/128/256/512/1024바이트)마다 SlabCache 하나씩 두고 요청 크기를
// 올림해 맞는 버킷을 고른다(malloc류 범용 할당자의 표준 기법).
class GenericSlabAllocator {
public:
    static void init();
    static void* alloc(unsigned long size);
    // free는 크기를 재계산하지 않고 호출부가 그대로 알려준다(더
    // 간단하고 빠름 - 대부분의 호출부는 이미 그 크기를 알고 있음).
    static void free(void* ptr, unsigned long size);
};

}  // namespace kernel
```

## 3. 비동기 프레임워크와의 관계

`GenericSlabAllocator::alloc/free`가 `AsyncTask`의 `args` 할당,
그리고 `AsyncTask` 자신의 (상대적으로 작은) 전용 스택 확보에도
재사용될 수 있다 - 스택도 결국 고정 크기 객체이므로 버킷 하나로
다룰 수 있다(정확한 크기/공용 여부는 비동기 프레임워크 실행 계획
쪽에서 확정).

## 4. 결정이 필요한 항목 (별도 DC로 등록 예정)

1. **매거진 용량**: 코어별 매거진 하나에 몇 개까지 담을지(예: 15,
   31) - 크면 디포 접근이 줄지만 코어별 유휴 메모리가 늘어난다.
2. **버킷 크기 목록**: `GenericSlabAllocator`가 몇 개의 버킷을
   둘지(예: 32/64/128/256/512/1024/2048바이트) - 버킷이 많으면
   내부 단편화가 줄지만 캐시 개수(=메타데이터+매거진 배열)가
   늘어난다.
3. **슬랩 백킹 페이지 크기**: 슬랩 하나당 `PageFrameAllocator`
   order 0(4KiB)만 쓸지, 객체가 커지면 더 큰 order를 쓸지(작은
   객체를 4KiB 슬랩에 담으면 페이지당 개수가 많아 프리리스트
   초기화 비용이 있고, 큰 order를 쓰면 페이지당 개수는 늘지만
   버디 할당자에서 큰 블록을 더 자주 요구하게 됨).
4. **디포 고갈 시 정책**: `PageFrameAllocator`까지 완전히 고갈되면
   (물리 메모리 자체가 없음) `alloc()`이 null을 반환해야 하는지,
   호출한 Task/AsyncTask를 블로킹해야 하는지 - 비동기 프레임워크의
   `AsyncOp`/`AsyncTask` 풀 고갈 정책(DC-01434F82에서 이미 "지금
   포함"으로 결정된 AsyncTaskGroup 관리와도 연동).
