## 배경

PL-2D3184BC 3단계(Task 커널 스택 가드 페이지)를 구현하던 중, IST가
전혀 없어 가드 페이지가 잡은 #PF를 전달하려는 시도 자체가 재폴트 ->
#DF -> 트리플 폴트(조용한 리셋)로 격상되어 진단 로그를 전혀 남기지
못하는 문제를 발견했다(DC-3D3212A4). 설계자 답변(QU-4E00C118):

> "TSS+IST를 정식 구현하여 가드 페이지가 실제 진단 로그를 남기게
> 만들고, TSS+IST가 다른 곳에서도 활용 할 수 있도록 설계하여
> 설계안을 제출하라. 규모가 커지면 이 부분을 디버깅하기 더
> 어려워진다."

이 문서는 그 설계안이자, 이미 구현·실측까지 마친 결과 보고다(설계
제안과 구현 검증을 한 번에 진행 - 설계자 지시가 "구현하여 ...
설계하여 설계안을 제출하라"로 구현까지 포함해 명시적으로 지시했기
때문이다).

**[2026-09-14 추가]** 설계자가 후속 지시: "#DF 외 다른 벡터(NMI/#MC/
#DB)의 IST 배정도 고려하라." - §"IST 슬롯 배정" 절과 실측 검증 3번
항목에 반영, 구현·실측 완료.

**[완료, 2026-09-14, 계획 PN-3B781046]** 이 서브시스템은 아래 내용대로 구현·검증까지 완료됐다.

## 설계 원칙

- **x86 하드웨어 태스크 스위칭(레지스터 상태 전체를 하드웨어가 통째로
  갈아 끼우는 방식)은 여전히 안 쓴다** - PL-2D3184BC 3번 결정
  ("컨텍스트 전환은 소프트웨어 방식")은 그대로 유효하다. 이 TSS는
  x86_64에서 사실상 두 가지 용도로만 쓰는 "설정 그릇"일 뿐이다:
  1. **IST(Interrupt Stack Table)** - 특정 예외 벡터에 대해, 현재
     RSP가 무엇이든(설령 고장나 있어도) CPU가 항상 정해진 별도
     스택으로 강제 전환한 뒤 핸들러를 실행하게 한다.
  2. **RSP0** - 향후 유저랜드가 생기면 ring3->ring0 전환(syscall
     진입 등) 시 커널 스택 포인터로 재사용할 자리(이번 범위에서는
     필드만 존재, 아직 안 씀 - SP-8B6B8D25 유저랜드 계획과 맞물림).
- **"다른 곳에서도 활용 가능하게" 설계**: IST 슬롯은 1개(#DF)만
  하드코딩하지 않고, x86_64가 제공하는 IST1-7 전부를 구조체에 그대로
  두어 향후 다른 벡터가 필요해지면 같은 패턴(그 벡터 전용 스택 확보
  + IDT 게이트의 ist 필드 설정)으로 바로 확장할 수 있게 했다 - 그리고
  실제로 이 확장성이 바로 다음 지시(NMI/#MC/#DB 추가)에서 검증됐다.
  RSP0 필드도 같은 이유로 미리 자리를 잡아 뒀다.
- **코어별 독립** - SMP(PL-65C20380)가 이미 존재하므로, TSS/IST
  스택은 코어마다 완전히 독립된 것이어야 한다(여러 코어가 동시에
  #DF에 빠져도 서로의 스택을 밟지 않게). "테이블 내용은 전역 하나,
  포인터 레지스터는 코어마다 개별 적재"라는 이 프로젝트의 기존 IDT
  패턴(`Idt::init()`/`Idt::reloadOnThisCore()`)을 GDT/TSS에도 그대로
  적용했다 - 코드 스타일과 정신 모델의 일관성을 위해서다.

## 구현

### GDT 확장

`minicore/kernel/gdt.h`/`gdt.cpp` 신설. boot.S가 부팅 초기에 이미
최소 GDT(`gdt64`: null/code64/data, 3개 8바이트 디스크립터)를 실어
long mode에 들어와 있었지만, 거기엔 TSS 디스크립터를 넣을 자리가
없었다. `Gdt::init()`이 코드/데이터 디스크립터 값은 `gdt64`와 **완전히
동일하게** 유지한 채(그래서 이미 캐시된 CS 히든 디스크립터를 다시
로드할 필요가 없다 - GDTR을 바꿔도 CPU가 CS 캐시를 스스로 재적재하진
않으므로, 같은 셀렉터 위치에 같은 내용만 있으면 `lgdt`만으로 안전하게
갈아탈 수 있다), 코어마다 하나씩 16바이트 TSS 디스크립터 슬롯
(`kAcpiMaxCpus`개, acpi.h)을 추가한 새 GDT로 교체한다.

```
GDT 배치: [0]=null(8B), [1]=code64(8B), [2]=data64(8B),
          [3.. ]=코어0 TSS(16B), 코어1 TSS(16B), ...
```

### TSS 구조체

Intel SDM Vol.3 Figure 8-11을 그대로 따르는 104바이트 packed 구조체
(`reserved0, rsp0-2, reserved1, ist1-7, reserved2, reserved3,
ioMapBase`) - `static_assert(sizeof(Tss) == 104)`로 레이아웃 오류를
컴파일 타임에 잡는다. IOPB(I/O 권한 비트맵)는 안 쓰므로
`ioMapBase = sizeof(Tss)`로 세그먼트 한계 밖을 가리키게 해 비활성화
한다(표준 관례).

### IST 슬롯 배정 (2026-09-14 확장)

설계자 후속 지시로 #DF 외 세 벡터도 IST를 받는다 - 넷 다 "현재 RSP가
뭐든 무관하게 항상 유효한 스택이 필요한" 벡터라는 공통점이 있다:

| IST 슬롯 | 벡터 | 이름 | 이유 |
|---|---|---|---|
| IST1 | 8 | #DF (Double Fault) | 다른 예외 전달 중 재폴트 시 격상 - IST 없으면 그 재폴트가 다시 실패해 트리플 폴트로 이어진다(DC-3D3212A4 실측). |
| IST2 | 2 | NMI | 마스크 불가능(cli로도 못 막음) - 스핀락을 쥔 채거나 컨텍스트 전환 도중처럼 RSP가 일시적으로 불안정한 어떤 순간에도 끼어들 수 있다. |
| IST3 | 18 | #MC (Machine Check) | 하드웨어 오류 - NMI와 같은 이유로 임의 시점에 들어올 수 있다. |
| IST4 | 1 | #DB (Debug) | 브레이크포인트/싱글스텝 - 향후 디버깅 지원 시 같은 이유로 필요해질 것을 대비해 미리 배정. |

`minicore/kernel/gdt.cpp`의 `gIstStacks[4][kAcpiMaxCpus][8192]` -
슬롯 0-3이 각각 위 표의 IST1-4에 대응하는 코어별 전용 스택이다(각
8KiB, Task 기본 커널 스택과 동일 크기). IST5-7은 아직 안 쓴다 -
다른 벡터가 필요해지면 이 배열을 늘리고 `idt.cpp`에 같은 패턴으로
추가하면 된다(계획 PN-5377545F).

### 코어별 초기화 흐름 (IDT 패턴과 동일)

- `Gdt::init()` - **BSP 전용**, 부팅 중 한 번. GDT 내용(코드/데이터 +
  전체 코어의 TSS 디스크립터 슬롯)을 만들고, 자기 자신의 GDTR도
  적재한다. `Idt::init()` 바로 앞에서 호출한다 - 실제 코어 수를 몰라도
  되게 설계했다(`kAcpiMaxCpus` 상한만큼 슬롯을 미리 다 만들어 둠).
- `Gdt::reloadOnThisCore()` - **AP 전용**. `ap_trampoline.S`가 boot.S의
  예전 `gdt64`(TSS 디스크립터 없음)를 그대로 쓴 채로 `kApMain`에
  진입하므로, BSP가 만들어 둔 새 GDT로 이 코어의 GDTR을 갈아 껴야
  `loadTssForThisCore`가 쓸 TSS 디스크립터를 찾을 수 있다.
  `Idt::reloadOnThisCore()`와 같은 타이밍(`kApMain` 맨 앞)에 호출한다.
- `Gdt::loadTssForThisCore()` - **모든 코어**(BSP + 각 AP)가 자기
  자신의 `Lapic::init()` 직후 호출한다. `Lapic::id()`로 `Acpi::
  cpuApicId()` 배열에서 자기 코어 인덱스를 찾아(page_frame_allocator.cpp
  의 `kCurrentNumaNode()`와 같은 패턴), 그 인덱스의 TSS의 `ist1-4`를
  이 코어 전용 8KiB 스택 4개(정적 배열, `gIstStacks[slot][coreIndex]`)
  의 꼭대기로 각각 채운 뒤, 그 코어의 TSS 셀렉터로 `ltr`을 실행한다.
  TR도 GDTR/IDTR과 마찬가지로 코어별 레지스터라 공유 불가능하다.

### IDT 연동

`minicore/kernel/idt.cpp` - `Idt::init()`이 벡터 0-31 게이트를 다
만든 직후 `gIdt[1].ist = 4`(#DB), `gIdt[2].ist = 2`(NMI),
`gIdt[8].ist = 1`(#DF), `gIdt[18].ist = 3`(#MC) 네 줄을 설정한다.
IDT 내용 자체는 전역 하나뿐이라(기존 패턴 그대로) 이 네 줄이면 모든
코어에 적용된다 - 각 코어가 자기 TSS의 IST1-4을 미리 채워 두기만
하면 된다.

## 실측 검증 (QEMU)

1. **기본(guard 페이지 OFF) 빌드, 단일 코어**: `minicore: GDT ready`
   -> `minicore: IDT ready` -> ... -> `minicore: TSS/IST ready (core
   0)` 순서로 정상 출력, 이후 부팅 전 과정(PCI 열거까지) 회귀 없음
   확인.
2. **기본 빌드, q35 `-smp 4`**: BSP의 GDT/TSS 준비 후 AP 3개가 전부
   정상 기동(`AP started, index=1/2/3`, `SMP - APs started=3
   expected=3`) - 각 AP가 자기 GDTR을 재적재하고 자기 TSS/IST를
   올바르게 채웠음을 간접 확인(TSS가 깨졌다면 이 시점 이전에 실패
   했을 것).
3. **가드 페이지 ON 빌드 + 임시 스택 오버플로우 테스트**
   (`MINICORE_TASK_STACK_GUARD_PAGE=ON`, PL-2D3184BC 3단계 검증 때와
   동일한 4KiB 스택 재귀 오버플로우 테스트를 재사용) - **DC-3D3212A4
   가 보고한 트리플 폴트/조용한 리셋이 사라지고, 다음과 같이 정상
   적으로 #DF 진단이 출력된 뒤 안전하게 멈췄다**:
   ```
   minicore: [TEST] triggering deliberate stack overflow under guard page + IST

   minicore: PANIC - unhandled exception: Double Fault
     vector=0x0000000000000008 error_code=0x0000000000000000
     rip=0xffffffff8010cc5f cs=0x0000000000000008 rflags=0x0000000000000286
   ```
   (QEMU가 리셋되지 않고 `cli; hlt` 무한루프에서 멈춰 `-no-reboot`
   타임아웃까지 그대로 유지됨을 확인).
4. **[2026-09-14 추가] NMI(IST2) 실제 스택 전환 검증** - 소프트웨어
   `int $2`로 NMI 게이트에 강제 진입시켜(하드웨어 NMI 조건을 재현할
   방법이 없어 게이트 진입 메커니즘만 확인 - IST 전환은 게이트의
   ist 필드만으로 결정되므로 진입 경로와 무관하게 동일하게 동작),
   `Gdt::loadTssForThisCore()`가 계산한 IST2 꼭대기 주소
   (`0xffffffff8015a540`)와 `kPanic` 안에서 실제로 읽은 현재 RSP
   (`0xffffffff8015a440`, 그 사이 차이 256바이트는 CPU가 푸시한
   인터럽트 프레임(5워드)+isr_common_stub이 푸시한 15개 GPR+
   vector/error_code, 그리고 `kPanic`의 지역 스택 사용분)를 비교해
   **RSP가 정확히 그 전용 IST2 버퍼 안에 들어 있음을 확인**(이전
   커널 스택이었던 `0x105dc0` 부근과는 전혀 다른, 커널 이미지
   higher-half `.bss` 영역인 `0xffffffff8015axxx`대) - IST1(#DF)에서
   이미 검증된 메커니즘이 다른 슬롯(IST2)에도 동일하게 적용됨을
   실측으로 재확인했다. #MC/#DB(IST3/4)는 코드가 완전히 같은 패턴
   (배열 인덱스만 다름)이라 별도 실측 없이 이 메커니즘 검증으로
   갈음한다.

   검증 후 모든 임시 테스트/디버그 코드는 제거 - 영구 코드는
   `gdt.h`/`gdt.cpp`와 idt.cpp/kmain.cpp/smp.cpp의 호출부만 남았다.

**결론: DC-3D3212A4가 제기한 문제와 설계자의 후속 지시(NMI/#MC/#DB
IST 배정)가 모두 해결됐다** - 가드 페이지가 이제 계획(PL-2D3184BC
4번 항목)이 원래 의도한 대로 "#PF(가 #DF로 격상되어)로 걸려 진단
가능하게" 동작하고, NMI/#MC/#DB도 임의 시점에 들어와도 항상 유효한
전용 스택에서 실행된다.

## 이번 범위에 포함하지 않은 것

- **[완료, 2026-09-15] RSP0(ring3->ring0 전환)** (계획 PN-124C105B,
  `completed`) - `kSyncRsp0ForDispatch`가 TSS.RSP0을 모든 디스패치
  지점에서 채우고, int 0x80/syscall 명령 두 트랩 경로 모두 실제
  ring3 진입/복귀로 검증 완료됐다(SP-83A07867 §8 체크리스트 ②).
- **IST5-7** (계획 PN-5377545F): 구조체는 이미 준비돼 있으나, 지금 그 이상 격리해야 할
  구체적인 벡터가 없어 배정하지 않았다. 필요해지면 `gIstStacks`
  배열을 늘리고 그 벡터의 `ist` 필드를 그 번호로 설정하면 된다.
- **NMI/#MC/#DB에 대한 실제 처리 로직** (계획 PN-F443FE73): 지금은 다른 미등록 예외와
  동일하게 `kPanic`으로 떨어진다. 이번 지시는 "IST 배정"(안전한
  스택 확보)까지였고, 이 세 벡터를 실제로 의미 있게 처리하는 것
  (예: #DB 기반 디버거 지원, #MC 복구 시도)은 별도 범위다.
  **[확정, 2026-09-16, QU-F3832FC6 답변]** "실제로 의미 있게
  처리"의 구체적 방향 - 설계자 답변: "소비자가 없어도 구현해야
  한다. #MC는 MSR 기반 정정 가능 여부 구분을 추가. #DB는 소비자가
  있다고 가정하여 설계 먼저." 즉 NMI/#DB 모두 "실제 소비자가
  생기기 전까지 미룬다"는 CLAUDE.md 규칙 4식 유보를 적용하지 않고
  지금 구현한다(#DB는 "소비자가 있다고 가정"하고 먼저 설계). 세부는
  PN-F443FE73 참고.
- **#DF 핸들러가 원래 폴트의 정확한 레지스터 상태(CR2 등)까지 복구해
  보여주는 것** (계획 PN-AD3B2D5B): x86_64 스펙상 더블 폴트 진입 시점엔 원래 컨텍스트가
  이미 상당 부분 유실된 상태라(SDM 6.15) 일반적인 OS들도 이 이상을
  시도하지 않는다 - "더블 폴트가 났다"는 사실 자체와 그 시점의
  RIP/CS/RFLAGS만으로도 트리플 폴트 대비 진단 가치는 충분하다고
  판단했다.

## NMI 활용 - 워치독 및 디버그 강제 정지 IPI (설계, 2026-09-16, Opinion "워치독/디버그 강제 정지 IPI 등 설계해줘" 반영, 계획 PN-F443FE73)

NMI(IST2, `kNmiVector=2`)가 마스크 불가능(cli로도 못 막음)하다는
바로 그 성질을 이용하는 두 가지 코어 간 통지 메커니즘 - 둘 다 실측
확인한 기존 공백을 메운다: `kPanic`(panic.cpp)은 지금 **패닉이 난
그 코어만** 멈추고(`cli; hlt` 루프) 나머지 코어는 계속 실행된다
(실측 확인, 2026-09-16) - 공유 상태를 계속 건드릴 수 있어 이후
진단을 어렵게 만든다.

### 공통 기반 - `Lapic::sendNmiIpi(destApicId)`(신규)

`Lapic::sendFixedIpi`(TLB 샷다운/로드밸런싱이 이미 쓰는 패턴)와 같은
`kSendIcr` 경로를 재사용하되, delivery mode만 Fixed(0b000, 벡터
필드 사용)에서 **NMI(0b100)**로 바꾼다 - NMI delivery mode는 벡터
필드를 무시하고 하드웨어가 항상 벡터 2(IDT의 `kNmiVector`)로
전달하므로 별도 벡터 인자가 필요 없다.

```cpp
// lapic.cpp - kIcrDeliveryModeInit/Startup와 같은 위치에 추가
constexpr kernel::uint32_t kIcrDeliveryModeNmi = 4U << 8;

void Lapic::sendNmiIpi(kernel::uint32_t destApicId) {
    const kernel::uint32_t command = kIcrDeliveryModeNmi | kIcrLevelAssert;
    kSendIcr(destApicId, command);
}
```

### NMI 발신 사유 구분 (신규, `nmi.h`/`.cpp` 또는 idt.cpp에 위치)

NMI 자체는 "왜 왔는지"를 실어 나르지 못한다(항상 벡터 2, 페이로드
없음) - TLB 샷다운의 `gPendingMask` 패턴처럼, **발신자가 보내기
전에 코어별 사유 슬롯을 먼저 세팅**해 수신측 ISR이 구분하게 한다:

```cpp
enum class NmiReason : kernel::uint32_t { None = 0, DebugHalt = 1, WatchdogTrap = 2 };
kernel::AtomicU32 gNmiReason[kAcpiMaxCpus];  // 코어별, 발신자가 발신 직전에만 씀

void kSendNmi(kernel::uint32_t targetCoreIndex, NmiReason reason) {
    gNmiReason[targetCoreIndex].store(static_cast<kernel::uint32_t>(reason));
    kernel::Lapic::sendNmiIpi(kernel::Acpi::cpuApicId(targetCoreIndex));
}
```

### NMI ISR 재구성 (`idt.cpp`, 지금은 `frame->vector==2`도 다른 미등록 벡터와 동일하게 그냥 `kPanic(frame)`으로 떨어짐 - 실측 확인)

`kPanic(InterruptFrame*)`의 최상단(다른 벡터 분기보다 먼저)에
`frame->vector == kNmiVector` 분기를 추가:

```cpp
if (frame->vector == kNmiVector) {
    const auto reason = static_cast<NmiReason>(
        gNmiReason[Scheduler::currentCoreIndex()].load());
    switch (reason) {
        case NmiReason::DebugHalt:
            // 아래 "디버그 강제 정지" 참고 - 이 코어를 영구 정지.
            Serial::write("\nminicore: NMI - debug forced halt\n");
            for (;;) { asm volatile("cli; hlt"); }
        case NmiReason::WatchdogTrap:
            // 아래 "워치독" 참고 - 진단 로그 후 이 코어도 정지
            // (재개 안전성을 확신할 수 없어 kPanic과 동일하게 처리).
            Serial::write("\nminicore: NMI - watchdog: this core unresponsive\n");
            // frame->rip/rsp/cs/rflags 등을 기존 kPanic 레지스터
            // 덤프 포맷 그대로 출력(코드 재사용).
            for (;;) { asm volatile("cli; hlt"); }
        case NmiReason::None:
        default:
            // 설명 안 되는 NMI(하드웨어 스퓨리어스 등 극히 드문 경우) -
            // 로그만 남기고 계속(과잉 대응 방지 - 실제로 겪어본 뒤
            // 재검토, RM-23F4B687 §4 원칙).
            Serial::write("\nminicore: NMI - unexplained, continuing\n");
            return;
    }
}
```

### 워치독(Watchdog)

**목적**: 어떤 코어가 인터럽트를 오래 막아 둔 채(cli) 멈춰 있거나,
그 외 이유로 스케줄러 틱조차 못 도는 상황을 자동으로 탐지한다 -
일반 IPI(Fixed)는 그런 코어에 절대 전달되지 않지만(cli가 막음),
NMI는 막을 수 없어 진단 가치가 있다.

- **하트비트**: 기존 스케줄러 틱 핸들러(코어마다 100Hz로 이미 돎)의
  맨 앞에서 `gHeartbeat[coreIndex].fetchAdd(1)` 한 줄 추가 - 이
  카운터가 최근에 늘지 않았다는 것은 "이 코어가 최근 1초 가까이
  자기 타이머 인터럽트조차 처리 못 했다"는 뜻이다.
- **감시자**: v1은 **BSP(코어0) 자신의 틱 핸들러**가 맡는다(전용
  워치독 코어를 따로 두지 않음 - 단순함 우선, RM-23F4B687 §4) -
  100틱(약 1초)마다 자신을 제외한 온라인 코어 전부의
  `gHeartbeat[]`를 이전에 저장해 둔 스냅샷(`gHeartbeatLastSeen[]`)
  과 비교, 변화 없으면 그 코어가 멈췄다고 판단한다.
- **트리거**: 멈춘 것으로 판단된 코어마다 `kSendNmi(coreIndex,
  NmiReason::WatchdogTrap)`를 호출 - 같은 코어에 반복 발사하지
  않도록 `gWatchdogTriggered[coreIndex]` 플래그로 1회만 보낸다.
- **1초 임계값/체크 주기는 구현 세부**(설계자 확인이 필요한 지점이
  아님, 실측 후 조정 가능) - `kWatchdogCheckIntervalTicks`처럼 이름
  붙은 상수로 둔다.
- 도달한 코어(watchdog NMI ISR)는 위 NMI ISR 설계대로 레지스터
  덤프를 로그에 남긴 뒤 그대로 정지한다(안전하게 재개할 수 있다는
  보장이 없으므로 kPanic과 동일하게 취급) - "조용한 행"을 "진단
  정보가 있는 시끄러운 정지"로 바꾸는 게 이 기능의 핵심 가치다.

### 디버그 강제 정지(Debug forced-halt) IPI - "stop the world" on panic

**목적**: 한 코어가 패닉에 진입하면 **나머지 모든 코어도 즉시
멈춘다** - 지금은 패닉 코어만 멈추고 나머지는 계속 돌아 공유 상태를
계속 바꾸고(진단 스냅샷을 오염시킴) 시리얼 로그도 서로 뒤섞인다
(실측 확인).

- `kPanic`의 두 진입점(`panic.cpp`의 `kernel::kPanic(const char*)`,
  `idt.cpp`의 `kPanic(InterruptFrame*)`) 둘 다 - **첫 줄에서**(다른
  로그를 찍기 전에, 코어 간 레이스를 최소화하기 위해 최대한 빨리)
  자기 자신을 제외한 온라인 코어 전부를 순회하며 `kSendNmi(otherCore,
  NmiReason::DebugHalt)`를 호출한다.
- 두 진입점의 정확한 호출 관계(하나가 다른 하나를 감싸는지, 완전히
  별개인지)는 실제 착수 시 코드를 다시 읽어 확인 필요 - 이 설계
  문서는 "패닉 진입점 전부"라는 요구사항만 고정한다.
- 받는 쪽은 위 NMI ISR의 `DebugHalt` 분기 그대로 - 로그 한 줄 남기고
  영구 정지. 이미 락을 쥔 채로 멈출 수 있다는 걸 감수한다("시스템이
  어차피 끝나는 상황이니 법의학적 진단을 위해 그 자리에서 얼린다"는
  의도적 트레이드오프 - 정상적인 락 해제/정리 절차를 시도하지
  않는다).
- 자기 자신을 세지 않도록 코어 인덱스 순회에서 `Scheduler::
  currentCoreIndex()`는 건너뛴다(TLB 샷다운 Active CPU Mask 스캔과
  동일 패턴, `Scheduler::taskOnCore()`류 접근자 재사용 가능).

## #MC(Machine Check) 상세 설계 (2026-09-16, 설계자 메시지 "남은 하위 과제들도 모아서 설계안 작성해줘" 반영, 계획 PN-F443FE73)

QU-F3832FC6 답변("MSR 기반 정정 가능 여부 구분")을 구체 설계로
채운다. x86_64 MCA(Machine Check Architecture, SDM Vol.3 §15)
표준 절차 그대로 - 이 프로젝트가 새로 발명하는 부분은 없다.

```cpp
namespace kernel {

constexpr uint32_t kMsrMcgCap = 0x179;
constexpr uint32_t kMsrMcgStatus = 0x17A;
constexpr uint32_t kMsrMc0StatusBase = 0x401;  // bank i: base + 4*i
constexpr uint32_t kMsrMc0AddrBase = 0x402;    // valid이면서 ADDRV 비트 세팅 시만 의미 있음
constexpr uint32_t kMsrMc0MiscBase = 0x403;    // valid이면서 MISCV 비트 세팅 시만 의미 있음

constexpr uint64_t kMcgStatusMcipBit = 1ULL << 2;   // Machine Check In Progress
constexpr uint64_t kMciStatusValBit = 1ULL << 63;   // 이 뱅크 항목이 유효한지
constexpr uint64_t kMciStatusUcBit = 1ULL << 61;    // Uncorrected(정정 불가)
constexpr uint64_t kMciStatusPccBit = 1ULL << 57;   // Processor Context Corrupt

void kHandleMachineCheck(InterruptFrame* frame) {
    const uint64_t mcgStatus = kReadMsr(kMsrMcgStatus);
    // MCIP가 꺼져 있으면 이례적인 상황(소프트웨어 유발 등) - 안전 쪽으로
    // fatal 취급한다.
    bool fatal = (mcgStatus & kMcgStatusMcipBit) == 0;

    const uint32_t bankCount = static_cast<uint32_t>(kReadMsr(kMsrMcgCap) & 0xFF);
    for (uint32_t i = 0; i < bankCount; ++i) {
        const uint64_t status = kReadMsr(kMsrMc0StatusBase + 4 * i);
        if ((status & kMciStatusValBit) == 0) continue;  // 이 뱅크는 보고할 게 없음

        // 로그 포맷: 뱅크 번호 + status/addr(ADDRV 세팅 시)/misc(MISCV
        // 세팅 시) 전부 - 실제 필드명은 기존 Logger::panic류 포맷
        // 관례를 따른다.
        Logger::warn("MC bank %u status=%llx", i, status);

        if (status & (kMciStatusUcBit | kMciStatusPccBit)) {
            fatal = true;  // 정정 불가 또는 컨텍스트 손상 - 계속 실행 불안전
        }
        kWriteMsr(kMsrMc0StatusBase + 4 * i, 0);  // SDM 15.3.1.2 - 처리 후 뱅크 클리어
    }
    kWriteMsr(kMsrMcgStatus, 0);

    if (fatal) {
        kPanic(frame);  // 정정 불가 - 위 "디버그 강제 정지" 브로드캐스트도 함께 발동
        return;
    }
    // 전부 corrected - 로그만 남기고 iretq로 정상 재개(별도 처리 없음)
}

}  // namespace kernel
```

**구현 메모**: `kReadMsr`/`kWriteMsr`가 이미 `syscall_fastpath.cpp`와
`lapic.cpp`에 각각 파일-로컬(익명 네임스페이스)로 중복 존재한다
(실측 확인) - 이 기능이 세 번째 사본을 만들기 전에
`minicore/libs/x86_64/msr.h`(inline)로 통합해 재사용하는 걸 권장한다
(사소한 정리 - 설계자 확인 불필요, RM-23F4B687 §4).

## #DB(Debug) 상세 설계 (2026-09-16, 설계자 메시지 "남은 하위 과제들도 모아서 설계안 작성해줘" 반영, 계획 PN-F443FE73)

QU-F3832FC6 답변("소비자가 있다고 가정하여 설계 먼저")을 따라
설계한다. **범위를 의도적으로 나눈다** - #DB 예외 자체의 라우팅/
해독이라는 아키텍처 층위는 지금 확정하지만, "누가 브레이크포인트를
거는가"(유저 syscall API + 권한 모델, 사실상 크로스 프로세스
디버깅/ptrace급 하위 시스템)는 이 프로젝트에 아직 프로세스 신원/
권한 체계(SP-EAB162FC, PN-645CF608 구현 중)조차 완성되지 않은
상태에서 임의로 발명하면 CLAUDE.md 규칙 4를 벗어난다 - 아래 마지막
항목에서 별도 확인을 구한다.

### DR6/DR7 배경 (실측 없음, SDM Vol.3 §17.2 그대로)

- `DR7`: 하드웨어 브레이크포인트 활성화(L0-L3/G0-G3 비트) + 조건
  (실행/쓰기/I/O/읽기-쓰기, LEN 필드)을 `DR0`-`DR3`의 선형 주소와
  짝지어 설정.
- `DR6`(상태 레지스터, CPU가 자동으로 0으로 안 지움 - 핸들러가
  명시적으로 클리어해야 함): `B0`-`B3`(어느 `DRn` 브레이크포인트가
  걸렸는지) + `BS`(Single-Step, `RFLAGS.TF`로 유발) + `BD`(디버그
  레지스터 접근 감지, 이번 범위 밖).

### #DB ISR 핵심 라우팅 (지금 확정)

```cpp
namespace kernel {

constexpr uint32_t kDr6BsBit = 1u << 14;  // Single-step

// 커널 내부에서 #DB를 소비하고 싶은 쪽(디버거 서브시스템 등)이
// 등록하는 콜백 - Idt::registerHandler와 같은 관례(단, #DB는 고정
// 벡터 0-31이라 저 함수는 못 쓰고 이 전용 슬롯을 쓴다).
using DebugCallback = bool (*)(InterruptFrame*, uint64_t dr6);
DebugCallback gDebugCallback = nullptr;

void kHandleDebugException(InterruptFrame* frame) {
    uint64_t dr6;
    asm volatile("mov %%dr6, %0" : "=r"(dr6));

    bool handled = false;
    if (gDebugCallback != nullptr) {
        handled = gDebugCallback(frame, dr6);  // true면 콜백이 처리 완료
    }

    asm volatile("mov %0, %%dr6" : : "r"(uint64_t{0}));  // DR6는 항상 클리어(SDM 요구)

    if (!handled) {
        // 등록된 소비자가 없거나 콜백이 "내 것 아님"이라고 반환 -
        // 지금은 소비자가 실제로 없으므로 이 경로가 기본값이다.
        Serial::write("\nminicore: #DB unhandled (dr6=...)\n");
        return;  // 계속 실행(고장이 아니므로 panic 아님 - #MC/NMI와 다름)
    }
    // handled == true면 그대로 iretq(콜백이 필요한 상태 조작을 이미
    // 마쳤다고 전제).
}

}  // namespace kernel
```

**설계 근거**: #DB는 NMI/#MC와 성격이 다르다 - 하드웨어 오류나
마스크 불가 통지가 아니라 "누군가 의도적으로 건 브레이크포인트/
싱글스텝"이라 기본 동작이 panic이면 안 된다(콜백 미등록 = 아직 아무도
안 쓴다는 뜻이지 오류가 아님). 따라서 미처리 시 로그 후 계속을
기본값으로 둔다.

### [확인 필요] 유저 syscall 노출 범위 - 아직 미확정

"소비자가 있다고 가정"이 위 커널 내부 콜백 슬롯까지인지, 아니면
**유저 프로세스가 다른 프로세스에 브레이크포인트를 거는 syscall
API**(예: `SetBreakpoint(pid, address, condition)`/
`SetSingleStep(pid, enable)`, `DR0-3`/`DR7`를 대상 프로세스의 저장된
컨텍스트에 쓰는 방식)까지 포함하는지는 이 메시지만으로 확정할 수
없다. 후자는:

- 프로세스 신원/권한 체계(SP-EAB162FC)가 아직 구현 중(PN-645CF608)
  이라 "누가 누구를 디버깅할 수 있는가" 같은 권한 질문이 먼저
  풀려야 한다.
- 대상 프로세스가 블로킹돼 대기 중이 아닐 때 어떻게 컨텍스트를
  들여다보는지(현재 이 프로젝트엔 프로세스 stop/attach 개념 자체가
  없음, SP-2602CAA6/SP-71DA77B3과도 무관한 완전히 새 영역)도 별도
  설계가 필요하다.

위 커널 내부 라우팅(#DB ISR + 콜백 슬롯)까지는 확정해 착수 가능하게
해 뒀고, 유저 syscall API까지 지금 설계할지는 별도 질의로 확인한다
(PN-F443FE73에 QU 등록 예정).
