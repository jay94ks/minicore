## 배경

PL-2D3184BC 3단계(Task 커널 스택 가드 페이지)를 구현하던 중, IST가
전혀 없어 가드 페이지가 잡은 #PF를 전달하려는 시도 자체가 재폴트 ->
#DF -> 트리플 폴트(조용한 리셋)로 격상되어 진단 로그를 전혀 남기지
못하는 문제를 발견했다(DC-3D3212A4). 설계자 답변(QU-4E00C118):

> "TSS+IST를 정식 구현하여 가드 페이지가 실제 진단 로그를 남기게
> 만들고, TSS+IST가 다른 곳에서도 활용 할 수 있도록 설계하여
> 설계안을 제출하라. 규모가 커지면 이 부분을 디버깅하기 더
> 어려워진다."

이 문서는 그 설계안이자, 이미 구현·실측까지 마친 결과 보고다(설계
제안과 구현 검증을 한 번에 진행 - 설계자 지시가 "구현하여 ...
설계하여 설계안을 제출하라"로 구현까지 포함해 명시적으로 지시했기
때문).

## 설계 원칙

- **x86 하드웨어 태스크 스위칭(레지스터 상태 전체를 하드웨어가 통째로
  갈아 끼우는 방식)은 여전히 안 쓴다** - PL-2D3184BC 3번 결정
  ("컨텍스트 전환은 소프트웨어 방식")은 그대로 유효하다. 이 TSS는
  x86_64에서 사실상 두 가지 용도로만 쓰는 "설정 그릇"일 뿐이다:
  1. **IST(Interrupt Stack Table)** - 특정 예외 벡터에 대해, 현재
     RSP가 무엇이든(설령 고장나 있어도) CPU가 항상 정해진 별도
     스택으로 강제 전환한 뒤 핸들러를 실행하게 한다.
  2. **RSP0** - 향후 유저랜드가 생기면 ring3->ring0 전환(syscall
     진입 등) 시 커널 스택 포인터로 재사용할 자리(이번 범위에서는
     필드만 존재, 아직 안 씀 - SP-8B6B8D25 유저랜드 계획과 맞물림).
- **"다른 곳에서도 활용 가능하게" 설계**: IST 슬롯은 1개(#DF)만
  하드코딩하지 않고, x86_64가 제공하는 IST1-7 전부를 구조체에 그대로
  두어 향후 NMI/#MC(머신체크)/#DB(디버그) 등 다른 벡터가 필요해지면
  같은 패턴(그 벡터 전용 스택 확보 + IDT 게이트의 ist 필드 설정)으로
  바로 확장할 수 있게 했다. RSP0 필드도 같은 이유로 미리 자리를
  잡아 뒀다.
- **코어별 독립** - SMP(PL-65C20380)가 이미 존재하므로, TSS/IST
  스택은 코어마다 완전히 독립된 것이어야 한다(여러 코어가 동시에
  #DF에 빠져도 서로의 스택을 밟지 않게). "테이블 내용은 전역 하나,
  포인터 레지스터는 코어마다 개별 적재"라는 이 프로젝트의 기존 IDT
  패턴(`Idt::init()`/`Idt::reloadOnThisCore()`)을 GDT/TSS에도 그대로
  적용했다 - 코드 스타일과 정신 모델의 일관성을 위해서다.

## 구현

### GDT 확장

`minicore/kernel/gdt.h`/`gdt.cpp` 신설. boot.S가 부팅 초기에 이미
최소 GDT(`gdt64`: null/code64/data, 3개 8바이트 디스크립터)를 실어
long mode에 들어와 있었지만, 거기엔 TSS 디스크립터를 넣을 자리가
없었다. `Gdt::init()`이 코드/데이터 디스크립터 값은 `gdt64`와 **완전히
동일하게** 유지한 채(그래서 이미 캐시된 CS 히든 디스크립터를 다시
로드할 필요가 없다 - GDTR을 바꿔도 CPU가 CS 캐시를 스스로 재적재하진
않으므로, 같은 셀렉터 위치에 같은 내용만 있으면 `lgdt`만으로 안전하게
갈아탈 수 있다), 코어마다 하나씩 16바이트 TSS 디스크립터 슬롯
(`kAcpiMaxCpus`개, acpi.h)을 추가한 새 GDT로 교체한다.

```
GDT 배치: [0]=null(8B), [1]=code64(8B), [2]=data64(8B),
          [3.. ]=코어0 TSS(16B), 코어1 TSS(16B), ...
```

### TSS 구조체

Intel SDM Vol.3 Figure 8-11을 그대로 따르는 104바이트 packed 구조체
(`reserved0, rsp0-2, reserved1, ist1-7, reserved2, reserved3,
ioMapBase`) - `static_assert(sizeof(Tss) == 104)`로 레이아웃 오류를
컴파일 타임에 잡는다. IOPB(I/O 권한 비트맵)는 안 쓰므로
`ioMapBase = sizeof(Tss)`로 세그먼트 한계 밖을 가리키게 해 비활성화
한다(표준 관례).

### 코어별 초기화 흐름 (IDT 패턴과 동일)

- `Gdt::init()` - **BSP 전용**, 부팅 중 한 번. GDT 내용(코드/데이터 +
  전체 코어의 TSS 디스크립터 슬롯)을 만들고, 자기 자신의 GDTR도
  적재한다. `Idt::init()` 바로 앞에서 호출한다 - 실제 코어 수를 몰라도
  되게 설계했다(`kAcpiMaxCpus` 상한만큼 슬롯을 미리 다 만들어 둠).
- `Gdt::reloadOnThisCore()` - **AP 전용**. `ap_trampoline.S`가 boot.S의
  예전 `gdt64`(TSS 디스크립터 없음)를 그대로 쓴 채로 `kApMain`에
  진입하므로, BSP가 만들어 둔 새 GDT로 이 코어의 GDTR을 갈아 껴야
  `loadTssForThisCore`가 쓸 TSS 디스크립터를 찾을 수 있다.
  `Idt::reloadOnThisCore()`와 같은 타이밍(`kApMain` 맨 앞)에 호출한다.
- `Gdt::loadTssForThisCore()` - **모든 코어**(BSP + 각 AP)가 자기
  자신의 `Lapic::init()` 직후 호출한다. `Lapic::id()`로 `Acpi::
  cpuApicId()` 배열에서 자기 코어 인덱스를 찾아(page_frame_allocator.cpp
  의 `kCurrentNumaNode()`와 같은 패턴), 그 인덱스의 TSS의 `ist1`을
  이 코어 전용 8KiB 스택(정적 배열, `gIst1Stacks[coreIndex]`)의
  꼭대기로 채운 뒤, 그 코어의 TSS 셀렉터로 `ltr`을 실행한다. TR도
  GDTR/IDTR과 마찬가지로 코어별 레지스터라 공유 불가능하다.

### IDT 연동

`minicore/kernel/idt.cpp` - `Idt::init()`이 벡터 0-31 게이트를 다
만든 직후 `gIdt[8].ist = 1`(더블 폴트 전용, IST1)을 설정한다. IDT
내용 자체는 전역 하나뿐이라(기존 패턴 그대로) 이 한 줄이면 모든
코어에 적용된다 - 각 코어가 자기 TSS의 IST1을 미리 채워 두기만
하면 된다.

## 실측 검증 (QEMU)

1. **기본(guard 페이지 OFF) 빌드, 단일 코어**: `minicore: GDT ready`
   -> `minicore: IDT ready` -> ... -> `minicore: TSS/IST ready (core
   0)` 순서로 정상 출력, 이후 부팅 전 과정(PCI 열거까지) 회귀 없음
   확인.
2. **기본 빌드, q35 `-smp 4`**: BSP의 GDT/TSS 준비 후 AP 3개가 전부
   정상 기동(`AP started, index=1/2/3`, `SMP - APs started=3
   expected=3`) - 각 AP가 자기 GDTR을 재적재하고 자기 TSS/IST를
   올바르게 채웠음을 간접 확인(TSS가 깨졌다면 이 시점 이전에 실패
   했을 것).
3. **가드 페이지 ON 빌드 + 임시 스택 오버플로우 테스트**
   (`MINICORE_TASK_STACK_GUARD_PAGE=ON`, PL-2D3184BC 3단계 검증 때와
   동일한 4KiB 스택 재귀 오버플로우 테스트를 재사용) - **DC-3D3212A4
   가 보고한 트리플 폴트/조용한 리셋이 사라지고, 다음과 같이 정상
   적으로 #DF 진단이 출력된 뒤 안전하게 멈췄다**:
   ```
   minicore: [TEST] triggering deliberate stack overflow under guard page + IST

   minicore: PANIC - unhandled exception: Double Fault
     vector=0x0000000000000008 error_code=0x0000000000000000
     rip=0xffffffff8010cc5f cs=0x0000000000000008 rflags=0x0000000000000286
   ```
   (QEMU가 리셋되지 않고 `cli; hlt` 무한루프에서 멈춰 `-no-reboot`
   타임아웃까지 그대로 유지됨을 확인). 검증 후 임시 테스트 코드는
   제거 - 영구 코드는 `gdt.h`/`gdt.cpp`와 idt.cpp/kmain.cpp/smp.cpp의
   호출부만 남았다.

**결론: DC-3D3212A4가 제기한 문제가 해결됐다** - 가드 페이지가 이제
계획(PL-2D3184BC 4번 항목)이 원래 의도한 대로 "#PF(가 #DF로 격상되어)
로 걸려 진단 가능하게" 동작한다.

## 이번 범위에 포함하지 않은 것

- RSP0(ring3->ring0 전환) - 필드만 존재, 유저랜드 syscall 진입점을
  실제로 만들 때 채운다.
- #DF 외 다른 벡터(NMI/#MC/#DB)의 IST 배정 - 구조체(IST1-7)는 이미
  준비돼 있으나, 지금 그 벡터들을 강제 격리해야 할 구체적인 필요가
  없어 배정하지 않았다. 필요해지면 `gIst1Stacks`와 같은 패턴으로
  전용 스택을 하나 더 만들고 그 벡터의 `ist` 필드를 그 번호로 설정
  하면 된다.
- #DF 핸들러가 원래 폴트의 정확한 레지스터 상태(CR2 등)까지 복구해
  보여주는 것 - x86_64 스펙상 더블 폴트 진입 시점엔 원래 컨텍스트가
  이미 상당 부분 유실된 상태라(SDM 6.15) 일반적인 OS들도 이 이상을
  시도하지 않는다 - "더블 폴트가 났다"는 사실 자체와 그 시점의
  RIP/CS/RFLAGS만으로도 트리플 폴트 대비 진단 가치는 충분하다고
  판단했다.
