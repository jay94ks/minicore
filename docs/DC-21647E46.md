# 배경

SP-201238BB(커널용 lock-free `SharedPtr<T>`/`WeakPtr<T>`) 승인 대기
중 설계자 Opinion: "대부분의 포인터를 이걸로 교체하는 방안을 검토해서
결정 요청으로 올려줘." - 커널 전역의 기존 raw 포인터를 대규모로
`SharedPtr`/`WeakPtr`로 교체할지 여부를 조사해 이 DC로 올린다.

**[개정, 2026-09-16, 설계자 Opinion "UniquePtr 같은 것들도 추가
설계하고, 다시 검토해봐"]** 아래 조사에서 확인한 "소유(owning)"
범주가 실은 **공유가 아니라 배타적 소유**라는 점에 착안해
`UniquePtr<T>`(배타적 소유, 원자 연산 불필요, SP-201238BB §2-A)를
추가로 설계했고, 이 문서의 분석/권장을 그에 맞춰 다시 정리했다.

# 조사 방법

Explore 에이전트로 `minicore/kernel/*.h`(+필요한 `.cpp`)의 포인터
필드를 전수 조사해 각 필드를 **소유(owning)** / **비소유 관찰·역참조
(non-owning observer)** / **정적·전역 싱글턴** / **불명확** 네
범주로 분류했다(process.h/task.h/async_task.h/channel.h/scheduler.h/
wait_queue.h/syscall.h/address_space.h/mount_table.h/livefs.h 및
관련 `.cpp` 파일의 file-scope 전역까지 포함).

# 조사 결과

**규모**: 약 45-55개의 raw 포인터 필드/전역을 확인 - 헤더의 구조체
멤버 약 21개, `.cpp` 로컬 구조체 약 10개, file-scope 전역 싱글턴
약 10개. 아직 프로젝트 규모 자체가 작다(멀티스레드 프로세스도,
동적 프로세스 풀도 아직 없음 - PN-543C0CE9/PN-2E4E9D79 둘 다 미착수).

**분류 결과**:

- **소유(owning) - 3건 확인, 전부 "배타적" 소유(공유 아님)**:
  `RingBuffer::data`(할당/해제를 Channel이 직접 관리, 다른 소유자
  없음), `Channel::pendingHead/pendingTail`(침습적 큐, Channel이
  생성/해제, 다른 소유자 없음) - 이 둘은 **`UniquePtr<T>` 후보**.
  세 번째는 **`AsyncTask::weakRef`**(`AsyncTaskWeakRef` 자신) -
  이건 실제로 **공유**(AsyncTask 쪽 몫 1 + 타이머 콜백 쪽 몫 1,
  참조 카운트 2로 시작)라 `UniquePtr`가 아니라 `SharedPtr` 계열에
  해당하지만, 이미 동작 중인 코드라 교체 범위 밖(SP-201238BB §3).
- **비소유 관찰/역참조** - 8건 이상 확인, 전부 명시적 소유권 부정
  주석 있음: `Process::mainThread`("thread는 호출부가 소유"),
  `UserThread::process`(역참조, 순환 include 회피용), `Task::
  blockedOn`(대기 구조체가 직접 nullptr로 되돌림), `AsyncTask::
  waitingTask`, `BridgePipe::peer`(양쪽 다 닫혀야 반납, 레퍼런스
  카운트 대신 프로토콜로 수명 관리), `PendingConnectRequest::task`,
  `MmapArgs`/`MunmapArgs`/`BrkArgs`의 `Process* process`(syscall
  1회 동안만 유효한 in-파라미터), `MountEntry::kernelDriver`(부팅 시
  등록된 정적 드라이버). **이 범주는 `UniquePtr`도 `SharedPtr`도
  아니다** - 소유권 자체가 없는 관찰자라 raw 포인터가 정확한 표현.
- **정적/전역 싱글턴** - `gCurrentTask[kMaxCores]`, `gCurrentAsyncTask
  [kMaxCores]`, `gHandlers[kMaxHandlers]`, `gForcedMigrationRequest.
  target` 등 - 전부 "부팅 시 한 번 등록, 이후 안 바뀜" 또는 "코어당
  고정 슬롯" 패턴. 마찬가지로 소유권 이전/공유 개념 자체가 없다.
- **불명확** - 1건(`KernelReservedEntry::tierA`, `void*`라 헤더만으로
  판단 불가).

**기존 use-after-free/댕글링 포인터 사례** - 정확히 **2건**만 발견:
1. AsyncTask 타임아웃 - 이미 `AsyncTaskWeakRef`(PN-D01B7D07)로 해결
   완료. SP-201238BB가 일반화한 바로 그 패턴(=진짜 공유 소유권 문제).
2. `Scheduler::retireTask` - Resurrect가 같은 정적 Process/Task
   인스턴스를 재사용하는 도중 지연 정리 큐가 이미 덮어써진
   `kernelStackPhys`를 참조하던 버그 - **참조 카운팅이 아니라 즉시
   회수(immediate reclamation)로 해결**했다(레퍼런스 카운팅도
   배타적 소유 래퍼도 필요하지 않았던 사례 - 정적 싱글턴 재사용
   타이밍 문제였을 뿐).

다른 곳에서는 "dangling/UAF/수명/weak" 관련 논의 자체를 찾지 못했다.

# 검토한 선택지

**(A) 대부분의 포인터를 `SharedPtr`/`WeakPtr`로 교체** (Opinion이
처음 제시한 원안) - 위 조사 결과 이 코드베이스의 포인터 압도적
다수(비소유 참조 8건 이상 + 정적 싱글턴 전부, 소유 포인터 3건 중
2건도)는 애초에 "여럿이 공유하다 런타임에 마지막 소유자가 정해지는"
문제 자체가 없다. 강제로 `SharedPtr`/`WeakPtr`를 끼워 맞추면:
- 필드 접근마다 컨트롤 블록 간접 참조 + `AtomicU32` 원자 연산
  오버헤드가 스케줄러 디스패치 같은 가장 뜨거운 경로에 들어간다.
- 객체당 별도 컨트롤 블록 할당이 추가된다(이중 할당 비용).
- 잘 동작 중인 코드 수십 곳을 건드리는 대규모 리팩터라 회귀 위험이
  인위적으로 커진다(RM-23F4B687 §4 원칙 위배).

**(B) `UniquePtr`로도 교체하지 않는다 - 전부 raw 포인터 유지, 신규
코드에서 공유 소유권이 필요한 곳만 `SharedPtr`/`WeakPtr`** - 가장
보수적인 선택지. `RingBuffer::data`/`pendingHead·pendingTail` 같은
배타적 소유조차 굳이 `UniquePtr`로 감싸지 않는다(지금 방식대로
생성자/소멸 경로에서 수동 관리).

**(C) 세 계층 모델을 전면 채택** - **소유권의 실제 성격에 맞는
도구를 쓴다**:
1. **비소유 관찰/역참조 + 정적 싱글턴(대다수, 18건 이상)**: raw
   포인터 그대로 유지 - 소유권이 없다는 사실 자체가 지금 관례
   (설명 주석)로 이미 정확히 표현돼 있다. 손댈 필요 없음.
2. **배타적 소유(`RingBuffer::data`, `pendingHead/pendingTail`,
   2건)**: **`UniquePtr<T>`로 교체** - 원자 연산 오버헤드
   없이(raw 포인터와 사실상 동일 비용) RAII 안전성만 얻는다
   (소멸 경로 누락 방지, move-only로 실수로 복사돼 이중 해제되는
   걸 컴파일 타임에 차단). 회귀 위험이 낮다(대상이 2건뿐, 각각
   지역적).
3. **진짜 공유 소유권이 필요한 신규 코드(향후)**: `SharedPtr`/
   `WeakPtr` 표준 도구로 채택(SP-201238BB §4 후보 - DebugSession,
   프로세스 트리 등). 기존 `AsyncTask::weakRef`(이미 동작 중인
   특수 사례)는 그대로 둔다.

**(D) (A) 그대로, 단 "대부분"의 범위를 비소유/싱글턴까지 포함해
문자 그대로 강행** - Opinion 원문이 정말 "대부분"을 의도했다면
이 경로도 배제하지 않는다. 다만 위 조사가 보여주듯 이 경우
`SharedPtr<Process>`류로 바뀐 `UserThread::process` 같은 필드는
"프로세스와 스레드가 서로 다른 시점에 죽을 수 있다"는, 지금
설계에는 없는 새로운 의미를 암묵적으로 도입하게 된다 - 이건 단순
포인터 교체가 아니라 프로세스/스레드 수명 모델 자체의 재설계가
필요할 수 있다는 뜻이라 별도로 언급해 둔다.

# 권장 (제 판단, 확정 아님)

**(C)를 권장한다.** `UniquePtr` 추가로 그림이 더 분명해졌다 - 이
코드베이스의 포인터는 세 가지뿐이다: (1) 소유권이 아예 없는
관찰자(대다수, 손댈 이유 없음), (2) 배타적 소유(극소수, `UniquePtr`로
안전성만 개선), (3) 진짜 공유 소유권이 필요한 경우(지금은 `AsyncTask::
weakRef` 하나뿐이고 이미 해결돼 있음, 앞으로 새 동적 자료구조에서
나올 것). "포인터를 스마트 포인터로 바꾼다"를 목표로 삼기보다,
**"소유권의 실제 성격에 맞는 도구를 쓴다"**는 원칙이 더 정확한
목표라고 본다 - 그 원칙을 적용한 결과가 바로 (C)다.

# [개정, 2026-09-16] 설계자 지시로 범위 재확장 - "싱글톤 제외, 나머지
전반에 목적을 명확히 해서 검토"

설계자 Opinion: "조금 더 완화해서 싱글톤을 제외하고 '소멸 경로
누락 방지, move-only로 실수로 복사돼 이중 해제되는 걸 컴파일
타임에 차단'라는 목적으로 두고 WeakPtr, SharedPtr, UniquePtr 도입
검토해봐." 위 (A)/(B)/(C)/(D)는 "소유권 모델이 실제로 공유인가
아닌가"를 기준으로 나눈 선택지였는데, 이 답변은 기준을 바꿨다 -
**목적이 RAII 안전성(널 체크/해제 순서/복사 방지를 컴파일러가
강제)이지 "소유권을 재정의하자"가 아니다.** 이 기준으로 다시 보면:

- **정적/전역 싱글턴** - 명시적으로 제외 확정(`gCurrentTask[]`류,
  10건 - 옮길 이유 자체가 없다는 원래 조사 결론 그대로 유지).
- **배타적 소유(2건)** - `UniquePtr`로(기존 결론 그대로, 변화 없음).
- **비소유 관찰자(8건 이상)** - **이번 개정의 핵심.** 원래는 "소유권
  문제가 없으니 raw 그대로"가 결론이었지만, 목적이 "소유권 정의"가
  아니라 "안전성 강제"라면 관찰자 쪽도 `WeakPtr<T>`로 감싸 "대상이
  이미 없어졌는지"를 타입 시스템이 강제로 체크하게 만드는 가치가
  있다. **다만 이건 관찰 대상(예: `Process`, `Waitable`)의 실제
  소유자도 함께 `SharedPtr<T>`로 옮겨야 완성된다**(`WeakPtr`가
  기댈 컨트롤 블록이 필요 - `UniquePtr` 소유 대상엔 못 붙는다,
  SP-201238BB §4.1에 반영). 즉 관찰자 필드 하나만 바꾸는 얕은
  작업이 아니라, 대상 타입(`Process` 등)의 소유 방식 자체를 함께
  바꾸는 작업이 된다 - SP-201238BB §4.2에 `Process`/`UserThread`
  쌍을 구체 예시로 작성해 뒀다.

## 남은 핵심 열린 질문

정적 boot-time `Process` 인스턴스(`gInitProcess`/`gServiceProcess
[4]`, kmain.cpp)는 **"정적/전역 싱글턴"(제외 대상)과 "관찰자가
있는 소유 객체"(SharedPtr 대상) 두 범주에 동시에 해당할 수 있어
모호합니다** - `Process*` 자체는 지금 정적 전역이라 위 "싱글턴"
정의에 들어맞지만, `UserThread::process`처럼 그걸 관찰하는 비소유
포인터도 있어 "비소유 관찰자" 개정 취지에도 걸립니다. 둘 중 어느
분류를 따를지에 따라 실제 작업량이 크게 갈립니다:

- **제외 쪽으로 읽으면**: `Process` 자신은 그대로 두고(정적 전역
  이므로), `UserThread::process`도 그대로 raw 유지(관찰 대상이
  SharedPtr가 아니므로 WeakPtr를 못 붙임) - 이번 확장의 실질 대상은
  `Task::blockedOn`/`AsyncTask::waitingTask`처럼 **대상이 이미
  동적으로 관리되는(Slab 할당 등) 경우**로 좁혀집니다.
- **포함 쪽으로 읽으면**: 정적 `Process` 인스턴스까지 `SharedPtr`로
  옮겨야 하고(지금 "정적 전역"인 걸 "동적 SharedPtr 관리"로 바꾸는
  더 큰 변경), 그래야 `UserThread::process`도 `WeakPtr`가 됩니다.
  이 경우 사실상 PN-543C0CE9(동적 Process 풀)의 일부 작업을
  앞당기는 셈이 됩니다.

**결정 요청**: 위 두 갈래 중 어느 쪽으로 읽어야 할지 확인 부탁드립니다
- 특히 `Process`/`Task` 자체를 지금 `SharedPtr` 관리로 옮기는 것까지
  포함하는지(포함 쪽), 아니면 이미 동적으로 관리되는 대상(`Waitable`,
  `AsyncTask` 등)에 한해서만 관찰자를 `WeakPtr`로 바꾸는지(제외 쪽,
  더 좁고 안전한 범위)가 핵심 갈림길입니다.

## [결정, 2026-09-16, QU-76409699 설계자 답변] (B) 포함 쪽 확정

설계자 답변 원문: "(B) 포함으로 읽자. 이쪽이 코드 관리가 쉬워져."

즉 정적 boot-time `Process` 인스턴스(`gInitProcess`/
`gServiceProcess[4]`)도 최종적으로 `SharedPtr` 관리 대상에
포함한다 - "정적 전역"을 "동적 SharedPtr 관리"로 바꾸는 더 큰
변경까지 확정 범위. 이에 따라:

- `UserThread::process`(→ `Process*` 관찰)는 `WeakPtr<Process>`로
  전환 대상 확정(더 이상 "컨트롤 블록이 없어 불가능"한 상태가
  아니게 됨 - `Process` 자신이 SharedPtr 관리로 옮겨가므로).
- 이 작업은 PN-543C0CE9(동적 Process 풀, `Process::allocate()/
  release()` 이미 구현됨, commit c4936e3)의 연장선이자 그 위에
  쌓이는 후속 작업이다 - `gInitProcess`/`gServiceProcess[]` 자체를
  boot 경로에서 `kMakeShared<Process>(...)`로 만들도록 바꾸고,
  이를 가리키는 모든 관찰 지점(`UserThread::process` 등)을
  `WeakPtr<Process>`로 바꾸는 별도 마이그레이션 계획이 필요하다
  (이 DC/PN-68871BC9의 범위인 "템플릿 자체 구현"과는 분리 -
  아래에 별도 PN으로 등록).

## [업데이트, 2026-09-16] PN-543C0CE9 진행 - "포함 쪽"에 힘 실리는 새 사실

구현 세션이 PN-543C0CE9(SpawnProcess/COW) 2번째 증분(commit c4936e3)
으로 `Process::allocate()/release()` + `UserThread::allocate()/
release()`를 이미 추가했다 - `GenericSlabAllocator`로 raw 메모리를
받아 초기화하는 방식이라, **`Process`/`UserThread`는 이제 원리상
"정적 전역만 가능"이 아니라 실제로 동적 슬랩 할당이 가능**하다(단,
`gInitProcess`/`gServiceProcess[]` 자체는 여전히 정적 전역이고,
이 API를 실제로 쓰는 `SpawnProcess` 핸들러는 아직 미착수). 구현
세션 판단(참고, 확정 아님): 이 사실이 위 "포함 쪽"(정적 `Process`
인스턴스까지 `SharedPtr`로 옮긴다) 해석에 힘을 싣는 방향이라고 봄 -
Process가 더 이상 "본질적으로 정적인" 대상이 아니게 됐기 때문.
최종 판단은 설계자 확인(QU-76409699)에 맡긴다.
