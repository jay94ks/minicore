# VFS 파일 소유자/모드(uid/gid/mode) 메타데이터 + Chmod/Chown + EXEC_SETUID — 설계 제안

## 0. 배경

`DC-1526389A`(review, 설계자 답변 수령)가 발견한 구조적 공백 -
sudo/su의 S 비트+exec-time 승격(`DC-34764C25` 항목2/3-나머지/4)을
구현하려면 파일의 uid/gid/mode를 VFS가 알아야 하는데, 지금
`KernelFsStatArgs`/`StatArgs`(`minicore/kernel/mount_table.h`/
`vfs_syscall.h`)는 `size`/`type` 두 필드뿐이다. 설계자 답변
(2026-09-28, `QU-85099CFF`) 그대로 이 문서에서 나머지를 설계한다:

> "FAT32/exFAT에서는 S 비트가 지원되지 않아도 돼. 나머지 문제는
> 별도 설계안을 작성해줘. livefs의 소유자는 항상 root지만, 프로세스나
> 유저별로 자동으로 노출되는 것들은 해당 유저 소유로."

## 1. 실제 코드 조사 결과(구현 착수 전 확인 완료)

- **ext4는 이미 준비돼 있다** - `libext4::InodeCore`(`ext4.h:391`)가
  `mode`/`uid`/`gid`를 리눅스 i_mode/i_uid/i_gid와 동일한 레이아웃으로
  이미 파싱한다(모든 inode 읽기마다 채워짐). `mode`는 디렉터리 판정에,
  `uid`/`gid`는 디스크 쿼터 회계에 이미 실사용 중이나, **Stat 처리
  경로(`ext4_driver.cpp`의 `KernelFsOpCode::Stat` 케이스)가 이 세
  필드를 읽고도 `KernelFsStatArgs`에 복사하지 않고 버린다** - 노출만
  안 돼 있을 뿐 저장/파싱은 이미 완성돼 있다.
- **NTFS는 소유자/권한 개념 자체가 전혀 없다** - ACL/보안 서술자
  파싱이 아예 없음(코드에 관련 필드 0건).
- **FAT32/exFAT도 마찬가지**(설계자가 이미 확인해 준 대로) - DOS
  속성 비트(`kAttrReadOnly` 등)만 있고 uid/gid/mode 개념 없음. 단
  `kAttrReadOnly` 비트 하나는 "쓰기 가능 여부"와 자연스럽게 대응된다.
- **livefs**는 각 서브트리(`named/`, `initrd.cpio`, `kernel/<name>`,
  `proc/`, `resourcegroup/`)가 커널이 즉석에서 만드는 가상 파일이라
  엔트리별 소유자 필드 자체가 없다. `proc/self` 안쪽의 pid별 동적
  목록(설계자가 언급한 "프로세스나 유저별로 자동으로 노출되는 것")은
  `RM-48E1E610` 그룹3 Readdir 항목이 이미 "아직 후속"으로 남겨 둔
  범위 - 지금 당장 만들 대상은 없으나 **나중에 그 서브트리가 생기면
  이 문서의 §3.4 규칙을 따라야 한다**.
- **`SpawnProcessFlags`의 다음 미사용 비트는 `1u << 2`**
  (`process.h:698`) - `EXEC_SETUID`류 플래그 후보.
- **`SpawnProcessArgs`는 파일 경로를 전혀 모른다** - `imageBuffer`
  (이미 메모리에 올라온 바이트)만 받는다(`process.h:742`). exec-time
  S 비트 승격을 하려면 커널 자신이 "이 이미지가 어느 파일에서 왔는지"
  를 알아야 하는데, 지금 구조로는 호출자가 이미 Open+Read로 읽어 둔
  버퍼만 넘기므로 **커널이 그 출처 파일을 다시 조회할 방법이 없다**
  - 이 설계의 핵심 구조적 결정 지점(§5).

## 2. `KernelFsStatArgs`/`StatArgs` 확장

```cpp
// mount_table.h
struct KernelFsStatArgs {
    KernelFsOpCode op = KernelFsOpCode::Stat;
    const char* relPath = nullptr;
    uint32_t relPathLen = 0;
    // out
    uint64_t size = 0;
    FileType type = FileType::Regular;
    Uid uid = kRootUid;              // 신규
    Gid gid = kRootGid;              // 신규
    Permission mode = 0;             // 신규 - libkenv/permission.h 타입 재사용
    VfsError error = VfsError::None;
};

// vfs_syscall.h - StatArgs도 동일하게 uid/gid/mode 추가, StatHandler가 그대로 복사
```

`Permission`은 이미 `libkenv/permission.h`에 있는 범용 타입(owner/
group/other rwx 9비트 + S 비트, `kPermSpecialS = 1u<<9`)을 그대로
재사용한다 - 새 타입 불필요.

## 3. 파일시스템별 채우는 방법

### 3.1 ext4 - 실제 값

`ext4_driver.cpp`의 Stat 케이스가 이미 읽어 둔 `targetInode.mode/
uid/gid`를 그대로 `args->mode`/`uid`/`gid`에 복사만 하면 된다(추가
파싱 불필요, 이미 있는 값을 버리지 않고 넘기기만 하는 수준의 변경).
Open/Mkdir 등 다른 op들이 만드는 새 inode의 초기 mode/uid/gid도
같은 필드를 그대로 쓰면 된다(이미 파싱 코드는 있으니 "쓰기" 방향도
대칭적으로 채우면 됨 - Mkdir이 새 inode를 만들 때 mode 인자를 받지
않는 현재 시그니처는 §4에서 Chmod와 함께 확장).

### 3.2 NTFS - **제안: FAT32/exFAT와 동일하게 취급**

NTFS는 ACL 파싱이 전혀 없어(§1) ext4처럼 "이미 파싱해 뒀다"가
성립하지 않는다 - 실제 NTFS 보안 서술자를 파싱하려면 이 증분과는
비교가 안 되게 큰 작업(SID 파싱, ACE 순회)이 필요하다. **설계자가
FAT32/exFAT만 명시적으로 면제했으나, NTFS도 같은 이유(네이티브
POSIX 권한 개념 부재)로 같은 취급을 제안한다** - 승인 시 아래
3.3과 동일한 규칙(마운트한 유저 소유, S 비트 불가)을 NTFS에도 적용.

### 3.3 FAT32/exFAT - 마운트한 유저 소유(설계자 답변, 2026-09-28 opinion)

> "FAT나 exFAT에서 소유권과 그룹은 그 디스크를 마운트한 유저에게
> 귀속되면 돼."

S 비트는 항상 꺼짐(설정 시도 시 `NotSupported`, 이건 그대로 확정).
uid/gid는 고정 root가 아니라 **그 볼륨을 마운트한 유저**의 것을
쓴다 - 이를 위해 `MountEntry`(`mount_table.h`)에 `Uid mountUid`/
`Gid mountGid` 필드를 신설한다. `MountHandler`(`vfs_syscall.cpp`,
`MountKind::Channel`용 syscall)는 `task->submitterTask.lock()`으로
얻은 호출자 `Process::uid/gid`를 `MountTable::mount()`에 함께
넘겨 채운다. **`MountKind::KernelDriver`(ext4/FAT32/exFAT/NTFS,
`fs.cpp`가 블록장치 감지 시 내부적으로 직접 마운트)는 지금 유저
syscall을 거치지 않는 자동 마운트라 귀속시킬 실제 호출자가 없다** -
이 경로는 당분간 `kRootUid`/`kRootGid`로 채운다(사실상 지금까지의
동작과 동일 - "커널이 부팅 중 스스로 마운트했다"는 의미로 자연스럽다).
나중에 사용자가 syscall로 직접 마운트를 트리거하는 경로(예: USB
드라이브 마운트 명령)가 생기면 그 호출자의 uid/gid를 그대로 넘기면
된다 - 이 SP는 그 구조(필드 신설+전달 경로)만 미리 마련해 둔다.

mode는 `kAttrReadOnly` 속성 비트 하나로부터 합성(변경 없음):
- 디렉터리: `kAttrReadOnly` 무관, 항상 `0755`(rwxr-xr-x) - 원래
  디렉터리 진입/탐색은 늘 가능해야 하므로.
- 파일: `kAttrReadOnly` 켜짐 → `0444`(r--r--r--), 꺼짐 →
  `0644`(rw-r--r--).

**§4의 Chmod가 이 두 포맷에서 실제로 하는 일**: S 비트 설정 시도는
거부(`NotSupported`). 그 외 owner-write 비트(`kPermOwnerWrite`)
켜짐/꺼짐만 보고 `kAttrReadOnly`를 끄거나 켜 실제 디스크에 반영 -
"진짜 mode 저장"이 아니라 "가장 가까운 근사치 하나만 왕복 가능"이라는
점을 알려진 제약으로 명시한다(다른 rwx 비트는 저장할 곳이 없어
무시됨 - 다음 Stat에서 그 비트들은 다시 위 고정 매핑으로 재계산됨).

### 3.4 livefs - root 고정 + 향후 per-user 서브트리 규칙(설계자 확정)

지금 존재하는 모든 livefs 엔트리(`named/`, `initrd.cpio`,
`kernel/<name>`, `proc/{self,meminfo,uptime}`,
`resourcegroup/*`)는 **항상 `uid=gid=kRootUid/kRootGid`,
`mode=0444`(디렉터리는 `0555`)** - 커널이 만드는 가상 파일이라 실제
"쓰기"가 의미 없고(이미 항상 `PermissionDenied` 정책, §3의 Write
핸들러 참고) 읽기만 되면 충분하다.

**향후 규칙(지금 구현 대상 없음, 설계만 확정)**: `RM-48E1E610`
그룹3 Readdir이 이미 "후속"으로 남겨 둔 `proc/self` 안쪽의 pid별
동적 목록처럼 **"프로세스나 유저별로 자동으로 노출되는" 서브트리가
나중에 추가되면, 그 엔트리들은 root가 아니라 그 프로세스/uid의
소유(`uid` = 그 프로세스의 `Process::uid`)로 채운다** - 설계자
답변 그대로. 이 규칙은 이번 증분에서 즉시 적용할 코드가 없으므로
(그런 서브트리 자체가 아직 없음) 다음에 그 서브트리를 실제로 만드는
세션이 지켜야 할 제약으로 이 문서에 기록해 둔다.

## 4. 새 syscall - Chmod/Chown (그룹3 Vfs, call 14/15)

`RM-48E1E610` 그룹3의 다음 미사용 call은 14(현재 최고는 13=Rmdir) -
이 설계 제안 단계에서 14/15로 예약(승인 즉시 그 현황판에 반영).

```cpp
constexpr SyscallEndpointId kSyscallEndpointChmod = kMakeSyscallEndpointId(3, 14);
struct ChmodArgs {
    const char* path = nullptr;
    uint32_t pathLen = 0;
    Permission mode = 0;   // in - rwx 9비트 + S 비트
    // out
    ChannelError error = ChannelError::None;
};

constexpr SyscallEndpointId kSyscallEndpointChown = kMakeSyscallEndpointId(3, 15);
struct ChownArgs {
    const char* path = nullptr;
    uint32_t pathLen = 0;
    Uid uid = kRootUid;   // in
    Gid gid = kRootGid;   // in
    // out
    ChannelError error = ChannelError::None;
};
```

**권한 판정(제안, Linux 관례 그대로)**:
- `Chmod`: 호출자가 root이거나 대상 파일의 소유자(`callerUid ==
  fileUid`)일 때만 허용, 그 외 `PermissionDenied`. **S 비트를
  새로 세우는 것은 파일 소유자 본인만 가능**(`DC-34764C25` 항목4
  "S 비트를 설정하는 것 자체가 해당 파일의 소유자만 가능해야 해"
  - 이미 위 조건에 포함되므로 별도 분기 불필요, 소유자 판정 자체가
  이 요구를 만족시킴).
- `Chown`: root만 허용(Linux와 동일하게 일반 사용자의 소유권 이전은
  막는다 - 임의 확장 아님, POSIX 표준 관례).
- ext4에 대해서만 실제로 동작(inode의 mode/uid/gid를 갱신하고 dirty
  마킹 후 write-back). NTFS/FAT32/exFAT/livefs는 `Chown`이
  `NotSupported`(§3.2/3.3/3.4에서 이미 실제 저장소가 없다고 확정한
  그대로 - 소유자는 "마운트한 유저"로 고정, 개별 파일 단위로 바꿀
  방법이 없음) - 단 FAT32/exFAT/NTFS의 `Chmod`만 예외로 owner-write
  비트 하나를 `kAttrReadOnly`로 근사 반영(§3.3, owner 판정은
  `callerUid == mountEntry.mountUid`).

`KernelFsOpCode`에 `Chmod`/`Chown` 2종 추가, `KernelFsChmodArgs`/
`KernelFsChownArgs`(경로 기반, fd 불필요 - `Stat`/`Mkdir`과 동일한
모양) 신설.

## 5. EXEC_SETUID - SpawnProcess 확장

### 5.1 구조적 선행 조건 - `SpawnProcessArgs`에 경로 필드 신설

`SpawnProcessArgs`는 지금 `imageBuffer`(이미 메모리에 있는 바이트)만
받아 **커널이 그 이미지의 출처 파일을 다시 조회할 방법이 없다**(§1).
S 비트 승격은 보안이 걸린 판정이라 호출자가 "이 파일은 S 비트가
있었다"고 주장하는 값을 그대로 믿을 수 없다 - 커널 스스로 Stat해야
한다. 따라서:

```cpp
struct SpawnProcessArgs {
    const void* imageBuffer = nullptr;
    uint64_t imageSize = 0;
    char* const* argv = nullptr;
    char* const* envp = nullptr;
    uint32_t flags = SpawnProcessFlags::kSpawnNone;
    const char* imagePath = nullptr;   // 신규, optional(nullptr 허용)
    uint32_t imagePathLen = 0;         // 신규
    // out
    SpawnProcessError error = SpawnProcessError::None;
    int64_t pid = kInvalidProcessId;
};

enum SpawnProcessFlags : uint32_t {
    kSpawnNone = 0,
    kSpawnDebugStart = 1u << 0,
    kSpawnInheritFds = 1u << 1,
    kSpawnAllowSetuid = 1u << 2,  // 신규 - "EXEC_SETUID" 답변 그대로
};
```

`kSpawnAllowSetuid`가 켜졌는데 `imagePath`가 없으면
`SpawnProcessError::InvalidArgument`로 즉시 거부(승격 판정 자체가
불가능하므로) - 이미 메모리 버퍼만으로 스폰하는 기존 모든 호출부
(init/서비스 고정 스폰 등)는 이 플래그를 그냥 안 쓰면 되므로 하위
호환 100% 유지.

### 5.2 승격 로직

`SpawnProcessHandler::onExec()`이 `kSpawnAllowSetuid` 플래그를 보면,
ELF 로드가 끝나 새 `Process`/`UserThread`가 만들어진 직후(uid는
아직 부모로부터 상속된 상태) 다음을 수행:

1. `imagePath`로 내부 Stat 등가 조회(§2의 확장된 필드 포함) - 실패
   하면 승격 없이 그냥 부모 uid 그대로 진행(파일이 사라졌다고 exec
   자체를 실패시키지 않음 - 이미 메모리에 이미지가 있으므로).
2. 조회된 `mode`에 `kPermSpecialS`가 없으면 승격 없음(정상 종료).
3. 있으면 새 프로세스의 `uid`를 그 파일의 `uid`(소유자)로 즉시
   전환 - `kSetuid()`의 조상-자손/화이트리스트 판정을 거치지
   않는다(Linux setuid-exec와 동일 - 파일 자체의 S 비트가 이미
   그 판정을 대신함, 대신 "그 파일에 그 비트를 세울 수 있었던 것은
   소유자뿐"이라는 §4의 Chmod 권한 판정이 사전 게이트 역할을 한다).
4. FAT32/exFAT/NTFS/livefs 출신 파일은 §3에서 이미 mode에 S 비트가
   절대 없으므로(설정 자체가 거부됨) 자동으로 이 경로를 안 탄다 -
   별도 파일시스템 분기 불필요.

## 6. 참고 - 이번 설계가 명시적으로 다루지 않는 것

- NTFS 실제 ACL 파싱(§3.2에서 FAT류와 동일 취급으로 대체 제안) -
  승인 시 별도 계획으로 등록.
- `RM-48E1E610` 갱신(Chmod/Chown call 14/15 확정), `RM-32D06563`
  (새 용어), `RM-7C249618`(해당 없음 - 새 라이브러리 아님)은 이
  SP 승인 후 구현 세션이 처리.
- Mkdir/Open(생성 경로)이 새 inode의 초기 mode를 umask류 개념 없이
  어떤 기본값으로 만들지는 이 SP 범위 밖(기존 Mkdir 시그니처 변경
