# 부트 경로 구현 착수 순서 및 부트로더 구현 방식 — 요구분석

## 배경

SP-8B6B8D25 §1은 x86-64에서 BIOS/PVH(QEMU)/multiboot2/EFI 네 가지
부팅 경로를 "지원 대상"으로만 확정했고, 그중 무엇을 먼저 구현하는지,
각 경로의 부트스트랩 코드를 직접 작성할지 기존 부트로더에 위임할지는
정해지지 않았다. 커널 코드(`minicore/kernel`)나 아키텍처 스텁
(`minicore/arch`)에 착수하려면 최소 하나의 부팅 경로가 실제로 동작해야
검증(QA-26450C3E "부팅" 항목)이 가능하므로, 이 결정이 구현 착수 순서
전체를 좌우한다.

## 결정이 필요한 항목과 각 선택의 영향

1. **첫 구현 대상**: `--kernel`/`--initrd` 직접 전달 방식이 사실상
   "0번째"(부트로더 없이 QEMU가 커널을 바로 올려주는) 경로인지, 그것과
   별개로 BIOS/PVH/multiboot2/EFI 중 우선순위가 있는지. 어떤 걸 먼저
   골라도 되지만, 나중 경로들이 첫 경로의 부트스트랩 코드를 얼마나
   재사용할 수 있는지가 아키텍처 추상화 계층(`minicore/arch`) 설계에
   영향을 준다.
2. **부트로더 구현 방식**: 각 프로토콜의 부트 스텁을 직접 작성할지,
   기존 부트로더(예: Limine, GRUB)를 체인로더로 두고 그 프로토콜 규약만
   커널이 맞출지 — 직접 작성은 학습/제어 범위가 넓어지고, 기존 부트로더
   의존은 초기 구현 속도를 높이지만 그만큼 외부 의존성이 생긴다.
3. **EFI 지원 범위**: 자체 UEFI 애플리케이션(.efi)을 직접 작성할지,
   아니면 기존 UEFI 부트로더에 의존할지 — 2번 항목의 결정과 맞물린다.
