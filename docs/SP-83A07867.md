# 스케줄러 디스패치 CR3 동기화 통합 및 최적화 — 설계 제안

QU-892AB38A 설계자 답변(2026-09-15)을 그대로 설계 명세로 확정한다.
같은 종류의 CR3 미복원 버그가 이미 두 번(PN-63BCFE45, PN-71C3D483)
재발했고, 세 번째 잠재 공백(`yieldCurrent`/`parkCurrent` 재개 경로)이
아직 남아 있다 - 이 문서는 그 근본 원인(디스패치 경로마다 CR3 동기화
로직이 따로 흩어져 있고, 그중 일부 경로엔 아예 없음)을 없애기 위해
**모든 디스패치 경로가 공유하는 단일 동기화 지점**을 설계한다.

## 1. 확정된 불변조건 (설계자 답변 1번 그대로)

> 디스패처가 제어를 특정 Task로 넘기기 전, 현재 CPU의 CR3는 반드시
> 해당 Task가 속한 `Process::pml4Phys`(커널 태스크의 경우 커널 기본
> PML4)와 일치해야 한다.

이 불변조건은 `Scheduler`의 **모든** 디스패치 경로에 예외 없이
적용된다 - onTick()의 Task-to-Task 직접 전환, runLoop()의 idle->Task
전환(최초 실행이든 재개든), yieldCurrent()/parkCurrent()로 파킹됐다가
재개되는 경우 전부.

## 2. 왜 지금까지 두 번 깨졌는가 - 근본 원인

CR3 동기화 로직이 디스패치 경로마다 **따로** 구현돼 있었다(§1의
불변조건이 "장소" 하나가 아니라 여러 곳에 각자 흩어진 규칙으로
존재) - 새 디스패치 경로가 추가되거나 기존 경로의 대상 범위가
넓어질 때마다(UserThread만 → UserThread+커널 Task 전부) 그 흩어진
곳들을 전부 찾아 고쳐야 했는데, 실제로는 매번 한 곳만 고치고 다른
곳은 놓쳤다:

- `kEnterRing3`(process.cpp) - UserThread의 **첫** ring3 진입 때만
  CR3를 직접 설정. 재진입은 다루지 않음 → PN-63BCFE45 근본 원인 #1.
- `kSyncCr3ForDispatch`(scheduler.cpp, `onTick()` 전용) - 처음엔
  UserThread만 처리(else 분기 없음) → 커널 Task로 전환 시 CR3
  미복원 → PN-71C3D483에서 재발, `next->isUserLevel`이 아니면
  `gBootPml4Phys`로 되돌리는 것으로 부분 수정됨(commit a9b858a).
- `runLoop()`의 idle→Task 전환, `yieldCurrent()`/`parkCurrent()`의
  재개 지점 - **지금까지 단 한 번도 CR3를 건드린 적이 없다.**
  현재는 어떤 ring3 코드도 yield/park 경로를 타지 않아 발현되지
  않았을 뿐(§4 참고), 언제든 네 번째로 재발할 수 있는 상태다.

## 3. 새 설계 - 두 개의 안전한 통합 지점

CR3 쓰기(`mov cr3`)는 **반드시 이미 안전한 스택 위에서 실행 중일
때만** 해도 된다(PN-58501EAA "중요 발견" - 코어의 최초 부트 스택은
저지대 identity map이라 어떤 프로세스의 PML4에도 없음, 그 스택
위에서 CR3를 바꾸면 다음 스택 접근이 즉시 폴트한다). 이 제약이
"완전히 하나의 함수/하나의 호출 지점"으로 통합하는 것을 막는다 -
디스패치가 근본적으로 두 갈래(①트랩으로 들어와 있어 항상 안전한
경로, ②idle/파킹 컨텍스트에서 스택 자체를 옮겨야 하는 경로)이기
때문이다. 그래서 통합의 단위는 "함수 호출 지점 1곳"이 아니라
**"같은 로직을 재사용하는 함수 1개 + 그 함수를 부르는 지점의
일관된 규칙"**이다.

### 3.1 공용 함수

```cpp
// scheduler.cpp (kSyncCr3ForDispatch를 대체)
void kSyncCr3(Task* task) {
    const uint64_t targetPml4 = task->isUserLevel ? task->userPml4Phys : gBootPml4Phys;
    if (Paging::currentPml4Phys() != targetPml4) {  // 최적화, §5 참고
        asm volatile("mov %0, %%cr3" : : "r"(targetPml4) : "memory");
    }
}
```

`gBootPml4Phys`는 이미 `Scheduler::init()`이 캡처해 둔 값(commit
a9b858a)을 그대로 재사용 - "커널 기본 PML4"가 정확히 이 값이다.

### 3.2 호출 규칙 - 두 갈래

**갈래 ①: 이미 안전한(트랩) 스택 위에서, 전환 "직전"에 호출**

- `Scheduler::onTick()` - 지금과 동일(그대로 유지) - `next`로
  전환하기 직전에 `kSyncCr3(next)`. `onTick()` 자신이 인터럽트로
  들어와 있어(트랩 프레임 스택, 커널 higher-half 공유) 안전.

**갈래 ②: kContextSwitch로 스택 자체가 바뀌는 지점 - 반드시 전환
"이후"(자기 자신의 스택으로 이미 넘어온 뒤)에 호출**

이 갈래에 속하는 지점은 전부 "Task가 방금 실행을 (재)시작하는"
지점이고, 정확히 다음 세 곳이다(`kContextSwitch`(context_switch.S)
의 `ret`가 돌아가는 세 목적지와 정확히 대응):

1. **`kTaskStartTrampoline`**(context_switch.S) - Task가 태어나서
   처음 실행되는 지점(`call rbx`, entry 콜백 호출 직전). 지금은
   UserThread 전용으로 `kEnterRing3`(process.cpp) 안에서 수동으로
   CR3를 설정하는데(자기 자신의 스택으로 넘어온 뒤라 이미 안전),
   이걸 `kSyncCr3(Scheduler::currentTask())` 호출로 대체하면 커널
   Task의 첫 실행에도 같은 안전망이 자동으로 적용된다(지금은 커널
   Task 첫 실행 시 CR3를 아예 안 건드리는데, 부팅 시점 CR3가 이미
   `gBootPml4Phys`라 우연히 항상 맞았을 뿐 - 부팅 이후 동적으로
   커널 Task를 새로 만드는 기능이 생기면 이 우연이 깨질 수 있다,
   §4 참고).
2. **`Scheduler::yieldCurrent()`의 `kContextSwitch(&current->savedRsp,
   gIdleSavedRsp[coreIndex])` 반환 직후** - 파킹에서 풀려 재개되는
   지점. 지금 이 자리의 `asm volatile("sti")` 바로 앞에
   `kSyncCr3(current)` 추가.
3. **`Scheduler::parkCurrent()`의 대응 지점** - yieldCurrent()와
   완전히 동일한 위치에 동일하게 추가.

**`runLoop()`의 idle→Task 전환 자체(`kContextSwitch(&gIdleSavedRsp
[coreIndex], next->savedRsp)`)에는 새로 추가할 지점이 없다** - 그
전환의 "도착 지점"이 정확히 위 세 곳 중 하나(최초 실행이면
kTaskStartTrampoline, yieldCurrent/parkCurrent로 파킹됐다가 이
idle→Task 경로로 재개되는 것이면 그 함수들의 재개 지점)이므로,
runLoop() 자신은 아무것도 몰라도 된다 - 이게 이 설계의 핵심 이점
(§5).

### 3.3 kEnterRing3 변경

`kEnterRing3`(process.cpp)의 수동 CR3 설정 코드(`asm volatile("mov
%0, %%cr3" ...)`)는 제거하고, `kTaskStartTrampoline`이 `call rbx`
전에 `kSyncCr3()`를 호출하는 것으로 대체된다 - `kEnterRing3` 자신은
그 뒤(entry 콜백 안)에서 실행되므로 이미 CR3가 맞춰진 채로 시작한다.

## 4. 이 설계가 막아 두는 것 - 아직 실제로 발현되지 않은 공백까지 포함

- §3.2의 세 지점 통일로, 설계자가 지적한 "yieldCurrent/parkCurrent
  재개 시 CR3 미복원" 공백(미래에 Mutex/Semaphore 경합으로 유저
  스레드가 파킹되면 네 번째로 재발했을 버그)이 **아직 그 경로를
  실제로 쓰는 코드가 없는 지금 시점에 선제적으로** 막힌다.
- "부팅 시점 CR3가 우연히 gBootPml4Phys라서 커널 Task 첫 실행이
  우연히 맞았던" 것(§3.2-1)도 더 이상 우연에 의존하지 않는다 -
  나중에 어떤 코드가 UserThread 실행 도중(CR3가 그 프로세스로 바뀐
  상태) 새 커널 Task를 만들어 즉시 실행시키는 기능이 생겨도 안전.

## 5. 최적화 - 불필요한 TLB flush 회피 (설계자 답변 지시)

`mov cr3`는 실행되는 즉시 이 코어의 TLB 전체를 무효화한다 - 대상이
바뀌지 않았는데도(예: 커널 Task 두 개가 연달아 전환되는 경우, 둘 다
`gBootPml4Phys`) 매번 쓰면 불필요한 전체 TLB flush를 유발해 그
직후의 모든 메모리 접근이 느려진다. `kSyncCr3()`는 `Paging::
currentPml4Phys()`(이미 있는 함수, 단순 `mov cr3, reg` 레지스터
읽기라 매우 저렴)로 현재 값을 읽어 target과 같으면 아예 쓰지 않는다
- 의미상 100% 안전한 최적화다(§3.2가 이미 "매 재개 지점마다 반드시
확인은 한다"를 보장하므로, 비교 후 생략해도 불변조건이 깨지지
않는다 - 생략은 "이미 맞는 값을 다시 쓰지 않는다"는 뜻일 뿐).

현재 v1(프로세스당 스레드 하나, 커널 Task는 리액터 하나뿐)에서
실제로 이 최적화가 스킵을 만들어내는 대표 경우:
- 리액터가 연속으로 여러 tick에 걸쳐 계속 선택되는 구간(다른
  UserThread가 실행 준비가 안 된 동안) - 매번 `gBootPml4Phys`로
  다시 쓸 필요가 없어진다.
- 같은 UserThread가 자기 타임퀀텀을 소진하고 다시 자기 자신이
  다음 tick에 뽑히는 경우(다른 Task가 없어 `onTick()`의 `next`가
  `current`와 같을 일은 없지만 - `pickNext`가 다른 Task가 없으면
  전환 자체를 안 함, §2 참고 - 실제로는 이 경우가 아니라 "그
  UserThread → 리액터 → 다시 그 UserThread"처럼 짧게 왕복하는
  패턴에서 리액터 쪽 CR3 쓰기 1회는 여전히 필요하지만 그 다음
  UserThread로 돌아올 때도 항상 필요 - 즉 스킵 이득은 "같은 대상이
  연속되는 구간"에 국한된다, 멀티프로세스가 실제로 늘어나면 이
  구간이 짧아지므로 최적화 효과도 자연히 줄어드는 정직한 트레이드
  오프).

## 6. 적용 대상 코드 변경 목록 (구현은 이 설계 승인 후 별도 계획으로)

- `scheduler.cpp`: `kSyncCr3ForDispatch` → `kSyncCr3`로 개명 + §5의
  비교 최적화 추가. `onTick()`의 호출부는 그대로(위치 불변).
- `scheduler.cpp`의 `yieldCurrent()`/`parkCurrent()`: 각각의
  `kContextSwitch` 반환 직후, 기존 `asm volatile("sti")` 바로 앞에
  `kSyncCr3(current)` 추가.
- `context_switch.S`의 `kTaskStartTrampoline`: `call rbx` 전에 C++
  헬퍼(`kSyncCr3(Scheduler::currentTask())`를 감싼 작은 `extern "C"`
  함수) 호출 추가.
- `process.cpp`의 `kEnterRing3`: 수동 CR3 설정 asm 블록 제거(§3.3).
- 회귀 검증: PN-63BCFE45/PN-71C3D483이 이미 확립해 둔 QEMU
  시나리오(PVH 단일코어/GRUB SMP4, 실제 init self-terminate +
  진단 UserThread 동시 실행) 전부 재확인 + 가능하면
  yieldCurrent/parkCurrent 경로를 실제로 타는 새 진단 시나리오
  (손으로 만든 스레드가 파킹 후 재개되는 왕복)를 추가해 §4가 막은
  공백을 직접 실측 검증.

## 7. 범위 밖

- Mutex/Semaphore 등 실제로 `parkCurrent`/`yieldCurrent`를 쓰는
  유저 syscall 자체의 설계(SP-0666DB3C §13에 이미 커널 레벨
  구현은 있음 - 유저 syscall 노출은 별도 계획). **[갱신, 2026-09-16,
  설계자 지시("범위 밖으로 표기된 것들도 설계 시작해")]** SP-0666DB3C
  §17로 설계 완료(PN-E82744B1) - 결론은 유저 syscall이 실제로는
  `parkCurrent`가 아니라 **`yieldCurrent`만** 쓴다는 것이었다(§17.1 -
  syscall 핸들러가 공유 리액터 Task 위에서 돌아 `parkCurrent`를 쓰면
  그 코어 전체가 멈추므로 `AsyncMutex`/`AsyncSemaphore`의
  YieldingPolicy만 안전).
- 코어 간 Task 이관(load balancing, PN-7679813D) - 이 설계는
  "target의 마지막 실행 코어 == 지금 이 코어"라는 v1 전제를 그대로
  유지한다(scheduler.h의 `retireTask` 문서 주석과 동일한 전제). **[검토,
  2026-09-16]** 이 항목은 PN-7679813D 자신이 "착수 시 반드시 재검토"
  로 이미 추적 중이라 이 문서에서 추가로 설계할 내용은 없음(중복
  방지 - 새 내용 없음).

## 8. 하드웨어 불변조건(Invariant) 체크리스트 — 디스패치 동기화 상태

설계자 답변(QU-CCB9353C, 2026-09-15) - CR3만이 아니라 "Task 디스패치
때마다 그 Task 자신의 상태로 동기화해야 하는" 하드웨어 상태 전부를
한 곳에 모은 체크리스트. §3.2가 확립한 두 갈래(①트랩 경로/②
kContextSwitch 재개 경로, 그 안의 세 지점)는 CR3 전용이 아니라
**이 체크리스트 전체가 재사용해야 하는 공용 디스패치 동기화 지점**이다
- 새 항목이 추가될 때마다 §3.2의 지점을 처음부터 다시 찾지 않는다.

| # | 상태 | 동기화 함수 | 상태 |
|---|---|---|---|
| ① | CR3 (PML4) | `kSyncCr3`(§3.1) | 이 문서로 확정 |
| ② | TSS.RSP0 (Kernel Stack) | `kSyncRsp0ForDispatch` | 완료(PN-AEA74E1B, "모든 디스패치 지점"으로 일반화됨) |
| ③ | CR0.TS (FPU Lazy Trap) | `kSyncFpu` | **[개정, 2026-09-15] 완료**(PN-F258698E, 커밋 134985d) - §3.2가 정의한 같은 세 지점(`onTick()`, `kTaskStartTrampoline`(실제로는 `kSyncCr3OnTaskStart`), `yieldCurrent()`/`parkCurrent()` 재개)에 `kSyncFpu()` 호출을 끼워 넣는 방식으로 구현, 새 디스패치 훅 없음(아래 선행 조건 그대로 지켜짐) |

**PN-F258698E(FPU) 착수 시 선행 조건(설계자 지시) - 지켜짐**: FPU 상태
관리는 별도의 새 디스패치 훅을 파지 않는다는 지시대로, §3.2가 정의한
공용 동기화 진입점(`onTick()`, `kTaskStartTrampoline`,
`yieldCurrent()`/`parkCurrent()` 재개 지점) 그대로에 `kSyncFpu()`를
얹어 구현이 완료됐다 - 새로 찾은 지점 없음.
