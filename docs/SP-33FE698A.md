# 코루틴 AsyncTask 전용 뮤텍스(AsyncCoroMutex) — 재시도 폴링을 없앤 명시적 wait-queue 기반 설계

## 0. 배경 — 왜 이 설계가 필요한가

`DC-59F63D0E`(QU-5CE6FA42, 설계자 지시 "이걸 설계안으로 작성해봐")로
등록된 문제를 설계로 정리한다.

`PN-F2594E93`가 `AsyncTaskCoroYield`(코루틴 `onExec` 안에서 "하드웨어
레지스터를 다시 읽는" 식의 자기 완결적 폴링 전용으로 설계된
프리미티브, `PN-A0CEF82D`/`QU-CC8A31F6`)를 락 재시도 용도로 전용한
`gQuotaCurspaceMutexCore`(`PN-D168A778`)/`gBlockBitmapAllocMutexCore`
(`PN-ADA46BF4`)에서 우선순위 역전 라이브락을 발견하고, 설계자 답변
"(b) 재시도 카운트 기반 강등"을 구현했다(commit `d190008`).

그런데 `PN-ADA46BF4`가 이 수정을 재적용해 실제 AHCI I/O로 재검증하자
**8-writer는 물론 2-writer(락 경합자 정확히 1개)조차 100% 다시
hang**했다(`DC-59F63D0E` 상세 재현 기록) — `gQuotaCurspaceMutexCore`
로 같은 패턴을 검증했을 때는 8-writer도 통과했는데, 이번엔 임계구역이
실제 AHCI I/O `co_await`를 4회(비트맵 read/gd read/비트맵 write/gd
write) 연달아 감싼다는 점이 다르다.

### 0.1 오늘 재조사로 새로 확인한 사실 (이 설계안의 근거)

이 문제를 다시 들여다보며 기존에 몰랐던 사실 세 가지를 코드로
확인했다:

1. **`gPreemptiveQueues`/`gExecQueues`는 진짜 FIFO 큐다**
   (`async_task.cpp`의 `AsyncTaskQueue::pushBack`/`popFront`,
   연결 리스트 tail-push/head-pop) — "선점 큐가 LIFO라 최근 재시도가
   계속 새치기한다"는 가설은 성립하지 않는다.
2. **`co_await AsyncTaskCoroAwaiter(target)`로 대기하던 코루틴이
   재개될 때도 `preemptive=true`로 선점 큐에 들어간다**
   (`kWakeWaitingAsyncTask()`, async_task.cpp:590-600) — 즉 락
   보유자 자신의 "I/O 완료 후 재개"도 재시도자와 **같은 우선순위,
   같은 큐**를 공유한다. FIFO이므로 이것만으로는 직접적인 아사
   (starvation) 메커니즘이 설명되지 않는다.
3. **`AsyncTaskWaitGroup::waitAll()`은 IF=1인 평범한 Task 컨텍스트에서
   `drainOnce()`를 직접 반복 호출**하고(async_task.cpp:624-643),
   **`kAsyncDrainIsr`(self-IPI 핸들러)는 IF=0인 ISR 컨텍스트에서
   최대 `kAsyncDrainBatchLimit`(32)개까지 처리한 뒤 자기 자신에게
   IPI를 재발사하고 반환**한다(`PN-4859FDE9` 수정, async_task.cpp:
   286-296) — 즉 이 시스템은 **서로 다른 인터럽트 우선순위 레벨에서
   같은 큐를 동시에 드레인하는 두 개의 독립된 드레인 루프**를 갖고
   있고, 그 상호작용(같은 코어에서 ISR 드레인 배치 도중 실제 AHCI
   하드웨어 인터럽트가 몇 번이나 지연되는지, `waitAll()`의 busy-poll
   루프와 self-IPI 드레인이 같은 `gPreemptiveQueues` 항목을 놓고
   경쟁할 때 정확히 무슨 순서로 소비되는지)은 **정적 코드 분석만으로
   완전히 확정할 수 없다** — 라이브 gdb/하드웨어 트레이스가 있어야
   끝까지 규명 가능하다.

**정직하게 기록**: 이번 조사로 "task별 재시도 카운터가 N-way 경합에서
뚫린다"는 최초 가설은 **반증**됐다(2-writer, 즉 경합자가 정확히 1개인
가장 단순한 경우조차 hang한다 — N-way와 무관). 그러나 정확히 어느
지점에서 재시도가 승자가 되고 진행이 멈추는지 그 미시적 메커니즘은
**아직 완전히 확정하지 못했다**(§0.1-3 참고, gdb 라이브 세션이
필요한 영역). 이 설계안은 그 정확한 메커니즘을 규명하는 대신 —
정확히 **DC-5F0AC0D3가 제시했던 후보 (c)** 방향으로 — 재시도/폴링
자체를 구조적으로 없애 이 메커니즘이 무엇이든 성립할 수 없게 만드는
쪽을 택한다. 재시도 폴링 기반 접근을 세 번째로 패치하며 새로운
공정성 파라미터를 추가하는 것보다, 이미 이 커널에 실사용 선례가 있는
"명시적 깨우기" 패턴으로 갈아타는 편이 근본적이고 검증 부담도 적다고
판단했다.

## 1. 왜 기존 프리미티브로는 안 되는가

이 커널은 이미 `mutex_core.h`에 `BasicMutex<Policy>` 템플릿과 두
정책을 갖고 있다:

- **`Mutex = BasicMutex<ParkingPolicy>`**: 경합 시 `WaitQueue::
  parkCurrentAndUnlock()`으로 **진짜 `kernel::Task`**를 재운다 -
  일반 동기 실행 흐름(코루틴 아님) 전용.
- **`AsyncMutex = BasicMutex<YieldingPolicy>`**: 경합 시
  `AsyncTask::yield()`(스택풀 컨텍스트 스위치 기반)로 재시도한다 -
  **"스택풀" AsyncTask 전용**, 진짜 C++20 코루틴에서 부르면 무한
  대기(`PN-A0CEF82D`/`QU-CC8A31F6`가 이미 실측 확인한 함정 -
  `AsyncTask::yield()`는 코루틴 프레임이 아니라 `kContextSwitch`
  전용 스택을 필요로 함).

`Ext4Driver::onExec`처럼 **진짜 C++20 코루틴**(`co_return`이 있어
컴파일러가 상태 기계로 변환한 함수)인 `onExec`에는 이 둘 다 못 쓴다 -
그래서 `PN-D168A778`/`PN-ADA46BF4`가 원시 `MutexCore`(정책 없는
코어) + 호출부에서 직접 `co_await kernel::AsyncTaskCoroYield{}`로
재시도하는 방식을 손수 조립했다. 이게 바로 이번 라이브락/hang
계열의 근본 원인이다 - **애초에 "코루틴 안에서 경합 시 진짜로
정지했다가 release()가 명시적으로 깨워 주는" 세 번째 정책이 이
프레임워크에 없었다.**

`BasicMutex<Policy>::lock()`/`onContended`는 **평범한 비-코루틴
함수**라 이 자리에 새 정책을 끼워 넣는 방식으로는 해결되지 않는다 -
코루틴을 실제로 정지시키려면 정지 지점이 **호출부 코루틴 자신의
`co_await` 식**이어야 하기 때문이다(C++20 언어 규칙). 그래서 이
설계는 `BasicMutex<Policy>`를 확장하는 대신, `AsyncTaskCoroAwaiter`/
`AsyncTaskCoroYield`와 같은 급의 **독립된 co_await 가능 프리미티브**
하나를 새로 추가한다.

## 2. 확정된 설계 — `AsyncCoroMutex`

### 2.1 이미 이 커널에 있는 선례를 그대로 재사용

`interrupt_subscription.cpp`의 `WaitInterruptHandler`가 정확히 같은
문제(코루틴 `onExec` 안에서 "이벤트가 준비될 때까지 진짜로 정지")를
이미 풀어 뒀다 - 그 해법을 이름만 일반화해 그대로 가져온다:

1. **하나의 스핀락으로 "상태 확인"과 "대기열 등록"을 원자적으로
   묶는다**(lost-wakeup 방지 - `MutexCore::tryAcquireOrKeepLock`
   계약과 동일한 원칙, `WaitInterruptHandler`의 §3 "onExec 원자성
   계약" 주석 참고).
2. **대기자는 `kernel::SuspendAlways{}`로 순수 정지한다** -
   `AsyncTaskCoroYield`처럼 스스로 재큐잉하지 않는다(그래서 애초에
   "재시도"라는 개념 자체가 없다 - 매 리액터 패스마다 다시 확인하는
   폴링이 아니라, 한 번 등록되면 `release()`가 명시적으로 깨울
   때까지 큐 어디에도 나타나지 않는다).
3. **깨우기는 소유자(락을 놓는 쪽)가 대기열에서 직접
   `popFront()`한 뒤 `AsyncReactor::submitCompletion()`을 호출한다**
   - `kInterruptSubscriptionIsr`의 `popFront()`+`submitCompletion()`
   패턴과 동일.
4. **대기열 노드는 `AsyncTask::next`를 재사용하는 침습적 FIFO**
   (`channel.h`의 `AsyncTaskWaitQueue`, `interrupt_subscription.h`의
   `InterruptWaiterQueue`와 완전히 같은 관례 - 이 커널은 이 작은
   구조체를 서브시스템마다 독립적으로 다시 두는 걸 의도된 패턴으로
   삼는다, "관계없는 두 서브시스템의 불필요한 결합 방지").

### 2.2 핵심 설계 결정 — "직접 인계(direct handoff)"

기존 `WaitQueue::wakeOne()`/`ParkingPolicy`는 "대기자 하나를 깨우고,
그 대기자가 다시 `tryAcquire()`로 재경쟁"하는 방식이다(§2.1의
`Mutex` 참고) - 이 방식은 깨어난 대기자보다 **먼저 도착한 새
요청자**가 그 사이 락을 새치기할 수 있다(release 순간 `_locked`가
잠깐 false가 되므로).

`AsyncCoroMutex::release()`는 이와 다르게 **직접 인계**한다 - 대기열이
비어 있지 않으면 `_locked`를 **여전히 true로 유지한 채** 다음
대기자에게 소유권을 그대로 넘긴다(그 대기자의 `await_resume()`이
"이미 락을 쥔 채로 재개됐다"는 뜻). 이렇게 하면:

- **새치기가 원천적으로 불가능**하다 - `_locked=false`가 되는 순간
  자체가 "대기자가 없을 때"로 한정되므로, release와 동시에 다른
  코어의 새 `tryAcquire()`가 끼어들 여지가 없다.
- **순서가 항상 FIFO로 확정**된다 - 몇 번째로 등록됐는지가 곧 몇
  번째로 락을 받는지와 정확히 같다. "재시도 카운터"/"드레인 배치
  상한" 같은 스케줄러 공정성 파라미터에 전혀 의존하지 않는다 - 이번
  hang 계열 전체의 근본 원인(그 파라미터들의 상호작용)이 설계적으로
  성립할 수 없어진다.
- 대가는 `release()`가 대기자 유무를 확인하는 짧은 스핀락 구간뿐 -
  기존 `MutexCore::release()`도 이미 같은 비용을 지불하고 있다.

### 2.3 API (제안)

```cpp
// minicore/kernel/mutex_core.h에 추가(또는 별도 async_coro_mutex.h -
// 착수 세션이 기존 파일 크기/응집도를 보고 결정, RM-23F4B687 §4
// 취지상 구현 세부).
class AsyncCoroMutex {
public:
    void init() { _locked = false; }

    // co_await 가능한 획득 - 진짜 C++20 코루틴 onExec 안에서만 쓴다
    // (AsyncTaskCoroAwaiter/AsyncTaskCoroYield와 동일한 제약).
    class LockAwaiter {
    public:
        explicit LockAwaiter(AsyncCoroMutex& mutex) : _mutex(mutex) {}
        bool await_ready() noexcept { return false; }  // 항상 await_suspend 안에서 원자적으로 판단
        bool await_suspend(std::coroutine_handle<>) noexcept {
            AsyncTask* self = AsyncTask::current();
            SpinlockGuard guard(_mutex._lock);
            if (!_mutex._locked) {
                _mutex._locked = true;
                return false;  // 무경합 - 정지 없이 즉시 재개(락 획득 완료)
            }
            _mutex._waiters.pushBack(self);
            return true;  // 정지 - release()의 직접 인계가 재개시킴(그때 이미 락 보유 상태)
        }
        void await_resume() noexcept {}
    private:
        AsyncCoroMutex& _mutex;
    };
    LockAwaiter lockAsync() { return LockAwaiter(*this); }

    // 기존 gQuotaCurspaceMutexCore류 호출부와의 점진 이행/비-코루틴
    // 호출부 호환용 - 의미는 기존 MutexCore::tryAcquire()와 동일.
    bool tryAcquire() {
        SpinlockGuard guard(_lock);
        if (_locked) return false;
        _locked = true;
        return true;
    }

    void release() {
        AsyncTask* next = nullptr;
        {
            SpinlockGuard guard(_lock);
            next = _waiters.popFront();
            if (!next) {
                _locked = false;
            }
            // next가 있으면 _locked=true 유지 - §2.2 직접 인계.
        }
        if (next) {
            AsyncReactor::submitCompletion(next, /*preemptive=*/true);
        }
    }

private:
    // interrupt_subscription.h의 InterruptWaiterQueue/channel.h의
    // AsyncTaskWaitQueue와 동일한 구조 - 이 파일 안에 독립적으로 다시
    // 둔다(§2.1-4 관례).
    struct Waiters {
        AsyncTask* head = nullptr;
        AsyncTask* tail = nullptr;
        void pushBack(AsyncTask* task) { ... }   // 기존 두 사례와 바이트 단위로 동일
        AsyncTask* popFront() { ... }
    };

    Spinlock _lock;
    bool _locked = false;
    Waiters _waiters;
};
```

사용 예(`gBlockBitmapAllocMutexCore` 재적용 시):

```cpp
co_await gBlockBitmapAllocMutex.lockAsync();
{
    // 기존 do-while(false)/조기 break 임계구역 그대로 - 이번엔
    // MutexCoreReleaseGuard 대신 스코프 종료 시 release()를 호출하는
    // 동일한 RAII 래퍼(AsyncCoroMutexReleaseGuard)로 감싼다.
    AsyncCoroMutexReleaseGuard guard(gBlockBitmapAllocMutex);
    ...  // 비트맵 read → 조작 → write, 그대로 co_await 여러 번 포함
}
```

**임계구역 안에 실제 I/O `co_await`가 몇 개 들어있든(1개든 4개든)
설계상 아무 문제가 없다** - 대기자는 폴링하지 않고 그냥 정지해
있으므로, 보유자가 그 사이 얼마나 오래(몇 번의 I/O를 거쳐) 실행되든
스케줄러 큐 경합 자체가 발생하지 않는다.

### 2.4 취소(cancel) 처리 — 구현 시 반드시 채워야 하는 부분 (열린 세부)

`WaitInterruptHandler::onCancel`이 이미 겪은 것과 같은 위험이
그대로 적용된다 - 대기열에 매달린 채로 그 AsyncTask의 소유자
(제출자 프로세스)가 강제 종료되면, 프레임워크가 `onExec`을 재개하는
대신 `onCancel`만 부르고 코루틴 프레임 자체를 반납한다 - 그 시점에
`_waiters`에 남아 있는 포인터가 댕글링돼 다음 `release()`의
`popFront()`가 UAF를 일으킨다(`SP-1FBC0EEB` Channel IPC의
`PN-C4611402`, `interrupt_subscription.cpp`의 동일 클래스 결함과
같은 패턴).

`Ext4Driver`(등 이 뮤텍스를 쓸 각 `AsyncTaskHandler`)의 `onCancel`이
"이 task가 `_waiters`에 매달려 있으면 제거한다"를 구현해야 한다 -
`WaitInterruptHandler`처럼 소유자 식별 없이 리스트 선형 탐색 후
제거하는 방식을 그대로 재사용할 수 있는지, 아니면 `AsyncCoroMutex`
자신이 "이 task가 지금 내 대기열에 있는지" 조회하는 헬퍼를 노출해야
하는지는 **착수 세션이 실제 취소 재현으로 확정할 부분**으로 남긴다
(CLAUDE.md 규칙 4 - 실측 없이 구조를 추측하지 않음).

## 3. 마이그레이션 대상

- **`gBlockBitmapAllocMutexCore`**(`PN-ADA46BF4`) - 이 설계안의
  직접 계기, 9개 호출부 전부 `co_await ... .lockAsync()`/
  `AsyncCoroMutexReleaseGuard`로 재작성.
- **`gQuotaCurspaceMutexCore`**(`PN-D168A778`) - 지금까지 우연히
  hang이 안 났을 뿐 정확히 같은 위험군(임계구역이 실제 I/O
  `co_await`를 포함)이다 - 같이 이전하고 8-writer 재검증 권장.
- **`AsyncTaskCoroYield`/`kAsyncTaskCoroYieldFairnessThreshold`
  ("(b)" 수정) 자체는 원복하지 않는다** - `ahci.cpp`의 자기 완결적
  폴링 등 원래 설계 의도인 용도에는 여전히 유효하고 무해하다. 다만
  "코루틴 안 락 재시도" 용도로는 이제 이 설계(`AsyncCoroMutex`)를
  표준으로 삼고, `AsyncTaskCoroYield`를 그 목적으로 다시 쓰지 않는다
  (§0.1이 확인했듯 이 조합의 정확한 실패 지점을 완전히 규명하지
  못했으므로, "왜 (b)가 부족한지"를 계속 파고드는 것보다 이 패턴
  자체를 폐기하는 게 더 안전하고 검증 비용도 적다).

## 4. 검증 계획 (착수 세션)

1. `AsyncCoroMutex` 단위 구현 - 디스크 없는 순수 재현(`PN-F2594E93`가

3. `gQuotaCurspaceMutexCore` 동일 이전 + 재검증.
4. 표준 5시나리오(PVH SMP1/SMP4, GRUB SMP4, GRUB SMP4+AHCI,
   stock-initrd) 무회귀.
5. §2.4(취소 처리)를 실제 프로세스 강제 종료 시나리오로 재현/검증.

## 5. 대안으로 검토했으나 채택하지 않은 것

- **"task별 재시도 카운터" 대신 "코어별 연속 선점 드레인 횟수 전역
  상한"**(이 DC의 원 질문 (2)번 후보) - §0.1-3이 확인했듯 이 hang의
  정확한 메커니즘이 `waitAll()`의 IF=1 폴링과 `kAsyncDrainIsr`의
  IF=0 배치 드레인이라는 **서로 다른 두 드레인 경로의 상호작용**일
  가능성이 있어, 코어별 카운터 하나로 두 경로 모두를 올바르게
  다스릴 수 있다는 보장이 없다 - 게다가 이 파라미터는 이미 한 번
  ("task별" 버전)실패했다. 폴링 자체를 없애는 §2 설계가 이 불확실성
  전체를 무의미하게 만든다.
- **`AsyncMutex`(`YieldingPolicy`)를 코루틴에서도 쓸 수 있게 고친다**
  - `AsyncTask::yield()`가 스택풀 전용(`kContextSwitch` 기반)이라
    코루틴 프레임 자체를 이해하지 못한다 - 이 정책을 코루틴 호환으로
    바꾸려면 결국 §2와 동일한 "코루틴 전용 awaiter"를 새로 만들어야
    해서, `BasicMutex<Policy>` 프레임워크를 억지로 재사용하는 이득이
    없다(오히려 기존 `YieldingPolicy` 사용처의 안전성 가정을 깨뜨릴
    위험만 늘어남).
