## 배경

`SP-CC1CF30E` §3/§5(승인됨)는 커널의 `gUserRecordCache`(`PN-B6DB692C`)가
authmgr의 read-through 캐시이고, 캐시 미스 시 `kSetuid()`/
`kCheckPermission()`이 authmgr에 **비동기 Channel 질의**로 캐시를
채운다고 확정했다. 그러나 `PN-24A2B6F5` 재착수를 위해
`minicore/kernel/user_record.cpp`/`kSetuid()`를 실제로 다시 읽어보니
이 경로는 여전히 전혀 구현돼 있지 않다(캐시 미스는 즉시
`ChannelError::ServiceUnavailable`을 반환할 뿐) - `PN-B6DB692C`가
"다음 착수 세션" 메모로 이미 남겨 둔 정확히 그 지점이다.

## 왜 지금 결정이 필요한가

이 커널에서 지금까지 Channel IPC는 항상 **유저랜드가 클라이언트,
커널이 서버**(syscall 엔드포인트) 역할이었다 - `authtest`가
authmgr에, `pubreg` 클라이언트가 `pubreg`에 연결하는 식. **커널
코드 자신이 유저랜드 서비스(authmgr)에 Channel로 연결하는 클라이언트가
되는 사례가 이번이 처음**이다. `SP-CC1CF30E`는 "비동기 질의로
채운다"고만 적었을 뿐, 아래 세부는 명시하지 않았다 - `kSetuid()`가
보안 판정 경로(권한 승격/거부를 직접 좌우)라 이 세부를 구현 세션이
임의로 정하지 않고 설계자 확인을 받고자 한다(CLAUDE.md 규칙 4).

## 결정이 필요한 지점

1. **연결 수명주기**: 매 캐시미스 질의마다 새 Channel을 열고
   닫는지(단순하지만 연결당 handshake 오버헤드), 아니면 커널이
   authmgr 기동 시점에 한 번 연결해 그 Channel을 계속 재사용하는지
   (효율적이지만 authmgr이 죽었다 재시작하면 커널이 그 사실을 어떻게
   알고 재연결하는지 별도로 필요).
2. **authmgr이 아직 안 뜬 시점의 첫 질의**: 부팅 시퀀스상 devmgr/fs
   KernelThread와 서비스 프로세스(authmgr 포함)들이 거의 동시에
   스폰되는데, 그 사이 극초반에 첫 `kSetuid()` 캐시미스가 발생하면
   (이론상 가능 - 정확한 스폰 순서가 스케줄러에 달려 있음) 어떻게
   하는지 - 그냥 `ServiceUnavailable`로 즉시 실패(기존 fail-closed류
   동작 유지)인지, 아니면 authmgr이 뜰 때까지 일정 시간 재시도하는지.
3. **동시 다중 캐시미스**: 여러 코어에서 동시에 서로 다른 uid로
   캐시미스가 나면(예: 여러 UserThread가 동시에 setuid 시도), 커널이
   authmgr과의 Channel을 코어별/요청별로 몇 개나 열어 두는지(직렬화
   해서 한 번에 하나씩 처리? 여러 개 동시 연결 허용?).
4. **타임아웃 정책**: authmgr이 응답 없이 오래 걸리면(비정상 상태)
   `kSetuid()` 호출자가 무한정 대기하는지, 일정 시간 후
   `ServiceUnavailable`로 포기하는지.

  필요한지도 착수 시 확인 필요.

## [답변 반영 + 새 장애물 발견, 2026-09-28] 연결 수명주기는 확정, 그러나 착수해 보니 더 근본적인 구조적 장애물 발견

설계자 답변: "고정 연결이 수립되어 있고, 끊어지면 자동으로 재연결."
(항목1 확정 - 부팅 시 한 번 연결해 계속 재사용, 끊기면 자동 재연결).

이 답변을 반영해 실제 구현에 착수했다가, **이 결정만으로는 풀리지
않는 더 깊은 구조적 문제**를 발견했다:

1. `Syscall::submit()`(syscall.cpp:180)가 `auto* self =
   static_cast<UserThread*>(Scheduler::currentTask());`로 **무조건**
   캐스트한다 - `self->pendingSyscalls`(UserThread 전용 필드)에
   기록해야 나중에 `wait()`/`waitForAnyOf()`가 찾을 수 있기 때문이다.
   커널 자신(KernelThread 컨텍스트, 또는 이 클라이언트를 위해 새로
   만들 전용 코루틴 컨텍스트)이 이 함수를 그대로 부르면 `PN-AA9D7030`
   에서 실제로 겪었던 것과 같은 클래스의 버그(KernelThread를
   UserThread*로 잘못 캐스트)가 재발한다.
2. **더 심각한 문제**: `channel.cpp`의 `kValidateUserBuffer()`
   (495행)가 `Connect`/`Open`/`Read`/`Write` **전부**에서 무조건
   호출돼, `task->submitterTask.lock()`으로 얻은 제출자를
   `UserThread*`로 캐스트한 뒤 `Paging::isUserRangeValid(ptr, length,
   thread->userPml4Phys)`로 "그 프로세스의 유저 주소 공간 범위
   안인가"를 검사한다. **커널 자신이 제출자면 이 버퍼는 유저 주소
   공간이 아니라 커널 주소 공간의 포인터**이므로, 이 검사는 원리적으로
   항상 실패한다(`InvalidPointer`) - 단순히 "커널 전용 우회 경로를
   추가"하는 게 아니라, `PN-B552E75F`가 임의 커널 메모리 읽기 취약점을
   막으려고 도입한 바로 그 보안 검사를 건드리는 일이라 매우 신중해야
   한다.

**결론**: 커널이 Channel 클라이언트가 되려면 기존 `Syscall::submit()`/
`kValidateUserBuffer()` 경로를 그대로 재사용할 수 없다 - 최소한
아래 중 하나가 필요해 보이는데, 어느 쪽이 맞을지, 혹은 다른 방향을
원하시는지 여쭙고 싶다:

- (A) **커널 전용 별도 제출 경로 신설** - `Syscall::submit()`을 안
  거치고 `AsyncTask::submit()`을 직접 불러(기존 ext4/fat32가
  `AsyncTaskCoroAwaiter`로 다른 AsyncTask 완료를 기다리는 것과
  동일한 패턴) 완료를 기다리되, `ConnectChannelHandler`/
  `ChannelReadHandler`/`ChannelWriteHandler` 안의 `kValidateUserBuffer`
  호출을 "제출자가 UserThread가 아니면(커널 자신이면) 그 버퍼는
  이미 신뢰된 커널 주소이므로 검사를 건너뛴다"로 명시적으로
  확장한다 - 기존 보안 검사의 의도(유저가 임의 커널 주소를 넘기는
  것 차단)는 그대로 유지하면서, "제출자 자체가 커널"이라는 새
  케이스만 추가한다.
- (B) **완전히 별도의 경량 커널 전용 Channel 클라이언트** -
  `AsyncTaskHandler` 계층을 아예 안 거치고, `Channel`/`Bridge`/
  `RingBuffer` 내부 구조체를 커널 코드가 직접 조작하는 전용 함수
  (예: `kKernelChannelConnect`/`kKernelChannelRead`/
  `kKernelChannelWrite`)를 신설한다 - 기존 유저랜드 경로를 전혀
  안 건드려 더 안전하지만 코드 중복이 생긴다.
- (C) 다른 방향이 있다면.
