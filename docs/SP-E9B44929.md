# Syscall Group+Call 2단계 인코딩 — 설계 제안

**배경 지시(2026-09-17, RM-48E1E610 대상 opinion)**:

> "Syscall 할당 체계를 개편할 방법을 찾아야 할 것 같네.
> 1. Syscall Group -> Syscall 로 맵핑되는 방식으로.
> 2. 개별 Group 안에서 각 Group에 배정된 기능(e.g. Channel)이 자기
>    자신의 Call 번호를 관리하는 체계가 되는거지.
> 그러니까 Syscall 페러미터가 SyscallEndpointId 하나만 받았었는데,
> 이걸 16비트(혹은 그 이상)로 올려서 하위 8비트는 Syscall 번호,
> 그외 상위 비트는 그룹 번호로 해석하도록."

## 1. 왜 필요한가 — 현재 체계의 한계

`RM-48E1E610`이 현재 하는 일은 **모든 subsystem의 모든 syscall을
하나의 평평한 0-255 번호 공간에서 중재**하는 것이다 - 새 syscall을
설계할 때마다 그 표에서 "다음 미사용 번호"를 확인하고 예약해야
하고, 이미 47-49(`SubscribeEvent` 등)처럼 "설계 확정 시점에 번호
등록이 누락됐다가 뒤늦게 발견"되는 사고가 실제로 있었다. subsystem
수가 늘어날수록(Channel/VFS/PnP/Debug/Mutex 등 이미 9개 계열) 이
단일 좁은 공간(`kMaxSyscallEndpoints=256`, `syscall.cpp:11`)이
조율 병목이자 충돌 위험이 된다.

## 2. 인코딩 설계

`SyscallEndpointId`는 **`uint32_t` 그대로 유지**(커널/유저 양쪽
`syscall.h`가 이미 `uint32_t` - 와이어 타입 자체는 안 바뀜, ABI
트랩 경로(RDI=endpointId)도 무변경). 그 32비트 값의 **해석**만
바뀐다:

```
비트 [31:16]  예약(반드시 0) - 향후 확장용, v1은 검증만
비트 [15:8]   그룹 번호 (0-255)
비트 [7:0]    그룹 내 call 번호 (0-255)
```

```cpp
// syscall.h (제안)
constexpr uint32_t kSyscallCallBits = 8;
constexpr uint32_t kSyscallCallMask = 0xFF;

constexpr SyscallEndpointId kMakeSyscallEndpointId(uint8_t group, uint8_t call) {
    return (static_cast<uint32_t>(group) << kSyscallCallBits) | call;
}
constexpr uint8_t kSyscallGroupOf(SyscallEndpointId id) {
    return static_cast<uint8_t>((id >> kSyscallCallBits) & 0xFF);
}
constexpr uint8_t kSyscallCallOf(SyscallEndpointId id) {
    return static_cast<uint8_t>(id & kSyscallCallMask);
}
```

16비트(그룹 8비트+call 8비트)만 실제로 쓰고 남는 상위 16비트는
지시대로 "16비트 혹은 그 이상" 중 여유분으로 예약 - v1은 반드시
0이어야 하고(`registerHandler`/`resolveSubjectCode`가 0이 아니면
즉시 실패), 실제 용도(예: API 버전 태그)는 필요해질 때 별도 설계.

**"그룹 안에서 각 그룹의 기능이 자기 번호를 관리"의 의미**: 그룹
번호(상위 8비트)만 이 문서/`RM-48E1E610`이 중재하는 유일한 공유
자원이고, 그 안의 call 번호(하위 8비트)는 그 그룹을 소유한
subsystem의 설계 문서(예: `SP-1FBC0EEB`가 Channel 그룹을 소유)가
**다른 그룹과 조율할 필요 없이 독자적으로** 0부터 채워 나간다 -
지금처럼 "다음 미사용 전역 번호"를 확인할 필요가 없어진다(그
subsystem 문서 자신의 이력만 보면 됨).

- `userland/libs/libmc/syscall.h`: 커널과 동일한 헬퍼+상수 재정의

- 이미 이 상수를 쓰는 모든 호출부(devmgr 스켈레톤, kmain.cpp TEMP

- `RM-48E1E610`: **[확정, 2026-09-17, 설계자 의견]** "Syscall
  테이블은 그룹이 나뉘어도 이 문서에서 통합 관리하도록 해. 그룹별로
  챕터를 나눠서 따로따로 카운팅하며 모아." - 제안했던 방향(완전

  챕터(하위 절)**로 재구성한다 - 각 챕터 안에서 그 그룹의 call
  번호를 독립적으로 카운팅(0부터)하되, 실제 등재/기록은 여전히

  "조율 없이 번호를 정할 수 있다"는 §2의 장점은 유지하면서도, 그
  결과를 최종적으로 기록하는 단일 장소는 지금처럼 하나로 유지 -

## 6-A. [완료, 2026-09-17, commit 예정] 구현 및 실측으로 발견한 버그

설계자 답변 반영: (1) 그룹별 테이블 + 포인터 + min/max로 공간 절약,
(2) breaking ABI 마이그레이션 승인, (3) 그룹 번호는 연속 배정.

**실측으로 발견한 버그(구현 중, 자체 발견)**: §6 질문1의 "그룹별
call 테이블을 동적으로 잡는다"는 원안을 `GenericSlabAllocator::alloc()`
으로 그대로 구현했다가 **부팅 극초반 페이지 폴트로 즉시 패닉**했다 -
원인은 `SelfTerminateHandler`가 `Scheduler::init()`(kmain.cpp) 안에서
`SyscallRegistry::registerHandler()`를 호출하는 시점이
`GenericSlabAllocator::init()`보다 **먼저**라는, kmain.cpp의 이미
확정된 부팅 순서였다(슬랩 할당자가 아직 초기화되지 않은 채로 그
API를 썼다). 기존 flat 배열 설계는 정적 배열이라 이 문제 자체가
없었는데, "포인터로 가리키는 동적 테이블"로 바꾸며 새로 생긴
암묵적 선행 조건(할당자 준비)을 놓쳤다.

**수정**: 힙 할당 대신 **정적 범프(bump) 풀**(`gCallSlotPool[1024]`,
전역 배열 - 할당자 초기화와 무관)에서 그룹 call 테이블 조각을 잘라
쓰도록 변경 - "그룹별 테이블+포인터+min/max"라는 설계 골격은 그대로
유지하면서 실제 메모리 출처만 힙에서 정적 풀로 바꿨다(재할당(그룹
범위 확장) 시 옛 조각은 반납하지 않고 그냥 버림 - 등록이 부팅 시
한 번뿐이라 낭비가 무시할 수준). QEMU 무-initrd+SMP4 재검증 - 클린
부팅+9개 그룹 전부(SelfTerminate 포함) 정상 등록 확인.

## 6. 열린 질문 — 설계자 확인 필요 (전부 해소됨, §6-A 참고)

1. **`gEndpointSlots` 저장 구조**: 이론상 그룹 8비트+call 8비트라
   `EndpointSlot gEndpointSlots[65536]`(dense) - 항목이 몇 바이트면
   (subjectCode+used) 수백 KB대 정적 배열이 된다. 대안은 **그룹당
   256개 슬롯을 실제 그 그룹이 처음 등록될 때만 동적/정적으로
   할당하는 2단 테이블**(`EndpointSlot* groupTables[256]`, 각 그룹
   테이블은 그 그룹에 실제 syscall이 생길 때 lazy 할당) - 메모리는
   절약되지만 조회 경로에 포인터 역참조가 한 단계 늘어난다. 지금
   9개 그룹만 쓰므로 dense 65536도 실무적으로 크게 부담은 아닐 수
   있음(RM-23F4B687 §4 - 실측 후 조정 대상으로 남길지, 지금
   결정할지 확인 필요).
2. **breaking ABI 마이그레이션 승인**: §4가 바꾸는 값들 중 이미
   구현된 syscall이 다수라 `SP-9CB55C5B §6`/`PN-C39882D0`과 같은
   패턴으로 명시적 승인이 필요하다고 판단했다 - 동의하시면 착수
   PN을 등록하겠습니다.
3. **그룹 번호 자체도 0부터 채우는지, 아니면 여유를 두고 듬성듬성
   배정할지**(예: 향후 세분화 대비) - §3은 0-8 연속으로 제안했다.

## 7. 요약

- **확정 제안**: 32비트 `SyscallEndpointId` 유지, 하위 8비트
  call+그다음 8비트 그룹(상위 16비트 예약)으로 재해석, §3의 9개
  그룹 배정, §4의 전체 마이그레이션 표.
- **확정 안 함(§6 질의 대기)**: 슬롯 저장 구조(dense vs 2단 lazy),
  마이그레이션 실제 착수 승인, 그룹 번호 배정 방식(연속 vs 여유).
