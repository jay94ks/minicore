# 실행 계획: IOAPIC 외부 인터럽트 라우팅

**[완료, 2026-09-14, 2026-09-14 재작업 반영]** QA-26450C3E 체크됨. 아래는 완료 기록으로 남긴다.

ACPI MADT로 IOAPIC 주소는 이미 확보했다(Acpi::ioApicAddress()). 지금은
그 주소를 아무데도 안 쓴다 - 실제로 매핑하고 리다이렉션 테이블을
설정해야 키보드 등 핀 기반 레거시 장치 인터럽트가 들어온다.

## 선행 조건

- Acpi::ioApicAddress() (완료)
- Paging::mapPage + PAGE_CACHE_DISABLE (완료 - LAPIC 매핑과 동일한
  패턴 재사용)

## 한 것

1. **IOAPIC MMIO 매핑**: `minicore/kernel/ioapic.h/.cpp` 신설.
   `kIoApicVirtBase = 0xFFFF901000001000UL`(LAPIC의 `kLapicVirtBase`
   바로 다음 4KiB 페이지 - 서로 다른 물리 프레임이라 독립된 가상주소
   필요) + `PAGE_CACHE_DISABLE`로 매핑.
2. **간접 레지스터 접근**: `IOREGSEL`(오프셋 0x00에 레지스터 번호
   기록)+`IOWIN`(오프셋 0x10 읽기/쓰기)의 2단계 방식을 파일 static
   `kReadReg`/`kWriteReg`로 구현.
3. **리다이렉션 테이블 설정**: `IoApic::setRedirection(gsi, vector,
   destApicId, polarity, triggerMode)` - REDTBL 엔트리(레지스터
   0x10+2*gsi/+1)에 벡터+목적지 APIC ID+극성+트리거 모드를 쓴다.
   `mask()`/`unmask()`도 추가.
4. **IDT를 벡터->콜백 표로 일반화**: 기존엔 CPU 예외(0-31)+타이머(32)+
   spurious(0xFF)만 있었다 - `isr.S`에 GAS `.altmacro`+`.rept` 숫자
   루프로 벡터 33-254 스텁 222개를 한꺼번에 찍어내고, 그 주소들을
   `kIsrDynamicStubTable`(rodata 배열)로 노출했다(손으로 222개 extern
   선언하는 대신 이 표 하나만 idt.cpp가 참조). `Idt::registerHandler(
   vector, InterruptHandler)`/`unregisterHandler(vector)`를 공개 API로
   추가 - `kIsrHandler`가 33-254 대역에서 등록된 콜백을 찾아 호출한
   뒤 자동으로 `Lapic::sendEoi()`를 보낸다(장치 핸들러가 EOI를 직접
   안 챙겨도 되게 구조적으로 강제 - 빼먹는 실수 방지). 등록 안 된
   벡터로 인터럽트가 들어오면(라우팅은 했는데 핸들러 등록을 깜빡한
   버그) 조용히 무시하지 않고 `kPanic`으로 멈춘다 - 이때 CPU 예외용
   이름 배열(`kExceptionNames`, 0-31 전용)을 잘못 인덱싱하지 않도록
   벡터 32 이상이면 "Unrouted hardware interrupt"로 별도 표기하게
   `kPanic`도 같이 고쳤다.
5. **검증(실측, 2026-09-14, QEMU 8.2.2)**: 키보드 IRQ1을 벡터 0x21로
   라우팅하고 핸들러를 등록한 뒤, QEMU 모니터의 `sendkey` 명령으로
   실제 키 입력을 주입했다(`-monitor stdio`를 named pipe로 제어해
   부팅 완료 후 지연을 두고 전송). 'a' 입력 → make 0x1E/break 0x9E,
   'b' 입력 → make 0x30/break 0xB0 스캔코드가 핸들러에 정확히
   전달됨을 확인(포트 0x60에서 직접 읽음) - IOAPIC 매핑→REDTBL
   설정→IDT 디스패치→EOI까지 전체 경로가 실제로 동작함을 확인했다.
   검증 후 임시 핸들러/라우팅 호출 코드는 제거했고, `IoApic::init()`
   (MMIO 매핑까지)은 영구 초기화 시퀀스에 남겨 뒀다(HPET 등 후속
   장치가 바로 `setRedirection`을 쓸 수 있게).
   x2APIC(PL-D65F49CC) 모드와 함께 켜도(`-accel kvm -cpu host`) 회귀
   없음을 재확인했다.

## 재작업 - ISO 파싱 + 8비트 목적지 한계 반영 (2026-09-14, 설계자 지시)

애초에 "이번엔 안 한 것"으로 남겨 뒀던 두 항목을 설계자가 검토 후
지금 시점에 구현하라고 확정했다(QU-2EF510B4, QU-F89355A8).

- **QU-2EF510B4 답변 반영**: ACPI MADT Interrupt Source Override
  (타입2)를 `acpi.cpp`가 실제로 파싱한다(`Acpi::resolveIsaIrq`) -
  더 이상 "IRQ==GSI" 가정에 의존하지 않는다. override가 없는 IRQ는
  ACPI 스펙의 ISA 기본값(GSI=IRQ, active-high, edge)으로 자연스럽게
  떨어진다.
- **QU-F89355A8 답변 반영**: `IoApic::setRedirection`의 `destApicId`는
  이미 32비트 타입(`unsigned int`)이었다 - 이번엔 하드웨어 REDTBL
  물리 목적지 필드가 8비트라는 사실을 **조용히 자르지 않고 명시적으로
  실패(false 반환)**하도록 바꿨다. 0xFF를 넘는 목적지가 실제로
  필요해지면(대규모 SMP) MSI 등 32비트 목적지를 지원하는 다른 전달
  경로를 써야 한다는 뜻을 코드가 스스로 드러낸다.
- API가 `setRedirection(gsi, vector, destApicId, polarity,
  triggerMode)`(GSI 직접 지정 + 극성/트리거 명시)과
  `setRedirectionForIsaIrq(isaIrq, vector, destApicId)`(ISA IRQ 편의
  래퍼, 내부에서 resolveIsaIrq 호출)로 나뉘었다 - HPET의 임의 GSI
  라우팅(PL-E68894CD 재작업)과 레거시 ISA IRQ 라우팅(키보드, PIT)
  둘 다 자연스럽게 지원한다.
- IOAPICVER 레지스터에서 최대 리다이렉션 엔트리 수를 읽어 범위 밖
  GSI 요청도 명시적으로 거부하도록 함께 추가(원래 없던 방어 로직).
- **실측(2026-09-14, QEMU 8.2.2)**: 키보드 IRQ1(sendkey 실주입, 이전
  검증 그대로)이 ISO 인지 경로를 거쳐도 여전히 정상 동작함을
  재확인. PIT IRQ0 레거시 폴백(PL-E68894CD 재작업의 `Timer::
  enableLegacyPitIrq`가 이 경로를 그대로 씀)도 HPET+LAPIC 타이머
  둘 다 끈 채로 PIT IRQ0 단독으로 틱이 정상 증가함을 확인해, ISA
  IRQ 해석 경로 전체가 실제로 올바르게 동작함을 검증했다.

## 이번엔 안 한 것 (후속 과제로 남김)

- 없음 - 원래 이 절에 있던 두 항목(ISO 파싱, 8비트 목적지 한계)은
  위 재작업으로 전부 반영됐다. (아래 재작업에서 "IOAPIC이 하나뿐"이라는
  가정도 제거함.)

## 미결 사항

- 없음(원래 PL에 있던 "PIT 등 레거시 IRQ도 IOAPIC으로 라우팅할지"는
  QU-FC9D80FF 답변으로 확정됨 - PL-E68894CD/timer.cpp의
  `enableLegacyPitIrq`/`disableLegacyPitIrq` 참고).

## 재작업 - 다중 IOAPIC 지원 (2026-09-14, 설계자 메시지)

설계자 지시(CNW 메시지, 2026-09-14 - "IOAPIC는 한개가 아니라 여러개가
존재할 수도 있는데, 이 부분에 대해서도 고려해야해"): 서버급 멀티소켓/
멀티칩셋 구성은 IOAPIC이 여러 개고, 각자 서로 다른 GSI 구간을
담당한다(ACPI MADT IO APIC 엔트리의 `globalSystemInterruptBase`). 지금까지
는 첫 번째 IOAPIC 엔트리만 저장해 "IOAPIC은 시스템에 하나"라고 암묵적으로
가정하고 있었다 - 이를 제거했다.

- **Acpi 쪽**: MADT 파싱이 IO APIC 엔트리(타입1)를 만날 때마다
  (`ioApicId`/`ioApicAddress`/`globalSystemInterruptBase`) 최대
  `kAcpiMaxIoApics`(8, v1 임시 상한)개까지 배열에 저장하도록 확장.
  기존 단일값 접근자 `Acpi::ioApicAddress()`를 제거하고
  `ioApicCount()`/`ioApicId(index)`/`ioApicAddress(index)`/
  `ioApicGsiBase(index)`로 교체.
- **IoApic 쪽**: `init()`이 발견된 IOAPIC 인스턴스 전부를 각자의
  가상주소 페이지(`kIoApicVirtBase`부터 인스턴스당 4KiB씩 순차 배치 -
  MMCONFIG 영역 시작 전까지 여유 공간 확인해 둠)에 매핑하고, 각각의
  IOAPICVER에서 최대 리다이렉션 엔트리 수를 읽어 `{virtAddr, gsiBase,
  maxRedirectionEntry}`로 보관한다. `setRedirection`/`mask`/`unmask`는
  더 이상 "GSI == 유일한 IOAPIC의 로컬 인덱스"로 가정하지 않고, GSI
  값으로 그 GSI를 담당하는 인스턴스를 먼저 찾은 뒤(`gsiBase <= gsi <
  gsiBase+maxRedirectionEntry+1`) 그 인스턴스 안에서의 지역 인덱스
  (`gsi - gsiBase`)로 REDTBL을 접근한다. 담당 인스턴스를 못 찾으면
  `setRedirection`은 false, `mask`/`unmask`는 조용히 무시(둘 다 이미
  검증된 GSI만 넘어오는 게 일반적이라 안전한 기본값).
- 공개 API 변경은 전부 **호출부 무관**하다 - `setRedirection(gsi,...)`/
  `setRedirectionForIsaIrq`/`mask`/`unmask` 시그니처는 그대로라 HPET/
  Timer 레거시 PIT/키보드 라우팅 등 기존 호출부는 코드 변경 없이
  그대로 동작한다.
- **실측(2026-09-14, QEMU 8.2.2)**: 기본 i440fx/`-machine q35` +
  `-smp 4` 둘 다에서 `ioapic_count=1`(QEMU는 IOAPIC을 하나만
  에뮬레이트)로 정상 인식하고, HPET/PIT/키보드/PCI/MSI/SMP AP 기동
  전부 이전과 동일하게 회귀 없이 동작함을 재확인했다. **진짜 다중
  IOAPIC(gsiBase가 0이 아닌 두 번째 인스턴스가 실제로 GSI를 담당하는
  경로)은 QEMU가 단일 IOAPIC만 에뮬레이트해 실측 검증할 방법이 없었다**
  - 인스턴스 탐색 로직 자체는 코드 리뷰 수준으로 스펙(ACPI MADT IO
    APIC 엔트리, globalSystemInterruptBase)을 그대로 따랐고 단일
    인스턴스(gsiBase=0) 케이스에서 기존 동작과 100% 동일함을 실측으로
    증명했지만, 두 번째 이상의 인스턴스가 실제로 GSI를 담당하는
    코드 경로 자체는 미검증 상태로 남는다 - 실제 멀티-IOAPIC
    하드웨어/하이퍼바이저(또는 그런 토폴로지를 흉내내는 ACPI 테이블)를
    확보하면 재검증이 필요하다(관계도에 기록).
