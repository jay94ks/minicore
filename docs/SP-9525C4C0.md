# Push/Pull 로드밸런싱 — 설계 제안

설계자 지시(2026-09-16, 메시지) - "[SP-83A07867] 여기에 범위 밖으로
표기된 것들도 설계 시작해." SP-83A07867 §7이 명시적으로 범위 밖(별도
설계)으로 남겨 둔 두 항목 중 "코어 간 Task 이관(load balancing,
PN-7679813D)"을 다룬다 - "target의 마지막 실행 코어 == 지금 이
코어"라는 SP-83A07867의 v1 전제를 이 설계가 실제로 깨는 첫 사례이므로,
그 문서가 이미 확립한 CR3/FPU/RSP0 동기화 불변조건(§3.2 체크리스트)이
코어 이관 앞에서도 그대로 성립하는지를 항목별로 재검증하는 것이
이 문서의 핵심 작업이다.

## 0. 범위 - `kernel::Task`만, `AsyncTask`는 명시적으로 제외

PN-7679813D 원문 그대로 **`kernel::Task`(일반 스케줄링 단위, UserThread
포함)만** 이 설계의 대상이다. `AsyncTask`는 PN-40E976F2가 이번에
확정한 소유권 모델("AsyncTask의 실제 소유자는 UserThread가 아니라
그것을 실행하는 리액터(커널 Task)")과 정면으로 배치된다 - 리액터
자신이 이관 대상이 될 수는 있지만(그러면 그 위에서 도는 모든 AsyncTask
가 통째로 따라간다, 아래 §4), **개별 AsyncTask 하나만 다른 코어의
리액터로 옮기는 것은 이 문서의 범위 밖**이다(그러려면 AsyncTask의
전용 스택 자체를 다른 코어로 옮기고 `gCurrentAsyncTask`/
`gReactorSavedRsp` 등 코어별 전역 배열 전제를 재설계해야 하는 별도
과제 - Channel IPC(PL-C8648D4D)가 이미 남긴 "완료 시점의 그 코어에서만
대기자를 깨움" 경고가 정확히 이 재설계를 가리킨다).

## 1. 이관 대상 판별 - "Ready 큐에 대기 중인 Task만" (핵심 단순화)

로드밸런싱이 손댈 수 있는 것은 **`Scheduler::pickNext()`가 아직
뽑지 않은, `gImmediateQueues`/`gRtQueues`/`gNormalQueues`에 대기
중인 Task뿐**이다 - 이미 다른 코어에서 `Running`이거나 `Blocked`
(파킹)인 Task는 절대 건드리지 않는다. 이 제약 하나가 아래 §3의
정합성 문제 대부분을 원천 차단한다:

- **`Blocked` Task는애초에 어느 큐에도 없다** - `parkCurrent()`는
  큐에 넣지 않고 그냥 `gCurrentTask[coreIndex]`에서 지우기만 한다
  (scheduler.cpp). 따라서 `AsyncTask::waitingTask`가 가리키는,
  "어떤 AsyncTask의 완료를 기다리며 파킹된" Task는 **정의상 Ready
  큐에 나타날 수 없다** - Channel IPC/Syscall wait의 "완료 시점의
  그 코어에서만 깨움"(`Scheduler::scheduleImmediate(coreIndex,
  waitingTask)`, coreIndex는 그 AsyncTask를 실행한 리액터의 코어)
  전제가 **이 v1 로드밸런싱 범위에서는 절대 깨지지 않는다** - 이관
  대상 자체가 될 수 없으므로. PL-C8648D4D가 남긴 경고는 여전히
  유효한 경고지만, "AsyncTask 완료 대기 중인 Task를 이관하는" 미래
  확장(§0에서 제외한 AsyncTask 자체의 코어 간 이관과 함께 묶이는
  문제)에만 해당하고 이번 v1 범위에는 해당하지 않는다.
- **`Running` Task는 대상이 아니다** - 실행 중인 Task를 강제로
  다른 코어로 옮기려면 그 자리에서 즉시 컨텍스트 스위치를 유발해야
  하는데(선점형 이관), 이는 지금 스케줄러가 갖고 있지 않은 훨씬
  무거운 메커니즘이다 - v1은 다루지 않는다(§6 열린 질문).

즉 로드밸런싱의 실질은 "Ready 큐 안에서 어느 코어 줄에 서 있을지"를
조정하는 것뿐이다 - 이미 존재하는 `TaskQueue`(scheduler.cpp)가
내부적으로 `Spinlock`으로 보호돼 있으므로(§13/`SpinlockGuard`,
이미 다른 코어의 `enqueue()`/`scheduleImmediate()`가 서로 다른
`coreIndex`의 큐를 건드리는 것도 이미 안전하게 지원한다는 뜻 -
**새 동시성 프리미티브가 전혀 필요 없다**), 다른 코어의 큐에 직접
`pushBack`/`popFront`해도 기존 락 규율만으로 안전하다.

## 2. Push - `enqueue()`에서 임계치 확인

```cpp
// scheduler.cpp, 기존 enqueue()에 삽입 (가칭)
void Scheduler::enqueue(uint32_t coreIndex, Task* task) {
    // ... 기존 inRunQueue cli 가드 그대로 ...

    // [신규] affinityMask가 전체 코어가 아니면(특정 코어 고정) 로드
    // 밸런싱 대상에서 완전히 제외 - PN-7679813D 원문 그대로.
    if (task->affinityMask != kTaskAffinityAllCores) {
        gNormalQueues[coreIndex].pushBack(task);  // 기존 경로 그대로
        return;
    }

    // [신규] Push - 이 코어 큐 길이가 임계치(최대 길이의 90%)를
    // 넘었으면 다른(가장 한가한) 코어로 대신 넣는다. 큐 길이 자체를
    // 매번 순회로 세면 비싸므로, TaskQueue에 원자적 카운터(§2.1)를
    // 추가해 O(1)로 조회한다.
    uint32_t targetCore = coreIndex;
    if (gNormalQueues[coreIndex].approxLength() > kPushThreshold) {
        targetCore = kFindLeastLoadedCore(coreIndex);  // §2.2
    }
    gNormalQueues[targetCore].pushBack(task);
    if (targetCore != coreIndex) {
        kWakeCoreIfIdle(targetCore);  // §4
    }
}
```

**`kPushThreshold`("최대 길이"의 90%) 정의 - [확정, 2026-09-16,
QU-9325BD40 답변]** 실제 코드 조사(`TaskQueue`는 연결리스트 기반이라
고정 용량 상한 필드 자체가 없음, PN-7679813D 구현 착수 중 발견) 후
확인을 구했다 - 설계자 답변: "설정가능한 최대/최소값 + 코어 수 대비
상대적 기준." 즉 순수 고정 상수도, 순수 상대적 비율도 아니라 **둘을
결합**한다:

```cpp
// scheduler.cpp(가칭) - 정확한 산식/상수명은 구현 시점 확정, 형태만 결정
constexpr uint32_t kMinQueueMaxLength = /* 설정 가능, 구현 시 확정 */;
constexpr uint32_t kMaxQueueMaxLength = /* 설정 가능, 구현 시 확정 */;

// 코어 수 대비 상대적 기준으로 산출한 뒤 [min, max] 범위로 clamp.
uint32_t kComputePushThreshold() {
    uint32_t relative = /* 예: 전체 대기 Task 수 / 코어 수 기반 산식 -
                            정확한 배수/가중치는 구현 시 실측 확정 */;
    return kClamp(relative, kMinQueueMaxLength, kMaxQueueMaxLength);
}
```

핵심은 "최대 길이"가 **고정된 하나의 매직 넘버가 아니라, 코어 수/
워크로드 규모에 따라 상대적으로 산출되면서도 설정 가능한 하한/상한
범위 안에 clamp되는 값**이라는 것 - 정확한 산식·상수값 자체는 이
문서가 확정하지 않는다(RM-23F4B687 §4 "추측성 숫자값은 실측 후
확정" 원칙 그대로) - 구현 세션이 실제 워크로드로 실측하며 확정한다.

### 2.1 큐 길이 - 근사 카운터 (정밀 동기화 불필요)

`TaskQueue`에 `AtomicU32 _approxLength`를 추가해 `pushBack`/
`popFront`마다 증감한다 - **정확한 값일 필요 없다**(로드밸런싱은
"대략 얼마나 밀렸는지"만 알면 충분, 정밀도가 필요한 스케줄링 결정이
아니다). `Spinlock` 임계구역 밖에서 원자적으로 갱신해도 무방 -
잠깐의 오차(±1~2)가 Push/Pull 판단을 한 틱 정도 늦추는 것뿐이라
정합성에 영향 없다.

### 2.2 `kFindLeastLoadedCore` - O(코어 수) 선형 스캔

```cpp
uint32_t kFindLeastLoadedCore(uint32_t excludeCore) {
    uint32_t best = excludeCore;
    uint32_t bestLen = UINT32_MAX;
    for (uint32_t i = 0; i < gCoreCount; ++i) {
        if (i == excludeCore) continue;
        uint32_t len = gNormalQueues[i].approxLength();
        if (len < bestLen) { bestLen = len; best = i; }
    }
    return best;
}
```

SP-0666DB3C §12가 이미 지적한 "`PerCpu<T>::get()`의 O(코어 수) 선형
스캔이 코어 수가 적을 땐 무시할 만하다"는 것과 정확히 같은 성격의
트레이드오프 - 코어 수가 매우 많아지면 실측 후 재검토(별도 DC
불필요, RM-23F4B687 §4 취지).

### 2.3 NUMA 노드 우선 이관 (확정, 2026-09-17, QU-759C9C1C 답변)

**설계자 답변: (A) 참고함 - 같은 NUMA 노드 안의 코어를 우선 대상으로
고른다.** `Task::numaNode`(PN-A74871F2, 그 Task가 생성된 코어의
NUMA 노드를 기록)가 먼저 반영돼야 이 절이 실제로 동작할 수 있다 -
그 전까지는 이 절 자체가 no-op(모든 Task가 같은 값)이어도 안전
하도록 아래처럼 "우선 후보가 없으면 기존 전체 스캔으로 자연히
폴백"하는 형태로 짠다(별도 feature flag 불필요):

```cpp
// §2.2 kFindLeastLoadedCore(Push)의 NUMA 인지 버전 - 대상 Task의
// numaNode와 같은 코어들만 먼저 스캔하고, 그중 하나도 없거나(코어가
// 그 노드에 없는 경우) 전부 excludeCore 자신뿐이면 기존 전체 스캔
// (§2.2 원안)으로 폴백한다 - "우선순위 두 단계"이지 "필터로 배제"가
// 아니다(설계자 단점 우려 - 유휴 코어를 아예 못 쓰게 되는 상황을
// 피하기 위해 두 번째 스캔이 전체 코어를 다시 본다).
uint32_t kFindLeastLoadedCoreNumaAware(uint32_t excludeCore, uint32_t taskNumaNode) {
    uint32_t best = excludeCore;
    uint32_t bestLen = UINT32_MAX;
    bool foundSameNode = false;
    for (uint32_t i = 0; i < gCoreCount; ++i) {
        if (i == excludeCore) continue;
        if (Acpi::cpuNumaNode(i) != taskNumaNode) continue;  // 1단계: 같은 노드만
        uint32_t len = gNormalQueues[i].approxLength();
        if (len < bestLen) { bestLen = len; best = i; foundSameNode = true; }
    }
    if (foundSameNode) return best;
    return kFindLeastLoadedCore(excludeCore);  // 2단계: 원안 그대로(전체 스캔)
}
```

`kFindMostLoadedCore`(§3, Pull)도 대칭적으로 확장한다 - Pull은
"자기 자신(idle 코어)이 속한 노드 안에서 가장 바쁜 코어"를 먼저
찾고, 없으면 원안대로 전체 코어에서 찾는다(훔쳐오는 Task 자신의
`numaNode`가 아니라 **훔쳐오는 쪽 코어의 노드**를 기준으로 삼는다 -
Pull의 목적은 "이 코어가 노는 걸 막는 것"이라 이관될 Task의 원래
노드보다 지금 훔쳐가는 코어의 지역성이 우선이라는 점이 Push와의
비대칭 - Push는 "이 Task를 어디로 보낼까"라 Task 자신의 노드가
기준, Pull은 "내가 뭘 가져올까"라 자기 코어의 노드가 기준).

**적용 지점**: §2의 `kFindLeastLoadedCore(coreIndex)` 호출을
`kFindLeastLoadedCoreNumaAware(coreIndex, task->numaNode)`로,
§3의 `kFindMostLoadedCore(coreIndex)` 호출을 대칭적인 NUMA 인지
버전으로 교체한다(정확한 함수명/시그니처는 착수 시 확정,
RM-23F4B687 §4). SRAT 없는 환경(`Acpi::numaNodeCount()==1`)에서는
모든 코어가 노드 0이라 1단계 스캔이 사실상 원안과 동일한 전체
스캔이 되므로 별도 분기 없이도 안전하다.

## 3. Pull - `runLoop()`의 idle 직전 스캔

```cpp
// scheduler.cpp, Scheduler::runLoop() 수정 (가칭)
Task* next = pickNext(coreIndex);  // 기존 - 자기 큐 먼저 확인
if (!next) {
    // [신규] Pull - hlt 전에 가장 바쁜 다른 코어에서 하나 훔쳐온다.
    // "~100ms 이상 idle 지속"(원문 제안)은 이 v1에서는 채택하지
    // 않는다 - 매 idle 진입마다 즉시 시도해도 비용이 낮다(§2.2와
    // 같은 O(코어 수) 스캔 한 번 + 실패하면 그냥 기존 hlt로 진행,
    // 타이머 기반 지연을 추가로 두면 오히려 불필요한 상태(마지막
    // steal 시각)를 코어마다 유지해야 해 복잡도만 는다). 실측으로
    // "너무 공격적으로 훔쳐서 오히려 캐시 지역성이 나빠진다"는
    // 신호가 나오면 그때 지연을 추가(RM-23F4B687 §4 취지).
    uint32_t victimCore = kFindMostLoadedCore(coreIndex);
    if (victimCore != coreIndex) {
        next = gNormalQueues[victimCore].popFront();
    }
}
if (!next) {
    asm volatile("sti; hlt");
    continue;
}
// ... 기존 dispatch 로직 그대로(kSyncRsp0ForDispatch/kContextSwitch) ...
```

`popFront()`가 `nullptr`을 반환할 수 있다(스캔 시점과 실제 pop
시점 사이에 다른 코어가 먼저 가져갔을 수 있음 - `approxLength()`가
근사치이므로 당연히 있을 수 있는 경쟁) - 이 경우 그냥 `next ==
nullptr`로 남아 기존 `hlt` 경로로 자연스럽게 빠진다(추가 처리
불필요, 다음 틱/다음 idle 진입에서 다시 시도).

## 4. 코어 깨우기 - 기존 `Lapic::sendFixedIpi` 재사용

**새 IPI 메커니즘을 만들지 않는다** - `minicore/kernel/tlb_shootdown.cpp`
가 이미 정확히 같은 문제("다른 코어가 지금 `hlt`로 잠들어 있을 수도
있는데, 그 코어에 뭔가 즉시 알려야 한다")를 풀고 있고, 그 해법
(전용 벡터 + `Lapic::sendFixedIpi(destApicId, vector)` + ISR은
`Lapic::sendEoi()`만 하고 반환)을 그대로 재사용한다:

```cpp
// scheduler.cpp 또는 새 파일, tlb_shootdown.cpp와 동일한 패턴
constexpr uint8_t kLoadBalanceWakeVector = 0xE1;  // RM-28225668에 배정

void kWakeCoreIfIdle(uint32_t coreIndex) {
    // gCurrentTask[coreIndex] == nullptr이면 그 코어가 idle(hlt)
    // 상태일 가능성이 높다 - 정확한 판정은 아니지만(idle 진입 직전/
    // 직후의 좁은 창) 안전한 근사다: 이미 실행 중인 코어에 괜히
    // IPI를 보내도 그냥 무해한 인터럽트 하나 처리하고 마는 것뿐이라
    // (기존 스케줄러 틱과 동일하게 EOI 후 즉시 반환), false positive
    // 비용이 낮다.
    if (gCurrentTask[coreIndex] == nullptr) {
        Lapic::sendFixedIpi(Acpi::cpuApicId(coreIndex), kLoadBalanceWakeVector);
    }
}

// idt.cpp에 벡터 등록 - 핸들러는 EOI만 하면 된다. hlt 자체가
// "다음 인터럽트가 오면 실행 재개"이므로, 벡터가 뭘 나르는지는
// 중요하지 않다 - runLoop()의 for(;;) 루프가 hlt에서 깨어나자마자
// 다시 pickNext()/Pull 스캔을 돈다(§3).
```

## 5. 기존 SP-83A07867 불변조건 재검증 - 코어 이관 앞에서도 성립하는가

SP-83A07867 §3.2가 확립한 "디스패치 도착 지점" 훅(`onTick()`,
`kSyncCr3OnTaskStart`, `yieldCurrent()`/`parkCurrent()` 재개) 각각을
"이 Task가 방금 다른 코어로 이관돼 왔을 수도 있다"는 전제로 재검증한다:

### 5.1 CR3 (`kSyncCr3`) - **변경 불필요, 이미 안전**

`kSyncCr3(Task* task)`는 `task->userPml4Phys`(Task 자신이 들고
있는 값, 코어와 무관)와 `task->isUserLevel`만 본다 - **어느 코어가
호출하든 완전히 동일하게 동작한다**. 코어 이관은 "이 Task를 어느
코어의 `runLoop()`가 `pickNext()`로 뽑아 `kContextSwitch`하는가"만
바꿀 뿐, `kSyncCr3`가 참조하는 값 자체는 전혀 코어에 묶여 있지
않다 - §3.2의 세 훅이 새로 이관된 코어에서 호출돼도 그대로 올바른
CR3를 설정한다.

### 5.2 TSS.RSP0 (`kSyncRsp0ForDispatch`) - **변경 불필요, 이미 안전**

같은 이유 - `task->kernelStackTop`도 Task 소유 메모리(물리 프레임은
`Task::init()`이 할당해 그 Task에 귀속, 코어에 귀속되지 않음)를
가리키는 값이라 어느 코어의 TSS에 적어 넣든 그대로 유효하다.

### 5.3 CR0.TS/FPU (`kSyncFpu`) - **[해소, PN-F55FB154] Push/Pull 양쪽 다 구현 완료**

`gFpuOwner[coreIndex]`는 **코어별** 전역 배열이다 - "이 코어의
하드웨어 FPU 레지스터가 지금 누구 것을 담고 있는가"를 추적한다.
Task가 코어 A에서 FPU를 쓰다가(즉 `gFpuOwner[A] == task`인 상태)
아직 아무도 그 소유권을 뺏지 않은 채로(코어 A에서 그 이후 다른
Task가 FPU를 쓴 적이 없어 FXSAVE가 한 번도 안 일어난 채로) 코어
B로 이관되면, **`task->fpuState`에는 낡은 값만 남고 코어 A의
실제 하드웨어 레지스터에 있는 최신 값은 어디에도 저장되지 않은
채로 유실된다** - 코어 B에서 이 Task가 재개돼 FPU를 다시 쓰면
`fpuInitialized == true`이므로 `FXRSTOR`로 그 낡은 `fpuState`를
복원해 버려, 마지막으로 실제 계산한 FPU 결과가 조용히 사라지는
**진짜 정합성 버그**다(SP-83A07867/PN-F258698E 문서 어디에도
"코어 간 이관"이 없었으므로 이 경우가 존재하지 않았을 뿐, 로드밸런싱
도입으로 처음 발현되는 공백).

**해법 - 이관 결정 시점에 강제 소유권 반납**:

```cpp
// 로드밸런싱이 Task를 다른 코어 큐로 옮기기 직전(§2 Push/§3 Pull
// 둘 다) 반드시 호출 - 이 Task가 원래 코어의 현재 FPU 소유자라면
// 그 자리에서 강제로 FXSAVE해 fpuState를 최신화하고 소유권을 비운다.
void kEvictFpuBeforeMigration(Task* task, uint32_t fromCore) {
    if (gFpuOwner[fromCore] == task) {
        asm volatile("fxsave (%0)" : : "r"(task->fpuState) : "memory");
        gFpuOwner[fromCore] = nullptr;
    }
}
```

**왜 안전한가**: 이관 대상은 §1에 따라 항상 Ready 큐에 대기 중인
Task, 즉 **지금 그 코어에서 `Running`이 아니다** - 하드웨어 FPU
레지스터를 건드릴 코드가 지금 이 순간 실행되고 있지 않으므로(그
Task 자신이든 다른 Task든, `Running` Task의 FPU 레지스터를
`gFpuOwner[coreIndex] == currentTask`인 동안 다른 코어가 손대는
것도 아니다 - `fxsave`가 읽는 것은 **그 코어의** 현재 하드웨어
레지스터 값인데, 이관 대상 Task는 이미 그 하드웨어의 소유자로
남아 있는(아직 아무도 안 뺏은) 상태이므로 그 값이 정확히 이 Task의
값이다) 이 시점에 `fxsave`해도 경쟁이 없다. 단, **이 함수는 반드시
`fromCore`가 실행 중인 코어 자신이 아니라 로드밸런싱을 수행하는
아무 코어에서나 호출될 수 있다는 점에 주의** - `fxsave`는 항상
"이 명령을 실행하는 코어의" 하드웨어 레지스터를 읽으므로, Push
(다른 코어가 이 코어의 큐를 보고 결정)의 경우 **이관을 결정한
코어가 아니라 원래 코어(`fromCore`) 자신이 이 `fxsave`를 실행해야
한다** - 즉 Push/Pull 둘 다 실제 이관(대기열 이동) 자체는 원격
코어의 큐에 안전하게 `pushBack`할 수 있지만, `kEvictFpuBeforeMigration`
호출만은 반드시 **IPI로 `fromCore`에게 위임**하거나, **Pull은
자기 자신이 훔쳐오는 것이므로 이 문제가 아예 없다**(Pull에서는
`fromCore`가 곧 "훔쳐가는 대상 큐를 가진 코어"이고 실행 주체는
훔치는 코어이므로, 사실 Pull도 evict를 원격에서 하는 셈 - **결론:
Push든 Pull이든, evict는 항상 `fromCore` 자신에게 위임해야 하는
비동기 스텝**이다).

**실용적 절충안(v1 제안)**: 매 이관마다 IPI 왕복을 강제하면
로드밸런싱 자체의 비용이 커진다 - 대신 **`fpuInitialized == false`
(이 Task가 FPU를 한 번도 안 쓴 것) 또는 `gFpuOwner[fromCore] !=
task`(이미 다른 누군가에게 소유권을 뺏겨 `fpuState`가 최신인 것이
보장된) 경우에만 즉시 이관을 허용하고, 그렇지 않으면(정말 이
Task가 그 코어의 살아있는 FPU 소유자인 경우) **이번 틱은 이관을
보류하고 다음 기회로 미룬다**(단순 스킵 - Push는 이번엔 그냥 원래
큐에 넣고, Pull은 다음 후보를 본다) - 대부분의 워크로드에서 이
경우는 드물 것으로 예상되므로(FPU를 실제로 쓰는 Task 비율 자체가
낮음, kernel 코드는 `-mgeneral-regs-only`라 SSE조차 안 씀,
PN-F258698E) 실측 전에는 이 회피만으로 충분하다고 제안한다 - IPI
기반 강제 evict는 실측으로 이 스킵이 로드밸런싱 효과를 유의미하게
떨어뜨리는 것으로 드러나면 후속 최적화로 추가.

### 5.4 결론 - CR3/RSP0는 무료로 안전, FPU만 실제 설계 추가가 필요

이 §5 전체가 이번 설계의 핵심 기여다 - SP-83A07867이 "v1은 코어
이관이 없다"는 전제 위에 세운 세 훅 중 둘(CR3/RSP0)은 우연이 아니라
**설계상 처음부터 코어 독립적**이었음을 확인했고(Task 소유 데이터만
참조), 나머지 하나(FPU)만 코어 소유 자원(하드웨어 레지스터 그 자체)
을 다루기 때문에 로드밸런싱 도입 시 실제로 새 코드가 필요하다는
것을 밝혔다.

## [발견 및 해소, 2026-09-17, RM-F2DAFF66 설계공백 검수 → PN-F55FB154 완료] Push 경로에 §5.3 FPU 가드 누락

실제 구현(`Scheduler::enqueue()`, scheduler.cpp)을 확인한 결과, Pull(`runLoop()`)은 `kCanMigrateFpuSafely()`를 정확히 호출해 §5.3 그대로 구현됐으나, **Push(`enqueue()`)는 이 가드 없이 곧바로 다른 코어 큐로 밀어 넣는다** - §5.3이 "진짜 정합성 버그"라고 지목한 시나리오가 Push 경로에서 여전히 열려 있었다.

**해소(`PN-F55FB154` 완료)**: `kCanMigrateFpuSafely(task, fromCore)`를 Push에 그대로 재사용할 수 없었다 - `Scheduler::enqueue(coreIndex, task)`의 `coreIndex` 인자는 실제 호출부 5곳(`debug_session.cpp`/`kmain.cpp`×2/`process.cpp`/`resource_group.cpp`) 전수 조사 결과 전부 `Scheduler::currentCoreIndex()`(Task를 지금 깨우는 waker 자신의 코어)일 뿐, "Task가 마지막으로 FPU를 쓴 코어"라는 보장이 전혀 없었다(Pull의 `victimCore`는 반대로 `popFront()`한 바로 그 큐라 의미상 정확함). 그래서 `gFpuOwner[]` 전체를 스캔해 task의 실제 살아있는 FPU 소유 코어를 찾는 `kFindFpuOwnerCore(const Task*)`를 새로 추가하고, Push 이관 후보 코어가 그 소유 코어와 다르면 이번 이관을 스킵(Pull과 동일한 보류 정책)하도록 구현했다. commit `f753d19`.
