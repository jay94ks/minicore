# Minicore 멀티스레드 유저 프로세스 지원 — 설계 제안

## 배경

`PN-2E4E9D79`("멀티스레드 유저 프로세스 지원") 비판적 재검토 중
발견(2026-09-16) - `SP-9A6D579F`(프로세스 디버깅)가 요구받은 "멀티
스레드 디버깅"은 그보다 먼저 "한 프로세스가 여러 스레드를 가질 수
있다"는 훨씬 근본적인 인프라를 요구하는데, 이 코드베이스엔 그게
없었다(`Process::mainThread`가 단일 `UserThread*` 필드 하나뿐, 클래스
주석 자체가 "v1: 프로세스당 스레드 하나"라고 명시). 설계자가
2026-09-18 opinion(`PN-2E4E9D79` 대상 2건 + 이 문서 대상 1건 추가
정정)으로 구체적인 방향을 줘 이 문서로 정식화한다.

## 1. 현재 구조 조사 (설계자 지시 - "Process와 UserThread가 사실상
동일한 개념으로 취급되고 있음, 조사 후 재설계")

`process.h`/`task.h`를 직접 읽어 확인한 결과:

- `Process`와 `UserThread`(`Task` 상속)는 **코드상으로는 이미 분리된
  별개 클래스**다 - `Process`가 주소공간(`pml4Phys`, `addressSpace`)을
  소유하고, `UserThread`가 실제 스케줄링 단위(`Task::isUserLevel=true`,
  ring3 진입점/유저 스택 등)라는 구분 자체는 존재한다.
- 하지만 `Process`가 정확히 스레드 **하나**만 가리킬 수 있게 고정돼
  있어(`UserThread* mainThread`, 배열도 리스트도 아닌 단일 포인터)
  실질적으로 1:1 대응이다 - 설계자가 지적한 "사실상 동일한 개념"이
  바로 이 지점이다.
- **결정적 증거**: 스레드 종료 상태(`isZombie`/`exitCode`)가 지금
  `UserThread`가 아니라 **`Process` 자신**의 필드로 있다 - "그
  하나뿐인 스레드가 어떻게 끝났는지"를 프로세스 자신이 대신 들고
  있는 것. `Process::parent`/`children`(프로세스 트리, `wait()`가
  좀비를 찾는 그 트리)도 이 필드들을 프로세스 단위로 소비한다
  (`SP-6BEAE0C1` §6).
- 반대로 `pml4Phys`/`addressSpace`(VMA 장부)/`fileDescriptors`/
  `pendingSignals`/`group`(ResourceGroup)/`debugSession`은 이미
  **프로세스 단위로 존재하는 게 맞는** 필드들이다 - 여러 스레드가
  생겨도 이들은 프로세스당 하나씩 공유돼야 한다(POSIX 스레드 모델과
  동일한 경계).

**결론**: 재설계는 "전부 다시 짠다"가 아니라 "스레드 개수에 따라
스케일해야 하는 것(종료 상태)과 프로세스에 고정으로 남아야 하는 것
(주소공간/자원)을 정확히 가른다"에 가깝다 - 아래 §2가 그 경계를
확정한다.

## 2. 재설계 — `Process` : `UserThread` = 1 : N

### 2.1 자료구조

```cpp
// process.h
// [정정, 2026-09-18, 설계자 opinion] "16비트 정수로, 프로세스 내에서만
// 유일" - 최초 uint32_t 초안을 축소.
using ThreadId = uint16_t;
constexpr ThreadId kInvalidThreadId = 0xFFFFu;

class Process : public EnableSharedFromThis<Process> {
public:
    // 기존 mainThread(UserThread*) 단일 필드를 대체 - 이 프로세스가
    // 소유한 모든 스레드. [정정, 2026-09-18, 설계자 opinion] "한
    // 노드당 16개 정도" - children/openBridges(청크 8)보다 큰 값을
    // 명시적으로 받음(스레드는 다른 프로세스 자원보다 더 많이 생길
    // 여지가 크다는 취지로 이해).
    static constexpr uint32_t kMaxThreadsChunkCapacity = 16;
    ChunkedList<SharedPtr<UserThread>, kMaxThreadsChunkCapacity> threads;
    // ...
};

// [신규, 2026-09-18, 설계자 opinion] "최대 갯수는 커널 전역 설정으로
// 제어할 수 있어야하고, 이를 초과하면 단순히 CreateThread를
// 실패시키면 된다" - 프로세스 하나가 무한정 스레드를 만들어 커널
// 전역 자원(슬랩 등)을 고갈시키는 것을 막는 단일 전역 상한. 정확한
// 값은 순수 구현 세부(실측 후 조정 가능, RM-23F4B687 §4) - 임시로
// 프로세스당 스레드 상한이라는 상수 이름과 자리만 잡아 둔다.
constexpr uint32_t kMaxThreadsPerProcess = 256;  // 실측 후 조정 가능
```

`UserThread`(`Task` 상속)에 새로 옮겨오는 필드:

```cpp
// task.h 또는 process.h의 UserThread 정의부
class UserThread : public Task {
public:
    ThreadId threadId = kInvalidThreadId;   // 이 프로세스 안에서 발급
    bool isZombie = false;                  // Process::isZombie를
                                             // 여기로 이전(§3)
    int32_t exitCode = 0;                   // Process::exitCode를
                                             // 여기로 이전(§3)
    bool detached = false;                  // §3의 Detached 플래그
    // [신규, 2026-09-18, 설계자 opinion 반영 - §3.1] 이 스레드가
    // 좀비가 되는 순간 즉시 깨워야 할, 지금 이 스레드를 Join() 중인
    // AsyncTask(있다면 단 하나, v1은 다중 joiner 미지원 - §3.1 참고).
    WeakPtr<AsyncTask> joinerAsyncTask;
    // ...
};
```

### 2.2 CreateThread syscall (신규)

```cpp
struct CreateThreadArgs {
    uint64_t entry = 0;       // 유저 포인터 - 새 스레드의 시작 함수
    uint64_t arg = 0;         // entry에 그대로 전달되는 1개 인자
    uint64_t stackSize = 0;   // 0이면 기존 execImage()와 동일한 기본값
    // out
    ThreadId threadId = kInvalidThreadId;
    // [갱신, 2026-09-18] kMaxThreadsPerProcess 초과 시 TooManyThreads
    CreateThreadError error = CreateThreadError::None;
};
```

`SpawnProcess`(새 프로세스+새 주소공간)와는 완전히 다른 축이다 -
`CreateThread`는 **호출자와 같은 프로세스 안에** 스레드를 추가한다.
새 `UserThread`가 호출자의 `pml4Phys`를 그대로 공유(주소공간 필드
자체가 이미 `Process` 레벨이라 구조적으로 저절로 공유됨) - 스택만
새로 확보해 스레드별로 분리한다(`registerFixedRegion`으로 장부
등록, 기존 `execImage()`의 스택 확보 패턴 재사용).

## 3. 스레드 종료 정책 (설계자 확정, 2026-09-18)

> "종료/정리 정책: 한 쓰레드가 죽었을 때, 발생되는 예외가 처리되지
> 못했을 때 프로세스 전체를 죽임. 예외가 처리되었거나 정상적으로
> 종료된 경우(Thread return code = 0) 그 쓰레드만 좀비 상태가
> 되었다가, 그걸 관찰하는 같은 프로세스 내 쓰레드가 Join할 경우 그
> 쓰레드를 정리. 단, Detached라는 내부 플래그가 있어서, 이 플래그가
> 설정된 경우, 좀비 상태를 거치지 않고 즉시 정리."

이를 세 갈래로 구현한다 - 전부 **기존 `Process` 레벨 좀비/`wait()`
패턴(`SP-6BEAE0C1` §6)과 정확히 같은 모양을 스레드 레벨로 복제**한
것이라 새 개념이 아니다(정상종료→좀비→회수 / 강제종료→즉시 처리
라는 뼈대는 이미 이 프로젝트가 프로세스 단위로 검증해 둔 패턴):

1. **미처리 예외(unhandled exception)**: 지금 프로세스 전체를 죽이는
   기존 강제종료 경로(예: 미처리 유저 폴트 → 그 프로세스
   `SelfTerminate` 강제, §2-B/`Process::FaultInfo`)를 그대로 쓴다 -
   달라지는 건 트리거 조건뿐: 지금은 "이 프로세스의 유일한 스레드가
   예외를 냈다"였지만, 앞으로는 "이 프로세스의 **어느** 스레드가
   미처리 예외를 냈다"로 넓어진다 - 어느 스레드든 상관없이 프로세스
   전체(모든 스레드)가 함께 종료된다.
2. **정상 종료 — [정정, 2026-09-18, 설계자 opinion] 자연 반환에
   기대지 않고 명시적 `SelfTerminateThread` syscall(신규)로 통일**:
   최초 초안은 `kTaskFallingToEnd`(자연 반환 경로)를 그대로
   재사용하려 했으나, 설계자가 "CreateThread한 스레드는
   SelfTerminateThread로 분리하는 것이 안전하다. 단순 반환시,
   유저랜드 C 런타임이 내부적으로 wrapping하여 SelfTerminateThread로
   syscall을 하도록 구현하라"고 지시했다 - 프로세스의 기존
   `SelfTerminate`(RM-48E1E610 그룹0 0번)와 대칭되는 스레드 전용
   syscall을 신설하고, `entry` 함수가 단순 `return`해도 유저랜드
   런타임의 스레드 진입 트램폴린(`_threadStart(entry, arg)`류, 신규
   - `execImage()`가 프로세스 진입점을 감싸는 것과 같은 역할)이
   그 반환값을 잡아 `SelfTerminateThread(returnValue)`를 명시적으로
   호출한다 - 유저 코드는 여전히 그냥 `return`만 하면 되고(POSIX
   `pthread_exit()` 자동 호출과 동일한 사용자 경험), 커널은
   `kTaskFallingToEnd`의 불안정한 자연 반환 경로(`PN-05162577`이
   문서화한, 순수 커널 Task가 자연 반환할 때 나는 #DB 패닉과 같은
   부류의 위험)를 스레드 종료 경로에서 아예 배제한다. `SelfTerminate`
   가 프로세스를, `SelfTerminateThread`가 스레드를 끝낸다는 대칭이
   명확해져 §4의 옛 열린 질문 2번("자연 종료 vs 명시적 syscall")도
   함께 해소된다.

   ```cpp
   // process.h 또는 signal.h - SelfTerminate(RM-48E1E610 0번)와 같은 묶음
   struct SelfTerminateThreadArgs {
       int32_t exitCode = 0;
   };
   ```

   핸들러는 호출한 `UserThread`를 `isZombie=true`로 표시하고
   `exitCode`를 기록한 뒤, `joinerAsyncTask.lock()`이 있으면 그
   자리에서 바로 완료 처리한다(§3.1) - 프로세스 나머지 스레드는
   영향 없이 계속 실행.
3. **`Detached` 플래그**(§2.1의 `UserThread::detached`): 세팅돼
   있으면 위 2번의 좀비 단계를 완전히 건너뛰고 `SelfTerminateThread`
   핸들러가 그 자리에서 즉시 스택/`UserThread` 슬랩 메모리까지
   반납한다 - join 대상이 될 수 없다는 뜻이므로 회수를 기다릴
   이유가 없다(pthread의 `PTHREAD_CREATE_DETACHED`와 동일한 의미).
   `joinerAsyncTask`가 이미 세팅돼 있는 상태에서 `Detach()`가
   호출되면(경쟁 상황) 에러로 거부한다(§3.1).

### 3.1 `Join`/`Detach` syscall (신규) — [전면 정정, 2026-09-18,
설계자 opinion] 논블로킹이 아니라 진짜 블로킹

> "여기서 Join은 유저 쓰레드들 입장에서 기술된 것이다. 유저 쓰레드
> 입장에선, 해당 좀비 쓰레드가 정리되기 전에 반환되면 안된다. 커널
> 내 메커니즘은 비동기라고 하더라도, 유저 입장에서는 완료 후
> 반환된 것이어야 한다. 즉, Syscall의 대기 토큰을 반환하여 같은
> 매커니즘으로 대기하는 식으로 구현하면 된다."

최초 초안은 `Wait`(RM-48E1E610 3번)의 "v1은 논블로킹" 선례를
그대로 베껴 `Join`도 논블로킹으로 가정했는데, 이건 **`Wait`가 왜
논블로킹인지를 착각한 것**이었다 - `Wait`가 논블로킹인 이유는 "이
프로젝트의 syscall 토큰 메커니즘(`Syscall::submit()`+`wait()`)
자체가 블로킹을 지원 못해서"가 아니라, `WaitHandler::onExec()`
자신이 "지금 이 순간 좀비가 있는지"만 확인하고 곧장 끝나도록
**짜여 있어서**다(코루틴이 대기 없이 즉시 반환) - `Syscall::wait()`
자체는 이미 이 프로젝트 전체가 쓰는 **진짜 블로킹** 프리미티브다
(`ChannelRead`/`ConnectChannel` 등 실제로 완료를 기다리는 모든
syscall이 이 메커니즘으로 이미 블로킹한다, `token=Syscall::submit()`
→ 완료 전까지 `Syscall::wait(token)`이 호출 Task를 파킹). `Join`은
그 표준 패턴을 그대로 쓰면 된다 - **`JoinHandler::onExec()`가
대상이 아직 좀비가 아니면 코루틴을 그 자리에서 정지(suspend)시켜
두고, 대상이 나중에 좀비가 되는 순간(§3의 `SelfTerminateThread`
핸들러가) 직접 깨워 완료시킨다.**

```cpp
struct JoinArgs {
    ThreadId targetThread = kInvalidThreadId;
    // out - 완료 시점엔 항상 대상이 이미 정리(reap)까지 끝난 상태.
    int32_t exitCode = 0;
    JoinError error = JoinError::None;  // 예: 대상이 detached/존재하지
                                         // 않음/이미 다른 스레드가 join 중
};

struct DetachArgs {
    ThreadId targetThread = kInvalidThreadId;
    // out
    DetachError error = DetachError::None;  // 이미 joinerAsyncTask가 있으면 에러
};
```

**메커니즘**:
1. `JoinHandler::onExec()`가 대상 `UserThread`를 찾는다 - 없거나
   `detached`면 즉시 `JoinError`로 완료(코루틴이 곧장 끝남, 블로킹
   없음).
2. 대상이 이미 `isZombie==true`(호출 시점에 이미 좀비)면 그 자리에서
   바로 회수(`exitCode` 복사, `Process::threads`에서 제거, 슬랩 반납)
   하고 완료 - 역시 블로킹 없음(빠른 경로).
3. 대상이 아직 살아 있으면, 이미 다른 `joinerAsyncTask`가 걸려
   있는지 확인(있으면 `JoinError` - v1은 대상 하나당 동시 joiner
   1명만 지원, `RM-23F4B687` §4 - 다중 joiner 대기열은 실사용처가
   생기면 후속). 없으면 `target->joinerAsyncTask`에 이 AsyncTask의
   약한 참조를 걸고 코루틴을 정지시킨다(co_await, 스스로 완료시키지
   않음) - 유저 쪽에서 보면 `Syscall::wait(token)`이 그동안 호출
   `UserThread`를 파킹해 둔다.
4. 나중에 대상이 `SelfTerminateThread`(정상 종료) 경로를 타면,
   그 핸들러가 `joinerAsyncTask.lock()`을 확인해 있으면 **그 자리에서
   직접**(3번에서 정지시켜 둔 `JoinHandler`의 코루틴을 대신 마저
   실행하는 형태로) 회수까지 끝내고 `AsyncReactor::submitCompletion()`
   으로 완료 처리한다 - 이 시점에 `Syscall::wait()`가 걸려 있던
   Join 호출자가 깨어난다. **정리(reap)가 이 완료 이전에 이미
   끝나 있으므로 "정리되기 전에 반환되면 안 된다"는 요구를 그대로
   만족한다.**

### 3.2 프로세스 자신의 좀비/`exitCode`와의 관계

기존 `Process::isZombie`/`exitCode`(부모-자식 **프로세스** 간
`wait()`용, §6)는 그대로 남는다 - 다만 의미가 "이 프로세스의 마지막
스레드가 어떻게 끝났는지"로 재정의된다: 프로세스의 **모든** 스레드가
종료(정상 종료 후 Join됨, 또는 detached라 즉시 정리됨, 또는 §3
항목1처럼 미처리 예외로 강제 종료됨)되는 순간 `Process` 자신도
좀비화된다 - POSIX가 프로세스의 마지막 스레드 종료 시 그 프로세스도
종료된 것으로 보는 것과 동일한 모델. `Process::exitCode`는 그
마지막 스레드의 `exitCode`(또는 강제종료 사유)를 그대로 물려받는다.
