# 실행 계획: 물리 메모리 관리 범위를 1GiB 한도 밖으로 확장

**[완료, 2026-09-14 - 계획 PN-1411E4A6]** QA-26450C3E 체크됨. 아래는 완료 기록으로 남긴다.

원래 `PageFrameAllocator`는 boot.S가 정적으로(어셈블리, 512개 2MiB
페이지 루프) identity map해 둔 저지대 1GiB 안에서만 관리했다.
Paging의 direct physical map은 이미 4GiB까지 1GiB 페이지로 매핑돼
있었으므로, 실제 병목은 "물리 프레임 포인터 변환에 identity map을
가정한다"는 점이었다 - 그런데 이 가정이 **두 곳**에 따로 있었다
(아래 2번째가 실제로 실측 중 걸린 회귀).

## 한 것

1. **`page_frame_allocator.cpp`의 free list 표현을 물리주소 기반으로
   전환**: `FreeBlock::next`가 가상 포인터가 아니라 다음 블록의
   물리주소(0=끝)를 담게 바꾸고, 실제로 읽고 쓸 때만 `kAsBlock()`
   (내부에서 `kPhysToVirt` 사용)로 변환한다. `Node::freeListHeads`도
   `FreeBlock*`가 아니라 물리주소 배열로 바꿨다.
2. **`kMappedLimit`을 1GiB에서 4GiB로**(Paging의 direct map 한도와
   일치).
3. **`paging.cpp`의 `kAsTable`도 같은 문제였다(실측으로 발견,
   2026-09-14)**: `Lapic::init()`이 자기 MMIO 페이지 테이블용으로
   `PageFrameAllocator::allocPage()`를 부르는데, 그 결과 프레임이
   이제 1GiB를 넘어설 수 있다 - `paging.cpp`가 여전히 물리주소를
   그대로 포인터로 캐스팅하고 있어서, QEMU를 `-m 2048`로 띄우자마자
   실제로 페이지폴트가 났다(CR2가 2GiB 근처 주소로 찍힘). `kAsTable`
   을 `kPhysToVirt` 경유로 바꾸고, `Paging::init()` 자신이 direct map
   생기기 **전에** 자기 PML4를 읽는 단 한 곳만 `kLowIdentityTable`
   (예전 방식, 주석으로 "여기 말고 다른 데서 쓰면 안 됨" 명시)로
   분리했다.
4. **검증**: QEMU `-m`(기본 128MB/2048/4096)으로 3단계 실측 -
   free_pages가 각각 정확히 스케일됨(128MB: 변화 없음(회귀 없음),
   2GiB: ~522K페이지, 4GiB: ~786K페이지 + 4GiB 초과분은 설계대로
   클리핑되어 안 잡힘), 어느 크기에서도 패닉/폴트 없음.

## 이번엔 안 한 것 (후속 과제로 남김)

- **direct map을 4GiB보다 늘리는 것** (계획 PN-4AA5425D): 지금 PDPT는 4개 엔트리만
  쓴다(512개까지, 즉 512GiB까지 정적으로 늘릴 여지가 있음) - 실제로
  더 큰 메모리를 다뤄야 할 때 `Paging::init()`의 반복 횟수만 늘리면
  된다(설계 변경 불필요, 순수 확장).
