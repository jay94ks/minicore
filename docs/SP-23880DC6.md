# 디바이스 이벤트/노드 계층(udev 유사 시스템) — 설계 제안

설계자 요청(대화, 2026-09-29) - "udev와 유사한 역할을 하는 시스템을
설계하자." 이어진 확인 질의에 대한 답변으로 스코프를 다음과 같이
확정했다: (1) devmgr이 관리하는 PnP 장치뿐 아니라 fs가 직접 소유한
AHCI/블록 장치까지 포함해 **모든 장치 클래스를 통일된 방식**으로
다룬다, (2) 이번 설계가 중점을 둘 udev의 역할은 **디바이스 노드
네임스페이스** + **핫플러그 이벤트 알림** + **이름 부여/우선순위
규칙** 세 가지다, (3) 실행 위치(devmgr 내부 통합 vs 별도 유저랜드
서비스 분리)는 설계자가 선호 없음으로 위임 - 아래 §2.3에서 근거와
함께 제안한다.

## 0. 용어 정정 - "udev"의 의미

`SP-9DD4F3EA` §0이 이미 "PnP"라는 이름에 대해 같은 정정을 한 바 있다 -
이 문서도 동일한 원칙을 따른다. 실제 Linux `udev`는 커널이 netlink로
쏘는 uevent를 받아 디바이스 노드를 만들고 규칙을 적용하는 **별도
유저랜드 데몬**이다. 이 프로젝트는 (a) 커널 자신이 이미 신뢰된
통제자(`SP-8B6B8D25` §2-A)이고 (b) `devmgr`/`fs`가 이미 Process 없는
순수 `KernelThread`로 커널에 흡수돼 있어(`SP-43331889`) uevent를
"커널 밖 프로세스로 넘겼다가 다시 처리"할 필연적 이유가 없다 - 그래서
이 문서는 **udev가 하는 일(노드 생성+이벤트 알림+이름 규칙)을 커널
내부 모듈 하나로 흡수**하는 것을 제안한다(§2.3). 이름도 "udev"를
그대로 쓰지 않고 이 프로젝트의 기존 명명 관례(`NamedObjectTable`/
`DeviceOwnerTable`/`KernelReservedTable`)를 따라 **`DeviceRegistry`**
로 부른다.

**`DeviceOwnerTable`(`SP-9DD4F3EA` §3.3a)과의 구분**: `DeviceOwnerTable`
은 "이 BAR/IRQ를 어느 프로세스가 점유했는가"(자원 소유권, IO 권한
중복 요청 방지가 목적)를 추적한다. 이 문서의 `DeviceRegistry`는
완전히 다른 관심사 - "이 장치가 사용자 공간에 어떤 이름으로 보이고,
언제 나타나고 사라졌는지"(가시성/네이밍/이벤트)를 추적한다. 하나의
실제 장치가 두 테이블 모두에 독립적으로 항목을 가질 수 있다(예: AHCI
포트 하나가 `DeviceOwnerTable`엔 BAR 소유권으로, `DeviceRegistry`엔
`sd0`라는 이름으로 각각 등록).

## 1. 배경 및 위치

`SP-9DD4F3EA`가 이미 "장치 자동 인식(enumeration) + 드라이버 매칭 +
핫플러그 알림"을 다뤘지만, 그 문서의 범위는 **커널 쪽 드라이버
코어**(Linux 커널 자신의 device model/driver core에 해당)에 멈춘다 -
장치를 찾아 알맞은 드라이버(자식 프로세스든 `fs`/`devmgr` 자신의
내장 코드든)에 연결하는 것까지만 다루고, 그 이후 **그 장치가
일반 유저 프로세스에게 어떻게 보이는지**(이름 있는 노드, 핫플러그
통지, 발견 가능성)는 전혀 다루지 않는다 - 현재 실제로 `/sys/dev`는
`RM-C65F7760`에 자리만 예약된 채 완전히 비어 있고, `devmgr`은
장치를 한 번 열거한 뒤 영원히 `pause`만 반복한다(`minicore/kernel/
devmgr.cpp` 실측 확인). `fs`가 AHCI를 직접 소유하게 된 뒤로도
(`QU-1FB6A7A4`) 그 장치가 "존재한다"는 사실을 확인할 방법은 `/sys/mnt`
에 파일시스템이 마운트됐는지 간접적으로 보는 것뿐이다. 이 문서가
메우려는 자리가 바로 여기다.

## 2. 스코프 결정

### 2.1 대상 장치 클래스 - 통일

`devmgr`이 매칭하는 (현재는 빈) PnP 장치와 `fs`가 직접 소유하는
AHCI/블록 장치를 **같은 `DeviceRegistry`에, 같은 네임스페이스
(`/sys/dev/<name>`)로, 같은 이벤트 채널로** 노출한다. 두 서브시스템
다 커널 내부에 있으므로(§2.3) 이 통일에 새로운 프로세스 경계나 IPC가
필요하지 않다 - `DeviceRegistry::announce()`/`withdraw()`를 양쪽이
그냥 직접 호출하면 된다.

### 2.2 중점 기능

1. **디바이스 노드 네임스페이스** - `/sys/dev/<name>`(§3.2).
2. **핫플러그 이벤트 알림** - 새 `DeviceEventsOpen` syscall이 여는
   fd로 Add/Remove 이벤트를 스트리밍(§3.3, POSIX 대응물 없음 - Linux
   netlink uevent 소켓에 해당).
3. **이름 부여/우선순위 규칙** - v1은 클래스 접두어+순번(§3.4)만
   기계적으로 확정하고, 사용자 재정의 규칙 파일(`/sys/etc/dev.cnf`)은
   자리만 예약한다(실제 파싱 규칙은 후속 - RM-23F4B687 §4, 아래
   §5-D처럼 임의로 채우지 않음).

**범위 밖(이 문서가 명시적으로 다루지 않음)**: 장치 노드를 통한
실제 I/O 의미론(§4, 미정으로 남기고 §5-B로 질의), 영속적 이름(udev의
by-id/by-serial류 심볼릭 링크), AF_INET류 네트워크 장치(NIC 자체가
아직 없음).

### 2.3 실행 위치 제안 - 별도 서비스가 아니라 커널 내부 모듈

**제안: 별도 프로세스/서비스를 새로 만들지 않고, `DeviceRegistry`를
`devmgr`/`fs`와 같은 층위의 커널 내부 모듈(`minicore/kernel/
device_registry.h/.cpp`)로 둔다.**

근거:
- `devmgr`/`fs` 둘 다 이미 Process 없는 `KernelThread`다
  (`SP-43331889`) - 이 둘이 새 유저랜드 서비스와 통신하려면 다시
  Channel IPC 경로를 만들어야 하는데, 그러면 "커널이 이미 신뢰하는
  정보를 프로세스 경계 너머로 옮겼다가 그대로 다시 커널 자료구조로
  반영"하는 왕복이 생긴다 - 실제 udev가 필요한 이유(커널과 신뢰
  경계가 다른 유저랜드 정책 엔진)가 이 프로젝트에는 아직 없다.
- `NamedObjectTable`/`KernelReservedTable`/`DeviceOwnerTable` 모두
  같은 패턴(커널 내부 고정 슬롯 테이블 + `livefs`를 통한 유저랜드
  노출)이라 `DeviceRegistry`도 그 관례를 그대로 따르는 것이 이
  프로젝트 안에서 가장 낮은 리스크다.
- 유저랜드 정책(예: "어떤 uid가 어떤 장치를 열 수 있는가")은 §3.6의
  producer 지정 uid/gid/mode + 기존 Chmod/Chown(`SP-9039F955`)
  syscall만으로 충분히 표현 가능해 보인다 - 별도 정책 데몬이 필요할
  만큼 복잡한 규칙(udev rules.d의 셸 스크립트 수준 유연성)은 이
  프로젝트 단계에서 실사용 근거가 없다(RM-23F4B687 §4).

**단, 이것으로 "별도 유저랜드 데몬은 영구히 안 한다"를 확정하는 것은
아니다** - `SP-43331889` §5의 `kSpawnUserModeDriver()`(ring3 PnP
드라이버 자식)가 실제로 쓰이기 시작하면, 그 자식들이 `DeviceRegistry`
에 syscall로 등록해야 하는 문제가 생긴다(§5-C, 미정으로 남김).

## 3. 아키텍처

### 3.1 `DeviceRegistry`(신규, `minicore/kernel/device_registry.h/.cpp`)

```cpp
enum class DeviceClass : uint8_t {
    Unknown = 0,
    Block = 1,
    // Char/Network/Input 등은 실사용처(문자 장치, NIC, PnP 입력 장치)가
    // 실제로 생기면 추가한다(RM-23F4B687 §4 - 미리 만들지 않음).
};

constexpr uint32_t kMaxDeviceRegistryEntries = 64;  // v1 상한, 실측 후 조정
constexpr uint32_t kMaxDeviceNameLength = 32;

struct DeviceRegistryEntry {
    char name[kMaxDeviceNameLength] = {};
    uint32_t nameLength = 0;
    DeviceClass deviceClass = DeviceClass::Unknown;
    // 등록한 서브시스템이 이 값의 의미를 정한다(§4) - v1 Block은
    // fs::BlockDevice*를 그대로 담는다(같은 커널 주소공간이라 안전).
    uint64_t backingHandle = 0;
    Uid ownerUid = kRootUid;
    Gid ownerGid = kRootGid;
    uint16_t mode = 0400;  // §3.6 v1 기본값
};

class DeviceRegistry {
public:
    // 성공하면 실제 배정된 이름/길이를 채운다(클래스 접두어+순번
    // 자동 생성 - §3.4, 이름 충돌은 원리적으로 불가능). 슬롯 고갈만
    // 실패 사유.
    static bool announce(DeviceClass cls, uint64_t backingHandle, Uid ownerUid, Gid ownerGid,
                          uint16_t mode, char* outName, uint32_t* outNameLength);
    static void withdraw(const char* name, uint32_t nameLength);
    static bool resolve(const char* name, uint32_t nameLength, DeviceRegistryEntry* outEntry);
    // livefs Readdir용 - named_object.cpp의 getByIndex와 동일한 관례.
    static bool getByIndex(uint32_t index, DeviceRegistryEntry* outEntry);
};
```

`named_object.cpp`와 동일하게 고정 슬롯 배열 + 선형 스캔으로
구현한다(v1 단순성 우선, 같은 근거).

### 3.2 노드 네임스페이스 - `/sys/dev/<name>` (+ usermode 드라이버는 `/sys/dev/<run-uid>/<name>`)

`livefs.cpp`에 "named"/"kernel"과 완전히 같은 패턴으로 셋째
하위 디렉터리를 추가한다:

- `Open("/sys/dev/<name>")` → `DeviceRegistry::resolve()` → 성공 시
  `FileHandle{backingHandle}`(클래스별 실제 read/write 의미는 §4,
  아직 미정).
- `Readdir("/sys/dev")` → `DeviceRegistry::getByIndex()`로 순서대로
  나열(named/kernel과 동일 관례 - 커서는 fd 자신의 offset).
- **`Stat("/sys/dev/<name>")`도 이번에 지원한다** - `named`/`kernel`
  이 지금까지 못 하던 것(`kLiveFsStatImpl`이 그 경로들에 대해
  `InvalidArgument`만 반환 - 애초에 구현된 적이 없었을 뿐, named/
  kernel도 원하면 같은 패턴으로 나중에 채울 수 있다)을 이 문서가
  처음 채운다 - `size=0`/`type=Regular`/`uid`/`gid`/`mode`를
  `DeviceRegistryEntry`에서 그대로 노출(`SP-9039F955`가 이미 확장한
  `StatArgs`/`KernelFsStatArgs` 재사용, 새 필드 불필요).

**[답변, 2026-09-29, `QU-E5CC3073`, §5-C 부분 확정]** "유저모드
드라이버는 `/sys/dev`가 아닌 `/sys/dev/<run-uid>/<dev>`로 노출된다."
- 이 답변을 다음과 같이 해석해 반영한다(문자 그대로 대비되는 두
경로를 말했으므로, **`devmgr`/`fs`처럼 커널 자신이 직접 소유하는
장치는 계속 평평하게 `/sys/dev/<name>`에 남고**, **`kSpawnUserModeDriver()`
(§5-C, `SP-43331889` §5)로 뜨는 ring3 드라이버 자식이 등록하는
장치만 그 자식 프로세스의 실제 uid 아래 `/sys/dev/<uid>/<name>`로
중첩된다**):

- `DeviceRegistry::announce()`의 API 자체는 바꾸지 않는다 - 이미
  받고 있는 `ownerUid` 파라미터(§3.1)를 그대로 경로 계산에 쓴다:
  `ownerUid == kRootUid`면 평평하게, 아니면
  `/sys/dev/<ownerUid>/<name>`로 중첩. 즉 **평평/중첩 여부는 별도
  플래그가 아니라 `ownerUid` 값 자체가 결정**한다(`devmgr`/`fs`는
  항상 `kRootUid`로 `announce()`하므로 자동으로 평평하게 남는다).
- `livefs.cpp`의 "dev" 하위 Open/Readdir은 이제 두 계층을 처리해야
  한다 - 루트(`/sys/dev`) 나열은 (a) `ownerUid==kRootUid`인 항목은
  이름 그대로, (b) `ownerUid!=kRootUid`인 항목들은 실제 항목 대신
  그 **uid들의 집합**을 디렉터리 항목으로 합성해 보여준다(같은
  uid가 여러 장치를 가지면 디렉터리 하나로 묶임) - 그 서브디렉터리
  (`/sys/dev/<uid>`)를 다시 Open/Readdir하면 그 uid가 소유한 장치들만
  나열된다. **정확한 합성 알고리즘/자료구조는 착수 세션이 확정한다**
  (RM-23F4B687 §4 - `named`/`kernel`의 단순 선형 스캔과 달리 "고유
  uid 집합 뽑기"라는 한 단계가 더 필요해 구현 세부가 좀 더 크다).
- 이 답변은 §5-A(권한 모델)에도 시사점을 준다 - `/sys/dev/<uid>/`
  아래 항목은 구조적으로 이미 "이 uid가 만든 것"이 경로에 드러나므로,
  그 서브디렉터리 자체의 열람/진입을 그 uid 본인과 root로만
  제한하는 것이 자연스러워 보인다(Linux `/proc/<pid>`가 그 프로세스
  소유자+root만 들여다볼 수 있는 것과 같은 정신) - 다만 이것도
  **확정은 아니다**, §5-A 재질의에 포함해 다시 확인한다.

### 3.3 핫플러그 이벤트 - `DeviceEventsOpen`

새 syscall(그룹2 Device - `EnumerateDevices`/`RequestIoPermission`과
같은 그룹, 다음 미사용 call은 4):

```cpp
constexpr SyscallEndpointId kSyscallEndpointDeviceEventsOpen = kMakeSyscallEndpointId(2, 4);

struct DeviceEventsOpenArgs {
    // out
    ChannelError error = ChannelError::None;
    int64_t fd = -1;
};

enum class DeviceEventKind : uint8_t { Added = 1, Removed = 2 };

struct DeviceEvent {
    DeviceEventKind kind = DeviceEventKind::Added;
    DeviceClass deviceClass = DeviceClass::Unknown;
    char name[kMaxDeviceNameLength] = {};
    uint32_t nameLength = 0;
};

// signalfd.h의 RtSignalQueue와 완전히 동일한 패턴(고정 용량 링버퍼,
// 가득 차면 가장 오래된 것부터 버림) - "새 정책을 또 만들지 않는다"는
// SP-A7479F83 §6-B의 판단을 그대로 재사용.
class DeviceEventQueue {
public:
    static constexpr uint32_t kCapacity = 32;
    void push(const DeviceEvent& event);
    bool pop(DeviceEvent* outEvent);
private:
    DeviceEvent _entries[kCapacity]{};
    uint32_t _head = 0;
    uint32_t _count = 0;
};

struct DeviceEventFdState {
    DeviceEventQueue queue;
    AsyncTaskWaitQueue pendingReaders;
    EpollObserverQueue epollReadObservers;
    void destroy() {}
};
```

- `MountKind::DeviceEvents = 6` 신설, `Process::FileDescriptor::
  deviceEvents`(`SharedPtr<DeviceEventFdState>`) - `timerfd`/`signalfd`
  와 완전히 동일한 배선(그룹3 기존 `Read`/`Close` 재사용, epoll 통합).
- **팬아웃**: `DeviceRegistry::announce()`/`withdraw()`가 성공하면
  그 순간 열려 있는 **모든** `DeviceEventFdState`에 이벤트를
  브로드캐스트한다(전역 약한 참조 목록 순회 - 각 fd는 자기만의
  큐를 가지므로 한 리더가 느려도 다른 리더에 영향 없음, Linux
  netlink uevent 소켓의 "모든 구독자가 각자 사본을 받는다"는 시맨틱과
  동일).
- `Read()`가 큐에서 `DeviceEvent` 하나를 꺼내 반환 - 큐가 비어 있으면
  기존 `pendingReaders`로 블로킹(POSIX 논블로킹 O_NONBLOCK류 옵션은
  이번 범위 밖).

### 3.4 이름 부여 규칙 (v1)

`<DeviceClass 접두어><순번>` - `Block`="sd", `Unknown`="dev". 순번은
`DeviceRegistry` 내부에서 클래스별로 단조 증가하는 카운터(등록 순서
그대로, 재사용하지 않음 - 이름 충돌 가능성을 원천 차단하는 대신
장치가 빠지면 번호에 구멍이 남을 수 있다, v1은 이를 허용한다 -
Linux도 실제로 `sda`가 빠지면 `sdb`가 `sda`로 재명명되지 않는 것과
같은 태도).

영속적 이름(udev의 by-id/by-serial 심볼릭 링크, 벤더/시리얼 기반
안정적 이름)은 **v1 범위 밖**이다 - 대신 `/sys/etc/dev.cnf`를
이름 재정의/우선순위 규칙 파일로 **자리만 예약**한다
(`SP-9DD4F3EA` §4a-2의 `/sys/etc/pnp.cnf`와 동일한 폴백 관례를
그대로 재사용할 것을 제안 - `fs`가 마운트를 마치기 전엔 initrd
동봉본으로 폴백, 나중에 실제 파일로 다시 읽어 갱신). **파싱
형식/규칙 문법 자체는 이 문서가 확정하지 않는다** - 착수 세션이
실사용 패턴을 보고 정한다(RM-23F4B687 §4, "구현 세부 수준의 결정,
새 DC 불필요"에 해당한다고 판단 - 단, 이 판단 자체에 이견이 있으면
§5-D처럼 별도로 질의할 수 있다).

### 3.5 등록 시점 (devmgr/fs 통합)

- **`fs`**: `kProbeAndInitAhci()`가 포트를 성공적으로 초기화한
  직후 `DeviceRegistry::announce(DeviceClass::Block, ...)`를 호출한다
  (`backingHandle`은 그 `fs::BlockDevice*`를 그대로 담는다 - 같은
  커널 주소공간이므로 안전, §4 참고).
- **`devmgr`**: `SP-9DD4F3EA` §3.2의 PnP 매칭이 성공할 때(현재
  매칭 테이블이 비어 있어 실질적으로 미래 일) 동일하게
  `announce()`를 호출한다.
- 두 서비스 다 `KernelThread`라 정상적으로는 절대 종료되지 않는다 -
  `withdraw()`는 실질적으로 실제 핫언플러그(`SP-9DD4F3EA` §3.4,
  아직 미구현) 경로에서만 호출된다(v1은 이론적 경로).

### 3.6 소유권/권한

**[답변, 2026-09-29, `QU-C726B3C8`, §5-A 확정]** "`/sys/dev/<uid>/`
서브디렉터리 자체의 열람/진입을 그 uid 본인과 root로만 제한" -
권한 모델은 **구조적**으로 확정됐다: `/sys/dev/<uid>/`(§3.2의 중첩
경로) 자체를 그 uid 본인 또는 root가 아니면 `Open`/`Readdir`
단계에서 `PermissionDenied`로 거부한다(디렉터리 진입 자체를 막음 -
그 안의 개별 파일까지 갈 필요도 없음). 이로써:

- **producer가 `announce()` 시점에 uid/gid/mode를 정하는 것으로
  충분하다** - 소유권이 경로 구조 자체에 이미 드러나므로, 개별
  파일 단위 `Chmod`/`Chown`은 **v1에 노출하지 않는다**(§5-A 완전
  해소 - "예" 모델은 별도 가변 상태 관리가 필요한데, 디렉터리
  구조만으로 이미 목적을 달성해 그 복잡성이 불필요해졌다).
  `livefs` 전체가 여전히 쓰기 계열 op에 `PermissionDenied`를
  반환하는 기존 태도와도 일관된다.
- **평평한 `/sys/dev/<name>`(root 소유, devmgr/fs 자신의 장치)**은
  이 uid 게이트가 걸릴 대상이 없다(루트 자신이 이미 전체 접근
  권한) - 이 디렉터리 수준 문턱은 `root:root` 기본값 제안(v1)
  그대로 유지, 필요해지면 재검토.

### 3.7 `mode`/`ownerUid`/`ownerGid` 필드의 실사용처

§3.1의 `DeviceRegistryEntry::mode`는 §3.6이 확정한 모델에서는
파일 단위 권한이 아니라 **§3.2 경로 계산의 입력**(어느 uid 아래
중첩되는지)으로만 쓰인다 - `Stat()`이 그대로 노출하는 값이긴
하지만(정보 제공용), 그 값 자체가 접근 통제에 직접 관여하지는
않는다(통제는 디렉터리 진입 단계에서 끝남).

## 4. Open()된 노드의 실제 I/O 의미론

**[답변, 2026-09-29, Opinion, §5-B/§4 확정]** "1. 열린 장치를 중복
Open 불가, 2. 마운트된 장치는 Open 불가, 3. 일단 Open된 장치는
Raw IO." - §4가 열어 뒀던 (a)/(b)/(c) 중 **(b) raw 섹터 접근**이
채택됐고, 그때 우려했던 두 위험(중복 접근/캐시 일관성)이 정확히
이 답변의 1번/2번 규칙으로 해소된다:

1. **배타적 Open(단일 오프너)** - `DeviceRegistryEntry`(§3.1)에
   현재 열려 있는지를 추적하는 상태(예: 연 프로세스를 가리키는
   `WeakPtr<Process>` 또는 단순 bool - 착수 세션이 확정)를 추가한다.
   이미 열려 있는 노드를 다시 `Open()`하면 `AlreadyExists`류 에러로
   거부(기존 `ChannelError` 값 재사용 - 새 값 추가는 구현 세부).
2. **마운트된 장치는 Open 불가** - `Open()` 시점에 그
   `backingHandle`(`fs::BlockDevice*`)이 현재 어떤 마운트의 백킹으로
   쓰이고 있는지 `MountTable`과 대조한다(정확한 조회 방법 - `fs`가
   이미 아는 마운트-디바이스 매핑을 재사용할지, `MountTable`에
   역방향 조회를 추가할지는 착수 세션이 정함) - 마운트돼 있으면
   `PermissionDenied`류 에러로 거부. **1번과 결합하면**: 마운트
   해제(`Unmount`) 후에만 raw 열기가 가능해지고, raw로 열려 있는
   동안은(1번 배타성) 그 장치를 다시 마운트할 수도 없어야
   일관적이다(마운트 경로도 이 배타성 상태를 확인하도록 함께
   맞춰야 함 - 착수 세션이 `fs`의 마운트 로직과 연동).
3. **Raw I/O** - `Read(fd, buf, len)`/`Write(fd, buf, len)`을
   `fs::BlockDevice`의 섹터 단위 I/O로 직접 매핑(오프셋은
   `Process::FileDescriptor::offset`, 섹터 정렬 강제 - 정렬 안
   맞으면 `InvalidArgument`, §3.6이 확정한 권한 모델과 함께 적용).

**Block 외 클래스(`Unknown`, 미래의 `Char` 등)에 이 규칙이 그대로
적용되는지는 아직 명시되지 않았다** - 이 답변이 예시로 든 것이
"장치"/"마운트" 일반론이라 Block에 국한하지 않는 것으로 보이나,
`Unknown`류처럼 애초에 마운트 개념이 없는 클래스는 2번 규칙이
자명하게 공집합("마운트된 적 없음")으로 성립해 문제가 없다 - 1번/
3번은 클래스 무관하게 동일하게 적용 가능하다고 판단, 별도 재질의는
하지 않는다(RM-23F4B687 §4 수준의 자연스러운 일반화).

## 5. 결정 현황 (`DC-BD28632D` 진행 결과)

- **§5-A(권한 모델) - 해소**: 위 §3.6/§3.7 참고 - 구조적 디렉터리
  진입 통제로 확정, `Chmod`/`Chown`은 v1에 노출하지 않는다.
- **§5-B(Open I/O 의미론) - 해소**: 위 §4 참고 - 배타적 Open +
  마운트-충돌 거부 + Raw I/O.
- **§5-C(향후 ring3 usermode 드라이버 등록) - 경로 규칙만 해소,
  syscall 표면은 실사용처 등장 시 후속 문서로 이관**: `/sys/dev/
  <run-uid>/<name>` 경로 자체는 확정(§3.2)됐으나, `kSpawnUserModeDriver()`
  (`SP-43331889` §5)가 아직 `PN-A8BE8BED` 항목1/2로 보류 중이라
  실제 소비자가 없다 - RM-23F4B687 §4 원칙(실사용처 없이 미리
  설계하지 않는다) 그대로 (B)를 채택, 그 자식이 실제로 등장할 때
  별도 후속 문서가 `DeviceRegistry::announce()`의 syscall 노출
  방식을 확정한다. 별도 재질의는 하지 않는다 - 이건 "설계자 판단이
  필요한 가치 판단"이 아니라 "아직 대상이 없는 API를 지금 만들지
  말자"는 이 프로젝트 전반의 기존 관례를 그대로 적용한 것뿐이다.
- **§5-D(`DeviceClass` v1 범위) - v1 최소로 확정**: `Block`/`Unknown`
  두 개만(§3.1 그대로) - 현재 실존하는 소비자가 AHCI(`Block`)
  하나뿐이고, `Char`/`Network`/`Input`을 지금 추가해도 실측으로
  검증할 소비자가 없다(`SP-E35FD36C` USB 스택은 `RM-F2DAFF66`
  §2-추가5 확인 결과 구현 자체가 아직 없음). 이것도 RM-23F4B687
  §4 수준의 구현 세부 판단으로 보아 별도 재질의하지 않는다 - 실사용
  클래스가 실제로 생기면(예: USB 스택 착수 시) 그때 enum 값을
  추가한다.

**이로써 `DC-BD28632D`의 4개 결정 요청이 전부 해소됐다** - 이
문서는 이제 순수 설계 검토(용어/구조/구현 세부) 단계로 넘어간다.
