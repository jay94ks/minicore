## 0. 목적

현재 `scheduled`(예정) 상태인 계획 11건을 실제로 어떤 순서로 착수해야
하는지 정리한다. 개별 계획의 `dependencies` 필드는 이미 등록돼
있지만, 실측으로 확인한 실제 선후 관계(특히 "완전히 막힌 것" vs
"저비용으로 바로 착수 가능한 것"의 구분)는 그래프만 봐서는 드러나지
않는다 - 이 문서가 그 실무적 판단을 보탠다.

## 1. 그룹 A - 지금 바로 착수 가능, 서로 독립적 (선행 세션 착수 우선순위)

다른 계획과 무관하게 즉시 시작할 수 있고, 5분 간격 자동 루프 틱으로도
증분 진행이 가능한 일반 기능 구현이다.

1. **`PN-D28DD9F3`** - 4K 페이지의 2M 페이지 병합/분할 구현. 의존성 없음.
2. **`PN-04258584`** - HPET 멀티 비교기를 스케줄러 코어별 독립 틱과 연동.
   의존성 없음.
3. **`PN-7528A406`**(항목3만 남음) - RequestIoPermission v1의
   `DeviceOwnerTable` teardown hook 연동, 저우선순위로 명시돼 있음.
   선행 조건이던 `PN-B87A5BBA`/`PN-4FF8CCBE` 둘 다 **completed 확인
   완료**(이번 조사로 재확인) - 착수 조건은 충족됐으나 계획 자신이
   이미 "저우선순위 유지"로 낮춰 둔 항목이라 그룹 A의 다른 둘보다는
   뒤에 놓는다.

이 셋은 서로 얽혀 있지 않으므로 어느 순서로 하든 무방 - 준비된
세션이 있는 대로 아무거나 집어 진행 가능.

## 2. 그룹 B - 전용 디버깅 세션이 필요한 두 heisenbug (다른 모든 것의 실질적 상류)

**이 그룹이 실질적으로 가장 중요하다** - 그룹 C 전체(authmgr 계열)가
이 중 하나(`PN-6360E6E9`)의 해소를 기다리고 있다. 두 계획 다
이전 세션들이 이미 "5분 간격 자동 루프 틱으로는 진행 불가 - gdb를
붙인 채 여러 차례 조건부 재현을 기다려야 하는 연속 작업, 한 세션을
온전히 투입할 때 재개"로 명시적으로 결론 내렸다 - **이 프로젝트의
표준 관례(`PN-BC3A2F5F`/`PN-4859FDE9`/`PN-E4C6AF72` 등에 이미 적용된
기준)와 같은 선이므로, 다음 착수는 이 조사 하나에만 집중할 수 있는
세션에서 진행할 것을 권장**.

1. **`PN-6360E6E9`**(우선) - `kSyncCr3`/`kSyncRsp0ForDispatch`에서
   반복 재현되는 Task 포인터 오염(`0x100000000`, 정확히 2^32) PANIC.
   최근 세션이 반환주소 진단(diag_ring `rsp` 필드 재활용)을 이미
   영구 계측으로 심어 뒀다 - 재현되는 즉시 그 값이 6개 알려진
   호출부 주소와 일치하는지부터 확인하면 가설 분기가 빠르다(계획
   본문 "다음 세션 권장" 절 참고). **`PN-24A2B6F5`가 이걸 직접
   의존성으로 걸어 뒀으므로 먼저 푸는 쪽이 그룹 C 전체를 연다.**
2. **`PN-E4C6AF72`** - AHCI+SMP4 iretq CS/SS 오염 #GP. `PN-61D908EB`
   (UEFI 스텁 버그, completed)와의 "공통 원인" 가설은 이미 반증됨 -
   독립된 결함으로 재출발해야 한다. 계획 본문이 이미 다음 방법론
   (gdb로 소프트웨어 로깅보다 먼저 실제 CS 레지스터 직접 확인 -
   `PN-61D908EB`가 결국 이 방법으로 답을 찾았음)을 정리해 뒀다.

**주의**: 두 계획 다 재현율이 낮아지는(레이아웃 변화로 "휴면"
상태가 되는) 패턴이 반복돼 왔다 - 착수 세션은 먼저 재현 여부부터
확인하고, 안 되면 "이번에도 안 됨"을 데이터로 기록한 뒤 물러나는
기존 관례(완료 처리하지 않고 scheduled 유지)를 그대로 따른다.

## 3. 그룹 C - authmgr 계열, 그룹 B(PN-6360E6E9)가 풀려야 실질적으로 전진

```
PN-6360E6E9(그룹 B) ──▶ PN-24A2B6F5 E2E 검증 ──▶ PN-B6DB692C 항목1(authmgr 비동기 질의 배선)
```

- **`PN-24A2B6F5`**(authmgr 커널 서비스+libkvdb+sudo/su) - 스키마
  의존성(`PN-CFEAEF40`/`PN-B6DB692C`의 UserRecord 정의)은 이미 충족
  완료(commit cf09655) - **이 계획의 실질적 유일한 남은 블로커는
  `PN-6360E6E9`(그룹 B)뿐이다**. 계획 자신의 최신 갱신 절이 이미
  "diag_ring 계측으로 그 결함부터 좁히는 작업이 사실상 선행 조건"
  이라고 명시. 그룹 B가 풀리면 §1-C 항목3(생성 권한, caller uid
  와이어 규약)/§1-B(sudo/su)로 바로 이어갈 수 있다.
- **`PN-B6DB692C`**(항목1: authmgr 비동기 질의 배선 + 항목4:
  libkcrypto) - 핵심 로직(캐시+LRU+kSetuid tree-walk)은 이미 완료
  (commit cf09655), 남은 항목1(cache-miss 시 authmgr 비동기 질의
  경로)은 `PN-24A2B6F5`가 실제로 응답 가능한 상태가 돼야 의미가
  있다. **항목4(libkcrypto SHA256/AES256)는 독립적으로 먼저 착수
  가능** - authmgr 완성을 안 기다려도 된다(별도 라이브러리 신설,
  `RM-7C249618` 등록 필요, CLAUDE.md 규칙 8).

**형식적 순환처럼 보이는 이유(설명, 그래프 수정 없음)**:
`PN-B6DB692C.dependencies=[PN-24A2B6F5]`이고
`PN-24A2B6F5.dependencies=[...,PN-B6DB692C,...]`라 `plan_depend`
그래프만 보면 순환이다. 실제로는 순환이 아니라 **엇갈린 진행** -
`PN-B6DB692C`가 먼저 자기 몫(스키마)을 끝내 `PN-24A2B6F5`를
언블록했고, 이제 `PN-24A2B6F5`가 자기 몫(실제 질의 엔드포인트)을
끝내야 `PN-B6DB692C`의 남은 항목1이 의미를 갖는다 - 두 계획의
"이미 끝난 부분"과 "아직 남은 부분"이 서로 다른 방향을 가리킬 뿐,
어느 쪽도 상대의 완료 전체를 기다리며 진짜로 멈춰 있지 않다. CNW의
`plan_depend`는 순환을 막지 않는다는 점(설계상 허용)도 참고.

- **`PN-0B461E6F`**(FileSystemDriver unmount + clean shutdown) -
  핵심 목표(정상 종료 경로 자체)는 이미 완료. 남은 유일한 항목(GRUB
  SMP4에서 100% 재현되는 크래시)은 그룹 B의 heisenbug 계열과 같은
  근본 원인일 가능성이 있다고 계획 자신이 교차 참조해 뒀다 -
  **별도로 착수하지 말고, 그룹 B 진행 중 같은 진단으로 같이
  좁혀질 가능성을 열어 둔다**(중복 투자 방지).

## 4. 그룹 D - 설계자가 명시적으로 보류시킨 항목 (트리거 없이는 착수하지 않음)

아래 셋은 착수 조건이 기술적으로 충족돼 있어도 **설계자가 직접
"보류"/"재검토는 나중에"로 지시**했으므로, 그 트리거(유저랜드 본격
착수, 실측 병목 확인 등)가 오기 전까지 이번 실행 순서에서 제외한다.
백로그 설계안 작업(`SP-94C6A764` 등)과 달리, 이건 "설계가 없어서"가
아니라 **"착수 자체를 하지 말라"는 명시적 지시**라 그룹 A로 당겨오지
않는다.

- **`PN-63A38823`** - AsyncTask `gExecQueues`를 `LockFreeQueue`로
  마이그레이션 검토. "현재 Spinlock 기반 확인 완료, 실제 마이그리션은
  계속 보류."
- **`PN-C6CDC26A`** - `AsyncTask` 유저 포인터 접근 CR3→물리주소 매핑
  전면 교체. "1단계 완료, 전면 교체는 설계자 결정으로 보류."
- **`PN-A8BE8BED`**(항목1/2만) - 유저모드 드라이버 지원 +
  `AllocDmaBuffer` 커널 모드 매핑. "설계자 지시, 유저랜드 본격 착수
  시 재검토." (항목3은 이미 completed로 이 계획 자체에 반영됨.)

## 5. 권장 착수 순서 요약

1. (병행 가능) 그룹 A 셋 중 아무거나 - 일반 자동 루프 틱으로 진행.
2. (전용 세션 확보 시 최우선) 그룹 B의 `PN-6360E6E9` - 그룹 C 전체를 연다.
3. 그룹 B의 `PN-E4C6AF72` - `PN-6360E6E9`와 독립적이므로 순서 무관,
   다만 둘 다 전용 세션이 필요해 동시에 두 세션이 있다면 병행.
4. `PN-6360E6E9` 해소 후 → `PN-24A2B6F5` 재개 → 그 진전에 따라
   `PN-B6DB692C` 항목1 재개. `PN-B6DB692C` 항목4(libkcrypto)는 이
   순서와 무관하게 언제든 병행 착수 가능.
5. 그룹 D는 트리거 발생 시까지 이번 순서에서 제외.

## 6. [갱신, 2026-09-26] "계획됨"(planned) 전체 재점검 - 3건 착수 가능으로 승격, 6건은 계속 보류

`docs pending`/`plan_list(status=planned)` 전수 재점검 결과 - 착수
가능한 것은 즉시 그룹 A에 편입하고(예정으로 전환 완료), 나머지는
왜 아직 안 되는지 이유를 명시해 둔다(CLAUDE.md 규칙 4 - 이유 없이
방치하지 않음).

### 6.1 새로 착수 가능(scheduled로 전환 완료) - 그룹 A에 편입

- **`PN-0556C759`** - 멀티스레드 동시 브레이크포인트 Double/Page
  Fault. 재현 인프라 자체를 새로 만들어야 하는 비용이 늘었을 뿐
  (devmgr가 더 이상 유저랜드 프로세스가 아니라 재현 드라이버를
  처음부터 새로 만들어야 함), 실제 착수를 막는 의존성/설계자 보류는
  없다. **다음 세션 최우선**: 완전히 새로운 유저랜드 "디버거
  드라이버" 프로그램(SpawnProcess로 dbgtarget을 자식으로 스폰,
  DebugAttach/SetBreakpoint/GetRegisters/Continue 호출)을 만드는
  것부터 시작 - 계획 본문 "다음 세션이 판단할 것" 절 참고.
- **`PN-9625F395`** - PageFrameAllocator order=1 이중 할당 관측.
  강한 정황 증거로 "실제 버그가 아니라 gdb Python
  `FinishBreakpoint` 계측 자체의 허위 이중 발동"으로 판정됐지만
  완전히 반증되지는 않아 낮은 우선순위로 남아 있다 - 착수 세션은
  계획 본문의 "후속 조사가 필요하다면" 절(디버그 빌드 전용 O(1)
  비트맵 자체 검증)부터 시도하거나, 이 결론을 그대로 받아들여
  `rejected`/`completed`(반증 확정)로 종결하는 것도 선택지다.
- **`PN-C33B5D28`** - rdtscp 전환 성능 정량 측정(부팅 시간/컨텍스트
  스위칭 비용). 순수 측정 작업, 다른 어떤 작업도 막고 있지 않음 -
  측정 방법론(QEMU 계측 vs 실하드웨어)만 착수 시 확정.

### 6.2 계속 "계획됨"으로 남김 (착수하지 않는 이유)

- **`PN-6EB7F9D2`** - 실제 다중 IOAPIC **하드웨어**에서 재검증.
  이 프로젝트는 QEMU 환경에서만 작업하므로 실물 하드웨어가 없는 한
  구조적으로 착수 불가능.
- **`PN-81223433`**/**`PN-2EA94B1A`**/**`PN-2CD26587`** - 각각
  `SP-94C6A764`/`SP-5D62DCCF`/`SP-BF0B31B5`(전부 review, 미승인)의
  구현 대상이다 - **설계자가 그 SP들을 승인하기 전에 구현 착수로
  전환하면 미승인 설계로 코드를 짜는 것**이라 CLAUDE.md 규칙4
  위반이다. 세 SP 다 review 상태로 확인(2026-09-26 재확인) - 승인
  즉시 이 셋도 scheduled로 전환할 것.
- **`PN-A0EF864B`** - systemd 포팅. 설계자가 명시적으로 "우선 보류"
  라고 지시한 항목(§4 그룹 D와 동일한 사유) - 트리거 없이 착수하지
  않음.
- **`PN-7030D201`**/**`PN-3DDF2797`** - 둘 다 `PN-E4C6AF72`(그룹 B,
  아직 미해결 heisenbug)에 의존 - 그 계획이 풀려야 재개 가능, §2의
  그룹 B 우선순위와 같은 선상.
