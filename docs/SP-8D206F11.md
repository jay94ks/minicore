# Minicore CPU 캐시 관리 정책

이 문서는 SP-8B6B8D25 §2 항목9("CPU 캐시 관리, Fault 시 원인 조사,
적절한 커널 서비스로 라우팅")가 커널 책임으로 명시했지만 별도 설계
문서가 없던 "CPU 캐시 관리" 절반을 다룬다(Fault 원인 조사/라우팅
절반은 이미 구현되어 있으며 이 문서의 범위가 아니다). PN-5BCA7AB9가
이 공백을 최초로 포착했고, 그 계획의 조사 결과 실제로 프로젝트
어디에도 MTRR/PAT/wbinvd 관련 정책 문서가 없음을 확인했다(docs
search 0건).

**[개정, 2026-09-18, 설계자 opinion]** 최초 작성 시점엔 "실사용처가
없으니 상위 캐시 관리 기능(MTRR/PAT/write-combining)은 지금 설계하지
않는다"는 방향이었으나, 설계자가 명시적으로 "이것도 이 설계안에 미리
작성해두어라"고 지시해 §2를 실제 설계로 채웠다. 아래 §1은 여전히
그대로 유효하고(매핑 단위 PCD가 지금까지 유일한 실제 적용 방침), §2가
그 위에 PAT 기반 캐시 타입 선택 메커니즘을 추가한다.

## 1. 확정된 현재 방침 — 매핑 단위 PCD (Page Cache Disable)

캐시 코히런시가 문제가 될 수 있는 두 종류의 메모리 매핑에 대해,
**개별 페이지 매핑 시점에 PAGE_CACHE_DISABLE(PCD) 플래그를 설정하는
것**이 이미 실제로 적용된 유일한 방침이다.

- **MMIO 매핑**: RequestIoPermissionHandler::onExec
  (minicore/devmgr/pnp.cpp:284)가 PnP 드라이버의 MMIO 영역 요청을
  처리할 때 PAGE_CACHE_DISABLE을 설정한다. 이미 구현되어 있고
  실제 버그 없이 동작 중이다.
- **DMA 대상 메모리**: SP-39F18E30 §3.3("캐시 속성")이 "이 프로젝트는
  아직 캐시 스누핑(하드웨어 캐시 코히런시) 여부를 확정하지 않았으므로,
  안전한 기본값으로 PAGE_CACHE_DISABLE(UC, uncached)를 제안한다(PnP의
  MMIO 매핑과 동일 속성 재사용)"이라고 명시했고, 이 방향대로 구현됐다.

두 경우 모두 근거는 동일하다 - 하드웨어 캐시 스누핑 여부를 아직 모르는
상태에서, 성능보다 정확성을 우선해 캐시를 아예 끄는 쪽이 안전한
기본값이라는 것. §2는 이 방침을 대체하지 않는다 - 여전히 기본값이다.

## 2. [확정, 2026-09-18, 설계자 지시] PAT 기반 캐시 타입 선택 - MTRR은 쓰지 않는다

### 2.1 왜 MTRR이 아니라 PAT인가

x86_64에서 소프트웨어가 페이지 단위로 캐시 정책을 제어하는 방법은
두 가지다:

- **MTRR**(Memory Type Range Register): 물리 주소 범위 단위로 캐시
  타입을 지정 - 가변 레인지 레지스터 쌍이 보통 8~10개뿐이라 슬롯이
  희소하고, 전역 상태라 모든 코어에 동일하게 맞춰야 한다.
- **PAT**(Page Attribute Table): `IA32_PAT` MSR(0x277)에 8개의
  캐시 타입 슬롯을 정의해 두고, 각 페이지 테이블 엔트리의 PAT/PCD/PWT
  3비트 조합으로 그중 하나를 페이지 단위로 직접 선택한다.

이 프로젝트는 이미 페이지 단위 매핑(§1의 PCD)으로 캐시 정책을
다뤄 왔고, 앞으로도 MMIO/DMA/프레임버퍼처럼 매핑 하나하나가 서로 다른
캐시 요구를 갖는 상황이 계속 생긴다 - 범위 단위로 미리 다 예약해 둬야
하는 MTRR보다 매핑 시점에 자유롭게 고르는 PAT 쪽이 이 프로젝트의
기존 방향과 맞다. **따라서 이 프로젝트는 소프트웨어가 직접 제어하는
캐시 타입 선택에 PAT만 쓰고, MTRR은 건드리지 않는다** - 펌웨어/UEFI가
부팅 시 이미 구성해 둔 MTRR(전형적으로 전체 RAM=WB, PCI/MMIO 구멍=UC)은
그대로 상속해 쓰되 커널이 재구성하지 않는다.

### 2.2 IA32_PAT 레이아웃 (부팅 시 1회 설정)

부팅 초기(페이징 활성화 직후) `IA32_PAT`를 아래처럼 설정한다.

**[정정, 2026-09-18, 설계자 답변(QU-9F758912)]** 최초 작성 시점의
"AP 코어들도 kMain의 같은 초기화 경로를 타므로 모든 코어에 자동으로
동일하게 적용됨"이라는 전제는 **사실이 아니다** - AP 코어는 `kMain`
이 아니라 별도의 `kApMain`(minicore/kernel/smp.cpp)을 타고, `kMain`
안에서 한 번만 실행되는 `Paging::init()`을 AP는 거치지 않는다.
`IA32_PAT`는 STAR/LSTAR/SFMASK/EFER.SCE 등과 마찬가지로 논리
프로세서별(코어별) MSR이므로(Intel SDM), **BSP(`kMain`)와 각
AP(`kApMain`) 양쪽 모두에서 각자 설정해야 한다** -
`SyscallFastPath::initForThisCore()`가 이미 확립해 둔 "코어별 MSR은
각 코어가 스스로 설정" 관례를 그대로 따른다(`Paging::
initPatForThisCore()`로 구현, BSP는 `kMain()`이 `Paging::init()`
직후, AP는 `kApMain()`이 `SyscallFastPath::initForThisCore()`와
같은 자리에서 호출).

인덱스 0~3(레거시 PAT 비트=0인 엔트리 - 기존에 이미 쓰던 모든 페이지
테이블 엔트리가 여기 걸림)은 x86 표준 BIOS 기본값과 **동일하게
유지**해 기존 코드(§1의 PCD/PWT 조합)를 전혀 건드리지 않는다.
인덱스 4(레거시 PAT 비트=1, PCD=0, PWT=0)만 새로 WC로 재정의한다:

| 인덱스 | PAT.PCD.PWT | 타입 | 비고 |
|---|---|---|---|
| 0 | 0.0.0 | WB (Write-Back) | 기존 기본값, 변경 없음 |
| 1 | 0.0.1 | WT (Write-Through) | 기존 기본값, 변경 없음 |
| 2 | 0.1.0 | UC- (Uncached, MTRR로 WC 승격 가능) | 기존 기본값, 변경 없음 |
| 3 | 0.1.1 | **UC** (Uncached) | §1의 PAGE_CACHE_DISABLE이 지금까지 쓰던 슬롯 |
| 4 | 1.0.0 | **WC (Write-Combining)** — [신규] | 프레임버퍼 등 §3용 |
| 5~7 | 1.0.1 / 1.1.0 / 1.1.1 | 1~3과 동일(레거시 기본값 유지) | 변경 없음 |

인덱스 4를 고르려면 PTE(4K 페이지)의 PAT 비트(비트 7, 4K PTE에서는
비트 12 위치의 별도 PAT 필드 - 아키텍처 매뉴얼 표기 주의)를 켜야
한다. 이 변경 하나로 커널 전체의 기존 PAGE_CACHE_DISABLE 사용처(§1)는
아무 영향도 받지 않는다 - 여전히 인덱스 3(UC)에 그대로 매핑된다.

### 2.3 신규 커널 API - `kMapPageWithCacheType`

앞으로 매핑 시점에 캐시 타입을 고를 땐 원시 `PAGE_CACHE_DISABLE`
플래그를 직접 조합하지 말고, 이 API를 새 진입점으로 삼는다(§1의
기존 PCD 사용처들은 하위 호환을 위해 그대로 둬도 무방 - 강제 이관은
아님):

```cpp
enum class CacheType : uint8_t {
    WriteBack,        // 인덱스 0 - 일반 RAM 기본값
    WriteThrough,      // 인덱스 1
    Uncached,          // 인덱스 3 - 지금까지 PAGE_CACHE_DISABLE이 쓰던 것과 동일
    WriteCombining,    // 인덱스 4 - [신규] 프레임버퍼 등
};

// virtAddr에 physAddr을 매핑하되, flags에 더해 cacheType이 가리키는
// PAT 인덱스에 맞는 PAT/PCD/PWT 비트 조합을 자동으로 계산해 얹는다.
bool kMapPageWithCacheType(uint64_t virtAddr, uint64_t physAddr,
                            uint64_t flags, CacheType cacheType);
```

`Paging`(또는 그에 대응하는 기존 매핑 계층)이 `CacheType → PAT/PCD/PWT`
변환표(§2.2)를 내부에 하나 두고 이 세 비트를 계산해 PTE에 얹는 얇은
래퍼로 구현한다 - 새로운 자료구조나 전역 상태는 필요 없다.

**[추가, 2026-09-18, 설계자 opinion]** 같은 물리 페이지를 서로 다른
`CacheType`으로 동시에 매핑하는 건 x86_64에서 사실상 미정의 동작이다
- 이 일관성을 물리 프레임 단위로 추적/검사하는 자리는 `SP-6CEFBE9B`
("물리 페이지 프레임 메타데이터 — `PageFrame` 구조체") §3이 새로
맡는다 - 그 문서의 `PageFrame::lastCacheType`/`cacheTypeAssigned`
참고.

### 2.4 MMIO/DMA 매핑도 이 API로 이관할지는 후속 판단

**[정정, 2026-09-18]** 최초 작성 시점엔 §1의 기존 두 사용처
(pnp.cpp:284, SP-39F18E30 §3.2)가 `CacheType::Uncached`(PAT 인덱스3,
PCD=1+PWT=1)와 "결과가 완전히 같다"고 적었으나, 실제로는 다르다 -
기존 코드는 `PAGE_CACHE_DISABLE`만 켜고 PWT는 안 건드리므로
PCD=1+PWT=0으로 실제로는 **PAT 인덱스2(UC-)** 에 해당한다(인덱스3
UC가 아님). 기능적으로는 두 인덱스 모두 MTRR이 그 물리 범위를 WC로
승격하지 않는 한 동일하게 동작하므로(UC-는 "MTRR이 WC로 올려주지
않으면 UC와 동일") 지금까지 실제 문제를 일으키지는 않았지만, 정확한
설명은 "기존 두 사용처는 인덱스2(UC-)를 쓰고 있고, 새 API의
`CacheType::Uncached`는 인덱스3(진짜 UC)을 쓴다 - 둘 다 실질적으로
캐시를 끄는 효과는 같다"이다. 다만 지금 당장 기존 호출부를 이 API로
바꿔야 할 필요는 없다(동작이 사실상 같아 리팩터가 급하지 않음,
RM-23F4B687 §4 취지).
새로 캐시 타입을 고르는 매핑(예: §3의 프레임버퍼)부터 이 API를 쓰고,
기존 두 곳은 실제로 손댈 일이 생길 때(버그 수정, 근처 코드 변경 등)
자연스럽게 이관하면 된다.

## 3. [열린 확인 — 설계자] 아직 실사용처가 없어 결정을 미룬 항목

§2가 메커니즘(PAT 슬롯/API)을 마련해 뒀지만, 그 메커니즘을 실제로
누가 어떻게 호출할지는 여전히 구체적 실사용처가 생겨야 확정된다 -
아래는 그 사용처가 없어 지금 임의로 결정하지 않는 항목이다.

1. ~~**프레임버퍼 등 write-combining이 유리한 매핑**~~ - **[부분 해소,
   2026-09-18]** 메커니즘(§2의 PAT 인덱스4/`CacheType::WriteCombining`)은
   이제 준비돼 있다. 다만 이 프로젝트엔 아직 프레임버퍼 드라이버 자체가
   없어 실제로 이 메커니즘을 호출하는 코드는 없다 - 프레임버퍼 드라이버가
   설계될 때 `kMapPageWithCacheType(..., CacheType::WriteCombining)`을
   호출하기만 하면 된다.
2. **하드웨어 캐시 스누핑 여부 확인**: SP-39F18E30 §3.3이 언급한
   "아직 캐시 스누핑 여부를 확정하지 않았다"는 전제 자체가 아직 유효한
   열린 질문이다 - 대상 하드웨어/QEMU 환경이 DMA 캐시 스누핑을
   지원한다면 DMA 매핑에 UC 대신 WB를 쓰고 소프트웨어 캐시 플러시
   (wbinvd/clflush)로 전환하는 편이 나을 수 있으나, 이 프로젝트는
   아직 이 여부를 조사하지 않았다.
3. ~~**전역 MTRR 관리 체계 도입 여부**~~ - **[해소, 2026-09-18]** §2.1이
   명시적으로 답했다 - MTRR은 건드리지 않고 PAT만 쓴다.
