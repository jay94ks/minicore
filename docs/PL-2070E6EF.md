# 실행 계획: MSI/MSI-X 인터럽트 지원

**[MSI 부분 완료, 2026-09-14]** QA-26450C3E 체크됨. 아래는 완료 기록으로
남긴다. **MSI-X는 범위 밖으로 남겼다**(아래 "안 한 것" 참고) - 제목은
원래대로 두되 실제로 구현/검증한 것은 MSI뿐이다.

설계자 지시(DS-D4E5C451)로 등록. **이 프로젝트엔 아직 PCI/PCIe 설정
공간 접근 코드 자체가 전혀 없다** - 이게 실질적인 선행 조건이자
이 계획의 0단계였다.

## 선행 조건 (이 계획에 포함해서 진행)

- 최소 PCI Configuration Space 접근(레거시 메커니즘 #1: 포트
  0xCF8/0xCFC) - 없었음 → 이번에 신규 구현.
- IOAPIC 계획(PL-2D149D8F, 완료) - 벡터->콜백 표를 그대로 재사용.

## 한 것

1. **PCI 설정 공간 최소 구현**: `minicore/kernel/pci.h/.cpp` 신설.
   포트 0xCF8(CONFIG_ADDRESS)/0xCFC(CONFIG_DATA)로 bus/device/
   function/register 지정 접근. `readConfig32/16/8`, `writeConfig32/16`
   구현 - 16/8비트 접근은 CONFIG_DATA에 오프셋 하위 2비트를 더한
   포트로 직접 outw/outb하는 방식을 썼다(32비트로 통째로 읽어
   마스킹하는 것보다 실제 칩셋 동작과 일치). `io_port.h`에
   `kOutW/kInW/kOutL/kInL` 추가(기존엔 8비트 접근만 있었음).
   MMCONFIG(ACPI MCFG 기반)는 v1 범위 밖으로 명시(PL 자체 결정,
   PCIe 확장 설정 공간이 실제로 필요해지면 추가).
2. **PCI 버스 열거**: `Pci::enumerate(callback)` - bus 0부터 32개
   device × (멀티펑션이면 8개 function)를 훑어 vendor ID(0xFFFF면
   없음)로 존재 여부 판정. PCI-PCI 브리지(class 0x06/subclass 0x04)를
   만나면 secondary bus를 재귀 탐색. `kmain.cpp`가 부팅 시퀀스의
   영구 로그 항목으로 채택(ACPI/메모리맵 로그와 같은 위치의
   진단 정보) - vendor/device/class/subclass를 시리얼에 남긴다.
3. **MSI capability 탐색**: `Pci::findCapability` - Status 레지스터
   bit4(Capabilities List 존재)를 먼저 확인하고, 0x34의 포인터부터
   연결 리스트를 따라가며 capability id를 비교한다.
4. **MSI 메시지 프로그래밍**: `Pci::enableMsi` - Message Address =
   `0xFEE00000 | (destApicId << 12)`, Message Data = 벡터 번호(하위
   8비트, 델리버리모드/트리거모드는 기본값 0=Fixed/edge). Message
   Control 레지스터의 64비트 주소 지원 비트(bit7)로 32/64비트 주소
   레이아웃을 구분해서 쓴다. Multiple Message Enable은 항상 0(벡터
   1개)로 고정 - 여러 벡터를 요청하는 장치 지원은 범위 밖.
5. **벡터/핸들러 등록**: IOAPIC 계획(PL-2D149D8F)에서 만든
   `Idt::registerHandler(vector, callback)`를 그대로 재사용 - MSI는
   IOAPIC 리다이렉션 테이블 슬롯(제한된 개수)을 안 쓰므로 더 많은
   장치를 붙일 수 있다는 설계 의도가 실제로 확인되는 지점이었다.
6. **검증(실측, 2026-09-14, QEMU 8.2.2, `-device edu`)**: QEMU의
   교육용 PCI 장치 edu(vendor 0x1234, device 0x11e8, 스펙:
   `/usr/share/doc/qemu-system-data/specs/edu.rst` - INTx/MSI 둘 다
   지원)를 붙여 검증했다. PCI 열거로 호스트 브리지/ISA/IDE/ACPI/
   VGA(1234:1111)/네트워크/edu 장치가 전부 정상 인식됨을 확인. edu의
   BAR0(config offset 0x10, 1MB MMIO)를 매핑하고 Command 레지스터에서
   Memory Space+Bus Master 비트를 켠 뒤 `enableMsi`로 임시 벡터(0x23)를
   등록, edu의 인터럽트 발생 레지스터(0x60)에 값 0x1을 쓰자 실제로
   그 벡터로 MSI 인터럽트가 들어와 상태 레지스터(0x24)에서 정확히
   0x1을 읽고 ack 레지스터(0x64)에 되돌려 씀을 확인 - PCI 설정 공간
   읽기/쓰기, capability 탐색, MSI 메시지 프로그래밍, IDT 동적
   디스패치(kIsrHandler의 33-254 대역)까지 전체 경로가 실측으로
   검증됐다. edu가 없는 환경(장치 미연결)에서도 PCI 열거만 정상
   수행되고 나머지 코드는 실행 안 됨을 확인(회귀 없음). 검증 후
   임시 핸들러/BAR 매핑/MSI 활성화 호출 코드는 제거 - 영구 코드는
   `Pci::enumerate` 호출(부팅 로그)까지만 남겼다.

## 이번엔 안 한 것 (후속 과제로 남김)

- **MSI-X**: BAR 안의 별도 테이블(Table/PBA)에 메시지를 써야 해서
  구조가 다르다 - capability id 0x11 탐색까지는 `findCapability`가
  그대로 지원하지만, 실제 테이블 프로그래밍은 구현하지 않았다.
  MSI-X가 필요한 장치(다중 큐 NIC 등)를 실제로 붙일 때 추가.
- **MMCONFIG(MCFG 기반)**: 레거시 0xCF8/0xCFC는 256바이트 설정
  공간만 접근 가능(PCIe 확장 설정 공간 4KB는 MMCONFIG 필요) - MSI
  자체엔 지장 없었지만, 다른 PCIe 확장 기능을 나중에 쓸 때 재검토.
- **여러 MSI 벡터(Multiple Message)**: 지금은 장치가 여러 벡터를
  지원해도 항상 1개(MME=0)로 고정한다 - 인터럽트 부하 분산이 필요한
  고성능 장치를 다룰 때 확장.

## 미결 사항

- 없음(원래 PL의 미결 사항 - MMCONFIG를 지금 할지 - 는 PL 본문이
  이미 "v1은 레거시만"으로 자체 확정해 뒀던 내용이라 별도 결정 불필요
  했음).

## 재작업(2026-09-14, QU-7B67E05A/QU-4C2DD71C/QU-A62F3008/QU-7C65048E)

설계자가 위 "안 한 것" 세 가지를 전부 지금 시점에 구현하라고 확정
지시(QU-7B67E05A/QU-4C2DD71C: "MMCONFIG 및 0xCF8 둘 모두 고려하고
준비해야 Legacy fallback을 구현할 수 있다", QU-A62F3008: "실제 테이블
프로그래밍도 지금 시점에서 구현하여 검증하라", QU-7C65048E: "장치가
여러 벡터를 지원하면 부하 분산이 가능하도록 설계하라"). 세 가지 모두
구현하고 실측 검증했다.

1. **MMCONFIG(ACPI MCFG) 지원 추가**: `Acpi`에 MCFG 파싱(`hasMcfg`/
   `mcfgBaseAddress`/`mcfgStartBus`/`mcfgEndBus`, 첫 엔트리=세그먼트
   그룹 0만 지원) 추가. `Pci::init()`(Acpi::init 이후, Paging::init
   이후 호출)가 MCFG가 있고 시작 버스가 0이면 bus 0의 ECAM 전체
   1MiB(32 device × 8 function × 4KiB)를 `Paging::mapPage`로 매핑한다.
   `readConfig8/16/32`/`writeConfig16/32`는 이제 매번
   `kShouldUseMmconfig(bus)`로 분기 - bus 0이고 MMCONFIG가 활성화됐으면
   MMIO 포인터 접근, 아니면 레거시 포트 접근. **bus 0 이외의 버스는
   여전히 레거시로 폴백**(설계 의도 - 이 프로젝트가 실제로 만나는
   버스는 bus 0뿐이라 실용적 범위, 관계도 기록됨).
2. **MSI-X 실제 테이블 프로그래밍 구현**: `Pci::enableMsix(bus,
   device, function, tableIndex, vector, destApicId)` - Message
   Control에서 테이블 크기를 읽고, Table Offset/BIR 필드로 BAR와
   BAR 안 오프셋을 찾아 그 BAR(64비트 BAR 포함, `kReadBarAddress`가
   자동 감지)를 매핑한 뒤 해당 엔트리(16바이트: address_low/high,
   data, vector_control)를 직접 쓴다. Command 레지스터의 Memory
   Space+Bus Master를 켜고, 해당 엔트리 마스크 해제 + 함수 전체
   마스크(bit14) 해제 + MSI-X Enable(bit15) 설정까지 수행한다.
3. **다중 벡터 MSI(부하 분산)**: `Pci::enableMsiVectors(bus, device,
   function, requestedCount, preferredBase, destApicId, outBaseVector,
   outGrantedCount)` - Message Control의 Multiple Message Capable로
   장치 한도를 확인하고, requestedCount를 2의 거듭제곱으로 내림한 뒤
   장치 한도로 다시 캡한다. 실제로 확보되는 벡터 개수의 배수로
   preferredBase를 정렬(하드웨어가 벡터 번호 하위 비트를 델리버리
   인덱스와 OR하기 때문). `enableMsi`는 이제 이 함수에 위임하는
   벡터-1개 래퍼가 됐다. `enableMsi`/`enableMsiVectors` 모두
   destApicId가 8비트(고전 MSI/IOAPIC과 동일한 목적지 필드 제약)를
   넘으면 false.
4. **검증(실측, 2026-09-14, QEMU 8.2.2)**:
   - MMCONFIG 경로: `-machine q35`(ICH9, 실제 MCFG 보유)에서 PCI
     열거가 MMCONFIG로 정상 동작(`PCI config access=mmconfig+legacy`
     로그), edu 장치의 `enableMsi`가 MMCONFIG 경유로도 실제 인터럽트를
     발생시킴을 확인(`fired=yes`). 기본 i440fx(MCFG 없음, 레거시
     전용)에서도 동일 테스트가 그대로 성공해 레거시 폴백 경로에
     회귀가 없음을 확인.
   - MSI-X: `virtio-net-pci-non-transitional`(vendor 0x1af4, MSI-X
     테이블 크기 4)에서 엔트리 0을 프로그래밍(vector=0x41) 후
     재조회 - Message Control의 Enable/FunctionMask 비트, 그리고
     테이블 엔트리의 address_low/data/vector_control이 쓴 값과 정확히
     일치함을 확인. 이어서 엔트리 1을 다른 벡터(0x42)로 별도
     프로그래밍해도 엔트리 0이 덮어써지지 않고 두 슬롯이 독립적으로
     유지됨을 확인 - 부하 분산 시나리오(서로 다른 벡터를 서로 다른
     코어로 분산)의 전제인 "엔트리별 독립 프로그래밍"이 실제로
     동작함을 실측했다. 이 장치는 소프트웨어 트리거 레지스터가 없어
     드라이버 없이 스스로 인터럽트를 발생시킬 수 없으므로, "실제
     인터럽트 발동"까지는 검증 범위에 넣지 않았다(레지스터
     프로그래밍/라운드트립 레벨 검증).
   - 다중 벡터 MSI(고전, Multiple Message): edu(MMC=0, 1벡터 한도)와
     ICH9 AHCI 컨트롤러(q35 내장, MMC=0)에 4개 벡터를 요청해 실제로
     1개로 정확히 캡됨을 확인 - 협상/정렬 로직 자체는 검증됐으나,
     **QEMU 표준 장치 중 MMC>0(진짜 다중 벡터)를 노출하는 고전 MSI
     장치를 찾지 못했다**(현대 다중 큐 장치는 전부 MSI-X를 쓰지
     classic MSI의 Multiple Message를 안 씀). 이 부분은 "협상 로직이
     capped case에서 올바르게 동작함"까지만 실측되고, "실제
     grantedCount>1이 나오는 경우"는 관계도에 남기고 실물 장치가
     필요해질 때 재검증하기로 한다(예: 리얼 하드웨어이거나, MMC>0을
     흉내내는 커스텀 QEMU 장치).
   - 디버깅 중 발견한 두 가지 실제 버그도 함께 수정: (a) MSI 트리거
     전 Bus Master Enable을 켜지 않아 QEMU가 "Invalid write ...
     rejected"를 내던 문제, (b) 인터럽트 핸들러 안에서 비재진입
     Serial 락을 잡으려다 데드락 나던 문제. 그리고 이 두 개를 고친
     뒤에도 남아있던 진짜 원인 - **`sti`(인터럽트 활성화) 호출
     이전에 인터럽트 대기 `hlt` 루프를 뒀던 순서 버그**(IF=0이면
     hlt가 어떤 인터럽트로도 깨어나지 않는다) - 를 찾아 고쳐서 최종
     검증을 완료했다. 세 가지 모두 관계도에 기록(`docs relation
     list`로 kmain.cpp/pci.cpp/serial.cpp/acpi.cpp 참고).
   - 임시 검증 코드(edu MSI 발동 테스트, virtio-net MSI-X 테이블
     검증, AHCI 다중벡터 협상 테스트, MSI 스캐너)는 전부 제거 -
     영구 코드는 `Pci::init()` 호출 + `PCI config access=...` 로그
     까지만 남겼다.
