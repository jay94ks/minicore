# AHCI(SATA 스토리지 컨트롤러) 드라이버 — 설계 제안

설계자 지시(2026-09-14, 메시지) - "AHCI와 PnP 그리고 USB도 설계
제안서 작성해줘." PnP(SP-9DD4F3EA, 장치 자동 인식/핫플러그
프레임워크)를 통해 발견된 AHCI 컨트롤러를 실제로 구동하는 드라이버
설계다.

## 1. 배경

AHCI(Advanced Host Controller Interface)는 SATA 컨트롤러의 사실상
표준 인터페이스(Intel 사양, PCI 클래스 코드 `0x01`(Mass Storage) /
서브클래스 `0x06`(SATA) / prog-if `0x01`(AHCI 1.0)). SP-8B6B8D25
§2-A 원칙에 따라 이 드라이버는 **devmgr(유저랜드) 안에서 구동**되고,
커널은 PnP 제안(SP-9DD4F3EA §3.3)이 정의한 IO 권한 부여 syscall로 MMIO
BAR(ABAR, BAR5)와 인터럽트 벡터만 내준다.

## 2. AHCI 하드웨어 모델 요약

- **HBA(Host Bus Adapter) 메모리 레지스터**: BAR5가 가리키는 MMIO
  영역 하나(보통 4KiB 이상) - 전역 레지스터(GHC, CAP, IS 등) +
  포트별 레지스터 블록(최대 32포트, 포트당 0x80바이트) 배열.
- **명령 리스트(Command List)**: 포트마다 최대 32개 커맨드 슬롯 -
  각 슬롯은 Command Header(FIS 종류, PRDT 개수 등) + FIS(Frame
  Information Structure, ATA 명령을 SATA 프레임으로 감싼 것) +
  PRDT(Physical Region Descriptor Table, DMA 스캐터-개더 목록)를
  가리키는 포인터 구조 - 전부 물리 메모리에 있어야 하고, 컨트롤러가
  DMA로 직접 읽는다.
- **동작 흐름**: (1) 커맨드 리스트/FIS/PRDT/데이터 버퍼용 물리 메모리
  확보 → (2) Command Header에 채워 슬롯에 등록 → (3) 포트의
  Command Issue(CI) 레지스터에 슬롯 비트 세팅 → (4) 컨트롤러가 DMA로
  처리 후 인터럽트(포트별 Interrupt Status) → (5) 드라이버가 완료
  확인 후 자원 반납.

## 3. 설계 제안

### 3.1 계층 구조 (devmgr 내부)

```
[fs 서비스 등 상위 소비자]
        |  (블록 장치 read/write 요청 - Channel IPC, PL-C8648D4D 재사용)
        v
[AhciBlockDevice]  - 포트 하나 = 논리 블록 장치 하나로 노출
        |
[AhciController]   - HBA 초기화, 포트 스캔, 커맨드 슬롯 관리
        |
[HBA MMIO 레지스터] - PnP가 매핑해 준 가상주소로 직접 접근
```

- **`AhciController::init(mmioVirtAddr)`**: GHC.AE(AHCI Enable) 설정,
  CAP 레지스터로 포트 수/커맨드 슬롯 수 확인, PI(Ports Implemented)
  비트마스크로 실제 존재하는 포트만 순회해 `AhciPort` 인스턴스 생성.
- **`AhciPort`**: 포트 하나당 커맨드 리스트(1페이지)/FIS 수신
  버퍼(1페이지)를 확보(devmgr이 자기 프로세스 힙 또는 전용 DMA
  버퍼 풀에서 할당 - 아래 §3.2 참고), 슬롯 free-list 관리.
- **`AhciBlockDevice`**: `AhciPort` 하나를 감싸 "논리 블록 번호(LBA) +
  개수"로 읽기/쓰기하는 상위 API 제공 - fs 서비스가 이 API를
  Channel IPC로 호출한다(구체 syscall/Channel 프로토콜은 이 문서
  범위 밖 - PL-C8648D4D의 기존 Channel 패턴을 그대로 재사용 제안).

### 3.2 DMA 메모리 관리 (열린 문제 - §4 참고)

AHCI 커맨드 구조체/데이터 버퍼는 **물리적으로 연속**이어야 하고
컨트롤러가 직접 DMA로 접근하므로, devmgr(유저 프로세스)이 확보한
가상 메모리의 **물리 주소를 커널에게 알아내는 방법**이 필요하다 -
지금 이 프로젝트엔 유저 프로세스가 자기 페이지의 물리 주소를 알아낼
방법이 전혀 없다(§4 미결 1번). 두 가지 후보를 제안한다:

- (a) **커널이 DMA 버퍼를 대신 확보**: devmgr이 "N바이트 DMA 가능
  버퍼를 달라"고 syscall로 요청하면 커널이 `PageFrameAllocator`로
  물리적으로 연속인 프레임을 확보해 devmgr 주소공간에 매핑하고,
  그 물리 주소도 같이 알려준다(devmgr은 이 물리 주소를 그대로 AHCI
  커맨드 구조체에 채워 넣는다). **이 문서가 선호하는 방향** - 물리
  메모리 관리를 커널에만 집중시키는 기존 원칙(§2 6/7번)과 일치.
- (b) **유저 프로세스가 자기 페이지의 물리 주소를 조회하는 syscall**:
  범용성은 높지만 유저 프로세스에게 물리 주소 정보를 노출하는 것
  자체가 보안/추상화 측면에서 더 무겁다.

### 3.3 인터럽트 처리

PnP 제안(SP-9DD4F3EA §3.3)의 IO 권한 부여로 MSI/MSI-X 벡터를 배정받는다 - AHCI는
포트별 인터럽트를 하나의 벡터로 합치거나(single MSI) 포트마다
별도 벡터(MSI-X)를 쓸 수 있다 - v1은 **단일 MSI 벡터 + HBA의 전역
Interrupt Status(IS) 레지스터로 어느 포트가 완료됐는지 조회**하는
단순한 방식을 제안한다(포트 수가 많지 않은 v1 환경에서는 충분).

### 3.4 오류 처리

- 포트 오류(SATA 링크 끊김, 커맨드 타임아웃)는 포트별 SERR/TFD
  레지스터로 감지 - 발생 시 해당 슬롯의 요청을 실패로 완료 처리하고
  포트를 재시작(COMRESET) 하는 절차가 필요(AHCI 사양 10.4.2) - 세부
  절차는 구현 시점에 사양을 그대로 따르는 수준이라 별도 DC 불필요.

## 4. 아직 열려 있는 설계 영역

1. **DMA 가능 물리 메모리를 유저 프로세스가 어떻게 확보하는지**
   (§3.2) - 이 프로젝트의 프로세스 모델(PN-16CA347D)에 아직 없는
   개념이라 확정 필요. AHCI뿐 아니라 USB(벌크 전송 버퍼)도 동일하게
   필요로 하므로, 두 드라이버가 공유할 수 있는 공용 "DMA 버퍼 확보"
   syscall로 일반화해 제안한다.
2. **블록 장치 ↔ fs 서비스 프로토콜**: `AhciBlockDevice`가 노출할
   정확한 API(LBA 읽기/쓰기, TRIM, 캐시 플러시 등)는 fs 서비스
   설계와 맞물려야 한다 - fs 서비스 자체가 아직 설계되지 않음
   (SP-8B6B8D25 §3.1의 자리 표시만 있음).
3. **NCQ(Native Command Queuing) 지원 여부**: v1은 큐 깊이 1(한 번에
   커맨드 하나만 진행)로 단순화 제안 - 여러 커맨드 슬롯을 동시에
   사용하는 NCQ는 성능 최적화 단계에서 재검토.

## 5. 선행 조건

- PnP 프레임워크(SP-9DD4F3EA)의 IO 권한 부여 syscall.
- 프로세스 모델(PN-16CA347D) - devmgr 프로세스 자체.
- DMA 버퍼 확보 메커니즘(§4-1, 신규 설계 필요 - USB와 공유).
- Channel IPC(PL-C8648D4D, 이미 구현 완료) - 블록 장치 API 전달에
  재사용.
