# AHCI(SATA 스토리지 컨트롤러) 드라이버 — 설계 제안

## [정정, 2026-09-24, minicore-3c 세션] §3.1/§4-A/§5가 2026-09-20 이후
두 차례 더 뒤집힌 실제 구조를 반영 못 하고 있었음

이 문서가 마지막으로 갱신된 시점(§4-A, 2026-09-20) 이후 이 프로젝트
전체에 걸친 큰 구조 변경이 두 차례 더 있었는데, 이 문서엔 반영되지
않은 채 남아 있었다 - 직접 소스를 대조해 확인:

1. **`fs`는 더 이상 Process가 아니다** - §3.1이 여전히 "`fs` **프로세스**
   자신이 직접 수행"이라고 서술하지만, `fs`는 `SP-43331889`/
   `PN-D6A05E78`/`PN-615C48D5`(2026-09-20/21 완료)로 **Process 없는
   순수 커널 `KernelThread`**로 이미 흡수됐다(`SP-8B6B8D25` §2-A
   정정 각주 참고) - "프로세스"라는 표현 자체가 틀렸다.
2. **실제 파일 위치가 다르다** - §4-A가 인용하는 `minicore/devmgr/
   ahci.h/.cpp`는 더 이상 존재하지 않는다(확인: 저장소에 해당 경로
   없음) - 현재 실제 구현은 **`minicore/kernel/ahci.h/.cpp`**에 있다
   (fs가 커널에 흡수되며 그 소유 코드도 함께 옮겨짐).
3. **Channel IPC를 거치지 않는다** - §3.1의 계층도(`[fs 서비스 등
   상위 소비자] <- Channel IPC -> [AhciBlockDevice]`)와 §5의
   "Channel IPC(PL-C8648D4D)... 블록 장치 API 전달에 재사용"이라는
   서술 둘 다 더 이상 사실이 아니다 - 현재 `gAhciBlockDevice`
   (`fs.cpp`)는 `Ext4Driver`/`Fat32Driver`(`kernel::FileSystemDriver`
   구현체, `RM-C65F7760`의 `/sys/mnt` 항목 참고)가 **같은 KernelThread
   안에서 직접 함수 호출**로 소비한다 - IPC 메시지 왕복 자체가 없다
   (KernelThread가 된 이후로는 Channel IPC를 거칠 이유가 사라졌다는,
   `PN-452FF696`/`RM-C65F7760`이 이미 정리해 둔 사실과 정확히 일치).
4. **인터럽트 구독도 SP-71DA77B3 메커니즘을 통한다** - §3.3이
   "MSI/MSI-X 벡터를 배정받는다"고만 서술하지만, 실제로는
   `kSubscribeAhciInterrupt()`(`ahci.cpp:224`)가 `SP-71DA77B3`(인터럽트
   구독 서브시스템)의 `SubscribeInterrupt` 핸들러를 syscall 트랩이
   아니라 내부 재사용으로 호출한다(KernelThread 제출자이므로) -
   `RM-B5764185`/`RM-28225668` 갱신 시점에 함께 확인된 사실.

**결론**: §3.1~§3.5의 AHCI 컨트롤러/포트 초기화 로직(GHC.AE/CAP/PI
파싱, 커맨드 리스트/FIS 구성, NCQ 등) 자체는 여전히 정확하고 유효한
설계다 - 틀린 부분은 오직 "누가/어디서/어떤 경로로 이 로직을 호출
하는가"에 대한 상위 배선 서술뿐이다. 아래 §3.1/§4-A/§5 원문은 역사적
기록으로 보존하되, 이 정정 절을 정본으로 삼는다.

설계다.

## 1. 배경

AHCI(Advanced Host Controller Interface)는 SATA 컨트롤러의 사실상
표준 인터페이스(Intel 사양, PCI 클래스 코드 `0x01`(Mass Storage) /
서브클래스 `0x06`(SATA) / prog-if `0x01`(AHCI 1.0)). SP-8B6B8D25
§2-A 원칙에 따라 이 드라이버는 **devmgr(유저랜드) 안에서 구동**되고,
커널은 PnP 제안(SP-9DD4F3EA §3.3)이 정의한 IO 권한 부여 syscall로 MMIO
BAR(ABAR, BAR5)와 인터럽트 벡터만 내준다.

## 2. AHCI 하드웨어 모델 요약

- **HBA(Host Bus Adapter) 메모리 레지스터**: BAR5가 가리키는 MMIO
  영역 하나(보통 4KiB 이상) - 전역 레지스터(GHC, CAP, IS 등) +
  포트별 레지스터 블록(최대 32포트, 포트당 0x80바이트) 배열.
- **명령 리스트(Command List)**: 포트마다 최대 32개 커맨드 슬롯 -
  각 슬롯은 Command Header(FIS 종류, PRDT 개수 등) + FIS(Frame
  Information Structure, ATA 명령을 SATA 프레임으로 감싼 것) +
  PRDT(Physical Region Descriptor Table, DMA 스캐터-개더 목록)를
  가리키는 포인터 구조 - 전부 물리 메모리에 있어야 하고, 컨트롤러가
  DMA로 직접 읽는다.
- **동작 흐름**: (1) 커맨드 리스트/FIS/PRDT/데이터 버퍼용 물리 메모리
  확보 → (2) Command Header에 채워 슬롯에 등록 → (3) 포트의
  Command Issue(CI) 레지스터에 슬롯 비트 세팅 → (4) 컨트롤러가 DMA로
  처리 후 인터럽트(포트별 Interrupt Status) → (5) 드라이버가 완료
  확인 후 자원 반납.

## 3. 설계 제안

### 3.1 계층 구조 (fs **프로세스 자신** 내부 - [뒤집힘, 2026-09-20])

**[뒤집힘, 2026-09-20, QU-1FB6A7A4 답변 - "블록 디바이스는 그냥
아예 fs한테 던져버려. 인식/인식 해제까지 전부."]** 아래 [갱신,
2026-09-15] 절이 확정했던 "devmgr이 매칭 성공 시 fork()로 스폰하는
별도 자식 프로세스" 구조는 **폐기됐다** - 그 자식이 개설하는 이름
없는 Channel을 fs가 어떻게 찾아 연결하는지에 대한 설계 공백
(QU-1FB6A7A4가 실제로 발견)의 답으로, devmgr의 PnP 매칭·fork() 경로
자체를 블록 스토리지 장치에 대해서는 아예 타지 않는 것으로
확정됐다 - **PCI 열거(`EnumerateDevices`)/AHCI 클래스 매칭/
`RequestIoPermission`/HBA 초기화 전부를 `fs` 프로세스 자신이 직접
수행**한다(`minicore/fs/main.cpp`의 `kProbeAndInitAhci()`,
PN-F60E405A 완료). `fs`가 이미 §3.1의 `AhciBlockDevice`/
`FileSystemDriver` 양쪽을 다 갖고 있는 프로세스이므로, 같은
주소공간 안에서 통째로 실행하면 Channel IPC 핸드오프 자체가 필요
없어진다는 것이 이 결정의 핵심 - 아래 로직 계층도는 "devmgr 자식
프로세스"를 "fs 프로세스"로 바꿔 읽으면 그대로 유효하다. devmgr은
더 이상 AHCI(블록 스토리지 일반)를 다루지 않는다 - devmgr의 PnP
매칭·fork() 프레임워크 자체는 향후 비-스토리지 장치 클래스를 위해
계속 존재한다.

## [폐기된 이전 설계, 2026-09-15, 참고용으로 보존] devmgr 자식 프로세스 구조

**[갱신, 2026-09-15, SP-9DD4F3EA §3.2/§4a-3 답변 반영]** 이 계층
전체는 devmgr **자신의 프로세스가 아니라**, devmgr이 매칭 성공 시
스폰하는 별도 **자식 프로세스** 안에서 실행된다(설계자 지시 -
"devmgr 인스턴스는 무조건 1개고 그 밑에 자식 프로세스들이 달려야
하는 구조로만 설계해야 해") - 코드는 devmgr 실행 파일에 정적
링크돼 있지만 실행 시점엔 격리된 별도 프로세스다. 아래 §3.2의
"devmgr이 자기 프로세스 힙에서 할당"이라는 서술은 정확히는 **이
자식 프로세스 자신의 힙**을 가리키는 것으로 정정한다 - 논리
계층도(아래)는 그대로 유효하다.

```
[fs 서비스 등 상위 소비자]
        |  (블록 장치 read/write 요청 - Channel IPC, PL-C8648D4D 재사용)
        v
[AhciBlockDevice]  - 포트 하나 = 논리 블록 장치 하나로 노출
        |
[AhciController]   - HBA 초기화, 포트 스캔, 커맨드 슬롯 관리
        |
[HBA MMIO 레지스터] - PnP가 매핑해 준 가상주소로 직접 접근
```

- **`AhciController::init(mmioVirtAddr)`**: GHC.AE(AHCI Enable) 설정,
  CAP 레지스터로 포트 수/커맨드 슬롯 수 확인, PI(Ports Implemented)
  비트마스크로 실제 존재하는 포트만 순회해 `AhciPort` 인스턴스 생성.
- **`AhciPort`**: 포트 하나당 커맨드 리스트(1페이지)/FIS 수신
  버퍼(1페이지)를 확보(devmgr이 자기 프로세스 힙 또는 전용 DMA
  버퍼 풀에서 할당 - 아래 §3.2 참고), 슬롯 free-list 관리(컨트롤러가
  광고하는 슬롯 수만큼 - 아래 §3.5의 NCQ 동시 발급에도 그대로 쓰임).
- **`AhciBlockDevice`**: `AhciPort` 하나를 감싸 "논리 블록 번호(LBA) +
  개수"로 읽기/쓰기하는 상위 API 제공 - fs 서비스가 이 API를
  Channel IPC로 호출한다(구체 syscall/Channel 프로토콜은 이 문서
  범위 밖 - PL-C8648D4D의 기존 Channel 패턴을 그대로 재사용 제안).

### 3.2 DMA 메모리 관리

AHCI 커맨드 구조체/데이터 버퍼는 **물리적으로 연속**이어야 하고
컨트롤러가 직접 DMA로 접근하므로, devmgr(유저 프로세스)이 확보한
가상 메모리의 **물리 주소를 커널에게 알아내는 방법**이 필요했다(원래
§4 미결 1번). **[해결, 2026-09-14] DMA 버퍼 관리자(SP-39F18E30)가
이 문제를 커널 syscall(`AllocDmaBuffer`/`FreeDmaBuffer`)로 구체화**
했다 - 커널이 `PageFrameAllocator`로 물리적으로 연속인 프레임을
확보해 devmgr 주소공간에 매핑하고 물리 주소도 함께 알려주는 방향
(이 문서가 원래 선호했던 (a) 후보)이 그대로 채택됐다. AHCI의 모든
DMA 구조체(Command List/FIS/PRDT)는 64비트 물리 주소 필드를 쓰므로
`AllocDmaBufferArgs::physAddrLimit = 0`(제한 없음)으로 호출하면 된다.

### 3.3 인터럽트 처리

PnP 제안(SP-9DD4F3EA §3.3)의 IO 권한 부여로 MSI/MSI-X 벡터를 배정받는다 - AHCI는
포트별 인터럽트를 하나의 벡터로 합치거나(single MSI) 포트마다
별도 벡터(MSI-X)를 쓸 수 있다 - v1은 **단일 MSI 벡터 + HBA의 전역
Interrupt Status(IS) 레지스터로 어느 포트가 완료됐는지 조회**하는
단순한 방식을 제안한다(포트 수가 많지 않은 v1 환경에서는 충분).

### 3.4 오류 처리

- 포트 오류(SATA 링크 끊김, 커맨드 타임아웃)는 포트별 SERR/TFD
  레지스터로 감지 - 발생 시 해당 슬롯의 요청을 실패로 완료 처리하고
  포트를 재시작(COMRESET) 하는 절차가 필요(AHCI 사양 10.4.2) - 세부
  절차는 구현 시점에 사양을 그대로 따르는 수준이라 별도 DC 불필요.
  NCQ 명령 도중 오류가 나면 개별 슬롯이 아니라 **포트 전체**가
  정지된다(AHCI 사양 - NCQ 오류는 포트 단위로 보고됨) - 이 경우
  아래 §3.5가 정의한 진행 중인 모든 슬롯을 전부 실패로 간주하고
  동일한 COMRESET 절차를 거친다.

### 3.5 NCQ (Native Command Queuing) — [확정, 2026-09-18, 설계자 지시]

v1의 큐 깊이 1(§4에서 재검토 대상으로 남겨 뒀던 단순화)을 폐기하고,
컨트롤러/장치가 지원하는 만큼 여러 커맨드를 동시에 진행 중(in-flight)
상태로 둘 수 있도록 확정한다.

- **동시 실행 가능 슬롯 수 산정**: 컨트롤러 쪽 상한은
  `AhciController::init`이 이미 읽는 `CAP.NCS`(Number of Command
  Slots, 0-based)에서 `CAP.NCS + 1`로 구한다. 장치 쪽 상한은
  `AhciPort` 초기화 직후 비-NCQ IDENTIFY DEVICE 명령(슬롯 0 하나만
  써서 발급)으로 얻은 응답 데이터의 워드76 비트8(NCQ 지원 여부)과
  워드75 비트[4:0]+1(큐 깊이)로 판별한다. 실제 동시 사용 가능 슬롯
  수는 `min(컨트롤러 상한, 장치 큐 깊이)` - 장치가 NCQ를 지원하지
  않으면 이 값은 1이 되어 기존 v1 동작(슬롯 1개, §3.1의 free-list가
  1개짜리로 줄어든 특수 사례)과 코드 경로 변경 없이 자연스럽게
  일치한다(별도 분기 불필요).
- **발급 절차**: 비-NCQ 읽기/쓰기는 `PxCI`(Command Issue)에 슬롯
  비트를 세팅하는 것만으로 발급되지만, NCQ 명령(READ FPDMA QUEUED /
  WRITE FPDMA QUEUED)은 그 전에 `PxSACT`(SATA Active) 레지스터에
  먼저 슬롯 비트를 세팅해야 발급된다(AHCI 사양 §5.5.1). 여러 슬롯을
  동시에 준비했다면 각각 `PxSACT`를 먼저 세팅한 뒤 `PxCI`에 해당
  비트들을 세팅해 진짜 동시 진행 상태로 만든다.
- **완료 판별**: NCQ 명령은 완료될 때 순서를 보장하지 않는다(컨트롤러가
  자체 스케줄링으로 재정렬할 수 있음) - 완료된 슬롯은 컨트롤러가
  `PxSACT`에서 해당 비트를 클리어하고 `PxIS.SDBS`(Set Device Bits FIS
  Interrupt) 비트를 세팅해 알린다. 인터럽트 핸들러는 직전에 자신이
  기록해 둔 "발급된 슬롯 비트마스크"와 인터럽트 시점의 `PxSACT`를
  비교해, 새로 클리어된 비트들을 "이번에 완료된 슬롯"으로 판별한다 -
  §3.3이 이미 다루는 "IS 레지스터로 어느 포트가 완료됐는지" 확인 위에,
  포트 내부적으로 이 `PxSACT` 비교 한 단계가 NCQ 한정으로 추가된다.
