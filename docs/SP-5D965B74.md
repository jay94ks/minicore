# procfs — 커널 상태 노출 파일시스템 스키마 설계 제안

DS-D4E5C451이 "아직 열려 있는 설계 영역"으로 남겨 둔 procfs 스키마를
구체화한다(QU-4B14289E 답변, PN-48F0F90C). SP-8B6B8D25 §2 항목13
("procfs 루트")과 §4의 경로 표(`sys/live/proc/`)가 요구하는 자리를
채운다.

## 1. 배치 - 새 마운트 아님, `/sys/live` 안의 새 하위 경로

`/sys/live`는 이미 `LiveFs`(SP-7CC5693A §2.4, `KernelFsDriver`
구현체)가 통째로 마운트해 `named/`/`initrd.cpio`/`kernel/<name>`
세 하위 경로를 처리하고 있다(RM-C65F7760). procfs도 **별도
`MountTable::mountKernel("/sys/live/proc", ...)` 호출로 새 마운트를
만들지 않고, `LiveFs`가 이미 하는 것과 동일하게 자기 자신의
`relPath`가 `proc/`로 시작하면 위임하는 네 번째 하위 경로로
추가한다** - `named`/`initrd.cpio`/`kernel`과 완전히 대칭인 구조.
별도 `ProcFs` 클래스(`AsyncTaskHandler` 아님, 순수 헬퍼)를
`minicore/kernel/procfs.h/.cpp`에 새로 만들고 `LiveFs::onExec`이
`proc/` 접두사를 보면 그 헬퍼의 정적 메서드로 위임한다(문자열 파싱/
처리 로직을 `livefs.cpp` 한 파일에 계속 몰아넣지 않기 위한 순수
코드 정리 - 관측 가능한 동작은 "네 번째 하위 경로 추가"와 동일).

## 2. v1 스키마 - `self`만, 임의 pid 열람은 하지 않는다

**핵심 제약(보안)**: 이 커널엔 프로세스 ID → `Process*` 를 안전하게
되돌리는 전역 조회 수단이 없다(`Kill`/`DebugAttach`가 이미 마주친
문제와 정확히 같음, `QU-764C5624`에서 설계자 답변 대기 중) - 임의의
`targetProcessId`를 검증 없이 `reinterpret_cast`해 역참조하면 Channel/
Bridge에서 이미 겪은 것과 같은 임의 포인터 역참조 보안 공백이 된다.
procfs가 "경로 문자열로 프로세스를 지정"하는 인터페이스인 이상 이
문제를 피해갈 수 없으므로, **v1은 `Kill`/`DebugAttach`와 동일한
원칙(호출자 자신 또는 직계 자식만) 대신 그보다도 더 좁게 "호출자
자기 자신만" 허용한다** - 다른 프로세스(자식 포함)의 정보 열람은
이번 증분에 포함하지 않는다(§6 "남은 것" 참고, 필요해지면
`QU-764C5624` 답변 이후 자식까지 확장).

```
/sys/live/proc/self/status   - 호출자 자신의 정보(§3)
```

`self`는 심볼릭 링크가 아니다(이 VFS엔 심볼릭 링크 개념 자체가 없음,
SP-7CC5693A 범위 밖) - `LiveFs`/`ProcFs`가 `relPath`의 첫 세그먼트가
문자 그대로 `self`일 때 "이 Open을 제출한 호출자 자신"으로 특별
취급하는 예약어일 뿐이다. `self` 대신 실제 pid 숫자 문자열을 받는
것은 v1 범위 밖(§6).

## 3. `status` 파일 포맷 - 고정 텍스트, 파싱 가능한 `key: value` 줄

Linux procfs 관례를 그대로 차용한다(새 포맷을 발명하지 않음) - 한
줄에 하나씩 `key: value\n`, 순서 고정, 라인 추가는 이후 증분에서
끝에만 덧붙인다(기존 파서 하위호환):

```
Pid:    140737488355328
ParentPid: 140737488351232
Role:   Normal
Zombie: 0
ThreadState: Running
```

- `Pid`/`ParentPid`: 기존 전체 syscall 계층(`SpawnProcess`/`Wait`/
  `Kill`/`DebugAttach`)이 이미 쓰고 있는 것과 정확히 같은 값 -
  `reinterpret_cast<int64_t>(Process*)`를 10진수로 찍은 것(§11
  QU-764C5624 문서 주석이 "프로세스 ID 체계, 아직 열려 있는 설계
  영역"이라고 남겨 둔 바로 그 잠정 값 - procfs가 새 체계를 만들지
  않고 기존 잠정 체계를 그대로 노출할 뿐이다. 그 체계가 나중에
  바뀌면 이 필드의 값 형식도 자동으로 같이 바뀐다). 부모가 없으면
  (orphanRoot 등) `ParentPid: -1`.
- `Role`: `Process::role`(`ProcessRole::Normal`/`KernelService`)을
  그대로 문자열화.
- `Zombie`: `Process::isZombie`를 `0`/`1`로.
- `ThreadState`: `mainThread`가 있으면 `Task::state`(`Ready`/
  `Running`/`Blocked`/`Zombie`)를 문자열화, 없으면 `None`.

정수/불리언 값이라 v1 libjson(`SP-CCACB192`, 아직 미구현) 완성을
기다릴 필요가 없다 - 고정 포맷 텍스트로 충분하고, JSON화가 필요해지면
나중에 별도 `status.json` 파일을 추가하는 식으로 확장 가능(기존
`status` 텍스트 파일은 유지).

## 4. `KernelFsDriver` 오퍼레이션 매핑

`mount_table.h`의 9개 op 중 실제 의미 있는 것만:

- **Open**(`relPath == "self/status"`): 새 `FileHandle`을 발급하되,
  실제 콘텐츠는 미리 만들지 않는다 - Read 시점에 그때그때 스냅샷을
  만든다(status는 매 순간 바뀌는 값이라 open()~read() 사이에 갱신될
  수 있음, procfs 관례와 동일). `relPath`가 그 외 값이면
  `VfsError::NotFound`.
- **Read**: 핸들이 가리키는 게 `self/status`면 §3 포맷으로 문자열을
  생성해 `offset`부터 `len`만큼 복사(기존 `LiveFs::initrd.cpio`의
  offset-슬라이스+EOF 관례와 동일 패턴 재사용).
- **Close**: 핸들 반납(v1은 상태 없는 핸들이라 사실상 아무 일도 안
  해도 무방하지만, 관례상 유효하지 않은 핸들에 다시 Close/Read하면
  `VfsError::InvalidHandle`).
- **Write/Mkdir/Rmdir/Unlink**: 항상 `PermissionDenied`(LiveFs와
  동일 - 읽기 전용 뷰).
- **Stat**: `self/status`면 `size`=그 순간 포맷팅한 문자열 길이,
  `isDirectory=false`. 그 외 `NotFound`.
- **Readdir**: `entryCount=0`(디렉터리 나열 ABI 자체가 이 프로젝트
  전체에 아직 없음, `mount_table.h` 기존 "v1 축소 범위" 주석과 동일한
  이유 - 새 설계 아님).

**호출자 식별**: `Open`을 실은 `AsyncTask::submitterTask.lock()`으로
얻는다(`PN-5BBD4301`이 확립한, `onExec()` 안에서 `Scheduler::
currentTask()`를 쓰지 않는 유일하게 안전한 패턴) - `self`가 가리키는
`Process`는 이 제출자 `UserThread::process.lock()`이다.

## 5. 왜 별도 `ProcFs` 클래스인가 (구현 세부, 새 DC 불필요)

`LiveFs`에 네 번째 `if (relPath가 "proc/"로 시작)` 분기를 더
추가하는 대신 별도 파일/클래스로 뽑는 이유는 순수 코드 구성 판단이다
- `livefs.cpp`가 이미 `named`/`initrd.cpio`/`kernel/<name>` 세 갈래
분기를 담고 있어 더 커지면 한 파일의 책임이 과도해진다는 판단(RM-23F4B687
§4 "실측 후 조정" 범주) - `LiveFs::onExec`은 `relPath`의 첫
세그먼트만 보고 네 곳 중 하나로 위임하는 라우터 역할만 유지한다.

## 6. 남은 것 (이번 증분 범위 밖)

**[갱신, 2026-09-17, 설계자 의견(opinion) 반영]** 아래 세 항목은
설계자가 명시적으로 "이번에 설계 시작"을 지시해, 더 이상 막연한
"범위 밖" 메모가 아니라 각각 독립된 `PN-*` 계획으로 분리 등록됐다 -
이 문서(SP-5D965B74) 자체는 여전히 self-only v1 스키마만 확정하고,
아래 계획들이 완료되며 그 결과를 이 문서에 §반영한다:

- **`self` 외 임의/자식 pid 열람**(`/sys/live/proc/<pid>/status`
  일반화) - **`PN-85FA4992`**로 분리 등록. §2가 원래 들었던 이유(pid
  → Process* 안전 해석 수단 부재)는 `SP-9CB55C5B`의
  `kResolveProcessId()`로 이미 해소됐으나, 그 자리를 대신하는 진짜
  블로커는 권한 판정이다 - `QU-78E4159E` 답변으로 이 판정 전체가
  Linux 유사 uid/gid+RWX+root 체계(`PN-617F4E52`, 아직 미설계)로
  확정됐으므로, `PN-617F4E52` 완료 전까지는 "직계 자식만" 같은 축소판을
  이 문서가 독자적으로 발명하지 않는다(CLAUDE.md 규칙 4). 참고:
  `QU-764C5624`는 이 QU-78E4159E로 대체·확장돼 더 이상 별도로
  추적하지 않는다.
- **`meminfo`/`uptime`류 커널 전역 통계 파일** - **[완료, 2026-09-17,
  `PN-0C282BB7`, commit 3b7e6f7]** `/sys/live/proc/meminfo`
  (`MemFreeKb`/`NumaNodeCount`/`MemFreeNode<N>Kb` - `PageFrameAllocator`가
  실제로 추적하는 값만, `MemTotal`류는 미보유라 미포함)와
  `/sys/live/proc/uptime`(`UptimeSeconds`/`UptimeCentiseconds` -
  `Timer::tickCount()`가 100Hz 고정임을 확인해 그대로 재사용)로
  구현 완료. 특정 프로세스에 안 매이는 전역 정보라 `self`의 "호출자
  자신만" 제약과 무관하게 항상 허용 - `self/status` 핸들과는
  `kProcFsGlobalHandleBit`(procfs.h)로 구분해 절대 충돌하지 않는다.
  QEMU 무-initrd 베이스라인에서 open+read 왕복 실측 검증 완료(세부는
  `PN-0C282BB7` 참고).
- **디렉터리 나열(`readdir`)** - **`PN-770A28FB`**로 분리 등록.
  procfs만의 문제가 아니라 `mount_table.h`/`LiveFs`까지 포함한 VFS
  전체 ABI 공백이라, procfs 문서 단독이 아니라 `SP-7CC5693A` 레벨의
  공통 설계로 범위를 넓혀 등록했다.
- **실제 유저 syscall 경로** - `LiveFs`와 완전히 동일한 상황
  (`SP-2AAD7C8D §9` Open/Read syscall 자체가 아직 미착수) - 이번
  증분은 `KernelFsDriver` 인터페이스 구현까지만, 실제로 유저
  프로세스가 이 경로를 열 수 있게 되는 건 §9 착수 이후(이 항목은
  설계자 의견 대상이 아니라 그대로 유지).
