## 배경

`SP-30FCC8AE` §1-B와 그 재구성 문서 `SP-CC1CF30E` §7은 sudo/su 메커니즘의
큰 방향(sudoers류 자격을 가진 사용자가 특정 절차로 root 권한을 얻는다,
setuid 비트 활용)만 확정하고, 구체적인 5개 항목을 "착수 세션이
구체화"로 명시적으로 열어 뒀다. `PN-24A2B6F5`(authmgr E2E) 재착수
현황 정리 중 이 항목들을 실제로 구체화하려 했으나, 각각이 이
프로젝트의 다른 핵심 서브시스템(ELF 로더, syscall 설계, 인증 로직
소유권)에 새 개념을 도입하는 수준이라 임의로 결정하지 않고 설계자
확인을 받고자 한다(CLAUDE.md 규칙 4) - 권한 승격은 보안에 직접적인
영향을 주는 메커니즘이라 특히 신중하고자 한다.

## 결정이 필요한 지점 (SP-CC1CF30E §7 원문 그대로)

1. **sudoers류 멤버십 표현 방식** - 특정 `Gid`(다중 그룹 포함
   가능성, §6)에 속하면 자격을 주는 방식인지, authmgr 내부의 별도
   화이트리스트(예: `libkvdb`의 세 번째 Store)인지.
2. **특수 비트 S(Permission)의 의미 확정 여부** - `SP-30FCC8AE` §2가
   예약해 둔 이 비트가 "이 실행 파일은 실행 시 소유자 uid로 승격"
   이라는 Linux setuid 비트와 동일한 의미로 확정될지, 아니면 다른
   의미인지.
3. **승격이 일어나는 지점** - `exec()` 시점이라면 이 커널의 ELF
   로더(`minicore/libs/libelf`)가 지금 전혀 모르는 새 동작이 필요
   하다 - `SP-6BEAE0C1`(일반 프로세스 생성 syscall)과 교차 확인 필요.
4. **"sudo 명령 자체"가 syscall 레벨에서 무엇을 의미하는지** - 승격된
   uid로 새 프로세스를 실행하는 것인지, 기존(호출) 프로세스의 uid를
   바꾸는 것인지(이미 있는 `kSetuid()`/`Setuid` syscall을 그대로
   재사용하는 형태일 수도 있음).
5. **인증(비밀번호 요구 시) 로직의 소유권** - authmgr이 자신의
   `libkvdb`에 저장된 `passwordHash`(§8 SHA256, `libkcrypto`로 이미
   구현됨)를 authmgr **자신이** 검증하는지, 아니면 커널이 검증을
   요청/수행하는지 - `SP-CC1CF30E`는 "authmgr이 갖는 편이 아키텍처와
   일관적"이라고 참고 의견을 남겼으나 확정은 아니다.

## 참고 자료(이미 준비된 것)

- `kSetuid()`(`PN-B6DB692C`, 완료) - "누가 누구로 전환할 수 있는가"를
  시도-실패 방식으로 판정하는 기존 메커니즘, 항목4의 재사용 후보.
- `libkcrypto::sha256`(신규, `PN-85EDD3B5`) - 항목5의 비밀번호 검증에
  바로 쓸 수 있는 해시 함수, 이미 NIST 벡터로 검증 완료.
- `UserRecord::passwordHash`(`"algorithm:value"` 형식) - 필드 자체는
  이미 있으나 아무도 채우거나 검증하지 않음.

## [항목1/3-일부/5 구현+실측 검증 완료, 2026-09-28, commit c26c89a]

답변(항목1: authmgr 내부 계정별 화이트리스트, "sudo -u <root 아닌
유저>"도 허용 / 항목3: setuid가 내부적으로 호출하는 syscall
(`kSetuid()`) 내부에서 화이트리스트 확인 / 항목5: 인증은 authmgr
소유) 그대로 구현했다.

- authmgr에 `CheckSudoPermission`/`GrantSudoPermission` 요청 2종
  추가 - `(callerUid, targetUid)` 쌍의 존재 여부만 보는 새 libkvdb
  Store로 화이트리스트 관리(`GrantSudoPermission`은 `CreateUser`와
  동일한 이유로 아직 권한 검사 없음). **[정정, 2026-09-28]** 이
  자리의 "관리 API 설계는 아래 §2 참고"는 잘못된 참조였다(이 문서
  에는 §2가 없다 - 코드 주석의 "DC-1526389A 답변 대기"도 같은
  혼동으로, `DC-1526389A`는 실제로는 무관한 VFS uid/gid/mode
  메타데이터 공백을 다룬 문서다). 이 미해결 항목은 별도로
  `PN-812A139B`로 등록했다.
- `kSetuidOnExecImpl`(user_record.cpp)이 root/조상-자손 판정 모두
  실패(`PermissionDenied`)하면 `authmgr_client.h`의 새
  `kAuthmgrCheckSudoPermission()`으로 화이트리스트를 마지막 수단으로
  질의 - 통신 실패는 fail-closed(불허)로 처리.

`minicore/sudotest`(신규 E2E 검증 클라이언트, authtest/setuidtest와
동일한 관례로 영구 보존)로 서로 형제 관계인 두 uid(공통 조상만 있고
조상-자손 관계 아님) 사이에서 화이트리스트 등록 전
`PermissionDenied`, `GrantSudoPermission` 등록 후 성공을 커널 로그로
결정적으로 재현 확인(GRUB SMP1/SMP4). 표준 회귀 3종 클린.

**항목2/3-나머지/4(S 비트+exec-time 승격)는 이번 범위 밖** - 구현
착수 중 VFS에 파일 소유자(uid/gid/mode) 메타데이터 자체가 전혀 없다는
훨씬 근본적인 구조적 공백을 발견해 `DC-1526389A`로 별도 등록,
답변 대기 중이다.
