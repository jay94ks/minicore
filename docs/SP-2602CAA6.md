# 커널 이벤트 발행/구독(Kernel Event Notification) — 설계 제안

설계자 지시(2026-09-16, 채팅): "각 AsyncTask나 커널상 중요한 동작이
끝났을 때 푸시 알림처럼 메시지를 발신할 기반이 필요하네."

## 1. 현재 상태 (실측, 2026-09-16) - 이미 있는 두 인접 메커니즘

이 요구를 새 메커니즘 없이 기존 것으로 풀 수 있는지부터 확인했다 -
결론은 "부분적으로만" 이다:

1. **`AsyncTaskCompletion`(SP-F682B889 §9)** - 이미 "완료를 기다린다"는
   문제를 풀고 있지만, **정확히 그 AsyncTask를 제출한 쪽 하나만을
   위한 1:1 완료 신호**다(`waitSync()`/`waitAsync()`) - 여러 구독자가
   같은 완료를 동시에 받는 멀티캐스트가 아니다. "각 AsyncTask가 끝날
   때"는 다루지만 "푸시 알림처럼"이 함의하는 임의의 관찰자에게
   브로드캐스트하는 개념은 없다.
2. **`InterruptSubscription`(SP-71DA77B3, approved, 2026-09-16 실측
   확인 - **아직 코드 자체가 존재하지 않음**, `minicore/kernel/
   interrupt_subscription.h/.cpp` 미생성)** - 이미 정확히 이 문제의
   형태(구독자 슬롯 + 구독자별 이벤트 큐 + `WaitXxx` syscall + 우선
   순위/배타적 선별 + 프로세스 종료 시 자동 정리)를 하드웨어
   인터럽트 하나에 대해 완성도 높게 설계해 뒀다 - 다만 "벡터"(0-255
   고정 범위, IDT/ISR 전제)에 강하게 결합돼 있어 "AsyncTask 완료"나
   "커널상 중요한 동작"처럼 인터럽트가 아닌 이벤트에는 그대로 못
   쓴다.

**핵심 관찰**: SP-71DA77B3의 자료구조/API 모양(§3-§7)은 사실 인터럽트
전용이 아니라 **범용 발행/구독 패턴 그 자체**다 - "이 코드(vector)에
대해 누가 구독 중인가 → 이벤트 발생 시 구독자별 큐에 채우고 대기자를
깨운다"는 로직 어디에도 "인터럽트"라서 필요한 부분이 없다(IDT/ISR/
EOI는 그 앞단에서 "무엇이 이벤트를 발행시키는가"에만 관여). **그리고
아직 한 줄도 구현되지 않았으므로, 지금이 일반화하기에 가장 비용이
낮은 시점이다.**

## 2. 제안 - SP-71DA77B3의 구독자/큐/우선순위 패턴을 일반화

"인터럽트 벡터"를 구독 대상으로 못 박는 대신, 커널의 어떤 서브시스템
이든 새 **`EventTopic`**(가칭)을 하나 발급받아 "이 토픽에 대해
발행(publish)한다"고 선언할 수 있게 한다 - 인터럽트는 그 토픽 중
하나(발행자가 ISR인 경우)가 되고, AsyncTask 완료/기타 커널상 중요한
동작도 각자 자기 토픽을 발급받아 같은 구독 메커니즘을 재사용한다.

```cpp
namespace kernel {

// SP-71DA77B3 §2의 InterruptDelegation과 동형 패턴 - "부팅 시 한 번
// 발급받아 재사용"(RM-48E1E610/SP-F682B889 §3.1과 동일 관례).
using EventTopicId = uint32_t;

class EventTopicRegistry {
public:
    // 커널 서브시스템이 부팅/초기화 시 한 번 호출 - 그 이후 이
    // topicId로 publish()한다. 유저랜드가 임의로 새 토픽을 만들 수는
    // 없다(구독만 가능) - SP-71DA77B3의 InterruptDelegation allow-list
    // 정신과 동일하게, 발행자는 항상 커널 코드로 한정.
    static EventTopicId registerTopic();
};

// SP-71DA77B3 §4의 InterruptEvent/InterruptSubscription을 일반화 -
// "레지스터 상태" 대신 발행자가 자유롭게 채우는 작은 페이로드.
struct EventPayload {
    uint64_t code;     // 토픽 안에서 이벤트 종류를 더 세분화하고 싶을 때(옵션)
    uint64_t data0;
    uint64_t data1;
};

// SP-71DA77B3 §5 ISR 쪽 로직과 동형 - 다만 인터럽트 컨텍스트 한정이
// 아니라 커널 코드 어디서든(리액터 Task 컨텍스트 포함) 호출 가능.
class EventPublisher {
public:
    static void publish(EventTopicId topic, const EventPayload& payload);
};

// SP-71DA77B3 §3의 SubscribeInterrupt/WaitInterrupt/UnsubscribeInterrupt와
// 동형 - syscall 번호만 새로 예약(RM-48E1E610).
// SubscribeEvent(topic, priority, exclusive) -> error
// WaitEvent(topic, outPayload) -> error
// UnsubscribeEvent(topic) -> error

}  // namespace kernel
```

`SP-71DA77B3`의 §4(내부 자료구조)/§5(발행 시 순회 로직)/§6(정리)/
§7(에러 케이스)는 "vector"를 "topic"으로, "ISR"을 "발행 호출부"로
바꾸는 것 외에는 사실상 그대로 재사용 가능해 보인다(exclusive/
priority 개념도 "커널 서비스에게만 배타적으로 전달"이라는 취지가
인터럽트가 아닌 이벤트에도 동일하게 유효).

## 3. AsyncTask 완료를 이 메커니즘에 연결

`AsyncTaskHandler`(SP-F682B889 §3.1)의 `onExec`/`onFailure`/`onCancel`
구현부가 자기 작업이 끝나는 시점에 원하면 `EventPublisher::publish()`
를 직접 호출하는 방식을 제안한다 - **프레임워크가 모든 AsyncTask
완료마다 자동으로 발행하는 것이 아니라**, 각 `AsyncTaskHandler`가
"이 작업 종류는 다른 관찰자에게도 알릴 가치가 있다"고 판단할 때만
옵트인으로 쓴다(대부분의 AsyncTask는 제출자 하나만 결과를 알면
충분 - §9의 `AsyncTaskCompletion`으로 이미 충분하므로, 모든 완료를
무조건 발행하면 불필요한 오버헤드/노이즈가 된다).

## 4. 확인 필요 - 설계 확정 전 답 기다림 (CLAUDE.md 규칙 4)

1. **SP-71DA77B3와의 관계**: 아직 한 줄도 구현되지 않았으므로,
   SP-71DA77B3 자체를 이 일반화된 설계로 **개정**(벡터를 토픽의
   특수 사례로 재정의)할지, 아니면 SP-71DA77B3은 인터럽트 전용으로
   그대로 두고 이 문서가 **별개의 새 메커니즘**으로 나란히 존재할지
   확인 필요합니다. 전자는 중복 코드가 없어지지만 이미 승인된 문서를
   다시 여는 것이고, 후자는 당장은 더 간단하지만 구조가 거의 같은
   두 서브시스템이 생깁니다.
2. **"커널상 중요한 동작"의 v1 범위**: AsyncTask 완료 외에 구체적으로
   어떤 이벤트를 v1에 포함할지(예: 프로세스 종료, Signal 전달,
   VFS 마운트 변경 등) - 이 문서는 예시를 들지 않고 메커니즘만
   제안했습니다. 처음부터 구체적 이벤트 목록을 정할지, 아니면
   메커니즘만 먼저 확정하고 실제 발행 지점은 각 서브시스템이 필요할
   때 알아서 `registerTopic()`하는 식으로 열어 둘지 확인 필요합니다.
3. **구독자가 커널 코드 자신일 수도 있는지**: SP-71DA77B3은 구독자를
   전부 유저랜드 UserThread(syscall 경유)로 전제합니다 - 커널
   서브시스템 A가 커널 서브시스템 B의 이벤트를 (syscall 없이) 직접
   구독하고 싶은 경우도 이 메커니즘 범위에 포함해야 할지, 아니면
   그런 경우는 기존처럼 직접 함수 호출/콜백 등록으로 계속 풀지
   확인 필요합니다.
