**[독립 설계 확정, 2026-09-16, QU-3BFAC7C0 답변]** 설계자 답변:
**"'범용 이벤트 발행/구독'을 기존과 독립된 형태의 '이벤트 발행'

흡수/일반화하는 문서가 아니라, **그와 완전히 무관하게 독립 설계된
별도의 이벤트 발행 프레임워크**다. 본문 전체를 이 방향으로
재작성했다(2026-09-16) - 주요 변경:

- 구독자 슬롯/우선순위/배타적 선별을 SP-71DA77B3 §3-9를 참조로
  상속하던 방식(구 §5)을 폐기하고, 이 문서 자신의 더 단순한
  **멀티캐스트 구독 모델**(§5/§6/§7)로 교체했다.
- `GetEventDump`(인터럽트 레지스터 덤프 조회)를 제거했다 - 인터럽트
  전용 개념이라 SP-71DA77B3에만 남는다.
- `priority`/`exclusive` 파라미터를 제거했다 - "하나의 IRQ를 정확히
  누가 처리할지"를 정하는 인터럽트 라우팅 특유의 요구사항이었고,
  범용 발행/구독(1:N 멀티캐스트)에는 해당하지 않는다(§2 서베이가
  확인한 실사용처 - AsyncTask 완료 통지 등 - 는 전부 멀티캐스트로
  충분하다).
- 그 외(§2 서베이 결론, §3 3방향 발행 요구사항, QU-B76FB9CF의 유저
  노출 범위 결정 - 커널→유저 유지/유저→커널 제거)는 SP-71DA77B3과
  무관하게 설계자가 직접 확정한 내용이라 그대로 유지한다.

## 1. 배경

기존엔 커널 전역에 걸친 범용 알림 메커니즘이 없었다 -
`Idt::registerHandler`는 순수 C++ 콜백만, Channel IPC의
`AsyncTaskWaitQueue`는 "특정 syscall 제출자 하나"만 대상, 신호(Signal)
도 프로세스 하나를 타겟팅한다. SP-71DA77B3(인터럽트 구독)이
**인터럽트**라는 한 발행원에 대해서는 이미 완성도 높은 해법을 갖고
있지만(우선순위/배타적 선별/GPR 덤프 등 인터럽트 라우팅 특유의
요구사항까지 포함), 이 문서는 **그와 독립적으로**, 더 단순한 범용
"토픽 발행/구독" 모델을 새로 설계한다.

## 2. 기존 이벤트/알림 메커니즘 서베이 (Opinion 항목 2)

| 메커니즘 | 이 설계와 통합? | 이유 |
|---|---|---|
| **인터럽트 구독(SP-71DA77B3)** | **통합 안 함(완전 독립, 2026-09-16 롤백)** | 설계자 지시로 이 문서와 SP-71DA77B3을 서로 겹치지 않는 완전히 별개 메커니즘으로 유지한다 - 우선순위/배타적 선별/GPR 덤프 같은 인터럽트 라우팅 특유의 요구사항은 SP-71DA77B3에만 남는다. |
| **`AsyncTaskCompletion`(SP-F682B889 §9)** | **흡수 안 함(별도 유지)** | 정확히 "제출자 하나"를 위한 1:1 완료 신호로 의도적으로 설계됐다(멀티캐스트 불필요, 매 AsyncTask마다 토픽을 만드는 건 과설계) - RM-23F4B687 §4 원칙. 다만 **`AsyncTaskGroup`(PN-22438B73, QU-86DD998F)은 이 새 메커니즘을 채택할 후보**로 §12에 기록해 뒀다 - 별개로 남긴다. |
| **Signal 전달(SP-0666DB3C §4)** | **흡수 안 함(별도 유지)** | POSIX 시그널 시맨틱(마스킹 불가 신호, 체크포인트 전달, 강제 취소와의 §9 연동)이 이미 그 자체로 특수하고 확정돼 있다 - "구독"이 아니라 "타겟 프로세스에 즉시/체크포인트 전달"이라는 고유 배달 모델이라 억지로 토픽화하면 오히려 복잡해진다. |
| **Channel IPC(SP-1FBC0EEB)** | **흡수 안 함(별도 유지)** | 양방향 데이터 채널(요청-응답)이지 "이벤트 발행"이 아니다 - 1:N 브로드캐스트 개념 자체가 없다. |
| **pubreg(SP-B071E628, "공개 인터페이스" Registry)** | **흡수 안 함(별도 유지, 다른 층위)** | 프로세스가 자신의 제어 채널을 이름으로 노출/검색하는 디렉터리 서비스 - "이벤트가 발생했다"를 알리는 게 아니라 "이 서비스가 여기 있다"를 찾는 것이라 목적이 다르다. |

**결론**: 이 문서는 **어느 기존 메커니즘도 흡수하지 않는 완전히
독립적인 신규 프레임워크**다(2026-09-16 확정) - 각 기존 메커니즘은
저마다 다른 문제를 풀고 있어 억지로 통합하지 않는다(RM-23F4B687 §4
취지 - 과도한 일반화도 과설계의 일종).

## 3. 발행 방향 3가지 (Opinion 항목 3) - `TopicDirection`

```cpp
namespace kernel {

// registerTopic() 시점에 그 토픽이 허용하는 발행 방향을 선언한다.
// [2026-09-16, QU-B76FB9CF] 유저→커널(PublishEvent) 방향은 v1에서
// 완전히 제거됐다(아래 "유저→커널" 항목 참고) - 따라서 이 enum은
// 현재 유일한 값만 갖는다. 필요해지면(구체적 소비자가 생기면) 별도
// 질의로 재검토한다(CLAUDE.md 규칙 4).
enum class TopicPublishSource : uint32_t {
    KernelOnly,        // 커널→커널, 커널→유저만 - v1의 유일한 값
};

}  // namespace kernel
```

- **커널→커널**: `EventPublisher::publish()`를 커널 코드가 직접
  C++ 함수 호출로 부른다 - syscall 왕복이 없으므로 가장 저렴하다.
  구독자가 커널 코드 자신인 경우(§6 "커널 구독" API)도 같은 발행
  호출 하나로 커버된다 - 발행 로직(§7)은 구독자가 유저 UserThread인지
  커널 콜백인지 구분하지 않는다(둘 다 같은 구독자 목록에 섞여
  들어간다, 다만 구독자 종류 태그로 깨우는 방식만 다름 - §6).
- **커널→유저**: `SubscribeEvent`/`WaitEvent` syscall(§5/§6, 이 문서
  자체의 독립 설계)로 유저 UserThread가 토픽을 구독한다. 이 방향은
  **모든 토픽에서 기본 허용**(`TopicPublishSource`와 무관 - "누가
  발행하는가"가 아니라 "누가 구독하는가"의 문제라 별도 게이트가
  필요 없다).
- **유저→커널: v1에서 완전히 제거됨** [2026-09-16, QU-B76FB9CF]. 원래
  이 절이 제안했던 `PublishEvent` syscall/`UserAllowed` 옵트인 경로는
  구체적 소비자가 없는 채로 추론만으로 추가한 것이었고(§13 참고),
  설계자 답변(B+C 혼합)에 따라 v1 범위에서 완전히 빠진다 - 실제
  소비자가 나타나면 그때 별도 질의로 재도입 여부를 다시 검토한다.

## 4. 토픽 레지스트리

```cpp
namespace kernel {

using EventTopicId = uint32_t;

class EventTopicRegistry {
public:
    // 커널 서브시스템이 부팅/초기화 시 한 번 호출(SP-F682B889 §3.1과
    // 동일 관례 - 요청마다 등록/해제하지 않음).
    static EventTopicId registerTopic(TopicPublishSource source);

    // "이 토픽이 유저 발행을 허용하는가" - 현재는 PublishEvent가
    // 없어 호출부가 없지만, 향후 재도입 시를 대비해 API 자체는
    // 남겨둔다(§3).
    static bool allowsUserPublish(EventTopicId topic);
};

struct EventPayload {
    uint64_t code;     // 토픽 안에서 이벤트 종류를 세분화(옵션)
    uint64_t data0;
    uint64_t data1;
};

class EventPublisher {
public:
    // 커널 코드(ISR 포함, 인터럽트 컨텍스트에서도 호출 가능)가 직접
    // 부르는 발행 경로.
    static void publish(EventTopicId topic, const EventPayload& payload);
};

}  // namespace kernel
```

## 5. syscall API

```
SubscribeEvent(topic: EventTopicId) -> error
UnsubscribeEvent(topic: EventTopicId) -> error
WaitEvent(topic: EventTopicId, outPayload: EventPayload* [유저 메모리]) -> error
```

(`PublishEvent`는 QU-B76FB9CF 답변에 따라 v1에 없다 - §3 참고.
`GetEventDump`도 없다 - 인터럽트 레지스터 덤프 전용 개념이라
SP-71DA77B3에만 남는다, 2026-09-16 독립 설계 확정.)

**구독(`SubscribeEvent`)**: 호출한 UserThread를 그 토픽의 구독자
목록에 추가한다(동적 리스트 - 구독자 수 상한을 미리 알 수 없는 범용
상황을 가정, 인터럽트처럼 고정 슬롯을 미리 할당하지 않는다).
**우선순위/배타적 선택 개념은 없다** - 이 문서가 다루는 발행/구독은
전부 멀티캐스트(모든 구독자가 매 이벤트를 받는다)이므로 "누가
우선/독점으로 받는가"라는 질문 자체가 성립하지 않는다(그런 요구가
있는 발행원은 SP-71DA77B3의 영역).

**대기(`WaitEvent`)**: 구독 중인 토픽에 이벤트가 발행될 때까지
블로킹, 발행되면 `outPayload`에 채워 반환한다. **구독자별로 작은
pending 큐(고정 용량 N=8 - 설계자 확인이 필요 없는 구현 세부, 실측
후 조정 가능)를 둬서**, `WaitEvent`를 호출하지 않은 사이에 발행된
이벤트도 유실 없이 순서대로 쌓인다(큐가 가득 차면 가장 오래된 것부터
버린다 - "최근 이벤트가 더 중요하다"는 일반적 가정, 필요하면 토픽별로
뒤집을 수 있게 설계는 열어둔다).

**해제(`UnsubscribeEvent`)**: 구독자 목록에서 제거하고, 대기 중이던
`WaitEvent` 호출자를 `Cancelled`류 에러로 깨운다.

## 6. 커널 내부 구독 API (Opinion 항목 3 - 커널→커널)

```cpp
namespace kernel {

// 커널 서브시스템이 syscall 없이 직접 구독하는 경로 - 부팅/초기화
// 시 한 번 등록. 콜백은 발행 시점의 컨텍스트(ISR이면 인터럽트
// 컨텍스트, 커널 직접 호출이면 그 호출 컨텍스트)에서 그 자리에서
// 바로 호출된다 - **무거운 작업을 여기서 직접 하면 안 된다**
// (SP-F682B889 §1의 "ISR은 무거운 로직을 직접 실행하면 안 된다"
// 원칙이 여기도 동일하게 적용 - 콜백 안에서 `AsyncTask::submit()`
// 등으로 실제 작업은 리액터에 위임하는 게 권장 패턴).
using EventCallback = void (*)(EventTopicId topic, const EventPayload& payload);

class EventTopicRegistry {
public:
    // (위 §4에 이어)
    static void subscribeKernel(EventTopicId topic, EventCallback callback);
};

}  // namespace kernel
```

구독자 목록에 "유저 UserThread"와 "커널 콜백"이 같은 목록에 섞여
들어가되, `subscriber.kind`(`UserThread`/`KernelCallback`)로
구분한다 - 발행 로직(§7)이 깨울 때 `kind`를 보고 `UserThread`면
§5의 pending 큐에 적재 후 `AsyncReactor::submitCompletion()`으로,
`KernelCallback`이면 그 자리에서 직접 콜백을 호출한다.

## 7. 발행 로직 및 동시성

`EventPublisher::publish(topic, payload)`가 호출되면(ISR/커널 직접
호출 두 지점 - `PublishEvent`가 없으므로 syscall 처리부 지점은
없다) 그 토픽의 구독자 목록을 순회하며 각 구독자에게 멀티캐스트한다:

- `kind == UserThread`: 그 구독자의 pending 큐(§5)에 payload를
  push하고, `WaitEvent`로 블로킹 중이면 `AsyncReactor::
  submitCompletion()`으로 깨운다.
- `kind == KernelCallback`: 그 자리에서 콜백을 직접 호출한다(§6과
  동일 계약 - 무거운 작업 금지).

구독자 목록은 코어 간에 공유되는 자료구조이므로 Spinlock으로
보호한다(목록의 삽입/삭제/순회 전부 같은 락 하나로 직렬화 - 세밀한
락 분할 같은 최적화는 실측 후 필요하면 진행).

## 8. 정리

명시적 `UnsubscribeEvent` + 프로세스/UserThread 종료 시 자동 정리
(PN-40E976F2의 "사망 전파 목록" 재사용 - 이 패턴은 AsyncTask 등
여러 곳에서 이미 쓰는 범용 커널 서비스라, 재사용해도 SP-71DA77B3에
대한 설계 결합을 만들지 않는다).

## 9. 에러 케이스

- 존재하지 않는 토픽ID로 `SubscribeEvent`/`WaitEvent`/
  `UnsubscribeEvent` 호출: `InvalidArgument`.
- 구독하지 않은 토픽에 `WaitEvent`/`UnsubscribeEvent` 호출:
  `InvalidState`.
- `WaitEvent` 대기 중 `UnsubscribeEvent`/프로세스 종료: `Cancelled`
  류 에러로 깨움(§5).

## 10. 검증 계획

1. **커널→커널**: `EventPublisher::publish()` → `subscribeKernel()`
   콜백이 실제 호출되는지 확인(ISR 경로/직접 호출 경로 양쪽).
2. **커널→유저**: 진단 UserThread가 `SubscribeEvent` 후 `WaitEvent`로
   블로킹, 커널이 `publish()` 호출 시 정상 수신하는지 확인. devmgr
   실사용처가 나오기 전까지는 진단용 임시 발행원으로 검증한다(이
   문서는 인터럽트와 무관하므로 SP-71DA77B3처럼 실제 인터럽트에
   연결하지 않는다).
3. **멀티캐스트**: 구독자 2개 이상이 동시에 같은 이벤트를 받는지
   확인.
4. **pending 큐 유실 방지**: `WaitEvent` 호출 전에 발행된 이벤트가
   이후 `WaitEvent`로 정상 회수되는지 확인.
5. **정리**: 구독자 프로세스 종료 시 구독자 목록에서 자동 제거되는지
   확인.

## 11. 범위 밖 (v1)

- 우선순위/배타적 구독 없음(§5 참고 - 애초에 이 설계의 목표가 아님,
  필요하면 SP-71DA77B3 영역).
- pending 큐 용량 조정 API 없음(고정 N=8, 실측 후 상수 조정 가능).

## 12. `AsyncTaskGroup`(QU-86DD998F)과의 연관성 (minicore-88 지적, 2026-09-16)

QU-86DD998F(SP-F682B889 §3.3)가 이미 "weak ref로 들고 폴링"으로
확정돼 있다 - 이 문서는 그 결정을 재론하지 않는다. 다만 이 메커니즘이
자리 잡으면 "`AsyncTaskHandler`가 완료 시 `EventPublisher::publish()`

메커니즘으로 바꿀지 별도로 재확인한다.

## 13. 유저랜드 노출 범위 - QU-B76FB9CF 답변 반영 (2026-09-16 독립 설계 이후에도 유효)

approved 전환 직후 설계자가 Opinion으로 "유저랜드에 이 API를
노출하는게 맞을지가 가장 의문이 드네"라고 문제를 제기했고,
QU-B76FB9CF로 (A)/(B)/(C) 세 후보를 구체화해 재확인을 요청했다
(B=커널→유저만 유지·유저→커널 제거, C=유저 노출 전체를 v1에서 제거).
설계자 답변: **"(B + C)혼합으로 가자."**

- **범위는 (B)를 따른다** - 커널→유저(`SubscribeEvent`/`WaitEvent`/
  `UnsubscribeEvent`)는 설계에 남긴다(PN-B3DD3D19라는 확정된
  실사용처가 있으므로). 유저→커널(`PublishEvent`)은 완전히
  제거한다(§3/§5/§9/§10 전부 반영 완료).
- **시점은 (C)를 따른다** - 범위에 남은 커널→유저 syscall 3종도,
  devmgr 실코드가 실제로 이 API를 필요로 하는 시점까지는 **구현
  착수를 보류**한다(§5는 이미 확정 설계이므로, 그때 가서 재설계가
  아니라 바로 구현하면 된다). **[정정, 2026-09-21]** devmgr는
  `PN-615C48D5`(completed)로 이미 커널 `KernelThread`로서 실코드를
  갖췄다 - "아직 미착수"였던 원 서술은 낡았다. 다만 그 실코드는
  지금 `EnumerateDevices`만 쓸 뿐(PnP 매칭 테이블이 비어 있어 핫플러그
  자체가 아직 트리거되지 않음, `PN-A8BE8BED` 참고) 이 이벤트
  발행/구독 API를 실제로 필요로 하지는 않으므로, 이 게이팅 조건
  ("실제 필요 시점까지 보류")은 이유만 바뀌었을 뿐 여전히 미충족
  상태 - 결론(구현 착수 보류)은 그대로 유효하다.
- §4/§6/§7(토픽 레지스트리/커널 내부 구독/발행 로직의 커널 전용
  부분)은 애초에 유저 노출과 무관했으므로 계속 즉시 착수 가능.

**이 §13의 결론은 2026-09-16의 SP-71DA77B3 흡수 롤백/독립 설계
확정과 무관하게 그대로 유효하다** - "유저 노출 범위"와 "구독
메커니즘을 SP-71DA77B3에서 상속할지 독립 설계할지"는 서로 다른
축의 결정이다.
