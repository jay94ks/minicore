# Mkdir 자신의 데이터 블록에 대한 bhardlimit 검사 필요 여부

## 배경

`PN-D15D06AA`(Mkdir이 새 디렉터리 자신의 데이터 블록을 curspace에
반영 안 함)를 구현하는 중이다. Mkdir은 새 디렉터리의 "."/".."
엔트리를 담을 데이터 블록을 하나 할당하는데, 이 블록 할당이
`PN-D168A778`이 구현한 curspace(블록 쿼터 사용량) 증분 로직을
거치지 않아 curspace가 실제보다 4096바이트(블록 1개분) 적게
기록되는 버그가 있다. 이 자체(curspace 수치를 정확히 맞추는 것)는
순수 버그 수정이라 임의로 진행해도 안전하다.

## 결정이 필요한 지점

기존 Write 경로는 새 블록을 할당할 때 curspace를 증분하기 **전에**
`bhardlimit`(블록 쿼터 하드리밋)을 검사해, 한도를 넘으면
`NoSpace`류 오류로 그 Write 자체를 거부한다. Mkdir에도 이 검사를
똑같이 적용해야 하는가?

- **적용하면**: 디렉터리 생성이 순수히 블록 쿼터(파일 내용과 무관한
  구조적 오버헤드) 때문에 실패할 수 있는 새 동작이 생긴다 - 이
  커널의 v1 범위에서 "디렉터리 생성이 쿼터로 거부될 수 있다"는
  것이 의도된 동작인지 불명확하다(실제 리눅스 ext4는 이 검사를
  한다 - `dquot_alloc_block`이 파일/디렉터리를 구분하지 않음).
- **적용하지 않으면**: curspace 수치는 정확해지지만(초과분이 있어도
  기록만 하고 거부는 안 함), 이 프로젝트의 uid=0 고정 제약상 현재
  Mkdir을 거부할 실사용 시나리오 자체가 이미 거의 없어(uid=0은
  보통 하드리밋 예외 취급되는 경우가 많음) 실질적 차이가 작을 수도
  있다.

## 참고
- `PN-D15D06AA` - 이 결정을 필요로 하는 구현 계획.
- `PN-D168A778`(completed) - 기존 Write 경로의 curspace 증분+
  bhardlimit 검사 원 구현.
- `SP-3B8D77A3` - curinodes/그룹쿼터/트리삽입 쿼터 2차 증분 설계
  원본(이 결정은 그 문서 범위 밖의 새 발견).
