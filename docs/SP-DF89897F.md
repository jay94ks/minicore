# 커널 로깅 인프라 추상화 — 설계 제안

설계자 지시(2026-09-16, 메시지): "커널 로깅 인프라를 추상화하고 기존
Serial만 이용할 수 있게 하드코딩된 부분을 변경할 설계안을 작성해줘."

**[확정, 2026-09-16, QU-4A825E21 답변 반영]** §4의 세 확인 사항 전부
답변받아 아래 본문을 최종 설계로 갱신했다. 원래 초안의 클래스명
(`LogSink`/`Log`)은 설계자 지시로 **`LoggingDriver`/`Logger`**로
개칭됐다.

## 1. 현재 상태 (실측, 2026-09-16)

`kernel::Serial`(`minicore/kernel/serial.h/.cpp`)은 COM1 UART 기반
폴링 출력만 제공하는 최소 클래스(`init`/`putChar`/`write`/
`writeHex`)다. 로그 레벨도, 추상 인터페이스도 없이 **`kernel::
Serial::write(...)`/`writeHex(...)`가 코드 전역에 직접 하드코딩**돼
있다 - 실측으로 확인한 호출 지점만:

- `minicore/kernel/panic.cpp` - 패닉 메시지 출력(3줄).
- `minicore/kernel/kmain.cpp` - **150줄 이상**, 부팅 시퀀스 각 단계
  로그(PCI 열거, cpio 목록, ACPI MADT, 메모리 맵, 프로세스 스폰 등)
  전부가 `kernel::Serial::write("라벨")` + `writeHex(값)` +
  `write("\n")`를 몇 줄씩 수동으로 이어붙이는 방식.

문제:
1. **백엔드가 하나로 고정** - 나중에 다른 출력 경로를 추가하려면
   이 150개 이상의 호출부를 전부 다시 고쳐야 한다.
2. **로그 레벨이 없다** - 부팅 진행 로그(정보성)와 실패/FAILED 로그가
   똑같은 `Serial::write()`라 필터링/우선순위 구분이 불가능하다.
3. **포맷팅이 수작업** - `write("라벨: ")` + `writeHex(값)` +
   `write(" 다음라벨=")` + ... 패턴이 반복돼 실수하기 쉽고 장황하다.
4. **동시성 안전성 불명확** - UART는 코어 여러 개가 공유하는 자원인데
   `Serial::write()` 자체에 락이 있는지 확인되지 않았다.

## 2. 목표 / 비목표

**목표**
1. 호출부가 구체적 백엔드를 몰라도 되게 `kernel::Logger` 파사드
   뒤로 감춘다 - 호출부는 레벨별 API만 쓴다.
2. 백엔드를 **`LoggingDriver` 인터페이스**로 추상화한다(§3.1/§3.3 -
   v1부터 정확히 2개의 내장 드라이버, 확장 가능한 임의의 레지스트리
   아님).
3. 로그 레벨 6단계(§3.2, 확정) 도입, 부팅 커맨드라인으로 최소 레벨
   조정 가능.
4. **부팅 극초반부터 안전하게 동작**해야 한다 - `Serial::init()`이
   `kmain()` 초반(Slab/힙 준비 전)에 불리므로, `Logger`/1번 드라이버
   자신도 동적 할당 없이(정적 인스턴스) 동작해야 한다.
5. SMP 안전성 확보 - 드라이버에 실제로 쓰는 지점을 Spinlock으로
   보호해 여러 코어의 로그 출력이 한 줄 단위로는 섞이지 않게 한다.
6. `Fatal`/`Panic` 레벨은 레벨 필터와 무관하게 항상 출력돼야 한다.
7. **포맷터는 확장을 전제로 설계**(설계자 지시, §4-2 답변 - "언제
   어디서 어떻게 더 확장이 필요할지 몰라") - 최소 지시자 집합으로
   시작하지 않고, 처음부터 표준 printf 계열 지시자를 폭넓게(부호
   있는/없는 10진수, 16진수, 문자열, 문자, 폭/0-패딩, 64비트 길이
   변경자 등) 지원하는 것을 전제로 구현한다.
8. C++ 예외 없이, freestanding 환경에서 동작(RM-23F4B687).

**비목표(v1 범위 밖)**
- 유저랜드 로깅(devmgr/fs/tty가 유저랜드 서비스인 이상 이 프레임워크는
  커널 자신의 내부 로깅에만 쓰인다).
- `LoggingDriver` #2(§3.3-2)가 실제로 파일에 flush하려면 진짜
  파일시스템 쓰기 경로(fs 서비스, ext4/AHCI)가 필요한데 **아직
  이 프로젝트에 없다**(RM-7C249618 - libext4/libswapfs "예정,
  미구현") - 이 드라이버는 설계/구현하되, "파일로 flush" 단계는
  fs 서비스가 실제로 준비될 때까지 스텁(또는 충분히 큰 인메모리
  링버퍼로 대체 보관)으로 남긴다. §6 참고.
- 기존 150개 이상 호출부의 실제 마이그레이션(코드 변경) - 이 설계
  승인 후 별도 PN 계획으로 등록해 진행(CLAUDE.md 규칙 7).

## 3. 핵심 개념 (확정)

### 3.1 `LoggingDriver` - 출력 백엔드 추상 인터페이스

```cpp
namespace kernel {

// 로그 한 줄(레벨 프리픽스/타임스탬프까지 포맷 완료)을 실제로
// 어딘가에 내보내는 백엔드. v1은 정확히 2개(§3.3)만 존재한다 -
// 임의 확장 가능한 범용 레지스트리가 아니라, "부팅 단계 텍스트
// 드라이버"와 "인메모리 버퍼링 → 파일 flush 드라이버" 두 역할
// 고정.
class LoggingDriver {
public:
    virtual ~LoggingDriver() = default;
    virtual void writeLine(const char* line) = 0;
};

}  // namespace kernel
```

### 3.2 `LogLevel` (확정, 6단계)

```cpp
namespace kernel {

// Verbose는 기존 "Debug" 개념을 포함한다(설계자 지시, 별도 Debug
// 레벨을 안 둔다). Fatal/Panic은 레벨 필터와 무관하게 항상 출력.
enum class LogLevel : uint32_t { Verbose, Info, Warn, Error, Fatal, Panic };

}  // namespace kernel
```

### 3.3 `Logger` - 파사드 (확정, `Log`에서 개칭)

```cpp
namespace kernel {

class Logger {
public:
    // 부팅 극초반 호출(Serial::init() 직후) - 1번 드라이버(정적
    // 인스턴스)를 등록, 동적 할당 없음.
    static void init();

    // 부팅 커맨드라인으로 조정(기본값 Info - §4 답변, 현재 동작과
    // 동일한 체감 유지). Fatal/Panic은 이 필터를 무시한다.
    static void setMinLevel(LogLevel level);

    // 2번 드라이버(§3.3-2)를 나중에(부팅 완료 시점, fs 준비 후 등)
    // 등록/교체하기 위한 진입점 - "1번 드라이버를 대체할 뭔가가
    // 생기면 그 타이밍에 교체" 요구(§4 답변)도 이 API로 수용한다.
    // 정확한 교체 시점/트리거는 구현 계획에서 확정.
    static void setDriver(unsigned int slot, LoggingDriver* driver);

    static void verbose(const char* fmt, ...);
    static void info(const char* fmt, ...);
    static void warn(const char* fmt, ...);
    static void error(const char* fmt, ...);
    static void fatal(const char* fmt, ...);
    // panic() 전용 - 레벨 필터 무시, 항상 출력. panic.cpp도 이제
    // 포맷 인자를 쓸 수 있다(§4 답변 - "panic시에도 포멧팅 출력을
    // 내보낼 수 있어야 해").
    static void panic(const char* fmt, ...);
};

}  // namespace kernel
```

`Logger::verbose/info/.../panic`은 내부에서 **freestanding 전체
지원 포맷터**(표준 `vsnprintf` 없음 - libc/STL 미사용이지만, 최소
서브셋이 아니라 `%s`/`%c`/`%d`/`%u`/`%x`/`%%`와 폭/0-패딩, 64비트
길이 변경자(`%llx`/`%lu` 등, 이 커널이 실제로 다루는 물리주소/틱
카운트가 대부분 `uint64_t`이므로 필수)까지 지원)를 새로 구현한다 -
기존 코드의 `write("라벨: ") + writeHex(v) + write(" ")` 반복 패턴을
`Logger::info("라벨: %llx ", v)` 한 줄로 대체한다. 내부 버퍼는 스택의
고정 크기 지역 배열(예: 256바이트) - 힙 할당 없음.

**드라이버는 정확히 2개(설계자 확정)**:

1. **부팅 단계 드라이버(`SerialLoggingDriver`, 가칭)** - `Serial`을
   직접 제어하는 텍스트 기반 기본 드라이버. 부팅 극초반부터 존재,
   동적 할당 없음(정적 인스턴스). "이걸 대체하는 뭔가가 설정되면
   그 타이밍에 교체"(§4 답변) - 정확히 무엇으로 언제 대체되는지는
   아직 미정(설계자도 "그런 타이밍이 생기긴 할 것"이라고만 언급) -
   `Logger::setDriver()`로 나중에 교체 가능하게만 열어 둔다, 구체적
   대체 대상은 이 문서 범위 밖.
2. **인메모리 버퍼링 → 파일 flush 드라이버(`BufferedFileLoggingDriver`,
   가칭)** - 부팅 중에는 로그를 내부 메모리(고정 크기 링버퍼 또는
   성장 가능한 버퍼, 구현 계획에서 크기 확정)에 쌓아 두고, **부팅이
   완료되면 파일로 flush**한다. 그 이후 들어오는 로그는 큐/버퍼에
   쌓았다가 **주기적으로** 파일에 flush한다(설계자 지시) - 이
   "주기적으로"는 이미 구현된 `DelayedExecutionQueue`(SP-F15B4A63,
   completed)를 그대로 재사용해 스케줄링하는 것을 제안한다(새 타이머
   메커니즘을 또 만들지 않음, RM-23F4B687 §4 취지). 실제 파일 쓰기
   경로(fs 서비스/VFS)가 아직 없으므로(§2 비목표), v1은 이 드라이버의
   버퍼링/주기 트리거 로직까지만 구현하고 "파일에 실제로 쓰기"는 fs
   서비스가 준비된 뒤 연결한다.

## 4. 확인 완료 (QU-4A825E21, 2026-09-16 답변)

1. 레벨 세트: Verbose(Debug 포함)/Info/Warn/Error/Fatal/Panic - §3.2
   반영 완료.
2. 포맷터: 최소 서브셋이 아니라 전체 지원 고려 - §3.3 갱신 완료.
3. panic도 포맷팅 지원 - §3.3 `Logger::panic(fmt, ...)`로 반영.
4. 네이밍: `LogSink`→`LoggingDriver`, `Log`→`Logger` - 전체 반영
   완료. 드라이버는 정확히 2개(부팅 텍스트 드라이버 + 인메모리→파일
   드라이버) - §3.3 반영 완료.

## 5. 새로 등장하는 용어 (RM-32D06563 §12 규칙 대상)

`LoggingDriver`/`Logger`/`LogLevel`/`SerialLoggingDriver`/
`BufferedFileLoggingDriver`를 RM-32D06563에 등록 필요(승인 후 반영).

## 6. 구현 계획 (설계 승인 후 별도 PN 등록, CLAUDE.md 규칙 7)

150개 이상 호출부 마이그레이션 + 두 드라이버 구현은 이 문서의 범위가
아니다 - `approved` 전환 후 별도 PN 계획으로 등록해 (1)
`LoggingDriver`/`Logger`/포맷터 신규 구현, (2) `SerialLoggingDriver`
구현 + 부팅 배선, (3) `panic.cpp` 3곳 치환, (4) `kmain.cpp` 전체
치환, (5) `BufferedFileLoggingDriver`(버퍼링/주기 flush 로직만,
실제 파일 쓰기는 fs 서비스 대기) 순으로 진행한다. (5)는 fs 서비스
자체가 아직 없어 실제 파일 flush 완성까지는 별도 후속 선행 조건이
남는다.
