# 실행 계획: HPET 지원

**[완료, 2026-09-14, 2026-09-14 재작업 반영]** QA-26450C3E 체크됨. 아래는 완료 기록으로 남긴다.

설계자 지시(DS-D4E5C451)로 등록. **역할 확정(QU-8E14D3D9,
2026-09-14): HPET을 작업 스케줄러의 기본(default) 시간원으로 쓰고,
LAPIC 타이머는 fallback으로 유지한다.** PIT는 최초 LAPIC 타이머
보정에만 계속 쓰고(현재 그대로), HPET/LAPIC 두 타이머 경로는 서로
대체가 아니라 "평소엔 HPET, HPET가 없거나 실패하면 LAPIC 타이머"
관계로 유지한다.

## 선행 조건

- 없음(ACPI 파싱 인프라는 이미 있음 - acpi.cpp의 kFindTable을 그대로
  재사용해 "HPET" 시그니처 테이블을 찾으면 됨).
- (구현 중 실제로 필요했던 것: IOAPIC 라우팅(PL-2D149D8F) - HPET
  인터럽트를 IOAPIC을 거쳐야 해서, IOAPIC이 먼저 구현돼 있어야
  실제로 CPU까지 전달할 수 있었다. 원래 PL에는 명시 안 돼 있었지만
  IOAPIC PL을 먼저 완료한 뒤 이 작업을 진행했다.)

## 한 것

1. **ACPI HPET 테이블 파싱**: `acpi.cpp`에 `HpetTable` 구조체(SdtHeader
   +eventTimerBlockId+Generic Address Structure+hpetNumber+minimumTick+
   pageProtection) 추가, `kFindTable<...>(sdtPhys, "HPET")` 호출을
   MADT/SRAT와 나란히 추가. `Acpi::hasHpet()`/`Acpi::hpetAddress()`로
   공개 - HPET은 선택 테이블이라 있음/없음을 명확히 구분해야 해서
   IOAPIC 주소처럼 값 하나만 두지 않고 별도 bool을 뒀다.
2. **HPET MMIO 매핑**: `minicore/kernel/hpet.h/.cpp` 신설.
   `kHpetVirtBase = 0xFFFF901000002000UL`(LAPIC/IOAPIC 다음 4KiB
   페이지) + `PAGE_CACHE_DISABLE`.
3. **메인 카운터 주기 읽기 + 비교기 설정**: General Capabilities
   레지스터(0x000, 64비트) 상위 32비트에서 카운터 주기(펨토초)를
   읽어 목표 Hz에 맞는 comparator 값을 계산(`10^15 / Hz / periodFs`).
   Timer N Config 레지스터(0x100+0x20*N)의 PER_INT_CAP 비트로 주기
   모드 지원 여부를 먼저 확인(미지원이면 실패 반환 - 호출부가
   폴백해야 함).
4. **주기 모드 설정의 실제 하드웨어 quirk**: HPET 스펙 2.3.9.2.1대로,
   TIMER_VAL_SET_CNF 비트를 세운 채로 comparator 레지스터에 값을
   **두 번 연속** 써야 한다(한 번만 쓰면 하드웨어에 따라 한 번 쏘고
   멈추는 것처럼 보일 수 있음) - 초기 지연과 주기가 같은 값이라 그냥
   같은 값을 두 번 썼다. 이 사실을 몰랐다면 재발견하는 데 시간이
   걸렸을 것 - 관계도에 기록.
5. **LAPIC 타이머는 fallback으로 유지**: `Timer::init()`이
   `Acpi::hasHpet() && Hpet::init()`으로 분기 - 성공하면 그대로
   반환(기존 PIT 보정+LAPIC 주기 설정 코드는 안 건드리고 그대로
   둠), 실패(HPET 없음 또는 Timer0 주기모드 미지원)하면 자동으로
   기존 경로로 넘어간다. 시간원이 무엇이든 결국 `Timer::onTick()`을
   부르므로 `tickCount()`의 의미는 동일 - 스케줄러 쪽에서 시간원을
   구분할 필요가 없다. 진단용으로 `Timer::usesHpet()`을 추가해
   부팅 로그에 `source=hpet`/`source=lapic+pit`를 남긴다(Lapic의
   `usesX2Apic()` 로그와 같은 패턴).
6. **검증(실측, 2026-09-14, QEMU 8.2.2)**: 기본 머신(HPET 있음) →
   `hpet=yes`/`source=hpet`, 부팅 후 5회 연속 hlt-루프로 대기하며
   틱이 정확히 1씩 증가함을 확인. `-machine pc,hpet=off` →
   `hpet=no`/`source=lapic+pit`로 정상 폴백, 마찬가지로 5회 연속
   증가 확인(회귀 없음). x2APIC(`-accel kvm -cpu host`, PL-D65F49CC)
   과 함께 켜도 `source=hpet`로 정상 동작 - IOAPIC(PL-2D149D8F)까지
   세 기능이 동시에 켜진 상태에서 문제 없음을 확인했다.

## 재작업 - GSI 비트맵 라우팅 + 멀티 비교기 (2026-09-14, 설계자 지시)

애초에 "이번엔 안 한 것"으로 남겨 뒀던 두 항목을 설계자가 검토 후
지금 시점에 구현하라고 확정했다(QU-2247A01E, QU-1CC6BB1D).

- **QU-1CC6BB1D 답변 반영("고정된 Legacy Replacement가 아닌 비트맵을
  읽어 원하는 GSI를 골라야 한다")**: `Hpet::enableTimer`가 이제
  Legacy Replacement Route(GSI2 고정)를 아예 쓰지 않는다 - 각
  Timer N Config 레지스터의 상위 32비트(Tn_INT_ROUTE_CAP, 이 타이머가
  실제로 라우팅 가능한 IOAPIC GSI 비트맵)를 읽어 그중 가장 낮은
  번호의 GSI를 고르고, Tn_INT_ROUTE_CNF(같은 레지스터 비트9-13)에
  그 GSI를 직접 써서 라우팅을 확정한다. IOAPIC REDTBL에도
  `IoApic::setRedirection(gsi, vector, destApicId, kAcpiPolarityActiveHigh,
  kAcpiTriggerLevel)`로 그대로 반영한다(레벨 트리거로 전환 - 여러
  장치가 같은 GSI를 공유할 수 있는 임의 라우팅에는 엣지보다 레벨이
  안전하다는 HPET 스펙 권장을 따름). 레벨 트리거는 인터럽트 소스를
  직접 꺼야(ack) 계속 걸리지 않으므로, General Interrupt Status
  Register(오프셋 0x020)에서 해당 타이머 비트를 인터럽트 핸들러가
  직접 지우도록 추가했다(안 하면 레벨이 계속 asserted 상태로 남아
  같은 인터럽트가 폭주하거나 완전히 멈출 수 있음 - 관계도에 기록).
- **QU-2247A01E 답변 반영("HPET을 여러 개 비교기로 확장하여 멀티
  타이머를 구성해야 한다")**: `Hpet::enableTimer(timerIndex,
  frequencyHz, vector, destApicId)`를 공개 API로 분리했다 -
  Timer0(기본 스케줄러 틱)은 `Hpet::init()`이 내부적으로 이 API를
  호출해 설정하고, 그 외 비교기(`Hpet::timerCount()`로 개수 확인
  가능)도 독립된 주파수/벡터/목적지로 설정할 수 있다. 아직 SMP
  스케줄러가 없어 "코어별 독립 틱"을 실제로 거는 호출부는 없지만,
  그 시점에 코어 수만큼 `enableTimer`를 반복 호출하면 되도록 미리
  일반화해 뒀다. 벡터별로 어느 타이머가 인터럽트를 냈는지 알아야
  올바른 비교기의 ack 비트를 지울 수 있어서, 벡터→타이머 인덱스
  매핑 표(`gVectorToTimerIndex[256]`)를 내부에 추가했다.
- **실측(2026-09-14, QEMU 8.2.2)**: 기본 머신에서 GSI 비트맵 기반
  라우팅으로 전환한 뒤에도 `source=hpet`로 정상 부팅, hlt 루프로
  기다리며 틱이 처음 한 번 큰 폭으로(부팅 중 PCI 열거 등 실제 경과
  시간 반영) 뛴 뒤 이후 1씩 정확히 연속 증가함을 확인 - 레벨
  트리거+ack 로직이 실제로 반복 인터럽트를 올바르게 처리함을
  증명했다(ack를 안 하면 한 번 뜨고 멈추거나 폭주했을 것).

## 이번엔 안 한 것 (후속 과제로 남김)

- 없음 - 원래 이 절에 있던 두 항목(멀티 비교기, GSI 비트맵 라우팅)은
  위 재작업으로 전부 반영됐다.
- **실제 코어별 독립 틱 배정**: `enableTimer` API는 준비됐지만, 이를
  스케줄러와 실제로 엮어 AP마다 별도 비교기를 배정하는 건 스케줄러
  자체가 없어 여전히 범위 밖(SMP 스케줄러 설계 시점 과제).

  방식"은 스케줄러 설계 시점에 별도로 구체화하기로 이미 합의됨.
