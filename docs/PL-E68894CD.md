# 실행 계획: HPET 지원

**[완료, 2026-09-14]** QA-26450C3E 체크됨. 아래는 완료 기록으로 남긴다.

설계자 지시(DS-D4E5C451)로 등록. **역할 확정(QU-8E14D3D9,
2026-09-14): HPET을 작업 스케줄러의 기본(default) 시간원으로 쓰고,
LAPIC 타이머는 fallback으로 유지한다.** PIT는 최초 LAPIC 타이머
보정에만 계속 쓰고(현재 그대로), HPET/LAPIC 두 타이머 경로는 서로
대체가 아니라 "평소엔 HPET, HPET가 없거나 실패하면 LAPIC 타이머"
관계로 유지한다.

## 선행 조건

- 없음(ACPI 파싱 인프라는 이미 있음 - acpi.cpp의 kFindTable을 그대로
  재사용해 "HPET" 시그니처 테이블을 찾으면 됨).
- (구현 중 실제로 필요했던 것: IOAPIC 라우팅(PL-2D149D8F) - HPET
  Legacy Replacement Route의 인터럽트가 GSI2를 거쳐야 해서, IOAPIC이
  먼저 구현돼 있어야 실제로 CPU까지 전달할 수 있었다. 원래 PL에는
  명시 안 돼 있었지만 IOAPIC PL을 먼저 완료한 뒤 이 작업을 진행했다.)

## 한 것

1. **ACPI HPET 테이블 파싱**: `acpi.cpp`에 `HpetTable` 구조체(SdtHeader
   +eventTimerBlockId+Generic Address Structure+hpetNumber+minimumTick+
   pageProtection) 추가, `kFindTable<...>(sdtPhys, "HPET")` 호출을
   MADT/SRAT와 나란히 추가. `Acpi::hasHpet()`/`Acpi::hpetAddress()`로
   공개 - HPET은 선택 테이블이라 있음/없음을 명확히 구분해야 해서
   IOAPIC 주소처럼 값 하나만 두지 않고 별도 bool을 뒀다.
2. **HPET MMIO 매핑**: `minicore/kernel/hpet.h/.cpp` 신설.
   `kHpetVirtBase = 0xFFFF901000002000UL`(LAPIC/IOAPIC 다음 4KiB
   페이지) + `PAGE_CACHE_DISABLE`.
3. **메인 카운터 주기 읽기 + Timer0 비교기 설정**: General
   Capabilities 레지스터(0x000, 64비트) 상위 32비트에서 카운터 주기
   (펨토초)를 읽어 100Hz 목표에 맞는 comparator 값을 계산
   (`10^15 / 100 / periodFs`). Timer0 Config 레지스터(0x100)의
   PER_INT_CAP 비트로 주기 모드 지원 여부를 먼저 확인(미지원이면
   `Hpet::init()`이 false 반환 - 호출부가 폴백해야 함).
4. **주기 모드 설정의 실제 하드웨어 quirk**: HPET 스펙 2.3.9.2.1대로,
   TIMER_VAL_SET_CNF 비트를 세운 채로 comparator 레지스터에 값을
   **두 번 연속** 써야 한다(한 번만 쓰면 하드웨어에 따라 한 번 쏘고
   멈추는 것처럼 보일 수 있음) - 초기 지연과 주기가 같은 값이라 그냥
   같은 값을 두 번 썼다. 이 사실을 몰랐다면 재발견하는 데 시간이
   걸렸을 것 - 관계도에 기록.
5. **LAPIC 타이머는 fallback으로 유지**: `Timer::init()`이
   `Acpi::hasHpet() && Hpet::init()`으로 분기 - 성공하면 그대로
   반환(기존 PIT 보정+LAPIC 주기 설정 코드는 안 건드리고 그대로
   둠), 실패(HPET 없음 또는 Timer0 주기모드 미지원)하면 자동으로
   기존 경로로 넘어간다. 시간원이 무엇이든 결국 `Timer::onTick()`을
   부르므로 `tickCount()`의 의미는 동일 - 스케줄러 쪽에서 시간원을
   구분할 필요가 없다. 진단용으로 `Timer::usesHpet()`을 추가해
   부팅 로그에 `source=hpet`/`source=lapic+pit`를 남긴다(Lapic의
   `usesX2Apic()` 로그와 같은 패턴).
6. **IOAPIC 라우팅**: Legacy Replacement Route(General Config
   레지스터 비트1)를 켜면 하드웨어 스펙상 Timer0 인터럽트가 GSI2로
   고정 라우팅되지만, IOAPIC은 HPET 내부 라우팅 결정을 알 방법이
   없어(그냥 GSI2 핀 신호로만 봄) `IoApic::setRedirection(2, vector,
   destApicId)`를 직접 호출해 REDTBL 엔트리를 채워야 한다 -
   `Idt::registerHandler(kHpetVector, ...)`로 핸들러(내부에서
   `Timer::onTick()` 호출)를 등록.
7. **SMP와의 관계**: 원래 PL대로 지금 단계에서는 확정하지 않고
   미룬다(스케줄러 설계 시점에 재검토 - HPET은 코어별이 아니라
   전역 카운터/비교기 하나뿐이라는 점을 그때 다시 짚어야 함).
8. **검증(실측, 2026-09-14, QEMU 8.2.2)**: 기본 머신(HPET 있음) →
   `hpet=yes`/`source=hpet`, 부팅 후 5회 연속 hlt-루프로 대기하며
   틱이 정확히 1씩 증가함을 확인. `-machine pc,hpet=off` →
   `hpet=no`/`source=lapic+pit`로 정상 폴백, 마찬가지로 5회 연속
   증가 확인(회귀 없음). x2APIC(`-accel kvm -cpu host`, PL-D65F49CC)
   과 함께 켜도 `source=hpet`로 정상 동작 - IOAPIC(PL-2D149D8F)까지
   세 기능이 동시에 켜진 상태에서 문제 없음을 확인했다. 검증 후 임시
   틱 로그 코드는 제거, 영구 코드(`Hpet::init()` 호출, `Timer::init()`
   분기)는 그대로 남김.

## 이번엔 안 한 것 (후속 과제로 남김)

- **HPET을 여러 개 비교기로 확장(멀티 타이머)**: 지금은 Timer0
  하나만 쓴다 - 스케줄러가 코어별 독립 틱이 필요해지면(SMP) 이
  구조 자체를 재검토해야 한다(원래 PL의 5번 항목).
- **Legacy Replacement 대신 임의 GSI 라우팅**: Tn_INT_ROUTE_CAP
  비트맵을 읽어 원하는 GSI를 고르는 대신, 항상 GSI2 고정인 Legacy
  Replacement만 구현했다 - 더 유연한 라우팅이 필요해지면 추가.

## 미결 사항

- 없음(핵심 정책은 이미 확정돼 있었음) - 5번(SMP에서의 정확한 동작
  방식)은 스케줄러 설계 시점에 별도로 구체화하기로 이미 합의됨.
