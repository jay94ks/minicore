# libvfat — FAT32/16 온디스크 포맷 읽기/쓰기 라이브러리 설계

## 1. 배경

`SP-2BCE5D60` §1/§2가 `minicore/libs/libvfat`을 이미 지정해 뒀지만
(`RM-7C249618` "예정, 미구현") 실제 온디스크 포맷 설계는 없었다 -
`PN-452FF696`(fs 서비스)의 남은 세 블로커(libext4/libswapfs/libvfat)
중 하나. 설계자 답변(`QU-CE388254`, `SP-D02C4A73` 대상)이 "libext4/
libswapfs/libvfat 모두 설계해야 하고"라고 명시한 데 따라 이어서
등록한다.

**libswapfs와 같은 원칙**: FAT32/16은 Microsoft의 기존 외부 표준
스펙(Microsoft "FAT32 File System Specification")을 그대로 따른다 -
이 프로젝트가 새로 고안할 내용이 없다(CLAUDE.md 규칙4). 이 문서가
옮기는 구조체 필드 폭/오프셋은 FAT 스펙 문헌에 널리 공개된 값이라
신뢰도가 높지만, **구현 착수 시 반드시 실제 스펙 문서 또는 리눅스
커널 `fs/fat/fat.h`와 대조해 재확인할 것**(SP-D02C4A73이 이미 세운
관례 그대로 - 불확실한 세부를 이 문서 하나로 단언하지 않음).

## 2. 스코프

- **경로**: `minicore/libs/libvfat`.
- **커널/유저 공용**: `SP-7CC5693A` §2 기존 결정 그대로(매크로로
  컴파일 모드만 구분, v1은 유저랜드 `fs` 서비스만 실사용).
- **대상**: FAT32(우선) + FAT16(가능하면 같이) - FAT12는 범위 밖
  (플로피 디스크 시절 포맷, `SP-2BCE5D60` §1이 지목한 두 용도
  - `/boot/uefi` ESP, USB/외부 매체 상호운용성 - 어느 쪽도 FAT12를
  요구하지 않음).
- **v1 범위(스코프 컷)**:
  - **짧은 8.3 이름만 지원, LFN(Long File Name) 읽기/쓰기는 범위
    밖** - LFN은 여러 개의 특수 디렉터리 엔트리(속성 0x0F)를 역순
    체인+체크섬으로 엮는 별도 서브포맷이라 복잡도가 크다. LFN
    엔트리가 있는 디렉터리를 읽을 때는 그 엔트리들을 무시하고 그
    뒤에 오는 짧은 이름 엔트리만 사용(표준이 이미 이 하위호환을
    보장 - LFN을 모르는 구현은 짧은 이름만 보고 무시하면 된다는
    것이 스펙 자체의 설계 의도).
  - **디렉터리 엔트리 생성(mkdir/파일 생성) 시 짧은 이름만 생성** -
    LFN 엔트리를 새로 쓰지 않는다(파일명이 8.3 규칙을 못 지키면
    실패 - v1 제약으로 명시).
  - FAT12는 후속 증분에서 지원(영구 제외 아님, 아래 [정정] 참고).
- **범위 밖**: 슈퍼블록(부트섹터) 자동 판별 알고리즘 자체의 구현
  세부는 `SP-2BCE5D60` §6이 "각 드라이버 착수 시점"으로 이미 미뤄
  둠 - 이 문서는 판별에 필요한 시그니처/필드만 고정한다.

**[정정, 2026-09-22, 설계자 답변 QU-F884AB69]** 위 §2 원안은 "LFN/
FAT12를 v1 범위 밖(영구)"으로 그었으나 반려됐다 - 설계자 답변 원문:
**"기능은 전체 지원해야 하고 vfat에서 정의하는 모든걸 유지보수까지
해야해."** `SP-7A9CED3E`(libext4)와 동일 원칙으로 재구성한다 - 위는
"영구 제외"가 아니라 "1차 증분 다음에 순서대로 이어지는 증분 목록"
이다.

**1차 증분(이 문서가 지금 구조를 확정하는 범위)**: FAT32/16 부트
섹터+BPB(§3.1), 클러스터 수 기반 포맷 판별(§3.2), FAT 테이블/
클러스터 체인(§3.4), 8.3 짧은 이름 디렉터리 엔트리(§3.5) - LFN
엔트리가 섞여 있어도 무시하고 짧은 이름만으로 읽기/쓰기(스펙
자체의 하위호환 보장을 그대로 활용, 데이터 손상 없이 동작).

**후속 증분(순서대로 "VFAT 전체 지원+유지보수"에 도달)**:
1. **LFN(Long File Name) 읽기/쓰기** - VFAT을 정의하는 핵심 확장
   (속성 0x0F 엔트리 체인+체크섬, UTF-16 인코딩). 1차 증분은 그냥
   무시했지만 이 증분이 실제로 파싱/생성한다.
2. **FAT12 지원** - 세 번째 FAT 변종. §3.2의 판별 로직에 이미
   임계값이 있으나(`clusterCount < 4085`) 1차 증분은 그 경우
   거부만 한다 - 이 증분이 12비트 팩 엔트리 처리를 채운다.
3. **FSInfo 유지보수**(§3.1의 `fsInfoSector`, FAT32 전용) - 빈
   클러스터 수/다음 빈 클러스터 힌트를 실제로 읽고 갱신 - 1차
   증분은 무시하고 매번 §3.4 선형 스캔만 했으나, 이 증분이 그
   캐시를 정확히 유지해 마운트 시점 스캔 없이도 빠르게 시작하고
   변경마다 정확히 갱신한다("유지보수"의 핵심 사례).
4. **타임스탬프 읽기/쓰기** - `crtTime`/`wrtTime`/`lastAccessDate`
   등(§3.5) FAT 고유 인코딩(1980년 기준, 2초 단위)을 실제로
   채우고 갱신. wall-clock 소스가 이 커널에 아직 없다면 그 확정도
   이 증분의 일부로 함께 처리(구현 세션이 확인).
5. **NT 대소문자 확장**(`ntReserved` 바이트) - 8.3 이름을 실제로는
   소문자로 표시하되 온디스크는 대문자로 유지하는 NT/VFAT 확장 -
   유지보수 관점의 완전성.
6. **볼륨 dirty 비트 관리** - FAT32/16의 예약 FAT 엔트리(인덱스 1)
   상위 비트에 "정상 언마운트 여부"를 기록하는 표준 관례 -
   `libext4`의 `s_state`(`EXT4_VALID_FS`)와 대응되는 개념. 1차
   증분은 이 비트를 안 건드리므로, 이 증분이 마운트 시 세팅/
   언마운트 시 클리어를 구현한다.

각 항목은 별도 `PN-` 계획으로 등록해 CLAUDE.md 규칙7을 지킨다(문서
승인과 함께 등록, 1차 증분 완료를 선행 조건으로 건다).

## 3. 온디스크 포맷 — Microsoft FAT32/16 스펙 준수

### 3.1 부트 섹터 / BPB(BIOS Parameter Block) — LBA 0, 512바이트

FAT12/16/32가 공유하는 공통 필드(BPB) + FAT32 전용 확장 필드로
구성된다. 스펙 문헌의 필드명을 그대로 따른다(대조 편의):

```cpp
#pragma pack(push, 1)
struct FatBpbCommon {
    uint8_t  jmpBoot[3];
    char     oemName[8];
    uint16_t bytesPerSector;      // 보통 512(4096도 스펙상 허용)
    uint8_t  sectorsPerCluster;   // 반드시 2의 거듭제곱(1,2,4,...,128)
    uint16_t reservedSectorCount; // FAT32는 보통 32, FAT16은 보통 1
    uint8_t  numFats;             // 보통 2
    uint16_t rootEntryCount;      // FAT32는 반드시 0(루트가 클러스터 체인)
    uint16_t totalSectors16;      // 0이면 totalSectors32 사용(FAT32는 항상 0)
    uint8_t  media;               // 0xF8 = 고정 디스크(일반적 값)
    uint16_t fatSize16;           // FAT32는 반드시 0(fatSize32 사용)
    uint16_t sectorsPerTrack;     // 지오메트리 - LBA만 쓰는 이 커널엔 무의미, 값만 보존
    uint16_t numHeads;
    uint32_t hiddenSectors;       // 파티션 시작 전 섹터 수
    uint32_t totalSectors32;      // FAT32는 항상 이 필드 사용
};
static_assert(sizeof(FatBpbCommon) == 36);

// FAT32 전용 확장(오프셋 36부터)
struct Fat32Extended {
    uint32_t fatSize32;           // FAT 하나의 섹터 수
    uint16_t extFlags;
    uint16_t fsVersion;           // 0이어야 함(이 스펙 버전)
    uint32_t rootCluster;         // 보통 2 - 루트 디렉터리의 시작 클러스터
    uint16_t fsInfoSector;        // 보통 1 - FSInfo 구조체 위치(예약영역 내)
    uint16_t backupBootSector;    // 보통 6, 0이면 백업 없음
    uint8_t  reserved[12];
    uint8_t  driveNumber;
    uint8_t  reserved1;
    uint8_t  bootSig;             // 0x29면 아래 세 필드 유효
    uint32_t volumeId;
    char     volumeLabel[11];
    char     fileSystemType[8];   // "FAT32   " - 진단용, 실제 포맷 판별에
                                   // 쓰지 않는다(스펙이 이 필드를 판별
                                   // 근거로 신뢰하지 말라고 명시 - §3.4 참고)
};
static_assert(sizeof(Fat32Extended) == 54);
// 부트 섹터 끝(오프셋 510)에 시그니처 0x55 0xAA(리틀엔디안 0xAA55)
#pragma pack(pop)
constexpr uint16_t kFatBootSignature = 0xAA55;
```

FAT16의 확장 필드는 `Fat32Extended`보다 훨씬 짧다(fatSize32/
extFlags/fsVersion/rootCluster/fsInfoSector/backupBootSector/
reserved[12] 없이 곧바로 driveNumber부터 시작) - v1이 FAT16도
지원한다면 별도 `Fat16Extended` 구조체를 둔다(필드는 동일, 위치만
오프셋 36으로 당겨짐).

### 3.2 포맷 판별 — FAT32 vs FAT16 (파일시스템 타입 필드를 신뢰하지 않는다)

Microsoft 스펙 자체가 명시하는 표준 판별법: **부트섹터의
`fileSystemType` 문자열이 아니라 클러스터 수로 판별한다** -

```cpp
uint32_t dataSectors = totalSectors32 - (reservedSectorCount +
    numFats * fatSize32Or16 + rootDirSectors /* FAT32는 0 */);
uint32_t clusterCount = dataSectors / sectorsPerCluster;

if (clusterCount < 4085)       → FAT12(v1 미지원, mount() 거부)
else if (clusterCount < 65525) → FAT16
else                             → FAT32
```

`mount()`가 이 계산으로 실제 타입을 재확인하고, `fileSystemType`
문자열과 불일치해도 계산 결과를 신뢰한다(스펙 원문의 경고 그대로 -
많은 포맷 도구가 이 문자열을 부정확하게 채운다).

### 3.3 영역 배치

1. **예약 영역**: LBA 0부터 `reservedSectorCount`섹터 - 부트섹터
   자신 + (FAT32만) FSInfo 섹터 + 백업 부트섹터.
2. **FAT 영역**: 예약 영역 직후, `numFats`개의 FAT 테이블이 각각
   `fatSize32`(또는 FAT16의 `fatSize16`) 섹터씩 연속 배치.
3. **루트 디렉터리 영역(FAT16만)**: FAT 영역 직후, 고정 크기
   `ceil(rootEntryCount * 32 / bytesPerSector)`섹터 - FAT32는 이
   영역이 아예 없다(루트도 §3.5의 일반 클러스터 체인).
4. **데이터 영역**: 위 다음부터 끝까지, `sectorsPerCluster`섹터
   단위의 클러스터로 분할. **클러스터 번호는 2부터 시작**(0/1은
   예약) - 클러스터 N의 첫 섹터 = 데이터 영역 시작 섹터 +
   `(N - 2) * sectorsPerCluster`.

### 3.4 FAT 엔트리 — 클러스터 체인

FAT 테이블은 클러스터 번호로 색인되는 배열 - 엔트리 값이 "다음
클러스터 번호" 또는 특수값:

| 타입 | 엔트리 폭 | Free | EOC(체인 끝) | Bad |
|---|---|---|---|---|
| FAT16 | 16비트 | 0x0000 | 0xFFF8~0xFFFF | 0xFFF7 |
| FAT32 | 32비트(하위 28비트만 유효, 상위 4비트 예약) | 0x00000000 | 0x0FFFFFF8~0x0FFFFFFF | 0x0FFFFFF7 |

파일/디렉터리의 클러스터 체인은 디렉터리 엔트리(§3.5)의 시작
클러스터부터 FAT를 따라가며 EOC를 만날 때까지 이어진다. **쓰기
(할당)**: free 클러스터를 찾아(선형 스캔, v1은 `libswapfs`의
`allocateSlot`과 동일한 방식 - 힌트 포인터 기반 선형 스캔) 체인
끝에 연결하고 그 클러스터를 EOC로 마킹, **`numFats`가 2 이상이면
모든 FAT 사본에 동일하게 반영**(표준이 요구하는 이중화 - 하나가
손상돼도 복구 가능하게 하려는 목적, v1은 단순히 매 갱신마다 양쪽에
동일하게 쓴다).

### 3.5 디렉터리 엔트리 (32바이트, 8.3 짧은 이름)

```cpp
#pragma pack(push, 1)
struct FatDirEntry {
    char     name[8];      // 공백 패딩, 0x00=디렉터리 끝, 0xE5=삭제됨,
                            // 0x05=실제 문자가 0xE5인 특수 이스케이프
    char     ext[3];       // 공백 패딩
    uint8_t  attr;         // READ_ONLY=0x01 HIDDEN=0x02 SYSTEM=0x04
                            // VOLUME_ID=0x08 DIRECTORY=0x10 ARCHIVE=0x20
                            // LFN=0x0F(READ_ONLY|HIDDEN|SYSTEM|VOLUME_ID
                            // 전부 세팅된 조합 - v1은 이 값이면 §2의
                            // "LFN 엔트리 스킵" 규칙으로 건너뜀)
    uint8_t  ntReserved;
    uint8_t  crtTimeTenth;
    uint16_t crtTime;
    uint16_t crtDate;
    uint16_t lastAccessDate;
    uint16_t fstClusHi;     // 시작 클러스터 상위 16비트(FAT32만 유효,
                            // FAT16은 항상 0)
    uint16_t wrtTime;
    uint16_t wrtDate;
    uint16_t fstClusLo;     // 시작 클러스터 하위 16비트
    uint32_t fileSize;      // 바이트 단위, 디렉터리는 항상 0(디렉터리
                            // 크기는 클러스터 체인 길이로만 앎)
};
static_assert(sizeof(FatDirEntry) == 32);
#pragma pack(pop)

inline uint32_t kFatFirstCluster(const FatDirEntry& e) {
    return (static_cast<uint32_t>(e.fstClusHi) << 16) | e.fstClusLo;
}
```

`"."`/`".."` 엔트리는 모든 비-루트 디렉터리의 첫 두 엔트리로
직접 기록된다(표준 관례 - 자기 자신/부모의 시작 클러스터를 가리킴,
FAT32 루트는 `".."`이 클러스터 0을 가리키는 특수 규칙 - 스펙 원문
확인 필요).

### 3.6 `mount()` 판별 절차

1. LBA 0(512바이트) 읽어 `kFatBootSignature`(오프셋 510) 확인 -
   불일치 시 즉시 실패("이 포맷 아님", ext4/swapfs와 동일 관례).
2. `bytesPerSector`가 512/4096 등 2의 거듭제곱이 아니거나
   `sectorsPerCluster`가 2의 거듭제곱이 아니면 실패(스펙 위반 -
   실제 FAT 이미지가 아닐 가능성).
3. §3.2 클러스터 수 계산으로 FAT12/16/32 재확인 - FAT12면 실패
   (v1 미지원).
4. FAT32면 `rootCluster`부터, FAT16이면 §3.3의 고정 루트 디렉터리
   영역부터 루트를 연다.

## 4. `Fat32Driver`/`Fat16Driver` 구현 — `FileSystemDriver`(`kernel::KernelFsDriver` 확장) 인터페이스

**[해소, 2026-09-22, `QU-08ACD701` 설계자 답변("양쪽 모두를 수정하면서
구현해")]** `SP-2BCE5D60` §3.1이 전면 재작성됐다 - `FileSystemDriver`는
`kernel::KernelFsDriver`(`minicore/kernel/mount_table.h`,
`AsyncTaskHandler` 상속)를 확장하는 것으로 재정의됐다. 새 타입을
정의하지 않고 `mount_table.h`가 이미 가진 `VfsError`/`FileHandle`/
`OpenResult`/`ReadResult`/`VfsDirEntry` + `KernelFsOpCode` 9종 Args
구조체를 그대로 재사용한다 - `libext4`(`SP-7A9CED3E` §4)와 동일한
패턴, 이 문서가 §2에서 이미 권장했던 "§3+무상태 읽기 API 먼저"
전략도 그대로 유효(오히려 이 재정의로 그 전략이 자연스럽게
`onExec` 어댑터 계층으로 이어지게 됨).

```cpp
// minicore/libs/libvfat/vfat.h
class Fat32Driver : public FileSystemDriver {  // FileSystemDriver : kernel::KernelFsDriver
public:
    bool mount(BlockDevice* device, bool readOnly) override;
    bool remount(bool writable) override;
    // 파일 op 9종은 onExec 하나로 - args의 KernelFsOpCode 태그로
    // 분기해 §3/§4.1~4.3의 무상태 함수(경로 해석/read/write/mkdir 등)를
    // 그대로 호출하고 결과를 해당 KernelFsXxxArgs에 채운다
    // (mount_table.h의 LiveFs/ProcFs와 동일 관례).
    void onExec(AsyncTask* task, void* args) override;
    void onFailure(AsyncTask* task) override;
    void onCancel(AsyncTask* task, void* args) override;

private:
    BlockDevice* device_ = nullptr;
    FatBpbCommon bpb_{};
    Fat32Extended ext32_{};
    bool readOnly_ = true;
    uint32_t fatStartSector_ = 0;
    uint32_t dataStartSector_ = 0;
    uint32_t nextClusterScanHint_ = 2;  // §3.4 free 클러스터 스캔 힌트
};
// FAT16은 루트 디렉터리 영역/클러스터 필드 폭만 다를 뿐 나머지
// 로직이 거의 동일 - v1 구현 판단(공용 베이스 클래스로 묶을지,
// 완전히 별도 클래스로 둘지)은 구현 세션 재량(RM-23F4B687 §4).
class Fat16Driver : public FileSystemDriver { /* 후속, §3과 동일 원칙 */ };
```

`mount()`/`remount()`는 `AsyncTaskHandler` 프로토콜과 별개로
`MountTable::mountKernel()` 등록 전/후 한 번만 동기 호출되는 준비
단계라 일반 가상함수로 남는다(파일 op처럼 매번 제출되는 요청이
아님).

### 4.1 경로 해석

`relPath`를 `/`로 분리한 각 세그먼트를 8.3 형식(대문자, 이름 8자+
확장자 3자, 공백 패딩)으로 정규화한 뒤 현재 디렉터리의 엔트리
목록(§3.5, LFN 스킵)에서 선형 검색 - 매 세그먼트마다 그 디렉터리의
전체 클러스터 체인을 순회하며 이름이 일치하는 엔트리를 찾는다.
찾으면 그 엔트리의 시작 클러스터로 내려가 다음 세그먼트 반복.

### 4.2 `open`/`read`/`write`

`open()`이 성공하면 `FileHandle`에 시작 클러스터 + 현재 논리
오프셋이 가리키는 클러스터/클러스터 내 바이트 오프셋을 캐싱 -
`read`/`write`는 요청된 `offset`이 캐시된 위치보다 앞이면 시작
클러스터부터 다시 체인을 따라가고(느리지만 정확), 뒤거나 같으면
캐시된 위치에서 이어서 진행(순차 접근 최적화 - 이 프로젝트의 다른
드라이버가 이미 쓰는 "정직하게 단순한 v1" 원칙과 동일). `write`가
파일 끝을 넘어서면 §3.4의 클러스터 할당으로 체인을 늘리고
`fileSize` 필드를 갱신(디렉터리 엔트리 자신도 다시 씀).

### 4.3 `mkdir`/`unlink`/`rmdir`

- `mkdir`: 부모 디렉터리에 새 32바이트 엔트리(§3.5, ATTR_DIRECTORY)
  추가(빈 슬롯 - `name[0]==0x00` 또는 `0xE5` - 재사용, 없으면
  디렉터리 체인에 클러스터 추가), 새 클러스터 하나 할당해 그 안에
  `"."`/`".."` 엔트리 기록.
- `unlink`: 대상 디렉터리 엔트리의 `name[0]`을 `0xE5`로 마킹(스펙
  표준 삭제 관례 - 엔트리 슬롯 재사용 가능 상태로 전환), 그 파일이
  쓰던 클러스터 체인 전체를 free로 되돌림(FAT 엔트리를 0으로).
- `rmdir`: 대상이 빈 디렉터리(`"."`/`".."` 두 엔트리만 존재)인지
  먼저 확인 - POSIX `rmdir`과 동일 제약, 비어있지 않으면 실패.
  나머지는 `unlink`와 동일.

## 5. 이 문서가 확정하지 않는 것

- FSInfo 섹터(§3.1의 `fsInfoSector`)를 실제로 유지보수할지(빈
  클러스터 수/다음 빈 클러스터 힌트 캐시 - 순수 성능 최적화, 없어도
  정확성엔 영향 없음) - v1은 무시하고 매번 §3.4 선형 스캔으로
  충분(`RM-23F4B687` §4 취지, 실측 후 재검토).
- 타임스탬프(`crtTime`/`wrtTime` 등) 인코딩/갱신 정책 - FAT 타임스탬프
  포맷(연도 오프셋 1980, 2초 단위 등) 자체는 스펙에 고정돼 있으나,
  이 커널이 아직 wall-clock 시각 소스를 어디서 얻는지 확정한 문서가
  없다면(확인 필요) 일단 0으로 채워도 마운트/읽기 자체엔 지장 없음 -
  구현 세션이 판단.
- 대소문자 정책(`ntReserved` 바이트의 NT 확장 - 소문자 이름 표시
  비트) - v1은 항상 대문자로 정규화(스펙 원안 그대로), 소문자 표시
  확장은 범위 밖.

## 6. 다른 설계와의 관계

- `SP-2BCE5D60` §3.1/§3.0 — 이 문서가 구현하는 `FileSystemDriver`/
  `BlockDevice` 인터페이스의 출처.
- `SP-D02C4A73` — 같은 블로커(`PN-452FF696`)를 푸는 자매 설계
  (libswapfs), 외부 표준 준수 원칙을 먼저 확립한 선례.
- `SP-8B6B8D25` §4 — `/boot/uefi`(ESP) 마운트 지점, 이 라이브러리의
  용도 중 하나.
- `RM-7C249618` — 라이브러리 목록, 이 문서 승인 후 `libvfat` 행 갱신
  필요.
