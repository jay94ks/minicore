# 실행 계획: 커널 전용 비동기 프레임워크(AsyncTask)

**[설계 확정, 구현 대기, 2026-09-14]** SP-F682B889(2026-09-14 확정,
설계자 메시지/QU-4F905C08/QU-1BE6B8D2로 추가 갱신)의 `AsyncTask`/
`AsyncTaskHandler`/`AsyncTaskGroup`/`AsyncTaskWaitGroup`/
`AsyncTaskAwaiter`/`AsyncReactor` 설계를 실제로 구현하기 위한 순서를
남긴다. **착수 전제조건**: Slab 할당자(SP-D7013B26, 확정)와
스케줄러(PL-2D3184BC)의 선점 비활성화(8단계)/즉시 스케줄링(8-1단계)
프리미티브가 먼저 구현돼야 한다 - 순서는 "스케줄러 선점 금지 구간 →
Slab 할당자 → 이 프레임워크"(SP-F682B889 §5 참고).

## 배경

SP-F682B889/DC-01434F82/QU-F86426D5 참고 - 원래 제안(스택 없는
콜백 체인)이 검토 결과 스택풀(`AsyncTask`, 자체 yield) + 코어당
전용 리액터 Task로 확정됐다. 이후 설계자 메시지(2026-09-14)와
QU-4F905C08(Slab 할당자 답변에 포함된 실패 처리 위임)로 콜백이
`AsyncTaskHandler`(실행/실패 두 경로 구현 책임) 인터페이스로,
식별자가 `subjectCode`(uint32_t)+`manageCode`(uint64_t) 두 코드로
바뀌었다. **추가로 QU-1BE6B8D2(2026-09-14)로 C++20 코루틴 지원이
확정**됐다 - `AsyncTask`(스택풀) 자체는 그대로 두고, `onExec`을
코루틴으로도 구현할 수 있게 한다(SP-F682B889 §7). 코루틴 프레임
할당 실패 시 스택풀 `AsyncTask`가 `yield()`하며 재시도하는 결합도
같이 구현한다.

## 구현 순서 (착수 계획)

0. **[선행조건, 확정] Slab 할당자**: SP-D7013B26 확정 - 코어당
   더블 매거진(loaded/previous, 각 16개 고정)+전역 디포+슬랩(Order 0
   고정)+버킷 7단계(32~2048B). `libkmm/slab.h/.cpp` 신설,
   `SlabCache`/`GenericSlabAllocator`/`sizeToBucket`/
   `PreemptionGuard` 구현. **`PreemptionGuard`는 스케줄러의 선점
   비활성화 프리미티브(아래 0-1단계)에 의존** - 그게 먼저 있어야
   Slab 쪽 구현을 시작할 수 있다. 고갈 시 즉시 `nullptr`(비블로킹)
   반환 확인까지 실측 검증.
0-1. **[선행조건] 스케줄러 선점 비활성화**: PL-2D3184BC 8단계의
   "선점 비활성화 카운터"를 `PreemptionGuard`가 쓸 수 있는 공개
   프리미티브로 노출(예: `Scheduler::disablePreemption()`/
   `enablePreemption()` 또는 RAII 래퍼 자체를 스케줄러가 제공).
0-2. **[선행조건] 스케줄러 즉시 스케줄링**: PL-2D3184BC 8-1단계 -
   `Scheduler::scheduleImmediate(Task*)` 구현 - 스케줄러 큐 구현
   (4~7단계) 이후.
1. **`AsyncTask` 자료구조**: `minicore/kernel/async_task.h/.cpp`
   신설 - `savedRsp`/`stackBase`/상태/`subjectCode`(uint32_t)/
   `manageCode`(uint64_t)/`args`/`next`. `Task::init()`과 거의 같은
   트램폴린 스택 구성이지만 훨씬 작은 전용 스택(`GenericSlabAllocator`
   에서 확보 - 정확한 버킷 크기는 실측 확정) - `kContextSwitch`/
   `kTaskStartTrampoline`(context_switch.S)을 그대로 재사용할 수
   있는지, 아니면 더 작은 레지스터 셋만 저장하는 경량 버전이
   필요한지 구현 시 판단.
2. **`AsyncTask::yield()`**: 현재 AsyncTask 컨텍스트에서 리액터
   컨텍스트로 돌아가는 전용 컨텍스트 전환 경로 - 리액터가 다음
   AsyncTask를 고를 수 있는 지점을 명확히 설계.
3. **`AsyncTaskHandler`/`AsyncCallbackRegistry`**: 처리기 등록 표
   (고정 크기 배열, 벡터 테이블과 비슷한 패턴 - `Idt::
   registerHandler`의 벡터->콜백 표 재사용 경험을 참고).
   `onExec`/`onFailure` 둘 다 순수 가상 함수 - 등록 시점에 강제.
4. **`AsyncReactor` - 코어당 전용 Task**: `reactorTaskEntry`가
   이 코어의 실행 큐(lock-free, 스케줄러 4단계와 같은 방향)를
   드레인하며 각 AsyncTask에 대해 `handler->onExec(task, args)`
   (또는 Slab 고갈 등으로 애초에 실행 불가면 `onFailure`)를
   호출/재개한다. `submitCompletion()`이 인터럽트 컨텍스트에서
   안전하게 호출 가능해야 한다(락 없이 push + `Scheduler::
   scheduleImmediate`로 이 코어 리액터 Task를 깨움).
5. **`AsyncTaskGroup`/`AsyncTaskWaitGroup`/`AsyncTaskAwaiter`**:
   3.3절 API 그대로 구현 - `subjectCode`+`manageCode`로 그룹 내
   특정 작업을 비교/매칭. `AsyncTaskWaitGroup::waitAll()`은 스케줄러의
   비공개 block/wake를 쓰고, `AsyncTaskAwaiter::await()`는
   `AsyncTask::yield()` 반복으로 구현.
6. **타임아웃**: HPET 기반 마감 시각을 옵션으로 지원.
7. **[확정, QU-1BE6B8D2] 코루틴 기반 `onExec` 지원**:
   `libkenv/coroutine.h`(실측 검증 완료 - `std::coroutine_handle`/
   `std::coroutine_traits`만 표준 이름 유지, `kernel::SuspendAlways`/
   `SuspendNever`로 나머지 개명)를 이용해 `AsyncExecCoro`(코루틴
   반환 타입, `promise_type::operator new`가 `GenericSlabAllocator`
   를 씀) 정의. `onExec`을 이 타입으로 선언하는 경우를 지원 -
   `AsyncTaskAwaiter`를 이 코루틴의 awaitable로 재사용. **할당 실패
   시 재시도**: `AsyncExecCoro::promise_type::
   get_return_object_on_allocation_failure()`가 "할당 실패" 신호를
   돌려주면, 이 코루틴을 시작시킨 스택풀 `AsyncTask`가 `yield()`로
   리액터에 제어를 돌려주고 다음 턴에 코루틴 생성을 재시도한다
   (실측으로 프로토콜 자체는 이미 검증됨 - 재시도 루프 배선만
   남음).
8. **검증**: 임시 디버그 처리기(예: HPET 틱을 완료 이벤트로 흉내내는
   가짜 비동기 작업, onFailure 강제 유도 테스트 포함)로 등록→요청→
   완료/실패→처리기 실행 전체 경로를 QEMU에서 실측 - 여러 AsyncTask가
   순서대로/중첩(Awaiter)으로 처리되는지, 리액터가 우선순위 무시
   즉시 스케줄링으로 깨어나는지, Slab 고갈 시 onFailure가 정확히
   불리는지, 코루틴 기반 `onExec`이 할당 실패 시 정확히 재시도되는지
   확인 후 임시 코드 제거.
