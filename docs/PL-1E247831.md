# 실행 계획: 커널 전용 비동기 프레임워크(AsyncTask)

**[핵심(스택풀) 구현 완료, 2026-09-14 - 계획 PN-226CD1B5]** SP-F682B889의 `AsyncTask`/
`AsyncTaskHandler`/`AsyncCallbackRegistry`/`AsyncReactor`를 구현했다.
**착수 전제조건**이었던 Slab 할당자(PL-16E2CDA4)와 스케줄러의 즉시
스케줄링(`scheduleImmediate`, 이미 완료)이 먼저 끝나 그대로 재사용했다.
`AsyncTaskGroup`/`AsyncTaskWaitGroup`/`AsyncTaskAwaiter`, 코루틴 기반
`onExec`, 타임아웃, 실제 취소(onCancel) 호출 경로는 **아직 미착수**
(아래 "남은 것" 참고) - Syscall 서브시스템(SP-04EE2A18)이 필요로 하는
최소 substrate(제출/실행/yield/재개/완료)까지만 이번에 완성했다.

## 배경

SP-F682B889/DC-01434F82/QU-F86426D5 참고 - 원래 제안(스택 없는
콜백 체인)이 검토 결과 스택풀(`AsyncTask`, 자체 yield) + 코어당
전용 리액터 Task로 확정됐다. 이후 설계자 메시지(2026-09-14)와
QU-4F905C08(Slab 할당자 답변에 포함된 실패 처리 위임)로 콜백이
`AsyncTaskHandler`(실행/실패 두 경로 구현 책임) 인터페이스로,
식별자가 `subjectCode`(uint32_t)+`manageCode`(uint64_t) 두 코드로
바뀌었다. QU-1BE6B8D2(2026-09-14)로 C++20 코루틴 지원도 확정됐으나
이번 구현 범위에는 아직 없다(아래 참고).

## 구현 (완료된 부분)

0. **[완료, 선행] Slab 할당자**: PL-16E2CDA4 - `GenericSlabAllocator::
   alloc/free`를 AsyncTask 구조체 자신과 전용 스택 양쪽에 그대로
   재사용한다.
0-1/0-2. **[완료, 선행] 스케줄러 선점 비활성화/즉시 스케줄링**:
   PL-2D3184BC에서 이미 완료 - `Scheduler::scheduleImmediate`를
   `AsyncReactor::submitCompletion`이 그대로 쓴다.
1. **`AsyncTask` 자료구조**: `minicore/kernel/async_task.h/.cpp` 신설 -
   `savedRsp`(오프셋 0 고정)/`stackBase`/`state`/`subjectCode`/
   `manageCode`/`args`/`next`(`AtomicPtr<AsyncTask>`, 리액터 실행 큐용
   침습적 포인터). **`kContextSwitch`/`kTaskStartTrampoline`을 그대로
   재사용**하기로 확정(계획이 남겨 둔 판단 사항) - `task.cpp`의
   `Task::init()`과 완전히 동일한 스택 레이아웃을 구성하되, entry를
   고정된 `kAsyncTaskEntryWrapper`로, arg를 AsyncTask 자기 자신으로
   설정한다. 전용 스택 크기는 4KiB로 시작(`kAsyncTaskStackSize`) -
   `GenericSlabAllocator::alloc(4096)`은 2048B 초과라 자동으로
   PageFrameAllocator 직행(Order 0) 경로를 타므로 버킷화 없이 페이지
   하나를 그대로 받는다(설계 문서가 요구한 "GenericSlabAllocator
   재사용"을 그대로 만족).
   - `kAsyncTaskEntryWrapper(void* arg)`가 `AsyncCallbackRegistry::
     resolve(subjectCode)`로 처리기를 찾아 `onExec(task, args)`를
     호출하고, 정상 반환하면 `Completed`, 처리기가 없으면(등록 누락 -
     설계/구현 오류) `Failed`로 표시한 뒤 **반드시**
     `AsyncTask::yield()`로 리액터에 영구 복귀한다(Task와 달리 이
     함수가 "반환"해 트램폴린의 halt 루프로 떨어지면 이 코어가
     영원히 멈추므로).
2. **`AsyncTask::yield()`**: 리액터가 `gReactorSavedRsp[coreIndex]`에
   저장해 둔 자기 컨텍스트로 `kContextSwitch`한다. **Task 수준의
   `yieldCurrent()`/`onTick`과 달리 `cli`가 필요 없다** - AsyncTask는
   틱 기반 선점 대상이 아니고(협조적 yield만 존재), `submitCompletion`
   도 "이 AsyncTask가 지금 current인지"로 분기하지 않고 그냥 큐에
   넣기만 하므로 Scheduler 쪽에서 실측으로 발견했던 이중 스케줄링
   경쟁 조건이 애초에 발생할 수 없는 구조다(설계 검토로 확인, 실측
   으로도 재확인 - 이 결론은 여전히 유효하다: 아래 "실측으로 발견한
   추가 경쟁"은 전부 `kernel::Task` 수준(리액터 자신의 파킹/재개)
   에서만 일어났지 `AsyncTask::yield()` 자체의 문제는 아니었다).
3. **`AsyncTaskHandler`/`AsyncCallbackRegistry`**: 설계 그대로
   `onExec`/`onFailure`/`onCancel` 세 순수 가상 함수 + 고정 배열
   기반 등록 표(`kMaxHandlers=64`, v1 상한). **부수적으로 발견/해결한
   빌드 문제**: `AsyncTaskHandler`처럼 가상 소멸자를 가진 클래스의
   구체 타입을 정의하면(예: 실제 처리기 구현체), 컴파일러가 그
   vtable에 넣는 "delete하는 소멸자"(Itanium ABI D0)가 `operator
   delete` 심볼을 항상 참조한다 - 이 커널은 `-nostdlib`이라 그
   심볼이 없어 링크가 실패했다(실제로 `delete`를 호출하는 코드는
   전혀 없었는데도). `minicore/libs/libkenv/cxxabi.cpp`에 아무 일도
   하지 않는 전역 `operator delete(void*)`/`operator delete(void*,
   size_t)`를 추가해 해결 - 이 커널은 폴리모픽 포인터에 `delete`를
   쓰지 않으므로(프레임워크가 소유물을 직접 `GenericSlabAllocator::
   free`로 반납) 실제로 호출될 일은 없고, 순수히 링크를 통과시키는
   용도다(코루틴 promise_type이 각자 operator new/delete를 직접
   제공해야 했던 것과 같은 종류의 freestanding 제약).
4. **`AsyncReactor` - 코어당 전용 리액터 Task**: `Task::init`으로
   만든 일반 `kernel::Task`(코어당 하나, `gReactorTasks[coreIndex]`)
   가 `reactorTaskEntry`를 돈다 - 이 코어의 실행 큐(`AsyncTaskQueue`,
   `scheduler.h`의 `TaskQueue`와 정확히 같은 Spinlock 폴백 패턴,
   `AsyncTask::next` 재사용)에서 하나씩 꺼내 `kContextSwitch`로 진입/
   재개하고, `Completed`/`Failed`면 구조체+전용 스택을 반납한다.
   할 일이 없으면 **`Scheduler::parkCurrent()`로 파킹**한다(아래
   6단계 참고 - 이번에 새로 필요해진 스케줄러 프리미티브).
   `submitCompletion(task)`는 큐에 push한 뒤, 리액터가 **지금
   current가 아닐 때만** `scheduleImmediate`로 깨운다(이미 실행
   중이면 자기 루프가 다음에 자연히 집어가므로 - 실행 중인데도 다시
   깨우면 이중 스케줄링이 된다, Scheduler 실측 버그와 같은 종류).
   `initForThisCore()`를 BSP/AP 각자 부팅 중 한 번씩 호출한다
   (kMain은 스케줄러 틱 준비 직후, kApMain도 동일 위치).

   **[2026-09-14 추가, Channel IPC(PL-C8648D4D) 스트레스 테스트로
   실측 발견한 버그 2건 - 자세한 발견 경위는 PL-C8648D4D 참고]**
   위 "리액터가 지금 current가 아닐 때만 깨운다"는 판단 기준
   (`Scheduler::currentTask() != &gReactorTasks[coreIndex]`)이
   스케줄러 틱이 리액터를 Task 수준에서 그냥 보통의 라운드로빈으로
   선점해 버리는 경우에 완전히 어긋난다는 게 드러났다 - 그 순간
   `currentTask()`는 더 이상 리액터가 아니지만, 리액터 자신은
   (`parkCurrent()`를 실제로 부른 게 아니므로) 이미 스스로 다시
   스케줄될 수 있는 상태다. 그런데도 "안 돌고 있다"고 오판해
   `scheduleImmediate`로 또 다른 큐에 넣으면, 같은 Task가 두 큐에
   동시에 들어가는 이중 스케줄링이 된다(runLoop/yieldCurrent에서
   이미 실측 발견한 것과 같은 근본 원인). **수정 두 가지, 둘 다
   `async_task.cpp`**:
   1. `Scheduler::currentTask()` 기반 판단을 **전용 플래그
      `gReactorParked[coreIndex]`**로 대체 - `reactorTaskEntry()`가
      진짜로 `Scheduler::parkCurrent()`를 부르기 직전(`cli`로 보호된
      구간)에만 `true`로 세우고, `submitCompletion()`이 그 값을
      확인+소비(`false`로 되돌림)한다 - `currentTask()`가 무엇이든
      (틱 선점으로 바뀌었든 말든) 상관없이 "진짜로 명시적 wake가
      필요한가"만 정확히 반영한다. 이 함수는 인터럽트 컨텍스트에서도
      호출 가능하다고 문서화돼 있어(위 헤더 주석) 무조건 `sti`로
      끝내면 안 된다 - `pushfq`로 원래 RFLAGS.IF 값을 저장해 뒀다가
      그 값이었을 때만 되돌린다.
   2. `reactorTaskEntry()`가 AsyncTask 하나를 실제로 구동하는
      `kContextSwitch` 호출 전체를 **`PreemptionGuard`로 감싼다** -
      AsyncTask 프레임워크의 원래 설계 의도(위 2번 항목 - "AsyncTask는
      틱 기반 선점 대상이 아니다")를 실제로 강제한다(이전에는
      kContextSwitch의 기계적 안전성에만 기대고 있었을 뿐 이
      불변조건 자체는 강제되지 않았다). `reactorTaskEntry()`가
      `Scheduler::parkCurrent()`를 부르는 지점(할 일이 없을 때) 자체는
      이 결론과 같은 종류의 또 다른 틈이 있어 별도로 `cli`를
      추가했다(PL-2D3184BC "이중 스케줄링 버그 클래스의 구조적
      방지책" 절 참고 - 최종적으로는 `Task::inRunQueue` 구조적
      수정으로 이 부류 전체가 해결됨).
5. **[신규, 이번 구현에서 추가] `Scheduler::parkCurrent()`**:
   PL-2D3184BC 6단계("특정 이유로 블로킹 후 누군가 깨울 때까지 대기")
   가 "첫 소비자가 생길 때" 노출하기로 미뤄 뒀던 바로 그 프리미티브 -
   **AsyncReactor가 그 첫 소비자**였다(당초 계획은 Syscall 서브시스템을
   첫 소비자로 예상했으나, 구현 순서상 AsyncReactor가 더 먼저 이
   프리미티브를 필요로 함이 드러났다). `yieldCurrent()`와 거의 같지만
   **큐에 다시 넣지 않는다** - 깨우는 쪽은 별도 API 없이 이미 있는
   `scheduleImmediate()`를 그대로 쓴다(파킹된 Task는 어느 큐에도 없어
   이중 스케줄링 걱정이 없다). `yieldCurrent()`와 동일한 이유로
   `cli` 보호가 필요하다(같은 종류의 경쟁을 사전에 차단).

## 검증(QEMU, 완료)

임시 디버그 처리기(검증 후 제거)로 제출→실행→yield→외부 재제출→재개
→완료→정리 전체 경로를 확인했다 - 단일 코어(PVH)와 4코어 SMP
(GRUB+q35 `-smp 4`) 둘 다 회귀 없이 통과:

- 리액터 Task 최초 실행 시 할 일이 없으면 정상적으로 파킹(멈추지
  않고 이후 부팅이 계속 진행됨을 확인).
- `AsyncTask::submit`이 args(힙에 할당한 값)를 정확히 전달 -
  `onExec`에서 그 값을 읽어 그대로 출력함을 확인(`[A1-0x2a]`).
- `onExec` 안에서 `AsyncTask::yield()`로 중단한 뒤, 별도 Task가
  (실제 I/O 완료 인터럽트를 흉내내) `submitCompletion`으로 다시
  제출하자 **같은 `onExec` 호출이 yield 직후 지점부터 정확히
  이어져** 재개됨을 확인(`[A2]`) - 스택풀 컨텍스트 보존이 Task
  수준과 동일하게 AsyncTask 수준에서도 성립함을 실측으로 검증.
- 4코어 SMP 부팅(3개 AP 정상 기동) 및 10초 연속 실행 중 크래시 없음.

검증 후 임시 처리기/드라이버 Task 코드는 제거 - 영구 코드는
`async_task.h/.cpp`, `scheduler.h/.cpp`의 `parkCurrent()`,
`libkenv/cxxabi.cpp`, `kmain.cpp`/`smp.cpp`의
`AsyncReactor::initForThisCore()` 호출 두 줄만 남았다.

**[2026-09-14 추가]** 위 4단계의 `gReactorParked`/`PreemptionGuard`
수정은 Channel IPC(PL-C8648D4D)의 4-Task 동시 동작 스트레스 테스트로
재검증됐다 - 진단 코드를 완전히 제거한 최종 빌드로 SMP4 연속 50회
무크래시(자세한 수치는 PL-C8648D4D 참고, `Task::inRunQueue` 구조적
수정과 함께 적용된 뒤의 결과).

## 남은 것 (아직 미착수 - Syscall/Channel IPC의 필수 전제조건은 아님)

5(원문 번호). **`AsyncTaskGroup`/`AsyncTaskWaitGroup`/
`AsyncTaskAwaiter`** (계획 PN-22438B73): 여러 AsyncTask를 묶어 대기하는 상위 조합
API - Syscall 서브시스템의 기본 흐름(submit 하나 -> yield ->
완료 알림으로 재개)은 이것 없이도 동작하므로 후순위로 미룸. **참고
(2026-09-14, 설계자 지시)**: `waitForMultipleSyscall`/
`waitAnyForMultipleSyscall`(Syscall 수준 변형, 별도 문서에서 다룸,
계획 PN-BCE6CFF3)이 먼저 필요해졌다 - 이 AsyncTask 수준 Group/
WaitGroup/Awaiter는 그 구현이 실제로 필요로 하게 되면 같이 재검토한다.
6(원문 번호). **타임아웃** (계획 PN-D01B7D07): HPET 기반 마감 - 아직 미착수.
7(원문 번호). **코루틴 기반 `onExec` 지원** (계획 PN-C62F7908): SP-F682B889 §7이 확정한
`AsyncExecCoro`/`kernel::SuspendAlways` 등 - `libkenv/coroutine.h`
자체는 이전 세션에 이미 실측 검증돼 있으나, `onExec`을 코루틴으로
선언하는 실제 경로/할당 실패 시 재시도 루프는 아직 연결 안 함.
**취소(onCancel) 실제 호출 경로** (계획 PN-40E976F2): Task/프로세스 종료 절차 자체가
이 프로젝트에 아직 없어 `onCancel`을 부르는 지점이 없다 - 프로세스
모델이 생길 때 같이 연결해야 한다(SP-04EE2A18에도 동일하게 기록됨).
8(원문 번호). **검증**: 이번 스택풀 substrate만 QEMU 실측 완료(위
참고) - Group/WaitGroup/Awaiter/코루틴/타임아웃은 그 기능이 실제로
구현될 때 각각 검증 예정.

## 다음 소비자

**Syscall 디스패치 서브시스템(SP-04EE2A18)**이 이 AsyncTask
substrate의 첫 실제 소비자였다(PL-21344323) - 그 다음 **Channel
IPC(SP-1FBC0EEB, PL-C8648D4D)**가 이 substrate를 훨씬 더 높은
제출/yield 밀도로 스트레스 테스트하며 위 4단계의 두 버그를
드러냈다. 다음은 `waitForMultipleSyscall`/`waitAnyForMultipleSyscall`
(설계자 지시, 2026-09-14)이다.
