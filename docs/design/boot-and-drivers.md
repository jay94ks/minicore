## ADR-017. 부트 프로토콜: Multiboot2 + UEFI 이중 지원, initrun은 커널이 직접 시작 (해결: OPEN-7)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널은 **Multiboot2**(BIOS/GRUB 경로)와 **UEFI**(직접 부팅) 양쪽에서
  진입 가능한 엔트리포인트를 모두 갖는다. 어느 경로로 부팅되었든 커널 초기화가
  끝나면, 커널이 initrd/부트 이미지 안의 initrun 바이너리를 **직접 로드**하여
  첫 유저 프로세스로 실행한다 (별도의 2단계 유저 로더 없음).
- **근거**: Multiboot2는 QEMU/GRUB 개발 반복이 빠르고, UEFI는 실기(특히 최신
  하드웨어)와 향후 aarch64 부팅에 필요하다. initrun을 커널이 직접 시작하면
  "부트로더가 유저 프로세스 개념을 알아야 하는" 계층 누수를 없앨 수 있다.
- **영향**:
  - 커널 진입점이 두 개(Multiboot2 헤더 경유 / UEFI 애플리케이션 경유)이며,
    이후 공통 초기화 경로로 합류하는 arch 계층 코드가 필요하다.
  - aarch64(ADR-009 2순위 타겟)는 QEMU virt 관례상 디바이스 트리 기반의 별도
    진입 방식이 필요해, 사실상 세 번째 부팅 경로가 된다. → **미결정 (OPEN-19)**
  - initrun에게 넘길 초기 인자(메모리 맵, 커맨드라인, initrd 위치 등)의
    형식 정의가 필요하다. → OPEN-19에 포함.

## ADR-026. aarch64 부팅: 공통 boot_info 구조체로 통일 (해결: OPEN-19)

- **상태**: 확정 (2026-09-08)
- **결정**: x86_64(Multiboot2/UEFI)와 aarch64(FDT)는 각자의 네이티브 부팅
  프로토콜을 arch 계층에서 파싱한 뒤, 공통 `boot_info` 구조체(메모리맵,
  initrd 위치·크기, 커맨드라인, CPU 코어 정보 등)로 변환하여 커널 코어
  초기화와 initrun에 전달한다.
- **근거**: ADR-002(HAL 경계)와 ADR-017(부팅 이중 지원)의 자연스러운 연장 —
  커널 코어와 initrun이 부팅 프로토콜의 존재 자체를 몰라도 되게 한다.
- **영향**:
  - `kernel/include`에 아키텍처 독립적인 `boot_info` 구조체(공유 ABI)를
    정의해야 한다 (`docs/design/repo-layout.md`의 `kernel/include` 위치와 일치).
  - aarch64 arch 계층은 FDT 파서를 **직접 구현**해야 한다(ADR-006과 일치 —
    서드파티 FDT 라이브러리 사용 금지, 필요한 최소 파싱만 자체 구현).
  - `boot_info`를 initrun에게 실제로 전달하는 메커니즘(레지스터/스택/
    공유 페이지)은 별도 결정 필요. → **미결정 (OPEN-22)**

## ADR-030. boot_info 전달 메커니즘: 아키텍처 관례상의 첫 인자 레지스터 (해결: OPEN-22)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널은 `boot_info`(spec/boot.md §3)가 담긴 페이지를 initrun
  주소공간에 읽기전용으로 매핑하고, 그 가상주소를 initrun 최초 스레드
  진입 시 **아키텍처 관례상 "첫 인자" 레지스터**로 전달한다: x86_64는
  `RDI`, aarch64는 `X0`.
- **근거**: 각 아키텍처의 함수 호출 규약에서 이미 "첫 인자"로 쓰이는
  레지스터를 재사용하면, initrun 진입 스텁을 평범한 함수 호출처럼
  `_start(const boot_info* info)` 형태로 작성할 수 있어 가장 단순하다.
  `docs/spec/boot.md` 작성을 구체화하는 과정에서 확정이 필요해 이 시점에
  결정했다(사용자 확인 전 임시 채택 — 이견 시 언제든 대체 가능).
- **영향**:
  - initrun 이후 다른 서버를 기동할 때는 이 관례를 강제하지 않는다 —
    각 서버의 시작 인자 형식은 initrun 자신의 설계(기동 매니페스트,
    미정)에 맡긴다.

## ADR-037. 디버그 콘솔: 커널 내장 시리얼 드라이버로 확정 (ADR-007 구체화)

- **상태**: 확정 (2026-09-08)
- **결정**: ADR-007에서 "커널 내부에 둘 것"으로 이미 정한 "시리얼/초기
  콘솔(디버그용)"을 구체화한다. x86_64는 **16550 호환 UART(COM1, I/O
  포트 `0x3F8`)**, aarch64는 **PL011 UART(QEMU virt MMIO `0x09000000`)**를
  커널이 직접 구동하는 **폴링 기반** 디버그 로깅 경로로 삼는다. 이 경로는
  유저 프로세스에게 노출되지 않으며, ADR-007이 말하는 "이후 유저
  프로세스로 구현될 실제 콘솔 드라이버"와는 완전히 별개다.
- **근거**: 유저 프로세스는커녕 IPC조차 없는 부팅 극초기부터 커널
  개발 전 과정에 걸쳐 관찰 가능한 로그가 없으면 디버깅이 사실상
  불가능하다. [kernel-bootstrap.md](../plan/kernel-bootstrap.md) M1의
  첫 관찰 가능한 산출물("hello from kernel")도 이 경로에 의존한다.
- **영향**:
  - [debug-console.md](../spec/debug-console.md)에 레지스터 수준 스펙과
    커널 내부 `klog` API를 정의한다(즉시 작성).
  - 이 로그 경로는 성능이 중요하지 않으므로 ADR-033("필요한 곳만 최소
    범위 락")의 예외로 **전역 스핀락 1개**를 허용한다 — 여러 코어가
    동시에 로그를 남겨도 출력 순서가 뒤섞이지 않게 한다.
  - 인터럽트 기반 비동기 로깅, 커널 패닉 덤프 절차는 이 ADR의 범위
    밖이며 필요 시 후속 결정으로 다룬다.

## ADR-038. PCIe 설정 공간 접근: ECAM 우선 + 레거시 I/O 포트 폴백

- **상태**: 확정 (2026-09-08)
- **결정**: PCIe 설정 공간은 ACPI MCFG 테이블로 알려지는 ECAM(메모리
  매핑) 방식을 우선 사용한다. MCFG가 없거나 실패하면 x86 레거시
  I/O 포트(`0xCF8`/`0xCFC`, CONFIG_ADDRESS/CONFIG_DATA)로 대체한다.
- **근거**: ECAM은 QEMU q35 및 대부분의 실제 하드�웨어에서 표준이며
  전체 설정 공간(4KB/장치)에 접근 가능하다. 레거시 폴백은 극히 오래된
  환경이나 MCFG 파싱 실패 시의 안전망이다.
- **영향**:
  - ECAM은 그냥 MMIO 영역이므로 ADR-007의 기존 "MMIO 캐패빌리티 매핑"
    메커니즘을 그대로 재사용한다 — 새 캐패빌리티 종류가 필요 없다.
  - 레거시 I/O 포트 접근은 x86 전용 특권 명령(`in`/`out`)이 필요하므로
    **새로운 캐패빌리티 종류(I/O 포트 범위 권한)**가 필요하다 — 이
    권한은 devmgr에게만 부여되고, PCIe 자체 드라이버들은 devmgr가
    이미 열거한 결과(BAR, IRQ 등)만 넘겨받으므로 직접 포트 접근이
    필요 없다.
  - MCFG 파싱은 x86_64 `arch_data_addr`(ACPI RSDP, ADR-036)을 통해
    devmgr가 접근한다.

## ADR-039. 버스 열거·PnP 매칭 책임: devmgr 전담, 새 syscall 없음

- **상태**: 확정 (2026-09-08)
- **결정**: PCIe 버스 열거와 장치-드라이버 매칭(PnP)은 devmgr가 전담한다
  (ADR-007에서 이미 devmgr의 역할로 정한 "버스 열거"의 구체화). ECAM은
  일반 MMIO 영역이므로, 커널에 PCI 전용 syscall을 추가하지 않고 기존
  MMIO 캐패빌리티 매핑 메커니즘만으로 devmgr가 설정 공간을 직접 읽는다.
- **근거**: ADR-007의 경계(버스 열거는 유저 프로세스)와 정확히 일치하며,
  새로운 커널 개념을 도입하지 않아 커널이 작게 유지된다(ADR-001의
  "커널 밖으로 미는" 원칙).
- **영향**:
  - devmgr는 부팅 후 ECAM 영역 전체(또는 필요한 버스 범위)를 자신의
    주소공간에 매핑할 캐패빌리티를 커널/initrun으로부터 받아야 한다 —
    구체적 위임 경로는 initrun의 기동 매니페스트 설계(OPEN-29)에서 다룬다.
  - 레거시 I/O 포트 폴백(ADR-038)이 필요한 경우에만 devmgr가 포트
    접근 캐패빌리티를 추가로 받는다.

## ADR-040. PCIe 핫플러그 이벤트: 커널 인터럽트 → 비동기 notification

- **상태**: 확정 (2026-09-08)
- **결정**: PCIe 핫플러그/PME 인터럽트는 커널이 수신하여 ADR-004의
  비동기 notification으로 devmgr에게 전달한다. devmgr는 notification을
  받으면 ECAM을 다시 스캔해 변경 사항(장치 추가/제거)을 스스로 판별한다.
- **근거**: ADR-007이 이미 "인터럽트는 커널이 받아 유저 드라이버에게
  notification으로 전달"로 정해두었다 — 핫플러그도 결국 인터럽트이므로
  기존 구조를 그대로 재사용할 뿐 새로운 개념이 필요 없다. ACPI GPE
  경유 방식은 커널이 ACPI 이벤트 해석까지 직접 구현해야 해서 범위가
  불필요하게 커진다.
- **영향**:
  - devmgr는 notification 수신 시 "무엇이 바뀌었는지"를 스스로
    diff(이전 열거 결과와 재스캔 결과 비교)해야 한다 — 커널은 변경
    내용을 알려주지 않고 "뭔가 바뀌었을 수 있다"는 신호만 준다.

## ADR-041. 드라이버 등록/매칭(PnP): 실행 중 devmgr에 동적 ID 등록

- **상태**: 확정 (2026-09-08)
- **결정**: 드라이버 프로세스는 기동 후 devmgr에게 IPC로 "나는 이
  vendor:device(또는 클래스) 목록을 처리한다"고 동적으로 등록한다.
  devmgr는 이미 열거된 장치와 새로 등록된 드라이버를 그때그때 매칭하며,
  드라이버가 재시작되어도(ADR-007의 감시자 재시작) 동일한 등록 절차를
  다시 밟으면 되므로 재시작에 자연스럽게 대응한다.
- **근거**: initrd 정적 테이블 방식은 구현이 간단하지만 "드라이버를
  나중에 파일시스템에서 추가로 발견"하는 시나리오(ADR-001의 범용 OS
  지향, 장기적으로 드라이버 패키지를 설치하는 것과 같은 그림)를 처음부터
  막는다. 동적 등록은 초기엔 그대로 "부팅 시점에 이미 떠 있는 드라이버들만
  등록"하는 것으로 시작해도 되므로, 정적 방식과 초기 동작이 동일하면서
  확장 여지를 남긴다.
- **영향**:
  - devmgr↔드라이버 간 "등록" IPC 프로토콜(ID 목록 형식, 우선순위/충돌
    시 정책)을 정의해야 한다 — spec 대상.
  - 드라이버 자신도 기동 시점을 알아야 하므로, initrun의 기동
    매니페스트(OPEN-29)가 "이 드라이버들을 언제 띄울지"를
    결정하는 지점이 된다 — devmgr 자체는 정적 목록을 몰라도 되지만,
    누군가는(initrun) 드라이버 프로세스를 실행시켜야 한다.
  - 동일 장치에 여러 드라이버가 등록을 시도할 때의 충돌 해소 정책은
    미정 → **미결정 (OPEN-26)**

## ADR-043. 디바이스 드라이버 로드맵: virtio 계열 우선, 실기 표준은 후속

- **상태**: 확정 (2026-09-08)
- **결정**: 스토리지·NIC·그래픽 드라이버(모두 유저 프로세스, ADR-007)는
  각자 독립적인 우선순위를 갖되, 공통적으로 **QEMU virtio 계열을 먼저
  구현하고 실기 표준 프로토콜은 그 다음 단계로 미룬다**.

  | 클래스 | 1순위 | 2순위 | 비고 |
  |---|---|---|---|
  | 스토리지(블록 드라이버) | `virtio-blk` | AHCI(SATA) → NVMe(M.2) | AHCI가 NVMe보다 먼저 |
  | 파일시스템 서버 | FAT32 | (추가 FS는 필요 시 결정) | virtio-blk 검증 직후 착수 (ADR-057). 블록 드라이버 무관하게 재사용 |
  | NIC | `virtio-net` | e1000(실기용) | |
  | 그래픽 | `virtio-gpu`(프레임버퍼 모드) | VESA(BIOS)/UEFI GOP(프레임버퍼) | 3D 가속은 이 로드맵 범위 밖(장기 과제) |

- **근거**: virtio는 QEMU 개발 환경에서 프로토콜이 가장 단순해 각
  드라이버 클래스(그리고 그 위의 서버 — 파일시스템, netsrv, 콘솔)를
  빠르게 수직으로 검증할 수 있게 한다. 실기 표준(AHCI/NVMe/e1000/
  VESA·GOP)은 범용 OS 지향(ADR-001)에 필수적이지만 프로토콜이 훨씬
  복잡해, virtio로 상위 스택(파일시스템, 네트워크 스택, 콘솔 서버)을
  먼저 검증해둔 뒤에 하드웨어 드라이버만 교체하는 순서가 이중 작업을
  줄인다. AHCI가 NVMe보다 사양이 오래되고 자료·구현 난이도가 낮아
  먼저 선택되었다. 그래픽은 3D 가속이 사실상 별도 대형 프로젝트급
  범위이므로 프레임버퍼(모드 설정 + 픽셀 버퍼)까지만 이 로드맵에 넣는다.
- **영향**:
  - 모든 항목은 PCIe 장치이므로 ADR-038~041(설정공간 접근, devmgr
    열거, 핫플러그, 동적 드라이버 등록)을 그대로 따른다 — 클래스별
    특수 규칙이 필요 없다.
  - `servers/drivers/`(repo-layout.md) 하위에 클래스별 서브디렉토리를
    추가할 때 이 순서를 기본 작업 순서로 삼는다.
  - 각 드라이버의 레지스터 수준 프로토콜 스펙은 해당 마일스톤 착수
    시점에 `docs/spec/`에 개별 작성한다(지금은 로드맵 순서만 확정).
  - 3D 가속, GPU 컴퓨트는 로드맵 밖으로 명시적으로 제외했다 —
    필요해지면 별도 ADR로 범위를 연다.

## ADR-046. /boot 구성: 일반 디렉토리 + /boot/uefi에 ESP 마운트

- **상태**: 확정 (2026-09-08)
- **결정**: `/boot`는 루트 파일시스템 안의 평범한 디렉토리이며,
  커널 이미지·initrd 등 Multiboot2 경로(ADR-017)에 필요한 파일들이
  직접 위치한다. UEFI 부팅(ADR-017)에 필요한 EFI System
  Partition(FAT32)은 `/boot/uefi`에 **마운트**된다.
- **근거**: 대부분의 부팅 자산(커널, initrd)은 일반 디렉토리로
  충분하고, UEFI ESP만 FAT32라는 특수 포맷 제약이 있으므로 그
  부분만 별도 마운트로 분리하는 것이 가장 단순하다.
- **영향**:
  - FAT32 드라이버(FS 서버)가 `/boot/uefi` 마운트에 필요하다 —
    ADR-043의 드라이버 로드맵에는 아직 없으므로, UEFI 부팅 경로를
    실제로 완성하려면 FAT32 FS 서버 작업이 로드맵에 추가되어야 한다.
    → 로드맵 갱신 필요 (실제 착수 시점에 ADR-043 갱신 또는 후속 ADR).
  - Multiboot2 전용 개발(현재 kernel-bootstrap.md M1~M8, ADR-009)에는
    `/boot/uefi` 마운트가 필요 없다 — ESP는 UEFI 부팅 경로를 실제로
    쓸 때만 의미가 있다.

## ADR-056. 드라이버 등록 충돌: 선착순 기본 + 관리자 설정으로 대체 가능 (해결: OPEN-26)

- **상태**: 확정 (2026-09-08)
- **결정**: 기본 정책은 **선착순**(먼저 등록한 드라이버가 소유, 이후
  시도는 거부)이다. 다만 시스템 관리자(root) 계정이 명시적 설정
  (설정 파일 또는 관리 명령)으로 특정 장치-드라이버 바인딩을 고정하면,
  devmgr는 그 설정을 선착순보다 **우선 적용**한다 — 관리자가 지정한
  드라이버가 기존 선착순 소유자를 대체할 수 있다.
- **근거**: 선착순은 구현이 단순하고 예측 가능한 기본 동작이다.
  그러나 실제 운영에서는 특정 장치에 항상 특정 드라이버를 강제하고
  싶은 경우(예: 범용 드라이버보다 벤더 특화 드라이버 우선)가 있으므로,
  관리자 오버라이드 경로를 열어둔다.
- **영향**:
  - 관리자 설정은 `/sys/etc`(ADR-044) 아래의 설정 파일로 보관하는
    것이 자연스럽다 — 구체적 파일 위치·형식은 devmgr 설계 시 정한다.
  - devmgr는 "root 권한으로 인증된 요청"을 검증하는 수단이 필요하다
    — ADR-027/ADR-024와 같은 정책 서버 프록시 기반 특권 메커니즘을
    재사용할 수 있다(관리자 전용 프록시 핸들).
  - 관리자 설정에 의해 대체된 기존 드라이버는 `device_removed`
    통지(pcie.md §4)를 받는다.

## ADR-057. FAT32 FS 서버를 드라이버 로드맵에 즉시 추가 (ADR-043 갱신) (해결: OPEN-27)

- **상태**: 확정 (2026-09-08)
- **결정**: FAT32는 블록 드라이버가 아니라 그 위에 얹히는 **파일시스템
  서버**(`servers/fs/`, memfs와 같은 층)다. ADR-043의 스토리지
  로드맵과는 다른 축이지만, 우선순위를 명시적으로 확정한다: **virtio-blk
  검증 완료 직후 착수** — virtio-blk가 이미 1순위 블록 드라이버이므로
  FAT32는 그 위에서 바로 개발·검증을 시작할 수 있고, AHCI/NVMe가
  나중에 준비되어도 FAT32 서버 자체는 블록 드라이버에 무관하게
  재사용된다.
- **근거**: `/boot/uefi`(ADR-046)의 ESP 마운트에 FAT32가 필요하며,
  UEFI 부팅 경로(ADR-017)를 실제로 검증하려면 이 서버가 있어야 한다.
  블록 드라이버 우선순위 리스트에 끼워 넣지 않고 별도로 명시하는
  이유는, FAT32가 "어떤 블록 드라이버 위에서도" 동작해야 하는
  블록-드라이버-비의존적 컴포넌트이기 때문이다.
- **영향**:
  - ADR-043의 표에 "파일시스템 서버" 행으로 FAT32를 추가한다(즉시
    반영).
  - `vfs-layout.md`의 OPEN-27이 이 결정으로 해소된다 — 로드맵
    편입 시점은 "지금 확정, virtio-blk 다음"이다.

## ADR-097. 콘솔/TTY 드라이버: 다중 가상 TTY + 텍스트/그래픽 렌더링 백엔드 자동 전환 (OPEN-39 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. ADR-007이 예고한, 커널 디버그 콘솔(ADR-037)과는 완전히 별개인
     **유저 프로세스 콘솔 드라이버**를 신설한다(`servers/drivers/console/`).
     이 드라이버는 N개의 **가상 TTY**를 관리하며, 각각
     `/sys/dev/tty{N}` 장치 노드로 VFS에 노출한다(devmgr의 `/sys/dev`
     관례, ADR-048).
  2. **TTY 개수와 "메인 TTY"**(부팅 직후 화면에 바로 보이는 TTY)는
     시스템 설정으로 제어한다 — `@global/system/tty` 레지스트리
     테이블(`count`: TTY 개수, `main`: 부팅 시 기본으로 보여줄 TTY
     번호), super만 쓰기 가능.
  3. **렌더링 백엔드는 두 가지이며 자동으로 전환된다**:
     - 그래픽 드라이버가 아직 초기화되지 않았으면 **텍스트 모드**
       (VGA 텍스트 버퍼 또는 그에 준하는 최소 경로)로 렌더링한다.
     - 그래픽 드라이버(virtio-gpu 등, ADR-043 로드맵)가 초기화되면,
       같은 TTY 문자 버퍼를 프레임버퍼 위에 글리프로 그리는 방식
       (Linux의 fbcon류)으로 전환한다.
     TTY 자체의 개념(문자 버퍼, 장치 노드, 입출력 프로토콜)은 두
     백엔드에서 동일하다 — **렌더링 방식만 다르다.**
  4. TTY 여러 개 중 **한 번에 하나만 화면에 실제로 보인다**(활성
     TTY, 기본값은 "메인 TTY") — 나머지는 백그라운드에서 계속
     동작한다(예: 다른 TTY의 로그인 프롬프트가 계속 입력을 기다림).
     TTY 간 전환(키 조합 등)의 정확한 UX는 이 ADR의 범위 밖이다.
- **근거**: 사용자가 "부팅 시 바로 보이는 TTY가 메인이고, Linux처럼
  여러 TTY가 있을 수 있으며 시스템 설정으로 제어되어야 한다"고,
  또 "그래픽 드라이버가 초기화되면 그래픽 모드로 TTY를 렌더링하면
  된다"고 명시했다. 이미 있는 메커니즘만 재사용한다 —
  `/sys/dev`·synthetic FS 패턴(ADR-047/048), 레지스트리 설정 저장
  (ADR-060~062), 드라이버 로드맵(ADR-043)의 그래픽 드라이버 항목.
  새로 도입하는 개념은 "TTY 자체는 렌더링 백엔드로부터 독립적이다"
  하나뿐이며, 이는 Linux의 VT(가상 터미널)+fbcon 모델을 그대로
  참고한 것이다.
- **영향**:
  - [vfs-layout.md](../spec/vfs-layout.md)에 `/sys/dev/tty{N}` 관례를
    반영해야 한다(devmgr 담당, 스펙 갱신 대상).
  - `@global/system/tty` 레지스트리 스키마를
    [registry.md](../spec/registry.md) 갱신 시점에 반영해야 한다.
  - procsrv의 로그인 프롬프트 프로세스 기동 개수는 이제
    `@global/system/tty`의 `count`를 따른다 — initrun 기동 매니페스트
    (OPEN-29)가 "TTY 개수만큼 로그인 프롬프트를 띄운다"는 규칙을
    반영해야 한다.
  - stdin/stdout/stderr가 실제로 어느 TTY로 연결되는지(세션별 fd
    라우팅)는 procsrv/신원 모델 쪽 결정이라 이 ADR의 범위 밖이다 —
    [security-model.md](security-model.md) ADR-098에서 다룬다.
  - 콘솔 드라이버의 상세 프로토콜(문자 버퍼 형식, 커서 위치, 프레임
    버퍼 글리프 렌더링 세부, TTY 전환 키 조합)은 이 ADR의 범위
    밖이다 → 신규 **미결정 (OPEN-43)**.

## ADR-111. 콘솔 드라이버 상세 프로토콜: 새로 고안하지 않고 기존 표준 TTY 관례를 채택 (해결: OPEN-43)

- **상태**: 확정 (2026-09-08)
- **결정**: 문자 버퍼 형식, 프레임버퍼 글리프 렌더링, TTY 전환 키
  조합 등 콘솔 드라이버의 상세 프로토콜은 **minicore 고유의 새
  프로토콜을 고안하지 않고, 이미 널리 쓰이는 TTY/가상 터미널
  관례를 그대로 채택**한다(예: 문자 셀 버퍼 레이아웃과 표준 콘솔
  글리프 비트맵 포맷, ANSI/VT100류 이스케이프 시퀀스, Ctrl+Alt+F<N>
  류의 TTY 전환 키 조합 — Linux VT/fbcon이 대표적 참고 사례). 정확히
  어떤 기존 구현·표준을 참고할지의 세부 목록은
  `servers/drivers/console/` 구현 시점에 정한다.
- **근거**: 사용자가 "이미 다른 TTY 시스템에 존재하는 개념이라 따로
  고안할 이유가 없다"고 명시했다. ADR-097의 근거에서도 이미 Linux의
  VT(가상 터미널)+fbcon 모델을 참고하기로 했으므로, 이 결정은 그
  방향을 상세 프로토콜 수준까지 일관되게 확장한 것이다 — 커널·서버
  전반에서 이미 지켜온 "새 개념을 발명하지 않고 검증된 기존
  메커니즘을 재사용한다"는 원칙(ADR-004, ADR-097 등)과도 같다.
- **영향**:
  - `servers/drivers/console/` 구현 및 관련 스펙 문서에, 채택할
    구체적 기존 표준(문자 셀 버퍼 포맷, 이스케이프 시퀀스 방언, 글리프
    폰트 형식 등)을 명시하는 작업은 상세 설계 단계로 넘긴다.
  - OPEN-43은 "새로 설계하지 않는다"는 원칙 수준에서 해소된다.

## ADR-114. QEMU 검증 경로: PVH ELF Note 추가 (Multiboot2/UEFI 부팅 프로토콜 자체는 불변)

- **상태**: 확정 (2026-09-08)
- **결정**: `docs/plan/kernel-bootstrap.md` M1 구현 중, QEMU(11.1, 이
  개발 머신에 설치)의 **내장 `-kernel` 직접 로더는 Multiboot2를 전혀
  인식하지 못하고, 64비트 ELF(`EM_X86_64`) 커널도 명시적으로 거부
  한다**는 사실을 실제 QEMU 소스(`hw/i386/multiboot.c`)와 실행 결과로
  확인했다 — `ADR-017`이 Multiboot2를 선택한 근거("QEMU/GRUB 개발
  반복이 빠르고")는 GRUB를 통한 반복을 가정한 것이었는데, 이 개발
  머신(Windows, MSYS2)에는 GRUB(`grub-mkrescue`)를 구할 패키지가 없어
  그 경로를 그대로 쓸 수 없다. 대신 QEMU가 함께 배포하는 `qboot.rom`
  펌웨어를 통한 **Xen/PVH 직접 부팅**(ELF Note
  `XEN_ELFNOTE_PHYS32_ENTRY=18`로 32비트 물리 진입점을 알림, 64비트
  ELF 컨테이너를 그대로 지원)을 QEMU 검증 전용 경로로 추가한다.
  `tools/run-qemu.sh`가 `-bios qboot.rom -kernel <elf>`로 이 경로를
  사용한다.
- **근거**: PVH 진입 시 CPU 상태(32비트 보호모드, 페이징 꺼짐, 플랫
  세그먼트, "GDT/IDT/스택은 커널이 직접 구성")가 Multiboot2 진입
  상태와 사실상 동일해([boot.md](../spec/boot.md) §1.1/§1.4),
  `_start32`를 두 경로가 그대로 공유할 수 있다 — 새 진입 스텁을 따로
  만들 필요가 없다. 반대로 GRUB를 이 개발 머신에 실제로 설치하는
  것(소스 빌드 필요, MSYS2 패키지 없음)은 M1의 범위를 크게 벗어나는
  별도 작업이라 지금 시점에는 보류한다.
- **영향**:
  - **ADR-017(Multiboot2+UEFI 이중 지원)은 변경 없음** — 이 ADR은
    실제 배포·실기 부팅 경로를 하나도 바꾸지 않는다. PVH 노트는
    §1.1의 Multiboot2 헤더 옆에 추가되는 것일 뿐, 그것을 대체하지
    않는다.
  - `kernel/arch/x86_64/link.ld`가 `PT_NOTE` 프로그램 헤더를 명시적으로
    생성해야 한다(PHDRS 블록 필요) — 자동 세그먼트 생성에 맡기면
    노트가 다른 섹션과 섞여 `PT_NOTE`가 만들어지지 않는다.
  - 실제 GRUB(Multiboot2 ISO) 기반 검증은 여전히 하지 않은 상태로
    남는다 — 실기 또는 GRUB를 구할 수 있는 환경에서 별도로 검증이
    필요하다. 지금까지 확인한 것은 "PVH 경로로 QEMU 부팅 성공"까지다.
  - `docs/spec/boot.md` §1.4에 이 경로를 명시했다.

## ADR-117. Multiboot2 파서 검증: GRUB 부재 시 자체 제작 fixture로 self-test

- **상태**: 확정 (2026-09-08)
- **결정**: `kernel-bootstrap.md` M2(Multiboot2 태그 파서,
  `kernel/arch/x86_64/boot_info_x86_64.cpp`)는 ADR-114가 이미 확인한
  "이 개발 머신에는 GRUB가 없다"는 한계 때문에, 실제 GRUB가 준
  Multiboot2 정보로는 검증할 수 없다(QEMU PVH 경로는 애초에 Multiboot2
  정보 자체를 주지 않는다). 대신 손으로 만든 최소 Multiboot2 info 블록
  (메모리맵 태그 2개 항목, 모듈 태그 1개, 커맨드라인 태그 1개, 끝 태그)을
  커널 이미지 안에 정적으로 두고, **실제 파서 함수
  (`build_boot_info()`)를 그 블록에 대해 그대로 호출**해 결과를 klog에
  `[boot_info:selftest]` 태그로 덤프한다 — 파서 전용 별도 코드 경로를
  만들지 않고 실제 파서를 그대로 재사용한다. `tools/smoke-test-x86_64.sh`가
  이 출력(`memory_map_count=4`, `initrd_addr=...`)을 검사해 CI/반복
  검증 가능하게 만든다.
- **근거**: ADR-077이 이미 "libk은 호스트 네이티브 단위테스트, 하드웨어
  의존 부분은 QEMU 산출물 정적 분석"이라는 원칙을 세웠다 — Multiboot2
  파싱 로직 자체는 순수 포인터 연산(하드웨어 의존 없음)이라 원칙상
  호스트 네이티브 테스트 대상이지만, 지금은 별도 호스트 테스트 빌드
  인프라가 없다(ADR-077이 "필요해지는 시점에 정한다"고 미뤄둔 부분).
  GRUB 없이도 QEMU 부팅 자체로 반복 검증하려면 fixture를 커널에 내장하는
  것이 가장 빠른 경로였다 — 실제 파서 함수를 그대로 쓰므로 "테스트만
  통과하고 실제 경로는 다른 버그가 있는" 위험도 없다.
  `kernel/arch/x86_64/boot_info_x86_64.cpp`의 self-test 코드는 실제
  GRUB 데이터가 아님을 로그 태그로 항상 구분한다.
- **영향**:
  - 이후 마일스톤(M8 initrun 로딩 등)도 GRUB 없이 QEMU로 검증해야
    하는 "부트로더가 준 데이터를 파싱하는" 코드를 다시 만나면, 먼저
    ADR-077의 호스트 네이티브 테스트 인프라를 M3에서 실제로 갖출지,
    아니면 이 ADR과 같은 내장 self-test 패턴을 반복할지 그때 판단한다
    — 이 ADR은 M2 한정 선례를 남길 뿐, 향후 마일스톤에 이 패턴을
    강제하지 않는다.
  - 실기 또는 GRUB 확보 환경에서의 실제 검증은 여전히 미해결로 남는다
    (ADR-114와 동일한 한계).

## ADR-119. M8 initrd 공급: initrun ELF를 MCPACK으로 패키징해 커널 이미지에 직접 임베딩(개발 환경 한정)

- **상태**: 확정 (2026-09-08)
- **결정**: `kernel-bootstrap.md` M8은 `tools/mkinitrd.py`(boot.md §5의
  MCPACK v1 그대로 구현)로 `init/initrun`을 패키징한 뒤, 그 결과
  이미지를 `kernel/arch/x86_64/initrd_blob.S.in`(`.incbin`)을 통해
  커널 ELF 자신의 `.rodata`에 직접 심는다 — `boot_info.initrd_addr`가
  가리키는 실제 Multiboot2 모듈 전달을 흉내 내지 않고, 파서
  (`kernel/core/initrd/mcpack.cpp`)가 이 임베딩된 위치를 바로 읽는다.
- **근거**: ADR-114/117이 이미 확인한 "이 개발 머신에 GRUB가 없어
  QEMU PVH 직접 부팅 경로로는 진짜 Multiboot2 모듈 전달을 검증할 수
  없다"는 한계의 직접적 연장이다. MCPACK 파서와 ELF 로더
  (`elf_loader.cpp`)는 진짜 구현이며 이 임베딩된 데이터를 실제로
  파싱·로드한다 — ADR-117과 같은 정신("테스트만 통과하고 실제 경로는
  다른 버그가 있는" 위험을 피한다)으로, 대체되는 것은 "데이터의 출처"
  뿐이다.
- **영향**:
  - `CMakeLists.txt`(최상위)가 `init/initrun`을 `kernel`보다 먼저
    `add_subdirectory`해야 한다 — `initrd.img` 경로를 담은 GLOBAL
    PROPERTY를 `kernel/arch/x86_64`가 `configure_file` 시점에 읽어야
    하기 때문이다.
  - `initrd_blob.S`(생성됨)의 오브젝트 파일은 `OBJECT_DEPENDS`로
    `initrd.img`에 명시적으로 의존해야 한다 — `.incbin`은 ninja의
    의존성 추적 대상이 아니라서, 이게 없으면 `initrd.img` 내용이
    바뀌어도(예: mkinitrd.py 수정) 커널 바이너리에 반영되지 않는
    문제를 실제로 겪었다.
  - 실제 Multiboot2 모듈 전달 경로 자체의 검증은 여전히 미해결로
    남는다(ADR-114/117과 동일한 한계) — GRUB 확보 시 별도로 확인
    필요.

## ADR-120. .boot.bss 명시적 제로화 — NOBITS가 로더에게 0 초기화를 보장하지 않음

- **상태**: 확정 (2026-09-08)
- **결정**: `_start32`(boot.S)는 `pml4`/`low_pdpt`/`low_pd`(.boot.bss,
  연속 배치)를 GDT 적재 직전 `rep stosl`로 **명시적으로** 0을 채운다 —
  더 이상 NOBITS 섹션이 "당연히 0으로 시작한다"는 가정에 의존하지
  않는다.
- **근거**: M8에서 `create_address_space_root()`(ADR-121)가 `pml4[0]`을
  모든 새 주소공간에 공유하게 되면서, ELF 로더가 `low_pd`의 (부팅
  시점에 명시적으로 채운 [0,3] 밖) 미기록 엔트리를 처음으로 실제
  걸어 봤다 — 그 자리에 쓰레기 값이 남아 있어, 새 주소공간을 만들 때
  이를 유효한 다음 레벨 페이지테이블 포인터로 오인하는 문제를 QEMU에서
  실제로 재현·확인했다. M1~M7은 이 저지대 identity 매핑의 [4..511]
  엔트리를 한 번도 실제로 걸어 본 적이 없어(M4의 데모조차 이 범위
  밖의 가상주소를 썼다) 이 가정이 한 번도 검증되지 않은 채 남아 있었다.
  이 개발 머신의 qboot.rom(PVH 직접 부팅, ADR-114)이 표준 ELF 로더의
  NOBITS-제로화 관례를 실제로 지키는지는 검증 수단이 없어, 관례에
  기대지 않고 직접 채우는 쪽을 택했다.
- **영향**:
  - 다른 `.boot.bss`/`.bss` 구조체도 같은 가정에 기대고 있을 수
    있다(예: `object::thread`/`run_queue` 등은 이미 slab/mm 위에서
    `new`로 명시 초기화되어 안전하지만, 아직 걸러보지 않은 다른
    저지대 부트 구조체가 있다면 같은 패턴의 버그를 낼 수 있다) —
    이 ADR은 `.boot.bss`의 페이지테이블 3종만 고쳤을 뿐, 일반적인
    "NOBITS는 항상 0"이라는 가정을 프로젝트 전체에서 금지하는 것은
    아니다(실제 배포 경로인 GRUB Multiboot2/UEFI, ADR-017는 표준
    로더라 이 가정이 유효하다 — 이 문제는 어디까지나 ADR-114의 QEMU
    개발 전용 경로 한정이다).

## ADR-122. SYSCALL ABI 관례: syscall 번호는 RDI, 4번째 인자는 R10(RCX 대체)

- **상태**: 확정 (2026-09-08)
- **결정**: M8이 도입하는 x86_64 `syscall_entry`(SYSCALL/SYSRET)의
  호출 규약은 리눅스의 "번호는 RAX"를 따르지 않고, **번호를 RDI(1번
  인자 자리)**, 나머지 인자를 RSI/RDX/R10에 싣는다(RAX는 반환값
  전용). 4번째 인자는 관례상 RCX 자리이지만 SYSCALL 명령 자체가
  진입 시 RCX를 유저 복귀 RIP로 덮어써 쓸 수 없으므로, 리눅스와 같은
  이유로 R10을 대신 쓴다.
- **근거**: 번호를 RAX가 아니라 RDI에 두면, `syscall_entry.S`가 RCX를
  R10에서 RCX로 옮기기만 하면(`movq %r10, %rcx`) 4개 인자
  (rdi,rsi,rdx,rcx)가 SysV C 호출 규약의 처음 4개 정수 인자 레지스터와
  **그대로 일치**해, `call syscall_dispatch`가 별도 인자 재배치 없이
  바로 성립한다 — 이는 minicore 자신의 ABI이므로(리눅스와 호환할
  필요가 없다) 이렇게 단순화할 자유가 있다.
- **영향**:
  - `kernel/include/uapi.hpp`(`k_syscall_ipc_call` 등)와
    `init/initrun/main.cpp`의 `do_syscall()` 인라인 asm, `syscall.cpp`의
    `syscall_dispatch()` 서명이 모두 이 관례를 공유한다 — 이후 syscall
    번호가 추가되면 같은 관례를 따른다.
  - libc/POSIX 계층(ADR-005/008)을 실제로 포팅하는 시점에, 포팅 대상
    libc가 리눅스식 "번호는 RAX" 관례를 하드코딩하고 있다면 그
    부분만 minicore ABI에 맞게 고쳐야 한다 — 지금은 커널·initrun만
    있어 문제가 되지 않는다.

## ADR-123. initrun 링크 베이스 주소: 저지대 항등 매핑 범위([0,8MiB)) 밖인 0x10000000

- **상태**: 확정 (2026-09-08)
- **결정**: `init/initrun/link.ld`는 initrun을 `0x0000000000400000`
  (관례적인 낮은 유저 베이스)이 아니라 `0x0000000010000000`(256MiB)에
  링크한다.
- **근거**: ADR-121이 모든 새 주소공간에 부팅 시점 저지대 항등 매핑
  (물리/가상 `[0, 8MiB)`, GDT가 그 안에 있어 공유해야 함)을 공유시킨다
  — initrun이 관례적인 0x400000에 링크되면 이 범위와 정확히 겹쳐,
  ELF 로더의 `map_page()`가 이미 존재하는 2MiB 거대 페이지 PDE를
  다음 레벨 테이블로 착각해 매핑이 깨지는 문제를 QEMU에서 실제로
  겪었다(`map_page()`/`next_level()`은 거대 페이지 분할을 지원하지
  않는다 — 이 마일스톤 범위 밖). 8MiB보다 훨씬 위인 256MiB는 이
  범위와 절대 겹치지 않아 문제 자체를 피한다.
- **영향**:
  - 이후 procsrv 등이 일반 유저 프로세스를 로드할 때도, ELF 로더가
    저지대 항등 매핑 범위와 겹치는 가상주소를 매핑하려 들면 같은
    문제를 겪는다 — 당장은 "링크 주소를 그 범위 밖으로 잡는다"는
    이 ADR의 해법을 일반 규칙으로 삼되, `map_page()`가 거대 페이지를
    실제로 분할하는 기능을 갖추면(이후 계획) 이 제약 자체가 사라질
    수 있다.
  - `elf_loader.cpp`는 이 충돌을 스스로 감지·거부하지 않는다(조용히
    매핑이 깨진 채 "성공"을 반환한다) — 실제 안전장치는 아직 없고,
    이번엔 링크 주소를 옮겨 회피했을 뿐이라는 한계를 남겨 둔다.

## ADR-126. 커널 패닉 시 프레임포인터 기반 스택 백트레이스(주소만) 출력 — 심볼 해석·GPR 덤프는 범위 밖

- **상태**: 확정 (2026-09-08)
- **결정**: `kernel/core/panic.cpp`의 `panic_hook`이 `[PANIC] file:line:
  msg`를 찍은 직후, `__builtin_frame_address(0)`로 얻은 프레임부터
  rbp(x86_64)/x29(aarch64) 체인을 최대 16단까지 걸어 각 프레임의
  return address만 `#N 0xADDR` 형식의 raw hex로 시리얼에 출력한다.
  두 아키텍처 모두 프레임 레코드 레이아웃이 `[fp+0]=saved fp`,
  `[fp+8]=return address`로 같아 arch 매크로 분기 없이 한 구현으로
  동작한다. 함수명 해석은 **커널 안에서 하지 않는다** — 출력은 주소
  까지만이고, `llvm-addr2line -e <kernel.elf> <addr>`(또는
  `llvm-symbolizer -e <kernel.elf>`)로 빌드 호스트에서 사후에
  함수명·파일:줄로 변환하는 워크플로를 전제한다. CPU 레지스터 전체
  스냅샷(GPR dump)은 이 ADR의 범위 밖이다 — `panic_hook`은 동기적
  함수 호출 시점에 불려 호출 시점 레지스터 상태 자체의 진단 가치가
  낮고, 진짜 필요한 지점(페이지 폴트 등 예외 핸들러)은 아직 IDT가
  없어(M9 이후, [foundations.md](foundations.md) 범위) 존재하지 않는다
  — IDT/예외 핸들러가 생기는 시점에 그 핸들러가 저장한 예외 프레임을
  덤프하는 별도 ADR을 새로 낸다.
- **근거**: [debug-console.md](../spec/debug-console.md) §"아직 정하지
  않은 것"이 "커널 패닉 시 로그 출력·스택 덤프·시스템 정지 절차는
  별도 스펙 대상"이라고 비워 둔 항목을 해소한다. 프레임포인터 체인
  방식을 택한 이유는 (1) DWARF CFI 언와인드 테이블을 파싱하는 것보다
  훨씬 단순하고 freestanding 빌드에 새 의존성이 없으며, (2) 이미
  ADR-125가 모든 코드를 `-fno-omit-frame-pointer`로 빌드하기로 했으므로
  전제 조건이 항상 성립한다. 커널 내부 심볼 해석(함수명 자체 임베딩)은
  현재 필요성 대비 구현 비용(심볼 테이블 추출·임베딩 파이프라인 신설)이
  커서 채택하지 않았다 — `llvm-symbolizer` 사후 변환으로 실용적으로
  충분하다. 실제로 `kernel_main`에서 3단 깊이로 중첩 호출한 뒤
  `LIBK_PANIC`을 유발해 QEMU로 부팅, 출력된 4개 주소를
  `llvm-symbolizer`로 역변환해 `panic_hook ← (호출 지점) ← (중간
  함수) ← kernel_main`의 정확한 호출 체인이 그대로 복원됨을 확인했다
  (검증 후 되돌린 임시 코드였다).
- **영향**:
  - `docs/spec/debug-console.md`가 이 절차를 반영하도록 갱신한다(이
    ADR과 함께 즉시 반영, "아직 정하지 않은 것"에서 해당 항목 제거).
  - 스택이 손상되어 rbp 체인 자체가 깨진 경우(더블 폴트, 스택 오버플로우
    등) 이 백트레이스는 무의미하거나 중간에 끊길 수 있다 — `fp`가
    NULL/미정렬이거나 다음 프레임 주소가 이전 프레임보다 낮으면(스택은
    아래로 자라므로 비정상) 그 자리에서 멈추는 최소 방어만 있고, 그
    이상의 스택 무결성 검증(가드 페이지 등)은 이 ADR의 범위 밖이다.
  - 커널 심볼 테이블을 이미지에 심어 패닉 시점에 함수명까지 바로
    보여주는 것은 필요성이 확인되면 별도 ADR로 다룬다(지금은 새 OPEN
    항목으로 등록하지 않는다 — `llvm-symbolizer` 워크플로로 이미
    충분히 대체된다고 판단했기 때문).

## ADR-129. 파일시스템 로드맵 확장: ext4를 FAT32 다음으로 추가, v1 구현 범위는 저널 재생 없는 extent-only 읽기/쓰기

- **상태**: 확정 (2026-09-09)
- **결정**:
  1. ADR-043의 "파일시스템 서버" 항목에 **ext4를 FAT32 다음
     순서**로 추가한다 — ADR-043 표는 수정하지 않는다(과거 ADR
     불변 원칙), 이 ADR이 그 뒤를 잇는 새 결정이다. 순서는 여전히
     FAT32(virtio-blk 검증 직후 착수, ADR-057)가 먼저이고, ext4는
     그 다음(system-servers-bringup.md M16)이다.
  2. **v1 구현 범위**를 명시적으로 좁힌다 — ext4는 기능 플래그가
     매우 많은 포맷이라 전부 구현하면 이 마일스톤 하나가 별도
     프로젝트급이 된다:
     - **extent 트리 기반 블록 매핑만** 지원한다(레거시 간접 블록
       포인터 방식은 지원하지 않는다) — `mkfs.ext4`가 만드는 현대
       ext4 볼륨은 기본적으로 전부 extent 기반이라 실용적으로
       충분하다.
     - **저널(JBD2) 재생을 구현하지 않는다** — 마운트 시 저널이
       "clean"(재생 불필요) 상태인지만 확인하고, dirty 저널이
       발견되면 읽기전용으로만 마운트하거나 마운트를 거부한다(구현
       시점에 정함). 저널 자체에 쓰기(트랜잭션 기록)도 하지 않는다
       — v1은 저널링 없이 직접 메타데이터를 갱신한다(정전 시
       일관성 손실 위험을 감수 — 이 프로젝트는 QEMU 개발 환경이
       1차 목표라 허용 가능한 트레이드오프).
     - **htree(해시 디렉터리 인덱스)는 인덱스 자체를 쓰지 않는다** —
       디렉터리 항목은 인덱스 블록(`fake` dirent, inode=0으로 표시)을
       건너뛰고 나머지 데이터 블록을 선형 스캔해서 읽는다. htree가
       걸린 대형 디렉터리도 이 방식으로 읽기는 가능하다(인덱스는
       탐색 가속용일 뿐 항목 자체의 유일한 저장소가 아니므로).
     - **마운트 시 `feature_incompat`/`feature_ro_compat` 비트마스크를
       검사**해, 이 목록에 없는 기능(64bit, metadata_csum, encrypt,
       inline_data 등)을 요구하는 볼륨은 마운트를 거부한다 — 지원
       범위 밖 기능을 조용히 무시하고 진행하는 것보다 명시적 거부가
       ADR-001의 정확성 우선 원칙에 맞는다.
  3. ext4의 네이티브 inode 번호가 [filesystem.md](filesystem.md)
     ADR-128이 새로 정의한 `fs_node_id`의 ext4 쪽 구현이다(그대로
     사용, 별도 매핑 불필요).
- **근거**: 사용자가 M16에 ext4를 추가해달라고 요청하며 "inode 개념
  또는 매칭 구조가 필요하다"고 짚었다 — 그 요구 자체는
  [filesystem.md](filesystem.md) ADR-128로 해소했고, 이 ADR은 ext4
  구현 자체의 범위를 정한다. 저널·htree·최신 기능 플래그를 전부
  구현하면 M16 하나가 사실상 별도 파일시스템 드라이버 프로젝트가
  되어 ADR-001("정확성·단순성 우선")과 이 계획 전체의 성격(다중
  프로세스 시스템의 수직 슬라이스 검증, docs/plan/system-servers-bringup.md
  §배경)에 맞지 않는다. FAT32(단순한 클러스터 체인)를 이미
  먼저 구현하기로 한 것과 같은 논리로, ext4도 "가장 흔한 실사용
  형태(extent, 저널 없이 깨끗하게 unmount된 이미지)"만 우선
  지원한다.
- **영향**:
  - QEMU 검증용 ext4 이미지는 호스트에서 `mkfs.ext4`로 만든 뒤
    **정상적으로 unmount(저널 clean)한 상태**로 준비해야 한다 —
    이 계획의 스모크 테스트가 dirty 저널 이미지를 다루지 않는다.
  - 저널 재생·쓰기 지원, htree 인덱스 직접 활용(대형 디렉터리 탐색
    가속), 암호화·압축 등은 전부 필요성이 확인되면 별도 ADR
    대상이다 — 지금은 새 OPEN 항목으로 등록하지 않는다(v1 범위
    자체가 이미 이 ADR에 명시돼 있어 "미정" 상태가 아니다).
  - `docs/spec/`에 ext4 레지스터/온디스크 구조 수준 스펙은 M16
    착수 시점에 개별 작성한다(ADR-043이 이미 확립한 관례).

## ADR-130. 입력 장치 로드맵: PS/2 우선(고정 레거시 프로브) + USB HID 후속(devmgr의 중첩 버스 열거)

- **상태**: 확정 (2026-09-09)
- **결정**:
  1. ADR-043의 드라이버 로드맵 표에 없던 **입력 장치(키보드/마우스)
     클래스**를 새로 추가한다(표 자체는 수정하지 않는다 — 이 ADR이
     새 클래스를 정의) — 1순위 **PS/2**(i8042 컨트롤러), 2순위
     **USB HID**(xHCI 위의 표준 HID 클래스 드라이버).
  2. **PS/2는 devmgr의 버스 열거 대상이 아니다** — PCIe/USB 같은
     "버스"가 아니라 고정 레거시 I/O 포트(`0x60`/`0x64`)이므로,
     PS/2 드라이버가 부팅 시 devmgr를 거치지 않고 **직접 존재
     여부를 프로브**한다(디버그 콘솔의 UART 초기화, ADR-037과 같은
     패턴 — "버스 열거"가 아니라 "알려진 고정 위치를 직접 확인").
     ACPI FADT의 "IA-PC Boot Architecture Flags" 중 8042 존재 비트를
     힌트로 참고할 수 있으나(있으면 신뢰, 없어도 QEMU 기본 구성엔
     항상 존재하므로 직접 프로브로 최종 확인), 이 비트가 없다고
     드라이버 자체를 아예 안 띄우지는 않는다.
  3. **USB는 devmgr의 버스 열거 책임(ADR-039)을 중첩 버스로
     확장한다** — xHCI 컨트롤러 자체는 여느 PCIe 장치와 같이
     ADR-038/039 경로(ECAM 설정공간)로 devmgr가 먼저 찾는다. 그
     위에서 devmgr는 **두 번째 계층의 열거**(xHCI 명령 링으로 USB
     장치 기술자를 읽어 VID:PID/클래스 코드를 얻음)를 추가로
     수행하고, PnP 매칭(ADR-041)도 PCIe의 vendor:device 대신 USB의
     VID:PID/클래스 코드 기준으로 이뤄진다 — 매칭 알고리즘 자체
     (동적 등록, 재시작 시 재등록)는 ADR-041을 그대로 재사용한다.
  4. **USB 핫플러그**는 xHCI의 포트 상태변화 이벤트를 커널 인터럽트로
     받아 ADR-040과 동일한 "비동기 notification → devmgr가 재스캔"
     패턴을 그대로 재사용한다 — PCIe 핫플러그와 별개 메커니즘을
     새로 만들지 않는다.
- **근거**: 사용자가 M14에 USB와 PS/2를 추가해달라고 요청했다 —
  검토해보니 ADR-038~041은 전부 PCIe에 특화된 결정이라(ECAM
  설정공간, PCIe PME 인터럽트, vendor:device 매칭) USB를 그대로
  얹을 수 없었고(중첩 버스 개념이 없었다), PS/2는 애초에 버스가
  아니라 devmgr의 "버스 열거"라는 틀 자체에 맞지 않는다는 점을
  확인했다. PS/2를 1순위로 둔 이유는 ADR-043이 이미 확립한 "QEMU
  개발 환경에서 가장 단순한 경로 먼저" 원칙과 정확히 같다 — PS/2는
  버스 열거·기술자 파싱·엔드포인트 관리가 전혀 없이 고정 포트
  폴링/인터럽트만으로 동작해 M17(콘솔/로그인)이 요구하는 "키보드
  입력"을 가장 빨리, 가장 단순하게 확보하는 길이다. USB는 실기
  호환성(PS/2가 없는 최신 하드웨어)과 마우스·다른 HID 장치 지원에
  필요해 2순위로 남긴다.
- **영향**:
  - `servers/drivers/`(repo-layout.md)에 `ps2/`와 `usb/`(xHCI 컨트롤러
    드라이버 + HID 클래스 드라이버) 서브디렉토리가 추가된다.
  - devmgr의 내부 자료구조가 "PCIe 장치 목록" 단일 계층에서 "버스
    종류(PCIe/USB) × 그 버스의 장치 목록"으로 일반화돼야 한다 —
    구체적 자료구조는 M14 착수 시점에 정한다.
  - USB 저장장치(USB Mass Storage)·USB 네트워크 어댑터 등 HID
    이외의 USB 장치 클래스는 이 ADR의 범위 밖이다 — 필요해지면
    별도 ADR.
  - PS/2 스캔코드 세트(1/2/3) 중 어느 것을 쓸지, USB HID 리포트
    디스크립터 파싱의 구체적 범위는 M14 착수 시점에 `docs/spec/`
    개별 문서로 정한다(ADR-043과 같은 관례).

## ADR-131. initrun 기동: 커널이 initrd로 전달한 부트 디바이스 서술자를 initrun이 직접 마운트해 procsrv·코어 서버들을 찾아 기동 (해결: OPEN-29)

- **상태**: 확정 (2026-09-09)
- **결정**:
  1. **initrun이 하는 일은 "procsrv 하나 실행"이 아니라 "부트
     디바이스를 물리적으로 마운트해 시스템 디스크로 삼고, 그 위에서
     procsrv를 포함한 서비스 바이너리들을 찾아 순서대로 기동"이다.**
     (초안이었던 "고정 이름 하나만 spawn" 방식은 폐기 — 사용자가
     지적한 대로 그 정도로는 부족하다.)
  2. **부트 디바이스 서술자는 initrd 안의 새 엔트리 `"disk.cfg"`로
     전달된다** — 이 서술자는 **OS 설치 시점에 구성되는 값**이다
     (실제 설치 절차 자체는 이 프로젝트에 아직 없으므로, 지금 QEMU
     개발 환경에서는 `tools/mkinitrd.py`가 그 설치 절차를 대신해
     고정된 개발용 기본값을 채워 넣는다 — 이 자리는 나중에 진짜
     설치 도구가 생기면 그게 채우는 자리로 자연스럽게 교체된다).
     내용은 최소한 (a) 장치 식별자(개발 환경: virtio-blk PCI
     BDF — 정확한 인코딩은 M12 착수 시 boot.md 갱신으로 확정),
     (b) 파일시스템 종류(태그, 지금은 FAT32 하나뿐) 두 가지다.
     커널은 initrun을 로드할 때(M8이 이미 하는 `initrd::find_entry()`
     호출과 같은 자리에서) 이 엔트리도 함께 찾아 그 내용을
     `boot_info`의 새 필드(`boot_device_descriptor`)에 실어
     initrun에게 넘긴다 — **새 syscall 없이** 기존 boot_info 전달
     경로(boot.md §6)를 그대로 재사용한다. 이 값이 **1차** 경로다 —
     커널은 이 값을 얻으려고 스스로 PCIe를 뒤지지 않는다(이미 설치
     시점에 정해진 값을 그대로 읽을 뿐).
  3. **폴백**: `disk.cfg`가 가리키는 장치가 실제로 없거나(디스크
     이미지가 옮겨졌거나, QEMU가 PCI 슬롯을 다르게 배정하는 등)
     응답하지 않으면, **initrun 자신**이 최소한의 임베디드 PCIe
     스캔(ECAM 설정공간을 처음부터 선형 탐색해 virtio-blk 클래스
     코드와 일치하는 첫 장치를 찾는 정도, ADR-038의 ECAM 접근
     방식만 재사용 — devmgr의 진짜 열거 알고리즘, ADR-039와는
     별개의 훨씬 좁은 구현)로 대체 장치를 찾는다. 이 폴백은
     "설정값이 있으면 그대로 믿고 스캔하지 않는다"는 1차 경로의
     단순함을 해치지 않으면서, 설정이 틀어졌을 때 완전히 멈춰버리는
     것을 막는 안전망이다.
  4. **initrun은 이렇게 확보한 장치를, 자신의 주소공간 안에 내장한
     최소한의 1회성 드라이버로 직접 마운트한다** — M14~M16이 만들
     devmgr/virtio-blk 서버와는 **완전히 별개의 코드**다:
     - 최소 virtio-blk 클라이언트(블로킹, 읽기 전용, 큐 1개만).
     - 최소 **cpio**(newc 포맷) 읽기 전용 파서 — 순차 엔트리 나열 +
       이름 비교만 필요해 FAT32(클러스터 체인, 디렉터리 엔트리,
       긴 파일명 등)보다 훨씬 단순하다. 파티션 포맷 자체를 FAT32에서
       cpio로 바꾼다(이전 초안의 FAT32는 폐기 — 사용자가 "과도하게
       복잡한 구현"이라고 지적했다). `/boot/uefi` ESP(ADR-046/057)는
       UEFI 스펙상 FAT32여야 하는 **별개의 파티션**이라 이 결정과
       무관하다 — 이 ADR이 다루는 건 어디까지나 initrun이 서비스를
       찾는 부트 디바이스 하나뿐이다.
  5. **서비스 발견 규칙 (해결: OPEN-50, 2026-09-09 개정)**: 이
     cpio 아카이브는 **실제 VFS 경로 트리를 흉내 내지 않는다** —
     "부팅 극초기, VFS조차 없는 시점에 진짜 `/sys` 경로 구조를
     담은 파티션을 마운트한다"는 이전 초안의 표현은 비현실적이라는
     지적을 받아들여 폐기한다. 대신 **아카이브 자체의 평범한
     내부 레이아웃**일 뿐이다 — VFS도, `/sys`도 아직 없는 시점이므로
     경로가 VFS 트리와 같아 보일 이유가 없다:
     ```
     bin/procsrv
     bin/vfs
     lib/000-procsrv.ini
     lib/001-fs.ini
     lib/002-vfs.ini
     ...
     ```
     `lib/` 안 파일명은 두 자리 이상 0패딩 숫자 접두사로 **실행
     순서**를 매긴다. initrun은 `lib/*.ini`를 파일명 사전순(=숫자순)
     으로 나열해 그 순서 그대로 spawn한다 — 이것이 "서버 실행
     순서"의 실제 기술 방법이다. 각 파일은 INI 형식:
     ```ini
     [서버명]
     exec=bin/서버명
     args=<argv로 이어붙일 인자들>
     ; 기타 key=value — 레지스트리(cfgsrv, M19)가 아직 뜨지 않은
     ; 부팅 극초기에 그 서비스가 대신 참고할 설정값들
     ```
     `exec=`가 가리키는 이름을 같은 cpio 아카이브의 `bin/`에서
     찾아 읽어 §결정8의 `sys_process_spawn`으로 만들고, `args=`는
     §결정9의 argv blob으로 전달한다. **`[서버명]` 섹션의 그 외
     key=value(§결정 근거의 "레지스트리 접근 제한" 문제 해소용)는
     initrun이 해석하지 않는다** — 해당 `.ini` 파일 원본 바이트
     전체를 읽기전용으로 매핑해 그 주소·길이를 `boot_info`의 새
     필드(`config_blob_addr`/`config_blob_size`)로 그 서비스
     자신에게 전달한다. 그 서비스가 스스로 자기 섹션을 파싱해
     부팅 극초기 폴백 설정으로 쓴다 — 레지스트리가 뜬 뒤에는
     그쪽을 우선하는지는 서비스 각자의 판단(이 ADR의 범위 밖).
     **각 서비스의 그 이상의 세부 설정(포트·마운트 옵션 등 이
     bootstrap-ini 폴백 범위를 넘는 것)은 이 단계의 책임이 아니다**
     — cfgsrv(M19)나 VFS 경유 `/sys/etc`(M13/M17)에서 각 서비스가
     스스로 읽어가는 문제다. **`/sys/srv` 같은 VFS 경로는 이 ADR이
     더 이상 도입하지 않는다** — 실제 시스템 서버 바이너리를 VFS
     상에서 어디에 두고 보여줄지(`/sys/bin`을 그냥 쓸지, 별도
     경로를 새로 만들지)는 M13(VFS) 이후 필요해지면 별도로 정한다.
  6. **초기화 완료를 기다린 뒤 순차 진행한다는 방향만 확정한다**:
     initrun은 §결정5의 각 서비스를 spawn만 하고 넘어가지 않는다 —
     그 서비스가 "초기화 완료"를 알릴 때까지 기다린 뒤에야 다음
     줄로 넘어간다. 즉 이전 초안의 "동기화는 범위 밖"은 폐기한다 —
     사용자가 명시적으로 "기다렸다가"라고 정정했다. **다만 실제
     신호 프로토콜(어느 IPC 형태를 쓰는지 등)은 이 ADR이 다루기엔
     너무 크다고 판단해 완전히 별도 design으로 분리한다** →
     OPEN-52(§영향).
  7. **모든 서비스 초기화가 끝나면, initrun은 "systemd류의 초기
     프로세스"를 마지막으로 하나 더 자식으로 실행시키고, 자신은
     정리되어 사라진다 — 그 자식이 프로세스 트리의 새 루트가 된다.**
     이 마지막 프로세스는 **procsrv 등 코어 서버가 아니라 별도의
     유저랜드 서비스 관리자 데몬**이다(정체성 확정 — Linux systemd에
     대응, 커널 서버가 아니다). 다만 이 컴포넌트의 실제 이름·책임
     범위와 "루트가 된다"는 것의 구체적 의미(procsrv 프로세스
     테이블의 `parent_pid=0` 규약이 이 프로세스를 가리키게 되는
     절차, initrun 자신이 procsrv 테이블에 애초에 등록돼 있었는지
     등)는 이 ADR이 정하지 않는다 → 신규 **미결정 (OPEN-51)**, M12
     착수 시점에 확정한다. 여기서 확정하는 건
     "initrun은 영구적으로 살아있는 프로세스가 아니라 부트스트랩이
     끝나면 사라지는 일회성 절차"라는 생명주기 방향뿐이다.
  8. **`sys_process_spawn`은 initrd 이름 조회가 아니라 호출자가
     이미 읽어 둔 원본 ELF 바이트를 받는 형태로 일반화한다**:
     `sys_process_spawn(const void* elf_data, size_t elf_size,
     argv_blob, bool grant_trusted) -> (address_space handle,
     thread handle)` — trusted 전용(ADR-074, 이전 초안과 동일).
     이러면 커널은 그 바이트가 initrd에서 왔는지 initrun이 방금
     cpio에서 읽어 온 것인지 몰라도 되고, 별도의 "initrd 이름으로
     읽기" syscall(`sys_initrd_read`, 이전 초안)이 **더 이상
     필요 없다** — initrun은 자신의 임베디드 cpio 리더로 파일을
     직접 읽어 그 바이트를 그대로 이 syscall에 넘긴다.
  9. **argv 전달 관례**(이전 초안 그대로 유지): `sys_process_spawn`이
     만든 프로세스는 RDI(boot_info, M8 관례)에 더해 RSI에 argv
     blob 포인터(`uint32_t argc` + NUL 종료 문자열들)를 받는다.
  10. **커널이 initrun 자신을 로드하는 방식(M8, MCPACK을 커널
      이미지에 직접 임베딩, ADR-119)은 바꾸지 않는다** — ADR-119
      자신이 이미 "개발 환경 한정"이라고 명시해 둔 자리이므로, "그
      이후 모든 프로세스"부터 이 ADR의 방식(실제 부트 디바이스에서
      찾기)을 적용하는 것으로 경계를 긋는다.
- **근거**: 사용자가 여섯 차례에 걸쳐 정정했다 — "procsrv를 고정적으로
  띄우는 게 아니라, 파일시스템을 초기화·마운트한 뒤 procsrv와 각종
  서비스들을 찾아 기동해야 한다", "부트 디바이스가 무엇인지 syscall이나
  파라미터로 확인하고 물리적으로 마운트해 시스템 디스크로 취급",
  "그 부트 디바이스 정보는 OS 설치 시점에 구성되어 initrd에 함께
  팩킹돼야 한다", §결정5의 발견 규칙 자체(0패딩 숫자 접두사로 순서
  표현, INI 안에 `exec`/`args`+레지스트리 대체용 폴백 설정), "1차
  경로에 폴백이 필요하다", "FAT32는 과도하게 복잡하니 cpio를 쓴다",
  "initrun은 모든 서비스의 초기화를 기다린 뒤 systemd류 프로세스를
  마지막으로 실행하고 스스로 사라진다", 그리고 마지막으로 "VFS도
  없는 시점에 진짜 `/sys` 경로 구조를 담은 파티션을 마운트한다는
  건 비현실적이니, `/sys/srv/bin`·`/sys/srv/lib`라는 VFS 경로
  서술 자체를 없애고 cpio 아카이브 내부의 평범한 상대 경로
  (`bin/`, `lib/`)로 팩킹하라" — 이 여섯 차례의 정정을 그대로
  반영한 결과가 §결정 1~10이다. 마지막 정정의 핵심은 "VFS 경로를
  흉내 낼 이유가 없다"는 지적이다 — VFS 자체가 아직 없는 시점에
  `/sys`로 시작하는 경로를 쓰면 마치 진짜 VFS 트리의 일부인 것
  처럼 보이지만 실제로는 그냥 cpio 아카이브 안의 문자열일 뿐이라,
  나중에 진짜 VFS(M13)가 뜬 뒤 그 경로와 혼동될 위험만 만들고
  얻는 것은 없다. 부트 디바이스 자체가 필요하다는 큰 그림은
  boot-and-drivers.md ADR-057이 이미 "`/boot/uefi` ESP에 FAT32가
  필요하다"고 밝혀 둔 것과 같은 맥락이다(다만 그 ESP와 이 ADR의
  cpio 부트 디바이스는 **서로 다른 파티션**이다 — §결정4 참고).
  cpio를 택한 이유는 FAT32(클러스터 체인, 디렉터리 엔트리, 긴
  파일명, FAT 테이블 자체의 무결성 규칙)보다 파서가 훨씬 단순해서다
  — initrun의 임베디드 리더는 "이름으로 파일 하나 찾아 순차
  읽기"만 하면 되므로, cpio의 "헤더 하나 읽고 다음 엔트리로
  건너뛰기"만 반복하는 선형 스캔이면 충분하다(Linux initramfs가
  같은 이유로 cpio를 쓰는 것과 같은 논리). 임베디드 드라이버를
  devmgr/M15의 "진짜" virtio-blk 구현과 **의도적으로 공유하지 않는**
  이유는, 부트스트랩 전용 최소 구현(에러 복구·핫플러그·동시성을
  신경 쓸 필요가 없다)과 범용 장기 실행 서버가 요구하는 것이 실제로
  다르고, 지금 억지로 공유 계층을 만드는 비용이 그 이득보다 크다고
  판단했기 때문이다(ADR-001) — Linux initramfs가 부팅 후
  "pivot_root"로 완전히 버려지는 것과 같은 패턴이다: 이 cpio 부트
  디바이스도 initrun이 다 읽고 나면 다시 쓰이지 않는다. PCIe
  폴백 스캔(§결정3)을 둔 이유는
  install-time 설정값 하나에만 전적으로 의존하면, 그 값이 실제
  환경과 어긋나는 순간(디스크 슬롯 변경 등) 시스템이 아예 못
  뜨는 단일 실패점이 되기 때문이다 — 사용자가 정확히 이 위험을
  지적했다.
- **영향**:
  - `kernel/core/syscall.cpp`(M8)에 새 syscall `sys_process_spawn`
    (번호는 M12 구현 시점에 uapi.hpp에 배정, ADR-122 관례) 하나만
    추가된다 — 이전 초안의 `sys_initrd_read`는 필요 없어졌다.
  - `boot_info`(boot.md §3)에 `boot_device_descriptor`,
    `config_blob_addr`/`config_blob_size`(§결정5) 필드가 추가되고,
    `tools/mkinitrd.py`가 `"disk.cfg"` MCPACK 엔트리를 새로 채워
    넣도록 확장돼야 한다. 정확한 바이트 레이아웃은 M12 착수 시점에
    `boot.md` 갱신으로 확정한다.
  - `init/initrun/`에 임베디드 최소 virtio-blk 클라이언트 + **cpio**
    리더 + INI 파서 + PCIe 폴백 스캔이 새로 필요하다 —
    `docs/plan/system-servers-bringup.md`의 M12가 이를 반영하도록
    크게 갱신돼야 한다(이 ADR과 함께 즉시 처리).
  - **부트 디스크 이미지를 만드는 새 도구**(가칭
    `tools/mkbootdisk.py`)가 필요하다 — 아카이브 루트의 `bin/<서버명>`에
    procsrv 등 서비스 바이너리를, `lib/NNN-이름.ini`에 §결정5 형식의
    시동 파일을 넣은 **cpio(newc) 이미지**를 만들고, `tools/run-qemu.sh`
    가 이를 virtio-blk로 붙이도록(`-drive`/`-device virtio-blk-pci`)
    확장해야 한다. `tools/mkinitrd.py`(initrun 자신을 담는 initrd)와는
    별개의 산출물이다.
  - **[vfs-layout.md](../spec/vfs-layout.md)는 이 ADR로 바뀌지
    않는다** — 이전 초안이 추가했던 `/sys/srv`(`bin`/`lib`) 경로는
    VFS 경로를 흉내 낸 것이었을 뿐 실체가 없어 폐기한다(§근거의
    마지막 정정). 시스템 서버 바이너리를 실제 VFS 위 어디에
    두고 보여줄지(`/sys/bin`을 그냥 쓸지, 별도 경로를 새로 만들지)는
    M13(VFS) 이후 필요해지면 별도로 정한다 — 이 cpio 레이아웃과는
    무관한 결정이다.
  - **초기화 완료 대기(§결정6)의 정확한 신호 프로토콜은 이 ADR의
    범위 밖이다 (해결: OPEN-49 → OPEN-52로 이관)** — "기다린다"는
    방향만 여기서 확정하고, 실제 프로토콜(어떤 IPC 형태로, 어느
    프로세스가 관여하는지, procsrv의 일반 fork/exec와의 관계 등)은
    ADR-131 안에서 다루기엔 범위가 너무 커서 완전히 분리한다 —
    별도 design 문서·계획이 필요하다 → 신규 **미결정 (OPEN-52)**,
    아직 착수 시점도 정하지 않았다.
  - **§결정7의 "systemd류 초기 프로세스"**는 procsrv 등 코어 서버가
    아닌 별도의 유저랜드 서비스 관리자 데몬으로 정체성이 확정됐다
    — 실제 이름·책임 범위와 "루트가 된다"는 것의 구체적 절차는 →
    신규 **미결정 (OPEN-51)**.
  - procsrv.md §3(`fork()`)·§4(`exec()`)의 **일반** 프로세스 생성/
    치환 syscall(COW 복제, 임의 VFS 경로의 ELF 교체)은 여전히
    미정이다 — 이 ADR은 오직 "부팅 극초기, VFS조차 없는 시점에
    고정 부트 파티션에서 서비스를 찾아 띄우는" 좁은 문제만 푼다.
    §4.1의 fd 진실 공급원 프로토콜, §7~8의 계정 생성·로그인도 이
    ADR의 영향을 받지 않는다.

## ADR-143. TSS(RSP0) 최소 설정 — GDT에 시스템 세그먼트(TSS) 디스크립터를 추가한다

- **상태**: 확정 (2026-09-10)
- **결정**: 새 파일 [tss.hpp](../../kernel/arch/x86_64/tss.hpp)/
  [.cpp](../../kernel/arch/x86_64/tss.cpp)에 최소 64비트 TSS(RSP0만
  의미 있게 채움, IST 전부 미사용, IOPB 없음)를 만들고,
  `boot.S::gdt64_start`(7개 엔트리)를 그대로 복사한 뒤 TSS
  디스크립터(셀렉터 0x38, 시스템 세그먼트라 16바이트) 하나를
  덧붙인 확장 GDT를 새로 구성해 `lgdt`+`ltr`로 적재한다.
  `kernel_main.cpp`가 `install_syscall_entry()` 바로 다음, 첫 유저
  스레드가 뜨기 **전**에 `arch_x86_64::init_tss()`를 호출한다.
  RSP0에 쓰는 스택은 스레드별로 나누지 않는다(16KiB 하나로 충분 —
  이 협조적 단일 코어 스케줄러에서 예외 처리는 항상 순차적이고,
  `syscall_kernel_rsp`처럼 "블로킹된 채 남겨 둘" 상태가 없다).
- **근거**: [usermode.S](../../kernel/arch/x86_64/usermode.S)가 M8
  시점에 이미 정확히 지적해 뒀다 — "TSS(RSP0)는 ring3→ring0
  방향(인터럽트로 되돌아올 때)에만 필요하므로, ring0→ring3
  방향(`enter_usermode`의 IRETQ)은 TSS 없이도 동작한다." 그
  반대 방향(유저 스레드 실행 중 실제 예외/인터럽트 발생)이
  M8~M11 어디에도 없어(모든 예외 테스트가 커널 스레드=ring0에서만
  있었다) TSS 없이도 문제가 드러나지 않았다. M12에서
  `sys_fork`(ADR-142)의 자식이 자기 스택에 처음 쓰려는 순간 COW
  쓰기 폴트(ADR-140)가 **실제 유저 스레드(ring3)에서 최초로** 발생
  하면서, TSS/RSP0가 없으면 CPU가 ring3→ring0 전환 시 어느 커널
  스택으로 갈지 알 수 없어 그 자체로 결함(관찰상 진단 불가능한
  행 — 아래 §검증 참고)이 된다는 사실이 실제로 드러났다.
- **검증 결과(QEMU+GDB 실측)**: 이 ADR 이전에는 자식의 첫 스택
  쓰기가 아무 진단 로그도 남기지 못한 채(디버그 콘솔조차 침묵)
  QEMU가 멈췄다(재현: `MINICORE_QEMU_GDB=1`로 붙여 확인 — 정상적인
  예외 처리라면 IDT의 catch-all이라도 찍혔을 텐데 전혀 없었다,
  TSS 부재로 인한 처리 자체의 실패로 추정). TSS 추가 직후 같은
  시나리오가 `[pf] cow copy ...`(ADR-140의 정상 로그)로 바뀌었다 —
  즉 #PF가 처음으로 **정상적으로 ring3→ring0 전환에 성공**해
  진단 가능한 상태가 됐다.
- **영향**:
  - `kernel/arch/x86_64/CMakeLists.txt`에 `tss.cpp` 추가.
  - GDT 자체가 이제 두 곳에 존재한다: boot.S의 `gdt64_start`(부팅
    극초기, `init_tss()` 호출 전까지만 유효)와 `tss.cpp`의 확장판
    (그 이후 계속 유효). 둘의 인덱스 0~0x30 엔트리 값은 반드시
    동일해야 한다(지금은 손으로 중복 유지 — 값이 갈리면 이미 로드된
    CS/SS 셀렉터의 캐시된 의미와 새 GDT의 내용이 어긋난다).
  - AP(다중 코어)는 여전히 TSS를 적재하지 않는다 — AP는 유저모드에
    진입하지 않으므로(M10/M11 done 보고에 이미 명시) ring3→ring0
    전환 자체가 없어 필요 없다.

## ADR-146. boot_info에 boot_device_descriptor 필드 추가(ADR-131 §결정2 구체화)

- **상태**: 확정 (2026-09-10)
- **결정**: [boot_info.hpp](../../kernel/include/boot_info.hpp)에
  `boot_device_descriptor{valid, pci_bus, pci_device, pci_function,
  fs_tag, io_port_ok, io_port_base}`를 추가하고(`k_boot_info_version`을
  3으로 올림), `boot_info.boot_device`로 담는다. 앞 5개 필드(정적,
  20바이트)는 initrd의 `"disk.cfg"` 엔트리(값 그대로 바이트 복사)에서
  오고, 뒤 2개(런타임)는 커널이 부팅 중 실제로 BAR를 배정한 결과로
  채운다(ADR-147). `tools/mkinitrd.py`에 `--disk-cfg=BUS,DEVICE,
  FUNCTION,FS_TAG` 옵션을 추가해 그 정적 부분을 만든다.
- **근거**: ADR-131 §결정2가 "장치 식별자+파일시스템 종류"라고
  개념만 정해 두고 "정확한 바이트 레이아웃은 M12 착수 시점에 확정"
  이라고 미뤄 뒀던 부분을 실제로 정한다. `io_port_ok`/`io_port_base`
  를 disk.cfg가 아니라 커널이 채우기로 한 이유는 ADR-147의 발견(BAR가
  실제로 배정돼 있지 않다) 때문이다 — 정적 설정값이 아니라 매 부팅
  마다 새로 계산해야 하는 값이라 애초에 disk.cfg에 넣을 수 없다.
- **영향**: disk.cfg 엔트리 크기(20바이트)와
  `sizeof(boot_device_descriptor)`(28바이트)가 더 이상 같지 않다 —
  `kernel_main.cpp::setup_initrun_process()`가 disk.cfg를 읽을 때
  전체 구조체 크기가 아니라 정적 부분(5×4바이트)만으로 크기를
  검증하고 그만큼만 복사한다(실제로 처음엔 전체 크기로 비교해
  disk.cfg가 있는데도 항상 무효로 읽히는 버그를 만들었다가 QEMU에서
  `[pci]` 로그가 전혀 안 찍히는 것을 보고 발견·수정했다).

## ADR-147. virtio-blk 부트 디바이스의 PCI BAR를 커널이 직접 배정 + I/O 포트 IOPB로 initrun에 위임

- **상태**: 확정 (2026-09-10)
- **결정**:
  1. **MCFG 파싱** — [acpi.hpp](../../kernel/arch/x86_64/acpi.hpp)/
     [.cpp](../../kernel/arch/x86_64/acpi.cpp)에
     `find_and_parse_mcfg()`를 추가한다(PCI segment 0의 ECAM 베이스만
     — ADR-038의 "ECAM 우선" 그대로, 레거시 0xCF8/0xCFC 폴백은
     다루지 않는다). RSDP 검색은 `find_and_parse_madt()`와 완전히
     같은 경로(기존 파일 지역 `find_acpi_table()`)를 재사용한다.
  2. **BAR 배정** — 새 파일
     [pci_bringup.hpp](../../kernel/arch/x86_64/pci_bringup.hpp)/
     [.cpp](../../kernel/arch/x86_64/pci_bringup.cpp)에
     `assign_virtio_blk_bar(ecam_base, bus, device, function)`을
     추가한다. disk.cfg가 가리키는 그 **하나의 BDF만** 다룬다 —
     devmgr(M14~M16)의 진짜 버스 열거(ADR-039)와는 무관하다. 크기
     탐색(0xFFFFFFFF를 써 보고 되읽어 마스크 확인) 후 고정 포트
     베이스(0xC000)에 배정하고, PCI COMMAND 레지스터의 I/O space
     enable 비트를 켠다.
  3. **TSS IOPB** — [tss.cpp](../../kernel/arch/x86_64/tss.cpp)가
     TSS 바로 뒤에 8193바이트 IOPB(Intel SDM Vol.3 §8.7)를 붙여
     기본값 전부 거부(0xFF)로 초기화하고, 새 함수
     `grant_io_port_range(base, count)`로 배정된 포트 범위만 허용
     (0)으로 지운다 — `kernel_main.cpp`가 BAR 배정 성공 직후
     [io_port_base, io_port_base+0x20)에 대해 이걸 호출해, ring3의
     initrun이 `inb`/`outb`로 그 포트를 직접 두드릴 수 있게 한다.
- **근거**: 이 필요성 자체가 QEMU에서 실측으로 드러났다 — 이
  프로젝트는 PVH 직접 부팅(ADR-114)이라 SeaBIOS 등 어떤 펌웨어도
  PCI 리소스(BAR) 배정을 대신해 주지 않는다. bus0/device4/function0
  (disk.cfg가 가리키는 자리에 `-device virtio-blk-pci`를 붙인 것)의
  BAR0을 커널 진단 코드로 직접 읽어 보니 `vendor=0x1af4 device=0x1001
  bar0=0x1`이었다 — vendor/device는 정상(virtio-blk legacy)이지만
  BAR0의 낮은 비트(I/O 공간 표시)만 리셋 상태로 서 있고 실제 주소
  부분은 0이었다. 즉 **누군가 BAR에 실제 주소를 배정해 줘야
  장치를 쓸 수 있는 상태**였다 — 이걸 커널이 부팅 중 한 번 대신
  해 주면, initrun은 ECAM이나 PCI 열거를 전혀 몰라도 되고 그냥
  넘겨받은 포트 베이스로 legacy virtio 레지스터를 두드리기만 하면
  된다(모던 virtio의 MMIO BAR+capability list 파싱보다 훨씬
  단순하다 — QEMU virtio-blk-pci가 기본으로 노출하는 것도 legacy
  인터페이스였다, device id 0x1001이 이를 확인해 준다).
- **검증 결과(QEMU 실측)**: `tools/run-qemu.sh`에
  `MINICORE_QEMU_BOOTDISK` 환경변수(가짜 1MiB 파일로 시작)를 추가해
  `-device virtio-blk-pci,drive=bootdisk,addr=04.0`을 붙인 뒤,
  `[pci] assign_virtio_blk_bar ok=1 vendor=0x1af4 device=0x1001
  io_base=0xc000`을 실제로 확인했다. 장치를 안 붙인 기본 스모크
  테스트 경로(disk.cfg는 있지만 실제 PCI 장치가 없음)에서는
  `ok=0 vendor=0x0 device=0x0`으로 안전하게 실패하며, 이 경로가
  포함된 `tools/smoke-test-x86_64.sh`(50개)를 포함한 4개 스위트
  전부 회귀 없이 통과했다.
- **영향**:
  - `kernel/arch/x86_64/CMakeLists.txt`에 `pci_bringup.cpp` 추가.
  - `tools/run-qemu.sh`에 `MINICORE_QEMU_BOOTDISK` 환경변수 추가 —
    설정하면 그 파일을 `virtio-blk-pci`(bus0/device4/function0
    고정, `init/initrun/CMakeLists.txt`의 `--disk-cfg=0,4,0,0`과
    반드시 일치해야 한다)로 붙인다.
  - **알려진 단순화**: IOPB는 TSS 하나에 전역으로 공유된다(코어당
    TSS 하나) — 지금은 유일한 트러스트 프로세스(initrun)만
    존재해 문제가 없지만, 신뢰하지 않는 유저 프로세스가 생기는
    시점에는 이 접근이 그 프로세스에게도 그대로 열려 있다는 뜻이다.
    docs/design/open-items.md에 재검토 항목으로 등록한다(OPEN-58).
  - 이 커널 측 BAR 배정은 이 프로젝트가 관리하는 **단 하나의 알려진
    장치**에만 통한다 — devmgr(M14~M16)이 실제로 여러 PCI 장치를
    다뤄야 할 때는 이 코드를 재사용하지 않고 ADR-039의 일반
    열거+배정 알고리즘을 새로 구현해야 한다.

## ADR-150. M12 완성: initrun의 legacy virtio-blk 클라이언트 + 실제 부트 디스크 마운트 + procsrv 골격 (OPEN-55/56/57 해소)

- **상태**: 확정 (2026-09-09)
- **결정**: system-servers-bringup.md §M12 전체를 실제로 구현했다.
  1. `init/initrun/virtio_blk.{hpp,cpp}` — legacy virtio-blk 레지스터
     프로토콜(리셋→ACKNOWLEDGE|DRIVER→feature 협상(0, 옵션 기능 없음)
     →큐 0 선택/크기 확인→vring을 DMA 버퍼 앞 16KiB에 구성→
     QueueAddress=PFN→DRIVER_OK)과, 3-디스크립터(요청 헤더→데이터→
     상태 바이트) 블로킹 읽기 요청 1회(`read_all`, 순수 폴링, 유한
     반복 상한). 디바이스 config space(오프셋 0x14)에서 읽은 용량과
     호출자가 준 상한 중 작은 쪽까지만 읽는다.
  2. `init/initrun/main.cpp` — RDI로 받는 실제 `boot::boot_info`를
     이제 읽는다(M8~M11은 안 읽었다). `boot_device.valid &&
     io_port_ok`면 `sys_alloc_dma_buffer(order=10, 4MiB)`로 DMA
     버퍼를 받아 virtio-blk를 초기화하고 부트 디스크 전체(≤3MiB)를
     읽어, 그 cpio 아카이브를 순회해 `lib/*.ini`(아카이브 기록
     순서=파일명순=실행순, ADR-131 §결정5)를 찾아 각각의 `exec=`가
     가리키는 `bin/*` ELF를 `sys_process_spawn`한다. **M8~M11이
     검증에 쓰던 "initrun 자신을 fork/exec/spawn하는 self-test
     데모"는 이 자리에서 완전히 제거했다** — `uapi.hpp::m12_self_info`
     의 주석이 이미 "procsrv/cpio가 실제로 생기면 통째로 사라진다"고
     예고해 둔 그대로다.
  3. `servers/procsrv/main.cpp` — M12 골격(procsrv.md §2~9는 구현하지
     않는다, 핸들러 자리조차 만들지 않는다 — 아래 OPEN-56 해소 참고).
     `sys_fork`+`sys_exec`로 자기 자신을 다시 실행하는 것이 이
     마일스톤의 유일한 책무다. initrun의 boot_info-vs-null 구분과
     같은 비대칭을 얻기 위해, **initrun이 procsrv를 처음 스폰할 때만
     비어있지 않은 1바이트 argv를 주고(procsrv 자신의 self-exec
     호출은 항상 argv 없이)** "원본이냐 사본이냐"를 구분한다
     (ADR-149의 self_info 일반화가 procsrv에도 self_elf/self_info를
     자동으로 채워 주므로 가능해졌다).
  4. `tools/mkbootdisk.py` — `bin/<이름>` + `lib/NNN-<이름>.ini`
     (`[<이름>]\nexec=bin/<이름>\n`)를 cpio(newc)로 담는 최소 자체
     구현(ADR-006, 서드파티 cpio/tar 없음) — `tools/mkinitrd.py`의
     MCPACK(커널이 자신에 심는 initrd)와는 완전히 다른, virtio-blk로
     붙는 진짜 디스크 이미지를 만든다.
  5. `servers/procsrv/CMakeLists.txt` — `minicore_procsrv_elf`를
     `init/initrun/CMakeLists.txt`와 같은 ET_EXEC/ld.lld 직접 호출
     패턴으로 빌드하고, `minicore_bootdisk_image` 타겟으로
     `tools/mkbootdisk.py`를 호출한다.
  6. `tools/smoke-test-x86_64.sh` — `MINICORE_QEMU_BOOTDISK`가
     비어 있으면 `<빌드 디렉토리>/servers/procsrv/bootdisk.img`를
     기본값으로 자동 첨부하도록 바꿔, **기본 스모크 테스트가 이제
     항상 실제 부트 디스크 경로를 검증**한다 — `"[process] fork/exec/
     spawn ok"` 어써션은 문자열이 그대로지만(process_ops.cpp가
     호출자를 구분하지 않고 남기는 로그) 이제는 procsrv가 실제
     디스크 I/O로 만들어진 뒤 자기 자신을 fork/exec한 결과다. 새
     어써션 `"[pci] assign_virtio_blk_bar ok=1 vendor=0x1af4
     device=0x1001"`을 추가했다.
- **OPEN-55 해소**: "서비스 준비완료 신호"의 M12 임시방편으로 **아무
  신호도 두지 않는다** — M12의 부트 디스크에는 서비스가 procsrv
  하나뿐이라 "다음 서비스로 넘어가기 전에 기다린다"는 상황 자체가
  없다(순서 의존성이 없으면 기다릴 이유가 없다). 게다가 이 협조적
  스케줄러에는 `sys_yield`가 없어(uapi.hpp 참고) initrun이 스폰 후
  "잠깐 기다렸다가 계속"할 수단 자체가 없다 — 스폰 후 곧바로
  `sys_thread_exit()`해 스케줄러가 procsrv에게 기회를 주는 것만이
  유일한 선택이었다. 여러 서비스가 실제로 순서 의존성을 갖게 되는
  시점에 OPEN-52(정식 신호 프로토콜)가 필요해진다 — 그때까지 이
  결정을 다시 열 필요는 없다.
- **OPEN-56 해소**: procsrv.md §5(계정 생성)/§7(로그인)/§8(su/sudo)의
  "프로토콜 골격"을 **코드상 자리조차 만들지 않는 것**으로 정한다 —
  핸들러 스텁도, 라우팅도, 항상-실패 응답도 없다. `servers/procsrv/
  main.cpp`는 fork/exec 자기증명 외에 아무 IPC도 받지 않는다(참고:
  procsrv는 아직 어떤 endpoint도 갖지 않는다 — `sys_process_spawn`이
  만드는 handle_table은 비어 있다). 근거: 아직 존재하지 않는
  프로토콜(OPEN-54가 미정)의 빈 자리를 미리 만들어 두는 것은 그
  프로토콜이 실제로 확정될 때 오히려 잘못된 모양의 스텁을 뜯어내는
  비용을 더할 뿐이다 — "골격"은 procsrv라는 **프로세스**가 존재하고
  뜬다는 사실 자체로 충분하다.
- **OPEN-57 해소**: 구현 순서는 virtio_blk(레지스터 프로토콜) →
  cpio/ini(이미 구현돼 있던 것을 그대로 재사용) → mkbootdisk.py →
  initrun 통합 → procsrv 골격 순으로 진행했다 — virtio_blk을 가장
  먼저 둔 이유는 그 성패가 나머지 전부(부트 디스크에서 실제로 무엇을
  읽는지)를 좌우해 가장 위험도가 높았기 때문이다. 범위는 큐 협상을
  최대한 단순화(feature 0개, 큐 1개, 요청 1개, 인터럽트 없이 순수
  폴링)했다 — virtio_blk.hpp 상단 주석이 이미 이렇게 M14~M16의
  "진짜" 구현과 의도적으로 분리해 뒀다.
- **검증 결과(QEMU 실측)**: 기본 `tools/smoke-test-x86_64.sh`(부트
  디스크 자동 첨부, 51개 어써션 — ADR-147 검증 때의 50개에 새 PCI
  어써션 1개 추가) 전체 통과. 로그로 `[pci] assign_virtio_blk_bar
  ok=1 vendor=0x1af4 device=0x1001 io_base=0xc000` →
  `[process] spawn ok entry=0x10000000 trusted=0`(procsrv, 실제
  디스크에서 읽은 ELF) → `[process] fork ok child_pml4=...` →
  `[process] exec ok entry=0x10000000`(procsrv 자기 자신) 순서를
  실제로 확인했다 — M12의 QEMU 검증 목표("실제 디스크 I/O를 거친
  프로세스 생성은 이번이 처음")를 그대로 만족한다.
- **알려진 단순화(M12 범위 밖으로 명시적으로 남긴 것)**: ADR-131
  §결정3의 PCIe 폴백 스캔 미구현(disk.cfg 없으면 그냥 실패), OPEN-51
  ("systemd류 초기 프로세스") 미구현(procsrv 스폰 후 initrun은 그냥
  종료), config_blob 전달 미구현(스폰되는 서비스에게 원본 key=value
  나머지를 넘기는 경로 없음 — 지금은 procsrv가 그걸 쓸 일이 없다).

## ADR-154. TSS IOPB를 스레드별 활성 I/O 포트 범위로 전환 — `sys_io_activate`/`sys_io_deactivate` + 컨텍스트 스위치 시 diff 기반 재프로그래밍 (해결: OPEN-58)

- **상태**: 확정 (2026-09-09) — **설계만 확정, 구현은 착수 전**(아래
  §실행 계획 참고).
- **결정**:
  1. `object::thread`에 `io_port_base`/`io_port_count`(둘 다 0이면
     "활성 I/O 범위 없음") 필드를 추가한다 — ADR-147의 "코어당 TSS
     하나에 전역으로 열어 둔 IOPB"를 "지금 스케줄된 스레드가 실제로
     활성화해 둔 범위만 열리는 IOPB"로 바꾼다.
  2. 새 syscall 두 개(가칭 `sys_io_activate(io_base, count)`/
     `sys_io_deactivate()`) — **활성화/비활성화 call**. `trusted`
     (ADR-074/147이 이미 확립한 "이 프로세스가 실제로 하드웨어를
     직접 다뤄야 한다는 사실이 검증된 신원") 스레드만 호출할 수
     있다 — 별도의 새 권한 비트를 만들지 않고 기존 판정을 그대로
     재사용한다. 호출한 스레드 자신의 `io_port_base`/`count`를
     설정/해제하고, 지금 그 스레드가 실행 중이면 즉시 TSS IOPB에도
     반영한다.
  3. 컨텍스트 스위치(`kernel/core/sched/scheduler.cpp`)마다, 새로
     스케줄되는 스레드의 `io_port_base`/`count`가 "지금 IOPB에
     프로그램된 범위"와 다르면 **차이만** 재프로그래밍한다 — 이전
     범위를 다시 차단(비트를 1로)하고 새 범위를 개방(비트를 0으로)
     한다. 매 전환마다 8KiB 전체를 만지지 않는다(범위가 대개 32바이트
     안팍이라 실제 비용은 무시할 수 있다).
  4. **"활성화를 허가할 권한" 자체**는 새 커널 객체가 아니라
     지금처럼 `sys_process_spawn`의 `grant_trusted`(ADR-147, 스폰하는
     쪽 — 지금은 initrun — 이 하드코딩으로 결정)로 충분하다 —
     "누가 트러스트를 받는가"와 "누가 I/O를 활성화할 수 있는가"를
     같은 판정으로 묶는다. 부팅 완료 이후 cfgsrv 레지스트리를 읽어
     **다른** 특수 프로세스에게도 이 권한을 동적으로 부여/회수하는
     것은 cfgsrv가 실제로 존재하는 M19 이후 재검토 대상으로
     남긴다 → 신규 **미결정 (OPEN-60)**.
  5. `sys_fork`(ADR-142)는 자식에게 부모의 `io_port_base`/`count`를
     기본적으로 그대로 물려준다(부모가 trusted면 자식도 trusted를
     물려받는 것과 같은 정신, `fork_current()`가 이미 그렇게 한다).
     이를 제한하는 fork 특수 변형(예: `sys_fork_no_io`)은 **이
     ADR에서 만들지 않는다** — 지금 이걸 실제로 쓸 서비스가 없다
     (YAGNI, ADR-131 §근거와 같은 절제). 실제로 필요해지는 시점(예:
     신뢰하는 프로세스가 신뢰하지 않는 자식을 fork로 만드는 특정
     서비스가 생길 때)에 별도로 추가한다.
  6. `kernel_main.cpp::setup_initrun_process()`가 지금 무조건 호출하는
     `grant_io_port_range()`(전역 1회성)는 제거하고, initrun의
     virtio-blk 클라이언트가 실제로 I/O가 필요해지는 시점
     (`virtio_blk::init()` 호출 직전)에 `sys_io_activate()`를 직접
     호출하도록 바꾼다.
- **근거**: docs-dashboard "답변 입력"으로 받은 방향 제안(2026-09-09,

## ADR-156. `sys_map_phys` — 임의 물리주소 매핑 syscall (ADR-007/038/039가 예고한 "MMIO 캐패빌리티"의 실제 도입)

- **상태**: 확정 (2026-09-09)
- **결정**: 새 syscall `sys_map_phys(phys_addr, size) -> virt_addr`
  (trusted 프로세스만) — 호출자가 이미 알고 있는 임의의 물리주소
  범위를 그대로 자기 주소공간에 매핑한다. `sys_alloc_dma_buffer`
  (ADR-147)와 다른 점: 그건 **커널이 새로 할당한** RAM을 매핑하고
  그 물리주소를 알려주는 것이고, 이건 **호출자가 이미 알고 있는
  기존 물리주소**(하드웨어가 소유 — 페이지 할당자가 전혀 모르는
  영역: ACPI 테이블, PCIe ECAM 설정공간, 디바이스 BAR)를 그대로
  매핑하는 것이다 — `mm::frame_add_ref` 등 프레임 참조 카운트를
  전혀 건드리지 않는다. `phys_addr`은 페이지 정렬이 필요 없다(커널이
  내림/올림 처리 후 `out_virt_addr`에 오프셋까지 보정된 값을 돌려
  준다). `alloc_dma_buffer`와 같은 단순화로 프로세스당 고정
  가상주소 슬롯 하나를 재사용한다(동시에 두 매핑이 필요 없는 순차
  사용만 가정 — devmgr가 ACPI 테이블을 다 읽은 뒤에야 ECAM을
  매핑하는 식).
- **근거**: ADR-007이 "디바이스 MMIO 영역을 드라이버 주소공간에
  매핑할 수단(capability)을 제공해야 한다"고 이미 예고했고,
  ADR-038/039도 devmgr가 "ECAM은 그냥 MMIO 영역이므로 기존 MMIO
  캐패빌리티 매핑 메커니즘을 재사용한다"고 전제했지만, 이 수단
  자체가 실제로 구현된 적이 한 번도 없었다(`objects.md`에도 "객체
  종류가 늘어날 때(메모리 객체, MMIO 캐패빌리티 등)"라는 미래
  서술로만 남아 있었다) — M14(devmgr의 ACPI/PCIe ECAM 접근, USB
  드라이버의 xHCI BAR 접근)가 이 수단을 처음으로 실제로 요구하는
  마일스톤이라 지금 만든다. 새 커널 객체 종류(예: 별도의 "MMIO
  handle")를 추가하지 않고 `sys_alloc_dma_buffer`와 같은 "trusted
  판정 + 고정 슬롯" 패턴을 그대로 재사용한 이유는, 두 syscall이
  근본적으로 같은 일(물리주소를 유저 주소공간에 매핑)을 하고 있어
  새 객체·핸들 개념을 얹으면 오히려 과설계이기 때문이다.
- **영향**: `kernel/arch/x86_64/process_ops.hpp/.cpp`에 `map_phys()`
  추가(`k_mmio_user_vaddr` 고정 슬롯, `k_dma_buffer_user_vaddr` 다음
  자리). `uapi.hpp`에 `k_syscall_map_phys`(9)/`map_phys_request`/
  `k_max_mmio_map_bytes`(16MiB 상한) 추가. `syscall.cpp`에 새 case.
  devmgr/USB 드라이버(M14)가 이 syscall의 첫 실제 소비자다.

## ADR-157. M14 완성: devmgr(유저랜드 ACPI/PCIe ECAM 열거) + PS/2 컨트롤러 자체 테스트 + USB(xHCI) 리셋·포트 스캔

- **상태**: 확정 (2026-09-09)
- **결정**: system-servers-bringup.md §M14를 다음 범위로 구현했다.
  1. `servers/devmgr/main.cpp` — `kernel/arch/x86_64/acpi.cpp`의
     RSDP 검색(EBDA/BIOS ROM 스캔, arch_data_addr 우선)과 MCFG 파싱
     절차를 **유저랜드용으로 다시 구현**한다(ADR-006/039 — devmgr는
     커널 코드를 호출할 수 없다, 커널 자신의 부트스트랩 전용 구현과
     의도적으로 분리된 채 유지된다 — ADR-131 §근거와 같은 정신).
     `sys_map_phys`(ADR-156)로 물리 메모리를 필요할 때마다 다시
     매핑하는 작은 "물리 창(phys window)" 캐시 하나로 임의 위치의
     ACPI 테이블/ECAM 설정공간을 전부 읽는다. bus 0의 device 0~31,
     function 0만 열거한다(PCI-PCI 브리지 재귀·멀티펑션은 M14 범위
     밖 — pcie.md §2의 완전한 재귀 요구를 아직 만족하지 않는 알려진
     단순화, QEMU의 virtio-blk/xHCI가 전부 bus 0에 있어 이 정도로
     충분히 검증된다).
  2. 드라이버 등록/매칭(pcie.md §4)의 **M14 최소 버전** — devmgr의
     `register_driver`(label=1) 요청 **자체의 응답**에 매칭된 장치의
     BAR 정보를 바로 싣는다(pcie.md가 원래 그려 둔 "devmgr가 나중에
     `device_claimed`로 먼저 말을 거는" 비동기 push 경로는 핫플러그
     (ADR-040)가 아직 없는 지금 필요 없다 — 정적으로 한 번 매칭하는
     것으로 충분). BAR0 배정은 ADR-147의 I/O BAR 배정 절차를 **메모리
     BAR**로 일반화한 것 — PVH 직접 부팅이라 여기서도 아무 펌웨어가
     대신해 주지 않는다. 32비트 메모리 BAR만 다룬다(M14가 실제로
     만나는 xHCI가 그렇다).
  3. `servers/drivers/ps2/main.cpp` — ADR-130의 고정 레거시 프로브.
     실제 키 입력이 QEMU 자동화 환경에 주입되지 않으므로, 8042
     컨트롤러 자체 테스트(커맨드 0xAA → 항상 결정적으로 0x55) 핸드셰이크
     로 검증 가능한 결과를 얻는다 — `sys_io_activate`(ADR-154)로
     포트 0x60~0x64를 스레드 자신에게 활성화한다.
  4. `servers/drivers/usb/main.cpp` — devmgr에 PCI 클래스 코드
     `0x0C0330`(xHCI)로 등록해 BAR0(물리주소+크기)을 위임받고,
     `sys_map_phys`로 매핑해 캐패빌리티 레지스터(HCIVERSION/
     MaxSlots/MaxPorts)를 읽는다. 여기서 멈추지 않고 **컨트롤러
     리셋(USBCMD.HCRST)**을 실제로 수행하고, USBSTS.CNR이 꺼질
     때까지 기다린 뒤 각 포트의 PORTSC를 읽어 로그로 남긴다.
  5. `tools/mkbootdisk.py`에 `--trusted=<이름>` 추가(해당 서비스의
     ini에 `trusted=1`을 써 넣는다) — devmgr/ps2/usb는
     `sys_alloc_dma_buffer`/`sys_io_activate`/`sys_map_phys`를 쓰려면
     trusted가 필요하다(ADR-147/154/156). `init/initrun/main.cpp`의
     스폰 루프가 이 키를 읽어 `grant_trusted`를 켜고, devmgr에게는
     일반 마커 대신 `boot_info.arch_data_addr`를 실제 argv로 넘긴다.
     `tools/run-qemu.sh`에 `MINICORE_QEMU_XHCI=1`(기본 켬, 스모크
     테스트) — QEMU 기본 `qemu-xhci` 컨트롤러를 bus0/device5에 붙인다.

  스캔까지만 — 이것만으로도 별도 마일스톤급 작업이라 명시적으로
  범위 밖으로 남긴다, 사용자 확인 하에 결정).

## ADR-158. M15 완성: `servers/drivers/virtio-blk` — 첫 실제 유저 드라이버, devmgr BAR 재사용 일반화, 부트 디바이스 배제

- **상태**: 확정 (2026-09-09)
- **결정**:
  1. `servers/drivers/virtio-blk/main.cpp` — legacy virtio-blk
     레지스터 프로토콜 클라이언트를 독립적으로 구현한다(`init/
     initrun/virtio_blk.cpp`와 레지스터 레이아웃은 같지만 코드는
     공유 라이브러리가 없어 별도로 작성 — libmc 이전 단계의 알려진
     중복, ADR-132가 예고한 libmc가 나중에 흡수할 대상). 3-디스크립터
     체인(header→data→status) 하나를 재사용해 `VIRTIO_BLK_T_IN`(읽기)
     /`VIRTIO_BLK_T_OUT`(쓰기)을 모두 지원한다.
  2. devmgr의 `assign_memory_bar0`을 `assign_or_get_bar0`으로
     일반화 — I/O BAR와 메모리 BAR를 모두 다루고, 요청받은 BAR가
     **이미 배정돼 있으면(0이 아니면) 재배정하지 않고 그대로
     반환**한다. virtio-blk 드라이버가 등록하는 장치(vendor:device
     `0x1af4:0x1001`)의 BAR는 initrun이 부팅 중 이미 배정해 둔
     상태(ADR-147)라 devmgr가 다시 배정하면 그 값이 깨진다 — BAR
     재사용은 M14에서는 필요 없었지만(그때는 매칭 대상이 항상
     미배정 상태) M15에서 처음 요구된다.
  3. devmgr `_start`의 argv를 `devmgr_argv{arch_data_addr, boot_bdf}`
     로 확장 — initrun이 부트 디바이스의 BDF(`(bus<<16)|(device<<8)|
     function`)를 함께 넘긴다. `handle_register_driver`가 후보
     장치의 BDF가 `boot_bdf`와 같으면 매칭에서 제외한다.
- **근거(실행 중 발견한 버그)**: 최초 구현은 virtio-blk 드라이버가
  부트 디바이스(`initrun`이 cpio 아카이브를 읽어 procsrv 등을
  스폰하는 그 디스크, bus0/device4)에 **그대로** 등록해 쓰기
  테스트를 수행했다 — "부팅 목적은 이미 끝났으니 안전하다"고
  가정했지만, `tools/run-qemu.sh`의 `-drive format=raw`는 기본이
  read-write라 그 쓰기가 호스트 파일(`bootdisk.img`)의 실제 바이트를
  물리적으로 덮어썼다. 하필 그 바이트가 cpio 아카이브 앞부분(첫
  엔트리의 ELF 내용)과 겹쳐, 이후 모든 QEMU 부팅에서 `procsrv`의
  코드 일부가 깨진 상태로 로드됐다 — 증상은 `run_vfs_roundtrip_test()`
  중간 어딘가로 실행이 튀어 `#UD`(vector=6)가 나는 것으로 나타났다.
  CMake의 `bootdisk.img` 커스텀 커맨드는 ELF **입력**이 바뀔 때만
  재실행되므로, 손상된 이미지가 재빌드 전까지 그대로 재사용돼
  **100% 재현되는 크래시**가 "가끔 나는 버그"처럼 보였다(최초
  1회만 클린 이미지로 성공했고, 이후 재실행은 전부 같은 크래시).
  디스어셈블(`llvm-objdump -d`)로 크래시 지점이 멀쩡한 명령
  중간으로 점프한 흔적임을 확인해 "손상된 코드"라는 결론에
  도달했고, 파일 오프셋(섹터10×512=5120)이 cpio 첫 엔트리와 겹친다는
  계산으로 원인을 특정했다. **교훈**: 테스트 드라이버가 실제로 쓰기
  테스트를 하는 장치는 부팅 경로가 의존하는 장치와 반드시 물리적으로
  분리해야 한다 — "논리적으로 이미 다 썼으니 안전하다"는 가정은
  호스트 파일 백엔드가 프로세스 종료 시점이 아니라 매 부팅마다
  재사용된다는 사실과 충돌한다.
- **수정**: `tools/run-qemu.sh`에 `MINICORE_QEMU_TESTDISK` 추가
  (bus0/device6, 부트 디바이스와 별도의 파일 — 없으면 1MiB 빈
  파일을 새로 만든다) + devmgr의 `boot_bdf` 배제(위 §결정3) 이중
  방어 — 드라이버가 실수로 부트 디바이스를 다시 요청해도 devmgr가
  넘겨주지 않는다.
- **영향**: `servers/devmgr/main.cpp`(BAR 재사용+BDF 배제),
  `init/initrun/main.cpp`(`devmgr_argv` 확장), `servers/drivers/
  virtio-blk/*`(신설), `servers/drivers/CMakeLists.txt`/`servers/
  CMakeLists.txt`(빌드/부트디스크 배선, `--depends=virtio-blk:devmgr`,
  `--trusted=virtio-blk`), `tools/run-qemu.sh`/`tools/
  smoke-test-x86_64.sh`(`MINICORE_QEMU_TESTDISK`).
- **검증 결과(QEMU 실측)**: `tools/smoke-test-x86_64.sh`(59개 — M14의
  58개+신규 1개) 전체 통과를 분리된 테스트 디스크로 **2회 연속**
  재확인(재사용해도 손상 없음, 수정 전에는 재실행마다 100% 크래시).
  SMP(11개)/NUMA(24개)/AVX(12개) 전체 회귀 없음. 실측 로그 발췌:
  ```
  [pci] assign_virtio_blk_bar ok=1 vendor=0x1af4 device=0x1001   ← 부트 디바이스(initrun 직접 배정)
  [virtio-blk] write_ok=0x1
  [virtio-blk] read_ok=0x1
  [virtio-blk] write/read roundtrip ok=1                         ← 별도 테스트 디바이스(devmgr 매칭+재배정)
  ```
- **실행 중 발견한 버그(2번째)**: `avail_idx`를 매 요청마다 1로
  되돌리는 초기 구현은 두 번째 요청(쓰기 다음 읽기)에서 디바이스가
  "새 작업 없음"으로 보고 무시했다(읽기가 항상 타임아웃). virtio
  가용 링의 `avail_idx`는 큐가 살아있는 동안 계속 증가하는
  카운터([큐 크기]로 모드 연산해 슬롯만 계산)여야 한다는 사실을
  놓친 것 — 지속되는 `g_avail_idx`/`g_queue_size` 전역으로 고쳤다.
  **알려진 단순화(M15 범위 밖)**: 큐 협상(feature negotiation)은
  ADR-150이 이미 정한 대로 여전히 최소(feature 0개/큐 1개/순수
  폴링), 멀티큐·인터럽트 기반 완료 통지는 다루지 않는다.

## ADR-163. devmgr I/O BAR 배정을 고정 주소 재사용에서 전진하는 커서로 전환 — M16이 처음으로 "동시에 여러 새 BAR"를 요구하며 드러난 버그

- **상태**: 확정 (2026-09-09)
- **결정**: `servers/devmgr/main.cpp::assign_or_get_bar0()`의 "새로
  배정" 분기가 매번 같은 고정 상수(`k_assigned_io_base=0xC100`,
  `k_assigned_mmio_base=0xE0000000`)에서 정렬해 반환하던 것을,
  실제로 배정한 만큼 전진하는 전역 커서(`g_next_io_base`/
  `g_next_mmio_base`)로 바꾼다 — 배정할 때마다 그 크기만큼 다음
  커서 값을 갱신한다. "이미 배정돼 있으면 재사용"(ADR-158) 분기는
  그대로다 — 이 변경은 순수하게 **처음** 배정하는 경로에만 영향을
  준다.
- **근거(실행 중 발견한 버그)**: ADR-158/159가 이미 "여러 장치를
  배정해야 하는 시점에는 실제 공간 할당기가 필요해진다"고 예견해
  뒀던 상황이 M16에서 처음으로 실제로 왔다 — M14(xHCI, MMIO만)와
  M15(virtio-blk 테스트 장치, I/O만)는 매 마일스톤마다 "새로 배정해야
  하는 장치가 최대 하나"였어서 고정 상수 재사용이 우연히 문제를
  드러내지 않았다. M16은 fat32와 ext4가 **동시에 둘 다** 새 I/O
  BAR를 요구하는 첫 시나리오였고, 고정 상수를 그대로 쓰면 두 서로
  다른 물리 PCI 장치의 BAR0 설정 레지스터에 **똑같은 I/O 포트
  번호**가 적혀 실제로 그 포트를 두 장치가 동시에 점유해 버렸다 —
  QEMU 실측에서 `[fat32] io_base=0xc100`/`[ext4] io_base=0xc100`
  (동일값)로 확인, 그 결과 `[fat32] mount ok=0x0`(포트가 실제로는
  ext4 쪽 장치나 다른 장치로 라우팅되고 있어 BPB를 읽어도 FAT32
  시그니처가 아닌 값이 나옴)로 재현됐다. 전진 커서로 고치자
  `[fat32] io_base=0xc180`/`[ext4] io_base=0xc200`(서로 다른 값)로
  바뀌었고 둘 다 mount ok=0x1로 성공했다.
- **영향**: `servers/devmgr/main.cpp`에 `g_next_io_base`/
  `g_next_mmio_base` 전역 추가, `assign_or_get_bar0()`의 "새로 배정"
  분기가 고정 상수 대신 이 커서를 읽고 갱신한다. **알려진 단순화**
  (M16 범위 밖으로 남긴 것): 이 커서는 절대 되감기지 않는다(장치가
  드라이버에서 "해제"되는 경로가 아직 없으므로, ADR-040의 핫플러그와
  마찬가지로 아직 필요 없다) — 프로세스 재시작 없이 동적으로
  드라이버를 껐다 켰다 하는 시나리오가 생기면 재검토 대상.

## ADR-164. M17 콘솔/TTY 범위 좁힘 — cfgsrv 의존 없는 단일 고정 TTY + VGA 텍스트 모드(0xB8000)

- **상태**: 확정 (2026-09-09)
- **문제**: ADR-097이 TTY 개수/메인 TTY를 `@global/system/tty`
  레지스트리(cfgsrv)에서 읽도록 설계했지만, cfgsrv는 system-servers-bringup.md
  §M19(M17보다 **뒤**)에야 생긴다 — M17 착수 시점에 그 레지스트리
  테이블 자체가 존재하지 않는다. ADR-097은 이 순서 문제를 예상하지
  못했다(둘 다 2026-09-08에 같은 자리에서 확정됐지만, 마일스톤 순서
  자체는 계획 문서가 별도로 정한 것이라 그때는 드러나지 않았다).
- **결정**:
  1. **TTY는 M17 한정 1개만, 하드코딩한다** — 멀티 TTY·TTY 전환
     UX·`@global/system/tty` 레지스트리 연동은 전부 M19(cfgsrv 등장)
     이후로 미룬다. `servers/drivers/console`은 지금 단일 TTY(장치
     노드 개념도 아직 없다 — `/sys/dev/tty0` 노출은 ADR-097 §영향이
     이미 "devmgr 담당, 스펙 갱신 대상"이라고 미뤄 둔 부분과 같이
     후속 라운드) 하나만 구동한다. cfgsrv가 실제로 생기면 이
     하드코딩을 레지스트리 조회로 교체하는 후속 ADR이 필요하다 —
     지금 새 OPEN 항목으로 등록하지 않는다(이미 이 ADR에 명시돼
     있어 "미정" 상태가 아니다, ADR-129 §영향과 같은 근거).
  2. **렌더링 백엔드는 VGA 텍스트 모드(물리주소 `0xB8000`, 80x25,
     셀당 2바이트: 문자+속성) 하나만 구현한다** — ADR-097 §결정3이
     이미 "그래픽 드라이버가 없으면 텍스트 모드"라고 정해 뒀고,
     지금 그래픽 드라이버(virtio-gpu 등)가 전혀 없으므로 이 ADR은
     그 첫 번째 분기만 구현하는 것이지 새 결정을 더하는 게 아니다.
     `sys_map_phys`(ADR-156)로 매핑한다 — devmgr가 ACPI/ECAM을 읽는
     것과 같은 패턴, PCI 장치가 아니라 QEMU q35의 레거시 VGA
     호환 영역에 직접 접근하므로 devmgr 등록이 필요 없다. 프레임
     버퍼 위에 글리프를 그리는 두 번째 분기(fbcon류)는 그래픽
     드라이버가 실제로 생기는 시점까지 범위 밖.
  3. **콘솔 드라이버의 상세 프로토콜은 ADR-111이 이미 "새로 고안하지
     않는다"고만 정했을 뿐 구체 오퍼레이션을 정하지 않았다** — M17은
     `OP_PRINT`(문자열 출력, 개행 시 다음 줄, 25번째 줄을 넘으면
     스크롤, `0x08`을 만나면 커서를 한 칸 물리고 그 자리를 공백으로
     지우는 backspace 처리) 하나만 정의한다. ANSI/VT100 이스케이프
     시퀀스, TTY 전환 키 조합 등은 여전히 범위 밖(ADR-111 §영향이
     이미 "구현 시점에 정한다"고 미뤄 둔 것 — M17은 그 구현 시점의
     첫 조각일 뿐, 최소한만 정한다).
- **근거**: 사용자가 이 세 가지 모두 "권장(최소)" 선택을 확인했다 —
  TTY 1개 하드코딩, VGA 텍스트 모드, (아래 security-model.md ADR-165의)
  최소 실제 계정 저장소. cfgsrv를 먼저 만들지 않고 M17을 진행하는
  것은 계획 문서의 마일스톤 순서(M17이 M19보다 먼저) 자체를 지키는
  선택이다 — 순서를 바꾸는 것(M19를 앞당김)은 훨씬 큰 범위 변경이라
  이 ADR의 대상이 아니다.
- **영향**: `servers/drivers/console`(신설) — `sys_map_phys`로
  `0xB8000`을 매핑, `trusted=1` 필요. `docs/spec/vfs-layout.md`의
  `/sys/dev/tty{N}` 반영과 `registry.md`의 `@global/system/tty` 스키마
  반영은 여전히 미뤄진다(ADR-097 §영향이 이미 그렇게 정해 둔 대로).

## ADR-166. M17 완성: 콘솔/ps2/procsrv/login 배선 중 발견한 버그 둘 — initrun 서비스 레지스트리 크기 초과, ps2 폴링 예산 과다

- **상태**: 확정 (2026-09-09)
- **결정**: system-servers-bringup.md §M17을 ADR-164(콘솔)/ADR-165
  (로그인 인증)가 좁힌 범위로 구현했다 — `servers/drivers/console`
  (VGA 텍스트), `servers/drivers/ps2`(self-test 후 종료하던 것을
  `OP_READ_KEY`를 받는 진짜 서버로 전환), `servers/procsrv`(처음으로
  자기 자신의 endpoint에 `sys_recv` 루프를 돌며 `OP_LOGIN`에
  응답), `servers/login`(신설, console/ps2/procsrv 세 서버 모두에
  의존). 실행 중 서로 무관한 두 버그를 발견해 고쳤다.
- **근거(실행 중 발견한 버그 1) — initrun 서비스 레지스트리 크기
  초과**: `init/initrun/main.cpp::k_max_registered_services`가
  M13부터 `8`로 고정돼 있었는데, M17까지 오며 부트 디스크 서비스가
  11개(memfs/devmgr/ps2/console/usb/virtio-blk/fat32/ext4/vfs/
  procsrv/login)로 늘어 그 상한을 넘었다 — 9번째로 스폰되는 `vfs`
  부터는 `spawn_visit()`의 `ctx->registry_count < k_max_registered_services`
  검사가 막혀 이름-핸들 레지스트리에 **등록조차 되지 않았다**.
  그 결과 `vfs`에 의존하는 `procsrv`의 `depends=vfs`가
  `find_registered_handle()`에서 못 찾아 `dep_handle=0`으로 조용히
  실패했고, `procsrv`가 애초에 유효한 vfs 핸들을 받지 못해 자신의
  하드코딩된 `k_vfs_handle=2`가 존재하지 않는 핸들을 가리키게 됐다
  (QEMU 실측에서 `[procsrv] vfs open failed`/`fat32 open failed`/
  `ext4 open failed`로 재현 — M16까지는 8개 이하라 드러나지 않았던
  버그다). `k_max_registered_services`를 `16`으로 늘려 고쳤다 —
  등록/조회 로직 자체는 바꿀 필요가 없었다(순전히 배열 크기 문제).
- **근거(실행 중 발견한 버그 2) — ps2 `OP_READ_KEY` 폴링 예산 과다**:
  `servers/drivers/ps2`의 `OP_READ_KEY` 한 번은 출력 버퍼가 찰 때까지
  `2,000,000`회를 폴링(포트 I/O 트랩 하나하나가 QEMU 에뮬레이션에서
  실제로 비싸다)하고, `servers/login`은 사용자명 한 필드를 읽는 데
  이 호출을 최대 `50`번 재시도했다 — 실제 키 입력이 QEMU 자동화
  환경에 없으므로(ADR-165 §결정4가 이미 전제한 상황) 이 예산이
  전부 소진되며, 합쳐서 **최대 1억 회**의 포트 I/O 트랩이 발생했다.
  스모크 테스트(`TIMEOUT_SEC=90`)에서 한 번은 66개 중 4개(콘솔/로그인
  관련 전부)가 그 시간 안에 도달하지 못해 실패했다 — 다른 실행에서는
  통과해 처음엔 "가끔 나는" 문제처럼 보였지만, 원인은 결정적이다
  (호스트 부하에 따라 포트 트랩 처리 속도가 달라질 뿐). ps2의 예산을
  `50,000`, login의 재시도 횟수를 `10`으로 줄여(합계 `500,000`,
  약 200배 절감) 고쳤다 — 이후 66/66을 2회 연속 안정적으로 통과했다.
- **영향**: `init/initrun/main.cpp`(레지스트리 크기), `servers/drivers/
  ps2/main.cpp`/`servers/login/main.cpp`(폴링 예산). 두 버그 모두
  코드 로직 자체는 정확했고 **크기 상수만** 잘못됐다는 점에서
  ADR-149(self_elf/self_info 간격)·ADR-163(devmgr I/O BAR 고정
  주소)와 같은 종류다 — 이 프로젝트에서 반복적으로 나타나는 "고정
  상수를 실제 사용 규모가 넘어설 때"라는 버그 패턴.

## ADR-173. 레거시 8259 PIC 마스킹: 실제 GRUB Multiboot2 부팅 경로에서 발견한 IRQ0/#DF 벡터 충돌

- **상태**: 확정 (2026-09-10)
- **결정**: `kernel/arch/x86_64/idt.cpp::init_idt()`가 IDT를 적재하기
  전에 레거시 8259 PIC(마스터 포트 0x20/0x21, 슬레이브 0xA0/0xA1)의
  IRQ 마스크 레지스터(OCW1)에 `0xFF`를 써서 **모든 레거시 IRQ를
  막는다**(슬레이브 먼저, 그다음 마스터 — 마스터의 캐스케이드 라인
  IRQ2로 슬레이브 IRQ가 전달될 수 있으므로 이 순서가 안전하다).
  리맵(벡터 오프셋을 8~15에서 다른 곳으로 옮기는 것)은 하지 않는다
  — 이 커널은 M10(smp-fpu-bringup.md)부터 LAPIC/MADT 경로만 쓰고
  8259를 쓸 계획이 전혀 없어서, "쓰되 벡터를 옮긴다"는 리맵 자체가
  불필요하다.
- **근거**: ADR-114가 "실제 GRUB(Multiboot2 ISO) 기반 검증은 여전히
  하지 않은 상태로 남는다"고 명시적으로 남겨 둔 갭을 이번에 실제로
  검증했다 — MSYS2에 GRUB 패키지가 없어(ADR-114 원문과 같은 사정,
  여전히 해결되지 않음) Docker(`debian:bookworm-slim` +
  `grub-pc-bin`/`grub-common`/`xorriso`)로 `grub-mkrescue`를 실행해
  진짜 Multiboot2 부팅 ISO를 만들고, QEMU를 `-bios qboot.rom
  -kernel ...`(PVH 개발 경로) 대신 `-cdrom <iso>`(SeaBIOS 기본
  펌웨어, 진짜 GRUB가 Multiboot2 헤더를 읽어 진입)로 띄웠다. 커널의
  Multiboot2 헤더/`_start32`(boot.S) 자체는 정확히 동작해 M1~M19의
  모든 커널 자체 테스트를 그대로 통과했지만, **initrun이 처음으로
  ring3(유저모드)에 진입하는 순간**(`enter_usermode`, usermode.S —
  `RFLAGS.IF=1`이 이 커널 전체에서 처음 켜지는 지점) 직후
  `vector=8`(#DF, 더블폴트) 예외로 죽었다 — PVH/qboot.rom 개발
  경로(ADR-114)에서는 M1부터 지금까지 단 한 번도 나타나지 않은
  증상이다. `MINICORE_QEMU_TRACE=1`(ADR-125)이 이미 마련해 둔
  `-d cpu_reset,guest_errors,int` 트레이스로 실제 원인을 확인했다 —
  진짜 CPU 더블폴트가 아니라 `Servicing hardware INT=0x08`(CPL=3,
  IP=0x10000000=initrun 진입점)로, **하드웨어 IRQ0(타이머)가 그대로
  벡터 8로 들어온 것**이었다. 이 커널은 8259를 한 번도 초기화(마스킹
  이든 리맵이든)하지 않았는데, 실제 BIOS(SeaBIOS)+GRUB 경로는 8259/
  PIT를 살려 둔 채 커널에 제어권을 넘긴다 — 리맵하지 않은 8259는
  기본 벡터 오프셋(마스터=8~15)을 그대로 쓰므로 IRQ0이 정확히
  `#DF`(8)와 충돌한다. QEMU의 PVH/qboot.rom 경로는 이 레거시 PIT를
  같은 방식으로 살려 두지 않아(정확한 내부 동작은 qboot.rom 구현
  세부이지만, 그 결과로 이 문제 자체가 이 경로에서는 전혀 나타나지
  않는다) 지금까지 드러나지 않았다. (부수적으로, 실제 CPU 예외가
  아닌 하드웨어 인터럽트가 그 자리를 차지하면서 `idt.hpp::
  interrupt_frame`이 기대하는 `[error_code, rip, cs, rflags,
  user_rsp, ss]` 슬롯 배치와 실제 스택 내용이 어긋나 보였다 — 진단
  로그의 `rip=0x33`/`cs=0x202` 등 뒤섞인 값은 이 IRQ 자체의 증상이며
  `interrupt_frame`의 버그는 아니다.)
- **영향**:
  - 이것으로 **이 프로젝트에서 처음으로 실제 GRUB Multiboot2 부팅
    경로가 M1~M20 전체 스모크 테스트 기준(공식 82개 어써션)까지
    끝까지 검증됐다** — 결과는
    [real-hardware-boot-verification.md](../done/real-hardware-boot-verification.md)
    참고. ADR-114의 "실기 또는 GRUB를 구할 수 있는 환경에서 별도로
    검증이 필요하다"는 남겨진 과제 중 "GRUB를 구할 수 있는 환경"
    부분이 Docker로 해소됐다 — 실제 물리 하드웨어 검증은 여전히
    범위 밖이다.
  - 이 변경은 `kernel/arch/x86_64/idt.cpp` 한 곳, 4줄(outb 헬퍼 +
    마스킹 함수 + 호출 한 줄)뿐이다 — 기존 스모크 테스트(82개)·
    SMP(11개)·NUMA(24개)·AVX(12개) 회귀 스위트 전부 재확인해 회귀가
    없음을 확인했다.
  - 8259를 실제로 리맵해 써야 하는 시나리오(예: LAPIC이 없는 아주
    오래된 실기, 또는 IOAPIC이 아예 없는 극단적 환경)는 이 커널의
    현재 로드맵(ADR-009: x86_64 우선, LAPIC/MADT 전제)에 없다 —
    필요해지면 별도 ADR.

## ADR-174. initrun/devmgr에 전달되는 arch_data_addr을 self-test 고정값(0)이 아니라 실제 감지값으로 교체

- **상태**: 확정 (2026-09-10)
- **결정**: `kernel_main.cpp::setup_initrun_process()`가 initrun에게
  넘기는 `boot_info`(유저 가상주소로 매핑되는 그 페이지)의
  `arch_data_addr` 필드를 `run_boot_info_self_test()`의 고정값(항상
  0)이 아니라, `dump_real_boot_info()`가 이미 계산해 둔 **실제
  감지값**(Multiboot2 RSDP 태그 또는 ADR-175의 UEFI RSDP)으로
  덮어쓴다. 새 전역 `g_real_arch_data_addr`(kernel_main.cpp, `g_mcfg`
  와 같은 부트스트랩 전역 관례)로 그 값을 `dump_real_boot_info()`
  호출 시점부터 `setup_initrun_process()` 호출 시점까지 들고 온다.
  `boot_info`의 나머지 필드(메모리맵 등)는 여전히 self-test 값이다
  — initrun 자신은 그 필드들을 읽지 않는다(기존 주석 그대로).
- **근거**: M12(system-servers-bringup.md) 시절 "GRUB가 없어(ADR-114)
  진짜 Multiboot2 boot_info가 없다"는 전제로 self-test 값을 그대로
  실었던 코드가 M20까지 그대로 남아 있었다 — `servers/devmgr`의
  자체 EBDA/BIOS ROM RSDP 스캔 폴백(`scan_for_rsdp()`)이 QEMU
  PVH 개발 경로와 실제 SeaBIOS+GRUB 경로 양쪽에서 우연히 계속
  성공해 이 결함이 드러나지 않았을 뿐이다. ADR-175(UEFI 경로)를
  실제로 검증하며 처음으로 드러났다 — OVMF는 그 폴백 영역에 legacy
  호환 RSDP 사본을 남기지 않아, devmgr의 ACPI/MCFG 파싱이 조용히
  실패했다(실측: `[devmgr] mcfg ecam_base=0xffffffffffffffff
  device_count=0x0`, 이후 usb/virtio-blk/fat32/ext4가 전부 "BAR
  없음"으로 건너뛰고 최종적으로 스케줄러 데드락 PANIC까지 이어졌다).
- **영향**:
  - 세 경로(PVH 개발/실제 GRUB/UEFI) 전부에서 devmgr가 이제 **진짜**
    ACPI RSDP를 받는다 — 폴백 스캔에 더 이상 의존하지 않는다(폴백
    자체는 그대로 남아 있다, 두 경로 모두 우연히 잘 동작해 왔으므로
    제거할 근거가 없다).
  - 이 수정은 UEFI 전용이 아니다 — PVH/GRUB 경로도 이전에는 항상
    0을 받다가 이제 실제 값을 받는다(동작 결과는 두 경로 모두
    바뀌지 않았다 — 표준 스모크 테스트 82개+SMP/NUMA/AVX 회귀
    스위트 재확인, 회귀 없음).

## ADR-175. 실제 UEFI 부팅 경로 최초 구현 — 별도 PE32+ EFI 스텁이 커널 ELF를 GRUB처럼 로드

- **상태**: 확정 (2026-09-10)
- **결정**: `docs/spec/boot.md` §1.2가 정의만 해 두고 실제로는 전혀
  없던 UEFI 진입 경로를 만든다. 커널 ELF 자체를 PE32+로 다시 빌드하는
  것이 아니라(이 커널의 higher-half 설계는 ELF의 `AT()`/`p_paddr`
  물리 적재 주소 분리 기능에 의존하는데, PE/COFF 포맷에는 그
  대응 개념이 없다 — VMA/RVA만 있고 "파일이 적재되는 물리주소와
  실행되는 가상주소가 다르다"는 것을 표현할 방법이 없다), **별도의
  작은 PE32+ EFI 애플리케이션**(`kernel/arch/x86_64/efi_stub/`)이
  기존 커널 ELF를 자기 안에 통째로 심어 두고 GRUB의 Multiboot2
  로더가 하는 일을 UEFI Boot Services로 그대로 재현한다.
  1. **커널 임베딩**: `kernel_blob.S.in`(`kernel/arch/x86_64/
     initrd_blob.S.in`과 완전히 같은 패턴)이 `.incbin`으로 커널
     ELF 전체를 심는다.
  2. **ELF 로딩**: `efi_main.cpp`가 그 ELF의 PT_LOAD 프로그램 헤더를
     직접 파싱해 각 세그먼트를 **`p_paddr`**(가상주소가 아니라)에
     그대로 복사한다 — `p_memsz > p_filesz`인 나머지는 0으로 채운다
     (`.bss` 관례). `AllocatePages(EFI_ALLOCATE_ADDRESS)`로 그 물리
     범위를 먼저 예약한다.
  3. **ACPI RSDP**: `EFI_CONFIGURATION_TABLE`에서 ACPI 2.0 GUID
     (`8868e871-e4f1-11d3-bc22-0080c73c8881`, 없으면 1.0 GUID
     `eb9d2d30-2d88-11d3-9a16-0090273fc14d`)로 찾아, 커널의
     `efi_acpi_rsdp_phys`(신규, `.boot.bss`, `mb2_magic`/
     `mb2_info_addr` 옆) 물리주소에 직접 써 넣는다 — 이 값은 빌드
     시점에 `tools/gen-efi-entry-addr.py`가 `llvm-nm`으로 뽑는다
     (이 커널은 ASLR/PIE가 없어 재현 가능, `_efi_entry`의 물리주소도
     같은 방식으로 뽑는다). `kernel_main.cpp::dump_real_boot_info()`
     는 이 값이 0이 아니면 Multiboot2 태그 파싱 대신 그대로
     `arch_data_addr`로 채택한다(코드 3줄 추가).
  4. **Boot Services 반납**: `GetMemoryMap`+`ExitBootServices`를
     스펙대로 호출한다(실패 시 표준 재시도 관례 한 번).
  5. **커널로 점프**: `_efi_entry`(신규, `boot.S`, `.boot.text` —
     물리 [0,8MiB) 안이라 CR3를 바꿔도 이 코드 자신의 페이지가
     매핑에서 빠지지 않는다)로 점프한다. UEFI는 **이미 long
     mode(페이징 켜짐)로 진입**하므로 `_start32`의 32비트 보호모드
     단계를 통째로 건너뛰고, `_start32`가 하던 일 중 필요한 부분
     (저지대 8MiB 항등 매핑 구성, 커널 자신의 GDT 재적재)만 64비트로
     다시 써서 재현한 뒤, 기존 `_start64`가 이미 쓰는
     `boot_setup_paging()`+`kernel_main()` 진입 꼬리를 그대로
     재사용한다.
- **근거**: 커널 본체(mm/sched/ipc/objects/servers 전부)를 통째로
  다시 빌드/링크하는 대신 "이미 완성된 ELF를 그대로 다른 방식으로
  적재하는 로더"만 새로 만드는 쪽이 검증된 코드를 건드리지 않는다
  — GRUB가 이미 정확히 이 역할을 하고 있고(ADR-173으로 처음
  검증됨), UEFI 스텁은 그 로더 역할을 UEFI Boot Services로
  다시 구현한 것뿐이다.
- **실행 중 발견하고 고친 버그 — retf 트릭이 UEFI의 원래 스택에
  push함**: CR3를 우리 페이지테이블(저지대 8MiB identity map만
  있음)로 바꾼 뒤, CS를 우리 GDT의 `SEL_CODE64`로 바꾸려고
  `push $CS; push $RIP; lretq` 트릭을 쓰는데, 이 시점의 RSP가 여전히
  UEFI가 `efi_main`에 넘겨준 원래 스택(대개 저지대 8MiB 밖)이었다
  — push 자체가 새 페이지테이블에 없는 주소에 쓰려다 실패하고, 이
  시점엔 유효한 IDT도 없어 아무 진단도 없이 조용히 멈췄다. 그 시점엔
  `klog`/`printf`가 전혀 없어(IDT조차 아직 없다) 포트 0x3F8에 문자
  하나씩(`'A'`~`'F'`) 직접 `outb`하는 체크포인트를 단계마다 심어
  원인을 좁혔다 — C(CR3 교체 직후)까지는 찍히고 D(retf 이후)부터
  안 찍혀, retf 직전 push가 원인임을 확인했다. retf 전에
  `low_boot_stack_top`(저지대, 항등 매핑 보장)으로 먼저 옮기도록
  순서를 바꿔 고쳤다.
- **영향**:
  - `docs/done/real-hardware-boot-verification.md`에 UEFI 경로
    검증 결과를 추가했다 — ADR-114/173이 시작한 "실제 배포 경로
    검증" 작업의 연장이다.
  - **알려진 제약(고치지 않고 남긴 것)**: USB xHCI 컨트롤러 리셋
    자체 테스트가 OVMF에서만 실패한다(`hcrst_done=0
    controller_ready=0`, `bar_phys=0x10000`처럼 명백히 잘못된 BAR
    값을 읽는다 — PCI 열거 자체는 xHCI 장치를 정확히 찾는다). OVMF가
    자신이 안 쓰는 PCI 장치의 BAR를 SeaBIOS와 달리 미리 구성해
    두지 않고, devmgr의 BAR 재사용/신규 배정 판단 로직(M15/M16,
    ADR-158/163)이 이 "미구성" 상태를 잘못 해석하는 것으로 보인다
    — 다운스트림에서 크래시나 행을 유발하지 않고(자체 테스트만
    실패로 기록), USB HID 실제 열거는 이미 M14 완료 보고서가 범위
    밖으로 명시해 뒀던 항목이라 더 깊이 조사하지 않고 알려진 한계로
    남긴다.
  - PE32+/UEFI 빌드는 `x86_64` 전용이다(다른 아키텍처의 UEFI
    스텁은 없다, ADR-009와 같은 우선순위).
  - `configure_file()`은 `$<TARGET_FILE:...>` 같은 제네레이터
    표현식을 평가하지 않는다는 것(구성 단계 vs 생성 단계의 시점
    차이) — 구현 중 실제로 겪은 실수라 여기 기록해 둔다. 커널 ELF의
    출력 경로를 문자열로 직접 구성해 피했다.

## ADR-181. 최소 네트워킹 — virtio-net 드라이버 + netsrv의 DHCP 왕복 자기테스트(ARP 없이)

- **상태**: 확정 (2026-09-10)
- **결정**: [general-purpose-completion.md §M25](../plan/general-purpose-completion.md)
  를 구현한다. [servers/drivers/virtio-net](../../servers/drivers/virtio-net/main.cpp)
  가 [servers/drivers/virtio-blk](../../servers/drivers/virtio-blk/main.cpp)
  (ADR-043 1순위, M15)와 **완전히 같은 legacy virtio I/O 포트
  레지스터 레이아웃**(VirtIO 1.0 §4.1.4.8 — host/guest_features,
  queue_address/size/select/notify, device_status)을 재사용해
  devmgr에 vendor:device=0x1AF4:0x1000으로 등록하고, RX(큐 0)/TX
  (큐 1) 두 virtqueue로 이더넷 프레임을 그대로 송수신한다(ARP/IP/UDP
  는 전혀 모른다 — 순수 하드웨어 계층). [servers/netsrv](../../servers/netsrv/main.cpp)
  가 이 드라이버에 IPC로 의존해(`depends=virtio-net`) 그 위에
  이더넷/IP/UDP 프레이밍을 직접 구현한다 — 실제 소켓 API
  (bind/connect/send/recv)는 만들지 않고, 부팅 시 자기테스트로
  "UDP 패킷 하나의 왕복"을 증명한다(다른 서버들의 self-test 관례와
  동일, procsrv.md §3.6류의 완전한 프로토콜은 M22/M23이 이미 좁혀
  온 것과 같은 정신으로 범위 밖). 왕복 대상은 DHCP(UDP 67/68,
  DHCPDISCOVER→DHCPOFFER)다 — ARP는 구현하지 않는다: DHCPDISCOVER는
  이더넷(`ff:ff:ff:ff:ff:ff`)과 IP(`255.255.255.255`) 둘 다
  브로드캐스트라 목적지 MAC을 ARP로 미리 구할 필요가 원천적으로
  없고, QEMU의 usermode 네트워킹(SLIRP, `MINICORE_QEMU_NET=1`,
  `tools/run-qemu.sh`)이 내장 DHCP 서버를 항상 갖고 있어 외부
  네트워크/인터넷 접근 없이도 결정적으로 응답이 온다.
- **근거**: 계획이 스스로 "UDP 정도로 시작, TCP는 후속"이라고
  좁혀 뒀고, "QEMU의 usermode 네트워킹(또는 loopback)으로 UDP
  패킷 하나를 왕복"만을 목표로 명시했다 — ARP까지 구현하는 것은
  이 목표에 꼭 필요하지 않은 범위 확장이었다(DHCP를 고른 것 자체가
  ARP 없이도 성립하는 왕복을 찾은 결과). virtio-blk와 코드를
  공유하지 않는 이유도 그 드라이버 자신의 주석과 같다 — 서로 다른
  신뢰 경계, 실제로 공유할 방법도 없다(별도 프로세스, 별도
  주소공간).
- **실제로 겪은 버그**: `compute_layout()`(virtio-blk와 동일)이
  반환하는 `desc_off`/`avail_off`/`used_off`는 **그 큐 자신의 vring
  시작을 기준으로 한 상대 오프셋**인데, 드라이버 초기 구현이 이
  값을 DMA 버퍼 전체의 시작(`g_dma_virt`)에 곧바로 더했다 — RX는
  `k_rx_vring_off==0`이라 이 실수가 우연히 값이 맞아 드러나지
  않았지만, TX는 `k_tx_vring_off!=0`이라 즉시 드러났다(디바이스는
  `queue_address` 레지스터로 정확히 안내받은 물리주소만 보는데,
  드라이버는 avail 링 갱신을 그 주소가 아니라 DMA 버퍼 맨 앞(RX의
  자리)에 써 버려 디바이스 쪽에서는 새 버퍼가 전혀 안 보였다 —
  `used_idx`가 영원히 그대로였다). 모든 vring 접근에 그 큐의 vring
  베이스 오프셋을 명시적으로 더하도록 고쳤다. 별도로, RX 버퍼
  영역의 총 크기(개수×버퍼크기)가 4096의 배수가 아니어서 그 다음에
  오는 TX vring이 페이지 정렬되지 않는 문제도 함께 발견해 버퍼
  크기를 1536→2048로 늘려 해결했다(`queue_address` 레지스터는
  페이지 프레임 번호, 즉 물리주소/4096을 저장하므로 정렬이 깨지면
  잘린 값이 완전히 다른 위치를 가리킨다) — `static_assert`로 이
  두 vring 오프셋이 실수로 다시 깨지는 것을 컴파일 타임에 막아
  뒀다.
- **검증 결과(QEMU 실측)**: [general-purpose-completion-m25.md](../done/general-purpose-completion-m25.md)
  참고 — `tools/smoke-test-net-x86_64.sh`(신설, `MINICORE_QEMU_NET=1`
  opt-in — ADR-125의 "기본값 유지" 패턴) 신설, DHCPDISCOVER 전송과
  DHCPOFFER 수신을 모두 확인(`"[netsrv] dhcp discover sent=1"`/
  `"[netsrv] udp roundtrip ok=1"`). 기본 스모크(네트워킹 미활성)와
  SMP/NUMA/AVX 4개 스위트 전부 회귀 없음 — virtio-net/netsrv가
  부트 디스크 서비스 목록에 새로 끼어들어도(virtio-blk와 fat32
  사이, servers/CMakeLists.txt) 나머지 순서를 깨지 않았다.
- **알려진 단순화**:
  - ARP를 구현하지 않는다 — DHCPDISCOVER의 브로드캐스트 특성에
    의존한 선택이라, 유니캐스트 목적지로 보내야 하는 임의의 UDP
    송신(예: 실제 DHCP 서버가 유니캐스트로 응답하거나, 이후
    유니캐스트 목적지로 patch를 보낼 때)은 아직 안 된다.
  - `netsrv`의 DHCP 응답 파싱은 BOOTP 옵션을 전혀 해석하지 않는다
    (op/xid만 확인) — 실제 임대(lease) 관리, IP 주소 확정은
    범위 밖이다. 이 커널의 어떤 프로세스도 아직 "내 IP"를 갖지
    않는다(전부 여전히 정적 부재 상태로 통신한다).
  - TCP는 계획이 스스로 "후속"으로 미뤄 둔 대로 전혀 없다.
  - 실제 소켓 API(bind/connect/send/recv, 여러 동시 연결)는 없다 —
    이 라운드는 왕복 메커니즘 자체의 증명이다.

## ADR-192. OPEN-51 방향 전환: "커널 서버"는 initrun이 하드코딩 직접 실행, "유저 서비스"는 별도 systemd류 데몬이 관리 — 두 계층으로 분리

- **상태**: 확정 (2026-09-10, 사용자 지시로 ADR-131 §결정7의 방향을
  바꾼다 — ADR-131 자신은 수정하지 않고 이 새 ADR로 대체 결정을
  기록한다, 문서 체계 원칙). **이 ADR은 같은 번호로 한 차례 갱신됐다**
  — 최초 초안은 "systemd류 데몬을 아예 폐기한다"였으나, 사용자가
  "systemd류 데몬도 필요하다 — '커널 서버'들만 커널(initrun)이
  하드코딩된 이름으로 구동하는 것이고, systemd는 유저랜드에서
  구동되는 유저 서비스를 관리하는 것"이라고 정정했다. 이 계획
  자체가 아직 실행되지 않은 순수 설계 단계였으므로(ADR-189가 이미
  보인 것과 같은 방식) 새 ADR 번호를 새로 매기지 않고 이 자리에서
  갱신한다.
- **결정**:
  1. **"커널 서버"(procsrv/vfs/devmgr/cfgsrv/`servers/drivers/*`/
     netsrv 등, ADR-006/007이 "직접 구현"으로 정한 것들)는 여전히
     initrun이 하드코딩된 이름·순서·의존관계로 직접 spawn한다** —
     `servers/CMakeLists.txt`의 `--service=`/`--depends=` 빌드 시점
     목록과 initrun의 cpio `lib/*.ini` 순차 spawn(ADR-131 §결정5)을
     그대로 유지한다. 이 계층은 부팅에 절대적으로 필요하고 컴파일
     타임에 고정되므로, 동적 발견/플러그인식 관리자를 두지 않는다 —
     이 부분은 최초 초안과 바뀌지 않았다.
  2. **모든 커널 서버 초기화가 끝나면, initrun은 ADR-131 §결정7이
     원래 계획한 대로 유저랜드 데몬을 마지막으로 하나 더 spawn하고
     스스로 사라진다** — 이 데몬이 실제 "systemd류" 컴포넌트다
     (정확한 이름은 착수 시점에 확정, `servers/svcmgr` 가칭).
     **이 데몬의 역할은 "커널 서버"를 관리하는 것이 아니라 —
     그건 이미 1번에서 initrun이 끝낸 일이다 — 그보다 위 계층인
     "유저 서비스"(시스템 관리자가 나중에 추가/제거/설정할 수 있는,
     컴파일 타임에 고정되지 않는 더 동적인 서비스 집합 — 예: 로그인
     세션 프로그램, 사용자가 등록한 백그라운드 작업 등)를 관리하는
     것**이다. 정확한 유저 서비스 등록/기술 방법(유닛 파일에 대응하는
     것이 무엇인지, cfgsrv 레지스트리를 쓸지 등)은 이 ADR의 범위 밖 —
     별도 설계 라운드 대상.
  3. **프로세스 트리의 영구 루트는 이 유저 서비스 관리자 데몬이다**
     (ADR-131 §결정7 원안 그대로 복원) — initrun이 사라질 때, 그
     시점까지 initrun의 자식이었던 커널 서버들은 procsrv의 프로세스
     테이블(M27, [procsrv.md](../spec/procsrv.md) §2)에서 **이
     데몬으로 재부모화(reparent)**된다(전통적 POSIX의 "고아
     프로세스는 pid 1에 재부모화"와 같은 역할). procsrv는 여전히
     이 재부모화를 실제로 수행하는 쪽(프로세스 테이블의 소유자)이지만,
     논리적 루트는 procsrv 자신이 아니라 이 데몬이다.
  4. **부팅에 필요한 파라미터(마운트 계획 포함)는 initrd/부트
     파라미터(Multiboot2 cmdline 등)에서 해석해 각 서버에게 인자로
     전달한다** — ADR-131 §결정5가 이미 만들어 둔 두 경로
     (`args=`로 argv 전달, `.ini`의 나머지 key=value를
     `config_blob_addr`/`size`로 원본 그대로 전달)를 **실제로
     활용**하도록 방향을 정한다. 구체적으로, M16이 VFS 소스 코드에
     직접 하드코딩한 "정적 마운트 테이블"을 이 `.ini`/`config_blob`
     경로를 통해 **부팅 파라미터로 넘어오는 값**으로 바꾸는 것을
     다음 VFS/마운트 작업 라운드의 목표로 삼는다(이번 ADR은 방향만
     정하고, 실제 코드 변경은 별도 실행 라운드로 미룬다 — 이
     계획(real-libc-syscall-layer.md)의 범위 밖이다). 이 결정은
     최초 초안과 바뀌지 않았다.
- **근거**: 사용자가 정정한 그대로다 — "커널이 procsrv 등 중요한
  서비스들의 이름을 하드코딩해 직접 실행"하는 것과 "systemd류
  데몬이 존재"하는 것은 서로 배타적이지 않다. 둘은 **서로 다른
  계층**을 담당한다: 전자는 이 OS 자신이 기능하기 위해 절대적으로
  필요한, 컴파일 타임에 고정된 핵심 서버 집합이고, 후자는 그 위에서
  동작하는, 사용자/관리자가 나중에 자유롭게 구성하는 서비스
  집합이다. 최초 초안은 이 둘을 하나로 뭉뚱그려 "데몬이 필요 없다"고
  결론 내렸는데, 이는 OPEN-51이 원래 묻던 질문(이 데몬의 정체성과
  책임 범위)에 대한 답을 "존재 자체를 없앤다"로 잘못 좁힌 것이었다 —
  실제로 필요한 답은 "존재하되, 책임 범위를 커널 서버와 겹치지 않게
  분리한다"였다.
- **영향**:
  - **OPEN-51은 이 ADR로 해소된다** — 데몬의 정체성(유저 서비스
    관리자)과 책임 범위(커널 서버는 다루지 않음)가 이제 명확하다.
    정확한 유저 서비스 등록 프로토콜/유닛 기술 방식은 **ADR-196
    (이 문서, 바로 다음)+ADR-197(registry-decisions.md)**로 이어서
    다룬다 — 같은 세션에서 바로 설계했으므로 별도 OPEN 번호를 새로
    만들지 않는다.
  - procsrv의 프로세스 테이블(M27)이 "재부모화" 절차를 실제로
    구현해야 한다 — 재부모화 **대상은 이 유저 서비스 관리자
    데몬**이다(procsrv 자신이 아니다). 다만 이 데몬 자체를 만드는
    작업은 [real-libc-syscall-layer.md](../plan/real-libc-syscall-layer.md)
    의 범위 밖이므로, M27은 "재부모화 메커니즘"만 일반적으로
    구현하고(대상 pid를 매개변수로 받는 형태), 이 데몬이 실제로
    생기기 전까지는 initrun의 고아들을 잠정적으로 `parent_pid = 0`
    (부모 없음)으로 둔다 — 데몬이 생기는 시점에 그 잠정 처리를
    대체한다.
  - VFS 정적 마운트 테이블을 boot 파라미터 기반으로 바꾸는 실제
    작업은 이 ADR이 방향만 정했을 뿐 구현하지 않는다 — 별도 라운드
    대상으로 [open-items.md](open-items.md)에 새 OPEN으로 남긴다.

## ADR-196. 유저 서비스 관리자 데몬(`servers/svcmgr`) 설계 — 유닛 모델, 시작 절차, 재부모화 완성, 컨트롤 프로토콜 개요

- **상태**: 확정 (2026-09-10, 계획 단계 — [user-service-manager.md](../plan/user-service-manager.md)
  M40 착수 전에 전략만 먼저 결정한다. ADR-192가 "유저 서비스 등록
  프로토콜은 별도 설계 대상"으로 남긴 것을 이 ADR이 채운다)
- **결정**:
  1. **새 서버 `servers/svcmgr`**(ADR-192가 예약해 둔 자리 — 이름을
     여기서 확정한다) — initrun이 "커널 서버" 전부를 기동한 뒤
     **마지막으로** spawn하는 유일한 프로세스다. initrun은 그 뒤
     스스로 사라진다(ADR-131 §결정7 원안, ADR-192 §결정2 유지).
  2. **유닛 모델** — 유저 서비스 하나는 다음 구조체로 기술된다
     (레지스트리 저장 형식은 ADR-197):
     ```cpp
     struct service_unit {
         char     name[32];
         char     exec_path[256];      // VFS 절대경로
         char     args[192];           // NUL로 구분된 argv, 마지막도 NUL
         bool     enabled;             // 부팅 시 자동 시작 여부
         uint32_t depends_on_count;
         char     depends_on[4][32];   // 이름으로 참조, 최대 4개(YAGNI)
     };
     ```
  3. **시작 절차** — svcmgr는 부팅 시 `@global/system/services`
     테이블(ADR-197)의 `enabled` 항목 전부를 읽어, `depends_on`
     그래프를 단순 위상정렬한 순서로 하나씩 procsrv에 fork+exec을
     요청해 spawn한다. **순환 의존은 감지만 하고 해소하지 않는다**
     — 순환에 걸린 서비스들은 스킵하고 debug_log로 남긴다(YAGNI,
     실제 유닛 수가 적을 것이므로 그래프 알고리즘에 투자하지 않는다).
     **각 서비스 spawn마다 ADR-193의 준비완료 신호**(spawn 시점
     전용 endpoint의 `k_service_ready_label` Call)**를 기다린 뒤에야
     다음 서비스로 넘어간다** — initrun이 커널 서버에게 쓰는 것과
     정확히 같은 패턴을 데이터 기반으로 재사용한다.
  4. **신원(v1 고정)** — 모든 유저 서비스는 v1에서 **단일 고정
     시스템 계정** 아래 실행된다(ADR-087의 시스템 서비스 uid 대역
     1~999에서 하나 예약, 정확한 값은 착수 시점에 확정). 계정별
     인스턴스(systemd의 `user@.service`에 대응, 로그인한 사용자마다
     별도 실행)는 v1 범위 밖 — 아래 "포함하지 않는 것" 참고.
  5. **재부모화 대상 확정** — ADR-192 §결정3이 만든 재부모화
     메커니즘(대상을 매개변수로 받음, M27에서는 데몬이 없어
     잠정적으로 `parent_pid=0`)의 실제 대상이 이제 **svcmgr 자신의
     pid**로 확정된다. initrun이 사라지는 시점에 procsrv가 남은
     커널 서버들의 `parent_pid`를 svcmgr로 갈아치운다.
  6. **재시작 정책(restart policy)은 v1 범위 밖이다** — 서비스가
     죽으면 다시 시작하지 않는다(YAGNI, systemd `Restart=` 대응 기능
     없음). 실패 시 procsrv의 `OP_WAIT`로 회수한 exit code를 svcmgr가
     debug_log로만 남긴다.
  7. **컨트롤 프로토콜 개요**(런타임 시작/정지/조회) — 이 ADR은
     오퍼레이션 목록만 정하고 바이트 레이아웃은 ADR-195의 마크업
     컨벤션에 따라 실제 착수 시점(계획의 해당 마일스톤)에 확정한다:
     `op_list`(등록된 전체 유닛+상태 조회), `op_status(name)`,
     `op_start(name)`/`op_stop(name)`/`op_restart(name)`(마지막
     둘은 기존 procsrv `OP_KILL`(ADR-178/186)과 재spawn을 그대로
     조합), `op_register`/`op_unregister`(런타임에
     `@global/system/services` 테이블을 갈아치움 — `systemctl
     enable`/`disable`에 대응, super 권한만 허용).
- **근거**: 새 커널/IPC 프리미티브를 하나도 추가하지 않는다 — 유닛
  시작은 procsrv의 기존 fork/exec, 준비완료는 ADR-193이 이미 정한
  관례, 정지는 ADR-178/186의 기존 kill/signal, 저장은 cfgsrv의
  기존 레지스트리 프로토콜(ADR-197)을 그대로 재사용한다. svcmgr는
  구조적으로 "procsrv/cfgsrv를 호출하는 또 하나의 유저 프로세스"일
  뿐이다 — ADR-006/007이 이미 강제하는 "커널은 최소한만" 원칙과
  ADR-132의 "새 프로토콜도 결국 `libmc`를 통해서만" 원칙을 그대로
  따른 결과다.
- **영향**:
  - `libmc/include/mc/svcmgr_protocol.h`(신규)가 이 프로토콜의
    정본이 된다 — ADR-195의 `@wire-op` 마크업을 처음부터 적용한다
    (M27의 procsrv 프로토콜에 이어 두 번째 적용 사례).
  - [repo-layout.md](repo-layout.md)의 `servers/` 목록에 `svcmgr`를
    추가해야 한다.
  - [registry.md](../spec/registry.md)가 ADR-197의 새 스키마를
    반영해야 한다.
  - **포함하지 않는 것**(v1 범위 밖, 향후 필요해지면 재검토):
    계정별 서비스 인스턴스(`user@.service` 대응), 소켓 활성화,
    타이머/cron 대응, 리소스 제한(cgroups 대응), 의존성 순환의
    자동 해소, 유닛 템플릿.

## ADR-193. OPEN-52 해소: 서비스 준비완료 신호를 기존 "spawn 시점 전용 endpoint의 Call/Reply"로 통일 (신규 프리미티브 없음)

- **상태**: 확정 (2026-09-10, 사용자 지시: "프로세스와 서비스 간
  IPC, 커널·서비스·프로세스 간 통신 메커니즘을 추상화하고 일관된
  채널을 설계하는 데 중점을 둬야 한다")
- **결정**: ADR-131 §결정6이 "기다렸다가 다음으로 진행한다"는 방향만
  정하고 신호 프로토콜 자체는 OPEN-52로 미뤄 뒀던 것을 다음과 같이
  확정한다 — **새 커널 메커니즘을 전혀 추가하지 않는다.**
  1. **"준비완료" 신호는 이미 있는 "spawn 시점 전용 endpoint"
     (ADR-151/152의 `create_endpoint=true`, M22가 wait/kill에 이미
     재사용한 패턴) 위의 **첫 번째 Call**이다.** 스폰된 서비스는
     자기 초기화가 끝나면, procsrv나 initrun처럼 자신을 spawn한
     쪽이 미리 준 그 전용 endpoint에 예약된 label
     (`k_service_ready_label = 0`)로 Call을 보낸다. 스폰한 쪽은
     `sys_ipc_recv`로 그 Call을 블로킹 대기하다가 받으면
     `sys_ipc_reply`로 즉시 응답해 그 서비스가 계속 진행하게 하고,
     그제서야 **다음** 서비스를 spawn한다(ADR-131 §결정6의 순서
     보장이 이렇게 구현된다).
  2. **"종료 회수"(M22/M27의 `OP_WAIT`)와 "준비완료"는 이제 완전히
     같은 모양의 상호작용**이다 — 둘 다 "spawn 시점에 만들어진
     전용 endpoint 위의 단발성 Call/Reply"다. 차이는 **시점**
     (초기화 직후 vs 종료 시점)과 **label 값**뿐이다. 이것이
     사용자가 요구한 "일관된 채널"이다 — 커널이 제공하는 원시
     능력은 Call/Reply와 notification(ipc.md §2/§7) 두 가지뿐이고,
     이 ADR은 그 원시 능력을 "서비스 생명주기 신호" 전체에 단
     하나의 관례로 통일해 재사용하는 것이다.
  3. `libmc`에 이 관례의 클라이언트/서버 양쪽 얇은 래퍼
     (`mc_signal_ready()`/`mc_wait_ready()`)를 추가한다(ADR-183
     §결정4와 같은 이유 — 이 프로토콜의 조립 로직도 `libmc` 한
     곳에만 둔다).
- **근거**: 서비스 준비완료·프로세스 종료 회수·(향후) 그 밖의
  생명주기 이벤트 각각에 대해 별도의 커널 프리미티브나 별도의 IPC
  관례를 새로 만들면, "커널·서비스·프로세스 간 통신 메커니즘"이
  이벤트 종류마다 파편화된다 — 사용자가 지적한 위험이다. 이미
  M22(ADR-178)가 "spawn 시점 전용 endpoint" 패턴을 wait에 쓰기로
  결정해 둔 것을 그대로 준비완료 신호에도 적용하면, 새 메커니즘
  없이 "일관된 채널"이 자연히 성립한다.
- **영향**:
  - **OPEN-52는 이 ADR로 해소된다.**
  - ADR-131 §결정5의 각 서비스 spawn 절차에 "spawn 시 준비완료용
    전용 endpoint도 함께 만든다"(기존 `create_endpoint=true`를
    핵심 서비스 spawn 전부에 일관되게 적용)는 요구사항이 추가된다 —
    지금까지 일부 spawn 경로만 `create_endpoint=true`를 썼다면
    (M22의 wait 데모처럼) 이제 **모든** 핵심 서비스 spawn이 이
    패턴을 쓰도록 확장해야 한다.
  - `k_service_ready_label`은 procsrv 전용이 아닌 **전역 예약
    label 값**이다 — 각 서버 프로토콜의 label 네임스페이스
    (`proc_op`, `fs_op` 등)와 충돌하지 않도록 `libmc` 헤더(단일
    출처, ADR-132/183)에서 한 곳에 정의한다.
