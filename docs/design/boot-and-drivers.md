## ADR-017. 부트 프로토콜: Multiboot2 + UEFI 이중 지원, initrun은 커널이 직접 시작 (해결: OPEN-7)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널은 **Multiboot2**(BIOS/GRUB 경로)와 **UEFI**(직접 부팅) 양쪽에서
  진입 가능한 엔트리포인트를 모두 갖는다. 어느 경로로 부팅되었든 커널 초기화가
  끝나면, 커널이 initrd/부트 이미지 안의 initrun 바이너리를 **직접 로드**하여
  첫 유저 프로세스로 실행한다 (별도의 2단계 유저 로더 없음).
- **근거**: Multiboot2는 QEMU/GRUB 개발 반복이 빠르고, UEFI는 실기(특히 최신
  하드웨어)와 향후 aarch64 부팅에 필요하다. initrun을 커널이 직접 시작하면
  "부트로더가 유저 프로세스 개념을 알아야 하는" 계층 누수를 없앨 수 있다.
- **영향**:
  - 커널 진입점이 두 개(Multiboot2 헤더 경유 / UEFI 애플리케이션 경유)이며,
    이후 공통 초기화 경로로 합류하는 arch 계층 코드가 필요하다.
  - aarch64(ADR-009 2순위 타겟)는 QEMU virt 관례상 디바이스 트리 기반의 별도
    진입 방식이 필요해, 사실상 세 번째 부팅 경로가 된다. → **미결정 (OPEN-19)**
  - initrun에게 넘길 초기 인자(메모리 맵, 커맨드라인, initrd 위치 등)의
    형식 정의가 필요하다. → OPEN-19에 포함.

## ADR-026. aarch64 부팅: 공통 boot_info 구조체로 통일 (해결: OPEN-19)

- **상태**: 확정 (2026-09-08)
- **결정**: x86_64(Multiboot2/UEFI)와 aarch64(FDT)는 각자의 네이티브 부팅
  프로토콜을 arch 계층에서 파싱한 뒤, 공통 `boot_info` 구조체(메모리맵,
  initrd 위치·크기, 커맨드라인, CPU 코어 정보 등)로 변환하여 커널 코어
  초기화와 initrun에 전달한다.
- **근거**: ADR-002(HAL 경계)와 ADR-017(부팅 이중 지원)의 자연스러운 연장 —
  커널 코어와 initrun이 부팅 프로토콜의 존재 자체를 몰라도 되게 한다.
- **영향**:
  - `kernel/include`에 아키텍처 독립적인 `boot_info` 구조체(공유 ABI)를
    정의해야 한다 (`docs/design/repo-layout.md`의 `kernel/include` 위치와 일치).
  - aarch64 arch 계층은 FDT 파서를 **직접 구현**해야 한다(ADR-006과 일치 —
    서드파티 FDT 라이브러리 사용 금지, 필요한 최소 파싱만 자체 구현).
  - `boot_info`를 initrun에게 실제로 전달하는 메커니즘(레지스터/스택/
    공유 페이지)은 별도 결정 필요. → **미결정 (OPEN-22)**

## ADR-030. boot_info 전달 메커니즘: 아키텍처 관례상의 첫 인자 레지스터 (해결: OPEN-22)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널은 `boot_info`(spec/boot.md §3)가 담긴 페이지를 initrun
  주소공간에 읽기전용으로 매핑하고, 그 가상주소를 initrun 최초 스레드
  진입 시 **아키텍처 관례상 "첫 인자" 레지스터**로 전달한다: x86_64는
  `RDI`, aarch64는 `X0`.
- **근거**: 각 아키텍처의 함수 호출 규약에서 이미 "첫 인자"로 쓰이는
  레지스터를 재사용하면, initrun 진입 스텁을 평범한 함수 호출처럼
  `_start(const boot_info* info)` 형태로 작성할 수 있어 가장 단순하다.
  `docs/spec/boot.md` 작성을 구체화하는 과정에서 확정이 필요해 이 시점에
  결정했다(사용자 확인 전 임시 채택 — 이견 시 언제든 대체 가능).
- **영향**:
  - initrun 이후 다른 서버를 기동할 때는 이 관례를 강제하지 않는다 —
    각 서버의 시작 인자 형식은 initrun 자신의 설계(기동 매니페스트,
    미정)에 맡긴다.

## ADR-037. 디버그 콘솔: 커널 내장 시리얼 드라이버로 확정 (ADR-007 구체화)

- **상태**: 확정 (2026-09-08)
- **결정**: ADR-007에서 "커널 내부에 둘 것"으로 이미 정한 "시리얼/초기
  콘솔(디버그용)"을 구체화한다. x86_64는 **16550 호환 UART(COM1, I/O
  포트 `0x3F8`)**, aarch64는 **PL011 UART(QEMU virt MMIO `0x09000000`)**를
  커널이 직접 구동하는 **폴링 기반** 디버그 로깅 경로로 삼는다. 이 경로는
  유저 프로세스에게 노출되지 않으며, ADR-007이 말하는 "이후 유저
  프로세스로 구현될 실제 콘솔 드라이버"와는 완전히 별개다.
- **근거**: 유저 프로세스는커녕 IPC조차 없는 부팅 극초기부터 커널
  개발 전 과정에 걸쳐 관찰 가능한 로그가 없으면 디버깅이 사실상
  불가능하다. [kernel-bootstrap.md](../plan/kernel-bootstrap.md) M1의
  첫 관찰 가능한 산출물("hello from kernel")도 이 경로에 의존한다.
- **영향**:
  - [debug-console.md](../spec/debug-console.md)에 레지스터 수준 스펙과
    커널 내부 `klog` API를 정의한다(즉시 작성).
  - 이 로그 경로는 성능이 중요하지 않으므로 ADR-033("필요한 곳만 최소
    범위 락")의 예외로 **전역 스핀락 1개**를 허용한다 — 여러 코어가
    동시에 로그를 남겨도 출력 순서가 뒤섞이지 않게 한다.
  - 인터럽트 기반 비동기 로깅, 커널 패닉 덤프 절차는 이 ADR의 범위
    밖이며 필요 시 후속 결정으로 다룬다.

## ADR-038. PCIe 설정 공간 접근: ECAM 우선 + 레거시 I/O 포트 폴백

- **상태**: 확정 (2026-09-08)
- **결정**: PCIe 설정 공간은 ACPI MCFG 테이블로 알려지는 ECAM(메모리
  매핑) 방식을 우선 사용한다. MCFG가 없거나 실패하면 x86 레거시
  I/O 포트(`0xCF8`/`0xCFC`, CONFIG_ADDRESS/CONFIG_DATA)로 대체한다.
- **근거**: ECAM은 QEMU q35 및 대부분의 실제 하드�웨어에서 표준이며
  전체 설정 공간(4KB/장치)에 접근 가능하다. 레거시 폴백은 극히 오래된
  환경이나 MCFG 파싱 실패 시의 안전망이다.
- **영향**:
  - ECAM은 그냥 MMIO 영역이므로 ADR-007의 기존 "MMIO 캐패빌리티 매핑"
    메커니즘을 그대로 재사용한다 — 새 캐패빌리티 종류가 필요 없다.
  - 레거시 I/O 포트 접근은 x86 전용 특권 명령(`in`/`out`)이 필요하므로
    **새로운 캐패빌리티 종류(I/O 포트 범위 권한)**가 필요하다 — 이
    권한은 devmgr에게만 부여되고, PCIe 자체 드라이버들은 devmgr가
    이미 열거한 결과(BAR, IRQ 등)만 넘겨받으므로 직접 포트 접근이
    필요 없다.
  - MCFG 파싱은 x86_64 `arch_data_addr`(ACPI RSDP, ADR-036)을 통해
    devmgr가 접근한다.

## ADR-039. 버스 열거·PnP 매칭 책임: devmgr 전담, 새 syscall 없음

- **상태**: 확정 (2026-09-08)
- **결정**: PCIe 버스 열거와 장치-드라이버 매칭(PnP)은 devmgr가 전담한다
  (ADR-007에서 이미 devmgr의 역할로 정한 "버스 열거"의 구체화). ECAM은
  일반 MMIO 영역이므로, 커널에 PCI 전용 syscall을 추가하지 않고 기존
  MMIO 캐패빌리티 매핑 메커니즘만으로 devmgr가 설정 공간을 직접 읽는다.
- **근거**: ADR-007의 경계(버스 열거는 유저 프로세스)와 정확히 일치하며,
  새로운 커널 개념을 도입하지 않아 커널이 작게 유지된다(ADR-001의
  "커널 밖으로 미는" 원칙).
- **영향**:
  - devmgr는 부팅 후 ECAM 영역 전체(또는 필요한 버스 범위)를 자신의
    주소공간에 매핑할 캐패빌리티를 커널/initrun으로부터 받아야 한다 —
    구체적 위임 경로는 initrun의 기동 매니페스트 설계(OPEN-29)에서 다룬다.
  - 레거시 I/O 포트 폴백(ADR-038)이 필요한 경우에만 devmgr가 포트
    접근 캐패빌리티를 추가로 받는다.

## ADR-040. PCIe 핫플러그 이벤트: 커널 인터럽트 → 비동기 notification

- **상태**: 확정 (2026-09-08)
- **결정**: PCIe 핫플러그/PME 인터럽트는 커널이 수신하여 ADR-004의
  비동기 notification으로 devmgr에게 전달한다. devmgr는 notification을
  받으면 ECAM을 다시 스캔해 변경 사항(장치 추가/제거)을 스스로 판별한다.
- **근거**: ADR-007이 이미 "인터럽트는 커널이 받아 유저 드라이버에게
  notification으로 전달"로 정해두었다 — 핫플러그도 결국 인터럽트이므로
  기존 구조를 그대로 재사용할 뿐 새로운 개념이 필요 없다. ACPI GPE
  경유 방식은 커널이 ACPI 이벤트 해석까지 직접 구현해야 해서 범위가
  불필요하게 커진다.
- **영향**:
  - devmgr는 notification 수신 시 "무엇이 바뀌었는지"를 스스로
    diff(이전 열거 결과와 재스캔 결과 비교)해야 한다 — 커널은 변경
    내용을 알려주지 않고 "뭔가 바뀌었을 수 있다"는 신호만 준다.

## ADR-041. 드라이버 등록/매칭(PnP): 실행 중 devmgr에 동적 ID 등록

- **상태**: 확정 (2026-09-08)
- **결정**: 드라이버 프로세스는 기동 후 devmgr에게 IPC로 "나는 이
  vendor:device(또는 클래스) 목록을 처리한다"고 동적으로 등록한다.
  devmgr는 이미 열거된 장치와 새로 등록된 드라이버를 그때그때 매칭하며,
  드라이버가 재시작되어도(ADR-007의 감시자 재시작) 동일한 등록 절차를
  다시 밟으면 되므로 재시작에 자연스럽게 대응한다.
- **근거**: initrd 정적 테이블 방식은 구현이 간단하지만 "드라이버를
  나중에 파일시스템에서 추가로 발견"하는 시나리오(ADR-001의 범용 OS
  지향, 장기적으로 드라이버 패키지를 설치하는 것과 같은 그림)를 처음부터
  막는다. 동적 등록은 초기엔 그대로 "부팅 시점에 이미 떠 있는 드라이버들만
  등록"하는 것으로 시작해도 되므로, 정적 방식과 초기 동작이 동일하면서
  확장 여지를 남긴다.
- **영향**:
  - devmgr↔드라이버 간 "등록" IPC 프로토콜(ID 목록 형식, 우선순위/충돌
    시 정책)을 정의해야 한다 — spec 대상.
  - 드라이버 자신도 기동 시점을 알아야 하므로, initrun의 기동
    매니페스트(OPEN-29)가 "이 드라이버들을 언제 띄울지"를
    결정하는 지점이 된다 — devmgr 자체는 정적 목록을 몰라도 되지만,
    누군가는(initrun) 드라이버 프로세스를 실행시켜야 한다.
  - 동일 장치에 여러 드라이버가 등록을 시도할 때의 충돌 해소 정책은
    미정 → **미결정 (OPEN-26)**

## ADR-043. 디바이스 드라이버 로드맵: virtio 계열 우선, 실기 표준은 후속

- **상태**: 확정 (2026-09-08)
- **결정**: 스토리지·NIC·그래픽 드라이버(모두 유저 프로세스, ADR-007)는
  각자 독립적인 우선순위를 갖되, 공통적으로 **QEMU virtio 계열을 먼저
  구현하고 실기 표준 프로토콜은 그 다음 단계로 미룬다**.

  | 클래스 | 1순위 | 2순위 | 비고 |
  |---|---|---|---|
  | 스토리지(블록 드라이버) | `virtio-blk` | AHCI(SATA) → NVMe(M.2) | AHCI가 NVMe보다 먼저 |
  | 파일시스템 서버 | FAT32 | (추가 FS는 필요 시 결정) | virtio-blk 검증 직후 착수 (ADR-057). 블록 드라이버 무관하게 재사용 |
  | NIC | `virtio-net` | e1000(실기용) | |
  | 그래픽 | `virtio-gpu`(프레임버퍼 모드) | VESA(BIOS)/UEFI GOP(프레임버퍼) | 3D 가속은 이 로드맵 범위 밖(장기 과제) |

- **근거**: virtio는 QEMU 개발 환경에서 프로토콜이 가장 단순해 각
  드라이버 클래스(그리고 그 위의 서버 — 파일시스템, netsrv, 콘솔)를
  빠르게 수직으로 검증할 수 있게 한다. 실기 표준(AHCI/NVMe/e1000/
  VESA·GOP)은 범용 OS 지향(ADR-001)에 필수적이지만 프로토콜이 훨씬
  복잡해, virtio로 상위 스택(파일시스템, 네트워크 스택, 콘솔 서버)을
  먼저 검증해둔 뒤에 하드웨어 드라이버만 교체하는 순서가 이중 작업을
  줄인다. AHCI가 NVMe보다 사양이 오래되고 자료·구현 난이도가 낮아
  먼저 선택되었다. 그래픽은 3D 가속이 사실상 별도 대형 프로젝트급
  범위이므로 프레임버퍼(모드 설정 + 픽셀 버퍼)까지만 이 로드맵에 넣는다.
- **영향**:
  - 모든 항목은 PCIe 장치이므로 ADR-038~041(설정공간 접근, devmgr
    열거, 핫플러그, 동적 드라이버 등록)을 그대로 따른다 — 클래스별
    특수 규칙이 필요 없다.
  - `servers/drivers/`(repo-layout.md) 하위에 클래스별 서브디렉토리를
    추가할 때 이 순서를 기본 작업 순서로 삼는다.
  - 각 드라이버의 레지스터 수준 프로토콜 스펙은 해당 마일스톤 착수
    시점에 `docs/spec/`에 개별 작성한다(지금은 로드맵 순서만 확정).
  - 3D 가속, GPU 컴퓨트는 로드맵 밖으로 명시적으로 제외했다 —
    필요해지면 별도 ADR로 범위를 연다.

## ADR-046. /boot 구성: 일반 디렉토리 + /boot/uefi에 ESP 마운트

- **상태**: 확정 (2026-09-08)
- **결정**: `/boot`는 루트 파일시스템 안의 평범한 디렉토리이며,
  커널 이미지·initrd 등 Multiboot2 경로(ADR-017)에 필요한 파일들이
  직접 위치한다. UEFI 부팅(ADR-017)에 필요한 EFI System
  Partition(FAT32)은 `/boot/uefi`에 **마운트**된다.
- **근거**: 대부분의 부팅 자산(커널, initrd)은 일반 디렉토리로
  충분하고, UEFI ESP만 FAT32라는 특수 포맷 제약이 있으므로 그
  부분만 별도 마운트로 분리하는 것이 가장 단순하다.
- **영향**:
  - FAT32 드라이버(FS 서버)가 `/boot/uefi` 마운트에 필요하다 —
    ADR-043의 드라이버 로드맵에는 아직 없으므로, UEFI 부팅 경로를
    실제로 완성하려면 FAT32 FS 서버 작업이 로드맵에 추가되어야 한다.
    → 로드맵 갱신 필요 (실제 착수 시점에 ADR-043 갱신 또는 후속 ADR).
  - Multiboot2 전용 개발(현재 kernel-bootstrap.md M1~M8, ADR-009)에는
    `/boot/uefi` 마운트가 필요 없다 — ESP는 UEFI 부팅 경로를 실제로
    쓸 때만 의미가 있다.

## ADR-056. 드라이버 등록 충돌: 선착순 기본 + 관리자 설정으로 대체 가능 (해결: OPEN-26)

- **상태**: 확정 (2026-09-08)
- **결정**: 기본 정책은 **선착순**(먼저 등록한 드라이버가 소유, 이후
  시도는 거부)이다. 다만 시스템 관리자(root) 계정이 명시적 설정
  (설정 파일 또는 관리 명령)으로 특정 장치-드라이버 바인딩을 고정하면,
  devmgr는 그 설정을 선착순보다 **우선 적용**한다 — 관리자가 지정한
  드라이버가 기존 선착순 소유자를 대체할 수 있다.
- **근거**: 선착순은 구현이 단순하고 예측 가능한 기본 동작이다.
  그러나 실제 운영에서는 특정 장치에 항상 특정 드라이버를 강제하고
  싶은 경우(예: 범용 드라이버보다 벤더 특화 드라이버 우선)가 있으므로,
  관리자 오버라이드 경로를 열어둔다.
- **영향**:
  - 관리자 설정은 `/sys/etc`(ADR-044) 아래의 설정 파일로 보관하는
    것이 자연스럽다 — 구체적 파일 위치·형식은 devmgr 설계 시 정한다.
  - devmgr는 "root 권한으로 인증된 요청"을 검증하는 수단이 필요하다
    — ADR-027/ADR-024와 같은 정책 서버 프록시 기반 특권 메커니즘을
    재사용할 수 있다(관리자 전용 프록시 핸들).
  - 관리자 설정에 의해 대체된 기존 드라이버는 `device_removed`
    통지(pcie.md §4)를 받는다.

## ADR-057. FAT32 FS 서버를 드라이버 로드맵에 즉시 추가 (ADR-043 갱신) (해결: OPEN-27)

- **상태**: 확정 (2026-09-08)
- **결정**: FAT32는 블록 드라이버가 아니라 그 위에 얹히는 **파일시스템
  서버**(`servers/fs/`, memfs와 같은 층)다. ADR-043의 스토리지
  로드맵과는 다른 축이지만, 우선순위를 명시적으로 확정한다: **virtio-blk
  검증 완료 직후 착수** — virtio-blk가 이미 1순위 블록 드라이버이므로
  FAT32는 그 위에서 바로 개발·검증을 시작할 수 있고, AHCI/NVMe가
  나중에 준비되어도 FAT32 서버 자체는 블록 드라이버에 무관하게
  재사용된다.
- **근거**: `/boot/uefi`(ADR-046)의 ESP 마운트에 FAT32가 필요하며,
  UEFI 부팅 경로(ADR-017)를 실제로 검증하려면 이 서버가 있어야 한다.
  블록 드라이버 우선순위 리스트에 끼워 넣지 않고 별도로 명시하는
  이유는, FAT32가 "어떤 블록 드라이버 위에서도" 동작해야 하는
  블록-드라이버-비의존적 컴포넌트이기 때문이다.
- **영향**:
  - ADR-043의 표에 "파일시스템 서버" 행으로 FAT32를 추가한다(즉시
    반영).
  - `vfs-layout.md`의 OPEN-27이 이 결정으로 해소된다 — 로드맵
    편입 시점은 "지금 확정, virtio-blk 다음"이다.
