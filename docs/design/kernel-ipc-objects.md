## ADR-004. 커널 모델: 하이브리드 IPC (동기 호출 + 비동기 알림)

- **상태**: 확정 (2026-09-08)
- **결정**: 두 개의 독립적인 IPC 원시(primitive)를 제공한다.
  1. **동기 호출(Call/Reply)** — 클라이언트-서버 RPC. 호출자는 응답까지 블록되고,
     스케줄러는 가능하면 서버로 직접 전환한다(donation).
  2. **비동기 알림(Notification)** — 소실 없는 비트셋 시그널. 인터럽트, 이벤트,
     "할 일 생김" 통지용. 버퍼링/큐잉 없음.
- **근거**: RPC를 비동기로 흉내내면 유저랜드가 상태 기계로 오염되고, 인터럽트를
  동기 IPC로 처리하면 커널이 대기 큐를 떠안는다. 두 축을 분리하는 편이 양쪽 모두 단순하다.
- **영향**:
  - 메시지 데이터 전달 방식(레지스터/버퍼/공유메모리)을 정의해야 한다. → **미결정 (OPEN-3)**
  - 대용량 데이터는 IPC가 아니라 메모리 매핑 이전으로 처리하는 것을 기본으로 한다.

## ADR-011. 커널 객체 참조 모델: 프로세스당 단순 핸들 테이블 (해결: OPEN-5)

- **상태**: 확정 (2026-09-08)
- **결정**: seL4류 CSpace 트리 대신, 각 프로세스가 자신의 **단순 정수 핸들 테이블**을
  가진다. 스레드·주소공간·엔드포인트·notification·메모리 객체 등 모든 커널 객체는
  프로세스별 핸들을 통해서만 접근한다.
- **근거**: ADR-008(POSIX 서버 분해)에서 POSIX `fd`와 커널 핸들이 구조적으로 대응하기
  쉬워진다. CSpace 트리 대비 구현 복잡도가 훨씬 낮다.
- **영향**:
  - 핸들을 다른 프로세스에게 넘기는 것(권한 위임)은 IPC 중 "핸들 전달" 동작으로
    구현한다 — 커널이 송신자 핸들 테이블 항목을 수신자 핸들 테이블에 복제/이동.
  - CSpace만큼 세밀한 위임 체인 추적(파생 관계, 계층적 철회)은 포기하고 단순성을 취한다.
  - 핸들 철회(revoke)와 권한 축소(예: read-only로 파생된 핸들) 표현 방식은
    별도 설계 필요. → **미결정 (OPEN-12)**

## ADR-013. IPC 데이터 전달: 레지스터 + 프로세스 로컬 페이지 자동 번역 + 가변 길이 IDL 메시지 혼용 (해결: OPEN-3)

- **상태**: 확정 (2026-09-08)
- **결정**: IPC 데이터 전달을 세 계층으로 혼용한다.
  1. **레지스터**: 소량 데이터(동기 호출의 인자·반환값)는 레지스터로 전달한다 (ADR-004).
  2. **프로세스 로컬 페이지 + 커널 자동 번역**: 대용량 데이터는 송신자가 사전에
     공유 매핑을 설정할 필요 없이, **자신의 주소공간에 있는 메모리 페이지**를
     지정하면 커널이 IPC 호출 시점에 수신자 주소공간으로 **자동으로 주소를 번역**하여
     전달한다. 이는 ADR-004에서 언급한 "대용량은 매핑 이전으로"를 사전 설정 없이
     매 호출마다 수행하는 형태로 구체화한 것이다.
  3. **가변 길이 IDL 기반 메시지**: 위 페이지 전달 위에 구조화된 페이로드(필드 목록)를
     정의해, 서버 간 프로토콜(ADR-008의 VFS/FS/프로세스 서버 등)을 타입 있게 주고받는다.
- **근거**: 서비스마다 사전 공유 메모리 채널을 개별 설정하는 운영 부담을 없애면서도,
  레지스터만으로 부족한 대용량 데이터(예: 파일 읽기 결과)를 커널이 옮겨줄 수 있게 한다.
- **영향 (설계 부담이 크므로 최우선 후속 과제로 지정)**:
  - **"커널의 자동 주소 번역"의 정확한 의미를 정의해야 한다.** 후보는 최소 3가지이며
    성능·보안·구현 난이도가 크게 갈린다:
    - (a) **임시 매핑(map-then-unmap)**: 커널이 호출 동안만 송신자 페이지를 수신자
      주소공간에 매핑했다가 반환 시 해제. 복사 비용 없음, 그러나 수신자가 호출이
      끝난 뒤에도 데이터를 보관하려면 별도 복사가 필요.
    - (b) **물리 복사(copy)**: 커널이 페이지 내용을 수신자가 미리 지정한 버퍼로 복사.
      seL4의 IPC 버퍼와 유사, 단순하고 안전하나 대용량에서 복사 비용 발생.
    - (c) **페이지 이전(move/donate)**: 송신자의 페이지를 수신자 주소공간으로
      옮기고 송신자 매핑은 해제. 복사 없이 큰 데이터를 넘길 수 있으나 송신자가
      이후 그 데이터를 잃는다는 의미론을 유저랜드가 감내해야 함.
    → **미결정 (OPEN-14, 최우선)**
  - 송신자가 지정한 페이지가 아직 커밋/상주하지 않은 경우 페이지 폴트를 누가,
    언제 처리하는지 정의 필요 (OPEN-14에 포함).
  - 전달 크기 제한과 부분 전달 실패 시 규약 필요 (OPEN-14에 포함).
  - IDL 스키마는 초기엔 손으로 작성한 구조체+매크로로 시작하고, 코드 생성 도구화는
    이후 범위로 미룬다.

## ADR-015. IPC 페이지 전달 의미론: 호출별 플래그, 기본값 copy (해결: OPEN-14)

- **상태**: 확정 (2026-09-08)
- **결정**: IPC 시스템 콜에 전달 모드 플래그를 둔다. **기본값은 물리 복사(copy)**이며,
  성능이 중요한 경로(대용량 파일 읽기 등)에서는 호출자가 명시적으로 **move** 또는
  **map**을 선택할 수 있다 (ADR-013의 세 후보를 모두 채택하되 용도별로 구분).
- **근거**: 단일 의미론으로는 "안전한 소량 전달"과 "빠른 대용량 전달"을 동시에
  만족시킬 수 없다. 기본을 가장 안전한 copy로 두어, move/map을 실수로 잘못 써서
  발생하는 미묘한 버그(원본 페이지 재사용, 조기 unmap 등)를 예방한다.
- **영향**:
  - IPC 시스템 콜 ABI에 전달 모드 필드(2~3비트)가 필요하다.
  - **move**: 송신자의 이후 접근은 반드시 실패해야 한다 — 커널이 송신자 매핑을
    확실히 해제해야 한다.
  - **map**: 호출 반환 시점에 커널이 자동 unmap해야 하며, "호출이 끝나기 전까지만
    유효"라는 제약을 유저랜드 계약(스펙 문서)에 명시해야 한다.
  - move/map처럼 강한 부작용이 있는 모드를 아무 프로세스나 쓸 수 있게 할지,
    권한으로 제한할지는 추가 검토 필요. → **미결정 (OPEN-18)**

## ADR-023. 핸들 철회: 개별 프록시 핸들 객체 (해결: OPEN-12)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널 객체를 다른 프로세스에게 위임할 때 원본을 직접 넘기지 않고,
  원본을 가리키는 **프록시 핸들 객체**를 새로 만들어 위임한다. 프록시는
  독립적으로 파괴(철회)할 수 있으며, 프록시를 파괴해도 원본 객체나 다른
  위임에는 영향이 없다.
- **근거**: ADR-011(단순 핸들 테이블)의 단순성을 유지하면서도, POSIX 서버
  분해 구조(ADR-008)에서 흔히 필요한 "클라이언트별 개별 접근 회수"(예: 파일
  close, 연결 종료)를 지원해야 한다.
- **영향**:
  - 프록시 객체도 커널 메모리를 소비하므로 ADR-012/ADR-024 쿼터 대상이다.
  - 프록시의 프록시(위임 체인)를 허용할지, 깊이를 제한할지 결정 필요.
    → **미결정 (OPEN-20)**
  - 원본이 프록시보다 먼저 파괴된 경우 프록시 접근 시의 오류 반환 규약은
    spec 단계에서 정의한다.

## ADR-028. 도네이션 IPC 우선순위: 호출자 우선순위를 서버가 일시 상속 (해결: OPEN-16)

- **상태**: 확정 (2026-09-08)
- **결정**: 동기 호출(Call, ADR-004)이 서버로 실행을 넘길 때, 서버 스레드는
  호출을 처리하는 동안 **호출자의 우선순위(ADR-014의 승격 결과 포함)를
  일시적으로 상속**한다. 응답 후 서버는 자신의 원래 우선순위로 복귀한다.
- **근거**: 서버가 자기 우선순위를 고정 유지하면, 낮은 우선순위 서버가
  높은 우선순위 호출자를 무한정 지연시키는 우선순위 역전이 구조적으로
  발생한다. seL4류 상속 방식이 이를 근본적으로 막는다.
- **영향**:
  - 상속된 우선순위도 ADR-014의 하드 상한(커널 밴드를 절대 넘지 못함)을
    그대로 따른다 — 호출자가 커널 밴드일 수 없으므로 자동으로 만족된다.
  - 서버가 여러 호출을 동시에 처리 중일 때(다중 클라이언트) 어떤 호출자의
    우선순위를 상속할지는 "현재 처리 중인 호출"별로 스레드가 나뉘어 있다면
    자연히 해결되며, 단일 서버 스레드가 여러 호출을 순차 처리하는 경우의
    세부 동작은 스케줄러 구현 시 정의한다.

## ADR-029. IPC move/map 권한 제약: 대상 엔드포인트에 달린 권한 (해결: OPEN-18)

- **상태**: 확정 (2026-09-08)
- **결정**: IPC 엔드포인트(핸들)마다 "move 허용"/"map 허용" 비트를 둘 수
  있다. 이 비트가 없는 엔드포인트로는 move/map 모드 요청이 거부되고 항상
  기본값인 copy로 처리된다. 서버가 자신의 엔드포인트를 특정 클라이언트에게
  위임(ADR-023 프록시)할 때, 그 프록시에만 move/map 비트를 붙여줄 수 있다.
- **근거**: move/map은 대용량 전송에 유용하지만 원본 데이터 유실(move)이나
  일시 매핑(map)이라는 부작용이 있다(ADR-015). 이를 전역 설정이 아니라
  "이 관계(이 서버 ↔ 이 클라이언트)에서는 신뢰하고 쓴다"는 **관계 단위**로
  제한하는 것이, ADR-023에서 이미 확립한 프록시 기반 권한 위임 모델과
  가장 자연스럽게 맞아떨어진다.
- **영향**:
  - IPC 엔드포인트 객체의 메타데이터에 move/map 허용 비트가 추가되어야 한다.
  - 프록시 발급 시 원본 권한의 부분집합만 위임 가능해야 한다(원본에 없는
    move/map 권한을 프록시가 새로 얻을 수 없음) — ADR-023 영향 항목과 연결.

## ADR-032. 프록시 핸들 체인 정책: 순환 금지, 기본 최대 깊이 64(설정 가능) (해결: OPEN-20)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 프록시 핸들(ADR-023)은 다른 프록시를 대상으로 위임할 수 있어 체인을
     이룰 수 있다.
  2. **순환 참조는 항상 금지**된다 — 커널은 새 프록시 생성 시점에 위임
     대상 체인을 검사하여, 자기 자신이나 자신의 상위 체인을 다시 가리키게
     되는 요청을 거부한다.
  3. 체인 깊이(루트 객체로부터의 위임 단계 수)는 **기본값 64**로 제한한다.
  4. 이 상한은 고정 상수가 아니라 **설정 가능한 값**이어야 한다 — 빌드
     타임 기본값(64)은 있지만, 부팅 파라미터 또는 커널 설정 API로
     조정할 수 있어야 한다.
- **근거**: ADR-023에서 프록시 체인을 허용하면서 깊이·순환에 대한 규율이
  없으면 (a) revoke·rights 검사 시 체인을 순회하는 비용이 무한정 커질 수
  있고, (b) 순환이 생기면 순회 로직이 무한 루프에 빠질 위험이 있다. 64는
  실제 위임 체인이 이보다 훨씬 얕을 것이라는 실용적 여유이며, 하드코딩하지
  않고 설정 가능하게 두어 향후 다단계 프록시를 많이 쓰는 서버 구조를
  미리 배제하지 않는다.
- **영향**:
  - 각 프록시 객체는 메타데이터로 최소한 `depth`(루트로부터의 단계 수)를
    가져야 한다. 새 프록시 생성 시 `depth = parent.depth + 1`이며,
    `depth > k_max_proxy_chain_depth`이면 생성 자체가 거부된다.
  - 프록시는 생성 시 부모가 고정되고 이후 재배치(부모 변경)를 지원하지
    않는 한 구조적으로는 순환이 생길 수 없다 — 그럼에도 커널은 생성
    시점에 "새 프록시의 대상이 자기 자신/상위 체인이 될 수 없다"는 검사를
    방어적으로 반드시 수행한다(향후 재배치 기능이 추가될 경우에 대비해
    불변식을 지킨다).
  - `k_max_proxy_chain_depth`의 구체적 설정 경로(커널 커맨드라인 인자 vs
    커널 설정 syscall vs 빌드 타임 오버라이드)는 구현 시 결정한다.
    기본값은 64.
  - `docs/spec/ipc.md`의 "아직 정하지 않은 것"에 있던 잠정 서술(OPEN-20)을
    이 결정으로 교체한다.

## ADR-151. IPC를 실제 서로 다른 유저 프로세스 사이에서 쓸 수 있게 확장 — 메시지 구조체 cross-address-space 전달 + `sys_reply`의 `handles[]` 지원 + `sys_recv`/`sys_reply` syscall 노출

- **상태**: 확정 (2026-09-09)
- **결정**:
  1. `kernel/core/ipc/endpoint.cpp`의 `deliver_message()`가 이제
     `message` 구조체 자체(label/regs/page_count/handle_count)를
     "그 메시지가 있는 스레드의 `owner_space`"로 번역해서 읽고
     쓴다 — 커널 스레드(owner_space==nullptr)면 기존처럼 직접
     포인터 역참조, 유저 스레드면 그 주소공간의 페이지테이블로
     vaddr을 물리 프레임으로 번역한 뒤 `mm::phys_to_virt`로 커널이
     접근 가능한 포인터를 얻는다. 이 번역 자체는
     `kernel/core`(ADR-002, arch 헤더 미포함)가 직접 하지 않고,
     `kernel-scheduler.md`의 `arch_context_switch` 등과 같은 패턴
     (extern "C" 훅, core가 선언만, arch(x86_64)가 정의)인
     `arch_translate_user_page(page_table_root, vaddr, &out_phys)`를
     통해서 한다.
  2. `sys_reply`가 이제 `handles[]`도 옮긴다 — 그래서 시그니처에
     `handle_table&`가 추가되고, 반환형이 `void`에서
     `result<void, ipc_error>`로 바뀐다(여전히 블록하지 않는다 —
     전달이 실패해도 caller를 그대로 깨운다).
  3. `sys_recv`/`sys_reply`를 유저모드 syscall로 새로 노출한다
     (`uapi::k_syscall_ipc_recv`=6, `k_syscall_ipc_reply`=7) — M8~M12는
     `sys_call`(클라이언트 전용)만 유저모드에 노출돼 있었고, 실제로
     IPC를 **받아 응답하는** 서버 역할은 전부 커널 스레드였다(M6~M8
     데모). M13부터 vfs/memfs 같은 진짜 유저 프로세스 서버가 생기므로
     이 노출이 필요해졌다.
- **근거**: M6~M12는 IPC의 두 상대가 항상 같은 주소공간(커널 컨텍스트,
  물리메모리 전체가 higher-half로 공유됨)이었거나 한쪽이 커널
  스레드였다 — 그래서 `message*` 포인터를 그냥 커널이 이미
  역참조 가능한 값으로 다뤄도 문제가 없었다. M13(system-servers-bringup.md)
  이 처음으로 진짜 서로 다른 유저 프로세스(procsrv/vfs/memfs) 사이의
  IPC를 요구하면서, 그 가정이 실제로 깨지는 걸 설계 중에 발견했다 —
  고치지 않으면 서버 스레드의 `recv_dest`/호출자의 `reply_dest`에
  전혀 다른 주소공간의 포인터로 직접 쓰기를 시도해 크래시하거나
  조용히 남의 메모리를 덮어쓴다. `sys_reply`의 `handles[]` 확장은
  ADR-018(filesystem.md, "VFS가 open() 응답에서 FS 서버 핸들을
  위임")이 요구하는 방향이 정확히 **reply**(서버→클라이언트)라서
  불가피했다 — 기존 시그니처(`endpoint.hpp` "알려진 단순화")는 이
  방향을 원천적으로 막고 있었다.
- **영향**:
  - `kernel/core/ipc/endpoint.cpp`에 `copy_from_user`/`copy_to_user`
    (내부 헬퍼, page 경계를 넘는 범위는 페이지 단위로 나눠 처리)와
    `table_for_thread`(커널 스레드는 기존 공유 handle_table로
    폴백, 실제 유저 스레드는 자신의 handle_table) 추가.
    `kernel/arch/x86_64/page_table.cpp`에 `arch_translate_user_page`
    정의(기존 `query_page()`를 그대로 감쌈).
  - **남은 단순화**: `pages[]`가 가리키는 실제 데이터 버퍼(설명 자체가
    아니라 그 내용)는 여전히 같은 주소공간 전제로만 안전하다 — M13은
    이 경로를 아예 쓰지 않는다(전부 32바이트 이하 값을 regs[]로만
    주고받는다, [fs-protocol.md](../spec/fs-protocol.md) 참고). 실제로
    필요해지면(파일 내용이 32바이트를 넘는 경우 등) 이 부분도 같은
    방식(주소공간별 페이지 번역)으로 재검토해야 한다 — 신규
    **미결정 (OPEN-59)**.
  - `docs/spec/ipc.md` §3/§3.1을 이 결정에 맞춰 갱신했다(`sys_reply`의
    새 시그니처/반환형, cross-address-space 번역 설명).
  - `kernel_main.cpp`의 M6~M8 커널 스레드 IPC 데모(`ipc::sys_reply`
    호출 3곳)는 새 시그니처(`handle_table&` 추가)로만 맞추고 동작은
    그대로다(50개/51개 스모크 테스트 전체 회귀 없음, QEMU 재검증).

## ADR-155. `pages[]` 페이로드의 cross-address-space 전달: 수신자 종류로 나뉘는 두 경로 — copy(번역) vs map(공유 매핑) (해결: OPEN-59)

- **상태**: 확정 (2026-09-09) — **설계만 확정, 구현은 착수 전**(아래
  §실행 계획 참고).
- **결정**: ADR-151이 메시지 **구조체 자체**(label/regs/page_count/
  handle_count)만 cross-address-space로 옮기도록 고쳤을 때 남겨 둔
  "`pages[]`가 가리키는 실제 데이터 버퍼 내용"의 전달 방식을, 수신자의
  종류에 따라 **두 경로**로 확정한다 — 둘 다 여전히 `ipc.md`의
  `transfer_mode::copy`(현재 유일하게 구현된 모드) 의미론 **안**에서
  다르게 구현되는 것이지, `move`/`map`(ADR-015가 이미 미래 계획으로
  둔, `CAN_MOVE`/`CAN_MAP` 권한이 필요한 별도 모드) 자체를 지금 앞당겨
  구현하는 게 아니다.
  1. **수신자가 커널 자신이거나 커널이 직접 구동하는 스레드**
     (`owner_space == nullptr`, 지금의 M6~M8 데모류)면: ADR-151이
     메시지 헤더에 이미 구현한 것과 정확히 같은 방식 — 발신자 쪽
     페이지를 발신자의 `owner_space`(=raw 주소 + "source pid" 역할)
     로 번역해 읽고, 수신자 쪽 목적지에 그대로 써 넣는다(`copy_from_user`/
     `copy_to_user`를 페이지 배열까지 그대로 확장). 커널 컨텍스트는
     이미 최고 신뢰 수준이라 이 이상의 장치가 필요 없다.
  2. **수신자가 실제 유저 프로세스**(`owner_space != nullptr`)면:
     커널이 발신자 쪽 프레임의 참조 카운트를 올리고(`mm::frame_add_ref`,
     ADR-140이 이미 COW용으로 확립한 것과 같은 카운터) 그 프레임을
     **수신자의 주소공간에도 읽기전용으로 매핑**한다 — 수신자
     프로세스에게는 "다른 프로세스의 vaddr을 번역해 달라"는 API를
     전혀 노출하지 않는다. 매핑이 끝나면 수신자는 자신의 로컬
     가상주소(커널이 `msg_out.pages[i].vaddr`에 실제로 매핑한 값을
     써서 돌려준다)로 평범한 load만으로 그 내용을 본다 — CPU MMU가
     나머지를 알아서 한다.
  3. 두 경로 모두 **여전히 copy 의미론**을 지킨다 — 수신자가 그
     내용을 다 읽고 난 뒤에는(§4에서 정할 명시적 해제 시점) 매핑을
     해제하고 `frame_release`한다. 발신자가 그 사이 자신의 원본
     버퍼를 다시 쓰면 수신자에게도 그 변경이 그대로 보인다는
     차이는 있다(진짜 바이트 복사가 아니므로) — **알려진 제약**으로
     남긴다: 이 경로를 쓰는 발신자는 "전달 후 재사용하지 않는
     일회성 버퍼"라는 전제를 지켜야 한다(이미 M7부터의 기존
     copy-mode 전제와 같다 — 발신자가 이후 그 버퍼를 재사용해도
     되는지는 애초에 스펙이 보장한 적이 없다).
  4. 매핑을 **언제 해제하는지**(수신자가 다음 IPC를 받을 때? 명시적
     `sys_ipc_unmap` 호출? 프로세스 종료 시 일괄?)는 이 ADR의 범위
     밖이다 → 신규 **미결정 (OPEN-61)**. 수신자 주소공간에서 그
     매핑을 배치할 정확한 위치(고정 슬롯 vs 수신자가 `msg_out.pages[i].vaddr`
     로 미리 지정한 자리를 "매핑해 달라"는 요청으로 재해석)도 실제
     구현 시점에 정한다 — `message.hpp`의 기존 방향 규약(수신자가
     미리 목적지를 채워 둔다)과 자연스럽게 이어질 것으로 보이지만
     확정은 아니다.
- **근거**: docs-dashboard "답변 입력"으로 받은 방향 제안(2026-09-09,
  이후 docs/reply.md에서 삭제·open-items.md에 흡수)을 그대로
  구체화했다 — "수신자가 유저랜드면 주소 번역 관련 호출을 노출하지
  않는 쪽이, 수신자가 커널/커널서버면 raw+source pid 쪽이 맞다"는
  지적이 핵심이다. 유저 프로세스에게 매번 번역을 요구하는 대신 한
  번 매핑해 두면, 그 이후의 모든 접근이 평범한 메모리 접근이 되어
  **매 접근마다 커널을 거칠 필요가 없다**(성능·단순성 모두 이득) —
  반면 커널(서버) 코드는 원래도 매 호출마다 커널 컨텍스트에서 도는
  것이므로 매핑을 따로 관리하는 비용을 들일 이유가 없다.
- **실행 계획**: 이 ADR도 설계만 확정한다. §1(커널/커널스레드 수신자용
  번역 확장)은 구현 비용이 작고 회귀 위험도 낮아
  [system-servers-bringup.md](../plan/system-servers-bringup.md)
  §M14 착수 시점에 먼저 넣는다. §2(유저 프로세스 수신자용 매핑
  경로)는 OPEN-61(해제 시점)이 먼저 정해져야 실제 구현이 가능하므로,
  memfs/vfs 등이 실제로 32바이트를 넘는 파일 내용을 주고받아야 하는
  시점(M16 FAT32/ext4 도입 전후로 예상)에 별도로 진행한다 —
  M13의 fs-protocol.md(regs[]만 사용하는 임시 인코딩)를 이 경로로
  교체하는 것이 그 작업의 목표가 된다.
- **영향**: `kernel/core/ipc/endpoint.cpp::deliver_message()`의 pages[]
  처리 루프를 수신자 종류로 분기시켜야 한다. §2는 `mm::frame_add_ref`/
  `frame_release`(kernel-memory.md ADR-140)와 `map_page`/`unmap_page`
  (arch_x86_64, page_table.hpp)를 그대로 재사용할 수 있어 새 저수준
  프리미티브는 필요 없다 — 조합하는 코드만 새로 필요하다.

## ADR-159. ADR-155 §2의 배치 위치 + 해제 시점 확정 — 스레드별 고정 IPC 매핑 슬롯 + "다음 sys_recv 직전 자동 해제" (해결: OPEN-61)

- **상태**: 확정 (2026-09-09) — **구현 완료(M16, 2026-09-09)**. §2의
  해제 트리거("다음 sys_recv 직전")는 구현 중 좁은 표현으로 밝혀져
  ADR-161이 정정했다 — 이 문서 §2는 원래 의도(설계 방향)를 보여주는
  기록으로 남기고, 실제 트리거 조건은 ADR-161을 따른다.
- **결정**:
  1. **배치 위치**: 유저 가상주소공간을 두 구역으로 나눈다 —
     (a) **일반 유저 영역** `[0, k_user_stack_top)`(지금 코드의
     `k_user_stack_top = 0x0000700000000000`, `process_ops.cpp`/
     `kernel_main.cpp` — ELF 코드/데이터, 힙, 스택이 전부 이 아래
     쪽에 있다. 스택은 이 주소에서 아래로 자란다), (b) **커널 지원
     고정 슬롯 구역** `[k_user_stack_top, ...)` — `argv`/`self_info`
     브릿지(M12)/`sys_alloc_dma_buffer`(ADR-148)/`sys_map_phys`
     (ADR-156)가 이미 이 구역에 각자의 고정 슬롯(`k_argv_user_vaddr`
     `...0x2000`, `k_dma_buffer_user_vaddr` `...0x200000`,
     `k_mmio_user_vaddr` `...0x300000`)을 두고 있다. 이 ADR은 그
     사다리의 다음 자리에 새 슬롯 `k_ipc_mapped_pages_user_vaddr =
     0x0000700000400000`를 추가한다 — 크기는 `uapi::
     k_max_page_descriptors`(4)페이지(`0x4000`바이트)로, 메시지가
     실을 수 있는 `pages[]`의 최대 개수를 그대로 반영한다.
  2. **해제 시점**: 수신 스레드가 **다음 `sys_recv`를 호출해 새
     메시지를 배달받기 직전**, 커널이 그 스레드가 이전에 갖고 있던
     IPC 매핑(있다면)을 먼저 `unmap_page`+`frame_release`한다 —
     "그 IPC 호출이 끝났다"를 "이 스레드가 그 메시지를 다 처리하고
     다음 것을 받으러 왔다"로 정의한다. Call/Reply 패턴이면
     `sys_reply`가 먼저 오지만 그 자체로 매핑을 해제하지는
     않는다(회신 데이터를 구성하는 동안에도 여전히 읽을 수 있어야
     하므로) — 실제 해제는 그 스레드가 스스로 다음 `sys_recv`를
     호출하는 순간까지 미룬다. 별도의 `sys_ipc_unmap`류 명시적
     해제 syscall은 만들지 않는다(ADR-155가 이미 정한 "수신자에게
     번역/관리 API를 노출하지 않는다" 원칙과 일치) — 유저 코드는
     아무것도 몰라도 된다.
  3. 슬롯은 **스레드 하나당 하나**(프로세스 전체 공유가 아니다) —
     `object::thread`에 "지금 이 슬롯에 매핑돼 있는 프레임들"의
     기록(프레임 물리주소 배열 + 개수, 최대 4개)을 추가해 위 §2의
     해제 시점에 그 기록을 그대로 읽어 해제한다. 슬롯의 **가상주소
     자체**는 스레드마다 다시 계산하지 않고 프로세스의 고정 슬롯
     (§1)을 그대로 재사용한다 — 즉 **한 프로세스 안에서 동시에
     `sys_recv`로 매핑을 받는 스레드가 둘 이상이면 충돌한다**(뒤에
     오는 스레드의 매핑이 앞 스레드의 슬롯을 덮어씀). 지금까지
     구현된 모든 서버(procsrv/vfs/memfs/devmgr 등)가 예외 없이
     "메인 루프 하나가 순차적으로 `sys_recv`→처리→`sys_reply`를
     반복"하는 단일 스레드 구조라 실제로 부딪히는 경우가 없다 —
     여러 스레드가 동시에 같은 엔드포인트에서 받는 서버가 실제로
     필요해지면(YAGNI) 슬롯을 스레드 로컬 인덱스로 나누는 확장이
     필요하다는 **알려진 제약**으로 남긴다.
  4. 프로세스가 다음 `sys_recv` 없이 그냥 종료되는 경우(크래시,
     정상 종료)는 별도 처리가 필요 없다 — 주소공간 전체 파괴 경로가
     그 페이지테이블 엔트리와 프레임 참조를 이미 정리한다(§2가 정한
     "명시적으로 다음 recv 전에 해제"는 **정상 경로의 최적** 시점일
     뿐, 종료 시 안전망은 기존 프로세스 정리 경로가 이미 보장한다).
- **근거**: docs-dashboard "답변 입력"으로 받은 방향 제안(2026-09-09,
  이후 docs/reply.md에서 삭제·여기 흡수)을 그대로 구체화했다 — "가상
  주소 세그멘테이션으로 일반 유저 영역과 IPC용 영역을 나눈다"는
  지적은 이미 코드에 존재하던 `k_user_stack_top` 경계(스택 위쪽은
  커널 지원 슬롯 전용, ADR-148/156이 이미 그렇게 쓰고 있었다)를 공식
  설계로 인정하고 그 사다리에 IPC 슬롯을 추가하는 것으로 구체화했다
  — 답변이 예시로 든 "512G"라는 구체적 경계값은 그대로 채용하지
  않았다(사용자가 "예시값"이라고 명시했고, 기존 고정 슬롯들이 이미
  훨씬 위쪽 `0x0000700000000000`대에 자리 잡고 있어 그 값을 그대로
  쓰면 기존 배치와 충돌하거나 재작업이 필요해진다 — 세그멘테이션
  이라는 **방향**은 그대로 따르되 **경계값**은 이미 검증된 기존
  상수를 재사용해 회귀 위험을 없앴다). "IPC 호출이 끝난 뒤 바로
  반납해야 한다"는 지적은 "다음 recv 직전 자동 해제"로 구체화했다
  — "바로"를 "그 메시지를 다 쓰기 전에 회수"가 아니라 "그 메시지
  처리 주기가 끝나는 자연스러운 다음 경계(다음 recv)에서 지체 없이"
  로 해석했다(회신을 구성하는 도중에도 매핑이 살아 있어야 하므로
  `sys_reply` 시점 즉시 해제는 불가능하다).
- **실행 계획**: 이 ADR도 설계만 확정한다. 실제 구현은
  [system-servers-bringup.md](../plan/system-servers-bringup.md)
  §M16(FAT32+ext4) 착수 시점, ADR-155 §2 구현과 함께 진행한다 —
  M16이 이 경로의 첫 실제 소비자(fs-protocol.md의 32/16바이트
  `regs[]` 임시 인코딩을 이 경로로 교체)다.
- **영향**: `kernel/arch/x86_64/process_ops.cpp`에 `k_ipc_mapped_pages_user_vaddr`
  상수 추가(기존 `k_dma_buffer_user_vaddr`/`k_mmio_user_vaddr` 사다리
  연장). `kernel/core/object/kernel_objects.hpp::thread`에 "현재
  매핑 중인 프레임" 기록 필드 추가(최대 4개). `kernel/core/ipc/
  endpoint.cpp`의 `sys_recv` 경로 — 새 메시지 배달 **직전**에 그
  스레드의 이전 매핑 해제 호출 삽입. `docs/spec/fs-protocol.md`가
  이 경로의 첫 실제 소비자로 M16에서 함께 갱신된다.

## ADR-161. ADR-159 §2/§3 구현 완료 — 해제 트리거를 "다음 sys_recv"에서 "다음 deliver_message 목적지 선택 시점"으로 정정, §1 경로는 여전히 미사용

- **상태**: 확정 (2026-09-09), M16 구현과 함께 반영.
- **결정**:
  1. **해제 트리거 정정**: ADR-159 §2가 "다음 `sys_recv` 직전"이라고
     특정한 표현은 구현 중 좁았던 것으로 드러났다 — `deliver_message`
     (`kernel/core/ipc/endpoint.cpp`)의 목적지는 `sys_recv`뿐 아니라
     `sys_call`(서버가 이미 대기 중이면 즉시 핸드오프, dst=서버)과
     `sys_reply`(dst=caller, **회신으로 매핑을 받는 경우** — M16의
     실제 사용 패턴, 예: procsrv가 vfs/fat32/ext4에 `sys_call`로
     읽기를 요청하고 그 **응답**으로 파일 내용 매핑을 받는다)에서도
     일어난다. 순수 클라이언트(서버 루프가 아닌 스레드)는 다음
     `sys_recv`를 영원히 부르지 않을 수 있어, "다음 recv 직전"으로는
     이런 스레드의 매핑이 절대 해제되지 않는다. 그래서 트리거를
     **"이 스레드가 `deliver_message`의 목적지(dst_thread)로 다시
     선택되는 시점 직전"**으로 일반화한다 — `sys_call`/`sys_recv`/
     `sys_reply` 세 진입점 전부가 여기 해당한다. "그 IPC 호출이
     끝났다"의 정의를 "이 스레드가 그 매핑을 쓸 차례가 끝나고 다시
     무언가를 받을 차례가 됐다"로 넓힌 것일 뿐, ADR-159의 핵심 결정
     (명시적 unmap syscall 없음, 자동 해제, 스레드당 하나의 고정
     슬롯)은 전혀 바뀌지 않았다.
  2. **§1 경로(커널/커널스레드 수신자용 pages[] 번역 확장)는 여전히
     구현하지 않는다** — 구현 도중 확인한 사실: M6~M9의 기존
     커널스레드 IPC 데모는 양쪽 다 `owner_space==nullptr`이라
     `deliver_message`의 기존 원시 포인터 복사가 이미 정확히
     들어맞는다(번역이 곧 항등 함수이므로). M16이 실제로 필요로 한
     조합은 §2(발신자·수신자 모두 실제 유저 프로세스)뿐이었다 —
     "발신자가 커널스레드, 수신자가 실제 유저 프로세스"처럼 아직
     아무도 쓰지 않는 조합은 만들지 않는다(YAGNI, ADR-131 §근거와
     같은 절제) — 이 조합은 `deliver_message`에서 명시적으로
     `permission_denied`를 반환한다.
  3. §2의 매핑은 **디스크립터당 정확히 1페이지**만 지원한다(ADR-159가
     "슬롯 예산 4페이지"라고만 말하고 디스크립터 대 페이지 배분을
     정하지 않았던 것을 이렇게 좁혔다) — `message.page_count`(최대 4)
     가 곧 그대로 전달 가능한 총 페이지 수가 된다. 4096바이트를
     넘는 파일은 이 경로 하나로 옮길 수 없다(fs-protocol.md v2 §4가
     명시하는 알려진 제약 — 여러 번의 `OP_READ`로 나눠 받는
     오프셋/seek 프로토콜은 범위 밖).
- **근거**: 설계(ADR-159)와 실제 구현 사이의 간극은 M16이 fs-protocol
  v2의 `OP_READ`를 이 경로로 옮기면서 처음으로 드러났다 — vfs/fat32/
  ext4에게 파일을 요청하는 클라이언트(procsrv)는 서버 루프가 아니라
  "필요할 때 한 번 부르고 마는" 호출자이므로, ADR-159가 가정한
  "서버가 다음 recv를 곧 다시 부른다"는 전제가 맞지 않는 첫 실제
  사례였다.
- **영향**: `kernel/core/ipc/endpoint.cpp::release_previous_ipc_mapping()`
  이 `deliver_message`의 §2 분기 진입 직후(새 매핑을 쓰기 전, 메시지에
  `page_count==0`이라도) 호출된다 — `sys_call`/`sys_recv`/`sys_reply`
  세 호출부 전부가 이제 dst를 `object::thread*`로 넘긴다(이전엔
  `object::address_space*`). `kernel/arch/x86_64/page_table.cpp`에
  `arch_map_ipc_page_readonly`/`arch_unmap_ipc_page` 두 훅 신설(
  `arch_translate_user_page`와 같은 패턴). 실측(QEMU): fs-protocol.md
  v2의 `OP_READ` 응답이 procsrv→memfs(M13 회귀 확인)/vfs→fat32/
  vfs→ext4 세 조합 모두에서 정확한 내용을 전달함을 확인했다(M16
  검증 결과, docs/done/system-servers-bringup-m16.md 참고).

## ADR-216. `thread::ipc.reply_target`을 스택으로 확장 — 서버 스레드의 재진입(nested) IPC 왕복 지원

- **상태**: 확정 (2026-09-10), user-service-manager.md §M42 구현 중
  발견한 진짜 교착을 고치며 반영.
- **문제**: `sys_reply`는 §3이 정한 대로 "가장 최근 `sys_recv`로 받은
  호출에 응답"하며, 이 대상은 스레드당 필드 하나(`ipc.reply_target`)
  뿐이다. 지금까지(M6~M41)는 어느 서버 스레드도 "아직 회신하지 않은
  호출을 들고 있는 채로 스스로 클라이언트가 되어 또 다른 `sys_call`/
  `sys_recv`+`sys_reply` 왕복을 하는" 경우가 없어 이 단일 슬롯으로
  충분했다. M42의 `servers/svcmgr`가 처음으로 이 패턴을 요구했다 —
  컨트롤 클라이언트(svcmgr-ctl-test)의 `op_start` 호출을 처리하는
  `handle_start`가, 아직 그 호출에 회신하지 않은 채로
  `spawn_unit_and_wait_ready()`(자식 프로세스를 spawn하고 ADR-193의
  준비완료 신호를 그 자식의 전용 endpoint에서 `sys_recv`+`sys_reply`
  로 직접 받는다)를 불렀다. 이 안쪽 `sys_recv`가 같은 스레드의
  `ipc.reply_target`을 (바깥쪽 호출자인 ctl-test에서) 자식 스레드로
  덮어썼고, 안쪽 `sys_reply`가 그 슬롯을 `nullptr`로 비웠다 — 바깥쪽
  루프가 나중에 `sys_reply`를 불렀을 때는 "대응하는 sys_recv가
  없다"(§3의 무동작 규칙)에 걸려 조용히 아무 일도 하지 않았다.
  ctl-test는 응답을 영원히 받지 못해 블록된 채 남았고, svcmgr는
  다음 `sys_recv`에서 새 메시지를 기다리며 겉보기엔 멈춘 적이 없는
  것처럼 보였다 — 진짜 교착이었다. 실행 중 임시 디버그 로그로
  안쪽 spawn+wait_ready 왕복 자체는 매번 정상 완료됨을 먼저 확인한
  뒤에야, 문제가 그 왕복이 끝난 **뒤** 바깥쪽 회신이 사라지는
  지점에 있음을 좁혀 찾았다.
- **결정**:
  1. `ipc_state`에 스레드당 `reply_target` 하나 대신, 그 값을
     덮어쓰기 직전 상태로 보존하는 고정 크기 스택
     (`reply_target_saved[4]`+`reply_target_saved_count`)을 추가한다.
     `kernel/core/ipc/endpoint.cpp`의 `push_reply_target(t, new_target)`
     이 `t.ipc.reply_target`이 이미 `nullptr`이 아니면 그 값을
     스택에 밀어 넣은 뒤 새 값으로 덮어쓴다 — `sys_call`(§5 1단계,
     이미 대기 중인 서버에게 즉시 핸드오프)과 `sys_recv`(이미 대기
     중인 호출자와 즉시 페어링)의 두 "회신 대상 확정" 지점 모두
     이 헬퍼를 거친다. `pop_reply_target(t)`는 `sys_reply`가 회신을
     전달한 뒤 `nullptr`로 지우는 대신 불러 스택이 비어 있지 않으면
     그 이전 값을 되돌린다.
  2. 깊이 상한은 4로 둔다 — 기존 `MC_MAX_SPAWN_INHERITED_HANDLES`류
     상수들과 같은 임의의 작은 여유(YAGNI, 지금 실제로 필요한 깊이는
     1뿐이다: 바깥쪽 클라이언트 호출 + 안쪽 자식-준비완료 왕복).
     초과분은(설계상 상정하지 않은 깊이의 재귀) 가장 오래된 값을
     버린다 — 그 호출은 다시는 회신받지 못하지만, 패닉으로 커널
     전체를 멈추기보다는 낫다고 판단했다.
  3. `docs/spec/ipc.md` §3의 "가장 최근 `sys_recv`로 받은 호출에
     응답"이라는 문구는 여전히 맞다 — 이 ADR은 그 규칙을 어기지
     않는다(`sys_reply`는 지금도 정확히 "가장 최근" 대상에게
     회신한다). 다만 "가장 최근"이 이제 **재진입 스택**으로
     관리된다는 점, 그리고 서버 스레드가 아직 회신하지 않은 호출을
     들고 재진입 왕복을 해도 바깥쪽 호출의 회신 대상이 더 이상
     사라지지 않는다는 점을 스펙에 명시했다.
- **관련해서 발견한 별개 버그(새 ADR 불필요, 기존 ADR-161 규칙
  위반)**: 위 수정 후 `op_start`는 통과했지만 `op_register`에서
  진짜 페이지폴트가 새로 드러났다. `servers/svcmgr::handle_register`
  가 수신 메시지의 IPC 매핑 슬롯(`in.pages[0].vaddr`)을 가리키는
  원시 포인터(`unit`)를 nested `mc_reg_set_binary()` 호출(cfgsrv에게
  `sys_call`로 등록을 요청) **뒤까지** 들고 있다가
  `alloc_runtime(unit->name)`에서 다시 읽었다 — 그 nested 호출이
  cfgsrv의 응답을 받는 순간 이 스레드가 다시 `deliver_message`의
  목적지가 되어(ADR-161의 `release_previous_ipc_mapping`) 그 매핑이
  이미 해제된 뒤였다. 이건 커널 설계의 간극이 아니라 ADR-161이
  이미 명시한 "이 스레드가 다시 배달 목적지가 되는 시점"이라는
  규칙을 svcmgr 쪽 코드가 어긴 것이다 — `mc/cfgsrv_client.c`가
  `mc_reg_set_binary`/`mc_reg_open_or_create` 등에서 이미 지키고
  있는 관례(nested 호출 전에 값을 자기 정적 버퍼로 복사)를 그대로
  따라, 수신 즉시 `mc_svcmgr_service_unit` 구조체 전체를 로컬
  변수로 복사하도록 고쳤다.
- **근거**: M27~M41의 `spawn_unit_and_wait_ready`류 준비완료 대기는
  전부 서버의 메인 IPC 루프가 시작되기 **전**(부팅 시퀀스)에서만
  불렸다 — 그 시점엔 애초에 회신할 바깥쪽 호출이 없어 이 경합이
  드러날 수 없었다. M42가 그 함수를 살아있는 컨트롤 호출 처리
  도중 처음으로 재진입 호출한 첫 소비자였고, 이 프로젝트가 반복해
  겪은 "X가 Y의 첫 실제 소비자가 나타나기 전까지는 멀쩡했다" 패턴의
  가장 최근 사례다.
- **영향**: `kernel/core/object/kernel_objects.hpp::ipc_state`에
  `k_max_reply_nesting`(=4)/`reply_target_saved[4]`/
  `reply_target_saved_count` 추가. `kernel/core/ipc/endpoint.cpp`에
  `push_reply_target`/`pop_reply_target` 신설, `sys_call`/`sys_recv`의
  두 `reply_target =` 대입을 `push_reply_target`으로, `sys_reply`의
  `reply_target = nullptr`를 `reply_target = pop_reply_target(*self)`
  로 교체. `servers/svcmgr/main.cpp::handle_register`가 수신 페이지를
  즉시 로컬 복사. 실측(QEMU): `svcmgr-ctl-test`의 status→stop→
  status→start→status→register→cfgsrv 직접 확인 7단계 전부 통과
  (docs/done/user-service-manager-m42.md 참고).
