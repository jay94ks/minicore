## ADR-012. 커널 메모리 할당 정책: 슬랩/페이지 할당자 + 프로세스별 쿼터 (해결: OPEN-4)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널이 자체 물리 페이지 할당자(buddy/bitmap 등)와 커널 객체용 슬랩
  할당자를 갖는 전통적 방식을 사용한다. 각 프로세스/서버에는 메모리 쿼터가 부여되어
  폭주를 방지한다.
- **근거**: Untyped+retype(seL4식)은 원칙적으로 우수하지만, ADR-008의 다중 POSIX
  서버 구조를 유저랜드에서 전부 관리하게 하면 초기 구현 부담이 지나치게 커진다.
  전통적 할당자가 구현 속도·실용성 면에서 이 프로젝트(범용 OS 지향, ADR-001)에 더 맞는다.
- **영향**:
  - 커널 메모리 부족(OOM) 시 정책(어느 쿼터를 우선 거부할지, 커널 자체 할당은
    절대 실패해선 안 되는 예약 영역을 둘지)이 필요. → **미결정 (OPEN-13)**
  - 쿼터 초과는 시스템 콜의 `result` 실패로 반환한다 (ADR-010과 일치).
  - 부모→자식 쿼터 위임/재분배 지원 여부도 OPEN-13에서 함께 정한다.

## ADR-016. fork 구현: 커널 네이티브 COW + 프로세스 서버의 fd 복제 조율 (해결: OPEN-10)

- **상태**: 확정 (2026-09-08)
- **결정**: 주소공간 복제(Copy-on-Write)는 **커널이 직접** 수행한다 (페이지테이블
  복제, 쓰기 폴트 시 페이지 프레임 분리, 참조 카운트 관리). 열린 fd 목록의 복제는
  **프로세스 서버**가 조율한다 — 부모의 fd 테이블을 순회하며 각 fd가 속한 서버
  (FS/네트워크 등)에 "핸들 복제"를 요청한다.
- **근거**: 순수 유저 pager 위임 방식은 매 쓰기 폴트마다 IPC 왕복이 발생해
  범용 OS 워크로드(ADR-001)에는 비용이 너무 크다. 반면 fd 복제는 본질적으로
  여러 서버에 걸친 조율 작업이라 ADR-008(서버 분해) 구조상 프로세스 서버의 몫이다.
- **영향**:
  - 커널은 주소공간 객체에 "COW 복제"와 "쓰기 폴트 시 프레임 분리" 오퍼레이션을
    구현해야 하며, 페이지 프레임 참조 카운트가 ADR-012 메모리 할당자에 통합되어야 한다.
  - `fork()`의 실제 흐름: ① 유저(libc)가 프로세스 서버에 fork 요청 → ② 프로세스
    서버가 커널에 새 프로세스 + 주소공간 COW 복제를 요청 → ③ 프로세스 서버가
    부모 fd 테이블을 순회하며 각 서버에 "핸들 복제" IPC 전송 → ④ 완료 후 자식 실행 시작.
  - 모든 FS/네트워크 서버는 "핸들 복제" 프로토콜을 구현해야 한다 (OPEN-11/ADR-018과 연동).

## ADR-024. 메모리 쿼터: 중앙 정책 서버의 동적 재분배 (해결: OPEN-13)

- **상태**: 확정 (2026-09-08)
- **결정**: 정책 서버(또는 프로세스 서버 하위 기능)가 시스템 전체 메모리
  현황을 파악하고, 프로세스별 쿼터 증감 요청을 그때그때 승인·거부한다.
  fork/exec 시 자식의 초기 쿼터도 정책 서버를 거쳐 결정된다.
- **근거**: 고정 쿼터는 fork 직후 메모리 부족을 흔히 유발하고, 부모→자식
  고정 분할은 장기 실행 시스템에서 경직된다. 범용 OS 지향(ADR-001)에는
  동적 재분배가 실질적으로 필요하다.
- **영향**:
  - 정책 서버는 시스템의 새로운 신뢰 경계가 된다 — 커널 메모리 할당자
    (ADR-012)는 정책 서버만 가진 특수 권한 없이는 어떤 프로세스의 쿼터
    상한도 늘릴 수 없도록 커널 API 수준에서 강제해야 한다.
  - 정책 서버 다운 시 쿼터 조정이 멈춘다 — 장애 시 폴백 정책(마지막
    승인값 유지 등) 필요. → **미결정 (OPEN-21)**
  - "물리 메모리 자체 고갈(OOM)"과 "정책상의 쿼터 초과"는 서로 다른
    실패로 구분해 반환해야 한다.

## ADR-033. 커널 락 모델: 락-프리 + per-CPU 구조 우선

- **상태**: 확정 (2026-09-08)
- **결정**: 커널 내부 자료구조는 최대한 CPU별(local) 자료구조로 설계하고,
  공유가 불가피한 경우에만 최소 범위의 스핀락을 사용한다. 전역 Big
  Kernel Lock은 두지 않는다.
- **근거**: 범용 OS 지향(ADR-001)과 다중 코어 확장성을 우선한다. Big
  Kernel Lock에서 세분화 락으로 나중에 리팩터링하는 비용은 처음부터
  per-CPU로 설계하는 비용보다 훨씬 크다 — 자료구조가 "코어가 하나"라는
  가정을 곳곳에 깔고 있으면 나중에 뜯어고치기 매우 어렵다.
- **영향**:
  - `kernel/core/mm`: per-CPU 로컬 프리 리스트 + NUMA 노드별 전역 풀
    (ADR-036과 결합) — 로컬이 고갈되면 같은 노드의 전역 풀에서 보충한다.
  - `kernel/core/sched`: 노드별 런큐(ADR-034)에 노드 단위 스핀락 하나만
    사용 — 코어별 세분화는 v1 범위가 아니다.
  - `kernel/core/ipc`: 엔드포인트 대기열은 여러 코어의 스레드가 동시에
    접근하므로 엔드포인트당 스핀락이 필요하다 — "완전 락-프리"가 아니라
    "필요한 곳만 최소 범위 락"이 이 ADR의 실제 원칙이다.
  - 프로세스별 핸들 테이블(ADR-011)은 다중 스레드 프로세스에서 동시
    접근될 수 있어 프로세스당 스핀락 하나가 필요하다.
  - 락 순서(lock ordering) 규칙과 교착상태 방지 정책은 아직 없다.
    → **미결정 (OPEN-23)**

## ADR-036. NUMA 인지 범위: 메모리 할당자 + 스케줄러 모두

- **상태**: 확정 (2026-09-08)
- **결정**: 물리 메모리 할당자와 스케줄러 양쪽 모두 NUMA 토폴로지를
  인지한다. 페이지 할당은 요청자의 선호 노드에 따라 노드별 풀에서
  이뤄지고, 스레드는 가능한 한 자신이 메모리를 할당받은 노드의 코어에서
  실행되도록 스케줄링된다(ADR-034의 노드별 런큐와 결합).
- **근거**: 메모리 할당자만 NUMA를 인지하고 스케줄러가 무시하면(또는
  반대) 지역성 이득의 절반만 얻는다 — 메모리는 노드 0에 할당됐는데
  스레드가 노드 1 코어에서 실행되면 원격 접근이 발생해 NUMA 인지의
  의미가 사라진다. 두 서브시스템을 함께 설계해야 실질적 이득이 있다.
- **영향**:
  - `kernel/core/mm`의 물리 페이지 할당자는 노드별 풀(ADR-033과 결합)을
    가지며, 할당 API에 "선호 노드" 인자가 추가된다.
  - 스레드 생성 시 선호 노드가 결정되며(부모 스레드의 노드를 상속하는
    것이 기본), ADR-034의 노드별 런큐에 배치된다.
  - 토폴로지 발견: x86_64는 ACPI SRAT/SLIT(§`arch_data_addr` 경유),
    aarch64는 디바이스 트리의 NUMA 노드 기술을 **자체 파싱**해야
    한다(ADR-006 직접구현 원칙 유지 — 서드파티 ACPI/FDT 라이브러리 금지).
  - QEMU 기본 구성(단일 소켓, 노드 1개)에서는 이 로직 전체가 "노드 0만
    존재"로 자연히 단순화되어 M1~M8 검증에 지장이 없다.
  - 노드 간 로드밸런싱의 구체적 임계치·정책은 OPEN-24와 함께 다룬다.

## ADR-051. 정책 서버 다운 시 쿼터 폴백: 마지막 승인값 유지 (해결: OPEN-21)

- **상태**: 확정 (2026-09-08)
- **결정**: 정책 서버(ADR-024)가 응답하지 않는 동안, 각 프로세스의
  메모리 쿼터는 **마지막으로 승인된 값에 고정(freeze)**된다. 새
  프로세스는 미리 정해진 기본값 쿼터를 받는다. 정책 서버가 복구되면
  정상적인 동적 재분배가 재개된다.
- **근거**: 관대한 기본치로 대체하면 정책 서버가 다운된 틈을 타 쿼터
  남용이 가능해지고, 완전 거부는 정책 서버 장애가 시스템 전체를
  마비시킨다. 마지막 승인값 유지는 두 극단 사이의 안전하고 예측
  가능한 절충이다.
- **영향**:
  - `quota_state`(memory.md §5)에 "마지막 갱신 시각" 또는 "freeze
    여부" 플래그가 필요하지 않다 — freeze는 단순히 "정책 서버로부터
    새 값을 못 받으면 기존 값을 계속 쓴다"는 것뿐이므로 별도 상태가
    필요 없다.
  - 새 프로세스의 기본값 쿼터 크기는 구현 시 정한다.

## ADR-052. 락 순서 규칙: 문서화된 정적 규칙만 (런타임 검증 없음) (해결: OPEN-23)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널의 락 획득 순서는 설계 문서(이 결정 기록 및 각 서브
  시스템 스펙)에 명시적으로 규칙화하고 코드 리뷰로 강제한다. 디버그
  빌드에서 락 획득 이력을 추적해 역전을 자동 검출하는 런타임 검증기는
  두지 않는다.
- **근거**: ADR-033이 이미 "필요한 곳만 최소 범위 락"을 원칙으로 삼아
  락이 많지 않다 — 엔드포인트 락, 노드별 메모리/스케줄러 락, 프로세스별
  핸들 테이블 락, 디버그 콘솔 전역 락(ADR-037) 정도로 가짓수가 적어
  런타임 검증기 없이도 정적 규칙만으로 관리 가능하다고 판단한다.
  구현 복잡도를 낮추는 선택이다.
- **영향**:
  - 락 순서 규칙 자체(어떤 락을 어떤 순서로 잡아야 하는지)는 실제
    각 서브시스템 코드를 작성하면서 확정하고, 이 문서 체계에
    갱신한다 — 지금은 "정적 문서화"라는 방식만 확정했다.
  - 나중에 락 가짓수가 늘어나 정적 규칙만으로 부족하다고 판단되면
    런타임 검증기를 추가하는 것을 막지 않는다(이 ADR은 v1 방침).

## ADR-054. 물리 메모리 NUMA 자동 폴백: 가까운 노드부터 순차 시도 (해결: OPEN-24 잔여 항목)

- **상태**: 확정 (2026-09-08)
- **결정**: `alloc_pages`(memory.md §4)가 선호 노드에서 실패하면,
  커널은 **거리가 가까운 노드부터 순차적으로** 다른 NUMA 노드를
  자동 시도한다. 모든 노드가 고갈되어야 최종적으로
  `alloc_error::out_of_memory`를 반환한다.
- **근거**: (ADR-053의 스케줄러 워크 스틸링과는 별개 문제) 완전
  실패 정책은 노드 간 메모리 압박이 불균형할 때 시스템 안정성을
  해친다 — 한 노드만 소진돼도 그 노드를 선호하는 프로세스들이
  즉시 실패한다. 자동 폴백이 훨씬 실용적이며, "가까운 노드부터"는
  원격 접근 비용을 최소화하는 순서다.
- **영향**:
  - 노드 간 거리를 표현하는 행렬이 필요하다 — x86_64는 ACPI
    SLIT(boot.md §2), aarch64는 FDT의 distance-map에서 얻는다.
    토폴로지 정보가 없으면(단일 노드) 이 로직은 자명하게 스킵된다.
  - `memory.md` §4의 "v1에서는 폴백하지 않고 그대로 실패"를 이
    결정으로 갱신해야 한다.
  - 폴백으로 할당된 페이지의 실제 위치는 요청 스레드의
    `preferred_node`와 다를 수 있다는 점을 문서화해야 한다.

## ADR-078. 커널 가상메모리 레이아웃: 고정 오프셋 물리 다이렉트맵(physmap) + 별도 스택/이미지 영역 (해결: OPEN-34)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 커널 가상주소공간(두 아키텍처 공통 개념)은 세 개의 고정 영역으로
     구성한다.
     - **물리 다이렉트맵(physmap)**: 물리주소 앞쪽 512GiB를(RAM·MMIO
       구분 없이) 고정 오프셋으로 1:1 매핑한다. `memory.md`의 물리
       할당자가 반환하는 `physical_address`를 커널이 실제로
       읽고/쓰려면 `phys_to_virt(phys) = physmap_base + phys`만
       계산하면 된다 — 프레임별 임시 매핑/언매핑이 필요 없다.
     - **커널 스택 영역**: 스레드별 커널 스택 슬롯 + 슬롯 사이
       미매핑 가드 페이지. physmap과 분리해 따로 관리한다.
     - **커널 이미지 영역**: 커널 자신의 ELF 텍스트/rodata/data/bss.
       섹션별 권한(RX/RO/RW+NX)을 적용한다.
  2. 두 아키텍처가 **동일한 상대 배치**(주소공간 맨 위에서부터 이미지
     2GiB, 그 아래 스택 2GiB, 커널 공간 시작 지점부터 512GiB
     physmap)를 따르되, 절대 주소는 각자의 커널/유저 분할 관례를
     따른다:
     - x86_64(4-level, 48비트 canonical): physmap = `0xFFFF800000000000`,
       스택 = `0xFFFFFFFF00000000`, 이미지 = `0xFFFFFFFF80000000`.
     - aarch64(TTBR0/TTBR1 분리, 48비트, 4KiB 그래뉼): physmap =
       `0xFFFF000000000000`, 스택 = `0xFFFFFFFF00000000`, 이미지 =
       `0xFFFFFFFF80000000`(x86_64와 "맨 위에서부터의 거리"를 그대로
       재사용).
  3. 부팅 극초기 모드 전환 트램폴린에 필요한 항등 매핑(boot.md
     §1.1/§1.3)은 이 physmap과는 **별개의 임시** 매핑이다 — higher-half로
     점프한 뒤에도 정리(unmap)하지 않고 그대로 둔다(어차피 이후 코드가
     그 주소를 참조하지 않으므로 무해하며, 정리 비용을 들일 이유가 없다).
  4. physmap은 실제 감지된 물리 메모리 크기와 무관하게 **항상 512GiB
     고정**으로, huge/block 페이지만으로(x86_64는 PDPT 1GiB 페이지,
     aarch64는 레벨1 1GiB 블록) 매핑한다 — `boot_info.memory_map`을
     순회하며 점진적으로 구축하지 않고 커널 공간 시작 지점부터 통째로
     미리 매핑해버리는 편이 부팅 초기화 코드를 훨씬 단순하게 만든다.
- **근거**:
  - 프레임별 임시 매핑 대신 **다이렉트맵**을 선택한 이유는 커널
    자신의 메모리 접근이 압도적으로 빈번해서다 — 매 접근마다
    페이지테이블을 조작하면 ADR-033(락-프리·per-CPU 우선)의 성능
    지향과 충돌한다. seL4/Zircon/Redox 등 실제 마이크로커널들이
    공통적으로 채택하는 방식이기도 하다.
  - RAM과 MMIO를 구분하지 않고 통째로 매핑하는 이유는, ADR-007이
    커널 내부에 두기로 한 장치(타이머, 인터럽트 컨트롤러, 시리얼)가
    전부 물리주소 512GiB 이내의 낮은 고정 주소(x86_64 APIC
    `0xFEE00000`대, aarch64 QEMU virt PL011 `0x09000000`/GIC 등)에
    있으므로, 별도의 "MMIO 전용 동적 매핑 영역"을 만들지 않고도
    `phys_to_virt`만으로 접근할 수 있다 — 새 개념을 추가하지 않는
    쪽을 택했다(ADR-001의 "커널 밖으로 미는" 원칙과 일치 — 커널이
    다루는 장치 자체가 이미 최소 집합이다).
  - 스택 영역을 physmap과 분리한 이유는 순전히 **가드 페이지**
    때문이다 — physmap 안에 가드 페이지를 두려면 그 물리 페이지를
    영원히 할당 불가로 예약해야 해서 "physmap은 곧 전체 물리주소
    1:1"이라는 불변식이 깨진다. 별도 영역이면 가상주소만 소비하고
    실제 물리 페이지를 배정하지 않으면 되므로 간단하다.
  - 커널 이미지에 섹션별 권한(W^X)을 적용하는 것은 페이지테이블을
    어차피 만드는 김에 거의 추가 비용 없이 얻는 하드닝이다(ADR-001의
    "정확성 우선").
  - 두 아키텍처의 상대 배치를 동일하게 맞춘 것은 아키텍처별 특수
    케이스를 최소화하기 위함이다 — 절대 주소 프리픽스 차이(`0xFFFF8...`
    vs `0xFFFF0...`)는 canonical/TTBR 분할 규칙 차이로 불가피하지만,
    그 이후 레이아웃 논리는 완전히 동일하게 재사용된다.
  - 512GiB 고정 크기는 QEMU 개발 환경과 실제 데스크톱/서버급 하드웨어의
    전형적 RAM 용량을 넉넉히 커버하면서, "감지된 메모리만큼만 매핑"하는
    점진적 구축 로직을 부트 초기화에서 완전히 없애준다 — 대가로 "512GiB를
    넘는 물리 메모리는 이 시점에서 다이렉트맵으로 접근 불가"라는 명시적
    제약을 감수한다(아래 영향에 기록).
  - 4-level/48비트를 유지하는 이유는 ADR-009가 이미 "4-level, 추후
    5-level 고려"로 정해두었고, 이 레이아웃(512GiB physmap + 4GiB
    안팎의 스택·이미지)이 128TiB 커널 공간의 극히 일부만 쓰므로
    5-level(57비트)로 전환되어도 그대로 재사용 가능해 지금 서두를
    이유가 없기 때문이다.
- **영향**:
  - `kernel/arch/x86_64/boot/`, `kernel/arch/aarch64/boot/`는 boot.md
    §1.1/§1.3의 항등 매핑 트램폴린 **이후**, 이 ADR이 정한 physmap+
    스택+이미지 페이지테이블을 구성하고 나서야 higher-half
    `kernel_main`으로 점프해야 한다 — boot.md를 갱신한다(이 ADR과
    함께 반영).
  - `kernel/core/mm`(memory.md)의 물리 할당자가 반환하는
    `physical_address`를 커널이 실제로 역참조하려면 `phys_to_virt()`
    헬퍼(신설, physmap 오프셋 덧셈)를 거쳐야 한다 — memory.md에 이
    의존성을 명시한다(스펙 갱신, 이 ADR과 함께 반영).
  - 상세 주소 상수·섹션 권한 표·부팅 시퀀스 통합은 새 스펙 문서
    [virtual-memory-layout.md](../spec/virtual-memory-layout.md)에서
    구현 가능한 수준으로 정의한다.
  - **제약**: 물리 메모리가 512GiB를 넘는 환경에서는 초과분이 이
    physmap으로 직접 접근되지 않는다 — 필요해지면 physmap 크기를
    늘리거나(커널 공간에 여유가 충분해 어렵지 않음) 온디맨드 매핑을
    추가하는 후속 ADR을 쓴다. M1~M8(kernel-bootstrap.md) 및 QEMU
    개발 환경에서는 문제가 되지 않는다.
  - 커널 스택 영역의 슬롯 크기·할당 알고리즘(비트맵 vs free-list)은
    스케줄러가 스레드 생성 API를 구체화하는 시점(M5)에 정한다 — 이
    ADR은 "영역 위치와 가드 페이지 사용"까지만 고정한다.

## ADR-104. 물리 메모리 예약: 전체의 10%(기본값)를 스왑/장치 IO 전용으로 항상 확보 (OPEN-44 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 물리 페이지 할당자([memory.md](../spec/memory.md) §2~4)는 시스템
     전체 물리 메모리의 **10%(기본값)**를 "가용 예약분(reserve)"으로
     항상 유지한다 — 이 예약분은 일반 할당 요청(`alloc_pages`)에는
     쓰이지 않고, [filesystem.md](filesystem.md) ADR-100/103의
     SWAPFS 스왑 아웃/스왑 인 I/O 및 기타 물리 장치 I/O(블록 드라이버
     DMA 버퍼 등)처럼 "메모리를 회수하려면 메모리가 필요한" 상황
     전용으로 남겨둔다.
  2. 계산은 페이지(order-0, 최소 단위) 개수 기준으로 하며, NUMA
     노드가 여러 개면(ADR-036) **각 노드의 전체 용량 중 10%를 그
     노드 자신의 예약분**으로 잡는다 — 특정 노드에 예약이 몰리지
     않게 노드별로 독립 계산한다.
  3. 이 비율은 `@global/system/memory`(신설) 레지스트리 테이블의
     `reserve_percent` 키로 조정 가능하다(super만 쓰기 가능) — 10%는
     기본값이지 하드코딩된 상수가 아니다.
- **근거**: 사용자가 정확히 이 위험을 지적했다 — 스왑 아웃 자체가
  I/O이고 I/O는 버퍼/DMA용 메모리를 필요로 하므로, 시스템이 메모리를
  100% 소진한 상태에서는 "메모리를 회수하려는 시도 자체가 메모리
  부족으로 실패"하는 교착(deadlock)이 생길 수 있다. 고정 비율(10%)을
  기본값으로 둔 이유는 시스템 총 메모리 크기에 자동으로 비례해
  예약량이 늘어나게 하기 위해서다. 이 세션에서 이미 여러 차례 쓴
  패턴(TTY 개수, 위임 타임아웃 등)과 마찬가지로 레지스트리로 조정
  가능하게 해, 고정 상수로 하드코딩하지 않는다.
- **영향**:
  - `memory.md` §2의 `per_node_pool`에 `reserved_pages`(또는
    `reserved_bytes`) 필드가 필요하다.
  - 일반 `alloc_pages` 경로는 이 예약분을 침범할 수 없다 — 침범하면
    `alloc_error::out_of_memory`로 실패한다(예약분이 있어도 "일반
    용도로는 없는 것"과 동일하게 취급).
  - 예약분에 접근할 수 있는 특수 경로(SWAPFS 자신의 I/O 버퍼 할당 등)를
    구분하는 정확한 API 형태(별도 플래그 vs 전용 caller 식별)는
    이 ADR의 범위 밖이다 — SWAPFS 상세 설계 시점에 정한다.
  - `@global/system/memory` 레지스트리 스키마를
    [registry.md](../spec/registry.md) 갱신 시점에 반영해야 한다.

## ADR-105. 메모리 회수 순서: 캐시 우선 해제 → 최저 우선순위 프로세스부터 스왑 아웃 (OPEN-44 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**: 가용 메모리가 ADR-104의 예약 임계치에 가까워지면, 다음
  순서로 회수를 시도한다:
  1. **캐시 회수**: 페이지 캐시/버퍼 캐시처럼 "디스크에서 다시 읽어올
     수 있는" 재구성 가능한 메모리를 먼저 해제한다.
  2. 그것만으로 부족하면, **가장 낮은 우선순위**를 가진 프로세스의
     메모리부터 [filesystem.md](filesystem.md) ADR-100의 SWAPFS로
     밀어낸다(우선순위는 [scheduler.md](../spec/scheduler.md)의
     커널/유저 밴드 및 승격 결과, ADR-014/025/027/034를 그대로
     사용 — 새 우선순위 축을 만들지 않는다).
- **근거**: 사용자가 "최저 우선순위 프로세스의 메모리부터 스왑으로
  밀어내고, 캐시로 예약된 물리 메모리를 해제한다"는 두 조치를
  명시했다. 이 ADR은 그중 **캐시 회수를 먼저** 두는 순서를 이
  근거로 확정한다: clean 캐시 페이지는 원본이 이미 디스크에 있어
  버리는 데 쓰기 I/O가 필요 없는 반면, 스왑 아웃은 쓰기 I/O(및
  ADR-104가 확보해 둔 예약분 소비)가 필요하다 — 항상 더 싼 쪽을
  먼저 시도하는 것이 합리적이다. 프로세스 선정에 스케줄러의 기존
  우선순위 체계를 재사용하는 이유는 "누가 밀려나야 하는가"를 판단할
  새 기준을 또 만들지 않기 위해서다 — 이미 낮은 우선순위로 밀려난
  프로세스가 메모리에서도 먼저 밀려나는 것이 일관적이다.
- **영향**:
  - "캐시"의 정확한 정의·소유자(어느 서버가 캐시를 들고 있다고
    보는지 — VFS인지 각 FS 서버인지)와 캐시 회수를 트리거하는
    정확한 워터마크(몇 % 시점에 회수를 시작하는지)는 이 ADR의
    범위 밖이며 SWAPFS/FS 서버 상세 설계 시점에 정한다.
  - 같은 우선순위의 프로세스가 여럿이면 그중 어떤 것부터 스왑할지
    (예: 메모리 사용량이 큰 순서)의 세부 정책도 후속 결정 대상이다.

## ADR-106. 논블로킹 메모리 할당의 실패 시맨틱: 블로킹 미지정 시 즉시 실패, 재시도는 호출자 책임 (OPEN-44 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**: 메모리 할당 요청(`alloc_pages` 및 그 위에 얹히는 유저랜드
  대면 API — `mmap`류)은 기본적으로 **논블로킹**이다. 호출자가
  명시적으로 블로킹 옵션을 지정하지 않으면, 즉시 가용 메모리를
  확보할 수 없을 때 **곧바로 실패를 반환**한다(대기하지 않는다).
  반환되는 오류는 "일시적 부족이니 나중에 다시 시도하라"는 의미의
  전용 에러 코드(`alloc_error::try_again`, memory.md §4 갱신 대상)로
  구분하며, **재시도는 호출자(유저랜드 앱)의 책임**이다.
- **근거**: 사용자가 "블로킹 옵션이 명시되지 않은 요청은 모두 실패
  후 재시도하도록 만들어야 한다"고 명시했다. 커널이 내부적으로
  블록하는 대신 즉시 실패를 돌려주는 이유는, ADR-105의 회수 절차가
  스왑 I/O를 포함해 얼마나 걸릴지 예측할 수 없는 과정이기 때문이다 —
  커널 스레드를 무기한 블록시키는 대신 호출자에게 제어권을 돌려줘
  재시도 타이밍(예: 지수 백오프)을 유저랜드 정책으로 결정하게 하는
  편이 예측 가능성과 정확성(ADR-001)에 부합한다.
- **영향**:
  - `memory.md` §4의 `alloc_error`에 `try_again`을 추가해야 한다
    (스펙 갱신).
  - 블로킹 옵션을 명시적으로 요청하는 API(정확한 플래그 형태, 대기
    시간 상한 유무)는 이 ADR의 범위 밖이다 — 유저랜드 대면 메모리
    API(`mmap`류) 상세 설계 시점에 정한다.

## ADR-107. 메모리 압박 신호: 대형 힙 보유 프로세스에게 Notification으로 자진 반납 요청 (해결: OPEN-44)

- **상태**: 확정 (2026-09-08)
- **결정**: 메모리 압박이 감지되면(ADR-104/105의 회수 절차가 이미
  시작된 상황), 커널 또는 정책 서버(ADR-024)는 현재 **큰 메모리
  풋프린트를 가진 프로세스**를 식별해, [ipc.md](../spec/ipc.md)의
  기존 **비동기 Notification**(ADR-004)으로 "메모리 압박" 비트를
  보낸다. 이 신호를 받는 프로세스(정확히는 그 프로세스의 런타임/
  할당자)는 자신의 힙 중 즉시 필요 없는 부분을 커널에 반환(`free_pages`에
  대응하는 unmap/decommit)하는 것이 **권장**된다 — 강제는 아니다
  (협조적 메커니즘, 응답하지 않아도 오류가 되지 않는다).
- **근거**: 사용자가 "메모리를 많이 먹는 앱들에게 압박 신호를 보내
  안 쓰는 힙을 뱉게 해야 한다"고 명시했다. 새 IPC 원시를 추가하지
  않고 이미 있는 Notification(ADR-004 — "소실 없는 비트셋 신호",
  정확히 이런 "무언가 일어났다"는 통지 용도로 이미 설계됨)을 그대로
  재사용한다 — 새 커널 개념이 필요 없다.
- **영향**:
  - "큰 메모리 풋프린트"의 정확한 기준(절대량 vs 시스템 대비 비율)과
    신호를 받을 프로세스 선정 정책은 정책 서버(ADR-024) 설계 시점에
    정한다.
  - 유저랜드 libc/할당자가 이 신호를 어떻게 처리하는지(예:
    `malloc_trim`류 자동 훅)는 libc 포팅/설계 대상이며 이 ADR의
    범위 밖이다.
  - OPEN-44("SWAPFS 압박 상황이 물리 메모리 할당자·정책 서버 쿼터에
    어떻게 반영되는지")는 ADR-104~107로 해소된다.

## ADR-108. 스왑 아웃 압축: 우선순위·스케줄링 빈도 기반 대상 선정, 압축 이득 없으면 그대로 저장 (ADR-105 갱신)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 메모리 압축 기능은 커널 설정으로 켜고 끌 수 있다 —
     `@global/system/memory`(ADR-104가 이미 도입) 테이블에
     `compression_enabled`(bool) 키를 추가한다.
  2. 압축이 켜져 있을 때, ADR-105의 스왑 아웃 대상 선정 기준을
     확장한다 — **우선순위가 낮은 프로세스**뿐 아니라 **최근
     스케줄링 빈도가 낮은(오래 실행되지 않은) 프로세스**도 압축+
     스왑 대상 후보가 된다. 둘 중 하나만 만족해도 후보가 된다(OR
     조건) — 우선순위는 높지만 오래 잠들어 있는 프로세스(예:
     백그라운드 대기 서비스)의 메모리도 대상이 될 수 있다는 뜻이다.
  3. 대상으로 선정된 프로세스의 페이지를 SWAPFS로 밀어낼 때(ADR-105
     §결정 2단계), 먼저 압축을 시도한다. **압축 결과가 원본보다
     작을 때만** 압축된 형태로 저장하고, 그렇지 않으면(비압축성
     데이터 등) **압축하지 않은 원본을 그대로 저장**한다 — 압축
     여부와 원본 크기는 스왑 슬롯의 메타데이터에 함께 기록해
     재적재(swap-in) 시 정확히 역과정을 수행할 수 있게 한다.
  4. 기본 압축 알고리즘은 **LZ4류**(단순하고 빠르며, 특히 압축
     해제 속도가 빠른 알고리즘)를 권장한다 — ADR-006의 "직접 구현"
     원칙에 따라 커널이 자체 구현하며, 알고리즘 자체는 설정으로
     교체 가능한 구조로 둔다(구체적 플러그인 방식은 후속 결정).
- **근거**: 사용자가 "압축 알고리즘이 필요하고, 커널 설정으로 제어
  가능해야 하며, 우선순위가 낮거나 스케줄링 빈도가 떨어지면 압축해
  스왑으로 밀어내고, 압축 이득이 없으면 압축하지 않고 저장해도
  된다"고 명시했다. 스케줄링 빈도를 우선순위와 별개의(OR) 기준으로
  추가하는 이유는, 우선순위는 높지만 오랫동안 깨어나지 않는
  프로세스의 메모리도 압축 대상이 되어야 한다는 의도를 반영한
  것이다. LZ4류를 기본으로 권장하는 이유는, 스왑 인(재적재) 지연이
  곧 유저 프로세스의 페이지 폴트 지연으로 직결되므로 압축률보다
  압축 해제 속도가 더 중요하기 때문이다 — ADR-079가 암호 알고리즘을
  고를 때 "직접 구현 리스크가 낮은 것"을 우선한 것과 같은 논리로,
  복잡한 압축 알고리즘(zstd류)보다 훨씬 단순해 커널 내 직접 구현
  위험도 낮다.
- **영향**:
  - `@global/system/memory`의 스키마에 `compression_enabled`를
    추가해야 한다([registry.md](../spec/registry.md) 갱신 대상).
  - "최근 스케줄링 빈도"를 정확히 어떻게 측정·기록하는지(예: 마지막
    실행 이후 경과 시간, 최근 N회 스케줄러 틱당 실행 횟수)는
    [kernel-scheduler.md](kernel-scheduler.md)/[scheduler.md](../spec/scheduler.md)
    상세 설계 대상이며 이 ADR의 범위 밖이다 → 신규 **미결정
    (OPEN-46)**.
  - 스왑 슬롯 메타데이터(압축 여부·원본 크기 플래그)의 정확한
    자료구조는 SWAPFS 상세 설계 시점에 정한다.
  - 압축·압축 해제 루틴의 정확한 구현 위치(커널 내부 vs SWAPFS
    서버 내부)는 이 ADR의 범위 밖이다 — 스왑 아웃 자체가 커널의
    물리 페이지 회수 경로에서 트리거되므로 `kernel/core/mm`에 두는
    것이 자연스럽지만, 최종 결정은 SWAPFS 프로토콜 설계 시점에
    한다 → 신규 **미결정 (OPEN-47)**.

## ADR-110. 스왑 압축/해제 실행 위치: SWAPFS 서버, 커널은 후보 통지만 + 압박 시 사후 압축 (해결: OPEN-47)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 실제 압축/압축 해제 루틴은 **커널이 아니라 SWAPFS
     서버**([filesystem.md](filesystem.md), ADR-099~103)가 수행한다.
     커널의 `kernel/core/mm`은 압축 알고리즘을 직접 구현하지 않고,
     스왑 아웃 대상 페이지가 정해지면 그 페이지를 SWAPFS 서버에게
     넘기는 역할까지만 맡는다.
  2. 커널 스케줄러는 ADR-109([kernel-scheduler.md](kernel-scheduler.md))의
     "최근 스케줄링 빈도" 카운터를 계속 유지하다가, 어떤 프로세스가
     이 ADR-108의 압축 후보 조건(우선순위 낮음 OR 최근 스케줄링
     빈도 낮음)에 새로 진입하면 이를 SWAPFS 서버에게 통지한다. 실제
     압축 여부·시점의 결정과 압축 자체의 수행은 SWAPFS 서버가
     담당한다.
  3. SWAP이 압력을 받는 상태(ADR-104의 예약 영역 잠식 등)에서는,
     이미 **비압축 상태로 저장되어 있는** 스왑 페이지 중 그 사이
     소유 프로세스가 압축 후보 조건에 새로 진입한 것이 있다면,
     SWAPFS 서버가 그 페이지들을 **사후적으로(retroactively)
     압축**하는 작업을 수행한다 — 원래 스왑 아웃 시점에는 후보가
     아니었지만(예: 그때는 자주 실행 중이었음) 이후 오래 잠들어
     후보가 된 경우까지 압축 이득을 회수한다.
- **근거**: 사용자가 "압축과 압축 해제는 SWAPFS 서버가 수행하는 것이
  맞고, 스케줄러가 카운팅하면서 압축이 되어야 할 때 SWAPFS 서버에게
  알려주면 된다"고, 또 "SWAP이 압력을 받을 때 미압축 상태인데 그런
  상태에 빠져든 프로세스의 스왑 페이지들을 압축하는 작업을 수행하면
  된다"고 명시했다. 압축 로직을 커널이 아니라 SWAPFS 서버에 두면
  ADR-006/007의 "드라이버/서비스는 유저 프로세스로"라는 원칙과
  일치하고, 커널은 신호 전달자 역할만 맡아 결합도가 낮아진다. 이
  ADR로 ADR-108 §영향의 "커널 내부가 자연스럽다"는 잠정 방향은
  뒤집힌다.
- **영향**:
  - SWAPFS 프로토콜([filesystem.md](filesystem.md))에 커널 → SWAPFS
    통지 오퍼레이션(압축 후보 진입 알림)과, 압박 신호를 받아 기존
    비압축 슬롯을 재압축하는 백그라운드 작업이 추가되어야 한다.
  - 스왑 슬롯 메타데이터(압축 여부·원본 크기)는 SWAPFS 서버가
    소유·갱신한다.
  - 정확한 통지 IPC 오퍼레이션 형식과 사후 압축 작업의 스케줄링
    방식(백그라운드 우선순위 등)은 SWAPFS 프로토콜 상세 설계
    시점에 정한다.
  - OPEN-47은 이 ADR로 해소된다.
