## ADR-012. 커널 메모리 할당 정책: 슬랩/페이지 할당자 + 프로세스별 쿼터 (해결: OPEN-4)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널이 자체 물리 페이지 할당자(buddy/bitmap 등)와 커널 객체용 슬랩
  할당자를 갖는 전통적 방식을 사용한다. 각 프로세스/서버에는 메모리 쿼터가 부여되어
  폭주를 방지한다.
- **근거**: Untyped+retype(seL4식)은 원칙적으로 우수하지만, ADR-008의 다중 POSIX
  서버 구조를 유저랜드에서 전부 관리하게 하면 초기 구현 부담이 지나치게 커진다.
  전통적 할당자가 구현 속도·실용성 면에서 이 프로젝트(범용 OS 지향, ADR-001)에 더 맞는다.
- **영향**:
  - 커널 메모리 부족(OOM) 시 정책(어느 쿼터를 우선 거부할지, 커널 자체 할당은
    절대 실패해선 안 되는 예약 영역을 둘지)이 필요. → **미결정 (OPEN-13)**
  - 쿼터 초과는 시스템 콜의 `result` 실패로 반환한다 (ADR-010과 일치).
  - 부모→자식 쿼터 위임/재분배 지원 여부도 OPEN-13에서 함께 정한다.

## ADR-016. fork 구현: 커널 네이티브 COW + 프로세스 서버의 fd 복제 조율 (해결: OPEN-10)

- **상태**: 확정 (2026-09-08)
- **결정**: 주소공간 복제(Copy-on-Write)는 **커널이 직접** 수행한다 (페이지테이블
  복제, 쓰기 폴트 시 페이지 프레임 분리, 참조 카운트 관리). 열린 fd 목록의 복제는
  **프로세스 서버**가 조율한다 — 부모의 fd 테이블을 순회하며 각 fd가 속한 서버
  (FS/네트워크 등)에 "핸들 복제"를 요청한다.
- **근거**: 순수 유저 pager 위임 방식은 매 쓰기 폴트마다 IPC 왕복이 발생해
  범용 OS 워크로드(ADR-001)에는 비용이 너무 크다. 반면 fd 복제는 본질적으로
  여러 서버에 걸친 조율 작업이라 ADR-008(서버 분해) 구조상 프로세스 서버의 몫이다.
- **영향**:
  - 커널은 주소공간 객체에 "COW 복제"와 "쓰기 폴트 시 프레임 분리" 오퍼레이션을
    구현해야 하며, 페이지 프레임 참조 카운트가 ADR-012 메모리 할당자에 통합되어야 한다.
  - `fork()`의 실제 흐름: ① 유저(libc)가 프로세스 서버에 fork 요청 → ② 프로세스
    서버가 커널에 새 프로세스 + 주소공간 COW 복제를 요청 → ③ 프로세스 서버가
    부모 fd 테이블을 순회하며 각 서버에 "핸들 복제" IPC 전송 → ④ 완료 후 자식 실행 시작.
  - 모든 FS/네트워크 서버는 "핸들 복제" 프로토콜을 구현해야 한다 (OPEN-11/ADR-018과 연동).

## ADR-024. 메모리 쿼터: 중앙 정책 서버의 동적 재분배 (해결: OPEN-13)

- **상태**: 확정 (2026-09-08)
- **결정**: 정책 서버(또는 프로세스 서버 하위 기능)가 시스템 전체 메모리
  현황을 파악하고, 프로세스별 쿼터 증감 요청을 그때그때 승인·거부한다.
  fork/exec 시 자식의 초기 쿼터도 정책 서버를 거쳐 결정된다.
- **근거**: 고정 쿼터는 fork 직후 메모리 부족을 흔히 유발하고, 부모→자식
  고정 분할은 장기 실행 시스템에서 경직된다. 범용 OS 지향(ADR-001)에는
  동적 재분배가 실질적으로 필요하다.
- **영향**:
  - 정책 서버는 시스템의 새로운 신뢰 경계가 된다 — 커널 메모리 할당자
    (ADR-012)는 정책 서버만 가진 특수 권한 없이는 어떤 프로세스의 쿼터
    상한도 늘릴 수 없도록 커널 API 수준에서 강제해야 한다.
  - 정책 서버 다운 시 쿼터 조정이 멈춘다 — 장애 시 폴백 정책(마지막
    승인값 유지 등) 필요. → **미결정 (OPEN-21)**
  - "물리 메모리 자체 고갈(OOM)"과 "정책상의 쿼터 초과"는 서로 다른
    실패로 구분해 반환해야 한다.

## ADR-033. 커널 락 모델: 락-프리 + per-CPU 구조 우선

- **상태**: 확정 (2026-09-08)
- **결정**: 커널 내부 자료구조는 최대한 CPU별(local) 자료구조로 설계하고,
  공유가 불가피한 경우에만 최소 범위의 스핀락을 사용한다. 전역 Big
  Kernel Lock은 두지 않는다.
- **근거**: 범용 OS 지향(ADR-001)과 다중 코어 확장성을 우선한다. Big
  Kernel Lock에서 세분화 락으로 나중에 리팩터링하는 비용은 처음부터
  per-CPU로 설계하는 비용보다 훨씬 크다 — 자료구조가 "코어가 하나"라는
  가정을 곳곳에 깔고 있으면 나중에 뜯어고치기 매우 어렵다.
- **영향**:
  - `kernel/core/mm`: per-CPU 로컬 프리 리스트 + NUMA 노드별 전역 풀
    (ADR-036과 결합) — 로컬이 고갈되면 같은 노드의 전역 풀에서 보충한다.
  - `kernel/core/sched`: 노드별 런큐(ADR-034)에 노드 단위 스핀락 하나만
    사용 — 코어별 세분화는 v1 범위가 아니다.
  - `kernel/core/ipc`: 엔드포인트 대기열은 여러 코어의 스레드가 동시에
    접근하므로 엔드포인트당 스핀락이 필요하다 — "완전 락-프리"가 아니라
    "필요한 곳만 최소 범위 락"이 이 ADR의 실제 원칙이다.
  - 프로세스별 핸들 테이블(ADR-011)은 다중 스레드 프로세스에서 동시
    접근될 수 있어 프로세스당 스핀락 하나가 필요하다.
  - 락 순서(lock ordering) 규칙과 교착상태 방지 정책은 아직 없다.
    → **미결정 (OPEN-23)**

## ADR-036. NUMA 인지 범위: 메모리 할당자 + 스케줄러 모두

- **상태**: 확정 (2026-09-08)
- **결정**: 물리 메모리 할당자와 스케줄러 양쪽 모두 NUMA 토폴로지를
  인지한다. 페이지 할당은 요청자의 선호 노드에 따라 노드별 풀에서
  이뤄지고, 스레드는 가능한 한 자신이 메모리를 할당받은 노드의 코어에서
  실행되도록 스케줄링된다(ADR-034의 노드별 런큐와 결합).
- **근거**: 메모리 할당자만 NUMA를 인지하고 스케줄러가 무시하면(또는
  반대) 지역성 이득의 절반만 얻는다 — 메모리는 노드 0에 할당됐는데
  스레드가 노드 1 코어에서 실행되면 원격 접근이 발생해 NUMA 인지의
  의미가 사라진다. 두 서브시스템을 함께 설계해야 실질적 이득이 있다.
- **영향**:
  - `kernel/core/mm`의 물리 페이지 할당자는 노드별 풀(ADR-033과 결합)을
    가지며, 할당 API에 "선호 노드" 인자가 추가된다.
  - 스레드 생성 시 선호 노드가 결정되며(부모 스레드의 노드를 상속하는
    것이 기본), ADR-034의 노드별 런큐에 배치된다.
  - 토폴로지 발견: x86_64는 ACPI SRAT/SLIT(§`arch_data_addr` 경유),
    aarch64는 디바이스 트리의 NUMA 노드 기술을 **자체 파싱**해야
    한다(ADR-006 직접구현 원칙 유지 — 서드파티 ACPI/FDT 라이브러리 금지).
  - QEMU 기본 구성(단일 소켓, 노드 1개)에서는 이 로직 전체가 "노드 0만
    존재"로 자연히 단순화되어 M1~M8 검증에 지장이 없다.
  - 노드 간 로드밸런싱의 구체적 임계치·정책은 OPEN-24와 함께 다룬다.

## ADR-051. 정책 서버 다운 시 쿼터 폴백: 마지막 승인값 유지 (해결: OPEN-21)

- **상태**: 확정 (2026-09-08)
- **결정**: 정책 서버(ADR-024)가 응답하지 않는 동안, 각 프로세스의
  메모리 쿼터는 **마지막으로 승인된 값에 고정(freeze)**된다. 새
  프로세스는 미리 정해진 기본값 쿼터를 받는다. 정책 서버가 복구되면
  정상적인 동적 재분배가 재개된다.
- **근거**: 관대한 기본치로 대체하면 정책 서버가 다운된 틈을 타 쿼터
  남용이 가능해지고, 완전 거부는 정책 서버 장애가 시스템 전체를
  마비시킨다. 마지막 승인값 유지는 두 극단 사이의 안전하고 예측
  가능한 절충이다.
- **영향**:
  - `quota_state`(memory.md §5)에 "마지막 갱신 시각" 또는 "freeze
    여부" 플래그가 필요하지 않다 — freeze는 단순히 "정책 서버로부터
    새 값을 못 받으면 기존 값을 계속 쓴다"는 것뿐이므로 별도 상태가
    필요 없다.
  - 새 프로세스의 기본값 쿼터 크기는 구현 시 정한다.

## ADR-052. 락 순서 규칙: 문서화된 정적 규칙만 (런타임 검증 없음) (해결: OPEN-23)

- **상태**: 확정 (2026-09-08)
- **결정**: 커널의 락 획득 순서는 설계 문서(이 결정 기록 및 각 서브
  시스템 스펙)에 명시적으로 규칙화하고 코드 리뷰로 강제한다. 디버그
  빌드에서 락 획득 이력을 추적해 역전을 자동 검출하는 런타임 검증기는
  두지 않는다.
- **근거**: ADR-033이 이미 "필요한 곳만 최소 범위 락"을 원칙으로 삼아
  락이 많지 않다 — 엔드포인트 락, 노드별 메모리/스케줄러 락, 프로세스별
  핸들 테이블 락, 디버그 콘솔 전역 락(ADR-037) 정도로 가짓수가 적어
  런타임 검증기 없이도 정적 규칙만으로 관리 가능하다고 판단한다.
  구현 복잡도를 낮추는 선택이다.
- **영향**:
  - 락 순서 규칙 자체(어떤 락을 어떤 순서로 잡아야 하는지)는 실제
    각 서브시스템 코드를 작성하면서 확정하고, 이 문서 체계에
    갱신한다 — 지금은 "정적 문서화"라는 방식만 확정했다.
  - 나중에 락 가짓수가 늘어나 정적 규칙만으로 부족하다고 판단되면
    런타임 검증기를 추가하는 것을 막지 않는다(이 ADR은 v1 방침).

## ADR-054. 물리 메모리 NUMA 자동 폴백: 가까운 노드부터 순차 시도 (해결: OPEN-24 잔여 항목)

- **상태**: 확정 (2026-09-08)
- **결정**: `alloc_pages`(memory.md §4)가 선호 노드에서 실패하면,
  커널은 **거리가 가까운 노드부터 순차적으로** 다른 NUMA 노드를
  자동 시도한다. 모든 노드가 고갈되어야 최종적으로
  `alloc_error::out_of_memory`를 반환한다.
- **근거**: (ADR-053의 스케줄러 워크 스틸링과는 별개 문제) 완전
  실패 정책은 노드 간 메모리 압박이 불균형할 때 시스템 안정성을
  해친다 — 한 노드만 소진돼도 그 노드를 선호하는 프로세스들이
  즉시 실패한다. 자동 폴백이 훨씬 실용적이며, "가까운 노드부터"는
  원격 접근 비용을 최소화하는 순서다.
- **영향**:
  - 노드 간 거리를 표현하는 행렬이 필요하다 — x86_64는 ACPI
    SLIT(boot.md §2), aarch64는 FDT의 distance-map에서 얻는다.
    토폴로지 정보가 없으면(단일 노드) 이 로직은 자명하게 스킵된다.
  - `memory.md` §4의 "v1에서는 폴백하지 않고 그대로 실패"를 이
    결정으로 갱신해야 한다.
  - 폴백으로 할당된 페이지의 실제 위치는 요청 스레드의
    `preferred_node`와 다를 수 있다는 점을 문서화해야 한다.

## ADR-078. 커널 가상메모리 레이아웃: 고정 오프셋 물리 다이렉트맵(physmap) + 별도 스택/이미지 영역 (해결: OPEN-34)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 커널 가상주소공간(두 아키텍처 공통 개념)은 세 개의 고정 영역으로
     구성한다.
     - **물리 다이렉트맵(physmap)**: 물리주소 앞쪽 512GiB를(RAM·MMIO
       구분 없이) 고정 오프셋으로 1:1 매핑한다. `memory.md`의 물리
       할당자가 반환하는 `physical_address`를 커널이 실제로
       읽고/쓰려면 `phys_to_virt(phys) = physmap_base + phys`만
       계산하면 된다 — 프레임별 임시 매핑/언매핑이 필요 없다.
     - **커널 스택 영역**: 스레드별 커널 스택 슬롯 + 슬롯 사이
       미매핑 가드 페이지. physmap과 분리해 따로 관리한다.
     - **커널 이미지 영역**: 커널 자신의 ELF 텍스트/rodata/data/bss.
       섹션별 권한(RX/RO/RW+NX)을 적용한다.
  2. 두 아키텍처가 **동일한 상대 배치**(주소공간 맨 위에서부터 이미지
     2GiB, 그 아래 스택 2GiB, 커널 공간 시작 지점부터 512GiB
     physmap)를 따르되, 절대 주소는 각자의 커널/유저 분할 관례를
     따른다:
     - x86_64(4-level, 48비트 canonical): physmap = `0xFFFF800000000000`,
       스택 = `0xFFFFFFFF00000000`, 이미지 = `0xFFFFFFFF80000000`.
     - aarch64(TTBR0/TTBR1 분리, 48비트, 4KiB 그래뉼): physmap =
       `0xFFFF000000000000`, 스택 = `0xFFFFFFFF00000000`, 이미지 =
       `0xFFFFFFFF80000000`(x86_64와 "맨 위에서부터의 거리"를 그대로
       재사용).
  3. 부팅 극초기 모드 전환 트램폴린에 필요한 항등 매핑(boot.md
     §1.1/§1.3)은 이 physmap과는 **별개의 임시** 매핑이다 — higher-half로
     점프한 뒤에도 정리(unmap)하지 않고 그대로 둔다(어차피 이후 코드가
     그 주소를 참조하지 않으므로 무해하며, 정리 비용을 들일 이유가 없다).
  4. physmap은 실제 감지된 물리 메모리 크기와 무관하게 **항상 512GiB
     고정**으로, huge/block 페이지만으로(x86_64는 PDPT 1GiB 페이지,
     aarch64는 레벨1 1GiB 블록) 매핑한다 — `boot_info.memory_map`을
     순회하며 점진적으로 구축하지 않고 커널 공간 시작 지점부터 통째로
     미리 매핑해버리는 편이 부팅 초기화 코드를 훨씬 단순하게 만든다.
- **근거**:
  - 프레임별 임시 매핑 대신 **다이렉트맵**을 선택한 이유는 커널
    자신의 메모리 접근이 압도적으로 빈번해서다 — 매 접근마다
    페이지테이블을 조작하면 ADR-033(락-프리·per-CPU 우선)의 성능
    지향과 충돌한다. seL4/Zircon/Redox 등 실제 마이크로커널들이
    공통적으로 채택하는 방식이기도 하다.
  - RAM과 MMIO를 구분하지 않고 통째로 매핑하는 이유는, ADR-007이
    커널 내부에 두기로 한 장치(타이머, 인터럽트 컨트롤러, 시리얼)가
    전부 물리주소 512GiB 이내의 낮은 고정 주소(x86_64 APIC
    `0xFEE00000`대, aarch64 QEMU virt PL011 `0x09000000`/GIC 등)에
    있으므로, 별도의 "MMIO 전용 동적 매핑 영역"을 만들지 않고도
    `phys_to_virt`만으로 접근할 수 있다 — 새 개념을 추가하지 않는
    쪽을 택했다(ADR-001의 "커널 밖으로 미는" 원칙과 일치 — 커널이
    다루는 장치 자체가 이미 최소 집합이다).
  - 스택 영역을 physmap과 분리한 이유는 순전히 **가드 페이지**
    때문이다 — physmap 안에 가드 페이지를 두려면 그 물리 페이지를
    영원히 할당 불가로 예약해야 해서 "physmap은 곧 전체 물리주소
    1:1"이라는 불변식이 깨진다. 별도 영역이면 가상주소만 소비하고
    실제 물리 페이지를 배정하지 않으면 되므로 간단하다.
  - 커널 이미지에 섹션별 권한(W^X)을 적용하는 것은 페이지테이블을
    어차피 만드는 김에 거의 추가 비용 없이 얻는 하드닝이다(ADR-001의
    "정확성 우선").
  - 두 아키텍처의 상대 배치를 동일하게 맞춘 것은 아키텍처별 특수
    케이스를 최소화하기 위함이다 — 절대 주소 프리픽스 차이(`0xFFFF8...`
    vs `0xFFFF0...`)는 canonical/TTBR 분할 규칙 차이로 불가피하지만,
    그 이후 레이아웃 논리는 완전히 동일하게 재사용된다.
  - 512GiB 고정 크기는 QEMU 개발 환경과 실제 데스크톱/서버급 하드웨어의
    전형적 RAM 용량을 넉넉히 커버하면서, "감지된 메모리만큼만 매핑"하는
    점진적 구축 로직을 부트 초기화에서 완전히 없애준다 — 대가로 "512GiB를
    넘는 물리 메모리는 이 시점에서 다이렉트맵으로 접근 불가"라는 명시적
    제약을 감수한다(아래 영향에 기록).
  - 4-level/48비트를 유지하는 이유는 ADR-009가 이미 "4-level, 추후
    5-level 고려"로 정해두었고, 이 레이아웃(512GiB physmap + 4GiB
    안팎의 스택·이미지)이 128TiB 커널 공간의 극히 일부만 쓰므로
    5-level(57비트)로 전환되어도 그대로 재사용 가능해 지금 서두를
    이유가 없기 때문이다.
- **영향**:
  - `kernel/arch/x86_64/boot/`, `kernel/arch/aarch64/boot/`는 boot.md
    §1.1/§1.3의 항등 매핑 트램폴린 **이후**, 이 ADR이 정한 physmap+
    스택+이미지 페이지테이블을 구성하고 나서야 higher-half
    `kernel_main`으로 점프해야 한다 — boot.md를 갱신한다(이 ADR과
    함께 반영).
  - `kernel/core/mm`(memory.md)의 물리 할당자가 반환하는
    `physical_address`를 커널이 실제로 역참조하려면 `phys_to_virt()`
    헬퍼(신설, physmap 오프셋 덧셈)를 거쳐야 한다 — memory.md에 이
    의존성을 명시한다(스펙 갱신, 이 ADR과 함께 반영).
  - 상세 주소 상수·섹션 권한 표·부팅 시퀀스 통합은 새 스펙 문서
    [virtual-memory-layout.md](../spec/virtual-memory-layout.md)에서
    구현 가능한 수준으로 정의한다.
  - **제약**: 물리 메모리가 512GiB를 넘는 환경에서는 초과분이 이
    physmap으로 직접 접근되지 않는다 — 필요해지면 physmap 크기를
    늘리거나(커널 공간에 여유가 충분해 어렵지 않음) 온디맨드 매핑을
    추가하는 후속 ADR을 쓴다. M1~M8(kernel-bootstrap.md) 및 QEMU
    개발 환경에서는 문제가 되지 않는다.
  - 커널 스택 영역의 슬롯 크기·할당 알고리즘(비트맵 vs free-list)은
    스케줄러가 스레드 생성 API를 구체화하는 시점(M5)에 정한다 — 이
    ADR은 "영역 위치와 가드 페이지 사용"까지만 고정한다.

## ADR-104. 물리 메모리 예약: 전체의 10%(기본값)를 스왑/장치 IO 전용으로 항상 확보 (OPEN-44 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 물리 페이지 할당자([memory.md](../spec/memory.md) §2~4)는 시스템
     전체 물리 메모리의 **10%(기본값)**를 "가용 예약분(reserve)"으로
     항상 유지한다 — 이 예약분은 일반 할당 요청(`alloc_pages`)에는
     쓰이지 않고, [filesystem.md](filesystem.md) ADR-100/103의
     SWAPFS 스왑 아웃/스왑 인 I/O 및 기타 물리 장치 I/O(블록 드라이버
     DMA 버퍼 등)처럼 "메모리를 회수하려면 메모리가 필요한" 상황
     전용으로 남겨둔다.
  2. 계산은 페이지(order-0, 최소 단위) 개수 기준으로 하며, NUMA
     노드가 여러 개면(ADR-036) **각 노드의 전체 용량 중 10%를 그
     노드 자신의 예약분**으로 잡는다 — 특정 노드에 예약이 몰리지
     않게 노드별로 독립 계산한다.
  3. 이 비율은 `@global/system/memory`(신설) 레지스트리 테이블의
     `reserve_percent` 키로 조정 가능하다(super만 쓰기 가능) — 10%는
     기본값이지 하드코딩된 상수가 아니다.
- **근거**: 사용자가 정확히 이 위험을 지적했다 — 스왑 아웃 자체가
  I/O이고 I/O는 버퍼/DMA용 메모리를 필요로 하므로, 시스템이 메모리를
  100% 소진한 상태에서는 "메모리를 회수하려는 시도 자체가 메모리
  부족으로 실패"하는 교착(deadlock)이 생길 수 있다. 고정 비율(10%)을
  기본값으로 둔 이유는 시스템 총 메모리 크기에 자동으로 비례해
  예약량이 늘어나게 하기 위해서다. 이 세션에서 이미 여러 차례 쓴
  패턴(TTY 개수, 위임 타임아웃 등)과 마찬가지로 레지스트리로 조정
  가능하게 해, 고정 상수로 하드코딩하지 않는다.
- **영향**:
  - `memory.md` §2의 `per_node_pool`에 `reserved_pages`(또는
    `reserved_bytes`) 필드가 필요하다.
  - 일반 `alloc_pages` 경로는 이 예약분을 침범할 수 없다 — 침범하면
    `alloc_error::out_of_memory`로 실패한다(예약분이 있어도 "일반
    용도로는 없는 것"과 동일하게 취급).
  - 예약분에 접근할 수 있는 특수 경로(SWAPFS 자신의 I/O 버퍼 할당 등)를
    구분하는 정확한 API 형태(별도 플래그 vs 전용 caller 식별)는
    이 ADR의 범위 밖이다 — SWAPFS 상세 설계 시점에 정한다.
  - `@global/system/memory` 레지스트리 스키마를
    [registry.md](../spec/registry.md) 갱신 시점에 반영해야 한다.

## ADR-105. 메모리 회수 순서: 캐시 우선 해제 → 최저 우선순위 프로세스부터 스왑 아웃 (OPEN-44 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**: 가용 메모리가 ADR-104의 예약 임계치에 가까워지면, 다음
  순서로 회수를 시도한다:
  1. **캐시 회수**: 페이지 캐시/버퍼 캐시처럼 "디스크에서 다시 읽어올
     수 있는" 재구성 가능한 메모리를 먼저 해제한다.
  2. 그것만으로 부족하면, **가장 낮은 우선순위**를 가진 프로세스의
     메모리부터 [filesystem.md](filesystem.md) ADR-100의 SWAPFS로
     밀어낸다(우선순위는 [scheduler.md](../spec/scheduler.md)의
     커널/유저 밴드 및 승격 결과, ADR-014/025/027/034를 그대로
     사용 — 새 우선순위 축을 만들지 않는다).
- **근거**: 사용자가 "최저 우선순위 프로세스의 메모리부터 스왑으로
  밀어내고, 캐시로 예약된 물리 메모리를 해제한다"는 두 조치를
  명시했다. 이 ADR은 그중 **캐시 회수를 먼저** 두는 순서를 이
  근거로 확정한다: clean 캐시 페이지는 원본이 이미 디스크에 있어
  버리는 데 쓰기 I/O가 필요 없는 반면, 스왑 아웃은 쓰기 I/O(및
  ADR-104가 확보해 둔 예약분 소비)가 필요하다 — 항상 더 싼 쪽을
  먼저 시도하는 것이 합리적이다. 프로세스 선정에 스케줄러의 기존
  우선순위 체계를 재사용하는 이유는 "누가 밀려나야 하는가"를 판단할
  새 기준을 또 만들지 않기 위해서다 — 이미 낮은 우선순위로 밀려난
  프로세스가 메모리에서도 먼저 밀려나는 것이 일관적이다.
- **영향**:
  - "캐시"의 정확한 정의·소유자(어느 서버가 캐시를 들고 있다고
    보는지 — VFS인지 각 FS 서버인지)와 캐시 회수를 트리거하는
    정확한 워터마크(몇 % 시점에 회수를 시작하는지)는 이 ADR의
    범위 밖이며 SWAPFS/FS 서버 상세 설계 시점에 정한다.
  - 같은 우선순위의 프로세스가 여럿이면 그중 어떤 것부터 스왑할지
    (예: 메모리 사용량이 큰 순서)의 세부 정책도 후속 결정 대상이다.

## ADR-106. 논블로킹 메모리 할당의 실패 시맨틱: 블로킹 미지정 시 즉시 실패, 재시도는 호출자 책임 (OPEN-44 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**: 메모리 할당 요청(`alloc_pages` 및 그 위에 얹히는 유저랜드
  대면 API — `mmap`류)은 기본적으로 **논블로킹**이다. 호출자가
  명시적으로 블로킹 옵션을 지정하지 않으면, 즉시 가용 메모리를
  확보할 수 없을 때 **곧바로 실패를 반환**한다(대기하지 않는다).
  반환되는 오류는 "일시적 부족이니 나중에 다시 시도하라"는 의미의
  전용 에러 코드(`alloc_error::try_again`, memory.md §4 갱신 대상)로
  구분하며, **재시도는 호출자(유저랜드 앱)의 책임**이다.
- **근거**: 사용자가 "블로킹 옵션이 명시되지 않은 요청은 모두 실패
  후 재시도하도록 만들어야 한다"고 명시했다. 커널이 내부적으로
  블록하는 대신 즉시 실패를 돌려주는 이유는, ADR-105의 회수 절차가
  스왑 I/O를 포함해 얼마나 걸릴지 예측할 수 없는 과정이기 때문이다 —
  커널 스레드를 무기한 블록시키는 대신 호출자에게 제어권을 돌려줘
  재시도 타이밍(예: 지수 백오프)을 유저랜드 정책으로 결정하게 하는
  편이 예측 가능성과 정확성(ADR-001)에 부합한다.
- **영향**:
  - `memory.md` §4의 `alloc_error`에 `try_again`을 추가해야 한다
    (스펙 갱신).
  - 블로킹 옵션을 명시적으로 요청하는 API(정확한 플래그 형태, 대기
    시간 상한 유무)는 이 ADR의 범위 밖이다 — 유저랜드 대면 메모리
    API(`mmap`류) 상세 설계 시점에 정한다.

## ADR-107. 메모리 압박 신호: 대형 힙 보유 프로세스에게 Notification으로 자진 반납 요청 (해결: OPEN-44)

- **상태**: 확정 (2026-09-08)
- **결정**: 메모리 압박이 감지되면(ADR-104/105의 회수 절차가 이미
  시작된 상황), 커널 또는 정책 서버(ADR-024)는 현재 **큰 메모리
  풋프린트를 가진 프로세스**를 식별해, [ipc.md](../spec/ipc.md)의
  기존 **비동기 Notification**(ADR-004)으로 "메모리 압박" 비트를
  보낸다. 이 신호를 받는 프로세스(정확히는 그 프로세스의 런타임/
  할당자)는 자신의 힙 중 즉시 필요 없는 부분을 커널에 반환(`free_pages`에
  대응하는 unmap/decommit)하는 것이 **권장**된다 — 강제는 아니다
  (협조적 메커니즘, 응답하지 않아도 오류가 되지 않는다).
- **근거**: 사용자가 "메모리를 많이 먹는 앱들에게 압박 신호를 보내
  안 쓰는 힙을 뱉게 해야 한다"고 명시했다. 새 IPC 원시를 추가하지
  않고 이미 있는 Notification(ADR-004 — "소실 없는 비트셋 신호",
  정확히 이런 "무언가 일어났다"는 통지 용도로 이미 설계됨)을 그대로
  재사용한다 — 새 커널 개념이 필요 없다.
- **영향**:
  - "큰 메모리 풋프린트"의 정확한 기준(절대량 vs 시스템 대비 비율)과
    신호를 받을 프로세스 선정 정책은 정책 서버(ADR-024) 설계 시점에
    정한다.
  - 유저랜드 libc/할당자가 이 신호를 어떻게 처리하는지(예:
    `malloc_trim`류 자동 훅)는 libc 포팅/설계 대상이며 이 ADR의
    범위 밖이다.
  - OPEN-44("SWAPFS 압박 상황이 물리 메모리 할당자·정책 서버 쿼터에
    어떻게 반영되는지")는 ADR-104~107로 해소된다.

## ADR-108. 스왑 아웃 압축: 우선순위·스케줄링 빈도 기반 대상 선정, 압축 이득 없으면 그대로 저장 (ADR-105 갱신)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 메모리 압축 기능은 커널 설정으로 켜고 끌 수 있다 —
     `@global/system/memory`(ADR-104가 이미 도입) 테이블에
     `compression_enabled`(bool) 키를 추가한다.
  2. 압축이 켜져 있을 때, ADR-105의 스왑 아웃 대상 선정 기준을
     확장한다 — **우선순위가 낮은 프로세스**뿐 아니라 **최근
     스케줄링 빈도가 낮은(오래 실행되지 않은) 프로세스**도 압축+
     스왑 대상 후보가 된다. 둘 중 하나만 만족해도 후보가 된다(OR
     조건) — 우선순위는 높지만 오래 잠들어 있는 프로세스(예:
     백그라운드 대기 서비스)의 메모리도 대상이 될 수 있다는 뜻이다.
  3. 대상으로 선정된 프로세스의 페이지를 SWAPFS로 밀어낼 때(ADR-105
     §결정 2단계), 먼저 압축을 시도한다. **압축 결과가 원본보다
     작을 때만** 압축된 형태로 저장하고, 그렇지 않으면(비압축성
     데이터 등) **압축하지 않은 원본을 그대로 저장**한다 — 압축
     여부와 원본 크기는 스왑 슬롯의 메타데이터에 함께 기록해
     재적재(swap-in) 시 정확히 역과정을 수행할 수 있게 한다.
  4. 기본 압축 알고리즘은 **LZ4류**(단순하고 빠르며, 특히 압축
     해제 속도가 빠른 알고리즘)를 권장한다 — ADR-006의 "직접 구현"
     원칙에 따라 커널이 자체 구현하며, 알고리즘 자체는 설정으로
     교체 가능한 구조로 둔다(구체적 플러그인 방식은 후속 결정).
- **근거**: 사용자가 "압축 알고리즘이 필요하고, 커널 설정으로 제어
  가능해야 하며, 우선순위가 낮거나 스케줄링 빈도가 떨어지면 압축해
  스왑으로 밀어내고, 압축 이득이 없으면 압축하지 않고 저장해도
  된다"고 명시했다. 스케줄링 빈도를 우선순위와 별개의(OR) 기준으로
  추가하는 이유는, 우선순위는 높지만 오랫동안 깨어나지 않는
  프로세스의 메모리도 압축 대상이 되어야 한다는 의도를 반영한
  것이다. LZ4류를 기본으로 권장하는 이유는, 스왑 인(재적재) 지연이
  곧 유저 프로세스의 페이지 폴트 지연으로 직결되므로 압축률보다
  압축 해제 속도가 더 중요하기 때문이다 — ADR-079가 암호 알고리즘을
  고를 때 "직접 구현 리스크가 낮은 것"을 우선한 것과 같은 논리로,
  복잡한 압축 알고리즘(zstd류)보다 훨씬 단순해 커널 내 직접 구현
  위험도 낮다.
- **영향**:
  - `@global/system/memory`의 스키마에 `compression_enabled`를
    추가해야 한다([registry.md](../spec/registry.md) 갱신 대상).
  - "최근 스케줄링 빈도"를 정확히 어떻게 측정·기록하는지(예: 마지막
    실행 이후 경과 시간, 최근 N회 스케줄러 틱당 실행 횟수)는
    [kernel-scheduler.md](kernel-scheduler.md)/[scheduler.md](../spec/scheduler.md)
    상세 설계 대상이며 이 ADR의 범위 밖이다 → 신규 **미결정
    (OPEN-46)**.
  - 스왑 슬롯 메타데이터(압축 여부·원본 크기 플래그)의 정확한
    자료구조는 SWAPFS 상세 설계 시점에 정한다.
  - 압축·압축 해제 루틴의 정확한 구현 위치(커널 내부 vs SWAPFS
    서버 내부)는 이 ADR의 범위 밖이다 — 스왑 아웃 자체가 커널의
    물리 페이지 회수 경로에서 트리거되므로 `kernel/core/mm`에 두는
    것이 자연스럽지만, 최종 결정은 SWAPFS 프로토콜 설계 시점에
    한다 → 신규 **미결정 (OPEN-47)**.

## ADR-110. 스왑 압축/해제 실행 위치: SWAPFS 서버, 커널은 후보 통지만 + 압박 시 사후 압축 (해결: OPEN-47)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 실제 압축/압축 해제 루틴은 **커널이 아니라 SWAPFS
     서버**([filesystem.md](filesystem.md), ADR-099~103)가 수행한다.
     커널의 `kernel/core/mm`은 압축 알고리즘을 직접 구현하지 않고,
     스왑 아웃 대상 페이지가 정해지면 그 페이지를 SWAPFS 서버에게
     넘기는 역할까지만 맡는다.
  2. 커널 스케줄러는 ADR-109([kernel-scheduler.md](kernel-scheduler.md))의
     "최근 스케줄링 빈도" 카운터를 계속 유지하다가, 어떤 프로세스가
     이 ADR-108의 압축 후보 조건(우선순위 낮음 OR 최근 스케줄링
     빈도 낮음)에 새로 진입하면 이를 SWAPFS 서버에게 통지한다. 실제
     압축 여부·시점의 결정과 압축 자체의 수행은 SWAPFS 서버가
     담당한다.
  3. SWAP이 압력을 받는 상태(ADR-104의 예약 영역 잠식 등)에서는,
     이미 **비압축 상태로 저장되어 있는** 스왑 페이지 중 그 사이
     소유 프로세스가 압축 후보 조건에 새로 진입한 것이 있다면,
     SWAPFS 서버가 그 페이지들을 **사후적으로(retroactively)
     압축**하는 작업을 수행한다 — 원래 스왑 아웃 시점에는 후보가
     아니었지만(예: 그때는 자주 실행 중이었음) 이후 오래 잠들어
     후보가 된 경우까지 압축 이득을 회수한다.
- **근거**: 사용자가 "압축과 압축 해제는 SWAPFS 서버가 수행하는 것이
  맞고, 스케줄러가 카운팅하면서 압축이 되어야 할 때 SWAPFS 서버에게
  알려주면 된다"고, 또 "SWAP이 압력을 받을 때 미압축 상태인데 그런
  상태에 빠져든 프로세스의 스왑 페이지들을 압축하는 작업을 수행하면
  된다"고 명시했다. 압축 로직을 커널이 아니라 SWAPFS 서버에 두면
  ADR-006/007의 "드라이버/서비스는 유저 프로세스로"라는 원칙과
  일치하고, 커널은 신호 전달자 역할만 맡아 결합도가 낮아진다. 이
  ADR로 ADR-108 §영향의 "커널 내부가 자연스럽다"는 잠정 방향은
  뒤집힌다.
- **영향**:
  - SWAPFS 프로토콜([filesystem.md](filesystem.md))에 커널 → SWAPFS
    통지 오퍼레이션(압축 후보 진입 알림)과, 압박 신호를 받아 기존
    비압축 슬롯을 재압축하는 백그라운드 작업이 추가되어야 한다.
  - 스왑 슬롯 메타데이터(압축 여부·원본 크기)는 SWAPFS 서버가
    소유·갱신한다.
  - 정확한 통지 IPC 오퍼레이션 형식과 사후 압축 작업의 스케줄링
    방식(백그라운드 우선순위 등)은 SWAPFS 프로토콜 상세 설계
    시점에 정한다.
  - OPEN-47은 이 ADR로 해소된다.

## ADR-121. 모든 유저 주소공간이 부팅 시점 저지대 항등 매핑(GDT 포함)을 공유해야 한다 — 중간 레벨도 USER 비트 필요

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. `arch_x86_64::create_address_space_root()`는 기존에 공유하던
     physmap(`pml4[256]`류)·커널 이미지(`pml4[511]`류) 엔트리에
     더해, **`pml4[0]`(부팅 시점 저지대 항등 매핑, 물리/가상
     `[0, 8MiB)`)도 모든 새 주소공간에 그대로 공유**한다.
  2. 이 공유를 가능하게 하려면, 그 경로의 **중간 레벨**(`pml4[0]`,
     `low_pdpt[0]`)도 USER 비트(PTE 비트2)를 가져야 한다 — x86
     페이징은 유저모드 접근이 성립하려면 리프뿐 아니라 **모든
     레벨**이 U/S 비트를 가져야 한다(AND 관계). 리프 자체
     (`low_pd[0..3]`, 원래 물리 `[0,8MiB)` 항등 매핑)는 여전히
     USER 비트가 없어 그 범위 자체는 계속 supervisor 전용으로
     남는다 — 오직 그 아래(예: `low_pd[128]` 등 부팅 시점에 안
     쓰인 엔트리)에 이후 새로 만들어지는 유저 매핑만 이 변경으로
     통과 가능해진다.
- **근거**: GDT(`gdt64_start`, `boot.S`)는 저지대 항등 매핑 안(`.boot.rodata`,
  VMA==LMA)에 있다 — CR3가 새 주소공간으로 전환된 뒤 IRETQ가 새
  CS/SS 셀렉터를 검증하려고 GDT 자체를 읽는데, 이 매핑이 없으면 GDT가
  통째로 미매핑 상태가 되어 **IRETQ 자체가 #PF로 죽는다**(M8에서
  QEMU로 실제 확인: `CR2`가 GDT 안의 정확한 엔트리 오프셋을 가리켰다).
  중간 레벨 USER 비트 누락은 별개로 겪은 문제다 — 리프(ELF 로더가
  매핑한 initrun 코드 페이지) 자체는 USER 비트가 정확히 켜져 있는데도
  부모 레벨(`pml4[0]`/`low_pdpt[0]`)에 그 비트가 없어 유저모드
  명령어 페치가 계속 보호 위반으로 실패했다(에러코드 `I/D=1`,
  QEMU로 재현·`objdump`/레지스터 덤프로 확진).
- **영향**:
  - `page_table.hpp`의 `create_address_space_root()` 문서 주석을
    "physmap+커널 이미지 두 엔트리 공유"에서 "저지대 항등 매핑 포함
    세 엔트리 공유"로 갱신했다.
  - `low_pd[0..3]`(원래 물리 `[0,8MiB)` 항등 매핑) 자체의 접근 범위는
    바뀌지 않는다 — 이 ADR은 오직 그 **부모 레벨**의 USER 비트만
    다룬다.
  - `map_page()`가 이 공유된 저지대 항등 매핑과 **겹치는 가상주소**를
    매핑하려 들면 여전히 깨진다(거대 페이지를 다음 레벨 테이블로
    오인하는 별개의 버그, `map_page()`가 거대 페이지 분할을 지원하지
    않음) — [boot-and-drivers.md](boot-and-drivers.md) ADR-123이
    이 문제 자체는 "링크 주소를 겹치지 않게 잡는다"로 회피했을 뿐,
    `map_page()`를 고치지는 않았다.

## ADR-134. slab_header를 16바이트로 정렬 — 모든 크기 클래스 청크가 16바이트 정렬을 갖도록 보장

- **상태**: 확정 (2026-09-09)
- **결정**: `kernel/core/mm/slab.cpp`의 내부 `slab_header` 구조체에
  `alignas(16)`을 추가한다. 이 구조체는 세 멤버(포인터 2개 + `uint32_t`
  1개, 8바이트 정렬 요구라 자연 크기가 24바이트로 패딩됨)로, `alignas`
  추가 전에는 `sizeof(slab_header)==24`였다 — 16의 배수가 아니다.
- **근거**: `slab_alloc()`(memory.md §6)은 order-0 페이지(4096바이트,
  항상 16의 배수로 정렬됨) 맨 앞에 `slab_header`를 두고, 그 바로
  뒤(`area = header + sizeof(slab_header)`)부터 고정 크기(전부 16의
  배수, `k_slab_size_classes`) 청크를 순서대로 잘라 낸다. `sizeof(
  slab_header)`가 16의 배수가 아니면 `area` 자체가 이미 16바이트
  정렬에서 8바이트 어긋나고, 청크 크기가 16의 배수라 그 어긋남이
  모든 후속 청크에 그대로 전파된다 — 즉 **`slab_alloc()`으로 받은
  메모리는 애초에 16바이트 정렬을 전혀 보장하지 않았다**. M1~M8은
  이 사실이 드러날 일이 없었다(어떤 슬랩 할당 대상도 8바이트보다
  엄격한 정렬을 요구하지 않았다) — M9(ADR-127)이 `object::thread`에
  `alignas(16) uint8_t fxsave_area[512]`를 추가하면서 **처음으로**
  16바이트 정렬을 요구하는 타입을 `mm::slab_alloc(sizeof(object::
  thread))`로 할당했고, QEMU에서 `FXRSTOR` 실행 시 실제 `#GP`(General
  Protection Fault, 정렬 안 된 메모리 피연산자)로 이어져 IDT가 없는
  탓에 트리플폴트로 즉시 드러났다 — 폴트 RIP를 `llvm-symbolizer`로
  역추적하고(ADR-126의 백트레이스 워크플로와 같은 도구), `objdump`로
  정확한 명령어(`fxrstor (%r8)`)를 확인한 뒤, 그 레지스터 값(주소)이
  16의 배수가 아님을 확인해 원인을 좁혔다. `slab_header`에
  `alignas(16)`만 추가하면(24→32바이트로 패딩) `area`와 그 뒤 모든
  청크가 다시 16의 배수 오프셋에 놓인다 — 근본 원인(헤더 크기)을
  고치는 가장 단순한 수정이다.
- **영향**:
  - 슬랩 페이지 1개(4096바이트)당 헤더가 8바이트 더 커져(24→32)
    사용 가능한 청크 영역이 그만큼 줄지만, 페이지당 한 번뿐이라
    무시할 수 있는 손실이다.
  - **이 수정 이전에 만들어진 어떤 코드도 "slab_alloc은 16바이트
    정렬을 보장한다"고 가정해서는 안 됐다** — 이 ADR 이후로는
    그 가정이 실제로 성립한다. 앞으로 슬랩으로 할당하는 타입에
    `alignas(N)`(N≤16)가 붙어 있어도 안전하다.
  - `docs/done/smp-fpu-bringup-m9.md`가 이 버그의 발견·진단 경위를
    상세히 기록한다.

## ADR-136. 실제 락 순서 표 확정 (ADR-052 구체화, M11)

- **상태**: 확정 (2026-09-09)
- **결정**: ADR-052가 "락 순서 규칙은 각 서브시스템 코드를 작성하며
  확정하고 이 문서 체계에 갱신한다"고 미뤄둔 부분을, M10/M11 시점까지
  실제로 만들어진 모든 락을 코드에서 직접 조사해 확정한다(런타임
  검증기는 여전히 두지 않는다 — ADR-052의 v1 방침 그대로).

  **락 목록**(전부 `libk::spinlock`, `ticket_lock`/`mcs_lock`은 정의만
  있고 커널·서버 어디서도 실제로 쓰이지 않는다):

  | 락 | 소유 구조체/위치 | 획득 지점 |
  |---|---|---|
  | `per_node_pool::lock` | `mm/page_allocator.hpp`, 노드당 1개 | `alloc_pages`, `free_to_node_pool`, `refill_cpu_cache`(노드별 루프) |
  | `size_class_state::lock` | `mm/slab.cpp`, 슬랩 크기 클래스당 1개 | `slab_alloc`, `slab_free` |
  | `run_queue::lock` | `sched/scheduler.hpp`, NUMA 노드당 1개 | `try_pick_band`, `enqueue` |
  | `object::endpoint::lock` | `object/kernel_objects.hpp`, 엔드포인트당 1개 | `sys_call`, `sys_recv`(둘 다 성공/에러 경로 각각 재획득) |
  | `object::notification::lock` | `object/kernel_objects.hpp`, notification당 1개 | `sys_notify`, `sys_wait` |
  | `klog::g_log_lock`(`irq_safe<spinlock>`) | `core/klog.cpp` 전역 1개(ADR-037 예외) | `klog::write`, `klog::vprintf` |

  **중첩(동시에 두 락을 쥐는) 경로는 현재 코드 전체에서 단 하나뿐이다**:
  `slab_alloc()`이 `size_class_state::lock`을 쥔 채 비어 있으면
  `grow_locked()` → `mm::alloc_pages()`를 호출하고, 그 안에서
  `per_node_pool::lock`을 추가로 잡는다 — **순서: `size_class_state::lock`
  (바깥) → `per_node_pool::lock`(안쪽)**. 이 방향으로만 발생하며,
  반대 방향(`per_node_pool::lock`을 쥔 채 슬랩 락을 잡는 경로)은
  코드 어디에도 없다 — 따라서 역전 가능성이 없다.

  그 외 모든 락(`run_queue`, `endpoint`, `notification`, `klog`)은
  항상 **리프(leaf) 락**이다 — 다른 어떤 락을 쥔 채로 이 락들을
  잡는 경로가 없고, 이 락들을 쥔 채로 다른 락을 잡는 경로도 없다
  (예: `sys_call`/`sys_recv`는 `endpoint::lock`을 놓은 뒤에야
  `sched::enqueue`/`sched::block`을 부른다 — `run_queue::lock`과
  절대 동시에 쥐지 않는다).

  `pick_next_with_stealing()`(scheduler.cpp, M11 §M11 다중 코어 검증
  도입)이 여러 노드의 `run_queue::lock`을 순회하며 조회하지만, 매
  노드마다 **잠그고-확인하고-바로 풀어서 다음 노드로 넘어가는 방식**
  이라 두 `run_queue::lock`을 동시에 쥐는 순간이 전혀 없다 — 같은
  종류의 락을 여러 인스턴스에 걸쳐 순차적으로만 잡는 이 패턴은
  `refill_cpu_cache()`/`alloc_pages()`의 노드별 폴백 루프도 동일하게
  따른다.

  `handle_table`은 **자체 락이 없다** — `create_owner`/`create_proxy`/
  `close`/`handle_info` 전부 동기화 없이 동작한다. 지금까지(M1~M11)
  안전한 이유는 이 함수들을 부르는 코드가 전부 논리적으로 1코어
  (BSP, ADR-035/M10 done 보고 — AP는 스케줄러에 참여하지 않는다)에서만
  실행되기 때문이다 — 락 순서 문제가 아니라 **아직 아무 락도 없다는
  사실 자체**가 M12 이후(procsrv 등 실제 다중 프로세스 동시 접근이
  생기는 시점) 반드시 재검토해야 할 결여로 남는다.
- **근거**: 사용자가 M11 완료 기준으로 요구한 "락 순서 규칙 문서화"를
  실제 코드 조사로 확정한다 — ADR-052가 이미 "빈도가 낮고 가짓수가
  적어 정적 문서화로 충분하다"고 판단한 전제가 실측으로도 그대로
  성립함을 확인했다(중첩 경로가 정확히 하나, 그것도 항상 같은
  방향으로만 발생).
- **영향**:
  - 향후 새 락을 추가할 때는 이 표에 없는 새 중첩 경로를 만들지
    않도록 검토한다 — 특히 `per_node_pool::lock`을 쥔 채 슬랩
    함수를 부르는 코드는 절대 추가하지 않는다(역전 발생).
  - `handle_table`의 무동기화 상태는 이 ADR이 해결하지 않는다 —
    procsrv 등 M12 이후 계획에서 실제로 여러 프로세스가 동시에
    핸들 테이블에 접근하게 되는 시점에 별도 결정이 필요하다.

## ADR-140. ADR-016 COW의 실제 커널 구현: 프레임 참조 카운트 테이블 + PTE 소프트웨어 비트 + 쓰기 폴트 분기

- **상태**: 확정 (2026-09-09~10)
- **결정**: ADR-016이 요구한 세 가지("페이지 프레임 참조 카운트가
  ADR-012 할당자에 통합", "커널이 직접 COW 복제/쓰기 폴트 분리를
  수행")를 다음과 같이 실제로 구현한다.
  1. **프레임 참조 카운트**: [page_allocator.hpp](../../kernel/core/mm/page_allocator.hpp)/
     [.cpp](../../kernel/core/mm/page_allocator.cpp)에 order-0(4KiB) 전용
     테이블을 추가한다. `mm::init()`이 usable 영역의 최대 물리주소를
     보고 필요한 크기를 order-N(최대 4MiB=4GiB 물리메모리 상당,
     넘으면 `LIBK_PANIC`)로 계산해 `alloc_pages()`로 한 번 확보한다.
     값의 의미는 "0=단독 소유, N=나 말고 N명 더"다(절대 소유자 수가
     아니라 **추가** 소유자 수) — `frame_add_ref`/`frame_release`/
     `frame_ref_count` 세 함수만 노출한다. `frame_release`는 "내가
     마지막 소유자였는가"를 `bool`로 직접 반환해(감소 후 값을 호출자가
     다시 해석하게 하지 않는다) 호출부 실수를 원천 차단한다 —
     `free_pages(order=0)`도 이 API로 갈아타 공유 중인 프레임은
     실제로 반환하지 않고 카운트만 줄인다.
  2. **PTE 소프트웨어 비트**: [page_table.hpp](../../kernel/arch/x86_64/page_table.hpp)의
     `page_perm`에 `cow`(비트 3, 실제 PTE에는 하드웨어가 무시하는
     bit 9로 인코딩)를 추가해 기존 `map_page`/`protect_page`/
     `query_page` 경로를 그대로 통과하게 만들었다 — 새 API를 따로
     만들지 않고 "권한 비트 하나 더" 취급만으로 충분했다. 이 비트가
     있고 write가 없는 페이지는 "권한이 없어서가 아니라 COW라 복사가
     필요할 뿐"이라는 뜻이다.
  3. **`clone_address_space_cow(src_pml4_phys)`**([page_table.cpp](../../kernel/arch/x86_64/page_table.cpp)):
     `create_address_space_root()`로 새 루트를 만든 뒤, 유저 영역(pml4
     index 1~255 — index 0의 저지대 GDT 항등 매핑과 256 이상의
     커널/physmap은 원본과 그대로 공유, `create_address_space_root`와
     동일 정책)만 4단계 전부(PDPT→PD→PT)를 직접 순회해 present인
     리프 페이지마다: 부모 PTE를 write 없이 값 다시 씀(재하강),
     자식에 같은 물리 페이지를 같은 권한(write 제외)+cow로 `map_page`,
     `mm::frame_add_ref` 1회. 이 프로젝트에 거대 페이지(2MiB/1GiB) 리프가
     전혀 없다는 사실(`walk_to_pt`가 항상 PT까지 내려간다) 덕분에
     4KiB 단위 순회만으로 충분하다.
  4. **쓰기 폴트 분기**: 새 파일 [page_fault.hpp](../../kernel/arch/x86_64/page_fault.hpp)/
     [.cpp](../../kernel/arch/x86_64/page_fault.cpp), IDT 벡터 14(`#PF`,
     idt.cpp가 이제 라우팅)로 진입한다. 진짜 로직은
     `try_handle_cow_write_fault_for(pml4_phys, fault_addr, error_code)`
     하나뿐이고, `try_handle_cow_write_fault(fault_addr, error_code)`는
     `sched::current()->owner_space`에서 pml4_phys를 뽑아 넘겨주는
     겉껍질이다(idt.cpp가 이걸 부른다) — 이렇게 나눈 이유는 실제
     fork() 시스템 콜이 아직 없는 이 마일스톤에서도(다음 단계) 진짜
     프로덕션 함수를 손으로 만든 부모/자식 주소공간에 직접 걸어
     QEMU에서 검증할 수 있게 하기 위해서였다(아래 검증 결과 참고).
     COW 표시 있는 present+비write 페이지에 대한 쓰기 폴트에서:
     `mm::frame_release(phys)`가 true(마지막 소유자)면 `protect_page`로
     쓰기 권한만 다시 켜고 끝(복사 없음, "fast-path") — false(아직
     다른 소유자)면 새 프레임에 memcpy 후 그쪽으로 `unmap_page`+
     `map_page` 재배선한다. COW 대상이 아니면(표시 없음, 이미 쓰기
     가능, not-present 등) false를 반환해 idt.cpp가 M10의 catch-all
     진단(`diagnose_and_halt`)으로 떨어뜨린다 — 유저에게 SIGSEGV류를
     전달하는 절차는 아직 없다(이 계획 범위 밖, 별도 OPEN 필요).
- **근거**: ADR-016이 "쓰기 폴트 시 페이지 프레임 분리"와 "참조
  카운트 관리"를 명시했지만 실제 자료구조·알고리즘·PTE 인코딩까지는
  정하지 않았다(당시엔 IDT/페이지폴트 핸들러 자체가 없었다,
  page_table.hpp M4 시절 주석 참고) — M12에서 실제로 필요해진
  지금, 기존 `page_perm`/`map_page`/`protect_page`/`query_page` API를
  최대한 그대로 재사용하는 쪽으로 설계해(새 API를 늘리지 않고) 코드
  표면을 작게 유지했다.
- **검증 결과(QEMU 실측, kernel_main.cpp::demo_frame_refcount/
  demo_cow_clone, tools/smoke-test-x86_64.sh)**:
  - `frame_add_ref` 2회 후 `frame_release` 3회 호출 시 앞의 2번은
    false(아직 소유자 있음), 마지막만 true — 설계한 계약대로 동작함을
    확인.
  - 부모 주소공간에 페이지 하나를 매핑하고 `clone_address_space_cow`
    호출 후, 부모/자식 모두 `write=0, cow=1`, 같은 물리주소,
    `frame_ref_count==1`(추가 소유자 1명)임을 확인.
  - `try_handle_cow_write_fault_for`를 자식 쪽에 먼저 걸면(부모가
    아직 있음) 새 프레임으로 복사되고(`refcount`가 다시 0으로),
    그 뒤 부모 쪽에 걸면(이제 유일한 소유자) 복사 없이 그대로 쓰기
    권한만 켜지는 fast-path를 탐을 로그로 직접 확인(둘 다 원래
    물리 페이지가 유지되는지/바뀌는지까지 검증).
  - **버그 발견·수정**: `page_fault.cpp` 최초 작성 시 `fault_addr &
    ~(mm::k_page_size - 1)`로 페이지 정렬을 계산했는데,
    `mm::k_page_size`가 `uint32_t`라 `~(k_page_size-1)`이 32비트
    마스크(`0xFFFFF000`)로 계산돼 `fault_addr`의 상위 32비트가 전부
    잘려 나갔다 — pml4 index 1(`1<<39`, 4GiB보다 훨씬 높은 주소)로
    데모를 처음 돌렸을 때 두 번의 `try_handle_cow_write_fault_for`
    호출이 모두 조용히 `false`를 반환하는 것으로 드러났다(하위
    4GiB 안의 주소만 다뤘다면 우연히 안 드러났을 것이다). `mm::
    k_page_size`를 `static_cast<uint64_t>`로 먼저 올려 수정.
  - **확인하지 못함**: 실제 `fork()` 시스템 콜을 통한 종단 간 흐름
    (유저 프로세스가 실제로 fork되어 CR3가 전환된 상태에서 하드웨어
    `#PF`가 발생하는 경로) — 이 ADR은 커널 프리미티브만 다룬다,
    시스템 콜 wiring은 이어지는 작업이다.
- **영향**:
  - `kernel/arch/x86_64/CMakeLists.txt`에 `page_fault.cpp` 추가.
  - `docs/spec/memory.md`/`docs/spec/objects.md`가 COW를 언급하는
    부분이 있다면 이 구현이 "쓰기 폴트 핸들러(IDT, M4 범위 밖)와
    프레임별 참조 카운트 저장소(mm이 아직 갖고 있지 않음)"라고 적어
    둔 전제(둘 다 미구현)를 갱신해야 한다 — page_table.hpp 상단
    주석은 이미 이 ADR 번호를 반영해 갱신했다.
  - `object::thread::owner_space`가 있는 실제 유저 스레드가 여러 개
    동시에 존재하고 서로 다른 코어에서 동시에 `#PF`를 낼 수 있게
    되는 시점(M12 이후, procsrv의 진짜 다중 프로세스)에는 프레임
    참조 카운트 테이블 자체에 락이 전혀 없다는 사실(현재는 BSP
    단일 코어 협조적 스케줄러라 안전, ADR-136의 handle_table과
    똑같은 처지)을 반드시 재검토해야 한다.

## ADR-141. syscall 진입 커널 스택을 스레드별로 분리(M8의 전역 스크래치 2개 제거)

- **상태**: 확정 (2026-09-10)
- **결정**: M8이 `syscall_entry.S`에 둔 전역 스크래치 두 개
  (`g_syscall_kernel_rsp`, `g_syscall_saved_user_rsp`)를 스레드별로
  분리한다.
  1. `object::thread`에 `syscall_kernel_rsp` 필드를 추가한다 —
     `create_user_thread()`가 그 스레드의 커널 스택을 할당하면서
     top 주소를 그대로 계산해 채워 둔다(고정값, 이후 안 바뀜).
  2. `kernel/core/sched/scheduler.cpp`에 `sync_syscall_kernel_rsp()`를
     추가해 `start()`/`yield()`/`block()`/`exit()`가 매번 다음
     스레드로 전환하기 직전에(`next_pml4_phys()`와 같은 자리) 전역
     `g_syscall_kernel_rsp`를 그 스레드의 값으로 맞춘다 — 커널
     스레드(`owner_space==nullptr`)는 건드리지 않는다.
  3. `g_syscall_saved_user_rsp`는 완전히 없앤다. `syscall_entry.S`가
     유저 RSP를 전역이 아니라 **그 스레드 자신의(1번 덕분에 이제
     스레드별로 분리된) 커널 스택 위에 직접 push**한다 — RCX/R11을
     push하는 것과 정확히 같은 방식.
- **근거**: M8 시절에는 유저 스레드가 정확히 하나(`initrun`)뿐이고
  그 스레드의 유일한 syscall(`sys_call`)도 서버가 이미 `sys_recv`로
  기다리고 있어 블로킹 없이 즉시 응답이 오는 데모 시나리오였다 —
  전역 스크래치 두 개로도 충돌이 날 여지가 없었다. 하지만
  ADR-140(COW)에 이어 실제 `fork()`가 생기면 유저 스레드가 2개
  이상 동시에 존재하고, 그중 하나가 `sys_call`/`sys_recv`로
  **블로킹된 채**(`sched::block()`을 거쳐 커널 콜스택 깊은 곳에
  멈춰 있는 상태) 다른 스레드가 또 syscall을 걸 수 있다 — 그 순간
  전역 스크래치 두 개는 "블록된 스레드가 나중에 재개될 때 읽을
  값"을 그새 다른 스레드가 덮어써 버린다(진짜 데이터 손상, 재현
  조건이 fork() 이전에는 아예 만들어지지 않아 M8~M11까지 드러날
  기회가 없었다). fork()를 실제로 구현하기 **직전**에 이 잠재
  버그를 먼저 없애 두는 편이, fork() 자체를 만들면서 동시에 이
  문제까지 진단하는 것보다 안전하다고 판단했다.
- **영향**:
  - `syscall_entry.S`의 `.bss` 심벌이 `g_syscall_kernel_rsp` 하나로
    줄었다 — `g_syscall_saved_user_rsp`를 참조하던 코드는 없었으므로
    (M8 이후 이 파일 안에서만 쓰였다) 다른 파일에 영향 없음.
  - `user_thread.cpp::arch_user_thread_trampoline()`이 더 단순해졌다
    (전역을 더 이상 직접 쓰지 않는다) — `sched::current()`로 자기
    자신을 찾아 `enter_usermode`만 호출한다.
  - **확인함**(QEMU, `tools/smoke-test-x86_64.sh` 전체 46개 +
    smp/numa/avx 스위트): 기존 M8 단일 유저 스레드 IPC Call 경로가
    이 변경 후에도 그대로 성공한다(실제 SYSCALL/SYSRET 왕복).
  - **확인하지 못함**: 정확히 이 ADR이 고치려 한 시나리오(유저
    스레드 2개, 한쪽이 블록된 채 다른 쪽이 syscall) 자체 — 아직
    fork()가 없어 유저 스레드가 2개 동시에 존재할 방법이 없다.
    fork()가 실제로 구현되면 그 시점에 반드시 실제로 재현·검증해야
    한다.

## ADR-142. sys_fork/sys_process_spawn/sys_exec/sys_thread_exit — 새 syscall 4종 + fork()의 레지스터 수준 POSIX 재현

- **상태**: 확정 (2026-09-10)
- **결정**: [OPEN-53](open-items.md)을 해소한다. 새 커널 파일
  [process_ops.hpp](../../kernel/arch/x86_64/process_ops.hpp)/
  [.cpp](../../kernel/arch/x86_64/process_ops.cpp)에 syscall 번호
  1~4를 배정한다([uapi.hpp](../../kernel/include/uapi.hpp)).
  1. **`sys_process_spawn`**(1, ADR-131이 이름만 정해 둠) —
     `process_spawn_request{elf_data, elf_size, argv_blob, argv_size,
     grant_trusted}`(a1 = 이 구조체의 유저 가상주소, 호출자 자신의
     주소공간이라 커널이 그대로 역참조). 완전히 새 주소공간+ELF
     로드+유저 스택(16KiB)+선택적 argv(한 페이지 이내, 읽기전용
     매핑)+새 유저 스레드를 만들어 enqueue까지 마친다. `grant_trusted`
     만이 새 신원의 trusted 여부를 정한다(ADR-074 "부여 권한" —
     fork와 달리 완전히 새로운 생성이므로).
  2. **`sys_fork`**(2) — 인자 없음. 호출자의 주소공간을
     `clone_address_space_cow`(ADR-140)로 복제하고, fd 테이블은
     **복제하지 않는다**(procsrv.md §3.6 — 소유 서버별 복제 요청은
     procsrv 자신의 몫, 커널은 자식에게 빈 handle_table만 준다).
     반환값은 부모 관점: 1=성공, 그 외 process_spawn_error. 자식은
     이 값을 syscall 반환으로 받지 않는다(§레지스터 재현 참고).
  3. **`sys_exec`**(3) — `exec_request{elf_data, elf_size, argv_blob,
     argv_size}`. 호출한 스레드의 `owner_space`를 완전히 새 주소공간
     +ELF로 교체하고, 그 자리에서 CR3를 직접 전환한 뒤
     `enter_usermode()`로 곧바로 진입한다(성공하면 반환하지 않음 —
     procsrv.md §4 6단계와 동일한 관례). **알려진 단순화**: 이전
     address_space와 그 페이지테이블/프레임은 회수하지 않고
     버려둔다(누수) — 회수는 이후 마일스톤.
  4. **`sys_thread_exit`**(4) — 인자 없음, `sched::exit()`을 그대로
     노출한다. 협조적 스케줄러에서 유저 스레드가 스스로 CPU를
     물러날 유일한 수단(아직 `sys_yield`는 없다 — 이 스레드가 다시
     실행될 필요가 없는 경우에만 쓸 수 있다).
  5. **fork()의 레지스터 수준 재현**(POSIX가 "두 번 반환하는 것처럼
     보이게" 하는 핵심) — `syscall_entry.S`가 이제 rflags/rip/
     user_rsp 3개(M12 이전)에 더해 rbx/rbp/r12~r15 콜리세이브
     6개까지 **총 9개**를 매 syscall마다 push/pop한다(일반
     syscall에는 아무 동작 변화가 없다 — syscall_dispatch가 SysV
     호출 규약상 이미 보존하던 값을 그대로 다시 pop할 뿐). 이 9개
     값의 시작 주소를 `%r8`로 `syscall_dispatch`에 넘겨(5번째
     인자) fork 케이스만 활용한다.
     `sched::create_forked_thread()`(scheduler.hpp/cpp)가 자식의
     손짜기 초기 스택에 이 9개를 **부모가 SYSCALL을 실행한 순간의
     실제 값 그대로**(0 아님) 채워 넣고, 새 arch 훅
     `arch_fork_child_resume`(syscall_entry.S)를 자식의 "복귀 주소"
     자리에 심는다 — `arch_context_switch`가 이 스레드로 처음
     전환할 때 자신의 6-레지스터 pop(rbp,rbx,r12~r15)을 이미 소비한
     뒤 `ret`으로 이 라벨에 뛰어들면, 남은 3개(rflags,rip,user_rsp)
     만 pop하고 RAX를 0으로 설정한 뒤 `sysretq`한다 — 그 결과
     자식은 부모가 `syscall` 명령을 실행한 바로 그 지점에서, 콜리
     세이브 레지스터까지 부모와 동일한 값으로 재개된다(RAX=0만
     다르다).
- **근거**: ADR-131이 이름만 정해 둔 `sys_process_spawn`을 실제로
  구현해야 M12가 진행 가능했고, procsrv가 자기 자신을 fork/exec할
  수 있으려면 fork()가 "그냥 자식이 0을 반환하고 끝"이 아니라
  실제로 **부모가 호출한 지점으로 되돌아가야** 한다 — 그러지 않으면
  procsrv의 평범한 C++ 코드(mc_fork() 같은 일반 함수 호출 형태)가
  자식 쪽에서 전혀 다른 동작을 하게 된다. rbx/rbp/r12~r15까지
  캡처/복원하는 이유: 이 값들은 SYSCALL 명령 자체가 전혀 건드리지
  않고 syscall_dispatch(C++ 함수 호출)도 SysV 규약상 보존하므로
  **캡처 시점에 물리 레지스터에 그대로 남아 있다** — 그래서
  syscall_entry.S에서 직접 push하는 것만으로 정확한 값을 얻을 수
  있다(별도로 "읽어내는" 코드가 필요 없다).
- **검증 결과(QEMU 실측)**: initrun 자신을 fork()한 뒤 자식이
  exec()으로 자기 자신을 다시 실행하고, 부모는 boot IPC call
  이후 process_spawn()으로 또 다른 사본을 띄우는 전체 흐름을
  실제로 확인했다 — `[process] fork ok` → (자식 스케줄) →
  `[process] exec ok entry=0x10000000` → (부모로 복귀) →
  `[process] spawn ok entry=0x10000000 trusted=0` 순서로 로그가
  남는다(`tools/smoke-test-x86_64.sh`에 세 줄 모두 추가, 49개 전부
  PASS). 이 과정에서 ADR-143/144/145(각각 별도 ADR) 세 가지 실제
  버그를 추가로 발견·수정해야 했다 — 자세한 진단 경위는 그쪽 참고.
- **영향**: `kernel/arch/x86_64/CMakeLists.txt`에 `process_ops.cpp`
  추가. `kernel/core/object/handle_table.hpp/.cpp`에
  `object::create_handle_table()` 공용 팩토리 추가(M4 시절
  kernel_main.cpp 전용이던 것을 공용화, process_spawn/fork 양쪽이
  씀). M12의 나머지(procsrv 자체, virtio-blk, cpio)는 여전히
  OPEN-54~57로 남아 있다.

## ADR-145. `create_address_space_root()`의 pml4[0] 공유 범위를 [0,8MiB)로 정확히 좁힌다

- **상태**: 확정 (2026-09-10)
- **결정**: `create_address_space_root()`가 `table[0] = pml4[0]`으로
  **pml4 index 0 전체**(가상주소 [0, 512GiB) 전부)를 공유하던 것을,
  이 주소공간 전용 `low_pdpt`/`low_pd`를 새로 만들어 GDT가 실제로
  필요로 하는 [0, 8MiB)(boot.S가 채운 `low_pd[0..3]`, 2MiB 거대
  페이지 4개) **내용만** 복사하는 방식으로 바꾼다. 그 외([8MiB,
  512GiB))는 이 주소공간만의 것으로 비워 둔다.
  [clone_address_space_cow()](kernel-memory.md#adr-140-adr-016-cow의-실제-커널-구현)
  (ADR-140)도 유저 영역 순회를 pml4 index **1**부터가 아니라
  **0**부터 시작하도록 고치고, index 0에서는 [0,8MiB)에 해당하는
  `i3==0 && i2<4`만 건너뛴다.
- **근거**: pml4 index 0은 하드웨어상 [0, 512GiB) 전체를 가리키는데,
  기존 설계(M8, ADR-121)는 "GDT 접근용으로 [0,8MiB)만 공유하면
  된다"는 **의도**였지만 실제 구현(`table[0] = pml4[0]`)은 그
  인덱스가 가리키는 PDPT 자체를 통째로 공유해 버려, [8MiB,
  512GiB) 전체(예: initrun의 링크 주소 `0x10000000` — link.ld가
  정한 값으로 여전히 pml4 index 0에 속한다)까지 함께 공유됐다.
  M8~M11은 유저 주소공간이 동시에 하나뿐이라 이 사실이 전혀
  드러나지 않았다 — M12에서 `sys_process_spawn`으로 **두 번째**
  독립 주소공간을 만들어 같은 링크 주소(0x10000000)에 매핑을
  시도하자, 첫 번째 주소공간이 이미 (공유된 테이블에) 채워 둔
  엔트리를 그대로 보고 `already_mapped`로 충돌하는 것을 실제로
  QEMU에서 재현했다.
- **검증 결과(QEMU 실측)**: 이 수정 전에는 `sys_process_spawn`이
  `load_elf`에서 `map_failed(already_mapped)`로 실패했다. 수정
  직후 같은 재현 절차가 `load_elf ok=1`로 성공했고, 이어서 발견된
  `clone_address_space_cow`의 index-0 스킵 버그(자식의 코드 페이지
  자체가 없어 명령어 페치가 not-present `#PF`로 죽는 문제)까지
  고치고서야 fork()도 완전히 성공했다 — 두 문제는 같은 근본 원인
  (index 0 처리 방식)에서 나온 두 개의 다른 증상이었다.
- **영향**:
  - `create_address_space_root()`가 이제 주소공간 하나당 2페이지
    (low_pdpt+low_pd)를 추가로 소비한다 — 무시할 수 있는 비용.
  - `kernel/arch/x86_64/boot/boot.S`의 `low_pdpt`/`low_pd`에
    `.global`을 추가해 `page_table.cpp`가 그 **내용**(물리
    프레임을 가리키는 거대 페이지 엔트리 값)만 읽어 가도록 노출
    했다 — 그 두 테이블 자체(포인터)는 여전히 boot 전용이며 그
    누구도 직접 쓰지 않는다.
  - ADR-121(모든 유저 주소공간이 저지대 항등 매핑을 공유해야
    한다는 결정)은 그대로 유지된다 — 이 ADR은 "공유의 정확한
    범위"만 좁혔을 뿐, "공유해야 한다"는 결론 자체는 바꾸지
    않았다.
