# 설계 결정: VFS·파일시스템

## ADR-018. fd 라우팅: open()만 VFS 경유, 이후 FS 서버와 직접 통신 (핸들 위임) (해결: OPEN-11)

- **상태**: 확정 (2026-09-08)
- **결정**: 경로 탐색과 마운트 판정(`open()`, `stat()` 경로 등)만 VFS 서버가 담당한다.
  성공하면 VFS는 대상 FS 서버의 커널 핸들(ADR-011)을 호출 프로세스에게 **위임**하고,
  이후 `read`/`write`/`close` 등은 프로세스가 해당 FS 서버와 **직접** 통신한다.
- **근거**: 모든 I/O가 VFS를 프록시로 거치면 VFS가 시스템 전체 처리량의 병목이자
  단일 장애점이 된다(ADR-008에서 서버를 분해한 취지와 정면으로 배치됨). 상대적으로
  드문 연산(경로 탐색)만 중앙화하고, 빈번한 I/O는 탈중앙화하는 편이 합리적이다.
- **영향**:
  - fd의 "진짜 소유자"는 각 FS/네트워크 서버이며, 프로세스의 커널 핸들 테이블
    (ADR-011)은 그 핸들의 로컬 별칭 역할을 한다.
  - fork 시(ADR-016) 프로세스 서버는 어떤 fd가 어떤 서버에 속하는지 알아야 하므로,
    fd 테이블에 서버 식별 메타데이터를 함께 보관해야 한다.
  - VFS가 다운되어도 이미 열린 fd의 read/write는 영향받지 않는다는 장점이 있다.
    다만 마운트 변경/권한 재검사가 필요한 시나리오는 FS 서버가 독자적으로 처리해야 한다.
  - VFS↔FS 간 "핸들 위임" 프로토콜과 FS 서버의 위임 유효성 검증 방식은
    spec 단계에서 상세 정의한다.

## ADR-044. VFS 전역 디렉토리 구성 확정

- **상태**: 확정 (2026-09-08)
- **결정**: 시스템 전체의 VFS 네임스페이스를 다음과 같이 확정한다.

  | 경로 | 의미 |
  |---|---|
  | `/` | VFS 루트 |
  | `/boot` | 부팅 루트 (커널 이미지, initrd 등) |
  | `/sys` | 운영체제를 구성하는 모든 요소·파일이 위치하는 루트 |
  | `/sys/proc` | 리눅스 procfs류 — 프로세스 상태 열람 |
  | `/sys/live` | 현재 구동 중인 설정·옵션·현황 전체. 외부 수정이 **즉시 반영**되어야 함 |
  | `/sys/etc` | 전역 시스템 설정(영속) |
  | `/sys/bin` | 전역 시스템 바이너리 |
  | `/sys/mnt` | 시스템 수준 마운트 루트 (USB, CDROM, 네트워크 경로 등) |
  | `/sys/dev` | 디바이스 노드 (ADR-048) |
  | `/sys/tmp` | 휘발성 스크래치 공간 (ADR-048) |
  | `/run` | 사용자별로 설치·관리할 수 없는 공용 설치 경로 (라이브러리·바이너리·설정) |
  | `/usr/{사용자명}` | 사용자별 격리 공간 — 라이브러리·바이너리·설정 전부 사용자마다 분리 |
  | `/usr/{사용자명}/home` | 사용자의 기본 작업 디렉터리 |

- **근거**: `/sys`를 "OS 구성요소 전체의 단일 루트"로 삼아 시스템 자체와
  사용자 영역을 명확히 분리하고, `/usr/{사용자명}`을 완전히 격리된
  사용자별 트리로 둬서 사용자 간 라이브러리·바이너리 의존성 충돌을
  구조적으로 없앤다. `/sys/live`는 sysfs/configfs류의 즉시 반영 계약을
  명시적으로 요구한다.
- **영향**: 이 구조는 **표준 FHS(Filesystem Hierarchy Standard)와
  의도적으로 다르다** — 특히 `/usr`(표준: 시스템 공용 자원)와 `/run`
  (표준: 휘발성 런타임 상태)의 의미가 재정의되었다. ADR-005(기존
  소프트웨어 포팅)와의 충돌은 ADR-045에서 다룬다.
- 구체적인 경로별 소유 서버, 마운트 방식은 [vfs-layout.md](../spec/vfs-layout.md)에서 정의한다.

## ADR-045. POSIX 경로 호환 전략: 소프트웨어별 패치로 대응

- **상태**: 확정 (2026-09-08)
- **결정**: ADR-044의 경로가 표준 FHS(`/usr/bin`, `/etc` 등)와 다른
  데서 오는 충돌은, VFS에 호환 심볼릭 링크 계층을 두는 대신 **포팅
  대상 소프트웨어마다 ADR-022의 패치 메커니즘으로 개별 대응**한다.
- **근거**: 심볼릭 링크 계층은 모든 경로 충돌을 영구히 감추지만,
  이 프로젝트가 지향하는 "직접 설계한 시스템"(ADR-001)의 정체성과
  어긋난다 — 표준 경로를 흉내 내는 호환 레이어보다, 포팅되는
  소프트웨어가 minicore의 실제 경로를 알고 동작하는 편이 장기적으로
  더 투명하다. ADR-022가 이미 서드파티 소스별 패치 디렉토리 구조를
  갖추고 있어 추가 메커니즘이 필요 없다.
- **영향**:
  - 포팅 착수 시 각 소프트웨어의 하드코딩된 경로(`/usr/bin`,
    `/usr/lib`, `/etc` 등)를 ADR-044의 실제 경로로 바꾸는 패치를
    `third_party/patches/<project>/`에 추가해야 한다.
  - `libc`의 `sysdeps/minicore`(repo-layout.md)에 기본 검색 경로
    상수(예: 동적 링커의 라이브러리 탐색 경로)를 ADR-044 기준으로
    정의해, 대부분의 소프트웨어가 별도 패치 없이 링크·실행되게 한다.
  - 완전히 패치 없이 포팅 가능하다고 보장하지 않는다 — 이는 이
    프로젝트가 받아들인 트레이드오프다.

## ADR-047. 합성(synthetic) 파일시스템: 담당 서버가 FS 서버 역할 겸임

- **상태**: 확정 (2026-09-08)
- **결정**: `/sys/proc`, `/sys/live`처럼 정적 저장 매체가 없는 합성
  파일시스템은, 별도의 통합 sysfs류 서버를 두지 않고 **해당 주제를
  담당하는 기존 서버가 ADR-018의 FS 서버 프로토콜을 직접 구현**하는
  방식으로 제공한다. 예: 프로세스 서버(procsrv)가 `/sys/proc`의
  FS 서버 역할을 겸한다.
- **근거**: ADR-018이 이미 "VFS는 경로 탐색만, 실제 FS 서버가 나머지"
  구조를 정해두었다. 별도의 통합 sysfs 서버를 추가하면 그 서버가
  다시 모든 주제별 서버와 통신해야 하는 간접 계층이 하나 더 생긴다 —
  각 서버가 이미 자신의 상태를 가장 잘 알고 있으므로 직접 노출하는
  편이 계층을 줄인다.
- **영향**:
  - `/sys/live`처럼 여러 서비스의 상태를 아우르는 경로는, VFS의
    마운트 테이블에서 하위 경로별로 서로 다른 서버에 위임되도록
    구성해야 한다(예: `/sys/live/network`는 netsrv, `/sys/live/sched`는
    커널 노출용 별도 서버 등) — 즉 `/sys/live`는 여러 개의 하위
    마운트가 모인 지점이지 단일 서버가 통으로 서빙하는 트리가 아니다.
  - "외부에서 수정하면 즉각 반영"(ADR-044) 요구사항은 각 담당 서버가
    `write()` 요청을 받는 즉시 자신의 실제 상태를 변경하는 것으로
    구현한다 — 캐싱이나 지연 반영을 두지 않는다.
  - 각 서버가 FS 서버 프로토콜(lookup/read/write/getattr, ADR-008 영향
    항목)을 구현해야 하므로, 그 프로토콜을 최대한 작고 구현하기 쉽게
    유지해야 하는 압력이 커진다.

## ADR-048. /dev, /tmp: /sys 아래로 통합

- **상태**: 확정 (2026-09-08)
- **결정**: 디바이스 노드는 `/sys/dev`, 휘발성 스크래치 공간은
  `/sys/tmp`에 위치한다 (표준 FHS의 `/dev`, `/tmp`와 달리 루트
  직속이 아니다).
- **근거**: ADR-044의 "`/sys` = OS를 구성하는 모든 것"이라는 원칙을
  예외 없이 지킨다 — 디바이스 노드도, 휘발성 공간도 OS가 제공하는
  구성요소이므로 `/sys` 바깥에 둘 이유가 없다.
- **영향**:
  - `/sys/dev`는 devmgr가 FS 서버 역할을 겸해 제공한다(ADR-047과
    같은 패턴) — PCIe 등에서 열거된 장치가 여기 노드로 나타난다.
  - `/sys/tmp`는 memfs(ADR-008 수직 슬라이스에서 이미 계획된
    메모리 파일시스템)를 그대로 마운트해서 구현할 수 있다 — 새로운
    FS 구현이 필요 없다.
  - ADR-045의 패치 대상에 `/dev`, `/tmp`를 하드코딩한 소프트웨어도
    포함된다 — 사실상 거의 모든 POSIX 소프트웨어가 해당하므로,
    `libc`의 `sysdeps/minicore` 표준 경로 상수(ADR-045 영향 항목)에
    이 두 경로도 반드시 포함해야 한다.

## ADR-050. 사용자별 트리의 마운트 형태: 서브디렉토리가 기본, 별도 마운트도 허용

- **상태**: 확정 (2026-09-08)
- **결정**: `/usr/{사용자명}`은 다른 VFS 경로와 다르게 특별 취급하지
  않는다. 기본적으로는 `/usr`를 구성하는 FS의 평범한 서브디렉토리이지만,
  필요하면 특정 사용자의 트리를 별도 마운트(전용 볼륨, 쿼터 적용
  파티션, 네트워크 홈 등)로 대체할 수도 있다 — 사용자마다 다르게
  선택해도 된다(어떤 사용자는 서브디렉토리, 어떤 사용자는 별도 마운트).
- **근거**: 전통적 Unix에서도 `/home`이 별도 파티션일 수도, 루트 FS의
  일부일 수도 있는 것과 같은 유연성이다. ADR-018의 VFS 구조(임의의
  경로가 마운트 지점이 될 수 있음)가 이미 이 능력을 자연스럽게
  제공하므로, 사용자 트리만을 위한 별도 규칙을 둘 필요가 없다.
- **영향**:
  - VFS 마운트 테이블은 "이 경로가 마운트 지점인가"만 검사하면 되고,
    사용자 계정 생성과 마운트 여부를 별개로 다룬다 — procsrv가 사용자
    생성 시 서브트리를 초기화(디렉토리 생성)하는 경로와, 관리자가
    특정 사용자에게 전용 볼륨을 마운트해주는 경로가 동일한 마운트
    테이블 메커니즘을 공유한다.
  - 사용자별 격리(ADR-044)는 마운트 여부와 무관하게 네임스페이스
    분리만으로 이미 달성된다 — 별도 마운트는 순전히 운영상의 선택
    (쿼터, 성능 격리, 백업 단위 분리 등)이다.
  - [vfs-layout.md](../spec/vfs-layout.md)의 관련 "아직 정하지 않은
    것" 항목을 이 결정으로 대체한다.

## ADR-058. /sys/live 최소 매핑표 확정: network·sched·mem (해결: OPEN-28)

- **상태**: 확정 (2026-09-08)
- **결정**: `/sys/live` 하위에 최소 다음 항목을 지금 확정한다
  (vfs-layout.md §1/§5의 예시를 정식 채택):

  | 하위 경로 | 담당 서버 |
  |---|---|
  | `/sys/live/network` | netsrv |
  | `/sys/live/sched` | procsrv (스레드·스케줄링 상태 노출까지 겸임) |
  | `/sys/live/mem` | 정책 서버 (ADR-024, 메모리 쿼터·할당 현황) |

  이후 서비스가 늘어나면 이 표에 하위 경로를 추가하는 방식으로
  확장한다. `/sys/proc`(프로세스 목록)은 이 표와 별개로 이미
  ADR-047에서 procsrv 담당으로 정해져 있다 — `/sys/live/sched`는
  "프로세스 목록"이 아니라 "스케줄링 파라미터·현황"이라는 점에서
  다르다.
- **근거**: 새 서버(예: "schedsrv")를 신설하지 않고 기존 서버가
  겸임하는 ADR-047의 원칙을 그대로 따른다 — procsrv는 이미 스레드를
  다루므로 스케줄링 상태 노출의 자연스러운 소유자다.
- **영향**: `vfs-layout.md`의 관련 "아직 정하지 않은 것" 항목을 이
  결정으로 대체한다. 각 경로의 정확한 하위 키·값 형식은 해당 서버가
  실제로 설계되는 시점에 정의한다.

## ADR-059. /sys/mnt 시스템 마운트 권한: root 권한 프로세스의 명시적 요청만

- **상태**: 확정 (2026-09-08)
- **결정**: `/sys/mnt` 아래에 시스템 수준 마운트(USB, CDROM, 네트워크
  경로 등)를 트리거할 수 있는 것은 **root 권한 프로세스의 명시적
  요청**뿐이다. devmgr가 매체 삽입을 감지하더라도 자동으로 마운트를
  수행하지 않는다 — 감지와 마운트 실행 권한을 분리한다.
- **근거**: ADR-056(드라이버 충돌 해소)이 이미 root 전용 오버라이드
  경로를 도입했다 — 동일한 신뢰 모델(root의 명시적 개입)을 시스템
  마운트에도 일관되게 적용한다. 자동 마운트를 기본으로 허용하면
  외부 매체 삽입만으로 공격 표면이 넓어진다.
- **영향**:
  - devmgr는 매체 삽입을 감지하면 `/sys/live`(ADR-058) 또는
    `/sys/dev`(ADR-048)를 통해 "마운트 가능한 장치가 나타났다"는
    사실만 노출하고, 실제 마운트는 별도의 root 전용 syscall/IPC
    요청으로 트리거된다.
  - 사용자 세션에서 "USB 꽂으면 자동으로 열리는" 편의 기능이 필요하면,
    root 권한을 가진 별도의 유저 세션 데몬(예: 데스크톱 환경의
    자동마운트 서비스)이 이 root 전용 경로를 대신 호출하는 형태로
    구현해야 한다 — 커널·devmgr 차원의 자동 마운트는 없다.

## ADR-065. /home: /usr/{사용자명}/home으로의 VFS 경로 별칭(오버레이)

- **상태**: 확정 (2026-09-08)
- **결정**: 표준 FHS 관례를 따르는 `/home`을 VFS 루트에 추가하되,
  이는 실체 저장소가 아니라 **VFS 경로 별칭(alias)**이다.
  `/home/{사용자명}`에 대한 모든 조회는 VFS가 조회 단계에서
  `/usr/{사용자명}/home`으로 **재작성(rewrite)**한 뒤, 그 다음부터는
  평범하게 ADR-018의 경로 탐색·핸들 위임을 수행한다. `/home` 자체를
  나열(list)하면 `/usr` 아래의 사용자 이름 목록과 동일한 결과를
  보여준다.
- **근거**: 대부분의 POSIX 소프트웨어·스크립트가 `$HOME` 경로 감지,
  홈 디렉토리 존재 확인 등에 `/home/{user}` 패턴을 광범위하게
  가정한다. ADR-045는 일반적으로 심볼릭 링크·오버레이 호환 계층
  대신 소프트웨어별 패치를 원칙으로 삼았지만, `/home`은 **VFS
  레벨의 단일 별칭 규칙 하나**로 극히 많은 소프트웨어의 호환성
  문제를 한 번에 해소할 수 있어 비용 대비 효과가 뚜렷한 예외다 —
  ADR-045의 원칙을 부정하는 것이 아니라, 그 원칙이 "패치보다 별칭이
  압도적으로 싸게 먹히는" 이 한 가지 경로에 한해 의도적으로 예외를
  두는 것이다.
- **영향**:
  - VFS 경로 탐색(ADR-018)에 별칭 재작성 단계가 추가된다 — `/home`
    프리픽스는 조회 시점에 `/usr`로 치환되고, 사용자명 세그먼트
    다음에 암묵적으로 `home`이 삽입된다:
    `/home/alice/docs` → `/usr/alice/home/docs`.
  - 이 별칭은 읽기·쓰기에 대칭적으로 적용된다 — `/home/alice`에
    쓰는 모든 것은 실제로 `/usr/alice/home`에 쓰여진다.
  - `/home`(사용자명 없이) 나열은 `/usr`의 사용자 디렉토리 이름
    집합을 그대로 반환한다.
  - ADR-050(사용자 트리는 서브디렉토리 또는 별도 마운트 가능)과
    자연스럽게 결합한다 — 별칭은 순수 경로 재작성이므로
    `/usr/{사용자명}`이 어떤 방식으로 마운트되어 있든 그대로 통한다.
  - 이 별칭 규칙은 **VFS 서버 자체가 소유**한다 — 새로운 FS 서버나
    synthetic 마운트(ADR-047)가 필요 없다. 순수 경로 재작성이라
    별도 서버 위임조차 불필요하다.

## ADR-080. VFS 마운트 네임스페이스 + 에페메럴 오버레이

- **상태**: 확정 (2026-09-08)
- **결정**: 지금까지 가정한 "프로세스 전부가 하나의 전역 마운트
  테이블을 공유"하는 모델에, 프로세스(또는 프로세스 그룹)별로
  격리된 **마운트 네임스페이스**를 만들 수 있는 능력을 추가한다.
  1. 네임스페이스는 "경로 탐색 시 어떤 마운트 테이블을 참조하는가"를
     프로세스별로 다르게 만드는 것이다 — 기본값은 지금까지처럼 모든
     프로세스가 하나의 전역 네임스페이스를 공유하며, 특정 프로세스만
     별도 네임스페이스를 배정받을 수 있다(procsrv가 프로세스 생성
     시점에 지정).
  2. 네임스페이스는 **에페메럴 오버레이**로 구성할 수 있다 — 읽기는
     하위(전역) 네임스페이스로 그대로 통과(pass-through)시키되,
     쓰기(생성·수정·삭제)는 이 네임스페이스 전용의 휘발성 memfs
     레이어에만 기록한다(copy-on-write). 오버레이 레이어는 네임스페이스가
     파괴될 때(예: 프로세스 종료) 함께 사라지며, 하위 전역 상태는
     전혀 변경되지 않는다.
  3. 네임스페이스는 **경로별 패스스루(passthrough) 규칙**을 가질 수
     있다 — 특정 서브트리는 오버레이를 건너뛰고 하위 전역 네임스페이스에
     읽기·쓰기 모두 직접 연결된다.
- **근거**: 컨테이너/overlayfs류가 널리 쓰는 "읽기는 통과, 쓰기는
  격리"패턴을 재사용한다 — 새로 발명한 개념이 아니다. ADR-018이 이미
  "VFS는 경로 탐색만 담당"으로 정해두었으므로, 네임스페이스·오버레이
  판정도 결국 경로 탐색 단계에 판단 로직을 하나 더 추가하는 것뿐이라
  새로운 아키텍처 계층이 필요 없다. `/sys/tmp`(ADR-048)가 이미 memfs를
  마운트로 재사용하는 선례와도 같은 방향이다 — memfs를 오버레이
  레이어의 백엔드로 그대로 재사용할 수 있다.
- **영향**:
  - [vfs-layout.md](../spec/vfs-layout.md)에 네임스페이스/오버레이 개념을
    반영해야 한다(다음 vfs-layout.md 갱신 대상).
  - 네임스페이스 생성·파괴의 정확한 API(procsrv가 프로세스 생성
    syscall/IPC의 일부로 지정하는지, 별도 syscall인지)와 오버레이
    레이어의 정확한 자료구조(경로별 diff 기록 방식)는 VFS 상세 설계
    시점에 정한다 — 이 ADR은 개념 자체와 "경로별 패스스루" 정책까지만
    고정한다.
  - 이 메커니즘의 첫 실사용처는 [security-model.md](security-model.md)의
    jail 정책(ADR-081)이다.

## ADR-099. 유저 영역 파일시스템(FUSE/Dokan류)은 새 계층이 필요 없다 — 이미 있는 FS 서버 프로토콜이 곧 그것이다

- **상태**: 확정 (2026-09-08)
- **결정**: NAS·네트워크 스토리지·기타 외부 연동을 위한 "유저 영역
  파일시스템 드라이버"를 향후 추가할 때, Linux의 FUSE나 Windows의
  Dokan 같은 **별도의 커널 통과(passthrough) 계층을 새로 만들지
  않는다.** ADR-018/047이 이미 정한 "FS 서버는 그냥 lookup/read/
  write/getattr 프로토콜을 구현하는 평범한 유저 프로세스"라는 모델
  자체가 이미 FUSE/Dokan과 동일한 역할을 한다 — memfs, FAT32와
  똑같이 새 FS 서버 하나를 추가하고 VFS에 마운트하면 된다.
- **근거**: 사용자가 "NAS나 외부 연동을 쉽게 구현하려면 Dokan/FUSE
  같은 레이어가 필요하다"고 지적했다. 그러나 Linux/Windows에서
  FUSE/Dokan이 필요한 이유는 그 커널들이 특권 계층(커널 모드) VFS를
  갖고 있어 "커널 밖(유저 모드)에서도 파일시스템을 구현할 수 있게
  해주는 우회로"가 별도로 필요하기 때문이다. minicore는 애초에
  ADR-006/007/008에 따라 **모든** 파일시스템이 유저 프로세스로만
  구현되므로(커널에는애초에 특권 FS 구현이 존재하지 않는다), 우회로
  자체가 필요 없다 — 이 프로젝트의 마이크로커널 구조가 이미 FUSE가
  풀려는 문제를 구조적으로 갖고 있지 않다.
- **영향**:
  - 미래에 NAS/네트워크 연동 FS 서버를 실제로 만들 때는, ADR-043의
    드라이버 로드맵에 새 항목을 추가하는 것으로 충분하다 — 새로운
    설계 결정이 필요 없다.
  - 새로운 커널 syscall이나 VFS 프로토콜 확장도 필요 없다 — 지금
    설계만으로 이미 지원된다.

## ADR-100. SWAPFS: 스왑을 필수 구현 대상으로 확정, FS 서버 형태로 구현

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 스왑(가상 메모리를 디스크로 확장하는 기능)은 이 프로젝트에서
     **선택이 아니라 필수 구현 대상**으로 확정한다 — 로드맵에서
     무기한 미루는 대상이 아니다.
  2. 스왑은 ADR-099의 원칙을 그대로 따라 **커널 내부의 특별한
     메커니즘이 아니라, 다른 파일시스템과 동일하게 FS 서버 프로토콜
     (ADR-018/047)을 구현하는 유저 프로세스**(가칭 `swapfs`,
     `servers/fs/swapfs`)로 구현한다 — memfs/FAT32와 같은 층.
  3. 커널의 물리 페이지 할당자([kernel-memory.md](kernel-memory.md),
     ADR-012/033/036/054)는 메모리 압박 시 페이지를 SWAPFS로
     내보내고(evict), 필요할 때 다시 불러오는(fault-in) 경로를
     가져야 한다 — 정확한 프로토콜·정책(어떤 페이지를 언제 내보낼지
     등)은 이 ADR의 범위 밖이며 실제 착수 시점에 별도 설계한다.
  4. [registry-decisions.md](registry-decisions.md) ADR-063이 이미
     예고한 제약 — **trusted 프로세스의 페이지는 스왑 대상에서
     절대 제외**한다 — 는 SWAPFS 설계의 확정된 전제 조건으로 그대로
     유지된다.
- **근거**: 사용자가 스왑을 필수 구현 대상으로 명시했다. FS 서버
  형태로 구현하는 것은 ADR-099가 이미 확립한 "저장소 관련 기능은
  커널 특권이 아니라 유저 FS 서버"라는 원칙을 스왑에도 일관되게
  적용한 것뿐이다 — 새로운 아키텍처 예외를 만들지 않는다.
- **영향**:
  - `kernel-bootstrap.md`(M1~M8)나 이후 계획에 SWAPFS 착수를 위한
    마일스톤이 언젠가 추가되어야 한다 — 정확한 우선순위(드라이버
    로드맵 ADR-043과의 관계 등)는 실제 계획 수립 시점에 정한다.
  - 물리 메모리 할당자(ADR-012)와 정책 서버(ADR-024, 쿼터)가 스왑
    압박 상황을 어떻게 반영하는지는 완전히 미정이다 → 신규
    **미결정 (OPEN-44)**.
  - 페이지 폴트 처리(스왑아웃된 페이지 재적재)를 위한 커널-유저 간
    프로토콜은 [objects.md](../spec/objects.md)/[memory.md](../spec/memory.md)의
    후속 갱신 대상이다.

## ADR-101. 파일 잠금과 오픈 시점 공유 모드는 FS 서버 프로토콜의 통제 가능한 옵션이다

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. **오픈 시점 공유 모드(sharing mode)**: `open()`(ADR-018) 호출자는
     자신이 이 핸들을 여는 동안 다른 프로세스의 동시 접근을 어디까지
     허용할지(읽기 허용/쓰기 허용/삭제 허용, 또는 전부 거부·독점)
     지정할 수 있다 — Windows `CreateFile`의 공유 모드와 유사한
     개념이다. 소유 FS 서버는 새 `open()` 요청이 기존에 열려 있는
     핸들들의 공유 모드와 충돌하면 그 요청을 거부한다(공유 위반
     오류).
  2. **명시적 파일 잠금(advisory lock)**: 이미 열린 핸들에 대해
     별도로 공유(shared)/배타(exclusive) 잠금을 요청·해제할 수 있는
     오퍼레이션을 FS 서버 프로토콜에 둔다 — 전통적 POSIX `flock`/
     `fcntl(F_SETLK)`류와 대응되며, 포팅된 소프트웨어(ADR-005)와의
     호환성을 위해 필요하다. Advisory이므로 이 오퍼레이션을 거치지
     않고 직접 읽고/쓰는 것 자체를 막지는 않는다 — 협조적인 클라이언트
     간의 합의 메커니즘이다.
  3. 두 메커니즘 모두 **소유 FS 서버가 직접 구현·집행**한다(ADR-018의
     "VFS는 경로 탐색만" 원칙과 일치 — 공유 모드/잠금 상태는 파일별
     서버측 상태이므로 [procsrv.md](../spec/procsrv.md) §4.1의
     `open_file_id`와 함께 관리된다) — VFS나 커널은 관여하지 않는다.
- **근거**: 사용자가 "파일 lock과 런타임 IO 공유 정책도 제어 가능해야
  한다"고 명시했다. Windows류 공유 모드와 POSIX류 advisory lock을
  둘 다 지원하는 이유는, 전자는 "동시 접근 자체를 열 때부터 거부"하는
  강한 통제를, 후자는 "이미 연 뒤 협조적으로 조율"하는 유연한 통제를
  대표해 서로 보완적이기 때문이다 — 포팅 대상 소프트웨어(ADR-005)
  상당수가 POSIX lock을 가정하므로 이것 없이는 호환성이 깨진다.
- **영향**:
  - FS 서버 공통 프로토콜(ADR-018 §영향에서 "spec 단계에서 상세
    정의"라고 미뤄둔 부분)에 공유 모드 플래그와 lock/unlock
    오퍼레이션을 포함해야 한다 — 아직 이 프로토콜 자체의 전용 스펙
    문서가 없으므로, 실제 작성 시점(가칭 `docs/spec/fs-protocol.md`)에
    이 ADR을 구현한다.
  - procsrv.md §2의 `fd_entry`/`open_file_id` 개념이 이 잠금·공유
    상태의 식별 키로 재사용된다 — 새 자료구조가 필요 없다.
  - 잠금 범위(파일 전체 잠금만 지원할지, `fcntl`류의 바이트 범위
    잠금까지 지원할지)는 이 ADR의 범위 밖이다 → 신규 **미결정
    (OPEN-45)**.

## ADR-102. 파일 잠금 범위: 파일 전체 단위만 지원, 바이트 범위 잠금은 지원하지 않음 (해결: OPEN-45)

- **상태**: 확정 (2026-09-08)
- **결정**: ADR-101의 명시적 파일 잠금(advisory lock)은 **파일 전체
  단위**로만 동작한다 — `fcntl(F_SETLK/F_SETLKW)`류의 바이트 범위
  (byte-range) 잠금은 지원하지 않는다. 잠금 요청은 항상 "이 파일
  전체를 공유/배타로 잠근다"는 의미이며, 오프셋·길이 인자를 받지
  않는다.
- **근거**: 사용자가 명시적으로 "파일 단위로만 가능하면 충분하다"고
  정했다. 바이트 범위 잠금은 구현 복잡도(겹치는 범위 추적, 잠금
  분할/병합, 잠금 해제 시 범위 재계산)에 비해 이 프로젝트의 실제
  필요(포팅 소프트웨어 호환성, ADR-005)를 크게 넘어선다 — 대부분의
  소프트웨어는 파일 전체 잠금만으로 충분히 동작한다.
- **영향**:
  - `fcntl`을 바이트 범위와 함께 호출하는 포팅 소프트웨어는, libc의
    `sysdeps/minicore` 계층에서 범위 인자를 무시하고 파일 전체
    잠금으로 근사하거나, 그런 소프트웨어는 ADR-049에 따라 대체
    구현을 검토할 대상이 될 수 있다 — 구체적 매핑 전략은 libc 포팅
    시점에 정한다.
  - ADR-101의 lock/unlock 오퍼레이션 시그니처에서 오프셋·길이
    필드를 제외한다(FS 서버 프로토콜을 실제로 작성할 때 반영).
  - OPEN-45는 이 ADR로 해소된다.

## ADR-103. SWAPFS 백엔드: 스왑 파티션과 스왑 파일 두 가지를 모두 지원 (ADR-100 갱신)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. SWAPFS(ADR-100)는 하나 이상의 **스왑 영역(swap area)**을
     관리하며, 각 영역은 다음 두 종류 중 하나다:
     - **스왑 파티션**: devmgr가 노출하는 원시 블록 장치 노드
       (`/sys/dev/blk{N}`, ADR-048)를 SWAPFS가 직접 열어 그 블록
       범위 전체를 스왑 슬롯으로 사용한다 — 파일시스템 계층을
       거치지 않는다.
     - **스왑 파일**: 이미 마운트된 임의의 파일시스템 위의 평범한
       파일(예: `/sys/swap/swapfile`)을 SWAPFS가 VFS를 통해 평범한
       클라이언트로서 열고, 그 파일의 바이트 범위를 스왑 슬롯으로
       사용한다 — 이 경우 SWAPFS 자신도 다른 FS 서버(memfs/FAT32/
       향후 다른 FS)의 평범한 클라이언트가 된다.
  2. 어떤 스왑 영역을 사용할지는 `@global/system/swap` 레지스트리
     테이블(항목: 종류(`partition`/`file`), 대상 경로 또는 블록
     장치 식별자 — super만 쓰기 가능)로 설정한다.
  3. 두 종류 모두 SWAPFS 입장에서는 "고정 크기 슬롯의 배열"이라는
     동일한 내부 추상화로 다뤄진다 — 물리 페이지 할당자
     ([kernel-memory.md](kernel-memory.md))가 SWAPFS와 주고받는
     프로토콜(ADR-100 §결정 3)은 스왑 영역의 종류를 몰라도 된다.
- **근거**: 사용자가 "스왑 파티션과 스왑 파일 두 가지 종류가 있다"고
  명시했다 — Linux의 전통적인 스왑 모델과 동일하다. 파티션은 별도
  FS 계층 없이 최고 성능을 내고, 파일은 별도 파티션을 미리 마련하지
  않고도(설치 이후에도) 유연하게 스왑 공간을 조정할 수 있다는 서로
  다른 장점이 있어 둘 다 지원할 가치가 있다. 스왑 파일을 "SWAPFS가
  다른 FS 서버의 평범한 클라이언트가 되는" 방식으로 구현하는 이유는
  ADR-099의 원칙("저장소 관련 기능은 유저 FS 서버")과 정확히 같은
  재사용 논리다 — SWAPFS가 다른 파일시스템의 내부 구현을 알 필요가
  없다.
- **영향**:
  - `@global/system/swap` 레지스트리 스키마를
    [registry.md](../spec/registry.md) 갱신 시점에 반영해야 한다.
  - SWAPFS의 내부 슬롯 추상화(파티션/파일 공통 인터페이스)와 여러
    스왑 영역 간 배치 정책(우선순위, 라운드로빈 등)은 이 ADR의
    범위 밖이며 실제 SWAPFS 설계 착수 시점에 정한다.
  - 스왑 파일 방식은 그 파일이 위치한 파일시스템이 아직 마운트되지
    않은 부팅 극초기에는 사용할 수 없다 — 스왑 활성화 시점(부팅
    절차 어디쯤인지)은 initrun 기동 매니페스트(OPEN-29)와 맞물린
    후속 결정 대상이다.

## ADR-128. FS 서버 공통 프로토콜에 파일 신원(node id) 개념 도입 — FS별 매핑은 서버 재량

- **상태**: 확정 (2026-09-09)
- **결정**: ADR-018/ADR-101이 이미 전제하지만 한 번도 명시적으로
  정의된 적 없는 개념을 지금 확정한다 — FS 서버 공통 프로토콜(아직
  미작성인 `docs/spec/fs-protocol.md`, ADR-018 §영향이 이미 그
  존재를 예고함)에 **파일 신원을 나타내는 불투명한 64비트 값
  `fs_node_id`**를 추가한다.
  1. `fs_node_id`는 **"이 값이 같으면 같은 파일이다"**만 보장하는
     식별자다 — 그 이상의 의미(정렬 가능성, 재사용 여부, 디스크상
     실제 위치와의 대응)는 FS 서버마다 자유롭다.
  2. `stat()`류 오퍼레이션의 반환값에 포함되어 `open_file_id`(procsrv.md
     §4.1, "열린 파일 서술자")와는 **별개 개념**임을 명확히 한다 —
     `open_file_id`는 "이 오픈 인스턴스"를, `fs_node_id`는 "이
     디스크상의 파일 자체"를 가리킨다. 서로 다른 두 `open_file_id`가
     같은 `fs_node_id`를 가리킬 수 있다(같은 파일을 두 프로세스가
     독립적으로 연 경우) — ADR-101의 공유 모드 충돌 검사가 실제로
     성립하려면 FS 서버가 "이 open() 요청이 이미 열려 있는 어떤
     파일과 같은 파일을 가리키는가"를 판별할 수 있어야 하는데, 이
     판별의 열쇠가 바로 `fs_node_id`다.
  3. 각 FS 서버의 매핑 전략:
     - **ext4**: 네이티브 inode 번호를 그대로 쓴다 — 포맷 자체가
       이미 이 개념을 갖고 있어 추가 작업이 없다.
     - **FAT32**: 네이티브 개념이 없다 — 파일의 **첫 클러스터
       번호**를 `fs_node_id`로 합성한다(볼륨 내에서 안정적이고
       유일하다). 예외: 크기 0인 파일은 클러스터가 할당되지 않아
       첫 클러스터 값이 전부 0으로 충돌한다 — 이 경우 "부모 디렉터리
       클러스터 번호 + 그 디렉터리 안에서의 항목 오프셋"을 조합해
       구분한다(여러 실존 FAT 드라이버가 쓰는 잘 알려진 우회다).
     - **memfs**: 파일 생성 시 발급하는 단조증가 카운터 — 디스크
       개념이 없어 가장 단순하다.
- **근거**: 사용자가 M16(ext4 추가)을 검토하며 "inode 개념 또는
  매칭되는 설계 구조가 필요하다"고 정확히 지적했다 — 확인해보니
  ADR-101(공유 모드/잠금)이 "같은 파일인지 판별"을 이미 암묵적으로
  요구하면서도 그 판별 수단 자체는 한 번도 정의된 적이 없었다(순수
  FAT32 하나만 다룰 때는 첫 클러스터 번호를 즉석에서 써도 됐겠지만,
  ext4처럼 진짜 inode 번호를 갖는 FS가 섞이면 "FS마다 다른 정체불명의
  값"을 VFS/procsrv 계층까지 새어나가지 않게 **불투명한 공통 타입으로
  추상화**해 둬야 두 FS를 같은 프로토콜로 다룰 수 있다). VFS 계층
  (ADR-018)에 진짜 inode 캐시나 vnode 계층을 두지 않고 "불투명한
  64비트 값 + FS 서버가 알아서 판별"이라는 최소한만 정의한 이유는,
  ADR-018이 이미 "VFS는 경로 탐색만, 그 외 상태는 FS 서버가 직접
  소유"라는 원칙을 확정해뒀기 때문 — 이 ADR은 그 원칙 위에 딱 필요한
  개념 하나만 얹을 뿐, VFS를 무겁게 만들지 않는다.
- **영향**:
  - `docs/spec/fs-protocol.md`(아직 미작성, ADR-018 §영향이 예고한
    문서)를 실제로 작성하는 시점에 `fs_node_id`를 `stat()` 반환
    구조체 필드로 포함해야 한다.
  - M13(memfs)·M16(FAT32/ext4) 각 FS 서버 구현 시 위 매핑 전략을
    그대로 적용한다 — 이 ADR이 이미 세 가지 모두를 결정해뒀으므로
    각 마일스톤에서 새로 고민할 필요가 없다.
  - 하드링크(같은 `fs_node_id`를 가리키는 서로 다른 디렉터리 항목)는
    ext4에서는 네이티브로 가능하지만 FAT32는 애초에 지원하지 않는
    개념이라 자연히 막힌다 — VFS/procsrv 계층이 하드링크 생성
    오퍼레이션 자체를 어느 FS에서 허용할지는 이 ADR의 범위 밖(FS
    서버가 지원 여부를 스스로 보고하는 문제로, 실제 필요해지면
    별도 결정).

## ADR-153. M13 완성: `docs/spec/fs-protocol.md` 최소 버전 + vfs/memfs 서버 + procsrv의 VFS 클라이언트 역할

- **상태**: 확정 (2026-09-09)
- **결정**: system-servers-bringup.md §M13 전체를 구현했다.
  1. [fs-protocol.md](../spec/fs-protocol.md) — ADR-018 §영향이 예고해
     둔 FS 서버 공통 프로토콜의 **최소 버전**. `OP_OPEN`(클라이언트→
     VFS)/`OP_WRITE`/`OP_READ`(클라이언트→FS 서버 직접) 3개
     오퍼레이션만 정의한다. M13은 경로·데이터를 전부 `pages[]` 없이
     `regs[]`(최대 32/16바이트)로만 주고받는다 — ADR-151이 메시지
     구조체 자체는 서로 다른 프로세스 사이에서도 안전하게 만들었지만
     `pages[]`가 가리키는 실제 버퍼 내용까지는 아직 아니라서(OPEN-59),
     이 경로를 아예 피해 M13 검증을 완결하는 쪽을 택했다.
  2. `servers/fs/memfs/main.cpp` — 고정 8개 파일 슬롯(평평한
     이름공간, 파일마다 최대 4096바이트) + 열린 인스턴스 배열
     (`open_file_id`). `OP_OPEN`을 받으면 이름으로 찾거나 새로
     만든다(M13은 항상 암묵적 O_CREAT). `OP_WRITE`/`OP_READ`는 항상
     오프셋 0부터(seek/append는 이후 라운드).
  3. `servers/vfs/main.cpp` — M13은 마운트 테이블이 없다(memfs
     하나뿐) — `OP_OPEN`을 받으면 그대로 memfs에게 다시 보내고,
     성공하면 ADR-018이 요구하는 대로 **자신의 memfs 핸들에 대한
     프록시**를 응답(`handles[0]`)에 실어 클라이언트에게 위임한다
     (ADR-151의 `sys_reply` handles[] 확장이 있어야 가능했다).
  4. `servers/procsrv/main.cpp` — "M12의 두 번째 프로세스"(계획 §M13
     §목표의 표현 그대로)를 그대로 재사용해 VFS 클라이언트 역할을
     맡긴다: `open("test.txt")` → vfs가 위임한 memfs 핸들로 직접
     `write("hello vfs")` → `read()` → 내용 일치 확인. procsrv.md의
     실제 프로토콜(§2~9)은 여전히 구현하지 않는다 — 이 라운드트립은
     그것과 무관한 fs-protocol.md 클라이언트 검증일 뿐이다.
  5. `tools/mkbootdisk.py`에 `--depends=<이름>:<의존이름>` 추가 —
     해당 서비스의 `lib/NNN-이름.ini`에 `depends=` 키를 써 넣는다.
     `init/initrun/main.cpp`의 서비스 스폰 루프가 이제 스폰한
     서비스마다 (ADR-152의) endpoint 프록시 핸들을 이름으로
     기록해 두고, 다음 서비스의 `depends=`가 그 이름을 가리키면
     `inherited_handles`로 넘긴다. `servers/CMakeLists.txt`가
     `bootdisk.img`를 memfs→vfs→procsrv 순서(=의존성 해결 순서)로
     조립한다(이 조립 단계가 M12 때 있던 `servers/procsrv/
     CMakeLists.txt`에서 여기로 옮겨졌다 — 셋을 동시에 참조할 수
     있는 유일한 자리라서).
  6. 새 syscall `sys_debug_log`(uapi.hpp) — klog가 유저에 노출된 적이
     없어, procsrv가 이 라운드트립 결과를 관찰 가능하게 만드는
     최소 수단으로 추가했다(순수 진단용, procsrv.md의 실제 로깅
     서비스가 생기면 대체될 임시 수단).
- **검증 결과(QEMU 실측)**: 기본 `tools/smoke-test-x86_64.sh`(52개
  어써션, M12의 51개+새 procsrv 라운드트립 어써션 1개) 전체 통과.
  실측 로그 순서: `[process] spawn ok`×3(memfs/vfs/procsrv) →
  `[process] fork/exec ok`(procsrv 자기 자신) →
  `[procsrv] vfs write/read roundtrip ok=1`. SMP/NUMA/AVX 스위트도
  회귀 없음(부트 디스크를 안 붙이는 경로라 이 세 서비스와 무관).
- **알려진 단순화(M13 범위 밖으로 명시적으로 남긴 것)**: VFS의 실제
  마운트 테이블/경로 탐색(ADR-044 전체 트리, 지금은 모든 경로가
  memfs 하나로 감), `close`, 공유 모드/잠금(ADR-101), `fs_node_id`를
  프로토콜에 노출(ADR-128 — memfs 내부에는 슬롯 인덱스가 있지만
  아직 응답에 안 싣는다), 디렉터리 나열, 파일 크기/쓰기 길이 상한을
  넘는 요청(각각 4096/16바이트).

## ADR-162. M16 완성: FAT32/ext4 읽기전용 FS 서버 + VFS 정적 마운트 테이블 + `fs-protocol.md` v2(`OP_READ`의 `pages[]` 전환)

- **상태**: 확정 (2026-09-09)
- **결정**: system-servers-bringup.md §M16을 다음 범위로 구현했다.
  1. **`docs/spec/fs-protocol.md` v2** — `OP_READ`의 응답이 이제
     `regs[2..3]`(16바이트 상한) 대신 `pages[]`(ADR-155 §2/ADR-159/
     ADR-161이 구현한 유저 프로세스 매핑 경로)로 온다 — 한 번에
     최대 1페이지(4096바이트)까지, 항상 파일 오프셋 0부터. `OP_OPEN`/
     `OP_WRITE`(memfs만)는 M13과 동일하게 `regs[]`를 그대로 쓴다 —
     FAT32/ext4는 읽기전용이라 `OP_WRITE`를 구현하지 않는다.
  2. **`servers/vfs`에 정적 마운트 테이블 추가** — `/mnt/fat32/`,
     `/mnt/ext4/` 접두사를 각각 FAT32/ext4 서버에게, 그 외(M13의
     기본 경로)는 memfs에게 그대로 라우팅한다. 일치하는 접두사를
     벗겨낸 나머지 경로만 대상 FS 서버의 `OP_OPEN`으로 전달한다 —
     동적 마운트/언마운트 syscall은 아직 없다(정적 표, cfgsrv
     같은 동적 소스가 생기면 대체될 임시 수단).
  3. **`servers/fs/fat32`(읽기전용)** — devmgr에 vendor:device=
     `0x1af4:0x1001`(virtio-blk)로 등록해 위임받은 자신만의
     virtio-blk-pci 장치를 마운트한다(servers/drivers/virtio-blk의
     legacy 레지스터 프로토콜을 다시 구현 — 공유 라이브러리가 없어
     독립적으로, ADR-131 §근거와 같은 이유). BPB를 읽어 FAT32임을
     확인(`bytes_per_sector==512` 등 최소 검증)하고, 루트 디렉터리
     클러스터 체인을 평평하게 스캔해(LFN/볼륨 라벨/서브디렉터리
     엔트리는 건너뛴다 — 8.3 짧은 이름만 인식) 이름이 일치하는
     파일을 찾아 그 클러스터 체인에서 최대 1페이지를 읽는다.
  4. **`servers/fs/ext4`(읽기전용)** — 마운트 시 매직(`0xEF53`)과
     `feature_incompat`/`feature_ro_compat` 화이트리스트를
     검사한다(64bit/metadata_csum/encrypt 등 미지원 비트가 있으면
     거부). **저널이 있으면(재생 여부와 무관하게) 항상 마운트를
     거부한다**(재생을 구현하지 않았으므로 — dirty/clean 판정 대신
     "있으면 거부"로 더 단순하게 정했다, ADR-129가 이미 허용한
     범위). 그룹 디스크립터는 **그룹 0번만** 읽는다(단일 그룹 이미지
     전제 — 이 라운드의 작은 테스트 이미지가 항상 이 형태다). 루트
     (아이노드 2)의 extent 트리(depth==0, 단일 레벨만 지지)를 순회해
     디렉터리 데이터 블록을 읽고, `inode==0`(htree 인덱스/가짜
     엔트리, ADR-129가 이미 "건너뛴다"고 정한 것)을 건너뛰며 선형
     스캔한다. 찾은 파일의 아이노드도 같은 방식(extent depth==0)으로
     최대 1페이지를 읽는다.
  5. **`tools/make-fs-test-images.sh`(신설)** — 호스트에서 QEMU 검증용
     FAT32/ext4 이미지를 만든다. FAT32는 `mkfs.vfat`+`mcopy`(dosfstools/
     mtools)로 충분하지만, **ext4는 `mke2fs -d <디렉터리>`(내용으로
     즉시 채우는 옵션)가 이 환경의 빌드에서 깨져 있어**(경로 인코딩
     버그로 추정, 직접 확인) `tools/mkfs-ext4-testfile.py`(신설)가
     빈 이미지의 온디스크 구조(슈퍼블록/그룹 디스크립터/비트맵/
     아이노드 테이블/extent/디렉터리 엔트리)를 직접 읽고 고쳐 파일
     하나를 심는다 — 범용 ext4 쓰기 도구가 아니라 "테스트 픽스처
     하나 만들기"만을 위한 최소 스크립트다.
- **근거**: FAT32/ext4 둘 다 "가장 흔한 실사용 형태만" 지원한다는
  ADR-057/ADR-129의 결정을 그대로 따른다 — 저널 재생·htree 인덱스·
  하위 디렉터리·쓰기를 전부 구현하면 이 마일스톤 하나가 별도
  파일시스템 드라이버 프로젝트가 된다(ADR-129 §근거와 같은 논리).
  `OP_READ`를 `pages[]`로 옮긴 것은 애초에 OPEN-59/OPEN-61이 해소되기를
  기다리며 M13이 미뤄 둔 일 그대로다 — 16바이트 `regs[]` 상한으로는
  실제 파일 내용을 옮길 수 없다.
- **검증 결과(QEMU 실측)**: `tools/smoke-test-x86_64.sh`(63개 — M15의
  59개+신규 4개) 전체 통과를 **2회 연속** 재확인(두 이미지 모두
  읽기전용으로만 열리므로 파일 해시가 재부팅 후에도 그대로임을
  `sha256sum`으로 직접 대조). SMP(11개)/NUMA(24개)/AVX(12개) 전체
  회귀 없음. 실측 로그 발췌:
  ```
  [fat32] io_base=0xc180
  [fat32] mount ok=0x1
  [fat32] root_cluster=0x2
  [ext4] io_base=0xc200
  [ext4] mount ok=0x1
  [ext4] block_size=0x400
  [procsrv] fat32 read ok=1
  [procsrv] ext4 read ok=1
  ```
- **실행 중 발견한 버그**: `servers/devmgr`의 I/O BAR 배정 로직이
  이번에 처음으로 **동시에 두 개** 필요해졌는데(fat32/ext4가 각자
  다른 virtio-blk-pci 장치에 새 I/O BAR를 요구), devmgr가 매번 같은
  고정 포트(`0xC100`)를 다시 배정해 fat32/ext4의 서로 다른 물리
  장치가 같은 I/O 포트를 동시에 점유하는 충돌이 실제로 났다(fat32의
  `mount ok=0x0`로 재현) — 자세한 원인·수정은 boot-and-drivers.md
  ADR-163 참고.
- **알려진 단순화(M16 범위 밖으로 명시적으로 남긴 것)**: FAT32/ext4
  둘 다 쓰기, 하위 디렉터리 진입, 4096바이트를 넘는 파일의 나머지
  읽기(offset/seek), ext4 저널 재생·다단계 extent 트리·다중 블록
  그룹, FAT32 LFN(긴 파일 이름). VFS의 마운트 테이블은 여전히 코드에
  정적으로 박혀 있다(동적 마운트는 cfgsrv 등장 이후로 미룸).

## ADR-168. `fs-protocol.md` v3 — `OP_WRITE`도 `pages[]` 기반으로(대칭 마무리), memfs에 읽기/쓰기 커서 도입, `OP_OPEN`에 호출자 신원(guest/jail) 필드 추가

- **상태**: 확정 (2026-09-09)
- **결정**: system-servers-bringup.md §M18(security-model.md ADR-167)
  이 요구하는 "procsrv 자신의 ELF를 VFS에 실제로 쓰고 다시 읽어
  재조립"을 가능하게 하려고 프로토콜을 세 갈래로 확장한다.
  1. **`OP_WRITE`도 `OP_READ`(M16, ADR-159/161)와 대칭으로 `pages[]`
     기반이 된다** — `regs[0]`=open_file_id, `regs[1]`=길이(≤4096),
     `pages[0]`=쓸 내용(발신자의 페이지 정렬 버퍼). 기존 16바이트
     `regs[2..3]` 상한(M13)은 사라진다 — procsrv 자신의 ELF(수십
     KiB)를 몇 번의 페이지 단위 호출로 나눠 쓸 수 있어야 하므로.
  2. **memfs가 오픈 인스턴스마다 읽기/쓰기 커서를 각각 갖는다** —
     `open_instance`에 `read_cursor`/`write_cursor`(둘 다 open 시
     0으로 시작) 필드를 추가해, `OP_READ`/`OP_WRITE` 요청 자체의
     와이어 포맷은 그대로 두고(오프셋 필드를 새로 만들지 않는다)
     내부적으로 "마지막으로 읽은/쓴 위치 다음부터"로 자동 전진시킨다.
     이러면 클라이언트가 여러 번 연속으로 `OP_WRITE`(또는 `OP_READ`)
     를 호출하는 것만으로 큰 파일을 순차적으로 이어 쓰거나(읽거나)
     할 수 있다 — POSIX 파일 디스크립터의 암묵적 위치와 같은 개념.
     `k_max_file_bytes`(memfs)를 4096→65536으로 늘린다(procsrv
     ELF가 이 라운드 기준 약 30KiB대).
  3. **`OP_OPEN` 요청에 호출자 신원 필드를 추가한다** — 경로 예산을
     32→24바이트(`regs[0..2]`)로 줄이고, `regs[3]`에 호출자가
     스스로 밝히는 신원(bit0=guest, bit1=jail, bits[2:33]=uid)을
     싣는다. VFS는 호출자가 guest 또는 jail이면 경로가 `/home/`으로
     시작하지 않으면 거부한다(security-model.md ADR-167 §결정2 —
     jail을 이 라운드에 한해 guest와 같은 규칙으로 취급). **이
     신원은 자기 선언이며 커널이 강제하지 않는다** — badge 기반의
     위조 불가능한 신원 전파(ADR-084)는 아직 구현하지 않았다(신규
     **미결정, OPEN-38**이 이미 이 문제를 지적해 뒀다 — "핸들 전달
     경로의 우회"와 같은 성격의 근본적 제약, v1은 협조적인 호출자만
     가정한다).
- **근거**: M16이 `OP_READ`만 `pages[]`로 바꾸고 `OP_WRITE`는 그대로
  뒀던 이유(당시 검증 목표가 읽기뿐이었다)가 이제 사라졌다 — su/sudo
  로더가 쓰기도 큰 페이로드를 다뤄야 한다. 오프셋 필드를 와이어에
  추가하는 대신 서버 쪽 커서로 처리한 것은, 지금까지 유일한 클라이언트
  (procsrv)가 항상 "열고 처음부터 끝까지 순차적으로만" 접근하고
  임의 위치로 seek할 필요가 없어서다 — 필요해지면 그때 명시적
  seek 오퍼레이션을 추가하는 게 지금 안 쓰는 오프셋 필드를 미리
  만들어 두는 것보다 낫다(YAGNI).
- **영향**: `servers/fs/memfs/main.cpp`(커서, `k_max_file_bytes`,
  `pages[]` 기반 `handle_write`), `servers/vfs/main.cpp`(경로 24바이트
  + 신원 검사), `servers/procsrv/main.cpp`의 기존 M13
  `run_vfs_roundtrip_test()`가 이제 `OP_WRITE`도 페이지 정렬 버퍼로
  보내야 한다(같은 파일에서 이미 M16 때 `OP_READ` 쪽을 이렇게
  바꾼 전례를 그대로 따른다). `servers/fs/fat32`/`servers/fs/ext4`
  의 `OP_READ`는 그대로다(읽기전용 호스트 픽스처라 커서가 필요
  없다 — 항상 오프셋 0부터 1페이지만).
