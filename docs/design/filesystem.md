# 설계 결정: VFS·파일시스템

## ADR-018. fd 라우팅: open()만 VFS 경유, 이후 FS 서버와 직접 통신 (핸들 위임) (해결: OPEN-11)

- **상태**: 확정 (2026-09-08)
- **결정**: 경로 탐색과 마운트 판정(`open()`, `stat()` 경로 등)만 VFS 서버가 담당한다.
  성공하면 VFS는 대상 FS 서버의 커널 핸들(ADR-011)을 호출 프로세스에게 **위임**하고,
  이후 `read`/`write`/`close` 등은 프로세스가 해당 FS 서버와 **직접** 통신한다.
- **근거**: 모든 I/O가 VFS를 프록시로 거치면 VFS가 시스템 전체 처리량의 병목이자
  단일 장애점이 된다(ADR-008에서 서버를 분해한 취지와 정면으로 배치됨). 상대적으로
  드문 연산(경로 탐색)만 중앙화하고, 빈번한 I/O는 탈중앙화하는 편이 합리적이다.
- **영향**:
  - fd의 "진짜 소유자"는 각 FS/네트워크 서버이며, 프로세스의 커널 핸들 테이블
    (ADR-011)은 그 핸들의 로컬 별칭 역할을 한다.
  - fork 시(ADR-016) 프로세스 서버는 어떤 fd가 어떤 서버에 속하는지 알아야 하므로,
    fd 테이블에 서버 식별 메타데이터를 함께 보관해야 한다.
  - VFS가 다운되어도 이미 열린 fd의 read/write는 영향받지 않는다는 장점이 있다.
    다만 마운트 변경/권한 재검사가 필요한 시나리오는 FS 서버가 독자적으로 처리해야 한다.
  - VFS↔FS 간 "핸들 위임" 프로토콜과 FS 서버의 위임 유효성 검증 방식은
    spec 단계에서 상세 정의한다.

## ADR-044. VFS 전역 디렉토리 구성 확정

- **상태**: 확정 (2026-09-08)
- **결정**: 시스템 전체의 VFS 네임스페이스를 다음과 같이 확정한다.

  | 경로 | 의미 |
  |---|---|
  | `/` | VFS 루트 |
  | `/boot` | 부팅 루트 (커널 이미지, initrd 등) |
  | `/sys` | 운영체제를 구성하는 모든 요소·파일이 위치하는 루트 |
  | `/sys/proc` | 리눅스 procfs류 — 프로세스 상태 열람 |
  | `/sys/live` | 현재 구동 중인 설정·옵션·현황 전체. 외부 수정이 **즉시 반영**되어야 함 |
  | `/sys/etc` | 전역 시스템 설정(영속) |
  | `/sys/bin` | 전역 시스템 바이너리 |
  | `/sys/mnt` | 시스템 수준 마운트 루트 (USB, CDROM, 네트워크 경로 등) |
  | `/sys/dev` | 디바이스 노드 (ADR-048) |
  | `/sys/tmp` | 휘발성 스크래치 공간 (ADR-048) |
  | `/run` | 사용자별로 설치·관리할 수 없는 공용 설치 경로 (라이브러리·바이너리·설정) |
  | `/usr/{사용자명}` | 사용자별 격리 공간 — 라이브러리·바이너리·설정 전부 사용자마다 분리 |
  | `/usr/{사용자명}/home` | 사용자의 기본 작업 디렉터리 |

- **근거**: `/sys`를 "OS 구성요소 전체의 단일 루트"로 삼아 시스템 자체와
  사용자 영역을 명확히 분리하고, `/usr/{사용자명}`을 완전히 격리된
  사용자별 트리로 둬서 사용자 간 라이브러리·바이너리 의존성 충돌을
  구조적으로 없앤다. `/sys/live`는 sysfs/configfs류의 즉시 반영 계약을
  명시적으로 요구한다.
- **영향**: 이 구조는 **표준 FHS(Filesystem Hierarchy Standard)와
  의도적으로 다르다** — 특히 `/usr`(표준: 시스템 공용 자원)와 `/run`
  (표준: 휘발성 런타임 상태)의 의미가 재정의되었다. ADR-005(기존
  소프트웨어 포팅)와의 충돌은 ADR-045에서 다룬다.
- 구체적인 경로별 소유 서버, 마운트 방식은 [vfs-layout.md](../spec/vfs-layout.md)에서 정의한다.

## ADR-045. POSIX 경로 호환 전략: 소프트웨어별 패치로 대응

- **상태**: 확정 (2026-09-08)
- **결정**: ADR-044의 경로가 표준 FHS(`/usr/bin`, `/etc` 등)와 다른
  데서 오는 충돌은, VFS에 호환 심볼릭 링크 계층을 두는 대신 **포팅
  대상 소프트웨어마다 ADR-022의 패치 메커니즘으로 개별 대응**한다.
- **근거**: 심볼릭 링크 계층은 모든 경로 충돌을 영구히 감추지만,
  이 프로젝트가 지향하는 "직접 설계한 시스템"(ADR-001)의 정체성과
  어긋난다 — 표준 경로를 흉내 내는 호환 레이어보다, 포팅되는
  소프트웨어가 minicore의 실제 경로를 알고 동작하는 편이 장기적으로
  더 투명하다. ADR-022가 이미 서드파티 소스별 패치 디렉토리 구조를
  갖추고 있어 추가 메커니즘이 필요 없다.
- **영향**:
  - 포팅 착수 시 각 소프트웨어의 하드코딩된 경로(`/usr/bin`,
    `/usr/lib`, `/etc` 등)를 ADR-044의 실제 경로로 바꾸는 패치를
    `third_party/patches/<project>/`에 추가해야 한다.
  - `libc`의 `sysdeps/minicore`(repo-layout.md)에 기본 검색 경로
    상수(예: 동적 링커의 라이브러리 탐색 경로)를 ADR-044 기준으로
    정의해, 대부분의 소프트웨어가 별도 패치 없이 링크·실행되게 한다.
  - 완전히 패치 없이 포팅 가능하다고 보장하지 않는다 — 이는 이
    프로젝트가 받아들인 트레이드오프다.

## ADR-047. 합성(synthetic) 파일시스템: 담당 서버가 FS 서버 역할 겸임

- **상태**: 확정 (2026-09-08)
- **결정**: `/sys/proc`, `/sys/live`처럼 정적 저장 매체가 없는 합성
  파일시스템은, 별도의 통합 sysfs류 서버를 두지 않고 **해당 주제를
  담당하는 기존 서버가 ADR-018의 FS 서버 프로토콜을 직접 구현**하는
  방식으로 제공한다. 예: 프로세스 서버(procsrv)가 `/sys/proc`의
  FS 서버 역할을 겸한다.
- **근거**: ADR-018이 이미 "VFS는 경로 탐색만, 실제 FS 서버가 나머지"
  구조를 정해두었다. 별도의 통합 sysfs 서버를 추가하면 그 서버가
  다시 모든 주제별 서버와 통신해야 하는 간접 계층이 하나 더 생긴다 —
  각 서버가 이미 자신의 상태를 가장 잘 알고 있으므로 직접 노출하는
  편이 계층을 줄인다.
- **영향**:
  - `/sys/live`처럼 여러 서비스의 상태를 아우르는 경로는, VFS의
    마운트 테이블에서 하위 경로별로 서로 다른 서버에 위임되도록
    구성해야 한다(예: `/sys/live/network`는 netsrv, `/sys/live/sched`는
    커널 노출용 별도 서버 등) — 즉 `/sys/live`는 여러 개의 하위
    마운트가 모인 지점이지 단일 서버가 통으로 서빙하는 트리가 아니다.
  - "외부에서 수정하면 즉각 반영"(ADR-044) 요구사항은 각 담당 서버가
    `write()` 요청을 받는 즉시 자신의 실제 상태를 변경하는 것으로
    구현한다 — 캐싱이나 지연 반영을 두지 않는다.
  - 각 서버가 FS 서버 프로토콜(lookup/read/write/getattr, ADR-008 영향
    항목)을 구현해야 하므로, 그 프로토콜을 최대한 작고 구현하기 쉽게
    유지해야 하는 압력이 커진다.

## ADR-048. /dev, /tmp: /sys 아래로 통합

- **상태**: 확정 (2026-09-08)
- **결정**: 디바이스 노드는 `/sys/dev`, 휘발성 스크래치 공간은
  `/sys/tmp`에 위치한다 (표준 FHS의 `/dev`, `/tmp`와 달리 루트
  직속이 아니다).
- **근거**: ADR-044의 "`/sys` = OS를 구성하는 모든 것"이라는 원칙을
  예외 없이 지킨다 — 디바이스 노드도, 휘발성 공간도 OS가 제공하는
  구성요소이므로 `/sys` 바깥에 둘 이유가 없다.
- **영향**:
  - `/sys/dev`는 devmgr가 FS 서버 역할을 겸해 제공한다(ADR-047과
    같은 패턴) — PCIe 등에서 열거된 장치가 여기 노드로 나타난다.
  - `/sys/tmp`는 memfs(ADR-008 수직 슬라이스에서 이미 계획된
    메모리 파일시스템)를 그대로 마운트해서 구현할 수 있다 — 새로운
    FS 구현이 필요 없다.
  - ADR-045의 패치 대상에 `/dev`, `/tmp`를 하드코딩한 소프트웨어도
    포함된다 — 사실상 거의 모든 POSIX 소프트웨어가 해당하므로,
    `libc`의 `sysdeps/minicore` 표준 경로 상수(ADR-045 영향 항목)에
    이 두 경로도 반드시 포함해야 한다.

## ADR-050. 사용자별 트리의 마운트 형태: 서브디렉토리가 기본, 별도 마운트도 허용

- **상태**: 확정 (2026-09-08)
- **결정**: `/usr/{사용자명}`은 다른 VFS 경로와 다르게 특별 취급하지
  않는다. 기본적으로는 `/usr`를 구성하는 FS의 평범한 서브디렉토리이지만,
  필요하면 특정 사용자의 트리를 별도 마운트(전용 볼륨, 쿼터 적용
  파티션, 네트워크 홈 등)로 대체할 수도 있다 — 사용자마다 다르게
  선택해도 된다(어떤 사용자는 서브디렉토리, 어떤 사용자는 별도 마운트).
- **근거**: 전통적 Unix에서도 `/home`이 별도 파티션일 수도, 루트 FS의
  일부일 수도 있는 것과 같은 유연성이다. ADR-018의 VFS 구조(임의의
  경로가 마운트 지점이 될 수 있음)가 이미 이 능력을 자연스럽게
  제공하므로, 사용자 트리만을 위한 별도 규칙을 둘 필요가 없다.
- **영향**:
  - VFS 마운트 테이블은 "이 경로가 마운트 지점인가"만 검사하면 되고,
    사용자 계정 생성과 마운트 여부를 별개로 다룬다 — procsrv가 사용자
    생성 시 서브트리를 초기화(디렉토리 생성)하는 경로와, 관리자가
    특정 사용자에게 전용 볼륨을 마운트해주는 경로가 동일한 마운트
    테이블 메커니즘을 공유한다.
  - 사용자별 격리(ADR-044)는 마운트 여부와 무관하게 네임스페이스
    분리만으로 이미 달성된다 — 별도 마운트는 순전히 운영상의 선택
    (쿼터, 성능 격리, 백업 단위 분리 등)이다.
  - [vfs-layout.md](../spec/vfs-layout.md)의 관련 "아직 정하지 않은
    것" 항목을 이 결정으로 대체한다.

## ADR-058. /sys/live 최소 매핑표 확정: network·sched·mem (해결: OPEN-28)

- **상태**: 확정 (2026-09-08)
- **결정**: `/sys/live` 하위에 최소 다음 항목을 지금 확정한다
  (vfs-layout.md §1/§5의 예시를 정식 채택):

  | 하위 경로 | 담당 서버 |
  |---|---|
  | `/sys/live/network` | netsrv |
  | `/sys/live/sched` | procsrv (스레드·스케줄링 상태 노출까지 겸임) |
  | `/sys/live/mem` | 정책 서버 (ADR-024, 메모리 쿼터·할당 현황) |

  이후 서비스가 늘어나면 이 표에 하위 경로를 추가하는 방식으로
  확장한다. `/sys/proc`(프로세스 목록)은 이 표와 별개로 이미
  ADR-047에서 procsrv 담당으로 정해져 있다 — `/sys/live/sched`는
  "프로세스 목록"이 아니라 "스케줄링 파라미터·현황"이라는 점에서
  다르다.
- **근거**: 새 서버(예: "schedsrv")를 신설하지 않고 기존 서버가
  겸임하는 ADR-047의 원칙을 그대로 따른다 — procsrv는 이미 스레드를
  다루므로 스케줄링 상태 노출의 자연스러운 소유자다.
- **영향**: `vfs-layout.md`의 관련 "아직 정하지 않은 것" 항목을 이
  결정으로 대체한다. 각 경로의 정확한 하위 키·값 형식은 해당 서버가
  실제로 설계되는 시점에 정의한다.

## ADR-059. /sys/mnt 시스템 마운트 권한: root 권한 프로세스의 명시적 요청만

- **상태**: 확정 (2026-09-08)
- **결정**: `/sys/mnt` 아래에 시스템 수준 마운트(USB, CDROM, 네트워크
  경로 등)를 트리거할 수 있는 것은 **root 권한 프로세스의 명시적
  요청**뿐이다. devmgr가 매체 삽입을 감지하더라도 자동으로 마운트를
  수행하지 않는다 — 감지와 마운트 실행 권한을 분리한다.
- **근거**: ADR-056(드라이버 충돌 해소)이 이미 root 전용 오버라이드
  경로를 도입했다 — 동일한 신뢰 모델(root의 명시적 개입)을 시스템
  마운트에도 일관되게 적용한다. 자동 마운트를 기본으로 허용하면
  외부 매체 삽입만으로 공격 표면이 넓어진다.
- **영향**:
  - devmgr는 매체 삽입을 감지하면 `/sys/live`(ADR-058) 또는
    `/sys/dev`(ADR-048)를 통해 "마운트 가능한 장치가 나타났다"는
    사실만 노출하고, 실제 마운트는 별도의 root 전용 syscall/IPC
    요청으로 트리거된다.
  - 사용자 세션에서 "USB 꽂으면 자동으로 열리는" 편의 기능이 필요하면,
    root 권한을 가진 별도의 유저 세션 데몬(예: 데스크톱 환경의
    자동마운트 서비스)이 이 root 전용 경로를 대신 호출하는 형태로
    구현해야 한다 — 커널·devmgr 차원의 자동 마운트는 없다.

## ADR-065. /home: /usr/{사용자명}/home으로의 VFS 경로 별칭(오버레이)

- **상태**: 확정 (2026-09-08)
- **결정**: 표준 FHS 관례를 따르는 `/home`을 VFS 루트에 추가하되,
  이는 실체 저장소가 아니라 **VFS 경로 별칭(alias)**이다.
  `/home/{사용자명}`에 대한 모든 조회는 VFS가 조회 단계에서
  `/usr/{사용자명}/home`으로 **재작성(rewrite)**한 뒤, 그 다음부터는
  평범하게 ADR-018의 경로 탐색·핸들 위임을 수행한다. `/home` 자체를
  나열(list)하면 `/usr` 아래의 사용자 이름 목록과 동일한 결과를
  보여준다.
- **근거**: 대부분의 POSIX 소프트웨어·스크립트가 `$HOME` 경로 감지,
  홈 디렉토리 존재 확인 등에 `/home/{user}` 패턴을 광범위하게
  가정한다. ADR-045는 일반적으로 심볼릭 링크·오버레이 호환 계층
  대신 소프트웨어별 패치를 원칙으로 삼았지만, `/home`은 **VFS
  레벨의 단일 별칭 규칙 하나**로 극히 많은 소프트웨어의 호환성
  문제를 한 번에 해소할 수 있어 비용 대비 효과가 뚜렷한 예외다 —
  ADR-045의 원칙을 부정하는 것이 아니라, 그 원칙이 "패치보다 별칭이
  압도적으로 싸게 먹히는" 이 한 가지 경로에 한해 의도적으로 예외를
  두는 것이다.
- **영향**:
  - VFS 경로 탐색(ADR-018)에 별칭 재작성 단계가 추가된다 — `/home`
    프리픽스는 조회 시점에 `/usr`로 치환되고, 사용자명 세그먼트
    다음에 암묵적으로 `home`이 삽입된다:
    `/home/alice/docs` → `/usr/alice/home/docs`.
  - 이 별칭은 읽기·쓰기에 대칭적으로 적용된다 — `/home/alice`에
    쓰는 모든 것은 실제로 `/usr/alice/home`에 쓰여진다.
  - `/home`(사용자명 없이) 나열은 `/usr`의 사용자 디렉토리 이름
    집합을 그대로 반환한다.
  - ADR-050(사용자 트리는 서브디렉토리 또는 별도 마운트 가능)과
    자연스럽게 결합한다 — 별칭은 순수 경로 재작성이므로
    `/usr/{사용자명}`이 어떤 방식으로 마운트되어 있든 그대로 통한다.
  - 이 별칭 규칙은 **VFS 서버 자체가 소유**한다 — 새로운 FS 서버나
    synthetic 마운트(ADR-047)가 필요 없다. 순수 경로 재작성이라
    별도 서버 위임조차 불필요하다.
