# 설계 결정: 프로세스 신뢰·권한 모델

`address_space.trusted`(ADR-063) 부여 절차와, 일반 유저 프로세스의 권한
상승(사용자 요청 → 승인 → 캐패빌리티 부여) 정책에 관한 결정. 새로운
커널 개념을 추가하지 않고 기존 핸들·프록시 객체 모델([objects.md](../spec/objects.md),
ADR-011/023)만으로 표현한다.

**jail/guest의 격리 강도에 대한 기준선**: ADR-081~083이 정하는 jail은
전통적 Unix의 서비스 계정 분리(예: 웹서버 데이터를 `wwwdata` 계정으로
일반 사용자와 나누는 정도의 관례적 격리)가 **아니다** — 문자 그대로의
감옥(prison)이다. 홈 디렉토리 하나를 빼면 시스템의 나머지 전부가
가상 에뮬레이션이고, 실행 가능한 것은 `/run`에 설치된 것뿐이며, 다른
프로세스·장치·시스템 현황은 아예 보이지 않는다. guest는 이보다도
더 얇다 — 비유하자면 "인터넷 브라우저 정도만 써볼 수 있는 체험판
데스크톱" 수준이며, 그 이상의 시스템 접근은 처음부터 존재하지 않는
것처럼 취급된다. 이후 이 파일에 추가되는 jail/guest 관련 결정은 이
기준선(관례적 분리가 아니라 실질적 감금)에 맞춰 해석한다.

## ADR-074. 신뢰(trusted) 위임 체인: 커널→initrun 고정 부여, 이후 initrun이 재위임 (해결: OPEN-30)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 커널이 initrd에서 직접 로드해 최초로 실행하는 유저 프로세스 —
     즉 **initrun**의 `address_space`만 커널이 프로세스 생성 절차의
     일부로 **무조건 `trusted = true`**로 만든다([boot.md](../spec/boot.md) §4).
     다른 어떤 프로세스도 이런 식으로 자동 부여받지 않는다 — initrun이
     시스템의 유일한 최초 신뢰 루트(root of trust)다.
  2. initrun은 **"trusted 부여 권한"** 자체를 하나의 캐패빌리티(핸들)로
     보유한 채 시작된다. 이후 자신이 기동시키는 서버 중 신뢰 보호가
     필요하다고 판단되는 것(cfgsrv는 ADR-063에 의해 확정, 그 외 서버는
     실제 설계 시점에 판단)에 대해, 이 캐패빌리티를 사용해 대상
     프로세스 생성 시 `trusted` 설정을 요청할 수 있다.
  3. 이 권한을 initrun보다 아래로 더 위임할 필요가 생기면(예: procsrv가
     감시자 역할로 cfgsrv를 재시작할 때도 다시 `trusted`를 설정해야
     하는 경우), **새로운 메커니즘을 만들지 않고 ADR-023의 프록시
     위임을 그대로 재사용**한다 — "trusted 부여 권한"도 여느
     캐패빌리티와 동일하게 프록시로 파생될 수 있는 `handle_entry`로
     표현된다.
- **근거**: "누가 trusted를 부여할 수 있는가"라는 신뢰 루트 문제를
  새 커널 개념 없이 풀어야 ADR-006/007(최소 커널)을 지킨다. 이미 있는
  프록시 캐패빌리티 위임(ADR-011/023)을 재사용하면 충분하다. initrun을
  유일한 최초 루트로 삼는 것은 ADR-017("커널은 initrun만 직접 로드한다")과
  정확히 대응하므로 별도 규칙을 새로 만드는 것이 아니라 기존 결정을
  그대로 연장한 것이다.
- **영향**:
  - [objects.md](../spec/objects.md)에 "trusted 부여 권한"을 나타내는
    구체적 표현(새 `rights` 비트인지, 별도 `object_kind`인지)이
    필요하다 — 정확한 형태는 프로세스 생성 syscall/서버 API를 실제
    설계하는 시점(procsrv 상세 설계, ADR-075와 맞물림)에 정한다.
  - [boot.md](../spec/boot.md) §4("initrun 초기화 흐름")에 "커널이
    initrun의 address_space를 trusted로 생성하고, trusted 부여
    캐패빌리티를 함께 쥐어준다"는 내용을 반영해야 한다(스펙 갱신,
    이 ADR 작성과 함께 반영).
  - [registry.md](../spec/registry.md) §6.2, [objects.md](../spec/objects.md) §2.1의
    "OPEN-30(미정)" 표기를 이 ADR로 교체해야 한다(스펙 갱신, 이 ADR
    작성과 함께 반영).
  - initrun 기동 매니페스트 형식(OPEN-29)이 확정될 때, "이 서버는
    trusted로 띄운다"를 매니페스트 항목에 표시할 수 있어야 한다 —
    매니페스트 스키마 설계 시 이 요구사항을 반영한다.

## ADR-075. 유저 프로세스 권한 모델: 기본 무권한 + 요청/승인 기반 상승(sudo류) + ROOT(Supervisor) 전권

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. initrun이 기동하는 코어 서버들 이후, **procsrv를 통해 생성되는
     일반 유저 프로세스는 기본적으로 무권한(unprivileged) 상태로
     기동**된다 — 생성 시점의 핸들 테이블에는 시스템 관리용 캐패빌리티
     (디바이스 접근, trusted 부여, 정책 서버 조작 등)가 전혀 없다.
  2. 무권한 프로세스가 특정 권한이 필요해지면 **procsrv**에게 IPC로
     권한 상승을 요청한다. procsrv를 승인 주체로 삼는 이유는, procsrv가
     이미 사용자 계정(uid/gid)의 진실 공급원이 될 예정이라서(ADR-062의
     "uid/gid 발급 주체는 procsrv" 예정 사항과 일치) 승인에 필요한
     신원 정보를 별도 서버 없이 가장 가깝게 갖고 있기 때문이다 — 새
     서버(`authsrv`류)를 신설하지 않는다(ADR-001의 "서버를 필요 이상
     늘리지 않는다"는 취지와 일치).
  3. procsrv는 **sudo/gsudo류의 승인 절차**(요청 프로세스를 실행한
     사용자의 자격 증명 확인 — 구체적 인증 수단은 procsrv의 사용자
     계정 모델 설계 시 정함)를 거친다. 승인되면 요청된 권한에 해당하는
     캐패빌리티를 **프록시 핸들**(ADR-023)로 만들어 IPC 핸들 전달
     ([objects.md](../spec/objects.md) §4)로 요청 프로세스에게 건네준다.
     거부되면 `result` 실패로 반환한다(ADR-010 관례).
  4. **ROOT 사용자(Supervisor)** 소유로 생성되는 프로세스는 이
     요청/승인 절차를 거치지 않고 **생성 시점부터 시스템의 모든
     캐패빌리티를 보유**한다 — ROOT는 uid 체계상 "항상 전권"이라는
     예외적 취급을 받는 유일한 사용자다.
- **근거**: 사용자가 "기본 무권한 → 필요 시 요청·승인 후 부여 →
  ROOT는 항상 전권"이라는 sudo류 모델을 명시적으로 지정했다. 이미
  확립된 캐패빌리티 기반 객체 모델(ADR-011/023)에 그대로 얹을 수
  있다 — 커널에 uid 검사 같은 새 개념을 추가하지 않고, "승인되면
  프록시 핸들을 IPC로 건네준다"는 기존 메커니즘만으로 표현된다.
- **영향**:
  - procsrv가 각 시스템 서버(devmgr, cfgsrv 등)가 소유한 캐패빌리티를
    승인 시점에 어떻게 확보해 재위임하는지 — procsrv가 대행 발급하는
    구조인지, 각 서버가 procsrv의 승인 결과(서명된 토큰 또는 IPC
    콜백)를 신뢰하고 자신의 캐패빌리티를 직접 내주는 구조인지는
    procsrv 상세 설계 시점에 정한다.
  - ROOT가 "생성 시점부터 모든 캐패빌리티 보유"이려면, 프로세스 생성
    API가 "이 프로세스는 ROOT 소유"임을 procsrv(또는 커널)에 알릴
    방법이 필요하다 — 전통적 Unix의 `uid == 0` 같은 식별자 체계
    자체가 procsrv의 사용자 계정 모델 설계 대상이다.
  - 이 ADR은 **정책**만 정한다 — 구체적 IPC 프로토콜(권한 요청
    메시지 형식, 인증 수단, 승인에 대화형 확인이 필요한지 등)은
    procsrv 상세 설계 문서(아직 작성되지 않음 — 향후 별도 design 문서
    대상)로 넘긴다.
  - procsrv의 사용자 계정 모델(uid/gid 발급, ROOT 식별 방식, 인증
    수단) 전체가 이 ADR과 ADR-062 양쪽의 공통 선행 조건임에도 아직
    OPEN 항목으로 등록되어 있지 않았다 → 신규 **미결정 (OPEN-35)**.

## ADR-079. procsrv 사용자 계정 모델: uid/gid + S/G/J 비트, 레지스트리 저장, 해시 또는 공개키 인증 (해결: OPEN-35)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. **데이터 모델**:

     ```cpp
     enum class auth_kind : uint8_t { password_hash = 0, public_key = 1 };

     struct auth_method {
         auth_kind kind;
         // password_hash: PBKDF2-HMAC-SHA256 결과(§4) + salt + 반복 횟수
         // public_key:    Ed25519 공개키(32바이트, §4)
     };

     struct user_account {
         uint32_t    uid;
         uint32_t    gid;        // 주 그룹(primary group) — v1은 그룹 1개만, 보조 그룹 없음
         bool        super_bit;  // S — ADR-075의 ROOT(Supervisor)와 동일 개념
         bool        guest_bit;  // G — 게스트: 권한 상승 요청이 항상 거부됨(아래 3)
         bool        jail_bit;   // J — 격리 대상: 실행 환경 제한(세부 메커니즘 OPEN-36)
         auth_method auth;       // password_hash 또는 public_key 중 정확히 하나
     };

     struct group_account {
         uint32_t gid;
         bool     super_bit;
         bool     guest_bit;
         bool     jail_bit;
     };
     ```

     `super_bit`/`guest_bit`/`jail_bit`가 그룹에도 동일하게 있는 이유는
     계정마다 개별 설정하지 않고 "이 그룹에 넣으면 그 특성을 상속"하게
     하기 위해서다 — 전통적 Unix의 `wheel`/`sudo` 그룹 관례를 세 축
     (super/guest/jail) 모두로 일반화한 것이다.
  2. **유효 비트 계산**: `effective(user).X = user.X || group(user.gid).X`
     (`X` ∈ {super, guest, jail}). 단 **`super`가 true면 `guest`/`jail`은
     항상 false로 취급**한다 — "항상 전권"과 "게스트로 제한됨"/"격리됨"은
     동시에 성립할 수 없으므로 super가 무조건 우선한다. `guest`와
     `jail`은 서로 배타적이지 않다(게스트이면서 동시에 격리된 계정도
     허용 — 예: 익명 샌드박스 로그인).
  3. `effective(user).guest == true`인 계정이 ADR-075 §2~3의 권한
     상승을 요청하면 procsrv는 **항상 거부**한다 — 게스트는 인증
     수단과 무관하게 추가 권한을 얻을 수 없는 최하위 신뢰 등급이다.
  4. **저장 위치**: 계정은 `@global/system/users`, 그룹은
     `@global/system/groups` 레지스트리 테이블([registry.md](../spec/registry.md)
     §1~2)에 사용자명/그룹명을 key로, `user_account`/`group_account`를
     직렬화한 `binary` 타입 `reg_value`로 저장한다. `global`은 ADR-060이
     이미 예약해 둔 시스템 전용 스키마다. 두 테이블 모두 강한
     권한(§3의 `reg_permissions`)이 필요하다 — `other_rwx`는 전부
     0(읽기조차 불허), 쓰기는 `super` 등급 계정만 가능해야 한다.
  5. **인증 수단**(계정당 §1의 `auth_method` 하나만 등록, 두 수단
     동시 등록·OR 허용은 v1 범위 밖):
     - **해시 비밀번호**: `PBKDF2-HMAC-SHA256`(반복 횟수 ≥210,000,
       OWASP 최신 권장치 기준)으로 salt와 함께 해시해 저장한다.
       비밀번호 원문은 **최대 64바이트**까지만 받고 그 이상은 입력
       단계에서 거부한다.
     - **공개키**: Ed25519 공개키를 등록해두고, procsrv가 로그인 시도
       때마다 nonce를 발급 → 클라이언트가 개인키로 서명 → procsrv가
       등록된 공개키로 검증하는 챌린지-응답 방식을 쓴다.
- **근거**:
  - uid/gid + 3개 특수 비트는 procsrv가 필요로 하는 최소 신원
    모델이다 — ADR-075의 "ROOT는 항상 전권"이 곧 `super_bit`이고,
    "게스트는 상승 요청이 거부된다"가 `guest_bit`이며, 향후 격리/
    컨테이너 기능의 훅이 `jail_bit`이다. 세 개념 모두 그룹에도
    있어야 관리자가 계정 개별이 아니라 그룹 단위로 정책을 적용할
    수 있다.
  - 레지스트리에 저장하는 것은 ADR-060/061이 이미 만든 "타입 있는
    키-값 저장소"를 재사용할 뿐 새 저장소를 만들지 않기 위함이다 —
    `@global` 스키마가 정확히 이런 시스템 전역 데이터를 위해
    예약되어 있었다.
  - **비밀번호 해시로 PBKDF2-HMAC-SHA256을 선택한 이유**: procsrv는
    ADR-006 경계상 "시스템 서비스"로 **직접 구현** 대상이라 OpenSSL/
    libsodium 같은 외부 암호 라이브러리를 가져올 수 없다. Argon2류
    메모리-하드 알고리즘이 이론적으로 더 안전하지만 직접 구현 시
    실수 위험이 크다. PBKDF2-HMAC-SHA256은 명세(RFC 8018/2898)가
    단순해서, SHA-256 하나만 정확히 구현하면 HMAC과 PBKDF2 모두 그
    위에 조립할 수 있어 자체 구현 리스크가 가장 낮다.
  - **정정 사항 — 길이 제한과 길이 확장 공격의 관계**: 사용자가 요청한
    "비밀번호를 64자로 제한해 길이 확장 공격을 차단한다"는 목표는
    유효하지만, 정확히는 **길이 제한이 아니라 HMAC 구조 자체가 길이
    확장 공격을 막는다**. 길이 확장 공격은 raw Merkle–Damgård 해시
    (SHA-256 등)를 `H(secret ‖ message)` 형태로 직접 쓸 때, 공격자가
    `H(secret)`만 알아도 `secret`을 몰라도 `H(secret ‖ padding ‖
    attacker_data)`를 계산할 수 있는 취약점이다.
    `HMAC(key, msg) = H((key⊕opad) ‖ H((key⊕ipad) ‖ msg))`는 내부
    해시 출력을 한 번 더 감싸는 구조라 이 공격이 애초에 성립하지
    않는다 — 즉 PBKDF2-HMAC-SHA256을 쓰는 순간 입력 길이와 무관하게
    이미 차단되어 있다. **64바이트 상한은 별도로, 그 자체로 타당한
    조치**(과도하게 긴 입력의 처리 비용 낭비·DoS 방지, 임의 길이
    시크릿을 다루는 코드 경로를 단순하게 유지하기 위한 입력 검증)로
    유지한다 — 두 조치 모두 적용하되 서로 다른 문제를 해결한다는
    점을 명확히 기록해 둔다.
  - **공개키 인증에 Ed25519를 선택한 이유**: RSA는 패딩 스킴(PKCS#1
    v1.5 등) 구현 실수가 실제 취약점으로 이어진 사례가 많고 키/서명
    크기도 크다. Ed25519는 키(32바이트)·서명(64바이트)이 작고
    결정론적 서명(서명마다 별도 안전한 난수가 필요 없음)이라, 직접
    구현 시 난수 생성 실패로 개인키가 유출되는 사고(예: nonce 재사용)
    위험이 구조적으로 적다.
- **영향**:
  - [registry.md](../spec/registry.md)에 `@global/system/users`,
    `@global/system/groups` 테이블 스키마를 실제로 추가하는 것은
    이 ADR의 범위 밖이며, registry.md 갱신 시점(다음 스펙 작업)에
    반영한다.
  - PBKDF2-HMAC-SHA256/HMAC-SHA256/SHA-256/Ed25519 구현은 `libk`가
    아니라 procsrv 전용 암호 유틸리티로 둔다 — `libk`는 커널까지
    링크되는 범용 프리스탠딩 라이브러리([libk.md](libk.md))이므로
    보안 민감 암호 코드를 두면 공격 표면과 컴파일 단위가 불필요하게
    커진다. 구체적 위치(`servers/procsrv/crypto/`류)는 procsrv 상세
    설계 시점에 정한다.
  - ADR-075가 말한 "ROOT는 생성 시점부터 모든 캐패빌리티 보유"는
    이제 구체적으로 "`effective(user).super_bit == true`인 계정으로
    생성된 프로세스"로 정의된다 — ADR-075 자체는 수정하지 않고 이
    ADR이 그 의미를 구체화한다.
  - 새 미결정 항목: `jail_bit`의 구체적 격리 메커니즘(VFS 루트 제한,
    프로세스/IPC 가시성 제한 등)은 이 ADR의 범위 밖이다 → 신규
    **미결정 (OPEN-36)**.

## ADR-081. jail/guest의 VFS 격리 정책: jail은 홈 제외 전체 오버레이, guest는 홈만 접근 허용, 둘 다 캐패빌리티로 우회 불가 (해결: OPEN-36의 VFS 부분)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. **jail**: `effective(user).jail == true`(ADR-079)인 프로세스는
     procsrv가 생성 시점에 [filesystem.md](filesystem.md) ADR-080의
     **에페메럴 오버레이 네임스페이스**를 배정한다. 전역 네임스페이스
     전체가 오버레이 대상이며(모든 쓰기가 휘발성 레이어에만 남고
     실제 시스템에는 반영되지 않는다 — "모든 게 가상 에뮬레이션
     환경처럼 보인다"), 유일한 예외는 그 사용자의 home 서브트리
     (`/usr/{사용자명}/home`, 및 `/home/{사용자명}` 별칭, ADR-065)로,
     이 경로만 ADR-080의 패스스루 규칙으로 지정해 실제 백엔드에
     읽기·쓰기 모두 직접 연결한다.
  2. **guest**: `effective(user).guest == true`인 프로세스는 오버레이
     네임스페이스를 쓰지 않는다(jail처럼 "가상 환경처럼 보이게"
     만들지 않는다) — 대신 VFS의 경로 탐색 단계(ADR-018의 `open()`
     시점)에서 "요청자가 guest면 `/usr/{사용자명}/home`(및
     `/home/{사용자명}` 별칭) 밖의 모든 경로에 대한 `open()`을
     거부"하는 규칙을 추가한다. 대상 파일 자체의 소유자/그룹/기타
     권한 비트와 무관하게 이 규칙이 먼저, 그리고 항상 적용된다.
  3. `effective(user).super == true`이면(ADR-079의 super 우선 규칙)
     위 두 제약이 전혀 적용되지 않는다.
  4. **이 제약은 캐패빌리티로 우회할 수 없는 상한선이다.** guest/jail
     프로세스가 ADR-075의 권한 상승 절차를 거쳐 유효한 캐패빌리티를
     이미 보유하고 있더라도(예: 다른 프로세스로부터 IPC 핸들 전달로
     받은 파일/디렉토리 핸들이든, procsrv 승인으로 받은 프록시
     핸들이든), 위 1~2의 격리 범위 안에서는 그 캐패빌리티를 행사할
     수 없다. 즉 이 격리는 "기본값이 무권한이고 요청하면 풀린다"는
     ADR-075의 일반 모델과 달리, **guest/jail에 한해서는 무엇을
     보유하고 있든 넘을 수 없는 상한선**으로 강제된다 — ADR-079가
     이미 "guest의 권한 상승 요청은 항상 거부"라고 정한 것을, "요청이
     거부될 뿐 아니라 어떻게든 획득한 캐패빌리티도 무효화된다"는
     수준까지 명시적으로 확장한다.
- **근거**: 사용자가 "jail은 홈을 제외한 전체가 가상 에뮬레이션처럼
  보이고, guest는 그런 에뮬레이션 없이 홈에 대해서만 읽고 쓸 수
  있다"고 구분했고, 뒤이어 "권한이 있어도 guest/jail은 엄격한
  제한을 받는다"고 명시적으로 강화했다. ADR-080의 오버레이 메커니즘은
  jail에 정확히 맞는 도구이고, guest는 훨씬 단순한 접근 거부 규칙만으로
  충분해 새 메커니즘이 필요 없다 — 두 등급의 요구사항이 근본적으로
  달라 서로 다른 도구를 쓰는 것이 자연스럽다. "캐패빌리티로도 우회
  불가"는 이 프로젝트의 기본 신뢰 모델(ADR-011/023의 순수 캐패빌리티
  모델)에 대한 의도적 예외다 — guest/jail 등급에서만큼은 캐패빌리티
  보유 여부와 무관하게 강제되는 MAC(강제적 접근 통제)류 상한선을
  얹는다.
- **영향**:
  - guest의 거부 규칙은 `open()` 시점(ADR-018)에서 검사하면 되는
    "정상적인 VFS 탐색으로 파일을 여는 경우"는 충분히 막는다. 그러나
    **핸들이 VFS의 `open()`을 거치지 않고 다른 프로세스로부터 IPC
    핸들 전달(ADR-011/023)로 곧장 넘어오는 경우**는 이 지점만으로는
    막을 수 없다 — 이 격리를 결정 4처럼 "캐패빌리티로도 우회 불가"로
    만들려면, FS 서버 쪽(핸들을 실제로 써서 read/write를 수행하는
    시점, ADR-018)에서도 호출자의 `effective` 신원을 확인해 범위
    밖이면 거부하는 추가 검사가 필요하다는 뜻이다 — 즉 이 ADR이
    선언한 "상한선"을 완전히 지키려면 검사 지점이 VFS의 `open()`
    하나로 끝나지 않고 각 FS 서버의 요청 처리 경로까지 확장되어야
    한다. 정확한 확장 방식(모든 FS 서버 프로토콜에 호출자 신원을
    실어 보내는 방법 등)은 이 ADR의 범위를 넘으므로 → 신규
    **미결정 (OPEN-38)**.
  - jail 오버레이는 이 우회 문제가 구조적으로 덜하다 — 오버레이가
    네임스페이스(어떤 마운트 테이블을 보는가) 자체를 바꾸는 것이라,
    설령 다른 프로세스에게서 핸들을 받더라도 그 핸들이 가리키는
    객체 자체는 이미 오버레이가 적용된 세계에서 열린 것이거나
    전역 네임스페이스의 실체 그 자체이므로(핸들은 특정 객체에
    고정되고 재해석되지 않는다), guest처럼 "탐색 규칙 우회"라는
    형태의 구멍이 생기지 않는다.
  - exec() 시 로더(procsrv)가 게스트 소유가 아닌 시스템 바이너리·
    공유 라이브러리를 읽어야 하는 문제(게스트 자신은 home 밖을 읽을
    수 없음)는 이 ADR의 범위 밖이다 — procsrv가 게스트를 대신해
    자신의 권한으로 로딩을 수행하는 방식 등은 procsrv exec 설계
    시점에 정한다.
  - [vfs-layout.md](../spec/vfs-layout.md)/[filesystem.md](filesystem.md)에
    이 정책의 구체적 반영(guest 거부 규칙, jail 오버레이 배정 시점)이
    필요하다 — 다음 vfs-layout.md 갱신 시점에 반영한다.
  - 새 미결정 항목: jail의 synthetic 마운트(`/sys/proc` 등) 가시성
    필터링(예: 자신의 jail 안 프로세스만 보이는지, IPC 엔드포인트
    가시성 제한 범위)의 정확한 범위는 이 ADR의 범위 밖이다 → 신규
    **미결정 (OPEN-37)**.

## ADR-082. guest/jail 실행 제한: `/run`에 설치된 앱·라이브러리만 exec 가능 (ADR-081 갱신)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. `effective(user).guest == true` 또는 `effective(user).jail == true`인
     프로세스가 `exec()`(프로그램 실행, 동적 라이브러리 로드 포함)할
     수 있는 대상은 **`/run`**(ADR-044의 "사용자별 관리 불가 공용
     설치 경로") **아래에 설치된 것으로 한정**한다. `/sys/bin`(OS
     자체 바이너리), `/usr/{다른 사용자}` 등 그 외 어디에 있는
     실행파일도 exec 대상이 될 수 없다 — 설령 그 경로를 읽을 수
     있는 경우(jail의 패스스루 읽기, ADR-081)라도 실행 자체는 이
     규칙으로 별도 차단된다.
  2. 이 검사는 procsrv의 exec 로더가 **심볼릭 링크를 모두 따라간
     뒤의 최종 실제 경로**를 기준으로 수행한다 — `/run` 밖의 파일을
     가리키는 링크를 `/run` 안에 만들어 우회하는 것을 막는다.
  3. ADR-081의 guest 규칙(결정 2, "home 밖 `open()` 전면 거부")을
     이 ADR로 **갱신**한다 — guest의 `open()`은 이제 (a) 자신의
     home 서브트리, (b) `/run` 서브트리 중 하나에 속할 때만 허용된다.
     `/run`에 대해서는 **읽기만** 허용된다 — ADR-044가 이미 `/run`을
     "사용자별 관리 불가"로 정해 일반 사용자에게 쓰기 권한이 없으므로
     별도 규칙 없이 기존 소유자/그룹/기타 권한 비트로 이미 차단된다.
  4. jail의 오버레이 정책(ADR-081 결정 1)은 그대로 유지한다 — 일반
     데이터 열람 목적의 파일 읽기는 여전히 시스템 전역에 패스스루로
     허용된다. 이 ADR이 추가하는 것은 오직 **exec() 대상 제한**뿐이다 —
     "무엇을 읽을 수 있는가"와 "무엇을 실행할 수 있는가"를 서로 다른
     규칙으로 분리한다.
- **근거**: 사용자가 "Guest와 Jail은 시스템 전역으로 `/run`에 설치된
  앱과 라이브러리만 쓸 수 있다"고 명시했다 — ADR-081이 "exec() 시
  로더가 게스트 소유가 아닌 시스템 바이너리를 읽어야 하는 문제는
  범위 밖"이라고 미뤄뒀던 부분에 대한 답이다. `/run`을 유일한 실행
  대상으로 삼으면, ADR-044가 이미 이 경로를 "사용자별 관리 불가
  공용 설치 경로"로 정의해 둔 덕에 관리자가 설치·검증한 것만
  guest/jail이 실행할 수 있다는 화이트리스트 효과를 새 메커니즘
  없이 얻는다. jail에게도 동일하게 적용하는 이유는, jail의 "전체가
  가상 에뮬레이션처럼 보인다"는 읽기 투명성이 "무엇이든 실행할 수
  있다"까지 의미하지는 않기 때문이다 — 데이터 열람과 코드 실행은
  위험도가 다르므로 별도로 통제한다.
- **영향**:
  - procsrv의 exec 구현(아직 상세 설계 전)이 "대상 경로가 `/run`
    아래인가"를 검사하는 단계를 반드시 포함해야 한다 — 정확한 검사
    위치(커널 syscall 자체인지 procsrv 로더 레이어인지)는 procsrv
    상세 설계 시점에 정한다.
  - `/run`에 설치되는 소프트웨어(및 그 동적 라이브러리 의존성)가
    guest/jail이 실제로 쓸 수 있는 유일한 앱 집합이 되므로, 이
    경로에 설치할 수 있는 절차·권한(아마도 root/super 전용)이 향후
    procsrv/패키지 관리 설계에서 중요해진다.
  - ADR-081은 이 ADR로 **부분 갱신**되었다(guest의 열람 가능 경로
    확장) — ADR-081 전체를 대체하는 것이 아니므로 "대체됨" 표시는
    하지 않는다(jail 오버레이 정책, super 우선 규칙, 캐패빌리티
    우회 불가 원칙은 그대로 유효).

## ADR-083. guest/jail의 시스템 가시성 제한: `/sys/proc`은 자기 범위만, `/sys/dev`·`/sys/live`는 완전 차단 (해결: OPEN-37)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. **가시성 범위(visibility scope)** 개념을 둔다 — jail 프로세스는
     자신이 속한 jail 인스턴스(ADR-080/081의 마운트 네임스페이스와
     같은 단위 — 같은 jail로 기동된 프로세스들끼리는 서로 보인다)를,
     guest 프로세스는 **자기 자신과 그 자손 프로세스(fork/exec로
     만든 하위 트리)만**을 가시성 범위로 갖는다.
  2. `/sys/proc`(procsrv, ADR-047)을 guest/jail 신원이 조회하면
     시스템 전체 프로세스 목록이 아니라 **자신의 가시성 범위 안
     프로세스만** 나열·조회된다 — 범위 밖 프로세스는 목록에서 아예
     빠지고, 개별 조회를 시도해도 `not_found`류로 응답한다.
  3. `/sys/dev`(devmgr, ADR-048)와 `/sys/live/*`(ADR-058: network/
     sched/mem)는 guest/jail 신원에게 **완전히 차단**된다 — 부분
     필터링이 아니라 조회 자체가 거부된다(`permission_denied`류).
     시스템에 어떤 장치가 있는지, 무엇이 돌아가고 있는지 확인할
     수단 자체를 주지 않는다.
  4. 이 규칙은 ADR-081이 jail 오버레이에 기본 허용한 "읽기는 시스템
     전역에 패스스루"에 대한 **명시적 예외**다 — `/sys/proc`,
     `/sys/dev`, `/sys/live/*`는 synthetic 마운트(ADR-047)라 애초에
     "실제 파일을 읽는다"는 개념이 아니라 담당 서버가 매 요청마다
     자신의 실제 상태를 조합해 응답하는 것이므로, 그 서버 자신이
     호출자의 guest/jail 신원과 가시성 범위를 검사해 응답을 걸러낸다 —
     VFS의 오버레이·패스스루 메커니즘과는 별개로, 각 synthetic 서버
     자신의 책임이다.
  5. super는(ADR-079) 이 제한을 받지 않는다.
- **근거**: 사용자가 "jail 안에 있으면 자기 jail 프로세스만 보이고,
  시스템에 어떤 장치가 있는지·뭐가 실행 중인지 전혀 확인 불가해야
  한다"고 명시했고, guest도 동일 정책을 적용하라고 했다. `/sys/proc`을
  완전 차단이 아니라 "자기 범위만"으로 필터링한 이유는, 그렇지
  않으면 guest/jail 프로세스가 `ps`류로 자기 자신조차 조회할 수 없어
  정상적인 프로세스 관리(자식 대기, 자기 자원 사용량 확인 등)가
  불가능해지기 때문이다 — 반면 `/sys/dev`/`/sys/live`는 "내 것"이라는
  부분 집합 개념이 아예 없으므로(디바이스·시스템 설정은 특정
  프로세스 소유가 아니다) 완전 차단이 자연스럽다.
- **영향**:
  - procsrv가 `/sys/proc` FS 서버 프로토콜을 구현할 때, 호출자의
    guest/jail 여부와 가시성 범위(같은 jail 소속인지, 자손 관계인지)를
    판별하는 로직이 필요하다 — 프로세스 생성(fork/exec) 시 "어느
    jail/guest 세션 소속인지", "누구의 자손인지"를 추적하는 메타데이터가
    procsrv의 프로세스 테이블에 필요해진다(구체적 자료구조는 procsrv
    상세 설계 시점에 정한다).
  - devmgr(`/sys/dev`)와 `/sys/live/*`의 각 담당 서버(netsrv, procsrv,
    정책 서버)도 동일하게 호출자 신원 검사를 자신의 FS 서버 구현에
    추가해야 한다 — ADR-047이 이미 "각 서버가 FS 서버 프로토콜을
    직접 구현"하도록 정해 두었으므로 새 아키텍처 계층 없이 각 서버의
    구현 범위 안에서 해결된다.
  - synthetic 마운트는 핸들이 파일 내용을 "가리키는" 것이 아니라
    매 요청을 서버가 직접 처리하는 방식이라, OPEN-38이 우려하는
    "핸들만 넘겨받아 우회"가 애초에 성립하기 어렵다 — 오히려 일반
    FS(§OPEN-38)보다 이 영역은 구조적으로 더 안전하다.

## ADR-084. 신원 전파 메커니즘: procsrv가 badge에 uid/S·G·J/jail 인스턴스를 인코딩해 프로세스 생성 시 발급 (ADR-083 구체화)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. IPC에 이미 있는 `badge`(ipc.md §3, "엔드포인트 프록시 발급 시
     커널이 부여하는, 서버가 호출자를 구분하는 식별자")를 재사용해
     synthetic FS 서버(procsrv의 `/sys/proc`, devmgr의 `/sys/dev`,
     `/sys/live/*`의 각 서버)가 매 요청의 호출자 신원을 badge만으로
     즉시 판별하게 한다 — 새 커널 개념·시스템 콜을 추가하지 않는다.
  2. badge(`uint64_t`)는 다음과 같이 신원 정보를 직접 인코딩한다:

     ```cpp
     struct identity_badge {
         uint32_t uid;
         uint16_t jail_instance_id;  // 0 = jail 아님 (ADR-081/083의 "가시성 범위" 단위)
         uint8_t  flags;             // bit0=super, bit1=guest, bit2=jail (effective, ADR-079)
         uint8_t  _reserved;
     };
     static_assert(sizeof(identity_badge) == sizeof(uint64_t));
     ```

  3. **badge는 오직 "재위임 가능한 마스터" 캐패빌리티로부터 처음
     배지 붙은 프록시를 만드는 시점에만 값이 정해진다.** 그 프록시로부터
     다시 파생되는 하위 프록시(ADR-032의 체인)는 **동일한 badge 값을
     그대로 상속**하며, 재위임 과정에서 badge가 바뀌지 않는다 — 바뀌는
     것은 `rights`(부분집합으로 축소)뿐이다. 이는 objects.md의
     `handle_entry`(objects.md §3)에 `badge` 필드가 필요하다는 뜻이며,
     이 ADR로 그 필드를 추가한다(§영향 참고, objects.md 갱신).
  4. **발급 절차**: procsrv는 새 프로세스를 생성할 때(fork/exec, 또는
     initrun이 최초 서버들을 기동할 때), 그 프로세스가 필요로 하는
     각 시스템 서비스 엔드포인트(VFS, devmgr, netsrv, 정책 서버 등)에
     대해 부팅 시 미리 위임받아 둔 재위임 가능 프록시를 사용해, 그
     프로세스 전용의 새 배지 붙은 프록시를 만들어 초기 핸들 테이블에
     넣어준다. 배지 값은 그 프로세스의 `identity_badge`(uid,
     jail_instance_id, effective S/G/J)를 그대로 담는다.
  5. 각 시스템 서비스(VFS, procsrv 자신, devmgr, netsrv 등)는 부팅
     초기에 자신의 서비스 엔드포인트에 대한 재위임 가능 프록시를
     procsrv에게 발급해 둬야 한다 — initrun 기동 매니페스트(OPEN-29)가
     확정될 때 이 위임 절차가 함께 반영되어야 한다.
  6. 서버는 `sys_recv`가 반환한 badge(ipc.md §3)를 그대로 `identity_badge`로
     해석해, ADR-081(guest/jail VFS 경로 제한), ADR-082(exec 제한),
     ADR-083(가시성 필터링)의 규칙을 그 자리에서 직접 적용한다 —
     procsrv에게 "이 uid가 누구냐"를 매번 왕복 질의할 필요가 없다.
- **근거**: badge는 이미 "서버가 호출자를 구분하는 식별자"로 정의돼
  있었지만(ipc.md §3), 정확히 언제·누가 값을 정하고 재위임 시
  유지되는지는 명세된 적이 없었다 — 이 ADR이 그 공백을 메운다. 신원
  데이터를 badge 자체에 통째로 인코딩(자기서술적, self-describing)한
  이유는, `/sys/proc` 등 빈번한 synthetic 요청마다 procsrv에게 "이
  uid가 뭐냐" 왕복 질의를 하면 ADR-018/047이 지향하는 "탈중앙화된,
  빈번한 I/O는 직접 통신" 원칙과 정면으로 충돌하는 오버헤드가 되기
  때문이다. badge가 재위임 중 불변이라는 규칙은, 위임받은 프록시를
  다른 프로세스에게 다시 넘기더라도 "원래 누구 것이었는지"가 항상
  보존되게 한다 — 위임이 곧 신원 세탁이 되는 것을 구조적으로 막는다.
- **영향**:
  - [objects.md](../spec/objects.md) §3의 `handle_entry`에 `badge`
    필드(엔드포인트 종류의 프록시에서만 의미 있음)를 추가해야 한다 —
    소유 핸들(`parent == nullptr`)의 badge는 0(의미 없음)이며, 최초
    배지 부여는 오직 "재위임 가능 마스터"로부터 새 프록시를 만드는
    특정 연산에서만 값을 지정할 수 있고, 이후 그 프록시에서 파생되는
    모든 자손은 같은 badge를 상속한다(스펙 갱신, 이 ADR과 함께 반영).
  - `identity_badge`의 정확한 비트 배치·헬퍼 함수는 `libk`가 아니라
    procsrv/각 시스템 서버가 공유하는 별도의 작은 공통 헤더에 둔다 —
    정확한 위치는 procsrv 상세 설계 시점에 정한다(ADR-079가 암호
    유틸리티를 libk 밖에 둔 것과 같은 논리 — libk는 커널까지 링크되는
    범용 라이브러리라 서버 전용 정책 구조체를 두지 않는다).
  - `fork()`(ADR-016) 시 자식은 부모의 배지 붙은 핸들을 그대로
    물려받으므로(같은 `identity_badge`), 자식도 부모와 동일한
    uid/jail_instance_id로 필터링된다 — 별도 처리가 필요 없다.
  - `jail_instance_id`를 누가 할당·회수하는지(카운터 방식, 재사용
    정책)는 procsrv 상세 설계 시점에 정한다.
  - **OPEN-38 재평가**: badge가 재위임 중 불변이라는 규칙 덕분에,
    guest/jail 프로세스가 자신의 배지 붙은 핸들을 다른 프로세스에게
    IPC로 넘기더라도 그 핸들을 통한 호출은 여전히 원래 프로세스의
    `identity_badge`로 필터링된다 — "핸들을 넘겨서 신원을 위장"하는
    경로는 이 설계로 막힌다. 남는 위험은 방향이 반대인 경우다: super/
    root 프로세스가 **의도적으로** 자신의 상위 권한 badge가 붙은
    핸들을 jail/guest 프로세스에게 건네주는 경우로, 이는 이 프로젝트의
    캐패빌리티 모델(ADR-011/023) 전반에 내재한 일반적인 "confused
    deputy" 문제이지 jail/guest에 특화된 결함이 아니다 — OPEN-38의
    범위를 이 방향으로 좁혀 유지한다.

## ADR-085. super badge의 jail/guest 재위임 원천 차단: 커널이 handle_transfer 시점에 강제 (해결: OPEN-38)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. `address_space` 객체에 `confinement_tier`(uint8_t: `normal`=0,
     `guest`=1, `jail`=2) 필드를 추가한다 — ADR-063의 `trusted`와
     같은 성격의, 커널이 직접 보유하는 프로세스 속성이다. 이 값은
     프로세스 생성 시 **정확히 한 번** 설정되며 이후 변경할 수 없다.
  2. 이 값을 설정할 수 있는 권한은 ADR-074의 "trusted 부여 권한"과
     동일한 성격의 별도 캐패빌리티("confinement 설정 권한")로
     표현한다 — 커널이 initrun에게 부여하고, initrun이 procsrv(신원의
     진실 공급원, ADR-079)에게 위임한다. 이 권한 없이 `confinement_tier`를
     `normal` 이외 값으로 설정하려는 프로세스 생성 요청은 커널이 거부한다.
  3. **커널은 IPC의 handle_transfer(objects.md §4) 절차에 다음 검사를
     추가한다**: 전달하려는 `src_entry.badge`를 `identity_badge`
     (ADR-084)로 해석해 `flags`의 super 비트가 설정되어 있고, **수신
     프로세스의 `address_space.confinement_tier`가 `guest` 또는
     `jail`이면 이 핸들 전달을 거부**한다(`ipc_error::permission_denied`,
     objects.md §4의 기존 "부분 실패" 방식과 동일하게 그 핸들 항목만
     실패 처리하고 IPC 자체는 계속 진행). **발신자가 누구든 — 설령
     발신자 자신이 super라도 — 예외 없이 적용된다.** 이 경로에는
     어떤 우회 절차도 두지 않는다(아래 §영향 참고).
  4. 이 검사가 성립하려면 커널이 `identity_badge`의 `flags` 바이트
     레이아웃(적어도 super 비트의 위치)을 알아야 한다 — ADR-084가
     "badge는 커널에 불투명하다"고 한 원칙에 대한 **의도적이고 유일한
     예외**다. `identity_badge`의 `flags` 바이트는 이 순간부터
     커널·procsrv가 공유하는 고정 ABI로 승격된다(`boot_info`가
     커널·initrun 공유 ABI인 것과 같은 성격, ADR-026).
- **근거**: 사용자가 이 경로를 "원천적으로 금지"하라고 명시했다 —
  유저랜드 서버의 선의나 관례에 의존하는 정책이 아니라, 유일한 위임
  통로인 커널의 handle_transfer 자체가 예외 없이 차단해야 한다는
  뜻이다. objects.md §5가 이미 "핸들 생성은 오직 IPC의 부수 효과로만
  일어난다"고 정해뒀으므로, 이 한 지점만 막으면 어떤 유저랜드 코드도
  우회할 방법이 없다.
- **영향**:
  - [objects.md](../spec/objects.md) §2에 `confinement_tier` 필드(및
    설정 권한 절차)를, §4의 handle_transfer 절차에 이 검사 단계를
    추가해야 한다(스펙 갱신, 이 ADR과 함께 반영).
  - `confinement_tier` 설정 절차는 ADR-074의 `trusted` 부여 절차와
    사실상 동일한 위임 체인을 공유하므로, 두 필드를 프로세스 생성
    syscall의 같은 인자 묶음으로 함께 설계하는 것이 자연스럽다 —
    실제 프로세스 생성 syscall/서버 API 상세 설계 시점(procsrv 상세
    설계)에 하나로 묶어 정의한다.
  - **의도적으로 이 경로에 예외(우회) 절차를 두지 않는다.** "super가
    격리된 서버 데몬에게 특정 리소스 접근을 신중하게 열어주고 싶다"는
    유스케이스가 떠오를 수 있지만, 사용자가 이를 명시적으로 배제했다 —
    이런 요구(격리된 데몬에게 선별적으로 상위 권한 리소스를 제공)는
    이 캐패빌리티/badge 모델의 예외 규칙으로 풀 문제가 아니라, **아직
    설계되지 않은 별도의 가상화 지원(virtualization support) 기능**의
    영역으로 분리한다 — 서버 데몬 격리가 필요한 시나리오는 jail/guest
    사용자 신원 모델이 아니라 그 가상화 지원 메커니즘을 쓰도록
    안내한다. 가상화 지원 자체의 설계는 이 ADR의 범위 밖이며, 실제
    착수 시점에 별도 계획/설계 문서로 다룬다.
  - OPEN-38은 이 ADR로 해소된다.

## ADR-086. 신원 불변 원칙: 신원 변경은 항상 새 프로세스 생성으로만 이뤄진다

- **상태**: 확정 (2026-09-08)
- **결정**: 프로세스의 `identity_badge`(uid/gid/S·G·J, ADR-084)와
  `confinement_tier`/`trusted`(ADR-074/085)는 생성 시 한 번 정해지면
  **그 프로세스가 살아있는 동안 절대 변경되지 않는다.** 로그인(다른
  사용자로 세션을 시작), `su`/`sudo`류의 신원 전환처럼 "다른 신원이
  되어야 하는" 모든 시나리오는 **기존 프로세스를 변형하는 것이 아니라
  항상 새 프로세스를 생성**하는 방식으로만 구현된다.
- **근거**: ADR-074/085가 이미 `trusted`/`confinement_tier`를 "생성
  시 정확히 한 번 설정, 이후 변경 불가"로 못박아 뒀다 — 이 ADR은 그
  원칙을 `identity_badge` 전체로 명시적으로 일반화한다. 신원을 제자리
  변경(in-place mutation) 가능하게 두면, 어떤 시점에 어떤 코드가
  "지금 이 프로세스는 누구인가"를 가정하고 있었는지 추적하기 어려워져
  전통적 Unix의 `setuid()` 계열이 낳은 유명한 혼동·특권 상승 버그
  계열(예: 잘못된 순서로 권한을 낮추다 실패)이 그대로 재현될 위험이
  있다. 새 프로세스 생성은 이미 이 시스템의 기본 연산이고(ADR-011/016),
  생성 시점에만 신원을 정하면 "이 프로세스는 태어날 때부터 지금까지
  같은 신원"이라는 불변식이 코드 전체에서 공짜로 성립한다.
- **영향**:
  - ADR-075(권한 상승)는 이미 "기존 프로세스의 신원을 바꾸지 않고
    추가 캐패빌리티만 건네준다"는 방식이라 이 원칙과 원래부터
    일치한다 — 새삼 바뀌는 것은 없다.
  - 로그인(ADR-088)은 반드시 **새 프로세스 생성**으로 구현되어야
    한다 — 로그인 프롬프트 프로세스 자신의 신원을 인증된 사용자로
    "전환"하는 방식은 허용되지 않는다.
  - `su`/`sudo`류의 "다른 사용자로 셸 전환" 기능이 향후 유저랜드에
    추가되더라도, 내부적으로는 반드시 procsrv에게 새 프로세스 생성을
    요청하는 형태여야 한다 — 구체적 UX(같은 터미널에서 이어지는 것
    처럼 보이게 하는 방법 등)는 유저랜드 셸 설계 시점에 정한다.

## ADR-087. 계정 생성 절차: super 전용 + procsrv의 uid 채번 + 최초 부팅 시 root 계정 부트스트랩

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 계정(`user_account`)/그룹(`group_account`) 생성은 **super 등급
     계정만** 요청할 수 있다 — procsrv가 요청자의 badge(ADR-084)로
     `effective.super`를 확인하고, 아니면 즉시 거부한다.
  2. **uid 채번 규칙**: `uid 0`은 최초 부팅 시 자동 생성되는 root
     계정 전용으로 예약한다. `uid 1~999`는 시스템 서비스 계정
     (로그인 프롬프트 등 procsrv/initrun이 기동하는 비대화형 서비스,
     §ADR-088 참고) 대역이다. `uid 1000` 이상이 사람 계정이다. 이
     대역 배정은 procsrv가 채번 시 자동 적용한다(호출자가 uid를
     직접 지정하지 않음 — procsrv가 다음 빈 값을 고른다).
  3. uid 카운터는 `@global/system/counters` 레지스트리 테이블의
     `next_uid` 키(정수)에 보관한다 — procsrv가 계정 생성마다 원자적
     증가시킨다. procsrv는 계정 생성 요청을 내부적으로 직렬화하는
     락으로 경쟁을 막는다(계정 생성은 빈도가 낮은 관리 작업이므로
     성능보다 정확성을 우선한다, ADR-001).
  4. **최초 부팅 부트스트랩**: procsrv가 시작할 때 `@global/system/users`
     테이블이 비어 있으면(최초 부팅), `boot_info.cmdline`(boot.md §3)에서
     초기 root 계정의 인증 정보(비밀번호 또는 공개키, 커맨드라인
     파라미터 형식은 §영향에서 procsrv 상세 설계 시 정함)를 읽어 `uid=0,
     super=true`인 root 계정을 이 경로로만 생성한다 — 이 부트스트랩
     경로는 §결정 1의 "super만 요청 가능" 검사를 우회하는 **유일한
     예외**다(요청자가 없고 커널이 전달한 부팅 파라미터가 근거이므로
     애초에 "요청자 검증"이라는 개념이 성립하지 않는다). 테이블이
     이미 비어있지 않으면(두 번째 이후 부팅) 이 경로는 절대 실행되지
     않는다.
  5. 계정 생성 시 procsrv는 (a) `@global/system/users`에 새
     `user_account`를 쓰고, (b) 별도 gid가 지정되지 않으면 같은 이름의
     전용 그룹(`uid == gid`)을 `@global/system/groups`에 함께 만들며,
     (c) [vfs-layout.md](../spec/vfs-layout.md) §2의 `/usr/{사용자명}/{bin,lib,etc,home}`
     서브트리를 VFS에 생성 요청한다.
- **근거**: super 전용으로 제한하는 것은 ADR-079가 이미 이 테이블의
  쓰기 권한을 "super만"으로 정해 둔 것의 자연스러운 적용이다. uid
  대역 구분(0/1~999/1000+)은 전통적 Unix 관례를 그대로 채용해 낯설지
  않게 한다. 부트스트랩 문제(계정을 만들려면 super가 필요한데, 최초
  부팅 시점엔 어떤 계정도 없다)는 커널이 이미 갖고 있는
  `boot_info.cmdline`(boot.md, ADR-026/030)을 재사용해 푼다 — 새로운
  부팅 파라미터 전달 경로를 발명하지 않는다.
- **영향**:
  - cfgsrv는 부팅 초기(procsrv보다 먼저 기동, `trusted=true`는
    initrun이 직접 부여, ADR-074)에 `@global/system/users`,
    `@global/system/groups`, `@global/system/counters` 테이블을
    준비하고, procsrv에게 이 세 테이블에 대한 **전체 권한(rwx)
    `reg_table` 핸들**을 발급해야 한다 — initrun 기동 매니페스트
    (OPEN-29)의 서버 기동 순서에 "cfgsrv → procsrv" 의존관계로
    반영되어야 한다.
  - `boot_info.cmdline`에 root 초기 인증 정보를 담는 정확한 문법
    (예: `root_pubkey=<base64>` 또는 설치 스크립트가 별도 initrd
    파일로 제공)은 procsrv 상세 설계 시점에 정한다 — 평문 비밀번호를
    커맨드라인에 그대로 남기는 방식은 프로세스 목록 등으로 유출될
    수 있어(전통적 Unix에서도 알려진 안티패턴) 지양하고, 공개키
    등록 또는 initrd 내 일회성 파일 참조를 우선 검토한다.
  - `special_bits`(registry.md §3, setuid류)나 계정 삭제/그룹 멤버십
    변경 같은 나머지 계정 관리 오퍼레이션은 이 ADR의 범위 밖이다.

## ADR-088. 로그인 절차: 인증 성공 시 procsrv가 새 프로세스를 생성해 trusted/confinement_tier를 최초 결정

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 로그인은 **인증되지 않은(또는 시스템 서비스 등급, ADR-087의
     uid 1~999) 로그인 프롬프트 프로세스**가 procsrv에게 자격 증명을
     제시하는 것으로 시작한다. 이 프로세스는 initrun/procsrv가 기동
     매니페스트에 따라 콘솔/세션당 하나씩 띄우는 시스템 서비스이며,
     자기 자신은 어떤 사람 계정의 신원도 갖지 않는다.
  2. **인증 방식별 절차**(ADR-079의 `auth_method`):
     - `password_hash`: 로그인 프롬프트가 평문 비밀번호(≤64바이트,
       ADR-079)를 담아 단일 Call로 procsrv에 전달한다. procsrv가
       저장된 salt·반복 횟수로 서버 측에서 PBKDF2-HMAC-SHA256을
       계산해 저장값과 상수 시간 비교한다 — salt를 클라이언트에
       내주지 않는다(클라이언트가 직접 해시를 계산하지 않으므로
       네트워크 노출 등의 문제가 애초에 없다 — 로컬 IPC라는 전제와도
       맞다).
     - `public_key`: 2단계 챌린지-응답. ① 로그인 프롬프트가 사용자명만
       담아 `op_login_challenge` Call → procsrv가 무작위 nonce를
       생성해 짧은 TTL로 보관하고 반환. ② 로그인 프롬프트가 그 nonce에
       대한 서명을 담아 `op_login` Call → procsrv가 저장된 Ed25519
       공개키로 검증. TTL 만료 후 또는 검증 실패 시 해당 시도는
       폐기된다(재사용 금지 — 재전송 공격 방지).
  3. 인증에 실패하면 `proc_error::auth_failed`를 반환한다 — 실패
     사유(계정 없음/자격 증명 불일치)는 **구분해서 알려주지 않는다**
     (계정 존재 여부를 외부에 흘리지 않기 위한 통상적 관례).
  4. 인증에 성공하면 procsrv는 **로그인 프롬프트 프로세스를 변형하지
     않고**(ADR-086) 다음을 수행해 완전히 새로운 `process_entry`를
     만든다:
     a. `effective(user)`의 uid/gid/super/guest/jail(ADR-079)로
        `identity_badge`를 구성한다. jail이면 새 `jail_instance_id`를
        할당한다(같은 사용자의 재로그인은 새로운 jail 인스턴스로
        취급한다 — 이전 로그인 세션과 격리 공간을 공유하지 않는다).
     b. ADR-074/085로 위임받은 권한을 사용해 이 신규 프로세스의
        `trusted`(항상 `false` — 사람 로그인 세션은 신뢰 프로세스가
        아니다)와 `confinement_tier`(`effective.guest`/`effective.jail`에
        따라 `guest`/`jail`/`normal`)를 최초로 설정한다.
     c. jail이면 [filesystem.md](filesystem.md) ADR-080의 에페메럴
        오버레이 네임스페이스를 이 프로세스에 배정한다(홈 서브트리
        패스스루 포함, ADR-081).
     d. ADR-084 §4와 동일한 절차로 시스템 서비스 badge 붙은 초기
        핸들들을 발급한다 — badge는 방금 결정한 `identity_badge`를
        인코딩한다.
     e. 이 신규 프로세스에서 사용자의 기본 셸(`user_account`에 아직
        없는 필드 — 기본값은 시스템 전역 설정을 따르는 것으로
        procsrv 상세 설계 시 확정)을 `exec()`한다(§procsrv.md §4의
        일반 exec 절차를 그대로 따르며, guest/jail이면 ADR-082의
        `/run` 제한이 여기서도 그대로 적용된다 — 즉 guest/jail
        사용자의 로그인 셸 자체도 `/run`에 설치되어 있어야 한다).
  5. 로그인 프롬프트 프로세스는 신규 세션 프로세스의 부모가 **아니다**
     — procsrv 프로세스 테이블에서 신규 프로세스의 `parent`는 없음
     (`nullptr`)으로 둔다. 로그인 프롬프트는 자신의 콘솔에 대해
     계속 새 로그인을 받을 수 있도록 루프를 돈다(구체적 콘솔/세션
     관리 방식은 §영향 참고).
- **근거**: 사용자 인증이라는 민감한 절차를 로그인 프롬프트라는
  비교적 얇고 반복되는 서비스에 맡기지 않고 procsrv(신원의 유일한
  진실 공급원, ADR-079)가 직접 수행하게 함으로써 인증 로직이 한
  곳에만 존재한다. 신원 결정을 새 프로세스 생성으로 하는 것은
  ADR-086의 직접적인 적용이다. jail 재로그인마다 새
  `jail_instance_id`를 주는 것은 ADR-083의 "가시성 범위"가 로그인
  세션 단위로 자연스럽게 격리되게 한다 — 같은 사용자라도 다른 로그인
  세션의 프로세스를 서로 보게 하지 않는다.
- **영향**:
  - 로그인 프롬프트 프로세스 자체의 상세 설계(콘솔/tty 드라이버와의
    관계, 여러 콘솔에 걸친 다중 로그인 프롬프트 기동 방식)는 아직
    실제 콘솔 드라이버(ADR-007이 예고한, 디버그 콘솔과 별개인 유저
    프로세스 콘솔 드라이버)가 설계되지 않아 함께 미정이다 → 신규
    **미결정 (OPEN-39)**.
  - `user_account`에 "기본 셸" 필드가 아직 없다 — ADR-079의 구조체를
    확장할지, 별도 레지스트리 테이블(`@사용자/shell`류)로 둘지는
    procsrv 상세 설계 시점에 정한다.
  - 로그아웃(세션 종료) 절차, 세션 프로세스가 예기치 않게 죽었을 때의
    정리(cleanup) 절차는 이 ADR의 범위 밖이다.

## ADR-089. `user_account`에 `session_program` 필드 추가: 기본값 `/run/bin/hello`, 계정별 재정의 가능 (ADR-079/088 갱신)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. `user_account`(ADR-079)에 `session_program`(경로 문자열) 필드를
     추가한다. **기본값은 `/run/bin/hello`**다 — 계정 생성 시
     (procsrv.md §7.1) 별도로 지정하지 않으면 이 값이 채워진다.
  2. 로그인 성공 시(ADR-088 §결정 4) procsrv가 `exec()`하는 대상은
     "사용자의 기본 셸"이 아니라 **이 `session_program`**이다.
  3. `session_program`이 하는 일(사용자를 환영하고 셸 또는 데스크톱
     환경을 스폰하는 것)은 순수 유저랜드 관례다 — 커널·procsrv는
     이 프로그램의 내부 동작을 전혀 알거나 강제하지 않는다. procsrv
     입장에서는 "로그인 성공 시 exec할 경로" 하나일 뿐이다.
  4. guest/jail 계정의 경우 ADR-082(`/run` 밖 실행 금지)가 로그인
     시점의 `session_program` exec에도 그대로 적용된다 — guest/jail
     계정의 `session_program`은 반드시 `/run` 서브트리 안이어야 하며,
     계정 생성 시(procsrv.md §7.1) 이를 미리 검증해 잘못 설정된
     계정이 "로그인할 때마다 매번 실패"하는 상황을 생성 시점에
     방지한다.
- **근거**: 사용자가 "각 세션의 기본 프로세스는 `/run/bin/hello`로
  하고, 계정별로 변경될 수 있으며, 유저를 환영하고 셸/데스크톱
  환경을 스폰한다"고 명시했다. 필드명을 "셸"이 아니라
  `session_program`으로 정한 이유는, 이 프로그램의 역할이 POSIX
  `$SHELL`(대화형 명령줄 해석기)보다 넓기 때문이다 — 셸을 직접
  스폰할 수도, 그래픽 데스크톱 환경을 스폰할 수도 있으므로 "세션의
  시작점"이라는 더 일반적인 개념으로 이름 붙인다. 기본값을
  `/sys/bin`의 무언가가 아니라 `/run/bin/hello`로 둔 이유는, `/run`이
  이미 ADR-044의 "사용자별 관리 불가 공용 설치 경로"라 관리자가
  배포하는 세션 진입점을 모든 계정이 공유하는 기본값으로 삼기에
  자연스럽고, guest/jail의 실행 제약(ADR-082)과도 처음부터
  정합적이기 때문이다.
- **영향**:
  - [procsrv.md](../spec/procsrv.md) §7.1의 `create_user_request`에
    `session_program` 필드를 추가해야 한다(스펙 갱신, 이 ADR과 함께
    반영).
  - procsrv.md §8.3의 "사용자의 기본 셸을 exec()한다"는
    "`user_account.session_program`을 exec()한다"로 교체한다(스펙
    갱신).
  - ADR-088 §영향의 "user_account에 기본 셸 필드가 아직 없다"는 이
    ADR로 해소된다.
  - `/run/bin/hello`라는 실제 바이너리가 초기 시스템 이미지(패키징,
    `mkinitrd` 또는 별도 `/run` 시딩 절차)에 반드시 포함되어야 한다 —
    그렇지 않으면 모든 계정의 첫 로그인이 실패한다. 이 바이너리
    자체의 구현(환영 메시지, 셸/DE 선택 로직)은 유저랜드 애플리케이션
    설계 대상이며 이 ADR의 범위 밖이다.

## ADR-090. su/sudo: procsrv의 신원 결정 메커니즘을 재사용하되 부모는 호출 프로세스, 로그인 프롬프트를 거치지 않는다

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 셸에서 `su`/`sudo`류로 다른 신원의 프로세스를 만드는 것은
     ADR-088의 로그인과 **같은 근본 메커니즘**(procsrv가 대상 신원의
     `identity_badge`/`trusted`/`confinement_tier`를 새로 결정해
     **새 프로세스**를 생성 — ADR-086)을 재사용하지만, 다음 두 가지가
     로그인과 다르다:
     a. **부모-자식 관계**: 새 프로세스의 `parent`는 `nullptr`이 아니라
        **호출한 셸 프로세스**다 — su/sudo로 실행한 프로그램이 끝나면
        호출한 셸이 `wait()`으로 종료를 회수하고, 셸의 잡 컨트롤
        (포그라운드/백그라운드) 대상이 될 수 있어야 하기 때문이다.
     b. **로그인 프롬프트 프로세스를 거치지 않는다**: 이미 인증된
        셸이 procsrv에게 **직접** 신원 전환을 요청한다 — ADR-088의
        "인증되지 않은 로그인 프롬프트가 요청"이라는 전제가 애초에
        성립하지 않는다(호출자는 이미 어떤 신원으로든 로그인해 있는
        상태).
  2. `su <계정명>`은 **대상 계정의 자격 증명**을 검증한다(호출자가
     이미 super가 아닌 한 — super는 다른 계정의 자격 증명 없이
     전환 가능, 전통적 Unix의 "root는 비밀번호 없이 su 가능"과 동일한
     관례). 검증 절차는 ADR-088 §8.2를 그대로 재사용한다(대상이
     아니라 호출자가 재사용의 주체일 뿐, 해시 비교/공개키 챌린지
     로직 자체는 동일).
  3. `sudo <명령>`처럼 "정책에 따라 재확인만 하고 상승"하는 형태
     (호출자 자신의 자격 증명만 재확인하고, 대상 계정의 자격 증명
     없이 전환)는 **별도의 승인 정책**(누가 어떤 대상으로 전환을
     허가받았는지 — 전통적 `/etc/sudoers`류)이 **필요하며, 이 정책
     자체는 이 ADR의 범위 밖이다** → 신규 미결정(§영향).
  4. su/sudo로 생성된 프로세스도 §결정 1처럼 새 프로세스이므로, 원래
     셸의 신원은 전혀 바뀌지 않는다(ADR-086과 정확히 일치) — "셸
     안에서 root가 된 것처럼 보이는" 사용자 경험은 새 프로세스가 새
     터미널 세션처럼 동작하는 것으로 얻는다(구체적 터미널/tty
     재바인딩 방식은 콘솔 드라이버 설계 시점, OPEN-39와 함께 다룬다).
- **근거**: 사용자가 "셸에서 sudo나 su를 했을 땐 [로그인과] 조금
  달라야 한다"고 명시했다. 신원 결정 메커니즘 자체(새 프로세스 생성,
  ADR-086)를 재사용하는 것은 일관성을 위해서다 — su/sudo가 로그인과
  별개의 새로운 메커니즘을 만들 이유가 없다. 다만 "누가 요청하는가"
  (인증 안 된 로그인 프롬프트 vs 이미 인증된 셸)와 "결과 프로세스가
  어디 속하는가"(독립 세션 vs 호출 셸의 자식)는 근본적으로 다른
  문맥이므로 그 두 가지만 구분한다.
- **영향**:
  - procsrv IPC 프로토콜(procsrv.md §6)에 `su`/`sudo` 전용
    오퍼레이션이 추가되어야 한다 — 정확한 요청/응답 형식은 procsrv.md
    다음 라운드에서 정의한다.
  - `sudoers`류 승인 정책(§결정 3)의 데이터 모델·저장 위치(레지스트리
    테이블 추가 여부)·검사 절차는 완전히 미정이다 → 신규 **미결정
    (OPEN-40)**.
  - su 대상 계정의 `effective` 등급(guest/jail/super)이 호출자와
    다를 수 있으므로, 전환 후 프로세스의 `confinement_tier`/`trusted`는
    **대상 계정 기준으로 새로 결정**된다(호출자 것을 물려받지 않는다) —
    로그인과 동일한 규칙(ADR-088 §결정 4)이 그대로 적용된다.

## ADR-092. su/sudo 실행 대상: 호출자가 지정한 명령, `session_program`이 아님 (ADR-090 갱신)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 로그인(ADR-088)에서 procsrv가 `exec()`하는 대상은 항상
     `user_account.session_program`(ADR-089, 기본값 `/run/bin/hello`)
     이다 — 계정이 로그인할 때마다 "환영 + 셸/데스크톱 환경 준비"라는
     고정된 진입점을 거친다.
  2. su/sudo(ADR-090)에서 procsrv가 `exec()`하는 대상은 **호출자가
     그 요청의 인자로 전달한 명령(경로+인자)**이다 — 대상 계정의
     `session_program`은 이 경로에서 전혀 참조되지 않는다. su/sudo
     오퍼레이션은 명령 인자를 **필수**로 받는다.
  3. 이 차이는 두 절차의 목적이 다르기 때문이다 — 로그인은 "이
     사용자의 세션을 처음부터 준비"하는 것이고, su/sudo는 "이미 떠
     있는 셸에서 특정 명령 하나를 다른 신원으로 실행"하는 것이다.
     후자에서 `session_program`을 또 거치면(다시 "환영" 메시지를
     보여주고 새 셸/데스크톱 환경을 준비) su/sudo의 목적(단발성 명령
     실행)과 맞지 않는다.
- **근거**: 사용자가 "로그인했을 땐 `session_program`(`/run/bin/hello`)이
  구동되면서 셸/데스크톱 환경을 준비하고, su/sudo는 인자로 받은
  명령을 구동한다는 점이 다르다"고 명시적으로 구분했다. ADR-090이
  "새 프로세스 생성"이라는 메커니즘 자체는 로그인과 공유한다고
  정했지만 **그 새 프로세스가 무엇을 `exec()`하는지**는 명시하지
  않았다 — 이 ADR이 그 공백을 메운다.
- **영향**:
  - [procsrv.md](../spec/procsrv.md) §6의 `proc_op`에 추가될 su/sudo
    오퍼레이션(정확한 형식은 여전히 미정, procsrv.md §10)은 요청
    메시지에 **명령 경로+인자**를 필수 필드로 포함해야 한다 — 실제
    프로토콜을 정의하는 다음 라운드에 반영한다.
  - `su`를 명령 인자 없이 호출했을 때 "대상 계정의 로그인 셸을
    띄운다"는 전통적 Unix 관례는, procsrv의 su 오퍼레이션 자체가
    아니라 **유저랜드 `su` 커맨드라인 도구**가 인자를 생략하면 자기
    쪽에서 기본 명령(예: `$SHELL` 또는 대상 계정의 셸 경로)을 채워
    procsrv에 전달하는 방식으로 구현한다 — procsrv 프로토콜 자체는
    항상 명령을 요구하므로 단순하게 유지된다.
  - guest/jail 대상 계정으로의 su/sudo도 ADR-082의 `/run` 제한이
    명령 경로 자체에 그대로 적용된다(로그인의 `session_program`
    검증과 동일한 규칙). 다만 대상은 매 호출마다 다른 임의의 명령
    이므로, 계정 생성 시점의 사전 검증(ADR-089 §결정 4)과 달리
    **매 su/sudo 호출마다** 검사해야 한다.

## ADR-093. 신원 인증 위임: 중앙 sudoers 대신 각 계정이 레지스트리에 직접 위임장을 등록 (해결: OPEN-40)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. su/sudo(ADR-090/092)의 승인 절차는 Linux의 `/etc/sudoers`처럼
     **중앙 정책 파일이 누가 누구로 전환 가능한지를 관리자가 일괄
     기술하는 방식이 아니다.** 대신 **각 계정이 스스로 "누가 내
     신원으로 행동해도 되는지"를 레지스트리에 직접 등록**하는
     완전히 탈중앙화된 위임 방식이다.
  2. **저장 위치**: 계정 `A`(uid로 식별)가 계정 `B`에게 위임하면,
     `@global/system/delegates/A` 레지스트리 테이블(키: 위임받는
     계정명, 값: `boolean true`)에 `B`를 키로 하는 항목이 생긴다.
     이 테이블의 소유자(`owner_uid`, ADR-062)는 항상 `A` 자신이다 —
     `A`만 자기 위임 목록에 쓸 수 있고(그룹/기타는 권한 없음),
     procsrv는 부팅 시 이미 보유한 `@global/system/*` 전체 권한
     핸들(ADR-087)로 어떤 계정의 위임 테이블이든 읽을 수 있다.
  3. **효과**: `B`가 procsrv에게 "`A`로 명령 X를 실행"(su/sudo,
     ADR-092)을 요청하면, procsrv는 먼저
     `@global/system/delegates/A`에 `B`가 있는지 확인한다. **있으면
     `A`의 자격 증명(비밀번호/공개키) 검증을 완전히 생략**하고 바로
     신원 전환을 진행한다(ADR-090의 새 프로세스 생성 절차). **없으면**
     기존 규칙대로 `A`의 자격 증명을 요구한다(ADR-088 §8.2 재사용,
     ADR-090 §결정 2 — 즉 위임이 "없을 때의 기본값"은 여전히 전통적
     `su`처럼 대상 계정의 인증이 필요하다).
  4. **root의 관리 위임도 같은 메커니즘의 한 사례일 뿐이다** — root
     (uid 0)가 시스템 관리용 비-root 계정을 만든 뒤
     `@global/system/delegates/root`에 그 계정을 등록하면, 그 계정이
     root의 자격 증명 없이 root로 전환(su)할 수 있게 된다. 이를 위한
     "관리자 그룹" 같은 특수 개념은 필요 없다 — 그냥 root 자신의
     위임 테이블에 항목이 하나 있는 것뿐이다.
  5. **비-root 계정 간 위임도 대칭적으로 동일하게 동작한다** — 계정
     `A`(root가 아닌)가 `@global/system/delegates/A`에 `B`를
     등록하면, `B`는 `A`의 자격 증명 없이 `A`로 전환할 수 있다.
     root의 개입이나 승인이 전혀 필요 없다.
  6. **위임은 1단계로 제한한다(전이 없음)** — `A`가 `B`에게,
     `B`가 `C`에게 각각 위임했더라도 `C`가 자동으로 `A`가 될 수는
     없다(`C`는 `B`로만 전환 가능). 전이적 위임을 허용하면 `A`가
     직접 승인하지 않은 상대까지 자신의 신원으로 행동할 수 있게
     되어, "누구를 신뢰했는지"가 각 계정 자신의 위임 테이블 하나만
     보고는 더 이상 알 수 없게 된다 — v1은 이 복잡도를 배제한다.
  7. **위임 대상(delegate) 계정이 guest 또는 jail이면 이 위임은
     효과가 없다** — procsrv는 `B`가 `effective(B).guest` 또는
     `effective(B).jail`이면, `@global/system/delegates/A`에 `B`가
     있어도 무시하고 항상 `A`의 자격 증명을 요구한다. guest/jail의
     격리는 ADR-081/085에서 이미 "무엇을 보유하고 있든 넘을 수 없는
     상한선"으로 정해뒀다 — 위임을 받았다는 이유로 더 높은 신원이
     될 수 있다면 그 상한선이 무의미해진다.
- **근거**: 사용자가 "root가 비-root 관리 계정에 위임장을 등록하는
  것과, 비-root 계정 A가 비-root 계정 B에게 위임하는 것이 같은
  메커니즘"이라고 명시적으로 설명했다 — 즉 root가 특별한 것이 아니라
  "위임"이라는 하나의 일반 연산의 한 사례일 뿐이다. 이 설계는 이
  프로젝트가 이미 전반에서 써 온 **탈중앙화 위임 패턴**(ADR-023의
  프록시 위임, ADR-074의 trusted 위임 체인)을 신원 인증에도 그대로
  적용한 것이다 — 새로운 승인 모델을 발명하지 않고 "레지스트리에
  내 소유 테이블에 항목을 하나 추가한다"는, 이미 있는 저장·권한
  메커니즘(ADR-060~062)만으로 표현된다. 중앙 sudoers 파일이 없으므로
  관리 대상도, 파싱해야 할 별도 문법도 없다.
- **영향**:
  - [procsrv.md](../spec/procsrv.md)의 su/sudo 오퍼레이션(§10에서
    여전히 형식 미정)은 이제 인증 절차의 첫 단계로 **위임 테이블
    조회**를 포함해야 한다 — 정확한 IPC 오퍼레이션(`op_delegate_grant`/
    `op_delegate_revoke` 등)은 다음 라운드에서 정의한다.
  - `@global/system/delegates/<계정명>` 테이블 스키마와 그 소유권
    설정(계정 생성 시 procsrv가 아니라, 최초로 위임을 등록하는
    시점에 그 계정 소유로 테이블을 생성)은 [registry.md](../spec/registry.md)
    갱신 대상이다.
  - 위임 철회는 `delete_value`(registry.md §5)로 해당 키를 지우는
    것만으로 충분하다 — 별도 철회 절차가 필요 없다.
  - **새 미결정**: 위임에 유효기간(TTL)이나 세부 범위(특정 명령만
    허용 등)를 둘지는 v1 범위 밖이다 — 지금은 "전부 허용/전혀 없음"
    이진 위임만 지원한다 → **OPEN-41**(ADR-094의 제약을 반드시 지켜야
    한다).
  - OPEN-40은 이 ADR로 해소된다.

## ADR-094. 위임/승인 타임아웃은 "승인" 행위 자체에만 적용, 이미 생성된 프로세스에는 소급 적용되지 않는다

- **상태**: 확정 (2026-09-08)
- **결정**: ADR-093이 미결로 남긴(OPEN-41) 위임 유효기간(TTL) 개념이
  향후 추가되더라도, 그 타임아웃은 **"승인"이라는 행위 자체**(예:
  su/sudo 요청 시점에 위임 테이블을 조회해 통과시키는 순간, 또는
  ADR-088 §8.2의 공개키 로그인 nonce 같은 "인증 시도" 창)에만
  적용된다. **이미 그 승인을 통해 생성된 프로세스에는 어떤
  타임아웃도 소급 적용되지 않는다** — 그 프로세스는 승인 시점에
  결정된 신원을 그대로 유지한 채 정상 종료까지 계속 실행된다.
- **근거**: 사용자가 명시적으로 이 원칙을 요구했다. 사실 이는 새로운
  제약이 아니라 ADR-086("신원은 생성 시 한 번 정해지고 이후 절대
  변경되지 않는다")의 직접적인 귀결이다 — 이 시스템에는 애초에
  "이미 살아있는 프로세스의 신원·권한을 나중에 깎거나 취소하는"
  메커니즘 자체가 없다(그런 메커니즘을 만들지 않기로 이미 ADR-086에서
  정했다). 따라서 미래에 위임 TTL을 추가하더라도 그 TTL이 실행 중인
  프로세스에 적용될 방법이 애초에 존재하지 않는다 — 이 ADR은 그
  사실을 명시적으로 기록해, 향후 TTL을 설계하는 사람이 "만료되면
  실행 중인 프로세스를 죽여야 하나?"라는 질문을 다시 던지지 않도록
  한다.
- **영향**:
  - OPEN-41(위임 TTL/세부 범위)의 향후 해결책은 이 제약을 반드시
    지켜야 한다 — "승인 창"의 만료 검사와 "실행 중 프로세스 종료"는
    완전히 별개이며, 후자는 이 프로젝트의 신원 모델에 아예 존재하지
    않는 개념이다.
  - 로그인(ADR-088)의 nonce TTL도 같은 원칙의 기존 사례다 — nonce가
    만료되면 그 "로그인 시도"가 실패할 뿐, 이미 성공적으로 생성된
    세션 프로세스에는 영향이 없다(성공한 세션은 nonce와 무관하게
    독립적으로 계속 산다).

## ADR-095. 위임 승인 타임아웃: 시스템 전역 설정 + 위임자 개인 설정 중 작은 값(0은 예외) (해결: OPEN-41)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 위임 항목(`@global/system/delegates/<A>`, ADR-093)에 부여 시각을
     함께 기록한다:

     ```cpp
     struct delegation_entry {
         uint64_t granted_at;  // 유닉스 epoch 초
     };
     ```

  2. **타임아웃 값의 두 원천**: 시스템 전역 설정
     (`@global/system/settings`의 `delegation_timeout_seconds`,
     super만 쓰기 가능)과, **위임자(A) 본인**의 사용자별 설정
     (`@{A의 계정명}/system/settings`의 `delegation_timeout_seconds`,
     A 본인이 쓰기 가능) — 위임을 받는 B가 아니라 위임을 **주는** A의
     설정이 적용된다.
  3. **유효 타임아웃 계산**: 두 값 중 **작은 값**을 따르되, **0
     (타임아웃 없음)은 "가장 작은 값"이지만 이 비교에서 제외**한다:

     ```
     effective_ttl =
         if global == 0 and per_user == 0: 0        // 진짜로 타임아웃 없음
         elif global == 0: per_user
         elif per_user == 0: global
         else: min(global, per_user)
     ```

  4. B가 위임(ADR-093)으로 A의 신원 전환을 시도할 때, procsrv는
     `now - entry.granted_at`을 그 시점의 `effective_ttl`과 비교한다.
     `effective_ttl == 0`이면 항상 통과. 초과했으면 그 위임을 더
     이상 유효하지 않은 것으로 취급하고 ADR-093 §결정 3의 "위임
     없음" 경로(A의 자격 증명 요구)로 폴백한다.
  5. **ADR-094와의 관계**: 이 타임아웃은 오직 "지금 이 su/sudo 요청을
     위임만으로 통과시켜도 되는가"라는 판정에만 적용된다. 이미 그
     판정을 통과해 생성된 프로세스에는 어떤 영향도 없다(ADR-094
     원칙 그대로) — 타임아웃 만료는 그 시점 이후의 **새 요청**만
     막을 뿐, 실행 중인 것을 건드리지 않는다.
- **근거**: 사용자가 이 정확한 재조정 규칙(전역+위임자 개인 설정
  중 작은 값, 단 0은 예외)을 명시했다. "작은 값 우선"은 더 엄격한
  쪽이 이긴다는 뜻이라 보안상 자연스러운 기본값이다 — 관리자가
  시스템 전역 상한을 걸어두면 개별 사용자가 그보다 느슨하게(더 큰
  값으로) 풀 수 없고, 반대로 사용자가 전역보다 더 엄격하게(작은
  값으로) 죌 수는 있다. 0을 최솟값 비교에서 제외하는 이유는, 그렇지
  않으면 "0(무제한)"이 숫자상 항상 가장 작아 `min()` 규칙에서
  무조건 이겨버려 "0 하나만 설정해도 다른 쪽의 제한이 전부
  무력화"되는 구멍이 생기기 때문이다 — 0은 "값 없음/이 설정은
  관여하지 않음"으로 취급해야 두 설정 모두가 실제로 의미 있게
  작동한다.
- **영향**:
  - `@global/system/settings`, `@{계정명}/system/settings` 레지스트리
    테이블 스키마를 [registry.md](../spec/registry.md) 갱신 시점에
    반영해야 한다.
  - [procsrv.md](../spec/procsrv.md)의 위임 조회 절차(§10에서 여전히
    형식 미정)에 `granted_at` 비교 단계를 추가해야 한다.
  - 시스템 전역/사용자별 기본값(0인지 유한한 값인지)은 구현 시
    정한다 — 이 ADR은 재조정 규칙만 고정한다.
  - OPEN-41은 이 ADR로 해소된다(단, 위임의 "세부 범위" — 특정 명령만
    허용 등 — 는 여전히 v1 범위 밖으로 남는다 → 신규 **미결정
    (OPEN-42)**).

## ADR-096. 위임 기간의 세 가지 모드: 계정 기본값·명시적 기간·영구(확인 여부 선택) (OPEN-42 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 위임을 생성할 때(ADR-093) A는 그 위임 항목의 유효기간을 세
     가지 모드 중 하나로 지정한다:

     ```cpp
     enum class delegation_ttl_kind : uint8_t {
         account_default = 0,  // ADR-095 재조정 규칙(전역 vs A의 계정
                                 // 설정 중 작은 값, 0은 예외) 그대로 사용
         fixed_period     = 1,  // 이 위임 항목 전용 기간(초)
         permanent        = 2,  // 만료 없음
     };

     struct delegation_entry {
         uint64_t            granted_at;
         delegation_ttl_kind ttl_kind;
         uint64_t            period_seconds;         // fixed_period 전용
         bool                requires_confirmation;  // permanent 전용
         bool                confirmed;               // requires_confirmation이
                                                        // true일 때만 의미 있음
     };
     ```

  2. **`fixed_period`**: 이 위임 항목만의 만료 기간을 A가 직접
     초 단위로 정한다 — ADR-095의 A 계정 기본값 대신 이 값을 "A측
     TTL"로 써서 그대로 ADR-095의 재조정 계산(전역 설정과 min)에
     들어간다. 즉 전역 설정보다 더 느슨한 기간을 지정해도 **전역
     설정이 여전히 상한으로 작동**한다(ADR-095의 "작은 값 우선"
     원칙이 그대로 유지된다).
  3. **`permanent`**: 이 위임은 A측에서 볼 때 만료가 없다 — ADR-095의
     재조정 계산에서 "A측 TTL = 무한대"로 취급한다(0이 아니다 — 0과
     혼동하면 ADR-095의 "0은 비교에서 제외" 규칙이 뒤집혀 버린다).
     따라서 **전역 설정이 0이 아닌 한, 전역 설정이 여전히 실질
     상한으로 남는다** — `permanent`는 "A가 자기 쪽에서 추가
     제한을 걸지 않겠다"는 뜻이지 "전역 상한을 무시한다"는 뜻이
     아니다.
  4. `permanent`를 생성할 때 A는 `requires_confirmation`을 선택할 수
     있다:
     - `true`: 위임이 즉시 발효되지 않고 `confirmed = false`인
       "대기" 상태로 생성된다. 위임받는 B가 스스로 확인(수락)해야
       `confirmed = true`가 되어 그 뒤부터 유효해진다 — 정확한 확인
       IPC 절차는 다음 라운드(procsrv.md)에서 정의한다.
     - `false`(기본값): ADR-093의 기존 동작과 동일하게, A의
       등록만으로 즉시 발효된다(B의 별도 확인 불필요).
     `fixed_period`/`account_default` 위임에는 이 확인 절차를 두지
     않는다 — 시간이 지나면 스스로 만료되므로 영구 위임만큼의
     추가 안전장치가 필요하지 않다고 본다.
- **근거**: 사용자가 "위임 기간을 설정할 수 있거나 영구 위임(확인
  여부 선택)을 할 수 있다"고 정하고, 그 이상(특정 명령/시간대 제한
  등)은 후속 논의로 미뤘다. `permanent`를 무한대로 취급해 ADR-095의
  기존 재조정 로직에 그대로 흡수시킨 이유는, 별도의 "영구 위임은
  전역 상한 예외"같은 새 규칙을 만들지 않기 위해서다 — 그런 예외를
  두면 관리자가 전역 상한을 걸어도 각 계정이 `permanent`로 손쉽게
  무력화할 수 있어 ADR-095가 세운 "관리자 상한은 항상 이긴다"는
  보안 성질이 깨진다. 영구 위임에만 확인 절차를 선택할 수 있게 한
  이유는, 시간 제한이 있는 위임은 스스로 치유(만료)되지만 영구
  위임은 그렇지 않아 상대적으로 위험이 크므로, 원하는 경우 추가
  확인이라는 안전장치를 A가 선택할 수 있게 하는 것이 합리적이기
  때문이다 — 다만 필수로 강제하지는 않는다(A가 이미 자기 위임
  테이블의 유일한 쓰기 주체이므로, 확인을 요구할지는 A 스스로의
  판단에 맡긴다).
- **영향**:
  - [procsrv.md](../spec/procsrv.md)의 위임 생성 오퍼레이션(§10,
    형식 여전히 미정)에 `delegation_ttl_kind`/`period_seconds`/
    `requires_confirmation` 필드를 반영해야 한다.
  - B가 대기 중인 위임을 확인(수락)하는 정확한 IPC 절차(조회 방법,
    수락/거절 오퍼레이션)는 다음 라운드로 미룬다.
  - OPEN-42는 "위임 기간/영구성" 부분만 해소되고, "특정 명령만
    허용" 같은 세부 범위는 여전히 열려 있다 — 아래에서 범위를
    좁혀 유지한다.

## ADR-098. 세션의 stdin/stdout/stderr는 일반 fd 상속 규칙을 따른다 — 로그인은 로그인 프롬프트의 TTY fd를 명시적으로 복제 (OPEN-39 부분 해결)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. 세션의 표준 입출력이 어느 TTY로 연결되는지는 **별도의 "제어
     터미널" 개념을 새로 도입하지 않고, [procsrv.md](../spec/procsrv.md)
     §2의 일반 `fd_table` 안 fd 0/1/2로 표현**한다 — TTY는 그냥
     `owner_kind`가 콘솔 드라이버([boot-and-drivers.md](boot-and-drivers.md)
     ADR-097)인 fd일 뿐이다.
  2. `fork()`(procsrv.md §3)로 생성된 자식은 §4.1의 fd 복제
     프로토콜로 부모의 fd 0/1/2를 그대로 물려받는다 — 이미 있는
     일반 규칙이며 TTY 전용 특수 처리가 필요 없다.
  3. `exec()`(§4)도 마찬가지로 기존 `fd_table`을 유지한다
     (close-on-exec 표시분 제외) — 이미 있는 규칙 그대로다.
  4. **로그인(ADR-088 §결정 4)은 부모가 없으므로**(§5 — 신규 세션의
     `parent = nullptr`) **일반 fd 상속이 적용되지 않는다.** 대신
     procsrv가 로그인 프롬프트 프로세스(요청자)의 fd 0/1/2를 §4.1의
     `dup_for_new_client` 절차로 **명시적으로** 새 세션 프로세스의
     fd 0/1/2에 복제한다. 즉 새 세션은 "프로세스 계보상 부모는
     없지만 stdio는 요청자로부터 물려받는다"는, 프로세스 계보와 fd
     상속이 분리되는 유일한 경우다.
  5. `su`/`sudo`(ADR-090)는 부모가 호출 셸이므로 §결정 2의 일반
     fork류 fd 상속이 그대로 적용된다 — 별도 처리가 필요 없다.
- **근거**: 사용자가 "세션의 stdout/stderr 라우팅은 그 세션을
  시작시킨 프로그램이 어느 TTY에 물려있었는가에 따라 달라진다"고
  명시했다. 새로운 "제어 터미널" 커널/procsrv 개념을 만들지 않고
  이미 있는 fd 메커니즘(procsrv.md §4.1)을 재사용하는 이유는, TTY도
  결국 "열려서 읽고 쓸 수 있는 장치"일 뿐이라 다른 fd(파일, 소켓)와
  근본적으로 다르지 않기 때문이다 — 별도 개념을 두면 fd 테이블과
  항상 동기화해야 하는 중복 상태가 생긴다.
- **영향**:
  - `fd_entry.owner_kind`(procsrv.md §2)에 콘솔 드라이버 종류가
    추가되어야 한다.
  - ADR-088 §결정 4의 절차에 "로그인 프롬프트의 fd 0/1/2를 새
    세션에 복제하는" 단계를 명시적으로 추가해야 한다(procsrv.md
    갱신).
  - `setsid()`류(세션 분리, 제어 터미널로부터의 명시적 해제)는 이
    ADR의 범위 밖이다 — 필요해지면 후속 결정 대상.
  - OPEN-39는 "로그인 프롬프트가 실제 콘솔과 어떻게 연결되는지"
    부분이 ADR-097/098로 해소된다. "여러 콘솔에 걸쳐 로그인
    프롬프트를 어떻게 기동하는지"는 ADR-097 §영향("TTY 개수만큼")이
    답했지만, 정확한 initrun 매니페스트 문법 자체는 여전히 OPEN-29에
    묶여 있다.

## ADR-112. 위임을 통한 su/sudo도 위임받는 자 본인의 인증은 기본적으로 요구 — 대상 계정 자격 증명만 생략 (ADR-093 갱신, OPEN-42 관련)

- **상태**: 확정 (2026-09-08)
- **결정**:
  1. ADR-093 §결정 3을 다음과 같이 정정한다: `B`가 위임
     (`@global/system/delegates/A`에 `B` 존재)으로 `A`로 전환할 때
     생략되는 것은 **`A`의 자격 증명 검증뿐**이다. **`B` 본인의
     자격 증명(비밀번호 등)은 기본적으로 계속 요구된다** — 위임이
     있다고 해서 전환을 요청하는 사람이 정말 그 계정 본인인지까지
     생략되지는 않는다.
  2. 위임 항목(`delegation_entry`, ADR-096)에 `passwordless: bool`
     (기본값 `false`) 필드를 추가한다. `A`가 위임을 등록할 때 이
     값을 명시적으로 `true`로 설정한 경우에만, `B`가 `A`로 전환할 때
     `B` 본인의 자격 증명도 생략된다(ADR-093 §결정 3의 원래 동작
     그대로). 명시하지 않으면(기본값) `B`는 자기 자신의 자격
     증명으로 인증해야 한다.
  3. 이 규칙은 위임 체인의 각 홉(hop)에 독립적으로 적용된다 — 예:
     `A`가 `B`에게, `B`가 `C`에게 각각 위임했다면, `C`가 `B`로
     전환할 때는 `B→C` 위임 항목의 `passwordless` 값에 따라 `C`의
     비밀번호 요구 여부가 결정되고, 이어서 `B`가 `A`로 전환할 때는
     `A→B` 위임 항목의 `passwordless` 값에 따라 `B`의 비밀번호 요구
     여부가 별도로 결정된다. ADR-093 §결정 6("위임은 1단계로
     제한")은 그대로 유지된다 — `C`가 한 번에 `A`로 건너뛸 수는
     없다.
- **근거**: 사용자가 "B가 A로 넘어갈 때 B의 비밀번호를 물어보는 게
  맞고, 비밀번호 없이 승인이라고 명시되지 않은 이상 C의 패스워드도
  물어봐야 한다"고 명시했다. 위임이 있다고 해서 요청자 본인 확인까지
  생략하면, `B`의 로그인 세션이 탈취되었을 때 곧바로 `A`로도 전환
  가능해져 위임 하나가 뚫리면 체인 전체가 뚫리는 구조가 된다 — 각
  홉마다 "지금 요청하는 사람이 정말 그 계정 본인인가"를 재확인하는
  편이 ADR-086(신원 불변)·ADR-090(su/sudo 시 자격 증명 요구)의 기존
  보안 원칙과 더 일관된다. `passwordless` 옵트인을 남겨둔 이유는,
  사용자가 이미 그런 예외를 감수하고 완전 자동화된 전환을 원하는
  경우(예: 자동화 스크립트 계정)를 배제하지 않기 위해서다.
- **영향**:
  - `delegation_entry`(ADR-096) 구조체에 `passwordless` 필드를
    추가해야 한다 — [procsrv.md](../spec/procsrv.md) §10(형식
    미정)과 [registry.md](../spec/registry.md) 갱신 대상.
  - ADR-093 §결정 3의 "자격 증명 검증을 완전히 생략"이라는 표현은
    이 ADR로 "`A`의 자격 증명만 생략, `B` 본인의 인증은 기본 요구"로
    좁혀진다. ADR-093 본문 자체는 수정하지 않는다.
  - OPEN-42(위임의 세부 범위)의 "명령/시간대 단위 제한"은 이 ADR과
    별개로 여전히 미해결로 남는다 — 이 ADR은 "재인증 요구 여부"라는
    새 축을 추가로 결정한 것일 뿐이다.

## ADR-165. M17 로그인 인증 범위 좁힘 — procsrv 최소 실제 계정 저장소(평문 비교) + 세션 프로그램 스폰은 M20으로 미룸

- **상태**: 확정 (2026-09-09)
- **문제**: ADR-079가 `user_account` 구조체(uid/gid, S/G/J 비트, 해시
  또는 공개키 인증)를 이미 설계해 뒀지만, procsrv는 지금까지 이
  구조체를 실제로 구현한 적이 없다(M13 완료 보고가 이미 "procsrv.md의
  실제 프로토콜(§2~9)은 여전히 구현하지 않는다"고 명시). M17의
  목표("M12 계정으로 로그인에 성공한다")가 요구하는 최소 조건은
  실제 계정 저장소 하나와 그것과 비교하는 인증 절차뿐이다.
- **결정**:
  1. `servers/procsrv`에 고정 크기 계정 배열(이름+평문 비밀번호,
     ADR-079의 uid/gid/S/G/J 비트는 아직 채우지 않는다 — 이번
     라운드는 "계정이 존재하고 자격 증명이 맞으면 성공"만 증명하면
     된다)을 하드코딩으로 심는다. 새 IPC 오퍼레이션
     `OP_LOGIN`(사용자명+비밀번호 → 성공/실패)을 추가한다 — procsrv가
     이 라운드에서 **처음으로** 자신의 endpoint에 대해 `sys_recv`
     루프를 도는 진짜 서버가 된다(지금까지는 vfs/fat32/ext4의
     클라이언트 역할만 했다).
  2. **비밀번호는 평문으로 저장하고 바이트 비교로 인증한다** — 실제
     해싱 알고리즘(ADR-079가 예고한 "해시 또는 공개키")은 이 라운드의
     목표(로그인 성공/실패 흐름 자체를 검증하는 것)와 무관하다.
     해시 알고리즘 선택·salt·저장 형식은 실제 다중 사용자 계정
     관리가 필요해지는 시점(M18의 su/sudo 작업과 자연스럽게 맞물릴
     가능성이 크다)에 별도 ADR로 정한다.
  3. **로그인 성공 시 `session_program`(ADR-089, 기본
     `/run/bin/hello`)을 실제로 스폰하지 않는다** — VFS가 임의
     경로의 ELF를 찾아 실행하는 일반 메커니즘이 아직 없다(지금까지
     모든 서비스는 `initrun`이 부트 디스크 cpio에서 직접 읽어
     스폰했을 뿐, "경로로 실행 파일을 찾아 실행"은 한 번도 구현된
     적이 없다). system-servers-bringup.md §M20이 이미 "libc 포팅+
     로그인 후 셸"을 자신의 목표로 명시해 뒀으므로, "로그인 성공
     이후 무엇을 실행하는가"는 M20의 몫으로 남긴다 — M17은 정확히
     계획이 말한 "로그인 흐름"(인증 성공/실패 판정)까지만 증명한다.
  4. **실제 키보드 입력이 QEMU 자동화 환경에 주입되지 않는 문제**
     (ADR-130이 PS/2에서 이미 겪은 것과 같은 제약)는 같은 해법을
     재사용한다 — `servers/login`이 `servers/drivers/ps2`의 새
     `OP_READ_KEY`를 정해진 횟수만큼 폴링해도 키 입력이 없으면(자동화
     환경에서는 항상 이 경우다), 내장 자체 테스트 계정(위 §결정1의
     계정 중 하나)으로 **같은 `OP_LOGIN` 경로**를 그대로 호출해
     인증 파이프라인 전체(콘솔 출력+procsrv 검증)를 결정적으로
     검증한다. 실제 사람이 QEMU 화면 앞에서 타이핑하면 그 입력이
     자체 테스트보다 먼저 도착해 실제 경로를 그대로 탄다 — 두
     경로는 같은 `OP_LOGIN` 호출로 합류하므로 "자체 테스트만 되고
     실제 입력 경로는 검증 안 된 채로 남는다"는 위험이 없다.
- **근거**: 사용자가 "최소 실제 계정 저장소 + 평문/단순 해시 비교"를
  선택했다 — ADR-079의 전체 구조체를 지금 다 채우는 것은 M18(su/sudo/
  jail)이 실제로 그 필드들을 쓰기 시작할 때까지는 검증할 방법이 없는
  조기 일반화다(ADR-001의 "정확성·단순성 우선"과 이 계획 전반의
  "다중 프로세스 시스템의 수직 슬라이스 검증" 성격에 맞지 않는다).
- **영향**: `servers/procsrv/main.cpp`에 계정 배열 + `OP_LOGIN` 핸들러
  + `sys_recv` 서비스 루프 추가(기존 self-test들이 끝난 뒤 진입).
  `servers/login`(신설)이 `depends=console,ps2,procsrv`로 세 서버
  모두에 의존한다. `docs/spec/procsrv.md`의 §2~9(실제 프로세스
  테이블·계정 모델 전체)는 여전히 미구현 — 이 ADR은 그 스펙을
  구현하는 게 아니라 M17 검증에 필요한 최소 우회로를 놓는 것이다.

## ADR-167. M18 범위 좁힘 — procsrv 하드코딩 위임 테이블, jail을 guest와 같은 규칙으로 단순화, 실제 경로→ELF 로더로 su/sudo 실행 검증

- **상태**: 확정 (2026-09-09)
- **문제**: M18(su/sudo + jail/guest)이 그대로 요구하는 세 가지가
  지금 시점엔 없는 인프라에 의존한다 — (1) ADR-093의 위임 테이블은
  `@global/system/delegates/<계정>` 레지스트리(cfgsrv, M19에야 생김)
  에 저장돼야 한다. (2) ADR-081의 jail "홈 제외 전체 오버레이"는
  ADR-080의 에페메럴 오버레이 네임스페이스(VFS 마운트 네임스페이스
  기능, 지금 VFS는 정적 3-way 마운트 표뿐)를 요구한다. (3) ADR-092의
  "호출자가 지정한 명령"을 su/sudo가 실행하려면 경로로 임의 ELF를
  찾아 실행하는 일반 메커니즘이 필요한데, 지금까지 모든 서비스는
  initrun이 부트 디스크 cpio에서 직접 읽어 스폰했을 뿐 "경로로 파일을
  찾아 그 내용을 실행"한 적이 한 번도 없다(M17의 session_program
  스폰 보류, ADR-165 §결정3과 같은 종류의 공백).
- **결정**:
  1. **위임 테이블은 procsrv에 하드코딩한다** — M17의 계정 저장소
     (ADR-165)와 같은 정신. `@global/system/delegates/*`의 실제
     레지스트리 스키마 반영은 M19(cfgsrv 등장) 이후로 미룬다.
  2. **jail을 이 라운드에 한해 guest와 완전히 같은 규칙으로
     단순화한다** — 오버레이 네임스페이스(ADR-080/081 §결정1)는
     구현하지 않는다. jail/guest 둘 다 "VFS `open()` 시점에 호출자가
     guest 또는 jail이면 홈 경로(`/home/`) 밖 접근을 거부"라는 같은
     검사 하나로 처리한다 — ADR-081이 원래 구분해 둔 "jail=가상
     에뮬레이션처럼 보임, guest=단순 거부"라는 차이는 이 ADR로
     되돌리는 게 아니라, jail의 오버레이 부분만 구현을 다음 라운드로
     미루는 것이다(ADR-081 자체는 수정하지 않는다).
  3. **su/sudo는 실제 경로→ELF 로더로 검증한다** — 호출자가 IPC로
     임의 경로 문자열을 지정하는 것까진 아니지만(그건 여전히 범위
     밖), procsrv가 **자기 자신의 ELF 바이트**(M12 self_info 브릿지로
     이미 갖고 있다)를 VFS 경로(`/bin/su-target`)에 실제로 쓰고,
     다시 그 경로에서 읽어 재조립한 바이트가 원본과 정확히 일치함을
     확인한 뒤, 그 **재조립된 바이트**(원본을 직접 쓰는 게 아니라)로
     `sys_process_spawn`한다 — "경로로 저장하고 다시 읽어 실행"이라는
     로더의 실제 파이프라인 전체를 증명하면서도, 임의 명령 지정이라는
     아직 필요 없는 일반화는 피한다. 스폰된 프로세스는 procsrv와
     같은 바이너리이지만 magic 접두사가 붙은 argv로 "이번엔 su-target
     역할을 하라"고 구분해 받는다(procsrv 자신의 self-exec 관례와
     같은 argv 판별 패턴을 확장한 것).
- **근거**: 사용자가 세 질문에 각각 "procsrv 하드코딩 위임 테이블",
  "jail을 guest와 같은 규칙으로 단순화", "간단한 경로→ELF 로더를
  지금 만든다"를 확인했다 — 세 번째는 권장(더 단순한) 옵션이
  아니라 사용자가 명시적으로 더 어려운 쪽을 선택한 것이다: "임의
  명령 실행"이 아니라 "실제 명령 실행 자체"를 지금 증명하길
  원했다.
- **영향**: `docs/spec/fs-protocol.md` v3(filesystem.md ADR-168) —
  `OP_WRITE`가 `pages[]` 기반으로 바뀌고(M16이 `OP_READ`만 바꿨던 것을
  대칭으로 마무리), `OP_OPEN`에 호출자 신원(guest/jail 비트) 필드가
  추가된다. `servers/procsrv`에 계정별 uid/S·G·J 비트, 위임 테이블,
  `OP_SU` 핸들러, 로더(쓰기+읽기+검증+재조립) 추가. `servers/login`이
  로그인 성공 후 `OP_SU`를 두 번 호출해(위임으로 성공/자격증명
  불일치로 거부) 정책 확인 경로 양쪽을 검증한다. `docs/spec/
  procsrv.md`의 §10(su/sudo 형식 미정) 실제 형식은 여전히 미확정 —
  이 ADR은 그 스펙을 채우는 게 아니라 M18 검증에 필요한 최소
  프로토타입이다.

## ADR-171. M20: 로그인 후 셸 시작을 procsrv→셸 OP_START 신호로 단순화 (ADR-089 보강, 대체 아님)

- **상태**: 확정 (2026-09-09)
- **결정**: ADR-089가 정한 "로그인 성공 시 procsrv가 `session_program`을
  `exec()`한다"를 이번 라운드는 다음으로 단순화해 구현한다.
  1. 셸(`userland/shell/`, foundations.md ADR-170)은 **부팅 시
     initrun이 다른 서비스와 똑같이 직접 스폰**한다(`depends=vfs,
     console,ps2`) — procsrv가 fork/exec으로 만드는 게 아니다.
     스폰 직후 셸은 자기 자신의 IPC 엔드포인트(handle 1)에서
     `sys_ipc_recv`로 블록하며 대기한다.
  2. procsrv는 셸에 대한 캐패빌리티도 스폰 시점에 미리 받는다
     (`depends=vfs,cfgsrv,shell` — handle 2/3/4). `OP_LOGIN`이
     성공(자기 자신에게 딱 한 번만, 정적 플래그로 중복 방지)하면
     procsrv가 그 handle로 `OP_START`(신규, label=1) 메시지를 보낸다.
  3. 셸은 `OP_START`를 받으면 즉시 응답한 뒤(블로킹 해제),
     **다시는 `sys_ipc_recv`를 부르지 않고** 대화형 루프(프롬프트
     출력→키 입력→내장 명령 실행)로 넘어간다 — 이후 어떤 프로세스도
     셸의 handle 1을 다시 호출할 수 없다(이번 라운드는 세션 하나만
     다루므로 문제되지 않는다).
  4. `user_account.session_program` 필드, 계정별 재정의, guest/jail의
     `/run` 제약(ADR-089 §결정 1/4)은 이번 구현에 없다 — 모든 로그인이
     같은 단일 셸 인스턴스로 이어진다.
- **근거**: ADR-089의 "procsrv가 exec()한다"를 문자 그대로 구현하려면
  procsrv(또는 그 자식)가 **셸 바이너리의 원본 ELF 바이트**를 자기
  주소공간에 가져와야 하는데, 이 바이트를 얻을 방법이 없다 —
  M18의 su-target 로더는 procsrv 자신의 self_info 브릿지(자기
  자신의 ELF)를 재사용한 것이라 다른 바이너리로는 일반화되지 않고,
  일반화하려면 "임의 경로의 ELF를 다른 프로세스에 전달"하는 새
  메커니즘이 필요하다(M18이 이미 이걸 범위 밖으로 명시해 뒀다).
  반면 "이미 스폰된 프로세스에 캐패빌리티 주입 시점에 이미 확보한
  handle로 IPC 신호를 보내는 것"은 M13부터 검증된 기존 메커니즘
  그대로다 — 새 커널/IPC 기능이 전혀 필요 없다.
- **영향**:
  - [foundations.md](foundations.md) ADR-170의 M20 범위 좁힘과
    직접 연결된다.
  - `tools/mkbootdisk.py`/`servers/CMakeLists.txt`의 부팅 순서가
    `...→vfs→cfgsrv→shell→procsrv→login`으로 확정된다(shell이
    procsrv보다 먼저 떠 있어야 procsrv가 그 핸들을 받을 수 있다).
  - 계정별 `session_program`을 실제로 구현하려면(ADR-089 완성)
    "임의 경로의 ELF를 다른 프로세스가 로드해 실행하는 일반
    메커니즘"이 결국 필요하다 — 이번 라운드는 그 필요성을 다시
    한번 확인했을 뿐, 새 미결정 항목을 추가하지는 않는다(M18의
    기존 범위 밖 항목과 같다).
