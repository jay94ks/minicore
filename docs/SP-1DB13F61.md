# 가상 함수(vtable)를 쓰는 슬랩 할당 타입의 초기화 관례 — 설계 제안

**배경 질의**: QU-1D089097(DC-21647E46 대상, minicore-88 세션이 PN-B41D8C0E
착수 중 QEMU 실측으로 발견) — 설계자 답변(2026-09-16 16:10): *"트램폴린
패턴은 self를 Task와 함께 C스타일 콜백에 활용하기 위하여 고안된거라고
생각했는데. A가 정석이라서, 오히려 A쪽으로 생각해야해. 필요한 메모리
공간을 전역으로 올리던, 각 객체에 올리던간에. 일단 이건 추가로 설계
제안서를 작성해서 검토하도록 하자."*

이 문서는 그 지시에 따른 설계 제안서다 — **(A) 가상 함수를 쓰는 타입에
한해 placement new를 허용**하는 방향으로 이 프로젝트의 슬랩 할당
초기화 관례를 확장하는 구체안을 제시한다.

## 1. 문제 재정리

`Waitable::cancel()`(waitable.h)은 `virtual`이고 `WaitQueue`(wait_queue.h)
가 이를 override한다. `WaitQueue`는 `Mutex`/`Semaphore`(mutex_core.h/
semaphore_core.h)의 `ParkingPolicy` 안에 값(임베디드 멤버)으로 들어
있다. `Mutex`/`Semaphore`는 `kMakeShared<Mutex>(preConstructed)`로
`SharedPtr` 관리 대상이 되는데, 이 프로젝트의 기존 관례(`shared_ptr.h`
상단 "소멸 관례" 주석, `kDestroyAndFree<T>`의 전제)는 **"이미
`GenericSlabAllocator::alloc()` + `memset(0)` + 명시적 `init()`으로
준비를 마친 포인터"**를 `kMakeShared`에 넘기는 것이다 — 실제 C++
생성자(placement new)는 한 번도 실행되지 않는다.

가상 함수가 있는 타입은 컴파일러가 **생성자 실행 시점**에 vtable
포인터를 그 인스턴스에 심는다. 위 관례로 만들어진 `Mutex`/`Semaphore`
안의 `WaitQueue` 서브오브젝트는 생성자를 거친 적이 없으므로 vtable
포인터가 `memset(0)`이 남긴 0 그대로다 — `WaitQueue`가 상속한
`Waitable::cancel()`을 가상 호출하는 순간(`w->cancel(...)`) 그 0을
통해 점프해 즉시 General Protection Fault로 죽는다(QU-1D089097 실측
로그: `rip`가 `0xf000ff54f000ff53`류의 깨진 값으로 튐).

지금까지 이 문제가 안 드러난 이유: 이 코드베이스의 다른 가상 함수
타입(`AsyncTaskHandler`/`LoggingDriver`/`KernelFsDriver` 등)은 전부
정적 전역이거나 실제 `new`로 만들어져 생성자를 거쳤다. `Waitable`이
"raw slab + memset" 관례로 만들어지는 **최초의 가상 함수 타입**이고,
`Mutex`/`Semaphore`도 지금까지 실사용 소비자가 없어(PN-B41D8C0E가
처음으로 `lock()` 경합 + 강제 `cancel()`까지 실제로 실행) 아무도
이 충돌을 밟지 않았을 뿐이다.

## 2. 채택 방향 (설계자 지시 — (A))

가상 함수가 있는(또는 가상 함수가 있는 타입을 서브오브젝트로 임베디드
하는) 타입은 **실제 생성자를 거쳐야 한다** — `memset(0)` + 명시적
`init()` 관례의 예외로, placement new를 쓴다. 이 자체는 기존
"placement new 안 씀" 관례에 대한 예외 하나를 만드는 것이지만,
설계자 판단으로는 오히려 이쪽이 "정석"이고 지금까지의 관례가 (가상
함수가 없는 절대다수 타입에 한해) 특수 최적화였던 셈이다.

**"메모리 공간을 전역으로 올리든 각 객체에 올리든"에 대한 해석**: 이
제안은 메모리 공간의 *출처*(전역 정적 배열 vs 슬랩 할당)와 초기화
*방식*(placement new 여부)을 별개 축으로 본다. `Mutex`/`Semaphore`는
지금처럼 `GenericSlabAllocator::alloc(sizeof(Mutex))`로 슬랩에서
받은 원시 메모리 위에 `new (mem) Mutex()`를 실행하면 된다 — 메모리
출처 자체(슬랩 vs 전역)는 바꿀 필요가 없고, 그 위에서 생성자를
실제로 돌리느냐만 바뀐다. **이 접근의 핵심 이점**: `WaitQueue`는
`Mutex`/`Semaphore`의 서브오브젝트이므로, `Mutex`의 생성자가 실제로
실행되면 C++ 언어 규칙상 그 안의 `WaitQueue` 서브오브젝트 생성자도
자동으로 함께 실행된다 — `WaitQueue` 자신을 별도로 placement-new할
필요가 없다(`WaitQueue`는 사용자 정의 생성자가 없는 암시적 기본
생성자로 충분 — 가상 함수 vtable 심기는 암시적 기본 생성자도 그대로
수행한다).

## 3. 구체 설계 — `shared_ptr.h` 확장

기존 `kMakeShared<T>(T* preConstructed, Deleter)`의 계약(이미 `init()`
까지 마친 포인터를 받는다)은 **바꾸지 않는다** — `Process`/`RingBuffer`/
`Task` 등 절대다수의 기존 비-가상 타입이 이 계약에 의존하고 있어
바꾸면 전면 재검증이 필요해진다. 대신 가상 함수 타입을 위한 **새
팩토리 함수를 추가**하는 쪽을 제안한다(표준 `std::make_shared`와
같은 모양):

```cpp
// [신규] 가상 함수(vtable)가 있는 T 전용 - GenericSlabAllocator에서
// 받은 원시 메모리 위에 실제 생성자를 실행한다(placement new).
// T가 가상 함수/가상 소멸자가 없다면 kMakeShared(preConstructed, ...)
// 기존 경로를 그대로 쓴다 - 이 함수는 그 경로가 성립하지 않는(vtable
// 이 필요한) T에 한해서만 쓴다.
template <typename T, typename... Args>
SharedPtr<T, void (*)(T*)> kMakeSharedNew(Args&&... args) {
    void* rawMem = GenericSlabAllocator::alloc(sizeof(T));
    if (!rawMem) return SharedPtr<T, void (*)(T*)>();
    T* target = new (rawMem) T(kForward<Args>(args)...);
    return kMakeShared<T>(target, &kDestroyCtorAndFree<T>);
}

// kDestroyAndFree<T>(명시적 destroy()/init() 관례)와 달리, 실제
// 소멸자(~T())를 호출한다 - placement new로 만든 T 전용 짝.
template <typename T>
void kDestroyCtorAndFree(T* ptr) {
    ptr->~T();
    GenericSlabAllocator::free(ptr, sizeof(T));
}
```

`kMakeSharedNew`는 내부적으로 기존 `kMakeShared(preConstructed, deleter)`
를 그대로 재사용한다 — `ControlBlock<T,Deleter>` 초기화, `EnableSharedFromThis`
자동 배선(§2 `if constexpr` 분기) 전부 변경 없이 그대로 적용된다.
바뀌는 건 "T*를 어떻게 준비했는가"(placement new) 와 "소멸 시 무엇을
부르는가"(`~T()` vs `destroy()`) 두 가지뿐이다.

`Mutex`/`Semaphore` 호출부는 다음과 같이 바뀐다(예시):

```cpp
// 기존(문제 있음):
Mutex* m = static_cast<Mutex*>(GenericSlabAllocator::alloc(sizeof(Mutex)));
memset(m, 0, sizeof(Mutex));
m->init();  // 이 init()이 있어도 WaitQueue의 vtable은 못 심는다
auto sp = kMakeShared<Mutex>(m);

// 신규:
auto sp = kMakeSharedNew<Mutex>();  // Mutex()가 기본 생성자 - WaitQueue
                                     // 서브오브젝트 vtable도 자동 설치
```

`Mutex`/`Semaphore`가 지금 갖고 있는 `init()` 메서드(`MutexCore::init()`/
`SemaphoreCore::init()`)는 그대로 두되(`_locked = false`/`_count = n`
같은 실행 시점 값 설정은 여전히 필요), `BasicMutex`/`BasicSemaphore`
생성자가 그 `init()`을 자동으로 호출하도록 바꾸거나(NSDMI로 대체 가능한
범위라면 NSDMI로), 호출부가 `kMakeSharedNew<Mutex>()` 직후 명시적으로
`sp->initCore()`류를 한 번 더 부르는 것 중 착수 세션이 실측하며 더
단순한 쪽을 고른다(RM-23F4B687 §4 - 지금 임의로 정하지 않음).

## 4. 영향 범위

- **변경**: `mutex_core.h`(`BasicMutex`/`BasicSemaphore` 생성 경로),
  `semaphore_core.h`, 이 둘을 `kMakeShared`로 생성하는 모든 호출부.
- **변경 없음**: `waitable.h`/`wait_queue.h`(가상 함수 설계 그대로 유지 -
  QU-1D089097의 (B)안처럼 트램폴린으로 바꾸지 않는다), `shared_ptr.h`의
  기존 `kMakeShared`/`kMakeUnique` 계약과 그걸 쓰는 기존 타입(`Process`/
  `RingBuffer`/`Task` 등) 전부.
- **일반화 여부(미결)**: 이 제안은 지금 발견된 `Mutex`/`Semaphore`
  문제를 풀기 위해 `kMakeSharedNew`를 "가상 함수가 있는 T를 위한 범용
  대안 팩토리"로 `shared_ptr.h`에 추가하는 안이다 - 앞으로 다른 가상
  함수 타입이 `SharedPtr`로 관리돼야 할 일이 생기면 같은 함수를 재사용
  하면 된다. `kMakeUnique`에도 대칭적인 `kMakeUniqueNew<T>(Args...)`가
  필요할지는 **지금 시점엔 실제 수요가 없어 이 제안에 포함하지
  않는다**(RM-23F4B687 §4 - 필요해지면 그때 같은 패턴으로 추가).

## 5. 검증 계획

- `kMakeSharedNew<Mutex>()`/`kMakeSharedNew<Semaphore>()`로 만든
  인스턴스의 `w->cancel(task, reason)` 가상 호출이 실제로 올바른
  `WaitQueue::cancel()` 오버라이드로 도달하는지(현재 크래시의 직접
  재현/해소 확인) - PN-B41D8C0E가 이미 만들어 둔 kmain.cpp TEMP
  결정적 시나리오(C가 먼저 잠그고 D가 파킹된 뒤 강제 cancel)를 그대로
  재사용.
- 기존 `kMakeShared`/`kMakeUnique` 사용처(Process/RingBuffer/Task 등)
  무회귀 - 이 제안은 그 경로를 전혀 건드리지 않으므로 회귀 위험은
  낮지만, QEMU 표준 4개 시나리오로 재확인.
- `EnableSharedFromThis<Mutex>` 자동 배선(§2 `if constexpr`)이
  `kMakeSharedNew` 경로에서도 `kMakeShared` 위임을 통해 그대로
  동작하는지.
