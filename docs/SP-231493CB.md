# 소켓 계층 및 net 커널 서비스 — 설계 제안

설계자 Opinion(`SP-94CD958D` 대상, 2026-09-26): "소켓 계층 및 네트워크
커널 서비스를 구현할 계획과 설계안 (POSIX 소켓 포함)." - systemd
포팅 사전조사(`SP-94CD958D`)가 지목한 가장 큰 단일 갭(AF_UNIX 소켓
API + 소켓 활성화)에 대한 실제 설계 제안이다.

## 1. 실측 확인한 현재 상태

- **`net`은 이름만 예약돼 있다** - `kmain.cpp`의 부팅 매니페스트가
  "net"이라는 이름을 인식하지만(SP-EAB162FC §2.2), 실제 네트워크
  드라이버/스택 코드는 이 저장소에 전혀 없다(`RM-7C249618` 라이브러리
  목록에도 net 관련 항목 없음).
- **PCI 열거는 이미 되지만 NIC 드라이버가 없다** - `Pci::enumerate()`
  (`SP-9DD4F3EA` §2)가 부팅 시 모든 PCI 장치를 스캔하나, 이더넷
  컨트롤러(virtio-net/e1000 등)를 인식해 드라이버를 붙이는 코드는
  없다.
- **소켓과 가장 가까운 기존 메커니즘은 `Channel` IPC**(`SP-1FBC0EEB`)
  - 이름 있는 양방향 메시징 채널, 임의 바이너리 와이어 포맷. 다만
  POSIX 소켓과는 철학이 다르다: `Channel`은 처음부터 "이름으로 찾아
  연결"하는 모델이라 `accept()`/`listen()`류 서버 소켓 시맨틱이 없고,
  fd 테이블(`Process::FileDescriptor`, `SP-2AAD7C8D` §9.2)에도
  통합돼 있지 않다 - `Channel` 핸들은 VFS `Open`이 반환하는 fd와
  별개 네임스페이스다.
- **fd 테이블/VFS syscall(Open/Read/Write/Close)은 이미 있다**
  (`SP-2AAD7C8D` §9, 구현 완료 `RM-48E1E610` 그룹3) - 소켓 fd를
  이 테이블에 통합하면 `Read`/`Write`/`Close`를 그대로 재사용할 수
  있다.
- **`SpawnProcess`가 `argv`/`envp`를 System V ABI 관례로 이미 전달
  한다**(`SP-6BEAE0C1` §4) - 소켓 활성화의 `LISTEN_FDS` 환경변수
  규약을 얹을 자리가 이미 있다.

## 2. 스코프 결정 - v1은 AF_UNIX만, AF_INET(실제 네트워킹)은 범위 밖

**근거**: NIC 드라이버가 전혀 없어(§1) AF_INET(실제 TCP/IP 스택)은
이 문서 하나로 끝날 작업이 아니라 그 자체로 PnP 매칭(§SP-9DD4F3EA)
+ 드라이버(§SP-C2670F69/E35FD36C급 규모) + ARP/IP/TCP/UDP 스택이라는
독립된 대형 서브시스템이다. 반면 **AF_UNIX(로컬 소켓)는 하드웨어
의존성이 전혀 없다** - 이미 존재하는 `Channel` IPC와 fd 테이블만으로
POSIX 호환 API를 앞에 씌우는 문제로 좁아진다. systemd 포팅이 실제로
당장 필요로 하는 것도 소켓 활성화(로컬 `.socket` unit, 대부분
AF_UNIX)이지 원격 네트워킹이 아니다(`SP-94CD958D` §1 항목3 참고).

**따라서 이 문서는 AF_UNIX만 설계한다.** AF_INET/네트워크 커널
서비스는 §7에서 후속 계획으로만 분리해 둔다(RM-23F4B687 §4 -
지금 실사용 근거가 없는 것을 임의로 설계하지 않음).

## 3. 핵심 모델 - `Channel` 위에 POSIX 소켓 API를 얹는다

```cpp
// minicore/kernel/socket.h (신규 파일 제안)
namespace kernel {

enum class SocketDomain : uint32_t { Unix = 1 };  // AF_INET 등은 후속(§7)
enum class SocketType : uint32_t { Stream = 1, Datagram = 2 };

struct UnixSocket {
    SocketType type = SocketType::Stream;
    // 아직 bind() 안 됨 = 익명. bind() 후 named object로 등록(§4).
    char boundPath[kMaxNamedObjectNameLength] = {};
    bool bound = false;
    bool listening = false;
    uint32_t backlog = 0;
    // Stream: accept() 대기 중인 연결 요청 큐(양방향 Channel 핸들 쌍).
    // Datagram: 수신 큐(발신자 주소+페이로드).
    // 실제 자료구조는 기존 Channel의 AsyncTaskWaitQueue 패턴 재사용
    // (SP-1FBC0EEB §3) - 착수 세션이 구체화(순수 구현 세부).
};

}  // namespace kernel
```

- **핵심 설계 결정**: 소켓은 새 IPC 프리미티브가 아니라 **`Channel`의
  POSIX 호환 파사드**다 - `connect()`가 성립하면 그 밑바탕은 실제로
  `Channel`의 양방향 메시지 큐(`SP-1FBC0EEB` §3)와 동일하다. 이러면
  (a) 기존 Channel의 동시 다중 accepter/reader/writer 지원
  (`PN-C9625015`, completed)을 그대로 재사용할 수 있고, (b) 이 문서가
  새로 설계해야 하는 범위가 "POSIX 이름/시맨틱 매핑"으로 좁아진다.
- **소켓 fd는 `Process::FileDescriptor` 테이블에 통합**(§1) - `Read`/
  `Write`/`Close` syscall(그룹3)이 그대로 소켓 fd에도 동작해야
  한다(POSIX 소켓의 핵심 성질 - "소켓도 파일처럼 read/write된다").
  `FileDescriptor`에 `Kind::Socket` 태그를 추가하고, `Read`/`Write`
  핸들러가 그 태그를 보면 `UnixSocket`의 Channel로 위임한다(기존
  `Kind::KernelDriverFile`/`Kind::Channel`류 분기와 동일 패턴).

## 4. [갱신, 2026-09-26, 설계자 Opinion] 이름 있는 소켓 - 자동 등록 경로 + 실제 VFS 경로 바인드 둘 다 포함

**최초안은 실제 VFS 경로 바인드를 범위 밖으로 뒀으나, 설계자가
포함하라고 지시했다.** 이 절을 아래 세 부분으로 재설계한다.

### 4-1. 모든 소켓의 자동 등록 경로 (설계자 지시)

`Socket()`으로 만들어지는 **모든** 소켓은(명시적 `Bind()` 여부와
무관하게) 생성 시점에 소유자 기준으로 발견 가능한 경로에 자동
등록된다(`NamedObjectTable` 확장 - Linux `/proc/net/unix`류의 "전체
소켓 가시성"과 같은 목적):

- **유저랜드 프로세스가 만든 소켓**: `/sys/live/named/<pid>/<handle>`
  (`pid`=소유 프로세스, `handle`=그 소켓의 fd 값).
- **커널 또는 커널 서비스가 만든 소켓**: `/sys/live/named/unix/
  kernel/<ownerId>/<handle>` - **커널의 PID는 코어와 무관하게 항상
  `0`으로 고정**이므로 커널 자신이 직접 만든 소켓은 정확히
  `/sys/live/named/unix/kernel/0/<handle>`. devmgr/fs 같은 커널
  서비스(`KernelThread`, `PN-615C48D5`)가 만드는 경우의 `ownerId`는
  이 문서가 확정하지 않는다 - 각 서비스의 기존 식별 방식(있다면)을
  착수 세션이 확인해 채운다.

### 4-2. `Bind(fd, path)` - named object(단순 이름) + 실제 VFS 경로 둘 다 지원

`path`의 형태로 두 대상을 판별한다:

1. **슬래시 없는 단순 이름** - 기존 방식 그대로, `NamedObjectTable`
   에 등록(`PL-C8648D4D`, 변경 없음). 이미 존재하는 이름이면
   `AddressInUse`.
2. **`/`로 시작하는 실제 VFS 경로**(예: `/sys/etc/foo.sock`) - 그
   경로에 **소켓 특수 파일**을 만든다(POSIX `S_IFSOCK` 개념 - 실제
   데이터를 담는 파일이 아니라 "이 경로는 이 소켓을 가리킨다"는
   참조만 담음). **[해소, 2026-09-26, `DC-E441CB59`/`QU-A851B1AF`
   답변]** 실측 확인 결과 VFS엔 파일 타입 구분 필드가 `isDirectory:
   bool` 하나뿐이었다(일반화된 열거형 없음) - 설계자가 **(B)
   `enum class FileType` 전면 통합**으로 확정했다. `StatArgs::
   isDirectory`가 `StatArgs::type: FileType`(`Regular`/`Directory`/
   `Socket`)으로 교체되고, 이를 구현하는 모든 드라이버(livefs/
   procfs/resourcegroupfs/ext4/FAT32/FAT16/exFAT/NTFS)의 Stat
   핸들러가 동시에 수정된다 - 이 VFS 레벨 변경 자체는
   `PN-4BDA31FC`(scheduled)로 분리 추적, 이 소켓 계층 구현은 그
   완료를 선행 조건으로 삼는다(`plan_depend` 등록됨).
3. `Connect(fd, path)`도 대칭으로 확장 - `path`가 VFS 경로면
   `Open()`으로 그 경로를 열어 소켓 특수 파일인지 확인(아니면
   `NotASocket`류 에러로 거부) 후 그 소켓에 연결.

## 5. syscall API (새 그룹 11 - Socket, `RM-48E1E610` 다음 미사용
그룹)

```
Socket(domain: SocketDomain, type: SocketType) -> fd(int64_t, 실패 시 음수)
Bind(fd, path: char* [유저 메모리]) -> error
Listen(fd, backlog: uint32_t) -> error
Accept(fd) -> newFd(int64_t)              // Stream 전용, 연결 대기까지 블로킹
Connect(fd, path: char* [유저 메모리]) -> error
Shutdown(fd, how: ShutdownHow) -> error   // Read/Write/Both 중 하나 방향만 닫기
```

(`Send`/`Recv`는 별도 syscall을 만들지 않는다 - §3이 확정한 대로
기존 `Read`/`Write`(그룹3)를 그대로 쓴다. `Close`도 기존 그룹3
재사용. `SocketPair()`류 익명 소켓 쌍 생성은 v1 범위 밖 - 구체적
소비자가 나타나면 재검토.)

유저 포인터(`path`) 검증은 `SpawnProcess`(`SP-6BEAE0C1` §3)가
확립한 관례(호출 안에서 검증+복사, 별도 준비 단계 없음)를 그대로
따른다.

## 6. 소켓 활성화 (`LISTEN_FDS`)

systemd식 소켓 활성화의 핵심: 슈퍼바이저(향후 systemd 포팅, 또는
당장은 `init`)가 리슨 소켓을 미리 만들어 자식에게 fd를 물려주고
서비스를 지연 기동한다.

- `SpawnProcess`(§1, `SP-6BEAE0C1`)에 **fd 상속** 기능이 필요하다 -
  현재 그 설계는 인자/환경변수 전달만 다루고 fd 상속은 다루지 않았다.
  제안: `SpawnProcessArgs`에 `inheritFds: int64_t*`(부모 fd 번호
  배열) 필드를 추가 - 자식의 fd 테이블에 **fd 번호 3부터 순서대로**
  같은 `FileDescriptor` 항목을 복제(참조 카운트 증가, 소유권 공유 -
  `dup()`와 동일 시맨틱).
- `SpawnProcess`가 자식에게 `envp`로 `LISTEN_FDS=<개수>`와
  `LISTEN_PID=<자식 pid>`(systemd 규약 그대로)를 자동으로 주입한다.
- **정확한 트리거 조건(첫 연결 시점에 지연 기동)은 이 문서 범위
  밖** - 그건 "슈퍼바이저가 리슨 소켓의 `Accept`를 대신 걸어 두고,
  연결이 오면 그제서야 서비스를 스폰한다"는 슈퍼바이저 자신의 로직
  이다(systemd 자체를 포팅하거나 그 역할을 대신할 무언가가 필요 -
  `PN-A0EF864B` 영역). 이 문서는 그 슈퍼바이저가 쓸 수 있는 fd
  상속 프리미티브만 제공한다.

## 7. 범위 밖 - 후속 계획으로 분리

- **AF_INET(실제 TCP/IP 네트워킹)** - NIC 드라이버(PnP 매칭 +
  probe(), `SP-9DD4F3EA` §3.2 프레임워크 재사용) + ARP/IP/TCP/UDP
  스택이 전부 필요한 독립 서브시스템. `net` 커널 서비스라는 이름은
  이 후속 작업이 실제로 채우게 된다(devmgr/fs가 `KernelThread`로
  흡수된 것과 같은 패턴을 따를지는 그 시점에 결정, `SP-43331889`
  선례 참고).
- **소켓 옵션(`setsockopt`/`getsockopt`)** - v1 소비자 없음.
- **비블로킹 소켓(`O_NONBLOCK`)/`select`류 통합** - 별도 문서
  (epoll류 설계, 이번 세션에서 함께 요청됨)가 다룬다 - 소켓 fd가
  일반 fd 테이블에 통합돼 있으므로(§3) 그 설계가 자연히 적용된다.
- **`SocketPair()`** - 구체적 소비자 나타나면 재검토.

## 8. 검증 계획(초안)

1. 같은 프로세스 안에서 `Socket`+`Bind`+`Listen`, 다른 프로세스가
   `Connect` - `Accept`가 새 fd를 반환하고 그 fd로 `Write`/`Read`
   왕복이 실제로 되는지 확인(Stream).
2. Datagram - `Bind` 없이 `Connect` 후 `Write`/`Read`로 데이터그램
   왕복.
3. `SpawnProcess`의 fd 상속(§6) - 부모가 리슨 소켓을 만들고
   `inheritFds`로 넘긴 자식이 `LISTEN_FDS` 환경변수를 읽어 그 fd로
   바로 `Accept` 가능한지 확인.
4. 이름 충돌(`AddressInUse`)/존재하지 않는 경로(`Connect` 실패)
   에러 케이스.
5. 표준 5시나리오 무회귀.
