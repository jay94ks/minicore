## 요약

`PN-F2594E93`(설계자 답변 "(b) 재시도 카운트 기반 강등")를 적용해
디스크 없는 순수 격리 재현(1개 락 경합자)과 실제 AHCI ext4 8-writer
쿼터 재검증에서는 hang이 사라졌다고 확인하고 그 계획을 `completed`로
닫았다. 그런데 오늘 같은 틱에서 `PN-ADA46BF4`(Ext4Driver 블록 비트맵
동시성 수정)를 재개해 `gBlockBitmapAllocMutexCore`를 9개 호출부에
재적용하고 실제 AHCI로 재검증하자, **8-writer는 물론 2-writer조차
100% 다시 hang**했다(`AsyncTaskWaitGroup::waitAll()`이 전혀 반환하지
않고 NMI watchdog "this core unresponsive" 발동, 40초 타임아웃까지
무응답). "(b)" 수정이 완전한 해법이 아니었을 가능성 - 최소한 이
시나리오에서는 재현이 안 사라졌다.

## 재현 절차(그대로 재현 가능)

1. `minicore/libs/libext4/ext4_driver.cpp`: 파일 앞쪽에
   `kernel::MutexCore gBlockBitmapAllocMutexCore;`(+`MutexCoreReleaseGuard`
   재사용) 선언, 블록 할당/해제 9개 호출부(1163/1273/1339/1510/1598/
   2870/3373/4183/4946 - `PN-ADA46BF4` 본문에 정확한 목록/스코프 경계
   기록됨) 전부를 `while (!gBlockBitmapAllocMutexCore.tryAcquire()) {
   co_await kernel::AsyncTaskCoroYield{}; } MutexCoreReleaseGuard guard(...)`
   로 감싼다(비트맵 read → kExt4AllocateBlockInGroup/kExt4FreeBlockInGroup
   → 비트맵+gd write까지 반복 전체가 임계구역).
2. `minicore/kernel/fs.cpp`: `kFsKernelMain`의 `kTryAutoMountBlockDevice()`
   직후에 TEMP 검증 함수를 추가해 - (a) `gExt4Driver.remount(true)`로
   쓰기 허용 전환, (b) `Process::allocate()+init()+kMakeShared<Process>`
   +`UserThread::allocate()`로 uid=5001 가짜 프로세스/스레드 N개 생성
   (fd 테이블/kValidateVfsBuffer 등 상위 syscall 계층은 이 테스트와
   무관해 건너뛰고 `KernelFsOpenArgs`/`KernelFsWriteArgs`를
   `gExt4Driver.subjectCode()`에 직접 제출 - `kAcceptFromChannelDirect`
   와 동일한 관례, `task->submitterTask = TaskOwnerRef::capture(...)`로
   신원만 수동 주입), (c) 서로 다른 빈 파일 N개(`/qw0`..)를 Open,
   (d) N개의 `KernelFsWriteArgs`(4096바이트, 새 블록 필요)를 전부
   제출한 뒤 **하나의 `AsyncTaskWaitGroup`으로 한 번에 waitAll()**.
3. quota 기능 없는 순정 32MB ext4 이미지(`mke2fs -t ext4 -b 1024`,
   저널/metadata_csum 끔) + uid 5001 소유 빈 파일 8개(qw0~qw7).
4. GRUB SMP4+AHCI(`scripts/run-grub.sh`, `MINICORE_QEMU_SMP=4
   MINICORE_QEMU_AHCI=1 MINICORE_QEMU_AHCI_DISK=<위 이미지>`)로 부팅.
5. **N=8 100% hang**(NMI watchdog). 원인 이분 탐색을 위해 **N=2로
   축소해도 여전히 100% hang** - 즉 "8-way라 심하다"가 아니라 2-writer
   (락 경합자 정확히 1개)만으로도 재현된다.

## 왜 당혹스러운가 - 이미 검증됐다고 믿은 것과 정면 충돌

`PN-F2594E93`가 이미 "1개 락 보유자(임계구역 안에서 다른 AsyncTask
완료를 co_await) + 1개 재시도 대기자" 조합을 디스크 없는 더미
`AsyncTaskHandler`(즉시 co_return)로도, **실제 AHCI 8-writer 쿼터
재검증**(`gQuotaCurspaceMutexCore`, 새 블록 필요한 첫 쓰기)으로도
hang 없이 통과했다고 기록했다. 이번 `gBlockBitmapAllocMutexCore` 재현은
그 두 검증과 구조적으로 거의 동일해 보이는데(같은 `MutexCore`+
`co_await AsyncTaskCoroYield{}` 재시도 패턴, 같은 스케줄러, 같은
AHCI+SMP4 환경) 다시 100% hang한다. 확정하지 못한 차이 후보(다음
착수 세션이 gdb로 직접 확인해야 함):

- **임계구역이 감싸는 co_await 개수**: `gQuotaCurspaceMutexCore`
  구간(쿼터 리프 read→curspace 계산→write, 대략 read 1~2회+write
  1~2회)과 달리 `gBlockBitmapAllocMutexCore` 구간은 그룹 스캔 한
  반복마다 **`co_await kernel::AsyncTaskCoroAwaiter` 4회**(비트맵
  read, gd read, 비트맵 write, gd write)를 연달아 감싼다 - 훨씬 긴
  보유 시간이 근본 원인일 가능성.
- **AHCI 자신의 인터럽트 대기 경로**: `ahci.cpp`의
  `AhciCommandHandler::onExec`(:298-341)은 인터럽트가 배정된 경우
  `co_await kernel::AsyncTaskCoroAwaiter(waitTask)`(regular 큐,
  `preemptive=false`로 명시 제출 - PN-4859FDE9 데드락 회피 근거)로
  대기하고, **인터럽트 미배정 시에만** `co_await
  kernel::AsyncTaskCoroYield{}` 폴링 폴백을 쓴다(:341, 문서 주석
  "인터럽트 미배정 시의 폴백 경로로도 그대로 쓰인다"). 표준 회귀에서
  AHCI는 인터럽트 기반이므로(PN-FFFE892E) 이 폴백 경로가 이번 hang의
  원인일 가능성은 낮아 보이지만 실측 확인 안 됨.
- **N=2에서도 재현**된다는 사실이 "다수 경합자가 개별 강등 카운터를
  각자 다른 타이밍에 소진해 선점 큐가 통계적으로 거의 안 빈다"는
  N-way 가설과는 안 맞는다(N=2는 이미 검증됐다는 8-writer 쿼터
  케이스와 락 경합자 수 자체는 오히려 더 적다) - "(b)" 수정 자체의
  적용 범위(어떤 조건에서 통하고 어떤 조건에서 안 통하는지)를 아직
  정확히 모른다는 뜻으로 해석하는 게 더 정직하다.

## 조치

`gBlockBitmapAllocMutexCore` 재적용 코드와 TEMP 검증 하네스 전부
`git checkout --`로 완전히 원복(`git status`/재빌드로 클린 확인,
커밋된 것 없음) - `PN-ADA46BF4`(블록 비트맵 데이터 손상 자체)는
여전히 미해결로 남는다. `PN-F2594E93`는 상태를 되돌리지 않는다(그
계획이 검증한 두 시나리오 자체는 실제로 hang 없이 통과했다는 사실은
유효) - 대신 이 DC와 상호 참조를 그 계획 본문에 정정 섹션으로
추가한다(CLAUDE.md 규칙 11).

## 결정/조사 요청

1. 이 새 재현(임계구역이 실제 AHCI I/O co_await 4회를 연달아 감싸는
   경우)을 다음 착수 세션이 gdb로 직접 추적해야 하는가, 아니면 설계
   자체를 바꿔야 하는가?
2. 바꾼다면 방향 후보 - (a) `AsyncReactor::drainOnce()`를 "선점 큐
   우선"에서 "코어별 연속 선점 드레인 횟수 상한"(예: 연속 K회 선점
   큐만 처리했으면 그다음 1회는 무조건 일반 큐부터 확인, 어느 task의
   재시도인지와 무관한 전역 카운터)으로 바꾼다 - "(b)"의 task별
   카운터를 대체/보강. (b) 임계구역이 실제 I/O `co_await`를 포함하는
   패턴 자체를 금지하고(`gBlockBitmapAllocMutexCore`류 락은 비트맵을
   메모리에 올린 뒤 짧게만 잠그고 I/O는 락 밖에서 하도록 알고리즘을
   다시 설계 - 그룹 스캔 자체를 어떻게 원자적으로 유지할지는 별도
   설계 필요). (c) 그 외.
3. 재현이 "임계구역이 I/O co_await를 감싸는 모든 경우"로 일반화되면
   `gQuotaCurspaceMutexCore`(`PN-D168A778`)도 재검토 대상 - 왜 그쪽은
   같은 8-writer 실측에서 hang이 안 됐는지(우연/타이밍 차이인지, 구조가
   실제로 다른지) 부터 먼저 규명 필요.
