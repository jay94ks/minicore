# VFS 커널 서브시스템 — 설계 제안

설계자 지시(2026-09-14, 메시지) - "VFS는 커널 영역 서브시스템인데,
이것도 설계하고, 가장 처음 고려해야 할 FS는 ext4, 그 다음은 swapfs,
그 다음은 FAT32/16이야." SP-8B6B8D25 §4(파일 시스템 구조)/§4-A(VFS
루트 소유권과 마운트 포인트 처리 분담)가 이미 정해 둔 큰 원칙 -
"VFS 트리 구조 자체(루트, 경로 해석, 계층)는 **커널**이 소유·관리하고,
각 마운트 지점의 실질적인 파일시스템 처리는 유저랜드의 `fs` 서비스가
맡는다" - 을 실제 커널 서브시스템 설계로 구체화한다. 이 문서는 **모순이
아니라 §4-A의 구체화**다: "VFS가 커널 영역 서브시스템"이라는 이번
지시는 "VFS 트리/경로 해석 자체는 커널 코드"라는 뜻이고, 실제 ext4/
swapfs/FAT32/16 드라이버 자체는 여전히 §2-A 원칙대로 `fs` 서비스
(유저랜드) 안에서 구현된다.

**[재확인, 2026-09-14, 설계자 후속 메시지]** - "VFS 마운트는 VFS
트리를 커널이 유지하도록 해. 마운트된 지점 이후로만 fs 서비스 아래에
구현된 각 파일 시스템 드라이버가 처리하도록." 이 문서가 §1/§2에서
이미 설계한 그대로다(`MountTable`이 커널에 있고, `MountTable::resolve`
가 찾은 마운트 지점 **이후**의 상대 경로만 `fs` 서비스 쪽 드라이버가
처리) - 새로 바뀌는 설계는 없고, 방향이 정확히 일치함을 재확인한다.

**[추가, 2026-09-14, 설계자 후속 메시지]** - "유저랜드가 알아서
감지한다고 해도 fs 서비스가 식별은 해야 하는게 맞는데, 이것은 init
프로그램이 구동되면서 커널에 syscall로 유저 영역이 정상적으로 동작한다는
신호를 줬을 때(커널 전역으로 단 1회만 호출이 가능하도록 처리할것)부터
감지하도록 해야해." §2.5에서 이 "유저랜드 준비 신호" syscall을
설계했다 - `fs` 서비스의 파일시스템 자동 감지(§3.2 슈퍼블록 감지)는
이 신호 이후에만 시작해야 한다.

## 1. 배경 - 무엇이 커널이고 무엇이 유저랜드인가 (다시 정리)

| 계층 | 위치 | 역할 |
|---|---|---|
| VFS 트리/경로 해석/마운트 테이블 | **커널** (`minicore/kernel`) | 절대 경로를 받아 "어느 마운트가 담당하는지" 찾아 라우팅만 한다 - 실제 파일 내용은 절대 보지 않는다. |
| 파일시스템 드라이버(ext4/swapfs/FAT32/16) | **[개정, 설계자 지시, 2026-09-15] `minicore/libs/lib{ext4,swapfs,vfat}`**(커널/유저 공용 라이브러리, `libelf`/`libcpio`와 같은 패턴 - RM-7C249618) - `fs` 서비스(유저랜드, `minicore/fs`)가 이 라이브러리들을 링크해 `FileSystemDriver`(§3.2) 구현으로 얹는다 | 블록 장치(AHCI 등)를 실제로 파싱해 파일/디렉터리 읽기/쓰기를 구현한다. |

이미 구현된 선례: `/sys/live/named/`(SP-1FBC0EEB, `NamedObjectTable`,
PL-C8648D4D 완료)가 "진짜 마운트 기반 VFS는 아직 없지만 커널 내부
이름 테이블로 미리 이 원칙을 따른" 사례로 설계자 확인을 받았다
(RM-C65F7760 참고) - 이번 VFS 커널 서브시스템은 그 패턴을 "경로 전체"
로 일반화하는 것이다.

## 2. VFS 커널 서브시스템 설계

### 2.1 자료구조 - 마운트 테이블

커널은 파일 내용이나 디렉터리 엔트리를 전혀 모른다 - 아는 것은
**"이 절대 경로 접두사는 이 fs 서비스 인스턴스가 담당한다"**는
매핑뿐이다:

```cpp
// minicore/kernel, 가칭 - NamedObjectTable(SP-1FBC0EEB)과 같은 층위의
// 커널 내부 테이블. rbtree/해시가 아니라 "마운트 개수가 많지 않다"는
// 전제로 v1은 선형 배열 + 최장 접두사 일치(longest prefix match)로
// 충분하다고 제안(RM-23F4B687 §4 취지 - 실측 후 필요하면 트라이 등으로
// 교체).
//
// [개정, 설계자 지시, 2026-09-15] 마운트 소유자는 두 종류다 - §2.4
// livefs 참고. 기존 "MountTable을 우회해 /sys/live/ 접두사를 커널이
// 직접 가로챈다"는 설계는 철회한다 - livefs도 다른 fs 서비스와 똑같이
// **이 MountTable에 정식으로 마운트되는 대상**이어야 한다는 게 설계자
// 지시다. 다만 그 마운트의 "처리자"가 유저랜드 Channel이 아니라
// 커널 자신이 구현한 드라이버라는 점만 다르다.
enum class MountKind : uint8_t {
    Channel = 0,        // 기존: 유저랜드 fs 서비스 - IPC(Channel)로 라우팅
    KernelDriver = 1,   // 신규: 커널이 직접 구현한 드라이버(livefs 등) - IPC 없이 그 자리에서 직접 호출
};

// KernelDriver 종류 마운트가 구현해야 하는 인터페이스.
//
// **[확장, 2026-09-16, 설계자 지시 2건]** (1) "KernelFsDriver에도
// FileSystemDriver와 거의 동일한 동작들이 추가되어야 해 ... 해당
// 드라이버와 쌍을 이루는 구조가 될거야." (2) 후속 - "비동기
// 프레임워크를 기반으로 동작하도록 각 메서드 시그니쳐를 재검토해줘."
//
// **[정정]** 최초 개정에서 각 메서드가 `AsyncTaskCompletion*`를
// 직접 반환하도록 제안했으나, 이는 실제 비동기 프레임워크(SP-F682B889)
// 의 확립된 사용 패턴(§3.1 `AsyncTaskHandler`/`AsyncCallbackRegistry`
// + args 구조체)과 맞지 않는다 - 재검토 결과 **`KernelFsDriver` 자신이
// `AsyncTaskHandler`를 구현**하는 형태로 다시 설계했다:
//
// - 부팅 시 `mountKernel()` 호출 시점에 그 드라이버 인스턴스를
//   `AsyncCallbackRegistry::registerHandler(this)`로 **한 번만** 등록해
//   `AsyncTaskSubjectCode`를 발급받는다(§3.1 "기능별로 1회 등록" 관례 -
//   요청마다 등록/해제하지 않음).
// - syscall 처리부(SP-2AAD7C8D §9)는 op별 `args`(Slab 할당, §3.1
//   "args 생성/해제는 처리기 책임")를 만들어
//   `AsyncTask::submit(subjectCode, manageCode, args)`로 제출하고,
//   `AsyncTaskCompletion`(§9.2)을 통해 `waitSync()`/`waitAsync()`로
//   기다린다 - `MountKind::Channel`(fs 서비스로 IPC 왕복, 그 자체도
//   AsyncTaskCompletion으로 기다림)과 **정확히 같은 대기 방식**이라
//   호출부가 두 마운트 종류를 분기해서 다르게 취급할 필요가 없다
//   ("해당 드라이버와 쌍을 이루는 구조"라는 지시의 의도).
// - `args`는 op마다 다른 구조체이지만 전부 맨 앞에 `KernelFsOpCode op`
//   태그를 둔다(SP-04EE2A18/SP-1FBC0EEB의 각 syscall args 구조체와
//   동일 관례 - 하나의 `onExec()`가 여러 종류의 요청을 op 태그로
//   분기 처리) - 이 구조는 아래 pseudocode로 스케치, 정확한 9개
//   args 구조체 전부는 구현 착수 시 SP-2AAD7C8D §9의 syscall args와
//   1:1 대응시켜 확정한다(이 문서가 전부 미리 정의하지 않음).
//
// block device가 없으므로 `mount(BlockDevice*)`는 여전히 없다.
//
// **영향받는 기존 구현**: `LiveFs`(PN-71C2B857, completed)는 지금
// 동기 `open/close/read` 3개(가상 함수 직접 호출)만 구현하고 있어
// 이 확장(AsyncTaskHandler 상속 + args 기반 디스패치)에 맞춰
// 재작업이 필요하다 - 실제 데이터가 이미 메모리에 있는(livefs
// 특성상 진짜 블로킹은 없는) 연산이라도, `onExec()` 안에서 그 자리에서
// 바로 결과를 채우고 반환하면 프레임워크가 그걸 "즉시 완료"로
// 처리한다(§9.3) - 별도의 실제 비동기 대기 구현이 필요하다는 뜻은
// 아니다. 실제 마이그레이션은 PN-BC04D3DC로 추적.
enum class KernelFsOpCode : uint32_t {
    Open, Close, Read, Write, Stat, Mkdir, Rmdir, Unlink, Readdir
};

// 예시 스케치(2개만) - 나머지 7개도 같은 관례(op 태그 + 해당
// 오퍼레이션의 입력/출력 필드 + 실패 시 채울 에러 필드)로 구현 착수
// 시 확정.
struct KernelFsOpenArgs {
    KernelFsOpCode op = KernelFsOpCode::Open;  // 항상 KernelFsOpCode::Open
    const char* relPath; uint32_t relPathLen; uint32_t flags;
    OpenResult result;  // onExec()가 채움
};
struct KernelFsReadArgs {
    KernelFsOpCode op = KernelFsOpCode::Read;
    FileHandle handle; uint64_t offset; void* buf; uint32_t len;
    ReadResult result;
};
// ... Close/Write/Stat/Mkdir/Rmdir/Unlink/Readdir용 args 구조체 7개 추가(동형 패턴).

class KernelFsDriver : public AsyncTaskHandler {
public:
    // args(위 구조체 중 하나, op 태그로 판별)의 오퍼레이션을 실행하고
    // 그 args의 result 필드를 채운다 - 실행이 끝나면 프레임워크가 이
    // AsyncTask에 연결된 AsyncTaskCompletion을 확정한다(SP-F682B889 §9.3).
    void onExec(AsyncTask* task, void* args) override;
    // Slab 고갈 등으로 실행 자체가 불가능했을 때(§3.1) - 재시도 여부는
    // 이 드라이버가 결정.
    void onFailure(AsyncTask* task) override;
    // 대기자가 완료 전에 죽었을 때(§3.1, onExec이 아직 시작 전인
    // 경우만 - 이미 시작된 뒤라면 §8의 AsyncToken 협조적 취소 경로).
    void onCancel(AsyncTask* task, void* args) override;
};

struct MountEntry {
    char path[kMaxMountPathLen];  // 예: "/sys/etc" - 정규화된 절대 경로
    uint32_t pathLen;
    MountKind kind = MountKind::Channel;
    uint64_t ownerChannelId;      // kind == Channel일 때만 유효(기존과 동일)
    KernelFsDriver* kernelDriver; // kind == KernelDriver일 때만 유효(신규)
    bool used = false;
};

class MountTable {
public:
    static bool init();
    // 최장 접두사 일치로 path를 담당하는 마운트를 찾는다. kind까지
    // 함께 반환 - 호출부(§2.2 ResolvePath 처리부)가 Channel이면 기존
    // 그대로 채널ID를 유저에게 돌려주고, KernelDriver면 그 드라이버의
    // AsyncTaskSubjectCode로 AsyncTask::submit()해 요청한다([갱신,
    // 2026-09-16] IPC 왕복은 없지만 더 이상 "동기 직접 호출"도
    // 아니다 - AsyncTaskHandler 기반, §2.1 KernelFsDriver 참고).
    static bool resolve(const char* path, uint32_t pathLen,
                         MountKind* outKind, uint64_t* outChannelId,
                         KernelFsDriver** outKernelDriver, uint32_t* outRelOffset);
    static bool mount(const char* path, uint32_t pathLen, uint64_t channelId);  // 유저랜드 fs 서비스용(§2.2 Mount syscall)
    // 커널 자신이 부팅 시퀀스(kmain.cpp)에서 직접 호출 - syscall이
    // 아니다(유저 프로세스가 커널 드라이버를 마운트시킬 이유가 없음).
    static bool mountKernel(const char* path, uint32_t pathLen, KernelFsDriver* driver);
    static bool unmount(const char* path, uint32_t pathLen);
};
```

### 2.2 Syscall API

```cpp
// fs 서비스 → 커널: 이 fs 서비스 인스턴스가 이 경로 아래를 전담하겠다고
// 등록한다. PnP의 IO 권한 부여(SP-9DD4F3EA §3.3)/DMA 버퍼 관리자
// (SP-39F18E30 §2)와 같은 층위 - SyscallRegistry(PL-21344323)에 등록.
struct MountArgs {
    const char* path;       // in
    uint32_t pathLen;
    uint64_t channelId;     // in: 이 fs 서비스가 미리 만들어 둔 Channel(PL-C8648D4D)
    // out
    ChannelError error;     // AlreadyMounted / InvalidPath(루트 밖 등)
};

struct UnmountArgs {
    const char* path;
    uint32_t pathLen;
    ChannelError error;     // NotMounted
};

// 임의의 프로세스 → 커널: 절대 경로를 담당 fs 서비스의 Channel로
// 라우팅한다. 커널은 "누가 담당인지"만 알려주고, 실제 열기/읽기/쓰기는
// 호출부가 그 Channel로 직접 IPC해야 한다(§4-A "커널은 라우팅 대상으로만
// 안다" 원칙 그대로).
struct ResolvePathArgs {
    const char* path;         // in: 절대 경로
    uint32_t pathLen;
    // out
    ChannelError error;        // NotFound(어느 마운트도 담당 안 함)
    uint64_t ownerChannelId;   // 이 경로를 처리할 fs 서비스의 Channel
    uint32_t relPathOffset;    // path 안에서 마운트 지점 접두사를 뺀 나머지 시작 위치
};
```

표준 파일 API(open/read/write/close/lseek/stat 등)의 실제 syscall
설계는 **SP-2AAD7C8D §9**("표준 파일 API")에서 이 `ResolvePathArgs`를
기반으로 구체화됐다 - 그 문서가 `Process`의 파일 디스크립터 테이블과
`Open`/`Close`/`Read`/`Write`/`Lseek`/`Stat`/`Readdir`/`Mkdir`/
`Unlink` syscall을 전부 다룬다(이 문서의 범위는 "경로 → 담당 fs
서비스 채널" 라우팅까지로 유지).

### 2.3 부팅 시퀀스와의 관계

`fs` 서비스(devmgr과 마찬가지로 initrd의 정적 프로세스, QU-FF3F0CAA
답변 참고)는 기동 직후 자신이 담당할 마운트(`/sys/etc`, `/sys/bin`
등, SP-8B6B8D25 §4)를 위 `Mount` syscall로 순서대로 등록한다 - 등록
순서/실패 처리(예: 담당 블록 장치가 아직 준비 안 됨)는 `fs` 서비스
자체의 초기화 로직 범위이지 이 커널 서브시스템의 범위가 아니다.
**단, 실제 파일시스템 자동 감지(슈퍼블록 판별, §3.2)는 §2.5의
"유저랜드 준비 신호" 이후로 미뤄야 한다** - 마운트 테이블 자체의
등록(빈 마운트 지점을 미리 잡아 두는 것)과 그 마운트에 실제로 어떤
드라이버를 연결할지 판별하는 것은 서로 다른 시점이 될 수 있다는 뜻.

### 2.4 `/sys/live/` — livefs(커널 구현 마운트) [전면 개정,
설계자 지시, 2026-09-15]

**정정**: 이전 초안은 "`/sys/live/` 접두사를 `MountTable` 우회로
커널이 직접 가로챈다"고 설계했었는데, 설계자가 이를 명시적으로
정정했다 - "커널이 `/sys/live/` 접두사를 가로채 직접 응답이 아니라
그 경로 자체에 `livefs`라는 커널이 직접 구현한 구현체를 **마운트**
시키고 `livefs`가 저걸 노출하라는 거야." 즉 livefs는 다른 fs 서비스와
마찬가지로 **`MountTable`에 정식으로 등록된 마운트**여야 한다 - 다만
그 마운트의 처리자가 유저랜드 `Channel`이 아니라 커널 자신이 구현한
`KernelFsDriver`(§2.1)라는 점만 다르다.

**부팅 시퀀스**: `MountTable::init()` 직후, 어떤 유저 프로세스도 아직
없는 시점에 커널이 스스로 `MountTable::mountKernel("/sys/live", &gLiveFs)`
를 호출해 둔다(§2.3의 "fs 서비스가 `Mount` syscall로 등록"과는
다른 경로 - `livefs`는 유저랜드 fs 서비스가 아니라 커널 자신이 소유).

**`LiveFs`**(가칭, `minicore/kernel/livefs.h/.cpp`, `KernelFsDriver`
구현체) - 이전 초안에서 두 개의 별도 특수 경로로 나뉘어 있던 것을
이 하나의 마운트 아래 두 하위 경로로 통합한다:

- `/sys/live/named/<name>` — 이름 있는 IPC 오브젝트 네임스페이스
  (SP-1FBC0EEB). `LiveFs::open()`이 `named/` 접두사를 보면
  `NamedObjectTable`(기존 구현, PL-C8648D4D 완료)에 그대로 위임한다 -
  `NamedObjectTable` 자체를 다시 짤 필요 없음, `LiveFs`가 그 앞의
  얇은 라우팅 층만 새로 맡는다.
- `/sys/live/initrd.cpio` — PN-71C2B857. CPIO initrd를 실제
  파일시스템으로 **마운트하지 않는다**(엔트리를 디렉터리 트리로 풀어
  보여주지 않음) - `LiveFs::open()`이 이 정확한 경로를 보면 부팅 시
  보존해 둔 CPIO 버퍼(`libcpio` 파서가 참조하는 그 버퍼, PL-FC38956C)
  전체를 **하나의 불투명한 파일**로 노출한다 - 그 바이트를 다시 CPIO
  엔트리로 해석하는 건 이 드라이버의 책임이 아니라 읽는 유저랜드
  쪽(예: 설치 도구) 책임이다.
- **[추가, 2026-09-16, 설계자 지시, 2026-09-16 재정정]** `/sys/live/kernel/<name>` —
  "커널 ↔ 커널 서비스 통신 채널"(SP-00CA7175 §2 Tier A/Tier B)의
  예약 지점. `/sys/live/named/`(경쟁적 - 아무 프로세스나
  `openChannel(name)`으로 먼저 개설)와 달리, 이 하위 경로는 **커널이
  부팅 시 직접 예약**한다 - 신규 `KernelReservedTable`(SP-00CA7175
  §2.0)이 `devmgr`/`fs`/`net`/`tty` 4개 자리를 관리하고, `LiveFs::
  open("kernel/<name>", ...)`이 호출자의 `ProcessRole`+스폰 이름을
  그 예약 항목의 정당한 소유자와 대조해 일치할 때만 핸들을 내준다
  (**단순히 이름을 먼저 선점하는 것만으로는 불충분** - 이름을 아는
  임의 프로세스가 `connectChannel()`로 접근을 시도할 수 있어
  명시적 권한 검사가 필요하다는 것이 설계자 지시 이후 재확인된
  결론, SP-00CA7175 §2.0 근거 문단 참고). 실제 Channel 생성 자체는
  `kCreateNamedChannel()`(§2.0a, 기존 `openChannel` 핸들러 로직을
  재사용 가능하게 추출한 내부 함수)로 만든다 - 이 문서는 `livefs`가
  이 세 번째 하위 경로도 담당한다는 사실만 기록(자세한 내용·근거는
  SP-00CA7175 §2 참고).

**§2.2 syscall 처리부와의 관계**: `ResolvePathArgs`/`Open` 등(§2.2/
SP-2AAD7C8D §9)을 처리하는 코드는 `MountTable::resolve()`가 낸
`MountKind`를 확인해야 한다 - `Channel`이면 기존처럼 그 Channel의
소유 채널ID를 알려줘 호출부가 직접 IPC하게 하고, `KernelDriver`이면
그 자리에서 `KernelFsDriver::open/read`를 동기적으로 대행 호출해
결과를 돌려준다(유저 프로세스 입장에서는 두 경우 모두 표준 파일
API로 통일돼 보임 - "이 마운트가 유저랜드 fs 서비스인지 커널 자체
구현인지"는 몰라도 된다). SP-2AAD7C8D §9 착수 시 이 분기를 함께
반영해야 한다.

### 2.5 유저랜드 준비 신호 (2026-09-14, 설계자 지시 - 신규)

설계자 지시: "유저랜드가 알아서 감지한다고 해도 fs 서비스가 식별은
해야 하는게 맞는데, 이것은 init 프로그램이 구동되면서 커널에 syscall로
유저 영역이 정상적으로 동작한다는 신호를 줬을 때(커널 전역으로 단
1회만 호출이 가능하도록 처리할것)부터 감지하도록 해야해." - `fs`
서비스가 파일시스템 자동 감지(§3.2)를 시작해도 되는 시점을 커널이
직접 게이팅한다.

```cpp
// init(QU-FF3F0CAA로 확정된 "첫 프로세스") → 커널: 유저 영역이 정상
// 동작 중임을 커널 전역에 단 1회만 알린다. PnP/DMA 버퍼 관리자와
// 같은 SyscallRegistry(PL-21344323) 층위에 등록.
struct SignalUserlandReadyArgs {
    // in: 없음
    // out
    ChannelError error;   // AlreadyCalled - 두 번째 이후 호출은 전부 이 에러(프로세스가 누구든 무관)
};

// 다른 서비스(fs 등) → 커널: 신호가 아직 없으면 블로킹, 이미 왔으면
// 즉시 반환. Syscall::wait(SP-04EE2A18)의 기존 비동기 대기 인프라를
// 그대로 재사용하는 것을 제안 - 새 대기 메커니즘을 따로 만들지 않는다.
struct WaitForUserlandReadyArgs {
    // in: 없음
    // out
    ChannelError error;   // 성공만 있음(대기는 무한정 - init이 죽으면 어차피 시스템이 죽은 것)
};
```

**"커널 전역으로 단 1회만 호출 가능"의 구현**: 커널에 전역 플래그
하나(`AtomicU32` 또는 단일 `bool`, `libkenv/spinlock.h`의 `AtomicU32`
재사용 - CAS로 0→1 전이를 딱 한 번만 허용)를 두고, `SignalUserlandReady`
가 호출될 때마다 CAS를 시도해 성공한 최초 1회만 `ChannelError::None`을
반환하고 이후 호출은 전부 `AlreadyCalled`를 반환한다 - **어느
프로세스가 호출했는지는 검증하지 않는다**(v1 제안: "이 신호가 정말
init에서 온 것인지" 검증하려면 프로세스 신원/권한 체계가 더 필요한데,
지금은 "이 신호가 정확히 한 번만 발동한다"는 것 자체가 요구사항의
핵심이므로 호출자 신원 검증은 범위 밖으로 둔다 - 필요해지면 별도 DC).

`fs` 서비스는 부팅 초기(§2.3)에 마운트 지점을 미리 등록해 두되,
**실제 슈퍼블록 감지/드라이버 연결(§3.2)은 `WaitForUserlandReady`가
반환한 뒤에만 시작**한다.

## 3. `fs` 서비스 내부 - 파일시스템 드라이버 우선순위와 공통 인터페이스

### 3.1 우선순위 (설계자 확정, 2026-09-14)

1. **ext4** - 이 OS의 주 데이터/루트 파일시스템. 저널링·익스텐트
   기반 블록 매핑·htree 디렉터리 등 실사용에 필요한 현대적 기능을
   갖춘 표준 리눅스 파일시스템이라 최우선으로 지정된 것으로 이해된다.
2. **swapfs** - **이미 설계된 유저 프로세스 폴트 처리 정책이 이것을
   전제로 한다**: `Process::FaultInfo`/QU-0C4D25EF 답변("폴트 정보를
   읽고 그걸 처리해서 프로세스를 죽이거나 swapfs에서 읽어서 페이지를
   갈아 끼워 줘야해")이 이미 "swapfs가 존재한다"고 가정하고 있다 -
   ext4 다음으로 이게 필요한 이유가 이미 코드/설계에 박혀 있다.
3. **FAT32/16** - SP-8B6B8D25 §4의 `/boot/uefi`(ESP, UEFI 부팅 경로용)
   마운트, 그리고 USB/외부 매체와의 상호운용성(대부분 FAT로 포맷되어
   배포됨, AHCI/USB(SP-C2670F69/SP-E35FD36C) 스토리지 드라이버가 실제
   장치를 인식하기 시작하면 자연히 필요) 두 가지 용도로 세 번째.

### 3.1a 라이브러리 분리 [신규, 설계자 지시, 2026-09-15]

"fs 서비스에서 ext4와 swapfs를 `minicore/libs/libext4`와
`minicore/libs/libswapfs`로 분리하여 구현하라... FAT32/16도
`minicore/libs/libvfat`으로 분리 구현하라. 이 라이브러리들은 커널과
유저 랜드 양쪽에서 컴파일/참조가 가능해야 한다." - §3.1의 세 드라이버
전부 `fs` 서비스 소스 트리 안에 직접 구현하지 않고, `libelf`/`libcpio`
와 같은 패턴(커널/유저 공용, RM-7C249618)의 독립 라이브러리로 분리한다:

| 라이브러리 | 대상 파일시스템 |
|---|---|
| `minicore/libs/libext4` | ext4 |
| `minicore/libs/libswapfs` | swapfs |
| `minicore/libs/libvfat` | FAT32/16 |

`fs` 서비스(유저랜드)는 이 라이브러리들을 링크해 §3.2
`FileSystemDriver` 구현을 얹는다. **[해결됨, QU-4B1B6DDE 답변,
2026-09-15]** "커널/유저 공용"으로 만드는 이유: "추후에 최적화
옵션을 만들려고" - 지금 당장 커널이 이 파서들을 직접 호출하는 구체적
경로가 있는 건 아니고, 나중에(예: swapfs 핫패스를 IPC 없이 커널에서
직접 처리하는 등) 최적화 옵션을 열어 두기 위한 선제적 조치다. v1
구현 자체는 `libelf`처럼 매크로로 컴파일 모드만 구분해 두면 되고,
실제로 커널 쪽 경로를 쓰는 소비자가 생기기 전까지는 유저랜드 쪽만
실질적으로 쓰인다. RM-7C249618에 세 라이브러리를 "예정"으로 등록해
뒀다.

### 3.2 공통 드라이버 인터페이스 (제안, 2026-09-14 확장)

PnP 제안(SP-9DD4F3EA §3.2)의 `DeviceManager`/드라이버 매칭 패턴과
같은 결로, `fs` 서비스 내부에 드라이버 종류와 무관한 인터페이스를
두는 것을 제안한다. **[확장, 2026-09-14]** 설계자 지시("표준 파일
API들도 모두 설계에 포함시켜")에 따라 open/read/write 세 개뿐이던
초안을 표준 파일 API 전체(SP-2AAD7C8D §9)가 요구하는 수준까지
확장했다:

```cpp
// fs 서비스 내부(유저랜드), 파일시스템 종류와 무관한 공통 인터페이스(가칭)
struct StatBuf {
    uint64_t size;
    bool isDirectory;
    // 생성/수정 시각 등은 각 드라이버 착수 시점에 확장(후속)
};

struct DirEntry {
    char name[kMaxNameLen];
    uint32_t nameLen;
    bool isDirectory;
};

class FileSystemDriver {
public:
    virtual bool mount(BlockDevice* device) = 0;   // AHCI 등에서 넘어온 블록 장치(SP-C2670F69 §3.1의 AhciBlockDevice류)
    virtual OpenResult open(const char* relPath, uint32_t relPathLen, uint32_t flags) = 0;
    virtual void close(FileHandle handle) = 0;
    virtual ReadResult read(FileHandle handle, uint64_t offset, void* buf, uint32_t len) = 0;
    virtual WriteResult write(FileHandle handle, uint64_t offset, const void* buf, uint32_t len) = 0;
    virtual bool stat(const char* relPath, uint32_t relPathLen, StatBuf* out) = 0;
    virtual bool mkdir(const char* relPath, uint32_t relPathLen) = 0;
    virtual bool rmdir(const char* relPath, uint32_t relPathLen) = 0;
    virtual bool unlink(const char* relPath, uint32_t relPathLen) = 0;
    // 디렉터리 열거: open()으로 얻은 디렉터리 핸들에 대해 순차 호출 -
    // 호출마다 다음 엔트리 하나씩(끝나면 false) - 커서는 드라이버가
    // FileHandle에 매달아 관리.
    virtual bool readdir(FileHandle dirHandle, DirEntry* out) = 0;
};

class Ext4Driver : public FileSystemDriver { /* 후속 */ };
class SwapfsDriver : public FileSystemDriver { /* 후속 - §3.3 참고, 디렉터리 개념 자체가 없을 수 있음 */ };
class Fat32Driver : public FileSystemDriver { /* 후속 */ };
```

`read`/`write`가 명시적 `offset`을 받는 것(POSIX의 `pread`/`pwrite`
스타일)은 의도적이다 - "현재 커서 위치"라는 상태는 이 인터페이스가
아니라 **커널의 파일 디스크립터 테이블**(SP-2AAD7C8D §9.2)이 갖는다,
드라이버 자신은 무상태(stateless) 오퍼레이션만 구현하면 된다.

`fs` 서비스는 §2.2의 `Mount` syscall로 커널에 마운트를 등록하면서,
동시에 내부적으로 해당 마운트 경로에 어떤 `FileSystemDriver` 인스턴스
(어떤 블록 장치 + 어떤 포맷)를 연결할지 자신의 설정/슈퍼블록 감지
로직으로 결정한다 - 이 결정 로직은 **§2.5의 `WaitForUserlandReady`
반환 이후에만 시작**해야 한다(설계자 지시) - 구체 판별 절차 자체는
각 드라이버 착수 시점의 후속 설계 과제.

### 3.3 swapfs의 특수성 - 참고만

swapfs는 ext4/FAT32처럼 "디렉터리 트리를 가진 범용 파일시스템"이
아니라 **스왑 슬롯(고정 크기 블록) 배열에 가까운 단순 구조**일 가능성이
높다 - `open`/디렉터리 개념 없이 "슬롯 번호 ↔ 물리 페이지 내용"만
오가는 훨씬 좁은 인터페이스로 충분할 수 있다. `FileSystemDriver`를
그대로 구현하되 대부분의 메서드가 무의미(에러 반환)한 형태가 될지,
아니면 별도의 더 좁은 `SwapBackend` 인터페이스를 따로 둘지는 swapfs
착수 시점에 확정할 열린 질문으로 남긴다(§4 참고).

1. **마운트 테이블 탐색 자료구조**: v1은 선형 배열 + 최장 접두사

## 6. `fs` 서비스 메인 시퀀스 (설계자 지시, 2026-09-16, "FS 서비스 및
devmgr 서비스 설계 착수하라")

SP-9DD4F3EA §6(devmgr 메인 서비스 시퀀스)과 같은 목적/형식 - 위 §§가
각자 다룬 조각(마운트 테이블/livefs/유저랜드 준비 신호/드라이버
우선순위/공통 인터페이스)을 `fs` 프로세스 하나의 실제 시작 시퀀스로
엮는다. 새로운 설계 결정은 없고 기존 설계를 순서대로 나열한다:

1. **스폰**: `kmain.cpp`의 부팅 매니페스트(SP-EAB162FC §2.2 - initrd
   안의 `fs`라는 이름과 정확히 일치하는 실행 파일을 커널이 직접
   스폰, `ProcessRole::KernelService` 부여)로 `init`/`devmgr`과
   별개로 기동된다 - devmgr과 마찬가지로 **PN-D3C05C0B**가 요구하던
   스폰 체계 자체가 이 §2.2다(devmgr만의 전용 경로가 아니라 이름
   목록 전체에 공통 적용).
2. **마운트 지점 사전 등록**: §2.3에 따라 SP-8B6B8D25 §4가 정의한
   자신의 담당 경로들(`/sys/etc`, `/sys/bin`, `/sys/mnt`, `/sys/dev`,
   `/sys/tmp`, `/apps`, `/run`, `/usr/*`, `/home` 등 - `/sys/live`
   제외, 그건 §2.4의 livefs가 커널 자신의 `mountKernel()`로 별도
   등록)를 `Mount` syscall(§2.2)로 순서대로 등록한다 - 이 시점엔
   아직 어떤 드라이버도 연결되지 않은 "빈 마운트 지점" 예약뿐이다.
3. **유저랜드 준비 신호 대기**: §2.5의 `WaitForUserlandReady`를
   호출해 블로킹 - `init`이 `SignalUserlandReady`를 호출(커널 전역
   단 1회)할 때까지 실제 슈퍼블록 감지를 시작하지 않는다(설계자
   지시로 확정된 순서, §2.5/§2.3 참고).
4. **신호 수신 후 블록 장치 발견**: **[정정, 2026-09-16, SP-B071E628
   §5-A/§5-B 재확인]** 한때(2026-09-15~16 사이) 이 단계를 `pubreg`
   `query`(devmgr 드라이버 자식이 미리 `register`해 둔 블록 장치
   tool을 조회)로 갱신했었으나, 그 직후 SP-B071E628 §5-A(설계자
   지시 "커널 서비스들이 pubreg에 뭔가를 등록하지 않아")가 이
   전제(드라이버 자식이 애초에 pubreg에 등록한다는 것) 자체를
   뒤집었다 - **fs가 블록 장치를 찾는 경로는 pubreg와 무관하다**,
   기존 PnP "장치 열거 → IO 권한 요청" 패턴(devmgr의
   `EnumerateDevices`/`RequestIoPermission`, SP-9DD4F3EA §3.1/§6)을
   그대로 쓴다(SP-B071E628 §5-B가 명시 - "devmgr/fs는 둘 다 커널
   서비스라 Tier B로 직접 통신하도록 이미 설계돼 있으므로 pubreg를
   거칠 필요 자체가 없었다"). 예전 안의 커널 syscall
   `QueryInterfaces`는 여전히 폐기 상태 그대로지만, "pubreg query로
   대체"도 마찬가지로 폐기됐다(대체할 것 자체가 없어짐 - fs는 여기서
   pubreg를 아예 모른다). 이 문서의 이 절이 그 반전을 반영하지 못한
   채 남아 있었던 자리다.
5. **슈퍼블록 감지 및 드라이버 연결**: 각 블록 장치 채널에
   `connectChannel()`로 연결한 뒤, §3.1의 우선순위(ext4 → swapfs →
   FAT32/16)로 §3.1a의 라이브러리(`libext4`/`libswapfs`/`libvfat`)를
   차례로 시도해 슈퍼블록을 판별한다 - 판별에 성공한 `FileSystemDriver`
   구현(§3.2)을 해당 블록 장치와 함께 2단계에서 미리 예약해 둔 마운트
   지점 중 알맞은 곳에 연결한다(어떤 블록 장치를 어떤 마운트 지점에
   붙일지 판단하는 구체 규칙은 §4-3에 열린 질문으로 이미 명시돼
   있음 - 이 절은 "언제/어떤 순서로"만 다룬다).
6. **서비스 개시**: 이제 `ResolvePathArgs`(§2.2)/표준 파일 API
   syscall(SP-2AAD7C8D §9)이 이 `fs` 서비스의 마운트들을 실제로
   라우팅하기 시작한다 - 이 시점부터 다른 유저 프로세스의 `Open`/
   `Read`/`Write` 등이 정상 응답을 받는다.

이 시퀀스 자체의 실제 구현은 `fs` 프로세스의 최초 코드(현재
존재하지 않음)가 필요하므로, 착수 시 이 절을 그대로 구현 체크리스트
삼아 새 PN 계획으로 등록한다(CLAUDE.md 규칙 7) - 이 문서는 설계까지만
다룬다.
