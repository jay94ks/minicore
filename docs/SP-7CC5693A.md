# VFS 커널 서브시스템 — 설계 제안

설계자 지시(2026-09-14, 메시지) - "VFS는 커널 영역 서브시스템인데,
이것도 설계하고, 가장 처음 고려해야 할 FS는 ext4, 그 다음은 swapfs,
그 다음은 FAT32/16이야." SP-8B6B8D25 §4(파일 시스템 구조)/§4-A(VFS
루트 소유권과 마운트 포인트 처리 분담)가 이미 정해 둔 큰 원칙 -
"VFS 트리 구조 자체(루트, 경로 해석, 계층)는 **커널**이 소유·관리하고,
각 마운트 지점의 실질적인 파일시스템 처리는 유저랜드의 `fs` 서비스가
맡는다" - 을 실제 커널 서브시스템 설계로 구체화한다. 이 문서는 **모순이
아니라 §4-A의 구체화**다: "VFS가 커널 영역 서브시스템"이라는 이번
지시는 "VFS 트리/경로 해석 자체는 커널 코드"라는 뜻이고, 실제 ext4/
swapfs/FAT32/16 드라이버 자체는 여전히 §2-A 원칙대로 `fs` 서비스
(유저랜드) 안에서 구현된다.

## 1. 배경 - 무엇이 커널이고 무엇이 유저랜드인가 (다시 정리)

| 계층 | 위치 | 역할 |
|---|---|---|
| VFS 트리/경로 해석/마운트 테이블 | **커널** (`minicore/kernel`) | 절대 경로를 받아 "어느 마운트가 담당하는지" 찾아 라우팅만 한다 - 실제 파일 내용은 절대 보지 않는다. |
| 파일시스템 드라이버(ext4/swapfs/FAT32/16) | **`fs` 서비스**(유저랜드, `minicore/fs`) | 블록 장치(AHCI 등)를 실제로 파싱해 파일/디렉터리 읽기/쓰기를 구현한다. |

이미 구현된 선례: `/sys/live/named/`(SP-1FBC0EEB, `NamedObjectTable`,
PL-C8648D4D 완료)가 "진짜 마운트 기반 VFS는 아직 없지만 커널 내부
이름 테이블로 미리 이 원칙을 따른" 사례로 설계자 확인을 받았다
(RM-C65F7760 참고) - 이번 VFS 커널 서브시스템은 그 패턴을 "경로 전체"
로 일반화하는 것이다.

## 2. VFS 커널 서브시스템 설계

### 2.1 자료구조 - 마운트 테이블

커널은 파일 내용이나 디렉터리 엔트리를 전혀 모른다 - 아는 것은
**"이 절대 경로 접두사는 이 fs 서비스 인스턴스가 담당한다"**는
매핑뿐이다:

```cpp
// minicore/kernel, 가칭 - NamedObjectTable(SP-1FBC0EEB)과 같은 층위의
// 커널 내부 테이블. rbtree/해시가 아니라 "마운트 개수가 많지 않다"는
// 전제로 v1은 선형 배열 + 최장 접두사 일치(longest prefix match)로
// 충분하다고 제안(RM-23F4B687 §4 취지 - 실측 후 필요하면 트라이 등으로
// 교체).
struct MountEntry {
    char path[kMaxMountPathLen];  // 예: "/sys/etc" - 정규화된 절대 경로
    uint32_t pathLen;
    uint64_t ownerChannelId;      // 이 마운트를 처리하는 fs 서비스 Channel(PL-C8648D4D)
    bool used = false;
};

class MountTable {
public:
    static bool init();
    // 최장 접두사 일치로 path를 담당하는 마운트를 찾는다. 찾으면
    // ownerChannelId와 "마운트 지점 기준 상대 경로 시작 오프셋"을 낸다.
    static bool resolve(const char* path, uint32_t pathLen,
                         uint64_t* outChannelId, uint32_t* outRelOffset);
    static bool mount(const char* path, uint32_t pathLen, uint64_t channelId);
    static bool unmount(const char* path, uint32_t pathLen);
};
```

### 2.2 Syscall API

```cpp
// fs 서비스 → 커널: 이 fs 서비스 인스턴스가 이 경로 아래를 전담하겠다고
// 등록한다. PnP의 IO 권한 부여(SP-9DD4F3EA §3.3)/DMA 버퍼 관리자
// (SP-39F18E30 §2)와 같은 층위 - SyscallRegistry(PL-21344323)에 등록.
struct MountArgs {
    const char* path;       // in
    uint32_t pathLen;
    uint64_t channelId;     // in: 이 fs 서비스가 미리 만들어 둔 Channel(PL-C8648D4D)
    // out
    ChannelError error;     // AlreadyMounted / InvalidPath(루트 밖 등)
};

struct UnmountArgs {
    const char* path;
    uint32_t pathLen;
    ChannelError error;     // NotMounted
};

// 임의의 프로세스 → 커널: 절대 경로를 담당 fs 서비스의 Channel로
// 라우팅한다. 커널은 "누가 담당인지"만 알려주고, 실제 열기/읽기/쓰기는
// 호출부가 그 Channel로 직접 IPC해야 한다(§4-A "커널은 라우팅 대상으로만
// 안다" 원칙 그대로).
struct ResolvePathArgs {
    const char* path;         // in: 절대 경로
    uint32_t pathLen;
    // out
    ChannelError error;        // NotFound(어느 마운트도 담당 안 함)
    uint64_t ownerChannelId;   // 이 경로를 처리할 fs 서비스의 Channel
    uint32_t relPathOffset;    // path 안에서 마운트 지점 접두사를 뺀 나머지 시작 위치
};
```

`open()`/`stat()` 같은 표준 파일 API는 `libmc`(유저랜드 syscall 래퍼,
PN-16CA347D 로드맵)가 이 `ResolvePathArgs`를 내부적으로 호출한 뒤,
얻은 `ownerChannelId`로 실제 파일 오퍼레이션 메시지를 보내는 2단계
흐름으로 구현되는 것을 제안한다 - 이 2단계 자체를 매번 유저 코드가
직접 하지 않도록 `libmc`가 감싸는 것이 자연스럽다(구체 API는 `libmc`
설계 시점 과제).

### 2.3 부팅 시퀀스와의 관계

`fs` 서비스(devmgr과 마찬가지로 initrd의 정적 프로세스, QU-FF3F0CAA
답변 참고)는 기동 직후 자신이 담당할 마운트(`/sys/etc`, `/sys/bin`
등, SP-8B6B8D25 §4)를 위 `Mount` syscall로 순서대로 등록한다 - 등록
순서/실패 처리(예: 담당 블록 장치가 아직 준비 안 됨)는 `fs` 서비스
자체의 초기화 로직 범위이지 이 커널 서브시스템의 범위가 아니다.

### 2.4 `/sys/live/`와의 관계

`/sys/live/named/`(SP-1FBC0EEB)처럼 **fs 서비스를 거치지 않고 커널이
직접 응답하는 경로**는 이 `MountTable`과 별도의 우선 경로로 유지한다
- `MountTable::resolve()`가 실패하기 전에 먼저 `/sys/live/` 접두사인지
확인해 `NamedObjectTable` 등 커널 자체 서비스로 분기하는 순서를
제안한다(마운트 테이블에 억지로 끼워 넣지 않음 - 이쪽은 애초에 "fs
서비스로 라우팅"이 아니라 "커널이 직접 처리"이므로 성격이 다르다).

## 3. `fs` 서비스 내부 - 파일시스템 드라이버 우선순위와 공통 인터페이스

### 3.1 우선순위 (설계자 확정, 2026-09-14)

1. **ext4** - 이 OS의 주 데이터/루트 파일시스템. 저널링·익스텐트
   기반 블록 매핑·htree 디렉터리 등 실사용에 필요한 현대적 기능을
   갖춘 표준 리눅스 파일시스템이라 최우선으로 지정된 것으로 이해된다.
2. **swapfs** - **이미 설계된 유저 프로세스 폴트 처리 정책이 이것을
   전제로 한다**: `Process::FaultInfo`/QU-0C4D25EF 답변("폴트 정보를
   읽고 그걸 처리해서 프로세스를 죽이거나 swapfs에서 읽어서 페이지를
   갈아 끼워 줘야해")이 이미 "swapfs가 존재한다"고 가정하고 있다 -
   ext4 다음으로 이게 필요한 이유가 이미 코드/설계에 박혀 있다.
3. **FAT32/16** - SP-8B6B8D25 §4의 `/boot/uefi`(ESP, UEFI 부팅 경로용)
   마운트, 그리고 USB/외부 매체와의 상호운용성(대부분 FAT로 포맷되어
   배포됨, AHCI/USB(SP-C2670F69/SP-E35FD36C) 스토리지 드라이버가 실제
   장치를 인식하기 시작하면 자연히 필요) 두 가지 용도로 세 번째.

### 3.2 공통 드라이버 인터페이스 (제안)

PnP 제안(SP-9DD4F3EA §3.2)의 `DeviceManager`/드라이버 매칭 패턴과
같은 결로, `fs` 서비스 내부에 드라이버 종류와 무관한 인터페이스를
두는 것을 제안한다:

```cpp
// fs 서비스 내부(유저랜드), 파일시스템 종류와 무관한 공통 인터페이스(가칭)
class FileSystemDriver {
public:
    virtual bool mount(BlockDevice* device) = 0;   // AHCI 등에서 넘어온 블록 장치(SP-C2670F69 §3.1의 AhciBlockDevice류)
    virtual OpenResult open(const char* relPath, uint32_t relPathLen) = 0;
    virtual ReadResult read(FileHandle handle, uint64_t offset, void* buf, uint32_t len) = 0;
    virtual WriteResult write(FileHandle handle, uint64_t offset, const void* buf, uint32_t len) = 0;
    // 디렉터리 열거, stat 등은 실제 착수 시점에 구체화
};

class Ext4Driver : public FileSystemDriver { /* 후속 */ };
class SwapfsDriver : public FileSystemDriver { /* 후속 - §3.3 참고, 디렉터리 개념 자체가 없을 수 있음 */ };
class Fat32Driver : public FileSystemDriver { /* 후속 */ };
```

`fs` 서비스는 §2.2의 `Mount` syscall로 커널에 마운트를 등록하면서,
동시에 내부적으로 해당 마운트 경로에 어떤 `FileSystemDriver` 인스턴스
(어떤 블록 장치 + 어떤 포맷)를 연결할지 자신의 설정/슈퍼블록 감지
로직으로 결정한다 - 이 결정 로직 자체는 각 드라이버 착수 시점의
후속 설계 과제.

### 3.3 swapfs의 특수성 - 참고만

swapfs는 ext4/FAT32처럼 "디렉터리 트리를 가진 범용 파일시스템"이
아니라 **스왑 슬롯(고정 크기 블록) 배열에 가까운 단순 구조**일 가능성이
높다 - `open`/디렉터리 개념 없이 "슬롯 번호 ↔ 물리 페이지 내용"만
오가는 훨씬 좁은 인터페이스로 충분할 수 있다. `FileSystemDriver`를
그대로 구현하되 대부분의 메서드가 무의미(에러 반환)한 형태가 될지,
아니면 별도의 더 좁은 `SwapBackend` 인터페이스를 따로 둘지는 swapfs
착수 시점에 확정할 열린 질문으로 남긴다(§4 참고).

## 4. 아직 열려 있는 설계 영역

1. **마운트 테이블 탐색 자료구조**: v1은 선형 배열 + 최장 접두사
   일치(§2.1)로 제안 - 마운트 개수가 실제로 많아지면(다중 사용자
   `/usr/*/mnt` 등) 트라이 등으로 교체 검토(실측 후, 별도 DC 불필요).
2. **swapfs의 인터페이스 형태**: `FileSystemDriver`를 그대로 쓸지
   별도 `SwapBackend`로 좁힐지(§3.3) - swapfs 착수 시점에 확정.
3. **각 드라이버의 슈퍼블록 감지/자동 마운트 로직**: `fs` 서비스가
   블록 장치를 보고 "이건 ext4다/FAT32다"를 판별하는 절차 - 각
   드라이버 착수 시점의 구현 세부.
4. **디렉터리 열거/stat 등 나머지 표준 파일 API**: §3.2 인터페이스는
   open/read/write까지만 초안 - 나머지는 실제 드라이버 작업 시작
   시점에 함께 구체화.

## 5. 선행 조건

- Channel IPC(PL-C8648D4D, 이미 구현 완료) - 마운트 등록/경로 라우팅
  응답 전달의 기반.
- Syscall 서브시스템(PL-21344323, 이미 구현 완료) - `Mount`/
  `ResolvePath` syscall 등록.
- 프로세스 모델(PN-16CA347D) - `fs` 서비스 자체가 실행되려면 필요.
- AHCI(SP-C2670F69)/USB(SP-E35FD36C) - ext4/FAT32 드라이버가 실제로
  블록 장치를 얻는 경로.
- `Process::FaultInfo`/QU-0C4D25EF 답변(이미 확정) - swapfs가 실제로
  소비되는 지점(유저 폴트 처리).
