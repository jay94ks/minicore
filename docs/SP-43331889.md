# devmgr/fs 커널 흡수 + 유저모드 드라이버 지원

설계자 확정 답변(`QU-23B339AB`, 2026-09-20, 긴급도 최상):

1. devmgr/fs 둘 다 흡수 대상.
2. 완전 통합 + 유저모드 드라이버 지원 추가.
3. "커널 모드 프로세스로 바뀌는" 것이므로 기존 유저랜드 프로세스
   전제 구현들을 검토.
4. 긴급도 최상.

이 문서는 그 지시를 구체적인 메커니즘으로 옮긴 것 - `DC-91ABD922`가
정리해 둔 파급 범위를 실제 설계로 채운다.

## 1. 핵심 개념 - "커널 모드 프로세스" (KernelThread)

devmgr/fs는 **`Process` 추상화 자체는 그대로 유지**한다(자원그룹
소속/fd 테이블/essential+respawn/프로세스 트리 가시성을 전부 계속
써야 하므로) - 다만 그 프로세스를 실행하는 실행 단위가
`UserThread`(ring3, 별도 `pml4Phys`, ELF 로드)가 아니라 새 클래스
`KernelThread`(ring0, 커널 자신의 주소공간 공유, ELF 로드 없이
C++ 함수 포인터를 직접 entry로 씀)로 바뀐다.

```cpp
// task.h - UserThread와 나란히 신설, UserThread와 완전히 같은
// 상속 패턴(EnableSharedFromThis까지 포함 - process.cpp의 여러
// 헬퍼가 WeakPtr<Task> 별칭을 만들 때 재사용).
class KernelThread : public Task, public EnableSharedFromThis<KernelThread> {
public:
    WeakPtr<Task> weakAsTask() { return WeakPtr<Task>(sharedFromThis(), static_cast<Task*>(this)); }
    WeakPtr<Process> process;  // UserThread::process와 동일한 역할
    // entry는 순수 C++ 함수 포인터 - ELF entryPoint 대신.
    void (*entry)(void*) = nullptr;
    void* entryArg = nullptr;
};
```

`Task`에는 평범한 bool 필드 하나만 추가한다 - `bool isKernelMode
= false;`(`isUserLevel`과 같은 자리/같은 관례 - **가상 함수는 절대
추가하지 않는다, §4의 정정 참고**). `Process`에도 `bool isKernelMode
= false;`를 추가(생성 시점에 고정, `ProcessRole`과 같은 불변 원칙).
`Process::threads`
(`ChunkedList<SharedPtr<UserThread>>`)를 `KernelThread`까지 담을 수
있게 넓히는 대신, v1은 **커널 모드 프로세스는 스레드 1개만 허용**
(devmgr/fs 둘 다 지금도 단일 스레드) - `Process::kernelThread`
(`SharedPtr<KernelThread>`) 별도 필드로 단순하게 간다(기존
`Process::threads`를 건드리지 않아 유저모드 프로세스 코드 경로에
영향 없음).

## 2. 부팅 경로 변경 - `execImage()` 대신 `execKernelEntry()`

`kmain.cpp`의 `kSpawnServiceProcesses()`가 devmgr/fs에 한해 ELF를
initrd에서 찾아 파싱하는 대신, 새 함수를 쓴다:

```cpp
// process.h/.cpp 신설
UserThread* Process::execKernelEntry(void (*entry)(void*), void* arg);
```

- ELF 파싱/`mapRegion()`/유저 스택 준비 전부 생략.
- `pml4Phys`를 커널 자신의 것(`KernelAddressSpaceManager`가 이미
  들고 있는 것)으로 설정 - 새 주소공간을 만들지 않는다.
- `KernelThread::init(entry, arg)`가 `Task::init()`과 동일한
  패턴으로 `TaskTcb`를 준비하되, `cs`/`ss`는 커널 셀렉터, `rflags`는
  IF=1(ring0라 CPL 검사 없음 - iretq 없이 그냥 `ret`/직접 호출로
  재개해도 무방하나, 기존 `kContextSwitch`/`isr_common_epilogue`
  인프라를 그대로 재사용하기 위해 v1은 "합성 iretq to ring0"
  방식을 유지 - `kResumeForkedRing3`가 이미 증명해 둔 프레임 합성
  기법을 CPL=0 버전으로 그대로 재사용).
- `net`/`tty`(아직 미구현)도 이 경로를 쓸 수 있게 `ServiceManifestEntry`
  에 `bool isKernelMode`(또는 진입점 함수 포인터) 필드를 추가해
  일반화한다.

## 3. 내부 syscall 호출 - 트랩 우회, 직접 호출

devmgr/fs 내부 로직(`mc::submit(endpointId, &args)` 호출 수백 곳)은
지금 `int 0x80`/`syscall` 트랩을 거쳐 `SyscallRegistry`→
`AsyncTaskHandler::onExec()`로 간다. 커널 모드 프로세스는 이미
ring0이므로 트랩이 무의미할 뿐 아니라 **불가능**(자기 자신에게
소프트웨어 인터럽트를 걸 이유가 없음) - 대신 같은 효과를 내는
직접 호출 경로를 새로 만든다:

```cpp
// libmc를 그대로 재사용하되(devmgr/fs 소스 코드 자체를 거의 안
// 바꾸는 게 목표), 커널 링크 시점에 트랩 버전 대신 이 버전으로 치환.
namespace mc {
SyscallToken submit(SyscallEndpointId endpointId, void* args) {
    kernel::AsyncTaskSubjectCode subjectCode;
    if (!kernel::SyscallRegistry::resolveSubjectCode(endpointId, &subjectCode)) return 0;
    kernel::AsyncTask* task = kernel::AsyncTask::submit(subjectCode, 0, args, false, true);
    // submitterTask는 현재 실행 중인 KernelThread 자신 - `kProcessFromSubmitter`
    // 류 헬퍼가 이미 WeakPtr<Task>만 보므로 UserThread/KernelThread
    // 구분 없이 그대로 동작(4번 절 참고).
    task->submitterTask = TaskOwnerRef::capture(Scheduler::currentTask()->weakAsTask());
    return static_cast<SyscallToken>(reinterpret_cast<uintptr_t>(task));  // 트랩 없이 직접 포인터를 토큰으로
}
bool wait(SyscallToken token) { /* AsyncTaskAwaiter(...).await() 직접 호출 */ }
}
```

**이렇게 하면 devmgr/fs의 기존 `.cpp` 파일들은 사실상 한 줄도 안
바뀐다** - `#include "libmc/syscall.h"`가 커널 빌드에서는 트랩 버전
대신 이 직접 호출 버전으로 링크될 뿐이다(CMake 타겟 분리 - 유저랜드
`libmc`는 그대로, 커널이 링크하는 `libmc-kernel`을 새로 만들어 같은
헤더에 대해 다른 `.cpp` 구현을 제공). 이것이 3번 절("기존 구현을
검토")의 실제 답 - **대부분의 기존 devmgr/fs 로직 코드는 거의 그대로
재사용 가능**, 바뀌는 건 빌드 방식과 진입점/트랩 계층뿐.

## 4. `kProcessFromSubmitter`류 헬퍼 - 자유 함수로 일반화(가상함수 아님)

**[정정, 2026-09-20, 구현 착수 중 발견]** 최초 초안은 `Task`에
`virtual WeakPtr<Process> ownerProcess()`를 추가하자고 제안했으나,
이건 실제로 컴파일이 되더라도 **`Task::tcb`가 항상 오프셋 0이어야
한다는 불변조건을(문서 주석이 이미 명시 - "context_switch.S의
kContextSwitch/kTaskStartTrampoline이 이 구조체의 tcb 오프셋(항상
첫 필드, 오프셋 0)을 그대로 참조") 깬다** - `Task`에 가상 함수를
하나라도 추가하면 Itanium C++ ABI가 vtable 포인터를 객체 맨 앞
(오프셋 0)에 삽입해 `tcb`를 오프셋 8로 밀어내고, 그 순간
`context_switch.S`/`isr.S`가 절대 주소 0으로 읽던 `tcb`가 전부
깨진다. 이 프로젝트가 `Task`/`ResourceGroup` 등 핫패스 구조체에
`virtual`을 전혀 안 쓰고 `isUserLevel` 같은 평범한 bool 플래그 +
`static_cast`로 다형성을 흉내내 온 것(`kResourceGroupOf()`,
`resource_group.cpp` 등 기존 코드 전역이 이 관례)도 같은 이유다.

**정정된 설계**: `Task`에 가상 함수 대신 `bool isKernelMode = false;`
평범한 필드 하나만 추가(§1의 `KernelThread`가 자신을 만들 때
세팅) - `isUserLevel`과 같은 자리, 같은 관례. `process.h`(또는
`task.h`, 순환 include 없는 쪽)에 자유 함수를 신설:

```cpp
// UserThread/KernelThread 둘 다 이미 전방 선언돼 있는 헤더에 둔다.
SharedPtr<Process> kOwnerProcessOf(Task* task) {
    if (task->isUserLevel) {
        return static_cast<UserThread*>(task)->process.lock();
    }
    if (task->isKernelMode) {
        return static_cast<KernelThread*>(task)->process.lock();
    }
    return SharedPtr<Process>();  // 순수 커널 전용 Task(idle/리액터 등)
}
```

기존 `kProcessFromSubmitter(task)`(vfs_syscall.cpp/pnp.cpp 등 여러
곳에 중복 구현돼 있음) 안의 `static_cast<UserThread*>(submitter.get())
->process.lock()` 한 줄을 전부 `kOwnerProcessOf(submitter.get())`
호출로 교체 - 각 파일의 로컬 헬퍼 정의는 그대로 두고 내부 구현만
위임해도 되고, 아예 공용 함수 하나로 합쳐도 된다(착수 세션 재량).

## 5. 유저모드 드라이버 지원 (신규 능력) - `kSpawnUserModeDriver()`

devmgr(이제 커널 모드)이 실제 하드웨어 드라이버(AHCI 등)를 여전히
**ring3 격리된 프로세스**로 띄우는 새 경로. 기존 `PN-A0F72A3A`의
`mc::fork()` 기반 스폰은 "이미 떠 있는 ring3 프로세스를 복제"하는
연산이라 호출자가 ring0(주소공간 자체가 없음)이면 성립하지 않는다 -
`fork()`를 대체하는 새 커널 내부 API가 필요하다:

```cpp
// process.h/.cpp 신설 - execImage()를 그대로 재사용(ELF 로드/
// 새 주소공간/유저 스택 전부 기존 로직), 다만 호출자가 fork()처럼
// "복제할 부모 주소공간"을 요구하지 않고 그 자리에서 새 Process를
// 만든다(kSpawnInitProcess/kSpawnServiceProcesses가 이미 하는 것과
// 동일한 패턴 - 그 두 함수의 로직을 재사용 가능한 함수로 추출).
SharedPtr<Process> kSpawnUserModeDriver(const elf::Image& image, ResourceGroup* group,
                                          ProcessRole role = ProcessRole::KernelService);
```

devmgr(커널 모드)이 PCI 열거 후 AHCI 매칭 시 이 함수를 직접 호출해
AHCI 드라이버 자식을 ring3 `Process`로 띄운다 - **드라이버 코드
자체(`AhciController`/`AhciPort`류)는 계속 ring3 격리 프로세스 안에
산다**는 것이 이 설계의 핵심 원칙(설계자가 명시적으로 "유저모드
드라이버 지원"을 별도 항목으로 요구한 이유와 부합 - 완전 흡수라도
실제 하드웨어를 직접 건드리는 코드까지 커널 권한으로 끌어올리지
않는다는 하이브리드 커널 철학, `SP-8B6B8D25`의 프로젝트 정체성
자체와도 일치).

## 6. 아직 확정 안 된 것 - `fs`의 AHCI/BlockDevice 소유권 (재확인 필요)

`QU-1FB6A7A4`(2026-09-20 이전 답변)가 "블록 디바이스는 그냥 아예
fs한테 던져버려"라고 확정해, 현재 `AhciBlockDevice`/`AhciController`
(`minicore/fs/ahci.h/.cpp`)가 **`fs` 프로세스 자신의 코드**로
구현돼 있다(devmgr의 별도 드라이버 자식이 아니라). `fs`가 이제
커널 모드가 되면 이 배치가 두 갈래로 갈린다:

- **(a)** `fs`가 커널 모드이니 AHCI 코드도 커널 안으로 함께
  들어온다(주소공간 경계가 사라지므로 자연스러운 결과) - §5의
  "유저모드 드라이버"는 devmgr이 PnP로 매칭하는 *다른* 하드웨어
  (미래의 USB 등)에만 적용.
- **(b)** AHCI도 §5의 유저모드 드라이버 패턴으로 옮겨, `fs`(커널
  모드)가 `kSpawnUserModeDriver()`로 AHCI 자식을 띄우고
  `fs::BlockDevice` 인터페이스로 통신(지금 devmgr↔AHCI자식 관계와
  같은 모양, 다만 부모가 devmgr 대신 fs).

**[확정, 2026-09-20, QU-104C3E97 답변 - "앞으로도 (a)로 진행해"]**
(a)로 확정됐다 - AHCI 코드는 `fs`와 함께 커널로 들어온다. §5의
유저모드 드라이버 지원은 devmgr이 매칭하는 다른(미래) 하드웨어에만
적용된다.

## 7. 단계별 착수 순서 (긴급도 최상 - 착수 세션이 순서대로)

1. `KernelThread` 클래스 신설(§1) + `Task::isKernelMode` 평범한
   bool 필드 + 자유 함수 `kOwnerProcessOf(Task*)`(§4, **가상 함수
   아님** - §4의 정정 참고, `Task::tcb` 오프셋 0 불변조건을 깨지
   않기 위해 최초 초안의 virtual 접근자는 폐기됨) + 기존
   `kProcessFromSubmitter`류 중복 구현을 이 함수 호출로 위임.
2. `Process::execKernelEntry()`(§2) - `kResumeForkedRing3`의 프레임
   합성 기법을 ring0 버전으로 재사용.
3. `libmc-kernel`(§3) - CMake 타겟 분리, 트랩 없는 `mc::submit`/
   `mc::wait`/`waitForMultipleSyscall` 구현.
4. `kSpawnUserModeDriver()`(§5) - `kSpawnInitProcess`/
   `kSpawnServiceProcesses`의 공통 부분을 추출해 재사용.
5. `kmain.cpp`의 `kSpawnServiceProcesses()`를 devmgr/fs에 한해
   `execKernelEntry()` 경로로 전환(`ServiceManifestEntry`에
   `isKernelMode` 플래그 추가).
6. `minicore/devmgr`/`minicore/fs`의 CMake를 "유저랜드 ELF
   타겟"에서 "커널 정적 라이브러리로 컴파일해 `minicore_kernel`에
   링크"로 전환 - 소스 코드 자체(`main.cpp` 등)는 §3 덕분에 거의
   무수정.
7. `PN-A0F72A3A`(devmgr의 AHCI `mc::fork()` 스폰)를
   `kSpawnUserModeDriver()` 호출로 교체.
8. 표준 QEMU 회귀 3종 + 기존 devmgr/fs 기능(EnumerateDevices, VFS
   Open/Read 등) 전부 재검증 - 이 프로젝트 최대 규모 리팩터이니
   특히 꼼꼼히.
