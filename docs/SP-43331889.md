# devmgr/fs 커널 흡수 + 유저모드 드라이버 지원

설계자 확정 답변(`QU-23B339AB`, 2026-09-20, 긴급도 최상):

1. devmgr/fs 둘 다 흡수 대상.
2. 완전 통합 + 유저모드 드라이버 지원 추가.
3. "커널 모드 프로세스로 바뀌는" 것이므로 기존 유저랜드 프로세스
   전제 구현들을 검토.
4. 긴급도 최상.

이 문서는 그 지시를 구체적인 메커니즘으로 옮긴 것 - `DC-91ABD922`가
정리해 둔 파급 범위를 실제 설계로 채운다.

## 1. 핵심 개념 - "커널 모드 프로세스" (KernelThread)

**[재검토, 2026-09-20, 설계자 의견 반영 - "커널 내부에서도 Process
단위로 나눌 필요가 있는가?"]** 최초 초안이 `Process` 유지 근거로 든
네 가지(자원그룹 소속/fd 테이블/essential+respawn/프로세스 트리
가시성)를 다시 따져본다:

- **essential+respawn — 근거가 성립하지 않는다.** 이 시맨틱은 "격리된
  ring3 프로세스가 폴트를 내면 그 프로세스만 죽고 커널이 새 인스턴스로
  재기동"이 전제다. 커널 모드로 흡수되면 devmgr/fs 코드는 ring0에서
  커널 자신의 주소공간을 직접 건드리며 실행되므로, 거기서 나는 폴트는
  격리된 유저 프로세스 폴트가 아니라 **커널 자체의 폴트**(이미 커널
  데이터가 오염됐을 수 있음)다 - "새 인스턴스로 재기동"이 안전을
  보장해주지 못한다. 이 근거는 폐기한다.
- **자원그룹 소속 + 프로세스 트리 가시성 — 여전히 유효할 수 있다.**
  devmgr/fs의 CPU/메모리 사용량을 계속 어떤 단위로든 회계하고 싶다면
  (커널 자신의 idle/리액터 Task처럼 완전히 무회계 상태로 두지 않고),
  그리고 `ps`/procfs에 계속 "프로세스처럼" 보이게 하고 싶다면
  `Process` 껍데기(fd 테이블/essential+respawn은 제외)가 그 역할을
  가장 적은 신규 코드로 해낸다.
- **fd 테이블 — 재검토 필요.** `fs`가 직접 호출 방식(§3)으로
  바뀌면 VFS 연산은 **호출자(원래 syscall을 냈던 유저 프로세스)의**
  fd 테이블을 조작하는 것이지, `fs` 자신의 fd 테이블을 쓰는 게
  아니다 - `fs` 자신이 fd 테이블을 가져야 할 이유가 약해진다.

**[확정, 2026-09-20, QU-ECEE5990 답변]** "(B) devmgr/fs를 idle/리액터
처럼 Process에 전혀 속하지 않는 순수 커널 Task로 완전히 단순화" -
설계자 답변 원문: "devmgr/fs를 Process 없는 순수 커널 Task로 완전히
단순화. ps로 가시될 필요 없는 대상이야." 자원그룹 회계/프로세스 트리
가시성도 함께 포기한다 - `Process` 껍데기 자체를 완전히 없앤다.
이미 발행된 Phase 1 `KernelThread` 클래스(커밋 `973d533`)는 그대로
유효하되(`Task` 파생 클래스일 뿐 `Process`의 존재를 전제하지
않았으므로), 그 위에 얹으려던 `Process::execKernelEntry()`/
`Process::kernelThread`/`Process::isKernelMode`(모두 아직 로컬
미커밋 상태였음)는 이 답변으로 전량 폐기하고, `KernelThread::process`
필드도 함께 제거했다(구현 완료 - 아래 §2 참고).

devmgr/fs는 `UserThread`(ring3, 별도 `pml4Phys`, ELF 로드) 대신
새 클래스 `KernelThread`(ring0, 커널 자신의 주소공간 공유, ELF 로드
없이 C++ 함수 포인터를 직접 entry로 씀)로 실행되되, **어떤 `Process`
에도 속하지 않는다** - idle/리액터 Task와 정확히 같은 지위.

```cpp
// task.h - UserThread와 나란히 신설. Process 링크 없음(2026-09-20
// 확정) - EnableSharedFromThis 상속 패턴만 UserThread와 공유(process.cpp의
// 여러 헬퍼가 WeakPtr<Task> 별칭을 만들 때 재사용하는 것과 같은 이유).
class KernelThread : public Task, public EnableSharedFromThis<KernelThread> {
public:
    WeakPtr<Task> weakAsTask() { return WeakPtr<Task>(sharedFromThis(), static_cast<Task*>(this)); }
    // entry는 순수 C++ 함수 포인터 - ELF entryPoint 대신.
    void (*entry)(void*) = nullptr;
    void* entryArg = nullptr;
};
```

`Task`에는 평범한 bool 필드 하나만 추가한다 - `bool isKernelMode
= false;`(`isUserLevel`과 같은 자리/같은 관례 - **가상 함수는 절대
추가하지 않는다, §4의 정정 참고**. 단순 식별용 플래그일 뿐 `Process`
소유권과는 무관 - 이 클래스는 애초에 소유 Process가 없다).

## 2. 부팅 경로 변경 - `execImage()` 대신 자유 함수 `kSpawnKernelThread()`

**[구현 완료, 2026-09-20, QU-ECEE5990 반영]** 최초 설계
(`Process::execKernelEntry()`)는 devmgr/fs가 `Process`에 속한다는
전제였다 - 확정 답변으로 그 전제가 사라져, 대신 `Process`와 무관한
자유 함수로 만들었다(`task.h`/`task.cpp`에 구현):

```cpp
// task.h/task.cpp - Process 없이 KernelThread를 곧바로 띄운다.
// execImage()와 동일한 관례로 Scheduler::enqueue()는 호출부 책임.
KernelThread* kSpawnKernelThread(void (*entry)(void*), void* arg);
```

- ELF 파싱/`mapRegion()`/유저 스택 준비 전부 생략, `Process` 자체도
  아예 없음.
- `KernelThread::allocate()`로 슬랩에서 확보한 뒤, 상속받은
  `Task::init(entry, arg)`를 그대로 호출 - **새 어셈블리/프레임
  합성 코드 불필요**(아래 참고). `pml4Phys`도 별도로 안 건드린다 -
  `Task::init()`이 이미 커널 자신의 주소공간을 전제로 `TaskTcb`를
  준비하므로(idle/리액터와 동일).
- `kmain.cpp`의 `kSpawnServiceProcesses()`를 devmgr/fs에 한해 이
  경로로 전환하는 작업(§7 5번)은 아직 착수 전 - `net`/`tty`(아직
  미구현)도 함께 쓸 수 있게 `ServiceManifestEntry`에 커널 모드
  플래그를 추가하는 일반화도 그 단계에서 함께 한다.
- **[구현 중 확인, 2026-09-20]** `Task::init(entry, arg)`가 이미
  모든 커널 전용 Task(idle/리액터 등)를 위해 정확히 이 일(cs=0x08/
  ss=0x10/rflags=0x202/rip=kTaskStartTrampoline로 채운 TaskTcb 준비)
  을 하고 있어 그대로 재사용 가능함을 발견했다 - 최초 설계가 가정한
  `kResumeForkedRing3`류 별도 ring0 프레임 합성은 불필요했다.

## 3. 내부 syscall 호출 - 직접 호출로 재작성 (설계자 의견 반영, §3 전면 수정)

**[전면 수정, 2026-09-20, 설계자 의견 3건 반영]** 최초 초안은
"devmgr/fs 소스 코드를 거의 안 바꾸는 것"을 목표로 `libmc-kernel`
셔임(같은 `mc::submit`/`wait` 시그니처를 유지한 채 내부만 트랩 대신
`AsyncTask::submit()` 직접 호출로 치환)을 제안했다 - 설계자가 의견
3건으로 이 방향 자체를 기각했다:

> "커널 내부에선 syscall을 사용하지 말고 직접 호출하도록해"
> "devmgr/fs 소스 코드 자체를 바꿔서 전부 커널에 흡수시켜"

**정정된 방향**: `mc::submit`/`wait`이라는 "syscall 모양"의 API
자체를 유지하지 않는다 - devmgr/fs의 각 호출부(`EnumerateDevices`/
`OpenChannel`/`RequestIoPermission`/`AllocDmaBuffer`/VFS Open·Read·
Write/`ResourceGroupJoin` 등)를 **그 syscall이 실제로 감싸고 있던
커널 내부 로직을 직접 호출하도록 소스 자체를 다시 쓴다**. 지금 각
`AsyncTaskHandler::onExec()`(예: `pnp.cpp`의 `EnumerateDevicesHandler`,
`vfs_syscall.cpp`의 `OpenHandler`)는 "코루틴 안에서 args를 채우고
`co_return`" 모양인데, 이 자체가 **트랩 경계를 넘어온 유저 프로세스가
비동기로 결과를 기다린다는 전제** 위에 설계된 것이다 - 커널 모드
프로세스는 그 전제가 없다(같은 주소공간, 트랩도 없음, 코루틴
서스펜드가 필요한 이유 자체가 사라짐). 따라서:

1. 각 syscall 핸들러의 `onExec()` 본문(args 검증 이후의 실제 로직)을
   **동기 함수로 추출**한다 - 예: `EnumerateDevicesHandler::onExec()`
   본문을 `kernel::pnp::enumerateDevicesSync(startIndex, capacity,
   outDevices, uint32_t* outTotal)`류 평범한 함수로 뽑아, 기존
   핸들러는 그 함수를 호출하고 결과를 `args`에 옮기는 얇은 어댑터로
   남긴다(유저랜드 syscall 경로는 그대로 유지 - 아직 일반 유저
   프로세스도 이 syscall들을 쓰므로).
2. devmgr/fs의 `.cpp` 소스에서 `mc::submit(kSyscallEndpointX, &args)`
   +`mc::wait(token)` 두 줄을, 그 추출된 동기 함수 직접 호출 한 줄로
   **실제로 고쳐 쓴다** - "거의 안 바꾼다"는 목표 자체를 버린다(의견
   1건이 정확히 이걸 요구함). `libmc`/`mc::` 네임스페이스는 커널
   모드 devmgr/fs 코드에서 더 이상 쓰지 않는다 - 유저랜드 전용으로
   남는다.
3. 호출자 신원("어느 Process가 호출했는가")은 **직접 호출이 여전히
   호출자(원래 syscall을 낸 유저 프로세스)의 실행 컨텍스트 위에서
   동기적으로 일어난다는 사실** 그대로 얻는다 - `submitterTask`
   왕복도, `KernelThread` 쪽 특별 처리도 필요 없다. `mc::submit()`
   트랩을 거치지 않게 됐을 뿐 "누가 호출했는가"는 여전히
   `Scheduler::currentTask()`(= 트랩을 낸 그 `UserThread` 자신, 또는
   그 syscall을 대신 실행 중인 리액터 컨텍스트)이므로
   `kOwnerProcessOf(Scheduler::currentTask())`가 그대로 통한다 -
   `isUserLevel` 분기로 정상 해석된다(§1 2026-09-20 확정 - devmgr/fs
   자신은 `Process`가 없으므로, devmgr/fs의 `KernelThread`가 직접
   무언가를 호출하는 경우엔 애초에 "호출한 Process"가 없다는
   뜻이고 `kOwnerProcessOf`도 정확히 빈 값을 반환한다 - 별도 처리
   불필요).

**이것이 3번 절("기존 구현을 검토")의 정정된 실제 답**: devmgr/fs의
`.cpp` 파일들은 **실제로 다시 쓴다** - syscall 모양의 API를 걷어내고
커널 내부 함수를 직접 부르는 코드로 바뀐다. 재사용되는 건 각
핸들러의 **로직 자체**(검증/실행 절차)뿐이고, 그걸 감싸는 외피
(코루틴 args 구조체, `mc::submit`/`wait` 두 줄짜리 왕복)는 커널 모드
경로에서 사라진다. 이 재작성 범위가 커지는 만큼 §7 착수 순서도
"핸들러별로 동기 함수 추출 + devmgr/fs 호출부 재작성"을 명시적
단계로 넣는다(아래 §7 갱신 참고).

## 3-1. [중요, 2026-09-20, §3 실착수 중 발견] 각 syscall 핸들러가 캐스팅 이상으로 `Process`에 실제 자원을 걸어 둔다 - 단순 "호출자 식별" 문제가 아니다

§3/§4는 문제를 "호출자가 어느 Process인지 알아내는 캐스팅"(즉 낡은
`kProcessFromSubmitter(AsyncTask*)`류 함수들을 새 `kOwnerProcessOf
(Task*)`로 교체하는 일)으로만 다뤘다 - devmgr/fs가 실제로 쓰는
6개 syscall(`EnumerateDevices`/`RequestIoPermission`/`OpenChannel`/
`Mount`/`AcceptFromChannel`/`CloseBridge`)의 핸들러 코드를 실제로
읽어보니, 문제는 그보다 근본적이다: **각 핸들러가 `Process` 객체
자체에 실제 자원(핸들 테이블/주소공간/소유권 레코드)을 걸어 둔다** -
`Process` 없는 `KernelThread`(2026-09-20 확정, 위 §1)는 이 자원들을
저장할 곳이 아예 없다. 구체적으로 확인된 것:

- **`RequestIoPermissionHandler`**(pnp.cpp:242) - MMIO 영역을
  `process->addressSpace.mapRegion()`으로 **호출자의 유저 주소공간에**
  매핑한다. `KernelThread`는 별도 주소공간이 없다(커널 자신의
  주소공간을 공유) - 이건 단순히 "다른 곳에 저장"이 아니라 **완전히
  다른 매핑 경로**가 필요하다(예: 커널 자신의 uncached 매핑 헬퍼,
  `KernelAddressSpaceManager` 경유 - physmap은 캐시 가능이라 MMIO엔
  그대로 못 씀). 또한 `kClaimBar(..., const SharedPtr<Process>&
  owner)`(pnp.cpp:161)가 BAR 소유권을 `WeakPtr<Process>`로 기록한다 -
  타입 자체가 `Process` 전용이라 시그니처 변경(`WeakPtr<Task>`로
  넓히기 등)이 필요하다.
- **`OpenChannelHandler`/`AcceptFromChannelHandler`**(channel.cpp) -
  accept 성공 시 `acceptorProcess->openBridges.insert(serverSide)`
  (channel.cpp:604)로 서버측 `BridgePipe` 강한 참조를 호출자
  Process의 핸들 테이블에 넣는다 - **`acceptorProcess`가 비어 있으면
  그 자리에서 그냥 거절한다**(channel.cpp:582, "Process가 없는
  호출자 - 아직 실사용처 없음"이라 적혀 있던 그 경로를 devmgr/fs가
  처음으로 실제로 타게 된다). `Process::openBridges`
  (`ChunkedList<SharedPtr<BridgePipe>, 8>`, process.h:249-250)와
  동등한 자리가 `KernelThread`에도 있어야 한다.
- **`kProcessFromSubmitter`/`kProcessFromSubmitterForPnp`**(channel.cpp:310,
  pnp.cpp:105) - 아직 새 `kOwnerProcessOf(Task*)`로 교체 안 됨(§7
  1번이 "위임" 대상으로 지목했지만 실제로는 미착수) - 게다가 이
  함수들은 `submitter`를 **무조건 `static_cast<UserThread*>`**
  한다(`isUserLevel` 확인 없이) - `KernelThread`가 제출자가 되는
  경로가 생기면(직접 호출 자체는 AsyncTask를 안 거치니 문제없지만,
  이 함수들이 다른 목적으로 여전히 쓰일 수 있음) 잘못된 캐스팅으로
  UB.

**결론**: "핸들러 로직만 재사용, 껍데기만 벗긴다"는 최초 §3
서술은 낙관적이었다 - 실제로는 최소 3개 파일(pnp.cpp/channel.cpp,
아마 dma_buffer.cpp/mount_table.cpp/vfs_syscall.cpp도 같은 패턴일
가능성 높음, 아직 전수 확인 안 함)에 걸쳐 "자원의 소유자가
`Process`뿐이던 것을 `Process` 또는 `KernelThread`(Process 없는

## 3-2. [조사 완료, 2026-09-20, §3+§6 통합 필요성 재확인] "ring0 self-trap으로 §3을 우회" 지름길 검토 - 성립하지 않음(읽기 전용 조사, 코드 변경 없음)

§3-1의 "§3(직접 호출)과 §6(CMake 전환)이 실질적으로 한 덩어리"라는
결론이 너무 비관적인 건 아닌지 검토했다: `mc::submit()`이
`syscall`(SWAPGS 필요)이 아니라 `int $0x80`(userland/libs/libmc/
syscall.cpp:20/42/58/70/85)을 쓴다는 걸 확인했고, x86 보호 모델상
ring0(CPL=0) 코드가 `int 0x80`을 실행하는 것 자체는 항상 허용된다
(더 높은 특권이 더 낮거나 같은 DPL 게이트를 부르는 건 항상 허용) -
SWAPGS는 `syscall_fastpath.cpp`/`syscall_entry.S`(SYSCALL/SYSRET
전용)에만 있고 `int 0x80` 경로엔 아예 없어(isr.S에 swapgs 없음)
그 오염 경로도 없다. 즉 "devmgr/fs를 커널에 링크만 하고(§6), 트랩
메커니즘은 그대로 두면(§3 생략) 더 싸게 갈 수 있지 않을까"라는
가설을 세웠다.

**반증됨**: `Syscall::submit(SyscallEndpointId, void*)`(syscall.cpp:180)
자체가 진입점에서 `auto* self = static_cast<UserThread*>(Scheduler::
currentTask());`로 **무조건** `UserThread*`로 캐스팅하고 바로
`self->pendingSyscalls`(`UserThread` 전용 필드)에 접근한다 - 이
채널/pnp/dma 핸들러들과 완전히 같은 "무조건 UserThread" 가정이
**트랩 진입점 자체**에도 있다. `KernelThread`가 이 경로로 self-trap
하면 이 첫 줄에서 곧바로 잘못된 타입으로 재해석된 메모리를
읽는다(즉시 크래시/오염 가능성) - self-trap 지름길은 이 지점도
결국 고쳐야 해서 직접 호출(§3)보다 더 쌀 게 없다. **결론: §3(트랩을
아예 안 거치는 직접 호출)이 맞는 방향이었다** - self-trap으로
우회할 지름길은 없다. §3-1의 "§3+§6 통합" 결론 유지, 추가 작업
불필요(이 조사 자체가 §7 3+6번 착수 시 다시 검토할 필요를 없앤다).

## 3-3. [설계 명확화, 2026-09-20] devmgr/fs의 유일한 블로킹 syscall(`AcceptFromChannel`)은 직접 호출에서도 `AsyncTask::submit()`을 그대로 쓴다 - 새 대기열 일반화 불필요

devmgr/fs가 쓰는 6개 syscall 중 `AcceptFromChannel`만 진짜로
블로킹한다(연결이 올 때까지 대기) - 나머지(EnumerateDevices/
RequestIoPermission/Mount/OpenChannel/CloseBridge/AllocDmaBuffer)는
전부 즉시 끝나는 단발 호출이라 순수 동기 함수 추출(§3 본문, 이미
2개 완료)로 충분하다. `AcceptFromChannel`은 다르다 -
`AcceptFromChannelHandler::onExec()`(channel.cpp)가
`channel->pendingAccepters`(`AsyncTaskWaitQueue`, `AsyncTask::next`
라는 AsyncTask 전용 침습적 포인터로 구현됨)에 **자기 자신
(AsyncTask*)**을 걸어 두고 기다린다 - 처음엔 이걸 KernelThread
직접 호출용으로 일반화(예: `Task*`도 담는 대기열로 확장)해야
하는 줄 알았으나, 다시 보니 **그럴 필요가 없다**:

- `AsyncTask::submit(subjectCode, manageCode, args, autoFree, preemptive)`
  자체는 UserThread를 전혀 가정하지 않는다(§3-2가 반증한
  `Syscall::submit()`의 문제와 달리, `submitterTask`도 이 함수
  안에서 안 채운다 - 호출부가 별도로 채운다).
- `task->submitterTask = TaskOwnerRef::capture(caller->weakAsTask())`
  - `weakAsTask()`는 `UserThread`/`KernelThread` 둘 다 구현하는
    메서드라 KernelThread 호출자에도 그대로 성립한다.
- 완료 대기는 `AsyncTaskAwaiter`(코루틴 컨텍스트 전용 - "현재
  AsyncTask 컨텍스트 안에서"만 안전, 안 씀)가 아니라
  `AsyncTaskWaitGroup::waitAll()`(async_task.cpp:531-550)을 쓴다 -
  이건 `Scheduler::currentCoreIndex()` + `AsyncReactor::drainOnce()`
  + `Scheduler::yieldCurrent()`뿐인 **평범한 Task 레벨 블로킹**이라
  코루틴이 아닌 일반 함수(devmgr/fs의 KernelThread entry 안)에서도
  그대로 쓸 수 있다(이 프로젝트 자체 메모리 - "TEMP 검증 코드는
  Syscall::submit/wait 대신 AsyncTask::submit+AsyncTaskWaitGroup을
  쓴다"는 이미 확립된 선례와 정확히 같은 패턴).

**따라서 devmgr/fs의 §3 직접 호출부는**: `AcceptFromChannel` 하나만
"`AsyncTask::submit()` 직접 호출 + `submitterTask` 수동 캡처 +
`AsyncTaskWaitGroup::waitAll()`" 패턴을 쓰고, 나머지는 순수 동기
함수 직접 호출 - `AcceptFromChannelHandler::onExec()`/
`pendingAccepters`/`AsyncTaskWaitQueue`는 **전혀 안 건드린다**(이미
검증된 코루틴 로직 그대로 재사용, `kOwnerOpenBridgesOf`/`Channel::
owner`가 §3-1에서 이미 일반화돼 있어 KernelThread 제출자를 정확히
인식한다). 이 패턴은 아직 실제로 시도해 보지 않았다(§3+§6 통합
착수 시 처음 QEMU로 실측) - `AsyncTask::init()` 내부에 UserThread
전용 가정이 더 없는지 정도만 착수 시 한 번 더 확인할 것.

## 4. `kProcessFromSubmitter`류 헬퍼 - 자유 함수로 일반화(가상함수 아님)

**[정정, 2026-09-20, 구현 착수 중 발견]** 최초 초안은 `Task`에
`virtual WeakPtr<Process> ownerProcess()`를 추가하자고 제안했으나,
이건 실제로 컴파일이 되더라도 **`Task::tcb`가 항상 오프셋 0이어야
한다는 불변조건을(문서 주석이 이미 명시 - "context_switch.S의
kContextSwitch/kTaskStartTrampoline이 이 구조체의 tcb 오프셋(항상
첫 필드, 오프셋 0)을 그대로 참조") 깬다** - `Task`에 가상 함수를
하나라도 추가하면 Itanium C++ ABI가 vtable 포인터를 객체 맨 앞
(오프셋 0)에 삽입해 `tcb`를 오프셋 8로 밀어내고, 그 순간
`context_switch.S`/`isr.S`가 절대 주소 0으로 읽던 `tcb`가 전부
깨진다. 이 프로젝트가 `Task`/`ResourceGroup` 등 핫패스 구조체에
`virtual`을 전혀 안 쓰고 `isUserLevel` 같은 평범한 bool 플래그 +
`static_cast`로 다형성을 흉내내 온 것(`kResourceGroupOf()`,
`resource_group.cpp` 등 기존 코드 전역이 이 관례)도 같은 이유다.

**정정된 설계**: `Task`에 가상 함수 대신 `bool isKernelMode = false;`
평범한 필드 하나만 추가(§1의 `KernelThread`가 자신을 만들 때
세팅) - `isUserLevel`과 같은 자리, 같은 관례. `process.h`(또는
`task.h`, 순환 include 없는 쪽)에 자유 함수를 신설:

```cpp
// UserThread/KernelThread 둘 다 이미 전방 선언돼 있는 헤더에 둔다.
// [갱신, 2026-09-20, QU-ECEE5990 - KernelThread는 애초에 Process가
// 없으므로 isKernelMode 분기 자체가 불필요해졌다] 구현 완료.
SharedPtr<Process> kOwnerProcessOf(Task* task) {
    if (!task) {
        return SharedPtr<Process>();
    }
    if (task->isUserLevel) {
        return static_cast<UserThread*>(task)->process.lock();
    }
    return SharedPtr<Process>();  // 순수 커널 전용 Task(idle/리액터/KernelThread 전부)
}
```

기존 `kProcessFromSubmitter(task)`(vfs_syscall.cpp/pnp.cpp 등 여러
곳에 중복 구현돼 있음) 안의 `static_cast<UserThread*>(submitter.get())
->process.lock()` 한 줄을 전부 `kOwnerProcessOf(submitter.get())`
호출로 교체 - 각 파일의 로컬 헬퍼 정의는 그대로 두고 내부 구현만
위임해도 되고, 아예 공용 함수 하나로 합쳐도 된다(착수 세션 재량).

## 5. 유저모드 드라이버 지원 (신규 능력) - `kSpawnUserModeDriver()`

devmgr(이제 커널 모드)이 실제 하드웨어 드라이버(AHCI 등)를 여전히
**ring3 격리된 프로세스**로 띄우는 새 경로. 기존 `PN-A0F72A3A`의
`mc::fork()` 기반 스폰은 "이미 떠 있는 ring3 프로세스를 복제"하는
연산이라 호출자가 ring0(주소공간 자체가 없음)이면 성립하지 않는다 -
`fork()`를 대체하는 새 커널 내부 API가 필요하다:

```cpp
// process.h/.cpp 신설 - execImage()를 그대로 재사용(ELF 로드/
// 새 주소공간/유저 스택 전부 기존 로직), 다만 호출자가 fork()처럼
// "복제할 부모 주소공간"을 요구하지 않고 그 자리에서 새 Process를
// 만든다(kSpawnInitProcess/kSpawnServiceProcesses가 이미 하는 것과
// 동일한 패턴 - 그 두 함수의 로직을 재사용 가능한 함수로 추출).
SharedPtr<Process> kSpawnUserModeDriver(const elf::Image& image, ResourceGroup* group,
                                          ProcessRole role = ProcessRole::KernelService);
```

devmgr(커널 모드)이 PCI 열거 후 AHCI 매칭 시 이 함수를 직접 호출해
AHCI 드라이버 자식을 ring3 `Process`로 띄운다 - **드라이버 코드
자체(`AhciController`/`AhciPort`류)는 계속 ring3 격리 프로세스 안에
산다**는 것이 이 설계의 핵심 원칙(설계자가 명시적으로 "유저모드
드라이버 지원"을 별도 항목으로 요구한 이유와 부합 - 완전 흡수라도
실제 하드웨어를 직접 건드리는 코드까지 커널 권한으로 끌어올리지
않는다는 하이브리드 커널 철학, `SP-8B6B8D25`의 프로젝트 정체성
자체와도 일치).

## 7-1-b. [완료, 2026-09-20, commit 4e78492, 설계자 답변 QU-5FC58B06] fs 완전 전환 - devmgr 파일럿(§7-1-a)을 그대로 확장, AllocDmaBuffer 매핑만 명시적 미룸

fs가 devmgr과 유일하게 다른 점(`AllocDmaBuffer`의 커널 모드 매핑
설계 미정)에 대해 설계자가 직접 "(A) 전체 보류/(B) 부분 전환" 둘
다 아닌 제3의 답을 줬다 - "전부 옮긴 후에 맵핑을 후순위로 미뤄".
그대로 실행: fs 전체(VFS 마운트 라우팅 + AHCI 인식/구동)를
`kFsKernelMain(void*)` KernelThread로 전환하되,
`kAllocDmaBufferSync()`/`kFreeDmaBufferSync()`(dma_buffer.cpp)의
Kernel-Level 분기만 `ChannelError::NotSupported`로 명시적 미구현.

이 전환이 §3-1에서 "구조적으로 정확하나 미검증"으로 남겨 뒀던
`kMapMmioForCaller()`의 Kernel-Level 분기(예약된 스크래치 가상주소
슬롯)를 **처음으로 실제 검증**했다 - AHCI 활성 시나리오에서 실제
PCI 장치의 BAR를 그 경로로 매핑, 크래시 없음.

또한 §3-3이 "아직 실제로 시도해 보지 않았다"고 명시했던
`AcceptFromChannel`의 `AsyncTask::submit()` 직접 호출 패턴도 이
전환이 처음 실행했다 - 구현 중 실제로 위험이 발현됐다: 처음엔
`PreemptionGuard` 없이 작성해 GRUB 시나리오에서 즉시 General
Protection Fault(제출 직후 리액터가 끼어들어 아직 안 채운
`submitterTask`를 역참조)로 크래시했고, `syscall.cpp`의
`Syscall::submit()`이 이미 이 구간을 `PreemptionGuard`로 감싸 두고
있었다는 걸 뒤늦게 발견해 동일하게 감싸자 해결됐다 - 이 패턴을
재사용하는 다음 호출부는 반드시 이 가드를 함께 옮길 것.

Mount는 유저 포인터 검증이 필요 없어(fs의 경로는 컴파일타임 커널
상수) `MountHandler`/`kValidateVfsBuffer()`를 거치지 않고
`MountTable::mount()`를 직접 호출했다 - 그 과정에서 `kValidateVfsBuffer()`
가 `task->submitterTask.lock()`를 무조건 `static_cast<UserThread*>`
하는 미해결 버그(KernelThread 제출자에게 UB)를 발견했으나, fs가
이 경로를 안 타 이번 전환과는 무관 - `PN-A8BE8BED`(후속 계획)로
이관.

검증: WSL 클린 빌드 + 표준 QEMU 회귀 4종(PVH단일코어/GRUB단일코어/
SMP4/AHCI 활성, AHCI는 추가로 3회 반복) 전부 PANIC 없이 정상 종료.
AHCI 실제 식별(IDENTIFY)은 DMA 매핑 미구현으로 계속 실패하지만
크래시 없이 우아하게 넘어간다(설계상 의도된 동작) - VFS 마운트
지점 라우팅 자체는 정상. **devmgr/fs 둘 다 완전히 Process 없는
KernelThread로 전환 완료** - SP-43331889/PN-615C48D5의 핵심 목표
달성, 남은 항목(유저모드 드라이버 지원/AllocDmaBuffer 실제 설계
결정)은 `PN-A8BE8BED`로 분리.

## 7-1. [주의, 2026-09-20, PN-584DB994 조사 중 발견] `kSpawnKernelThread()`로 뜬 KernelThread는 자연 반환 시 미해결 비동기 작업 취소 없이 즉시 퇴역한다

`kTaskOnFallingToEnd()`(scheduler.cpp:2454-2500, `entry()`가 정상
반환했을 때 호출)의 두 분기 중 "Kernel-Level"(`!isUserLevel`) 쪽은
`Scheduler::retireCurrentTask()`를 **직접, 아무 정리 없이** 호출한다
- 반면 "User-Level" 쪽(devmgr/fs 등 현재의 유저랜드 프로세스가 타는
경로)은 자기종료 syscall을 제출해 리액터가 나중에
`Scheduler::cancelPendingSyscalls()`를 거친 뒤에야 실제로 퇴역시킨다
(scheduler.cpp:2476-2495, process.cpp:953 경유). 즉 **지금은
Kernel-Level 분기를 타는 Task가 사실상 idle/리액터뿐이라 문제가
드러나지 않지만**, `kSpawnKernelThread()`로 띄운 `KernelThread`(§2)의
entry 함수가 §3의 직접 호출 방식으로 바뀐 devmgr/fs 로직을 실행하다
자연 반환하면 정확히 이 무방비 경로를 타게 된다 - 그 시점에 이
KernelThread가 제출해 둔 미완료 비동기 작업(있다면)이 계속 그 스택을
참조하는 채로 스택이 즉시 회수되는 위험이 생긴다.

**착수 시 반영할 것**: §2(`kSpawnKernelThread`)나 §7의 devmgr/fs
이관 단계에서, KernelThread의 entry 함수가 자연 반환하기 전에
자신이 제출한 미완료 비동기 작업이 없음을 보장하거나(직접 호출
방식이면 애초에 비동기 제출 자체가 없을 수도 있음 - §3 재작성이
끝나면 이 우려가 자동으로 해소될 가능성도 있음, 재작성 완료 후
재확인 필요), 아니면 `kTaskOnFallingToEnd()`의 Kernel-Level 분기에도
User-Level 분기와 동등한 정리 절차를 추가해야 한다.
