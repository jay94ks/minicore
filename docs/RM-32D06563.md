## 1. 커널 아키텍처 총론

- **하이브리드 커널** — 커널(ring 0)은 최소 책임만, 나머지("커널
  서비스")는 유저랜드에서 구동 (SP-8B6B8D25 §0).
- **"커널이 모든 통제권을 쥔 유저랜드 서비스"** — devmgr/fs/net/tty
  등 "커널 서비스"는 이름과 달리 전부 유저랜드에서 구동되고, 커널은
  권한 부여/라우팅 등 통제권만 쥐는 원칙 (SP-8B6B8D25 §2-A). **[정정,
  2026-09-21]** devmgr/fs는 `DC-91ABD922`/`PN-615C48D5`(completed)로
  이 원칙의 예외로 커널 `KernelThread`에 흡수됐다 - net/tty(아직
  미구현)는 원칙 그대로 유효(SP-8B6B8D25 §2-A 정정 각주 참고).
- **devmgr** — 장치 관리 커널 서비스, 2026-09-21부로 커널
  `KernelThread`(`PN-615C48D5`) - 원래는 유저랜드였음(SP-8B6B8D25,
  DS-D4E5C451, §2-A 정정 각주 참고).
- **[추가, 2026-09-16, 갱신 2026-09-18] `pubreg`** — 5번째 커널
  서비스(유저랜드 구동), 프로세스간 "공개 인터페이스" 홍보/발견
  디렉터리(SP-B071E628, PN-185406F6 - **구현 완료**, commit 974adce).
  **[갱신, 2026-09-18, §6-6 QU-4B38857C 답변]** register/query
  프로토콜은 JSON이 아니라 완전 바이너리 고정 구조체
  (`PubregRegistration` - registryId/protocolCode/implementationId/
  endpoint/featureFlags, `userland/libs/libmc/pubreg.h`)다 - MCP
  스타일 tool 선언(이름/설명/JSON Schema)은 이 등록 체계 위에 얹히는
  "응용 프로그램" 계층의 몫으로 재배치됐다(`pubreg` 자신의 프로토콜
  에는 JSON이 전혀 없음). 소비자는 query 응답의 endpoint(Channel/
  Tcp/Udp 등 discriminated)로 등록자와 직접 연결한다 - `pubreg` 자신은
  신원만 중개, 실제 데이터는 거치지 않음(원칙 그대로 유지).
- **[신규, 2026-09-18] `protocolCode`/`RM-085694F8`** — `pubreg`
  등록의 4바이트 정적 식별 코드, "Minicore Pubreg 프로토콜 할당표"
  (`RM-085694F8`)에서 syscall/signal 번호와 같은 패턴으로 사전
  예약한다(등록 전 코드 예약 필수, CLAUDE.md 규칙 10/13과 동일 절차).
- **[신규, 2026-09-18] `구현체 식별자`(`implementationId`)** — `pubreg`
  등록의 28바이트 opaque 필드, 등록자가 자유롭게 정하는 값(같은
  `protocolCode`를 구현하는 서로 다른 프로세스/버전을 구분하는 용도) -
  `pubreg`는 이 바이트를 해석하지 않고 그대로 보관/반환한다.
- **[정정, 2026-09-15, 설계자 지시 - 폐기, 2026-09-18 갱신]** ~~`libjson`
  이 `pubreg`의 tool 등록/조회 프로토콜에 사용~~ - 위 갱신대로 §6-6
  전환 이후 더 이상 사실이 아니다. `libjson`(`minicore/libs/libjson`,
  커널/유저 공용) 자체는 유효한 범용 라이브러리로 남아 있으나(RM-
  7C249618 참고) 지금은 실사용 소비자가 없다.
- **[추가, 2026-09-16] pubreg 커널 서비스 대행 릴레이** — 커널
  서비스(devmgr/fs/net/tty 및 그 드라이버 자식)는 성능/프로토콜
  유지보수 부담 때문에 `pubreg`에 직접 register/query하지 않는다 -
  유저랜드의 별도 중계 구성요소가 이를 대행해야 한다는 제약(설계자
  지시, 형태는 미정) (SP-B071E628 §5-A). **[정정, 2026-09-16] 이
  릴레이 자체를 minicore가 설계/구현하려던 계획(PN-36E3164D,
  SP-40E5534D)은 설계자 답변(QU-722E72F5)으로 거부됨 - "유저 영역에
  설치될 앱들을 개발하는 제3자가 만들어야 하는 부분"으로 최종
  확정(범위 밖). 이 항목은 "그런 제약이 존재한다"는 사실만 기록하며,
  더 이상 minicore 자신의 미완료 후속 설계 과제가 아니다.**
- **fs 서비스** — 파일시스템 커널 서비스(유저랜드), VFS 마운트 지점의
  실제 처리 담당 (SP-8B6B8D25 §4-A, SP-7CC5693A).
- **RM-23F4B687 §4 원칙** — "명시되지 않은 설계는 임의로 결정하지
  않되, 숫자/전략 튜닝 수준은 구현 중 계측으로 판단 가능" - 이
  프로젝트 전체에서 반복 인용되는 판단 기준 (RM-23F4B687).
- **`SharedPtr<T, Deleter>`/`WeakPtr<T, Deleter>`/`ControlBlock<T,
  Deleter>`/`UniquePtr<T, Deleter>`/`EnableSharedFromThis<T>`**(커널용
  lock-free 공유/약한/배타적 포인터, 신규, 2026-09-16, SP-201238BB) —
  `AsyncTaskWeakRef`(async_task.h/.cpp, PN-D01B7D07)가 이미 증명한
  "대상 수명과 컨트롤 블록 수명을 분리하는" 락프리 패턴을 임의 타입
  `T`로 일반화. `AtomicPtr<T>`(대상)+`AtomicU32`(strong/weak count)
  둘만으로 스핀락 없이 구현 - CAS 기반 `tryAddStrongRef()`로 "0에서
  되살아나지 않음"을 보장. `Deleter`는 템플릿 파라미터로 커스텀
  가능(기본값 `&kDestroyAndFree<T>`). `AsyncTaskWeakRef` 자체를
  이걸로 교체하는 건 범위 밖(동작 중인 코드 리팩터 안 함).
- **`IntrusiveControlBlock<T, Deleter>`/`IntrusiveRefCounted<T,
  Deleter>`/`IntrusiveSharedPtr<T, Deleter>`/`IntrusiveWeakPtr<T,
  Deleter>`**(침습적 참조 카운트 변형, 신규, 2026-09-16, SP-201238BB
  §2-B, 설계자 지시 "ControlBlock<T>의 Intrusive 버전도 고안해봐") —
  위 `SharedPtr`/`ControlBlock`과 달리 참조 카운트를 대상 `T` 자신의
  메모리 안에 내장해 별도 ControlBlock 할당을 없앤다(할당 1회
  절약 + 캐시 지역성). 대가로 `T`가 `IntrusiveRefCounted<T>`를
  상속해야 하고, "논리적 소멸"(strongCount==0)과 "메모리 반납"
  (weakCount==0)을 반드시 분리해야 안전하다(그렇지 않으면
  `WeakPtr::lock()`이 이미 해제된 메모리를 건드림). v1에서 실제
  적용 대상은 아직 미정(설계만 제공).
- **`libkenv/type_traits.h`/`IntegralConstant`/`TrueType`/`FalseType`/
  `IsSame`/`kIsSame`/`IsBaseOf`/`kIsBaseOf`**(신규, 2026-09-16,
  SP-201238BB §2, 설계자 지시 "TypeTraits도 진행해", PN-3F2D88FF) —
  이 프로젝트의 베어메탈 타겟엔 `<type_traits>` 자체가 없다(실측
  확인, `<coroutine>`에 이어 두 번째 사례 - RM-23F4B687 참고)는
  제약 때문에, `kMakeShared`가 쓰던 1회성 `kIsBaseOf` SFINAE 트릭을
  재사용 가능한 정식 라이브러리로 일반화. `std::` 표준 이름을 그대로
  쓰되 전부 자체 구현(오버로드 해석 tie-break 규칙 이용) - 범위는
  지금 필요한 것만, 다른 trait은 실제로 필요해질 때 같은 패턴으로
  추가.
- **`ControlBlockBase`/별칭(aliasing) 생성자**(신규, 2026-09-16,
  SP-201238BB §2 2차 재설계, DC-21647E46 QU-4E449C65, PN-5FC484DF) —
  `SharedPtr`/`WeakPtr`가 "컨테이너의 컨트롤 블록을 공유하면서 그
  컨테이너의 멤버 하나만 가리키는" 핸들을 만들 수 있게 하는 기능
  (표준 `std::shared_ptr` 별칭 생성자와 동일). `ControlBlock<T,
  Deleter>`의 참조 카운팅 부분을 타입 소거된 `ControlBlockBase`로
  분리(가상 함수 대신 함수 포인터 트램폴린)하고, `SharedPtr`/
  `WeakPtr`가 컨트롤 블록과 독립적인 `T* _ptr`을 따로 든다(인스턴스
  크기 8→16바이트). `Task::blockedOn`처럼 임베디드 멤버(`WaitQueue`
  in `Mutex`)를 안전하게 관찰하려는 용도의 첫 실사용처가
  PN-B41D8C0E.
- **`kMakeSharedNew<T>`/`kDestroyCtorAndFree<T>`**(제안 중, 2026-09-17,
  SP-1DB13F61 review, DC-21647E46 QU-1D089097 답변 (A)) — 가상 함수
  (vtable)가 있는 T 전용 `SharedPtr` 팩토리. 기존 `kMakeShared(T*
  preConstructed, ...)`는 "이미 `GenericSlabAllocator::alloc()` +
  `memset(0)` + 명시적 `init()`으로 준비된 포인터"를 전제하는데(실제
  생성자 미실행), 이 관례로는 가상 함수 타입의 vtable 포인터가 0으로
  남아 가상 호출 시 GP fault가 난다(PN-B41D8C0E가 `Mutex`/`Semaphore`
  안에 임베디드된 `WaitQueue::cancel()`에서 실측). `kMakeSharedNew<T>`
  는 `GenericSlabAllocator::alloc(sizeof(T))` 원시 메모리 위에 실제
  placement new(`new (mem) T(args...)`)로 T를 생성해 vtable을 정상
  설치하고, 소멸 시 실제 소멸자(`~T()`)를 호출하는 `kDestroyCtorAndFree
  <T>`를 기본 삭제자로 쓴다 - 기존 `kMakeShared`/`kDestroyAndFree<T>`
  계약(대다수 비-가상 타입)은 전혀 바뀌지 않는다. 승인 대기 중
  (QU-0E745580) - 승인되면 `Mutex`/`Semaphore` 생성 경로가 이걸로
  전환된다.
- **"self-ref 패턴"**(신규, 2026-09-17, PN-B4987BF6, `UserThread`가 첫
  실사용처) — 기존 raw 소유권/명시적 반납 타이밍(`allocate()`/
  `release()`)은 전혀 안 바꾸면서, 그 타입을 `WeakPtr`로 관찰만
  하고 싶을 때 쓰는 opt-in 구성. 대상 타입이 `EnableSharedFromThis
  <T>`를 상속하고, 자기 생성 시점에 `kMakeShared<T>(this, 
  &kNoOpDeleter)`(no-op 삭제자 - 실제 해제는 절대 안 함)로 얻은
  컨트롤 블록을 자기 자신의 private 멤버 `_selfRef`(`SharedPtr<T>`)
  로 곁다리로 붙여 둔다. 기존 반납 지점(`release()`)에선 `_selfRef.
  reset()`(강한 참조 카운트만 0으로 - 메모리엔 손 안 댐) 호출 후
  기존 그대로 `GenericSlabAllocator::free()`로 실제 반납 - 그 순간
  이후 이 타입을 가리키던 모든 `WeakPtr::lock()`이 조용히 실패한다.
  `Task::blockedOn`처럼 "컨테이너의 멤버 하나만" 별칭하는 별칭
  생성자(`ControlBlockBase`)와 달리, 이건 "컨테이너 자기 자신"이
  관찰 대상일 때 쓰는 상호보완 패턴 - `UserThread::weakAsTask()`
  (`WeakPtr<Task>(sharedFromThis(), static_cast<Task*>(this))`)가
  공개 진입점. `EnableSharedFromThis`엔 가상 함수가 없어(shared_ptr.h
  확인) SP-1DB13F61이 다루는 vtable/placement-new 문제와는 무관.
  기존 raw 소유권을 유지해야 하는 다른 타입(대상이 명확히 하나뿐,
  변경 위험을 최소화해야 하는 경우)에 재사용 가능한 일반 패턴.
- **`AsyncTask::submitterTask`**(신규, 2026-09-17, PN-DB5153B6,
  commit 8575506) — `WeakPtr<Task>` 필드. `Syscall::submit()`이
  `Scheduler::currentTask()`로 제출자를 정확히 아는 시점에 자동으로
  채운다(`self->weakAsTask()` - self-ref 패턴 재사용, 신규 코드
  없음) - `onExec()`은 리액터가 나중에 별도 스택에서 실행하므로 그
  안에서 새로 `Scheduler::currentTask()`를 부르면 제출자가 아니라
  그 순간 리액터의 컨텍스트를 얻게 되는 문제를 해결한다(`address_
  space.h`의 `MmapArgs::process`가 예견했으나 실제로 배선된 적
  없던 자리). 비동기로 지연 실행되는 모든 현재/미래 syscall
  핸들러가 `task->submitterTask.lock()`으로 제출자 `Task`(필요시
  `UserThread`/`Process`까지 체이닝)를 얻는 공용 진입점 - 첫
  실사용처는 PN-9CC66142(BridgePipe).
- **`Process::openBridges`/`kResolveOwnedBridge`**(신규, 2026-09-17,
  PN-9CC66142, commit d7c2df4) — `BridgePipe`(Channel IPC 엔드포인트)
  소유권을 `Process::children`과 동일한 패턴(`ChunkedList<SharedPtr
  <BridgePipe>, 8>`)으로 관리하는 첫 "이용자 객체가 자원을 강하게
  소유" 사례(DC-21647E46 QU-16C8C038 방향). `ChannelReadHandler`/
  `WriteHandler`/`CloseBridgeHandler`는 유저가 넘긴 핸들 값을 더
  이상 검증 없이 `reinterpret_cast`하지 않고, `kResolveOwnedBridge
  (task, handle)`로 제출자 Process의 `openBridges`에서 실제로 찾은
  것만 쓴다 - 위조된(자기 소유가 아닌) 핸들은 `InvalidHandle`로
  거부됨을 실측 확인. 향후 fd 테이블류 자원(§9 표준 파일 API 등)에
  재사용 가능한 선례.
- **세대 태그 슬롯 테이블(generation-tagged slot table) 패턴** —
  유저 syscall이 넘긴 정수 핸들을 `reinterpret_cast`로 직접
  포인터로 캐스팅하던 관례(과거 `ChannelId`/`SpawnProcessArgs::pid`)
  가 임의 포인터 역참조 보안 취약점으로 이어져(§4 참고) 도입한
  공용 해법 - `{ T* ptr; uint32_t generation; }` 슬롯 배열을 두고,
  핸들 값 자체를 `(generation << 32) | index`로 인코딩한다. 조회는
  인덱스 범위 확인 + generation 일치 확인만으로 끝나
  `reinterpret_cast`를 한 번도 쓰지 않는다 - 위조/재사용된 값은
  전부 안전하게 "못 찾음"으로 실패한다(ABA 방지). 첫 적용:
  **`kResolveChannelId()`/`kAllocateChannelId()`/`kFreeChannelId()`**
  (신규, 2026-09-17, PN-CE6A04AB, commit 74f0f75, `channel.cpp`) -
  `gChannelTable[65536]`, `Channel`이 `SharedPtr`이 아니라 슬랩
  할당이라 `WeakPtr::lock()` 생존 판정 대신 슬롯의 `ptr==nullptr`
  로 수동 판정. 같은 패턴을 `ProcessId`에도 적용하는 설계가
  `SP-9CB55C5B`로 확정돼 있고, **[구현 완료, 2026-09-17, PN-C39882D0,
  commit ba7e4f5]** `kAllocateProcessId()`/`kResolveProcessId()`/
  `kFreeProcessId()`(process.cpp 익명 네임스페이스, `Process`는
  `WeakPtr<Process>::lock()`으로 생존 판정 - `Channel*==nullptr` 대신) -
  `SpawnProcess`/`Wait`의 `pid` 필드만 이 인코딩으로 마이그레이션됐다
  (값 형식 변경, 스코프는 그대로 "직계 자식만"). `kResolveProcessId()`
  자신은 아직 아무 데도 연결 안 됨(`[[maybe_unused]]`) - `Kill`의
  임의 대상 확장이 첫 실사용처(`PN-88E62419`, 완료 - 아래
  `Uid`/`Gid`/`Permission` 참고).
- **`Uid`/`Gid`/`Permission`/`kCheckPermission()`**(신규, 2026-09-18,
  `SP-30FCC8AE` §1/§2/§3, `PN-617F4E52`/`PN-88E62419`,
  `minicore/libs/libkenv/permission.h`) - Linux 유사 사용자/권한
  체계. `Uid`/`Gid`는 단순 `uint32_t`(root=0=`kRootUid`/`kRootGid`),
  `Permission`은 POSIX `mode_t` 하위 9비트(rwxrwxrwx, `kPermOwner*`/
  `kPermGroup*`/`kPermOther*`) + 특수 비트 S(`kPermSpecialS`, 의미
  미정 - §7 sudo/su 후속). `Process::uid/gid`는 SpawnProcess/fork()
  시 부모로부터 상속되며(승격 경로인 `kSetuid()`는 아직 없음, §1-A/
  `PN-B6DB692C` 후속), 최초 프로세스는 root로 시작한다.
  `kCheckPermission(callerUid, callerGid, resourceUid, resourceGid,
  mode, requested)`는 root 특권 + owner/group/other RWX 3분기만
  판정하는 범용 함수(커널/`ProcessRole::KernelService` 예외와
  조상-자손 관계 예외는 Process 트리 지식이 필요해 이 함수 밖,
  자원별 소비자가 담당) - `Kill`의 `kCanSendSignal()`(process.cpp,
  `Process::signalPermission` 소비)이 첫 실사용처.
- **`DontDeref<T>`**(신규, 2026-09-17, `SP-CA3C3E57` §6-A, 설계자
  의견, `libkenv/shared_ptr.h`) — "신원 비교만 하고 절대 역참조하면
  안 되는" 포인터를 위한 값 래퍼. `operator==`/`!=`/`bool`만
  제공하고 `operator*`/`->`/`T*` 변환이 전부 없어 역참조 실수가
  타입 시스템(컴파일 에러)으로 막힌다. `SharedPtr`/`WeakPtr`와
  달리 ref-counting이 전혀 없는 순수 값 타입이라 placement new
  없이 raw 슬랩 메모리 위에 대입해도 안전하다(`WeakPtr::operator=`
  가 대입 전 기존 값을 정리하려다 쓰레기 포인터를 역참조하는
  문제가 원천적으로 없음). 첫 적용: `Channel::ownerProcess`
  (`PN-18FDBFF3`, commit f454faf) - 호출자가 채널 생성자와 같은
  프로세스인지만 비교, 절대 `Process` 멤버에 접근하지 않음.
- **`ObserverPtr<T>`**(신규, 2026-09-18, `SP-CA3C3E57` §6-A.2,
  설계자 의견 "의미론적 템플릿들을 추가 설계하자", `PN-A4169F97`,
  `libkenv/shared_ptr.h`) — `DontDeref<T>`(신원 비교 전용)의
  바로 옆자리로, **비소유지만 역참조는 필요한** 포인터를 위한
  값 래퍼. `operator*`/`->`/`bool`/`get()`/`==`/`!=`를 제공 -
  `DontDeref<T>`와의 차이는 딱 역참조 연산자 유무 하나뿐이다.
  이 포인터의 생존은 이 타입 자신이 전혀 보장하지 않는다 -
  호출부가 더 오래 사는 무언가(`SharedPtr`/스택 변수 등)로 보장해야
  한다는 계약을 타입으로만 드러낸다(대상이 죽을 수 있어 매번 생존을
  확인해야 하면 이 타입이 아니라 기존 `WeakPtr<T>::lock()`을 쓴다 -
  `RM-23F4B687` §9 포인터 선택 관례 참고). `DontDeref<T>`와 마찬가지로
  ref-counting이 전혀 없는 순수 값 타입이라 placement new 없이 raw
  슬랩 메모리 위에 대입해도 안전하다. **기존 코드 일괄 교체는
  하지 않는다**(`RM-23F4B687` §4 - 회귀 위험 대비 이득이 낮음) -
  새로 작성되는 코드부터 이 관례를 따른다, 아직 실사용처 없음.
- **`Task::numaNode`**(신규, 2026-09-17, PN-A74871F2) — Task가
  생성된 코어의 NUMA 노드를 `Acpi::cpuNumaNode()`로 조회해 기록해
  두는 필드. `PL-2D3184BC`(스케줄러 설계)가 애초에 PCB 필드 목록에
  명시했으나 실제 코드에 반영된 적이 없던 갭을 메운다(설계자 지시로
  전수 조사 중 발견). **[확정, QU-759C9C1C]** Push/Pull 로드밸런싱
  (SP-9525C4C0 §2.3)이 코어 이관 시 이 필드로 같은 NUMA 노드를
  우선한다 - 순수 진단용이 아니라 실제 스케줄링 정책 입력값. 소비
  로직은 **PN-9DDFB774**로 별도 추적(PN-A74871F2 완료가 착수 조건).
- **NMI 워치독 / 디버그 강제 정지(stop-the-world) IPI**(신규,
  2026-09-16, 설계) — NMI(마스크 불가)를 이용한 두 코어 간 통지
  메커니즘: 발신자가 코어별 `gNmiReason[]`(`DebugHalt`/
  `WatchdogTrap`)을 세팅한 뒤 `Lapic::sendNmiIpi()`로 발사, 수신측
  NMI ISR이 그 사유로 분기(SP-677210E6). 워치독은 스케줄러 틱

  `kPanic`의 두 진입점이 첫 줄에서 나머지 온라인 코어 전부에 발사
  (지금은 패닉 코어만 멈추고 나머지는 계속 실행되던 공백을 메움 -
  실측 확인). 계획: PN-F443FE73.
- **[신규, 2026-09-22] `init`의 유저랜드 초기화 = "systemd 포팅"** —
  `SP-8B6B8D25`가 원래 열어 뒀던 "init이 설정 파일 기반으로 유저랜드
  서비스를 스폰"하는 부분(`PN-A60AC09F` 항목2)을, 커스텀 설정 포맷을

  보류) 구체적 범위/이식 전략(POSIX/Linux 호환 표면, glibc/musl,

## 2. 프로세스/스레드/스케줄링

- **`Task`** — 스케줄링 최소 단위(코드명 `kernel::Task`) - 프로세스는
  주소공간+자원의 소유자, Task는 실제 실행 흐름으로 분리 (PL-2D3184BC).
- **`Process`** — 유저 프로세스의 커널 쪽 표현(주소공간 PML4 소유자,
  `mainThread`, `FaultInfo lastFault`) (SP-68182FBD).
- **`UserThread`** — Task를 상속하는 유저 스레드(PCB 개념과 별개로
  "커널 Task ≠ 유저 스레드" 구분 확정) (SP-04EE2A18, 설계자 지시
  2026-09-14).
- **`KernelThread`** — devmgr/fs 등 "커널 모드 Task"의 실행 단위 -
  `UserThread`와 동일한 상속 패턴(`Task`+`EnableSharedFromThis`)이나
  ring0/커널 주소공간 공유, ELF 로드 없이 C++ 함수 포인터를 entry로
  씀(`Task::isKernelMode` 플래그로 구분 - `isUserLevel`과 같은
  평범한 bool 플래그 관례, `Task`에 가상 함수를 추가하면 `tcb`의
  오프셋 0 불변조건이 깨지므로 절대 안 씀). **[확정, 2026-09-20,
  QU-ECEE5990 답변]** 어떤 `Process`에도 속하지 않는다(idle/리액터
  Task와 동일한 지위 - "ps로 가시될 필요 없는 대상"이라는 설계자
  의견) - 자유 함수 `kSpawnKernelThread(entry, arg)`(task.h/.cpp)로
  Process 없이 곧바로 띄운다 (SP-43331889, DC-91ABD922/QU-23B339AB/
  QU-ECEE5990).
- **`kOwnerProcessOf(Task*)`** — Task를 소유한 `Process`를 묻는
  헬퍼(process.h) - `isUserLevel`이면 `UserThread::process`를,
  아니면(idle/리액터/`KernelThread` 전부 - `KernelThread`는 애초에
  `Process` 소속이 없다, 2026-09-20 QU-ECEE5990 확정) 빈 값을
  반환한다 (SP-43331889 §4).
- **`TaskState`**(`Ready`/`Running`/`Blocked`/`Zombie`) — 새 상태를
  추가하지 않고 재사용하는 원칙(유저 폴트/뮤텍스 대기 등 전부
  `Blocked` 하나로 표현) (PL-2D3184BC, QU-0C4D25EF).
- **`inRunQueue`** — 이중 스케줄링 경쟁 조건의 구조적 방지책(Task가
  이미 큐에 있는지 별도 플래그로 추적, `state`로는 판별 불가)
  (PL-2D3184BC, PL-C8648D4D에서 실측 발견).
- **`PreemptionGuard`** — 선점 비활성화 RAII, 코어별 카운터 기반
  (SP-D7013B26 §2.1, PL-2D3184BC 8단계).
- **`Scheduler::parkCurrent()`/`scheduleImmediate()`** — 범용 블로킹/
  즉시 재개 프리미티브 - Mutex/Semaphore/AsyncReactor/유저 폴트 재개
  전부가 공유하는 기반 (PL-2D3184BC, SP-F682B889, SP-0666DB3C).
- **즉시 스케줄링 큐(Immediate Queue)** — RT 클래스보다도 먼저
  실행되는 최상위 큐, 비동기 프레임워크 완료 통지 전용
  (PL-2D3184BC 8-1단계, SP-F682B889).
- **Task 종료 프로토콜** — `isUserLevel` 플래그로 자기종료 syscall
  제출(유저 레벨) vs `retireCurrentTask()`(커널 레벨, Zombie 표시 +
  지연 스택 회수)로 분기 (PL-2D3184BC, QU-26F9420E).
- **Push/Pull 로드밸런싱** — 코어 간 작업 이관(Pull=유휴 시 당겨옴,
  Push=90% 임계 시 밀어냄), CPU affinity 걸린 Task는 완전 제외
  (DS-D4E5C451, PL-2D3184BC §9, 아직 미구현 - PN-7679813D).
- **유저 페이지 폴트 재개 정책** — 폴트를 "또 하나의 대기 중인
  syscall 토큰"으로 모델링해 `pendingSyscalls`가 비어야 재개(공통
  리스트 방식) (SP-8B6B8D25 §2-B, SP-68182FBD §2.3, SP-0666DB3C §7).
- **`ThreadLocal<T>`/`TlsRegistry`** — [갱신, 2026-09-18, PN-22E5E9E7
  항목2/3] 예전엔 `Task`/`UserThread`에 내장된 고정 슬롯 배열
  (`tlsSlots`) 기반 명시적(explicit) TLS로 `get()`/`set()` 호출을
  흉내냈으나, 이제 진짜 컴파일러 `thread_local`(`tls.cpp`의
  `gTlsSlots`, FS_BASE 스왑 + `.tdata`/`.tbss`)로 교체됐다 - API
  시그니처는 그대로라 호출부 무수정. `AsyncTask`는 여전히 대상 밖(별개
  구조체) (`SP-F146B7F8` §1, 설계자 지시 2026-09-14 - 원래
  SP-0666DB3C §11이었으나 2026-09-17 별도 문서로 분리됨).
- **`Task::kernelFsBase`/`kMakeTaskTlsBlock()`/self-pointer TCB
  헤더** — [신규, 2026-09-18, PN-22E5E9E7 항목2] `Task::init()`이
  링커 경계 심볼(`kTlsTemplateStart`/`kTlsTemplateTdataEnd`/
  `kTlsTemplateEnd`)로 `.tdata`/`.tbss` 템플릿을 Slab에서 복사해 만드는
  Task 전용 TCB. x86_64 variant II 레이아웃 - 템플릿 복사본 바로 뒤에
  8바이트 self-pointer 헤더(`*(uint64_t*)fsBase == fsBase`)가 필수다 -
  `-ftls-model=local-exec`라도 extern thread_local(다른 TU에서 접근,
  예: `gTlsSlots`)에는 Itanium C++ ABI가 강제하는 TLS 래퍼 함수
  (`_ZTW...`)가 모델과 무관하게 항상 FS:0을 self-pointer로 역참조하기
  때문(QEMU 실측으로 발견, task.cpp 문서 주석 참고) - 유저랜드 PT_TLS
  인스턴스(항목6)도 같은 함정에 주의.
- **`elf::kSegmentTypeTls`/`Process::tlsTemplate*`** — [신규, 2026-09-18,
  PN-22E5E9E7 항목5] `PT_TLS`(=7) 세그먼트 타입 상수(elf.h)와
  `Process::execImage()`가 그 세그먼트의 vaddr/filesz/memsz/align을
  저장하는 필드(process.h) - 순수 파싱/저장만, 실제 UserThread별
  인스턴스 생성/FS_BASE 스왑은 항목6/7. 유저랜드 링커 스크립트
  (`userland/cmake/linker-userland-x86_64.ld`)에도 커널과 같은

  lld가 완전히 드롭해 그 `ALIGN(4K)`가 무효화되지만 `.tdata`/`.tbss`는
  경계 심볼 대입 때문에 내용이 비어도 항상 실체화된다는 함정을 실측
  발견 - `.tdata`를 `ALIGN(8)`이 아니라 `ALIGN(4K)`로 둬야 `:udata`
  세그먼트가 항상 새 페이지에서 시작해 `Process::execImage()`의
  세그먼트 오버랩 거부(`registerFixedRegion` 실패)를 피한다.
- **`UserThread::userFsBase`/`Process::makeUserTlsInstance()`** —
  [신규, 2026-09-18, PN-22E5E9E7 항목6] `Task::kernelFsBase`/
  `kMakeTaskTlsBlock()`(위 항목)의 유저랜드 대응 - 템플릿이 있으면

  ("설계 공백을 감당할 수 없을 거야, 채워나가자")에 따른 의도적 v1
  축소.

- **`Scheduler::enterIdleLoop()`/`gIdleStack`**(신규, 2026-09-17,
  PN-2008220B) — 코어당 전용 idle 컨텍스트 스택(정적 배열, 커널
  이미지/BSS - higher-half 공유라 모든 프로세스 PML4에서 항상
  유효). `kMain()`/`kApMain()`이 `Scheduler::runLoop()`을 직접 부르는
  대신 이 함수를 불러, 부팅 극초반의 위험한 저지대 identity map
  스택에서 이 안전한 스택으로 코어당 딱 한 번 옮겨 앉은 뒤
  `runLoop()`을 시작한다 - `Task::init()`의 "가짜 kContextSwitch
  프레임 위장" 기법을 재사용(`kIdleLoopTrampoline`, context_switch.S)
  하되 CR3 동기화는 하지 않고 RFLAGS도 고정값 대신 호출 시점 값을
  그대로 캡처해 넘긴다. `AsyncReactor::drainOnce()`의
  `coroHandle.resume()`(코루틴 재개, 스택 전환 없음)이 이 스택 위에서
  직접 실행되므로, 이 스택이 항상 안전해야 한다는 게 도입 이유.

- **`Task::weight`/`vruntime`/`cpuTicksUsed`, `kEffectiveWeightOf()`,
  `kVruntimeScale`, `NormalQueue`, `SetTaskWeight`**(신규, 2026-09-17,
  SP-B26CDBDD, PN-158B6B2F) — CFS류 상대 가중치 스케줄링. `weight`는
  유저가 보는 표면값([-100,100], 기본 0, `SetTaskWeight` syscall로
  설정), `kEffectiveWeightOf(weight)`(=clamp(100+weight,1,200))가
  vruntime 나눗셈에 쓸 항상-양수 실효 가중치로 변환한다. `vruntime`은
  "실효 가중치로 나눈 누적 실행 시간"(작을수록 우선 선택) - 매 틱
  `vruntime += (100 * kVruntimeScale) / kEffectiveWeightOf(weight)`로
  갱신하는데, `kVruntimeScale=1024`(고정소수점 배율)가 없으면 실효
  가중치가 100보다 큰(=weight>0인) 모든 경우에 정수 나눗셈이 0으로
  버려져 그 Task가 무한정 우선 실행되는 실질적 버그가 됐다(QU-DA6C52BA
  가 지적한 "수학적 동치값" 트릭으로 해소). `NormalQueue`(scheduler.cpp)
  는 `gNormalQueues`(코어별 Normal 클래스 Ready 큐)의 실제 타입 -
  `libkcont::OrderedList<Task,TaskVruntimeTraits>`(vruntime 오름차순)
  위에 기존 `TaskQueue`가 갖던 자체 `Spinlock`(Pull이 다른 코어의 이
  큐를 직접 훔쳐가므로 필요)과 `approxLength()` 근사 카운터를 그대로
  얹은 래퍼 - **정적 배열로 선언되므로 `Scheduler::init()`이 명시적으로
  `.init()`을 불러야 한다(컴파일러의 self-참조 sentinel 정적 초기화
  추론에 기대면 안 됨 - x86_64-elf-gcc 툴체인 전환 중 clang/GCC 차이로
  실측 발견, PN-22E5E9E7 참고)**. `TaskClass::Normal`+`isUserLevel`인
  Task에만 적용(RT/Immediate/커널 전용 Task는 무관).

- **`TaskTcb`(신규, 2026-09-20, PN-81E49523/QU-47A83CDF, commit
  fe151d0/83ca743) — "스레드의 최종 캡쳐 레지스터 상태"를 가리키는
  단일 소스** — `using TaskTcb = InterruptFrame;`(interrupt_frame.h,
  순수 별칭, 새 필드 없음). `Task::tcb`/`AsyncTask::tcb`가
  `TaskTcb*`(Slab에 독립·영속 할당, 커널 스택과 별개 수명)로
  존재하며, 레지스터/실행위치를 바꾸는 모든 동작(디버거 SetRegisters
  포함)은 이 하나의 캡쳐본을 대상으로 이뤄진다(설계자 답변:
  "인터럽트에서 인터럽트 지점으로 뭘 보내고 자시고 할 필요 자체가
  없는 동작이야"). `Scheduler::parkFromISR(Task*, InterruptFrame*)`
  (commit cfa05f9, PN-EA968DF0) — ISR 컨텍스트 전용 파킹 원시함수,
  하드웨어가 이미 만들어 둔 `InterruptFrame*`을 `kContextSwitchFromISR`
  로 곧장 `caller->tcb`에 복사해 넣고 `[[noreturn]]`으로 반환하지
  않는다(협조적 전환용 `Scheduler::parkCurrent()`와 대칭 - 콜스택을
  직접 캡처하는 대신 이미 있는 프레임을 재사용). 이 도입으로
  `gDebugParkedOnCore`/NMI `ClearDebugRegs` 방송(IST4 재진입 완화책)
  전체가 제거됐다.
  **주의 - 이름 충돌**: 위 "`Task::kernelFsBase`/`kMakeTaskTlsBlock()`/
  self-pointer TCB 헤더" 항목의 "TCB"는 **완전히 다른 개념**(TLS
  x86_64 variant II self-pointer 블록)이다 - 코드/문서 어디서도 그
  항목을 `TaskTcb`라는 타입명으로 부르지 않지만, 사람이 "TCB"라고
  줄여 말할 때 두 개념이 혼동될 수 있으니 언급 시 항상 정식 명칭
  (`TaskTcb`/`InterruptFrame` vs TLS self-pointer 헤더)으로 구분한다.

## 3. 메모리 관리

- **Direct Map**(`kDirectMapBase = 0xFFFF800000000000`) — 전체 물리
  메모리를 미리 매핑해 둔 higher-half 영역, canonical 경계와 정확히
  일치 (Paging 설계, SP-68182FBD).
- **`PageFrameAllocator`** — 물리 페이지 버디 할당자, NUMA 노드별
  분리, order 기반(`allocOrder`/`allocOrderOnNode`) (DS-D4E5C451,
  PL-99562483).
- **`PageFrame`** — 물리 프레임 하나당 하나씩 존재하는 메타데이터
  구조체(refCount/flags/lastCacheType) - Linux `struct page`에 대응,
  `PageFrameAllocator`가 direct map 크기만큼 bump 예약한 배열로 보관
  (SP-6CEFBE9B, 기존 COW 참조 카운트 배열 SP-6BEAE0C1 §11-3을 일반화).
- **`ThreadId`** — 한 `Process` 안에서만 유일한 스레드 식별자(전역
  `ProcessId`와 다른 네임스케일) - `Process::mainThread` 단일 필드를
  `threads`(ChunkedList) 목록으로 일반화하며 신설(SP-76250478,
  멀티스레드 유저 프로세스 지원). `CreateThread`/`Join`/`Detach`
  syscall(RM-48E1E610 그룹0 6/7/8번)이 이 식별자를 주고받는다.
- **`GenericSlabAllocator`/`SlabCache`** — 코어별 더블 매거진(loaded/
  previous) + 전역 디포 기반 slab 할당자, 7단계 고정 버킷(32~2048B)
  (SP-D7013B26, PL-16E2CDA4).
- **128TiB 유저 주소공간** — 4레벨 페이징 canonical 하위 절반의
  수학적 상한(256TiB는 오기였음) (SP-8B6B8D25 §5, QU-72108298).
- **유저 주소공간 레이아웃(§5-A)** — 코드 0x400000부터, 스택은 유저
  공간 끝점에서 하향, 코드/스택 양쪽 가드 페이지 필수, ELF 로더는
  항상 ELF 자신의 `p_vaddr`/`e_entry`를 우선(0x400000은 툴체인 관례일
  뿐) (SP-8B6B8D25 §5-A, QU-7043EA6D).
- **`Paging::createAddressSpace()`** — PML4 인덱스 256-511(higher
  half)만 엔트리째 복사해 새 주소공간 생성 - 모든 프로세스가 커널
  영역을 물리적으로 공유 (SP-68182FBD §1.1).
- **`ProcessAddressSpaceManager`/`KernelAddressSpaceManager`** —
  가상주소 관리를 프로세스별 파트(Maple Tree 1개, 프로세스별 락)와
  커널 영역 전용 파트(Maple Tree 1개, 전역 락 - SMP 전체가 공유해
  보므로)로 분리 (SP-2AAD7C8D §1/§2, 설계자 지시).
- **Maple Tree**(`MapleDenseNode`/`MapleLeaf64Node`/`MapleRange64Node`/
  `MapleArangeNode`, 포인터 태깅) — Linux 6.1 VMA 관리 구조를 이식,
  4가지 노드 타입 전부 처음부터 반영(메모리 절약 불필요해도) - RCU
  대신 Spinlock 사용 (SP-2AAD7C8D §3, 참고: minzkn.com Maple Tree 문서).
- **`VmaBacking`**(`Anonymous`/`FixedPhysical`/`FileBacked`) — VMA의
  물리 백킹 종류 (SP-2AAD7C8D §4).
- **DMA 버퍼 관리자**(`AllocDmaBuffer`/`FreeDmaBuffer`) — 커널이 물리
  연속 메모리를 확보해 유저 프로세스에 가상/물리 주소 쌍으로 내주는
  syscall - `physAddrLimit`로 32비트 제약(레거시 컨트롤러) 지원
  (SP-39F18E30).
- **`allocOrderBelow`** — 특정 물리 상한 미만에서만 버디 블록을
  찾는 확장(레거시 DMA 32비트 제약 대응) (SP-39F18E30 §5-B).
- **TLB 샷다운(IPI 기반)** — `Lapic::sendFixedIpi` + ISR + ACK
  카운트다운, `KernelAddressSpaceManager` 매핑 변경 시 필수
  (SP-DE19BB1C). **[갱신, 2026-09-16, PN-D132A1E9 구현 완료]** 유저
  영역(`ProcessAddressSpaceManager`) 확장에 맞춰 원래의 단일 우편함
  구조체를 **요청자별 슬롯(코어 수 배열, 요청자 코어=슬롯 인덱스라
  쓰기 락 불필요) + 수신자별 Target Pending Mask**(`AtomicU32` 비트맵)
  조합으로 재작성 - 커널 영역은 기존처럼 전체 브로드캐스트, 유저
  영역은 **Active CPU Mask**(대상 프로세스를 지금 실제로 실행 중인
  코어만, `Scheduler::taskOnCore()`로 스캔)로 범위를 좁힌다. 락 없는
  락프리 요청 슬롯 패턴이라 다른 코어 간 저수준 IPI 통지가 필요한
  곳이면 재사용 가능한 일반 패턴으로 참고할 만하다.
- **가상주소 공간 관리자 위임/철회** — mmap 서브시스템을 한 번
  미뤘다가(RM-9B8CA541) 곧바로 설계자 지시로 다시 착수해 대체된
  사례 - "위임"도 CNW 문서로 남긴다는 선례 (RM-9B8CA541, SP-2AAD7C8D §8).

## 4. IPC / Syscall

- **`Channel`(메시징 채널 IPC)** — raw binary IPC, `/sys/live/named/`
  네임스페이스에 등록 (SP-1FBC0EEB, PL-C8648D4D).
- **`NamedObjectTable`** — `/sys/live/named/` 경로를 커널 내부
  테이블로 구현한 VFS 이전 단계 선례 (SP-1FBC0EEB, RM-C65F7760).
- **`SyscallRegistry`/`SyscallEndpointId`** — 고정 슬롯(최대 256개)
  기반 syscall 등록/디스패치 (SP-04EE2A18, PL-21344323, 번호 현황판:
  RM-48E1E610).
- **`Syscall::wait`/`waitForMultipleSyscall`/`waitAnyForMultipleSyscall`**
  — 완료 대기 API, `waitForAnyOf` 공유 구현 - AND/OR 세만틱은 호출부
  반복 횟수 관례로만 구분 (SP-04EE2A18). **[갱신, 2026-09-18,
  PN-B5C2845A]** `waitForAnyOf`는 이제 `AsyncTaskState::Cancelled`도
  `Completed`/`Failed`와 같은 급의 "끝남"으로 인식한다(`Failed`
  outcome에 매핑) - 다른 프로세스의 `Kill`이 대상의 pendingSyscalls를
  취소시킬 수 있게 됐기 때문(아래 `Scheduler::cancelPendingSyscalls`
  참고).
- **`Scheduler::cancelPendingSyscalls(UserThread*)`** — [신규,
  2026-09-18, PN-B5C2845A] `SelfTerminateHandler`(PN-40E976F2) 전용
  이던 "제출자 사망 시 미완료 pendingSyscalls를 Cancelled로 전이"
  스윕을 공용화한 것 - 이제 `Process::raiseSignal()`의 Kill/Terminate
  경로도 재사용해, `Syscall::wait()`로 파킹된 UserThread를 다른
  프로세스가 Kill로 죽일 수 있게 한다. 항목별로 `waitingTask`(실제
  대기자) 유무를 확인해 두 시나리오(제출자 자신이 죽음 vs 여전히
  살아서 파킹됨)를 모두 안전하게 처리한다.
- **`ChannelError::Interrupted`** — [신규, 2026-09-18, PN-B5C2845A]
  `AcceptFromChannel`/`ConnectChannel`/`ChannelRead`/`ChannelWrite`가
  대기 도중 호출자 자신이 Kill/Terminate 대상이 돼 강제로 실패
  완료됐다는 뜻(QU-8E137FFD 답변 - "얘들을 실패시키면 되잖아").
- **`UserThread::pendingSyscalls`** — 스레드가 기다리는 syscall 토큰의
  `ChunkedList` - 유저 페이지 폴트도 이 리스트를 재사용 (SP-04EE2A18,
  SP-0666DB3C §7).
- **`ChunkedList<T, ChunkCapacity>`** — 청크 기반 범용 컨테이너,
  할당자는 함수 포인터 주입(libkmm 의존 회피) (libkenv, 여러 SP가
  재사용: `pendingSyscalls`/`DmaBuffer`/`PendingSignal`/`FileDescriptor` 등).
- **`libkcont`(신규, 2026-09-17, SP-FAF768AB, PN-633BF2D8, 커널/유저
  공용, `minicore/libs/libkcont`)** — `Node`/`List<T, Traits>`(침습적
  이중 연결, intrusive_list.h) 위에 얹은 `OrderedList<T, Traits>`
  (항상 정렬 유지, 선형 탐색 삽입)/`LruList<T, Traits>`(접근 시 맨
  앞 재배치)/`Queue<T, Traits>`(FIFO), `Vector<T, Policy>`(비침습
  동적 배열, vector.h), `RbNode`/`Rbtree<T, Traits>`(침습적 CLRS
  레드-블랙 트리)/`RbMultiTree<T, Traits>`(중복 키 허용 변형,
  rbtree.h), `Map<K, V>`(Rbtree 기반 정렬 맵, map.h) - 9종 전부 구현
  완료(commit 6c7441e). Lock-free/Concurrent 변형은 별도 계획
  (PN-013215F9/PN-DAE91888/PN-A8EF29F7)으로 분리 - `LockFreeList`/
  `LockFreeQueue`/`ConcurrentMap`/`ConcurrentRbtree`는 옛 노드/서브트리를
  읽는 리더가 있을 수 있어 `SP-B1E258D8`(RCU) 선행이 필요하지만,
  `LockFreeVector`는 세그먼트 자체가 재할당/이동/회수되지 않는 구조라
  RCU 선행 조건이 없다(SP-4DCD0E6A §2/§6) - **[완료, 2026-09-17,
  PN-DAE91888, 그러나 아래 경고 참고]** `minicore/libs/libkcont/lockfree_vector.h`로
  이미 구현 완료(commit c0f35a0), 아래 별도 항목 참고. **[완료, 2026-09-17,
  PN-013215F9]** `LockFreeList`/`LockFreeQueue`도 구현 완료(commit
  7e6c438, 아래 별도 항목 참고) - 단 `minicore/libs/libkcont`가 아니라
  `minicore/kernel/lockfree_list.h`/`lockfree_queue.h`에 있다(RCU가
  `Scheduler`/`PerCpu` 기반의 순수 커널 개념이라 커널/유저 공용
  라이브러리인 `libkcont`에 두면 계층 위반 - `KernelVectorPolicy`가
  `minicore/kernel`에 있는 것과 같은 이유). `ConcurrentMap`/
  `ConcurrentMap`/`ConcurrentRbtree` 둘 다 완료(commit 1e45e20/
  53ad5db, 아래 별도 항목 참고). `ConcurrentRbtree`는 착수 전 코드
  감사에서 `Rbtree`의 회전이 락 없는(lock-free) 읽기와 근본적으로
  안 맞는 문제를 발견해(RbCore가 여러 필드를 순차 mutate하는
  in-place 회전이라 원자적 1회 교체가 아님) QU-B5CA4008로 설계자
  방향을 확인 - "(A) 읽기 seqlock류 검증/재시도" 채택, Rbtree/RbCore
  알고리즘 자체는 무수정.
- **`LockFreeList<T, Traits>`**(신규, 2026-09-17, SP-4DCD0E6A §1,
  PN-013215F9, `minicore/kernel/lockfree_list.h`) — Harris 2001
  알고리즘의 침습적(intrusive) 단일 연결 lock-free 정렬 집합(오름차순,

  과제로 이월. 실제 소비자(`fork()`, PN-44C91D6E)는 아직 없음 - 인프라만
  미리 준비.
- **`SpawnProcess`(syscall 59)/`SpawnProcessFlags`** — 범용 프로세스
  생성 syscall(`posix_spawn`류, `imageBuffer`/`argv`/`envp`/

  비트마스크로 설계(설계자 지시, QU-9585F6C4) - 정의된 비트:
  `kSpawnDebugStart`(디버깅 대상으로 스폰 시 정지 상태로 시작,
  SP-9A6D579F §3.3용). 정의 안 된 비트는 `InvalidArgument`로 거부
  (SP-6BEAE0C1 §3, PN-543C0CE9).

  swapfs 존재를 전제하기 때문 (SP-7CC5693A §3.1, 설계자 지시).
- **유저랜드 준비 신호**(`SignalUserlandReady`/`WaitForUserlandReady`)
  — init이 커널 전역에 단 1회만 보내는 신호, fs 서비스의 파일시스템
  자동 감지는 이 신호 이후에만 시작 (SP-7CC5693A §2.5).
- **`FileDescriptor`**(프로세스별) — offset은 커널이 소유, 드라이버는
  항상 명시적 offset을 받는 무상태(pread/pwrite 스타일) 오퍼레이션
  (SP-2AAD7C8D §9.2).
- **[추가, 2026-09-23] `jbd2` 저널** — ext4의 저널링 서브시스템 온디스크
  포맷(보통 inode 8), 비정상 언마운트 이미지의 커밋 안 된 트랜잭션을
  리플레이해 안전하게 마운트하는 데 쓰인다. **이 프로젝트의 다른
  온디스크 포맷(ext4 자신/vfat/exfat/ntfs)과 달리 필드가 전부
  빅엔디안** - `ext4::kJbd2Be32`가 유일한 빅엔디안 변환 지점
  (`libext4/ext4.h` §3.6, `SP-7A9CED3E` §2.2, `PN-BC3A2F5F` 준비
  작업, 리플레이 로직 자체는 아직 미구현).

## 8. 동기화 / Signal

- **`WaitQueue`** — `Task::next`(파킹 시 비어 있음을 재사용) 기반
  FIFO, Mutex/Semaphore가 공유하는 내부 대기열, `Waitable` 구현체
  (SP-0666DB3C §1/§9).
- **재경쟁(Wake-and-Compete)** — unlock/release가 소유권을 직접
  고르지 않고 대기자 하나를 "재시도 기회"로만 깨워, 그 사이 새
  호출자와 경쟁하게 두는 방식 - 처음 제안했던 직접 핸드오프(호위
  효과 문제로 폐기)를 대체 (SP-0666DB3C §2.1, PN-69E2D9E7).
- **`Mutex`/`Semaphore`** — Mutex는 개념상 Semaphore(count=1)의
  특수형이지만 소유자 추적 여지로 별도 타입 유지 - v1 Mutex는 재진입
  안전하지 않다는 결함이 알려져 있으며 스케줄러 진척 후 개정 예정
  (SP-0666DB3C §2/§3/§5-5).
- **`AsyncMutex`/`AsyncSemaphore`** — `AsyncTask` 컨텍스트 전용
  동기화 프리미티브 - 경합 시 `Scheduler::parkCurrent()`(리액터
  Task 전체를 재움) 대신 `AsyncTask::yield()`로 리액터에 양보하고
  재시도한다(대기열 없음, `AsyncTaskAwaiter`의 "yield 반복" 관용구
  재사용) - §2/§3의 Mutex/Semaphore를 AsyncTask 안에서 그대로 쓰면
  리액터 전체가 멈춘다는 문제의 해결책 (SP-0666DB3C §10, 설계자
  지시 2026-09-14).
- **`SignalNumber`/`SignalDisposition`** — Kill(마스킹 불가)/
  Terminate/Segv/IllegalInstruction 등, 번호 자체는 RM-B5764185
  ("Minicore Signal 번호표", POSIX 표준과 동일한 0/1~22/31)를 그대로
  사용, 체크포인트+강제 취소(`Waitable`) 병행 전달 (SP-0666DB3C §4,
  RM-B5764185).
- **`Waitable`/`Task::blockedOn`/`WaitCancelReason`** — 임의의 대기
  상태에서 Task를 강제로 끄집어내는 범용 인터페이스(`cancel()`) -
  `WaitQueue`(§9.3, 완전히 즉시) vs `pendingSyscalls` 기반 대기(§9.4,
  연결된 AsyncTask의 `AsyncTokenSource`를 트리거하는 협조적 경로,
  SP-F682B889 §8) 두 경로가 서로 다른 즉시성 보장을 가짐, Kill 신호
  전달(§4.4/§9.5)이 이 메커니즘을 사용 (SP-0666DB3C §9, 설계자 지시
  2026-09-14).

- **RCU(Read-Copy-Update)/`Quiescent State`/`Grace Period`/
  `call_rcu`** — 락 없는 읽기 + 지연 회수 기법(`minicore/kernel/rcu.h`/
  `.cpp`, Classic 비선점 RCU). **[구현 완료, 2026-09-17, PN-495C11B7,
  commit 0c8f187]** 착수 시점을 "커널단 v1 완료"에서 SP-B1E258D8 §7
  기반 제원(선행 조건) 4개 충족으로 정정 후 즉시 착수 - `RcuReadGuard`
  (기존 `Scheduler::disablePreemption()`/`enablePreemption()`을 그대로
  재해석, 새 read-side 프리미티브 없음), `Rcu::noteQuiescentStateOnThisCore()`
  (`enablePreemption()`이 카운터 0 도달 시 자동 호출), `Rcu::
  startGracePeriod()`/`isGracePeriodComplete()`(전역 시퀀스 +
  `PerCpu<AtomicU64>` per-core watermark, 온라인 코어 열거는
  `Smp::isCoreOnline()` 재사용), `RcuCallback`/`RcuCallbackTraits`/
  `Rcu::callAfterGracePeriod()`(콜백 큐는 libkcont `List<T, Traits>`
  (PN-633BF2D8) 재사용 - 손짜기 연결 리스트 없음). 콜백 드레인은
  `AsyncReactor::drainOnce(coreIndex)`에 통합(SP-B1E258D8 원문의
  "reactorTaskEntry()"는 PN-FEAAF154 재구조로 이미 이 함수에 흡수됐음
  - 실제 코드 구조에 맞춰 배선). `AtomicU64`(`libkenv/spinlock.h`,
  `AtomicU32`와 동일 관례) 신규 추가. 인프라만 제공 - 실제 소비자
  전환(Maple Tree 등, §3.2 후보)은 범위 밖(SP-B1E258D8, PN-495C11B7).
  이 완료로 `PN-013215F9`(LockFreeList/LockFreeQueue)/`PN-A8EF29F7`
  (ConcurrentMap/ConcurrentRbtree)의 선행 조건도 해소됨.

- **`AsyncTaskCompletion` 패턴을 표준으로**/`MutexCore`·`SemaphoreCore`
  (공통 코어 + 정책 주입) — "동기 구현 = 비동기 구현의 wrapper"
  원칙을 어디에 적용할지 판단한 결과: 완료형 1회성 작업(§3)은
  `AsyncTaskCompletion`을 표준 패턴으로, "상태를 계속 들고 있는"
  Mutex/Semaphore는 wrapper가 아니라 공통 코어 추출로(문자 그대로의
  wrapper화는 성능/순환의존 문제로 미채택) - QU-0A7D5AAE로 승인됨,
  SP-0666DB3C §13에 최종 반영 (SP-5A255B7C, PN-2ADA2AA7).
- **§13.1 계약**(`tryAcquireOrKeepLock`) — `MutexCore`가 확인 실패
  시 Spinlock을 놓지 않고 그 `SpinlockGuard`를 살아있는 채로 Policy에
  넘겨, "확인"과 "대기열 등록" 사이에 lost-wakeup을 만드는 빈 창을
  없애는 계약 - 최초안(자체적으로 락을 열고 닫는 `tryAcquire()`)이
  이 계약을 깨는 레이스가 있어 QU-707024C0로 발견·수정됨. 향후
  `SemaphoreCore`도 반드시 같은 계약을 따라야 함 (SP-0666DB3C §13.1).
- **[추가, 2026-09-15, 상태 갱신 2026-09-22] `AsyncLocal<T>`** —
  `SP-F146B7F8` §1 `ThreadLocal<T>`(Task 단위 명시적 슬롯 TLS)와 동형
  패턴을 `AsyncTask` 단위로 적용하려던 지역 변수 설계였으나, **실제
  구현(PN-4D60D49C, commit 86703e7)에서는 만들지 않았다** - 재진입
  Mutex(`ReentrantAsyncMutex`)의 유일한 소비 후보가 결국 `AsyncTask::
  current()`(포인터 동일성 비교)만 쓰고 `AsyncLocal<T>` 슬롯 자체는
  전혀 참조하지 않아, 실제 소비자가 없는 순수 범용 인프라로 남았기
  때문(RM-23F4B687 §4 미니멀리즘 - SP-0666DB3C §15 "완료" 절 참고).
  `AsyncTask::current()` 자체는 신규 접근자로 실제 구현됐다(아래 참고).
- **[추가, 2026-09-15, 상태 갱신 2026-09-22] `AsyncTask::current()`** —
  "지금 이 코어에서 실행 중인 AsyncTask"를 반환하는 정적 접근자
  (async_task.h, PN-4D60D49C로 실제 구현 완료, commit 86703e7). 설계
  제안 당시엔 새 `TaskLocal<AsyncTask*>`(`PerCpu<T>` 래퍼) 전역으로
  감싸는 안이었으나, 실제로는 `AsyncReactor::drainOnce()`가 이미
  디스패치 경계마다 정확히 갱신해 온 기존 파일-로컬 배열
  `gCurrentAsyncTask[coreIndex]`(async_task.cpp, PN-622BA93C 이전부터
  실측 검증된 코드)가 그 의미를 이미 만족하고 있어, 그 배열을 그대로
  드러내는 얇은 접근자만 추가했다(검증된 코드를 순수 리팩터링
  목적으로 건드리지 않는 RM-23F4B687 §4 원칙).
- **[추가, 2026-09-15, 완료, 2026-09-22, commit 86703e7, PN-4D60D49C]
  `ReentrantMutex`/`ReentrantAsyncMutex`** — §13의 비재진입 `Mutex`/
  `AsyncMutex`와 컴파일 타임에 완전히 분리된 별도 타입(`mutex_core.h`) -
  항상 소유자(동기는 `Scheduler::currentTask()`, 비동기는 위
  `AsyncTask::current()`)를 추적해 같은 소유자의 재귀 `lock()` 호출을
  데드락 없이 허용한다. `Semaphore`는 "복수 소유자가 정상"인 카운팅
  프리미티브라 재진입 개념 자체가 성립하지 않는다고 판단해 이 패턴
  적용 대상에서 제외됨(SP-0666DB3C §16.2, QU-C06793C2 승인). 원 설계
  스케치의 `WaitQueue::parkCurrentAndUnlock()` 1-인자 호출은 실제
  시그니처와 맞지 않아 §13 `Mutex`(`BasicMutex<ParkingPolicy>`)와
  동일한 `EnableSharedFromThis` 기반 자기-참조 등록 패턴으로 형태만
  정정해 구현했다(SP-0666DB3C "완료" 절 참고).
- **[추가, 2026-09-16] 유저 Mutex/Semaphore syscall**(`MutexCreate`/
  `Lock`/`Unlock`/`Destroy`, `SemaphoreCreate`/`Wait`/`Post`/`Destroy`) —
  내부적으로 항상 `AsyncMutex`/`AsyncSemaphore`(YieldingPolicy)만 씀 -
  syscall 핸들러가 코어 공유 리액터 Task 위에서 돌아 `Mutex`
  (ParkingPolicy)를 쓰면 그 코어 전체가 멈추기 때문. 핸들은 Channel과
  같은 "구조체 포인터값" 관례 (SP-0666DB3C §17, 계획 PN-E82744B1,
  `scheduled`).
- **[추가, 2026-09-16] `UserMutex`**(`{ AsyncMutex core; ProcessId
  owner; }`) — 유저 Mutex syscall 전용 래퍼, `AsyncMutex` 코어 자체는
  여전히 소유자 미추적(§13)이지만 "소유자가 있는 타입은 반드시 검증"
  (설계자 지시, QU-18A1D625)에 따라 이 래퍼가 lock 성공자의
  `ProcessId`를 기억해 `MutexUnlock`에서 대조 (SP-0666DB3C §17.2/§17.4).

## 9. 유저랜드 빌드 체계

- **`userland/{apps,libs,tests}/<이름>`** — 모든 유저 영역 서브
  프로젝트의 표준 배치, 첫 라이브러리는 `userland/libs/libmc`
  (SP-68182FBD §2.4, QU-FF3F0CAA).
- **`minicore/init`** — 유저/커널 앱의 중간 지점이라 예외적으로
  `userland/` 밖에 위치, initrd가 하드코딩으로 최초 구동하는 유일한
  유저 프로그램 (SP-68182FBD §2.4).
- **`minicore/libs/libelf`** — ELF64 파서, 커널/유저 양쪽 링크 가능,
  매크로(`MINICORE_LIBELF_KERNEL`)로 구분, 기본값은 유저 영역용 컴파일
  (SP-68182FBD §2.4, PN-58501EAA).
- **initrd(CPIO) 평면 배치** — 서브디렉터리 없이 모든 파일을 루트에
  배치 (SP-68182FBD §2.4, QU-FF3F0CAA).
