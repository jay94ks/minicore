## 1. 커널 아키텍처 총론

- **하이브리드 커널** — 커널(ring 0)은 최소 책임만, 나머지("커널
  서비스")는 유저랜드에서 구동 (SP-8B6B8D25 §0).
- **"커널이 모든 통제권을 쥔 유저랜드 서비스"** — devmgr/fs/net/tty
  등 "커널 서비스"는 이름과 달리 전부 유저랜드에서 구동되고, 커널은
  권한 부여/라우팅 등 통제권만 쥐는 원칙 (SP-8B6B8D25 §2-A).
- **devmgr** — 장치 관리 커널 서비스(유저랜드) (SP-8B6B8D25, DS-D4E5C451).
- **[추가, 2026-09-16] `pubreg`** — 5번째 커널 서비스(유저랜드
  구동), 프로세스간 "공개 인터페이스" 홍보/발견 디렉터리 - 각 유저
  프로세스가 MCP(Model Context Protocol) 스타일 tool 선언(이름/
  설명/입력·출력 JSON Schema)을 등록하면, 다른 프로세스가 조회해
  찾은 뒤 직접 연결(Channel IPC)해 그 tool을 JSON 메시지로 호출한다
  - `pubreg` 자신은 신원(채널ID)만 중개, 실제 데이터는 거치지 않음
  (SP-B071E628, 설계자 지시로 커널 내부 자료구조 안을 대체).
- **[추가, 2026-09-16] `libjson`** — JSON 파서/직렬화 라이브러리
  (신규, `minicore/libs/libjson`, **[정정, 2026-09-15, 설계자 지시]**
  커널/유저 공용 - `libelf`류 매크로 게이팅 패턴) - `pubreg`의 tool
  등록/조회 프로토콜에 사용 (SP-B071E628 §4).
- **[추가, 2026-09-16] pubreg 커널 서비스 대행 릴레이** — 커널
  서비스(devmgr/fs/net/tty 및 그 드라이버 자식)는 성능/프로토콜
  유지보수 부담 때문에 `pubreg`에 직접 register/query하지 않는다 -
  유저랜드의 별도 중계 구성요소가 이를 대행해야 한다는 제약(설계자
  지시, 형태는 미정) (SP-B071E628 §5-A). **[정정, 2026-09-16] 이
  릴레이 자체를 minicore가 설계/구현하려던 계획(PN-36E3164D,
  SP-40E5534D)은 설계자 답변(QU-722E72F5)으로 거부됨 - "유저 영역에
  설치될 앱들을 개발하는 제3자가 만들어야 하는 부분"으로 최종
  확정(범위 밖). 이 항목은 "그런 제약이 존재한다"는 사실만 기록하며,
  더 이상 minicore 자신의 미완료 후속 설계 과제가 아니다.**
- **fs 서비스** — 파일시스템 커널 서비스(유저랜드), VFS 마운트 지점의
  실제 처리 담당 (SP-8B6B8D25 §4-A, SP-7CC5693A).
- **RM-23F4B687 §4 원칙** — "명시되지 않은 설계는 임의로 결정하지
  않되, 숫자/전략 튜닝 수준은 구현 중 계측으로 판단 가능" - 이
  프로젝트 전체에서 반복 인용되는 판단 기준 (RM-23F4B687).

## 2. 프로세스/스레드/스케줄링

- **`Task`** — 스케줄링 최소 단위(코드명 `kernel::Task`) - 프로세스는
  주소공간+자원의 소유자, Task는 실제 실행 흐름으로 분리 (PL-2D3184BC).
- **`Process`** — 유저 프로세스의 커널 쪽 표현(주소공간 PML4 소유자,
  `mainThread`, `FaultInfo lastFault`) (SP-68182FBD).
- **`UserThread`** — Task를 상속하는 유저 스레드(PCB 개념과 별개로
  "커널 Task ≠ 유저 스레드" 구분 확정) (SP-04EE2A18, 설계자 지시
  2026-09-14).
- **`TaskState`**(`Ready`/`Running`/`Blocked`/`Zombie`) — 새 상태를
  추가하지 않고 재사용하는 원칙(유저 폴트/뮤텍스 대기 등 전부
  `Blocked` 하나로 표현) (PL-2D3184BC, QU-0C4D25EF).
- **`inRunQueue`** — 이중 스케줄링 경쟁 조건의 구조적 방지책(Task가
  이미 큐에 있는지 별도 플래그로 추적, `state`로는 판별 불가)
  (PL-2D3184BC, PL-C8648D4D에서 실측 발견).
- **`PreemptionGuard`** — 선점 비활성화 RAII, 코어별 카운터 기반
  (SP-D7013B26 §2.1, PL-2D3184BC 8단계).
- **`Scheduler::parkCurrent()`/`scheduleImmediate()`** — 범용 블로킹/
  즉시 재개 프리미티브 - Mutex/Semaphore/AsyncReactor/유저 폴트 재개
  전부가 공유하는 기반 (PL-2D3184BC, SP-F682B889, SP-0666DB3C).
- **즉시 스케줄링 큐(Immediate Queue)** — RT 클래스보다도 먼저
  실행되는 최상위 큐, 비동기 프레임워크 완료 통지 전용
  (PL-2D3184BC 8-1단계, SP-F682B889).
- **Task 종료 프로토콜** — `isUserLevel` 플래그로 자기종료 syscall
  제출(유저 레벨) vs `retireCurrentTask()`(커널 레벨, Zombie 표시 +
  지연 스택 회수)로 분기 (PL-2D3184BC, QU-26F9420E).
- **Push/Pull 로드밸런싱** — 코어 간 작업 이관(Pull=유휴 시 당겨옴,
  Push=90% 임계 시 밀어냄), CPU affinity 걸린 Task는 완전 제외
  (DS-D4E5C451, PL-2D3184BC §9, 아직 미구현 - PN-7679813D).
- **유저 페이지 폴트 재개 정책** — 폴트를 "또 하나의 대기 중인
  syscall 토큰"으로 모델링해 `pendingSyscalls`가 비어야 재개(공통
  리스트 방식) (SP-8B6B8D25 §2-B, SP-68182FBD §2.3, SP-0666DB3C §7).
- **`ThreadLocal<T>`/`TlsRegistry`** — `Task`/`UserThread`에 내장된
  고정 슬롯 배열(`tlsSlots`) 기반 명시적(explicit) TLS - 컴파일러의
  진짜 `thread_local`(FS_BASE 스왑 + `.tdata`/`.tbss`)은 아직 없어
  `get()`/`set()` 호출로 흉내낸다. `AsyncTask`는 대상 밖(별개 구조체)
  (SP-0666DB3C §11, 설계자 지시 2026-09-14).
- **`PerCpu<T>`** — "코어 개수만큼의 배열 + `Scheduler::
  currentCoreIndex()`로 인덱싱"하는, 스케줄러(`gCurrentTask`/
  `gPreemptDisableCount` 등)와 Slab 할당자가 이미 반복해 온 패턴을
  공식화한 템플릿 - `currentCoreIndex()` 자체가 O(코어 수) 선형
  스캔이라는 점이 열린 성능 과제로 남음 (SP-0666DB3C §12, 설계자
  지시 2026-09-14).
- **Task 디스패치 동기화 상태 체크리스트**(`kSyncCr3`/
  `kSyncRsp0ForDispatch`/`kSyncFpu`) — "디스패치 때마다 그 Task 자신의
  상태로 동기화해야 하는" 하드웨어 상태(CR3/TSS.RSP0/FPU)를 한 곳에
  묶어 §3.2의 공용 두 갈래(①트랩 경로 `onTick()`/②`kContextSwitch`
  재개 경로의 세 지점 - `kSyncCr3OnTaskStart`/`yieldCurrent`/
  `parkCurrent` 재개)에서 재사용하도록 못박은 원칙 - 새 상태가 추가될
  때마다 새 훅을 파지 않고 이 목록에 편입 (SP-83A07867 §3.2/§8).
- **`Scheduler::retireTask(Task*)`** — `retireCurrentTask()`(자기
  자신 전용)와 달리 이미 스위칭되어 나간 임의의 Task를 정리하는 API -
  self-terminate처럼 리액터가 대신 종료 처리를 수행하는 비동기 경로의
  기반 (PL-2D3184BC, PN-71C3D483).
- **`gBootPml4Phys`** — 부팅 시점(어떤 프로세스도 없을 때) 캡처해 둔
  커널 기본 PML4 - 커널 레벨 Task(리액터 등) 디스패치 시 CR3를 이
  값으로 되돌리는 기준점 (PN-71C3D483, SP-83A07867).
- **`ProcessRole`**(`Normal`/`KernelService`) — 프로세스가 "신뢰할
  수 있는 커널 서비스"인지를 syscall 레벨에서 판정하는 불변 속성 -
  부팅 매니페스트로 devmgr/fs/net/tty 네 프로세스, 그리고 devmgr의
  PnP 드라이버 스폰 경로(SP-9DD4F3EA §3.2)로 만들어진 자식 프로세스
  에도 부여되고(QU-3AAAB5E9, 2026-09-15 - "드라이버는 전부 유저랜드
  커널 프로세스로 신뢰"), 재조정 API나 임의 위임/상속 체인 없이
  생성 시점에 고정된다 (SP-EAB162FC, PN-645CF608).
- **`ProcessStartFlags::resurrect`** — 프로세스 생성 시점에 고정되는
  또 다른 불변 시작 플래그. true면 그 프로세스가 종료되는 즉시(별도
  감시 Task/폴링 없이 `Scheduler::retireTask()` 직후 같은 흐름
  안에서) 같은 스폰 경로로 재생성된다 - v1은 부팅 매니페스트/PnP
  드라이버 스폰 경로 두 곳에만 적용 (SP-EAB162FC §6, PN-645CF608).
- **`ProcessStartFlags::essential`** — **[추가, 2026-09-15, 설계자
  지시]** `resurrect`와 별개인 새 시작 플래그 - true(기본값)면 이
  프로세스가 죽는 즉시 재스폰 시도 없이 커널 패닉("커널 서비스가
  죽으면 커널이 정상동작 못 한다"는 원래 전제 그대로), false면
  패닉 없이 아래 백오프 일정으로만 무한정 재시도 (SP-EAB162FC §6.1/
  §6.3).
- **`Process::consecutiveFailures` / Resurrect 백오프 일정** —
  **[개정, 2026-09-15, 설계자 지시 - 이전 `kMaxResurrectAttempts=5→
  패닉` 폐기]** `essential=false` 서비스의 재스폰 간격 계산용 연속
  실패 카운터(재스폰마다 옛 `Process`에서 이어받는 런타임 값) -
  기본 간격 1분, 5회 실패마다 1분씩 증가, 최대 10분 상한. 커널
  패닉 방아쇠는 이제 `essential` 플래그 하나뿐, 재시도 횟수와 무관
  (SP-EAB162FC §6.4, PN-645CF608).
- **`DelayedExecutionQueue`**(지연 실행/타이머 인프라, 신규,

## 3. 메모리 관리

- **Direct Map**(`kDirectMapBase = 0xFFFF800000000000`) — 전체 물리
  메모리를 미리 매핑해 둔 higher-half 영역, canonical 경계와 정확히
  일치 (Paging 설계, SP-68182FBD).
- **`PageFrameAllocator`** — 물리 페이지 버디 할당자, NUMA 노드별
  분리, order 기반(`allocOrder`/`allocOrderOnNode`) (DS-D4E5C451,
  PL-99562483).
- **`GenericSlabAllocator`/`SlabCache`** — 코어별 더블 매거진(loaded/
  previous) + 전역 디포 기반 slab 할당자, 7단계 고정 버킷(32~2048B)
  (SP-D7013B26, PL-16E2CDA4).
- **128TiB 유저 주소공간** — 4레벨 페이징 canonical 하위 절반의
  수학적 상한(256TiB는 오기였음) (SP-8B6B8D25 §5, QU-72108298).
- **유저 주소공간 레이아웃(§5-A)** — 코드 0x400000부터, 스택은 유저
  공간 끝점에서 하향, 코드/스택 양쪽 가드 페이지 필수, ELF 로더는
  항상 ELF 자신의 `p_vaddr`/`e_entry`를 우선(0x400000은 툴체인 관례일
  뿐) (SP-8B6B8D25 §5-A, QU-7043EA6D).
- **`Paging::createAddressSpace()`** — PML4 인덱스 256-511(higher
  half)만 엔트리째 복사해 새 주소공간 생성 - 모든 프로세스가 커널
  영역을 물리적으로 공유 (SP-68182FBD §1.1).
- **`ProcessAddressSpaceManager`/`KernelAddressSpaceManager`** —
  가상주소 관리를 프로세스별 파트(Maple Tree 1개, 프로세스별 락)와
  커널 영역 전용 파트(Maple Tree 1개, 전역 락 - SMP 전체가 공유해
  보므로)로 분리 (SP-2AAD7C8D §1/§2, 설계자 지시).
- **Maple Tree**(`MapleDenseNode`/`MapleLeaf64Node`/`MapleRange64Node`/
  `MapleArangeNode`, 포인터 태깅) — Linux 6.1 VMA 관리 구조를 이식,
  4가지 노드 타입 전부 처음부터 반영(메모리 절약 불필요해도) - RCU
  대신 Spinlock 사용 (SP-2AAD7C8D §3, 참고: minzkn.com Maple Tree 문서).
- **`VmaBacking`**(`Anonymous`/`FixedPhysical`/`FileBacked`) — VMA의
  물리 백킹 종류 (SP-2AAD7C8D §4).
- **DMA 버퍼 관리자**(`AllocDmaBuffer`/`FreeDmaBuffer`) — 커널이 물리
  연속 메모리를 확보해 유저 프로세스에 가상/물리 주소 쌍으로 내주는
  syscall - `physAddrLimit`로 32비트 제약(레거시 컨트롤러) 지원
  (SP-39F18E30).
- **`allocOrderBelow`** — 특정 물리 상한 미만에서만 버디 블록을
  찾는 확장(레거시 DMA 32비트 제약 대응) (SP-39F18E30 §5-B).
- **커널 영역 TLB 샷다운(IPI 기반)** — 우편함 구조체 + `Lapic::
  sendFixedIpi`(신규) + ISR + ACK 카운트다운, `KernelAddressSpaceManager`
  매핑 변경 시 필수 (SP-DE19BB1C).
- **가상주소 공간 관리자 위임/철회** — mmap 서브시스템을 한 번
  미뤘다가(RM-9B8CA541) 곧바로 설계자 지시로 다시 착수해 대체된
  사례 - "위임"도 CNW 문서로 남긴다는 선례 (RM-9B8CA541, SP-2AAD7C8D §8).

## 8. 동기화 / Signal

- **`WaitQueue`** — `Task::next`(파킹 시 비어 있음을 재사용) 기반
  FIFO, Mutex/Semaphore가 공유하는 내부 대기열, `Waitable` 구현체
  (SP-0666DB3C §1/§9).
- **재경쟁(Wake-and-Compete)** — unlock/release가 소유권을 직접
  고르지 않고 대기자 하나를 "재시도 기회"로만 깨워, 그 사이 새
  호출자와 경쟁하게 두는 방식 - 처음 제안했던 직접 핸드오프(호위
  효과 문제로 폐기)를 대체 (SP-0666DB3C §2.1, PN-69E2D9E7).
- **`Mutex`/`Semaphore`** — Mutex는 개념상 Semaphore(count=1)의
  특수형이지만 소유자 추적 여지로 별도 타입 유지 - v1 Mutex는 재진입
  안전하지 않다는 결함이 알려져 있으며 스케줄러 진척 후 개정 예정
  (SP-0666DB3C §2/§3/§5-5).
- **`AsyncMutex`/`AsyncSemaphore`** — `AsyncTask` 컨텍스트 전용
  동기화 프리미티브 - 경합 시 `Scheduler::parkCurrent()`(리액터
  Task 전체를 재움) 대신 `AsyncTask::yield()`로 리액터에 양보하고
  재시도한다(대기열 없음, `AsyncTaskAwaiter`의 "yield 반복" 관용구
  재사용) - §2/§3의 Mutex/Semaphore를 AsyncTask 안에서 그대로 쓰면
  리액터 전체가 멈춘다는 문제의 해결책 (SP-0666DB3C §10, 설계자
  지시 2026-09-14).
- **`SignalNumber`/`SignalDisposition`** — Kill(마스킹 불가)/
  Terminate/Segv/IllegalInstruction 등, 번호 자체는 RM-B5764185
  ("Minicore Signal 번호표", POSIX 표준과 동일한 0/1~22/31)를 그대로
  사용, 체크포인트+강제 취소(`Waitable`) 병행 전달 (SP-0666DB3C §4,
  RM-B5764185).
- **`Waitable`/`Task::blockedOn`/`WaitCancelReason`** — 임의의 대기
  상태에서 Task를 강제로 끄집어내는 범용 인터페이스(`cancel()`) -
  `WaitQueue`(§9.3, 완전히 즉시) vs `pendingSyscalls` 기반 대기(§9.4,
  연결된 AsyncTask의 `AsyncTokenSource`를 트리거하는 협조적 경로,
  SP-F682B889 §8) 두 경로가 서로 다른 즉시성 보장을 가짐, Kill 신호
  전달(§4.4/§9.5)이 이 메커니즘을 사용 (SP-0666DB3C §9, 설계자 지시
  2026-09-14).

- **RCU(Read-Copy-Update)/`Quiescent State`/`Grace Period`/
  `call_rcu`** — 락 없는 읽기 + 지연 회수 기법. 이 커널은 아직 인프라가
  없어(SP-2AAD7C8D §3.2) SP-B1E258D8이 평가/v1 설계(기존 선점
  비활성화 카운터를 quiescent state로 재해석하는 Classic RCU,
  `RcuReadGuard`/`Rcu::startGracePeriod`/`Rcu::callAfterGracePeriod`)를
  제안했으나 QU-C29D8120에서 거부됨(규모가 커 커널단 v1 완료
  이후로 착수 시점을 미룸, SP-B1E258D8 §6-부) (SP-B1E258D8,
  PN-495C11B7).

- **`AsyncTaskCompletion` 패턴을 표준으로**/`MutexCore`·`SemaphoreCore`
  (공통 코어 + 정책 주입) — "동기 구현 = 비동기 구현의 wrapper"
  원칙을 어디에 적용할지 판단한 결과: 완료형 1회성 작업(§3)은
  `AsyncTaskCompletion`을 표준 패턴으로, "상태를 계속 들고 있는"
  Mutex/Semaphore는 wrapper가 아니라 공통 코어 추출로(문자 그대로의
  wrapper화는 성능/순환의존 문제로 미채택) - QU-0A7D5AAE로 승인됨,
  SP-0666DB3C §13에 최종 반영 (SP-5A255B7C, PN-2ADA2AA7).
- **§13.1 계약**(`tryAcquireOrKeepLock`) — `MutexCore`가 확인 실패
  시 Spinlock을 놓지 않고 그 `SpinlockGuard`를 살아있는 채로 Policy에
  넘겨, "확인"과 "대기열 등록" 사이에 lost-wakeup을 만드는 빈 창을
  없애는 계약 - 최초안(자체적으로 락을 열고 닫는 `tryAcquire()`)이
  이 계약을 깨는 레이스가 있어 QU-707024C0로 발견·수정됨. 향후
  `SemaphoreCore`도 반드시 같은 계약을 따라야 함 (SP-0666DB3C §13.1).
- **[추가, 2026-09-15] `AsyncLocal<T>`** — §11 `ThreadLocal<T>`(Task
  단위 명시적 슬롯 TLS)와 동형 패턴을 `AsyncTask` 단위로 적용한 지역
  변수 - `AsyncTask::current()`(신규 접근자, 리액터 디스패치 경계에서
  갱신)로 "지금 이 코어에서 실행 중인 AsyncTask"를 조회해 슬롯에
  접근한다. 재진입 가능 Mutex의 AsyncTask 단위 소유자 식별에 쓰인다
  (설계 제안, 설계자 확인 대기 - SP-0666DB3C §15, `AsyncTask::current()`/
  `localSlots` 필드 자체는 SP-F682B889 개정 필요, QU-21DB42F9).
- **[추가, 2026-09-15] `ReentrantMutex`/`ReentrantAsyncMutex`** — §13의
  비재진입 `Mutex`/`AsyncMutex`와 컴파일 타임에 완전히 분리된 별도
  타입 - 항상 소유자(동기는 `Scheduler::currentTask()`, 비동기는
  `AsyncLocal<T>` 기반 `AsyncTask::current()`)를 추적해 같은
  소유자의 재귀 `lock()` 호출을 데드락 없이 허용한다. `Semaphore`는
  "복수 소유자가 정상"인 카운팅 프리미티브라 재진입 개념 자체가
  성립하지 않는다고 판단해 이 패턴 적용 대상에서 제외됨(설계 제안,
  설계자 확인 대기 - SP-0666DB3C §16, QU-C06793C2).
- **[추가, 2026-09-16] 유저 Mutex/Semaphore syscall**(`MutexCreate`/
  `Lock`/`Unlock`/`Destroy`, `SemaphoreCreate`/`Wait`/`Post`/`Destroy`) —
  내부적으로 항상 `AsyncMutex`/`AsyncSemaphore`(YieldingPolicy)만 씀 -
  syscall 핸들러가 코어 공유 리액터 Task 위에서 돌아 `Mutex`
  (ParkingPolicy)를 쓰면 그 코어 전체가 멈추기 때문. 핸들은 Channel과
  같은 "구조체 포인터값" 관례 (SP-0666DB3C §17, 계획 PN-E82744B1,
  `scheduled`).
- **[추가, 2026-09-16] `UserMutex`**(`{ AsyncMutex core; ProcessId
  owner; }`) — 유저 Mutex syscall 전용 래퍼, `AsyncMutex` 코어 자체는
  여전히 소유자 미추적(§13)이지만 "소유자가 있는 타입은 반드시 검증"
  (설계자 지시, QU-18A1D625)에 따라 이 래퍼가 lock 성공자의
  `ProcessId`를 기억해 `MutexUnlock`에서 대조 (SP-0666DB3C §17.2/§17.4).
