# Slab 할당자 제안(SP-D7013B26)의 세부 결정 — 요구분석

## 배경

SP-D7013B26("Slab 할당자(libkmm) — 설계 제안")가 코어별 매거진 +
전역 디포 + 슬랩 페이지 3단 구조와 `SlabCache`/`GenericSlabAllocator`
API를 제안했다. §4에 남긴 네 가지 세부를 정식으로 묻는다.

## 결정이 필요한 항목

1. **매거진 용량**: 코어별 매거진 하나에 몇 개까지 담을지(예: 15,
   31) - 크면 디포 접근이 줄지만 코어별 유휴 메모리가 늘어난다.
2. **버킷 크기 목록**: `GenericSlabAllocator`가 몇 개의 버킷을
   둘지(예: 32/64/128/256/512/1024/2048바이트).
3. **슬랩 백킹 페이지 크기**: 슬랩 하나당 `PageFrameAllocator`
   order 0(4KiB)만 쓸지, 객체 크기에 따라 더 큰 order를 쓸지.
4. **디포 고갈 시 정책**: `PageFrameAllocator`까지 완전히 고갈되면
   `alloc()`이 null을 반환해야 하는지, 호출한 Task/AsyncTask를
   블로킹해야 하는지.

전체 제안(SP-D7013B26) 승인 여부와 위 네 항목에 대한 답을 부탁드립니다.

## 결정 (QU-4F905C08 답변, 2026-09-14)

Bonwick-Adams 2단 구조(Magazine/Depot) 자체는 타당하다고 승인하되,
동시성 방어와 세부 수치를 다음과 같이 확정/보강:

- **선점 방지 강제** - 매거진 alloc()/free() 진입 즉시 PreemptionGuard/
  인터럽트 마스킹으로 코어 ID를 고정, 코어 마이그레이션/인터럽트
  재진입으로 인한 프리리스트 파괴를 방지.
- **Double-Magazine(Loaded/Previous) 구조 채택** - 단일 매거진은
  경계값에서 디포 CAS 경합이 폭증(thrashing)하므로 Bonwick 표준대로
  코어당 loaded+previous 2개를 두고 스왑 로직으로 처리.
- **버킷 크기 라운드업 유틸(`sizeToBucket`)을 `free()` 내부에 강제**
  - 규약 불일치로 인한 슬랩 오분류 원천 차단.
- **매거진 용량 16개 고정**(포인터 16개=128B, L1D 캐시 2라인).
- **버킷 7단계 고정**: 32/64/128/256/512/1024/2048 - 32B 미만 금지,
  최대 초과분은 PageFrameAllocator로 직접 위임.
- **슬랩 백킹 페이지는 기본 Order 0(4KiB) 전용** - 512~2048 버킷에
  한해 Order 1 적용 여부는 실측 후 차후 검토(PN-DE8C27B1로 별도
  추적).
- **디포 고갈 시 즉시 nullptr 반환(non-blocking)** - 비동기 런타임
  내부에서 슬립/블로킹은 스케줄러 데드락을 유발하므로 절대 불허.
  재시도/실패 처리는 상위 `AsyncTaskHandler::onFailure`류 콜백 책임.

이 결정은 SP-D7013B26에 전부 반영돼 승인(approved) 완료됐고,
PL-16E2CDA4(Slab 할당자 구현)로 실제 구현·검증까지 끝났다.
