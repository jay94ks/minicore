# libexfat — exFAT 온디스크 포맷 읽기/쓰기 라이브러리 설계

## 1. 배경

설계자 opinion(`SP-A658A124`/libvfat 대상, 2026-09-22): "exfat과
ntfs도 지원해야해." - `libvfat`(FAT32/16)과 별개로 exFAT을 지원하는
새 라이브러리를 등록한다. `libext4`/`libvfat`이 이미 확립한 원칙과
동일 - exFAT은 Microsoft의 기존 외부 표준 온디스크 포맷(공개된
"exFAT File System Specification")이라 이 프로젝트가 새로 고안할
내용이 없다(CLAUDE.md 규칙4). **이 문서가 옮기는 필드 레이아웃은
공개 스펙 문헌에 근거하지만, 구현 착수 시 반드시 실제 스펙 문서와
1바이트 단위로 재확인할 것** - `SP-D02C4A73`/`SP-7A9CED3E`/
`SP-A658A124`가 이미 세운 관례 그대로.

**FAT32와의 관계**: exFAT은 FAT32의 후속이지만 온디스크 구조가
근본적으로 다르다(8.3 짧은 이름 없음, FAT 대신 별도 할당 비트맵
파일, 디렉터리 엔트리가 여러 개씩 묶여 하나의 파일을 표현) - 코드를
공유하기보다 완전히 독립된 파서로 다룬다(`SP-2BCE5D60` §2의
"라이브러리 하나당 포맷 하나" 관례를 그대로 확장).

**신규 라이브러리 등록**(CLAUDE.md 규칙8): `minicore/libs/libexfat`
- `RM-7C249618`에 이 문서 승인과 함께 행 추가.

## 2. 스코프 — 단계적 로드맵(`SP-7A9CED3E`/`SP-A658A124`와 동일 원칙)

**1차 증분(이 문서가 지금 구조를 확정하는 범위)**: 부트 섹터(§3.1),
할당 비트맵 파일 읽기(§3.3), Up-case 테이블 파일 읽기(§3.4), 디렉터리
엔트리 집합 파싱(파일 이름/스트림/속성, §3.5), 클러스터 체인(FAT
영역 - `NoFatChain` 최적화 포함, §3.2) - 읽기/쓰기 둘 다.

**후속 증분**:
1. **TexFAT(Transaction-safe FAT) 지원** - `NumberOfFats==2`인 이중
   FAT 구성, 트랜잭션 안전 쓰기(exFAT 스펙의 선택 기능). 1차 증분은
   `NumberOfFats==1`(일반적인 exFAT 포맷)만 다룬다.
2. **볼륨 dirty 비트/미디어 실패 플래그 관리**(`VolumeFlags` bit1/2,
   §3.1) - 마운트 시 세팅, 정상 언마운트 시 클리어(`libvfat`/
   `libext4`의 대응 증분과 동일한 성격).
3. **PercentInUse 유지보수**(§3.1) - 실사용률 필드를 실시간으로
   정확히 갱신(선택적 진단 필드, 없어도 기능엔 지장 없음).

각 항목은 별도 `PN-` 계획으로 등록한다(CLAUDE.md 규칙7, 문서 승인과
함께).

## 3. 온디스크 포맷 — exFAT 표준 준수

### 3.1 메인 부트 섹터 — LBA 0, 512바이트

```cpp
#pragma pack(push, 1)
struct ExfatBootSector {
    uint8_t  jumpBoot[3];
    char     fileSystemName[8];   // "EXFAT   " (8바이트, 공백 패딩)
    uint8_t  mustBeZero[53];      // 바이트 11~63 - FAT12/16/32 BPB와
                                   // 겹치는 자리를 일부러 0으로 채워
                                   // exFAT을 모르는 도구가 오해하지
                                   // 않게 하는 설계
    uint64_t partitionOffset;     // 미디어 시작부터 섹터 오프셋(0도 허용)
    uint64_t volumeLength;        // 볼륨 전체 크기(섹터 단위)
    uint32_t fatOffset;           // FAT 영역 시작(파티션 기준 섹터)
    uint32_t fatLength;           // FAT 영역 전체 크기(섹터, 모든 FAT 사본 포함)
    uint32_t clusterHeapOffset;   // 데이터 영역(클러스터 힙) 시작 섹터
    uint32_t clusterCount;        // 클러스터 힙의 총 클러스터 수
    uint32_t firstClusterOfRootDirectory;  // 보통 클러스터 5(구현마다 다를 수 있음 - 필드 그대로 신뢰)
    uint32_t volumeSerialNumber;
    uint16_t fileSystemRevision;  // 0x0100 = 1.00
    uint16_t volumeFlags;         // bit0=ActiveFat bit1=VolumeDirty
                                   // bit2=MediaFailure bit3=ClearToZero
    uint8_t  bytesPerSectorShift; // 섹터 크기 = 1 << 이 값(보통 9=512)
    uint8_t  sectorsPerClusterShift; // 클러스터 크기(섹터) = 1 << 이 값
    uint8_t  numberOfFats;        // 1(일반) 또는 2(TexFAT, §2 후속)
    uint8_t  driveSelect;
    uint8_t  percentInUse;        // 0~100, 또는 0xFF(모름)
    uint8_t  reserved[7];
    uint8_t  bootCode[390];
    uint16_t bootSignature;       // 0xAA55
};
static_assert(sizeof(ExfatBootSector) == 512);
#pragma pack(pop)
constexpr char kExfatFsName[8] = {'E','X','F','A','T',' ',' ',' '};
```

**`mount()` 판별**: `fileSystemName`이 `kExfatFsName`과 정확히
일치하는지 + `bootSignature == 0xAA55` 확인 - 불일치 시 "이 포맷
아님"(다음 드라이버 시도).

### 3.2 FAT 영역 — 32비트 엔트리(FAT32와 유사), `NoFatChain` 최적화

FAT 엔트리 폭/특수값은 FAT32(`SP-A658A124` §3.4)와 동일한 32비트
체계(free=0, EOC=0xFFFFFFFF, bad=0xFFFFFFF7) - 단 **exFAT 고유의
핵심 최적화**: 파일이 물리적으로 완전히 연속된 클러스터로 할당됐으면
(exFAT은 할당 시 연속 배치를 우선 시도) 그 파일의 스트림 확장 엔트리
(§3.5)에 `NoFatChain` 플래그가 세팅되고, 이 경우 **FAT를 아예
참조하지 않고 `FirstCluster`+`DataLength`만으로 전체 범위를 계산**
한다(FAT 순회 자체를 생략 - 단편화 안 된 대부분의 실사용 파일에서
큰 성능 이득). `NoFatChain`이 꺼져 있을 때만 FAT32처럼 클러스터
체인을 따라간다.

### 3.3 할당 비트맵 — 온디스크 "파일"로 존재(FAT32의 FSInfo와 다름)

exFAT은 클러스터 사용 여부를 FAT 엔트리 값(0=free)이 아니라 **별도
비트맵**으로 관리한다(FAT는 오직 체인 연결 정보만) - 이 비트맵
자신도 일반 파일처럼 루트 디렉터리의 특수 엔트리(§3.5, EntryType
`0x81`)가 가리키는 클러스터 체인에 저장된다. 1비트 = 클러스터 1개
(`clusterCount`비트), 클러스터 2(첫 데이터 클러스터)부터 시작.
`mount()` 시 이 비트맵을 통째로 읽어 메모리에 캐싱(`libswapfs`의
런타임 캐시 전략과 유사하되, **이건 진짜 온디스크 영구 구조라 쓰기
시 반드시 디스크에도 반영**해야 한다 - `libswapfs`/`libext4`의 비트맵
성격 차이 주의).

### 3.4 Up-case 테이블 — 대소문자 비교용, 역시 온디스크 "파일"

exFAT 이름은 대소문자 구분 없이 비교하되 원래 대소문자를 보존한다
(NTFS와 유사한 철학) - 이 비교/정규화에 쓰는 매핑 테이블도 볼륨마다
루트 디렉터리의 특수 엔트리(`0x82`)가 가리키는 클러스터 체인에 저장
된 "파일"이다. `mount()` 시 이 테이블을 읽어 메모리에 캐싱 - **표준
기본 테이블 값을 이 문서가 하드코딩하지 않는다**(스펙이 볼륨 생성
도구마다 커스텀 테이블을 허용 - 항상 볼륨 자신의 테이블을 읽어야
정확하다, CLAUDE.md 규칙4와 같은 정신 - 확정 안 된 값을 임의로
단언하지 않음).

### 3.5 디렉터리 엔트리 — 32바이트, 여러 개가 묶여 파일 하나를 표현

```cpp
#pragma pack(push, 1)
struct ExfatDirEntryHeader {   // 모든 32바이트 엔트리의 공통 첫 바이트
    uint8_t entryType;   // bit7=InUse(0이면 삭제/미사용), bits0-6=타입
                          // 0x00 = 디렉터리 끝(더 이상 엔트리 없음)
};

// EntryType 0x85(Primary) - "File Directory Entry": 파일 하나의 시작
struct ExfatFileDirEntry {
    uint8_t  entryType;      // 0x85
    uint8_t  secondaryCount; // 뒤따르는 보조 엔트리 수(스트림+이름 합)
    uint16_t setChecksum;    // 이 엔트리 집합(자신+보조 전부, 이 필드
                              // 제외) 전체에 대한 체크섬 - 무결성 보장
    uint16_t fileAttributes; // READ_ONLY/HIDDEN/SYSTEM/DIRECTORY/ARCHIVE
                              // 등 - FAT32 attr 비트와 값 자체는 호환
    uint16_t reserved1;
    uint32_t createTimestamp;
    uint32_t lastModifiedTimestamp;
    uint32_t lastAccessedTimestamp;
    uint8_t  create10msIncrement;
    uint8_t  lastModified10msIncrement;
    uint8_t  createUtcOffset;
    uint8_t  lastModifiedUtcOffset;
    uint8_t  lastAccessedUtcOffset;
    uint8_t  reserved2[7];
};

// EntryType 0xC0(Secondary) - "Stream Extension": 데이터 위치/이름 길이
struct ExfatStreamExtEntry {
    uint8_t  entryType;             // 0xC0
    uint8_t  generalSecondaryFlags; // bit0=AllocationPossible
                                     // bit1=NoFatChain(§3.2)
    uint8_t  reserved1;
    uint8_t  nameLength;             // UTF-16 코드유닛 수
    uint16_t nameHash;                // Up-case 정규화된 이름의 해시
                                       // (빠른 조회용, §3.6)
    uint16_t reserved2;
    uint64_t validDataLength;         // 실제 쓰여진 데이터 길이(<=dataLength)
    uint32_t reserved3;
    uint32_t firstCluster;
    uint64_t dataLength;              // 파일 전체 크기
};

// EntryType 0xC1(Secondary) - "File Name": 이름 조각 15자(UTF-16)씩
struct ExfatFileNameEntry {
    uint8_t  entryType;   // 0xC1
    uint8_t  generalSecondaryFlags;
    uint16_t fileName[15]; // UTF-16, 15자씩(부족하면 남는 자리도 필드
                            // 크기만큼 유지 - nameLength로 실제 길이 판단)
};
static_assert(sizeof(ExfatFileDirEntry) == 32);
static_assert(sizeof(ExfatStreamExtEntry) == 32);
static_assert(sizeof(ExfatFileNameEntry) == 32);
#pragma pack(pop)

constexpr uint8_t kExfatEntryInUseBit = 0x80;
constexpr uint8_t kExfatEntryTypeFile = 0x85;
constexpr uint8_t kExfatEntryTypeStreamExt = 0xC0;
constexpr uint8_t kExfatEntryTypeFileName = 0xC1;
constexpr uint8_t kExfatEntryTypeAllocBitmap = 0x81;
constexpr uint8_t kExfatEntryTypeUpcaseTable = 0x82;
constexpr uint8_t kExfatEntryTypeVolumeLabel = 0x83;
```

한 "파일"은 항상 `0x85`(Primary) 1개 + `0xC0`(Stream Extension) 1개
+ `0xC1`(File Name) N개(이름이 15자를 넘으면 여러 개 연속) 순서로
`secondaryCount`개의 보조 엔트리가 뒤따른다. **`setChecksum`은 읽기
시 검증, 쓰기 시 반드시 재계산**(무결성이 이 체크섬에 의존 - FAT32
에는 없던 exFAT 고유 요구사항).

### 3.6 이름 정규화/해시

경로 세그먼트 비교는 Up-case 테이블(§3.4)로 두 이름을 각각
정규화한 뒤 비교 - **8.3 짧은 이름 개념 자체가 없다**(exFAT이
FAT32/16 대비 오히려 단순해지는 지점 - `libvfat`의 LFN 체크섬 같은
별도 서브포맷이 필요 없음, 이름은 항상 `0xC1` 엔트리 체인 하나로
충분). `nameHash`(§3.5)는 정규화된 이름에 대한 단순 회전+가산 해시
(정확한 알고리즘은 구현 착수 시 스펙 재확인 - 이 문서가 알고리즘
의사코드까지 단언하지 않음, §1 재확인 경고 그대로).

## 4. `ExfatDriver` 구현 — `FileSystemDriver`(`kernel::KernelFsDriver` 확장) 인터페이스

**[해소, 2026-09-22, `QU-08ACD701` 설계자 답변("양쪽 모두를 수정하면서
구현해")]** `SP-2BCE5D60` §3.1이 전면 재작성됐다 - `FileSystemDriver`는
`kernel::KernelFsDriver`(`minicore/kernel/mount_table.h`,
`AsyncTaskHandler` 상속)를 확장하는 것으로 재정의됐다. 새 타입을
정의하지 않고 `mount_table.h`가 이미 가진 `VfsError`/`FileHandle`/
`OpenResult`/`ReadResult`/`VfsDirEntry` + `KernelFsOpCode` 9종 Args
구조체를 그대로 재사용한다 - `libext4`(`SP-7A9CED3E` §4)와 동일한
패턴.

**[추가, 2026-09-22, `PN-9AE5BFE4`/`PN-6EDED542` 실측 발견 - 착수 시 필독]**
`onExec()`는 진짜 C++20 코루틴(`AsyncExecCoro` 반환)으로 구현해야
하며, 그 안에서 `device_->readBlocks()`/`writeBlocks()` 같은 동기
래퍼(`AsyncTaskWaitGroup::waitAll()` 기반)를 직접 호출하면 실제로
무한 대기한다(코루틴 모드 `onExec()`이 `AsyncReactor::drainOnce()`의
C++ 호출 스택 위에서 직접 실행되기 때문 - 자세한 원인은
`SP-F682B889` §9.5 항목3). I/O가 필요한 지점은 반드시
`co_await kernel::AsyncTaskCoroAwaiter(device_->submitReadBlocks(...))`
패턴(같은 절에 정확한 코드 있음)을 써야 한다. **추가 제약**(`PN-9AE5BFE4`
Ext4Driver가 실제 재현으로 확인, `SP-F682B889` §9.5-3 2026-09-22
정정 문단 참고): I/O 헬퍼를 별도 코루틴 함수로 뽑아 `onExec`이 그걸
`co_await`하는 합성은 **컴파일은 되지만** `AsyncTaskCoroAwaiter::
await_suspend()`가 재개 대상을 항상 최상위 `onExec` 자신의
`AsyncTask`로 고정해 실행 시 그 중간 코루틴 프레임이 영원히 재개되지
않는다 - 그래서 이런 factoring은 쓸 수 없다. §4.1/4.2의
헬퍼(경로 해석/비트맵 갱신 등)는 전부 평범한 비-코루틴 함수로 두고,
실제 `co_await` 지점은 `onExec()` 자신의 코루틴 프레임 안에만 두는
"평탄화" 구조로 구현할 것(`PN-9AE5BFE4`의 Ext4Driver가 이미 같은
패턴을 적용 중이니 참고 가능).

```cpp
// minicore/libs/libexfat/exfat.h
class ExfatDriver : public FileSystemDriver {  // FileSystemDriver : kernel::KernelFsDriver
public:
    bool mount(BlockDevice* device, bool readOnly) override;
    bool remount(bool writable) override;
    // 파일 op 9종은 onExec 하나로 - args의 KernelFsOpCode 태그로
    // 분기해 §4.1/4.2의 무상태 함수를 그대로 호출하고 결과를 해당
    // KernelFsXxxArgs에 채운다(mount_table.h의 LiveFs/ProcFs와 동일 관례).
    void onExec(AsyncTask* task, void* args) override;
    void onFailure(AsyncTask* task) override;
    void onCancel(AsyncTask* task, void* args) override;

private:
    BlockDevice* device_ = nullptr;
    ExfatBootSector bs_{};
    uint32_t sectorSize_ = 0;      // 1 << bs_.bytesPerSectorShift
    uint32_t clusterSize_ = 0;     // sectorSize_ << bs_.sectorsPerClusterShift
    uint8_t* allocBitmap_ = nullptr;  // §3.3, 온디스크 파일 캐시
    uint16_t* upcaseTable_ = nullptr; // §3.4, 온디스크 파일 캐시
    bool readOnly_ = true;
};
```

`mount()`/`remount()`는 `AsyncTaskHandler` 프로토콜과 별개로
`MountTable::mountKernel()` 등록 전/후 한 번만 동기 호출되는 준비
단계라 일반 가상함수로 남는다.

### 4.1 경로 해석/읽기/쓰기

루트는 `firstClusterOfRootDirectory`부터 시작하는 클러스터 체인(§3.2)
- 그 안의 32바이트 엔트리들을 순회하며 `0x85` 시작 엔트리를 만날
때마다 그 파일 집합(§3.5)을 통째로 파싱해 이름(§3.6 정규화 후 비교)
이 일치하는지 확인. `open`/`read`/`write`는 `ExfatStreamExtEntry`의
`firstCluster`/`dataLength`/`NoFatChain`으로 논리 오프셋 → 물리
클러스터를 계산(§3.2 - NoFatChain이면 산술만으로 끝, 아니면 FAT
순회).

### 4.2 `mkdir`/`unlink`

`mkdir`: 새 클러스터 할당(§3.3 비트맵 갱신) + 부모 디렉터리에 새
엔트리 집합(0x85+0xC0+0xC1×N) 추가 + `setChecksum` 계산. `unlink`:
대상 엔트리 집합 전체의 `entryType` InUse 비트(0x80)를 클리어해
"삭제됨"으로 마킹(FAT32의 `0xE5`에 대응하는 exFAT 관례) + 클러스터
체인을 비트맵에서 해제.

## 5. 이 문서가 확정하지 않는 것

- `nameHash` 정확한 해시 알고리즘(§3.6) - 구현 시 스펙 재확인 필요.
- Up-case 테이블의 기본값(스펙이 제공하는 참조 테이블) - 볼륨 자신의
  테이블을 항상 읽어 쓰므로 v1엔 필요 없으나, **새 볼륨을 이
  라이브러리로 직접 포맷(mkfs 역할)하게 되면** 그때는 필요(현재
  범위 밖 - mkfs는 이 문서가 다루는 마운트/읽기/쓰기와 별개 기능).
- 타임스탬프 인코딩 세부(§3.5 `createTimestamp` 등) - `libvfat`과
  유사한 FAT 계열 인코딩으로 추정되나 정확한 비트 배치는 구현 시
  재확인.

## 6. 다른 설계와의 관계

- `SP-2BCE5D60` §3.1/§3.0 — 이 문서가 구현하는 `FileSystemDriver`/
  `BlockDevice` 인터페이스의 출처.
- `SP-A658A124` — 이 opinion이 원래 달렸던 문서(libvfat, FAT32/16) -
  exFAT은 그 후속 포맷이지만 완전히 별도 라이브러리로 분리(§1).
- `SP-D02C4A73`/`SP-7A9CED3E` — 같은 "외부 표준 준수 + 단계적
  로드맵" 원칙의 선례.
- `RM-7C249618` — 이 문서 승인 후 `libexfat` 신규 행 추가 필요
  (CLAUDE.md 규칙8).
