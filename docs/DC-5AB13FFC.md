# 커널 서비스 내부 알고리즘 및 라이선스 — 요구분석

## 배경

SP-8B6B8D25 §2~3은 커널/커널 서비스가 "무엇을 책임지는지"(스코프)와
"어느 디렉터리에 배치되는지"까지는 확정했지만, 각 책임을 실제로 어떤
알고리즘/포맷으로 구현할지는 비어 있다. 이 문서가 다루는 7가지는
서로 다른 하위 시스템에 걸쳐 있어 각각 별도로 결정돼야 하지만, 전부
"SP에 스코프는 있으나 내부 설계가 없는 항목"이라는 공통점으로 한
DC에 묶었다 — 실제 구현(코드 작성)이 시작되기 전, 각 항목별로 별도
SP/DS 문서가 추가로 필요할 만큼 큰 결정들이다.

## 결정이 필요한 항목과 각 선택의 영향

1. **메모리 할당자**: `libkmm`이 구현할 실제 할당 알고리즘(예: buddy
   allocator + slab, 다른 방식) — SP §2.6~2.8(NUMA/SWAP/페이지 병합)의
   실제 구현 난이도를 좌우한다.
2. **스케줄러 알고리즘**: SMP 환경 스케줄링 정책(CFS류/우선순위 기반/
   MLFQ 등)과 코어 간 로드밸런싱 — SP §2.2(SMP)의 구체화.
3. **IPC 메시지 포맷**: SP §2.3("IPC를 해석해 메시징 채널로 전파")의
   실제 직렬화 방식/포맷.
4. **공개 인터페이스 registry 스펙**: SP §2.12(프로세스간 "공개
   인터페이스" registry, 제어 채널 중계)가 실제로 어떤 API/프로토콜로
   동작하는지.
5. **procfs 스키마**: SP §2.13(procfs 루트) 아래 실제로 노출할 항목의
   구체 스키마.
6. **devmgr 드라이버 모델**: 디바이스 드라이버를 커널 내장으로 둘
   기준과 유저랜드 서비스로 둘 기준(PCIe/USB 등 IO 권한 부여 대상의
   구체적 분류 기준) — SP §2.5, §3.1(devmgr 서비스)과 연결된다.
7. **라이선스**: 이 프로젝트(minicore) 전체에 적용할 오픈소스 라이선스 —
   외부 기여/배포 방식에 영향을 주므로 코드가 쌓이기 전에 정하는 편이
   낫다.
