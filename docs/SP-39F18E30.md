# DMA 버퍼 관리자 및 메모리 관리자 확장 — 설계 제안

설계자 지시(2026-09-14, 메시지) - "DMA 버퍼 관리자는 설계하고 메모리
관리자와 관련된 설계사항 수정안 만들어놔." AHCI(SP-C2670F69 §3.2/§4-1)와
USB(SP-E35FD36C §3.2/§4-1)가 공통으로 남겨 둔 미결 문제 - devmgr(유저
프로세스)이 컨트롤러가 DMA로 직접 접근할 물리적으로 연속인 메모리를
확보하고 그 물리 주소를 알아내는 방법 - 을 실제 syscall과 커널 내부
자료구조로 구체화한다.

## 1. 배경

이 프로젝트는 물리 메모리 관리를 철저히 커널에만 집중시키는 원칙
(SP-8B6B8D25 §2 6/7번, §2-A)을 따른다 - 유저 프로세스가 자기 페이지의
물리 주소를 직접 조회하는 syscall은 그 원칙에 어긋나고 보안/추상화
측면에서도 더 무겁다(AHCI 제안 §3.2의 (b) 후보 기각 사유와 동일). 따라서
**"커널이 DMA 가능 버퍼를 대신 확보해 물리 주소와 함께 내주는" 방향
(AHCI 제안 §3.2의 (a) 후보)을 그대로 채택**해 이 문서에서 구체화한다.

기존 `PageFrameAllocator`(`minicore/kernel/page_frame_allocator.h`)는
이미 `allocOrder(order)`/`allocOrderOnNode(node, order)`로 2^order개
연속 물리 페이지(버디 할당자)를 내줄 수 있다 - 물리적 연속성 자체는
이미 해결된 문제다. 남은 것은 (1) 이걸 유저 프로세스 주소공간에 매핑해
가상/물리 주소 쌍으로 돌려주는 syscall, (2) 레거시 컨트롤러가 요구하는
"32비트 이내 물리 주소" 제약(§5 참고), (3) 프로세스 종료 시 자원 회수다.

## 2. Syscall API 제안

```cpp
// PnP 제안(SP-9DD4F3EA §3.3)의 RequestIoPermissionArgs와 같은 층위 -
// SyscallRegistry에 등록(PL-21344323 패턴 재사용).
struct AllocDmaBufferArgs {
    uint64_t sizeBytes;        // in: 요청 크기(내부에서 4KiB 페이지 단위로 올림)
    uint32_t physAddrLimit;    // in: 0=제한 없음(64비트 전역),
                                //     32=하위 4GiB 이내로 강제(레거시
                                //     UHCI/OHCI/EHCI용, §5 참고)
    // out
    ChannelError error;        // OutOfMemory / InvalidArgument(0바이트 등)
    uint64_t virtualAddr;      // devmgr 프로세스 주소공간에 매핑된 가상주소(페이지 정렬)
    uint64_t physicalAddr;     // 컨트롤러 DMA 구조체에 그대로 채워 넣을 물리주소(시작점, 물리적으로 연속)
    uint32_t handle;           // FreeDmaBuffer/프로세스 종료 시 정리용 식별자
};

struct FreeDmaBufferArgs {
    uint32_t handle;
    // out
    ChannelError error;        // InvalidHandle(이미 반납됐거나 존재하지 않음)
};
```

devmgr은 컨트롤러별 DMA 구조체(AHCI의 Command List/FIS, xHCI의
Command/Event/Transfer Ring, 레거시의 Frame List/QH/TD 등)를 만들
때마다 이 syscall로 필요한 만큼 확보하고, `physicalAddr`를 그대로
컨트롤러 레지스터/디스크립터에 채워 넣는다.

## 3. 커널 구현

### 3.1 할당 경로

1. `sizeBytes`를 4KiB 페이지 수로 올림 → 그 값을 담을 수 있는 최소
   `order`(2^order ≥ 페이지 수) 계산.
2. `physAddrLimit == 32`이면 §5-B의 `PageFrameAllocator::allocOrderBelow`
   (신규)를 호출, 아니면 기존 `allocOrder(order)`를 그대로 호출.
3. 확보한 물리 블록을 그 프로세스(devmgr)의 주소공간에
   `Paging::mapPage(virtAddr, physAddr, PAGE_USER | PAGE_CACHE_DISABLE,
   process->pml4Phys)`로 페이지 단위 매핑(§3.3 캐시 속성 참고).
4. 매핑에 쓴 가상주소 범위는 §3.2의 프로세스별 커서에서 뽑는다.
5. `Process`(§4 확장)에 `{physAddr, virtAddr, pageCount, handle}`를
   기록하고 `handle`을 발급.

### 3.2 가상주소 커서 (v1 단순화)

SP-8B6B8D25 §5-A는 코드(0x400000)/스택(끝점에서 하향)만 확정했고
"힙(brk)/mmap 영역의 정확한 경계는 아직 미정"이라고 명시했다 - DMA
매핑 전용 영역도 같은 미확정 공간의 일부다. 이 문서는 전체 mmap 설계를
확정하는 것은 범위 밖으로 두고, **v1 최소 범위**만 제안한다: 프로세스별로
"다음 DMA 매핑에 쓸 가상주소" 커서 하나를 `Process`에 두고, 코드/스택과
겹치지 않을 충분히 낮은 고정 상수(예: 코드 공간 바로 위쪽 - 정확한 값은
힙 레이아웃이 확정될 때 같이 정해야 하므로 지금은 자리만 예약)에서
페이지 크기만큼씩 증가시키며 내준다(bump 방식, 반납 시 재사용 없음 -
v1 devmgr은 부팅 초기에 필요한 DMA 버퍼를 몇 번만 확보하므로 충분).
실제 mmap/brk 서브시스템이 생기면 이 커서는 그 안으로 흡수되어야 한다
(후속 과제로 명시).

### 3.3 캐시 속성

컨트롤러가 DMA로 직접 읽고 쓰는 메모리이므로 CPU 캐시와의 일관성이
문제가 된다 - 이 프로젝트는 아직 캐시 스누핑(하드웨어 캐시 코히런시)
여부를 확정하지 않았으므로, 안전한 기본값으로 **`PAGE_CACHE_DISABLE`
(UC, uncached)**를 제안한다(PnP의 MMIO 매핑과 동일 속성 재사용). 성능이
문제가 되면 write-combining(PAT 활용)으로 전환을 검토할 수 있으나 이는
숫자/속성 튜닝 수준이라 별도 DC 없이 구현 중 계측으로 판단한다
(RM-23F4B687 §4 취지).

## 4. `Process` 확장 (소유권 추적, 자원 회수)

`minicore/kernel/process.h`의 `Process`에 DMA 버퍼 목록을 추가한다 -
`UserThread::pendingSyscalls`와 동일하게 `ChunkedList`(libkenv,
할당자는 함수 포인터 주입)를 재사용:

```cpp
struct DmaBuffer {
    uint64_t physAddr = 0;
    uint64_t virtAddr = 0;
    uint32_t pageCount = 0;   // freeOrder 호출 시 order 역산에 필요
    uint32_t handle = 0;
    bool used = false;        // ChunkedList::Slot 관례 재사용
};

// Process에 추가
uint64_t nextDmaVirtAddr = kDmaRegionStart;  // §3.2의 bump 커서
ChunkedList<DmaBuffer, kDmaBufferChunkCapacity> dmaBuffers;
```

`Process::destroy()`(현재는 PML4 프레임만 반납, 하위 절반 매핑 해제는
호출부 책임이라고 명시돼 있음)가 실제로 구현될 때, 이 목록을 순회하며
`Paging::unmapPage` + `PageFrameAllocator::freeOrder`로 각 DMA 버퍼를
먼저 반납하는 절차가 필요하다는 것을 여기 기록해 둔다(지금은 `Process`
자체가 "주소공간 소유 + 유저 폴트 정보"만 다루는 범위라 아직 구현하지
않음 - PN-16CA347D 로드맵의 프로세스 종료 시퀀스가 실제로 만들어질 때
반영).

## 5. 메모리 관리자(`PageFrameAllocator`) 확장안

### 5-A. 왜 필요한가 - 레거시 호스트 컨트롤러의 32비트 DMA 제약

UHCI/OHCI/EHCI(USB(SP-E35FD36C) §6에서 다루는 레거시 컨트롤러들)는
설계 시기상 **DMA 구조체(Frame List/Queue Head/Transfer Descriptor/
HCCA 등)의 물리 주소가 전부 32비트 레지스터/필드**로 정의돼 있다 -
64비트 물리 주소를 통째로 담을 수 없다. xHCI/AHCI는 64비트 물리
주소 필드를 갖고 있어 문제가 없지만, 레거시 컨트롤러를 지원하려면
**"하위 4GiB 이내"라는 물리 주소 제약을 만족하는 할당**이 반드시
필요하다 - 이것이 바로 이번 확장안의 동기다.

### 5-B. 신규 API: `allocOrderBelow`

```cpp
// page_frame_allocator.h에 추가 제안
class PageFrameAllocator {
public:
    // ... 기존 API ...

    // physLimit 미만의 물리주소 범위에서만 2^order 페이지 블록을
    // 찾는다(레거시 DMA 32비트 제약용, physLimit=0x1'0000'0000이면
    // "4GiB 미만"). 실패 시 0.
    static uint64_t allocOrderBelow(uint64_t physLimit, uint32_t order);
};
```

### 5-C. 구현 방향과 열린 문제

현재 버디 할당자의 각 NUMA 노드/order별 프리리스트는 (PL-99562483에서
확정된 대로) 물리주소를 직접 담는 단일 연결 리스트로 구현돼 있다 -
**주소 순으로 정렬돼 있지 않다.** `allocOrderBelow`가 이 제약을
만족하려면 두 가지 구현 후보가 있다:

- (a) **선형 탐색**: 해당 order의 프리리스트를 처음부터 순회하며
  `physAddr + (4KiB << order) <= physLimit`를 만족하는 첫 블록을
  찾아 분리(unlink)한다 - 구현이 간단하지만 워스트케이스(리스트가
  길고 조건을 만족하는 블록이 리스트 끝에 있거나 없는 경우) 비용이
  O(n)이다. **DMA 버퍼 확보는 드라이버 초기화 시점(포트/컨트롤러당
  한 번)에만 일어나는 저빈도 연산**이므로 v1은 이 방식으로 충분하다고
  제안한다.
- (b) **저지대 전용 별도 프리리스트**: 부팅 시 4GiB 미만 영역을
  별도 풀로 미리 분리해 관리 - 탐색은 빨라지지만 일반 할당
  (`allocOrder`)과 풀이 나뉘어 파편화/회계가 복잡해진다. 레거시
  컨트롤러 지원 자체가 "실제 구형 하드웨어 요구가 생기면"이라는
  조건부 후속 과제(USB 제안 §6 참고)이므로, 지금 이 복잡도를 감수할
  근거가 부족하다.

**이 문서는 (a) 선형 탐색을 v1 제안으로 채택**한다 - 성능이 실제로
문제가 되는 시점(레거시 컨트롤러 구현 착수 시점)에 실측하고 필요하면
(b)로 전환하는 것을 후속 과제로 남긴다(숫자/자료구조 튜닝 수준이라
별도 DC 불필요, RM-23F4B687 §4 취지).

### 5-D. NUMA와의 상호작용

`allocOrderBelow`는 노드를 지정하지 않는다 - 4GiB 미만 물리 메모리가
어느 NUMA 노드에 속하는지는 SRAT 메모리 어피니티에 달려 있고(보통
노드 0에 저지대가 몰려 있음), 레거시 DMA 버퍼는 애초에 흔치 않은
저빈도 요청이므로 노드별 지역성보다 "제약을 만족하는 아무 블록"을
우선한다 - 모든 노드의 해당 order 프리리스트를 순서대로 훑는 구현을
제안한다(`allocOrder`가 이미 "현재 코어 노드 우선, 바닥나면 다른
노드로" 하는 것과 다른 정책이지만, 이 경우엔 지역성보다 제약 충족이
우선이라는 점이 다르다).

## 6. 아직 열려 있는 설계 영역

1. **DMA 매핑 전용 가상주소 영역의 최종 경계**: §3.2에서 "자리만
   예약"한 bump 커서는 SP-8B6B8D25 §5-A가 아직 미정으로 남긴 힙/mmap
   레이아웃이 확정되면 그 안으로 흡수돼야 한다 - 지금 당장 별도 DC로
   답을 구할 만큼 급하지 않다(실제 mmap 서브시스템 설계 시점에 자연히
   해소).
2. **`allocOrderBelow`의 탐색 비용**: §5-C에서 이미 논의 - 실측 전까지
   선형 탐색으로 진행.
3. **프로세스 종료 시 DMA 버퍼 일괄 반납 절차**: §4에서 이미 언급 -
   `Process::destroy()`의 실제 구현이 아직 없어 지금은 자료구조 자리만
   설계.

## 7. 선행 조건

- 프로세스 모델(PN-16CA347D) - `Process::dmaBuffers` 등 확장 대상 자체.
- `PageFrameAllocator::allocOrder`(이미 구현 완료, PL-99562483) - 물리
  연속성 확보의 기반.
- `libkenv::ChunkedList`(이미 구현 완료) - 소유권 추적 자료구조 재사용.
- PnP의 IO 권한 부여 syscall(SP-9DD4F3EA §3.3) - 이 문서의 syscall과
  같은 층위/패턴으로 함께 `SyscallRegistry`에 등록될 예정.
