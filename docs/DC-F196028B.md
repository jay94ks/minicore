# UEFI 직접 부팅 - 메모리맵/ACPI RSDP를 kMain에 전달하는 방법

`PN-7FBF255A`(BIOS/UEFI 직접 부팅 경로 구현)가 `SP-CC2B18C6`(승인됨)
의 마커 기반 재배치 메커니즘을 구현해 실제로 `kMain`까지 도달시키는
데 성공했다(commit `0865640`, 이번 세션). 하지만 `SP-CC2B18C6` §4/§5가
"이 설계가 명시적으로 다루지 않는 것"으로 이미 분류해 둔 대로,
UEFI가 `GetMemoryMap()`으로 확보한 실제 메모리맵과 ACPI RSDP 물리
주소를 커널에 넘기는 방법이 아직 없다.

## 현재 상태 (실측)

`kmain.cpp`의 `kBootProtocolUefi` 분기는 지금 `memmap=nullptr`,
`memmapEntries=0`, `rsdpPaddr=0`으로 둔 채(기본값 그대로) 진행한다.
실제 QEMU+OVMF 부팅 로그:

```
minicore: booted via UEFI direct boot (relocated, physicalBaseDelta=1800000)
minicore: GDT ready
minicore: IDT ready
minicore: memory map (0 entries)
minicore: direct physical map ready
minicore: ACPI MADT parse FAILED   <- rsdpPaddr=0이라 파싱 자체가 안 됨
minicore: page frame allocator ready, nodes=1 free_pages=0
minicore: slab allocator ready (libkmm)
```

`free_pages=0`이라 이 경로는 프로세스를 스폰하거나 스케줄러를
실제로 구동할 수 없다 - 다음 단계로 진행하려면 반드시 필요하다.

## 이미 확립된 관련 기법 (재사용 가능한 전례)

`SP-CC2B18C6`이 정확히 같은 종류의 문제(별도 빌드 트리인 UEFI
로더가 커널 내부의 링크 타임 상수를 알아야 함)를 "매직 넘버 마커를
boot.S에 데이터로 박아 두고 UEFI 로더가 스캔해서 찾는다"는 방식으로
이미 두 차례 확장했다(`long_mode_entry`/`pml4`/`saved_start_info`/
`gdt64` 물리주소 4개 필드). `saved_start_info`/`saved_boot_protocol`은
"UEFI 로더가 원본(비재배치) 물리주소에 직접 스칼라 값을 써서
커널에 4바이트 정수 하나를 전달하는 스크래치 채널"로도 이미
쓰이고 있다(현재 physicalBaseDelta 전달에 사용 중).

메모리맵은 스칼라 하나가 아니라 **가변 길이 배열**이라 이 정확히
같은 스크래치 채널 패턴을 그대로 쓸 수는 없다 - 배열 자체를 어딘가
물리 메모리에 써 두고 그 "시작 주소 + 개수"만 스칼라로 전달하는
방식이 필요해 보이지만, 그 "어딘가"를 정하는 것 자체가 새로운 설계
결정이라 임의로 정하지 않는다(CLAUDE.md 규칙4).

## 결정이 필요한 지점

1. **메모리맵 전달 방식**: 후보 (a) UEFI 로더가 `HvmMemmapEntry`
   포맷(기존 PVH/GRUB 경로와 동일한 통일 구조체, `Multiboot2Info`가
   이미 이 포맷으로 변환해 재사용 중)으로 변환한 배열을 재배치된
   커널 이미지 안의 정적 버퍼(예: `.bss`에 예약해 둔 고정 크기
   배열)에 써 넣고, 그 배열의 "시작 물리주소"와 "개수"를 커널에
   전달할 두 번째/세 번째 스크래치 채널(마커에 그 정적 버퍼 심볼의
   원본 주소 추가)로 넘기는 방법 (b) 완전히 별도의 UEFI 전용
   전달 구조체를 새로 설계하는 방법 (c) 그 외 설계자가 선호하는
   다른 방식.
2. **ACPI RSDP 전달**: UEFI는 `EFI_SYSTEM_TABLE`의
   `ConfigurationTable`을 순회해 ACPI GUID로 RSDP를 이미 쉽게 찾을
   수 있다(BootServices만 있으면 됨, ExitBootServices 이전) - 이
   물리주소 하나(8바이트)는 스칼라라 saved_start_info와 같은
   패턴으로 전달 가능해 보이나, `saved_start_info` 자리는 이미
   physicalBaseDelta로 쓰고 있어 **별도의 스크래치 필드가
   하나 더 필요**하다 - 어디에(boot.S에 새 전용 필드를 추가할지,
   아니면 위 1번 메모리맵 채널과 같은 구조체에 합쳐 보낼지) 둘지도
   결정이 필요하다.
3. **스크래치 채널 자체의 확장성**: 지금처럼 필요할 때마다 boot.S에
   필드를 하나씩 추가하는 방식(현재 4개: pml4/entry/savedStartInfo/
   gdt64)을 메모리맵/RSDP까지 계속 이어갈지, 아니면 이 시점에
   "UEFI 전용 부팅 정보 구조체 하나"로 통합 설계할지 - 후자가
   더 깔끔해 보이지만 이미 동작 중인 마커 메커니즘을 다시 바꾸는
   범위가 있어 설계자 판단이 필요하다.
