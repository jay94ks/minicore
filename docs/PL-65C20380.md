# 실행 계획: SMP AP(나머지 코어) 기동

**[완료, 2026-09-14 - 계획 PN-BBF6CA37]** QA-26450C3E 체크됨. 아래는 완료 기록으로 남긴다.

ACPI MADT로 코어 목록/APIC ID 확보(완료), LAPIC 초기화(완료)까지는
끝났었다. 이 계획은 실제로 BSP 말고 나머지 코어(AP)를 깨워 커널
코드를 실행시키는 부분이었다.

## 선행 조건

- Acpi::cpuCount()/cpuApicId() (완료)
- Lapic (완료, ICR 레지스터는 이번에 추가)
- PageFrameAllocator (완료 - AP별 스택 할당에 씀)

## 한 것

0. **[이전에 완료, 2026-09-14] 최소 스핀락/원자 연산 프리미티브**
   (QU-B97FDA44) - 이번 작업의 `AtomicU32`(기동 완료 카운터)로
   실제로 쓰였다.
1. **16비트 실모드 트램폴린**: `minicore/arch/x86_64/ap_trampoline.S`
   신설. AP가 SIPI(벡터 0x08 = 물리주소 0x8000)를 받으면 16비트
   실모드로 시작 - 자체 임시 GDT(null+code32+data32, 실모드에서
   닿는 낮은 주소에 따로 둠, boot.S의 진짜 gdt32_ptr는 1MiB 근처라
   16비트에서 못 가리킴)로 32비트 보호모드 진입 → boot.S의 진짜
   (공유) GDT로 다시 로드 → `enable_long_mode`(boot.S 재사용,
   `.global`로 노출) 호출(코어별 CR3/CR4/EFER/CR0 설정이라 매번
   실행 필요 - `setup_page_tables`는 이미 다른 코어가 쓰는 페이지
   테이블을 망가뜨리므로 절대 다시 안 부름) → 64비트
   `ap_long_mode_entry` → C++ `kApMain(apIndex)`.
2. **트램폴린 배치(미결 사항이었던 부분)**: 처음엔 링커 스크립트로
   물리주소 0x8000에 대응하는 별도 PT_LOAD 세그먼트(`:aptramp`)를
   만들어 정적 예약하려 했으나, **QEMU의 PVH 직접 부팅 로더가 그
   세그먼트를 게스트 메모리에 아예 안 올리는 걸 실측으로 발견**
   (`xp` 모니터 명령으로 0x8000이 전부 0임을 확인 - ELF 파일 자체엔
   올바른 바이트가 있었음, 로더가 저지대/추가 PT_LOAD를 거르는
   것으로 보임). 그래서 최종적으로: 트램폴린의 **VMA(링크 주소)는
   여전히 0x8000**(16비트 코드의 내부 절대주소 참조가 실행 주소와
   일치해야 해서)로 두되, **LMA(파일에 실제로 저장되는 물리 위치)는
   이미 정상 로드됨이 검증된 `:boot` 세그먼트 바로 뒤**에 별도
   PT_LOAD(`:aptramp`, p_vaddr=0x8000, p_paddr=:boot 뒤)로 붙이고,
   **부팅 후 커널이 직접 `memcpy`로 진짜 0x8000에 복사**하는 방식으로
   전환했다(`Smp::startApCores()`가 AP를 깨우기 전 1회 실행).
   결과적으로 "정적 예약이냐 동적 할당이냐"는 미결 사항이 "링크는
   정적 주소로 하되 로딩은 커널이 직접 memcpy"라는 제3의 방식으로
   확정됐다 - 0-2MiB는 `page_frame_allocator.cpp`의 `kLowReservedEnd`
   가 이미 통째로 예약해 둬서 memcpy 대상 0x8000 자체는 별도 예약이
   필요 없었다.
3. **AP별 자원 준비**: `PageFrameAllocator::allocOrder`로 AP 하나당
   32KiB 스택을 확보, `ap_boot_stack_top`/`ap_boot_index`(boot.S
   스타일의 BSP-AP 핸드오프 스크래치, `.boot.data`)에 기록 - 순차
   기동(한 번에 AP 하나)이라 슬롯 하나를 공유해도 안전.
4. **Lapic ICR read/write 추가**: `Lapic::sendInitIpi(destApicId,
   assert)`/`sendStartupIpi(destApicId, vector)` - xAPIC(ICR_LOW
   0x300+ICR_HIGH 0x310, 두 32비트 레지스터, delivery status 폴링
   필요)과 x2APIC(MSR 0x830 하나, 64비트 통합, 항상 동기 완료)의
   차이를 내부에서 분기(PL-D65F49CC 설계 당시부터 예견된 차이 -
   readRegister/writeRegister로 일반화 불가능했던 유일한 레지스터).
5. **BSP의 기동 시퀀스**: `Smp::startApCores()` - 코어마다 INIT
   어서트 → 1틱 대기 → INIT 디어서트 → 1틱 대기 → SIPI → 1틱 대기 →
   `AtomicU32` 카운터가 기대값에 도달할 때까지 Timer 틱 기반
   타임아웃(50틱=500ms) 대기, 실패 시 SIPI 재전송 후 한 번 더 대기
   (구식 CPU 대응).
6. **동기화**: `AtomicU32 gApStartedCount` - 각 AP가 `kApMain`에서
   기본 초기화를 마치면 `fetchAdd(1)`.
7. **AP 진입 후**: `kApMain`이 `Idt::reloadOnThisCore()`(신설 - IDT
   내용은 전역 공유라 다시 안 만들고 이 코어의 IDTR만 로드)와
   `Lapic::init()`(코어별 MSR/MMIO라 매번 실행 필요, 순차 기동이라
   동시성 문제 없음)만 실행 - `Acpi::init`/`PageFrameAllocator::init`
   같은 전역 서브시스템 재초기화는 절대 안 함. 이후 자기 APIC ID를
   시리얼에 찍고 무한 `hlt` 루프(idle, 스케줄러 생기기 전까지 할
   일 없음). **[2026-09-14 이후 갱신]** 스케줄러(PL-2D3184BC) 도입
   이후로는 이 idle hlt 루프가 `Scheduler::runLoop()`로 대체돼
   AP도 실제로 Task를 받아 실행한다(QA-26450C3E "SMP 환경에서 여러
   코어가 스케줄링된다" 항목이 그 시점 실측으로 갱신됨).
8. **검증(실측, 2026-09-14, QEMU 8.2.2)**: `-smp 2/4/8`에서 기대한
   개수(1/3/7)만큼 AP가 정확히 기동, 각자 올바른 APIC ID를 찍음을
   확인. 기본(smp 미지정, 1코어)에서도 "APs started=0 expected=0"
   으로 정상 처리(회귀 없음). x2APIC(`-accel kvm -cpu host`)과
   multiboot2(GRUB ISO, `scripts/run-grub.sh`) 경로 둘 다에서도
   `-smp 4`로 동일하게 동작 확인 - 이 프로젝트의 부팅 경로/APIC
   모드/인터럽트 컨트롤러/타이머/PCI 서브시스템이 SMP AP 기동과도
   전부 호환됨을 실측으로 증명했다.

## 실측 중 발견한 진짜 버그 2개

1. **QEMU PVH 로더가 저지대 전용 PT_LOAD 세그먼트를 안 올림** - 위
   2번 항목 참고. `xp` 모니터 명령으로 게스트 물리 메모리를 직접
   들여다봐서 발견(ELF 파일 자체는 정상이었음 - `objdump`/`xxd`로
   대조 확인).
2. **AP의 스택 포인터 미설정** - SIPI 직후 ESP/SP가 정의되지 않은
   채로 시작하는데, 32비트 스텁 진입 직후 `push`+`retf`(GDT 재로드용
   far jump 트릭)를 바로 쓰면서 쓰레기 스택에 접근해 조용히 멈췄다
   (증상: 16비트/32비트 진입 브레드크럼은 찍히는데 그 이후로 전혀
   진행이 안 됨). 트램폴린 전용 임시 스택(<0x10000 - 16비트 real
   mode SP 레지스터 제약 때문에 반드시 낮은 트램폴린 페이지 안에
   둬야 함)을 추가해 16비트 진입 직후와 32비트 진입 직후 둘 다에서
   명시적으로 ESP/SP를 설정하도록 고쳤다. 디버깅은 포트 0x3F8(COM1)
   직접 바이트 쓰기로 각 전환 지점마다 "브레드크럼"을 남겨 어디서
   멈췄는지 이분탐색으로 좁혔다 - GDT/paging/Serial 클래스 전부가
   아직 준비 안 된 극초반 코드를 디버깅할 때 재사용 가능한 기법으로
   관계도에 기록.

  APIC ID를 찍고 idle에 들어간다"까지였다 - **스케줄러(PL-2D3184BC)

## 미결 사항

- 없음(원래 미결 사항이었던 "트램폴린 정적 예약 vs 동적 할당"은

## 재작업(2026-09-14, QU-CFAA5B3D)

설계자 지시: "AP 개별 LAPIC 타이머도 이번 테스트 범위에 포함시켜.
나중에 사용할거라면 복잡한 작업을 하기 전에 정상작동 여부를 테스트
해야 해." - 스케줄러가 아직 없어 AP 타이머를 실제로 쓰는 코드는 넣지
않되(그건 여전히 범위 밖), LAPIC 자체 주기 타이머가 코어마다 독립
적으로 실제 하드웨어에서 동작하는지는 지금 실측해 뒀다.

- **리팩터**: `Timer::init()`의 LAPIC+PIT 폴백 경로 안에 있던 PIT
  채널2 보정 로직(`kCalibrateLapicTicksPerWindow`)과 LAPIC 타이머
  레지스터 프로그래밍을 `Lapic::startPeriodicTimer(vector, hz)`로
  뽑아 `lapic.cpp`로 옮겼다 - BSP(Timer::init 경유)와 AP(직접 호출)가
  같은 코드를 재사용한다. 공개 API는 동작 변화 없음(같은 로직을
  같은 순서로 실행).
- **AP 타이머 실측(2026-09-14, QEMU 8.2.2)**: 각 AP가 자기 진입 직후
  `Lapic::startPeriodicTimer(테스트벡터, 20)`로 20Hz 주기 타이머를
  켜고, IDT에 임시로 등록한 공용 핸들러(인터럽트가 오면 `Lapic::id()`
  로 "어느 코어에서 왔는지" 판별해 그 코어 전용 카운터만 증가)로
  자기 코어에서만 틱이 쌓이는지 확인했다. `-smp 4`(기본 i440fx),
  `-smp 2`(`-accel kvm -cpu host`, x2APIC 실하드웨어)에서 각 AP가
  독립적으로 정확히 3틱씩(교차 오염 없이) 쌓임을 확인 - LAPIC 타이머가
  코어마다 완전히 독립된 하드웨어임이 실측으로 증명됐다.
- **디버깅 중 발견한 진짜 문제(회귀 아님, 테스트 설계 실수)**: AP의
  틱-대기 루프를 `gApStartedCount.fetchAdd(1)`보다 앞에 두면, BSP의
  AP-준비-확인 타임아웃(500ms)이 이 대기 시간까지 먹어서 실제로는
  정상 기동한 AP를 "did not respond"로 오판하고 SIPI를 중복 전송하는
  현상을 실측으로 확인했다. PIT 채널2 보정(전역 자원, 수 ms)만 순차
  보장하면 충분하고 그 이후 "몇 틱 쌓였는지" 기다리는 부분은 코어
  로컬 LAPIC만 건드리므로, `fetchAdd`를 보정 직후·대기 루프 이전으로
  옮겨서 해결했다 - 향후 AP에 시간이 걸리는 초기화를 추가할 때
  "무엇이 진짜 순차 보장이 필요한 부분인지"를 구분해야 한다는 교훈을
  얻었다.
- 임시 검증 코드(테스트 벡터/카운터 배열/핸들러)는 전부 제거 - 영구
  코드는 `Lapic::startPeriodicTimer` 리팩터만 남았다.
