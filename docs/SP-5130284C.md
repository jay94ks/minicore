설계자 지시(QU-A07B9019 답변, 2026-09-20) - "지금 바로 일반적 해법(SharedPtr 소멸이 유발하는 무거운 정리를 인터럽트 컨텍스트 밖으로 미루는 공용 매커니즘)을 설계/구현하되, 장기적으로는 가비지 컬렉터를 구현하는 방향으로 진행하자." 이 문서는 그 "공용 매커니즘"의 v1 설계다.

## 1. 문제 (PN-4137C88C 요약)

`SharedPtr<T>`(SP-201238BB)가 마지막 강한 참조를 잃으면 그 자리에서 즉시 커스텀 삭제자(예: `Process`의 경우 사실상 `Process::destroy()`)를 동기 실행한다. 이 소멸이 `Scheduler::onTick()`/`onForcedMigration()`(타이머/IPI 인터럽트 컨텍스트, IF=0) 안의 두 확인된 지점(`kSyncDebugRegs`의 `thread->process.lock()`, `onTick():1683`의 CPU 계정 코드)에서 일어날 수 있다.

`Process::destroy()`는 최소 세 개의 서로 다른 `Spinlock`(재진입 불가, libkenv/spinlock.h 자신의 문서 주석)을 잡는다 - `PageFrameAllocator`의 노드별 락(`freeOrder()`), `ResourceGroup::lock`(`removeMember()`), 주소공간별 락(`Paging::destroyAddressSpace()`). 이 코어의 다른 코드가 그 중 하나를 이미 쥔 채 타이머 틱을 맞고, 그 인터럽트 핸들러가 우연히 마지막 참조를 놓치면, 같은 코어가 자기 자신이 쥔 락을 다시 잡으려다 영원히 멈춘다(SMP1이면 전체 시스템 행).

## 2. 기존 인프라 검토 - 왜 그대로 재사용할 수 없는가

- **`DelayedExecutionQueue`(SP-F15B4A63)**: `schedule()`이 매번 `GenericSlabAllocator`에서 새 노드를 할당한다 - 그 할당자도 `Spinlock`(`_rawLock`, libkmm/slab.cpp)을 쓰므로, 인터럽트 컨텍스트에서 이 큐에 넣으려는 시도 자체가 같은 클래스의 재진입 데드락을 다른 락으로 옮길 뿐이다. **채택 불가(그대로는)**.
- **`LockFreeQueue<T, Traits>`(SP-4DCD0E6A §4)**: 알고리즘 자체(Michael-Scott)는 락을 안 쓰지만, `enqueue()`가 `_alloc(sizeof(Node))`로 래퍼 노드를 매번 할당한다 - 그 `AllocFn`이 결국 `GenericSlabAllocator`/`PageFrameAllocator` 등 락 기반 할당자를 가리킬 수밖에 없어 같은 문제. 또한 `enqueue`/`dequeue`가 `RcuReadGuard`로 감싸여 있는데, RCU read-side critical section 자체가 인터럽트 컨텍스트에서 진입 가능한지도 별도 검증이 필요하다(이번 설계에서는 확인하지 않음 - 아래 3번 설계가 이 문제 자체를 피해가므로 불필요). **채택 불가(그대로는)**.

**공통 결론**: 인터럽트 컨텍스트에서 안전하게 "지금 당장 큐에 넣기"가 가능하려면, 그 넣는 동작 자체가 **할당도 락도 전혀 쓰지 않아야** 한다 - 즉 침습적(intrusive) 노드 + 순수 CAS 기반 push만 허용된다.

## 3. 설계 - 침습적 락프리 스택 + SharedPtr 통합 + 안전한 컨텍스트에서 드레인

### 3.1 핵심 아이디어

`SharedPtr<T>`의 컨트롤 블록(참조 카운트 + 삭제자를 이미 담고 있는, 정확히 그 순간 존재하는 메모리)에 **필드 하나**(`next` 포인터)를 추가해, 별도 할당 없이 그 컨트롤 블록 자체를 지연 큐의 노드로 재사용한다 - Treiber 스택(단일 CAS push/pop, 원소 자신이 노드) 패턴.

```cpp
// libkenv/shared_ptr.h, ControlBlockBase 확장
struct ControlBlockBase {
    Atomic<uint32_t> strong{1};
    Atomic<uint32_t> weak{1};
    void (*deleter)(void*) = nullptr;   // 기존 필드(개념적 표기)
    void* ptr = nullptr;                 // 기존 필드(개념적 표기)
    AtomicPtr<ControlBlockBase> deferredNext{nullptr};  // [신규] 지연 파괴 스택 연결용
};

// 신규 전역(코어 무관 - 어느 코어에서 push해도 안전한 CAS 스택)
AtomicPtr<ControlBlockBase> gDeferredDestructionHead{nullptr};

// push - 할당 없음, 락 없음, 순수 CAS 루프. 인터럽트 컨텍스트를
// 포함해 어디서든 안전하게 호출 가능(NMI 포함 - CAS 자체가 원자적).
void kPushDeferredDestruction(ControlBlockBase* block) {
    ControlBlockBase* head = gDeferredDestructionHead.load();
    do {
        block->deferredNext.store(head);
    } while (!gDeferredDestructionHead.compareExchange(head, block));
}

// drain - 안전한(비인터럽트) 컨텍스트에서만 호출. 스택 전체를 한 번에
// 떼어내(head를 nullptr로 원자적 교체) 순회하며 각 컨트롤블록의
// 실제 삭제자를 지금(안전한 곳에서) 실행한다.
void kDrainDeferredDestructions() {
    ControlBlockBase* node = gDeferredDestructionHead.exchange(nullptr);
    while (node) {
        ControlBlockBase* next = node->deferredNext.load();
        node->deleter(node->ptr);   // 원래 여기서 실행됐어야 할 그 삭제자
        next... // 컨트롤 블록 자신의 반납은 기존 kDestroyAndFree 흐름과 동일하게 처리
        node = next;
    }
}
```

### 3.2 "지금 인터럽트 컨텍스트인가" 판정 - 코어별 깊이 카운터

`libs/x86_64/isr.S`의 `isr_common_stub`(모든 벡터가 공유하는 공통 진입점)과 `isr_common_epilogue`(모든 벡터가 공유하는 공통 탈출점 - `iretq` 직전)에 코어별 카운터 증감을 추가한다:

- `isr_common_stub` 진입 직후: 이 코어의 `gInterruptDepth[coreIndex]`를 1 증가.
- `isr_common_epilogue`(실제 `iretq` 직전): 1 감소.

**이 커널의 기존 디스패치 설계(오늘 PN-81E49523이 확립한 `kContextSwitchFromISR` 통일)와 정확히 맞아떨어지는 이유**: `onTick()`/`onForcedMigration()`이 다른 Task로 전환할 때도 항상 그 Task의 캡처된 TaskTcb를 통해 결국 `isr_common_epilogue`의 같은 `iretq`로 착지한다(scheduler.cpp 갱신 주석들이 이미 확인한 사실) - 즉 "어느 Task가 재개되든 정확히 같은 지점에서 인터럽트 컨텍스트를 벗어난다"는 성질이 이미 성립해 있어, 카운터를 그 한 지점에만 걸면 충분하다(개별 반환 경로마다 따로 챙길 필요 없음).

`gInterruptDepth`는 코어별(PerCpu 또는 고정 배열, `Scheduler::currentCoreIndex()`로 인덱싱) - 다른 코어가 읽을 필요가 없으므로 `Atomic` 불필요, 다만 같은 코어 위 중첩 인터럽트(NMI 등)에 안전하려면 단일 명령 증감(`inc`/`dec` on memory operand, 컴파일러 내장 `__atomic_fetch_add`를 "lock" 접두 없이 강제하거나 인라인 asm)이어야 한다 - 구현 시 확정.

`SharedPtr<T>::reset()`(또는 그 경로)의 "참조 카운트가 0이 됨" 분기에서:

```cpp
if (strongCountReachedZero) {
    if (gInterruptDepth[Scheduler::currentCoreIndex()] > 0) {
        kPushDeferredDestruction(block);
    } else {
        block->deleter(block->ptr);
        // 기존 즉시 반납 경로 그대로
    }
}
```

### 3.2-a [정정, 2026-09-20, minicore-8a 검토] `releaseWeak()`/`_freeSelf()`도
반드시 같이 지연해야 함 - `deleter` 호출만 미루면 여전히 데드락 가능

실제 `shared_ptr.h`(`ControlBlockBase::releaseStrong()`)를 대조해 보면,
이 문서 §1이 지적한 위험(락 재진입)은 `_destroyOwned(this)`
(=`_deleter(t)`, 예: `Process::destroy()`) 호출 한 곳에만 있는 게
아니다 - 실제 코드는:

```cpp
void releaseStrong() {
    if (_strongCount.fetchSub(1) == 1) {
        _destroyOwned(this);  // (1) 예: Process::destroy() - 이 문서가 지적한 그 위험
        releaseWeak();        // (2) 암묵적 weak 1개 해제
    }
}
void releaseWeak() {
    if (_weakCount.fetchSub(1) == 1) {
        _freeSelf(this);      // (3) GenericSlabAllocator::free(...) - 이것도 락!
    }
}
```

즉 outstanding `WeakPtr`가 없는 흔한 경우(대부분), `releaseStrong()`
한 번의 호출 안에 **두 개의 서로 다른 위험한 단계**가 연달아
일어난다 - (1) `_deleter`가 잡는 `PageFrameAllocator`/`ResourceGroup::
lock`/주소공간 락(이 문서 §1이 이미 지적)과, (2) `_freeSelf`가
잡는 **`GenericSlabAllocator`의 `_rawLock`**(이 문서 §2가 이미
"그 할당자도 Spinlock을 쓰므로 인터럽트 컨텍스트에서 이 큐에 넣으려는
시도 자체가 같은 클래스의 재진입 데드락을 다른 락으로 옮길 뿐"이라고
`DelayedExecutionQueue`/`LockFreeQueue`를 기각한 바로 그 근거).

**§3.2의 통합 지점 의사코드가 `if (interrupt) push else deleter(ptr)`
로만 표기돼 있어, "인터럽트 컨텍스트에서는 (1)만 미루고 (2)는 그대로
동기 실행한다"로 오독될 여지가 있다** - 실제로 그렇게 구현하면
`GenericSlabAllocator`의 락을 이 코어가 이미 쥔 채 타이머 틱을 맞는
경우(예: 다른 어떤 슬랩 할당/해제 도중) 이 문서가 고치려는 것과
정확히 같은 클래스의 데드락이 `_freeSelf` 경로로 그대로 남는다 -
이 수정의 존재 이유 자체를 무력화할 수 있는 완전성 공백이다.

**정정**: `kPushDeferredDestruction`을 타는 경우, `releaseStrong()`은
`_destroyOwned`/`releaseWeak()`(→`_freeSelf`) **둘 다** 호출하지 않고
그 자리에서 곧장 반환해야 한다 - 컨트롤 블록을 그대로(strongCount=0,
weakCount는 아직 감소 전 그대로) 지연 스택에 push해 두고, `kDrainDeferred
Destructions()`가 안전한 컨텍스트에서 원래 `releaseStrong()`이 했을
일 전체(즉 `_destroyOwned` 호출 다음 `releaseWeak()`까지, outstanding
`WeakPtr`이 그 사이 새로 생겼을 가능성까지 포함한 정확한 재현)를
대신 수행해야 한다. 구현 세션은 §7 착수 순서의 2/3단계에서 이
전체 시퀀스(단순히 `deleter` 포인터 하나만이 아니라 `releaseStrong()`
이 원래 하던 두 단계 전부)를 지연 스택 노드가 재현하도록 설계할 것 -
가능하면 `ControlBlockBase`에 "지연된 releaseStrong 완료" 전용
가상/트램폴린 함수를 하나 더 두고 `kDrainDeferredDestructions()`가
그걸 부르는 형태를 권장(§3.1 `deferredNext` 필드 옆에 나란히).

### 3.2-b [정정, 2026-09-20, 구현 착수 중 발견] `Scheduler::currentCoreIndex()`를
libkenv/shared_ptr.h에서 직접 부를 수 없음 - 순환 include, 함수포인터
훅으로 대체

§3.2 의사코드는 `gInterruptDepth[Scheduler::currentCoreIndex()]`를
`SharedPtr<T>::reset()`/`ControlBlockBase::releaseStrong()` 안에서
직접 참조하는 것처럼 그렸으나, 실제로 이건 컴파일이 불가능하다 -
`task.h`가 이미 `libkenv/shared_ptr.h`를 include하고 `scheduler.h`가
`task.h`를 include하므로, `shared_ptr.h`가 `scheduler.h`(또는
`Scheduler::currentCoreIndex()` 선언이 있는 어떤 헤더든)를 include하면
`shared_ptr.h` → `scheduler.h` → `task.h` → `shared_ptr.h` 순환
include가 된다. `libkenv`는 애초에 Scheduler/인터럽트 개념을 몰라야
하는 계층이기도 하다(코딩 컨벤션 - 아키텍처/커널 서브시스템 무관).

**정정**: 이 클래스가 이미 쓰고 있는 바로 그 패턴(`_destroyOwned`/
`_freeSelf` 함수포인터 트램폴린 - "T를 몰라도 되게 타입 소거") 을
그대로 재사용한다 - `ControlBlockBase`/`releaseStrong()`은 "지금
인터럽트 컨텍스트인지" 판정도, 실제 지연 스택 push/drain 구현도
전혀 모른다. 대신 `libkenv/shared_ptr.h`에 커널 레이어가 부팅 시
채워 넣는 두 개의 `inline` 함수포인터 전역만 선언한다:

```cpp
// libkenv/shared_ptr.h - 정의만, 실제 구현은 커널 레이어(scheduler.cpp
// 등)가 부팅 시 등록. nullptr이면(아직 등록 전, 또는 앞으로도 등록
// 안 하는 빌드) 항상 "지연 불필요"로 취급 - 기존 즉시 반납 경로 그대로.
using ShouldDeferHeavyDestructionFn = bool (*)();
using PushDeferredDestructionFn = void (*)(ControlBlockBase*);
inline ShouldDeferHeavyDestructionFn gShouldDeferHeavyDestruction = nullptr;
inline PushDeferredDestructionFn gPushDeferredDestructionHook = nullptr;
```

`ControlBlockBase::releaseStrong()`(§3.2-a 정정 반영, `_destroyOwned`/
`releaseWeak` 둘 다 건너뛰고 push만):

```cpp
void releaseStrong() {
    if (_strongCount.fetchSub(1) == 1) {
        if (gShouldDeferHeavyDestruction && gShouldDeferHeavyDestruction()) {
            gPushDeferredDestructionHook(this);
            return;  // _destroyOwned/releaseWeak 둘 다 미룸(§3.2-a)
        }
        _destroyOwned(this);
        releaseWeak();
    }
}
```

커널 레이어(예: `scheduler.cpp` 또는 새 파일)가 부팅 초기(`kMain`/
`Scheduler::init()`)에 `gShouldDeferHeavyDestruction = &kIsInInterruptContext;`
`gPushDeferredDestructionHook = &kPushDeferredDestruction;`로 실제
구현을 등록한다 - 이쪽은 `Scheduler::currentCoreIndex()`/
`gInterruptDepth[]`에 자유롭게 접근할 수 있다(커널 레이어 자신이므로
순환 include 문제가 없음). `kDrainDeferredDestructions()`(드레인,
§3.3)도 같은 커널 레이어 파일에 두고, 컨트롤 블록의 "지연된
releaseStrong 재현" 전용 공개 메서드(§3.2-a가 제안한 것)만
`ControlBlockBase`에 둔다.

### 3.3 드레인 호출 지점

설계자가 예시로 든 그대로 - `AsyncReactor::drainOnce()`(SP-F682B889) 안, 이미 `DelayedExecutionQueue::pump()`를 호출하는 것과 같은 자리에 `kDrainDeferredDestructions()`를 추가한다. `AsyncReactor`는 항상 리액터 자신의 독립된 `kernel::Task` 컨텍스트(인터럽트 아님, IF=1)에서 실행되므로 안전 - 이미 이 커널이 확립한 "리액터가 안전한 지연 실행 지점"이라는 전제(`DelayedExecutionQueue`가 이미 그렇게 쓰고 있음)를 그대로 재사용한다.

**지연 시간 특성**: 이 코어의 리액터가 다음에 `drainOnce()`를 도는 시점까지 실제 삭제자 실행이 미뤄진다 - 리액터는 매우 자주(비어 있어도 최소 매 스케줄러 퀀텀 주기로) 도므로 실용적으로는 밀리초 단위 이내로 짧다. 정확한 상한은 실측 후 필요하면 조정(RM-23F4B687 §4).

## 4. 적용 범위 - Process/ResourceGroup/BridgePipe 전부 자동 커버

이 설계는 `SharedPtr<T>` 자체(컨트롤 블록 레벨)를 고치므로, `T`가 무엇이든(Process/ResourceGroup/BridgePipe, 그리고 `PN-260D7D73`이 언젠가 착수되면 Channel까지) **자동으로** 적용된다 - 개별 호출부(`kSyncDebugRegs`/`onTick():1683` 등)를 하나하나 고칠 필요가 없고, 앞으로 새로 생기는 호출부도 별도 조치 없이 안전하다(설계자가 요구한 "공용 매커니즘"의 핵심 요건).

## 5. 장기 방향(GC)과의 관계 - 상충 없음, 확장 지점만 마련

설계자가 확정한 장기 방향(가비지 컬렉터 도입)은 아직 구체 설계가 없다(세부는 미정, 방향만 확정). 이 v1 설계는 그 방향과 상충하지 않도록 의도적으로 "지연 실행 큐" 인터페이스(`kPushDeferredDestruction`/`kDrainDeferredDestructions`)로 분리해 뒀다 - 나중에 GC가 도입되면 이 v1 메커니즘 자체를 대체하거나(GC가 참조 카운트 소멸 타이밍 문제를 근본적으로 없앰), 혹은 GC의 "finalizer 큐"가 이 인터페이스를 그대로 흡수할 수도 있다. GC 세부 설계는 이 문서의 범위 밖 - 구체화되면 별도 SP로 분리 등록한다(CLAUDE.md 규칙 7, RM-32D06563 §12 등록도 그때).

## 6. 검증 계획

- 재현(PN-4137C88C가 이미 제안한 스트레스 시나리오 - ResourceGroup 참여 프로세스 반복 생성/종료 + CPU 쿼터 활성화)으로 **수정 전** 실제 "행" 증상을 먼저 확보해 기준선을 만든다(가능하면 - 재현 조건이 좁아 못 잡을 수도 있음, 그래도 시도).
- 수정 후 같은 스트레스 시나리오 반복 실행 - 행 증상 재현 안 됨을 확인.
- 표준 회귀 3종(PVH/GRUB 단일코어/GRUB SMP4) 전부 통과 확인 - `SharedPtr` 컨트롤 블록 변경이라 파급 범위가 넓으므로 특히 꼼꼼히.
- `gInterruptDepth` 자체의 정확성 - 중첩 인터럽트(타이머 틱 도중 다른 IRQ, NMI) 시나리오에서 카운터가 정확히 0으로 돌아오는지 확인(예: TEMP 진단 카운터 assert 후 제거).

## 7. 착수 순서 (구현 세션 참고)

1. `gInterruptDepth[kMaxCores]` + isr.S 증감 배선(가장 기반, 다른 모든 것의 전제).
2. `ControlBlockBase`에 `deferredNext` 필드 + `kPushDeferredDestruction`/`kDrainDeferredDestructions` 구현(shared_ptr.h 또는 별도 헤더).
3. `SharedPtr<T>::reset()`(또는 참조카운트 0 도달 분기) 통합.
4. `AsyncReactor::drainOnce()`에 드레인 호출 배선.
5. 표준 회귀 + (가능하면) 재현 시도.
