# RCU(Read-Copy-Update) 인프라 도입 평가 및 설계 제안

설계자 지시(2026-09-14, 메시지) - "[SP-2AAD7C8D] quiescent state 추적,
grace period, call_rcu 콜백 큐 등을 이 커널의 설계와 비교하여 무엇을
더 설계해야하는지 평가서를 작성해." **SP-2AAD7C8D §3.2/§6-1**이 "RCU
인프라 자체가 없다"고 지적하며 "RCU 도입 여부"를 아키텍처 결정이
필요한 열린 설계 영역으로 남겨 뒀던 것에 대한 평가서 겸 v1 설계
제안이다 - 이 문서는 도입 여부를 임의로 확정하지 않고(RM-23F4B687
§4 원칙), 평가 결과를 바탕으로 §7의 DC 질의로 설계자 확인을 구한다.

## 1. 평가 범위

이 문서는 (1) Linux RCU의 핵심 개념(quiescent state, grace period,
call_rcu)을 간단히 정리하고, (2) 이 커널이 이미 가진 것 중 그대로
재사용 가능한 기반을 식별하고, (3) 정말로 없어서 새로 설계해야 하는
것이 무엇인지 격차를 정리한 뒤, (4) 이 커널 규모/스케줄러 구조에
맞는 v1 설계(Classic/QSBR 스타일)를 제안한다. 실제 도입 여부와
적용 대상 선정은 이 평가서의 범위를 넘는 아키텍처 결정이다.

## 2. Linux RCU 핵심 개념 (평가 대상)

- **Quiescent State(고요 상태)**: 그 CPU/스레드가 "지금 어떤 RCU
  보호 자료구조도 읽고 있지 않다"고 보장할 수 있는 시점 - 고전
  (non-preemptible) RCU는 컨텍스트 스위치나 인터럽트 복귀 같은
  지점을 고요 상태로 간주한다(선점 자체가 read-side critical
  section을 가로지를 수 없다는 전제).
- **Grace Period(유예 기간)**: 새 버전이 발행(publish)된 시점부터,
  그 이전 버전을 읽고 있었을 수 있는 **모든** CPU가 각자 최소 한 번
  고요 상태를 지날 때까지의 구간 - 이 구간이 끝나야 이전 버전을
  안전하게 회수(reclaim)할 수 있다.
- **`call_rcu` 콜백 큐**: "이 유예 기간이 끝나면 이 콜백(대개
  회수/해제 함수)을 실행해 달라"고 등록하는 큐 - 보통 CPU별로
  나뉘고, 유예 기간 완료 판정 후 인터럽트 컨텍스트가 아니라 별도
  실행 컨텍스트(Linux는 softirq)에서 드레인된다.

## 3. 이 커널의 현재 설계와 대조

### 3.1 지금 있는 동시성 보호 수단 - 전부 "읽기도 락"

현재 확정/구현된 동기화 프리미티브(SP-0666DB3C)는 `Spinlock`,
재경쟁형 `Mutex`/`Semaphore`(WaitQueue 기반 파킹), 그리고 비동기
프레임워크 전용 `AsyncMutex`/`AsyncSemaphore`(yield 기반) 셋 다
**읽기 접근도 반드시 락을 잡아야 한다** - RCU가 존재하는 이유(락
없는 읽기)를 제공하는 프리미티브가 지금 하나도 없다.

### 3.2 RCU가 실제로 이득을 볼 후보 구조

- **`KernelAddressSpaceManager`의 Maple Tree**(SP-2AAD7C8D §2/§3.2) -
  본인이 이미 §3.2에서 "RCU 기반 lock-free 읽기가 Linux Maple Tree의
  핵심 이점"이라고 지적하며 v1은 전역 Spinlock으로 대체한다고 명시한
  바로 그 자료구조. **모든 CPU가 공유하는 전역 자료구조**(§1의 이유)
  라 page fault 등 읽기 경로가 잦아지면 이 전역 락이 가장 먼저
  경합 지점이 될 후보다.
- **`AsyncCallbackRegistry`**(SP-F682B889 §3.1) - "기능별로 부팅 시
  한 번만 등록, 이후 조회만 반복"되는 전형적인 read-mostly 구조 -
  RCU의 가장 흔한 적용 사례(설정/등록 테이블)와 정확히 같은 모양.
- **공개 인터페이스 registry / procfs 스키마**(DS-D4E5C451 - "구현하며
  보강"으로 열어 둔 상태) - 아직 구현되지 않았지만, 등록은 드물고
  조회는 잦은 구조가 될 가능성이 높다.
- **PnP 장치 레지스트리**(SP-9DD4F3EA) - 핫플러그로 드물게 갱신되고
  드라이버들이 자주 조회하는 구조.

### 3.3 이미 있어서 그대로 재사용 가능한 기반

RCU 인프라를 처음부터 전부 새로 만들어야 하는 것은 아니다 - 이미
확정/구현된 다음 조각들이 그대로 재사용 가능한 기반이 된다:

- **`PerCpu<T>`**(SP-0666DB3C §12) - 코어별 quiescent 카운터/콜백
  큐를 담는 자연스러운 그릇.
- **코어별 선점 비활성화 카운터**(PL-2D3184BC §8-부분,
  `Scheduler::disablePreemption()`/`enablePreemption()`, 이미 구현
  완료이고 공개 API로 노출돼 있음) - **고전 비선점 RCU의 핵심
  트릭과 정확히 일치한다**: 이 프로젝트는 이미 "선점 비활성화 구간은
  선점되지 않는다"를 보장하므로, `disablePreemption()`/
  `enablePreemption()` 쌍을 RCU의 read-side critical section 경계로
  **그대로 재해석**할 수 있다 - 즉 `rcu_read_lock()`/`unlock()`에
  해당하는 새 프리미티브를 처음부터 새로 만들 필요 없이, 기존
  API를 그 의미로 확장하는 것으로 시작할 수 있다(§5.1).
- **`AsyncReactor`/인터럽트 통합 규칙**(SP-F682B889 §3.4/§3.5) - "ISR은
  최소한의 작업만 하고 실제 처리는 리액터 Task 컨텍스트에서 한다"는
  이 프로젝트의 기존 원칙이 `call_rcu` 콜백 드레인에 필요한 실행
  모델과 정확히 같다 - 유예 기간 완료 판정을 인터럽트에서 하더라도,
  콜백 실행 자체는 리액터로 미루면 된다.
- **`AsyncTaskCompletion::waitSync()`**(SP-F682B889 §9) - 만약 나중에
  "이 유예 기간이 끝날 때까지 동기적으로 기다리는" API(Linux의
  `synchronize_rcu()`에 해당)가 필요해지면, 이미 있는 동기/비동기
  겸용 대기 파사드를 그대로 재사용할 수 있다.

## 4. 격차(Gap) 분석 - 무엇이 정말 없는가

1. **Quiescent state의 명시적 정의 자체가 없다**: 지금은
   `disablePreemption()`/`enablePreemption()`이 "선점 금지 구간"으로만
   쓰이지, "이 코어가 RCU 관점에서 안전한 지점을 지났다"를 관찰/기록
   하는 별도 로직이 없다. §3.3의 재사용 아이디어는 있지만, "카운터가
   0으로 돌아온 시점을 누가/언제 기록하는지"는 아직 아무 데도 없다.
2. **Grace Period 상태 머신이 없다**: "새 유예 기간이 시작됐다"는
   전역 시퀀스 번호, 그리고 "각 코어가 그 시퀀스 번호 이후 최소 한 번
   고요 상태를 지났는가"를 코어별로 추적하는 자료구조/판정 로직이
   전혀 없다.
3. **`call_rcu` 콜백 큐가 없다**: 코어별로 "이 유예 기간이 끝나면
   실행할 콜백" 목록을 쌓아 두는 자료구조, 그리고 그 목록을 유예
   기간 완료 시점에 드레인하는 루프(AsyncReactor 루프에 낄 자리는
   있으나, §3.3처럼 "재사용 가능"과 "실제로 존재"는 다르다 - 지금은
   존재하지 않는다)가 없다.
4. **읽기 쪽 API 자체가 없다**: `Spinlock`/`Mutex` 계열은 전부
   "락을 잡는다"는 명시적 API가 있지만, "지금부터 RCU로 보호되는
   구조를 읽는다"는 의미의 별도 API(설령 내부적으로
   `disablePreemption()`을 재사용하더라도, 이름과 의미가 다른
   `Rcu::readLock()`류)가 없어서 호출부가 의도를 드러낼 방법이 없다.
5. **회수(reclaim) 타이밍 문제 자체를 지금은 안 다루고 있다**:
   SP-2AAD7C8D의 Maple Tree는 이 문제를 "그냥 전역 락으로 우회"해서
   해결한 것이지, 해결한 게 아니라 **회피**한 것이다 - 만약 나중에
   전역 락을 풀고 읽기를 lock-free로 만들고 싶다면, "노드를 다른
   CPU가 아직 읽고 있을 수 있는데 언제 안전하게 free()해도 되는가"라는
   질문에 답할 방법이 지금 전혀 없다 - Slab 할당자(SP-D7013B26)의
   `free()`는 즉시 회수를 전제하므로, RCU 없이 이 우회를 풀면 use-
   after-free가 된다.
6. **멀티스레드 프로세스/코어 증가 시나리오에서의 확장성 검토 없음**:
   Linux는 코어 수가 많아지면 단순 비트마스크 방식(Classic RCU)이
   아니라 트리 구조(Tree RCU)로 확장한다 - 이 커널의 목표 코어 규모
   (`kMaxCores = kAcpiMaxCpus`, SP-0666DB3C §12.2)가 그 정도로 크지
   않다면 이 확장은 불필요할 가능성이 높지만, 지금 이 문서에서
   확정하지 않는다(§5.6).

## 5. v1 설계 제안 - Classic(비선점) RCU, 기존 프리미티브 최대 재사용

### 5.1 Quiescent State 정의 - 기존 선점 비활성화 카운터를 그대로 재해석

**핵심 제안**: 새 잠금/대기 프리미티브를 만들지 않는다. 이 프로젝트는
이미 "선점 비활성화 카운터가 0인 구간에서만 선점(컨텍스트 스위치)이
일어날 수 있다"를 보장하므로(PL-2D3184BC §8-부분), **"이 코어의
선점 비활성화 카운터가 0으로 돌아온 순간"을 고요 상태로 정의**한다 -
이는 고전 비선점 RCU가 "컨텍스트 스위치 지점"을 고요 상태로 삼는
것과 동치다(이 카운터가 0일 때만 스위치가 가능하므로, 카운터가
0을 지나는 매 순간이 곧 "스위치될 수 있었던 지점"이다).

```cpp
// minicore/kernel, 가칭 rcu.h
namespace kernel {

// rcu_read_lock()/rcu_read_unlock()에 대응 - v1은 기존
// disablePreemption()/enablePreemption()을 그대로 감싼다(§3.3).
// 새 락/카운터를 추가하지 않는다 - 의미를 드러내는 별도 이름만 부여.
class RcuReadGuard {
public:
    RcuReadGuard() { Scheduler::disablePreemption(); }
    ~RcuReadGuard() { Scheduler::enablePreemption(); }
};

}  // namespace kernel
```

이 재해석의 대가(제약)를 명시한다: RCU 읽기 구간 안에서
`AsyncTask::yield()`나 블로킹 가능한 호출(Mutex::lock 등)을 하면
안 된다 - 선점 비활성화 카운터 규칙과 동일한 제약이 그대로 RCU
읽기 구간에도 적용된다(고전 RCU의 "read-side critical section 안에서
sleep 금지"와 동일한 제약 - 새로 생기는 제약이 아니라 기존 제약의
재확인).

### 5.2 전역 Grace Period 상태 머신

```cpp
// minicore/kernel, 가칭 rcu.h (이어서)
namespace kernel {

using RcuGraceperiodSeq = uint64_t;

class Rcu {
public:
    static void initOnThisCore();  // 부팅 시 코어별 1회 - lastObservedSeq 초기화

    // 이 코어가 방금 고요 상태를 지났음을 기록한다.
    // Scheduler::enablePreemption()이 카운터를 0으로 되돌리는 바로
    // 그 지점에서 내부적으로 호출한다(§5.1 - 호출부가 직접 부를
    // 필요 없음, PreemptionGuard/disablePreemption 사용자가
    // 몰라도 되게 하는 것이 원칙).
    static void noteQuiescentStateOnThisCore();

    // 새 유예 기간을 시작하고 시퀀스 번호를 반환한다(트리거만 - 이
    // 함수 자신은 완료를 기다리지 않는다).
    static RcuGraceperiodSeq startGracePeriod();

    // seq로 시작된 유예 기간이 끝났는지(=이 시퀀스 번호가 시작된
    // 이후 모든 온라인 코어가 최소 한 번 고요 상태를 지났는지)
    // 확인한다 - AsyncReactor 루프(§5.3)가 매 순회 폴링한다.
    static bool isGracePeriodComplete(RcuGraceperiodSeq seq);

private:
    // PerCpu<T>(SP-0666DB3C §12) 재사용 - 코어별 "마지막으로 고요
    // 상태를 지난 시점의 전역 시퀀스 번호".
    static PerCpu<AtomicU64> _lastObservedSeq;
    static AtomicU64 _currentSeq;
};

}  // namespace kernel
```

`isGracePeriodComplete`는 온라인 코어 전부(`Acpi::cpuCount()`류,
이미 있는 코어 열거 API 재사용)를 순회하며 `_lastObservedSeq.forCore(i)
>= seq`인지 확인하는 단순 선형 스캔으로 시작한다(§4.6의 확장성 논의와
같은 이유로, v1은 코어 수가 적다는 전제하에 단순 구현을 제안 -
`PerCpu<T>::get()`의 O(코어 수) 스캔 비용과 같은 성격의 트레이드오프,
SP-0666DB3C §12.3 참고).

### 5.3 `call_rcu` 콜백 큐 - 코어별 리스트 + 리액터 드레인

```cpp
// minicore/kernel, 가칭 rcu.h (이어서)
namespace kernel {

// [정정, 2026-09-17, 설계자 의견] "제네릭 템플릿들을 사용한 시나리오로
// 전면 개정" - SP-FAF768AB(libkcont)가 확정/구현(PN-633BF2D8) 완료된
// 뒤이므로, 손짜기 단일 연결 next 포인터 대신 libkcont의 침습적
// `List<T, Traits>`(SP-FAF768AB §1/§2/§0-B)를 그대로 재사용한다 -
// PN-73E61BD1이 기존 손짜기 리스트들에 적용 중인 것과 동일한
// 마이그레이션 원칙을 새로 짜는 코드에도 처음부터 적용.
//
// 콜백 자신의 메모리는 호출부 책임(AsyncTaskHandler의 args 원칙과
// 동일, SP-F682B889 §3.1) - 이 구조체 자체를 회수 대상 객체에
// 내장(intrusive)해 별도 Slab 할당을 피하는 것을 권장(Linux의
// rcu_head 관례와 동일) - `link` 멤버가 바로 그 내장 지점이다.
struct RcuCallback {
    void (*fn)(RcuCallback* self);
    Node link;  // libkcont::Node(SP-FAF768AB §1) - List<T,Traits> 연결용
    RcuGraceperiodSeq targetSeq = 0;  // 이 유예 기간이 끝나야 실행 가능
};

// §0-B의 Traits 형태(SP-FAF768AB) - Key/keyOf 없이 Link 멤버 포인터
// 하나만 필요한 단순 리스트(MyListTraits 예시와 동일 패턴).
struct RcuCallbackTraits {
    static constexpr Node RcuCallback::* Link = &RcuCallback::link;
};

class Rcu {
public:
    // (§5.2 이어서) 이 콜백을 "다음 유예 기간이 끝나면" 실행되도록
    // 이 코어의 콜백 큐에 등록한다 - Slab::free() 같은 즉시 회수
    // API 대신, 회수를 미루고 싶은 모든 지점에서 이 API를 쓴다.
    static void callAfterGracePeriod(RcuCallback* cb);

private:
    // 코어별 pending 콜백 리스트 - libkcont `List<RcuCallback,
    // RcuCallbackTraits>`(SP-FAF768AB §2) 재사용, 손짜기 단일 연결
    // 리스트를 직접 구현하지 않는다. AsyncReactor::reactorTaskEntry()의
    // 매 순회(§3.5 인터럽트 통합 규칙과 동일한 이유 - 콜백 실행은
    // ISR이 아니라 반드시 리액터 컨텍스트에서)가 이 리스트를 앞에서부터
    // 순회해 targetSeq가 지난 유예 기간이 이미 완료된 항목만
    // `List<RcuCallback, RcuCallbackTraits>::remove()`로 떼어내 실행한다
    // (완료 안 된 항목을 만나면 그 뒤는 더 최근에 등록된 것들이므로
    // 순회를 멈춘다 - pushBack으로 등록 순서가 유지되는 전제, §2 참고).
    static PerCpu<List<RcuCallback, RcuCallbackTraits>> _pendingList;
};

}  // namespace kernel
```

`AsyncReactor::reactorTaskEntry()`(SP-F682B889 §3.4)의 순회 루프에
"이 코어의 RCU 콜백 큐 드레인"을 한 단계로 추가하는 것을 제안한다 -
이미 있는 "각 코어마다 하나씩 배치된 리액터 Task가 반복 순회한다"는
실행 모델에 자연스럽게 낀다(§3.3의 "재사용 가능한 기반" 중 하나가
실제로 소비되는 지점).

### 5.4 발행(publish)/해제 경로 예시 - Maple Tree 적용 시나리오

이 문서는 Maple Tree(SP-2AAD7C8D)를 실제로 lock-free 읽기로
바꾸는 것까지 확정하지 않지만(§6), 위 프리미티브들이 어떻게
맞물리는지 보이기 위한 예시:

```cpp
// 쓰기 경로(여전히 전역 Spinlock 하에서 직렬화, SP-2AAD7C8D §2 그대로) -
// 바뀌는 것은 "옛 노드를 언제 해제하는가"뿐이다.
// [정정, 2026-09-17] 이 예시의 트리 노드를 `MapleNode`로 명명 - §5.3에서
// libkcont `Node`(SP-FAF768AB §1)를 RcuCallback 링크로 도입한 뒤라,
// 같은 문서 안에서 "Node"를 Maple Tree 자체 노드 타입으로도 쓰면
// 이름이 겹친다(실제 Maple Tree 구현은 SP-2AAD7C8D 소유, 이 예시는
// 여전히 순수 설명용 - Maple Tree를 libkcont로 옮기는 것 자체는 이
// 문서 §6이 명시한 대로 범위 밖).
void MapleTree::replaceNodeUnderLock(MapleNode* oldNode, MapleNode* newNode) {
    // ... 부모의 slot[]을 newNode로 원자적으로 교체(release 순서) ...
    RcuCallback* cb = &oldNode->rcuHead;   // 내장형(§5.3)
    cb->fn = [](RcuCallback* self) {
        // containerOf는 §5.3 List<T,Traits>가 내부적으로 쓰는 오프셋
        // 계산(offsetof 대체, §0-B)과 같은 발상의 예시용 표기 - 실제
        // 구현 시점엔 MapleTree 자신의 동일한 오프셋 계산 관용구를 쓴다.
        MapleNode* node = containerOf(self, &MapleNode::rcuHead);
        GenericSlabAllocator::free(node, sizeof(MapleNode));  // 이제야 안전
    };
    cb->targetSeq = Rcu::startGracePeriod();
    Rcu::callAfterGracePeriod(cb);
}

// 읽기 경로 - 지금의 전역 Spinlock 획득을 이걸로 교체.
void* MapleTree::find(uint64_t addr, ...) {
    RcuReadGuard guard;  // §5.1 - 사실상 disablePreemption()
    // ... 포인터를 따라가며 순회(교체 중인 노드를 만나도 옛 버전
    // 아니면 새 버전 중 일관된 하나만 보게 되는 것은 발행 순서
    // (release 스토어)가 보장 - Linux RCU와 동일한 요구사항) ...
}
```

### 5.5 v1이 하지 않는 것 (명시적 축소)

- **`synchronize_rcu()`(동기 대기) API는 v1에 포함하지 않는다** -
  지금까지 식별된 소비자(§3.2)가 전부 "회수를 미루면 그만"인
  콜백형 사용처이지, "유예 기간이 끝날 때까지 그 자리에서 기다려야"
  하는 소비자가 아직 없다. 필요해지면 §3.3이 이미 지목한
  `AsyncTaskCompletion::waitSync()` 패턴으로 쉽게 추가 가능하다.
- **Tree RCU(계층적 고요 상태 집계)는 v1 범위 밖** - §5.2의 선형
  스캔으로 충분하다고 보는 코어 수 전제가 실측으로 깨지면 별도
  설계(§6-2 후속 검토 대상).
- **선점형(preemptible) RCU는 다루지 않는다** - 이 프로젝트의
  스케줄러가 "선점 비활성화 구간은 진짜로 선점되지 않는다"를
  전제로 하는 한(§5.1), 고전 비선점 방식이 그대로 성립한다 -
  스케줄러가 나중에 이 전제를 깨는 방향으로 바뀌면(예: 선점 금지
  구간 안에서도 강제 전환 허용) 이 §5 전체가 재검토 대상이 된다.

### 5.6 아직 열려 있는 하위 과제

1. **코어 오프라인/핫플러그와 온라인 코어 열거**: §5.2의
   `isGracePeriodComplete`가 순회할 "온라인 코어 목록"이 이 프로젝트
   에서 지금 정확히 어떻게 열거되는지(SMP AP 기동, PL-65C20380) 확인
   필요 - 코어가 부팅 후 오프라인될 수 있는 설계가 아직 없다면 단순
   전체 코어 수 순회로 충분.
2. **Grace Period 시작 트리거 주체**: `startGracePeriod()`를 누가
   언제 호출하는지(콜백 등록 시점마다 자동 호출할지, 배치로 묶을지)는
   구현 시점에 실측 후 확정(RM-23F4B687 §4 원칙 - 숫자/전략 튜닝).
3. **인터럽트 컨텍스트에서의 `callAfterGracePeriod` 호출 안전성**:
   §5.3의 코어별 리스트가 ISR에서도 안전하게 push 가능해야 하는지
   (인터럽트 컨텍스트에서 회수를 예약해야 하는 소비자가 실제로
   나타나는지)는 구체적 소비자가 확정되면 재검토.

## 6-부. 설계자 결정 (2026-09-14, QU-C29D8120 답변 + 후속 메시지)

**거부 - 커널단 v1 완료 이후로 미룸.** 설계자 결정: "이 설계안은
규모가 너무 커서 커널단 v1 완료 이후로 미루자." §6이 예상했던

## 6. 도입 여부 - 여전히 설계자 결정 필요

이 평가서는 "무엇을 더 설계해야 하는가"에 답하고 v1으로 즉시 착수
가능한 구체안(§5)을 제시했지만, **RCU를 실제로 이 커널에 도입할지
자체는 SP-2AAD7C8D §3.2/§6-1이 이미 명시한 대로 숫자 튜닝이 아니라
아키텍처 결정**이다(RM-23F4B687 §4 원칙 - 명시되지 않은 설계는
임의로 확정하지 않는다) - §7의 DC 질의로 답을 구한다. 이 평가의
결론 요약: **처음 우려했던 것보다 훨씬 적은 신규 코드로 시작할 수
있다** - quiescent state 추적의 핵심이 이미 있는 선점 비활성화
카운터의 재해석만으로 해결되기 때문에(§5.1), §3.2가 "상당한 규모의
별도 서브시스템"이라고 걱정했던 것에 비해 실제 v1 범위(§5.2-§5.3의
그레이스 피리어드 상태 머신 + 콜백 큐)는 작다.
