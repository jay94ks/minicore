## 배경 - 이 설계가 왜 필요한가 (PN-9326B06F)

`gInterruptDepth`(deferred_destruction.cpp) 카운터 + 그 값에 따라
조건부로 32KiB 전용 스택으로 스왑하는 현재 메커니즘(`PN-D7B66FE4`,
`DC-53B93BFF`)이, 여러 세션에 걸쳐 서로 다른 것처럼 보이던 다수의
간헐적 크래시(`PN-1DFCB337`/`PN-584DB994`/`PN-9326B06F` 전부 결국
같은 근본 계열로 수렴)의 근본 원인이었다. 이번 세션(`PN-9326B06F`
7차 갱신)이 실측으로 확인한 두 갈래:

- **(a)류**: `gInterruptDepth` 카운터 자체가 알 수 없는 경로로
  음수로 새어(트레이서로 "1 ENTER -> 4~5 LEAVE" 버스트까지 실측),
  `kEnterInterruptDepth()`의 `depth==1` 판정이 misfire해 진짜
  outermost 인터럽트에서도 32KiB 스왑을 건너뛰고 8KiB Task
  kernelStack 위에서 그대로 실행 - 스택이 크게 넘쳐 인접 메모리를
  광범위하게 손상.
- **(b)류**: 카운터는 정상(depth==1)인데도 같은 크래시 서명이
  재현 - `Scheduler::currentCoreIndex()`가 `rdtscp` 미지원 환경에서
  `kScanCoreIndexByApicId()`(매 인터럽트 Enter/Leave마다 `Lapic::id()`
  MMIO 읽기까지 포함)로 폴백하며 Task의 평범한(비인터럽트) 콜체인이
  8KiB를 초과.

설계자 질의(`QU-D83CF559`)에 대한 답변(2026-09-21) - "인터럽트
핸들러가 짧게 끝나게 설계돼 있어야 하는데, 그렇다면 인터럽트
중첩을 허용할 필요가 있나?" - 이 질문을 실측으로 조사한 결과
(`PN-9326B06F` 7차 갱신), **일반 마스커블 인터럽트끼리의 진짜
중첩은 이미 이 커널에 구조적으로 존재하지 않는다**(전체 저장소
`sti` 11곳 전수 검색 - `kEnterInterruptDepth`~`kLeaveInterruptDepth`
구간 안에서 `sti`를 실행하는 코드가 단 한 곳도 없음, 그 구간 내내
IF=0 유지). 실제로 발생하는 "중첩"은 전부 **CPU가 IF와 무관하게
강제로 진입시키는 것들**(동기적 예외 - 특히 온디맨드 페이징 #PF,
그리고 NMI)뿐이다 - 이건 핸들러를 아무리 짧게 만들어도 막을 수
없다(핸들러 "길이"가 아니라 "무엇을 건드리는가"의 문제).

후속 질의(`QU-BD62308E`)에 대한 답변(2026-09-21) - "막을 수 없는
인터럽트만 분리하는 방법은 없어?" - 이 문서는 그 방향(옵션 A)을
정식 설계로 제출한다.

## 핵심 통찰

인터럽트를 두 카테고리로 완전히 분리한다:

1. **회피 불가능(unmaskable) 카테고리** - `IF`와 무관하게 언제든
   강제로 발생할 수 있는 것들: NMI(2), `#DF`(8), `#MC`(18),
   `#DB`(1), **`#PF`(14)**. 이 중 NMI/`#DF`/`#MC`/`#DB`는 이미
   `IST1-4`로 각자 전용 스택을 갖고 있다(`SP-677210E6`,
   `PN-3B781046`). **`#PF`만 아직 빠져 있다** - `PN-5377545F`
   ("TSS IST5-7 슬롯 확장 여지")가 예고해 둔 확장 자리를 정확히
   이 용도로 쓴다.
2. **일반(마스커블) 카테고리** - 타이머, 스케줄러 틱, IPI(강제
   이관/TLB 샷다운/비동기 드레인 등), 디바이스 인터럽트 등 나머지
   전부. **이들끼리는 서로 절대 중첩되지 않는다**(위 sti 전수 조사로
   확정) - 그래서 이 카테고리에는 "몇 단계까지 중첩됐는가"를 셀
   필요가 전혀 없다.

이 구분에서 바로 결론이 나온다: **회피 불가능 카테고리는 카테고리
전체가 이미 개별 IST로 격리돼 있으니 그대로 유지 + `#PF`만
추가하면 되고, 일반 카테고리는 "항상 코어당 전용 스택 하나로
무조건 스왑"하면 그만이지 `gInterruptDepth` 같은 카운터/조건부
분기가 애초에 필요 없다.**

## 제안 설계

### §1. `#PF`(vector 14)에 `IST5` 배정

`gdt.cpp`의 기존 `gIstStacks[슬롯][코어][kIstStackSize]` 배열을
그대로 재사용(슬롯 4 = IST5, `PN-5377545F` 문서가 이미 "필요해지면
`gIstStacks` 배열을 늘리고 그 벡터의 `ist` 필드를 그 번호로
설정하면 된다"고 예고해 둔 그대로) - `idt.cpp`의 IDT 게이트
설정에서 `gIdt[14].ist = kPageFaultIst(=5)`로 배정.

### §2. `#PF` 자체의 재진입(같은 코어에서 `#PF` 처리 중 또 `#PF`) - "위험 완화"가 아니라 "위반하면 안 되는 불변조건의 시행"

**[정정, `QU-13C77537` 답변 반영]** 최초 초안은 이걸 "`#PF`가
정상 동작 중에도 일어날 수 있는 위험"으로 프레이밍했었다 - 틀렸다.
**`#PF` 핸들러 자신의 코드**(`Paging::handlePageFault()`류 - 페이지
테이블을 직접 조작하는 코드)는 전부 **영구적으로 매핑된 커널
구조**(PML4/PDPT/PD/PT 테이블 자체, direct map 영역, 정적 커널
.text/.data/.bss, 이 IST5 스택 자신)만 건드린다 - 즉 이 코드가
제대로 작성돼 있다면 **자기 자신이 매핑 안 된 메모리를 건드릴
일이 구조적으로 없어야 한다.** 그래서 "`#PF` 처리 도중 또 `#PF`"가
실제로 발생한다면, 그건 온디맨드 페이징의 정상적인 부작용이
아니라 **`#PF` 핸들러 코드 자체의 버그**(예: 아직 안 매핑된
페이지 테이블 프레임을 매핑 전에 역참조, 잘못된 포인터 연산으로
direct map 밖을 건드림 등)라고 봐야 한다.

그래서 코어별 재진입 감지 플래그(`gInPageFaultHandler[coreIndex]`류,
`gInDispatchWindow`와 같은 패턴)를 `#PF` 핸들러의 **가장 첫 동작**
으로 두는 건 그대로 유지하되, 그 목적을 **"위험 완화/복구
시도"가 아니라 "이 불변조건이 깨졌다는 것 자체를 즉시 잡아내는
버그 탐지기"**로 재정의한다:
- 이미 서 있으면(=재진입) - 이건 곧 **`#PF` 핸들러 코드 어딘가가
  이 불변조건을 어겼다는 확정적 증거**다. 복구를 시도하지 않고
  (애초에 "복구해야 할 정상 상황"이 아니므로) 즉시 `kPanic`류의
  진단 경로로 넘어가 **어느 명령어에서 재진입이 일어났는지
  (`frame`의 `rip`/`cr2`)까지 남긴다** - 이게 바로 "핸들러 코드의
  버그를 고칠 단서"가 된다.
- 안 서 있으면 - 세우고 정상 처리, 반환 전에 내린다.

이 재정의는 §1의 IST 배정 자체와는 무관하다(여전히 필요) - 다만
"이 감지가 실제로 발동하면 그건 언젠가 고쳐야 할 이 프로젝트의
진짜 버그를 가리키는 것"이라는 해석이 맞다는 걸 명확히 한다.

### §3. 일반(마스커블) 인터럽트 - 무조건 단일 코어별 스택 스왑, `gInterruptDepth` 폐기

`isr_common_stub`(isr.S)의 현재 로직:
```
call kEnterInterruptDepth   ; depth==1일 때만 스왑 주소 반환
test rax, rax
jz 1f
mov rsp, rax
1:
call kIsrHandler
...
call kLeaveInterruptDepth   ; depth==0일 때만 원래 rsp 반환
```
을 다음으로 교체한다(일반 벡터 전용 - `#PF`/`#DF`/`#MC`/`#DB`/NMI
스텁은 각자 IST로 이미 하드웨어가 처리하므로 이 변경과 무관):
```
mov [gSavedTaskRsp + coreIndex*8], rsp   ; 원래 rsp만 저장(카운터 없음)
mov rsp, [gInterruptStackTop + coreIndex*8]  ; 무조건 스왑
call kIsrHandler
mov rsp, [gSavedTaskRsp + coreIndex*8]   ; 무조건 복원
```
**중첩이 구조적으로 불가능하므로**(§ 핵심 통찰) `gSavedTaskRsp`를
저장하는 시점과 읽는 시점 사이에 이 코어에서 이 코드가 다시
실행될 수 없다 - 매번 정확히 자기 자신의 저장값을 그대로 되찾는다.
`gInterruptDepth`/`kEnterInterruptDepth`/`kLeaveInterruptDepth`/
`kCurrentInterruptDepth`/`gInterruptDepthGuardPage`는 전부 삭제
대상.

`kIsrHandler`(idt.cpp)의 `kCurrentInterruptDepth() == 1` 의존 코드
(`captureCurrentFrame` 호출 조건, `PN-584DB994`)는 "이 인터럽트가
outermost인가"를 더 이상 카운터로 안 묻고, **일반 카테고리
진입점에서는 항상 outermost이므로 무조건 참**으로 바뀐다 -
`kIsrHandler`가 일반/회피불가 어느 스텁에서 불렸는지는 `frame->vector`
로 이미 구분 가능(§1의 IST 벡터들은 각자 자기 핸들러 분기 안에서
처리하고, `captureCurrentFrame` 호출부는 일반 카테고리 분기에
둔다).

### §4. 스택 크기

일반 카테고리 전용 스택은 현재 `gInterruptDispatchStacks`(32KiB,
`PN-D7B66FE4`가 관측 오버슈트 ~8.5KiB 대비 넉넉하게 잡은 값)를
그대로 재사용한다 - 이번 설계는 "몇 단계까지 중첩되는가"의 문제를
없애는 것이지 "한 인터럽트가 얼마나 깊이 호출하는가"의 문제와는
무관하므로 크기 재산정은 범위 밖(기존 크기가 부족하다는 실측이
나오면 그때 별도로 키운다).

## 위험/미해결 지점 (설계자 확인 필요)

1. **[해소, `QU-13C77537` 답변]** §2의 재진입 감지+즉시 정지는
   "위험 완화"가 아니라 "`#PF` 핸들러 코드가 절대 위반하면 안 되는
   불변조건(자기 자신은 항상 매핑된 메모리만 건드린다)의 시행"으로
   확정 - 위 §2 갱신 참고. 구현 착수 시 `Paging::handlePageFault()`
   류 실제 코드를 감사해 이 불변조건을 실제로 지키고 있는지(아직
   안 매핑된 페이지 테이블 프레임을 매핑 완료 전에 역참조하지
   않는지 등) 확인하는 것이 §2 구현의 일부가 된다.
2. **`kSyncCr3`/`onTick`/`onForcedMigration`처럼 현재
   `kCurrentInterruptDepth()`(또는 `interrupt_depth` 관련 값)를
   직접 참조하는 다른 호출부가 더 있는지 전수 조사 필요** -
   `deferred_destruction.h`/`.cpp` 삭제 전에 모든 참조를 다른
   방식으로 대체해야 함.
3. **`DC-06FC78E8`(A안, `DispatchWindowGuard`/`gInDispatchWindow`)와의
   관계** - 그 문서는 `onTick()`/`onForcedMigration()` 자신의
   EOI~`kContextSwitchFromISR` 창의 재진입을 막는 것으로,
   이번 설계(§3, 인터럽트 진입/이탈 자체의 스택 스왑 단순화)와는
   레이어가 다르다 - `DispatchWindowGuard`는 그대로 유지 대상으로
   보이나, 재검토 필요.
4. **회귀 검증 방법** - `PN-9326B06F`가 이미 확립한 도구(`scripts/
   pn584_repro_count.sh`, `pn584_alloc_hunt2.sh`+`pn584_alloc_watch.py`)
   재사용, 표준 4시나리오 + 표준 크래시율 배치(40회 반복, 이번
   세션 기준 rdtscp 없이 1~2/40이던 것이 이 재설계로 0/40에
   수렴하는지) 확인.
