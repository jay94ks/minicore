# rdtscp 기반 currentCoreIndex() 전환 - 타이밍 실측 QA

QU-7710DDDE(SP-0666DB3C §12.4-1) 답변(2026-09-16, "이건 별도 문서로
추적하자. QA 문서로 만들어줘")에 따라 분리한 QA 추적 문서.

## 배경

`Scheduler::currentCoreIndex()`를 기존 `Lapic::id()`+`Acpi::cpuApicId()`
선형 스캔(O(n))에서 `IA32_TSC_AUX`+`rdtscp` 기반 O(1)로 교체
(PN-25587A7D, commit 3c57c5d). §15/§16(`AsyncLocal<T>`/`ReentrantMutex`
류)이 이 함수를 `PerCpu<T>` 핫 패스로 자주 호출하게 될 구조라
"실측 후 결정"(RM-23F4B687 §4 원칙) 조건이 충족됐다고 판단해 착수한
최적화.

## 완료된 것 (실측 확인됨)

- **정확성**: QEMU(`-cpu qemu64,+rdtscp`)로 RDTSCP를 실제로 켜서 SMP4
  4개 코어 전부 정확한 인덱스(0/1/2/3)를 얻는 것을 실측 확인 완료.

## [신규 발견, 2026-09-21, PN-9326B06F] 성능이 아니라 안정성/정확성 문제로 재부상 - 크래시율과의 상관관계 실측

`PN-25587A7D` 재실측 당시 "기본 QEMU CPU 모델(rdtscp 미지원)에서
회귀 없음"을 확인한 건 맞지만, 그건 **부팅 성공 여부**만 봤을 때의
이야기였다 - 이번 세션(`PN-9326B06F`, `Lapic::id()+57` 절단 서명
크래시 조사)이 **간헐적 크래시율**까지 놓고 다시 비교해보니 전혀
다른 그림이 나왔다.

`kScanCoreIndexByApicId()` 폴백(=`Lapic::id()`를 매 `kEnterInterruptDepth`/
`kLeaveInterruptDepth` 호출마다, 즉 **매 인터럽트 진입/이탈마다**
호출 - MMIO 읽기 포함)이 활성화된 표준 테스트 환경(`run-grub.sh`
등, `-cpu` 플래그 없음)에서 GRUB SMP1+AHCI 표준 레시피 40회 반복 시
1~2/40 빈도로 간헐적 kPanic이 재현됐다(gdb로 정확한 콜체인까지
확보 - `currentCoreIndex → kScanCoreIndexByApicId → Lapic::id →
readRegister`). **동일 레시피를 `-cpu qemu64,+rdtscp`로 rdtscp
경로를 강제 활성화한 채로 40회 돌리니 0/40**(무크래시) - 표본이
크진 않지만 방향성은 뚜렷하다.

즉 이 QA가 원래 추적하던 "성능이 더 나아지는가"라는 질문과 별개로,
**"기본(폴백) 경로가 실제로는 그냥 느린 게 아니라 불안정할 수 있다"**
는 훨씬 심각한 질문이 새로 생겼다 - `PN-9326B06F`가 `DC-3D3212A4`에
`QU-BD62308E`로 이 발견 + 더 근본적인 재설계(인터럽트 depth 카운터
전체를 IST 기반으로 대체)를 함께 질의해 뒀다(답변 대기 중,
2026-09-21 기준). 표준 회귀 스크립트(`run-grub.sh`/`run-qemu.sh`/
`run-grub-gdb.sh`)의 기본 CPU 모델을 계속 폴백 경로 그대로 둘지,
아니면 항상 `+rdtscp`를 켜 둘지는 그 답변에 따라 결정한다 - 이
QA 문서 혼자 임의로 바꾸지 않는다.

않고 필요하면 별도 질의로 등록한다.
