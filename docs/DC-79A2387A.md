# 커널 C++ 런타임/코딩 컨벤션 세부 — 요구분석

## 배경

RM-23F4B687과 SP-8B6B8D25 §0이 확정한 것은 "프리픽스 + 파스칼 케이스
(예: `kMain`)"와 "네임스페이스 규칙은 커널 앱에만 적용"뿐이다. 그러나
freestanding 환경(표준 런타임/OS 지원 없이 동작하는 C++)에서 실제로
`minicore/kernel`, `libkenv`, `libkern`, `libkmm` 코드를 작성하려면
언어 기능 사용 범위 자체를 먼저 정해야 한다 — 이건 스타일 문제가
아니라, 정해두지 않으면 컴파일러 플래그(`-fno-exceptions`,
`-fno-rtti` 등)와 `libkenv`(early 런타임)가 무엇을 구현해야 하는지
자체가 결정되지 않는 선결 조건이다.

## 결정이 필요한 항목과 각 선택의 영향

1. **파일 확장자/헤더 가드**: `.cpp`/`.hpp`인지, 헤더 가드는
   `#pragma once`인지 매크로 가드인지 — 전체 리포에 걸친 기계적 규칙이라
   나중에 바꾸면 대규모 리네임 비용이 든다.
2. **예외/RTTI 사용 여부**: 커널에서 C++ 예외(`try`/`catch`)와 RTTI
   (`dynamic_cast`, `typeid`)를 허용할지 — 허용하면 언와인딩 테이블/
   런타임 지원을 `libkenv`가 구현해야 하고, 금지하면 대체 에러 처리
   방식(예: 리턴 코드/`std::expected`류)을 먼저 정해야 한다.
3. **표준 라이브러리 사용 범위**: freestanding에서 STL 컨테이너/알고리즘을
   어디까지 쓸 수 있게 할지 — `libkenv`가 STL 대체 런타임까지 포함하는지
   여부와 직결된다.
4. **프리픽스 규칙 세부**: `kMain`의 `k`가 "kernel 전역 함수" 프리픽스인
   건 확정됐지만, 타입/상수/멤버 변수/네임스페이스별로 프리픽스가 어떻게
   달라지는지(예: 멤버 변수 `m` 프리픽스 같은 흔한 관례를 따르는지)는
   아직 없다 — 첫 코드 리뷰 기준이 되므로 구현 착수 전에 정해야 반복
   수정을 피할 수 있다.
