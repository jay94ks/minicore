# 비동기 프레임워크 우선 설계 원칙 평가 - 동기 구현의 wrapper화 검토

설계자 지시(2026-09-14, 메시지) - "[SP-0666DB3C] 비동기 프레임워크부터
설계된 커널이기 때문에, 대부분의 로직을 비동기 프레임워크로 구현하고,
동기식 구현은 비동기식 구현의 wrapper로 전환이 가능한지 검토하고
설계 평가서 및 설계안을 작성해." 이 문서는 (1) 이 커널이 실제로
어디까지 비동기 프레임워크(SP-F682B889) 우선으로 설계돼 왔는지
점검하고, (2) "동기 구현 = 비동기 구현의 wrapper"라는 제안을
SP-0666DB3C의 Mutex/Semaphore ↔ AsyncMutex/AsyncSemaphore 쌍에
문자 그대로 적용했을 때 무엇이 좋고 무엇이 문제인지 평가하며,
(3) 그 평가를 바탕으로 이 원칙을 실제로 어디에 어떻게 적용할지
v1 설계안을 제시한다. 결론을 먼저 요약하면: **이 원칙은 이미 한
곳(§3)에서 성공적으로 성립하고 있고 앞으로 표준 패턴으로 삼을
가치가 있지만, Mutex/Semaphore처럼 "상태를 계속 들고 있는" 종류의
프리미티브에는 문자 그대로 적용하면 손해가 더 크다** - 대신 §5의
대안(공통 코어 추출 + 정책 주입)을 제안한다.

## 1. 평가 범위

"대부분의 로직을 비동기 프레임워크로 구현"이 정확히 무엇을 뜻하는지
분해한다: (a) 이미 존재하는 커널 로직 중 얼마나 AsyncTask 기반인가
(§2), (b) "동기 구현이 비동기 구현의 wrapper"라는 패턴이 이미
성립하는 사례가 있는가(§3), (c) 그 패턴을 SP-0666DB3C가 명시적으로
지적한 중복 사례(Mutex/Semaphore vs AsyncMutex/AsyncSemaphore,
§10.4-3)에 그대로 적용할 수 있는가(§4), (d) 적용 불가하거나 손해인
경우 대안은 무엇인가(§5), (e) 애초에 "동기로 남아야 하는" 로직의
범주는 무엇인가(§6).

## 2. 이 커널은 실제로 어디까지 비동기 프레임워크 우선인가

이미 확정/구현된 것만 봐도 커널의 핵심 실행 경로 대부분이 AsyncTask
기반이다 - "비동기 프레임워크부터 설계된 커널"이라는 전제는 과장이
아니다:

- **Syscall 디스패치**(SP-04EE2A18, PL-21344323) - syscall 처리 자체가
  AsyncTask 제출/완료 모델.
- **Channel IPC**(SP-1FBC0EEB, PL-C8648D4D) - 메시징 채널 왕복이
  AsyncTask 기반.
- **유저 페이지 폴트 재개**(SP-0666DB3C §7) - 폴트 처리 자체를
  "AsyncTask로 제출"하고 `pendingSyscalls`가 비어야 재개하는 흐름으로
  명시적으로 설계됨.
- **RCU 콜백 드레인**(SP-B1E258D8 §5.3, 이번 세션에 막 제안) - 콜백
  실행을 AsyncReactor 루프에 얹는 것을 그대로 제안했다 - 이 평가서가
  나오기도 전에 이미 "새 로직은 비동기 프레임워크에 얹는다"는 원칙을
  따르고 있었다는 뜻이다.

반대로 **아직 순수 동기식으로 남아 있는 것**: Mutex/Semaphore(§2/§3,
`kernel::Task` 전체를 파킹), Spinlock, Slab/PageFrameAllocator,
Scheduler 자신의 핵심 루프. 이 목록이 우연이 아니라는 것이 §6의
핵심 논지다.

## 3. "동기 구현 = 비동기 구현의 wrapper"가 이미 성립하는 사례

`AsyncTaskCompletion`(SP-F682B889 §9)이 정확히 이 패턴이다 - **하나의
비동기 실행 결과**(`AsyncTask`의 완료/실패/취소)에 대해 `waitSync()`
(WaitQueue 파킹)와 `waitAsync()`(yield 반복) 두 파사드를 제공하되,
**진짜 실행 로직(`onExec`)은 오직 하나, 비동기로만 존재**하고 동기
파사드는 그 결과를 기다리는 방법만 다르다. 이것이 이 평가서가 확인한
**성공 사례**다 - 설계자의 제안이 이미 검증된 패턴이라는 뜻이다.

이 패턴이 성립하는 이유를 일반화하면: **"한 번 시작해서 한 번
끝나는, 명확한 완료 시점이 있는 작업"**(요청→완료)일 때 자연스럽다 -
비동기 실행을 유일한 진실로 두고, 동기 호출자는 그저 "그 완료를
기다리는 방법"만 다르게 구현하면 되기 때문이다.

## 4. Mutex/Semaphore에 이 패턴을 문자 그대로 적용해 보기

### 4.1 시도 - `Mutex::lock()`을 `AsyncMutex` 기반 wrapper로

제안을 문자 그대로 따르면 이런 모양이 된다:

```cpp
// 시도안 - 채택하지 않음(§4.2 참고)
class Mutex {
public:
    void lock() {
        AsyncTask* task = /* AsyncMutex::lock()만 실행하는 AsyncTask 제출 */;
        AsyncTaskCompletion completion;
        completion.init(task);
        completion.waitSync();  // 완료까지 현재 kernel::Task를 파킹
    }
    // ...
private:
    AsyncMutex _inner;  // 실제 상태/알고리즘은 전부 여기
};
```

### 4.2 문제점 - §3과 달리 "완료형 작업" 모양이 아니다

1. **락 획득은 "완료 시점이 있는 1회성 작업"이 아니라 "상태를 계속
   들고 있는 것"이다**: `AsyncTaskCompletion`이 감싸는 대상(§3)은
   끝나면 사라지는 실행이지만, Mutex는 `lock()`이 반환한 뒤에도
   호출자가 "소유"라는 상태를 계속 유지한다 - `unlock()`은 그
   상태를 없애는 완전히 별개의 호출이다. `AsyncTask`/`AsyncTaskCompletion`
   모델은 "하나의 실행이 끝나면 끝"이라 이 지속적 소유 개념을
   자연스럽게 표현하지 못한다(둘로 쪼개거나 억지로 끼워 맞춰야 함).
2. **모든 lock()/unlock()마다 AsyncTask 제출 비용이 붙는다**: `AsyncTask`
   전용 스택을 Slab에서 할당/해제(SP-F682B889 §5)하고 리액터
   큐에 넣었다가 실행되길 기다리는 전체 과정이 **이 커널에서 가장
   빈번하게 호출될 프리미티브**(거의 모든 임계구역 보호)마다 반복된다
   - 원래 Mutex는 경합이 없으면 Spinlock 한 번으로 끝나는(§2의 빠른
   경로) 매우 가벼운 연산인데, 이걸 항상 AsyncTask 제출로 감싸면
   **경합이 없는 흔한 경우조차 리액터 왕복 비용을 강제**하게 된다 -
   손해가 이득보다 명백히 크다.
3. **리액터 자신이 Mutex를 쓰면 순환 의존이 생긴다**: `AsyncReactor::
   reactorTaskEntry()`(SP-F682B889 §3.4) 자신이나 그 초기화 경로가
   어떤 Mutex를 잡아야 한다면(예: 커널 내부 공용 자료구조), 그
   Mutex::lock()이 내부적으로 "AsyncTask를 제출하고 리액터가 처리해
   주길 기다리는" 구조가 되는 순간 **리액터가 자기 자신의 처리를
   기다리는 데드락**이 성립할 수 있다 - Mutex는 리액터보다 더
   기반에 있어야 하는 프리미티브인데, 이 wrapper안은 그 관계를
   거꾸로 뒤집는다.
4. **"완전한 kernel::Task 컨텍스트"라는 존재 이유 자체가 사라진다**:
   SP-0666DB3C §2/§3의 Mutex/Semaphore가 별도로 존재하는 이유는
   "리액터가 아닌 일반 Task 컨텍스트에서 진짜로 그 Task를 재울 수
   있을 때" 쓰기 위해서다(§10.1이 반대로 "리액터에서는 절대 이걸
   쓰면 안 된다"고 명시). 이 wrapper안은 결국 모든 Mutex 호출을
   "리액터를 거치는 비동기 작업"으로 만들어 버려서, 애초에 이
   구분을 만든 이유(§10.1의 문제 정의)를 없던 일로 만든다.

### 4.3 결론 - 이 조합에는 "wrapper" 방향이 맞지 않는다

§3의 성공 사례와 Mutex/Semaphore의 실패 사례를 비교하면 기준이
드러난다: **"완료되면 사라지는 1회성 실행"은 비동기가 유일한 구현이고
동기는 그 결과를 기다리는 방법일 뿐이지만, "호출 후에도 상태를
계속 들고 있는 동시성 프리미티브"는 애초에 "비동기 버전이 더
근본적인 유일한 구현"이라는 전제 자체가 성립하지 않는다** - Mutex의
"진짜" 알고리즘(CAS 기반 상태 전이)은 동기/비동기 어느 쪽에도
속하지 않는 중립적인 것이고, 동기/비동기는 둘 다 "경합 시 무엇을
하는가"(파킹 vs yield)만 다른 **대등한 두 정책**이다 - 한쪽이 다른
쪽을 감싸는 관계가 아니다.

## 5. 대안 설계 - 공통 코어 추출 + 경합 정책 주입 (v1 제안)

SP-0666DB3C §10.4-3이 이미 "Semaphore와의 코드 중복... 공통
템플릿화할지는 구현 시점에 검토"라고 열어 뒀던 질문에 대한 답이기도
하다. `Mutex`/`AsyncMutex`가 공유하는 부분(상태, 빠른 경로 CAS
확인)을 코어로 뽑고, 다른 부분(경합 시 무엇을 하는가)만 정책으로
분리한다:

```cpp
// minicore/kernel, 가칭 mutex_core.h
namespace kernel {

// Mutex/AsyncMutex가 공유하는 상태 + 빠른 경로. "경합했을 때 무엇을
// 하는지"는 전혀 모른다 - 그건 Policy가 결정한다.
class MutexCore {
public:
    void init() { _locked = false; }

    // 성공하면 true(즉시 획득), 실패하면 false(호출부가 Policy대로
    // 재시도/대기 처리) - 빠른 경로만 여기 있다.
    bool tryAcquire() {
        SpinlockGuard guard(_guard);
        if (_locked) return false;
        _locked = true;
        return true;
    }

    // 다음 소유자를 직접 고르지 않는다(재경쟁 철학, SP-0666DB3C
    // §2.1 그대로) - 상태만 풀고, 대기 중이던 쪽에 "재시도 기회"
    // 통지는 Policy 몫이다(아래 notifyOne 콜아웃).
    template <typename NotifyFn>
    void release(NotifyFn&& notifyOne) {
        SpinlockGuard guard(_guard);
        _locked = false;
        notifyOne();
    }

private:
    Spinlock _guard;
    bool _locked = false;
};

// 경합 시 정책 - "완전한 kernel::Task를 재우는" 쪽.
struct ParkingPolicy {
    WaitQueue waitQueue;
    void onContended() { /* WaitQueue::parkCurrentAndUnlock() 재사용, §1 SP-0666DB3C */ }
    void onRelease() { waitQueue.wakeOne(); }
};

// 경합 시 정책 - "AsyncTask가 리액터에 양보하는" 쪽.
struct YieldingPolicy {
    void onContended() { AsyncTask::yield(); }
    void onRelease() { /* 대기열 없음 - 아무 일도 안 함, §10.2 그대로 */ }
};

// Mutex = MutexCore + ParkingPolicy, AsyncMutex = MutexCore + YieldingPolicy.
template <typename Policy>
class BasicMutex {
public:
    void lock() {
        while (!_core.tryAcquire()) {
            _policy.onContended();
        }
    }
    void unlock() {
        _core.release([this] { _policy.onRelease(); });
    }

private:
    MutexCore _core;
    Policy _policy;
};

using Mutex = BasicMutex<ParkingPolicy>;
using AsyncMutex = BasicMutex<YieldingPolicy>;

}  // namespace kernel
```

`Semaphore`/`AsyncSemaphore`도 동일한 형태(`SemaphoreCore` +
`count` 상태)로 정리 가능 - `MutexCore`/`SemaphoreCore` 둘 다
Spinlock 하나와 원시 상태만 가진 얇은 클래스라, §4.2-2가 지적한
비용 문제(모든 lock()마다 AsyncTask 제출)가 전혀 발생하지 않는다
(빠른 경로는 여전히 Spinlock 한 번, §4.2-3의 순환 의존 문제도
없다 - `BasicMutex<ParkingPolicy>`는 리액터를 전혀 모른다).

이 설계는 "동기가 비동기를 wrap"하는 것도 "비동기가 동기를 wrap"하는
것도 아니다 - **둘 다 더 근본적인 공통 코어를 wrap**하는 대등한
관계다. §10.4-3이 걱정했던 "과도한 추상화"(RM-23F4B687 §4 취지)도
템플릿 하나 + 정책 구조체 두 개 수준이라 크지 않다.

## 6. "동기로 반드시 남아야 하는" 로직의 범주 - 판단 기준

"대부분의 로직을 비동기 프레임워크로"라는 지시를 넓게 해석해 모든
것을 AsyncTask 위에 얹으려 하면 §4가 보여준 것과 같은 함정에
반복해서 빠진다. 이 평가서가 제안하는 판단 기준:

1. **AsyncTask 프레임워크 자신이 딛고 선 기반은 동기·논블로킹으로
   남는다** - `Spinlock`, `GenericSlabAllocator`(AsyncTask 스택
   자체를 이걸로 할당, SP-F682B889 §5), `PageFrameAllocator`,
   `Scheduler`의 핵심 큐 연산(`enqueue`/`pickNext`/`scheduleImmediate`),
   `PerCpu<T>`. 이들을 비동기 위에 다시 얹으면 "AsyncTask를 실행하기
   위해 AsyncTask가 필요한" 순환 의존이 생긴다 - §4.2-3에서 확인한
   문제의 일반화된 형태다.
2. **"상태를 계속 들고 있는 동시성 프리미티브"는 §5의 공통 코어 +
   정책 패턴을 따른다** - Mutex/Semaphore가 첫 사례, 앞으로 비슷한
   모양(예: 읽기/쓰기 락 RwLock이 생긴다면)도 이 패턴을 기본으로
   검토한다.
3. **"요청 후 한 번 완료되는 작업"은 §3의 `AsyncTaskCompletion`
   패턴을 표준으로 채택한다** - 이미 존재하는 이 패턴을 향후 새
   비동기 소비자(devmgr 실제 연결, SP-F682B889 §6이 미완으로 남긴
   부분 포함)에도 계속 재사용한다. **이 범주가 "대부분의 로직을
   비동기 프레임워크로 구현"이라는 지시가 실제로 가장 잘 들어맞는
   지점**이다 - I/O 대기, IPC 왕복, syscall 처리 등 "완료를 기다리는"
   성격의 로직은 앞으로도 새로 작성할 때 기본값을 AsyncTask 기반으로
   잡는다(이미 §2가 확인했듯 지금까지도 그래왔다).
4. **판별 질문**: 새 로직을 설계할 때 "이것이 인터럽트/I/O/다른
   AsyncTask의 완료를 기다리는가?"이면 AsyncTaskHandler로 구현하는
   것이 기본값이고, "이것이 그 완료 대기 자체를 가능하게 만드는
   기반 장치인가?"이면 동기·논블로킹으로 남긴다.

## 7. 설계 제안 요약

- **채택**: §3의 "동기 파사드 = 비동기 실행 결과를 기다리는 방법"
  패턴(`AsyncTaskCompletion`)을 앞으로 모든 신규 "완료형" 비동기
  소비자의 표준으로 명문화한다 - 새로 문서화가 필요하진 않고(이미
  SP-F682B889 §9가 설계 완료), 이 평가서가 그 패턴의 적용 범위를
  확인/공식화하는 역할을 한다.
- **거부(문자 그대로의 제안)**: Mutex/Semaphore를 AsyncMutex/
  AsyncSemaphore 위에 얹는 wrapper화는 §4.2의 이유로 채택하지 않는다.
- **대안 채택 제안**: §5의 `MutexCore`/`SemaphoreCore` + 정책 주입
  구조로 SP-0666DB3C §2/§3/§10의 네 클래스(Mutex/Semaphore/
  AsyncMutex/AsyncSemaphore)를 재정리 - 코드 중복 제거(§10.4-3이
  이미 지적한 문제)라는 원래 동기는 그대로 달성하면서, §4.2의 성능/
  순환 의존 문제는 피한다.

## 8. 아직 열려 있는 하위 과제

1. **재진입(Recursive) Mutex와의 관계**(SP-0666DB3C §5-5): §5의
   `MutexCore`에 소유자 추적을 추가해 재진입 문제를 함께 풀 것인지,
   아니면 그 개정 작업(스케줄러 진척 후 예정)을 별도로 유지할지는
   그 개정 시점에 재검토 - 이 문서는 §5 구조가 그 확장을 막지 않는다는
   것만 확인한다(Policy 계층 아래에 소유자 필드를 추가하는 자연스러운
   확장 지점이 있음).
2. **`SemaphoreCore` 실제 코드 정리 시점**: §5는 Mutex 기준으로만
   스케치했다 - Semaphore/AsyncSemaphore를 동일 패턴으로 옮기는 실제
   작업은 구현 착수 시점에 진행(RM-23F4B687 §4 원칙 - 숫자/구조
   튜닝은 계측 후).
3. **devmgr 등 아직 없는 비동기 소비자에 §3 패턴을 적용하는 구체안**:
   SP-F682B889 §6이 미완으로 남긴 "실제 소비자 연결" 작업이 실제로
   시작되면, 이 문서 §6-3의 원칙(요청-완료형은 AsyncTaskCompletion
   기본값)을 그 설계에도 적용.

## 9. 도입 여부 - 설계자 확인 필요

이 평가서는 "대부분의 로직을 비동기로" 지시를 문자 그대로의
wrapper화가 아니라 **범주별 판단 기준(§6) + Mutex/Semaphore 공통
코어 추출(§5)**로 구체화하는 것을 제안한다 - 원래 지시의 문자 그대로
구현이 아니므로(RM-23F4B687 §4 원칙), §10의 DC 질의로 이 방향에
대한 승인을 구한다.
