# 스케줄러 — 프로세스/스레드 모델 및 컨텍스트 스위칭 구조 — 요구분석

## 배경

SP-8B6B8D25 §2 항목2가 "프로세스 및 권한 관리, 컨텍스트 스위칭 및
스케줄러, SMP"를 커널 책임으로 명시했고, DS-D4E5C451이 스케줄러
자체의 상위 구조("코어별 개별 큐 + CPU affinity + CAS 기반 동기화 +
Push/Pull 로드밸런싱")는 이미 확정해 뒀다. 하지만 그 큐 안에 실제로
무엇이 들어가는지 — 스케줄링 단위(프로세스 vs 스레드), 그 단위의
자료구조(PCB/TCB), 컨텍스트 전환 메커니즘, 커널 스택 관리 — 는 아직
전혀 정해진 바가 없다. 지금 코드베이스에는 프로세스/스레드/PCB/TCB/
컨텍스트 스위칭 관련 파일이 하나도 없다(그린필드).

SP-8B6B8D25 §2-B(유저 프로세스 페이지 폴트 처리 정책)는 이미 "유저
폴트가 나면 그 프로세스만 블로킹하고 스케줄러가 다음 작업으로
전환한다"까지 확정해 뒀다 — 즉 스케줄러가 "이 실행 흐름을 블로킹
상태로 만들고 다른 걸 고른다"는 동작을 지원해야 한다는 것 자체는
이미 결정 사항이다. 다만 그 실행 흐름을 무엇이라 부르고(PCB? TCB?
둘 다?) 어떤 필드를 갖는지는 이번 DC에서 정해야 한다.

## 결정이 필요한 항목과 각 선택의 영향

1. **스케줄링 최소 단위 — 프로세스 단일 실행흐름 vs 멀티스레드
   프로세스**: v1이 "프로세스 = 실행 흐름 1개"로 단순화할지, 아니면
   처음부터 "프로세스는 주소공간+자원의 묶음, 스레드가 실제 스케줄링
   단위"로 분리할지. 후자를 택하면 PCB(프로세스, 주소공간/파일
   테이블/자식 목록 등 소유)와 TCB(스레드, 레지스터 상태+스케줄링
   상태) 자료구조가 분리되고 컨텍스트 스위칭 코드가 "같은 프로세스
   안의 스레드 전환(CR3 유지)"과 "다른 프로세스로 전환(CR3 교체)"을
   구분해야 한다. 전자를 택하면 지금은 단순하지만, 나중에 멀티스레딩이
   필요해지면 PCB 구조 자체를 다시 쪼개야 한다.
2. **PCB/TCB에 담을 필드**: 최소한 다음이 후보인데 무엇을 v1 범위에
   넣을지 확인이 필요하다 — 저장된 레지스터 상태(범용 레지스터/RIP/
   RFLAGS/세그먼트 셀렉터/CR3), 스케줄링 상태(예: `Running`/`Ready`/
   `Blocked`/`Zombie`)와 상태 전이 규칙, 우선순위/nice 값, CPU
   affinity 비트마스크, 커널 스택 포인터/크기, 블로킹 사유(예: I/O
   대기/페이지폴트/IPC 응답 대기 - SP §2-B가 요구하는 "폴트 정보를
   PCB에 매단다"를 만족하려면 이 필드가 반드시 있어야 함), 부모/자식
   프로세스 관계(프로세스 트리 필요 여부), 소속 NUMA 노드(스케줄러가
   메모리 지역성도 고려할지).
3. **컨텍스트 전환 메커니즘**: x86-64에서 하드웨어 태스크 스위칭
   (TSS 기반 `jmp`/`call` to TSS selector)은 느리고 64비트 롱모드에서
   사실상 안 쓰인다는 게 업계 정설이라, 소프트웨어 방식(현재 레지스터를
   커널 스택에 수동으로 push하고 RSP를 다음 작업의 커널 스택으로
   바꾼 뒤 pop, 어셈블리 트램폴린 필요)이 사실상 유일한 선택지로
   보인다 - 그래도 이 프로젝트가 명시적으로 다른 방식을 원하는지
   확인이 필요하다(예: 완전히 다른 접근을 의도했을 수도 있음).
4. **커널 스택 할당 정책**: 실행 흐름(TCB 또는 PCB)마다 커널 스택을
   얼마나(고정 크기 - 예: SMP AP 트램폴린처럼 32KiB?), 어떻게(
   `PageFrameAllocator::allocOrder`) 할당할지, 스택 오버플로우 감지용
   가드 페이지(의도적으로 매핑 안 한 페이지를 스택 바로 아래 둬서
   오버플로우 시 #PF로 걸리게 하는 기법)를 v1부터 넣을지.
5. **주소공간 전환 최적화**: 같은 프로세스 내 스레드 간 전환에서는
   CR3를 그대로 두고(TLB 플러시 회피), 다른 프로세스로 전환할 때만
   CR3를 갈아끼우는 최적화를 v1부터 할지 - 이건 1번 항목("프로세스
   vs 스레드 분리 여부")과 직접 연동된 결정이라 같이 정해야 한다.
6. **블로킹/웨이크업 API 모양**: SP §2-B가 요구하는 "유저 폴트 시
   그 프로세스만 블로킹, 스케줄러가 다음 작업으로 전환"을 실제로
   어떤 커널 내부 API로 노출할지 - 예를 들어 `Scheduler::blockCurrent
   (BlockReason reason)`/`Scheduler::wake(Pcb* target)` 같은 형태를
   지금 정해 두면, 나중에 유저랜드가 생겼을 때 페이지폴트 핸들러가
   바로 이 API를 호출하기만 하면 되도록 만들 수 있다.

## 결정 (QU-BA001D73 답변, 2026-09-14)

1. 스케줄링 최소 단위는 `Task`로 명명 - 일반 프로세스는 다수의 스레드(Task)를 가질 수 있고, 각 Task는 특정 코어에서만 실행 가능/불가를 스스로 결정할 수 있어야 한다(CPU affinity). 2. PCB/TCB 필드는 제시된 후보 전부 채택하고 FPU 컨텍스트(on-demand)도 추가(PN-F258698E로 추적). 3. 컨텍스트 전환은 소프트웨어 방식을 기본으로 확정. 4. 커널 스택은 컴파일 시점 매크로로 가드 페이지를 켤 수 있어야 하며(MINICORE_TASK_STACK_GUARD_PAGE), 기본 크기는 8KiB이고 Task 생성 시 인자로 다른 크기 지정 가능. 5. 같은 프로세스 내 스레드 전환은 CR3 유지, 다른 프로세스 전환 시만 CR3 교체 - 채택 확정. 6. 블로킹/웨이크업 API는 외부로 노출하지 않는다 - 인터럽트로 깨워야 하는 것들은 각 기능별 특수 API가 내부적으로 이 메커니즘을 호출한다.

이 결정은 PL-2D3184BC(스케줄러 구현, 승인·완료)에 전부 반영돼 실제 구현·검증까지 끝났다.
