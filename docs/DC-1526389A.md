## 배경

`DC-34764C25`(설계자 답변 완료) 항목2/3/4가 확정한 것: 특수 비트 S는
Linux setuid와 동일한 의미(실행 시 파일 소유자 uid로 승격), 승격은
"exec할 때 EXEC_SETUID 플래그를 허용할지 여부를 전달"하는 방식으로
그 내부 syscall(사실상 kSetuid())이 화이트리스트를 확인, S 비트를
설정하는 것 자체는 파일 소유자만 가능해야 한다.

이 답변을 실제로 구현하려고 VFS/ELF 로더 경로를 확인해 보니, **파일
자체의 소유자(uid)/모드(mode, S 비트 포함) 메타데이터를 커널이 조회할
방법 자체가 없다**는 훨씬 근본적인 공백을 발견했다:

- `minicore/kernel/vfs_syscall.h`의 `StatArgs`(Stat syscall, 그룹3
  call10, 이미 구현 완료·RM-48E1E610)는 `size`/`type`(파일/디렉터리)
  두 필드뿐이다 - uid/gid/mode 필드가 아예 없다.
- `SP-30FCC8AE`(승인됨) §7 마지막이 이미 이 사실을 명시적으로
  적어 뒀다: "파일시스템 권한과의 통합 없음 - fs 서비스 자체가 0%
  구현이라 지금 통합할 게 없다"(승인 당시 시점 기준). 그러나 지금은
  fs 서비스와 ext4/FAT32/exFAT/NTFS 드라이버 4종이 상당히 구현돼
  있는데도(`RM-C65F7760`/`RM-48E1E610` VFS 그룹 참고) `StatArgs`는
  여전히 그 필드를 안 갖고 있다 - 즉 "나중에 fs가 생기면"이라던
  유예 조건이 이미 성립했는데 실제 배선은 안 따라왔다.
- 파일 모드/소유자를 "설정"하는 syscall(Linux의 `chmod`/`chown`
  격)도 전혀 없다 - `RM-48E1E610` 그룹3(Vfs) 어디에도 없음. `DC-34764C25`
  항목4의 "S 비트를 설정하는 것 자체가 해당 파일의 소유자만 가능"
  이라는 답변을 지키려면 이 syscall부터 새로 나와야 한다.

## 왜 지금 결정이 필요한가

S 비트+exec-time 승격을 구현하려면 최소한 아래가 먼저 정해져야
하는데, 전부 VFS 계층 전체(4개 파일시스템 드라이버 + livefs)를
가로지르는 설계라 이 세션이 임의로 결정하지 않고 여쭙는다
(CLAUDE.md 규칙 4):

1. **어느 계층이 uid/gid/mode를 실제로 저장하는가** - ext4/NTFS는
   각자 네이티브 온디스크 필드가 있지만(ext4 inode의 i_uid/i_gid/
   i_mode, NTFS는 POSIX 확장 속성 없이는 없음), FAT32/exFAT는
   **네이티브 형식 자체에 유닉스 권한 개념이 없다**(읽기전용/숨김
   속성 비트뿐) - FAT32/exFAT 볼륨의 파일에 uid/mode를 어떻게
   표현할지(예: 항상 root:root 0755로 고정, 별도 사이드카 메타데이터,
   아니면 이 두 포맷에서는 S 비트 자체를 항상 거부) 결정이 필요.
2. **`StatArgs`/`Chmod`/`Chown` syscall의 정확한 필드/시맨틱** -
   새 syscall이 몇 개나 필요한지(`Chmod`+`Chown` 별도 vs 통합),
   `RM-48E1E610` 그룹3(Vfs)의 다음 미사용 call(15)부터 예약.
3. **exec-time 승격의 정확한 트리거 지점** - `SpawnProcess`
   syscall(그룹0 call4)에 `EXEC_SETUID` 플래그를 추가해 호출자가
   명시적으로 켜야만 승격을 시도하는지(답변이 "허용할지 여부를
   전달"이라고 한 것과 일치), 아니면 파일의 S 비트만 보고 커널이
   플래그 유무와 무관하게 자동으로 승격하는지(더 Linux스럽지만
   "플래그를 전달"이라는 표현과 다소 어긋남).
4. **livefs(현재 유일하게 실사용 중인 KernelDriver 마운트) 자신의
   소유자** - `/sys/live` 하위 항목들이 전부 커널이 즉석에서 만든
   가상 파일이라 "소유자"라는 개념 자체가 부자연스러울 수 있음(항상
   root:root로 고정해도 되는지).

## [답변 반영 - 설계안 작성 완료, 2026-09-28]

설계자 답변(`QU-85099CFF`, 2026-09-28): "FAT32/exFAT에서는 S 비트가
지원되지 않아도 돼. 나머지 문제는 별도 설계안을 작성해줘. livefs의
소유자는 항상 root지만, 프로세스나 유저별로 자동으로 노출되는
것들은 해당 유저 소유로."

이 답변대로 `SP-9039F955`(review, 승인 대기)를 작성해 제출했다 -
`StatArgs`/`KernelFsStatArgs`에 uid/gid/mode 확장(ext4는 이미
파싱돼 있던 값을 그대로 노출만 하면 됨을 코드 조사로 확인, NTFS는
FAT32/exFAT와 동일하게 고정값 취급을 제안, livefs는 root 고정+
향후 per-user 서브트리 규칙), Chmod/Chown syscall(그룹3 call14/15,
chmod=소유자/root만·chown=root만), EXEC_SETUID(`SpawnProcessArgs`에
`imagePath` 필드 신설 - 커널이 호출자 주장을 안 믿고 직접 Stat해
S 비트를 확인해야 하는 구조적 이유 포함)를 담았다. 승인 대기 중 -
`QU-B4D4C5AC`.
