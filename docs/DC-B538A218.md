## 배경

SP-1FBC0EEB(메시징 채널 IPC — 설계 제안) 작성 중 임의로 정하지 않고
확인이 필요하다고 판단한 세부를 모았다. 전부 그 문서의 "결정이
필요한 사항" 절에서 이 문서를 참조했다.

## 결정 (QU-B9FFBD37 답변으로 전부 해소, 2026-09-14)

설계자 답변 원문: "1. 원문 이름을 그대로 유지할 필요는 없고, 형태만
제안한 것이지 고정된 구조로 받아들이지 마라. 2. 어떤 객체냐에
관계없이 `이름`들을 담는 공간은 결국 `/sys/live/named/` 하에
비치되는 `가상 파일`들이다. 이름이 충돌나면 개설을 실패시켜야 하고,
`개설`을 시도할 때 그 이름이 `메시징 채널`인지 `큐`인지 `공유
메모리`인지는 파악할 수 없어야 한다(보안정책). 3. recv/send가
아니라 write/read로 통일하고, 닫힌 파이프를 대상으로 RW를 하려고
하면 무조건 -1과 에러코드로 broken pipe를 나타내야 하며, 이
브릿지 파이프들은 기본적으로 비동기 동작을 한다. 단, 블로킹
옵션이 설정되면 블로킹 동작을 한다.(caller 관점에서) 4. 브릿지
파이프의 링 버퍼는 커널이 설정값을 보관하고, 그 값으로 제한한다
(최소 메모리 페이지 단위, 예: 4K). 열고 닫을 때 크기를 직접
지정할 수 없고 huge page(예: 2M)를 사용할지 아닐지만 플래그로
제출한다. 지원하지 않는 경우(커널이 설정에 의해 금지한 경우)엔
실패 코드를 반환하라. 5. destroyChannel도 포함되어야 한다."

1. **명명 교정 승인 여부** → **원문/제안 이름 전부 비고정으로
   확정**: `Channel`/`BridgePipe`/`closeBridge` 등은 형태를 보이기
   위한 예시일 뿐, 구현 단계에서 얼마든지 바뀔 수 있는 제안으로
   취급한다(고정된 API 이름 승인이 아니다).
2. **이름 있는 채널의 네임스페이스 범위와 충돌 정책** →
   **`/sys/live/named/` 단일 가상 파일 네임스페이스로 확정**: 채널
   뿐 아니라 큐/공유 메모리 등 이름 있는 커널 오브젝트 전부가 이
   경로 아래를 공유한다. 이름 충돌 시 개설은 그냥 실패(먼저 연
   쪽이 유지, 덮어쓰기 없음). **보안 정책**: 이름 충돌/조작 실패
   응답이 기존 오브젝트의 종류(채널/큐/공유메모리)를 유출해서는 안
   된다 - 종류 불문 동일한 일반 실패 코드만 반환.
3. **`recv`/`send`의 경계 조건** → **`read`/`write`로 통일, 경계
   조건 확정**: 닫힌 파이프 RW는 데이터 유무와 무관하게 항상 `-1`
   +"broken pipe" 에러코드(0바이트 EOF 관례는 채택 안 함). 부분
   전송 여부 질문은 상위 결정으로 대체됨 - 기본 동작이 **비동기**
   (submit 즉시 반환 + `waitForSyscall`로 완료 확인, SP-04EE2A18의
   모델 그대로 재사용)이므로 "가득 찼을 때 블로킹할지 부분 전송할지"
   질문 자체가 무의미해짐; `BridgePipe`에 **블로킹 옵션**을 설정한
   경우에만 유저랜드 스텁이 완료까지 기다려 호출자 관점에서 블로킹
   처럼 보이게 한다.
4. **`BridgePipe` 링버퍼 크기 정책과 `destroyChannel` 필요 여부** →
   **둘 다 확정**: 크기는 호출부가 지정하지 않고 **커널 설정값**
   (최소 페이지 단위)이 상한이며, 호출부는 `useHugePage` 플래그만
   제출한다(미지원 시 실패 코드, PL-57CF86EF와는 별개 메커니즘).
   `destroyChannel`은 **필수 API로 확정**(선택 사항 아니다).

이상 4개 항목 전부 해소되어 새로 열린 결정 사항은 없다(구현
세부사항은 PL 단계에서 다룬다).
