## 배경

SP-1FBC0EEB(메시징 채널 IPC — 설계 제안) 작성 중 임의로 정하지 않고
확인이 필요하다고 판단한 세부를 모았다. 전부 그 문서의 "결정이
필요한 사항" 절에서 이 문서를 참조한다.

## 결정이 필요한 사항

1. **명명 교정 승인 여부**: 설계자 지시 원문은 "채널"을 랑데부
   지점과 연결된 통로 둘 다에 섞어 쓰고, `closeChannel`이 실제로는
   연결된 통로(원문의 "브릿지 파이프")를 닫는 함수로 쓰였다.
   SP-1FBC0EEB는 `Channel`(랑데부 지점)/`BridgePipe`(연결된 통로)로
   객체를 분리하고 `closeChannel` → `closeBridge`로 개명할 것을
   제안한다 - 이대로 진행해도 되는지, 아니면 원문 이름
   (`closeChannel`)을 그대로 유지하되 "이건 브릿지 파이프를 닫는
   함수다"라고 문서로만 명확히 하는 쪽을 원하는지.
2. **이름 있는 채널의 네임스페이스 범위와 충돌 정책**: 커널 전역
   단일 네임스페이스로 할지, 프로세스/사용자별로 분리할지. 이름
   충돌 시 "먼저 연 쪽이 이긴다"(제안) 외에 다른 정책(예: 소유자
   권한에 따른 덮어쓰기 허용)이 필요한지.
3. **`recv`/`send`의 경계 조건**: 피어가 `closeBridge`한 뒤 `recv`를
   호출하면 0바이트 반환("EOF")과 실패 코드 중 어느 쪽으로 표현할지.
   `send`가 링버퍼가 가득 찼을 때 블로킹 대신 "가능한 만큼만 쓰고
   즉시 반환"(부분 전송)을 허용할지, 아니면 항상 전량 쓰기 성공까지
   블로킹할지.
4. **`BridgePipe` 링버퍼 크기 정책과 `destroyChannel` 필요 여부**:
   버퍼 크기를 커널이 고정값으로 정할지, `openChannel`/
   `connectChannel` 호출 시 요청 크기를 지정할 수 있게 할지. 프로세스
   종료 시 자동 정리 외에, 이름 있는 채널을 명시적으로 반납(이름
   재사용 목적)하는 `destroyChannel` API를 이번 범위에 포함할지.
