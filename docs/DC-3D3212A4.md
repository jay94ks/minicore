## 배경

PL-2D3184BC 3단계(Task 커널 스택 가드 페이지)를 구현하던 중 실측으로
발견한 문제다. 가드 페이지 자체(direct map 밖 전용 가상주소에 스택을
4KiB 단위로 개별 매핑하고 바로 아래 한 페이지를 비워 두는 방식,
`minicore/kernel/task.cpp`)는 정상 동작한다 - 실측(QEMU, `-d int`)으로
확인: 4KiB 스택에서 재귀로 스택을 소모시키면 정확히 가드 페이지
안쪽 주소(`CR2=0xffff902000000f00`, 예약된 가드 페이지 `0xffff902000000000
~0xffff902000000fff` 범위 안)에서 #PF(vector 14)가 발생한다.

## 문제

그런데 이 #PF를 CPU가 전달(deliver)하려면 인터럽트 프레임(SS/RSP/
RFLAGS/CS/RIP/에러코드)을 **그 시점의 RSP에** 푸시해야 하는데, RSP가
이미 가드 페이지 바로 앞(스택이 꽉 찬 상태)이라 그 푸시 자체가 다시
페이지 폴트를 일으킨다. x86_64 예외 조합 규칙상 "#PF 전달 중 #PF"는
더블 폴트(#DF, vector 8)로 격상되는데, 우리 IDT는 모든 벡터의
IST=0(`idt.cpp`의 `gIdt[vector].ist = 0`)이라 #DF 전달도 **똑같이
고장난 RSP**를 그대로 쓴다 - 결국 그 푸시도 다시 실패해 트리플
폴트(CPU 리셋)로 귀결된다. 실측 로그:

```
1: v=0e e=0002 ... SP=0010:ffff902000000f00 CR2=ffff902000000f00   (원래 #PF, 가드 페이지 정확히 명중)
check_exception old: 0xffffffff new 0xe
2: v=08 ...       SP=0010:ffff902000000f00 (같은 RSP)             (#PF 전달 중 재폴트 -> #DF로 격상)
check_exception old: 0x8 new 0xe                                    (#DF 전달도 재폴트 -> 트리플 폴트/리셋)
```

즉 **현재 구현 그대로는 가드 페이지가 오버플로우를 "막긴" 하지만
(인접 메모리를 조용히 덮어쓰는 대신 확실히 죽는다), 원래 계획서가
명시한 목적("오버플로우 시 #PF로 걸리게 함" - 즉 로그로 원인을
확인할 수 있게)은 달성하지 못한다** - 시리얼에 아무 메시지도 안
남기고 QEMU가 조용히 리셋(`-no-reboot`에서는 정지)해 버린다. 실제
디버깅 상황에서는 "커널이 알 수 없이 리셋됨"과 "스택 오버플로우로
확실히 죽음"을 구분할 수 없어 진단 가치가 크게 떨어진다.

## 표준적인 해법과 이 프로젝트에 미치는 영향

실제 OS들(Linux 등)은 이 문제를 **IST(Interrupt Stack Table)**로
해결한다 - GDT에 TSS(Task State Segment, "하드웨어 태스크 스위칭"과는
별개 기능 - RSP0/IST 슬롯만 쓰고 실제 태스크 전환에는 안 씀) 하나를
두고, 특정 벡터(#DF는 필수, #PF/NMI/#MC 등도 흔히 포함)에 대해 CPU가
현재 RSP와 무관하게 **항상 정해진 별도 스택으로 강제 전환**한 뒤
핸들러를 실행하게 지시한다. 이러면 원래 스택이 고장나 있어도 #DF(또는
#PF) 핸들러는 항상 유효한 스택에서 실행돼 진단 로그를 남기고 안전하게
멈출 수 있다.

이걸 도입하면 범위가 이번 3단계보다 커진다:
- GDT에 TSS 디스크립터 추가, 코어마다 별도 TSS(+IST 스택 메모리) 필요
  (SMP 이미 존재 - AP마다 자기 몫 필요).
- IDT의 `ist` 필드(현재 전부 0으로 고정, `idt.cpp`)를 최소 #DF(및
  선택적으로 #PF)에 대해 0이 아닌 값으로 설정.
- 이 TSS 인프라는 이후 유저랜드가 생기면 syscall/인터럽트 진입 시
  RSP0 전환에도 그대로 재사용된다(SP-8B6B8D25 유저랜드 계획과 맞물림) -
  즉 "가드 페이지 진단용"으로 끝나지 않고 커널의 영구적인 하드웨어
  구조가 하나 늘어난다.

## 결정이 필요한 사항

1. **지금 TSS+IST를 최소 구현(#DF만이라도)해서 가드 페이지가 실제로
   진단 로그를 남기게 만들 것인가**, 아니면
2. **지금은 가드 페이지를 "오버플로우를 조용한 메모리 손상 대신
   확실한 크래시(리셋)로 바꾸는 안전장치"로만 받아들이고**(진단
   메시지는 없음 - 리셋 자체가 신호), TSS/IST는 나중에 유저랜드
   syscall 진입점을 만들 때(RSP0 전환이 어차피 필요해지는 시점) 같이
   구현할 것인가.

2번을 고르면 이번 3단계 구현(현재 코드, `MINICORE_TASK_STACK_GUARD_PAGE`
CMake 옵션 + `task.cpp`의 전용 가상주소 매핑)은 이미 완료 상태로
간주하고 4단계로 넘어간다. 1번을 고르면 이번 3단계 범위에 TSS/IST
최소 구현을 추가한다.

## 결정 (QU-4E00C118 답변, 2026-09-14)

1번(지금 TSS+IST 정식 구현) 채택 - "TSS+IST를 정식 구현하여 가드 페이지가 실제 진단 로그를 남기게 만들고, 다른 곳에서도 활용할 수 있도록 설계하여 설계안을 제출하라. 규모가 커지면 이 부분을 디버깅하기 더 어려워진다"(설계자 답변 원문). #DF 전용 최소 구현에 그치지 않고 별도 SP 설계안(SP-677210E6)으로 격상해 확장 가능한 형태로 제출하도록 지시함.

이 결정에 따라 SP-677210E6이 작성·승인·구현·검증까지 완료됐다(IST1-4가 #DF/NMI/#MC/#DB에 배정, IST5-7 확장 여지는 PN-5377545F로 별도 추적).
