# 커널 전용 비동기 프레임워크(Task 기반) — 설계 제안

**[제안, 검토 대기, 2026-09-14]** 스케줄러(PL-2D3184BC)가 확정한
`kernel::Task` 위에 얹을 커널 전용 비동기 실행 프레임워크를 제안한다.
아직 어느 것도 구현되지 않았다 - 이 문서는 설계자 검토/승인을 받기
위한 제안이고, 승인되면 실행 계획(PL)으로 옮겨 착수한다. 개별 갈림길
(아래 "결정이 필요한 항목" 참고)은 별도 DC(DC-추후발급)로 등록해
확정을 받는다.

## 1. 문제 정의

`kernel::Task`(PL-2D3184BC)는 스케줄러의 최소 단위지만, **하나당
고정 커널 스택(기본 8KiB)과 전체 레지스터 컨텍스트를 통째로 가진
"무거운" 실행 흐름**이다. 반면 커널 내부에서 반복적으로 필요해질
패턴은 다음과 같다 — "장치에 요청을 하나 내고, 완료 인터럽트가 올
때까지 기다렸다가, 몇 줄짜리 후속 처리를 한다"(디스크 읽기, IPC
왕복, 타임아웃 대기 등). 대기 중인 요청마다 Task를 하나씩 만들면:

- 대기 중인 요청 수만큼 8KiB+ 스택이 낭비된다(수백~수천 개의 동시
  요청을 감당하기엔 비효율적).
- 완료 인터럽트가 왔다고 해서 그 안에서 후속 처리(콜백)를 직접
  돌리면 안 된다 — 이번 세션에 실측으로 확인한 교훈(ISR 안에서
  비재진입 락을 쥔 함수를 부르면 데드락)이 일반화된 규칙이다: **ISR은
  절대 무거운/블로킹 가능한 로직을 직접 실행해서는 안 된다.**

커널이 "기다렸다가 이어서 하는" 코드를 싸게, 안전하게 표현할 방법이
필요하다 — 이게 이 프레임워크의 존재 이유다.

## 2. 목표 / 비목표

**목표**
1. 대기 중인 비동기 작업 하나마다 전용 Task(전체 스택)를 만들지
   않고도 "요청 → 완료 시 후속 처리"를 표현할 수 있게 한다.
2. 인터럽트 컨텍스트에서 하는 일을 "완료 표시 + 큐에 넣기"까지로
   최소화한다 - 실제 후속 로직은 반드시 정상 Task 컨텍스트에서
   실행되게 한다.
3. 이미 확정된 스케줄러 설계(DC-8EA1E7F6/DC-B80D8D31)와 자연스럽게
   맞물린다 - Task를 대체하지 않고 그 위/옆에 얹는다. 특히
   "블로킹/웨이크업은 외부 비공개, 기능별 특수 API로 노출"이라는
   이미 확정된 원칙(QU-BA001D73 6번)을 그대로 따른다 - 이 프레임워크
   자체가 바로 그 "기능별 특수 API"의 첫 번째 실제 사례가 된다.
4. C++ 예외 없이, freestanding 환경에서 동작한다(RM-23F4B687 기존
   제약과 동일).

**비목표(v1 범위 밖)**
- 유저랜드용 비동기 I/O 모델이 아니다 - devmgr/fs/net은 전부
  유저랜드 서비스(SP §2-A)라 이들이 쓸 API는 시스템콜/IPC 경계
  건너편 얘기고, 이 프레임워크는 **커널 자신의 내부 구현**에만
  쓰인다.
- C++20 `std::coroutine`(컴파일러/표준 라이브러리 지원, 예외 처리와
  얽힌 프레임 할당 등)에 기대지 않는다 - 손으로 짠 콜백/상태 머신
  기반으로 간다.
- NUMA 인지형 리액터 배치 등 고급 최적화는 범위 밖(스케줄러의 기존
  Push/Pull에 편승).

## 3. 핵심 개념

### 3.1 `AsyncOp` - 스택 없는 완료 단위

풀에서 얻어 쓰는 고정 크기 객체 하나가 "대기 중인 비동기 작업 하나"를
표현한다 - 전용 스택이 없다.

```cpp
namespace kernel {

enum class AsyncResult { Success, Timeout, Cancelled, Error };

using AsyncCallback = void (*)(void* context, AsyncResult result, unsigned long value);

class AsyncOp {
public:
    // 콜백/컨텍스트를 등록해 풀에서 하나 얻는다 - 호출부가 이후
    // 이 포인터를 실제 요청(예: 장치 레지스터에 쓰기)에 결부시킨다.
    static AsyncOp* acquire(AsyncCallback callback, void* context);

    // 인터럽트 컨텍스트에서 호출 가능(락 없이 lock-free 완료 큐에
    // push만 함) - 콜백은 여기서 절대 실행하지 않는다. 목표2 직결.
    static void complete(AsyncOp* op, AsyncResult result, unsigned long value);

    // 콜백 실행 후 호출부(AsyncReactor)가 풀에 반납한다.
    void release();

private:
    AsyncCallback _callback = nullptr;
    void* _context = nullptr;
    AsyncResult _result = AsyncResult::Error;
    unsigned long _value = 0;
    AtomicPtr<AsyncOp> _next;  // 완료 큐 안에서만 쓰는 침습적 다음-포인터
};

}  // namespace kernel
```

### 3.2 완료 큐 - 코어별, lock-free

스케줄러 설계(DC-B80D8D31 10번, "CAS 기반 동기화 = 큐 자료형 자체를
lock-free로")와 같은 방향 - `AsyncOp::complete()`가 push하는 큐는
libkenv에 이미 추가된 `AtomicPtr<T>`(스케줄러용으로 마련해 둔 CAS
프리미티브, PL-2D3184BC 0단계 완료분)를 그대로 재사용하는 코어별
lock-free 스택/큐다. 인터럽트에서도 안전하게 push할 수 있어야 하므로
Spinlock 폴백은 이 큐에서는 필수가 아니라 **필요조건**이다(인터럽트
컨텍스트에서 스핀락을 잡는 건 그 자체로 위험 - 목표2와 직결).

### 3.3 `AsyncReactor` - 완료 큐를 정상 Task 컨텍스트에서 드레인

```cpp
namespace kernel {

class AsyncReactor {
public:
    // 완료 큐에서 하나 꺼내 콜백을 실행한다(정상 Task 컨텍스트 -
    // 인터럽트 아님). 없으면 즉시 리턴(false).
    static bool pumpOnce();

    // 각 코어의 idle 루프(스케줄러가 실행할 작업이 없을 때)를
    // 대체한다 - pumpOnce를 반복하다 완전히 할 일이 없으면 hlt.
    static void runIdleLoop();
};

}  // namespace kernel
```

리액터를 **전용 Task로 따로 둘지, 각 코어의 idle 상태 자체를 리액터로
쓸지**는 4번 "결정이 필요한 항목" 참고 - 이 제안은 후자(idle 대체)를
1차 추천안으로 제시한다: 이미 코어마다 idle hlt 루프가 있고
(`kmain.cpp`/`smp.cpp`), 그 자리를 "완료 큐가 비었을 때만 hlt하는"
`AsyncReactor::runIdleLoop()`로 바꾸면 새 Task를 하나도 안 만들고도
전체 프레임워크가 동작한다 - 스케줄러의 코어별 큐 개념과도 자연스럽게
합쳐진다(리액터 자체가 "가장 낮은 우선순위의 코어별 상시 작업"이라고
볼 수 있음).

### 3.4 대기(Wait) API - 기능별 특수 API로만 노출

DC-8EA1E7F6(QU-BA001D73) 6번 결정을 그대로 따른다 - 범용
`Scheduler::blockCurrent()`를 외부에 노출하지 않고, 이 프레임워크가
**자기 전용 대기 API**를 제공하고 내부적으로만 그 프리미티브를 쓴다.

```cpp
namespace kernel {

// N개의 AsyncOp가 전부 끝날 때까지 "현재 Task"를 재운다(내부적으로
// 스케줄러의 비공개 block 프리미티브 사용) - 진짜로 더 할 일이
// 없는 Task(예: 지금 당장 순차적으로 여러 I/O 결과가 다 필요한
// 경우)를 위한 것이지, 매번 이걸 쓰라는 뜻은 아니다 - 콜백 체이닝
// (AsyncOp 자체의 콜백에서 다음 AsyncOp를 또 등록)이 더 가벼운
// 기본 패턴이다.
class AsyncWaitGroup {
public:
    void add(AsyncOp* op);
    void waitAll();  // 내부적으로 block, 마지막 완료 콜백이 wake
};

}  // namespace kernel
```

### 3.5 인터럽트 통합 규칙

기존 장치 핸들러 등록 방식(`Idt::registerHandler`)은 그대로 두되,
**새 규칙 하나를 코딩 컨벤션에 추가할 것을 제안한다**: 비동기 요청과
결부된 ISR은 하드웨어 상태 확인/ack까지만 하고, 그 결과를
`AsyncOp::complete()`로 큐에 넣기만 한다 - 콜백 실행/추가 I/O 발행/
락 획득 같은 일은 전부 `AsyncReactor`가 정상 Task 컨텍스트에서
드레인할 때 한다.

### 3.6 타임아웃/취소

`AsyncOp`가 HPET(전역 시각 유지 용도로 재확인됨, DC-B80D8D31 7번)
기반 타임아웃을 옵션으로 가질 수 있다 - 마감 시각까지 완료되지
않으면 프레임워크 자신이 `AsyncOp::complete(op, Timeout, 0)`을
호출해 대기 중인 쪽이 무한정 안 걸리게 한다. 취소(`Cancelled`)는
호출부가 명시적으로 요청.

## 4. 결정이 필요한 항목 (별도 DC로 등록 예정)

1. **콜백 체인 vs 스택풀 마이크로파이버**: 이 제안은 "콜백 체인"
   방식(3.1~3.3)을 1차안으로 추천한다 - 스케줄러가 막 확정한 lock-free
   큐 방향과 자연스럽게 맞고, 새로운 스택 관리 체계를 또 만들 필요가
   없다. 대안으로 "AsyncOp마다 훨씬 작은(예: 512B~1KiB) 전용 스택을
   줘서 `kContextSwitch`를 재사용해 순차적인 코드 스타일(`co_await`
   비슷한 `AsyncOp::await(event)`)을 쓸 수 있게" 하는 스택풀 방식도
   있다 - 더 자연스러운 코드가 되지만 스택 풀 관리자를 하나 더
   만들어야 한다. 콜백 체인이 복잡해지면(콜백 안에 콜백) 나중에
   스택풀 방식을 추가하는 진화 경로를 열어 두는 게 이 제안의 의도다.
2. **리액터 배치**: idle 루프 대체(3.3의 추천안) vs 코어당 전용
   리액터 Task 별도 생성 - 후자는 idle과 분리돼 우선순위를 조정할
   여지가 있지만 Task를 코어 수만큼 추가로 만들어야 한다.
3. **`AsyncOp` 풀 크기/할당 전략**: 부팅 시 고정 크기 정적 배열
   (코어별? 전역?) vs `libkmm` 동적 할당 - 풀이 고갈되면 `acquire()`가
   실패를 반환해야 하는지, 아니면 블로킹(스케줄러에 위임)해야 하는지도
   같이 정해야 한다.
4. **`AsyncWaitGroup`의 실제 필요성**: 콜백 체이닝만으로 충분하다고
   보고 이번 범위에서 아예 뺄지, 특정 시나리오(예: 여러 디스크
   블록을 병렬로 읽고 전부 모여야 다음 단계로 가는 경우)를 위해
   지금 포함할지.

## 5. 이번 제안에 포함하지 않은 것

- 실제 소비자(devmgr 필수 IO 위임 경로, PL-2070E6EF의 MSI 라우팅
  등)에 이 프레임워크를 실제로 연결하는 작업 - 승인 후 별도 PL로
  진행.
- 코어 간 완료 이관(코어 A의 인터럽트로 완료된 AsyncOp를 코어 B의
  리액터가 대신 처리하는 것) - v1은 "인터럽트가 도착한 코어의
  리액터가 그 코어의 완료 큐만 드레인"으로 단순화(로드밸런싱은
  스케줄러의 Task 단위에서만 발생, AsyncOp 단위 이관은 범위 밖).
