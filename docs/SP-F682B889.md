# 커널 전용 비동기 프레임워크(Task 기반) — 설계 제안

**[확정, 2026-09-14, QU-F86426D5 답변 반영]** 원래 제안(콜백 체인 +
스택 없는 `AsyncOp`)은 설계자 검토 결과 **스택풀 방식(`AsyncTask`,
자체 yield 지원) + 코어별 전용 리액터 Task**로 확정됐다 - 아래
본문을 확정된 최종 설계로 갱신했다. 원래 제안에서 남는 부분(문제
정의/목표/인터럽트 통합 규칙)은 그대로 두고, 핵심 개념(3절)과 API를
전부 최종 결정대로 다시 썼다. 승인된 대로 구현 계획은 PL로 분리한다
(작성 예정).

**[개정, 2026-09-14, DC-D868D9EC/QU-EF643652 답변("onCancel 추가
승인한다") 반영]** §3.1의 `AsyncTaskHandler`에 `onCancel`을 추가했다
- Syscall 서브시스템(SP-04EE2A18)이 "대상 스레드/프로세스가 완료
전에 종료되면 그 비동기 작업을 취소해야 한다"는 요구사항 때문에
제안했고 승인됐다. 아래 3.1절 코드가 그 최종 형태다.

**[핵심(스택풀) 구현 완료, 2026-09-14, 계획 PN-226CD1B5]** PL-1E247831 참고.

**[추가, 2026-09-14, 설계자 지시]** - "AsyncTask에 AsyncToken,
AsyncTokenSource를 도입하고, 이게 트리거되면 취소된걸로 간주하는
메커니즘을 설계해봐." §8에서 설계한다 - SP-0666DB3C §9.6-2("AsyncTask
자체의 취소 지원 여부는 이 문서가 결정하지 않는다")가 열어 뒀던
질문에 대한 답이기도 하다.

**[추가, 2026-09-14, 설계자 지시]** - "AsyncTask와 AsyncTaskCompletion
객체로 나눠서 AsyncTaskCompletion이 완료/취소 여부를 전파하도록
만들고 AsyncTaskCompletion이 비동기 대기, 동기식 대기 두가지를
구현하는 구조를 고안해봐." §9에서 설계한다 - §3.3의 AsyncTaskGroup/
AsyncTaskWaitGroup/AsyncTaskAwaiter를 대체하지 않고, 그 위에 얹는
응집된 파사드로 구성한다.

## 1. 문제 정의

`kernel::Task`(PL-2D3184BC)는 스케줄러의 최소 단위지만, **하나당
고정 커널 스택(기본 8KiB)과 전체 레지스터 컨텍스트를 통째로 가진
"무거운" 실행 흐름**이다. 반면 커널 내부에서 반복적으로 필요해질
패턴은 다음과 같다 — "장치에 요청을 하나 내고, 완료 인터럽트가 올
때까지 기다렸다가, 몇 줄짜리 후속 처리를 한다"(디스크 읽기, IPC
왕복, 타임아웃 대기 등). 대기 중인 요청마다 Task를 하나씩 만들면:

- 대기 중인 요청 수만큼 8KiB+ 스택이 낭비된다(수백~수천 개의 동시
  요청을 감당하기엔 비효율적).
- 완료 인터럽트가 왔다고 해서 그 안에서 후속 처리를 직접 돌리면
  안 된다 — 이번 세션에 실측으로 확인한 교훈(ISR 안에서 비재진입
  락을 쥔 함수를 부르면 데드락)이 일반화된 규칙이다: **ISR은 절대
  무거운/블로킹 가능한 로직을 직접 실행해서는 안 된다.**

## 2. 목표 / 비목표

**목표**
1. 대기 중인 비동기 작업 하나마다 전체 Task(전체 스택)를 만들지
   않고도 "요청 → 완료 시 후속 처리"를 표현할 수 있게 한다 -
   `AsyncTask`는 Task보다 훨씬 가벼운 전용 스택을 쓴다(3.2절).
2. 인터럽트 컨텍스트에서 하는 일을 "완료 표시 + 큐에 넣기"까지로
   최소화한다 - 실제 후속 로직은 반드시 리액터 Task 컨텍스트에서
   실행되게 한다. **[재정정, 2026-09-19, PN-D47FBB8D 완료 반영]**
   목표("ISR 밖의 정상 컨텍스트에서 실행")는 그대로 유효하고, 그
   정상 컨텍스트는 다시 진짜 `kernel::Task`다 - 다만 §3.4가 원래(2026-09-14)
   뜻했던 "다른 Task와 경쟁하는 별도 리액터 Task"가 아니라, 코어당
   정확히 하나 존재하는 `TaskClass::Idle` Task(`gIdleTask[coreIndex]`,
   `PN-D47FBB8D` 신설)다 - `pickNext()`가 다른 후보가 없을 때 이 Task로
   폴백하고, 그 본문이 `AsyncReactor::drainOnce(coreIndex)` 펌핑
   루프다.
3. 각 코어에 전용 리액터 Task를 둬 "진짜 동시성"을 갖는 비동기
   처리를 구현한다(설계자 확정, 2026-09-14) - 스케줄러(PL-2D3184BC)
   위에 얹되, 긴급한 인터럽트가 왔을 때 그 코어의 리액터 Task를
   우선순위 무시하고 즉시 스케줄링할 수 있어야 한다(4절 - 스케줄러
   자체에 새 프리미티브 필요). **[정정, 2026-09-16, QU-96BBB769/
   QU-4034561A 답변 - 이 항목의 "전용 Task" 부분은 뒤집혔다]**
   코어별로 독립적인 비동기 처리라는 목표 자체는 그대로 유효하지만,
   "리액터가 다른 Task와 나란히 경쟁하는 전용 Task"라는 수단은
   폐기됐다 - 리액터는 이제 그 코어에 실행 가능한 다른 Task가 없을
   때 스케줄러가 들어가는 idle 자리 자체(runLoop()의 idle 폴백이
   AsyncReactor::drainOnce(coreIndex)를 직접 호출)로 통합됐다 -
   §3.4/PN-FEAAF154(completed) 참고.
4. 이미 확정된 스케줄러 설계(DC-8EA1E7F6/DC-B80D8D31)의 "블로킹/
   웨이크업은 외부 비공개, 기능별 특수 API로 노출" 원칙(QU-BA001D73
   6번)을 그대로 따른다 - `AsyncTaskWaitGroup`이 그 첫 실제 사례다.
5. 기능별로 콜백을 **한 번만 등록**해 두고, 실제 작업 발생 시엔
   Slab로 할당한 `args`만 콜백에 넘겨 실행한다(설계자 확정,
   2026-09-14) - 매번 콜백을 넣고 빼거나 비동기 작업 처리기가
   파편화되는 것을 피한다.
6. C++ 예외 없이, freestanding 환경에서 동작한다.

**비목표(v1 범위 밖)**
- 유저랜드용 비동기 I/O 모델이 아니다 - devmgr/fs/net은 전부
  유저랜드 서비스(SP §2-A)라 이 프레임워크는 **커널 자신의 내부
  구현**에만 쓰인다.
- **코어 간 완료 이관**(코어 A에서 완료된 AsyncTask를 코어 B의 리액터가
  대신 처리) (계획 PN-2CD26587) - v1은 인터럽트가 도착한 코어의
  리액터가 그 코어의 실행 큐만 처리한다(로드밸런싱은 Task 단위에서만).

## 3. 핵심 개념 (확정, 2026-09-14; 2026-09-14 메시지/QU-4F905C08로 갱신)

### 3.1 처리기 등록 - 기능별 1회 등록, 실행/실패/취소 전부 구현 책임

**갱신(2026-09-14, 설계자 메시지 + QU-4F905C08 답변)**: 단순 함수
포인터 콜백 대신, **실행(exec)과 실패(failure) 두 경로를 모두
구현해야 하는 처리기 인터페이스**로 바뀌었다 - Slab 할당자
(SP-D7013B26)가 메모리 고갈 시 블로킹 없이 즉시 실패를 반환하도록
확정됐기 때문에(스케줄러 데드락 방지), 그 실패를 받아 처리하는
쪽이 반드시 있어야 한다. **작업 주체별 내부 데이터(`args`)의
생성과 반납(해제) 책임도 전부 이 처리기가 진다** - 프레임워크
자신은 `args`를 대신 만들거나 해제하지 않는다(설계자 지시,
2026-09-14).

**추가 개정(2026-09-14, DC-D868D9EC/QU-EF643652 승인)**: `onCancel`
을 세 번째 순수 가상 함수로 추가한다 - 이 `AsyncTask`의 결과를
가져갈 예정이던 `UserThread`(Syscall 서브시스템, SP-04EE2A18)가
완료 전에 종료돼 강제로 취소될 때 호출된다. **[정정, 2026-09-16,
PN-40E976F2/PN-A8453D65 - 소유권 용어 정정]** 위 "소유"라는 표현이
오해를 부른다 - 이 `AsyncTask`의 실제 소유자는 그것을 실행하는
리액터(그 코어의 `gReactorTasks[coreIndex]`, 아래 신설 `ownerTask`
필드)이지 `UserThread`가 아니다. `UserThread`는 그 완료를 소비할
예정이었던 *대기자*일 뿐이고, 대기자가 먼저 죽으면 "결과를 가져갈
사람이 아무도 남지 않았다"는 이유로 취소가 트리거되는 것이지
소유권 관계 때문이 아니다(설계자 지시, PN-40E976F2). `args`
해제 등 정리는 여전히 이 처리기 책임(위 원칙 그대로) - 서비스에
위임 중이었다면 그 채널 요청(SP-1FBC0EEB의 `BridgePipe` 등)도 여기서
함께 정리해야 한다.

```cpp
namespace kernel {

// 작업 주체(기능)별로 구현 - 실행/실패/취소 셋 다 구현 책임을 진다.
// args(작업 주체별 내부 데이터)를 실행 전에 만드는 것도, 실행이
// 끝나거나(onExec) 실패하거나(onFailure) 소유자가 먼저 죽어
// 취소되거나(onCancel) 어느 쪽으로 끝나든 그 해제도 전부 이
// 처리기의 몫이다 - 프레임워크는 관여하지 않는다.
class AsyncTaskHandler {
public:
    virtual ~AsyncTaskHandler() = default;
    virtual void onExec(AsyncTask* task, void* args) = 0;
    // Slab 할당 실패(nullptr) 등 프레임워크 내부 사유를 포함해
    // 실행 자체가 불가능했을 때 호출된다 - 재시도 여부도 이 처리기가
    // 결정한다(예: 여기서 다시 submit).
    virtual void onFailure(AsyncTask* task) = 0;
    // 이 작업의 소유 스레드/프로세스가 완료 전에 종료돼 강제로
    // 취소될 때 호출된다(onExec/onFailure 둘 다와 배타적 - 셋 중
    // 정확히 하나만 불린다). 이 AsyncTask를 소비하는 첫 사례는
    // Syscall 서브시스템(SP-04EE2A18 "종료 시 취소 처리")이다
    // (계획 PN-40E976F2). **[추가, §8]** onExec이 이미 시작된
    // 뒤라면 onCancel은 불리지 않는다 - 대신 §8의 AsyncToken을
    // onExec 스스로 확인해 조기 종료하는 협조적 경로를 탄다.
    virtual void onCancel(AsyncTask* task, void* args) = 0;
};

// 기능별로 부팅/초기화 시 한 번만 등록한다 - 요청이 생길 때마다
// 등록/해제하지 않는다(설계자 지시, 2026-09-14).
class AsyncCallbackRegistry {
public:
    static AsyncTaskSubjectCode registerHandler(AsyncTaskHandler* handler);
    static AsyncTaskHandler* resolve(AsyncTaskSubjectCode subjectCode);
};

}  // namespace kernel
```

실제 요청이 생기면 처리기 자신이 `GenericSlabAllocator::
alloc(sizeof(Args))`(SP-D7013B26 참고)로 `args`를 만들고(실패하면
그 처리기가 알아서 처리 - 즉시 포기하거나 나중에 재시도), 아래
`AsyncTask`에 담아 리액터에 제출한다.

### 3.2 `AsyncTask` - 자체 스택을 갖는 스케줄링 가능 단위(구 `AsyncOp`)

`kernel::Task`와 같은 소프트웨어 컨텍스트 전환(`kContextSwitch`)을
재사용하되, **Task보다 훨씬 작은 전용 스택**을 쓴다(정확한 크기는
구현 계획에서 실측 확정 - Slab 할당자의 한 버킷을 스택으로 쓰는
방안 포함해 검토). 콜백 실행 중 스스로 `yield()`를 불러 리액터에게
제어를 돌려주고 나중에 재개될 수 있다(설계자 지시, 2026-09-14 -
"비동기 작업 자체에도 별도의 yield 기능이 있어서 이걸 호출하면
현재 진행중이던 비동기 작업을 suspend하고, 다음 비동기 작업을
처리할 수 있어야 한다").

**분류/비교 식별자 갱신(2026-09-14, 설계자 메시지)**: `callbackId`
하나였던 것을 **두 코드로 분리**한다 - `subjectCode`(uint32_t, 어느
`AsyncTaskHandler`에 속하는지)와 `manageCode`(uint64_t, 그 작업
주체 안에서 이 인스턴스를 식별/추적하는 관리 코드 - 예: 요청
시퀀스 번호, 상관관계 ID). `AsyncTaskGroup`/`AsyncTaskWaitGroup`/
`AsyncTaskAwaiter`가 "이 그룹의 이 작업"을 정확히 비교/매칭할 때
이 두 코드를 함께 쓴다.

**[추가, §8, 2026-09-14]** `AsyncTask`에 `AsyncTokenSource
cancelSource` 필드를 추가한다 - §8의 협조적 취소 채널.

```cpp
namespace kernel {

using AsyncTaskSubjectCode = unsigned int;   // uint32_t - 작업 주체 코드
using AsyncTaskManageCode = unsigned long;   // uint64_t - 작업 주체별 관리 코드(구현 시 64비트 폭 확정)

enum class AsyncTaskState { Ready, Running, Suspended, Completed, Failed,
    // [추가, 2026-09-16, PN-40E976F2 구현 반영] 결과를 기다리던
    // UserThread가 완료/실패보다 먼저 죽어 아무도 결과를 가져가지
    // 않게 됐을 때 전이하는 상태 - reactorTaskEntry()가 이 상태를
    // 보면 onExec을 실행/재개하지 않고 곧장 onCancel만 호출한 뒤
    // 자원을 반납한다(async_task.cpp).
    Cancelled };

struct AsyncTask {
    unsigned long savedRsp = 0;   // kContextSwitch 재사용(Task와 동일한 소프트웨어 스위칭) - 스택풀 모드 전용
    unsigned long stackBase = 0;  // Slab(또는 전용 풀)에서 받은 고정 크기 스택 - 스택풀 모드 전용
    AsyncTaskState state = AsyncTaskState::Ready;

    // [추가, 2026-09-15, §7.3] 코루틴 모드 전용 - onExec()가 코루틴으로
    // 구현된 경우에만 쓰인다(스택풀 모드는 위 savedRsp/stackBase만
    // 씀, 이 필드는 비어 있음). suspend된 coroutine_handle을 여기
    // 저장해 뒀다가 다음 디스패치에서 reactorTaskEntry()가 이 값으로
    // resume()한다.
    std::coroutine_handle<> coroHandle = nullptr;

    AsyncTaskSubjectCode subjectCode = 0;
    AsyncTaskManageCode manageCode = 0;
    void* args = nullptr;   // 생성/해제 전부 해당 AsyncTaskHandler 책임(3.1절)

    AsyncTokenSource cancelSource;  // §8 - 협조적 취소 신호(값 소유, 힙 불필요)

    AtomicPtr<AsyncTask> next;    // 리액터 실행 큐용 침습적 포인터
```

### 3.3 `AsyncTaskGroup` / `AsyncTaskWaitGroup` / `AsyncTaskAwaiter` (계획 PN-22438B73)

설계자 확정(2026-09-14) - "비동기 작업 그룹은 AsyncTaskGroup, 대기
그룹은 AsyncTaskWaitGroup, 특정 작업을 대기하는 객체는
AsyncTaskAwaiter로 설계하라." **[추가, §9, 2026-09-14]** 이 세 클래스는
`AsyncTaskCompletion`(§9)이 그 위에 얹는 파사드의 기반으로 계속
쓰인다 - 폐기되지 않는다.

**[확정, 2026-09-16, QU-86DD998F 답변]** "AsyncTaskGroup은 AsyncTask를
확장하는 무언가가 아니라 그 작업들을 대기하는 곳에서 작업들을 모아놓고
관리하는 유틸리티야. 얘는 AsyncTask를 weak ref로 들고 있으면 돼." -
PN-22438B73 착수 중 발견된 공백(멤버 완료를 그룹이 어떻게 아는지)에
대한 답 - 애초에 제시했던 두 후보(`AsyncTask`에 `owningGroup` 필드
추가/`waitingTask` 필드 재해석) **둘 다 기각**됐다. `AsyncTask`
구조체 자신은 전혀 건드리지 않는다 - 관계의 방향은 Group → AsyncTask
단방향(weak reference)뿐이고, `AsyncTask` 쪽에는 자신이 어느
Group에 속하는지 아는 필드가 없다. 즉 "멤버 완료" 감지는 리액터의
완료 처리 경로가 Group에 푸시 알림을 주는 방식이 아니라, **Group
자신이 보유한 멤버들을 능동적으로 확인(폴링)하는 방식**이어야 한다
(`pendingCount()`/`waitAll()`이 내부적으로 각 weak ref를 순회해
상태를 재확인) - `AsyncTaskAwaiter`의 `yield()` 반복 폴링과 같은
결의 메커니즘을 그룹 단위로 확장한 것에 가깝다. "weak ref"의 정확한
구현(예: 세대 카운터를 곁들인 핸들 - `AsyncTask`가 Slab에서 재사용될
때 순회 중인 Group이 죽은/재사용된 멤버를 안전하게 구분할 수 있어야
함)은 이 문서가 확정하지 않는다 - PN-22438B73 구현 시점에 확정.

```cpp
namespace kernel {

// 서로 관련된 AsyncTask 여러 개를 묶어 관리(예: "이 4개 디스크
// 블록 읽기").
class AsyncTaskGroup {
public:
    void add(AsyncTask* task);
    unsigned int pendingCount() const;
};

// 그룹 전체가 끝날 때까지 "현재 Task"를 재운다 - 내부적으로
// 스케줄러의 비공개 block 프리미티브를 쓴다(DC-8EA1E7F6 6번 원칙
// 그대로 - 범용 block API는 여전히 비공개, 이게 그 전용 API).
class AsyncTaskWaitGroup {
public:
    void add(AsyncTask* task);
    void waitAll();
};

// 다른 AsyncTask 하나가 끝나기를 "현재 AsyncTask 컨텍스트 안에서"
// 기다린다 - AsyncTask::yield()를 반복 호출하며 리액터에 제어를
// 돌려주는 방식으로 구현(전체 리액터를 블로킹하지 않음). 중첩된
// 비동기 의존관계(예: A가 B의 결과가 필요) 표현에 쓴다.
class AsyncTaskAwaiter {
public:
    explicit AsyncTaskAwaiter(AsyncTask* target);
    void await();  // target 완료까지 yield() 반복
};

}  // namespace kernel
```

### 3.4 `AsyncReactor` - 코어당 전용 Task, 우선순위 무시 즉시 스케줄링

설계자 확정(2026-09-14) - "리액터 루프는 Task로 wrapping되어 각
코어마다 하나씩 배치되어야 진짜 동시성을 갖는다... 긴급한 인터럽트가
발생했을 때 비동기 작업을 처리하는 리액터 task를 즉시 스케줄링하여
실행해야 한다." idle 루프 대체안(원래 제안의 1차 추천)은 **폐기**
됐다 - 리액터는 전용 Task다.

**[재설계 확정 방향, 2026-09-16, QU-96BBB769 답변 - 2026-09-14 결정을
뒤집음]** 설계자 답변: "Idle이 하던 동작을 비동기 프레임워크가
계승받아서 전부 통합." - 즉 위 2026-09-14 결정("idle 루프 대체안은
폐기됐다, 리액터는 전용 Task다")이 **뒤집혔다**. 새 방향: 코어별
리액터는 더 이상 "다른 Task들과 나란히 경쟁하는 전용 Task"가 아니라,
**그 코어에 실행 가능한 다른 Task가 없을 때 스케줄러가 들어가는 자리
자체**가 된다 - 기존 idle 루프(보통 HLT 대기)가 하던 역할을 리액터가
흡수해 통합한다.

**우선순위 무시 즉시 스케줄링도 이 자리에 적용된다(추가 확정)**:
"긴급 인터럽트 발생 시 전용 Task를 즉시 스케줄링"하던 요구사항(§4)이
이제 이 통합된 자리(구 idle)에도 그대로 적용돼야 한다 - 설계자 답변:
"Idle이 그 역할을 함께 맡았으니, Idle도 우선순위를 무시하고 즉시
스케쥴링 될 수 있어야해." §4의 `Scheduler::scheduleImmediate`류
프리미티브는 **폐기되지 않고 오히려 이 통합된 자리를 대상으로
확장**된다.

**[구조 확정, 2026-09-16, QU-4034561A 답변 - 선택지 (B) 채택]**
설계자 답변: **"(B)로 설계하자."** - 리액터는 더 이상 별도
`kernel::Task`(전용 스택/`kContextSwitch`)가 아니라, **`runLoop()`의
idle 폴백 자리(기존 `sti; hlt`)에서 직접 호출되는 인라인 로직**이
된다. 위 2026-09-14 "리액터는 전용 Task" 결정은 최종적으로
**폐기**됐다 - `AsyncReactor::reactorTaskEntry()`라는 별도 Task
진입점 개념 자체가 사라진다(§3.4 새 구조 아래에서 재정의, 아래
참고).

**"긴급 인터럽트 시 즉시 처리" 요구사항 - 설계자가 두 갈래로 답변**:
1. **코어가 진짜 idle(hlt)일 때**: 별도 메커니즘이 필요 없다 -
   "`hlt`를 해도 상관이 없는게, `긴급한 사건(인터럽트)`가 발생되면
   `hlt`를 탈출하게 되니 전혀 고려할 필요가 없어." `sti; hlt`는
   어떤 인터럽트로도 즉시 깨어나는 하드웨어 특성 그대로이므로,
   깨어난 뒤 다시 리액터 로직(§3.4 아래 새 구조)을 확인하면 된다 -
   §4의 `scheduleImmediate`류 프리미티브가 이 경우엔 **불필요**.
2. **코어에 다른 Task가 실제로 실행 중일 때**: "다른 Task가 비동기
   작업을 큐잉 하거나 뭔짓을 했을 때 스케쥴러 단에서 비동기
   프레임워크에 알림(Notification)을 보내어 깨우면 돼" - ISR의
   `submitCompletion()`이나 다른 Task의 async 작업 제출 경로가
   스케줄러에 **Notification**을 보내고, 스케줄러가 그걸 받아 이
   코어의 실행 흐름에 개입해 리액터 처리를 앞당긴다. 정확한 전달
   메커니즘(기존 IPI 인프라 재사용 여부, 플래그+다음 tick 확인
   vs 강제 IPI 등)은 이 문서 범위를 넘는 구현 세부라 §4 갱신에서
   개략만 제안하고 실제 구현 계획(PN-FEAAF154)에서 확정한다.

**영향 범위는 아직 미확정(설계자 지시로 보류)**: "비동기 프레임워크의
개정 상황에 따라서 영향 범위가 달라지니, 앞선 2개 항목을 먼저
고려해보자" - 즉 이 재설계가 AsyncReactor 전체(§3.4)에 적용되는지,
DelayedExecutionQueue 폴링 배선(PN-C46DF296)에 한정되는지는 위 통합/
개칭이 구체화된 뒤 다시 확인한다.

관련 재작업 계획: **PN-FEAAF154**(완료, commit `5f70565` - 아래 코드
스케치는 이 계획의 최종 구현을 반영해 갱신됨. `reactorTaskEntry()`/
전용 Task 개념은 실제로 완전히 폐기됐다 - 이 문단 바로 위가 이미
서술한 (B) 구조 그대로).

**[재정정, 2026-09-19, 설계자 직접 확인 - 위 (B) 해석/PN-FEAAF154
구현 둘 다 원래 지시를 잘못 좁혀 읽었다]** "리액터는 더 이상 별도
kernel::Task가 아니다"라는 위 문장은 **"Task 표현 자체가 전혀 없다"는
뜻이 아니었다** - 실제 지시: "idle 태스크는 모든 코어에 하나씩 있어야
하는 작업인데, async reactor가 idle과 통합된다면, async reactor
자체가 각 코어마다 하나씩 돌아야 하는거야." 즉 (B)가 폐기한 것은
"다른 일반 Task들과 나란히 경쟁하는 *별도의* 리액터 Task"뿐이고,
**"코어당 정확히 하나 존재하는 idle Task" 자체는 애초에 없어진 적이
없다** - 리액터가 그 자리(코어당 유일한 idle Task)에 흡수돼 들어간
것이지, 그 자리 자체가 통째로 사라지는 게 아니다.

**실제 구현(PN-FEAAF154, commit `5f70565`)은 이 점에서 지시를 벗어나
있다**: `Scheduler::pickNext()`는 `gImmediateQueues`/`gRtQueues`/
`gNormalQueues` 세 큐에서만 뽑고 idle/리액터를 반환할 수 있는 후보로
전혀 취급하지 않으며, idle 상태는 `gCurrentTask[coreIndex] = nullptr`
로만 표현되고 `Scheduler::runLoop()`가 그 바깥의 별도 raw 루프에서
`drainOnce()`를 직접 호출하는 구조다(pickNext()가 반환하는 어떤
Task도 아님) - 즉 "코어당 정확히 하나 존재하는 idle Task"가 스케줄러
관점에서 실체로 존재하지 않는다. 이 갭이 바로 **PN-D47FBB8D**가 실측
발견한 문제(`onTick()`이 `next==nullptr`일 때 `kCheckAndMarkFrozen()`/
`kIsPausedByDebugger()`를 건너뛰는 것)의 근본 원인이었다 - 그 검사들은
`next != nullptr`분기 안에만 있어서, idle/리액터가 pickNext()의 정식
후보(=next)로 존재했다면 그 코어가 idle/리액터로 전환될 때마다 자연히
평가됐을 것이다.

**정정된 요구사항**: 코어마다 정확히 하나씩 존재하는 `kernel::Task`
인스턴스(idle/리액터 통합체)를 두고, `pickNext()`가 세 큐가 모두
비었을 때 이 Task를 반환하도록 고쳐야 한다 - 그러면 `next`가 다시는
bare `nullptr`이 되지 않고, `onTick()`의 기존 `next != null` 분기
(freeze/디버그 정지 검사 포함)가 idle/리액터로의 전환에도 자연스럽게
적용된다.

**[완료, 2026-09-19, commit ec3ac2f, PN-D47FBB8D]** 위 정정된 방향
그대로 구현 완료 - `task.h`에 `TaskClass::Idle` 신설(pickNext()의
세 큐 어디에도 절대 안 들어감), `scheduler.cpp`에 코어당 정확히
하나인 `Task gIdleTask[kMaxCores]` 신설(`enterIdleLoop()`이 부팅
극초반 손수 만든 트램폴린 스택으로 직접 구성 - 일반 `Task::init()`은
Page/Slab 할당자 의존 때문에 안 씀), 옛 `gIdleSavedRsp[kMaxCores]`는
`gIdleTask[coreIndex].savedRsp`로 완전히 흡수(`runLoop()`/
`yieldCurrent()`/`parkCurrent()`/`retireCurrentTask()`/
`onForcedMigration()`이 idle로 전환할 때 `gCurrentTask[coreIndex]`를
이제 `nullptr`이 아니라 `&gIdleTask[coreIndex]`로 세팅). `onTick()`은
`pickNext()`가 빈손이면 이 Task로 폴백하되, **실제 전환은 current가
정말로 이 코어를 떠나야 하는 경우(Zombie 강제 퇴거, 또는 방금
frozen/디버그 정지로 Blocked됨)에만** 일어난다 - 초안 구현(무조건
전환)은 건강한 current를 매 유휴 틱마다 `enqueue()`했다가 다른 코어의
Pull 로드밸런싱이 훔쳐가 버리는 실측 크래시(SMP=4, #DB 폭주/워치독
NMI/Page Fault)를 냈다(PN-D47FBB8D 본문의 "두 번째 독립 버그" 절
참고) - `kCheckAndMarkFrozen()`/`kIsPausedByDebugger()`는 `next` 존재
여부와 무관하게 여전히 매 틱 평가하되, 건강한 current+대신 돌릴 것도
없으면 그냥 `return`(불필요한 전환 방지, 경쟁 창도 원천 차단)한다.

### 3.5 인터럽트 통합 규칙 (기존 유지)

비동기 요청과 결부된 ISR은 하드웨어 상태 확인/ack까지만 하고,
`AsyncReactor::submitCompletion()`으로 큐에 넣고 그 코어의 리액터
Task를 깨우기만 한다 - 콜백 실행/추가 I/O 발행/락 획득은 전부
리액터 Task(정상 컨텍스트) 안에서 한다.

**[정정, 2026-09-16, QU-96BBB769/QU-4034561A 답변]** "그 코어의
리액터 Task를 깨우기만 한다"는 표현의 수단은 폐기됐다(§3.4) - 더
이상 깨울 전용 Task가 없다. 실제로는 `submitCompletion(task,
preemptive)`가 완료된 AsyncTask를 그 코어의 실행 큐에 넣고,
`preemptive=false`면 그걸로 끝(다음에 그 코어가 idle에 들어갈 때
`AsyncReactor::drainOnce(coreIndex)`가 자연히 처리), `preemptive=true`
면 그 코어 자신에게 `kAsyncDrainVector`(0xE3) IPI를 추가로 발사해
`drainOnce()`를 즉시 강제한다. 어느 경로든 콜백 실행 자체는 여전히
ISR 밖의 정상 컨텍스트(`drainOnce()`가 호출하는 지점)에서만 돈다는
목표는 그대로 유효하다.

**[재정정, 2026-09-19, PN-D47FBB8D 완료 반영]** 위 "더 이상 깨울
전용 Task가 없다"는 다시 정확하지 않다 - `PN-D47FBB8D`가 §3.4를
정정하며 코어당 정확히 하나인 진짜 `kernel::Task`(`gIdleTask
[coreIndex]`, `TaskClass::Idle`)를 신설했다. 다만 이 절이 다루는
`preemptive=true` 경로 자체는 그 Task를 스케줄러를 통해 "깨우는"
것이 아니다 - `kAsyncDrainIsr`이 ISR 컨텍스트에서 `drainOnce()`를
직접 동기 호출하는 저지연 경로로, `gIdleTask`가 그 순간 실제로
`gCurrentTask[coreIndex]`이든 아니든 상관없이 그대로 작동한다.
`gIdleTask`의 실질적 역할은 이 절이 아니라 §3.4가 다루는 것 -
`pickNext()`가 항상 무언가(최소한 `gIdleTask`)를 반환하게 만들어
`onTick()`의 freeze/디버그 검사가 매 틱 평가되도록 보장하는 것 -
와 `preemptive=false` 완료가 다음에 그 코어가 idle로 전환될 때
`gIdleTask`의 본문(`drainOnce()` 펌핑 루프)에서 자연히 처리되게
하는 것이다. 즉 두 메커니즘(저지연 IPI-직접호출 vs 코어당 idle
Task로의 자연스러운 폴백)은 서로 배타적이지 않고 병존한다.

### 3.6 타임아웃/취소 (계획 PN-D01B7D07)

HPET 기반 타임아웃을 옵션으로 가질 수 있다 - 마감까지 완료되지
않으면 그 작업을 취소 처리한다.

**[확정, 2026-09-16, QU-681F256C 답변]** "Timeout은 Cancelled의
원인 중 하나일 뿐이야. cancelSource가 trigger되어 취소된 작업들이
가져야 하는 상태인데. 내 생각에는 Cancel Source 쪽에 timeout을
유발하는 설계를 해야 할것 같네" - PN-D01B7D07 착수 중 확인을 구했던
세 항목 중 두 가지가 이걸로 정리된다:

- **새 `AsyncTaskState::Timeout`이나 네 번째 콜백은 만들지 않는다** -
  타임아웃도 기존 `Cancelled` 상태/`onCancel` 경로를 그대로 쓴다.
- **§8 취소 채널과의 관계**: 타임아웃은 §8.3이 나열한 취소 트리거
  지점(소유자 종료, `Waitable::cancel()`)에 나란히 놓이는 **세 번째
  트리거**다 - 마감 시각이 되면 프레임워크가 직접 `task->
  cancelSource.trigger()`를 호출한다(§8.2의 "멱등, 어느 코어에서
  불러도 안전"이 여기서도 그대로 성립). 별도 경로를 새로 만들지 않고
  기존 협조적 취소 메커니즘에 합류한다.
- **비교 기준(첫 번째 항목)은 이 답변이 직접 언급하지 않았다** - 다만
  이미 구현된 `DelayedExecutionQueue`(PN-C46DF296, completed)가
  정확히 "N틱 뒤 콜백"이라는 같은 문제를 `Timer::tickCount()`
  (HPET 100Hz 틱) 기준으로 이미 풀어 뒀으므로, 타임아웃 마감 감시도
  그 기존 인프라를 그대로 재사용하는 것이 자연스러운 결론으로
  보인다(raw HPET 카운터를 새로 노출할 필요 없음) - **채택 확정,
  아래 §3.7 참고**.

### 3.7 [구현 완료, 2026-09-16] 타임아웃의 use-after-free 문제 - lock-free 약한 참조로 해결

착수 중 실제 안전성 문제를 발견했다(QU-0CB8CAEE) - `DelayedExecutionQueue::
schedule(delayTicks, callback, arg)`로 "N틱 뒤 `task->cancelSource.
trigger()`"를 예약하려면 콜백이 원시 `AsyncTask*`를 들고 있어야
하는데, 그 AsyncTask가 정상 완료돼 타이머가 울리기 **전에** 이미
반납(`autoFree=true`인 흔한 기본 경로)되면 뒤늦게 울리는 타이머
콜백이 이미 해제된 메모리를 건드리는 use-after-free가 된다.

**설계자 답변**: "lock-free 기반으로 약한 참조를 구현해." -
`AsyncTask` 구조체에 필드를 여럿 추가하거나(§8이 이미 확정한 "새
필드 최소화" 취지와 충돌) 모든 반납 지점에 개별 취소 배선을 하는
대신, 독립적으로 힙 할당되는 작은 컨트롤 블록으로 해결한다:

```cpp
class AsyncTaskWeakRef {
public:
    void init(AsyncTask* target) {
        _target.store(target);
        _refCount.store(2);  // AsyncTask 쪽 몫 1 + 타이머 콜백 쪽 몫 1
    }
    AsyncTask* lock() const { return _target.load(); }
    void invalidate() { _target.store(nullptr); }
    void release() {
        if (_refCount.fetchSub(1) == 1) {
            GenericSlabAllocator::free(this, sizeof(AsyncTaskWeakRef));
        }
    }
private:
    AtomicPtr<AsyncTask> _target;
    AtomicU32 _refCount;
};
```

- **`AsyncTask::weakRef`**(`AsyncTaskWeakRef*`, 기본 `nullptr`) - 새
  필드는 포인터 하나뿐이다. `scheduleTimeout(delayTicks)`가 최초
  호출 시 컨트롤 블록을 만들어 채운다(v1 - 한 AsyncTask에 타임아웃은
  최대 한 번만, 두 번째 호출은 무시).
- **`DelayedExecutionQueue::cancel()`이 전혀 필요 없다** - 이 설계의
  핵심. 타이머는 항상 예정대로 발화하고, `lock()`으로 AsyncTask가
  아직 살아있는지 그 자리에서 확인한다 - 이미 끝났으면(`lock()==
  nullptr`) 그냥 조용히 자기 몫만 `release()`하고 끝난다(cancel 호출
  자체가 없으니 "취소를 깜빡했다"는 버그 클래스 자체가 성립하지
  않는다).
- **반납 지점 통합**: 기존에 4곳(`AsyncTaskGroup::pendingCount()`/
  `AsyncTaskAwaiter` 소멸/`drainOnce()`의 Cancelled·Completed·Failed
  분기)에 각자 따로 있던 "스택 반납 + 구조체 반납" 로직을
  `kReleaseAsyncTask(AsyncTask*)`(async_task.cpp, 파일 스코프) 하나로
  모았다 - `weakRef`가 있으면 `invalidate()`+`release()`를 이 한
  곳에서만 하면 되게 하기 위함.
- **왜 `lock()`이 안전한가**: `invalidate()`는 `kReleaseAsyncTask()`
  안에서 실제 메모리 반납보다 먼저 불린다 - `lock()`이 non-null을
  반환했다는 건 그 순간 아직 무효화 전이었다는 뜻이고, 타임아웃
  콜백/`DelayedExecutionQueue::pump()`/`drainOnce()`가 전부 같은
  코어의 리액터 idle 경로에서만(협조적 스케줄링, 인터럽트 컨텍스트
  제외) 실행되므로 진짜 동시 실행 경쟁이 없다.

**실측 검증(TEMP 스캐폴딩, kmain.cpp, 되돌림 완료)**: (1) 영원히
끝나지 않는 task에 5틱 타임아웃 - 타이머 발화 시 `lock()`이 여전히
유효한 포인터 반환 + `cancelSource`가 실제로 트리거됨(20틱 뒤 별도
체커로 확인) 확인. (2) `co_return`만 있어 즉시 완료되는 task에
100틱 타임아웃 - task가 타이머보다 훨씬 먼저 완료+반납되는데도
타이머 발화 시 `lock()`이 정확히 `nullptr`을 반환(use-after-free
없음) 확인. QEMU S1/S2/SMP4 전부 무회귀.

## 4. 스케줄러에 필요한 변경 (PL-2D3184BC에 반영 예정)

**[재설계, 2026-09-16, QU-4034561A 답변 - (B) 채택으로 방향 전환]**
원래(2026-09-14) 요구사항이던 `Scheduler::scheduleImmediate(Task*)`
- "리액터 Task를 큐 맨 앞에 강제로 꽂아 넣는" 프리미티브는 리액터가
더 이상 Task가 아니므로 **그 형태로는 불필요**해졌다(§3.4). 대신
아래 두 경로로 나뉜다:

1. **코어가 이미 idle(hlt) 상태**: 아무 조치도 필요 없다 - `sti;
   hlt`는 어떤 인터럽트로도 즉시 깨어나며, 깨어난 직후 `runLoop()`은

   있다(추가 구현 불필요).
2. **코어에서 다른 Task가 실행 중일 때 - [확정, 2026-09-16,

   채택하는데, syscall 타입과 인터럽트에서 밀어올린거냐 아니냐에
   따라서 둘 중 무엇을 사용할지 결정하게 만들자." - 두 경로를 모두
   구현하고, **호출 상황(어떤 syscall/경로인지, 인터럽트 컨텍스트
   기원인지)에 따라 어느 쪽을 쓸지 선택**한다:
   - **(A) 잠정 무동작(passive)** - 그냥 완료 큐에 넣기만 하고 강제
     개입 없음. 다음에 이 코어가 idle(§3.4 인라인 리액터 경로)에
     진입하면 자연히 처리된다. 지연에 민감하지 않은 일반 syscall
     제출 경로(대부분)의 기본값.
   - **(C) 전용 IPI로 즉시 개입** - 새 IPI 벡터(정확한 번호는 구현
     시점에 RM-28225668 "다음 미사용 벡터"에서 예약, SP-DE19BB1C
     §5-1의 0xE0~0xFD 내부 IPI 규칙 적용) + ISR에서 이 코어의 인라인
     async 드레인 로직을 즉시 실행하도록 개입. 지연시간이 중요한
     경로(예: `exclusivePreemptive` Channel Tier B 핸드셰이크,
     SP-00CA7175) 및/또는 인터럽트 컨텍스트에서 직접 밀어올려진
     완료(향후 실제 ISR 기반 드라이버가 생기면 그 경로)에 사용.
   - **선택 기준의 정확한 판별 지점**(어느 syscall 종류가 (C)를
     쓰는지, "인터럽트에서 밀어올림"을 코드에서 어떻게 식별하는지)은
     이 SP 문서가 결정하지 않고 PN-FEAAF154(구현 계획)에서 실제

별도 DC 없이 직접 지시된 사항이라 PL-2D3184BC 실행 계획에도 이
갱신된 내용을 반영한다.

## 5. Slab 할당자 의존성 (확정, SP-D7013B26)

`args`/`AsyncTask` 전용 스택 할당에 Slab 할당자(SP-D7013B26, 확정)
를 쓴다. **Slab 할당자는 고갈 시 절대 블로킹하지 않고 즉시
`nullptr`을 반환한다**(스케줄러 데드락 방지, QU-4F905C08) - 이
프레임워크(정확히는 각 `AsyncTaskHandler`)가 그 실패를
`onFailure()`로 받아 처리할 책임을 진다(3.1절). Slab 할당자 자신도
스케줄러의 선점 비활성화 프리미티브(PL-2D3184BC 8단계)를 전제로
하므로, 구현 순서는 "스케줄러 선점 금지 구간 → Slab 할당자 →
이 프레임워크" 순이 된다.

## 7. C++20 코루틴 활용 (확정, 2026-09-14, QU-1BE6B8D2 답변 반영)

설계자 지시 - "Freestanding 환경에서 C++20의 coroutine을 활용할
방안을 찾아서 설계 제안에 반영하라." 그리고 스택풀(3.2절, 이미
확정) vs 코루틴 중 하나를 고르자는 후속 질의(DC-23AEA8B4/
QU-1BE6B8D2)에 대한 답 - **"둘 다 구현"**으로 확정됐다. 스택풀
`AsyncTask`(3.2절)는 그대로 유지하고, 그 위에서 `AsyncTaskHandler::
onExec`을 코루틴으로도 작성할 수 있게 한다.

### 7.1 실측: freestanding 환경에서 코루틴이 실제로 동작한다

이 프로젝트의 베어메탈 타겟(`x86_64-unknown-none-elf`)에는 C++
표준 라이브러리(libstdc++/libc++)가 아예 없어 표준 `<coroutine>`
헤더를 그대로 include할 수 없다(실측 확인 - `fatal error: 'coroutine'
file not found`). 하지만 컴파일러의 코루틴 변환(`co_await`/
`co_yield`/`co_return`)이 실제로 필요로 하는 이름은 `std::
coroutine_handle`과 `std::coroutine_traits` 딱 두 개뿐이다(언어
자체가 이 정확한 정규화 이름으로 조회 - clang/gcc 공통, 바꿀 수
없음). `std::suspend_always`/`std::suspend_never`는 순수 편의
타입(컴파일러가 이름으로 찾지 않고 awaiter 프로토콜만 확인)이라
설계자 지시대로 **최소 호환 네이밍만 std에 남기고 나머지는 이
프로젝트 컨벤션으로 개명**했다(2026-09-14) - `kernel::SuspendAlways`
/`kernel::SuspendNever`(RM-23F4B687 PascalCase). 이 최소 헤더를
`minicore/libs/libkenv/coroutine.h`로 신설했다.

**실측(2026-09-14, clang 18.1.3, 이 프로젝트와 동일한 플래그
`-ffreestanding -fno-exceptions -fno-rtti -mcmodel=kernel
-mgeneral-regs-only -nostdlib`)**:
- 이 헤더 하나로 `co_await`/`co_return`을 쓰는 코드가 정상
  컴파일됨을 확인 - 오브젝트 파일에 실제 코루틴 ramp/resume/
  destroy/cleanup 함수와 커스텀 `promise_type::operator new/delete`
  심볼이 생성됨을 확인.
- 커널 부팅 중 실제 코루틴을 실행 - "before-suspend"를 찍고
  `co_await`로 suspend한 뒤 커널 메인 흐름으로 제어가 돌아와
  "suspended, about to resume"을 찍고, 그 다음 명시적으로
  `coroutine_handle::resume()`을 호출해야만 "after-resume"이
  찍히는 순서를 확인 - **진짜 suspend/resume이 예외/RTTI/표준
  라이브러리 없이 동작함을 실측으로 증명**했다.
- `kernel::SuspendAlways`/`SuspendNever` 개명 후에도 동일하게
  정상 동작함을 재확인(2026-09-14).
- 전역 `operator new`가 없는(`-nostdlib`) 이 커널에서는 **모든
  `promise_type`이 `operator new`/`operator delete`를 직접 제공해야
  한다** - 코루틴 프레임 할당을 원하는 곳(Slab, 정적 버퍼 등)으로
  자유롭게 연결할 수 있다는 뜻이기도 하다.
- 검증 후 임시 테스트 코드는 전부 제거 - 영구 코드는
  `libkenv/coroutine.h` 헤더만 남겼다.

### 7.2 Slab 할당자와의 결합 + 할당 실패 시 재시도(확정)

`promise_type::operator new(size_t)`를 `GenericSlabAllocator::
alloc(size)`(SP-D7013B26)로 연결하면, 코루틴 프레임도 이 프로젝트가
이미 확정한 슬랩 캐시 경로를 그대로 탄다. Slab 할당자는 고갈 시
`nullptr`을 반환하는데(비블로킹 확정, QU-4F905C08), 코루틴의
`operator new`가 `nullptr`을 반환하면 그 자체로는 정의되지 않은
동작이다 - **표준 C++20 할당 실패 프로토콜**
(`promise_type::get_return_object_on_allocation_failure()`,
`operator new`는 `noexcept`로 선언)을 구현하면 예외 없이 실패를
표현할 수 있다.

**실측(2026-09-14)**: `operator new`가 의도적으로 `nullptr`을
반환하도록 만든 뒤, 코루틴 몸체가 **전혀 실행되지 않고**
`get_return_object_on_allocation_failure()`의 반환값만 호출부에
돌아옴을 확인 - 반대로 할당이 성공하면 몸체가 정상 실행됨도 같이
확인(두 경우 모두 커널 부팅 중 실측).

**설계자 지시(2026-09-14) - 할당 실패 시 "yield하며 대기"**: 코루틴
프레임 할당이 실패했을 때 그 자리에서 바로 실패 처리하지 않고,
이 코루틴을 시작시키려던 **스택풀 `AsyncTask`가 `yield()`를 호출해
리액터에 제어를 돌려주고, 나중에 다시 스케줄링됐을 때 코루틴
생성을 재시도**하도록 만든다 - 즉 두 메커니즘(스택풀의 yield/재개,
코루틴의 stackless suspend/resume)이 "할당 실패 시 재시도"라는
한 가지 상황에서 자연스럽게 맞물린다. 구현 계획(PL-1E247831,
계획 PN-C62F7908)에 재시도 루프의 정확한 형태를 반영한다.

**[확정, 2026-09-16, QU-5E58E361 답변] 실패 감지 메커니즘**: 설계자
답변 - "get_return_object_on_allocation_failure로 해." `promise_type::
get_return_object_on_allocation_failure()`가 "실패를 나타내는 빈
`coroutine_handle`"을 담은 `AsyncExecCoro`를 반환하고, `onExec()`을
호출한 `kAsyncTaskEntryWrapper`(async_task.cpp)가 그 반환값의 핸들이
비어 있는지 확인해 실패를 감지한다. **다만 이 실패를 감지한 뒤의
동작은 새로 정하는 게 아니라 바로 위 문단의 기존 확정("yield하며
대기·재시도")을 그대로 따른다** - 이 질의에 딸려온 후보안(핸들이
비어 있으면 `AsyncTaskState::Failed`로 처리)은 답변으로 명시적으로
재확인되지 않았고, 이미 확정된 "재시도" 결정과 충돌하므로 채택하지
않는다(핸들 비어 있음 = 재시도 트리거이지 실패 상태가 아니다). 이
해석이 설계자 의도와 다르면 정정 부탁드린다.

### 7.3 `AsyncTaskHandler::onExec`를 코루틴으로 구현하는 방식(확정, 계획 PN-C62F7908)

3.2절의 `AsyncTask`(스택풀, `kContextSwitch` 재사용)는 그대로
유지된다 - 코루틴은 그걸 대체하는 게 아니라, **`AsyncTaskHandler::
onExec`의 구현 방식 중 하나**로 추가된다.

- `onExec`을 코루틴 함수로 선언(예: `AsyncExecCoro onExec(AsyncTask*
  task, void* args)`, `AsyncExecCoro`는 이 프레임워크가 정의하는
  코루틴 반환 타입)하면, 본문에서 `co_await`로 다른 `AsyncTask`의
  완료를 자연스럽게 기다리는 순차적 코드를 쓸 수 있다 -
  `AsyncTaskAwaiter`(3.3절)를 그대로 이 코루틴의 awaitable로
  재사용한다.
- ~~이 코루틴은 `AsyncTask`를 실행 중인 리액터 Task의 스택 위에서
  돈다~~ **[정정, 2026-09-16 - 아래 QU-892A075E 답변 반영 문단 참고]**
  이 전제는 폐기됐다(공유되는 "리액터 스택" 자체가 더 이상 없음) -
  각 `AsyncTask`가 자기 전용 스택으로 진입하는 현재 구조는 아래
  문단을 본다. 리액터가 여전히 "우선순위 무시 즉시 스케줄링" 가능한
  전체 `kernel::Task`라는 요구사항은 변하지 않는다(4절)는 부분만
  유효하다.
- 코루틴 프레임 크기는 `AsyncTask`마다 다르다(지역 변수/중첩
  `co_await` 깊이에 따라 컴파일러가 결정) - Slab 버킷을 초과하면
  `PageFrameAllocator` 직행 경로(SP-D7013B26 2.3절)로 자연스럽게
  빠진다.
- **[정정, 2026-09-16, QU-892A075E 답변 - reactorTaskEntry() 폐기에
  따른 재구성]** 아래는 2026-09-15 작성 당시 전제("리액터 Task의
  공유 스택 위에서 돈다", "reactorTaskEntry()가 onExec()를 동기
  호출") 그대로였으나, §3.4가 QU-4034561A 답변(선택지 B, 2026-09-16)
  으로 `reactorTaskEntry()`라는 별도 Task 진입점 자체를 폐기했다 -
  실제 코드(async_task.cpp)에는 각 AsyncTask가 자기 전용 스택으로
  `kContextSwitch` 진입하는 `kAsyncTaskEntryWrapper`+`AsyncReactor::
  drainOnce()` 구조뿐이고, 공유되는 "리액터 스택" 자체가 없다.
  재개 드라이버 책임은 **`AsyncReactor::drainOnce()`**로 옮긴다
  (설계자 확인: "재개 드라이버 resume은 drainOnce에서") - `drainOnce()`
  가 뽑은 `AsyncTask`의 `coroHandle`이 이미 설정돼 있으면(=이전에
  suspend된 채로 남겨 둔 상태) `kContextSwitch`로 스택풀 재개를
  시도하는 대신 **`coroHandle.resume()`을 직접 호출**한다 -
  `coroHandle`이 비어 있으면(첫 실행이거나 스택풀 모드) 기존
  `kContextSwitch` 경로 그대로.
- **재개(resume) 드라이버 - 누가 언제 `coroutine_handle::resume()`을
  부르는가(위 정정 반영)**: 코루틴이 `co_await`로 suspend하면
  제어는 그 코루틴을 호출한 지점(`kAsyncTaskEntryWrapper`가
  `handler->onExec(task, task->args)`를 부른 지점)으로 돌아온다 -
  `AsyncExecCoro`(코루틴 반환 타입)가 그 호출의 반환값으로 직접
  넘어온다. `AsyncTask`(§3.2)의 `std::coroutine_handle<> coroHandle`
  필드에 이 반환값이 "아직 완료 안 됨(suspend 상태)"이면 그
  `coroutine_handle`을 저장해 두고 이 턴은 그대로 끝낸다(스택풀의
  `savedRsp` 저장과 정확히 같은 역할 - "다음에 이어갈 지점을 남겨
  둔다"). 다음에 이 `AsyncTask`가 실행 큐에서 다시 뽑히면,
  `drainOnce()`는 `onExec()`를 처음부터 다시 부르는 대신 **저장해
  둔 `coroHandle.resume()`을 부른다** - 스택풀 쪽이 `kContextSwitch`
  로 저장된 `savedRsp`에서 재개하는 것과 정확히 대응되는 코루틴 쪽
  경로다. `AsyncMutexLockAwaiter`(SP-0666DB3C §10.4-2)의
  `await_suspend()`가 `AsyncReactor::submitCompletion(AsyncTask::
  current())`로 재큐잉만 하고 handle 저장/실제 재개는 이쪽에 맡긴다는
  전제가 바로 이 메커니즘과 맞물린다 - 두 문서 사이에 충돌 없음을
  확인했다.
- **[정정, 2026-09-16, QU-892A075E 답변]** `AsyncTaskHandler::onExec`
  의 고정된 `virtual void onExec(AsyncTask*, void*)` 시그니처가
  코루틴 반환 타입(`AsyncExecCoro`)과 충돌한다는 우려에 대한 설계자
  답변: **"C++ 코루틴은 가상함수를 지원하는 걸로 알고 있는데,
  가상함수 정의를 코루틴으로 바꿔."** - 별도의 코루틴 전용 가상
  메서드를 새로 두지 않는다. `AsyncTaskHandler::onExec` 자신의
  시그니처를 `virtual AsyncExecCoro onExec(AsyncTask*, void*)`로
  바꾸고, 기존의 (코루틴을 안 쓰는) 단순 핸들러들도 전부 이 새
  시그니처로 마이그레이션한다 - `co_await`를 전혀 쓰지 않는 본문도
  `AsyncExecCoro` 반환 타입의 코루틴으로 컴파일되며(C++20 코루틴은
  본문에 `co_*` 키워드가 있는지 여부로만 컴파일러가 코루틴 변환을
  결정, 반환 타입 자체는 항상 지정한 대로), 그런 본문은 실행되자마자
  곧바로 완료 상태로 끝난다 - "onExec을 코루틴 대신 평범한 함수로
  구현하는 것도 가능"이라는 원안의 취지는 "시그니처까지 다르게"가
  아니라 "본문에서 co_await를 안 쓰면 그만"으로 정정된다. 기존
  핸들러 전체(channel.cpp/address_space.cpp/scheduler.cpp 등)의
  마이그레이션 범위는 PN-C62F7908 착수 시 확정한다.

## 8. 협조적 취소(Cooperative Cancellation) - AsyncToken/AsyncTokenSource (설계자 지시, 2026-09-14)

### 8.1 배경 - 왜 `onCancel` 하나로는 부족한가

3.1절의 `onCancel`은 **소유자가 죽었을 때 프레임워크가 대신 불러
주는** 훅이지만, 정확히 "AsyncTask가 아직 실행을 시작하지 않았을
때"에만 깔끔하게 적용된다 - 이미 `onExec`이 시작돼 `yield()`로
suspend와 resume을 반복하고 있거나(3.2절) 코루틴이 `co_await`
중간에 있으면(7절), 프레임워크가 그 실행 흐름 한가운데 안전하게
끼어들어 대신 정리를 해 줄 방법이 없다(freestanding 커널에는
임의 지점에서 스택을 강제로 되감는 장치가 없다) - SP-0666DB3C
§9.6-2가 "각 AsyncTaskHandler 구현 시점의 열린 과제"로 남겨 뒀던
바로 그 문제다. 설계자 지시("AsyncTask에 AsyncToken,
AsyncTokenSource를 도입하고, 이게 트리거되면 취소된 걸로 간주하는
메커니즘을 설계해봐")에 따라, **강제 중단이 아니라 협조적(cooperative)
신호**로 이 문제를 푼다 - 실행 중인 코드 스스로 "지금 취소됐는지"를
확인하고 자기 판단으로 조기 종료하게 한다.

### 8.2 설계 - `AsyncTokenSource`/`AsyncToken`

```cpp
namespace kernel {

// AsyncTask 하나당 정확히 하나씩 값으로 소유되는 취소 상태 -
// 힙 할당/참조 카운트 없이 AsyncTask 구조체에 직접 내장한다(3.2절
// cancelSource 필드). 한 번 트리거되면 되돌릴 수 없다(단방향).
class AsyncTokenSource {
public:
    // 취소를 요청한다 - 멱등(CAS 기반, 이미 트리거된 상태에서
    // 다시 불러도 안전하며 아무 일도 하지 않는다). 어느 코어에서
    // 불러도 안전(AtomicU32 사용, 별도 Spinlock 불필요).
    void trigger();

    bool isTriggered() const;

    // 이 소스를 가리키는 경량 읽기 전용 핸들을 발급한다 - 값
    // 복사 가능, 소유권 없음(AsyncTokenSource보다 오래 살아있으면
    // 안 됨 - 항상 그 소스를 담은 AsyncTask보다 짧게 유지).
    AsyncToken token() const;

private:
    AtomicU32 _triggered { 0 };
};

// onExec/코루틴 본문이 폴링하는 뷰 - AsyncTokenSource*를 감싼
// 얇은 값 타입.
class AsyncToken {
public:
    explicit AsyncToken(const AsyncTokenSource* source) : _source(source) {}

    bool isCancelled() const {
        return _source != nullptr && _source->isTriggered();
    }

private:
    const AsyncTokenSource* _source;
};

}  // namespace kernel
```

`AsyncTask`(§3.2)에 이미 추가한 `AsyncTokenSource cancelSource`
필드가 이 채널의 실체다 - `task->cancelSource.token()`으로 얻은
`AsyncToken`을 `onExec`/코루틴 몸체가 원하는 지점마다 확인한다.

### 8.3 트리거 지점 - 기존 취소 경로들이 전부 이걸 통해 나간다

1. **소유자 조기 종료(기존 3.1절 `onCancel` 경로)**: 프레임워크가
   `onCancel`을 부르기 **전에** 먼저 `task->cancelSource.trigger()`
   를 호출한다. **[정정, 2026-09-16, PN-40E976F2 실제 구현 반영]**
   아래 두 갈래 대신, 실제 구현은 `UserThread` 종료 처리
   (scheduler.cpp의 `SelfTerminateHandler::onExec`)가
   `userThread->pendingSyscalls`(§9.4가 이미 "사망 전파 목록"으로
   지목한 바로 그 `ChunkedList`, 새 자료구조 아님)를 순회하며 아직
   `wait()`로 소비되지 않은 `AsyncTask`마다 `autoFree = true` +
   `state = AsyncTaskState::Cancelled`로 즉시 전이시키는 **단일
   경로**로 통일했다 - `onCancel` 자체는 여기서 직접 부르지 않고,
   그 `AsyncTask`가 (이미 `Ready`로 큐에 있었다면 자연히, `Suspended`
   였다면 `AsyncReactor::submitCompletion()`을 직접 호출해) 리액터
   실행 큐로 돌아왔을 때 `reactorTaskEntry()`가 `state ==
   Cancelled`를 보고 `onExec`을 건너뛴 채 그 자리에서 `onCancel`만
   호출한다(§3.2 `AsyncTaskState::Cancelled` 참고) - 이하 원래
   서술(아직 한 번도 실행되지 않았다면/이미 실행이 시작됐다면의
   두 갈래)은 **정책 의도는 여전히 유효하지만, 실제로는
   `reactorTaskEntry()`의 단일 검사 지점으로 구현됐다**는 점만
   유의:
   `AsyncTask`가 아직 한 번도 실행되지 않았다면(즉
   `AsyncTaskState::Ready`) 그대로 `onCancel`만 불러 끝낸다(기존
   동작 그대로) - 이미 실행이 시작돼 suspend/resume 중이라면
   `onCancel`은 **부르지 않고**, 다음에 이 `AsyncTask`가
   `yield()`/`co_await`에서 재개될 때 `onExec`/코루틴 몸체가
   스스로 `isCancelled()`를 확인해 정리하고 조기 반환하는 것을
   기대한다(§8.4) - "onExec/onFailure/onCancel 중 정확히 하나만
   불린다"는 3.1절의 불변조건은 그대로 유지된다(트리거만으로는
   네 번째 콜백이 생기지 않는다).
2. **SP-0666DB3C §9의 `Waitable::cancel()` 경로**: §9.4가 "AsyncTask
   자체는 즉시 멈추지 않는다"며 best-effort로 남겨 뒀던 부분을
   구체화한다 - `pendingSyscalls` 기반 대기가 Kill 신호로 취소될
   때, 그 대기와 연결된 AsyncTask가 있다면 `cancelSource.trigger()`
   도 함께 호출한다. Task 자신은 즉시 Ready로 복귀하지만(§9.4 그대로),
   그 뒤에서 계속 돌고 있는 AsyncTask도 이제 다음 확인 지점에서
   스스로 멈출 기회를 얻는다 - SP-0666DB3C §9.6-2는 이 절로 해소된다.

### 8.4 `onExec`/코루틴 쪽 사용 관례 (권장, 강제 아님)

```cpp
// 스택풀 onExec 예시
void MyHandler::onExec(AsyncTask* task, void* args) {
    AsyncToken token = task->cancelSource.token();
    for (...) {
        if (token.isCancelled()) {
            // 자체적으로 정리(args 해제 등, 3.1절 원칙 그대로)하고
            // 조기 반환 - 별도 "취소됨" 콜백은 없다(위 §8.3-1).
            cleanupEarly(args);
            return;
        }
        doSomeWork(...);
        AsyncTask::yield();
    }
}
```

코루틴 몸체는 매 `co_await` 지점 앞뒤로 같은 방식의 확인을 넣을
수 있다(예: 공용 `co_await CheckCancelled(token)` awaitable을
프레임워크가 제공하는 것을 구현 계획에서 검토, §8.6-2).

### 8.5 의도적으로 "강제"가 아닌 이유

freestanding 환경에는 임의의 실행 지점에서 스택을 안전하게 되감는
장치(C++ 예외/longjmp류 안전장치)가 없고, 이 프로젝트는 애초에
C++ 예외 자체를 쓰지 않는다(RM-23F4B687) - 그래서 "트리거되면
즉시 멈춘다"가 아니라 **"트리거되면, 이후 스스로 확인하는 코드가
그 사실을 알 수 있다"**는 협조적 모델을 택했다. 이는 §9.6-2가
이미 예견했던 제약과 정확히 같은 이유다.

### 8.6 아직 열려 있는 하위 과제

1. **`onFailure` 이후 재시도 시 취소 확인**: `onFailure()`가 재시도
   목적으로 다시 `submit()`할 때, 이미 트리거된 `AsyncTokenSource`를
   재사용할지 새로 만들지는 구현 시점에 확정(원칙상 재사용 -
   한 번 취소 요청된 논리적 작업의 재시도는 여전히 취소된 것으로
   보는 것이 자연스럽다).
2. **코루틴 전용 헬퍼**: §8.4에서 언급한 `co_await CheckCancelled
   (token)` 스타일의 공용 awaitable을 프레임워크가 제공할지, 각
   핸들러가 직접 `isCancelled()`를 호출할지는 PL-1E247831 구현
   계획에서 확정.
3. **`yield()` 자동 확인 여부**: §3.2에서 명시했듯 v1은 `yield()`
   자체가 취소를 판단하지 않는다 - 매 호출마다 강제로 확인하게
   만들면 취소를 신경 쓰지 않는 단순 작업에도 분기가 추가되므로,
   지금은 명시적 호출부 책임으로 남긴다(실측 후 재검토 대상).

## 9. AsyncTask/AsyncTaskCompletion 분리 - 동기/비동기 대기 통합 (설계자 지시, 2026-09-14)

### 9.1 배경

§3.3의 `AsyncTaskGroup`/`AsyncTaskWaitGroup`/`AsyncTaskAwaiter`가
이미 "여러 개 묶기"/"동기 대기"/"비동기 대기"를 각각 커버하고
있었지만, 설계자가 "AsyncTask와 AsyncTaskCompletion 객체로 나눠서
AsyncTaskCompletion이 완료/취소 여부를 전파하도록 만들고,
AsyncTaskCompletion이 비동기 대기, 동기식 대기 두 가지를 구현하는
구조를 고안"하라고 지시함에 따라, "이 작업 하나가 끝났는가/어떻게
끝났는가/누가 어떻게 기다리는가"를 하나의 응집된 객체
`AsyncTaskCompletion`으로 재구성한다. `AsyncTask` 자신은 순수하게
"실행 단위"(스택/컨텍스트/args/§8의 취소 신호)만 남는다.

### 9.2 설계 - `AsyncTaskCompletionStatus`/`AsyncTaskCompletion`

```cpp
namespace kernel {

enum class AsyncTaskCompletionStatus : uint32_t {
    Pending,
    Completed,   // onExec이 정상 반환
    Failed,      // onFailure 호출됨
    Cancelled,   // onCancel 호출됐거나, onExec이 §8의 AsyncToken을
                 // 보고 스스로 조기 종료
};

// AsyncTask 하나(제출 1회)당 정확히 하나 발급 - AsyncTask 자체와는
// 분리된 객체(값으로 어디에 두든 상관없음 - 제출자가 스택/Slab 등
// 원하는 곳에 소유할 수 있다, §9.5-1). "완료/취소 여부의 전파"와
// "그 완료를 기다리는 두 가지 방식"을 모두 이 객체가 책임진다.
class AsyncTaskCompletion : public Waitable {
public:
    void init(AsyncTask* task);

    AsyncTaskCompletionStatus status() const;

    // 동기 대기 - 호출자가 완전한 kernel::Task(스택풀 AsyncTask가
    // 아닌 일반 Task) 컨텍스트일 때 사용. 완료될 때까지 그 Task를
    // WaitQueue에 파킹한다(Scheduler::parkCurrent 재사용, SP-0666DB3C
    // §1과 동일한 패턴) - 완료되면 정확히 한 번 깨어나 최종 상태를
    // 반환한다.
    AsyncTaskCompletionStatus waitSync();

    // 비동기 대기 - 호출자가 다른 AsyncTask(스택풀 또는 코루틴)
    // 컨텍스트 안에 있을 때 사용. §3.3의 AsyncTaskAwaiter를 그대로
    // 감싸 yield() 반복으로 구현하며, 코루틴에서는 awaiter
    // 프로토콜(await_ready/await_suspend/await_resume)을 구현해
    // `co_await completion`으로도 쓸 수 있게 한다(§7과 연동).
    AsyncTaskAwaiter waitAsync();

    // Waitable 구현(SP-0666DB3C §9) - waitSync()로 파킹된 Task를
    // 강제로 깨울 수 있게 한다(예: 기다리던 그 Task 자신이 Kill로
    // 취소되는 경우) - completion 자신의 상태는 바뀌지 않는다(그
    // 작업 자체가 취소된 게 아니라 "기다리던 쪽"이 취소된 것이므로).
    bool cancel(Task* task, WaitCancelReason reason) override;

private:
    AsyncTaskCompletionStatus _status = AsyncTaskCompletionStatus::Pending;
    Spinlock _guard;
    WaitQueue _syncWaiters;        // waitSync() 파킹 대상
    AsyncTaskGroup _asyncWaiters;  // waitAsync()/AsyncTaskAwaiter 대상(§3.3 재사용)
};

}  // namespace kernel
```

### 9.3 완료/취소 전파 - 누가 상태를 확정하는가

프레임워크(리액터/디스패치 코드)가 `AsyncTaskHandler`의 세 경로 중
정확히 하나가 끝난 직후 `AsyncTaskCompletion`의 상태를 확정하고
대기자를 전부 깨운다:

- `onExec`이 정상 반환 → `Completed`.
- `onFailure` 호출 → `Failed`.
- `onCancel` 호출(§8.3-1, 아직 실행 시작 전 강제 취소) → `Cancelled`.
- `onExec`이 §8의 `AsyncToken::isCancelled()`를 보고 스스로 정리
  후 조기 반환한 경우 — 프레임워크 입장에서는 "정상 반환"과
  구별이 안 되므로, **핸들러가 조기 종료 직전
  `task->completion->markCancelled()`를 직접 호출**해야 한다
  (3.1절의 "args 정리도 처리기 책임" 원칙과 같은 맥락 - 상태
  확정도 이제 그 목록에 추가된다).

상태 확정 시 `_syncWaiters`(WaitQueue)는 **전원 기상**시킨다(SP-0666DB3C
§2.1의 재경쟁과 달리, 여기서는 "하나가 자원을 갖는" 경쟁이 아니라
"모두가 같은 결과를 읽는" 브로드캐스트이므로 `wakeOne()` 반복이
아니라 전원을 깨우는 것이 맞다 - `WaitQueue`에 이 브로드캐스트
동작을 위한 API를 추가로 제안, §9.5-4). `_asyncWaiters`
(`AsyncTaskGroup`)에도 완료를 통지해, 등록된 `AsyncTaskAwaiter`들의
`yield()` 루프가 다음 확인에서 빠져나가게 한다.

### 9.4 §3.3과의 관계

`AsyncTaskGroup`/`AsyncTaskWaitGroup`/`AsyncTaskAwaiter`(§3.3)는
폐기되지 않는다 - `AsyncTaskCompletion`은 그 위에 얹히는 **응집된
파사드**다: `waitSync()`는 사실상 그 completion 하나만 담은
`AsyncTaskWaitGroup`과 동등하고, `waitAsync()`는
`AsyncTaskAwaiter(task)`를 그대로 반환한다. 여러 작업을 한꺼번에
기다려야 하면(§3.3의 원래 유스케이스, 예: "이 4개 디스크 블록
읽기") 여전히 `AsyncTaskGroup`/`AsyncTaskWaitGroup`을 직접 쓴다 -
`AsyncTaskCompletion`은 **작업 하나의 결과를 상태와 함께 관찰**
하는 경우를 위한 것이다.

### 9.5 아직 열려 있는 하위 과제

1. **`AsyncTaskCompletion`의 소유/수명 위치**: `AsyncTask` 구조체
   안에 값으로 내장할지(§3.2의 `cancelSource`와 같은 패턴), 제출자가
   별도로 Slab 할당해 넘길지는 구현 시점에 확정 - 내장 쪽이 §8의
   `cancelSource`와 일관성은 있지만 `AsyncTask` 크기가 커진다.
2. **`markCancelled()` 실수 방지**: §9.3에서 핸들러가 조기 종료 시
   명시적으로 호출해야 하는 이 규칙을 지키지 않으면 completion이
   `Pending`으로 영원히 남거나 `Completed`로 잘못 확정된다 - 헬퍼
   매크로/RAII 가드로 강제할지는 PL-1E247831 구현 계획에서 검토.
3. **코루틴 awaiter 프로토콜 세부**: `co_await completion` 지원을
   위한 `await_ready`/`await_suspend`/`await_resume` 정확한
   시그니처는 §7의 `libkenv/coroutine.h`와 함께 구현 시점에 확정.
4. **[해결됨, 2026-09-15]** ~~`WaitQueue` 전원 기상 API~~ -
   SP-0666DB3C §1의 `WaitQueue`에 `wakeAll()`을 추가했다(`wakeOne()`을
   큐가 빌 때까지 반복하는 것과 동치, 호출부 의도를 명시적으로
   드러내는 이름) - `AsyncTaskCompletion`은 이 API를 그대로 호출하면
   된다. 더 이상 이 문서의 미결 사항이 아니다.
