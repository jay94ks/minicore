# 커널 전용 비동기 프레임워크(Task 기반) — 설계 제안

**[확정, 2026-09-14, QU-F86426D5 답변 반영]** 원래 제안(콜백 체인 +
스택 없는 `AsyncOp`)은 설계자 검토 결과 **스택풀 방식(`AsyncTask`,
자체 yield 지원) + 코어별 전용 리액터 Task**로 확정됐다 - 아래
본문을 확정된 최종 설계로 갱신했다. 원래 제안에서 남는 부분(문제
정의/목표/인터럽트 통합 규칙)은 그대로 두고, 핵심 개념(3절)과 API를
전부 최종 결정대로 다시 썼다. 승인된 대로 구현 계획은 PL로 분리한다
(작성 예정).

**[개정, 2026-09-14, DC-D868D9EC/QU-EF643652 답변("onCancel 추가
승인한다") 반영]** §3.1의 `AsyncTaskHandler`에 `onCancel`을 추가했다
- Syscall 서브시스템(SP-04EE2A18)이 "대상 스레드/프로세스가 완료
전에 종료되면 그 비동기 작업을 취소해야 한다"는 요구사항 때문에
제안했고 승인됐다. 아래 3.1절 코드가 그 최종 형태다.

## 1. 문제 정의

`kernel::Task`(PL-2D3184BC)는 스케줄러의 최소 단위지만, **하나당
고정 커널 스택(기본 8KiB)과 전체 레지스터 컨텍스트를 통째로 가진
"무거운" 실행 흐름**이다. 반면 커널 내부에서 반복적으로 필요해질
패턴은 다음과 같다 — "장치에 요청을 하나 내고, 완료 인터럽트가 올
때까지 기다렸다가, 몇 줄짜리 후속 처리를 한다"(디스크 읽기, IPC
왕복, 타임아웃 대기 등). 대기 중인 요청마다 Task를 하나씩 만들면:

- 대기 중인 요청 수만큼 8KiB+ 스택이 낭비된다(수백~수천 개의 동시
  요청을 감당하기엔 비효율적).
- 완료 인터럽트가 왔다고 해서 그 안에서 후속 처리를 직접 돌리면
  안 된다 — 이번 세션에 실측으로 확인한 교훈(ISR 안에서 비재진입
  락을 쥔 함수를 부르면 데드락)이 일반화된 규칙이다: **ISR은 절대
  무거운/블로킹 가능한 로직을 직접 실행해서는 안 된다.**

## 2. 목표 / 비목표

**목표**
1. 대기 중인 비동기 작업 하나마다 전체 Task(전체 스택)를 만들지
   않고도 "요청 → 완료 시 후속 처리"를 표현할 수 있게 한다 -
   `AsyncTask`는 Task보다 훨씬 가벼운 전용 스택을 쓴다(3.2절).
2. 인터럽트 컨텍스트에서 하는 일을 "완료 표시 + 큐에 넣기"까지로
   최소화한다 - 실제 후속 로직은 반드시 리액터 Task 컨텍스트에서
   실행되게 한다.
3. 각 코어에 전용 리액터 Task를 둬 "진짜 동시성"을 갖는 비동기
   처리를 구현한다(설계자 확정, 2026-09-14) - 스케줄러(PL-2D3184BC)
   위에 얹되, 긴급한 인터럽트가 왔을 때 그 코어의 리액터 Task를
   우선순위 무시하고 즉시 스케줄링할 수 있어야 한다(4절 - 스케줄러
   자체에 새 프리미티브 필요).
4. 이미 확정된 스케줄러 설계(DC-8EA1E7F6/DC-B80D8D31)의 "블로킹/
   웨이크업은 외부 비공개, 기능별 특수 API로 노출" 원칙(QU-BA001D73
   6번)을 그대로 따른다 - `AsyncTaskWaitGroup`이 그 첫 실제 사례다.
5. 기능별로 콜백을 **한 번만 등록**해 두고, 실제 작업 발생 시엔
   Slab로 할당한 `args`만 콜백에 넘겨 실행한다(설계자 확정,
   2026-09-14) - 매번 콜백을 넣고 빼거나 비동기 작업 처리기가
   파편화되는 것을 피한다.
6. C++ 예외 없이, freestanding 환경에서 동작한다.

**비목표(v1 범위 밖)**
- 유저랜드용 비동기 I/O 모델이 아니다 - devmgr/fs/net은 전부
  유저랜드 서비스(SP §2-A)라 이 프레임워크는 **커널 자신의 내부
  구현**에만 쓰인다.
- 코어 간 완료 이관(코어 A에서 완료된 AsyncTask를 코어 B의 리액터가
  대신 처리) - v1은 인터럽트가 도착한 코어의 리액터가 그 코어의
  실행 큐만 처리한다(로드밸런싱은 Task 단위에서만).

## 3. 핵심 개념 (확정, 2026-09-14; 2026-09-14 메시지/QU-4F905C08로 갱신)

### 3.1 처리기 등록 - 기능별 1회 등록, 실행/실패/취소 전부 구현 책임

**갱신(2026-09-14, 설계자 메시지 + QU-4F905C08 답변)**: 단순 함수
포인터 콜백 대신, **실행(exec)과 실패(failure) 두 경로를 모두
구현해야 하는 처리기 인터페이스**로 바뀌었다 - Slab 할당자
(SP-D7013B26)가 메모리 고갈 시 블로킹 없이 즉시 실패를 반환하도록
확정됐기 때문에(스케줄러 데드락 방지), 그 실패를 받아 처리하는
쪽이 반드시 있어야 한다. **작업 주체별 내부 데이터(`args`)의
생성과 반납(해제) 책임도 전부 이 처리기가 진다** - 프레임워크
자신은 `args`를 대신 만들거나 해제하지 않는다(설계자 지시,
2026-09-14).

**추가 개정(2026-09-14, DC-D868D9EC/QU-EF643652 승인)**: `onCancel`
을 세 번째 순수 가상 함수로 추가한다 - 이 `AsyncTask`의 소유
스레드/프로세스(Syscall 서브시스템, SP-04EE2A18의 개념으로는
`UserThread`)가 완료 전에 종료돼 강제로 취소될 때 호출된다. `args`
해제 등 정리는 여전히 이 처리기 책임(위 원칙 그대로) - 서비스에
위임 중이었다면 그 채널 요청(SP-1FBC0EEB의 `BridgePipe` 등)도 여기서
함께 정리해야 한다.

```cpp
namespace kernel {

// 작업 주체(기능)별로 구현 - 실행/실패/취소 셋 다 구현 책임을 진다.
// args(작업 주체별 내부 데이터)를 실행 전에 만드는 것도, 실행이
// 끝나거나(onExec) 실패하거나(onFailure) 소유자가 먼저 죽어
// 취소되거나(onCancel) 어느 쪽으로 끝나든 그 해제도 전부 이
// 처리기의 몫이다 - 프레임워크는 관여하지 않는다.
class AsyncTaskHandler {
public:
    virtual ~AsyncTaskHandler() = default;
    virtual void onExec(AsyncTask* task, void* args) = 0;
    // Slab 할당 실패(nullptr) 등 프레임워크 내부 사유를 포함해
    // 실행 자체가 불가능했을 때 호출된다 - 재시도 여부도 이 처리기가
    // 결정한다(예: 여기서 다시 submit).
    virtual void onFailure(AsyncTask* task) = 0;
    // 이 작업의 소유 스레드/프로세스가 완료 전에 종료돼 강제로
    // 취소될 때 호출된다(onExec/onFailure 둘 다와 배타적 - 셋 중
    // 정확히 하나만 불린다). 이 AsyncTask를 소비하는 첫 사례는
    // Syscall 서브시스템(SP-04EE2A18 "종료 시 취소 처리")이다.
    virtual void onCancel(AsyncTask* task, void* args) = 0;
};

// 기능별로 부팅/초기화 시 한 번만 등록한다 - 요청이 생길 때마다
// 등록/해제하지 않는다(설계자 지시, 2026-09-14).
class AsyncCallbackRegistry {
public:
    static AsyncTaskSubjectCode registerHandler(AsyncTaskHandler* handler);
    static AsyncTaskHandler* resolve(AsyncTaskSubjectCode subjectCode);
};

}  // namespace kernel
```

실제 요청이 생기면 처리기 자신이 `GenericSlabAllocator::
alloc(sizeof(Args))`(SP-D7013B26 참고)로 `args`를 만들고(실패하면
그 처리기가 알아서 처리 - 즉시 포기하거나 나중에 재시도), 아래
`AsyncTask`에 담아 리액터에 제출한다.

### 3.2 `AsyncTask` - 자체 스택을 갖는 스케줄링 가능 단위(구 `AsyncOp`)

`kernel::Task`와 같은 소프트웨어 컨텍스트 전환(`kContextSwitch`)을
재사용하되, **Task보다 훨씬 작은 전용 스택**을 쓴다(정확한 크기는
구현 계획에서 실측 확정 - Slab 할당자의 한 버킷을 스택으로 쓰는
방안 포함해 검토). 콜백 실행 중 스스로 `yield()`를 불러 리액터에게
제어를 돌려주고 나중에 재개될 수 있다(설계자 지시, 2026-09-14 -
"비동기 작업 자체에도 별도의 yield 기능이 있어서 이걸 호출하면
현재 진행중이던 비동기 작업을 suspend하고, 다음 비동기 작업을
처리할 수 있어야 한다").

**분류/비교 식별자 갱신(2026-09-14, 설계자 메시지)**: `callbackId`
하나였던 것을 **두 코드로 분리**한다 - `subjectCode`(uint32_t, 어느
`AsyncTaskHandler`에 속하는지)와 `manageCode`(uint64_t, 그 작업
주체 안에서 이 인스턴스를 식별/추적하는 관리 코드 - 예: 요청
시퀀스 번호, 상관관계 ID). `AsyncTaskGroup`/`AsyncTaskWaitGroup`/
`AsyncTaskAwaiter`가 "이 그룹의 이 작업"을 정확히 비교/매칭할 때
이 두 코드를 함께 쓴다.

```cpp
namespace kernel {

using AsyncTaskSubjectCode = unsigned int;   // uint32_t - 작업 주체 코드
using AsyncTaskManageCode = unsigned long;   // uint64_t - 작업 주체별 관리 코드(구현 시 64비트 폭 확정)

enum class AsyncTaskState { Ready, Running, Suspended, Completed, Failed };

struct AsyncTask {
    unsigned long savedRsp = 0;   // kContextSwitch 재사용(Task와 동일한 소프트웨어 스위칭)
    unsigned long stackBase = 0;  // Slab(또는 전용 풀)에서 받은 고정 크기 스택
    AsyncTaskState state = AsyncTaskState::Ready;

    AsyncTaskSubjectCode subjectCode = 0;
    AsyncTaskManageCode manageCode = 0;
    void* args = nullptr;   // 생성/해제 전부 해당 AsyncTaskHandler 책임(3.1절)

    AtomicPtr<AsyncTask> next;    // 리액터 실행 큐용 침습적 포인터

    void init(AsyncTaskSubjectCode subjectCode, AsyncTaskManageCode manageCode, void* args);

    // 현재 실행 중인 AsyncTask 자신이 호출 - 진행 중인 작업을
    // suspend하고 리액터 컨텍스트로 복귀(kContextSwitch)해 다음
    // AsyncTask를 처리하게 한다. 나중에 리액터가 이 AsyncTask를
    // 다시 스케줄링하면 yield() 반환 지점부터 재개된다.
    static void yield();
};

}  // namespace kernel
```

### 3.3 `AsyncTaskGroup` / `AsyncTaskWaitGroup` / `AsyncTaskAwaiter`

설계자 확정(2026-09-14) - "비동기 작업 그룹은 AsyncTaskGroup, 대기
그룹은 AsyncTaskWaitGroup, 특정 작업을 대기하는 객체는
AsyncTaskAwaiter로 설계하라."

```cpp
namespace kernel {

// 서로 관련된 AsyncTask 여러 개를 묶어 관리(예: "이 4개 디스크
// 블록 읽기").
class AsyncTaskGroup {
public:
    void add(AsyncTask* task);
    unsigned int pendingCount() const;
};

// 그룹 전체가 끝날 때까지 "현재 Task"를 재운다 - 내부적으로
// 스케줄러의 비공개 block 프리미티브를 쓴다(DC-8EA1E7F6 6번 원칙
// 그대로 - 범용 block API는 여전히 비공개, 이게 그 전용 API).
class AsyncTaskWaitGroup {
public:
    void add(AsyncTask* task);
    void waitAll();
};

// 다른 AsyncTask 하나가 끝나기를 "현재 AsyncTask 컨텍스트 안에서"
// 기다린다 - AsyncTask::yield()를 반복 호출하며 리액터에 제어를
// 돌려주는 방식으로 구현(전체 리액터를 블로킹하지 않음). 중첩된
// 비동기 의존관계(예: A가 B의 결과가 필요) 표현에 쓴다.
class AsyncTaskAwaiter {
public:
    explicit AsyncTaskAwaiter(AsyncTask* target);
    void await();  // target 완료까지 yield() 반복
};

}  // namespace kernel
```

### 3.4 `AsyncReactor` - 코어당 전용 Task, 우선순위 무시 즉시 스케줄링

설계자 확정(2026-09-14) - "리액터 루프는 Task로 wrapping되어 각
코어마다 하나씩 배치되어야 진짜 동시성을 갖는다... 긴급한 인터럽트가
발생했을 때 비동기 작업을 처리하는 리액터 task를 즉시 스케줄링하여
실행해야 한다." idle 루프 대체안(원래 제안의 1차 추천)은 **폐기**
됐다 - 리액터는 전용 Task다.

```cpp
namespace kernel {

class AsyncReactor {
public:
    // 코어별로 하나씩 생성되는 리액터 Task의 진입점 - 실행 큐를
    // 드레인하며 각 AsyncTask를 kContextSwitch로 진입/재개한다.
    static void reactorTaskEntry(void* arg);

    // 인터럽트 컨텍스트에서 호출 가능 - 완료된 AsyncTask를 이
    // 코어의 실행 큐에 push하고, 이 코어의 리액터 Task를 즉시(RT
    // 클래스보다도 먼저, 4절 참고) 스케줄링하도록 요청한다.
    static void submitCompletion(AsyncTask* task);
};

}  // namespace kernel
```

### 3.5 인터럽트 통합 규칙 (기존 유지)

비동기 요청과 결부된 ISR은 하드웨어 상태 확인/ack까지만 하고,
`AsyncReactor::submitCompletion()`으로 큐에 넣고 그 코어의 리액터
Task를 깨우기만 한다 - 콜백 실행/추가 I/O 발행/락 획득은 전부
리액터 Task(정상 컨텍스트) 안에서 한다.

### 3.6 타임아웃/취소 (기존 유지)

HPET 기반 타임아웃을 옵션으로 가질 수 있다 - 마감까지 완료되지
않으면 프레임워크 자신이 해당 콜백을 `Timeout` 결과로 실행한다.

## 4. 스케줄러에 필요한 변경 (PL-2D3184BC에 반영 예정)

리액터 Task의 "우선순위를 무시하고 맨 앞으로 끼워넣기"는 기존
스케줄러 설계(DC-B80D8D31)에 없던 요구사항이다(설계자 직접 지시,
2026-09-14) - `Scheduler`에 즉시-스케줄링 프리미티브(예:
`Scheduler::scheduleImmediate(Task*)`)를 추가해, 코어별 큐의 맨
앞(RT 클래스보다도 앞)에 꽂아 넣을 수 있어야 한다. 별도 DC 없이
직접 지시된 사항이라 PL-2D3184BC 실행 계획에 그대로 반영한다.

## 5. Slab 할당자 의존성 (확정, SP-D7013B26)

`args`/`AsyncTask` 전용 스택 할당에 Slab 할당자(SP-D7013B26, 확정)
를 쓴다. **Slab 할당자는 고갈 시 절대 블로킹하지 않고 즉시
`nullptr`을 반환한다**(스케줄러 데드락 방지, QU-4F905C08) - 이
프레임워크(정확히는 각 `AsyncTaskHandler`)가 그 실패를
`onFailure()`로 받아 처리할 책임을 진다(3.1절). Slab 할당자 자신도
스케줄러의 선점 비활성화 프리미티브(PL-2D3184BC 8단계)를 전제로
하므로, 구현 순서는 "스케줄러 선점 금지 구간 → Slab 할당자 →
이 프레임워크" 순이 된다.

## 6. 이번 제안에 포함하지 않은 것

- 실제 소비자(devmgr 필수 IO 위임 경로, PL-2070E6EF의 MSI 라우팅
  등)에 이 프레임워크를 실제로 연결하는 작업 - 승인 후 별도 PL로
  진행.
- 코어 간 완료 이관 - 2절 비목표 참고.

## 7. C++20 코루틴 활용 (확정, 2026-09-14, QU-1BE6B8D2 답변 반영)

설계자 지시 - "Freestanding 환경에서 C++20의 coroutine을 활용할
방안을 찾아서 설계 제안에 반영하라." 그리고 스택풀(3.2절, 이미
확정) vs 코루틴 중 하나를 고르자는 후속 질의(DC-23AEA8B4/
QU-1BE6B8D2)에 대한 답 - **"둘 다 구현"**으로 확정됐다. 스택풀
`AsyncTask`(3.2절)는 그대로 유지하고, 그 위에서 `AsyncTaskHandler::
onExec`을 코루틴으로도 작성할 수 있게 한다.

### 7.1 실측: freestanding 환경에서 코루틴이 실제로 동작한다

이 프로젝트의 베어메탈 타겟(`x86_64-unknown-none-elf`)에는 C++
표준 라이브러리(libstdc++/libc++)가 아예 없어 표준 `<coroutine>`
헤더를 그대로 include할 수 없다(실측 확인 - `fatal error: 'coroutine'
file not found`). 하지만 컴파일러의 코루틴 변환(`co_await`/
`co_yield`/`co_return`)이 실제로 필요로 하는 이름은 `std::
coroutine_handle`과 `std::coroutine_traits` 딱 두 개뿐이다(언어
자체가 이 정확한 정규화 이름으로 조회 - clang/gcc 공통, 바꿀 수
없음). `std::suspend_always`/`std::suspend_never`는 순수 편의
타입(컴파일러가 이름으로 찾지 않고 awaiter 프로토콜만 확인)이라
설계자 지시대로 **최소 호환 네이밍만 std에 남기고 나머지는 이
프로젝트 컨벤션으로 개명**했다(2026-09-14) - `kernel::SuspendAlways`
/`kernel::SuspendNever`(RM-23F4B687 PascalCase). 이 최소 헤더를
`minicore/libs/libkenv/coroutine.h`로 신설했다.

**실측(2026-09-14, clang 18.1.3, 이 프로젝트와 동일한 플래그
`-ffreestanding -fno-exceptions -fno-rtti -mcmodel=kernel
-mgeneral-regs-only -nostdlib`)**:
- 이 헤더 하나로 `co_await`/`co_return`을 쓰는 코드가 정상
  컴파일됨을 확인 - 오브젝트 파일에 실제 코루틴 ramp/resume/
  destroy/cleanup 함수와 커스텀 `promise_type::operator new/delete`
  심볼이 생성됨을 확인.
- 커널 부팅 중 실제 코루틴을 실행 - "before-suspend"를 찍고
  `co_await`로 suspend한 뒤 커널 메인 흐름으로 제어가 돌아와
  "suspended, about to resume"을 찍고, 그 다음 명시적으로
  `coroutine_handle::resume()`을 호출해야만 "after-resume"이
  찍히는 순서를 확인 - **진짜 suspend/resume이 예외/RTTI/표준
  라이브러리 없이 동작함을 실측으로 증명**했다.
- `kernel::SuspendAlways`/`SuspendNever` 개명 후에도 동일하게
  정상 동작함을 재확인(2026-09-14).
- 전역 `operator new`가 없는(`-nostdlib`) 이 커널에서는 **모든
  `promise_type`이 `operator new`/`operator delete`를 직접 제공해야
  한다** - 코루틴 프레임 할당을 원하는 곳(Slab, 정적 버퍼 등)으로
  자유롭게 연결할 수 있다는 뜻이기도 하다.
- 검증 후 임시 테스트 코드는 전부 제거 - 영구 코드는
  `libkenv/coroutine.h` 헤더만 남겼다.

### 7.2 Slab 할당자와의 결합 + 할당 실패 시 재시도(확정)

`promise_type::operator new(size_t)`를 `GenericSlabAllocator::
alloc(size)`(SP-D7013B26)로 연결하면, 코루틴 프레임도 이 프로젝트가
이미 확정한 슬랩 캐시 경로를 그대로 탄다. Slab 할당자는 고갈 시
`nullptr`을 반환하는데(비블로킹 확정, QU-4F905C08), 코루틴의
`operator new`가 `nullptr`을 반환하면 그 자체로는 정의되지 않은
동작이다 - **표준 C++20 할당 실패 프로토콜**
(`promise_type::get_return_object_on_allocation_failure()`,
`operator new`는 `noexcept`로 선언)을 구현하면 예외 없이 실패를
표현할 수 있다.

**실측(2026-09-14)**: `operator new`가 의도적으로 `nullptr`을
반환하도록 만든 뒤, 코루틴 몸체가 **전혀 실행되지 않고**
`get_return_object_on_allocation_failure()`의 반환값만 호출부에
돌아옴을 확인 - 반대로 할당이 성공하면 몸체가 정상 실행됨도 같이
확인(두 경우 모두 커널 부팅 중 실측).

**설계자 지시(2026-09-14) - 할당 실패 시 "yield하며 대기"**: 코루틴
프레임 할당이 실패했을 때 그 자리에서 바로 실패 처리하지 않고,
이 코루틴을 시작시키려던 **스택풀 `AsyncTask`가 `yield()`를 호출해
리액터에 제어를 돌려주고, 나중에 다시 스케줄링됐을 때 코루틴
생성을 재시도**하도록 만든다 - 즉 두 메커니즘(스택풀의 yield/재개,
코루틴의 stackless suspend/resume)이 "할당 실패 시 재시도"라는
한 가지 상황에서 자연스럽게 맞물린다. 구현 계획(PL-1E247831)에
재시도 루프의 정확한 형태를 반영한다.

### 7.3 `AsyncTaskHandler::onExec`를 코루틴으로 구현하는 방식(확정)

3.2절의 `AsyncTask`(스택풀, `kContextSwitch` 재사용)는 그대로
유지된다 - 코루틴은 그걸 대체하는 게 아니라, **`AsyncTaskHandler::
onExec`의 구현 방식 중 하나**로 추가된다.

- `onExec`을 코루틴 함수로 선언(예: `AsyncExecCoro onExec(AsyncTask*
  task, void* args)`, `AsyncExecCoro`는 이 프레임워크가 정의하는
  코루틴 반환 타입)하면, 본문에서 `co_await`로 다른 `AsyncTask`의
  완료를 자연스럽게 기다리는 순차적 코드를 쓸 수 있다 -
  `AsyncTaskAwaiter`(3.3절)를 그대로 이 코루틴의 awaitable로
  재사용한다.
- 이 코루틴은 `AsyncTask`를 실행 중인 리액터 Task의 스택 위에서
  돈다 - 리액터가 여전히 "우선순위 무시 즉시 스케줄링" 가능한
  전체 `kernel::Task`라는 요구사항은 변하지 않는다(4절). 코루틴은
  그 리액터가 이 한 `AsyncTask`를 처리하는 동안 내부적으로 쓰는
  더 가벼운 실행 방식일 뿐이다.
- 코루틴 프레임 크기는 `AsyncTask`마다 다르다(지역 변수/중첩
  `co_await` 깊이에 따라 컴파일러가 결정) - Slab 버킷을 초과하면
  `PageFrameAllocator` 직행 경로(SP-D7013B26 2.3절)로 자연스럽게
  빠진다.
- `onExec`을 코루틴 대신 평범한 함수로 구현하는 것도 여전히
  가능하다(둘 다 지원) - 짧고 단순한 작업은 굳이 코루틴으로 쓸
  필요가 없다.
