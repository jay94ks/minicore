# 커널 전용 비동기 프레임워크(Task 기반) — 설계 제안

**[확정, 2026-09-14, QU-F86426D5 답변 반영]** 원래 제안(콜백 체인 +
스택 없는 `AsyncOp`)은 설계자 검토 결과 **스택풀 방식(`AsyncTask`,
자체 yield 지원) + 코어별 전용 리액터 Task**로 확정됐다 - 아래
본문을 확정된 최종 설계로 갱신했다. 원래 제안에서 남는 부분(문제
정의/목표/인터럽트 통합 규칙)은 그대로 두고, 핵심 개념(3절)과 API를
전부 최종 결정대로 다시 썼다. 승인된 대로 구현 계획은 PL로 분리한다
(작성 예정).

## 1. 문제 정의

`kernel::Task`(PL-2D3184BC)는 스케줄러의 최소 단위지만, **하나당
고정 커널 스택(기본 8KiB)과 전체 레지스터 컨텍스트를 통째로 가진
"무거운" 실행 흐름**이다. 반면 커널 내부에서 반복적으로 필요해질
패턴은 다음과 같다 — "장치에 요청을 하나 내고, 완료 인터럽트가 올
때까지 기다렸다가, 몇 줄짜리 후속 처리를 한다"(디스크 읽기, IPC
왕복, 타임아웃 대기 등). 대기 중인 요청마다 Task를 하나씩 만들면:

- 대기 중인 요청 수만큼 8KiB+ 스택이 낭비된다(수백~수천 개의 동시
  요청을 감당하기엔 비효율적).
- 완료 인터럽트가 왔다고 해서 그 안에서 후속 처리를 직접 돌리면
  안 된다 — 이번 세션에 실측으로 확인한 교훈(ISR 안에서 비재진입
  락을 쥔 함수를 부르면 데드락)이 일반화된 규칙이다: **ISR은 절대
  무거운/블로킹 가능한 로직을 직접 실행해서는 안 된다.**

## 2. 목표 / 비목표

**목표**
1. 대기 중인 비동기 작업 하나마다 전체 Task(전체 스택)를 만들지
   않고도 "요청 → 완료 시 후속 처리"를 표현할 수 있게 한다 -
   `AsyncTask`는 Task보다 훨씬 가벼운 전용 스택을 쓴다(3.2절).
2. 인터럽트 컨텍스트에서 하는 일을 "완료 표시 + 큐에 넣기"까지로
   최소화한다 - 실제 후속 로직은 반드시 리액터 Task 컨텍스트에서
   실행되게 한다.
3. 각 코어에 전용 리액터 Task를 둬 "진짜 동시성"을 갖는 비동기
   처리를 구현한다(설계자 확정, 2026-09-14) - 스케줄러(PL-2D3184BC)
   위에 얹되, 긴급한 인터럽트가 왔을 때 그 코어의 리액터 Task를
   우선순위 무시하고 즉시 스케줄링할 수 있어야 한다(4절 - 스케줄러
   자체에 새 프리미티브 필요).
4. 이미 확정된 스케줄러 설계(DC-8EA1E7F6/DC-B80D8D31)의 "블로킹/
   웨이크업은 외부 비공개, 기능별 특수 API로 노출" 원칙(QU-BA001D73
   6번)을 그대로 따른다 - `AsyncTaskWaitGroup`이 그 첫 실제 사례다.
5. 기능별로 콜백을 **한 번만 등록**해 두고, 실제 작업 발생 시엔
   Slab로 할당한 `args`만 콜백에 넘겨 실행한다(설계자 확정,
   2026-09-14) - 매번 콜백을 넣고 빼거나 비동기 작업 처리기가
   파편화되는 것을 피한다.
6. C++ 예외 없이, freestanding 환경에서 동작한다.

**비목표(v1 범위 밖)**
- 유저랜드용 비동기 I/O 모델이 아니다 - devmgr/fs/net은 전부
  유저랜드 서비스(SP §2-A)라 이 프레임워크는 **커널 자신의 내부
  구현**에만 쓰인다.
- 코어 간 완료 이관(코어 A에서 완료된 AsyncTask를 코어 B의 리액터가
  대신 처리) - v1은 인터럽트가 도착한 코어의 리액터가 그 코어의
  실행 큐만 처리한다(로드밸런싱은 Task 단위에서만).

## 3. 핵심 개념 (확정, 2026-09-14)

### 3.1 콜백 등록 - 기능별 1회 등록, 호출마다 args만 할당

```cpp
namespace kernel {

using AsyncCallback = void (*)(void* args);

// 기능별로 부팅/초기화 시 한 번만 등록한다 - 요청이 생길 때마다
// 등록/해제하지 않는다(설계자 지시, 2026-09-14).
class AsyncCallbackRegistry {
public:
    static unsigned int registerCallback(AsyncCallback callback);
    static AsyncCallback resolve(unsigned int callbackId);
};

}  // namespace kernel
```

실제 요청이 생기면 `GenericSlabAllocator::alloc(sizeof(Args))`
(SP-D7013B26 참고)로 `args`를 할당하고, 아래 `AsyncTask`에 담아
리액터에 제출한다.

### 3.2 `AsyncTask` - 자체 스택을 갖는 스케줄링 가능 단위(구 `AsyncOp`)

`kernel::Task`와 같은 소프트웨어 컨텍스트 전환(`kContextSwitch`)을
재사용하되, **Task보다 훨씬 작은 전용 스택**을 쓴다(정확한 크기는
구현 계획에서 실측 확정 - Slab 할당자의 한 버킷을 스택으로 쓰는
방안 포함해 검토). 콜백 실행 중 스스로 `yield()`를 불러 리액터에게
제어를 돌려주고 나중에 재개될 수 있다(설계자 지시, 2026-09-14 -
"비동기 작업 자체에도 별도의 yield 기능이 있어서 이걸 호출하면
현재 진행중이던 비동기 작업을 suspend하고, 다음 비동기 작업을
처리할 수 있어야 한다").

```cpp
namespace kernel {

enum class AsyncTaskState { Ready, Running, Suspended, Completed };

struct AsyncTask {
    unsigned long savedRsp = 0;   // kContextSwitch 재사용(Task와 동일한 소프트웨어 스위칭)
    unsigned long stackBase = 0;  // Slab(또는 전용 풀)에서 받은 고정 크기 스택
    AsyncTaskState state = AsyncTaskState::Ready;

    unsigned int callbackId = 0;
    void* args = nullptr;         // GenericSlabAllocator로 할당, 콜백이 끝나면 해제

    AtomicPtr<AsyncTask> next;    // 리액터 실행 큐용 침습적 포인터

    void init(unsigned int callbackId, void* args);

    // 현재 실행 중인 AsyncTask 자신이 호출 - 진행 중인 작업을
    // suspend하고 리액터 컨텍스트로 복귀(kContextSwitch)해 다음
    // AsyncTask를 처리하게 한다. 나중에 리액터가 이 AsyncTask를
    // 다시 스케줄링하면 yield() 반환 지점부터 재개된다.
    static void yield();
};

}  // namespace kernel
```

### 3.3 `AsyncTaskGroup` / `AsyncTaskWaitGroup` / `AsyncTaskAwaiter`

설계자 확정(2026-09-14) - "비동기 작업 그룹은 AsyncTaskGroup, 대기
그룹은 AsyncTaskWaitGroup, 특정 작업을 대기하는 객체는
AsyncTaskAwaiter로 설계하라."

```cpp
namespace kernel {

// 서로 관련된 AsyncTask 여러 개를 묶어 관리(예: "이 4개 디스크
// 블록 읽기").
class AsyncTaskGroup {
public:
    void add(AsyncTask* task);
    unsigned int pendingCount() const;
};

// 그룹 전체가 끝날 때까지 "현재 Task"를 재운다 - 내부적으로
// 스케줄러의 비공개 block 프리미티브를 쓴다(DC-8EA1E7F6 6번 원칙
// 그대로 - 범용 block API는 여전히 비공개, 이게 그 전용 API).
class AsyncTaskWaitGroup {
public:
    void add(AsyncTask* task);
    void waitAll();
};

// 다른 AsyncTask 하나가 끝나기를 "현재 AsyncTask 컨텍스트 안에서"
// 기다린다 - AsyncTask::yield()를 반복 호출하며 리액터에 제어를
// 돌려주는 방식으로 구현(전체 리액터를 블로킹하지 않음). 중첩된
// 비동기 의존관계(예: A가 B의 결과가 필요) 표현에 쓴다.
class AsyncTaskAwaiter {
public:
    explicit AsyncTaskAwaiter(AsyncTask* target);
    void await();  // target 완료까지 yield() 반복
};

}  // namespace kernel
```

### 3.4 `AsyncReactor` - 코어당 전용 Task, 우선순위 무시 즉시 스케줄링

설계자 확정(2026-09-14) - "리액터 루프는 Task로 wrapping되어 각
코어마다 하나씩 배치되어야 진짜 동시성을 갖는다... 긴급한 인터럽트가
발생했을 때 비동기 작업을 처리하는 리액터 task를 즉시 스케줄링하여
실행해야 한다." idle 루프 대체안(원래 제안의 1차 추천)은 **폐기**
됐다 - 리액터는 전용 Task다.

```cpp
namespace kernel {

class AsyncReactor {
public:
    // 코어별로 하나씩 생성되는 리액터 Task의 진입점 - 실행 큐를
    // 드레인하며 각 AsyncTask를 kContextSwitch로 진입/재개한다.
    static void reactorTaskEntry(void* arg);

    // 인터럽트 컨텍스트에서 호출 가능 - 완료된 AsyncTask를 이
    // 코어의 실행 큐에 push하고, 이 코어의 리액터 Task를 즉시(RT
    // 클래스보다도 먼저, 4절 참고) 스케줄링하도록 요청한다.
    static void submitCompletion(AsyncTask* task);
};

}  // namespace kernel
```

### 3.5 인터럽트 통합 규칙 (기존 유지)

비동기 요청과 결부된 ISR은 하드웨어 상태 확인/ack까지만 하고,
`AsyncReactor::submitCompletion()`으로 큐에 넣고 그 코어의 리액터
Task를 깨우기만 한다 - 콜백 실행/추가 I/O 발행/락 획득은 전부
리액터 Task(정상 컨텍스트) 안에서 한다.

### 3.6 타임아웃/취소 (기존 유지)

HPET 기반 타임아웃을 옵션으로 가질 수 있다 - 마감까지 완료되지
않으면 프레임워크 자신이 해당 콜백을 `Timeout` 결과로 실행한다.

## 4. 스케줄러에 필요한 변경 (PL-2D3184BC에 반영 예정)

리액터 Task의 "우선순위를 무시하고 맨 앞으로 끼워넣기"는 기존
스케줄러 설계(DC-B80D8D31)에 없던 요구사항이다(설계자 직접 지시,
2026-09-14) - `Scheduler`에 즉시-스케줄링 프리미티브(예:
`Scheduler::scheduleImmediate(Task*)`)를 추가해, 코어별 큐의 맨
앞(RT 클래스보다도 앞)에 꽂아 넣을 수 있어야 한다. 별도 DC 없이
직접 지시된 사항이라 PL-2D3184BC 실행 계획에 그대로 반영한다.

## 5. Slab 할당자 의존성

`args`/`AsyncTask` 전용 스택 할당에 Slab 할당자(SP-D7013B26, 설계
제안 중)를 쓴다 - 이 프레임워크의 구현은 SP-D7013B26 확정 이후로
순서가 정해진다.

## 6. 이번 제안에 포함하지 않은 것

- 실제 소비자(devmgr 필수 IO 위임 경로, PL-2070E6EF의 MSI 라우팅
  등)에 이 프레임워크를 실제로 연결하는 작업 - 승인 후 별도 PL로
  진행.
- 코어 간 완료 이관 - 2절 비목표 참고.
