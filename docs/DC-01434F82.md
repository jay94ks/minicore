# 비동기 프레임워크 제안(SP-F682B889)의 세부 결정 — 요구분석

## 배경

SP-F682B889("커널 전용 비동기 프레임워크(Task 기반) — 설계 제안")가
전체 구조를 제안했다 - 스택 없는 `AsyncOp`(콜백+컨텍스트), 코어별
lock-free 완료 큐, 정상 Task 컨텍스트에서 콜백을 실행하는
`AsyncReactor`, 기능별 전용 대기 API(`AsyncWaitGroup`). 이 제안의
§4에 "별도 DC로 등록 예정"이라고 명시한 네 가지 갈림길을 여기서
정식으로 묻는다 - 제안 자체를 승인할지와, 승인한다면 아래 세부를
어느 쪽으로 할지 둘 다 확인이 필요하다.

## 결정이 필요한 항목

1. **콜백 체인 vs 스택풀 마이크로파이버**: SP-F682B889는 콜백 체인
   방식(AsyncOp가 스택 없이 콜백만 들고, 완료 시 AsyncReactor가
   정상 Task 컨텍스트에서 그 콜백을 실행)을 1차안으로 추천했다.
   대안은 AsyncOp마다 훨씬 작은 전용 스택(예: 512B~1KiB)을 줘서
   `kContextSwitch`를 재사용해 순차적인 코드 스타일을 쓸 수 있게
   하는 스택풀 마이크로파이버 방식이다 - 더 자연스러운 코드가
   되지만 스택 풀 관리자를 별도로 만들어야 한다.
2. **리액터 배치**: 각 코어의 idle 루프 자체를 리액터로 대체(제안의
   추천안 - 새 Task를 하나도 안 만듦) vs 코어당 전용 리액터 Task를
   별도로 만들지(idle과 우선순위를 분리할 수 있지만 Task를 추가로
   써야 함).
3. **`AsyncOp` 풀 크기/할당 전략**: 부팅 시 고정 크기 정적 배열
   (코어별로 나눌지 전역 하나로 할지)로 할지, `libkmm` 동적 할당으로
   할지. 풀이 고갈되면 `acquire()`가 실패를 반환해야 하는지, 아니면
   호출한 Task를 블로킹시켜야 하는지도 같이 정해야 한다.
4. **`AsyncWaitGroup`의 필요성**: 콜백 체이닝만으로 충분하다고 보고
   이번 범위에서 아예 뺄지, 특정 시나리오(예: 여러 디스크 블록을
   병렬로 읽고 전부 모여야 다음 단계로 가는 경우)를 위해 지금
   포함할지.

전체 제안(SP-F682B889)에 대한 큰 방향 승인/반려 여부와, 승인한다면
위 네 항목에 대한 답을 부탁드립니다.
