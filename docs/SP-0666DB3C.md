# 커널 동기화 프리미티브(Mutex/Semaphore) 및 Signal 전달 — 설계 제안

설계자 지시(2026-09-14, 메시지) - "세마포어, 뮤텍스, Signal등에 대한
설계도 해라." `Spinlock`(libkenv, 이미 구현 완료)은 "짧게 잡고 바로
푸는" 저수준 상호배제만 제공한다 - 대기 시간이 길어질 수 있는 진짜
동기화 프리미티브(자고 있다가 깨어남)는 아직 없다. 이 문서는
`Scheduler::parkCurrent()`(PL-2D3184BC 6단계, 이미 구현 완료 - "특정
이유로 블로킹 후 누군가 깨울 때까지 대기"하는 범용 프리미티브)를
기반으로 Mutex/Semaphore를 설계하고, 별도로 프로세스 대상 비동기

연관 링크가 걸려 있다** - Mutex/Semaphore/폴트 재개 정책 전부가
그 문서의 스케줄링 프리미티브를 전제하기 때문이다(설계자 지시,
§5-5 참고).

## 1. 공통 기반 - 대기열(Wait Queue)

Mutex/Semaphore 둘 다 "지금 획득 못 하면 대기열에 매달렸다가, 나중에
누군가 그 중 하나를 깨워 재시도 기회를 준다"는 같은 패턴을 쓴다 -
`Task::next`(이미 있는 침습적 다음-포인터, 스케줄러 큐 전용이지만
**파킹된 Task는 어느 큐에도 없으므로 이 필드가 비어 있다** - 재사용
가능)로 간단한 FIFO를 구성한다. **`wakeOne()`이 깨우는 것은 "소유권을
넘겨받은 새 주인"이 아니라 "다시 한번 획득을 시도해 볼 기회를 얻은
후보"일 뿐**이라는 점이 §2.1에서 확정한 정책이다:

```cpp
// minicore/kernel, 가칭 wait_queue.h - Mutex/Semaphore가 공유하는 내부 헬퍼.
// Waitable을 구현해 §9의 강제 취소 메커니즘과 연동한다.
class WaitQueue : public Waitable {
public:
    // 현재 Task를 큐 꼬리에 매달고 파킹한다(Scheduler::parkCurrent
    // 호출 - 이 함수 자체가 반환하지 않고, 나중에 wakeOne()이나
    // §9의 cancel()이 이 Task를 다시 스케줄링해야 반환한다). 호출
    // 전에 반드시 상위 프리미티브(Mutex/Semaphore)의 Spinlock을
    // 잡고 있어야 하고, 이 함수 안에서 그 락을 풀고 파킹한다(락
    // 보유 중 파킹하면 다른 코어가 영원히 락을 못 잡음 - Mesa 모니터
    // 패턴). 파킹 직전 `task->blockedOn = this`를 설정한다(§9.2).
    // 반환 후에는 반드시 호출부가 조건을 재확인해야 한다(§2.1) -
    // "깨어났다"는 "획득했다"를 의미하지 않는다(강제 취소로 깨어난
    // 경우도 있음, §9.5).
    void parkCurrentAndUnlock(Spinlock& guard);

    // 큐 머리에서 하나 꺼내 그 Task가 파킹됐던 코어에서 즉시
    // 재개시킨다(Scheduler::scheduleImmediate 재사용 - 파킹된 Task는
    // 이중 스케줄링 걱정이 없다고 이미 문서화돼 있음). 이 Task가
    // 깨어나서 재시도했을 때 실패할 수 있다(다른 새 호출자가 먼저
    // 채갔을 경우, §2.1) - 그 경우 다시 파킹된다. 비어 있으면 아무
    // 일도 안 함.
    void wakeOne();

    // [추가, 2026-09-15, SP-F682B889 §9.5-4가 요구] 큐에 있는 대기자
    // 전원을 재시도 기회로 깨운다 - `wakeOne()`을 큐가 빌 때까지
    // 반복하는 것과 동치(각자 파킹됐던 코어에서 개별
    // `scheduleImmediate`)이지만, 이름을 붙여 호출부의 의도("이
    // 이벤트는 대기자 전원에게 알려야 한다" - 예:
    // `AsyncTaskCompletion`이 여러 대기자에게 완료를 동시에 알리는
    // 경우)를 명시적으로 드러낸다. `wakeOne()`과 똑같이 "소유권
    //이전"이 아니라 "재시도 기회"만 준다 - 깨어난 대기자들은 여전히
    // §2.1의 재경쟁 규칙을 따른다(다시 실패하면 다시 파킹).
    void wakeAll();

    bool isEmpty() const;

    // Waitable 구현(§9.3) - task가 이 큐 안에 있으면 리스트에서
    // 잘라내고 강제로 재개시킨다.
    bool cancel(Task* task, WaitCancelReason reason) override;

private:
    Task* _head = nullptr;
    Task* _tail = nullptr;
    // 각 Task가 파킹된 코어 인덱스를 어디에 저장할지는 §5-1의 열린
    // 질문 - v1은 Task 구조체 자체에 필드를 추가하는 것을 제안(§5-1).
};
```

## 2. Mutex

```cpp
// minicore/kernel, 가칭 mutex.h
class Mutex {
public:
    void init() { _locked = false; }

    // 재경쟁(wake-and-compete) 루프: Spinlock 아래에서 _locked가
    // false면 true로 바꾸고 즉시 반환(빠른 경로). true면(이미 잠겨
    // 있으면) 대기열에 매달려 파킹 - 깨어나도 소유권을 넘겨받은 게
    // 아니므로(§2.1) 루프 맨 앞으로 돌아가 다시 _locked를 확인한다
    // (졌으면 다시 파킹). 강제 취소로 깨어난 경우(§9)라면 재시도
    // 대신 인터럽트 에러를 반환하는 것을 제안(§9.6-3). **주의(§5-5):
    // 이 v1 구현은 재진입 안전하지 않다** - 이미 이 Mutex를 잠근
    // 바로 그 Task가 다시 lock()을 호출하면 자기 자신을 영원히
    // 대기시키는 데드락이 된다.
    void lock();

    // _locked = false로 바꾸고, 대기열에 누가 있으면 그 중 하나를
    // "재시도 기회"로만 깨운다(소유권을 넘기지 않는다, §2.1) - 그
    // 사이 다른 코어의 새 lock() 호출이 빠른 경로로 먼저 잠글 수
    // 있고, 그러면 깨어난 대기자는 재시도에 실패해 다시 파킹된다.
    void unlock();

    // 논블로킹 시도 - 실패해도 대기열에 매달리지 않고 즉시 false.
    bool tryLock();

private:
    Spinlock _guard;   // _locked/_waitQueue 자체를 보호하는 저수준 락(짧게만 보유)
    bool _locked = false;
    WaitQueue _waitQueue;
};
```

### 2.1 핸드오프(Direct Handoff) 대신 재경쟁(Wake-and-Compete) 방식을 쓰는 이유

**[수정, 2026-09-14, 설계자 재지시]** 이 문서는 처음에 `unlock()`이
다음 대기자를 직접 골라 소유권을 그대로 넘기는 **직접 핸드오프**
방식을 제안했었으나, 설계자가 "소유권을 unlock에서 고르는 것은
성능 손실이 더 크므로 다시 경쟁하게 두는 방식을 택해야 해"라고
지시함에 따라 **재경쟁(wake-and-compete)** 방식으로 교체한다.

핸드오프 방식의 문제: `unlock()`을 호출한 코어가 다음 대기자를
"정확히 그 Task"로 고정해 버리면, 그 대기자가 당장 실행 가능한
상태가 아니거나(다른 코어가 바쁘거나 스케줄 지연이 있으면) 그
사이에 **더 빨리 락을 쓸 수 있는 다른 새 호출자**가 있어도 무조건
그 특정 대기자가 깨어날 때까지 기다려야 한다(호위 효과, convoy
effect) - 이 지연이 직접 핸드오프가 절약하는 "재확인 로직 생략"
이득보다 실제로는 더 큰 성능 손실을 낸다는 것이 설계자의 판단이다.

**재경쟁 방식**은 `unlock()`이 그냥 상태만 풀어 놓고(`_locked =
false`/`_count++`), 대기열의 한 후보에게는 "다시 시도해볼 기회"만
주며, 그 사이 새로 `lock()`/`acquire()`를 호출하는 어떤 코어든
빠른 경로(Spinlock 아래 상태 확인 후 즉시 획득)로 먼저 채갈 수
있다 - 즉 **락은 항상 "그 순간 가장 먼저 확인하는 쪽"이 가져간다**.
대가로 깨어난 대기자가 재시도에 실패해 다시 파킹될 수 있다는
스퓨리어스 웨이크업 비용이 생기지만, 이는 호위 효과보다 훨씬 싸다고
판단(실측 후 재검토 대상, §5-2).

## 3. Semaphore

```cpp
// minicore/kernel, 가칭 semaphore.h
class Semaphore : public Waitable {
public:
    void init(uint32_t initialCount) { _count = initialCount; }

    // 재경쟁 루프: Spinlock 아래에서 카운트가 0보다 크면 즉시 차감
    // 후 반환(빠른 경로). 0이면 대기열에 매달려 파킹 - 깨어나도
    // 카운트를 넘겨받은 게 아니므로(§2.1과 동일 철학) 루프 맨
    // 앞으로 돌아가 다시 카운트를 확인한다(졌으면 다시 파킹).
    void acquire();

    // 카운트++ 후, 대기열에 누가 있으면 그 중 하나를 "재시도 기회"
    // 로만 깨운다(카운트를 직접 넘겨주지 않는다) - 그 사이 다른
    // 코어의 새 acquire() 호출이 먼저 채갈 수 있다.
    void release();

    bool tryAcquire();  // 논블로킹, 카운트가 0이면 즉시 false

    // Waitable 구현(§9.3) - 내부적으로 §1의 WaitQueue에 위임.
    bool cancel(Task* task, WaitCancelReason reason) override;

private:
    Spinlock _guard;
    uint32_t _count = 0;
    WaitQueue _waitQueue;
};
```

`Mutex`는 사실상 `Semaphore(initialCount=1)`의 특수형이지만, "누가
락을 쥐고 있는지"(재진입 감지, 소유자 오류 검출 등 후속 디버깅
기능의 여지)를 남겨 두기 위해 별도 타입으로 분리하는 것을 제안한다
(RM-23F4B687 §4 취지 - 지금은 숫자/타입 튜닝 수준의 결정). **Semaphore
는 애초에 "소유자"라는 개념이 없으므로(여러 스레드가 각기 카운트를
소비/반납) §5-5의 재진입 문제는 Mutex에만 해당한다.**

## 4. Signal 전달

### 4.1 범위 - 커널 쪽 플러밍만, 유저 핸들러 호출은 후속

SP-8B6B8D25 §2 11번("시그널 전파")이 이미 커널 책임으로 명시해 뒀다.
**유저 코드가 만든 시그널 핸들러를 ring3에서 실제로 호출하는 것**은
PN-124C105B(ring3 진입)가 아직 없어 이번 문서 범위 밖이다 - 이 문서는
"신호를 어떻게 커널 안에서 표현/전달/기본 처리하는지"까지만 다룬다.

### 4.2 신호 번호와 기본 동작

**[수정, 2026-09-14, 설계자 지시]** 신호 번호는 더 이상 이 문서가
임의로 정하지 않고, **RM-B5764185("Minicore Signal 번호표")** 의
번호를 그대로 사용한다(0=무효, 1~22/31=POSIX 표준과 동일) - 아래
enum 값은 그 표와 정확히 일치해야 한다:

```cpp
enum class SignalNumber : uint32_t {
    None = 0,          // 무효값 - 신호 없음

    Hup = 1,           // SIGHUP  - 터미널 세션 종료(주로 설정 리로드용)
    Int = 2,           // SIGINT  - 키보드 인터럽트(Ctrl+C)
    Quit = 3,          // SIGQUIT - 키보드 종료(Ctrl+\), 코어 덤프
    IllegalInstruction = 4,  // SIGILL  - 잘못된 머신 명령어(#UD 트랩 시 커널이 발생)
    Trap = 5,          // SIGTRAP - 디버깅 브레이크포인트 등
    Abort = 6,         // SIGABRT - abort() 등 비정상 종료 호출
    Bus = 7,           // SIGBUS  - 잘못된 메모리 주소 접근
    Fpe = 8,           // SIGFPE  - 산술 연산 오류(0 나누기 등)
    Kill = 9,          // SIGKILL - 즉시 강제 종료, 마스킹/무시 불가
    Usr1 = 10,         // SIGUSR1 - 사용자 정의 1
    Segv = 11,         // SIGSEGV - 잘못된 메모리 참조(유저 폴트 처리 §2-B가 커널이 스스로 발생)
    Usr2 = 12,         // SIGUSR2 - 사용자 정의 2
    Pipe = 13,         // SIGPIPE - 읽는 쪽 없는 파이프에 쓰기
    Alrm = 14,         // SIGALRM - 알람 타이머 만료
    Terminate = 15,    // SIGTERM - 기본 종료 신호, 핸들러로 가로챌 수 있음
    // 16번은 POSIX SIGSTKFLT 등에 대응하는 자리 - v1은 정의하지 않음(RM-B5764185)
    Chld = 17,         // SIGCHLD - 자식 프로세스 종료/중지 통지
    Cont = 18,         // SIGCONT - 중지된 프로세스 재개
    Stop = 19,         // SIGSTOP - 일시 중지, 마스킹/무시 불가
    Tstp = 20,         // SIGTSTP - 터미널 정지 신호(Ctrl+Z)
    Ttin = 21,         // SIGTTIN - 백그라운드 프로세스의 터미널 입력 시도
    Ttou = 22,         // SIGTTOU - 백그라운드 프로세스의 터미널 출력 시도
    // 23~30번은 v1 범위 밖(RM-B5764185) - 필요해지면 그 표에 먼저 예약
    Sys = 31,          // SIGSYS  - 잘못된 시스템 콜 요청
};
```

**v1이 실제로 발생시키는 것은 이 중 4개뿐**(`Kill`/`Terminate`/
`Segv`/`IllegalInstruction`, RM-B5764185 참고) - 나머지 번호는 이
enum에 자리만 예약돼 있을 뿐, 그 신호를 실제로 일으키는 커널 경로는
각 서브시스템(tty/프로세스 관리/알람 타이머/syscall 검증 등)이
구현될 때 별도로 설계한다.

```cpp
enum class SignalDisposition : uint32_t {
    Default,   // 기본 동작(대부분 프로세스 종료) - v1의 유일하게 실제
               // 구현 가능한 값(핸들러 호출 인프라가 없으므로)
    Ignore,    // 무시 - Kill/Stop에는 적용 불가(마스킹 불가 원칙)
    Handler,   // 유저 핸들러로 위임 - **PN-124C105B 완료 전까지는
               // 등록만 받아 두고 실제 호출은 하지 않는다**(§4.4)
};
```

### 4.4 전달 시점 - 체크포인트 + 강제 취소(§9) 병행 (v1)

**진짜 Unix 시그널**은 임의의 순간(시스템 콜 도중, 블로킹 대기
도중)에도 대상을 깨워 즉시 개입할 수 있다. **[수정, 2026-09-14,
설계자 지시]** 처음에는 이 프로젝트의 대기 프리미티브가 "대기열에
있는 걸 아는 쪽만 깨울 수 있다"는 한계 때문에 체크포인트 방식만
제안했었으나, 설계자가 "임의의 대기 상태에서 강제로 끄집어내는
범용 메커니즘도 설계 범위에 포함시켜"라고 지시해 §9에서 `Waitable`
인터페이스 기반 강제 취소 메커니즘을 추가했다.

**v1의 최종 전달 경로는 두 가지가 함께 동작한다**:

1. **대기 중(`Task::blockedOn != nullptr`)인 경우** — §9의 `cancel()`
   경로로 즉시 개입한다(§9.5). `WaitQueue` 기반 대기(Mutex/Semaphore)
   는 완전히 즉시, `pendingSyscalls` 기반 대기(§7의 폴트 재개 포함)
   는 §9.4의 한계(SP-F682B889 §8의 협조적 취소로 보강됨)가 적용된다.
2. **실행 중이거나 아직 어떤 대기에도 들어가지 않은 경우** — 기존
   체크포인트 방식(syscall 진입/반환 시점, ring3 진입 직전)이 그대로
   적용된다. `SignalNumber::Kill`은 `Process::killPending` 플래그로
   모든 체크포인트가 공통으로 확인해 최대한 빨리 처리한다.

이 두 경로를 합쳐도 "완전한 즉시성"은 아니다(예: 이미 실행 중인
코드가 다음 체크포인트/대기 진입 전까지는 개입 불가) - 이 한계는
여전히 v1의 알려진 제약으로 남는다.

## 5. 아직 열려 있는 설계 영역

1. **파킹된 Task의 "어느 코어에서 깨울지" 기록 위치**(§1): v1은
   `Task`에 `parkedCoreIndex` 필드를 추가하는 것을 제안 - 정확한
   필드 배치/스케줄러 마이그레이션(다른 코어로 옮겨 깨우는 로드밸런싱)
   여부는 PL-2D3184BC 쪽과 함께 확정 필요.
2. **재경쟁 방식의 기아(starvation) 가능성**(§2.1, 수정): 직접
   핸드오프의 convoy effect는 재경쟁 방식 채택으로 해소됐지만, 그
   대신 이론적으로 "항상 더 빠른 새 호출자에게 밀려 특정 대기자가
   계속 재시도에 실패"하는 기아 시나리오가 남는다 - v1은 이를
   허용하고(경쟁 심한 락은 애초에 설계 재검토 대상), 실측 후 필요
   시 대기 시간 기반 에이징(aging) 등을 재검토.
3. **[해결됨, 2026-09-14, §9로 대체]** ~~Signal의 진짜 비동기성
   한계~~ — "임의의 대기 상태에서 강제로 끄집어내는 범용 메커니즘"이
   설계자 지시로 이번 문서 범위에 포함됐다 - §9(`Waitable` 인터페이스
   기반 강제 취소) 참고. 완전한 즉시성까지는 아니라는 잔여 한계는
   §4.4/§9.6에 남아 있다.
4. **프로세스 ID 체계**: `KillArgs::targetProcessId`가 가리킬 정확한
   식별자 체계가 아직 없다(PN-268F062B "공개 인터페이스 registry"가
   유사한 문제를 다루는 중) - 실제 구현 시점에 그쪽과 통일.
   **[확정, 2026-09-17, QU-764C5624 답변]** `Kill`의 v1 스코프
   ("호출자 자신의 직계 자식만")를 그대로 확정 설계로 승격할지
   물었던 질의에 설계자가 답변 - "임의 프로세스 대상이 필요함 -
   설계안 작성해줘." 즉 직계 자식으로 좁힌 v1 범위는 최종이 아니고,
   `Kill`/`DebugAttach`(SP-9A6D579F) 둘 다 막고 있던 "pid→`Process*`
   안전 조회" 문제 자체를 정면으로 푸는 새 설계 문서가 필요하다 -
   아직 미착수(설계 작업 예정, minicore-88 세션).
5. **[추가, 2026-09-14, 설계자 지시] `Mutex`의 재진입(Recursive)
   안전성 미비**: "이 커널에서 Mutex는 기본적으로 Recursive Call
   Safe 해야 해. 그런데 현재 구조는 전혀 그렇지가 않아." §2의 v1
   `Mutex`는 소유자를 전혀 추적하지 않는 순수 `bool _locked` 구조라,
   같은 Task가 이미 잠근 Mutex를 다시 `lock()`하면 자기 자신을
   무한 대기시키는 데드락이 된다(재진입 불가) - 정상적인 재진입
   안전 Mutex가 되려면 최소한 (a) "현재 소유자 Task" 식별자 저장,
   (b) 같은 소유자의 재호출을 감지해 카운터만 증가시키고 즉시 반환,
   (c) `unlock()`이 카운터를 감소시켜 0이 될 때만 실제로 풀어주는
   재진입 카운트 구조가 필요하다 - 이는 §1의 `WaitQueue`/§2.1의
   재경쟁 정책과 맞물려 다시 설계해야 하는 범위라, **스케줄러
   (PL-2D3184BC)가 어느 정도 더 진척된 뒤 별도 개정판으로 다룬다**
   (설계자 판단) - 이번 문서는 결함을 명시적으로 기록만 해 두고
   수정하지 않는다(RM-23F4B687 §4 원칙 - 임의로 지금 결정하지 않음).

## 7. 유저 페이지 폴트 재개 정책 (SP-68182FBD §2.3 보완, 2026-09-14 설계자 지시)

### 7.1 무엇을 확정하는가

SP-68182FBD §2.3이 "그 프로세스만 블로킹시키고 스케줄러가 다음 작업
으로 전환, 폴트 정보는 PCB에 매달아 둔다"까지는 확정했지만, **그
뒤 누가/언제 다시 깨우는지**가 비어 있었다. 설계자 지시: "이전에
페이지 폴트에 관한 지침을 주면서 공통적으로 리스트를 두고, 그게
비어야 블로킹을 풀면 된다고 한 적이 있다" - 이 지침을 그대로
따른다. **이 프로젝트에 이미 정확히 같은 모양의 메커니즘이
구현돼 있다**: `UserThread::pendingSyscalls`(`ChunkedList`, SP-04EE2A18)
+ `Syscall::waitForMultipleSyscall`(모든 토큰이 끝나야 깨어남, AND
세만틱, 이미 구현 완료)가 바로 "공통 리스트가 비어야 블로킹을 푼다"
는 패턴이다 - 유저 페이지 폴트도 **새 자료구조를 만들지 않고 이
기존 메커니즘을 그대로 재사용**하는 것을 제안한다. (참고: 이 §7의
재개 경로는 §1-§3의 Mutex/Semaphore `WaitQueue`와는 별개의 기존
메커니즘 - `waitForMultipleSyscall`은 처음부터 "리스트가 비면
그 특정 Task를 재개"하는 확정적 대상 지정 방식이라 §2.1의 재경쟁
논의와는 무관하다. §9의 강제 취소 메커니즘은 이 경로에도 적용되지만
§9.4의 한계가 있다 - SP-F682B889 §8로 보강.)

### 7.2 설계 - 폴트 처리를 "또 하나의 대기 중인 syscall"로 모델링

```
유저 모드 실행 중 폴트 발생
   |
   v
1. 커널이 §2-B 정책대로 Task::state = Blocked, Process::lastFault에
   폴트 정보(faultAddr/errorCode/rip) 기록(기존 그대로, 변경 없음).
2. 폴트 처리 자체를 AsyncTask로 제출한다(Syscall::submit과 동일한
   경로 재사용, PL-21344323) - 이 AsyncTask가 "죽일지 swapfs에서
   읽어 페이지를 갈아 끼울지"를 판단하는 바로 그 작업(QU-0C4D25EF가
   이미 확정한 처리 주체).
3. 이 제출로 생긴 토큰을 UserThread::pendingSyscalls(이미 있는
   ChunkedList)에 그대로 추가한다 - 일반 syscall과 완전히 같은
   슬롯을 공유한다(폴트 전용 별도 리스트를 새로 만들지 않는다).
4. Task는 Syscall::waitForMultipleSyscall과 정확히 같은 대기 상태다
   - pendingSyscalls가 빌 때까지(이 폴트 토큰이 끝나고, 그 사이
     쌓였을 수 있는 다른 pending syscall/폴트 토큰도 전부 끝나야)
     재개하지 않는다.
5. AsyncTask 완료(kill 결정이든 swap-in 성공이든) → 토큰을
   pendingSyscalls에서 제거 → 리스트가 비었으면 Scheduler::
   scheduleImmediate()로 이 Task를 재개(이미 waitForAnyOf가 구현한
   경로 그대로) → 비지 않았으면(다른 대기 중인 항목이 남아 있으면)
   계속 Blocked.
```

**핵심**: 새 `TaskState`도, 새 대기열 자료구조도 필요 없다 - "유저
페이지 폴트"는 그저 "이 스레드가 기다리는 syscall 토큰 목록에 하나
추가된 특별한 종류의 항목"일 뿐이고, 그 목록이 비어야 재개된다는
규칙은 `waitForMultipleSyscall`이 이미 구현해 둔 그대로다.

### 7.3 왜 "리스트"인가 - 폴트가 여러 개 쌓일 수 있는 이유

v1은 프로세스당 스레드 하나뿐이지만(SP-68182FBD §Process), 그래도
리스트가 필요한 이유: (1) 이미 대기 중인 일반 syscall이 있는 상태
에서 그 syscall의 콜백/재개 경로 자체가 또 다른 페이지에 접근하다
새 폴트를 낼 수 있고, (2) 스레드가 여러 개로 확장되는 후속 과제
(SP-0666DB3C가 아니라 PL-2D3184BC/향후 멀티스레드 프로세스 과제)가
오면 한 프로세스에 여러 폴트가 동시에 존재할 수 있다 - 처음부터
"여러 개가 쌓일 수 있고 전부 비어야 재개"라는 형태로 설계해 두면
그때 가서 자료구조를 바꿀 필요가 없다.

### 7.4 SP-68182FBD §2.3과의 관계

SP-68182FBD §2.3이 미결로 남겨 뒀던 "새 `TaskState`가 필요한가,
`Blocked` 재사용으로 충분한가"는 이 설계로 **`Blocked` 재사용으로
확정**된다(QU-0C4D25EF 답변과 정확히 일치) - "누가/언제 깨우는지"의
공백만 이번에 채워진 것이다. §2.3 자체는 이 섹션으로 대체/흡수된
것으로 표시한다.

## 9. 임의의 대기 상태에서 강제로 끄집어내는 범용 메커니즘 (설계자 지시, 2026-09-14)

### 9.1 배경 - §5-3에서 열어 뒀던 질문의 해결

§5-3(원래 §4.4에 있던 열린 질문)이 "체크포인트 방식은 완전한
즉시성을 포기한 v1 단순화"이며, 나중에 정말 필요해지면 `WaitQueue`/
`Syscall::wait` 양쪽에 "이 Task를 신호로 강제 취소 가능"이라는 훅을
추가하는 별도 설계가 필요하다고 명시적으로 유보해 뒀는데, 설계자가
"임의의 대기 상태에서 강제로 끄집어내는 범용 메커니즘도 설계 범위에
포함시켜"라고 지시함에 따라 지금 그 훅을 설계한다.

### 9.2 설계 - `Waitable` 인터페이스

이 프로젝트에는 서로 다른 모양의 "대기 중" 상태가 이미/곧 여러 개
있다 - §1의 `WaitQueue`(Mutex/Semaphore), SP-04EE2A18의
`UserThread::pendingSyscalls`+`waitForMultipleSyscall`(§7이 유저
폴트 재개에도 재사용), 그리고 향후 추가될 대기 종류. 각각을 개별
취소 코드로 따로 구현하지 않도록, "이 Task가 지금 무엇에 막혀
있는지"를 추상 인터페이스로 표현한다:

```cpp
// minicore/kernel, 가칭 waitable.h
enum class WaitCancelReason : uint32_t {
    Signal,     // 강제 시그널(Kill 등)에 의한 취소
    Timeout,    // 향후 타임아웃 기능이 생기면 재사용(v1 범위 밖)
};

// 이 Task가 현재 파킹된 대기 구조체가 구현해야 하는 최소 인터페이스.
// Task::blockedOn이 이 포인터를 들고 있고, cancel()이 그 대기
// 구조체 자신의 내부 자료구조(WaitQueue의 연결 리스트,
// pendingSyscalls의 ChunkedList 등)에서 이 Task를 실제로 제거하고
// 재개시킬 책임을 진다.
class Waitable {
public:
    virtual ~Waitable() = default;

    // task를 이 대기 구조체에서 강제로 제거하고 Ready로 되돌린다.
    // 이미 정상적으로 깨어나 대기 구조체를 떠난 뒤라면(경쟁 상황)
    // 아무 일도 하지 않고 false를 반환한다 - 호출부는 이 반환값으로
    // "취소가 실제로 적용됐는지"를 판단한다.
    virtual bool cancel(Task* task, WaitCancelReason reason) = 0;
};
```

`Task`(minicore/kernel/task.h)에 필드 추가 제안:

```cpp
// Task 구조체에 추가
Waitable* blockedOn = nullptr;  // 파킹 시작 시 설정, 정상적으로
                                 // 깨어나면 스스로 nullptr로 되돌림.
                                 // 대기 구조체 자신의 Spinlock으로
                                 // 보호(별도 락 불필요, §9.6-1).
```

### 9.3 `WaitQueue`(Mutex/Semaphore) 쪽 구현

`WaitQueue`는 지금 `wakeOne()`으로 머리만 꺼내는 단순 FIFO였으나
(§1), `cancel()`을 지원하려면 **임의 위치의 노드를 제거**할 수
있어야 한다 - 리스트가 대개 짧다는 전제(경합이 심한 락은 애초에
설계 재검토 대상, §5-2와 같은 가정) 하에 head부터 순회해 O(n)
제거를 허용한다. `cancel()`이 성공하면 §9.3의 `WaitQueue`는 즉시
`Scheduler::scheduleImmediate()`로 그 Task를 재개시킨다 - 이 경로는
**완전히 즉시적**이다(§9.4의 pendingSyscalls 경로와 다른 점).

### 9.4 `pendingSyscalls`/`waitForMultipleSyscall` 쪽 구현

§7의 유저 페이지 폴트 재개나 일반 syscall 대기는 `WaitQueue`가
아니라 `UserThread::pendingSyscalls`(AsyncTask 완료를 기다리는 AND
세만틱)를 쓴다 - 여기서의 `cancel()`은 §9.3처럼 간단하지 않다:

- Task 자체를 Ready로 되돌리는 것(대기 목록에서 이 Task를 제거)은
  쉽다.
- 하지만 **이미 제출된 AsyncTask(예: swapfs에서 페이지를 읽어오는
  중인 I/O)는 즉시 멈추지 않는다**. **[갱신, 2026-09-14, SP-F682B889
  §8로 보강]** 이 부분은 이제 무작정 "AsyncTask 결과를 버린다"가
  아니라, `cancel()`이 그 AsyncTask의 `cancelSource.trigger()`도
  함께 호출해 **협조적 취소 신호**를 보낸다 - Task 자신은 즉시
  Ready로 복귀하지만(위 문단 그대로), 뒤에서 계속 도는 AsyncTask도
  다음 확인 지점(`AsyncToken::isCancelled()`)에서 스스로 정리하고
  멈출 기회를 얻는다. 다만 여전히 **강제 중단은 아니다** - 그
  AsyncTask의 `onExec`/코루틴 몸체가 실제로 그 지점을 확인하지
  않으면(레거시 핸들러 등) 계속 실행된다는 한계는 남는다(각
  AsyncTaskHandler 구현이 SP-F682B889 §8의 관례를 따르는지에 달림).

### 9.5 Signal 전달(§4.4)과의 연결

`SignalNumber::Kill`가 도착하면, 그 대상 Task의 `blockedOn`이
가리키는 대기 구조체가 있으면 즉시 `blockedOn->cancel(task,
WaitCancelReason::Signal)`을 호출해 체크포인트를 기다리지 않고
즉시 깨운다(§9.3 케이스는 완전히 즉시, §9.4 케이스는 Task 자신은
즉시 깨어나고 연결된 AsyncTask는 SP-F682B889 §8의 협조적 취소
신호를 받는다). Task가 지금 실행 중이거나(Running) 아직 어떤
대기에도 들어가 있지 않으면(`blockedOn == nullptr`) 기존 §4.4의
`Process::killPending` 체크포인트 경로가 그대로 다음 체크포인트에서
처리한다 - 두 경로가 함께 있어야 "대기 중이면 즉시, 실행 중이면
다음 체크포인트에"라는 완전한 커버리지가 된다.

### 9.6 아직 열려 있는 하위 과제

1. **[해결됨, PN-F5B33BE2, 2026-09-15]** ~~경쟁 조건~~: `cancel()`이
   호출되는 순간과 그 Task가 마침 정상적으로 깨어나는 순간이 겹칠 수
   있다는 우려 - **이미 구현·해결됨**(PN-F5B33BE2 본문: "§9.6-1(경쟁
   조건 처리)은 WaitQueue 자신의 `_lock` 아래서 `blockedOn` 정리를
   wakeOne()/cancel() 양쪽이 공유하도록 구현해 이미 해결"). 아래
   pseudocode는 그 원리(같은 Spinlock 임계구역 안에서 "먼저 읽고
   nullptr로 바꾼 쪽만 승리")를 설명하는 참고용이며, 실제
   `wait_queue.cpp`의 정확한 구현과 100% 동일한 코드는 아닐 수
   있다 - 원리 자체는 실제 구현과 일치함이 확인됐다:

   ```cpp
   // WaitQueue::wakeOne() 쪽(정상 경로) - 이미 §9.3이 head를 순회하는
   // 자리에 있으므로 자연스럽게 같은 임계구역 안.
   bool WaitQueue::wakeOne() {
       SpinlockGuard guard(_guard);   // 이 대기 구조체 자신의 락
       Task* task = popHead();        // 없으면 false
       if (!task) return false;
       task->blockedOn = nullptr;     // "내가 정상 경로로 처리했다" 표시
       Scheduler::scheduleImmediate(task);
       return true;
   }

   // Waitable::cancel() 쪽(§9.2) - 같은 락 임계구역 안에서 동작.
   bool WaitQueue::cancel(Task* task, WaitCancelReason reason) {
       SpinlockGuard guard(_guard);   // wakeOne()과 동일한 락
       if (task->blockedOn != this) {
           // 이미 wakeOne()이 먼저 처리해 blockedOn을 지웠거나
           // 애초에 이 대기 구조체 소속이 아니었음 - cancel 패배.
           return false;
       }
       removeFromList(task);          // 대기열에서 실제 제거
       task->blockedOn = nullptr;
       task->lastCancelReason = reason;  // §9.6-3
       Scheduler::scheduleImmediate(task);
       return true;
   }
   ```

   **핵심 불변조건**: `task->blockedOn`을 `nullptr`로 되돌리는 두
   경로(`wakeOne()`/`cancel()`) 모두 **같은 Spinlock을 쥔 채로만**
   그 필드를 읽고 쓴다 - 그래서 둘 중 먼저 락을 잡는 쪽이 항상
   유일하게 성공하고(`blockedOn != this`를 본 나머지 하나는 그
   즉시 패배를 알고 조용히 반환), "둘 다 성공"하거나 "둘 다 실패"하는
   경우가 구조적으로 없다. `§9.4`의 `pendingSyscalls` 기반 대기도
   같은 패턴을 그 자신의 락으로 반복한다.
2. **[해결됨, 2026-09-14, SP-F682B889 §8로 대체]** ~~AsyncTask
   자체의 취소 지원 여부~~ — "AsyncTask에 AsyncToken,
   AsyncTokenSource를 도입하고 트리거되면 취소된 걸로 간주하는
   메커니즘을 설계"하라는 설계자 지시로, SP-F682B889 §8이 협조적
   취소(강제 중단이 아니라 실행 중인 코드가 스스로 확인하는 방식)
   설계를 확정했다 - §9.4 참고. 다만 "핸들러가 그 확인 지점을 실제로
   넣었는지"는 여전히 각 AsyncTaskHandler 구현 책임으로 남는다.
3. **`cancel()`의 반환 상태 전달 방법**: `Mutex::lock()`이 깨어났을
   때 "정상적으로 재시도 기회를 얻은 것"과 "강제로 취소당한 것"을
   구분해야 재시도 루프를 멈추고 에러(예: `ChannelError::
   Interrupted`류)를 반환할 수 있다 - 정확한 전달 채널(Task에 별도
   필드? `cancel()`이 넘기는 값을 어디에 저장?)은 구현 시점에 확정.
   **[갱신, 2026-09-15] 설계 제안**: §9.2의 `Task` 필드 제안에
   `WaitCancelReason lastCancelReason = {}`(기본값 없음을 나타내는
   센티널, 예: 별도 `WaitCancelReason::None` 추가)을 함께 추가한다.
   `Waitable::cancel()`의 각 구현체(§9.3 `WaitQueue`/§9.4
   `pendingSyscalls`)가 `task`를 `Scheduler::scheduleImmediate()`로
   재개시키기 **직전에** `task->lastCancelReason = reason`을 써 둔다
   (blockedOn 정리와 같은 Spinlock 임계구역 안 - 경쟁 없음). 깨어난
   쪽(`Mutex::lock()`의 재경쟁 루프, §9.4 경로의 syscall 대기 등)은
   재시도/재확인 전에 `Scheduler::currentTask()->lastCancelReason`을
   확인 - `None`이 아니면 즉시 그 값을 로컬로 빼내고 필드를 다시
   `None`으로 리셋한 뒤(다음 대기에 오염되지 않도록) 재시도 대신
   에러를 반환한다. 정상 재시도 경로는 이 필드를 아예 안 건드리므로
   기존 §2.1 재경쟁 로직과 완전히 호환된다. **[확정, 2026-09-15,
   QU-846C5AE7 답변 승인]** 위 제안(`Task::lastCancelReason` 필드)
   그대로 확정.

## 10. 비동기 프레임워크 전용 동기화 프리미티브 - AsyncMutex/AsyncSemaphore (설계자 지시, 2026-09-14)

### 10.1 배경 - 왜 §2/§3의 Mutex/Semaphore를 AsyncTask 안에서 그대로 못 쓰는가

§2의 `Mutex::lock()`이 경합하면 `WaitQueue::parkCurrentAndUnlock()`
→ `Scheduler::parkCurrent()`를 호출한다(§1) - 이건 **"지금 실행 중인
`kernel::Task` 전체"를 재우는** 동작이다. 그런데 `AsyncTask`(구현
완료, SP-F682B889 §3.2)의 `onExec`은 독립된 `kernel::Task`가 아니라
**리액터 Task(`AsyncReactor::reactorTaskEntry`, SP-F682B889 §3.4)의
실행 흐름 위에서 `kContextSwitch`로 진입/재개되는 경량 실행 단위**일
뿐이다 - 그 안에서 `Mutex::lock()`이 경합해 `parkCurrent()`를 부르면
**"리액터 Task 자신"이 통째로 잠들어**, 그 코어의 리액터가 처리
중이던 다른 모든 `AsyncTask`까지 함께 멈춰 버린다. 이는 SP-F682B889
§1의 핵심 문제 정의("ISR/리액터는 절대 무거운/블로킹 가능한 로직을
직접 실행해서는 안 된다")를 정면으로 위반한다 - 그래서 `AsyncTask`
컨텍스트 전용 동기화 프리미티브가 별도로 필요하다.

### 10.2 설계 - `AsyncMutex`/`AsyncSemaphore`

핵심 아이디어: "블로킹 후 누군가 깨움"(`WaitQueue`)이 아니라
**"경합하면 `AsyncTask::yield()`로 리액터에 양보하고, 다시 스케줄될
때 재시도"** - `AsyncTaskAwaiter::await()`(SP-F682B889 §3.3, "target
완료까지 yield() 반복")와 정확히 같은 관용구를 재사용한다. 별도
대기열(`WaitQueue`) 자체가 필요 없다 - "파킹"이 아니라 "양보"이기
때문이다.

```cpp
// minicore/kernel, 가칭 async_mutex.h - AsyncTask(스택풀/코루틴 몸체)
// 컨텍스트에서만 호출한다. 완전한 kernel::Task(리액터 자신 포함)
// 컨텍스트에서 부르면 안 된다(AsyncTask::yield()가 그 전제).
class AsyncMutex {
public:
    void init() { _locked = false; }

    // 재경쟁(wake-and-compete, §2.1과 동일 철학) 빠른 경로: Spinlock
    // 아래에서 즉시 확인/획득. 실패하면 AsyncTask::yield()로 제어를
    // 리액터에 돌려주고, 이 AsyncTask가 나중에 다시 스케줄됐을 때
    // 루프 맨 앞부터 재시도한다 - 리액터 자신은 단 한 순간도
    // 블로킹되지 않는다(§10.1).
    void lock() {
        for (;;) {
            {
                SpinlockGuard guard(_guard);
                if (!_locked) { _locked = true; return; }
            }
            AsyncTask::yield();
        }
    }

    // §2.1과 동일 - 다음 소유자를 직접 고르지 않는다(핸드오프 없음).
    // 상태만 풀어 두면 재시도 중이던 다른 AsyncTask나 새로 lock()을
    // 부르는 쪽 중 가장 먼저 확인하는 쪽이 채간다.
    void unlock() {
        SpinlockGuard guard(_guard);
        _locked = false;
    }

    bool tryLock();  // 논블로킹 - 실패해도 yield()하지 않고 즉시 false

private:
    Spinlock _guard;
    bool _locked = false;
    // WaitQueue 불필요(§10.2) - 대기가 아니라 양보이므로 대기열
    // 자체가 없다.
};

// AsyncSemaphore도 동일한 형태 - Semaphore(§3)의 _count 필드 +
// 재경쟁 로직을 그대로 가져오되, 경합 시 parkCurrentAndUnlock() 대신
// AsyncTask::yield()를 쓴다.
class AsyncSemaphore {
public:
    void init(uint32_t initialCount) { _count = initialCount; }
    void acquire() {
        for (;;) {
            {
                SpinlockGuard guard(_guard);
                if (_count > 0) { --_count; return; }
            }
            AsyncTask::yield();
        }
    }
    void release() {
        SpinlockGuard guard(_guard);
        ++_count;
    }
    bool tryAcquire();

private:
    Spinlock _guard;
    uint32_t _count = 0;
};
```

### 10.3 취소(§8 AsyncToken)와의 연동 - 관례, 강제 아님

§8.4가 `onExec`/코루틴 몸체에게 권장한 것과 동일한 관례를
`AsyncMutex::lock()`/`AsyncSemaphore::acquire()`를 부르는 코드에도
적용할 수 있다 - `yield()` 직전/직후에 `AsyncToken::isCancelled()`
를 확인해 취소됐으면 루프를 빠져나가는 것을 호출부가 직접 구현한다
(`AsyncMutex` 자신은 어떤 `AsyncTokenSource`에도 묶이지 않는다 -
§8의 `cancelSource`는 `AsyncTask` 하나당 것이지 락 하나당 것이
아니므로, 락 프리미티브가 스스로 취소를 판단하지 않는 것이 맞다).

### 10.4 아직 열려 있는 하위 과제

1. **기아(starvation) 가능성**: §2.1/§9.6-2의 재경쟁 방식과 동일한
   근본 트레이드오프가 yield 루프에도 있다 - v1은 허용, 실측 후 재검토.
2. **[구체화, 2026-09-15] 코루틴 전용 awaitable 버전**: 코루틴 몸체가
   `AsyncMutex::lock()`(내부적으로 `AsyncTask::yield()` →
   `kContextSwitch`)을 그대로 호출하는 것은 **안 된다** - `yield()`는
   스택풀 `AsyncTask`의 실행 스택 자체를 통째로 스왑하는 하드웨어
   컨텍스트 전환인데, 코루틴 몸체는 그 스택 위에서 도는 것이 아니라
   컴파일러가 만든 별도 프레임(§7.1의 `promise_type` 힙 할당)에서
   도는 상태 기계다 - `yield()`가 스택을 바꿔버리면 그 코루틴
   프레임으로 돌아올 복귀 지점 자체가 꼬인다(정의되지 않은 동작).
   **`co_await`용 전용 awaiter가 반드시 필요하다** - §3.3의
   `AsyncTaskAwaiter`가 이미 세운 선례(같은 클래스가 스택풀 쪽에서는
   반복 `yield()` 호출로, 코루틴 쪽에서는 awaiter 프로토콜로 이중
   동작)를 그대로 따른다:

   ```cpp
   // minicore/kernel, 가칭 async_mutex_awaiter.h - AsyncMutex 전용,
   // 매 co_await 호출마다 "한 번의 재시도 기회"만 표현한다(§10.2
   // yield 루프의 한 번의 순회와 정확히 대응 - 루프 자체는 코루틴
   // 몸체가 돈다, 아래 사용 예 참고).
   class AsyncMutexLockAwaiter {
   public:
       explicit AsyncMutexLockAwaiter(AsyncMutex& mutex) : _mutex(mutex) {}

       // 이미 잠글 수 있으면 suspend 자체를 건너뛴다(§10.2의 빠른
       // 경로와 동일).
       bool await_ready() const { return _mutex.tryLock(); }

       // 못 잠갔다 - 코루틴을 suspend하고, 이 AsyncTask를 리액터
       // 실행 큐에 다시 넣어(AsyncReactor::submitCompletion과 동일한
       // 재큐잉 경로) 다음 턴에 이 handle이 재개(.resume())되도록
       // 한다. 실제 재개(.resume() 호출)는 코루틴 프레임을 소유한
       // AsyncExecCoro의 재개 경로(SP-F682B889 §7 소유)가 맡는다 -
       // 이 문서는 "재큐잉하면 다음 턴에 재개된다"는 계약만 전제한다.
       bool await_suspend(std::coroutine_handle<> handle) {
           AsyncReactor::submitCompletion(AsyncTask::current());
           return true;  // suspend 유지 - handle 저장/재개는 리액터 쪽 책임
       }

       // 재개됐다고 해서 이번엔 반드시 잠겼다는 보장은 없다(§10.2와
       // 동일한 재경쟁 철학 - "언젠가 확인할 기회를 얻었다"일 뿐) -
       // 그래서 성공 여부를 bool로 돌려주고, 호출부가 직접 루프를
       // 돈다(아래).
       bool await_resume() const { return _mutex.tryLock(); }

   private:
       AsyncMutex& _mutex;
   };
   ```

   **사용 예(코루틴 `onExec` 안)**:
   ```cpp
   AsyncExecCoro onExec(AsyncTask* task, void* args) {
       while (!co_await AsyncMutexLockAwaiter(myMutex)) {
           // 이번 턴엔 못 잠갔다 - 다음 co_await 재시도로 넘어감
       }
       // 여기 도달 = 잠금 성공(§10.2 yield 루프의 while과 정확히 동형)
       // ... 임계구역 ...
       myMutex.unlock();
   }
   ```

   `AsyncMutex::lockAsync()`(멤버 함수, 위 awaiter를 생성해 반환)를
   추가해 호출부가 `AsyncMutexLockAwaiter` 타입명을 직접 안 써도
   되게 한다 - `co_await mutex.lockAsync()`. **[확정, 2026-09-15]**
   문서 간 교차 검증 완료 - SP-F682B889 §7.3에 재개 드라이버가
   구체화됐다(`AsyncTask::coroHandle` 필드 + `reactorTaskEntry()`가
   suspend된 handle을 저장해 뒀다가 다음 디스패치에서 `resume()`)
   - 이 문서의 `await_suspend()`가 재큐잉만 하고 실제 재개는 리액터
   쪽이 맡는다는 전제와 정확히 맞물린다. 충돌 없음.
3. **[해결됨, 2026-09-14, §13으로 대체]** ~~Semaphore(§3)와의 코드
   중복~~ - "경합 시 무엇을 하는지"(파킹 vs yield)만 다른 정책으로
   분리해 공통 템플릿화하자는 제안 그대로 §13(`MutexCore`/
   `SemaphoreCore` + `ParkingPolicy`/`YieldingPolicy`)에서 확정·승인

## 11. Thread Local Variable (설계자 지시, 2026-09-14) — **[구현 완료, PN-E5860CCA, 2026-09-15]**

**[갱신, 2026-09-15] 이 §11 전체(아래 §11.2의 `TlsRegistry`/`ThreadLocal<T>`

이 문서가 §15(`AsyncLocal<T>`)/§16(`ReentrantMutex`)을 설계하며
반복해서 "아직 미구현"으로 서술한 것은 이 완료를 놓친 것이었다 -
설계자 지시("계획에 완료된 것들이 섞여있는데 조사해봐")로 발견해
정정한다. 아래 §11.2/§12.2의 코드 블록은 실제 구현과 100% 일치함을
소스 대조로 확인했다(git_read로 `tls.h`/`percpu.h` 직접 확인,

### 11.1 배경 - 왜 진짜 컴파일러 `thread_local`이 아니라 명시적 슬롯인가

유저랜드 C++의 `thread_local`/`__thread`는 컴파일러가 자동으로 FS
세그먼트 상대 주소로 코드를 생성하고, 링커가 `.tdata`/`.tbss`
섹션과 초기화 이미지를 구성하며, 컨텍스트 전환 시 `FS_BASE` MSR을
스레드마다 교체해야 동작한다 - 이 프로젝트는 이 셋 중 어느 것도
아직 갖추지 않았다(컨텍스트 전환은 `kContextSwitch`가 범용 레지스터
+ RFLAGS만 저장/복원, PL-2D3184BC). 지금 이 전체 인프라를 새로
구축하는 것은 이번 요청의 범위를 크게 넘는다 - 대신 이 프로젝트가
이미 반복 채택한 패턴(`SyscallEndpointId`/`AsyncTaskSubjectCode` -
"부팅 시 슬롯/코드를 한 번 발급받아 재사용", RM-48E1E610/
SP-F682B889 §3.1)을 그대로 재사용하는 **명시적(explicit) TLS**를
v1으로 제안한다 - `thread_local` 키워드는 지원하지 않고, `get()`/
`set()` 호출로 흉내낸다.

### 11.2 설계 - 슬롯 배열 + 타입 안전 뷰

```cpp
// minicore/kernel, 가칭 tls.h
using TlsSlotIndex = uint32_t;
constexpr uint32_t kMaxTlsSlots = 16;  // 실측 후 조정(RM-23F4B687 §4 원칙)

// 기능별로 부팅/초기화 시 한 번만 슬롯을 발급받는다 - 요청마다
// 등록/해제하지 않는다(AsyncCallbackRegistry, SP-F682B889 §3.1과
// 동일한 관례).
class TlsRegistry {
public:
    static TlsSlotIndex allocateSlot();
};

// onExec/코루틴 본문이나 syscall 처리 코드가 쓰는 타입 안전 뷰 -
// 실제 T 인스턴스의 생성/해제는 그 슬롯을 발급받은 서브시스템
// 책임이다(AsyncTaskHandler의 args와 동일 원칙, SP-F682B889 §3.1) -
// 이 클래스 자신은 슬롯 접근만 제공한다.
template <typename T>
class ThreadLocal {
public:
    explicit ThreadLocal(TlsSlotIndex slot) : _slot(slot) {}

    T* get() const {
        return static_cast<T*>(Scheduler::currentTask()->tlsSlots[_slot]);
    }
    void set(T* value) {
        Scheduler::currentTask()->tlsSlots[_slot] = value;
    }

private:
    TlsSlotIndex _slot;
};
```

`Task`(minicore/kernel/task.h)에 필드 추가 제안:

```cpp
// Task 구조체에 추가 - Task가 이미 커널 Task/UserThread 공통
// 베이스이므로(RM-32D06563 §2, SP-04EE2A18) 여기 두면 양쪽 다 커버.
void* tlsSlots[kMaxTlsSlots] = { nullptr, /* ... */ };
```

### 11.3 `AsyncTask`는 이 설계 대상이 아니다

`AsyncTask`(SP-F682B889 §3.2)는 `Task`를 상속하지 않는 별개
구조체다(리액터 위에서 도는 경량 실행 단위) - 이 §11의 TLS는
`Task`/`UserThread`(완전한 스케줄링 단위)에만 적용된다. `AsyncTask`
자체에 유사한 슬롯이 필요해지면(예: 하나의 `AsyncTask` 실행 동안만
유효한 임시 상태) 별도로 검토한다(§11.4-3) - 지금은 필요 소비자가
없다.

### 11.4 아직 열려 있는 하위 과제

   `.tdata`/`.tbss`) 별도 SP로 설계해야 한다 - 지금은 소비자가 없어

2. **`kMaxTlsSlots` 크기**: 16은 임의값 - 실제 소비자가 늘어나며
   실측 조정(RM-23F4B687 §4 원칙).
3. **[해결됨, 2026-09-15, §15로 대체]** ~~`AsyncTask` 자체의 TLS

percpu.h`(문서가 제안한 `minicore/libs/libkenv` 대신 `minicore/kernel`

구현 위에 의미론적 이름만 얹는 것이었다.

### 12.1 배경 - 이미 반복되고 있는 패턴의 공식화

스케줄러(PL-2D3184BC, minicore/kernel/scheduler.cpp)는 이미 "코어
개수만큼의 배열 + `Scheduler::currentCoreIndex()`로 인덱싱"하는
패턴을 여러 번 손으로 반복 구현했다 - `gCurrentTask[coreIndex]`,
`gPreemptDisableCount[coreIndex]`, `gCleanupQueues[coreIndex]`,
`gImmediateQueues`/`gRtQueues`/`gNormalQueues[coreIndex]`,
`gIdleSavedRsp[coreIndex]`(전부 `kMaxCores = kAcpiMaxCpus` 크기).
Slab 할당자(SP-D7013B26)의 코어별 매거진도 같은 성격이다. 이 §12는
이 반복 패턴을 재사용 가능한 프리미티브로 공식화한다.

### 12.2 설계 - `PerCpu<T>`

```cpp
// minicore/libs/libkenv, 가칭 percpu.h
template <typename T>
class PerCpu {
public:
    // 이 코어(호출 시점의 Scheduler::currentCoreIndex())의 값에
    // 대한 참조.
    T& get() { return _values[Scheduler::currentCoreIndex()]; }

    // 다른 코어의 값을 들여다봐야 할 때(예: 로드밸런싱 판단,
    // 진단/디버깅) 쓴다 - 동시성 보호는 T 자신의 책임이다(PerCpu는
    // 배열 인덱싱만 제공, 락을 걸어주지 않는다).
    T& forCore(uint32_t coreIndex) { return _values[coreIndex]; }

private:
    T _values[kMaxCores];  // scheduler.h의 kMaxCores(=kAcpiMaxCpus) 재사용
};
```

기존 스케줄러의 손으로 짠 배열들(`gCurrentTask` 등)은 이미 동작
검증된 코드이므로 **이 설계 때문에 지금 당장 재작성하지 않는다** -
순수 리팩터링 목적만으로 검증된 코드를 건드리지 않는다는 일반
원칙(변경 최소화)에 따라, 새로 만드는 서브시스템(§10의 AsyncMutex
내부 상태 등 코어별로 나눠야 할 것이 생기면, TLS 슬롯 레지스트리
등)부터 `PerCpu<T>`를 쓰기 시작하고, 스케줄러 쪽은 그 파일을 어차피
다른 이유로 손댈 자연스러운 기회에 정리한다.

### 12.3 성능 - `currentCoreIndex()`의 비용

`Scheduler::currentCoreIndex()`(scheduler.cpp)는 `Lapic::id()`를
읽은 뒤 `Acpi::cpuApicId(i)`와 순서대로 비교하는 **O(코어 수) 선형
스캔**이다 - 코어 수가 적을 땐(수십 개 미만) 무시할 만하지만,
`PerCpu<T>::get()`이 핫 패스(예: 매 `AsyncMutex::lock()` 시도, 매
Slab 할당)에서 반복 호출되면 누적 비용이 실측으로 문제가 될 수
있다.

### 12.4 아직 열려 있는 하위 과제

1. **[구체화, 2026-09-15] 코어 인덱스 캐싱**: 실제 소스
   (`Scheduler::currentCoreIndex()`, scheduler.cpp)를 확인하면
   `Lapic::id()`를 얻은 뒤 `Acpi::cpuCount()`만큼 `cpuApicId(i)`와
   선형 비교하는 **실제 O(n) 스캔**이다 - §12.2의 `PerCpu<T>::get()`이
   호출마다 이 함수를 부르고, 이제 §15/§16(`TaskLocal<T>`/
   `AsyncLocal<T>`/`ReentrantMutex`)이 전부 `PerCpu<T>` 위에 얹히므로
   "실측으로 필요성이 확인되면"이라는 조건이 사실상 이미 충족된
   상태다(핫 패스가 될 구조적 소비자가 여럿 확정됨) - "실측 후
   결정"을 넘어 지금 설계를 제안한다:

   **채택 제안: `IA32_TSC_AUX` 경로**(`GS_BASE` 방식 대신) - 이유는
   (a) 이 코드베이스가 syscall 고속 경로(`SyscallFastPath`,
   PN-124C105B 5차 증분)에서 이미 `KERNEL_GS_BASE`를 다른 용도
   (커널 스택 스왑)로 쓰고 있어 `GS_BASE`를 코어 인덱스 조회에도
   같이 쓰면 두 용도가 뒤섞이고, (b) `rdtscp`는 메모리 접근이 아예
   없는 순수 명령어 하나(GPR만 바뀜)라 캐시 미스 가능성조차 없다.

   ```cpp
   // 부팅 시 코어별로 한 번(SyscallFastPath::initForThisCore()와
   // 같은 자리 - Gdt::loadTssForThisCore() 직후) - 이 코어의
   // Scheduler::currentCoreIndex()가 원래 계산하던 값을 그대로 한
   // 번만 계산해 MSR에 심어 둔다.
   void kInitCoreIndexForThisCore(uint32_t coreIndex) {
       kWrMsr(kMsrTscAux, coreIndex);  // IA32_TSC_AUX = 0xC0000103
   }

   // Scheduler::currentCoreIndex() 교체 - 매번 선형 스캔 대신 1개
   // 명령어.
   uint32_t Scheduler::currentCoreIndex() {
       uint32_t aux;
       __asm__ volatile("rdtscp" : "=c"(aux) :: "rax", "rdx");
   ```

## 13. Mutex/Semaphore 공통 코어 재정리 (승인 완료, 2026-09-14,
    QU-0A7D5AAE/SP-5A255B7C §5 반영) — **[구현 완료, PN-F5B33BE2, 커밋 70fb2ae, 2026-09-15]**

**[갱신, 2026-09-15] 중대 정정 - 이 §13 전체는 이미 실제 코드로
구현·검증 완료됐다**(설계자 지시 "계획에 완료된 것들이 섞여있는데
조사해봐"로 발견) - `minicore/kernel/{waitable.h, wait_queue.h/.cpp,
mutex_core.h, semaphore_core.h}`(계획 PN-F5B33BE2). 그런데 실제
소스(`mutex_core.h`, 아래 갱신된 코드 참고)는 아래 원래 코드 블록과
**API 형태가 다르다** - `tryAcquireOrKeepLock()` + `BasicMutex::lock()`
의 for-루프라는 2단계 구조 대신, `MutexCore::lock(OnContended&&
onContended)` **템플릿 콜백 하나**가 확인+재시도 루프 전체를 안에서
직접 돈다(원자성 확보 방식은 동일 - `_guard`를 쥔 채로 `onContended`를
부르고, `onContended`가 그 안에서 락을 넘겨받아 해제). 이는 §16
(`ReentrantMutex`)을 설계할 당시 이 문서의 (당시엔 아직 실제 구현과
대조되지 않은) 원문 스케치를 그대로 따라간 결과, §16도 같은 구식
API 형태로 설계돼 실제 코드와 어긋나 있었다 - §16.1을 아래에서 함께
정정했다. 원문 스케치는 "무엇이 왜 바뀌었는지" 기록 가치가 있어
삭제하지 않고 남겨 두되, **실제 코드는 이 문단 바로 아래 새
코드블록을 따른다**:

```cpp
// minicore/kernel/mutex_core.h - 실제 구현(2026-09-15 소스 대조 확인)
namespace kernel {

class MutexCore {
public:
    void init() { _locked = false; }

    // 확인+대기 등록을 한 번의 _guard 보유 구간 안에서 수행 - onContended가
    // 그 안에서 guard.unlock()까지 책임진다(원자성 확보, 아래 참고).
    template <typename OnContended>
    void lock(OnContended&& onContended) {
        for (;;) {
            _guard.lock();
            if (!_locked) {
                _locked = true;
                _guard.unlock();
                return;
            }
            onContended(_guard);
        }
    }

    bool tryAcquire() {
        SpinlockGuard guard(_guard);
        if (_locked) return false;
        _locked = true;
        return true;
    }

    template <typename NotifyFn>
    void release(NotifyFn&& notifyOne) {
        SpinlockGuard guard(_guard);
        _locked = false;
        notifyOne();
    }

private:
    Spinlock _guard;
    bool _locked = false;
};

// onContended(Spinlock&)는 SpinlockGuard&가 아니라 원시 Spinlock&를 받는다.
struct ParkingPolicy {
    WaitQueue waitQueue;
    void onContended(Spinlock& guard) { waitQueue.parkCurrentAndUnlock(guard); }
    void onRelease() { waitQueue.wakeOne(); }
};

struct YieldingPolicy {
    void onContended(Spinlock& guard) {
        guard.unlock();
        AsyncTask::yield();
    }
    void onRelease() { /* 대기열 없음 */ }
};

template <typename Policy>
class BasicMutex {
public:
    void lock() {
        _core.lock([this](Spinlock& guard) { _policy.onContended(guard); });
    }
    void unlock() {
        _core.release([this] { _policy.onRelease(); });
    }
    bool tryLock() { return _core.tryAcquire(); }

private:
    MutexCore _core;
    Policy _policy;
};

using Mutex = BasicMutex<ParkingPolicy>;
using AsyncMutex = BasicMutex<YieldingPolicy>;

}  // namespace kernel
```

`SemaphoreCore`/`BasicSemaphore`/`Semaphore`/`AsyncSemaphore`도
`minicore/kernel/semaphore_core.h`로 **이미 구현 완료**(동일한
`ParkingPolicy`/`YieldingPolicy` 재사용, `MutexCore`와 완전히 동형인
`acquire(OnContended&&)`/`tryAcquire()`/`release(NotifyFn&&)`) -
아래 문단의 "PN-A64F56AC가 실제 구현을 미뤄 뒀다"는 서술은 더 이상
사실이 아니다. `Waitable`/`WaitQueue::cancel()`도 구현·검증
완료됐으나 Signal 인프라(PN-71E50394)가 아직 없어 호출부가 없는
채로 대기 중(dead code 아님 - 연결만 기다림).

QEMU PVH+SMP4에서 커널 Task 2개가 `Mutex` 하나로 400000회 경합
카운터 증가 테스트를 통과(유실/경쟁 없음) - PN-F5B33BE2 참고.

---

**원문 스케치(2026-09-15 QU-707024C0 수정 직후, 실제 구현 착수 전
버전 - 위 실제 코드와 API 형태가 다름, 기록 보존용)**:

§2/§3(`Mutex`/`Semaphore`)과 §10(`AsyncMutex`/`AsyncSemaphore`)이
경합 시 동작(파킹 vs yield)만 다를 뿐 상태/빠른 경로가 사실상 같은
코드를 반복하고 있다는 §10.4-3의 지적에 대해, SP-5A255B7C §5가
평가한 대로 **"동기가 비동기를 wrap"하는 방향은 채택하지 않는다**
(SP-5A255B7C §4의 성능/순환의존 문제) - 대신 공통 코어를 뽑고 경합
정책만 주입하는 구조로 확정한다:

**[수정, 2026-09-15, QU-707024C0 답변 반영]** 최초 초안의 `tryAcquire()`가
자기 안에서 Spinlock을 열고 닫아 버려, "잠겨 있는지 확인"과 "대기열에
스스로를 매다는 것" 사이에 빈 창이 생기는 lost-wakeup 결함이 있었다
(unlock()이 그 창에 끼어들면 아직 대기열에 없는 Task를 못 깨움). 아래는
그 결함을 고친 최종 형태 - **확인과 대기 등록이 반드시 같은 Spinlock
임계구역 안에서 원자적으로 이어지도록**, Spinlock을 호출자(`BasicMutex::
lock()`)가 직접 들고 있다가 실패 시 그 `SpinlockGuard`를 살아있는 채로
Policy에 넘긴다(§1의 원래 계약 - `WaitQueue::parkCurrentAndUnlock(Spinlock&
guard)`가 "이미 그 락을 쥔 채로 호출돼야 한다" - 을 그대로 지킨다):

```cpp
// minicore/kernel, 가칭 mutex_core.h
namespace kernel {

// §2 Mutex/§10 AsyncMutex가 공유하는 상태 + 빠른 경로 - 경합 시
// 무엇을 하는지는 전혀 모른다(Policy가 결정). Spinlock 자체는 이제
// 호출자(BasicMutex::lock())가 SpinlockGuard로 들고 있는다 -
// MutexCore는 그 Spinlock이 보호하는 상태(_locked)만 갖는다.
class MutexCore {
public:
    void init() { _locked = false; }

    Spinlock& lockObject() { return _guard; }

    // 호출자가 이미 _guard를 쥔 상태(SpinlockGuard 생존 중)에서만
    // 호출한다. 성공(true)하면 그 SpinlockGuard는 호출자가 바로 놓아도
    // 안전하다. 실패(false)하면 **Spinlock을 놓지 않는다** - "확인"과
    // "대기열 등록" 사이에 빈 창을 만들지 않기 위해 그 책임을 그대로
    // 호출자(Policy)에게 넘긴다.
    bool tryAcquireOrKeepLock() {
        if (_locked) return false;
        _locked = true;
        return true;
    }

    // 다음 소유자를 직접 고르지 않는다(재경쟁 철학, §2.1 그대로) -
    // 상태만 풀고 통지는 Policy 몫. 이 함수 자신이 Spinlock을 잡는다
    // (unlock()은 항상 처음부터 Spinlock을 안 쥔 채로 호출되므로
    // tryAcquireOrKeepLock()과 달리 자체적으로 SpinlockGuard를 연다).
    template <typename NotifyFn>
    void release(NotifyFn&& notifyOne) {
        SpinlockGuard guard(_guard);
        _locked = false;
        notifyOne();
    }

private:
    Spinlock _guard;
    bool _locked = false;
};

// §1의 WaitQueue를 그대로 재사용하는 정책 - 완전한 kernel::Task를 재움.
// onContended()가 받는 guard는 BasicMutex::lock()이 이미 열어 둔,
// 아직 살아있는 SpinlockGuard다 - parkCurrentAndUnlock()이 §1의 계약
// 그대로 "이 함수 안에서 그 락을 풀고 파킹"하므로, MutexCore::
// tryAcquireOrKeepLock()의 실패 확인 시점부터 대기열 등록 시점까지
// Spinlock이 한 번도 풀리지 않는다(원자성 확보).
struct ParkingPolicy {
    WaitQueue waitQueue;
    void onContended(SpinlockGuard& guard) { waitQueue.parkCurrentAndUnlock(guard); }
    void onRelease() { waitQueue.wakeOne(); }
};

// §10.2의 yield 반복을 그대로 재사용하는 정책 - 리액터를 블로킹하지
// 않음. ParkingPolicy와 달리 대기열이 없어 원자성 요구 자체가 없으므로,
// 리액터를 계속 막지 않기 위해 yield 전에 Spinlock을 명시적으로 먼저
// 놓는다(SpinlockGuard::unlock() - 소멸자 전에 조기 해제하는 멱등
// 연산, 아직 없다면 이 설계의 선행 조건으로 추가).
struct YieldingPolicy {
    void onContended(SpinlockGuard& guard) {
        guard.unlock();
        AsyncTask::yield();
    }
    void onRelease() { /* 대기열 없음 - §10.2 그대로 */ }
};

template <typename Policy>
class BasicMutex {
public:
    void lock() {
        for (;;) {
            SpinlockGuard guard(_core.lockObject());
            if (_core.tryAcquireOrKeepLock()) return;   // guard는 스코프 종료 시 자동 해제
            _policy.onContended(guard);                  // 실패 시엔 guard가 살아있는 채로 여기 진입 - Policy가 해제 시점을 결정
        }
    }
    void unlock() {
        _core.release([this] { _policy.onRelease(); });
    }
    bool tryLock() {
        SpinlockGuard guard(_core.lockObject());
        return _core.tryAcquireOrKeepLock();
    }

private:
    MutexCore _core;
    Policy _policy;
};

using Mutex = BasicMutex<ParkingPolicy>;        // §2를 대체(시그니처 동일)
using AsyncMutex = BasicMutex<YieldingPolicy>;  // §10을 대체(시그니처 동일)

}  // namespace kernel
```

**§13.1 계약 요약**(QU-707024C0 답변으로 확정) - `MutexCore::
tryAcquireOrKeepLock()`이 `false`를 반환하는 순간부터 `Policy::
onContended(guard)`가 그 `SpinlockGuard`를 처리(해제)하는 순간까지
Spinlock은 절대 놓이지 않는다. 이 계약을 지키는 한 §1이 명시한
"확인과 대기열 등록의 원자성"이 그대로 유지되어, unlock()이 그
사이에 끼어들어도 대기자를 놓치는 lost-wakeup이 발생하지 않는다.

`Semaphore`/`AsyncSemaphore`(§3/§10)도 `SemaphoreCore`(카운트 상태 +
동일한 두 Policy)로 동일하게 재정리한다 - 구체적인
`SemaphoreCore` 코드는 `MutexCore`와 거의 동형이라 이 문서에서
반복하지 않는다(실제 구현 착수 시점에 작성, PN-A64F56AC). **반드시
§13.1 계약(`tryAcquireOrKeepLock` 스타일 - 확인 실패 시 Spinlock을
놓지 않고 그대로 Policy에 넘김)을 그대로 따라야 한다** - `MutexCore`의
수정 전 형태(QU-707024C0이 지적한, 확인과 대기열 등록 사이에 Spinlock을
놓아버리는 버전)를 그대로 베껴 옮기지 않도록 주의.

**이 재정리는 §2/§3/§10이 확정한 동작(재경쟁 철학, `WaitQueue`/
yield 분기, `Waitable::cancel()` 연동)을 하나도 바꾸지 않는다** -
호출부(§7 유저 페이지 폴트 재개, §9 강제 취소 등)가 참조하는
`Mutex`/`Semaphore`/`AsyncMutex`/`AsyncSemaphore` 타입 이름과
`lock`/`unlock`/`tryLock`/`acquire`/`release`/`tryAcquire` 시그니처는
그대로 유지된다 - 순수 내부 구현 리팩터링이다. **재진입(§5-5)
문제는 이 재정리와 별개로 남는다** - `MutexCore`에 소유자 필드를
추가하는 확장 지점은 있으나(PN-4D60D49C), 이번 재정리 자체가 그
결함을 해결하지는 않는다.

**[갱신, 2026-09-15] 이 문단은 더 이상 사실이 아니다** - 당시엔
"아직 코드로 구현돼 있지 않다"가 맞았지만, 그 직후 PN-F5B33BE2로
실제 구현이 완료됐다(위 "구현 완료" 코드블록 참고) - 단 실제 구현은
이 원문 스케치를 문자 그대로 베끼지 않고 `tryAcquireOrKeepLock()`
2단계 구조 대신 `lock(OnContended&&)` 콜백 1단계 구조로 API를
다듬었다(원자성 보장 방식 자체는 동일). 이 스케치는 "왜/어떻게
바뀌었는지"의 기록으로만 남긴다.

## 14. Mutex 재진입(Recursive) 안전성 (§5-5/PN-4D60D49C 해소 - 설계 제안, 2026-09-15)

**착수 조건 재확인**: PN-4D60D49C는 "MutexCore에 소유자 추적을
추가할지는 스케줄러가 더 진척된 뒤 재검토"로 미뤄 뒀다 - 그 선행
조건(PN-2ADA2AA7, §13 승인)은 이미 충족됐고, 스케줄러(PL-2D3184BC)
자체도 self-terminate/CR3 동기화 통합/Signal 전달 설계까지 진행되며
크게 성숙했다. 아래는 그 재검토를 실제로 진행한 설계 제안이다 -
**최종 확정은 아니며 설계자 확인이 필요**(아래 질의 참고).

### 14.1 핵심 문제 - "소유자"의 정의가 Policy마다 다르다

§13의 `MutexCore`에 단순히 "소유자 Task*" 필드를 추가하는 것만으로는
부족하다 - `Mutex`(`ParkingPolicy`)와 `AsyncMutex`(`YieldingPolicy`)는
"누가 잠갔는가"의 단위 자체가 다르기 때문이다:

- **`Mutex`(동기, kernel::Task 기반)**: 호출 스레드는 항상 하나의
  `kernel::Task`다 - `Scheduler::currentTask()`로 언제든 조회 가능한
  전역 상태이므로 소유자 식별이 자명하다.
- **`AsyncMutex`(비동기, AsyncTask 기반)**: 같은 `kernel::Task`(리액터)
  위에서 **서로 다른 여러 AsyncTask가 인터리빙**돼 실행된다
  (`AsyncTaskHandler::onExec(AsyncTask* task, ...)`가 그 AsyncTask를
  매개변수로 받는 구조 그대로 - 전역 "현재 AsyncTask" 접근자는 이
  코드베이스에 없다). `Scheduler::currentTask()`(리액터의 kernel::Task)를
  소유자로 쓰면 **같은 리액터에서 실행되는 서로 무관한 두 AsyncTask를
  같은 소유자로 오인**해, 실제로는 별개인 두 번째 호출을 "재진입"으로
  잘못 허용해버리는 안전성 결함이 생긴다 - 이건 지금 고치려는
  데드락보다 더 나쁜 결과(상호 배제 자체가 깨짐)다.

### 14.2 설계 제안 - Policy가 "소유자 식별자"도 함께 정의한다

`MutexCore`를 소유자 타입에 대해 제네릭하게 만들고, 그 식별자를
"현재 호출자가 누구인지 알려주는" 방식도 Policy가 함께 책임지도록
확장한다:

```cpp
// minicore/kernel, 가칭 mutex_core.h (§13 확장)
namespace kernel {

// Mutex/AsyncMutex 재사용 - "동일 호출자의 재귀 호출"을 판별하는
// 불투명 식별자. Policy별로 실제 타입은 다르지만 항상 포인터 크기
// (동등 비교 가능한 값)로 통일한다.
using OwnerId = const void*;

class MutexCore {
public:
    void init() { _locked = false; _owner = nullptr; _recursionDepth = 0; }

    Spinlock& lockObject() { return _guard; }

    // owner==nullptr(§13 원래 동작, 비재진입 정책)이면 순수 §13
    // 그대로: 실패 시 Spinlock 유지, 성공 시 소유자 기록 없음.
    // owner!=nullptr(§14 재진입 정책)이면: (a) 안 잠겨 있으면 잠그고
    // owner를 기록, depth=1. (b) 이미 이 owner가 잠근 상태면 depth만
    // ++하고 성공 반환(재진입 - 대기열에 매달리지 않음). (c) 다른
    // owner가 잠근 상태면 §13과 동일하게 실패(Spinlock 유지).
    bool tryAcquireOrKeepLock(OwnerId owner = nullptr) {
        if (!_locked) {
            _locked = true;
            _owner = owner;
            _recursionDepth = 1;
            return true;
        }
        if (owner != nullptr && owner == _owner) {
            ++_recursionDepth;
            return true;
        }
        return false;
    }

    // depth를 내려 0이 될 때만 실제로 풀고 통지한다 - 재진입 중간
    // unlock()은 상태를 바꾸지 않는다(호출자가 lock()과 짝수/홀수로
    // 맞춰 부른다는 표준 재진입 뮤텍스 계약, 다른 커널/런타임과 동일).
    template <typename NotifyFn>
    void release(NotifyFn&& notifyOne) {
        SpinlockGuard guard(_guard);
        if (--_recursionDepth > 0) return;   // 재진입 중 - 아직 안 풀림
        _locked = false;
        _owner = nullptr;
        notifyOne();
    }

private:
    Spinlock _guard;
    bool _locked = false;
    OwnerId _owner = nullptr;
    uint32_t _recursionDepth = 0;
};

// Mutex(ParkingPolicy)의 소유자 식별자 - Scheduler::currentTask()는
// 항상 어디서든 조회 가능하므로 lock()/unlock() 시그니처를 바꿀
// 필요가 없다(§13과 동일하게 파라미터 없는 API 유지).
struct ParkingPolicy {
    WaitQueue waitQueue;
    static OwnerId currentOwner() {
        return static_cast<OwnerId>(Scheduler::currentTask());
    }
    void onContended(SpinlockGuard& guard) { waitQueue.parkCurrentAndUnlock(guard); }
    void onRelease() { waitQueue.wakeOne(); }
};

// AsyncMutex(YieldingPolicy)의 소유자 식별자 - 전역 "현재 AsyncTask"가
// 없으므로 **호출자가 자신의 AsyncTask*를 명시적으로 넘겨야 한다**
// (AsyncTaskHandler::onExec(AsyncTask* task, ...)가 이미 갖고 있는
// 값을 그대로 전달). §13의 파라미터 없는 AsyncMutex::lock()/unlock()
// 시그니처와 달라지는 유일한 지점 - 아래 §14.3 참고.
struct YieldingPolicy {
    void onContended(SpinlockGuard& guard) {
        guard.unlock();
        AsyncTask::yield();
    }
    void onRelease() { /* 대기열 없음 - §10.2 그대로 */ }
};

template <typename Policy>
class BasicMutex {
public:
    // owner를 안 넘기면(기본값 nullptr) §13 그대로 비재진입 동작 -
    // 기존 호출부(§7/§9 등)는 전부 무변경으로 계속 동작한다.
    void lock(OwnerId owner = nullptr) {
        for (;;) {
            SpinlockGuard guard(_core.lockObject());
            if (_core.tryAcquireOrKeepLock(owner)) return;
            _policy.onContended(guard);
        }
    }
    void unlock() { _core.release([this] { _policy.onRelease(); }); }
    bool tryLock(OwnerId owner = nullptr) {
        SpinlockGuard guard(_core.lockObject());
        return _core.tryAcquireOrKeepLock(owner);
    }

private:
    MutexCore _core;
    Policy _policy;
};

using Mutex = BasicMutex<ParkingPolicy>;
using AsyncMutex = BasicMutex<YieldingPolicy>;

}  // namespace kernel
```

### 14.3 호출 관례 - 재진입을 켜고 끄는 것은 호출자의 선택

재진입 추적은 **기본으로 켜져 있지 않다** - `lock()`을 인자 없이
부르면(§13과 동일한 기존 호출부 전부) `owner=nullptr`가 들어가
§13의 원래(비재진입) 동작 그대로다. 재진입 안전성이 필요한 호출부만
명시적으로 식별자를 넘긴다:

- `Mutex::lock(ParkingPolicy::currentOwner())` - 동기 경로, 인자
  없이도(`Scheduler::currentTask()`가 항상 조회 가능하므로) 헬퍼로
  감쌀 수 있다.
- `AsyncMutex::lock(static_cast<OwnerId>(task))` - `task`는
  `AsyncTaskHandler::onExec`가 받은 그 `AsyncTask*` - **호출자가
  실수로 안 넘기면 조용히 비재진입 모드로 동작**(nullptr 기본값) -
  이 조용한 폴백이 바람직한지, 아니면 재진입이 필요한 Mutex는
  타입 자체를 분리(`ReentrantMutex`/`ReentrantAsyncMutex`)해 실수로
  안 넘기면 컴파일 에러가 나게 할지는 §14.4 질의 참고.

### 14.4 확정 필요 - 설계자 확인 요청

1. **API 시그니처 변경 허용 여부**: `AsyncMutex::lock()/tryLock()`에
   `OwnerId owner` 파라미터가 추가된다(기본값 있어 하위 호환은
   되지만, §13이 "타입 이름과 시그니처는 그대로 유지"라고 명시한
   것과는 다른 지점) - 재진입 문제 해소에 불가피한 변경으로 보이나
   확인 필요.
2. **기본값 nullptr의 "조용한 비재진입 폴백"이 안전한가**: 위 §14.3
   참고 - 실수로 식별자를 빠뜨리면 컴파일 에러 없이 그냥 데드락
   가능성이 그대로 남는다. 타입을 분리해 강제하는 대안도 있다.
3. **`Semaphore`/`AsyncSemaphore`에도 같은 패턴 적용 여부**: 세마포어는
   개념적으로 "소유자"가 없는 카운팅 프리미티브라(뮤텍스와 달리 여러
   Task가 동시에 획득 가능) 재진입이라는 개념 자체가 자연스럽지
   않다 - 적용 안 함이 기본이라고 보지만 명시적 확인 필요.

DC 없이 임의로 확정하지 않고 질의로 등록해 둔다(RM-23F4B687 §4
원칙, CLAUDE.md 규칙 4).

**[갱신, 2026-09-15] QU-AD1A3CC0 답변 반영 - 위 §14.2/§14.3의
"명시적 `OwnerId` 파라미터" 접근은 폐기, §15/§16으로 대체**. 설계자
답변 요지: (1) `AsyncMutex::lock()`에 파라미터를 추가하는 대신 Per-CPU/
Per-Task Variable(§11/§12)을 응용해 범용 `AsyncLocal<T>`를 먼저 설계하고
그걸로 소유자를 암묵적으로 추적하라 - "이쪽이 범용성이 더 높다", (2)
타입을 `ReentrantMutex`/`ReentrantAsyncMutex`로 분리해 실수로 식별자를
안 넘기면 컴파일 에러가 나도록 강제(§14.4 항목 2 그대로 채택), (3)
Semaphore 적용 여부는 "소유자 개념이 1번으로 해소될 테니 다시 고려".
아래 §15가 `AsyncLocal<T>`를, §16이 이를 사용하는 최종
`ReentrantMutex`/`ReentrantAsyncMutex`/`ReentrantSemaphore` 설계를
담는다 - 이번 섹션(§14.1/§14.2/§14.3)의 `OwnerId` 파라미터 방식은
더 이상 채택되지 않는다(비교 대상으로 남겨 둠 - 무엇이 왜 바뀌었는지
기록 가치가 있어 삭제하지 않음).

## 15. `AsyncLocal<T>` - AsyncTask 단위 지역 변수 (§11.3이 예고한 확장, 설계 제안, 2026-09-15)

### 15.1 배경 - §11 `ThreadLocal<T>`과 같은 패턴을 `AsyncTask` 단위로

§11.3은 "`AsyncTask` 자체에 유사한 슬롯이 필요해지면 별도 슬롯 배열을
`AsyncTask` 구조체에 추가하는 형태로 검토"라고 미리 예고해 뒀다 -
§14의 재진입 Mutex 소유자 추적(QU-AD1A3CC0 답변)이 바로 그 실제
필요가 됐다. §11의 `TlsRegistry`/`ThreadLocal<T>` 패턴(부팅 시 슬롯을
한 번 발급받아 재사용, RM-48E1E610/SP-F682B889 §3.1과 동일 관례)을
그대로 `AsyncTask` 단위에 적용한다.

### 15.2 [갱신, 2026-09-15, QU-21DB42F9 답변 반영] `TaskLocal<T>` - `PerCpu<T>` 기반 "현재 실행 단위" 추적으로 통일

당초 제안(전용 `AsyncTask::current()` 정적 접근자를 새로 만드는 안)은
설계자 답변으로 대체됐다 - **"AsyncTask도 Task의 일종"이라는 관점에서,
전용 접근자를 따로 만들지 않고 §12의 `PerCpu<T>`를 그대로 활용하는
범용 `TaskLocal<T>` 프리미티브를 먼저 정의**하고, 그 위에 "지금 이
코어에서 실행 중인 AsyncTask"를 얹는 방식으로 통일한다. 설계자 원문:
"현재 Task가 무엇인지 보고, 이걸로 TaskLocal<T>로 어떤 AsyncTask가
진행중인지 보고, 거기서 또 비동기 작업이 전환되는 간극마다 셋팅하면
돼" - 그리고 "TaskLocal은 나중에 ThreadLocal Variable(§11)을
구현하기 위해 사용될 수 있어"(지금 §11을 다시 쓰라는 요구는 아님 -
장래에 §11의 `Scheduler::currentTask()` 의존을 `TaskLocal<Task*>`로
통일할 수도 있다는 방향성 표시로만 기록해 둔다, RM-23F4B687의 "검증된
코드는 순수 리팩터링 목적만으로 건드리지 않는다" 원칙과 동일하게
지금은 §11을 그대로 둔다).

```cpp
// minicore/libs/libkenv, 가칭 tasklocal.h - §12 PerCpu<T> 바로 위의
// 얇은 계층. PerCpu<T> 자신은 "코어별로 독립된 값"이라는 뜻만 가질
// 뿐 "무엇이 지금 실행 중인가"라는 의미를 모른다 - TaskLocal<T>는
// 그 의미(디스패치 경계마다 갱신되는 "현재 단위" 포인터)를 명명한
// 별칭 계층일 뿐, 저장 자체는 PerCpu<T> 그대로 재사용한다.
template <typename T>
using TaskLocal = PerCpu<T>;

// "지금 이 코어에서 실행 중인 AsyncTask" - 이 하나의 전역 인스턴스가
// §15.3의 AsyncLocal<T>가 의존하는 유일한 "현재 단위" 소스다.
// minicore/kernel, AsyncTask 쪽(SP-F682B889)이 소유.
extern TaskLocal<AsyncTask*> gCurrentAsyncTask;

// 편의 정적 래퍼 - AsyncLocal<T>/그 외 호출부가 매번
// gCurrentAsyncTask.get()을 직접 안 써도 되게.
class AsyncTask {
public:
    static AsyncTask* current() { return gCurrentAsyncTask.get(); }
    // ...
};
```

**갱신 시점(비동기 작업이 전환되는 간극)**: 리액터가 어떤
`AsyncTask`의 `onExec()`를 호출하기 직전에 `gCurrentAsyncTask.get() =
task`로 세팅하고, 반환 직후(또는 §10.3의 yield로 제어가 리액터
루프로 돌아온 직후) 이전 값(보통 nullptr - 리액터 자신은 AsyncTask가
아니므로)으로 복원한다 - `Scheduler::currentTask()`가
`kContextSwitch`/`kTaskStartTrampoline` 경계에서만 갱신되는 것과
정확히 같은 자리(디스패치 경계)에서만 갱신되므로 중첩 걱정이 없다
(한 코어에서 한 번에 정확히 하나의 `AsyncTask::onExec()`만 실행
중). **이 갱신 코드 자체는 SP-F682B889가 소유한 AsyncReactor
디스패치 루프에 속한다** - 정확히 어느 지점인지는 그 문서가 확정.

### 15.3 설계 - `AsyncLocal<T>` 슬롯 배열 (§11.2와 동형, 슬롯 수 조정)

```cpp
// minicore/kernel, 가칭 async_local.h
namespace kernel {

using AsyncLocalSlotIndex = uint32_t;
// [갱신, 2026-09-15, QU-21DB42F9 답변] AsyncTask는 실행 빈도가 Task
// 보다 훨씬 높고 잠재적 소비자도 많다는 판단으로 §11의 16이 아니라
// 64로 확정.
constexpr uint32_t kMaxAsyncLocalSlots = 64;

class AsyncLocalRegistry {
public:
    static AsyncLocalSlotIndex allocateSlot();  // 부팅/초기화 시 1회
};

template <typename T>
class AsyncLocal {
public:
    explicit AsyncLocal(AsyncLocalSlotIndex slot) : _slot(slot) {}

    T* get() const {
        return static_cast<T*>(AsyncTask::current()->localSlots[_slot]);
    }
    void set(T* value) {
        AsyncTask::current()->localSlots[_slot] = value;
    }

private:
    AsyncLocalSlotIndex _slot;
};

}  // namespace kernel
```

`AsyncTask`(SP-F682B889 §3.2가 소유하는 구조체) 필드 추가 확정:

```cpp
// AsyncTask 구조체에 추가 (§11.2의 Task::tlsSlots와 동형, 크기만 64)
void* localSlots[kMaxAsyncLocalSlots] = { nullptr, /* ... */ };
```

### 15.4 문서 소유권 - SP-F682B889 반영 확정

QU-21DB42F9로 확인받은 대로, `AsyncTask::localSlots` 필드/
`gCurrentAsyncTask` 전역/디스패치 경계 갱신 코드는 `AsyncTask` 구조체
자체(SP-F682B889 §3.2)에 속하는 변경이라 실제 반영은 그 문서 쪽에서
진행한다 - `TaskLocal<T>`/`PerCpu<T>` 자체는 이 문서(SP-0666DB3C
§12)가 정의하므로 SP-F682B889는 이 §15.2의 `extern TaskLocal<AsyncTask*>
gCurrentAsyncTask;` 선언과 그 갱신 지점만 실제 코드에 반영하면 된다.

## 16. `ReentrantMutex`/`ReentrantAsyncMutex` 최종 설계 (§14 대체, `AsyncLocal<T>` 기반, 설계 제안, 2026-09-15)

### 16.1 타입 분리 - 컴파일 타임에 재진입 지원 여부를 강제

QU-AD1A3CC0 답변 (2)를 그대로 채택 - "조용한 nullptr 폴백"(§14.3의
접근) 대신, §13의 `BasicMutex<Policy>`와 **완전히 별개인** 재진입
지원 템플릿을 만들어 실수로 재진입 추적을 빠뜨리면 그 자체가
컴파일 에러가 나게 한다:

**[갱신, 2026-09-15] 아래 코드는 원래 §13의 (구식) `tryAcquireOrKeepLock()`
스케치를 확장해 설계됐으나, §13이 실제로는 `lock(OnContended&&)`
콜백 1단계 구조로 구현돼 있음을 소스 대조로 확인해(PN-F5B33BE2)
**실제 `MutexCore`와 같은 형태로 다시 맞췄다** - 재진입 판정 로직/
소유자 추적 자체는 바뀌지 않았고, 순수하게 실제 `mutex_core.h`와
같은 API 관례를 따르도록 형태만 정정:

```cpp
// minicore/kernel, mutex_core.h 확장 (§13 이어서, 실제 MutexCore와 동일한 관례)
namespace kernel {

// §13의 MutexCore와 달리 항상 소유자를 추적한다 - "소유자 없음"
// 모드 자체가 없다(그게 §13의 BasicMutex/MutexCore 몫).
class ReentrantMutexCore {
public:
    void init() { _locked = false; _owner = nullptr; _recursionDepth = 0; }

    // 실제 MutexCore::lock()과 동일한 콜백 루프 구조 - _guard를 쥔 채로
    // onContended를 부르고, onContended가 그 안에서 guard.unlock()까지
    // 책임진다(원자성 확보 방식 동일).
    template <typename OnContended>
    void lock(const void* owner, OnContended&& onContended) {
        for (;;) {
            _guard.lock();
            if (!_locked) {
                _locked = true;
                _owner = owner;
                _recursionDepth = 1;
                _guard.unlock();
                return;
            }
            if (owner == _owner) {
                ++_recursionDepth;
                _guard.unlock();
                return;
            }
            onContended(_guard);
        }
    }

    template <typename NotifyFn>
    void release(NotifyFn&& notifyOne) {
        SpinlockGuard guard(_guard);
        if (--_recursionDepth > 0) return;
        _locked = false;
        _owner = nullptr;
        notifyOne();
    }

private:
    Spinlock _guard;
    bool _locked = false;
    const void* _owner = nullptr;
    uint32_t _recursionDepth = 0;
};

// 동기 재진입 뮤텍스 - 소유자는 Scheduler::currentTask()(항상 어디서든
// 조회 가능), lock()/unlock() 시그니처는 §13의 Mutex와 동일하게
// 파라미터 없이 유지된다(내부에서 currentTask()를 알아서 읽으므로
// AsyncMutex와 달리 API 변경이 필요 없다).
class ReentrantMutex {
public:
    void lock() {
        const void* owner = Scheduler::currentTask();
        _core.lock(owner, [this](Spinlock& guard) { _waitQueue.parkCurrentAndUnlock(guard); });
    }
    void unlock() { _core.release([this] { _waitQueue.wakeOne(); }); }

private:
    ReentrantMutexCore _core;
    WaitQueue _waitQueue;
};

// 비동기 재진입 뮤텍스 - 소유자는 §15의 AsyncLocal<T> 인프라가 만드는
// AsyncTask::current()로 조회한다(YieldingPolicy와 마찬가지로 대기열이
// 없어 원자성 요구 자체가 없다 - 확인 실패 시 바로 yield).
// **lock()/unlock() 시그니처도 파라미터 없이 유지** - §14가 제안했던
// "명시적 OwnerId 파라미터"는 AsyncTask::current()로 완전히
// 대체되어 더 이상 필요 없다(QU-AD1A3CC0가 지적한 API 변경 우려
// 자체가 해소됨).
class ReentrantAsyncMutex {
public:
    void lock() {
        const void* owner = static_cast<const void*>(AsyncTask::current());
        _core.lock(owner, [](Spinlock& guard) {
            guard.unlock();
            AsyncTask::yield();
        });
    }
    void unlock() { _core.release([] {}); }

private:
    ReentrantMutexCore _core;
};

}  // namespace kernel
```

`§13`의 `Mutex`/`AsyncMutex`(비재진입, 기본)와 이 `ReentrantMutex`/
`ReentrantAsyncMutex`(재진입)는 **완전히 다른 타입**이다 - 호출부가
재진입이 필요한지 스스로 판단해 선언 시점에 타입을 고른다(런타임
분기 없음, §13의 비재진입 경로는 소유자 추적 오버헤드를 전혀 지지
않는다는 이점도 유지된다).

### 16.2 `Semaphore`는 재진입 대상에서 제외 (QU-AD1A3CC0 답변 (3) 반영)

§14.4-3이 예상한 대로, "소유자" 개념이 `AsyncLocal<T>`/`ReentrantMutex`
쪽으로 옮겨가며 재확인한 결론은 동일하다 - **세마포어는 이 패턴을
적용하지 않는다**. 뮤텍스는 "정확히 하나의 소유자가 반복 호출"이라는
재진입 개념이 자연스럽지만, 세마포어는 카운트가 N이면 최대 N개의
*서로 다른* Task/AsyncTask가 동시에 보유하는 것이 정상 동작이라
"소유자가 자기 자신을 다시 획득"이라는 개념 자체가 없다 - 같은
Task/AsyncTask가 세마포어를 두 번 `acquire()`하면 그냥 카운트를
두 번 정상 소비하는 것이지 재진입이 아니다. `Semaphore`/
`AsyncSemaphore`는 §13 그대로 유지, `ReentrantSemaphore`류는
만들지 않는다.

3. §16.2(`Semaphore`는 재진입 대상에서 제외) - **승인**.

## 17. 유저 syscall 노출 - Mutex/Semaphore (설계자 지시, 2026-09-16,
"[SP-83A07867] 여기에 범위 밖으로 표기된 것들도 설계 시작해")

SP-83A07867 §7이 명시적으로 범위 밖(별도 계획)으로 남겨 둔 "Mutex/
Semaphore 등 실제로 parkCurrent/yieldCurrent를 쓰는 유저 syscall
자체의 설계"를 다룬다. §13의 커널 레벨 구현(PN-F5B33BE2, 완료)은
이미 있으므로, 이 절은 그걸 유저랜드에 어떤 syscall로 노출할지만
설계한다.

### 17.1 핵심 결정 - 유저 syscall은 반드시 `AsyncMutex`/`AsyncSemaphore`
(YieldingPolicy)만 쓴다, `Mutex`/`Semaphore`(ParkingPolicy)는 쓸 수 없다

**왜 선택의 여지가 없는가**: SP-04EE2A18의 syscall 디스패치 모델에서
모든 syscall 핸들러(`AsyncTaskHandler::onExec`)는 **코어별 공유
리액터(AsyncReactor)의 Task 위에서 실행된다** - 그 코어의 유일한
리액터 Task가 그 코어의 모든 syscall(과 그 밖의 모든 AsyncTask)을
차례로 처리한다. `Mutex`(ParkingPolicy)의 `OnContended`는 **호출한
Task 자체**를 `parkCurrent()`로 재운다(§13) - syscall 핸들러 안에서
이걸 쓰면 그 코어의 리액터 Task 전체가 멈춰 **그 코어의 다른 모든
대기 중인 syscall/AsyncTask까지 전부 같이 멈춘다**(치명적 - 한 유저
프로세스의 Mutex 경합이 무관한 다른 프로세스들의 syscall까지 막아
버림). 따라서 `AsyncMutex`(YieldingPolicy - `OnContended`가 Task가
아니라 **그 AsyncTask 자신만** `AsyncTask::yield()`로 리액터에게
돌려준다)만 안전하다 - 리액터는 그동안 다른 AsyncTask를 계속 처리할
수 있다. **유저에게는 이름 그대로 `Mutex`/`Semaphore`로 보이지만,
커널 내부 구현은 항상 `AsyncMutex`/`AsyncSemaphore`다** - 사용자
입장에서 "동기냐 비동기냐"를 선택할 필요가 없다(어차피 SP-04EE2A18의
모든 syscall이 이미 submit/wait 분리로 사용자에게 비동기처럼 보인다).

### 17.2 핸들 - [정정, 2026-09-17, PN-CE6A04AB] 더 이상 "포인터값 =
핸들" 관례가 아니다

**이 절 아래의 "Channel과 동일한 포인터값 관례" 서술은 낡았다** -
`PN-CE6A04AB`(실측 발견) 이후 `Channel`의 "포인터값 = ChannelId"
관례 자체가 **보안 취약점**으로 확인되어 폐기됐다: 유저 syscall이
넘긴 값을 검증 없이 `reinterpret_cast<T*>`로 역참조하면, 임의의
64비트 값을 넘긴 프로세스가 그 주소의 락/구조체를 건드리게 만들 수
있다(커널 패닉 또는 임의 주소 조작). `MutexHandle`/`SemaphoreHandle`
을 그대로 `UserMutex*`/`AsyncSemaphore*` 포인터값으로 설계하면
**Channel이 겪었던 것과 완전히 동일한 취약점**을 처음부터 갖고
태어난다 - 아직 구현 전(PN-E82744B1 미착수)이라 이번엔 실측 발견이
아니라 사전에 잡은 것이다.

**교체 방향**: `SP-9CB55C5B`(ProcessId)/`SP-CA3C3E57`(ChannelId)가
이미 두 번 확정한 것과 같은 **세대 태그 슬롯 테이블 + 안전한
resolve 함수** 패턴을 `MutexHandle`/`SemaphoreHandle`에도 그대로
적용한다 - `MutexCreate`/`SemaphoreCreate`가 슬롯 테이블에서 발급한
불투명 핸들을 돌려주고, `MutexLock`/`Unlock`/`SemaphoreWait`/`Post`
전부 그 핸들을 `kResolveMutexHandle()`류 함수로만 실제 포인터로
해석한다(직접 `reinterpret_cast` 금지). 아래 원문의 `UserMutex*`
"포인터값" 서술과 `MutexHandle = uint64_t; // UserMutex* 값` 주석은
이 새 관례로 교체돼야 한다 - 정확한 테이블 설계(공유 테이블 하나로
Mutex/Semaphore/Channel/Process를 전부 묶을지, 타입별로 따로 둘지
등)는 실제 착수(PN-E82744B1) 시점에 확정한다.

### 17.2(원문, 참고용 - 위 정정 적용 후엔 "포인터값" 부분만 낡음)

```cpp
// devmgr/fs 등이 만드는 프로세스간 공유 동기화 프리미티브 - Slab
// 할당(SP-D7013B26), 핸들은 그 구조체 자신의 포인터값(PL-21344323의
// Channel/토큰 관례 그대로 - 새 테이블 불필요).
//
// [갱신, 2026-09-16, QU-18A1D625 답변("커널 내부에서는 소유자가 있는
// 모든 타입에서 검증을 해야돼") 반영] Mutex는 개념상 소유자가 있는
// 타입이므로 §13 AsyncMutex 코어 자체(재진입 지원을 위해 일부러
// 비재진입 경로엔 소유자 추적을 안 붙이기로 한 결정, §13/§16)와는
// 별개로 이 syscall 레벨 래퍼가 마지막 lock 성공자의 ProcessId를
// 추가로 기억한다 - MutexCore를 건드리지 않고 소비자 계층에서만
// 검증을 추가하는 방식(§17.3/§17.4 참고).
struct UserMutex {
    kernel::AsyncMutex core;
    ProcessId owner = kInvalidProcessId;  // lock 보유 중이 아니면 무효값
};
using MutexHandle = uint64_t;      // UserMutex* 값(AsyncMutex* 아님 - 위 변경)
using SemaphoreHandle = uint64_t;  // AsyncSemaphore* 값 - Semaphore는 소유자
                                    // 개념 자체가 없어(§16.2) 그대로 유지.
```

**프로세스간 공유**: v1은 "프로세스당 스레드 하나"(SP-68182FBD)라
**같은 프로세스 안에서의 경합은 아직 존재할 수 없다** - 그렇다면
이 syscall들의 v1 실사용처는 **서로 다른 프로세스 간의 동기화**뿐이다
(예: devmgr이 스폰한 여러 드라이버 자식이 공유 자원에 접근할 때).
따라서 핸들 전달 메커니즘은 **ChannelId와 완전히 동일한 문제**이고
동일한 해법을 그대로 재사용한다 - PN-6D497EB0(Channel ID 전달)이
이미 다루는 "프로세스 생성 시 인자로 전달" 또는 `/sys/live/named/`
이름 기반 발견(SP-1FBC0EEB) 중 하나로 핸들 값을 공유한다. 새 전달
메커니즘을 이 문서가 따로 만들지 않는다.

### 17.3 Syscall API (SyscallRegistry, PL-21344323 패턴)

```cpp
// 생성 - 블로킹 없음(즉시 완료), 소유자는 없음(핸들을 아는 모든
// 프로세스가 동등하게 lock/unlock 가능 - Channel의 "이름 아는 사람은
// 누구나 connect 가능"과 같은 신뢰 모델, 별도 ACL 없음).
struct MutexCreateArgs { /* in: 없음 */ MutexHandle handle; };
struct MutexDestroyArgs { MutexHandle handle; ChannelError error; /* NotFound */ };

// lock/unlock - submit/wait 분리(SP-04EE2A18) 그대로. MutexLock은
// UserMutex::core.lock()을 그 syscall의 AsyncTask::onExec 안에서 호출 -
// 경합이 없으면 즉시 완료, 있으면 §17.1대로 AsyncTask::yield()로
// 리액터에 양보했다가 재개된다(호출한 유저 syscall 관점에서는 그냥
// "완료까지 시간이 걸리는 syscall" - waitForSyscall로 관찰). lock 성공
// 직후 onExec이 `handle->owner = callingProcessId`를 기록한다(§17.2).
struct MutexLockArgs { MutexHandle handle; ChannelError error; /* NotFound */ };
// [확정, 2026-09-16, QU-18A1D625] Unlock은 반드시 owner 검증한다 -
// onExec이 `handle->owner != callingProcessId`면 core.release()를
// 아예 호출하지 않고 NotOwner로 즉시 실패(락 상태 불변 유지). 검증
// 통과 시 core.release() 호출 후 `owner = kInvalidProcessId`로 리셋.
struct MutexUnlockArgs { MutexHandle handle; ChannelError error; /* NotFound / NotOwner */ };

struct SemaphoreCreateArgs { uint32_t initialCount; /* in */ SemaphoreHandle handle; };
struct SemaphoreDestroyArgs { SemaphoreHandle handle; ChannelError error; };
struct SemaphoreWaitArgs { SemaphoreHandle handle; ChannelError error; };  // acquire, 카운트 0이면 yield
struct SemaphorePostArgs { SemaphoreHandle handle; ChannelError error; };  // release
```

취소 처리(프로세스 종료 시 lock 대기 중이던 syscall)는 SP-04EE2A18
"종료 시 취소 처리"/PN-40E976F2(사망 전파 목록, 아직 미구현)가 이미
다루는 일반 메커니즘을 그대로 쓴다 - Mutex/Semaphore 전용 특수 취소
로직을 새로 만들지 않는다. **단, lock을 보유한 채로 죽으면 그 Mutex는
영원히 잠긴 채로 남는다(robust mutex 아님)** - v1은 이 실패 모드를
명시적으로 허용하지 않는다(RM-23F4B687 §4 원칙상 지금 결정할 필요
없는 세부는 아니고, 오히려 "커널 서비스가 죽으면 커널 패닉"(SP-EAB162FC
§6.4)류 상위 정책이 이미 이런 상황 자체를 드물게 만든다는 전제) -
필요해지면 별도 DC.

### 17.4 `MutexUnlock` 소유자 검증 - 확정 (QU-18A1D625 답변, 2026-09-16)

설계자 답변: "커널 내부에서는 소유자가 있는 모든 타입에서 검증을
해야돼." - Mutex는 개념상 소유자가 있는 타입이므로 검증이 필수로
확정됐다. §13의 `AsyncMutex` 코어 자체는 (재진입 정책과의 오버헤드
분리를 위해) 여전히 소유자를 추적하지 않지만, §17.2가 도입한
`UserMutex` 래퍼가 그 바깥에서 마지막 lock 성공자의 `ProcessId`를
기억해 `MutexUnlock`이 이를 검증한다(§17.2/§17.3 코드 참고) - "타입
자체(`AsyncMutex`)는 그대로 두고 소비자 계층에서 소유자 개념을
추가한다"는 이 설계의 방향이 그대로 유효하다는 뜻으로 해석했다(§16의
재진입 Mutex가 이미 같은 패턴 - 코어는 그대로, 그 위에 소유자 추적
계층을 얹음 - 을 썼으므로 일관됨).

**`Semaphore`는 이 규칙의 예외가 아니라 애초에 대상이 아니다** -
§16.2가 이미 확정한 대로 세마포어는 "복수의 서로 다른 소유자가
동시에 보유"하는 것이 정상 동작이라 소유자 개념 자체가 성립하지
않는다(설계자 답변의 "소유자가 있는 타입"이라는 조건 자체를 충족하지
않음) - `SemaphorePost`/`Wait`는 검증 없이 그대로 유지.
