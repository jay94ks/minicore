# 커널 동기화 프리미티브(Mutex/Semaphore) 및 Signal 전달 — 설계 제안

설계자 지시(2026-09-14, 메시지) - "세마포어, 뮤텍스, Signal등에 대한
설계도 해라." `Spinlock`(libkenv, 이미 구현 완료)은 "짧게 잡고 바로
푸는" 저수준 상호배제만 제공한다 - 대기 시간이 길어질 수 있는 진짜
동기화 프리미티브(자고 있다가 깨어남)는 아직 없다. 이 문서는
`Scheduler::parkCurrent()`(PL-2D3184BC 6단계, 이미 구현 완료 - "특정
이유로 블로킹 후 누군가 깨울 때까지 대기"하는 범용 프리미티브)를
기반으로 Mutex/Semaphore를 설계하고, 별도로 프로세스 대상 비동기
알림인 Signal 전달을 설계한다. **`스케줄러` 문서(PL-2D3184BC)에
연관 링크가 걸려 있다** - Mutex/Semaphore/폴트 재개 정책 전부가
그 문서의 스케줄링 프리미티브를 전제하기 때문이다(설계자 지시,
§5-5 참고).

페이지 폴트 재개 정책)의 '그 뒤 누가/언제 다시 깨우는지'가 아직
없었는데, 이전에 준 지침(공통 리스트를 두고 그게 비어야 블로킹을

**[수정, 2026-09-14, 설계자 재지시]** - "직접 핸드오프(Direct

§9로 대체된다.

## 1. 공통 기반 - 대기열(Wait Queue)

Mutex/Semaphore 둘 다 "지금 획득 못 하면 대기열에 매달렸다가, 나중에
누군가 그 중 하나를 깨워 재시도 기회를 준다"는 같은 패턴을 쓴다 -
`Task::next`(이미 있는 침습적 다음-포인터, 스케줄러 큐 전용이지만
**파킹된 Task는 어느 큐에도 없으므로 이 필드가 비어 있다** - 재사용
가능)로 간단한 FIFO를 구성한다. **`wakeOne()`이 깨우는 것은 "소유권을
넘겨받은 새 주인"이 아니라 "다시 한번 획득을 시도해 볼 기회를 얻은
후보"일 뿐**이라는 점이 §2.1에서 확정한 정책이다:

```cpp
// minicore/kernel, 가칭 wait_queue.h - Mutex/Semaphore가 공유하는 내부 헬퍼.
// Waitable을 구현해 §9의 강제 취소 메커니즘과 연동한다.
class WaitQueue : public Waitable {
public:
    // 현재 Task를 큐 꼬리에 매달고 파킹한다(Scheduler::parkCurrent
    // 호출 - 이 함수 자체가 반환하지 않고, 나중에 wakeOne()이나
    // §9의 cancel()이 이 Task를 다시 스케줄링해야 반환한다). 호출
    // 전에 반드시 상위 프리미티브(Mutex/Semaphore)의 Spinlock을
    // 잡고 있어야 하고, 이 함수 안에서 그 락을 풀고 파킹한다(락
    // 보유 중 파킹하면 다른 코어가 영원히 락을 못 잡음 - Mesa 모니터
    // 패턴). 파킹 직전 `task->blockedOn = this`를 설정한다(§9.2).
    // 반환 후에는 반드시 호출부가 조건을 재확인해야 한다(§2.1) -
    // "깨어났다"는 "획득했다"를 의미하지 않는다(강제 취소로 깨어난
    // 경우도 있음, §9.5).
    void parkCurrentAndUnlock(Spinlock& guard);

    // 큐 머리에서 하나 꺼내 그 Task가 파킹됐던 코어에서 즉시
    // 재개시킨다(Scheduler::scheduleImmediate 재사용 - 파킹된 Task는
    // 이중 스케줄링 걱정이 없다고 이미 문서화돼 있음). 이 Task가
    // 깨어나서 재시도했을 때 실패할 수 있다(다른 새 호출자가 먼저
    // 채갔을 경우, §2.1) - 그 경우 다시 파킹된다. 비어 있으면 아무
    // 일도 안 함.
    void wakeOne();

    bool isEmpty() const;

    // Waitable 구현(§9.3) - task가 이 큐 안에 있으면 리스트에서
    // 잘라내고 강제로 재개시킨다.
    bool cancel(Task* task, WaitCancelReason reason) override;

private:
    Task* _head = nullptr;
    Task* _tail = nullptr;
    // 각 Task가 파킹된 코어 인덱스를 어디에 저장할지는 §5-1의 열린
    // 질문 - v1은 Task 구조체 자체에 필드를 추가하는 것을 제안(§5-1).
};
```

## 2. Mutex

```cpp
// minicore/kernel, 가칭 mutex.h
class Mutex {
public:
    void init() { _locked = false; }

    // 재경쟁(wake-and-compete) 루프: Spinlock 아래에서 _locked가
    // false면 true로 바꾸고 즉시 반환(빠른 경로). true면(이미 잠겨
    // 있으면) 대기열에 매달려 파킹 - 깨어나도 소유권을 넘겨받은 게
    // 아니므로(§2.1) 루프 맨 앞으로 돌아가 다시 _locked를 확인한다
    // (졌으면 다시 파킹). 강제 취소로 깨어난 경우(§9)라면 재시도
    // 대신 인터럽트 에러를 반환하는 것을 제안(§9.6-3). **주의(§5-5):
    // 이 v1 구현은 재진입 안전하지 않다** - 이미 이 Mutex를 잠근
    // 바로 그 Task가 다시 lock()을 호출하면 자기 자신을 영원히
    // 대기시키는 데드락이 된다.
    void lock();

    // _locked = false로 바꾸고, 대기열에 누가 있으면 그 중 하나를
    // "재시도 기회"로만 깨운다(소유권을 넘기지 않는다, §2.1) - 그
    // 사이 다른 코어의 새 lock() 호출이 빠른 경로로 먼저 잠글 수
    // 있고, 그러면 깨어난 대기자는 재시도에 실패해 다시 파킹된다.
    void unlock();

    // 논블로킹 시도 - 실패해도 대기열에 매달리지 않고 즉시 false.
    bool tryLock();

private:
    Spinlock _guard;   // _locked/_waitQueue 자체를 보호하는 저수준 락(짧게만 보유)
    bool _locked = false;
    WaitQueue _waitQueue;
};
```

### 2.1 핸드오프(Direct Handoff) 대신 재경쟁(Wake-and-Compete) 방식을 쓰는 이유

**[수정, 2026-09-14, 설계자 재지시]** 이 문서는 처음에 `unlock()`이
다음 대기자를 직접 골라 소유권을 그대로 넘기는 **직접 핸드오프**
방식을 제안했었으나, 설계자가 "소유권을 unlock에서 고르는 것은
성능 손실이 더 크므로 다시 경쟁하게 두는 방식을 택해야 해"라고
지시함에 따라 **재경쟁(wake-and-compete)** 방식으로 교체한다.

핸드오프 방식의 문제: `unlock()`을 호출한 코어가 다음 대기자를
"정확히 그 Task"로 고정해 버리면, 그 대기자가 당장 실행 가능한
상태가 아니거나(다른 코어가 바쁘거나 스케줄 지연이 있으면) 그
사이에 **더 빨리 락을 쓸 수 있는 다른 새 호출자**가 있어도 무조건
그 특정 대기자가 깨어날 때까지 기다려야 한다(호위 효과, convoy
effect) - 이 지연이 직접 핸드오프가 절약하는 "재확인 로직 생략"
이득보다 실제로는 더 큰 성능 손실을 낸다는 것이 설계자의 판단이다.

**재경쟁 방식**은 `unlock()`이 그냥 상태만 풀어 놓고(`_locked =
false`/`_count++`), 대기열의 한 후보에게는 "다시 시도해볼 기회"만
주며, 그 사이 새로 `lock()`/`acquire()`를 호출하는 어떤 코어든
빠른 경로(Spinlock 아래 상태 확인 후 즉시 획득)로 먼저 채갈 수
있다 - 즉 **락은 항상 "그 순간 가장 먼저 확인하는 쪽"이 가져간다**.
대가로 깨어난 대기자가 재시도에 실패해 다시 파킹될 수 있다는
스퓨리어스 웨이크업 비용이 생기지만, 이는 호위 효과보다 훨씬 싸다고
판단(실측 후 재검토 대상, §5-2).

## 3. Semaphore

```cpp
// minicore/kernel, 가칭 semaphore.h
class Semaphore : public Waitable {
public:
    void init(uint32_t initialCount) { _count = initialCount; }

    // 재경쟁 루프: Spinlock 아래에서 카운트가 0보다 크면 즉시 차감
    // 후 반환(빠른 경로). 0이면 대기열에 매달려 파킹 - 깨어나도
    // 카운트를 넘겨받은 게 아니므로(§2.1과 동일 철학) 루프 맨
    // 앞으로 돌아가 다시 카운트를 확인한다(졌으면 다시 파킹).
    void acquire();

    // 카운트++ 후, 대기열에 누가 있으면 그 중 하나를 "재시도 기회"
    // 로만 깨운다(카운트를 직접 넘겨주지 않는다) - 그 사이 다른
    // 코어의 새 acquire() 호출이 먼저 채갈 수 있다.
    void release();

    bool tryAcquire();  // 논블로킹, 카운트가 0이면 즉시 false

    // Waitable 구현(§9.3) - 내부적으로 §1의 WaitQueue에 위임.
    bool cancel(Task* task, WaitCancelReason reason) override;

private:
    Spinlock _guard;
    uint32_t _count = 0;
    WaitQueue _waitQueue;
};
```

`Mutex`는 사실상 `Semaphore(initialCount=1)`의 특수형이지만, "누가
락을 쥐고 있는지"(재진입 감지, 소유자 오류 검출 등 후속 디버깅
기능의 여지)를 남겨 두기 위해 별도 타입으로 분리하는 것을 제안한다
(RM-23F4B687 §4 취지 - 지금은 숫자/타입 튜닝 수준의 결정). **Semaphore
는 애초에 "소유자"라는 개념이 없으므로(여러 스레드가 각기 카운트를
소비/반납) §5-5의 재진입 문제는 Mutex에만 해당한다.**

## 4. Signal 전달

### 4.1 범위 - 커널 쪽 플러밍만, 유저 핸들러 호출은 후속

SP-8B6B8D25 §2 11번("시그널 전파")이 이미 커널 책임으로 명시해 뒀다.
**유저 코드가 만든 시그널 핸들러를 ring3에서 실제로 호출하는 것**은
PN-124C105B(ring3 진입)가 아직 없어 이번 문서 범위 밖이다 - 이 문서는
"신호를 어떻게 커널 안에서 표현/전달/기본 처리하는지"까지만 다룬다.

### 4.2 신호 번호와 기본 동작

**[수정, 2026-09-14, 설계자 지시]** 신호 번호는 더 이상 이 문서가
임의로 정하지 않고, **RM-B5764185("Minicore Signal 번호표")** 의
번호를 그대로 사용한다(0=무효, 1~22/31=POSIX 표준과 동일) - 아래
enum 값은 그 표와 정확히 일치해야 한다:

```cpp
enum class SignalNumber : uint32_t {
    None = 0,          // 무효값 - 신호 없음

    Hup = 1,           // SIGHUP  - 터미널 세션 종료(주로 설정 리로드용)
    Int = 2,           // SIGINT  - 키보드 인터럽트(Ctrl+C)
    Quit = 3,          // SIGQUIT - 키보드 종료(Ctrl+\), 코어 덤프
    IllegalInstruction = 4,  // SIGILL  - 잘못된 머신 명령어(#UD 트랩 시 커널이 발생)
    Trap = 5,          // SIGTRAP - 디버깅 브레이크포인트 등
    Abort = 6,         // SIGABRT - abort() 등 비정상 종료 호출
    Bus = 7,           // SIGBUS  - 잘못된 메모리 주소 접근
    Fpe = 8,           // SIGFPE  - 산술 연산 오류(0 나누기 등)
    Kill = 9,          // SIGKILL - 즉시 강제 종료, 마스킹/무시 불가
    Usr1 = 10,         // SIGUSR1 - 사용자 정의 1
    Segv = 11,         // SIGSEGV - 잘못된 메모리 참조(유저 폴트 처리 §2-B가 커널이 스스로 발생)
    Usr2 = 12,         // SIGUSR2 - 사용자 정의 2
    Pipe = 13,         // SIGPIPE - 읽는 쪽 없는 파이프에 쓰기
    Alrm = 14,         // SIGALRM - 알람 타이머 만료
    Terminate = 15,    // SIGTERM - 기본 종료 신호, 핸들러로 가로챌 수 있음
    // 16번은 POSIX SIGSTKFLT 등에 대응하는 자리 - v1은 정의하지 않음(RM-B5764185)
    Chld = 17,         // SIGCHLD - 자식 프로세스 종료/중지 통지
    Cont = 18,         // SIGCONT - 중지된 프로세스 재개
    Stop = 19,         // SIGSTOP - 일시 중지, 마스킹/무시 불가
    Tstp = 20,         // SIGTSTP - 터미널 정지 신호(Ctrl+Z)
    Ttin = 21,         // SIGTTIN - 백그라운드 프로세스의 터미널 입력 시도
    Ttou = 22,         // SIGTTOU - 백그라운드 프로세스의 터미널 출력 시도
    // 23~30번은 v1 범위 밖(RM-B5764185) - 필요해지면 그 표에 먼저 예약
    Sys = 31,          // SIGSYS  - 잘못된 시스템 콜 요청
};
```

**v1이 실제로 발생시키는 것은 이 중 4개뿐**(`Kill`/`Terminate`/
`Segv`/`IllegalInstruction`, RM-B5764185 참고) - 나머지 번호는 이
enum에 자리만 예약돼 있을 뿐, 그 신호를 실제로 일으키는 커널 경로는
각 서브시스템(tty/프로세스 관리/알람 타이머/syscall 검증 등)이
구현될 때 별도로 설계한다.

```cpp
enum class SignalDisposition : uint32_t {
    Default,   // 기본 동작(대부분 프로세스 종료) - v1의 유일하게 실제

    Ignore,    // 무시 - Kill/Stop에는 적용 불가(마스킹 불가 원칙)
    Handler,   // 유저 핸들러로 위임 - **PN-124C105B 완료 전까지는
```

### 4.4 전달 시점 - 체크포인트 + 강제 취소(§9) 병행 (v1)

**진짜 Unix 시그널**은 임의의 순간(시스템 콜 도중, 블로킹 대기
도중)에도 대상을 깨워 즉시 개입할 수 있다. **[수정, 2026-09-14,
설계자 지시]** 처음에는 이 프로젝트의 대기 프리미티브가 "대기열에
있는 걸 아는 쪽만 깨울 수 있다"는 한계 때문에 체크포인트 방식만
제안했었으나, 설계자가 "임의의 대기 상태에서 강제로 끄집어내는
범용 메커니즘도 설계 범위에 포함시켜"라고 지시해 §9에서 `Waitable`
인터페이스 기반 강제 취소 메커니즘을 추가했다.

**v1의 최종 전달 경로는 두 가지가 함께 동작한다**:

1. **대기 중(`Task::blockedOn != nullptr`)인 경우** — §9의 `cancel()`
   경로로 즉시 개입한다(§9.5). `WaitQueue` 기반 대기(Mutex/Semaphore)
   는 완전히 즉시, `pendingSyscalls` 기반 대기(§7의 폴트 재개 포함)
   는 §9.4의 best-effort 한계가 적용된다.
2. **실행 중이거나 아직 어떤 대기에도 들어가지 않은 경우** — 기존
   체크포인트 방식(syscall 진입/반환 시점, ring3 진입 직전)이 그대로
   적용된다. `SignalNumber::Kill`은 `Process::killPending` 플래그로
   모든 체크포인트가 공통으로 확인해 최대한 빨리 처리한다.

이 두 경로를 합쳐도 "완전한 즉시성"은 아니다(예: 이미 실행 중인
코드가 다음 체크포인트/대기 진입 전까지는 개입 불가) - 이 한계는
여전히 v1의 알려진 제약으로 남는다.

## 5. 아직 열려 있는 설계 영역

1. **파킹된 Task의 "어느 코어에서 깨울지" 기록 위치**(§1): v1은
   `Task`에 `parkedCoreIndex` 필드를 추가하는 것을 제안 - 정확한
   필드 배치/스케줄러 마이그레이션(다른 코어로 옮겨 깨우는 로드밸런싱)
   여부는 PL-2D3184BC 쪽과 함께 확정 필요.
2. **재경쟁 방식의 기아(starvation) 가능성**(§2.1, 수정): 직접
   핸드오프의 convoy effect는 재경쟁 방식 채택으로 해소됐지만, 그
   대신 이론적으로 "항상 더 빠른 새 호출자에게 밀려 특정 대기자가
   계속 재시도에 실패"하는 기아 시나리오가 남는다 - v1은 이를
   허용하고(경쟁 심한 락은 애초에 설계 재검토 대상), 실측 후 필요
   시 대기 시간 기반 에이징(aging) 등을 재검토.
3. **[해결됨, 2026-09-14, §9로 대체]** ~~Signal의 진짜 비동기성
   한계~~ — "임의의 대기 상태에서 강제로 끄집어내는 범용 메커니즘"이
   설계자 지시로 이번 문서 범위에 포함됐다 - §9(`Waitable` 인터페이스
   기반 강제 취소) 참고. 완전한 즉시성까지는 아니라는 잔여 한계는
   §4.4/§9.6에 남아 있다.
4. **프로세스 ID 체계**: `KillArgs::targetProcessId`가 가리킬 정확한
   식별자 체계가 아직 없다(PN-268F062B "공개 인터페이스 registry"가
   유사한 문제를 다루는 중) - 실제 구현 시점에 그쪽과 통일.
5. **[추가, 2026-09-14, 설계자 지시] `Mutex`의 재진입(Recursive)
   안전성 미비**: "이 커널에서 Mutex는 기본적으로 Recursive Call
   Safe 해야 해. 그런데 현재 구조는 전혀 그렇지가 않아." §2의 v1
   `Mutex`는 소유자를 전혀 추적하지 않는 순수 `bool _locked` 구조라,
   같은 Task가 이미 잠근 Mutex를 다시 `lock()`하면 자기 자신을
   무한 대기시키는 데드락이 된다(재진입 불가) - 정상적인 재진입
   안전 Mutex가 되려면 최소한 (a) "현재 소유자 Task" 식별자 저장,
   (b) 같은 소유자의 재호출을 감지해 카운터만 증가시키고 즉시 반환,
   (c) `unlock()`이 카운터를 감소시켜 0이 될 때만 실제로 풀어주는
   재진입 카운트 구조가 필요하다 - 이는 §1의 `WaitQueue`/§2.1의
   재경쟁 정책과 맞물려 다시 설계해야 하는 범위라, **스케줄러
   (PL-2D3184BC)가 어느 정도 더 진척된 뒤 별도 개정판으로 다룬다**
   (설계자 판단) - 이번 문서는 결함을 명시적으로 기록만 해 두고
   수정하지 않는다(RM-23F4B687 §4 원칙 - 임의로 지금 결정하지 않음).

## 7. 유저 페이지 폴트 재개 정책 (SP-68182FBD §2.3 보완, 2026-09-14 설계자 지시)

### 7.1 무엇을 확정하는가

SP-68182FBD §2.3이 "그 프로세스만 블로킹시키고 스케줄러가 다음 작업
으로 전환, 폴트 정보는 PCB에 매달아 둔다"까지는 확정했지만, **그
뒤 누가/언제 다시 깨우는지**가 비어 있었다. 설계자 지시: "이전에
페이지 폴트에 관한 지침을 주면서 공통적으로 리스트를 두고, 그게
비어야 블로킹을 풀면 된다고 한 적이 있다" - 이 지침을 그대로
따른다. **이 프로젝트에 이미 정확히 같은 모양의 메커니즘이
구현돼 있다**: `UserThread::pendingSyscalls`(`ChunkedList`, SP-04EE2A18)
+ `Syscall::waitForMultipleSyscall`(모든 토큰이 끝나야 깨어남, AND
세만틱, 이미 구현 완료)가 바로 "공통 리스트가 비어야 블로킹을 푼다"
는 패턴이다 - 유저 페이지 폴트도 **새 자료구조를 만들지 않고 이
기존 메커니즘을 그대로 재사용**하는 것을 제안한다. (참고: 이 §7의
재개 경로는 §1-§3의 Mutex/Semaphore `WaitQueue`와는 별개의 기존
메커니즘 - `waitForMultipleSyscall`은 처음부터 "리스트가 비면
그 특정 Task를 재개"하는 확정적 대상 지정 방식이라 §2.1의 재경쟁
논의와는 무관하다. §9의 강제 취소 메커니즘은 이 경로에도 적용되지만
§9.4의 best-effort 한계가 있다.)

### 7.2 설계 - 폴트 처리를 "또 하나의 대기 중인 syscall"로 모델링

```
유저 모드 실행 중 폴트 발생
   |
   v
1. 커널이 §2-B 정책대로 Task::state = Blocked, Process::lastFault에
   폴트 정보(faultAddr/errorCode/rip) 기록(기존 그대로, 변경 없음).
2. 폴트 처리 자체를 AsyncTask로 제출한다(Syscall::submit과 동일한
   경로 재사용, PL-21344323) - 이 AsyncTask가 "죽일지 swapfs에서
   읽어 페이지를 갈아 끼울지"를 판단하는 바로 그 작업(QU-0C4D25EF가
   이미 확정한 처리 주체).
3. 이 제출로 생긴 토큰을 UserThread::pendingSyscalls(이미 있는
   ChunkedList)에 그대로 추가한다 - 일반 syscall과 완전히 같은
   슬롯을 공유한다(폴트 전용 별도 리스트를 새로 만들지 않는다).
4. Task는 Syscall::waitForMultipleSyscall과 정확히 같은 대기 상태다
   - pendingSyscalls가 빌 때까지(이 폴트 토큰이 끝나고, 그 사이
     쌓였을 수 있는 다른 pending syscall/폴트 토큰도 전부 끝나야)
     재개하지 않는다.
5. AsyncTask 완료(kill 결정이든 swap-in 성공이든) → 토큰을
   pendingSyscalls에서 제거 → 리스트가 비었으면 Scheduler::
   scheduleImmediate()로 이 Task를 재개(이미 waitForAnyOf가 구현한
   경로 그대로) → 비지 않았으면(다른 대기 중인 항목이 남아 있으면)
   계속 Blocked.
```

**핵심**: 새 `TaskState`도, 새 대기열 자료구조도 필요 없다 - "유저
페이지 폴트"는 그저 "이 스레드가 기다리는 syscall 토큰 목록에 하나
추가된 특별한 종류의 항목"일 뿐이고, 그 목록이 비어야 재개된다는
규칙은 `waitForMultipleSyscall`이 이미 구현해 둔 그대로다.

### 7.3 왜 "리스트"인가 - 폴트가 여러 개 쌓일 수 있는 이유

v1은 프로세스당 스레드 하나뿐이지만(SP-68182FBD §Process), 그래도
리스트가 필요한 이유: (1) 이미 대기 중인 일반 syscall이 있는 상태
에서 그 syscall의 콜백/재개 경로 자체가 또 다른 페이지에 접근하다
새 폴트를 낼 수 있고, (2) 스레드가 여러 개로 확장되는 후속 과제
(SP-0666DB3C가 아니라 PL-2D3184BC/향후 멀티스레드 프로세스 과제)가
오면 한 프로세스에 여러 폴트가 동시에 존재할 수 있다 - 처음부터
"여러 개가 쌓일 수 있고 전부 비어야 재개"라는 형태로 설계해 두면
그때 가서 자료구조를 바꿀 필요가 없다.

### 7.4 SP-68182FBD §2.3과의 관계

SP-68182FBD §2.3이 미결로 남겨 뒀던 "새 `TaskState`가 필요한가,
`Blocked` 재사용으로 충분한가"는 이 설계로 **`Blocked` 재사용으로
확정**된다(QU-0C4D25EF 답변과 정확히 일치) - "누가/언제 깨우는지"의
공백만 이번에 채워진 것이다. §2.3 자체는 이 섹션으로 대체/흡수된
것으로 표시한다.

## 9. 임의의 대기 상태에서 강제로 끄집어내는 범용 메커니즘 (설계자 지시, 2026-09-14)

### 9.1 배경 - §5-3에서 열어 뒀던 질문의 해결

§5-3(원래 §4.4에 있던 열린 질문)이 "체크포인트 방식은 완전한
즉시성을 포기한 v1 단순화"이며, 나중에 정말 필요해지면 `WaitQueue`/
`Syscall::wait` 양쪽에 "이 Task를 신호로 강제 취소 가능"이라는 훅을
추가하는 별도 설계가 필요하다고 명시적으로 유보해 뒀는데, 설계자가
"임의의 대기 상태에서 강제로 끄집어내는 범용 메커니즘도 설계 범위에
포함시켜"라고 지시함에 따라 지금 그 훅을 설계한다.

### 9.2 설계 - `Waitable` 인터페이스

이 프로젝트에는 서로 다른 모양의 "대기 중" 상태가 이미/곧 여러 개
있다 - §1의 `WaitQueue`(Mutex/Semaphore), SP-04EE2A18의
`UserThread::pendingSyscalls`+`waitForMultipleSyscall`(§7이 유저
폴트 재개에도 재사용), 그리고 향후 추가될 대기 종류. 각각을 개별
취소 코드로 따로 구현하지 않도록, "이 Task가 지금 무엇에 막혀
있는지"를 추상 인터페이스로 표현한다:

```cpp
// minicore/kernel, 가칭 waitable.h
enum class WaitCancelReason : uint32_t {
    Signal,     // 강제 시그널(Kill 등)에 의한 취소
    Timeout,    // 향후 타임아웃 기능이 생기면 재사용(v1 범위 밖)
};

// 이 Task가 현재 파킹된 대기 구조체가 구현해야 하는 최소 인터페이스.
// Task::blockedOn이 이 포인터를 들고 있고, cancel()이 그 대기
// 구조체 자신의 내부 자료구조(WaitQueue의 연결 리스트,
// pendingSyscalls의 ChunkedList 등)에서 이 Task를 실제로 제거하고
// 재개시킬 책임을 진다.
class Waitable {
public:
    virtual ~Waitable() = default;

    // task를 이 대기 구조체에서 강제로 제거하고 Ready로 되돌린다.
    // 이미 정상적으로 깨어나 대기 구조체를 떠난 뒤라면(경쟁 상황)
    // 아무 일도 하지 않고 false를 반환한다 - 호출부는 이 반환값으로
    // "취소가 실제로 적용됐는지"를 판단한다.
    virtual bool cancel(Task* task, WaitCancelReason reason) = 0;
};
```

`Task`(minicore/kernel/task.h)에 필드 추가 제안:

```cpp
// Task 구조체에 추가
Waitable* blockedOn = nullptr;  // 파킹 시작 시 설정, 정상적으로
                                 // 깨어나면 스스로 nullptr로 되돌림.
                                 // 대기 구조체 자신의 Spinlock으로
                                 // 보호(별도 락 불필요, §9.6-1).
```

### 9.3 `WaitQueue`(Mutex/Semaphore) 쪽 구현

`WaitQueue`는 지금 `wakeOne()`으로 머리만 꺼내는 단순 FIFO였으나
(§1), `cancel()`을 지원하려면 **임의 위치의 노드를 제거**할 수
있어야 한다 - 리스트가 대개 짧다는 전제(경합이 심한 락은 애초에
설계 재검토 대상, §5-2와 같은 가정) 하에 head부터 순회해 O(n)
제거를 허용한다. `cancel()`이 성공하면 §9.3의 `WaitQueue`는 즉시
`Scheduler::scheduleImmediate()`로 그 Task를 재개시킨다 - 이 경로는
**완전히 즉시적**이다(§9.4의 pendingSyscalls 경로와 다른 점).

### 9.4 `pendingSyscalls`/`waitForMultipleSyscall` 쪽 구현 - 부분적 한계

§7의 유저 페이지 폴트 재개나 일반 syscall 대기는 `WaitQueue`가
아니라 `UserThread::pendingSyscalls`(AsyncTask 완료를 기다리는 AND
세만틱)를 쓴다 - 여기서의 `cancel()`은 §9.3처럼 간단하지 않다:

- Task 자체를 Ready로 되돌리는 것(대기 목록에서 이 Task를 제거)은
  쉽다.
- 하지만 **이미 제출된 AsyncTask(예: swapfs에서 페이지를 읽어오는
  중인 I/O)는 즉시 멈추지 않는다** - AsyncTask 자체의 취소는 이
  문서 범위 밖(각 AsyncTaskHandler가 취소를 지원하는지는 그 핸들러
  설계에 달림). 따라서 이 경로의 `cancel()`은 "Task를 깨우고 이후
  AsyncTask 결과는 버린다"는 **최선 노력(best-effort)** 수준까지만
  보장한다 - 이미 진행 중인 부수효과(예: 페이지 매핑 절반 완료)는
  별도로 안전하게 처리해야 하며, 이는 각 AsyncTaskHandler 구현
  시점의 열린 과제로 남긴다(§9.6-2).

### 9.5 Signal 전달(§4.4)과의 연결

`SignalNumber::Kill`가 도착하면, 그 대상 Task의 `blockedOn`이
가리키는 대기 구조체가 있으면 즉시 `blockedOn->cancel(task,
WaitCancelReason::Signal)`을 호출해 체크포인트를 기다리지 않고
즉시 깨운다(§9.3 케이스는 완전히 즉시, §9.4 케이스는 §9.4의
best-effort 한계 적용). Task가 지금 실행 중이거나(Running) 아직
어떤 대기에도 들어가 있지 않으면(`blockedOn == nullptr`) 기존
§4.4의 `Process::killPending` 체크포인트 경로가 그대로 다음
체크포인트에서 처리한다 - 두 경로가 함께 있어야 "대기 중이면
즉시, 실행 중이면 다음 체크포인트에"라는 완전한 커버리지가 된다.

### 9.6 아직 열려 있는 하위 과제

1. **경쟁 조건**: `cancel()`이 호출되는 순간과 그 Task가 마침
   정상적으로 깨어나는 순간이 겹칠 수 있다 - 두 경로 모두 같은
   Spinlock(WaitQueue/대기 구조체 자신의 락) 아래에서 `blockedOn`을
   확인/정리하도록 강제해 "정확히 한쪽만 성공"하게 만드는 것을
   제안(구현 시점에 확정).
2. **AsyncTask 자체의 취소 지원 여부**: §9.4에서 언급한 대로, 각
   AsyncTaskHandler(파일 I/O, DMA 등)가 "진행 중인 작업을 실제로
   중단할 수 있는지"는 이 문서가 결정하지 않는다 - 필요해지는
   시점(swapfs 등 실제 블로킹 I/O가 생길 때)에 그 핸들러 설계에서
   다룬다.
3. **`cancel()`의 반환 상태 전달 방법**: `Mutex::lock()`이 깨어났을
   때 "정상적으로 재시도 기회를 얻은 것"과 "강제로 취소당한 것"을
   구분해야 재시도 루프를 멈추고 에러(예: `ChannelError::
   Interrupted`류)를 반환할 수 있다 - 정확한 전달 채널(Task에 별도
   필드? `cancel()`이 넘기는 값을 어디에 저장?)은 구현 시점에 확정.
