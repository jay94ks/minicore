# 커널 동기화 프리미티브(Mutex/Semaphore) 및 Signal 전달 — 설계 제안

설계자 지시(2026-09-14, 메시지) - "세마포어, 뮤텍스, Signal등에 대한
설계도 해라." `Spinlock`(libkenv, 이미 구현 완료)은 "짧게 잡고 바로
푸는" 저수준 상호배제만 제공한다 - 대기 시간이 길어질 수 있는 진짜
동기화 프리미티브(자고 있다가 깨어남)는 아직 없다. 이 문서는
`Scheduler::parkCurrent()`(PL-2D3184BC 6단계, 이미 구현 완료 - "특정
이유로 블로킹 후 누군가 깨울 때까지 대기"하는 범용 프리미티브)를
기반으로 Mutex/Semaphore를 설계하고, 별도로 프로세스 대상 비동기
알림인 Signal 전달을 설계한다.

## 1. 공통 기반 - 대기열(Wait Queue)

Mutex/Semaphore 둘 다 "지금 획득 못 하면 대기열에 매달렸다가, 나중에
누군가 정확히 한 명씩 깨워준다"는 같은 패턴을 쓴다 - `Task::next`
(이미 있는 침습적 다음-포인터, 스케줄러 큐 전용이지만 **파킹된
Task는 어느 큐에도 없으므로 이 필드가 비어 있다** - 재사용 가능)로
간단한 FIFO를 구성한다:

```cpp
// minicore/kernel, 가칭 wait_queue.h - Mutex/Semaphore가 공유하는 내부 헬퍼.
class WaitQueue {
public:
    // 현재 Task를 큐 꼬리에 매달고 파킹한다(Scheduler::parkCurrent
    // 호출 - 이 함수 자체가 반환하지 않고, 나중에 wakeOne()이 이
    // Task를 다시 스케줄링해야 반환한다). 호출 전에 반드시 상위
    // 프리미티브(Mutex/Semaphore)의 Spinlock을 잡고 있어야 하고,
    // 이 함수 안에서 그 락을 풀고 파킹한다(락 보유 중 파킹하면
    // 다른 코어가 영원히 락을 못 잡음 - Mesa 모니터 패턴).
    void parkCurrentAndUnlock(Spinlock& guard);

    // 큐 머리에서 하나 꺼내 그 Task가 파킹됐던 코어에서 즉시
    // 재개시킨다(Scheduler::scheduleImmediate 재사용 - 파킹된 Task는
    // 이중 스케줄링 걱정이 없다고 이미 문서화돼 있음). 비어 있으면
    // 아무 일도 안 함.
    void wakeOne();

    bool isEmpty() const;

private:
    Task* _head = nullptr;
    Task* _tail = nullptr;
    // 각 Task가 파킹된 코어 인덱스를 어디에 저장할지는 §5-1의 열린
    // 질문 - v1은 Task 구조체 자체에 필드를 추가하는 것을 제안(§5-1).
};
```

## 2. Mutex

```cpp
// minicore/kernel, 가칭 mutex.h
class Mutex {
public:
    void init() { _locked = false; }

    // 이미 잠겨 있으면 대기열에 매달려 파킹 - 깨어나면(직접 소유권을
    // 넘겨받은 것이므로) 재확인 없이 바로 반환한다(핸드오프 방식,
    // 아래 §2.1 참고).
    void lock();

    // 대기열에 아무도 없으면 그냥 unlock. 있으면 첫 대기자에게
    // 소유권을 그대로 넘긴다(_locked는 계속 true) - 그 대기자를
    // 깨우기만 하고 자신은 반환.
    void unlock();

    // 논블로킹 시도 - 실패해도 대기열에 매달리지 않고 즉시 false.
    bool tryLock();

private:
    Spinlock _guard;   // _locked/_waitQueue 자체를 보호하는 저수준 락(짧게만 보유)
    bool _locked = false;
    WaitQueue _waitQueue;
};
```

### 2.1 핸드오프(Direct Handoff) 방식을 쓰는 이유

`unlock()`이 그냥 `_locked = false`만 하고 대기자들이 다시 경쟁하게
두는 방식(배리어 스타일)도 있지만, 이 프로젝트는 **직접 핸드오프**
(`unlock()`이 다음 대기자를 골라 소유권을 그대로 넘김)를 제안한다 -
`WaitQueue::wakeOne()`이 이미 "정확히 그 Task만" 깨우므로, 깨어난
`lock()` 호출부는 "내가 락을 가졌다"를 재확인할 필요 없이 바로
진행할 수 있다(불필요한 재시도 루프/스퓨리어스 웨이크업 처리가
없어져 코드가 단순해진다) - 단점(호위 효과, convoy effect - 느린
소유자가 다음 대기자를 강제로 그 코어에 묶어 둘 수 있음)은 v1
범위에서 무시할 만하다고 판단(실측 후 재검토 대상, §5-2).

## 3. Semaphore

```cpp
// minicore/kernel, 가칭 semaphore.h
class Semaphore {
public:
    void init(uint32_t initialCount) { _count = initialCount; }

    // 카운트가 0보다 크면 즉시 차감 후 반환. 0이면 대기열에 매달려
    // 파킹 - 깨어나면 이미 카운트를 하나 받은 것이므로(핸드오프,
    // Mutex와 동일 철학) 바로 반환.
    void acquire();

    // 대기열에 누가 있으면 그 첫 대기자에게 직접 핸드오프(카운트
    // 변화 없음 - "받은 단위를 그대로 넘겨줌"). 없으면 카운트++.
    void release();

    bool tryAcquire();  // 논블로킹, 카운트가 0이면 즉시 false

private:
    Spinlock _guard;
    uint32_t _count = 0;
    WaitQueue _waitQueue;
};
```

`Mutex`는 사실상 `Semaphore(initialCount=1)`의 특수형이지만, "누가
락을 쥐고 있는지"(재진입 감지, 소유자 오류 검출 등 후속 디버깅
기능의 여지)를 남겨 두기 위해 별도 타입으로 분리하는 것을 제안한다
(RM-23F4B687 §4 취지 - 지금은 숫자/타입 튜닝 수준의 결정).

## 4. Signal 전달

### 4.1 범위 - 커널 쪽 플러밍만, 유저 핸들러 호출은 후속

SP-8B6B8D25 §2 11번("시그널 전파")이 이미 커널 책임으로 명시해 뒀다.
**유저 코드가 만든 시그널 핸들러를 ring3에서 실제로 호출하는 것**은
PN-124C105B(ring3 진입)가 아직 없어 이번 문서 범위 밖이다 - 이 문서는
"신호를 어떻게 커널 안에서 표현/전달/기본 처리하는지"까지만 다룬다.

### 4.2 신호 번호와 기본 동작

```cpp
enum class SignalNumber : uint32_t {
    Kill,       // 마스킹/무시 불가 - 항상 즉시 종료(SIGKILL 대응)
    Terminate,  // 기본 동작 종료, 핸들러로 가로챌 수 있음(SIGTERM 대응)
    Segv,       // 유저 폴트 처리(SP-8B6B8D25 §2-B)가 "진짜 잘못된 접근"
                // 이라고 판단했을 때 커널이 스스로 발생시킨다(SIGSEGV 대응)
    IllegalInstruction,  // #UD 트랩 시 커널이 발생(SIGILL 대응)
    // 필요에 따라 후속 추가 - v1은 프로세스 모델이 실제로 필요로 하는
    // 최소 집합만(Kill/Terminate/Segv/IllegalInstruction).
};

enum class SignalDisposition : uint32_t {
    Default,   // 기본 동작(대부분 프로세스 종료) - v1의 유일하게 실제
               // 구현 가능한 값(핸들러 호출 인프라가 없으므로)
    Ignore,    // 무시 - Kill에는 적용 불가(마스킹 불가 원칙)
    Handler,   // 유저 핸들러로 위임 - **PN-124C105B 완료 전까지는
               // 등록만 받아 두고 실제 호출은 하지 않는다**(§4.4)
};
```

### 4.3 `Process` 확장 - 대기 중인 신호 표현

```cpp
// minicore/kernel/process.h에 추가 제안
struct PendingSignal {
    SignalNumber number;
    bool used = false;
};

// Process에 추가
ChunkedList<PendingSignal, kPendingSignalChunkCapacity> pendingSignals;  // DmaBuffer(SP-39F18E30 §4)와 동일 패턴
SignalDisposition dispositions[kSignalCount] = { SignalDisposition::Default, ... };
```

### 4.4 전달 시점 - 비동기 즉시 개입이 아니라 체크포인트 방식 (v1 단순화)

**진짜 Unix 시그널**은 임의의 순간(시스템 콜 도중, 블로킹 대기
도중)에도 대상을 깨워 즉시 개입할 수 있다 - 이 프로젝트가 지금
가진 대기 프리미티브(§1의 `WaitQueue`, `Syscall::wait` 등)는
전부 "이 대기열에 있는 걸 아는 쪽만 깨울 수 있다"는 전제라, 임의의
대기 상태에서 강제로 끄집어내는 범용 메커니즘이 아직 없다.

**이 문서의 v1 제안**: 시그널은 **체크포인트에서만** 확인/처리한다 -
(1) syscall 진입/반환 시점, (2) 유저 모드로 복귀하기 직전(ring3 진입
경로, PN-124C105B). `SignalNumber::Kill`만은 예외로, 프로세스의
`FaultInfo.pending`과 같은 패턴으로 **커널이 아는 모든 대기 지점에서
공통으로 확인하는 별도 플래그**(`Process::killPending`)를 두어, 다음
체크포인트를 최대한 빨리 맞을 수 있게 한다(그래도 "완전히 즉시"는
아니다 - 그 한계를 명시적으로 인정한다, §5-3).

### 4.5 Syscall API

```cpp
struct KillArgs {
    uint64_t targetProcessId;  // 프로세스 ID 체계 자체는 아직 없음 - PN-268F062B(공개 인터페이스 registry)류 식별자 재사용 예정(§5-4)
    SignalNumber signal;
    ChannelError error;   // NotFound

struct SignalActionArgs {
    SignalNumber signal;
    SignalDisposition disposition;  // Handler는 §4.4 조건 전까지 syscall 자체가 NotSupported 반환 제안

```

## 5. 아직 열려 있는 설계 영역

1. **파킹된 Task의 "어느 코어에서 깨울지" 기록 위치**(§1): v1은
   `Task`에 `parkedCoreIndex` 필드를 추가하는 것을 제안 - 정확한
   필드 배치/스케줄러 마이그레이션(다른 코어로 옮겨 깨우는 로드밸런싱)
   여부는 PL-2D3184BC 쪽과 함께 확정 필요.
2. **직접 핸드오프의 호위 효과(convoy effect)**: §2.1에서 이미 논의 -
   실측 후 재검토.
3. **Signal의 진짜 비동기성 한계**(§4.4): 체크포인트 방식은 "완전한
   즉시성"을 포기한 v1 단순화다 - 나중에 정말 필요해지면(예: 블로킹
   syscall 도중에도 즉시 반응해야 하는 요구) `WaitQueue`/
   `Syscall::wait` 양쪽에 "이 Task를 신호로 강제 취소 가능"이라는
   훅을 추가하는 별도 설계가 필요 - 지금은 그 요구가 없어 범위 밖.
4. **프로세스 ID 체계**: `KillArgs::targetProcessId`가 가리킬 정확한
   식별자 체계가 아직 없다(PN-268F062B "공개 인터페이스 registry"가
   유사한 문제를 다루는 중) - 실제 구현 시점에 그쪽과 통일.

## 6. 선행 조건

- `Scheduler::parkCurrent()`/`scheduleImmediate()`(이미 구현 완료,
  PL-2D3184BC) - `WaitQueue`의 파킹/깨우기 기반.
- `Spinlock`(이미 구현 완료) - Mutex/Semaphore 내부 보호.
- `ChunkedList`(이미 구현 완료) - `Process::pendingSignals`.
- 프로세스 모델(PN-16CA347D) - `Process` 확장 대상 자체.
- PN-124C105B(ring3 진입) - Signal 핸들러 실제 호출(§4.1/§4.4) 전제조건.
