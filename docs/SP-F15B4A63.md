# 지연 실행(타이머/알람) 인프라 — 설계 제안

계획 PN-BEC8FB65("지연 실행(타이머/알람) 인프라 — 별도 설계안 작성")
착수. 배경: SP-EAB162FC §6.4(Resurrect 백오프, 설계자 지시 2026-09-15
- "필수 서비스가 아니면 되살리는 간격을 조정할 수 있게 만들고,
간격의 기본값은 1분이고 5회 실패시마다 1분씩 늘려서 최대 10분까지")가
"임의 시간 뒤 콜백을 실행"하는 지연 실행이 필요한데, 이 프로젝트엔
아직 그런 범용 타이머/알람 인프라가 없다(RM-32D06563 확인 - 존재
안 함). PN-645CF608(ProcessRole/Resurrect 구현) 항목 5 재작업이
이 설계를 선행 조건으로 기다리고 있다.

## 1. 시간 소스

새 시간원을 만들지 않는다 - `Timer::tickCount()`(timer.h, HPET
기반 100Hz 전역 단조 카운터, PL-E68894CD)를 그대로 재사용한다.
이미 "SMP 전역 카운터는 BSP의 카운터를 직접 읽어라"는 원칙이
확립돼 있고(DC-0CC88ABB), 백오프가 요구하는 정밀도(분 단위)에
비해 100Hz(10ms) 해상도는 차고 넘친다 - 분 단위 지연은
`tickCount() + minutes * 60 * 100`으로 계산하면 끝난다. 스케줄러
자신의 LAPIC 틱(`kSchedulerTickHz`, 코어별 독립)과는 완전히 별개
시간원이라는 점도 기존 관례(PL-2D3184BC 7단계 "선점 결정은 코어별
독립 LAPIC 타이머가 각자 담당, 전역 시각과는 무관")와 일치한다.

## 2. 자료구조 및 스캔 방식 — [해소, QU-A8C0CC2C 설계자 답변 반영]

**설계자 답변(2026-09-16)**: "고정 크기는 안돼. 초과시 또 별도의
비용이 발생하니 linked list로 구현해야 해." - 아래 초안(고정 크기
배열)은 폐기하고 **연결 리스트**로 대체한다. 노드는 커널 힙(libkmm
slab 할당자, SP-D7013B26)에서 `schedule()` 시 할당하고 `pump()`
실행 후 또는 `cancel()` 시 해제한다 - 상한 자체가 없으므로 "상한
초과" 실패 경로가 사라지고, `schedule()`의 실패 가능성은 순수
할당 실패(OOM)로 좁혀진다:

```cpp
// minicore/kernel/delayed_exec.h (가칭)
using DelayedCallback = void (*)(void* arg);

struct DelayedTimerEntry {
    uint64_t deadlineTick = 0;   // Timer::tickCount() 기준 절대 시각
    DelayedCallback callback = nullptr;
    void* arg = nullptr;
    uint64_t token = 0;          // 발급 시 유일값(취소용)
    DelayedTimerEntry* next = nullptr;
};

class DelayedExecutionQueue {
public:
    static void init();

    // delayTicks 이후 callback(arg)를 실행하도록 예약한다. 노드 할당
    // 실패 시 0, 성공 시 0이 아닌 토큰(cancel()에 넘길 값).
    static uint64_t schedule(uint64_t delayTicks, DelayedCallback callback, void* arg);

    // 아직 실행 전이면 취소(리스트에서 unlink 후 노드 해제) - 이미
    // 실행됐거나 없는 토큰이면 false.
    static bool cancel(uint64_t token);

    // 만료된 항목을 찾아 실행하고 리스트에서 제거(노드 해제)한다
    // (아래 §3의 호출 지점에서 주기적으로 부름).
    static void pump();
};
```

연결 리스트로 바뀌어도 v1 동시 대기 항목 수 자체는 여전히 적을
것으로 예상되므로(단락 서두의 근거 그대로) 매 `pump()` 스캔은 선형
순회로 충분하다 - 정렬 리스트/최소 힙 도입은 실제로 항목 수가 늘어나는
게 확인된 뒤 재검토한다(RM-23F4B687 §4).

## 3. 콜백 실행 컨텍스트 — [해소, QU-A8C0CC2C]

**설계자 답변(2026-09-16)**: "DelayedExecutionQueue 전용으로 Task를
만들기 보다 DelayedExecutionQueue를 두고, 비동기 리액터를 활용하는
방향으로 가자." - 아래 후보 (a)/(b) 둘 다 아닌 **제3의 방향(비동기
리액터 재사용)**이 채택됐다. `DelayedExecutionQueue` 자체(§2)는 그대로
두되, 전용 커널 Task를 새로 만들지 않고 기존 **AsyncReactor**
(SP-F682B889)가 이미 갖고 있는 주기적 폴링/이벤트 루프 지점에서
`DelayedExecutionQueue::pump()`를 호출하도록 연결한다 - 전용 Task를
부팅 시퀀스에 추가하는 비용도, 콜백을 인터럽트 컨텍스트에서 실행하는
위험도 둘 다 피하면서 기존 리액터 인프라를 재사용하는 방식. 리액터
쪽의 정확한 호출 지점(매 리액터 사이클마다 무조건 `pump()`를 부를지,
아니면 리액터가 idle일 때만 부를지 등 세부)은 구현 PN 착수 시
AsyncReactor 소스(SP-F682B889 §2 이하)를 직접 확인해 확정한다 -
이 설계 문서 차원에서는 "전용 Task 없이 AsyncReactor를 통해 호출"
이라는 방향만 확정한다.

**[후속, 2026-09-16, QU-E2C303C2 → QU-96BBB769 → QU-4034561A로
최종 확정]** PN-C46DF296 구현 중 "타이머 대기 중엔 yieldCurrent()로
재폴링"하는 세부 방식을 구현 세션이 임의로 결정해 확인을 구했는데,
그 결과 SP-F682B889 §3.4/§4가 통째로 재설계됐다 - **리액터는 더
이상 별도 kernel::Task가 아니라 `Scheduler::runLoop()`의 idle
폴백(구 `sti; hlt`) 자리에 인라인된 로직**이다(SP-F682B889 §3.4
참고). 이 §3(`DelayedExecutionQueue::pump()` 호출 배선)도 이제
"리액터 Task의 idle 분기"가 아니라 **`runLoop()`의 새 인라인 리액터
경로 안**에서 호출되는 것으로 갱신해야 한다 - 정확한 재배선은
PN-FEAAF154(구현 계획)에서 실제 코드와 함께 진행, PN-C46DF296으로
이미 커밋된 `async_task.cpp`의 `reactorTaskEntry()` 기반 구현(commit
90679e0)은 이 재설계에 맞춰 재작성 대상이다. 이 절(§3)의 "AsyncReactor
재사용" 방향 자체는 유효하지만, 그 리액터가 "전용 Task로 남되 idle
시에도 폴링"인지 "아예 idle 핸들러 자체가 되는 것"인지는 아직
미확정 - 답변 오면 §3.4/이 절 양쪽 갱신.

**참고 - 원래 검토했던 두 후보(폐기)**:

- **후보 (a) - 틱 핸들러에서 직접**: `Scheduler::onTick()` 또는
  `Timer::onTick()` 안에서 매 틱(또는 N틱마다)마다 `pump()`를 직접
  호출 - 구현이 가장 간단하지만, 콜백(`respawn`, 결국
  `Process::execImage()`까지 이어짐 - ELF 파싱 + `PageFrameAllocator::
  allocPage()` 다수 호출)이 **인터럽트 컨텍스트 안에서** 실행된다는
  뜻이다. 이 프로젝트는 지금까지 무거운/임의 실행 시간을 가진 작업을
  인터럽트 컨텍스트에서 직접 돌린 선례가 없다(AsyncTask/AsyncReactor가
  정확히 "무거운 작업은 리액터 Task로 넘기고 인터럽트 컨텍스트는
  최소한만"이라는 원칙을 위해 존재 - SP-F682B889 §1).
- **후보 (b) - 전용 저빈도 커널 Task**: `DelayedExecutionQueue`
  전용으로 커널 Task 하나를 새로 만들어(BSP 부팅 시퀀스에서
  `Task::init()`+`Scheduler::enqueue()`로 스폰, 기존 리액터 Task와
  같은 층위) 짧게 자고 깨어나기를 반복하며(예: 매번 `yieldCurrent()`
  또는 짧은 시간만큼 대기 후 재스케줄) `pump()`를 정상 Task 컨텍스트
  (인터럽트 아님)에서 호출한다 - 콜백이 임의 시간 걸려도 이 코어의
  다른 인터럽트 처리를 막지 않는다. 다만 "짧게 자고 깨어나기"를
  구현할 대기 메커니즘 자체(예: 일정 틱마다 스스로 재스케줄)가
  필요한데, 이게 바로 이 문서가 설계하려는 지연 실행 메커니즘과
  순환 의존처럼 보일 수 있다 - 실제로는 순환이 아니다: 이 전용
  Task는 "정확히 언제 깰지"가 아니라 "대략 몇 틱마다 한 번씩
  스스로 확인"하면 충분해서(백오프 자체가 분 단위 정밀도), 예를
  들어 `Scheduler::yieldCurrent()`를 계속 반복하거나(바쁜 대기,
  간단하지만 CPU 낭비) 또는 매 스케줄러 틱마다 카운터를 증가시켜
  일정 값에 도달하면만 실제로 깨어나는 식의 훨씬 단순한 자체
  메커니즘으로 충분하다 - `DelayedExecutionQueue`가 이 전용 Task
  하나만을 위해 재사용될 필요는 없다.

위 두 후보 모두 최종 채택되지 않았다 - 실제 방향은 위 [해소] 문단의
AsyncReactor 재사용 방식이다.

## 4. 취소(cancel) 필요성

Resurrect 대상 프로세스가 재스폰 대기 중(백오프 타이머가 걸린 상태)
그 자체가 아예 사라질 시나리오(예: 커널 전체 종료)는 v1에 없으므로
`cancel()`은 API 완결성을 위해 제공하되 지금은 실사용처가 없다 -
`Process::destroy()` 등에서 호출할 필요가 생기면 그때 연결한다.

## 5. SP-EAB162FC §6.4 갱신 방향

이 설계가 확정되면 §6.4를 다음 형태로 갱신한다(§3 확인 답변에 따라
세부만 달라짐):

- `ProcessStartFlags`에 `essential`(bool, 기본값 true) 필드 추가.
- `consecutiveFailures`(uint32_t, Process 런타임 카운터, 기존
  `resurrectCount`를 대체하거나 겸함) - 재스폰 성공 시 리셋 여부는
  구현 시점 결정(실패가 "연속"인지 "누적"인지 - 설계자 지시 원문
  "5회 실패시마다"가 연속을 뜻하는 것으로 해석해 성공 시 리셋을
  기본으로 제안).
- 백오프 간격 계산: `min(10, 1 + consecutiveFailures / 5)`분 -
  0~4회는 1분, 5~9회는 2분, ... 45회 이상은 10분에서 고정.
- `essential == true`인 프로세스가 죽으면(기존 §6.4 그대로) 즉시
  `kPanic()`.
- `essential == false`면 패닉 없이 `DelayedExecutionQueue::schedule()`
  로 위 간격만큼 뒤에 `respawn` 콜백을 예약한다(기존 §6.2의 "즉시
  동기 재스폰"을 대체).
