PN-16CA347D/Channel IPC PL-C8648D4D/Syscall 서브시스템 PL-21344323)이

전체가 그 재설계 내용이다 - 예전 안(커널 내부 `InterfaceRegistry` +

기록으로만 남긴다.

## 0. 설계자 지시 원문 (QU-47D4C81D 답변, 2026-09-15)

> InterfaceRegistry는 `유저 프로세스`가 자신을 시스템 내에서
> 홍보하는 곳이야. 커널 관련 명세는 다른 문서로 다 옮겨야돼. 이게
> 뭘 하는 것이냐 하면, AI Agent처럼 `MCP` 도구들을 각 유저 프로세스가
> 정의하면, 그 정의에 포함된 선언대로 어떤 종류던 IPC 채널로 JSON
> 메시지를 송/수신할 수 있는 레지스트리야. 세부 명세는 `pubreg`라는
> 새로운 `커널 서비스`가 들고 있도록 만들면 돼.

핵심 정정 두 가지:
1. **커널 내부 자료구조가 아니라 새 "커널 서비스" `pubreg`**가 이
   레지스트리를 들고 있다 - devmgr/fs/net/tty와 같은 층위(유저랜드
   구동, SP-8B6B8D25 §2-A 원칙 그대로).
2. **등록 단위가 "채널 + kind 태그"가 아니라 "MCP 스타일 tool
   선언"**이다 - 이 프로젝트를 만드는 Claude Code 자신이 쓰는 MCP
   (Model Context Protocol)의 tool 선언(이름/설명/입력·출력 스키마)과
   같은 형태로, 각 유저 프로세스가 자신이 제공하는 기능을 선언하고
   그 선언대로 JSON 메시지를 주고받는다.

## 1. `pubreg` — 5번째 "커널 서비스"

SP-8B6B8D25 §3(디렉터리 배치)의 devmgr/fs/net/tty 4개에 **`pubreg`를
5번째로 추가**한다(`minicore/pubreg`, 유저랜드 구동) - §2-A 원칙
("커널이 모든 통제권을 쥔 유저랜드 서비스")을 그대로 따르는 평범한
다섯 번째 커널 서비스일 뿐, 커널 코드가 아니다. `pubreg`가 하는 일은
정확히 **디렉터리(카탈로그) 역할**뿐이다 - "누가 무슨 tool을
제공하는지" 등록/조회만 중계하고, 실제 tool 호출 트래픽 자체는
`pubreg`를 거치지 않는다(등록자↔소비자가 직접 연결).

이에 따라 다음 문서들도 갱신이 필요하다(§8 체크리스트):
- SP-8B6B8D25 §3 - 디렉터리 목록에 `pubreg` 추가.
- SP-EAB162FC §2.2 - 부팅 매니페스트 고정 이름 목록을
  `devmgr`/`fs`/`net`/`tty`/`pubreg` 5개로 확장.
- SP-9DD4F3EA §6/SP-7CC5693A §6 - devmgr/fs 메인 시퀀스가 예전
  커널 syscall(`PublishInterface`/`QueryInterfaces`) 대신 `pubreg`
  Channel과 대화하도록 갱신.

## 2. Tool 선언 - MCP 스타일

각 유저 프로세스가 자신을 "홍보"할 때 선언하는 단위는 **tool**이다 -
MCP의 tool 정의(이름/설명/입력 JSON 스키마)와 같은 모양을 그대로
차용한다:

```jsonc
// pubreg에 등록하는 tool 선언 하나 (JSON, raw binary Channel IPC
// 페이로드 안에 UTF-8 텍스트로 담김 - DS-D4E5C451 "IPC는 raw
// binary"와 모순 아님, "그 바이트가 우연히 JSON 텍스트"일 뿐이다)
{
  "name": "ahci.readBlocks",          // 프로세스 내에서 고유, 전역으로는 processName과 함께 식별
  "description": "AHCI 포트 0의 논리 블록을 읽는다",
  "inputSchema": { /* JSON Schema - 요청 payload 형태 */ },
  "outputSchema": { /* JSON Schema - 응답 payload 형태 */ }
}
```

- **누가 선언하는가**: tool을 제공하는 프로세스 자신(예: devmgr이
  스폰한 AHCI 드라이버 자식) - §3의 `Register` 메시지로 `pubreg`에
  보낸다.
- **무엇을 위한 것인가**: MCP가 AI 에이전트에게 "이런 함수를 호출할
  수 있다"고 알려주는 것과 똑같이, 이 프로젝트의 유저 프로세스들이
  서로에게 "나는 이런 기능을 제공한다"고 알려주는 것 - 소비자는
  `pubreg`에서 이름/설명으로 tool을 찾은 뒤, `inputSchema`에 맞는
  JSON을 만들어 그 프로세스와 직접 연결해 호출한다.

## 3. `pubreg` 프로토콜 - 등록/조회 (구체 스키마는 착수 시 확정)

`pubreg`는 부팅 시 자신의 Channel을 `/sys/live/named/pubreg`(또는
동급 고정 이름, SP-1FBC0EEB)로 개설해 둔다 - 새 커널 syscall이나
새 IPC 메커니즘 없이, 기존 Channel IPC(PL-C8648D4D)의 "이름 있는
Channel" 패턴 그대로다.

```jsonc
// 등록자 -> pubreg (Channel write, raw binary에 담긴 JSON)
{ "op": "register", "processName": "ahci-port0",
  "tools": [ { "name": "ahci.readBlocks", "description": "...",
               "inputSchema": {...}, "outputSchema": {...} } ],
  "channelId": 12345 }  // 이 프로세스가 이미 openChannel()로 만들어 둔, 실제 tool 호출을 받을 채널

// 소비자 -> pubreg (조회, 이름/설명 텍스트 매칭 또는 향후 태그 기반 - 구체 질의 문법은 착수 시 확정)
{ "op": "query", "match": "ahci" }

// pubreg -> 소비자 (응답 - 매칭된 tool 선언 + 연결 정보)
{ "results": [ { "processName": "ahci-port0", "tool": {...},
                 "channelId": 12345 } ] }
```

소비자는 응답의 `channelId`로 `connectChannel()`(SP-1FBC0EEB)해
등록자와 직접 연결한 뒤, 그 tool의 `inputSchema`에 맞는 JSON 요청을
Channel `write()`로 보내고 `outputSchema`에 맞는 JSON 응답을
`read()`로 받는다 - **"제어 채널 중계"의 실체는 여기까지다**:
`pubreg`는 신원(채널ID)만 중개하고, 실제 데이터는 `pubreg`를 거치지
않는다(예전 안의 커널 `InterfaceRegistry`와 같은 원칙, §7 참고 -
"디렉터리 서비스가 프록시가 아니다"라는 결론 자체는 유지됨).

**등록 해제**: 프로세스 종료 시(PN-71C3D483 Teardown Hook과 같은
정신 - 단, `pubreg`는 유저랜드 프로세스라 커널 후킹이 아니라
`pubreg` 자신이 Channel의 상대쪽이 끊겼음을 감지해 등록을 지운다,
Channel의 "닫힌 파이프"(SP-1FBC0EEB) 상태 확인으로 충분 - 새
메커니즘 불필요).

## 4. JSON 파싱 - 신규 라이브러리 필요

이 프로젝트에 지금까지 JSON 파서가 없었다(IPC는 지금까지 전부 raw
binary 고정폭 struct였음) - `pubreg`와, tool을 실제로 주고받는
프로세스들이 링크할 **`minicore/libs/libjson`**(신규) 신설이
필요하다. **[정정, 2026-09-15, 설계자 지시]** 유저 전용이 아니라
**커널/유저 공용**으로 구현한다 - `libelf`(`MINICORE_LIBELF_KERNEL`
매크로 게이팅, SP-68182FBD §2.4)와 동일한 패턴을 따라
`minicore/libs/libjson`에 매크로로 커널/유저 양쪽 링크를 분기한다
(기본값은 유저 영역용 컴파일, `libelf` 관례 그대로). CLAUDE.md
규칙 8에 따라 착수 시 RM-7C249618에 등재. 파서 자체의 설계(스트리밍
vs 전체 파싱, 메모리 할당 전략)는 이 문서 범위 밖 - 착수 시 별도 SP.

## 5. AHCI → fs 서비스 실사용 예 (**[무효화, 2026-09-15, 설계자
지시]** - 아래는 폐기된 예시, §5-A 참고)

**[무효화, 2026-09-15, 설계자 지시]** "AHCI → fs 서비스 실사용
같은건 이 스펙으로 가능하지 않아. 별도로 추가 설계해야해." - 아래
1~4단계는 devmgr이 스폰한 AHCI 드라이버 자식(`ProcessRole::
KernelService` 상속, RM-32D06563)이 `pubreg`에 **직접** `register`
하는 것을 전제하는데, §5-A가 새로 반영한 제약("커널 서비스는
pubreg에 직접 등록하지 않는다")과 정면으로 충돌한다 - 이 예시
전체가 성립하지 않으므로 후속 설계(PN-36E3164D)가 나올 때까지
폐기된 채로 보존한다(역사적 기록):

1. devmgr이 부팅 시 PCI 장치를 찾아 AHCI 드라이버 자식을 스폰
   (SP-9DD4F3EA §3.2).
2. 그 자식이 `probe()`+포트 스캔에 성공하면, `openChannel(name=null)`
   로 데이터 채널을 만들고 `pubreg`에 `register`(§3) - tool 이름
   예: `ahci.blockRead`/`ahci.blockWrite`, `inputSchema`에 LBA/개수,
   `outputSchema`에 데이터(또는 향후 §6 열린 질문대로 raw 채널
   재지정).
3. fs 서비스는 §2.5 `WaitForUserlandReady` 이후 `pubreg`에 `query`
   (예: `match: "ahci"` 또는 향후 구조화 태그)해 사용 가능한 블록
   장치 tool 목록+`channelId`를 얻는다.
4. 각 `channelId`로 `connectChannel()`해 실제 블록 IO를 수행 - 이때
   실제로 오가는 페이로드가 JSON인지(§6 열린 질문 참고) 원래 안대로
   raw binary(LBA 구조체)인지는 SP-C2670F69/§6에서 확정.

## 5-A. 커널 서비스는 pubreg에 직접 등록하지 않는다 (신설,
2026-09-15, 설계자 지시)

> 커널 서비스들이 pubreg에 뭔가를 등록하지 않아(성능문제, 프로토콜
> 유지보수 문제 등등). 유저 영역에서 `유저가 설치한 유저 서비스`가
> pubreg에 자신들의 동작을 등록해야해. 그러니까 결국, `유저 랜드`
> 에서 중계 패턴으로 구현된 무언가가 `대행`하는 방식이어야 하는거야.

정정 요지:
1. `pubreg`의 1차 등록 주체는 **"유저가 설치한 유저 서비스"**(devmgr/
   fs/net/tty 및 그 산하 드라이버 자식처럼 `ProcessRole::
   KernelService`인 프로세스가 아니라, 일반 유저 프로세스)다.
2. devmgr/fs/net/tty(및 AHCI 등 드라이버 자식)는 성능/프로토콜
   유지보수 부담 때문에 `pubreg`와 직접 통신하지 않는다.
3. 그럼에도 AHCI 같은 커널 서비스 산하 기능을 pubreg를 통해
   발견 가능하게 하려면, **유저랜드에 별도로 존재하는 "중계
   (relay) 패턴" 구성요소**가 커널 서비스를 대신해 `pubreg`에
   등록/조회를 대행해야 한다.

**[최종 확정, 2026-09-15, 설계자 답변 QU-722E72F5]** 이 중계
구성요소를 minicore 프로젝트 자신이 설계/구현하지 않는다 - "이
릴레이는 유저 영역에 설치될 앱들을 개발하는 제 3자가 만들어야
하는 부분으로 남겨두자." 이 세션이 초안(SP-40E5534D)을 작성해
승인을 요청했으나 거부됐다(PN-36E3164D는 `rejected`로 닫음).

**결론**: pubreg는 "유저가 설치한 유저 서비스"가 자기 자신을 직접
등록하는 경로로만 쓰인다 - devmgr/fs/net/tty 및 그 드라이버 자식이
제공하는 기능(예: AHCI 블록 장치)을 pubreg를 통해 발견 가능하게
만드는 것은 **이 프로젝트의 범위 밖**이다(제3자가 원하면 자신만의
대행 릴레이를 만들어 연동할 수 있는 여지는 pubreg의 공개 register/
query 프로토콜 자체로 이미 열려 있음 - 그 이상을 minicore가 미리
준비해 두지 않는다는 뜻). §5의 AHCI→fs 예시는 §5-B로 옮겨 "범위
밖" 상태로 보존한다.

## 5-B. AHCI → fs 서비스 실사용 (범위 밖 - 제3자 몫)

§5(무효화된 원안)가 전제했던 "devmgr 산하 AHCI 드라이버가 pubreg를
거쳐 fs에 발견되는" 흐름은 이 프로젝트가 직접 구현하지 않는다.
fs가 실제로 블록 장치를 찾는 경로는 pubreg와 무관한 별도
메커니즘(이미 있는 PnP "장치 열거 → IO 권한 요청" 패턴,
SP-9DD4F3EA §3.1/§6, `EnumerateDevices`/`RequestIoPermission`
syscall)을 그대로 쓴다 - 애초에 devmgr/fs는 둘 다 커널 서비스라
Tier B(`exclusivePreemptive` Channel, SP-00CA7175)로 직접
통신하도록 이미 설계돼 있으므로, pubreg를 거칠 필요 자체가 없었다.
pubreg는 커널 서비스 간 내부 발견용이 아니라 "유저가 설치한 유저
서비스"들 사이의 공개 발견용이라는 것이 이번 결정으로 명확해졌다.

## 6. 아직 열려 있는 설계 영역

1. ~~대용량 데이터(블록 IO 등)도 정말 JSON으로 주고받는가~~ -
   **[확정, 2026-09-16, QU-92578F9B 답변]** 설계자 답변: "tool
   정의만 JSON이고, 실제 도구 호출이나 인터렉션은 tool의 명세에
   따라서 달라져야해." - §6의 v1 제안(2단계 방식) 그대로 확정됐다:
   `pubreg`가 들고 있는 **tool 정의(선언) 자체는 항상 JSON**이지만,
   그 정의를 보고 실제로 tool을 호출하는 인터랙션의 payload 형식은
   **tool의 명세(각 tool이 스스로 규정)에 따라 자유**다 - AHCI
   블록 IO처럼 대용량인 tool은 raw binary 프로토콜을 명세로 삼으면
   된다(Channel IPC 페이지 크기 한도와 충돌 없음). 같은 답변의
   "Registry에 관한 중계를 커널이 맡고" 부분은 §3의
   `connectChannel()`(기존 Channel IPC, PL-C8648D4D의 커널 syscall)
   이 실제 채널 연결을 중계한다는 이미 있던 사실의 재확인이다 -
   `pubreg`가 새로 커널 기능을 갖는다는 뜻이 아니다(§0의 "커널
   관련 명세는 다른 문서로" 지시와 모순 없음 - `connectChannel`
   자체는 이미 SP-1FBC0EEB에 있는 기존 커널 syscall). **[정정,
   2026-09-15, 설계자 지시]** "tool을 호출하는 인터랙션의 payload
   라기 보다는 그 끝점의 통신 방식 자체가 tool의 명세에 따라
   달라지는거야" - 즉 tool마다 달라지는 것은 단순히 같은 Channel
   위에서 오가는 바이트 형식(JSON vs raw binary)만이 아니라, **그
   호출을 실어 나르는 통신 수단/끝점 자체**(예: 일반 Channel IPC
   vs SP-00CA7175의 Tier A 공유메모리 링버퍼 같은 완전히 다른
   메커니즘)까지도 tool의 명세가 규정할 수 있다는 뜻이다 - `pubreg`
   가 응답으로 주는 `channelId`는 그 tool의 "기본 연결 지점"일
   뿐, 그 너머의 실제 프로토콜/전송 수단은 전적으로 tool 명세에
   위임된다.
2. **tool 선언의 정확한 JSON Schema 버전/문법**: **[방향 확정,
   2026-09-15, 설계자 지시]** "가능한 현재 최대 표준 정의대로 만들지만,
   아무래도 통신 방식이라던지, 이런 것들이 달라질 수 있어야 하기에
   방언을 채택해야할지 요걸 별도로 검토해봐." - 기본은 최신 표준
   JSON Schema(Draft 2020-12) 그대로 채택하되, §6-1이 이미 확정한
   "통신 방식 자체가 tool 명세마다 다를 수 있다"는 점을 선언에서
   표현하려면 표준 JSON Schema만으로는 부족할 수 있다(예: 어떤 tool이
   raw binary 프로토콜을 쓰는지, 기본 Channel 외의 다른 연결 지점을
   쓰는지 명시할 필드가 표준 Schema 어휘에는 없음) - **착수 시 이
   프로젝트 전용 확장 필드(예: `x-minicore-transport` 같은 JSON
   Schema의 관례적 `x-` 확장 키)로 방언화할지 검토 필요, 아직 확정
   아님(설계자가 명시적으로 "검토"를 지시).**
3. **`query`의 매칭 문법**: 자유 텍스트 부분일치로 충분한지, MCP
   서버 디스커버리처럼 구조화된 태그/카테고리가 필요한지.
4. **`pubreg` 자신의 크래시/재시작 시 등록 복구**: **[확정,
   2026-09-15, 설계자 지시]** "얘가 결국 최종적으로 들고 있는 것은
   `JSON`데이터 뿐이고, 페이로드를 해당 유저 랜드 프로세스에게
   던져주는 역할만 하니, 끊김, 연결됨 등의 상태 관리만 하고 있으면
   자동으로 해결될거야." - 위 두 선택지 중 **전자(등록자가 자동
   재등록)로 확정** - `pubreg`가 크래시/재시작(PN-645CF608
   Resurrect)되면 기존 등록자와의 Channel이 전부 끊기므로(§3의
   "닫힌 파이프" 감지가 이미 다루는 것과 동일한 상태), `pubreg`
   자신은 별도 복구 로직 없이 빈 테이블로 재시작하면 되고, 살아있는
   등록자들이 (재연결 시도 시점에) 자연스럽게 다시 `register`한다 -
   `pubreg`가 살아있는 프로세스 목록을 능동적으로 스캔하는 경로는
   불필요.

## 6-4. [제안, 2026-09-18, QU-E05A55AD 3번 답변 후속] register/query
프로토콜 바이너리 직렬화 검토안 - 설계자 확인 대기

설계자가 QU-E05A55AD에서 §6-3(query 매칭 문법)/§6-2(스키마 방언)
답변과 함께 "1)/2) 전체를 뒤집을 수도 있는" 방향을 제시했다:
"JSON을 버리고 바이너리로 전환 검토를 해야 할 수도 있겠다. 일단
바이너리로 직렬화 하는 계획안을 작성해봐. 그걸 보고 결정하자." -
이 §6-4는 그 요청에 따른 **비교 검토용 제안**이다(아직 확정 아님 -
아래 §6-4.7의 승인 질의로 확인 요청).

### 6-4.1 왜 바이너리가 검토 대상이 됐는가 (추정)

`libjson`(SP-CCACB192)이 **SAX 콜백 파서(DOM 없음)**라는 점이 근본
원인으로 보인다 - QU-E05A55AD 자신의 "기술적 제약 참고" 절이 이미
지적했듯, `query`가 실제로 tool 목록을 매칭/열거하려면 등록된 JSON을
구조화된 형태로 유지해야 하는데, SAX 파서로는 임의 중첩 JSON을
일반적으로 보관하려면 원본 바이트 구간(byte span)을 통째로 복사해
두는 수밖에 없다 - 이러면 사실상 "그냥 원본 바이트를 그대로 들고
있는" 것과 큰 차이가 없어지고(§6-2 opaque passthrough가 반려된 이유),
그렇다고 완전한 JSON DOM(임의 트리 구조를 가리키는 포인터 그래프)을
새로 구현하는 것은 이 커널의 "동적 할당 없음, 고정 상한" 컨테이너
관례와 정면으로 부딪힌다.

### 6-4.2 핵심 아이디어 - "봉투는 바이너리, 내용물은 여전히 자유"

**§6-1(QU-92578F9B 답변, "tool 정의만 JSON")은 그대로 유지 가능하다**
- 이 제안이 바꾸는 것은 "메시지를 감싸는 봉투(envelope)의 인코딩"
뿐이고, `inputSchema`/`outputSchema` **내용물 자체는 여전히 원하는
어떤 바이트열이든(JSON Schema 텍스트 포함) 담을 수 있는 길이-접두
(length-prefixed) opaque 바이트 블록**으로 취급한다 - §6-2(스키마
방언)의 미확정 상태와 전혀 충돌하지 않는다. 대신 **`name`/`description`/
`channelId`처럼 `query` 매칭에 실제로 필요한 필드만 봉투 자체의
고정 폭 필드로 승격**한다 - 이 필드들은 이제 JSON 파싱을 전혀
거치지 않고 길이-접두 바이트 복사만으로 pubreg의 고정 상한 테이블에
그대로 들어간다(`libjson`이 필요 없어짐 - `pubreg` 자신은 이제
`libjson`을 링크하지 않아도 된다).

### 6-4.3 와이어 포맷 초안

Channel IPC(SP-1FBC0EEB)는 raw binary 스트림이라 메시지 경계가
없으므로, 모든 메시지는 자기 자신의 전체 길이를 담은 고정 헤더로
시작한다(리틀 엔디안, x86_64 네이티브 - 네트워크 바이트 순서 불필요,
이 채널은 항상 로컬 프로세스 간이므로).

```cpp
// minicore/libs/libkcont류가 아니라 pubreg 전용 프로토콜 헤더 -
// 어디 둘지(pubreg 전용 vs 신규 공용 라이브러리)는 §6-4.6 참고.
struct PubregMessageHeader {
    uint32_t totalLength;  // 이 헤더 포함 메시지 전체 바이트 수
    uint8_t opcode;        // 1=Register, 2=QueryRequest, 3=QueryResponse
    uint8_t reserved[3];   // 정렬용, 항상 0
};

// 길이-접두 문자열/바이트 블록 - 이 프로토콜 전체가 재사용하는 최소 단위.
// (uint32 length, 그 뒤 length바이트, null 종단 없음)

// opcode=1 (등록자 -> pubreg)
struct PubregRegisterMessage {
    PubregMessageHeader header;
    /* uint16 len + bytes */         processName;
    uint64_t                          channelId;   // 이 프로세스가 이미 openChannel()로 열어 둔, 실제 tool 호출을 받을 채널
    uint32_t                          toolCount;
    // toolCount번 반복:
    //   /* uint16 len + bytes */    name;          // query 매칭 대상 - 항상 파싱됨
    //   /* uint16 len + bytes */    description;   // query 매칭 대상 - 항상 파싱됨
    //   /* uint32 len + bytes */    inputSchema;   // opaque - JSON Schema 텍스트 등 자유(§6-2 미확정 그대로 유지)
    //   /* uint32 len + bytes */    outputSchema;  // opaque
};

// opcode=2 (소비자 -> pubreg)
struct PubregQueryRequest {
    PubregMessageHeader header;
    uint8_t  mode;      // 0=전체 획득, 1=문자열 매칭 (QU-E05A55AD 1번 답변 그대로)
    /* mode==1일 때만 */ /* uint16 len + bytes */ match;
    uint32_t offset;    // 페이지네이션(QU-E05A55AD 1번 답변 - 필수)
    uint32_t count;     // 이번 응답에 담을 최대 개수
};

// opcode=3 (pubreg -> 소비자)
struct PubregQueryResponse {
    PubregMessageHeader header;
    uint32_t totalMatched;    // 페이지네이션 전체 개수(offset/count와 무관하게 조건에 맞는 전체 수)
    uint32_t returnedCount;   // 이번 응답에 실제로 담긴 개수(<= 요청 count)
    // returnedCount번 반복, 각 항목:
    //   /* uint16 len + bytes */    processName;
    //   uint64_t                    channelId;
    //   /* uint16 len + bytes */    name;
    //   /* uint16 len + bytes */    description;
    //   /* uint32 len + bytes */    inputSchema;   // opaque, 등록 시 받은 그대로 되돌려줌
    //   /* uint32 len + bytes */    outputSchema;
};
```

**pubreg 내부 저장**(이 프로젝트의 "동적 할당 없음, 고정 상한"
컨테이너 관례 - `NamedObjectTable`의 `kMaxNamedObjects=128`류와 동일
패턴): 등록 프로세스 수/프로세스당 tool 수/name·description 길이/
schema 바이트 크기 전부 컴파일타임 고정 상한(정확한 숫자는 착수 시
실측하며 확정, RM-23F4B687 §4) - `inputSchema`/`outputSchema`는
그 상한 안에서 원본 바이트를 그대로 복사해 보관(여전히 opaque,
§6-2 그대로).

### 6-4.4 이 프로토콜과 `libkproto`(SP-30FCC8AE §1-D)의 관계 - 겹치지 않음

`SP-30FCC8AE` §1-D가 신설한 `libkproto`(Request/Response/
Notification + discriminator, 바이너리)는 명시적으로 **"커널
자신이 당사자인" 프로토콜**(예: authmgr) 전용으로 범위를 그어 뒀고,
"커널이 중개만 하고 실제 양 당사자는 유저 프로세스인" `pubreg`류
프로토콜과는 무관하다고 이미 확정했다(그 문서 인용: "이건 `pubreg`
하나만의 프로토콜이 아니라 **커널 자신이 당사자인** 모든 커널-서비스
프로토콜... 범위 명확화: 이건 커널 자신이 당사자인 프로토콜에
적용되지, 커널이 중개만 하고 실제 양 당사자는 유저 프로세스인
프로토콜(예: pubreg)과는 무관하다"). **이 제안이 그 경계를 흔들지
않는다** - `pubreg`가 JSON에서 바이너리로 바뀌어도 `pubreg`는
여전히 커널이 당사자가 아닌 유저-유저 발견 프로토콜이므로
`libkproto`를 재사용할 이유도, `libkproto`의 범위를 넓힐 이유도
생기지 않는다 - 우연히 비슷한 모양(길이-접두+discriminator)이 될
뿐 별개의 독립 구현으로 남는다. **다만 이 위 문단 자체가 이번
제안의 부수 효과로 새로 드러난 사실이라 설계자 확인 대상에 포함**
(아래 §6-4.7 질의 2번).

### 6-4.5 JSON(기존안) vs 바이너리(이 제안) 비교 요약

| | JSON(§0-§6-3 원안, `libjson`) | 바이너리(이 제안) |
|---|---|---|
| tool 정의 자체(§6-1 확정) | JSON | 그대로 JSON 가능(§6-4.2 - schema 필드에 opaque로 담음) |
| `pubreg` 구현 복잡도 | `libjson` SAX 파싱 필요 - 임의 중첩 구조 보관이 byte-span 우회에 의존 | `libjson` 불필요 - 길이-접두 필드 복사만 |
| `name`/`description` 매칭(query) | byte-span 저장 후 재파싱 필요(부담스러움, 이번 검토의 계기) | 봉투 고정 필드라 즉시 비교 가능 |
| 등록자/소비자 구현 부담 | `libjson`(이미 커널/유저 공용 구현됨) 사용 | 이 구조체를 직접 채우거나 별도 헬퍼 필요(§6-4.6) |
| 사람이 읽기(디버깅) | 쉬움(텍스트) | 어려움(hex dump 필요, 헬퍼 없이는) |
| §6-2 스키마 방언 미확정과의 관계 | 원래도 무관 | 무관(그대로 유지) |
| `libkproto`와의 관계 | 무관 | 무관(§6-4.4) |

### 6-4.6 열려 있는 하위 질문 (착수 시 확정 - 승인 이후)

1. 등록/조회 헬퍼 함수를 `userland/libs/libmc`에 pubreg 전용으로
   둘지, 아니면 이 문서가 새 공용 라이브러리(`minicore/libs/
   libpubregproto`류)를 신설할 만큼 다른 소비자가 예상되는지 -
   지금은 등록자/소비자가 각자 손으로 이 구조체를 채우는 v1으로
   제안(과설계 방지, RM-23F4B687 §4).
2. `name`/`description`/`processName`의 정확한 최대 길이, 프로세스당
   최대 tool 수, pubreg 전체 최대 등록 프로세스 수 - 착수 시 실측
   기준으로 확정.

### 6-4.7 승인 질의

이 §6-4 전체(바이너리 채택 여부, 채택 시 위 와이어 포맷)에 대해
`docs question`(kind=approval)으로 별도 승인 요청을 등록한다 -
거부되면 §0-§6-3의 JSON 원안이 그대로 유효하고 이 §6-4는 "검토했으나
채택 안 됨"으로 표시한다.

## 7. 폐기된 이전 설계 (역사적 기록, 2026-09-15~16 사이 짧게 유효했음)

원래 이 문서는 **커널 내부 자료구조**(`kernel::InterfaceRegistry`)
