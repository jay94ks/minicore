설계자 지시(2026-09-16, 메시지) - "FS 서비스 및 devmgr 서비스 설계 착수하라"에 따라, SP-8B6B8D25 §2 12번("프로세스간 '공개 인터페이스' registry 및 제어 채널 중계")이 요구하는 커널 서브시스템을 계획 PN-268F062B의 실제 설계로 구체화한다. DS-D4E5C451(QU-6EEFDBEE 답변)이 "구현하면서 보강"하기로 열어 둔 영역이지만, 이제 선행 조건(프로세스 모델 PN-16CA347D, Channel IPC PL-C8648D4D, Syscall 서브시스템 PL-21344323)이 전부 완료돼 착수 가능하다.

## 1. 이 문서가 푸는 문제

devmgr이 PCI 장치를 발견하고(SP-9DD4F3EA §3.1) 자식 드라이버 프로세스를 스폰해(§3.2) 각자 블록 장치/네트워크 인터페이스 등을 Channel IPC(PL-C8648D4D)로 노출하기 시작하면, **그 Channel을 실제로 쓰고 싶은 소비자(fs 서비스가 AHCI 블록 장치를 찾는 경우 등)가 어떻게 "어떤 드라이버가 어떤 인터페이스를 제공하는지" 알아내는가**라는 문제가 남는다. `/sys/live/named/`(SP-1FBC0EEB)는 "정확한 이름을 이미 아는 경우"의 채널 발견만 푼다 - 소비자가 미리 정확한 이름(예: 몇 번째 AHCI 포트인지)을 알아야 하는데, 그건 부팅마다/하드웨어마다 달라 미리 정할 수 없다. §2 12번이 요구하는 것은 **"이런 종류의 인터페이스를 제공하는 게 누구냐"는 질의(kind 기반 탐색)**와 **그 답으로 받은 Channel 신원을 실제로 연결 가능한 형태로 전달(중계)**하는 별도 계층이다.

## 2. 핵심 설계 - 새 IPC 메커니즘이 아니라 새 커널 syscall 두 개

새 원시 IPC 오브젝트(예: 별도 레지스트리 전용 Channel 종류)를 만들지 않는다 - SP-9DD4F3EA §3.1 `EnumerateDevices`(PCI 장치 목록을 페이지네이션으로 열거)와 **완전히 같은 패턴**을 프로세스가 스스로 등록하는 "논리 인터페이스"에 적용한다. 저장/조회 전부 **커널 자체의 내부 테이블**(§2 12번이 "커널이 담당하는 범위"로 명시했으므로 `/sys/live/named/`의 `NamedObjectTable`과 같은 층위 - 유저랜드 devmgr 프로세스에 위임하지 않는다) - `minicore/kernel/interface_registry.h/.cpp`(가칭).

### 2.1 자료구조

```cpp
namespace kernel {

using InterfaceKind = uint32_t;  // 값 목록은 §2.4

struct InterfaceEntry {
    InterfaceKind kind;
    ProcessId owner;             // 이 인터페이스를 등록한 프로세스(죽으면 자동 회수)
    uint64_t channelId;          // PL-C8648D4D의 ChannelId(=Channel 구조체 포인터, 이미 "다른 프로세스에게 전달 가능"한 값)
    uint8_t metadata[kMaxInterfaceMetadataLen];  // kind별 자유 형식(raw binary, DS-D4E5C451) - 예: BlockStorage면 논리 블록 크기/총 섹터 수
    uint32_t metadataLen;
    bool used = false;
};

class InterfaceRegistry {
public:
    static bool init();
    // 등록 - 성공 시 이 등록을 나중에 명시적으로 해제할 때 쓰는 핸들 반환.
    static InterfaceHandle publish(ProcessId owner, InterfaceKind kind,
                                    uint64_t channelId,
                                    const uint8_t* metadata, uint32_t metadataLen);
    static bool unpublish(InterfaceHandle handle, ProcessId caller);  // caller가 owner가 아니면 거부
    // kind로 필터링해 열거 - EnumerateDevices와 동일한 페이지네이션 관례.
    static uint32_t query(InterfaceKind kind, uint32_t startIndex,
                           InterfaceEntry* outEntries, uint32_t capacity,
                           uint32_t* outTotalCount);
    // 프로세스 종료 시퀀스(PN-71C3D483 Teardown Hook)가 호출 - 그 프로세스가
    // 등록한 모든 InterfaceEntry를 일괄 회수(Channel/DeviceOwnerTable과 동일한
    // "소유자 죽으면 자동 정리" 관례, SP-9DD4F3EA §3.3a 선례 재사용).
    static void releaseAllOwnedBy(ProcessId owner);
};

}  // namespace kernel
```

### 2.2 Syscall API (SyscallRegistry, PL-21344323 패턴)

```cpp
// 제공자(예: AHCI 드라이버 자식 프로세스) → 커널
struct PublishInterfaceArgs {
    InterfaceKind kind;             // in
    uint64_t channelId;             // in - 이 프로세스가 이미 openChannel()로 만들어 둔 채널
    const uint8_t* metadata;        // in
    uint32_t metadataLen;           // in
    // out
    ChannelError error;             // MetadataTooLarge 등
    InterfaceHandle handle;
};

struct UnpublishInterfaceArgs {
    InterfaceHandle handle;         // in
    ChannelError error;             // out: NotFound / NotOwner
};

// 소비자(예: fs 서비스) → 커널
struct QueryInterfacesArgs {
    InterfaceKind kind;              // in
    uint32_t startIndex;             // in (페이지네이션, EnumerateDevices와 동일)
    uint32_t capacity;                // in/out
    InterfaceEntry* outEntries;       // out - channelId를 그대로 받아 connectChannel()에 넘기면 됨
    uint32_t totalCount;              // out
};
```

`QueryInterfacesArgs`가 돌려주는 `channelId`를 소비자가 그대로 `connectChannel(channelId)`(SP-1FBC0EEB)에 넘기면 실제 데이터 채널이 연결된다 - **"제어 채널 중계"의 실체는 이 한 걸음**이다: 커널이 실제 데이터를 대신 전달(proxy)하는 게 아니라, "누구의 Channel인지"를 대신 찾아 그 신원(=`channelId`, 이미 확립된 "포인터값을 그대로 전달" 관례, PL-21344323/SP-1FBC0EEB "ChannelId 전달" 절)을 소비자에게 건네주는 중개 역할만 한다 - 새로운 데이터 경로를 만들지 않고 기존 Channel IPC 위에 "탐색" 계층 하나만 얹는 것이 이 설계의 핵심(불필요한 복잡도 회피).

### 2.3 소유권/정리

`InterfaceRegistry::releaseAllOwnedBy`는 `DeviceOwnerTable` 정리(SP-9DD4F3EA §3.3a)와 나란히 **PN-71C3D483의 Process Teardown Hook에 새 항목으로 추가**해야 한다 - 드라이버 자식 프로세스가 죽으면(crash-restart 포함, PN-645CF608 Resurrect) 그 프로세스가 등록해 둔 인터페이스도 반드시 같이 사라져야 소비자가 죽은 채널로 연결을 시도하는 일이 없다. Resurrect로 재시작되면 그 드라이버가 `probe()`를 다시 통과하며 새 Channel로 다시 `publish()`하므로 registry는 자연히 최신 상태로 복구된다(추가 특수 로직 불필요 - devmgr/fs 재시작과 같은 패턴).

### 2.4 `InterfaceKind` 초기 값 (v1, 확장 가능)

| 값 | 의미 | metadata 형태(제안) |
|---|---|---|
| 1 | `BlockStorage` | 논리 섹터 크기(4B)+총 섹터 수(8B) - SP-C2670F69 §"열려 있는 것" 2번(블록 장치↔fs 프로토콜)이 착수 시 이 metadata를 구체화 |
| 2 | `NetworkInterface` | MAC 주소(6B) 등 - net 서비스/드라이버 착수 시 구체화 |
| 그 외 | 착수 시점에 이 표에 행 추가(RM-32D06563에도 함께 기록) | |

숫자 자체(정확한 바이트 레이아웃)는 각 소비자(fs/net)가 실제로 착수할 때 확정하는 구현 세부로 남긴다(RM-23F4B687 §4 취지 - 지금 확정할 필요 없는 수준).

## 3. `/sys/live/named/`와의 관계 - 대체가 아니라 역할 분담

| | `/sys/live/named/`(기존, SP-1FBC0EEB) | `InterfaceRegistry`(신규, 이 문서) |
|---|---|---|
| 조회 키 | 정확한 이름(문자열) | `InterfaceKind`(종류) - "이름을 몰라도" 찾음 |
| 용도 | 이미 이름을 약속한 두 프로세스의 랑데부(예: 향후 `svc/fs`처럼 고정 이름을 쓸 단일 인스턴스 서비스) | "몇 개가 있는지/어떤 것들이 있는지 미리 모르는" 동적 발견(예: AHCI 포트가 몇 개인지는 부팅마다 다름) |
| 보안 정책 | 종류 은닉(이름 충돌 시 종류를 알려주지 않음) | 명시적으로 kind를 노출(발견이 목적이므로 은닉할 이유가 없음 - 등록 자체가 "나는 이런 인터페이스를 제공한다"는 공개 선언) |

둘 다 필요하다 - 배타적이지 않다. 예: fs 서비스가 devmgr 자체와 통신할 고정 채널이 필요하면 `/sys/live/named/svc/devmgr`류 이름을 계속 쓸 수 있고, "지금 이 부팅에서 AHCI 블록 장치가 몇 개 있는지"처럼 매번 달라지는 목록은 `InterfaceRegistry`로 푼다.

### 3.1 범위 한정 - "커널 ↔ 커널 서비스" 통신과는 별개 (설계자 지시,
2026-09-16, 메시지)

**중요한 경계 정정**: "이 계획안은 `유저랜드` 프로세스간 `공개
경로`야. `커널`과 `커널 서비스`가 통신하는 방식과 공존할 수 없어.
`커널`과 `커널 서비스`가 통신하는 경로는 `고속`이라는 제약 조건이
따라 붙기 때문에 전용 채널을 분리해야해."

이 문서(`InterfaceRegistry`)가 다루는 범위는 **유저랜드 프로세스
둘(예: devmgr이 스폰한 AHCI 드라이버 자식 ↔ fs 서비스) 사이의 발견/
연결**로 명확히 한정한다 - 둘 다 syscall 디스패치(SP-04EE2A18의
AsyncTask/리액터 모델)를 거치는 일반 경로이고, 그 위에 얹히는 실제
데이터 채널(§4의 `AhciBlockDevice` read/write 등)도 일반 Channel
IPC(PL-C8648D4D)다 - **"고속" 제약이 없는 일반 프로세스간 통신**이다.

**"커널과 커널 서비스가 통신하는 방식"(devmgr/fs/net/tty 자신이
커널과 직접 주고받는 제어 트래픽 - 예: 인터럽트 라우팅 통지, IO
권한 그랜트/철회, PnP 핫플러그 이벤트)은 이 `InterfaceRegistry`를
쓰지 않는다** - 그 자체가 이 문서와 공존할 수 없는 **별도의 전용
고속 채널**이어야 한다는 것이 설계자 지시다. 그 전용 채널 자체의
설계(무엇이 "고속"을 만족시키는 구조인지 - 예: 일반 syscall
submit/wait 왕복을 우회하는 공유메모리 링버퍼, 또는 별도 저지연
IPI/트랩 경로 등)는 **이 문서의 범위 밖**이며 아직 어디에도 설계돼
있지 않다 - 새 DC/질의로 별도 등록한다(§6 참고, CLAUDE.md 규칙 4).

## 4. AHCI → fs 서비스 실사용 예 (SP-C2670F69 §"열려 있는 것" 2번 해소)

1. devmgr이 부팅 시 `Pci::enumerate()` 결과로 AHCI 컨트롤러를 찾아 드라이버 자식 프로세스를 스폰(SP-9DD4F3EA §3.2).
2. 그 자식이 `probe()`+포트 스캔에 성공하면, 포트마다 `openChannel(name=null)`로 데이터 채널을 만들고 `PublishInterface(kind=BlockStorage, channelId=..., metadata={섹터크기, 섹터수})`를 호출.
3. fs 서비스는 부팅 초기 마운트 등록(SP-7CC5693A §2.3) 이후, 실제 파일시스템 자동 감지(§2.5 `WaitForUserlandReady` 이후)에 들어가기 전 `QueryInterfaces(kind=BlockStorage)`를 호출해 사용 가능한 모든 블록 장치 목록+채널ID를 얻는다.
4. 각 채널ID로 `connectChannel()`해 `AhciBlockDevice`(SP-C2670F69 §2)의 실제 read/write API를 그 위에서 호출 - 이때 오가는 요청/응답의 정확한 메시지 포맷(LBA 읽기/쓰기 등)은 SP-C2670F69가 이미 "fs 서비스 설계와 맞물려야 한다"고 열어 둔 부분으로, 이 문서가 아니라 그 문서(또는 후속 계획)에서 구체화한다 - 이 문서는 "채널을 찾아 연결하는 것"까지만 책임진다.

## 5. 선행 조건 / 관련 계획

- 프로세스 모델(PN-16CA347D, 완료), Channel IPC(PL-C8648D4D, 완료), Syscall 서브시스템(PL-21344323, 완료) - 전부 충족.
- PN-71C3D483(프로세스 종료 시퀀스) - Teardown Hook에 `InterfaceRegistry::releaseAllOwnedBy` 추가 필요(§2.3).
- SP-9DD4F3EA §3.2(devmgr 드라이버 자식 스폰) - 이 문서의 `publish()` 호출자.
- SP-C2670F69(AHCI)/SP-E35FD36C(USB) - 실제 `BlockStorage`/`NetworkInterface` metadata 형태를 구체화할 소비자.
- 이 문서 자체의 구현은 별도 계획으로 등록 필요(§6).

## 6. 남은 것

- 이 설계의 실제 구현(커널 `interface_registry.h/.cpp` + syscall 3종 등록)을 별도 PN 계획으로 등록해야 한다(CLAUDE.md 규칙 7).
- `kMaxInterfaceMetadataLen`/최대 등록 개수 같은 v1 상수는 구현 착수 시 확정(RM-23F4B689 §4 취지).
- RM-48E1E610(Syscall 할당표)에 `PublishInterface`/`UnpublishInterface`/`QueryInterfaces` 번호 예약 필요(구현 착수 시).
- **[추가, 2026-09-16]** §3.1이 명시한 "커널 ↔ 커널 서비스 전용
  고속 채널"은 이 문서와 완전히 별개의 새 설계 대상이다 - **DC-6E2500A6**
  로 등록(설계자 지시 원문 인용 + "고속"의 구체적 기준을 무엇으로
  삼을지 확인 필요).
