# Minicore 초기 QA 시나리오 — 부팅/커널 기본 동작

구현이 진행되면서 실측 확인된 항목만 체크 표시로 옮긴다(날짜/환경
명시). 체크 안 된 항목은 아직 검증 안 됨.

## 부팅

- [x] `--kernel`/`--initrd` 옵션으로 QEMU에 이미지를 직접 전달해
      커널이 부팅된다. (2026-09-14, QEMU 8.2.2, PVH 경로로 실측 확인 -
      `scripts/run-qemu.sh`)
- [x] 시리얼 포트로 커널 로그가 정상 출력된다. (2026-09-14 실측 -
      "minicore: booted via Xen PVH" + "hvm_start_info magic OK")
- [x] PVH(QEMU) 경로로 부팅된다. (2026-09-14 실측 - higher-half long
      mode 전환까지 확인, 트리플 폴트 없음)
- [x] multiboot2 경로로 부팅된다(PL-FC38956C 완료, 2026-09-14) - PVH가
      이미 검증해 둔 "GDT 적재/페이지 테이블 구성/long mode 전환/
      higher-half 점프" 자산을 `common_32bit_entry` 서브루틴으로 뽑아
      `pvh_start`/`mb2_start` 두 진입점이 공유한다. `mb2_start`는 EAX
      매직(0x36d76289) 확인 후 진입, 링커 전역 `ENTRY()`는 여전히
      `pvh_start`라 GRUB 전용 Entry Address 태그(멀티부트2 헤더
      type 3)로 `mb2_start`를 지정했다. multiboot2 정보 구조체(태그
      기반 가변 길이)는 `Multiboot2Info::parse`가 PVH의
      `HvmMemmapEntry` 배열/RSDP 물리주소와 같은 형태로 변환해
      `kMain`이 그 뒤로는 프로토콜을 구분할 필요가 없게 한다. **실측
      (2026-09-14, QEMU 8.2.2, `grub-mkrescue` 2.12 + 실제 GRUB
      부트로더 경유, `scripts/run-grub.sh` 신설)**: ISO를 만들어
      `-cdrom`으로 부팅 - "minicore: booted via multiboot2 (GRUB,
      higher-half, long mode)" 배너부터 메모리맵(PVH와 완전히 동일한
      7개 엔트리)/ACPI MADT+SRAT(RSDP 태그 파싱 경유로 정상 접근)/
      LAPIC/IOAPIC/HPET/PCI 열거까지 PVH 경로와 100% 동일한 로그로
      완주 확인. `scripts/run-qemu.sh`(PVH)도 리팩터 후 회귀 없이
      그대로 동작함을 재확인. **재작업(2026-09-14, QU-9DCDCE3E)**:
      커맨드라인/모듈/부트로더 이름 태그도 전부 파싱해 통합
      `BootInfo` 구조체(PVH의 hvm_start_info cmdline/module 필드도
      같이 통일)로 노출, CPIO("New ASCII Format") 파서를
      `minicore/libs/libcpio`로 신설(kernel/userland 공용). 실제
      newc CPIO 아카이브(파일+디렉터리+중첩 파일)를 GRUB `module2`로
      실어 부팅 - 커맨드라인/부트로더 이름/모듈 물리범위/모듈별
      커맨드라인이 전부 정확히 파싱되고, 그 모듈을 CPIO로 실제로
      훑어 3개 엔트리(파일명/크기/모드)가 원본과 정확히 일치함을
      실측 확인. PVH 경로의 `-append` 커맨드라인 파싱도 회귀 없이
      정상 동작.
- [ ] BIOS 경로로 부팅된다.
- [ ] EFI(UEFI) 경로로 부팅된다.

## 커널 기본 동작

- [ ] 유저랜드 준비(첫 프로세스 기동)까지 성공한다.
- [ ] SMP 환경에서 여러 코어가 정상적으로 스케줄링된다 - **AP 기동
      자체는 완료(PL-65C20380, 2026-09-14, 아래 항목 참고), 스케줄러가
      없어 "스케줄링"은 여전히 범위 밖**이다.
- [x] SMP AP(BSP 이외 코어)가 실제로 깨어난다(PL-65C20380 완료,
      2026-09-14) - `ap_trampoline.S`(물리주소 0x8000에서 16비트
      실모드로 시작, 임시 GDT로 32비트 진입 → boot.S의 진짜 GDT/
      `enable_long_mode`(재사용, `setup_page_tables`는 다시 안 부름)
      로 갈아탐 → 64비트 `ap_long_mode_entry` → C++ `kApMain`).
      `Lapic::sendInitIpi`/`sendStartupIpi`(ICR, xAPIC 2레지스터/
      x2APIC 단일 MSR 분기)로 BSP가 INIT-SIPI-SIPI를 순차 전송,
      `AtomicU32` 카운터로 기동 완료를 Timer 틱 기반 타임아웃으로
      확인. **실측(2026-09-14, QEMU 8.2.2)**: `-smp 2/4/8` 전부에서
      기대한 개수(1/3/7)만큼 AP가 정확히 기동해 각자 시리얼에 자기
      APIC ID를 찍고 idle(hlt 루프)에 들어감을 확인. x2APIC(`-accel
      kvm -cpu host`)·multiboot2(GRUB ISO) 경로 둘 다에서도 동일하게
      동작 확인(회귀 없음, 조합 전부 검증). 기본(smp 지정 없음, 1코어)
      환경에서도 "APs started=0 expected=0"으로 정상 처리(회귀 없음).
      실측 과정에서 진짜 버그 2개 발견/수정: (1) QEMU의 PVH 로더가
      물리주소 0x8000 전용 별도 PT_LOAD 세그먼트를 게스트 메모리에
      안 올려서, 트램폴린을 이미 정상 로드되는 `:boot` 세그먼트
      안에 저장해 두고 부팅 후 진짜 0x8000으로 memcpy하는 방식으로
      전환. (2) AP가 SIPI 직후 스택 포인터가 정의되지 않은 채로
      시작해서 32비트 진입 직후의 push+retf가 깨졌었음 - 트램폴린
      전용 임시 스택(<0x10000, 16비트 real mode SP 제약 때문에 낮은
      트램폴린 페이지 안에 둠)을 추가해 해결. 두 버그 모두 관계도에
      기록.
- [x] CPU 예외(벡터 0-31)가 발생하면 IDT를 거쳐 진단 로그(벡터명/
      에러코드/RIP/CS/RFLAGS, 페이지폴트는 CR2도)를 남기고 멈춘다.
      (2026-09-14 실측 - 의도적 int3(Breakpoint)로 확인, 이후 커밋에서
      제거함).
- [x] 하드웨어 타이머 인터럽트(LAPIC, 100Hz)가 실제로 반복 발생하고
      EOI 이후 계속 들어온다(2026-09-14 실측 - tick 카운트가 5회
      연속 증가함을 확인, 이후 테스트 코드 제거). PIC은 완전히
      마스크해 죽여 둠 - 레거시 IRQ 없음.
- [x] ACPI(RSDP→XSDT→MADT)를 파싱해 로컬 APIC 주소/코어 APIC ID
      목록/IO APIC 주소를 얻는다(2026-09-14 실측 - QEMU 기본 1코어
      환경에서 cpu_count=1, apic_id=0 확인).
- [ ] 인터럽트가 발생하면 올바른 커널 서비스로 라우팅된다.
- [ ] 프로세스 간 IPC 메시지가 의도한 커널 서비스로 전파된다.
- [x] 페이지 폴트 기반 on-demand 맵핑이 동작한다 - `Paging::kMapPage`가
      필요한 PML4/PDPT/PD/PT를 그때그때 만들어 임의 가상주소를 물리
      프레임에 매핑한다. (2026-09-14 실측 - 매핑한 가상주소로 쓰고
      direct physical map 별칭으로 같은 값을 읽어 확인, 이후 코드는
      제거함)
- [x] #PF(vector 14)가 나면 `Paging::kHandlePageFault`가 "지연 매핑
      구역"(`kLazyZoneBase`) 안의 not-present 폴트를 새 프레임 매핑
      으로 조용히 해결하고 재실행시킨다 - 양성(구역 안, 매핑 후 정상
      진행, 패닉 없음)과 음성(구역 밖, 여전히 패닉 + 정확한 vector/
      error_code/CR2 로그) 둘 다 2026-09-14 실측 확인, 이후 테스트
      코드는 제거함. 권한 위반(error_code bit0=1)은 구역 안이어도
      패닉시킨다(조용히 안 덮음).
- [ ] 4K 페이지가 조건에 따라 2M 페이지로 병합된다.
- [ ] procfs 루트가 마운트되어 조회 가능하다.

## 물리 메모리 관리 (DS-D4E5C451)

- [x] PVH `hvm_start_info`의 메모리맵을 파싱해 usable/reserved 영역을
      구분한다. (2026-09-14 실측 - QEMU 기본 128MB 환경에서 7개
      엔트리 정상 로그됨)
- [x] 물리 페이지 buddy 할당자가 order 0(4KiB)~order 3(32KiB) 할당/
      해제 후 정확히 같은 주소를 재사용하고(코얼레싱 확인), free
      페이지 총량이 alloc/free 전후로 정확히 원복됨. (2026-09-14
      실측 - 임시 자체 테스트로 확인 후 코드는 제거함)
- [x] 관리 범위가 정적 1GiB 매핑을 넘어서는 실제 전체 RAM까지
      확장된다(PL-99562483 완료, 2026-09-14) - free list를 물리주소
      기반으로 바꾸고 kMappedLimit을 direct map 한도(4GiB)로 올림.
      QEMU `-m` 128/2048/4096으로 3단계 실측 - free_pages가 정확히
      스케일되고 4GiB 초과분은 설계대로 클리핑됨. 과정에서
      `paging.cpp`의 동일한 identity-map 가정 버그도 실측으로 발견해
      같이 고침(-m 2048에서 실제 페이지폴트 재현 후 수정).
- [x] 멀티 NUMA 노드를 SRAT 기반으로 실제로 구분해 zone(노드별 buddy)을
      분리한다(QU-88936C2B 확정, 2026-09-14) - SRAT 있으면 메모리
      어피니티로 usable 영역을 노드별로 쪼개 배정, 없으면 노드 1개로
      안전하게 fallback. QEMU 기본(SRAT 없음) 환경에서 numa_nodes=1,
      free_pages 수치가 리팩터 전후로 동일함을 실측 확인 - 실제 멀티
      노드 배정 로직 자체는 SRAT 있는 환경에서 별도 검증 필요(QEMU
      `-numa` 옵션 등, 아직 안 함).

## 인터럽트 컨트롤러 (2026-09-14)

- [x] 레거시 PIC을 0xE0(마스터)/0xE8(슬레이브)로 리매핑한 뒤 완전히
      마스크한다 - CPU 예외 벡터(0-31)·타이머(32)·spurious(0xFF)
      전부와 안 겹침(설계자 지적으로 리매핑 없는 마스크만 하던 것을
      수정, 실측 - 리매핑 후에도 부팅/타이머 정상).
- [x] x2APIC 지원(PL-D65F49CC 완료, 2026-09-14) - CPUID.01H:ECX
      비트21로 감지해 있으면 MSR 기반 x2APIC으로, 없으면 기존
      xAPIC(MMIO)으로 폴백한다. 세 가지 환경 실측: ①QEMU 기본(TCG,
      x2APIC 미지원) → xAPIC 폴백 정상, id=0. ②`-cpu qemu64,+x2apic`
      (TCG) → QEMU 자체가 "TCG doesn't support requested feature:
      x2apic" 경고를 내고 미지원 그대로 두므로 역시 xAPIC 폴백(TCG
      한계, 코드 문제 아님 - 아래 참고 및 관계도 기록). ③`-accel kvm
      -cpu host`(진짜 x2APIC 하드웨어 가상화) → mode=x2apic로 정상
      전환, LAPIC ID 조회/spurious 벡터 설정/EOI/LAPIC 타이머 100Hz
      보정까지 폴트 없이 완주 확인. 공개 API(id/isReady/sendEoi/
      readRegister/writeRegister)는 xAPIC 때와 동일하게 유지.
      **재작업(2026-09-14, QU-6ABACEAD/QU-B569F367)**: 커널 커맨드라인
      `--disable-x2apic`로 강제 xAPIC 전환 가능(`Lapic::
      setX2ApicDisabled`), SDM 표준 LAPIC 레지스터 전체를 이름
      붙여 선언하고 초기화 시 미사용 LVT(Thermal/PerfCounter/
      LINT0/LINT1/Error)를 방어적으로 마스크+TPR=0 설정. `-accel kvm
      -cpu host`(x2APIC 지원 하드웨어)에서 플래그 유무에 따라
      `mode=x2apic`/`mode=xapic`이 정확히 갈림을 실측 확인(대조군
      포함).
- [x] IOAPIC을 통한 핀 기반 외부 인터럽트 라우팅(PL-2D149D8F 완료,
      2026-09-14) - IOAPIC MMIO를 매핑하고 IOREGSEL/IOWIN 간접 접근으로
      REDTBL 엔트리를 설정한다. IDT도 33-254 전 벡터에 스텁을 미리
      찍어 두고(isr.S) `Idt::registerHandler(vector, callback)`로 장치
      핸들러를 등록/해제하는 표로 일반화했다(MSI 등 다른 라우팅
      수단도 재사용 가능). **실측(2026-09-14, QEMU 8.2.2, monitor
      `sendkey`로 실제 키 입력 주입)**: 키보드 IRQ1을 벡터 0x21로
      라우팅 후 'a'/'b' 입력 - 각 키의 make/break 스캔코드(0x1E/0x9E,
      0x30/0xB0)가 등록한 핸들러에 정확히 전달됨을 확인, 검증 후 임시
      핸들러/라우팅 코드는 제거(영구 코드는 `IoApic::init()` MMIO
      매핑까지만 남김). **재작업(2026-09-14, QU-2EF510B4/QU-F89355A8)**:
      ACPI MADT Interrupt Source Override(타입2)를 실제로 파싱해
      `Acpi::resolveIsaIrq`로 반영(더 이상 "IRQ==GSI" 가정 아님),
      `IoApic::setRedirection`이 GSI/극성/트리거를 직접 받도록
      일반화(HPET의 임의 GSI 라우팅과 공유), destApicId가 IOAPIC
      REDTBL의 8비트 한도를 넘으면 조용히 자르지 않고 false 반환하도록
      수정. 레거시 PIT IRQ0도 이 경로로 IOAPIC 라우팅 가능해졌고
      (`Timer::enableLegacyPitIrq`/`disableLegacyPitIrq`, 기본 꺼짐,
      QU-FC9D80FF) - HPET/LAPIC 타이머를 모두 끈 채로 PIT IRQ0
      단독으로 틱이 정상 증가함을 실측 확인해 ISA IRQ 해석 경로
      전체가 올바르게 동작함을 검증했다.
- [x] MSI 지원(PL-2070E6EF 완료, 2026-09-14; MSI-X는 범위 밖으로 남김) -
      이 프로젝트에 전혀 없던 PCI 설정 공간 접근을 0단계로 먼저 구현
      (`minicore/kernel/pci.h/.cpp`, 레거시 포트 0xCF8/0xCFC 메커니즘,
      MMCONFIG는 v1 범위 밖) - bus 0부터 열거(멀티펑션/PCI-PCI 브리지
      재귀 포함), Capabilities List를 따라가 MSI capability(id 0x05)를
      찾고 Message Address(`0xFEE00000 | destApicId<<12`)/Data(벡터)를
      프로그래밍한 뒤 Enable 비트를 켠다. IOAPIC 계획에서 만든
      벡터->콜백 표(`Idt::registerHandler`)를 그대로 재사용 - MSI는
      IOAPIC 리다이렉션 테이블 슬롯을 안 쓰므로 더 많은 장치를 붙일
      수 있다는 설계 의도가 실제로 확인됨. **실측(2026-09-14, QEMU
      8.2.2, `-device edu`)**: PCI 버스를 열거해 호스트 브리지/ISA/
      IDE/ACPI/VGA/네트워크/edu 장치(vendor 0x1234, device 0x11e8)를
      전부 정상 인식(로그로 확인) - edu 장치의 BAR0(1MB MMIO)를
      매핑하고 Command 레지스터에서 Memory Space+Bus Master를 켠 뒤
      MSI를 활성화, 인터럽트 발생(raise) 레지스터(0x60)에 값을 쓰자
      실제로 우리가 등록한 벡터로 MSI 인터럽트가 들어와 상태
      레지스터(0x24) 값을 정확히 읽고 ack(0x64)까지 완료함을 확인 -
      PCI 설정 공간 읽기/쓰기, capability 탐색, MSI 프로그래밍,
      IDT 동적 디스패치 전체 경로가 실제로 동작함을 검증했다. 장치가
      없는 환경에서도(edu 미연결) PCI 열거만 정상 수행되고 나머지는
      건드리지 않음을 확인(회귀 없음). 검증 후 임시 핸들러/BAR
      매핑/MSI 활성화 코드는 제거 - 영구 코드는 `Pci::enumerate` 호출
      (부팅 로그)까지만 남김.
- [x] HPET 지원(PL-E68894CD 완료, 2026-09-14) - 정책 확정대로 HPET을
      스케줄러 기본 시간원으로, LAPIC 타이머(PIT 보정)는 fallback으로
      유지한다. `Acpi`가 "HPET" ACPI 테이블을 추가 파싱해
      `hasHpet()`/`hpetAddress()`로 노출, `Hpet::init()`이 Timer0을
      Legacy Replacement Route로 주기 모드 설정(GSI2 고정 라우팅 -
      IOAPIC REDTBL에도 직접 반영 필요, HPET 자체 라우팅 결정을
      IOAPIC이 알 방법이 없어서) 후 100Hz로 `Timer::onTick()`을 호출한다
      - 시간원이 무엇이든 `Timer::tickCount()`의 의미는 동일하다.
      `Timer::init()`이 `Acpi::hasHpet() && Hpet::init()` 성공 여부로
      분기(HPET 없음 또는 Timer0 주기모드 미지원 시 자동으로 기존
      PIT/LAPIC 경로 폴백). **실측(2026-09-14, QEMU 8.2.2)**: 기본
      머신(HPET 있음) → `source=hpet`, 틱이 5회 연속 정확히 1씩 증가
      확인. `-machine pc,hpet=off` → `source=lapic+pit`로 정상 폴백,
      마찬가지로 5회 연속 증가 확인(회귀 없음). x2APIC(`-accel kvm
      -cpu host`)과 함께 켜도 `source=hpet`로 정상 동작. 검증 후 임시
      틱 로그 코드는 제거. **재작업(2026-09-14, QU-1CC6BB1D/
      QU-2247A01E)**: Legacy Replacement Route(GSI2 고정) 대신
      Tn_INT_ROUTE_CAP 비트맵에서 실제로 라우팅 가능한 GSI를 골라
      쓰도록 전환(레벨 트리거+General Interrupt Status Register ack
      추가), `Hpet::enableTimer(timerIndex, frequencyHz, vector,
      destApicId)`로 멀티 비교기 API를 공개(현재는 Timer0만 실사용,
      SMP 스케줄러 생기면 코어별로 반복 호출 예정). 레벨 트리거
      전환 후에도 틱이 끊김/폭주 없이 정상 연속 증가함을 실측
      확인(ack 로직이 실제로 동작함을 증명).

## 실행 특권 경계 (SP-8B6B8D25 §2-A)

- [ ] devmgr/fs/net/tty("커널 서비스")는 전부 유저랜드(ring 3) 프로세스로

      devmgr).
