# 인터럽트 구독(Interrupt Subscription) 서브시스템 — 설계 제안

**[롤백, 2026-09-16, 설계자 Opinion("인터럽트 구독을 흡수하지 말자.
이건 기존으로 롤백")]** 이 문서를 SP-2602CAA6("커널 이벤트 발행/구독")로
일반화·흡수하기로 했던 2026-09-16 결정(아래 참고용으로 기록은 남겨둠 -
"**[대체, 2026-09-16 ...]**"였던 이 문단을 이 롤백 문단으로 교체)이
설계자 지시로 취소됐다. 이 문서는 다시 이 프로젝트의 정본
설계(approved)로 복귀한다 - SP-2602CAA6 쪽의 정확한 잔여 범위(완전
폐기인지 일부만 남기는지)는 QU-3BFAC7C0(SP-2602CAA6)로 재확인 요청
중이다.

PN-B3DD3D19("인터럽트/IPC를 유저랜드 커널 서비스로 실제 라우팅")
착수를 위해 QU-5F439001에서 여쭤본 두 가지("(A) waitForInterrupt류
syscall + AsyncTaskWaitQueue" vs "(B) 기존 BridgePipe에 ISR이 직접
write")에 대해, 설계자가 답변으로 두 가지 추가 요구사항을 주셨다
(2026-09-15):

1. 임의의 유저 프로세스가 타이머나 내부 IPC 벡터를 가로채지 못하도록,
   구독 시점에 "그 벡터가 유저랜드 위임이 허용된 벡터인지"를 검증하는
   유효성 체크가 필요하다.
2. 유저랜드가 `subscribeInterrupt(...)`류로 콜백(대상)을 등록하는
   방식이 되어야 하고, 이는 별도의 syscall 및 별도의 dispatch
   메커니즘이 필요하다.

**[개정 1, 2026-09-15]** 최초 승인 이후 설계자가 직접 메시지로 세 가지
확장을 추가 지시했다:

3. 인터럽트마다 페이로드(레지스터 상태 등)를 함께 전달할 것.
4. 한 벡터를 여러 프로세스가 동시에 구독(멀티캐스트)할 수 있어야 함.
5. 구독 해제/프로세스 종료 시 자동 정리도 이 설계 범위에 포함할 것 -
   PN-40E976F2와 공동으로 진행.

**[개정 2, 2026-09-15]** 개정 1 반영 직후 설계자가 세 가지를 추가로
더 지시했다 - 이 판은 그것까지 전부 반영한다:

6. 이벤트 페이로드에 **전체 GPR 덤프는 포함하지 않는다** - 대신
   덤프를 떠서 이벤트에 태깅해 두고, 별도 syscall로 요청하면 그때
   내준다(개정 1의 "전체 덤프 포함" 방향에서 한 단계 더 정제됨).
7. 살아있는 동안의 명시적 구독 취소(`UnsubscribeInterrupt`)도
   포함한다(개정 1의 "종료 시 자동 정리"에 더해, 스스로 끊는 경로도
   필요).
8. 한 벡터를 특정 소수 구독자에게만 순위/우선순위를 매겨 전달하는
   것도 가능해야 한다.

**[개정 3, 2026-09-15]** 개정 2에 대한 설계자 답변 - §4의 "특정
소수" 가정을 확정하고 세부 사항 두 가지를 추가로 확정했다:

9. priority 재조정 API는 명시적으로 만들지 않는다(고정) - 바꾸려면
   반드시 Unsubscribe 후 재구독.
10. §9가 언급했던 "우선순위 역전 방지"는 애초에 이 설계와 무관한
    개념이다 - priority는 순전히 "발신(ISR의 순회/완료 알림 제출)이
    먼저 이루어지는 순서"일 뿐, "그 처리 완료를 대기한다"는 개념이
    전혀 아니다(§4/§9 정정).
11. **"특정 소수"는 진짜 배타적 선별을 의미했다** - 배타적 우선순위
    (Exclusive Priority)를 별도로 구현해야 하고, 이 등급은 **"커널
    서비스"에게만 허용**된다. §4의 "전부 동등 브로드캐스트" 가정은
    이 배타적 등급에 한해 철회된다(§3-§5 재설계).

## §1 배경 — 왜 새 메커니즘이 필요한가

- `Idt::registerHandler(vector, handler)`(idt.h/cpp, PL-2D149D8F)는
  33-254 동적 벡터에 **순수 C++ 콜백**만 등록할 수 있다 - 이 콜백은
  인터럽트 컨텍스트(`kIsrHandler` 안, EOI 이후)에서 실행되는 커널
  코드일 뿐, ring3 UserThread를 깨우거나 데이터를 건네는 경로가 없다.
- Channel IPC(SP-1FBC0EEB)의 `AsyncTaskWaitQueue`(channel.h)는
  "다른 syscall(read/write/accept)을 제출한 AsyncTask"가 대기하는
  구조이지, "하드웨어 인터럽트가 특정 UserThread를 깨운다"는 개념
  자체가 없다.
- RM-48E1E610에 "인터럽트 대기"류 syscall이 예약된 적이 없다.

## §2 벡터 위임 허용 목록(Delegation Allow-list)

새 전역 상태(파일 범위, `minicore/kernel/interrupt_subscription.h/.cpp`
신설 - `minicore/kernel` 직속 커널 서브시스템 파일이라 RM-7C249618
(라이브러리 목록, `minicore/libs/<name>`/`userland/*` 전용)의 등록
대상은 아니다 - channel.cpp/async_task.cpp와 같은 분류):

```cpp
// 커널이 직접 처리해야 하는 벡터(kTimerVector/kSchedulerTickVector/
// kSyscallVector/스푸리어스 0xFF 등)는 절대 이 목록에 들어갈 수 없다 -
// allow()가 그런 고정 벡터를 거부한다(하드코딩된 배제 목록).
class InterruptDelegation {
public:
    static bool allow(uint32_t vector);
    static bool isAllowed(uint32_t vector);
};
```

이 allow-list가 없으면 어떤 유저 프로세스든 `SubscribeInterrupt`
하나로 예컨대 스케줄러 틱 벡터를 가로채 시스템 전체를 정지시킬 수
있다 - 설계자 지적 1번을 그대로 반영한 안전장치.

## §3 syscall API (RM-48E1E610 31/32/33/34번 예약)

콜백을 직접 ring3 함수 포인터로 호출하는 방식은 채택하지 않는다
(인터럽트 컨텍스트에서 임의 ring3 코드를 직접 호출하는 것은 CR3/
스택 안전성 문제가 SP-83A07867/PN-58501EAA가 이미 다룬 것과 동일한
성격으로 재발하므로) - 대신 기존 syscall submit/wait 패턴
(SP-04EE2A18)과 동일하게 "제출 -> 완료 대기"로 간접화한다.

```
SubscribeInterrupt(vector: uint32_t, priority: uint32_t, exclusive: bool) -> error
UnsubscribeInterrupt(vector: uint32_t) -> error
WaitInterrupt(vector: uint32_t, outEvent: InterruptEvent* [유저 메모리])
  -> outEvent에 그 사이 쌓인 이벤트 중 가장 오래된 것 하나가 채워지고
     남은 개수(hasMore)가 함께 반환된다 - §4 참고.
GetInterruptDump(dumpId: uint64_t, outDump: InterruptFullDump* [유저 메모리]) -> error
```

- `kSyscallEndpointSubscribeInterrupt = 31`
- `kSyscallEndpointWaitInterrupt = 32`
- `kSyscallEndpointUnsubscribeInterrupt = 33`
- `kSyscallEndpointGetInterruptDump = 34`

**SubscribeInterrupt(vector, priority, exclusive)**: `InterruptDelegation::
isAllowed(vector)` 확인 → 이미 이 UserThread가 구독 중인지 확인(중복
구독 거부) → **[개정 3] `exclusive=true`면 호출자가 "커널 서비스"
자격을 가졌는지 확인**([해결됨] SP-EAB162FC §2.3 - `Process::role ==
ProcessRole::KernelService` 확인, §7에 실패 케이스로 반영) → 빈 구독자 슬롯
(§4, 최대 `kMaxSubscribersPerVector`개, exclusive/비-exclusive 공용
풀)을 찾아 `owner = currentTask`, `priority = priority`,
`exclusive = exclusive`로 배정 → **슬롯 배열을 정렬**(§4/§5 참고 -
exclusive 구독자가 항상 맨 앞, 그다음 priority 오름차순 - **낮은
숫자 = 높은 우선순위**, 기존 스케줄러 RT 클래스 관례와 동일한
방향). 블로킹 없음, 즉시 반환.

**[개정 3, §11 반영] exclusive는 "먼저 받는다"가 아니라 "그들만
받는다"는 뜻이다** - 개정 2 §4가 썼던 "특정 소수 구독자에게만
전달"이라는 표현을 설계자가 문자 그대로("진짜 배타적 선별") 확정했다
(§4 "우선순위의 의미" 문단 참고). 그 벡터에 exclusive=true인 구독자가
**하나라도** 있으면, §5의 ISR은 그 벡터의 이벤트를 exclusive 구독자
들에게만 전달하고 비-exclusive 구독자는 완전히 건너뛴다(그들의 큐에
쌓이지도, 깨우지도 않는다) - exclusive 구독자가 하나도 없으면 종전
그대로 전원 브로드캐스트. exclusive 구독자는 여러 명일 수 있다("특정
소수"는 복수 허용 - 벡터당 1개로 제한하지 않는다, 커널 서비스가 여럿
같은 벡터를 나눠 처리하는 시나리오를 배제하지 않기 위함); 그들 사이의
순서는 여전히 priority 오름차순. 비-exclusive 구독은 exclusive 구독자
존재 여부와 무관하게 거부되지 않는다(등록 자체는 항상 허용 - 다만
exclusive 구독자가 존재하는 동안은 이벤트를 받지 못할 뿐이고, 그
exclusive 구독자들이 전부 Unsubscribe/종료로 사라지면 다음 이벤트부터
다시 브로드캐스트 대상에 자동으로 포함된다 - ISR이 매번 "지금 이
순간" exclusive 존재 여부를 확인하므로 별도 전환 로직이 필요 없다).

**[해결됨, QU-E6D37232 답변]** "커널 서비스" 자격 증명은 이제
**SP-EAB162FC**("프로세스 신원 및 커널 서비스 권한(Capability)
체계 — 설계 제안")가 정의한다 - `Process::role ==
ProcessRole::KernelService`(부팅 매니페스트로 devmgr/fs/net/tty
네 프로세스에만 부여, §2 참고) 확인 하나로 대체됐다. 이전에 여기
있던 "PnP IO 권한을 프록시로 쓰자"는 잠정안은 철회됐다(SP-EAB162FC
§2.3이 이 소비자엔 바로 적용 가능하다고 확정).

**UnsubscribeInterrupt(vector)** [신규, 개정 2]: 호출자가 그 벡터의
구독자가 아니면 실패. 구독자면 `sub.lock`을 쥔 채로 그 슬롯을
`used = false`로 되돌리고 큐/대기자를 정리한다(§6과 동일한 정리
로직을 재사용 - "누가 트리거하는가"만 다르고 "무엇을 정리하는가"는
동일). v1은 한 프로세스당 스레드 하나뿐이라는 기존 전제(SP-04EE2A18)
때문에, 자신이 그 벡터에 WaitInterrupt로 파킹돼 있는 도중에 스스로
Unsubscribe를 호출하는 경우는 생기지 않는다(직렬 실행이므로) - 후속
멀티스레드 프로세스 지원 시 재검토.

**WaitInterrupt**: 호출한 UserThread가 그 벡터의 구독자가 아니면
즉시 실패. 구독자가 맞으면 기존 `Syscall::submit`과 동일하게
`AsyncTask`를 만들어(subjectCode는 이 서브시스템 전용 핸들러) **그
구독자 자신의** 이벤트 큐(§4)에 쌓인 게 있으면 즉시 완료 처리(가장
오래된 이벤트 하나를 꺼내 `outEvent`에 씀), 없으면 **그 구독자
자신의** `AsyncTaskWaitQueue`에 파킹한다.

**GetInterruptDump(dumpId)** [신규, 개정 2]: `InterruptEvent.dumpId`
로 받은 태그를 그대로 넘기면, §4의 공유 덤프 링에서 아직 남아있는
전체 레지스터 덤프를 복사해 돌려준다. 이미 밀려나 없어졌으면
`NotFound`(덤프 링이 이벤트 큐보다 작을 수 있어, "이 이벤트는
받았지만 그 덤프는 이미 유실"될 수 있음 - §4 참고, 진단 목적의
best-effort 기능이라는 점을 명시).

**onExec 원자성 계약(§13.1과 동일한 패턴, QU-562F8B8E 답변으로 이미
확정)**: onExec은 `sub.lock`을 먼저 잡고, 그 락을 쥔 채로 자신의
구독자 슬롯 이벤트 큐를 확인한다 - 비어 있지 않으면 즉시 하나
소비하고 그 자리에서 락을 놓고 완료 처리, 비어 있으면 락을 쥔 채로
자신의 `waiters`에 스스로를 넣은 뒤에야 놓고 `AsyncTask::yield()`한다.
"확인"과 "대기열 등록" 사이에 락이 풀리는 구간이 있으면 안 된다 -
`MutexCore::tryAcquireOrKeepLock()`(SP-0666DB3C §13.1)과 동일한
lost-wakeup 방지 계약이며, 이 계약은 §5의 ISR 쪽 코드와 짝을 이룬다.

## §4 내부 자료구조 (개정 2 - 우선순위 + 덤프 태깅 추가)

```cpp
// 경량 페이로드 - 모든 구독자에게 매번 복사되는 부분이라 작게 유지한다.
// 전체 GPR은 여기 안 담는다(개정 2 - §3 GetInterruptDump로 분리).
struct InterruptEvent {
    uint64_t rip;
    uint64_t errorCode;   // 벡터에 하드웨어 에러코드가 없으면 0
    uint64_t rflags;
    uint64_t dumpId;      // §4 공유 덤프 링을 가리키는 태그 - GetInterruptDump로 조회
};

// 전체 레지스터 덤프 - idt.cpp의 kPanic이 이미 찍는 것과 같은 필드
// 집합을 재사용한다(커밋 ceb6deb, 전체 GPR+CR3). 이벤트마다 매번
// 모든 구독자 큐에 복사하기엔 무겁기 때문에 벡터당 공유 링 하나에만
// 저장하고, 이벤트는 그 가리키는 태그(dumpId)만 들고 다닌다.
struct InterruptFullDump {
    uint64_t dumpId;
    uint64_t rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp;
    uint64_t r8, r9, r10, r11, r12, r13, r14, r15;
    uint64_t rip, rflags, cr2, cr3;
};

constexpr uint32_t kInterruptEventQueueCapacity = 8;   // 구독자별 이벤트 링 - 실측 후 조정(RM-23F4B687 §4)
constexpr uint32_t kInterruptDumpRingCapacity = 8;      // 벡터당 공유 덤프 링 - 실측 후 조정
constexpr uint32_t kMaxSubscribersPerVector = 8;        // 벡터당 동시 구독자 상한 - 실측 후 조정

struct InterruptSubscriber {
    bool used = false;
    Task* owner = nullptr;
    uint32_t priority = 0;   // 낮을수록 높은 우선순위(§3/§5) - 슬롯 배열은 항상 (exclusive 먼저, 그다음 이 값 오름차순)으로 유지
    bool exclusive = false;  // [개정 3] true면 "커널 서비스" 전용 배타적 수신자 - §3/§5 참고
    InterruptEvent events[kInterruptEventQueueCapacity];
    uint32_t head = 0;
    uint32_t count = 0;
    uint32_t droppedCount = 0;   // 큐 가득 찼을 때 유실된 이벤트 수(진단용)
    AsyncTaskWaitQueue waiters;  // 이 구독자를 위해 대기 중인 WaitInterrupt AsyncTask(최대 1개, §3)
};

struct InterruptSubscription {
    InterruptSubscriber subscribers[kMaxSubscribersPerVector];  // exclusive 먼저, 그다음 priority 오름차순 유지(§3 SubscribeInterrupt가 정렬)
    InterruptFullDump dumps[kInterruptDumpRingCapacity];        // 공유 - 구독자 수와 무관하게 실제 발생 횟수만큼만 쌓임
    uint32_t dumpHead = 0;
    uint32_t dumpCount = 0;
    uint64_t nextDumpId = 1;   // 0은 "덤프 없음"이 아니라 이 설계에선 항상 유효한 dumpId를 배정하므로(모든 이벤트가 덤프를 가짐) 0 자체를 특수값으로 예약하진 않는다 - 단순 증가 카운터
    Spinlock lock;   // ISR과 syscall 양쪽에서 잡는다(§5) - 구독자 슬롯 + 덤프 링 전부 이 하나로 보호
};
InterruptSubscription gSubscriptions[256];  // 벡터로 직접 인덱싱, 0-32/kSyscallVector는 항상 비어 있음(allow-list가 보장)
```

**우선순위의 의미(개정 3 확정, §11)**: 두 가지가 합쳐져 동작한다.
(1) **exclusive**(배타적 선별, §3) - 그 벡터에 exclusive 구독자가
하나라도 있으면 이벤트는 exclusive 구독자들"에게만" 전달되고 비-
exclusive 구독자는 완전히 배제된다("특정 소수에게만 전달"의 문자
그대로 확정된 의미 - 개정 2 §4가 애초에 썼던 표현). (2) **priority**
(순서, §9) - exclusive 여부가 같은 구독자들 사이에서는 슬롯 배열이
priority 오름차순으로 유지되므로, §5의 ISR이 배열을 순서대로 순회하며
깨우는 것만으로 우선순위가 높은 쪽의 `WaitInterrupt` AsyncTask가
"즉시 스케줄링 큐(Immediate Queue)"(RM-32D06563 §2,
`AsyncReactor::submitCompletion`이 항상 제출하는 그 큐)에 **더 먼저**
들어간다 - 그 큐 자체가 FIFO이므로 먼저 들어간 쪽이 리액터에서 먼저
처리된다. priority 자체는 "그 처리 완료를 대기한다"는 개념이 전혀
아니다(§9 확정). 새 메커니즘을 발명하지 않고 기존 큐의 FIFO 순서만
활용하는 방식이다.

`droppedCount`를 두는 이유: 한 구독자가 `WaitInterrupt`를 충분히
자주 호출하지 않으면 그 구독자의 큐만 가득 차 새 이벤트를 놓칠 수
있다(다른 구독자는 영향 없음) - 이 카운터로 사후 진단 가능. v1은
가득 찼을 때 새 이벤트를 버린다(FIFO 순서 보존 우선).

**덤프 링이 이벤트 큐보다 먼저 차는 경우**: 구독자가 여럿이라도
덤프는 벡터당 1개(발생당 1개)만 쌓이므로, 개별 구독자 이벤트 큐보다
오히려 덜 찰 가능성이 높다 - 그래도 이론상 어떤 구독자도
`GetInterruptDump`를 안 부르는 채로 `kInterruptDumpRingCapacity`번
넘게 발생하면 오래된 덤프부터 밀려난다(§3의 `NotFound` 케이스).

## §5 ISR 쪽 처리 및 동시성 안전성

```cpp
void kInterruptSubscriptionIsr(InterruptFrame* frame) {
    auto& sub = gSubscriptions[frame->vector];
    SpinlockGuard guard(sub.lock);

    // 공유 덤프 링에 전체 레지스터 상태를 먼저 한 번만 기록(구독자 수와 무관).
    const uint64_t dumpId = sub.nextDumpId++;
    auto& dumpSlot = sub.dumps[(sub.dumpHead + sub.dumpCount) % kInterruptDumpRingCapacity];
    if (sub.dumpCount == kInterruptDumpRingCapacity) { sub.dumpHead = (sub.dumpHead + 1) % kInterruptDumpRingCapacity; }
    else { ++sub.dumpCount; }
    dumpSlot = InterruptFullDump{dumpId, frame->rax, frame->rbx, /* ... 전체 GPR ... */ frame->rip, frame->rflags, frame->cr2, frame->cr3};

    const InterruptEvent event{frame->rip, frame->errorCode, frame->rflags, dumpId};

    // [개정 3] exclusive 구독자가 하나라도 있으면 그들"에게만" 전달한다 -
    // "특정 소수에게만 전달"의 문자 그대로 확정된 의미(§4 "우선순위의 의미").
    // 슬롯 배열은 이미 exclusive가 앞쪽에 오도록 정렬돼 있으므로(§3/§4) 한 번만
    // 훑어 존재 여부를 확인한다.
    bool hasExclusive = false;
    for (auto& subscriber : sub.subscribers) {
        if (subscriber.used && subscriber.exclusive) { hasExclusive = true; break; }
    }

    // 우선순위(exclusive 먼저, 그다음 오름차순 정렬된) 순서로 순회 - hasExclusive이면
    // 비-exclusive 구독자는 완전히 건너뛴다(그들의 큐에도, waiters에도 손대지 않는다).
    // 먼저 순회되는(=우선순위 높은) 구독자의 완료 알림이 Immediate Queue에 먼저 들어간다.
    for (auto& subscriber : sub.subscribers) {
        if (!subscriber.used) continue;
        if (hasExclusive && !subscriber.exclusive) continue;
        if (subscriber.count < kInterruptEventQueueCapacity) {
            subscriber.events[(subscriber.head + subscriber.count) % kInterruptEventQueueCapacity] = event;
            ++subscriber.count;
        } else {
            ++subscriber.droppedCount;
        }
        if (AsyncTask* task = subscriber.waiters.popFront()) {
            AsyncReactor::submitCompletion(task);  // 인터럽트 컨텍스트에서 호출 가능(async_task.h에 이미 명시)
        }
    }
}
```

**같은 코어에서 ISR과 syscall이 `sub.lock`을 두고 데드락할 수
있는가**: 아니다 - 둘 다 인터럽트 게이트(`kInterruptGateTypeAttr`/
`kInterruptGateTypeAttrDpl3` = 0x8E/0xEE, idt.cpp)를 통해 진입하므로
진입 시 하드웨어가 IF를 자동으로 클리어한다 - 같은 코어에서 syscall
처리 도중에는 그 어떤 유지보수 인터럽트(이 벡터의 ISR 포함)도 끼어들
수 없다. **다른 코어**에서 동시에 같은 벡터의 ISR이 실행 중일
가능성은 여전히 있으므로 `Spinlock`(코어 간 상호배제용)은 그대로
필요.

## §6 구독 해제 / 프로세스 종료 시 정리

두 가지 트리거가 같은 정리 로직(슬롯 `used=false` + 큐/대기자 초기화)
을 공유한다:

1. **명시적 - `UnsubscribeInterrupt`(§3)**: 살아있는 동안 스스로 호출.
2. **암묵적 - 프로세스/UserThread 종료**: PN-40E976F2가 SP-F682B889에
   반영할 "사망 전파 목록"(propagation list, QU-B717B421 답변) 인프라를
   그대로 재사용한다 - 이 SP가 그 인프라를 새로 발명하지 않는다.
   `SubscribeInterrupt`가 슬롯을 배정할 때 그 슬롯의 정리를 "이
   UserThread가 죽으면 실행돼야 하는 정리 작업" 목록에 등록해 둔다
   (PN-40E976F2가 확정할 정확한 등록 API에 맞춰 착수 시 배선 - 지금은
   "그런 등록 지점이 존재한다"는 전제만 세워 둔다).

**착수 조건**: 1번(명시적 해제)은 지금 설계만으로 바로 구현 가능하다.
2번(종료 시 자동 정리)의 실제 배선은 PN-40E976F2가 SP-F682B889에
"사망 전파 목록" 인프라를 반영·구현한 뒤에야 가능하다 - 그 전까지는
1번 경로만으로 구독자가 스스로 정리하는 것에 의존한다(프로세스가
비정상 종료해 Unsubscribe를 못 부르면 슬롯이 누수되는 v1 한계 -
2번이 배선되면 해소됨).

## §7 에러 케이스

- `SubscribeInterrupt`: 벡터가 allow-list에 없음 / 이미 자기 자신이
  그 벡터를 구독 중(중복 구독 거부) / 구독자 슬롯이
  `kMaxSubscribersPerVector`만큼 이미 꽉 참 / **[개정 3]**
  `exclusive=true`인데 호출자가 "커널 서비스" 자격 검증을 통과하지
  못함(자격 판정 기준은 [해결됨] SP-EAB162FC §2.3 참고).
- `UnsubscribeInterrupt`: 호출자가 그 벡터의 구독자가 아님.
- `WaitInterrupt`: 호출자가 그 벡터의 구독자가 아님 / 벡터가
  구독된 적이 아예 없음.
- `GetInterruptDump`: `dumpId`가 이미 밀려나 없어짐(`NotFound`) /
  애초에 존재한 적 없는 값.

## §8 검증 계획 (착수 시)

PN-B3DD3D19가 이미 제안한 대로, 실제 devmgr 대신 손으로 만든 진단
UserThread를 "가짜 devmgr"로 삼아 검증한다(PL-C8648D4D의 임시
UserThread 드라이버 선례와 동일한 패턴) - 예: HPET/PIT처럼 이미
IOAPIC로 라우팅 가능한 주기적 인터럽트 하나를 골라 `InterruptDelegation::
allow()`로 위임 허용 처리한 뒤:

1. 진단 UserThread 하나가 `SubscribeInterrupt` + 반복 `WaitInterrupt`
   로 실제 발생 횟수를 세어 예상 주기와 맞는지, `outEvent.rip` 등
   페이로드가 그럴듯한 값으로 채워지는지 확인.
2. **멀티캐스트 검증** - 진단 UserThread 2개 이상이 같은 벡터를
   동시에 구독시켜, 둘 다 독립적으로 모든 이벤트를 받는지 확인.
3. **우선순위 검증** - 서로 다른 priority로 구독한 UserThread 여러
   개가 같은 인터럽트로 동시에 깨어날 때, 높은 우선순위 쪽의
   `WaitInterrupt` 완료가 실제로 먼저 반환되는지(리액터 처리 순서)
   확인.
4. **덤프 조회 검증** - `outEvent.dumpId`로 `GetInterruptDump`를
   불러 실제 레지스터 값과 일치하는지, 덤프 링 용량을 넘겨 유실시킨
   뒤 `NotFound`가 정확히 반환되는지 확인.
5. **명시적 해제 검증** - `UnsubscribeInterrupt` 호출 후 그 슬롯이
   재사용 가능해지는지(다른 구독자가 같은 슬롯 자리로 새로 구독
   가능한지), 해제 후 그 벡터의 `WaitInterrupt`가 즉시 실패하는지
   확인.
6. 큐 오버플로 검증(기존과 동일) - `droppedCount` 정상 증가 확인.
7. **[개정 3] 배타적 우선순위(exclusive) 검증** - (a) 커널 서비스
   자격이 없는 진단 UserThread가 `exclusive=true`로 구독 시도하면
   §7의 자격 실패 에러로 거부되는지 확인. (b) 자격을 가진 진단
   UserThread가 exclusive로 구독한 뒤, 그 벡터에 이미 있던 비-
   exclusive 구독자가 새 이벤트부터 전혀 받지 못하는지(큐가 더
   늘지 않는지) 확인. (c) 그 exclusive 구독자가 `UnsubscribeInterrupt`
   로 해제되면, 다음 이벤트부터 비-exclusive 구독자가 다시 정상
   수신하는지 확인(§3의 "자동으로 다시 포함" 서술 검증).

## §9 범위 밖 (v1)

- **[개정 3 확정]** 살아있는 동안 구독의 priority(및 exclusive 여부)를
  재조정하는 API는 명시적으로 만들지 않는다(v1은 구독 시점 1회 고정) -
  바꾸려면 반드시 Unsubscribe 후 재구독.
- **[개정 3 확정]** "우선순위 역전(priority inversion) 방지"는 애초에
  이 설계와 무관한 개념이다 - §4/§9의 priority는 순전히 "발신(ISR의
  순회/완료 알림 제출)이 먼저 이루어지는 순서"일 뿐이며, "그 처리
  완료를 대기한다"는 개념이 전혀 없으므로 한 구독자가 다른 구독자의
  처리를 지연시키는 상황 자체가 성립하지 않는다(별도 보호 불필요 -
  더 이상 "위험도가 낮아 보류"가 아니라 개념적으로 해당 사항 없음).
