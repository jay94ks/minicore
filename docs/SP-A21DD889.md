# ResourceGroup I/O 대역폭 컨트롤러 — 설계 제안 (인터페이스 레벨)

`PN-DEC738B8`("착수 조건 충족, PN-F60E405A 완료 - 설계 착수 가능")가
요청한 순수 인터페이스 레벨 설계 - "어느 지점에 훅을 거는지 /
ResourceGroup과 BlockDevice를 어떻게 연결하는지"까지만 다루고, 실제
쿼터 정책 세부(알고리즘 파라미터 등)는 실사용처가 생긴 뒤로 미룬다
(CLAUDE.md 규칙 4, `SP-245D130B` §7의 원 결정과 동일한 절제).

## 1. 배경 - `SP-245D130B` §7의 "전면 보류"가 풀린 이유

`SP-245D130B` §7은 "블록 I/O 경로 자체가 없어 설계할 대상이 없다"고
전면 보류했었다. `PN-F60E405A`(AhciBlockDevice 구현, completed)가
`minicore/fs/block_device.h`(`fs::BlockDevice`)/`minicore/fs/ahci.h`
(`AhciBlockDevice`)를 실제로 갖추고 QEMU 실측(IDENTIFY/READ/WRITE/
FLUSH)까지 검증하며 그 착수 조건이 충족됐다(`PN-DEC738B8`가 이미
확인해 둔 사실).

## 2. 핵심 발견 - "BlockDevice 위에 훅을 얹는다"는 원 표현은 오해의 소지가 있다

`SP-245D130B` §7과 `PN-DEC738B8` 둘 다 "그 인터페이스(`AhciBlockDevice`류)
위에 대역폭 제한 훅을 얹는다"고 표현했으나, 실제 코드 배치를 확인하면
이 표현이 실제로 구현 가능한 지점을 정확히 가리키지 않는다:

- **`ResourceGroup`**(`minicore/kernel/resource_group.h`)은 **커널**
  안에 산다.
- **`fs::BlockDevice`**(`minicore/fs/block_device.h`)/`AhciBlockDevice`
  (`minicore/fs/ahci.h`)는 **`fs` 프로세스(유저랜드) 자신의 주소공간**
  안에 산다(`QU-1FB6A7A4` 답변 - "블록 디바이스는 그냥 아예 fs한테
  던져버려").

즉 `ResourceGroup`이 `fs::BlockDevice::readBlocks()`/`writeBlocks()`
호출 지점에 **직접** 훅을 걸 방법이 없다 - 서로 다른 주소공간, 서로
다른 권한 레벨이다. 저 지점에서 쿼터를 강제하려면 `fs` 프로세스가
매 블록 I/O마다 커널에 "이 ResourceGroup의 남은 쿼터가 얼마인지"를
왕복 조회(syscall)해야 하는데, 이는 (a) 블록 단위로 매번 syscall
왕복이 필요해 오버헤드가 크고, (b) `fs`가 호출자의 `ResourceGroup`
소속을 알아야 하므로 그 정보를 IPC로 함께 넘겨야 하는(아직 미정인
`MountKind::Channel` 와이어 포맷, `SP-2BCE5D60` §9.1) 새 의존을
만든다.

## 3. 제안 - 커널이 이미 있는 지점에서 강제(CPU/메모리 계정과 동일한 원칙)

이 프로젝트가 이미 확립한 정확히 같은 패턴을 그대로 재사용한다 -
**CPU 쿼터**(`SP-6A563A8F`, `Scheduler::onTick()`/`pickNext()`가
커널 안에서 직접 강제)와 **메모리 계정**(`PN-158B6B2F`,
`Process::execImage()`가 커널 안에서 직접 가산/감산)은 둘 다
"커널이 이미 그 지점에 개입하고 있으므로 거기서 그대로 강제한다"는
원칙을 따른다 - 별도 IPC 왕복이 전혀 필요 없다.

I/O도 동일하게, 실제 파일 Read/Write가 **커널의 VFS syscall
디스패치**(`vfs_syscall.cpp`의 `OpenHandler`/`ReadHandler`/
`WriteHandler`, `SP-2AAD7C8D` §9)를 반드시 거친다는 사실을 이용한다 -
그 디스패치 지점에서 커널은 이미 `kProcessFromSubmitter(task)`로
호출자 `Process`(따라서 `Process::group` = `ResourceGroup*`)를 알고
있다. **강제 지점은 `fs`로 요청을 실제로 전달(`AsyncTask::submit
(driver->subjectCode(), ...)`, 현재는 `MountKind::KernelDriver`만
지원 - `MountKind::Channel`이 실제 IPC 프로토콜을 갖추면 그 전달
직전) 바로 그 자리다** - `fs`/`BlockDevice`/`AhciBlockDevice`는
`ResourceGroup`의 존재 자체를 몰라도 된다(레이어 분리 유지).

이렇게 하면 `PN-DEC738B8`이 우려했던 "`PN-A401DDF9`(BlockDevice
동기→비동기 재설계)가 끝날 때까지 기다려야 하는가"라는 질문 자체가
**해소된다** - 이 설계는 `fs::BlockDevice`를 전혀 건드리지 않으므로
그 인터페이스가 동기든 비동기든 무관하다. 유일한 진짜 선행 조건은
`SP-2BCE5D60` §9.1(`MountKind::Channel`의 실제 IPC 와이어 포맷)이지
`PN-A401DDF9`가 아니다.

## 4. 자료구조 스케치 - CPU 컨트롤과 완전히 같은 모양

```cpp
// resource_group.h - 기존 ResourceGroupCpuControl(§2, 이미 구현됨)과
// 나란히, byte 단위로 동일한 모양.
struct ResourceGroupIoControl {
    uint32_t periodTicks = 0;      // 0 = 무제한(기본값)
    uint64_t quotaBytes = 0;       // 이 주기 동안 허용되는 바이트 수(읽기+쓰기 합산 v1)
    uint64_t usedBytesInPeriod = 0;
    uint64_t periodStartTick = 0;
};

// ResourceGroupAccounting(이미 totalCpuTicks/totalMemoryBytesUsed를
// 갖고 있음, resource_group.h)에 두 필드만 추가.
struct ResourceGroupAccounting {
    uint64_t totalCpuTicks = 0;
    uint64_t totalMemoryBytesUsed = 0;
    uint64_t totalIoBytesRead = 0;     // [신규]
    uint64_t totalIoBytesWritten = 0;  // [신규]
};
```

`ResourceGroup`에 `ResourceGroupIoControl io;` 필드 추가(기존 `cpu`
필드와 나란히). `kCheckAndResetCpuPeriod()`와 완전히 동일한 모양의
`kCheckAndConsumeIoQuota(ResourceGroup* group, uint64_t bytes)` -
주기 롤오버 처리 후 `usedBytesInPeriod + bytes > quotaBytes`면
`false`(거부), 아니면 `usedBytesInPeriod += bytes; return true`.

## 5. VFS 디스패치 통합 지점 (착수 세션이 실제로 배선할 곳)

`vfs_syscall.cpp`의 Read/Write 핸들러(§9.3, `OpenArgs`/`ReadArgs`/
`WriteArgs` 처리)가 `driver->subjectCode()`로 실제 전달(`fs`로의
Channel 왕복이든 `KernelDriver` 직접 호출이든)을 하기 **직전에**:

```cpp
// 의사코드 - ReadHandler::onExec() 안, driver 전달 직전
SharedPtr<Process> process = kProcessFromSubmitter(task);
if (process && process->group) {
    if (!kCheckAndConsumeIoQuota(process->group, args->len)) {
        args->error = ChannelError::ResourceExhausted;  // 기존 값 재사용, 새 enum 불필요
        co_return;
    }
}
process->group->accounting.totalIoBytesRead += /* 실제 읽힌 바이트, 완료 후 */;
```

**v1 범위 판단**: 요청 크기(`args->len`)로 미리 차감(낙관적)할지,
실제 완료 후 바이트 수로 사후 정산할지는 착수 세션이 실측하며
정할 구현 디테일로 남긴다(CPU 쿼터가 "사용한 뒤 정산"인 것과 달리
I/O는 요청 크기를 미리 알 수 있어 선차감이 더 자연스러워 보이지만,
`args->len`보다 실제로 적게 읽힐 수 있는 EOF 케이스가 있어 소비자가
직접 확인 필요) - `RM-23F4B687` §4 취지상 새 DC 불필요 수준.

**적용 범위(v1)**: `MountKind::KernelDriver` 경로(`livefs`/`procfs`/
`resourcegroup` VFS 등)에도 기계적으로는 걸리지만, 그 경로들은 전부
가벼운 텍스트 스냅숏이라 대역폭 제한의 실질적 대상이 아니다 - 실제
목표는 향후 `MountKind::Channel`(`fs` 서비스, 진짜 블록 I/O)이다.
과도한 조건 분기를 피하기 위해 v1은 마운트 종류 구분 없이 모든
Read/Write에 동일하게 적용해도 무방하다고 판단(무제한이 기본값이라
그룹을 명시적으로 만들지 않는 한 관찰 가능한 영향 없음).

## 6. Syscall API 확장 (RM-48E1E610 그룹 9, 다음 빈 번호)

| 그룹 | 번호 | 이름 | 설명 |
|---|---|---|---|
| 9 | 6 | `ResourceGroupSetIoQuota` | §4의 `periodTicks`/`quotaBytes` 설정, 0/0=무제한 - `ResourceGroupSetCpuQuota`(그룹9 call3)와 완전히 동일한 계약(계층적 강제 포함 - `kValidateChildQuotaAgainstParent()`를 바이트 버전으로 재사용/특수화) |

VFS 노출은 `cpu.stat`/`memory.stat`(`PN-A40787C8`)과 동일한 관례로
`/sys/live/resourcegroup/<name>/io.stat`(`TotalIoBytesRead`/
`TotalIoBytesWritten`/`IoQuotaBytes`/`IoUsedBytesInPeriod` 필드) -
단 이건 §5의 실제 강제 배선이 끝난 뒤에나 의미 있는 후속이라 이번
설계 범위에는 포함하지 않는다(별도 PN으로 분리 권장).

## 7. 이번 설계가 명시적으로 다루지 않는 것

- **정확한 쿼터 알고리즘 파라미터**(주기 길이 기본값, 읽기/쓰기
  분리 과금 여부) - 실사용처가 생긴 뒤 결정(`SP-245D130B` §7 원
  결정 그대로 유지).
- **`fs` 캐시 몫 계정** - `fs` 서비스 자체가 실코드로 없어 여전히
  설계 불가(`SP-245D130B` §6과 동일한 이유).
- **`MountKind::Channel`의 실제 IPC 와이어 포맷**(`SP-2BCE5D60` §9.1) -
  이 설계의 진짜 선행 조건. 그 프로토콜이 나오기 전까지 §5의 통합
  지점은 `MountKind::KernelDriver` 경로에서만 실제로 동작(관찰
  가능한 실사용처가 아직 없다는 뜻 - 배선 자체는 가능하나 회귀
  검증 대상이 마땅치 않음).
- **`PN-A401DDF9`(BlockDevice 비동기 재설계)와의 관계** - §3이 이미
  밝혔듯 무관하다(이 설계는 `BlockDevice`를 아예 건드리지 않음).
