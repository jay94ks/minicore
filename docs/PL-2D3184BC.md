# 실행 계획: 스케줄러 (프로세스/태스크/컨텍스트 스위칭)

**[설계 확정, 구현 착수, 2026-09-14]** DC-8EA1E7F6/QU-BA001D73과
DC-B80D8D31/QU-77A52430 답변으로 설계가 확정됐다. 이 문서는 확정된
결정을 정리하고, 구현 순서를 계획한다 - 진행되면서 "한 것" 절을
채워 나간다.

## 배경

DS-D4E5C451(QU-C3EC2C63)이 스케줄러 상위 구조("코어별 개별 큐 +
CPU affinity + CAS 기반 동기화 + Push/Pull 로드밸런싱")를 이미
확정해 뒀고, PL-E68894CD §5가 "HPET/LAPIC 타이머 공존 방식은
스케줄러 설계 시점에 구체화"하기로 미뤄 뒀다. 이번에 그 하위
세부(프로세스/스레드 모델, 컨텍스트 전환, 큐 알고리즘, 타이머 틱
소스, 로드밸런싱 트리거, lock-free 자료구조 범위)를 DC-8EA1E7F6/
DC-B80D8D31로 등록해 설계자 확정을 받았다.

## 확정된 설계

### 1. 스케줄링 단위 — `Task`

- 스케줄링 최소 단위의 이름은 **`Task`**로 확정(코드에서도 `kernel::
  Task`로 명명 - `Thread`/`TCB` 같은 이름 대신). 하나의 **프로세스는
  여러 Task(스레드)를 가질 수 있다** - 즉 프로세스=주소공간+자원의
  소유자, Task=실제 스케줄링/실행 단위로 분리.
- 각 Task는 자신만의 **CPU affinity 제약**을 가질 수 있다 - "어떤
  코어에서만 실행 가능"(허용 목록, whitelist) 또는 "어떤 코어에서는
  실행 불가"(제외 목록, blacklist) 둘 다 표현 가능해야 한다 - 비트마스크
  (코어 수만큼의 비트, 1=허용)면 두 형태 모두 자연스럽게 표현된다
  (허용 목록 = 그 비트들만 세움, 제외 목록 = 그 비트들만 지움, 전체
  코어 마스크에서 시작).

### 2. Task 자료구조 (PCB/TCB 통합, 이름은 `Task`)

DC-8EA1E7F6가 제시한 후보 전부 + FPU 컨텍스트(on-demand)까지 포함:

- 저장된 레지스터 상태(범용 레지스터/RIP/RFLAGS/세그먼트 셀렉터/CR3)
- **FPU/SSE/AVX 컨텍스트는 on-demand(지연 저장/복원)** - 이 Task가
  실제로 FPU를 쓴 적이 있을 때만 컨텍스트 전환 시 저장/복원한다
  (CR0.TS 비트로 FPU 미사용 시 트랩시켜 최초 사용 시점을 감지하는
  고전적 lazy-FPU 기법 활용 예정 - 구현 시 확정).
- 스케줄링 상태 enum(`Running`/`Ready`/`Blocked`/`Zombie` 등)과 전이
  규칙
- 우선순위(RT 클래스 vs 일반 클래스 구분 포함, 아래 6번 참고)
- CPU affinity 비트마스크(1번 참고)
- 커널 스택 포인터(3번 참고)
- 블로킹 사유(SP §2-B가 요구하는 유저 폴트 정보 보관 포함)
- 부모/자식 프로세스 관계
- 소속 NUMA 노드

### 3. 컨텍스트 전환 - 소프트웨어 방식

- x86 하드웨어 태스크 스위칭(TSS)은 안 쓴다 - 현재 레지스터를 이
  Task의 커널 스택에 수동으로 push하고, RSP를 다음 Task의 커널
  스택으로 바꾼 뒤 pop하는 방식(어셈블리 트램폴린 필요).

### 4. 커널 스택

- **기본 크기 8KiB** - Task 생성 시 인자로 다른 크기를 지정할 수도
  있다(가변).
- **컴파일 시점 매크로**로 "스택 오버플로우 감지용 가드 페이지"를
  켤 수 있어야 한다(디버깅 빌드 전용 - 매크로 꺼지면 가드 페이지
  없이 컴팩트하게, 켜지면 스택 바로 아래 의도적으로 매핑 안 한
  페이지를 둬서 오버플로우 시 #PF로 걸리게 함).

### 5. 주소공간 전환 최적화

- 같은 프로세스 내 Task(스레드) 간 전환에서는 CR3를 그대로 두고
  TLB 플러시를 피한다 - 다른 프로세스로 전환할 때만 CR3를 갈아
  끼운다.

### 6. 블로킹/웨이크업 - 내부 전용, 기능별 특수 API

- 범용 공개 API(`Scheduler::blockCurrent(reason)`/`wake()`류)는 **외부에
  노출하지 않는다**. 스케줄러 내부에서 자동으로 결정한다.
- 인터럽트로 깨워야 하는 대기 상황(예: IPC 응답 대기, 향후 페이지폴트
  SWAP-in 대기 등)마다 **그 기능 전용의 특수 API**를 만들고, 그
  API가 내부적으로 공통 block/wake 프리미티브를 호출하는 구조로
  간다 - 예: `Ipc::waitForReply(...)`가 내부에서 스케줄러의 비공개
  block 프리미티브를 쓰지만, 스케줄러 자체의 범용 block API를 다른
  코드가 직접 호출할 일은 없다.

### 7. 타이머 틱 소스 - 혼합형

- **선점 결정은 코어별 독립 LAPIC 타이머**가 각자 담당한다(이전
  세션에 이미 실측 검증된 `Lapic::startPeriodicTimer`를 정식 스케줄러
  틱으로 채택).
- **HPET(전역 카운터)은 전역 시각/타임아웃 계산 용도로만 유지**한다
  (`Timer::tickCount()`가 지금처럼 계속 존재 - 스케줄러 선점 자체엔
  안 씀).

### 8. 선점 정책과 타임퀀텀

- **혼합 선점**: 일반 작업은 선점형(타이머 인터럽트가 강제 전환),
  **커널 내부 임계구역 실행 중엔 선점 금지 구간**을 둔다(예: 스핀락을
  쥔 채로는 선점 안 됨 - 구현 시 "선점 비활성화 카운터" 같은 표준
  기법 사용 예정). **이 선점 비활성화 카운터는 공개 API로도 노출해야
  한다**(2026-09-14 추가) - Slab 할당자(SP-D7013B26/PL-16E2CDA4)의
  `PreemptionGuard`가 코어별 매거진을 보호하는 데 그대로 재사용한다
  - 이 프로젝트의 다른 lock-free 자료구조도 같은 프리미티브를 쓸
    가능성이 높으므로, 순수 내부 구현 디테일로 남기지 말 것.
- **실시간(RT) 클래스**를 별도로 지원한다(SCHED_FIFO/RR류 - 항상
  일반 작업보다 먼저 실행).
- **타임퀀텀 길이**: 지금은 기존 100Hz/10ms 틱을 그대로 1퀀텀=1틱
  으로 쓴다. 나중에 실측하며 조정할 수 있도록 하드코딩하지 말고
  변수/상수 하나로 노출해 둔다.

### 8-1. 즉시 스케줄링(우선순위 무시) - 비동기 프레임워크가 요구 (2026-09-14 추가)

비동기 프레임워크(SP-F682B889, 설계자 직접 지시, 2026-09-14)가
요구하는 새 프리미티브 - 코어별 리액터 Task를 긴급한 인터럽트가
왔을 때 **RT 클래스보다도 먼저** 즉시 실행시켜야 한다. 별도 DC
없이 직접 지시된 사항이라 여기 실행 계획에 바로 반영한다.

- `Scheduler::scheduleImmediate(Task* task)` - 대상 코어 큐의 맨
  앞(RT 클래스 큐보다도 앞)에 꽂는다. 일반적인 큐 삽입(`enqueue`)과
  분리된 별도 API로 둬서, "즉시 스케줄링"이 남용되지 않고 정말
  긴급한 경로(비동기 프레임워크의 완료 통지 등)에서만 쓰이게 한다.
- 인터럽트 컨텍스트에서 호출될 수 있으므로 lock-free 큐 삽입 경로
  (4단계)와 동일한 제약(락 없이, 최소 연산)을 따라야 한다.
- RT 클래스와의 상호작용: 즉시 스케줄링된 Task가 실행되는 동안은
  RT 클래스도 선점되는지, 아니면 "즉시 스케줄링 큐"가 RT 클래스와
  별도의 최상위 큐로 존재하는지는 구현 시 6단계(RT 클래스 추가)와
  같이 확정한다. **[완료, 2026-09-14]** 별도 최상위 큐(즉시 ->
  RT -> 일반, 3단 우선순위)로 구현 - 아래 5/6단계 참고.

### 9. 로드밸런싱(Push/Pull) 트리거 조건

- **Pull**: 자기 큐가 일정 시간 이상(지금은 약 100ms, 실측하며 보정
  예정) idle 상태로 지속되면 다른 코어에서 작업을 당겨온다.
- **Push**: 자기 큐 길이가 **최대 길이의 90%**를 넘어선 상태에서
  새 작업이 큐잉되면, 그 중 일부를 솎아내어 다른 코어로 민다.
- **CPU affinity가 걸린 Task는 로드밸런싱 대상에서 완전히 제외**
  (다른 코어에서 절대 실행하지 않음).

### 10. CAS 기반 동기화 - lock-free 자료형 + 조건부 폴백

- "CAS 기반 동기화"는 **큐 자료형 자체를 lock-free로 구현**하는
  것을 의미한다(단순 카운터에만 CAS를 쓰는 게 아니라 큐 자체가
  lock-free 자료구조).
- 단, **lock-free가 오히려 경합(contention)을 유발할 수 있는
  경우를 대비해 Spinlock 기반 폴백 구현을 준비**해 두고, 그런
  상황에서는 폴백을 쓴다 - 즉 두 구현을 다 만들고 상황에 따라
  고를 수 있는 형태로 설계한다(구현 시 어떤 신호로 "이 상황"을
  판단할지 - 예: 코어 수/경합 실측 - 구체화 예정).

## 구현 순서 (착수 계획)

0. **[완료, 2026-09-14] libkenv 원자 프리미티브 확장**: `AtomicU32`에
   `compareExchange(expected, desired)` 추가, 포인터 CAS용
   `AtomicPtr<T>`(load/store/exchange/compareExchange) 템플릿 신설
   (`minicore/libs/libkenv/spinlock.h`) - lock-free 큐(4단계)의 기반.
1. **[완료, 2026-09-14] `kernel::Task` 구조체 정의**: (원문 그대로 유지)
2. **[완료, 2026-09-14] 소프트웨어 컨텍스트 전환 어셈블리**: (원문 그대로 유지)
3. **[완료, 2026-09-14] 커널 스택 가드 페이지**: (원문 그대로 유지,
   TSS/IST는 SP-677210E6로 분리)
4. **[완료, 2026-09-14] 코어별 개별 큐(Spinlock 폴백)**: (원문 그대로 유지)
5. **[완료, 2026-09-14] LAPIC 틱 기반 선점**: `scheduler.h/.cpp`에
   `kSchedulerTickVector`(0x24, HPET(0x22)/레거시 PIT(0x23)와 안
   겹치는 다음 벡터) 신설 - `Timer::tickCount()`(HPET)와 **완전히
   독립된** 전용 LAPIC 주기 타이머(7절 그대로)를 BSP/AP 각자
   `Scheduler::startTickOnThisCore()`로 킨다(kMain은 TSS/IST 이후,
   kApMain은 Lapic::init() 이후). `idt.cpp`에 이 벡터를
   `kTimerVector`와 같은 방식으로 **특례 처리**(일반 `Idt::
   registerHandler` 동적 핸들러 경로를 안 씀) - `Scheduler::onTick`이
   **EOI를 가장 먼저 직접 보낸 뒤** 선점 여부를 판단한다: 여기서
   Task 전환이 일어나면 이 함수 호출 자체가 그 Task가 다시 스케줄될
   때까지 "반환하지 않고" 콜스택에 매달려 있게 되므로, EOI를 뒤로
   미루면(일반 동적 핸들러처럼 "핸들러 반환 후 EOI") 그 사이 이
   코어에 다음 스케줄러 틱이 아예 전달되지 않는다(실측 전 코드
   리뷰로 미리 피한 함정).
6. **[완료, 2026-09-14] 기본 라운드로빈 + RT 클래스**: 코어별로 즉시
   스케줄링 큐/RT 큐/일반 큐 3개를 두고(`gImmediateQueues`/
   `gRtQueues`/`gNormalQueues`), `pickNext`가 이 순서로 훑는 것만으로
   "즉시 스케줄링이 RT보다도 먼저, RT가 일반보다 먼저"를 큐 우선순위
   자체로 표현했다(별도 정렬/비교 로직 불필요). `enqueue`는
   `task->taskClass`로 RT/일반을 자동 분기. 라운드로빈은 각 큐 내부의
   단순 FIFO로 자연히 나온다. **디스패치 루프(`Scheduler::runLoop()`)
   신설** - 코어별 idle 컨텍스트: 큐가 비어 있으면 `sti; hlt`로 다음
   인터럽트까지 대기, 있으면 그 Task로 전환한다. `kMain`/`kApMain`의
   기존 `for(;;) hlt` 자리를 이걸로 교체했다 - 이 지점부터 BSP/모든
   AP가 실제로 스케줄러 디스패치에 들어간다(이전엔 큐 자료구조만
   있고 아무도 소비하지 않았다).
8-부분. **[완료, 2026-09-14] 선점 비활성화 카운터 + 협조적 yield**:
   `Scheduler::disablePreemption()`/`enablePreemption()`(코어별 카운터,
   `onTick`이 이 값을 보고 0보다 크면 선점을 보류 - 인터럽트 자체는
   계속 처리) + `PreemptionGuard` RAII(SP-D7013B26가 요구하는 그대로
   `scheduler.h`에 위치). `Scheduler::yieldCurrent()`(협조적 양보,
   현재 Task를 Ready로 다시 큐에 넣고 idle로 전환)도 이 단계에서 같이
   구현 - "블로킹"(특정 이유로 재운 뒤 `wake()`가 있어야 다시 깨는
   버전)은 6번 원칙대로 **아직 범용 API로 노출하지 않는다** - 첫
   소비자(Syscall 서브시스템의 `waitForSyscall`, SP-04EE2A18)가 생길
   때 그 기능 전용 API로 구현할 예정(이번 단계 범위 밖).

   **실측 중 발견한 두 가지 경쟁 조건(둘 다 수정 완료)**:
   1. `runLoop()`이 `gCurrentTask[coreIndex] = next`를 **실제로
      `next`의 스택으로 넘어가기 전에**(`kContextSwitch` 호출 전에)
      먼저 써 둔다 - 이 사이(코드상 두 줄 차이지만 이 시점엔 이미
      인터럽트가 켜져 있음) 스케줄러 틱이 끼어들면, `onTick`이
      "`next`가 이미 실행 중"이라고 착각해 **아직 idle 스택 위에
      있는 `runLoop`의 이 `kContextSwitch` 호출 자체를** `next`의
      것인 양 가로채 다른 Task로 전환해 버린다 - `next->savedRsp`가
      idle 스택의 스냅샷으로 덮어써지고, 나중에 `next`가 진짜로
      선택되면 완전히 잘못된 상태를 복원해 RFLAGS(TF 등 쓰레기 값)/
      RBP가 깨진 채 실행되다가 `#DB`/`#PF`로 죽는다(4코어 SMP + 여러
      Task 부하가 걸려야 확률적으로 드러남 - 단일 Task/저부하에서는
      우연히 안 걸림). **수정**: `gCurrentTask[coreIndex] = next`
      직전에 `cli` - `kContextSwitch`의 `pushfq`/`popfq`가 이 "꺼짐"
      상태를 idle 쪽 저장 슬롯에만 반영하고(나중에 idle이 재개될 때만
      복원), `next`는 자신이 마지막으로 저장해 둔 RFLAGS(보통 IF=1)로
      독립적으로 재개되므로 "인터럽트 꺼짐"이 `next` 쪽으로 새어
      나가지 않는다 - 스케줄러 전체를 오래 막지 않는 아주 좁은 창만
      닫는 표준 기법.
   2. `yieldCurrent()`가 **`gCurrentTask`를 지우기 전에** 먼저
      `enqueue()`로 자신을 큐에 넣으면, 같은 이유(Task 실행 흐름은
      IF=1)로 그 사이 낀 틱이 "지금 실행 중인 Task"와 "막 큐에 들어온
      Task"를 같은 것으로 보고 자기 자신을 다시 뽑아 이중 스케줄링을
      일으킨다(침습적 `next` 포인터가 꼬여 큐가 깨지고, 아직 완성
      안 된 `kContextSwitch` 준비 상태 위에 또 다른 `kContextSwitch`가
      겹쳐 스택이 망가짐). **수정**: 1번과 동일하게 `cli` +
      "`gCurrentTask`를 먼저 nullptr로 지운 뒤에 enqueue" 순서로
      정정.
   두 버그 모두 4코어 SMP(`q35 -smp 4`) + 즉시/RT/일반 4개 Task
   동시 실행 스모크 테스트로 실측 발견 - 수정 후 같은 조건으로 20초
   연속 무크래시 재검증 완료(단일 코어 PVH/GRUB 부팅 회귀도 없음).

## 완료됨 (5/6/8-부분단계 - 위 참고), 남은 단계

7. **Push/Pull 로드밸런싱**: 9번 항목의 임계치대로 구현, CPU affinity
   제외 로직 포함 - 아직 미착수(Slab/AsyncTask/Syscall/Channel IPC
   구현에 필수 전제조건은 아니라 후순위로 미룸).
8-나머지. **"기능 전용" 블로킹/웨이크업**: 위에서 협조적 yield까지는
   구현됐으나, "특정 이유로 블로킹 후 누군가 깨울 때까지 대기"는
   아직 없음 - Syscall 서브시스템(SP-04EE2A18)의 `waitForSyscall`이
   첫 소비자가 될 예정.
9. **FPU 지연 컨텍스트**: CR0.TS 트랩 기반 lazy save/restore - 아직
   미착수.
10. **검증**: 매 단계마다 QEMU 실측 - 5/6/8-부분단계는 단일 코어
    (PVH/GRUB)와 `-smp 4`(GRUB+q35) 둘 다 즉시/RT/일반 클래스가
    섞인 임시 디버그 Task 4개로 검증 완료(위 버그 수정 포함), 임시
    코드는 제거함.

## 등록된 미해결 설계 공백 (구현 중 발견)

- **HPET 없는 환경에서 LAPIC 타이머 소유권 충돌**: `Timer::init()`은
  HPET가 없으면 기존에 `Lapic::startPeriodicTimer(kTimerVector, ...)`
  로 LAPIC 물리 타이머를 직접 점유해 전역 `tickCount()`를 공급했다.
  이번에 추가한 `Scheduler::startTickOnThisCore()`도 **같은 물리
  LAPIC 타이머**를 `kSchedulerTickVector`로 재프로그램한다 - 코어당
  하드웨어 LAPIC 타이머는 하나뿐이라 **두 벡터를 동시에 낼 수 없다**.
  HPET가 있는 환경(이 프로젝트의 QEMU 개발 환경 포함, 실측 전부 이
  경로)에서는 `Timer::init()`이 LAPIC을 아예 안 건드리므로 충돌이
  없지만, HPET가 없는 폴백 환경에서는 `Scheduler::startTickOnThisCore()`
  호출이 `Timer`가 이미 걸어 둔 LAPIC 프로그래밍을 조용히 덮어써
  전역 `Timer::tickCount()`가 더 이상 증가하지 않게 된다(스케줄러
  자체는 정상 동작). **DC-0CC88ABB/QU-3218B790으로 등록해 설계자
  확인을 받는 중**이다 - 후보안: (a) 그 경우 `Scheduler::onTick`이
  BSP 한정으로 `Timer::onTick()`도 같이 호출(SMP에서 코어 수만큼
  틱이 겹치지 않도록 BSP만), (b) `Timer::init()`을 아예 LAPIC
  프로그래밍 없이 "HPET 없으면 tickCount 없음"으로 단순화하고 그
  대신 문서화, (c) 그 환경만 별도 저속 폴링(PIT 등)으로 전역 시각을
  공급. 아직 코드에는 반영하지 않았다(현재 개발/실측 환경은 항상
  HPET가 있어 당장 막힌 경로는 아님).
