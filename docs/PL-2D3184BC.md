# 실행 계획: 스케줄러 (프로세스/태스크/컨텍스트 스위칭)

**[설계 확정, 구현 착수, 2026-09-14]** DC-8EA1E7F6/QU-BA001D73과
DC-B80D8D31/QU-77A52430 답변으로 설계가 확정됐다. 이 문서는 확정된
결정을 정리하고, 구현 순서를 계획한다 - 진행되면서 "한 것" 절을
채워 나간다.

## 배경

DS-D4E5C451(QU-C3EC2C63)이 스케줄러 상위 구조("코어별 개별 큐 +
CPU affinity + CAS 기반 동기화 + Push/Pull 로드밸런싱")를 이미
확정해 뒀고, PL-E68894CD §5가 "HPET/LAPIC 타이머 공존 방식은
스케줄러 설계 시점에 구체화"하기로 미뤄 뒀다. 이번에 그 하위
세부(프로세스/스레드 모델, 컨텍스트 전환, 큐 알고리즘, 타이머 틱
소스, 로드밸런싱 트리거, lock-free 자료구조 범위)를 DC-8EA1E7F6/
DC-B80D8D31로 등록해 설계자 확정을 받았다.

## 확정된 설계

### 1. 스케줄링 단위 — `Task`

- 스케줄링 최소 단위의 이름은 **`Task`**로 확정(코드에서도 `kernel::
  Task`로 명명 - `Thread`/`TCB` 같은 이름 대신). 하나의 **프로세스는
  여러 Task(스레드)를 가질 수 있다** - 즉 프로세스=주소공간+자원의
  소유자, Task=실제 스케줄링/실행 단위로 분리.
- 각 Task는 자신만의 **CPU affinity 제약**을 가질 수 있다 - "어떤
  코어에서만 실행 가능"(허용 목록, whitelist) 또는 "어떤 코어에서는
  실행 불가"(제외 목록, blacklist) 둘 다 표현 가능해야 한다 - 비트마스크
  (코어 수만큼의 비트, 1=허용)면 두 형태 모두 자연스럽게 표현된다
  (허용 목록 = 그 비트들만 세움, 제외 목록 = 그 비트들만 지움, 전체
  코어 마스크에서 시작).

### 2. Task 자료구조 (PCB/TCB 통합, 이름은 `Task`)

DC-8EA1E7F6가 제시한 후보 전부 + FPU 컨텍스트(on-demand)까지 포함:

- 저장된 레지스터 상태(범용 레지스터/RIP/RFLAGS/세그먼트 셀렉터/CR3)
- **FPU/SSE/AVX 컨텍스트는 on-demand(지연 저장/복원)** - 이 Task가
  실제로 FPU를 쓴 적이 있을 때만 컨텍스트 전환 시 저장/복원한다
  (CR0.TS 비트로 FPU 미사용 시 트랩시켜 최초 사용 시점을 감지하는
  고전적 lazy-FPU 기법 활용 예정 - 구현 시 확정).
- 스케줄링 상태 enum(`Running`/`Ready`/`Blocked`/`Zombie` 등)과 전이
  규칙
- 우선순위(RT 클래스 vs 일반 클래스 구분 포함, 아래 6번 참고)
- CPU affinity 비트마스크(1번 참고)
- 커널 스택 포인터(3번 참고)
- 블로킹 사유(SP §2-B가 요구하는 유저 폴트 정보 보관 포함)
- 부모/자식 프로세스 관계
- 소속 NUMA 노드

### 3. 컨텍스트 전환 - 소프트웨어 방식

- x86 하드웨어 태스크 스위칭(TSS)은 안 쓴다 - 현재 레지스터를 이
  Task의 커널 스택에 수동으로 push하고, RSP를 다음 Task의 커널
  스택으로 바꾼 뒤 pop하는 방식(어셈블리 트램폴린 필요).

### 4. 커널 스택

- **기본 크기 8KiB** - Task 생성 시 인자로 다른 크기를 지정할 수도
  있다(가변).
- **컴파일 시점 매크로**로 "스택 오버플로우 감지용 가드 페이지"를
  켤 수 있어야 한다(디버깅 빌드 전용 - 매크로 꺼지면 가드 페이지
  없이 컴팩트하게, 켜지면 스택 바로 아래 의도적으로 매핑 안 한
  페이지를 둬서 오버플로우 시 #PF로 걸리게 함).

### 5. 주소공간 전환 최적화

- 같은 프로세스 내 Task(스레드) 간 전환에서는 CR3를 그대로 두고
  TLB 플러시를 피한다 - 다른 프로세스로 전환할 때만 CR3를 갈아
  끼운다.

### 6. 블로킹/웨이크업 - 내부 전용, 기능별 특수 API

- 범용 공개 API(`Scheduler::blockCurrent(reason)`/`wake()`류)는 **외부에
  노출하지 않는다**. 스케줄러 내부에서 자동으로 결정한다.
- 인터럽트로 깨워야 하는 대기 상황(예: IPC 응답 대기, 향후 페이지폴트
  SWAP-in 대기 등)마다 **그 기능 전용의 특수 API**를 만들고, 그
  API가 내부적으로 공통 block/wake 프리미티브를 호출하는 구조로
  간다 - 예: `Ipc::waitForReply(...)`가 내부에서 스케줄러의 비공개
  block 프리미티브를 쓰지만, 스케줄러 자체의 범용 block API를 다른
  코드가 직접 호출할 일은 없다.

### 7. 타이머 틱 소스 - 혼합형

- **선점 결정은 코어별 독립 LAPIC 타이머**가 각자 담당한다(이전
  세션에 이미 실측 검증된 `Lapic::startPeriodicTimer`를 정식 스케줄러
  틱으로 채택).
- **HPET(전역 카운터)은 전역 시각/타임아웃 계산 용도로만 유지**한다
  (`Timer::tickCount()`가 지금처럼 계속 존재 - 스케줄러 선점 자체엔
  안 씀).

### 8. 선점 정책과 타임퀀텀

- **혼합 선점**: 일반 작업은 선점형(타이머 인터럽트가 강제 전환),
  **커널 내부 임계구역 실행 중엔 선점 금지 구간**을 둔다(예: 스핀락을
  쥔 채로는 선점 안 됨 - 구현 시 "선점 비활성화 카운터" 같은 표준
  기법 사용 예정). **이 선점 비활성화 카운터는 공개 API로도 노출해야
  한다**(2026-09-14 추가) - Slab 할당자(SP-D7013B26/PL-16E2CDA4)의
  `PreemptionGuard`가 코어별 매거진을 보호하는 데 그대로 재사용한다
  - 이 프로젝트의 다른 lock-free 자료구조도 같은 프리미티브를 쓸
    가능성이 높으므로, 순수 내부 구현 디테일로 남기지 말 것.
- **실시간(RT) 클래스**를 별도로 지원한다(SCHED_FIFO/RR류 - 항상
  일반 작업보다 먼저 실행).
- **타임퀀텀 길이**: 지금은 기존 100Hz/10ms 틱을 그대로 1퀀텀=1틱
  으로 쓴다. 나중에 실측하며 조정할 수 있도록 하드코딩하지 말고
  변수/상수 하나로 노출해 둔다.

### 8-1. 즉시 스케줄링(우선순위 무시) - 비동기 프레임워크가 요구 (2026-09-14 추가)

비동기 프레임워크(SP-F682B889, 설계자 직접 지시, 2026-09-14)가
요구하는 새 프리미티브 - 코어별 리액터 Task를 긴급한 인터럽트가
왔을 때 **RT 클래스보다도 먼저** 즉시 실행시켜야 한다. 별도 DC
없이 직접 지시된 사항이라 여기 실행 계획에 바로 반영한다.

- `Scheduler::scheduleImmediate(Task* task)` - 대상 코어 큐의 맨
  앞(RT 클래스 큐보다도 앞)에 꽂는다. 일반적인 큐 삽입(`enqueue`)과
  분리된 별도 API로 둬서, "즉시 스케줄링"이 남용되지 않고 정말
  긴급한 경로(비동기 프레임워크의 완료 통지 등)에서만 쓰이게 한다.
- 인터럽트 컨텍스트에서 호출될 수 있으므로 lock-free 큐 삽입 경로
  (4단계)와 동일한 제약(락 없이, 최소 연산)을 따라야 한다.
- RT 클래스와의 상호작용: 즉시 스케줄링된 Task가 실행되는 동안은
  RT 클래스도 선점되는지, 아니면 "즉시 스케줄링 큐"가 RT 클래스와
  별도의 최상위 큐로 존재하는지는 구현 시 6단계(RT 클래스 추가)와
  같이 확정한다.

### 9. 로드밸런싱(Push/Pull) 트리거 조건

- **Pull**: 자기 큐가 일정 시간 이상(지금은 약 100ms, 실측하며 보정
  예정) idle 상태로 지속되면 다른 코어에서 작업을 당겨온다.
- **Push**: 자기 큐 길이가 **최대 길이의 90%**를 넘어선 상태에서
  새 작업이 큐잉되면, 그 중 일부를 솎아내어 다른 코어로 민다.
- **CPU affinity가 걸린 Task는 로드밸런싱 대상에서 완전히 제외**
  (다른 코어에서 절대 실행하지 않음).

### 10. CAS 기반 동기화 - lock-free 자료형 + 조건부 폴백

- "CAS 기반 동기화"는 **큐 자료형 자체를 lock-free로 구현**하는
  것을 의미한다(단순 카운터에만 CAS를 쓰는 게 아니라 큐 자체가
  lock-free 자료구조).
- 단, **lock-free가 오히려 경합(contention)을 유발할 수 있는
  경우를 대비해 Spinlock 기반 폴백 구현을 준비**해 두고, 그런
  상황에서는 폴백을 쓴다 - 즉 두 구현을 다 만들고 상황에 따라
  고를 수 있는 형태로 설계한다(구현 시 어떤 신호로 "이 상황"을
  판단할지 - 예: 코어 수/경합 실측 - 구체화 예정).

   후속 단계에서 채운다.
2. **[완료, 2026-09-14] 소프트웨어 컨텍스트 전환 어셈블리**:
   `minicore/libs/x86_64/context_switch.S` 신설(post-boot 아키텍처
   종속 코드라 이 위치로 확정) - `kContextSwitch(oldRspSlot, newRsp)`
   가 콜리세이브 레지스터(rbx/rbp/r12-r15)+RFLAGS를 저장/복원하고,
   `kTaskStartTrampoline`이 최초 실행 태스크를 위한 진입점 역할을
   한다(스택 레이아웃 불변조건은 관계도에 기록,
   `minicore/libs/x86_64/context_switch.S` 참고). **실측(2026-09-14,
   QEMU 8.2.2)**: 태스크 A/B 둘을 만들어 6회 협조적으로 서로 전환한
   뒤 kmain 자신에게 정확히 복귀 - 시리얼 출력이 기대한 순서
   (`ABABAB`)와 정확히 일치함을 확인, 최초 실행(트램폴린 경로)과
   재개(저장/복원 경로) 둘 다 검증됨. 기본(1코어)/q35+`-smp 4`
   둘 다에서 기존 SMP AP 기동 등과 회귀 없음 확인. 검증 후 임시
   테스트 코드는 제거 - 영구 코드는 `task.h/.cpp`와
   `context_switch.S` 자체만 남음.
3. **[구현 완료, 설계자 결정 대기, 2026-09-14] 커널 스택 가드
   페이지**: `MINICORE_TASK_STACK_GUARD_PAGE` CMake 옵션(기본 OFF) +
   `task.cpp` - 켜지면 direct map(1GiB 거대페이지라 4KiB 단위로
   구멍을 낼 수 없음)을 안 쓰고, 스택마다 전용 가상주소
   (`0xFFFF902000000000` 이후)에 4KiB 페이지 단위로 개별 매핑한 뒤
   바로 아래 한 페이지를 의도적으로 비워 둔다. **실측(QEMU,
   `-d int`)으로 가드 페이지 자체는 정확히 동작함을 확인**(4KiB
   스택을 재귀로 오버플로우시키면 CR2가 정확히 가드 페이지 범위
   안을 가리키는 #PF 발생). 단, **그 #PF를 전달하려는 시도 자체가
   이미 꽉 찬 스택에 인터럽트 프레임을 푸시하려다 재폴트 -> #DF ->
   트리플 폴트(조용한 리셋)로 격상됨을 함께 발견** - IST가 전혀
   없어서(idt.cpp 전 벡터 ist=0) 벌어지는 일이다. 즉 지금 상태로는
   "오버플로우를 조용한 메모리 손상 대신 확실한 크래시로 바꾸는"
   효과는 있지만, 계획이 원래 의도한 "#PF로 걸려 진단 가능하게"는
   TSS+IST 없이는 달성 못함. 이 문제와 두 가지 해결 방향(지금
   TSS+IST 최소 구현 vs 유저랜드 syscall 구현 시점으로 미루기)을
   **DC-3D3212A4/QU-4E00C118**로 등록해 설계자 답변 대기 중 - 답변에
   따라 이 단계를 마무리 짓거나 TSS/IST를 추가한다.
4. **[완료, 2026-09-14] 코어별 개별 큐(Spinlock 폴백)**:
   `minicore/kernel/scheduler.h/.cpp` 신설 - `TaskQueue`(단일 연결
   리스트, `Task::next` 침습적 포인터 재사용, `Spinlock`으로 보호)
   + `Scheduler`(코어 수만큼 `TaskQueue` 배열 관리, `Acpi::cpuCount()`
   기준). `pushBack`/`popFront`로 일반 FIFO enqueue/dequeue,
   `pushFront`로 8-1의 `scheduleImmediate`(RT보다도 먼저 나가야 하는
   긴급 경로)를 구현. **계획 10번 지시대로 이번 단계는 Spinlock
   폴백만 구현** - lock-free 버전은 이 폴백으로 스케줄러 전체 흐름을
   먼저 검증한 뒤 교체/비교 예정(아직 안 함). **실측(QEMU, 단일
   코어/q35 `-smp 4` 둘 다)**: 임시 테스트로 `enqueue(t1)`,
   `enqueue(t2)`, `scheduleImmediate(t3)` 후 `pickNext`를 4번 불러
   `t3, t1, t2, nullptr` 순서가 정확히 나오는지 확인(`PASS`) - FIFO
   순서와 즉시 스케줄링의 선입 둘 다 검증됨. 검증 후 임시 테스트
   코드는 제거 - 영구 코드는 `scheduler.h/.cpp` 자체만 남음. 아직
   이 큐를 실제로 소비하는 디스패치 루프(LAPIC 틱 기반 선점=5단계,
   라운드로빈=6단계)는 없다 - `Scheduler::init()`도 kMain에서 아직
   호출하지 않는다(다음 단계에서 연결).
5. **LAPIC 틱 기반 선점**: 이전 세션에 검증해 둔 `Lapic::
   startPeriodicTimer`를 실제 스케줄러 틱으로 연결 - 선점 금지
   구간(임계구역) 처리 포함.
6. **기본 라운드로빈 + RT 클래스**: 큐 안에서 가장 단순한 알고리즘
   (라운드로빈)부터 동작시키고, RT 클래스(항상 우선)를 별도 큐로
   추가.
7. **Push/Pull 로드밸런싱**: 9번 항목의 임계치대로 구현, CPU affinity
   제외 로직 포함.
8. **블로킹/웨이크업 내부 프리미티브**: 6번 항목대로 범용 API는
   비공개로 두고, 첫 소비자가 생길 때(예: 아직 없지만 향후 IPC/
   페이지폴트 SWAP-in) 그 기능 전용 API로 노출.
9. **FPU 지연 컨텍스트**: CR0.TS 트랩 기반 lazy save/restore.
10. **검증**: 매 단계마다 이 세션의 기존 방식대로 QEMU 실측(단일
    코어부터 시작해 `-smp 2/4`로 실제 멀티코어 스케줄링까지) - 임시
    디버그 태스크를 만들어 서로 양보/선점되는지 확인 후 코드 제거.

## 아직 미정으로 남겨 둔 것 (구현 중 실측/판단, 새 DC 불필요 수준)

- 타임퀀텀 정확한 값 조정, pull idle 임계치(100ms) 정확한 값, lock-free
  "폴백 전환 조건"의 구체적 판단 기준 - 설계자가 "실측하며 보정"이라고
  명시적으로 남겨 둔 항목들.
