# systemd 포팅 준비 사전조사

설계자 Opinion(`PN-A0EF864B` 대상, 2026-09-26): "systemd를 포팅할
수 있는 기반이 얼마나 준비되었는지, 그리고 무엇이 필요한지 분석하여
`systemd 포팅 준비 사전조사`라는 문서를 작성하라." 이 문서는 그
요청에 답한다 - 설계 제안이 아니라 **현재 상태 대조 + 갭 목록**이
목적이다(CLAUDE.md 규칙4 - 갭을 발견해도 이 문서 안에서 해결책을
임의로 확정하지 않고, 필요한 것만 목록화해 후속 계획/질의로 넘긴다).

## 0. systemd가 PID 1로서 실제로 의존하는 것 (평가 기준)

`man systemd`/`man systemd.exec`/Linux 커널 요구사항을 기준으로,
systemd 코어(unit 관리자로서의 PID 1 역할)가 최소한 요구하는 커널·
플랫폼 기능을 항목화한다 - 이 각 항목을 아래 §1에서 minicore와
대조한다.

1. **프로세스 감독**: `fork()`+`exec()`(또는 `posix_spawn`), `wait()`/
   `waitpid()`, `SIGCHLD`, 좀비/고아 프로세스 처리(고아는 PID 1이
   입양).
2. **cgroup**: 각 서비스 unit을 독립 cgroup으로 격리, 자원 제한
   (CPU/메모리/IO), 프로세스 트리 강제 종료(`cgroup.kill`),
   freezer.
3. **소켓 활성화**: `AF_UNIX`/`AF_INET` 소켓을 systemd가 미리 만들어
   두고 그 fd를 서비스에 상속(`LISTEN_FDS` 환경변수 규약) - 첫 연결
   시점에 서비스를 지연 기동.
4. **D-Bus**: systemd 자신의 제어 인터페이스(`systemctl` 등)와 다른
   시스템 서비스 대부분(NetworkManager, logind 등)이 D-Bus로 통신 -
   `sd-bus` 또는 D-Bus 데몬 자체가 필요.
5. **이벤트 루프**: `epoll`(`sd-event`의 기반) - 다수의 fd/타이머/
   시그널을 단일 스레드에서 멀티플렉싱.
6. **udev/장치 이벤트**: `netlink` uevent 소켓, `/sys` sysfs 트리,
   장치 노드 자동 생성(`/dev`).
7. **마운트 네임스페이스**: 서비스별 `PrivateTmp`/`ProtectSystem`
   같은 격리 기능(`unshare()`/`mount namespace`) - 코어 기능은 아니나
   현대 systemd 배포판 unit 파일들이 기본값으로 흔히 사용.
8. **저널/로깅**: `journald`(구조화 바이너리 로그) 또는 최소
   syslog 호환 소켓(`/dev/log`).
9. **사용자/세션**: `logind`(세션·시트 관리), PAM 연동 - 로그인
   관리형 systemd 기능(멀티유저 세션 필요 시).
10. **파일시스템 계층**: FHS 경로 관례(`/etc`, `/run`, `/var`,
    `/proc`, `/sys`) - unit 파일 탐색 경로, `/run`에 소켓/PID 파일.
11. **시그널/타이머**: `SIGTERM`/`SIGKILL`/`SIGHUP` 전달, `timerfd`
    (systemd timer unit).
12. **Capabilities/seccomp**: 세밀한 권한 분리(`CapabilityBoundingSet`,
    `SystemCallFilter`) - unit 격리 기능, 코어 동작에는 필수 아님.

## 2. 종합 평가

**프로세스 감독 + cgroup 두 핵심 축은 이미 상당히 준비돼 있다** -
systemd의 근본 존재 이유(unit별 프로세스를 만들고, 그 프로세스를
cgroup으로 격리해 자원을 통제하고, 죽으면 회수한다)에 필요한 하위
인프라(`fork`/`SpawnProcess`/`wait`/좀비-고아 처리/`ResourceGroup`
트리/쿼터/freeze/계정)가 전부 실측 검증까지 마친 상태로 존재한다.
이 두 축만 보면 "포팅 기반이 없다"고 할 수 없다.

**그러나 systemd가 실제로 동작하려면 훨씬 많은 것이 더 필요하다**
- 특히 아래 세 가지는 단순 포팅이 아니라 **이 프로젝트 자체의 새
설계 영역**을 열어야 한다:

1. **소켓 활성화(AF_UNIX + LISTEN_FDS)** - systemd unit 파일 대부분이
   전제하는 핵심 메커니즘인데, 이 프로젝트의 IPC(`Channel`)는 처음부터
   POSIX 소켓과 다른 철학(이름 있는 메시징 채널, 와이어 포맷 자유)으로
   설계됐다. **완전히 새로운 계층**(POSIX 소켓 API 에뮬레이션 또는
   `Channel` 위에 `LISTEN_FDS` 규약을 얹는 어댑터)이 필요하다.
2. **D-Bus(또는 대체 IPC 버스)** - systemd 생태계 대부분의 서비스가
   D-Bus에 의존한다. `pubreg`가 개념적으로 가장 가깝지만 프로토콜
   자체가 다르다 - D-Bus 와이어 프로토콜을 그대로 구현할지, 아니면
   systemd 자체를 D-Bus 없이 구동 가능한 최소 구성(`sd-bus` 없이도
   PID 1 코어 기능만 쓰는 조합)으로 좁힐지는 **설계 결정이 필요**하다.
3. **FHS 경로 비호환** - systemd의 unit 파일 탐색 경로(`/etc/systemd/
   system`, `/usr/lib/systemd/system` 등)와 런타임 경로(`/run`)가
   이 프로젝트의 `/sys/etc`/`/sys/live` 네이밍과 전혀 다르다 - unit
   파일 경로를 그대로 포팅할지, 이 프로젝트 트리에 맞게 재매핑할지도
   **설계 결정이 필요**하다.

**낮은 우선순위로 미룰 수 있는 것**: journald(syslog 호환으로 축소
가능), logind/PAM(멀티세션 로그인 관리 자체가 이 프로젝트에 아직
없어 systemd 포팅과 별개로 이미 열려 있는 더 큰 공백), Capabilities/
seccomp(unit 격리 강화 기능, PID 1 코어 동작에는 필수 아님), 마운트
네임스페이스(`PrivateTmp` 등 일부 unit 옵션만 못 쓰게 될 뿐 코어는
동작 가능).

## 3. 결론 - "무엇이 필요한가"

systemd를 **일부 기능만이라도** 실제로 포팅하려면 최소한 다음이
필요하다(우선순위 순):

1. **AF_UNIX 소켓 API 에뮬레이션 + 소켓 활성화(`LISTEN_FDS`) 계층**
   - 가장 큰 단일 갭. `Channel` IPC 위에 얹거나 별도 구현.
2. **D-Bus 대체 전략 결정** - (a) D-Bus 프로토콜을 이 프로젝트에
   구현, (b) systemd를 D-Bus 없이 동작하는 최소 구성으로 포팅,
   (c) `pubreg`를 D-Bus 호환 계층으로 확장 - 셋 중 하나를 설계자가
   결정해야 한다.
3. **unit 파일 경로 재매핑 정책** - FHS 경로를 그대로 흉내낼지, 이
   프로젝트 트리에 맞게 unit 탐색 경로를 재정의할지.
4. **epoll 호환 계층(또는 `sd-event` 백엔드 교체)** - systemd 소스를
   그대로 가져온다면 필요, 이 프로젝트의 이벤트 모델로 새로
   구현한다면 불필요(선택은 "포팅"의 정의에 따라 갈림 - 소스
   그대로 빌드할지, 이 프로젝트 인프라 위에 새로 작성할지).
5. **udev 최소 기능(netlink uevent 소켓 또는 대체 통지 경로)** -
   PnP 프레임워크의 핫플러그 알림을 udev 규칙 엔진이 기대하는
   형태로 노출하는 어댑터.

**이 문서가 내리지 않는 결정**: 위 5가지 중 어느 것을 언제
설계할지, systemd를 "소스 그대로 빌드"할지 "핵심 개념만 재구현"할지
는 이 사전조사의 범위를 넘는 설계 결정이다(CLAUDE.md 규칙4) - 필요
시 별도 DC/질의로 등록한다.
