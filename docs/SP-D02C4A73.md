# libswapfs — 스왑 온디스크 포맷(Linux swap-space v2 준수) + SwapfsBackend 구현 설계

**[정정, 2026-09-22, 설계자 답변 QU-CE388254]** 이 문서의 최초안은
자체 고안 슈퍼블록/디스크 상주 비트맵 포맷을 제안했으나 반려됐다 -
설계자 답변 원문: "libext4/libswapfs/libvfat 모두 설계해야 하고,
libswapfs도 외부 표준에 맞춰야해." **libswapfs도 ext4/FAT32와
마찬가지로 이미 존재하는 외부 표준(Linux swap-space v2, 매직
"SWAPSPACE2")을 따라야 한다** - 이 프로젝트가 새로 고안하는 포맷이
아니다. 아래는 그 표준에 맞춰 전면 재작성한 설계다. 원안(자체 고안
포맷)은 §3.5에 역사적 기록으로만 남긴다.

## 1. 배경 및 필요성

`SP-2BCE5D60` §4가 `SwapBackend` 추상 인터페이스(`mount`/`readSlot`/
`writeSlot`/`allocateSlot`/`freeSlot`)를 확정하며 `class SwapfsBackend
: public SwapBackend { /* 후속 */ };`로 실제 구현을 명시적으로 미뤄
뒀다. `SP-6CEFBE9B` §6/§7(rmap + swap LRU)도 스왑아웃 트리거·회수
순서·`SwapBackend::writeSlot` 호출 지점까지 전부 설계를 마쳤고,
`PN-4859FDE9`(회수 스캔 정책)도 "실제 구현 착수는 `PN-452FF696`(fs
서비스)를 기다린다"로 완결됐다. 그런데 `PN-452FF696`(fs 서비스 최초
구현) 자신은 "남은 블로커는 `libext4`/`libswapfs`/`libvfat` 부재뿐"
이라고 명시하고 있고, `RM-7C249618`은 이 세 라이브러리를 전부
"예정, 미구현"으로만 기록해 뒀다 - 즉 이 프로젝트에서 실제 디스크
파일 I/O로 이어지는 마지막 연결 고리가 통째로 비어 있다.

이 문서는 그 중 **`libswapfs`**를 설계한다 - **Linux swap-space v2
표준을 그대로 따르는 온디스크 포맷 읽기/쓰기 라이브러리**(§3)와,
지금까지 이 프로젝트 어디에도 없었던 **"스왑 PTE 인코딩"**(스왑아웃된
페이지를 PTE 안에 어떻게 표시해 두는지, 이 커널 자신의 x86_64 PTE
포맷 안에서만 의미를 갖는 순수 이 프로젝트 내부 설계라 외부 표준이
없음, §5)을 함께 채운다.

## 2. 스코프

- **경로**: `minicore/libs/libswapfs`(`RM-7C249618`가 이미 지정해 둔
  경로 그대로).
- **커널/유저 공용**: `SP-7CC5693A` §2의 기존 결정(추후 커널 직접
  링크 최적화 옵션을 위한 선제 조치, `QU-4B1B6DDE` 답변) 그대로 -
  `libelf`/`libjson`과 동일하게 매크로로 컴파일 모드만 구분, v1은
  유저랜드(`fs` 서비스)만 실제로 쓴다.
- **v1 범위**: Linux swap-space v2 포맷의 읽기/쓰기 + 슬롯(페이지)
  단위 alloc/free. `mkswap`이 만든 실제 스왑 파티션 이미지를 그대로
  마운트할 수 있어야 한다(표준 준수의 실질적 검증 기준).
- **범위 밖**: 슈퍼블록 자동 판별 알고리즘 자체의 구현 세부(`SP-2BCE5D60`
  §6이 이미 "각 드라이버 착수 시점의 구현 세부"로 명시적으로 미뤄 둠) -
  이 문서는 그 판별에 필요한 매직/헤더 포맷만 고정한다.
- **스왑 영역이 파티션인지 파일인지**: 별도 결정이 필요 없다 - `SwapBackend::
  mount(BlockDevice* device)`가 이미 `FileSystemDriver::mount`와 동일하게
  "device는 항상 불투명한 블록 장치"(`SP-2BCE5D60` §3 서두)를 받도록
  확정돼 있으므로, swapfs도 ext4/FAT32와 마찬가지로 **자신만의 블록
  장치(파티션)에 마운트**된다 - `SP-7CC5693A` §5 5단계(우선순위대로
  슈퍼블록 판별)가 그대로 적용된다. 새 DC 불필요.

## 3. 온디스크 포맷 — Linux swap-space v2(`SWAPSPACE2`) 준수

### 3.1 스왑 헤더 (블록 장치의 페이지 0, 4096바이트)

Linux swap-space v2 레이아웃을 그대로 따른다(`mkswap`/리눅스 커널
`include/linux/swap.h`의 `union swap_header`와 동일 구조). **정확한
필드 폭/패딩 바이트 수는 이 문서가 기억에 의존해 옮긴 것이라, 구현
착수 시 반드시 실제 리눅스 커널 헤더 또는 `mkswap`/`util-linux`
소스와 1바이트 단위로 대조해 재확인할 것** - 구조의 골격(필드 순서/
의미/매직 위치)은 신뢰도가 높으나 `padding[117]` 같은 정확한 배열
길이는 이 문서 하나만으로 확정하지 않는다(CLAUDE.md 규칙4 정신 -
불확실한 세부를 단언하지 않음).

```cpp
struct SwapHeaderInfo {
    char     bootbits[1024];   // 부트로더/디스크레이블 예약 공간 - 이
                                // 커널은 안 씀, 리눅스 호환을 위해
                                // 자리만 유지(이 영역에 실제 부트코드를
                                // 쓰지 않아도 포맷 자체는 유효).
    uint32_t version;          // 2 (swap-space 포맷 내부 버전 필드 -
                                // 매직 문자열 "SWAPSPACE2"의 "2"와는
                                // 별개 값이니 혼동 주의, 구현 시 실제
                                // 리눅스가 쓰는 값으로 재확인).
    uint32_t lastPage;         // 마지막 사용 가능 페이지 번호(1-based,
                                // 유효 슬롯은 1..lastPage - 슬롯 0은
                                // 헤더 자신이라 데이터로 안 씀).
    uint32_t nrBadPages;       // badPages[]의 실제 원소 수.
    uint8_t  uuid[16];
    uint8_t  volumeName[16];
    uint32_t padding[117];     // 정확한 길이는 구현 시 재확인(위 경고).
    uint32_t badPages[1];      // nrBadPages개, 가변 길이로 이어짐.
};
// 페이지 끝(오프셋 4096-10)에 10바이트 매직 - 별도 필드가 아니라
// 페이지의 마지막 10바이트 위치 자체가 매직 자리(실제 리눅스 구현도
// union으로 같은 페이지를 두 가지 시선으로 겹쳐 봄).
constexpr size_t kSwapMagicOffset = 4096 - 10;
constexpr char kSwapMagic[10] = {'S','W','A','P','S','P','A','C','E','2'};
```

### 3.2 슬롯 = 페이지 번호, 온디스크 할당 비트맵 없음

**Linux swap 포맷은 디스크에 free/used 비트맵을 두지 않는다** - 어느
슬롯이 쓰이고 있는지는 순수하게 런타임(메모리) 상태다(`swapon` 시
`1..lastPage` 전부를 free로 초기화하고, `badPages[]`에 나열된 페이지만
영구히 할당 불가로 표시). 이 원칙을 그대로 따른다.

- 슬롯 번호 = 페이지 번호(1..lastPage), 슬롯 0은 헤더 자신이라 데이터
  슬롯으로 절대 배정되지 않는다.
- 슬롯 i(1 ≤ i ≤ lastPage)의 바이트 오프셋은 `i * 4096`.
- `mount()` 시 `badPages[]`를 읽어 그 페이지 번호들을 영구 `false`
  (할당 불가)로 표시한 **런타임 전용** 비트맵을 만든다 - 이 비트맵은
  디스크에 절대 쓰지 않는다(Linux와 동일 - "크래시 시 상태 유실
  감수"가 표준 자체에 이미 내장돼 있어, 원안보다 오히려 단순하다).

### 3.3 슬롯 수 상한

`lastPage`가 `uint32_t`라 최대 약 42억 페이지(4KiB 기준 약 16TiB)로
제한된다 - 이 커널의 실제 스왑 시나리오(QEMU 개발 환경, 기가바이트
단위)에는 넉넉하다. §5의 PTE 인코딩 쪽 슬롯 필드 폭은 이 상한과
무관하게 넓게(52비트) 잡아 둔다 - `lastPage`는 "이 스왑 영역 하나의
크기" 제약일 뿐 PTE 인코딩 능력을 좁힐 이유가 아니다.

### 3.4 `SwapfsBackend` 구현

`SP-2BCE5D60` §4가 이미 확정해 둔 인터페이스를 그대로 상속:

```cpp
// minicore/libs/libswapfs/swapfs.h
class SwapfsBackend : public SwapBackend {
public:
    bool mount(BlockDevice* device) override;
    bool writeSlot(SwapSlot slot, const void* page) override;
    bool readSlot(SwapSlot slot, void* page) override;
    bool allocateSlot(SwapSlot* out) override;
    void freeSlot(SwapSlot slot) override;

private:
    BlockDevice* device_ = nullptr;
    SwapHeaderInfo header_{};
    // 런타임 전용 사용 비트맵(§3.2) - lastPage비트, mount() 시
    // badPages[]만 세팅된 상태로 시작. 디스크에 절대 쓰지 않는다.
    uint8_t* usedBitmap_ = nullptr;
    uint64_t nextScanHint_ = 1;  // 슬롯 0(헤더)부터 스캔하지 않도록
                                  // 1부터 시작 - 순수 성능 힌트.
};
```

**`mount(BlockDevice* device)`**:
1. `device->readBlock(0, &header_, sizeof(header_))`로 페이지 0을
   읽는다.
2. 오프셋 `kSwapMagicOffset`의 10바이트가 `kSwapMagic`과 정확히
   일치하는지 확인 - 불일치 시 즉시 `false`(§5 판별 실패, 다음
   드라이버 시도 경로 - ext4/FAT32와 동일하게 실패를 에러가 아니라
   "이 포맷이 아님"으로 취급).
3. `header_.version != 2`면 `false`(v1 "SWAP-SPACE" 포맷은 32비트
   시절 유물이라 v1 범위 밖 - 필요해지면 별도 후속).
4. `usedBitmap_`을 `header_.lastPage`비트만큼 확보해 전부 free로
   초기화한 뒤, `badPages[0..nrBadPages)`에 나열된 각 페이지 번호를
   영구 사용 중(실질적으로 "영원히 할당 불가")으로 표시.
5. `true` 반환 - 스왑은 절대 읽기 전용으로 마운트되면 안 된다
   (`SP-2BCE5D60` §4 원문 - 인터페이스 자체에 read-only 플래그가
   없음, 이 결정은 그대로 유효).

**`allocateSlot(SwapSlot* out)` / `freeSlot(SwapSlot slot)`**:
`nextScanHint_`부터 `usedBitmap_`을 선형 스캔해 첫 free 비트(슬롯
1..lastPage 범위)를 찾아 세팅 - 스왑 공간 완전 고갈 시 `false`(이
실패를 호출부가 어떻게 처리할지는 `SP-6CEFBE9B` §7.3의 기존 "실측
후 조정" 대상과 같은 층위, 이 문서 범위 밖). `freeSlot`은 해당
비트를 0으로 - 이중 해제는 방어하지 않는다(PTE당 슬롯 소유권 1:1이
불변조건, §5).

**`readSlot`/`writeSlot`**: `device_->readBlock(slot, page, 4096)` /
`device_->writeBlock(slot, page, 4096)`으로 그대로 위임(슬롯 번호 =
페이지 번호이므로 이 이상의 변환이 없음).

### 3.5 (역사적 기록) 원안 - 자체 고안 슈퍼블록/디스크 상주 비트맵 (반려됨, QU-CE388254)

아래는 이 문서의 최초 제안이었다 - 설계자 답변으로 반려됐으나
"왜 안 되는지"를 남겨 두기 위해 원문을 보존한다: 매직 `"MCSWAP01"`
(8바이트 리터럴)로 자체 슈퍼블록을 정의하고, 슈퍼블록 뒤에 슬롯
사용/해제를 기록하는 **디스크 상주 비트맵**을 두는 구조였다 - 슬롯
0이 슈퍼블록, 그 뒤가 비트맵, 그 뒤가 데이터 영역. `SwapfsSuperblock`
구조체(magic/version/slotSizeBytes/slotCount/bitmapOffsetSlots/
bitmapSizeSlots/dataOffsetSlots 필드)와 비트맵을 `mount()` 시 통째로
메모리에 로드해 관리하고 `unmount()` 시 1회 flush하는 방식이었다 -
**리눅스 swap 포맷엔 애초에 이런 디스크 비트맵 개념 자체가 없다**는
것이 반려 이유(§3.2 참고 - 사용 여부는 순수 런타임 상태).

## 4. 스왑 PTE 인코딩 (신규 - 이 커널 자신의 설계, 외부 표준 없음)

x86_64 PTE는 `Present`(bit0)가 0이면 하드웨어가 나머지 63비트를
완전히 무시한다(Intel SDM Vol.3A §4.5, "Not-Present" 엔트리는 포맷이
소프트웨어 자유) - `paging.h`의 `PAGE_COW`(bit9)는 `Present=1`인
페이지에만 쓰이므로 이 인코딩과 절대 충돌하지 않는다(직접 코드
확인, `minicore/kernel/paging.h`). **이 절은 §3(외부 표준 준수
대상)과 달리 이 커널 내부의 PTE 표현 방식이라 새로 설계해야 하는
영역 그대로다** - 참고로 Linux도 정확히 같은 원리(Not-Present PTE의
소프트웨어 영역에 스왑 타입+오프셋을 인코딩)를 쓰지만, 그 정확한
비트 배치는 이 커널의 PTE 구조 자체가 다르므로 그대로 가져오지
않고 이 프로젝트의 기존 `PAGE_COW` 관례에 맞춰 독자적으로 정한다.

```cpp
// paging.h에 추가 제안
constexpr uint64_t PAGE_SWAP_MARKER = 1UL << 1;
// Present=0인 PTE에서만 의미를 가진다: 1이면 "스왑아웃된 페이지"
// (슬롯 번호가 인코딩돼 있음), 0이면 기존 그대로 "진짜 미매핑"
// (예: 아직 손대지 않은 anonymous VMA 영역, 요구 페이징 이전).
// bit1은 Present=1일 때 PAGE_WRITABLE이지만 Present=0에서는 하드웨어가
// 안 보므로 재사용에 아무 문제 없다.

constexpr uint64_t kSwapSlotShift = 12;
// 슬롯 번호는 비트 12~63(52비트) - §3.3 참고, header_.lastPage(32비트
// 상한)와 무관하게 넓게 잡아 둔다.

inline uint64_t kMakeSwapPte(SwapSlot slot) {
    return (slot << kSwapSlotShift) | PAGE_SWAP_MARKER;  // PAGE_PRESENT 없음(0)
}
inline SwapSlot kSwapSlotFromPte(uint64_t pte) {
    return pte >> kSwapSlotShift;  // 호출 전 PAGE_SWAP_MARKER 확인 필수
}
```

### 4.1 스왑아웃 경로 (기존 설계와의 접합점)

`SP-6CEFBE9B` §6.2/§7.2가 이미 확정한 순서(rmap 순회 → 각 PTE
present=0 전환 + TLB shootdown → `SwapBackend::writeSlot`)에 정확히
한 단계만 끼워 넣는다: present=0으로 바꾸는 그 순간, 단순히 0을 쓰는
대신 `allocateSlot()`으로 얻은 슬롯 번호를 `kMakeSwapPte(slot)`으로
인코딩해 쓴다 - 순서/호출 지점 자체는 바뀌지 않는다.

### 4.2 폴트-인 경로 (신규 - `Paging::handlePageFault()` 확장 지점)

1. `#PF` 핸들러가 `Present=0` 폴트를 받으면 해당 PTE를 읽는다.
2. `PAGE_SWAP_MARKER`가 꺼져 있으면 기존 그대로(진짜 미매핑 - 온디맨드
   매핑/COW 등 기존 경로, 이 문서가 건드리지 않음).
3. 켜져 있으면 `kSwapSlotFromPte(pte)`로 슬롯 번호를 복원하고,
   `QU-0C4D25EF`가 이미 확정한 흐름 그대로 `Process::FaultInfo`에
   이 정보를 채워 `Process`를 Blocked로 전환한 뒤, `AsyncTask`로
   `SwapfsBackend::readSlot(slot, scratchPage)`를 제출한다.
4. 완료 콜백에서: 새 `PageFrame` 확보 → 읽어온 내용 복사 → PTE를
   `PAGE_PRESENT | PAGE_WRITABLE | ...`(원래 권한 그대로)로 정상화 →
   **`freeSlot(slot)`로 그 슬롯 반납**(스왑인은 항상 슬롯을 비운다) →
   Process Blocked 해제.

### 4.3 이 문서가 확정하지 않는 것

- 새 `PageFrame` 확보 실패 시 정책 - `SP-6CEFBE9B` §7.2의 기존
  "미루는 것" 목록과 같은 층위, 구현 세션이 계측 후 정한다.
- `readSlot` 실패(디스크 I/O 에러) 시 정책 - `PN-71E50394`(Signal
  전달 인프라)의 "치명적 폴트는 Signal로 처리" 원칙 재사용 가능성이
  높으나 이 문서 범위 밖.

## 5. 다른 설계와의 관계

- `SP-2BCE5D60` §4 — 이 문서가 구현하는 `SwapBackend` 인터페이스의
  출처.
- `SP-6CEFBE9B` §6/§7 — rmap 무효화, swap LRU, `writeSlot` 호출
  지점(스왑아웃), 회수 순서 - 이 문서는 그 순서의 마지막 한 단계
  (PTE 인코딩)만 채운다.
- `PN-4859FDE9` — 회수 스캔 정책 - 이 문서와 독립적으로 이미 완결.
- `Process::FaultInfo`/`QU-0C4D25EF`(`SP-68182FBD`) — 폴트 처리가
  swapfs를 소비하는 지점.
- `RM-7C249618` — 라이브러리 목록, 이 문서 승인 후 `libswapfs` 행
  갱신 필요.
- `minicore/kernel/paging.h` — `PAGE_COW`(bit9)와의 비충돌을 이미
  코드로 확인.

## 6. 범위 밖 - `libext4`/`libvfat`

이 문서는 `libswapfs`만 다룬다. **설계자 답변(QU-CE388254)이 이
둘도 "설계해야 한다"고 명시했으므로**, `libext4`(ext4 온디스크
포맷)/`libvfat`(Microsoft FAT32/16 스펙)도 각각 외부 표준을 그대로
옮기는 설계 문서가 별도로 필요하다 - 이 문서가 그 설계를 대신하지
않는다(범위가 크고 이 문서와 독립적으로 진행 가능). `PN-22784AD4`/
`PN-F32F55A8`로 이미 계획만 등록돼 있고(둘 다 "설계 미착수" 상태),
실제 설계 작성은 별도 세션/후속 작업으로 남긴다.
