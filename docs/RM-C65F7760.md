# Minicore VFS 구조

VFS 경로가 구현될 때마다 이 문서에 기록한다(설계자 지시, 2026-09-14
- CLAUDE.md 규칙에도 명시). SP-8B6B8D25 §4(파일 시스템 구조)/§4-A
(VFS 루트 소유권)가 정한 큰 그림 안에서, **실제로 코드로 구현된
경로만** 여기 적는다 - 설계 문서의 계획 트리 전체가 아니라 "지금 진짜
동작하는 것"의 현황판이다.

## 구현된 경로

| 경로 | 구현 위치 | 설명 | 상태 |
|---|---|---|---|
| `/sys/live/named/<name>` | `minicore/kernel/named_object.h/.cpp` + `minicore/kernel/livefs.h/.cpp`(`LiveFs::open`) | 이름 있는 IPC 오브젝트(메시징 채널 등) 네임스페이스(SP-1FBC0EEB) - 실제 파일 테이블은 커널 내부(`NamedObjectTable`, PL-C8648D4D 완료). **[구현 완료, 2026-09-16, commit 436f68e]** `/sys/live` 전체에 마운트된 `livefs`(`KernelFsDriver` 구현, SP-7CC5693A §2.4, PN-71C2B857)가 `named/` 접두사를 보면 `NamedObjectTable::resolve()`에 그대로 위임 | 구현 완료(스토리지 + livefs 라우팅 둘 다) - `read()`는 아직 미정의(아래 참고) |
| `/sys/live/initrd.cpio` | `minicore/kernel/livefs.h/.cpp`(`LiveFs::captureCpioArchive`/`open`/`read`) | CPIO initrd 이미지 전체를 **하나의 불투명한 파일**로 노출(내부 엔트리를 디렉터리 트리로 풀어 보여주지 않음) - `kmain.cpp`의 `kLogBootInfo`가 `PageFrameAllocator::init()`보다 먼저 원본 바이트 전체를 커널 BSS 전용 버퍼로 보존해 둔다(`gInitImageBuffer`류와 같은 이유, QU-A7D8E49B) | **[구현 완료, 2026-09-16, commit 436f68e]** open/read(offset 슬라이스+EOF) 전부 동작, 4개 QEMU 시나리오로 실측 검증 |
| `/sys/live/kernel/<devmgr\|fs\|net\|tty>` | `minicore/kernel/livefs.h/.cpp`(`KernelReservedTable`, `LiveFs::open`) | "커널 ↔ 커널 서비스 통신 채널"(SP-00CA7175 §2 Tier A/Tier B) 예약 지점 - 부팅 시 `KernelReservedTable::reserveForKernelService()`가 4자리를 선점하고, `LiveFs::open("kernel/<name>")`이 매번 호출자의 `ProcessRole == KernelService`이고 스폰 이름(`Process::spawnName`, 이번에 신설)이 정확히 일치하는지 검사한 뒤에만 핸들을 내준다 | **[구현 완료, 2026-09-16, commit 436f68e]** 코드는 존재하나, 실제 인증 성공/거부 분기는 아직 실측 검증되지 않았다(존재하지 않는 이름에 대한 NotFound만 확인) - `static_cast<UserThread*>(Scheduler::currentTask())`(Syscall::submit/wait과 동일한 기존 관례)가 실제로 안전하려면 진짜 UserThread 컨텍스트가 필요한데, 아직 이 경로를 실제로 호출하는 유저랜드 코드가 없다(SP-2AAD7C8D §9 Open syscall 착수 이후 실측 예정) |

| `/sys/live/proc/self/status` | `minicore/kernel/procfs.h/.cpp`(`ProcFs::open/read/stat`) + `minicore/kernel/livefs.cpp`(`LiveFs::onExec`가 `proc/` 접두사를 이 헬퍼로 위임) | 호출자 자기 자신의 상태(Pid/ParentPid/Role/Zombie/ThreadState) 텍스트 뷰(SP-5D965B74) - 임의/자식 pid 열람은 `QU-764C5624`(pid→Process* 안전 조회 수단 없음) 답변 이후로 미룸 | **[구현 완료, 2026-09-17, commit 7e37406]** open/read/stat 전부 동작, `AsyncTask::submit`+`AsyncTaskWaitGroup`로 실측 검증(§9 Open/Read syscall 자체는 여전히 미착수라 named/kernel/initrd.cpio와 같은 처지) |

| `/sys/etc`, `/sys/bin`, `/sys/mnt`, `/sys/tmp` | `minicore/fs/main.cpp`(신규, PN-452FF696 항목3) | `fs` 서비스(SP-8B6B8D25 §4-A - "VFS 루트는 커널이 소유, 마운트 지점 실질 처리는 fs")가 부팅 즉시 이름 없는 Channel 하나를 열고 이 네 경로를 전부 그 Channel로 `Mount` syscall 등록 - `MountTable::mount()`(§2.1) 라우팅 테이블에는 정확히 올라가지만, 그 뒤에 실제 파일시스템 드라이버는 아직 없다(`libext4`/`libswapfs`/`libvfat` 전부 미구현) - `fs`의 accept 루프도 연결을 받으면 바로 닫기만 한다(§9 Open/Read 프로토콜 미확정) | **[라우팅만 구현 완료, 2026-09-17, commit 437a2a6]** `Mount` 4회 전부 성공(error=None) 실측 확인(GRUB SMP4 + fs 단독 initrd 4회 반복, TEMP breadcrumb) - 실제 파일 열기/읽기는 여전히 불가능(§9 미착수, 아래 "표준 파일 API" 절과 동일한 처지) |

## 아직 구현 안 된 경로 (SP-8B6B8D25 §4 설계상의 나머지)

`/boot`, `/sys/dev`, `/apps`, `/run`, `/usr/{사용자명}/*`,
`/home/{사용자명}` - `/sys/dev`는 devmgr 담당(fs 범위 밖), `/boot`는
UEFI 경로 전용(PN-7FBF255A 미착수라 skip), `/usr/{사용자명}/*`는
사용자 계정 모델 자체가 아직 없어 skip(PN-452FF696 항목3이 정직하게
기록해 둔 스코프 결정) - `/apps`/`/run`/`/home`은 SP-8B6B8D25 §4의
트리 문서상 존재하나 명시적으로 "일반 FS 마운트 지점"으로 태그되지
않아(오버레이/별칭 개념에 가까움) 별도 설계 확정이 필요할 수 있다.
전부 필요해지는 시점에 하나씩 이 문서에 추가한다.

**표준 파일 API 자체가 아직 없음(SP-2AAD7C8D §9, 미착수)**: 위 표의
세 경로 모두 `LiveFs`/`MountTable` 코드 레벨로는 동작하지만, 이걸
실제로 호출하는 `Open`/`Read`/... syscall(§9.3)과 `Process`의 파일
디스크립터 테이블(§9.2)이 아직 없다 - 지금은 커널 내부 C++ 코드가
직접 `LiveFs::open()`/`read()`를 호출하는 것만 가능하고, 유저 프로세스가
`open("/sys/live/...")`를 호출할 방법 자체가 없다. §9 착수 시 `MountTable::
resolve()`가 낸 `MountKind::KernelDriver`를 보고 그 자리에서
`KernelFsDriver::open/read`를 동기 대행 호출하는 분기를 그 syscall
구현에 반영해야 한다(SP-2AAD7C8D §9.1이 이미 명시한 공백).

## 기록 규칙

- VFS 경로 하나가 실제 코드로 동작하기 시작하면(진짜 마운트 지점이든,
  `/sys/live/named/`처럼 그 전 단계의 임시 내부 구현이든) 이 문서의
  "구현된 경로" 표에 행을 추가한다.
- "상태" 칸에 "진짜 VFS/`fs` 서비스를 통한 구현"인지 "그 전 단계의
  임시 내부 구현"인지를 명시한다(`/sys/live/named/` 선례처럼).
