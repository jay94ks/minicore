# VFS StatArgs에 파일 타입 필드가 없음 - 소켓 특수 파일 지원을 위한 확장 방식 결정 요청

## 배경

`SP-231493CB`(소켓 계층 설계) §4-2에 설계자 Opinion으로 "실제
파일시스템 경로(`/sys/etc/foo.sock`류)에 소켓을 바인드하는 것도
범위에 포함해"가 지시됐다. 이를 구현하려면 그 경로에 "일반 파일이
아니라 소켓을 가리키는 특수 파일"(POSIX `S_IFSOCK`)이라는 사실을
VFS가 표현할 방법이 필요하다.

## 실측 확인 (코드로 직접 확인 완료)

`minicore/kernel/vfs_syscall.h`의 `StatArgs`(Stat syscall의 출력
구조체)를 확인한 결과:

```cpp
struct StatArgs {
    const char* path = nullptr;
    uint32_t pathLen = 0;
    uint64_t size = 0;
    bool isDirectory = false;   // 파일 종류를 나타내는 유일한 필드
    ChannelError error = ChannelError::None;
};
```

**파일 종류를 나타내는 필드가 `isDirectory`(bool) 하나뿐이다** -
일반화된 파일 타입 열거형(디렉터리/일반 파일/소켓/심볼릭 링크/
디바이스 특수 파일 등을 구분하는 `enum class FileType`류)이 이
프로젝트에 전혀 없다(`FileType`/`FileKind`/`DirEntryType`/`S_IFSOCK`
전부 grep 결과 0건). 즉 소켓 특수 파일 지원은 이 소켓 계층 설계
문서 하나로 끝나는 작업이 아니라, **VFS의 기본 파일 분류 체계
자체를 확장하는 더 큰 변경**이다 - 이 확장은 `KernelFsDriver`
인터페이스를 구현하는 모든 드라이버(livefs/procfs/resourcegroupfs/
ext4/FAT32/FAT16/exFAT/NTFS)에 영향을 준다.

## 결정이 필요한 것

1. **`isDirectory: bool`을 그대로 두고 `isSocket: bool`(또는
   `isSpecialFile`류) 하나만 나란히 추가할지**, 아니면 **`isDirectory`
   까지 포함해 일반화된 `enum class FileType { Regular, Directory,
   Socket, ... }` 하나로 통합할지.** 전자는 최소 변경(각 드라이버가
   그 필드만 false로 두면 기존 동작 무변경), 후자는 향후 심볼릭
   링크/디바이스 파일 등이 추가될 때 매번 새 bool을 또 추가하는
   패턴을 막지만 지금 당장은 모든 드라이버의 Stat 핸들러를 함께
   고쳐야 하는 더 큰 변경이다.
2. **소켓 특수 파일을 실제로 어느 드라이버가 "저장"하는가** - 소켓
   자체는 커널 메모리 안의 `UnixSocket` 구조체이지 디스크에 쓰는
   대상이 아니다. `/sys/etc/foo.sock`처럼 실제 디스크 기반
   파일시스템(ext4 등) 위의 경로에 바인드한다면, 그 드라이버는
   "이 inode는 소켓이다"라는 사실만 기록하고(ext4의 경우 실제로
   ext4도 `S_IFSOCK` inode 모드 비트를 지원함 - 온디스크 포맷
   자체는 문제 없음) 실제 소켓 상태(`UnixSocket`)는 여전히 커널
   메모리에 별도로 관리해야 한다 - 이 "온디스크 참조 + 메모리
   상태" 분리 설계를 이 DC가 확정할지, 착수 세션이 순수 구현
   세부로 정할지도 함께 판단이 필요하다.
3. **긴급도** - `SP-231493CB` 자체(named object 이름 바인드 - 슬래시
   없는 단순 이름)는 이 결정과 무관하게 착수 가능하다(§4-2 항목1).
   실제 VFS 경로 바인드(§4-2 항목2)만 이 결정을 기다린다 - 소켓
   계층 전체를 이 DC 때문에 블로킹할 필요는 없다.

## 후보 답변(설계자 판단용, 이 문서가 임의로 확정하지 않음)

- (A) `isSocket: bool` 추가 - 최소 변경, 빠른 착수 가능.
- (B) `enum class FileType` 전면 통합 - 더 일관된 장기 설계, 모든
  드라이버 동시 수정 필요.
- (C) 실제 VFS 경로 바인드 자체를 이번엔 named object 방식으로만
  구현하고(§4-2 항목1), VFS 파일 타입 확장은 별도 후속 계획으로
  분리(이 결정 자체를 지금 안 내리고 미룸).
