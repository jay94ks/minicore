# 컴파일러 진짜 thread_local 도입 (FS_BASE 스왑 + .tdata/.tbss) — 설계 제안

설계자 지시(2026-09-16, 메시지): "컴파일러의 진짜 thread_local(FS_BASE
스왑 + .tdata/.tbss)도 도입 계획을 작성해줘." SP-0666DB3C §11.1/
§11.4-1이 "진짜 컴파일러 thread_local"을 범위 밖에 두며 예고했던
바로 그 후속이다.

**[확정, 2026-09-16, QU-ECF3F878 답변 반영]** §9의 세 확인 사항
전부 답변받아 아래 본문을 최종 설계로 갱신했다 - **유저랜드도 v1
범위에 포함**하고, 기존 `ThreadLocal<T>`는 폐기하지 않되 **같은
메커니즘 위에 통합**한다.

## 1. 현재 상태 (실측, 2026-09-16)

- **`ThreadLocal<T>`(SP-0666DB3C §11, `minicore/kernel/tls.h/.cpp`,
  구현 완료 PN-E5860CCA)** - "부팅 시 슬롯을 한 번 발급받아 `get()`/
  `set()`으로 접근"하는 명시적(explicit) TLS. `Task::tlsSlots[16]`
  포인터 배열 기반 - 컴파일러의 `thread_local` 키워드는 전혀 관여하지
  않는다.
- **링커 스크립트(`minicore/arch/x86_64/linker.ld`) 실측 확인** -
  `.tdata`/`.tbss` 출력 섹션이 전혀 없다.
- **`gdt.cpp` 실측 확인** - FS 세그먼트나 `wrmsr(MSR_FS_BASE)` 설정
  코드가 전혀 없다. **다만 GS는 이미 정확히 이 문제(진입/이탈 시점
  스크래치 전환)를 겪어 본 선례가 있다** - `syscall_fastpath.cpp`/
  `syscall_entry.S`의 `swapgs` 패턴: `KERNEL_GS_BASE` MSR에 코어 전용
  `SyscallPerCpuScratch` 구조체를 등록해 두고, SYSCALL 진입 시
  `swapgs`로 유저 GS_BASE와 맞바꿔 커널 스크래치를 얻은 뒤 SYSRET
  전에 다시 `swapgs`로 되돌린다. **FS_BASE 스왑도 정확히 같은
  "진입 시 저장하고 커널 값으로, 이탈 시 유저 값으로 복원"** 구조가
  필요하다 - 다만 `swapgs` 같은 전용 명령이 FS에는 없어(x86_64는
  GS만 하드웨어 스왑 지원) `rdmsr`/`wrmsr(MSR_FS_BASE)`로 직접
  구현해야 한다.
- **프로세스 모델(SP-68182FBD) - "프로세스당 스레드 하나"(v1)** -
  `Process::mainThread` 하나뿐이라 지금 눈에 보이는 UserThread는
  항상 하나지만, **[정정, 2026-09-16, 설계자 지시]** 이 사실을
  근거로 "TLS 인스턴스도 하나면 충분"하다고 가정하지 않는다 - 아래
  §5.2부터 TLS 인스턴스 생성은 처음부터 **UserThread 단위**로
  설계한다(프로세스 단위가 아님). "지금 스레드가 하나뿐"인 건 이
  설계가 기댈 전제가 아니라 그저 현재 관측되는 결과일 뿐이다.

## 2. 목표 / 비목표

**목표**
1. 커널 코드가 `ThreadLocal<T>::get()/set()`을 매번 호출하는 대신
   컴파일러 `thread_local` 키워드를 직접 쓸 수 있게 한다(커널
   자신의 C++ 코드, kernel::Task 단위).
2. **[확장, QU-ECF3F878 답변]** 유저랜드 프로세스도 v1에 포함한다 -
   ELF `PT_TLS` 세그먼트를 파싱해 그 프로세스의 `UserThread`가 실제
   `thread_local`(유저 바이너리 자신이 컴파일한)을 쓸 수 있게 한다.
   **[정정, 2026-09-16, 설계자 지시 - "프로세스당 스레드 하나라
   인스턴스도 하나면 된다"는 가정 금지]** TLS 인스턴스 생성/해제는
   처음부터 **UserThread 생성/소멸에 정확히 1:1로 결부**시켜
   설계한다(§5.2) - "지금은 프로세스당 스레드가 하나"라는 현재
   상태에 기대 인스턴스 개수를 프로세스 단위로 가정하지 않는다.
   멀티스레딩 syscall(PN-543C0CE9류)이 나중에 생겨도 이 인스턴스
   생성 루틴은 코드 변경 없이 그대로 매 스레드 생성마다 재사용된다.
3. 링커가 실제로 `.tdata`/`.tbss`를 받는 출력 섹션 + 템플릿 경계
   심볼을 만들도록 `linker.ld` 갱신(커널 자신의 바이너리 기준 -
   유저 바이너리는 자신의 링커 스크립트/툴체인이 별도로 이미
   `.tdata`/`.tbss`를 만들어 낸다, ELF 표준이므로 이 프로젝트가
   손댈 필요 없음).
4. 각 커널 Task와 각 유저 프로세스가 자신만의 TLS 블록을 갖고,
   커널 쪽은 기존 CR3/RSP0/FPU 3개 디스패치 훅(SP-83A07867 §3.2)과
   같은 지점에서, 유저 쪽은 커널↔유저 전환 지점(§6)에서 자동으로
   FS_BASE가 교체된다.
5. 부팅 극초반에도 안전하게 동작.
6. **[확정, QU-ECF3F878 답변 - "교체보다는 통합"]** 기존
   `ThreadLocal<T>`(§11)를 폐기하거나 실제 `thread_local`로 단순
   교체하지 않는다 - **같은 하부 메커니즘(Task별 TLS 블록)을
   공유하도록 재구성**한다(§4.3).
7. C++ 예외 없이, freestanding 환경에서 동작.

**비목표(v1 범위 밖)**
- `AsyncTask` 단위 thread_local - 이미 별도 슬롯 메커니즘
  (`AsyncLocal<T>`, SP-0666DB3C §15)이 다루고 있고, `AsyncTask`는
  OS 스레드 개념이 아니다.
- 유저랜드 **멀티스레딩 syscall 자체**(pthread류 `CreateThread`) -
  그 syscall이 실제로 새 `UserThread`를 만드는 절차 자체는
  PN-543C0CE9류 별도 설계 범위다. 다만 **[정정, 2026-09-16] "TLS
  인스턴스를 만드는 절차"(§5.2)는 이 문서가 지금 확정한다** - 그
  syscall이 실제로 생기면 "새 UserThread 만들기"의 표준 부속
  절차로 §5.2의 인스턴스 생성 루틴을 그대로 호출하기만 하면 된다
  (추가 설계 불필요, 순수 재사용).
- FSGSBASE CPU 기능을 이용한 `wrfsbase` 최적화(확정, wrmsr로 시작).

## 3. x86_64 TLS ABI 개요

System V x86_64 ABI "Variant II" - FS_BASE(MSR `0xC0000100`)가
TCB(Thread Control Block)를 가리키고, `thread_local` 접근은
`mov %fs:-0x8, %rax`류로 컴파일된다. 커널/유저 각각 별도의 정적
바이너리(동적 링킹 없음)이므로 양쪽 다 가장 단순한 **Local Exec**
모델로 충분하다(`__tls_get_addr` 등 동적 TLS 디스크립터 불필요).

## 4. 커널 자신의 thread_local

### 4.1 TCB 레이아웃과 초기화

- **최소 TCB**: `struct Tcb { Tcb* self; };` (ABI 관례상 `%fs:0` 자기
  참조).
- `Task::init()` 시점에 Slab(SP-D7013B26)에서 "TCB + tdata/tbss
  크기"만큼 블록을 할당 - `.tdata` 템플릿(§4.2의 경계 심볼)을 복사,
  `.tbss`는 0으로 초기화, `Tcb::self` = 블록 시작 주소.
- **`Task`에 신규 필드 `uint64_t kernelFsBase`** 추가(task.h, §11.2의
  `tlsSlots`와 나란히 - 아래 §4.3에서 `tlsSlots` 자체도 이 메커니즘
  안으로 흡수된다).

### 4.2 링커 스크립트 변경 (`linker.ld`, 스케치)

```
.tdata ALIGN(16) : AT(ADDR(.tdata) - KERNEL_VMA) {
    kTlsTemplateStart = .;
    *(.tdata .tdata.*)
    kTlsTemplateTdataEnd = .;
} :kdata
.tbss ALIGN(16) (NOLOAD) : AT(ADDR(.tbss) - KERNEL_VMA) {
    *(.tbss .tbss.*)
    kTlsTemplateEnd = .;
} :kdata
```

### 4.3 `ThreadLocal<T>`와의 통합 (§11, [확정] "교체보다 통합")

기존 `Task::tlsSlots[kMaxTlsSlots]`(평범한 구조체 필드, 코어/Task
전환 시 자동으로 "같이" 따라오는 이유는 그냥 `Task` 자신의 필드라서
였다)를 **커널 쪽 `.tbss`에 실제 `thread_local` 배열로 재정의**한다:

```cpp
// tls.cpp (기존 Task::tlsSlots 필드를 대체)
thread_local void* gTlsSlots[kMaxTlsSlots] = {};
```

`ThreadLocal<T>::get()/set()`(공개 API, 기존 호출부 전부 무수정)은
이제 `Scheduler::currentTask()->tlsSlots[_slot]` 대신 `gTlsSlots[_slot]`
를 읽고 쓰도록 내부 구현만 바뀐다 - **API 시그니처는 완전히 동일하게
유지**(기존 소비자 전부 무수정, RM-23F4B687 §4 "검증된 코드는 순수
리팩터링 목적만으로 건드리지 않는다" 준수). 결과적으로:

- `Task` 구조체에서 `tlsSlots[16]` 필드 자체는 제거되고, 대신
  `kernelFsBase`(§4.1) 하나만 남는다 - 슬롯 배열은 이제 각 Task의
  TLS 블록(`.tbss` 인스턴스) 안에 산다.
- **왜 "호환"되는가**: `thread_local`로 선언한 어떤 변수든(이
  `gTlsSlots`든, 새 소비자가 직접 선언하는 변수든) 전부 같은 하나의
  TLS 블록/같은 FS_BASE 교체 메커니즘을 공유한다 - `ThreadLocal<T>`
  경유든 직접 `thread_local` 키워드든 "어느 Task의 것인가"를 결정하는
  기준(FS_BASE)이 정확히 하나로 통일된다(이전처럼 `Task::tlsSlots`
  필드와 미래의 `thread_local` 변수가 서로 다른 두 메커니즘으로
  따로 관리되는 상황을 피한다).

### 4.4 컨텍스트 전환 배선 (커널 Task 간)

기존 CR3/RSP0/FPU 3개 디스패치 훅(`kSyncCr3`/`kSyncRsp0ForDispatch`/
`kSyncFpu`, SP-83A07867 §3.2)과 정확히 같은 세 지점(`runLoop()`의
첫 진입, `onTick()`의 Task-to-Task 직접 전환, `yieldCurrent()`/
`parkCurrent()`의 재개 지점)에 `kSyncFsBase(next)`를 추가한다 -
`wrmsr(MSR_IA32_FS_BASE, next->kernelFsBase)`. 순수하게 `next` 소유
데이터만 참조하므로 코어 이관(SP-9525C4C0/SP-ECC59BAE)과도 자동
호환.

## 5. 유저랜드 프로세스의 thread_local

### 5.1 ELF `PT_TLS` 파싱

`elf::Image` 파서(현재 위치 미상 - 구현 착수 시 실제 파일 확인)가
프로그램 헤더에서 `PT_TLS` 세그먼트를 찾아 `p_vaddr`(원본 `.tdata`
위치)/`p_filesz`(`.tdata` 크기)/`p_memsz`(`.tdata`+`.tbss` 전체
크기)/`p_align`을 읽는다 - `PT_TLS`가 없는 바이너리(`thread_local`을
안 쓰는 프로그램)는 이 절차 전체를 건너뛴다(기존 `init` 등은 영향
없음).

### 5.2 "프로세스의 TLS 템플릿" vs "스레드의 TLS 인스턴스" 분리

- **템플릿**(`Process`에 저장) - `PT_TLS`가 가리키는 원본 `.tdata`
  이미지(그 프로세스의 유저 주소공간 안, ELF가 이미 로드해 둔 바로
  그 위치)와 총 크기(`p_memsz`)만 기억한다.
- **인스턴스**(`UserThread`에 저장) - **[정정, 2026-09-16, 설계자
  지시]** 프로세스 단위가 아니라 **`UserThread`가 새로 만들어질
  때마다** 그 프로세스의 템플릿(§5.2 위 항목)에서 하나씩 복사해
  만든다(유저 힙 또는 유저 스택 근처 - 배치는 구현 시점 확정) -
  "프로세스당 인스턴스 하나"를 전제로 하지 않는다. v1의 유일한
  UserThread 생성 경로가 `Process::execImage()`의 `mainThread`
  하나뿐이라 **지금 실제로 관측되는 인스턴스 수가 하나일 뿐**,
  생성 루틴 자체는 "이 UserThread 하나를 위한 인스턴스 하나"라는
  일반 규칙으로 설계한다 - 나중에 멀티스레딩 syscall이 새
  `UserThread`를 몇 개를 만들든 정확히 그만큼의 인스턴스가 같은
  루틴 재사용만으로 자연히 생긴다(코드 변경 불필요, §2 참고).
  스레드가 종료되면(그 `UserThread`가 소멸/Zombie 처리될 때) 그
  인스턴스도 함께 해제한다 - 인스턴스 수명은 UserThread 수명과
  1:1이지 Process 수명과 무관하다.
- `UserThread`에 신규 필드 `uint64_t userFsBase` 추가(§4.1의
  `kernelFsBase`와 나란히, `Task`가 아니라 `UserThread`에만 - 커널
  전용 Task는 유저 TLS가 없으므로).

### 5.3 커널↔유저 전환 지점의 FS_BASE 스왑 (신규 훅 - §4.4의 3곳과는 다른 지점)

§4.4의 3개 훅은 "Task 간" 전환(둘 다 커널 컨텍스트)만 다룬다 - 유저
FS_BASE는 **같은 UserThread 안에서 ring3↔ring0을 오갈 때**(Task
전환이 아니라 권한 레벨 전환) 별도로 스왑해야 한다. 이미 이 프로젝트
에 똑같은 모양의 문제(GS_BASE)가 있고 그 해법(`swapgs` 패턴,
`syscall_fastpath.cpp`)이 확립돼 있다 - FS_BASE도 같은 지점에서
같은 타이밍으로 스왑한다:

1. **SYSCALL 진입**(`kSyscallEntry`, `syscall_entry.S`) - `swapgs`
   직후, `rdmsr(FS_BASE)`로 지금 값(유저 값)을 그 UserThread의
   `userFsBase`에 저장하고, `wrmsr(FS_BASE, kernelFsBase)`로 전환.
2. **SYSRET 직전** - `wrmsr(FS_BASE, userFsBase)`로 유저 값 복원.
3. **`kEnterRing3`(process.cpp)** - 이 Task의 **첫** ring3 진입
   지점이므로, IRETQ 프레임 구성 전에 `userFsBase`(§5.2에서 이미
   설정된 초기값)로 `wrmsr` 한 번.
4. **인터럽트/예외가 ring3 실행 중에 발생하는 경우**(IDT 게이트,
   idt.cpp의 공통 ISR 스텁) - SYSCALL과 마찬가지로 진입 시 저장/
   전환, 반환(IRETQ) 전 복원이 필요하다. **정확한 배선 지점(공통
   스텁 매크로가 CPL을 이미 구분하는지 등)은 구현 착수 시
   `idt.cpp`를 직접 읽고 확정**(이 문서가 결정하지 않음 - 구현
   세부).

## 6. 부팅 극초반 - "커널 자신의" 초기 FS_BASE

`kmain()`/`kApMain()` 실행 중(아직 어떤 Task도 없는 idle 컨텍스트)
에도 커널 코드가 `thread_local`을 건드리면 폴트가 난다 - GDT/IDT
준비 직후, 다른 어떤 서브시스템보다도 먼저 코어별 "부팅 전용 TCB"
(정적 예약 공간, 힙 없이도 동작)로 FS_BASE를 먼저 설정해 둔다.
이후 실제 Task가 생기면 그 Task 전용 TCB로 자연스럽게 교체된다.

## 7. 확정된 사항 요약 (QU-ECF3F878 답변)
