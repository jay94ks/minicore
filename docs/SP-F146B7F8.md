# Minicore Thread-Local/Per-CPU 변수 인프라(TLS/PerCpu) — 설계 제안

**[분리, 2026-09-17]** `SP-0666DB3C`(커널 동기화 프리미티브 Mutex/
Semaphore 및 Signal 전달)의 §11(Thread Local Variable)/§12(Per-CPU
Variable)을 별도 문서로 독립시켰다 - 이 둘은 원래 Mutex/Semaphore/
Signal 전달(동기화·IPC)과 주제 자체가 다르다(스레드/코어별 저장
공간 프리미티브 - 동기화 프리미티브가 사용하는 기반 중 하나일 뿐,
동기화 자체가 아니다). 애초에 `SP-0666DB3C`에 실린 이유도 "설계자가
그 문서를 검토하던 중 이 요구를 추가로 지시"했기 때문이지 주제가
같아서가 아니었다 - 다른 다수의 문서(`SP-B1E258D8`의 RCU
`PerCpu<AtomicU64>`, 스케줄러 코어별 배열, Slab 코어별 매거진 등)가
동기화와 무관하게 이 프리미티브를 참조하는 것만 봐도 독립된 인프라
축임을 알 수 있다. 아래 내용은 `SP-0666DB3C` §11/§12의 문구를 그대로
옮긴 것이며(설계/구현 내용 변경 없음), 절 번호만 이 문서 기준으로
다시 매겼다(§11→§1, §12→§2).

**둘 다 이미 구현 완료**(`PN-E5860CCA`, 2026-09-15) - `minicore/kernel/
tls.h`/`minicore/kernel/percpu.h`, QEMU 실측 검증까지 끝났다.

**[주의, 문서 관리]** 이 분리 이전에 작성된 다른 문서/계획 중 일부가
여전히 "SP-0666DB3C §11" 또는 "SP-0666DB3C §12"를 가리키고 있을 수
있다 - 발견하는 대로 이 문서를 가리키도록 정정한다(진행 중, 루프
틱에서 점진적 스윕 - CLAUDE.md 규칙 4/11 취지와 동일하게 발견 즉시
처리, 일괄 전수조사는 하지 않는다).

## 1. Thread Local Variable (설계자 지시, 2026-09-14) — **[구현 완료, PN-E5860CCA, 2026-09-15]**

**[갱신, 2026-09-15] 이 §1 전체(아래 §1.2의 `TlsRegistry`/`ThreadLocal<T>`
포함)는 더 이상 설계 제안이 아니다 - `minicore/kernel/tls.h`로 실제
구현·QEMU 실측 검증까지 완료됐다(계획 PN-E5860CCA, 2026-09-15T04:25).
아래 §1.2의 코드 블록은 실제 구현과 100% 일치함을 소스 대조로 확인
했다(git_read로 `tls.h` 직접 확인, 2026-09-15).

### 1.1 배경 - 왜 진짜 컴파일러 `thread_local`이 아니라 명시적 슬롯인가

유저랜드 C++의 `thread_local`/`__thread`는 컴파일러가 자동으로 FS
세그먼트 상대 주소로 코드를 생성하고, 링커가 `.tdata`/`.tbss`
섹션과 초기화 이미지를 구성하며, 컨텍스트 전환 시 `FS_BASE` MSR을
스레드마다 교체해야 동작한다 - 이 프로젝트는 이 셋 중 어느 것도
아직 갖추지 않았다(컨텍스트 전환은 `kContextSwitch`가 범용 레지스터
+ RFLAGS만 저장/복원, PL-2D3184BC). 지금 이 전체 인프라를 새로
구축하는 것은 이번 요청의 범위를 크게 넘는다 - 대신 이 프로젝트가
이미 반복 채택한 패턴(`SyscallEndpointId`/`AsyncTaskSubjectCode` -
"부팅 시 슬롯/코드를 한 번 발급받아 재사용", RM-48E1E610/
SP-F682B889 §3.1)을 그대로 재사용하는 **명시적(explicit) TLS**를
v1으로 제안한다 - `thread_local` 키워드는 지원하지 않고, `get()`/
`set()` 호출로 흉내낸다.

### 1.2 설계 - 슬롯 배열 + 타입 안전 뷰

```cpp
// minicore/kernel, 가칭 tls.h
using TlsSlotIndex = uint32_t;
constexpr uint32_t kMaxTlsSlots = 16;  // 실측 후 조정(RM-23F4B687 §4 원칙)

// 기능별로 부팅/초기화 시 한 번만 슬롯을 발급받는다 - 요청마다
// 등록/해제하지 않는다(AsyncCallbackRegistry, SP-F682B889 §3.1과
// 동일한 관례).
class TlsRegistry {
public:
    static TlsSlotIndex allocateSlot();
};

// onExec/코루틴 본문이나 syscall 처리 코드가 쓰는 타입 안전 뷰 -
// 실제 T 인스턴스의 생성/해제는 그 슬롯을 발급받은 서브시스템
// 책임이다(AsyncTaskHandler의 args와 동일 원칙, SP-F682B889 §3.1) -
// 이 클래스 자신은 슬롯 접근만 제공한다.
template <typename T>
class ThreadLocal {
public:
    explicit ThreadLocal(TlsSlotIndex slot) : _slot(slot) {}

    T* get() const {
        return static_cast<T*>(Scheduler::currentTask()->tlsSlots[_slot]);
    }
    void set(T* value) {
        Scheduler::currentTask()->tlsSlots[_slot] = value;
    }

private:
    TlsSlotIndex _slot;
};
```

`Task`(minicore/kernel/task.h)에 필드 추가 제안:

```cpp
// Task 구조체에 추가 - Task가 이미 커널 Task/UserThread 공통
// 베이스이므로(RM-32D06563 §2, SP-04EE2A18) 여기 두면 양쪽 다 커버.
void* tlsSlots[kMaxTlsSlots] = { nullptr, /* ... */ };
```

### 1.3 `AsyncTask`는 이 설계 대상이 아니다

`AsyncTask`(SP-F682B889 §3.2)는 `Task`를 상속하지 않는 별개
구조체다(리액터 위에서 도는 경량 실행 단위) - 이 §1의 TLS는
`Task`/`UserThread`(완전한 스케줄링 단위)에만 적용된다. `AsyncTask`
자체에 유사한 슬롯이 필요해지면(예: 하나의 `AsyncTask` 실행 동안만
유효한 임시 상태) 별도로 검토한다(§1.4-3) - 지금은 필요 소비자가
없다.

### 1.4 아직 열려 있는 하위 과제

1. **진짜 하드웨어 TLS 필요 여부**: 유저랜드 libc류를 이식해 실제
   `thread_local` 키워드 지원이 필요해지면(`FS_BASE` 스왑 +
   `.tdata`/`.tbss`) 별도 SP로 설계해야 한다 - 지금은 소비자가 없어
   범위 밖.
2. **`kMaxTlsSlots` 크기**: 16은 임의값 - 실제 소비자가 늘어나며
   실측 조정(RM-23F4B687 §4 원칙).
3. **[해결됨, 2026-09-15, SP-0666DB3C §15(AsyncLocal<T>)로 대체]**
   ~~`AsyncTask` 자체의 TLS 필요성~~ - §1.3이 예고했던 바로 그 필요가
   실제로 생겼다(`ReentrantAsyncMutex`의 소유자 추적, `SP-0666DB3C`
   §16) - `SP-0666DB3C` §15(`AsyncLocal<T>`, `AsyncTask::
   localSlots[64]`)로 구체화·설계자 확정 완료(그 설계는 동기화
   프리미티브(`ReentrantAsyncMutex`)와 결합돼 있어 원 문서에 남겨
   뒀다 - 이 문서로 옮기지 않음). 더 이상 이 문서의 미결 사항이
   아니다.

## 2. Per-CPU Variable (설계자 지시, 2026-09-14) — **[구현 완료, PN-E5860CCA, 2026-09-15]**

**[갱신, 2026-09-15]** 이 §2 전체(§2.2의 `PerCpu<T>` 포함)도 §1과
같은 계획(PN-E5860CCA)으로 함께 구현 완료됐다 - `minicore/kernel/
percpu.h`(문서가 제안한 `minicore/libs/libkenv` 대신 `minicore/kernel`
로 배치 - `get()`이 `Scheduler::currentCoreIndex()`를 호출해 kernel::
의존이 생기므로 libkenv 레이어링 규칙상 불가피한 조정, PN-E5860CCA
참고). `SP-0666DB3C` §15(`TaskLocal<T>`)가 별칭으로 삼는 `PerCpu<T>`가
바로 이미 구현된 이 클래스다 - 그 절은 새 프리미티브를 만드는 게
아니라 기존 구현 위에 의미론적 이름만 얹는 것이었다.

### 2.1 배경 - 이미 반복되고 있는 패턴의 공식화

스케줄러(PL-2D3184BC, minicore/kernel/scheduler.cpp)는 이미 "코어
개수만큼의 배열 + `Scheduler::currentCoreIndex()`로 인덱싱"하는
패턴을 여러 번 손으로 반복 구현했다 - `gCurrentTask[coreIndex]`,
`gPreemptDisableCount[coreIndex]`, `gCleanupQueues[coreIndex]`,
`gImmediateQueues`/`gRtQueues`/`gNormalQueues[coreIndex]`,
`gIdleSavedRsp[coreIndex]`(전부 `kMaxCores = kAcpiMaxCpus` 크기).
Slab 할당자(SP-D7013B26)의 코어별 매거진도 같은 성격이다. 이 §2는
이 반복 패턴을 재사용 가능한 프리미티브로 공식화한다.

### 2.2 설계 - `PerCpu<T>`

```cpp
// minicore/libs/libkenv, 가칭 percpu.h
template <typename T>
class PerCpu {
public:
    // 이 코어(호출 시점의 Scheduler::currentCoreIndex())의 값에
    // 대한 참조.
    T& get() { return _values[Scheduler::currentCoreIndex()]; }

    // 다른 코어의 값을 들여다봐야 할 때(예: 로드밸런싱 판단,
    // 진단/디버깅) 쓴다 - 동시성 보호는 T 자신의 책임이다(PerCpu는
    // 배열 인덱싱만 제공, 락을 걸어주지 않는다).
    T& forCore(uint32_t coreIndex) { return _values[coreIndex]; }

private:
    T _values[kMaxCores];  // scheduler.h의 kMaxCores(=kAcpiMaxCpus) 재사용
};
```

기존 스케줄러의 손으로 짠 배열들(`gCurrentTask` 등)은 이미 동작
검증된 코드이므로 **이 설계 때문에 지금 당장 재작성하지 않는다** -
순수 리팩터링 목적만으로 검증된 코드를 건드리지 않는다는 일반
원칙(변경 최소화)에 따라, 새로 만드는 서브시스템(동기화 프리미티브
내부 상태 등 코어별로 나눠야 할 것이 생기면, TLS 슬롯 레지스트리
등)부터 `PerCpu<T>`를 쓰기 시작하고, 스케줄러 쪽은 그 파일을 어차피
다른 이유로 손댈 자연스러운 기회에 정리한다.

### 2.3 성능 - `currentCoreIndex()`의 비용

`Scheduler::currentCoreIndex()`(scheduler.cpp)는 `Lapic::id()`를
읽은 뒤 `Acpi::cpuApicId(i)`와 순서대로 비교하는 **O(코어 수) 선형
스캔**이다 - 코어 수가 적을 땐(수십 개 미만) 무시할 만하지만,
`PerCpu<T>::get()`이 핫 패스(예: 매 `AsyncMutex::lock()` 시도, 매
Slab 할당)에서 반복 호출되면 누적 비용이 실측으로 문제가 될 수
있다.

### 2.4 아직 열려 있는 하위 과제

1. **[구체화, 2026-09-15, 해소됨] 코어 인덱스 캐싱**: `Scheduler::
   currentCoreIndex()`가 선형 스캔이던 문제 - **채택: `IA32_TSC_AUX`
   경로**(`rdtscp`, `GS_BASE` 방식 대신 - syscall 고속 경로가 이미
   `KERNEL_GS_BASE`를 다른 용도로 쓰고 있어 충돌 방지 + `rdtscp`는
   메모리 접근 없는 순수 명령어). **[해소, 2026-09-16, commit
   3c57c5d]** 구현 완료, SMP4 정확성 QEMU 실측 확인. 부팅/컨텍스트
   스위칭 시간 변화 정량 측정은 `QA-08F8C96F`로 분리 추적(별도 QA
   문서).
2. **기존 전역 배열의 `PerCpu<T>` 교체 여부**: §2.2 참고 - 후속
   리팩터링 기회로 남김, 지금 일괄 변경하지 않는다.
3. **§1 Thread Local Variable과의 관계**: `PerCpu<T>`는 "이 코어"
   기준(한 코어가 여러 Task를 번갈아 실행), `ThreadLocal<T>`(§1)는
   "이 Task" 기준 - 축이 다르다는 것을 이름 규칙으로 구분해 뒀다
   (혼용 방지).

## 3. 관련 문서

- `SP-0666DB3C` - 이 문서가 분리돼 나온 원 문서(Mutex/Semaphore/
  Signal 전달 - 동기화 프리미티브). §15(`AsyncLocal<T>`)/§16
  (`ReentrantMutex`/`ReentrantAsyncMutex`)이 이 문서의 `PerCpu<T>`
  위에 얹히지만, 그 설계 자체는 동기화 프리미티브와 결합돼 있어
  원 문서에 남아 있다.
- `PL-2D3184BC`(스케줄러) - §2.1이 공식화한 반복 패턴의 원 소비자.
- `SP-D7013B26`(Slab 할당자) - 코어별 매거진, 같은 패턴의 또 다른
  소비자.
- `SP-B1E258D8`(RCU) - `PerCpu<AtomicU64>`로 grace-period 추적,
  동기화와 무관한 소비 사례.
- `QA-08F8C96F` - §2.4-1의 rdtscp 전환 성능 실측 QA.
- `PN-E5860CCA` - 이 문서 §1/§2 구현 계획(완료).
