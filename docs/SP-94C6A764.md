## 0. 배경

`PN-81223433`(백로그, "실사용처 없어 보류")이 추적하던 열린 질문을
설계자 지시(백로그 전체 대상 설계안 작성)로 앞당겨 설계한다.

`SP-8D206F11`(CPU 캐시 관리 정책) §2.3이 `kMapPageWithCacheType`을
도입하면서 설계자 opinion으로 남긴 문제: 같은 물리 페이지를 서로
다른 `CacheType`(WriteBack/WriteThrough/Uncached/WriteCombining -
PAT 인덱스 0/1/3/4)으로 **동시에** 매핑하는 것은 x86_64에서 사실상
미정의 동작이다(Intel SDM Vol.3A §11.5.2.1 - PAT aliasing, 최악의
경우 캐시 라인 내용 불일치나 머신체크까지 이어질 수 있다고 경고).
이 일관성을 추적하는 자리로 `SP-6CEFBE9B`(PageFrame 구조체) §3이
`PageFrame::lastCacheType`(1B)/`cacheTypeAssigned`(1B) 필드를
이미 예약해 뒀지만, 실제 검사/충돌 시 정책은 "실사용처가 생기기
전까지 임의로 정하지 않는다"(CLAUDE.md 규칙4)로 보류돼 있었다.

**현재 코드 상태(`minicore/kernel/page_frame_allocator.h:68-69`)**:
두 필드 다 "아직 미배선"(주석 그대로) - 값은 항상 0이고 아무도
읽거나 쓰지 않는다.

## 1. 핵심 통찰 — "동시에 활성 매핑이 여럿"일 때만 진짜 위험

이 위험은 "그 물리 페이지가 과거에 다른 타입으로 매핑됐던 적이
있다"가 아니라, **지금 이 순간 서로 다른 타입의 매핑이 동시에
살아 있다**는 것이다. 매핑을 완전히 해제한 뒤(그 물리 페이지를
가리키는 활성 PTE가 0개가 된 뒤) 다른 타입으로 다시 매핑하는 것은
안전하다 - CPU 캐시 라인 관점에서 항상 하나의 타입만 유효하기
때문이다.

`PageFrame`에는 이미 이 판단에 필요한 필드가 있다 - `mapCount`
(§6, "실제 PTE가 가리키는 횟수", 마찬가지로 아직 미배선). 이 SP는
`mapCount`의 전면 배선(§6 전체 범위)까지는 하지 않고, **이 목적에
필요한 최소 증감만** `kMapPageWithCacheType`/그 해제 경로에 한해
앞당겨 배선할 것을 제안한다(RM-23F4B687 §4 - 필요한 만큼만).

## 2. 확정할 설계

### 2.1 검사 시점 - `kMapPageWithCacheType()` 안

```
if (frame->mapCount == 0) {
    // 활성 매핑이 없던 프레임 - 새 타입으로 자유롭게 갱신
    frame->lastCacheType = static_cast<uint8_t>(cacheType);
    frame->cacheTypeAssigned = 1;
} else if (frame->cacheTypeAssigned &&
           frame->lastCacheType != static_cast<uint8_t>(cacheType)) {
    // 활성 매핑이 있는데 타입이 다름 - 진짜 충돌
    return VfsError::CacheTypeConflict;  // 또는 대응하는 errno_t 값
}
// mapCount>0 이고 타입이 같으면 그냥 통과(같은 타입으로 추가 매핑)
frame->mapCount++;
```

해제 경로(`kUnmapPage` 또는 대응 함수)는 `mapCount--`만 하고,
`mapCount`가 0이 되면 `cacheTypeAssigned = 0`으로 리셋한다 - 다음
매핑이 자유롭게 새 타입을 고를 수 있게.

### 2.2 충돌 시 반응 - 에러 반환(권장)

검토한 네 후보:

| 후보 | 내용 | 평가 |
|---|---|---|
| (a) 에러 반환 | 새 `errno_t` 값 추가, 매핑 실패로 처리 | **권장** - 이 프로젝트의 예외 없는 명시적 에러코드 철학(RM-23F4B687)과 가장 일치, 호출부가 반드시 처리(무시하면 컴파일 경고 없이 조용히 넘어갈 수 있는 값이 아니라 매핑 자체가 실패하므로) |
| (b) assert/panic | 조기 발견에 유리 | 커널 전체를 세운다 - 드라이버 버그 하나가 시스템 전체를 내려야 할 만큼 이 위험이 항상 치명적인지 불확실(실측된 실제 사고가 아직 없음), 과함 |
| (c) 기존 타입 유지(요청 무시) | 호출자가 원한 타입을 조용히 못 받음 | 최악 - 실패를 알리지 않아 디버깅이 가장 어려운 종류의 버그를 만듦, 채택 안 함 |
| (d) 안전한 공통 타입(UC)으로 강제 통일 | 항상 성공, 성능만 희생 | 호출자가 명시적으로 WC를 요청했는데 조용히 UC로 강등되면 "이 API가 무엇을 보장하는지"가 모호해짐, 채택 안 함 |

(a)를 권장한다 - 새 에러 값은 `RM-48E1E610`류 전역 번호표 등록
대상이 아니다(syscall 에러코드가 아니라 이 함수 자신의 반환값).

### 2.3 디버그 편의 - 위반 시 1회 로그

에러를 반환하는 것과 별개로, `kernel::Logger::warn()`으로 물리
주소/기존 타입/요청 타입/호출자 정보를 한 줄 남긴다(assert 없이도
조기에 원인을 알아볼 수 있게) - `PAGE_RECLAIM_INPROGRESS` 등 이미
비슷한 급의 진단 로그 관례를 따른다.

## 3. 이 설계가 다루지 않는 것 (명시적 비목표)

- **MMIO/DMA 매핑 간 충돌**: `PN-81223433`이 이미 확인했듯 물리적으로
  별개 영역이라 이 문제 자체가 성립하지 않는다 - 이 SP의 대상은
  "정말 같은 물리 프레임을 서로 다른 목적으로 동시에 매핑"하는
  경우뿐이다(예: 프레임버퍼를 WC로 매핑한 채, 같은 프레임을 커널
  내부 디버깅 목적으로 잠깐 WB로도 매핑하려는 시나리오).
- **`mapCount`의 나머지 용도**(COW, rmap 삽입/제거 트리거) - 이는
  `SP-6CEFBE9B` §6 전체 배선의 몫으로 그대로 남긴다. 이 SP는 그
  필드의 존재와 "0으로 떨어지면 매핑이 전부 사라졌다"는 의미만
  최소로 빌려 쓴다.
