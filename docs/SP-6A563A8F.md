## 배경

설계자 opinion(2026-09-18, `SP-245D130B` 대상): "CPU 쿼터 카운터 설계안
별도 문서로 작성해줘." - `SP-245D130B` §3(CPU 컨트롤러, v1 "쿼터
스로틀")을 독립 문서로 분리한다. `SP-B26CDBDD`(CPU 가중치/vruntime,
approved+구현 완료 `PN-158B6B2F`)가 §0/§6이 지적한 공백을 별도 문서로
분리했던 것과 정확히 같은 패턴이다 - 그 문서가 Task 단위 CPU
*우선순위*(상대 가중치)를 다뤘다면, 이 문서는 ResourceGroup 단위 CPU
*제한*(쿼터 스로틀)을 다룬다. 두 문서는 같은 스케줄러 재스케줄
결정 지점(`Scheduler::onTick()`)을 공유하지만 서로 다른 축이라
대체 관계가 아니라 병존한다(`SP-245D130B` §9-5 해소 기록 참고).

`SP-245D130B` §1이 이미 스케치해 둔 `ResourceGroupCpuControl` 구조체와
"쿼터 초과 시 pickNext()가 건너뛴다"는 한 줄짜리 정책을, 이 문서가
실제 구현 가능한 수준(자료구조/스로틀 알고리즘/계층 강제 검증/syscall)
으로 구체화한다.

## 1. 범위 - 이 문서가 다루는 것과 다루지 않는 것

- **다룸**: 그룹 단위 CPU 쿼터(주기당 최대 실행 시간) 강제 - Linux
  cgroup v2의 `cpu.max` 상당. 계층적 강제(자식 합이 부모를 넘지 못함,
  `QU-3356AD2B` §9-3 확정).
- **다루지 않음**: Task 단위 상대 가중치/vruntime(`SP-B26CDBDD` 소유),
  메모리/IO 제한(`SP-245D130B` §6/§7), freeze(`SP-245D130B` §4).
- **전제**: `ResourceGroup`/`Process::group`/`gRootResourceGroup`
  (`PN-4190BBD3` 항목1/2, 완료) + `Task::vruntime`/`OrderedList`
  기반 `gNormalQueues`(`SP-B26CDBDD`/`PN-158B6B2F`, 완료) + 그룹
  CPU 계정 카운터 증가 배선(`SP-B26CDBDD` §5, 완료 - 아래 §2 참고).

## 2. 자료구조 (SP-245D130B §1 그대로, 변경 없음)

```cpp
// resource_group.h (이미 존재, PN-4190BBD3 항목1)
struct ResourceGroupCpuControl {
    uint32_t periodTicks = 0;        // 0 = 무제한(기본값)
    uint32_t quotaTicks = 0;
    uint32_t usedTicksInPeriod = 0;  // SP-B26CDBDD §5가 이미 증가시킴
    uint64_t periodStartTick = 0;    // Timer::tickCount() 기준
};
```

**이미 살아있는 부분(`PN-158B6B2F` 완료)**: `Scheduler::onTick()`의
재스케줄 결정 지점(§3.2, `SP-B26CDBDD`)에서 매 틱 `usedTicksInPeriod`가
이미 증가하고 있다 - 이 문서는 그 카운터를 "읽어서 무엇을 할지"만
새로 설계한다. 카운터 자체를 다시 만들 필요 없음.

## 3. 주기 롤오버 - `kCheckAndResetCpuPeriod()`

```cpp
// resource_group.cpp (신규 함수)
// SP-245D130B §4의 kCheckAndMarkFrozen()과 동일한 명명 관례 -
// "확인하고 필요하면 갱신"을 한 함수로 묶어 호출부가 매번 각자
// 롤오버 로직을 반복하지 않게 한다.
bool kCheckAndResetCpuPeriod(ResourceGroup* group) {
    if (group->cpu.periodTicks == 0) {
        return false;  // 무제한 그룹 - 스로틀 대상 아님
    }
    const uint64_t now = Timer::tickCount();
    if (now - group->cpu.periodStartTick >= group->cpu.periodTicks) {
        group->cpu.periodStartTick = now;
        group->cpu.usedTicksInPeriod = 0;
    }
    return group->cpu.usedTicksInPeriod >= group->cpu.quotaTicks;
    // true = 이번 주기 쿼터 소진(스로틀 중), false = 아직 여유 있음
}
```

이 함수는 **두 곳에서 호출**된다 - §4(pickNext 스로틀 체크)와
`SP-B26CDBDD` §3.2의 기존 카운터 증가 지점(그 지점도 주기가 롤오버됐는지
먼저 확인해야 `usedTicksInPeriod`가 무한정 누적되지 않는다) - 후자는
이 문서 승인 후 `SP-B26CDBDD` 구현부에 이 함수 호출을 끼워 넣는 작은
후속 수정이 필요하다(아래 §7 착수 조건 참고).

## 4. 스로틀 메커니즘 - `pickNext()`의 Normal 큐 순회 변경

**SP-245D130B §3 작성 당시엔 `gNormalQueues`가 FIFO였지만, 그 사이
`SP-B26CDBDD`(vruntime)가 `OrderedList`로 교체했다** - "건너뛴다"는
한 줄짜리 정책을 그 새 자료구조 위에서 구체화해야 한다. `OrderedList`는
`popMin()`(최솟값 제거)만 제공하고 "일부만 보고 도로 넣기"를 자연스럽게
지원하지 않으므로, 스로틀된 후보를 임시로 옆에 모아 뒀다가 되돌려주는
방식을 쓴다:

```cpp
// scheduler.cpp, Scheduler::pickNext() 내부 - 기존
// "task = gNormalQueues[coreIndex].popMin();" 한 줄을 아래로 교체.
//
// 큐 앞쪽에 스로틀된 그룹 소속 Task가 여러 개 연달아 있을 수 있어
// (여러 그룹이 동시에 쿼터를 소진한 상황) 반복 확인이 필요하다 -
// 다만 실제로 몇 개나 스로틀돼 있을지는 "그 순간 쿼터 소진 상태인
// 그룹 수"로 제한되므로(그룹 수 자체가 적을 것으로 예상, RM-23F4B687
// §4 - 실측 후 문제되면 재검토) 무한 루프 위험은 없다(popMin()이
// 빈 큐에서 nullptr을 반환하면 while이 자연히 끝난다).
Task* task = nullptr;
{
    // 임시 보류 목록 - 이번 pickNext() 호출 안에서만 산다(스택,
    // 힙 할당 없음). kMaxHeldThrottledCandidates는 실측 후 조정
    // 가능한 상한(그룹 수 상한과 동일하게 시작 - 지금 유일한 그룹이
    // gRootResourceGroup 하나뿐이므로 v1 실측 부담 없음).
    Task* held[kMaxHeldThrottledCandidates];
    uint32_t heldCount = 0;
    while ((task = gNormalQueues[coreIndex].popMin()) != nullptr) {
        ResourceGroup* group = kResourceGroupOf(task);  // §6 헬퍼
        if (!group || !kCheckAndResetCpuPeriod(group)) {
            break;  // 그룹 없음(비정상, 방어적) 또는 스로틀 아님 - 이 Task를 뽑는다
        }
        if (heldCount < kMaxHeldThrottledCandidates) {
            held[heldCount++] = task;
        }
        // 보류 상한을 넘으면(비정상적으로 많은 그룹이 동시 스로틀) 그냥
        // 이 Task를 뽑아 스로틀을 어기는 대신, 상한 초과분은 held에서
        // 빠진 채로 재삽입되지 않고 그대로 큐에서 사라지는 버그가 될
        // 수 있으므로 - 상한 도달 시 남은 후보 탐색을 멈추고 nullptr로
        // 취급한다(스케줄 안 함, 다음 틱에 재시도). RM-23F4B687 §4 -
        // v1 상한은 넉넉히 잡아 실사용에서 닿지 않게 한다.
        if (heldCount == kMaxHeldThrottledCandidates) {
            task = nullptr;
            break;
        }
        task = nullptr;  // 계속 탐색
    }
    for (uint32_t i = 0; i < heldCount; ++i) {
        gNormalQueues[coreIndex].insert(held[i]);  // vruntime 그대로 - 다음 pickNext에서 다시 후보
    }
}
```

**대안(기각)**: `usedTicksInPeriod >= quotaTicks`인 그룹의 Task들을
Ready 큐에서 아예 빼서 별도 "스로틀 대기열"에 두고 주기 롤오버 시
한꺼번에 다시 큐에 넣는 방식도 검토했으나, 그러려면 주기 롤오버를
감지하는 별도 폴링(타이머 콜백 또는 매 틱 전수 검사)이 필요해 오히려
더 복잡하다 - 위 "매번 pickNext에서 확인" 방식이 새 상태/새 폴링
없이 기존 스케줄러 핫패스 패턴(§4 freeze/§3.5 debug pause와 동일하게
"필요한 순간에 확인"하는 lazy 방식)과 일치해 이쪽을 채택한다.

## 5. 계층적 쿼터 강제 (`QU-3356AD2B` §9-3 확정: "자식 합이 부모를 넘을 수 없다")

**적용 시점: 런타임 강제가 아니라 `ResourceGroupSetCpuQuota` 시점의
입력 검증**이다 - 매 틱마다 조상 체인을 따라 올라가며 검사하는 것은
스케줄러 핫패스에 O(트리 깊이) 비용을 추가하므로, 대신 "쿼터를 설정하는
순간"에만 한 번 검증해 핫패스를 건드리지 않는다(RM-23F4B687 §4).

```cpp
// resource_group.cpp - ResourceGroupSetCpuQuota 핸들러가 호출
// (§6 syscall 절 참고). 부모의 쿼터가 무제한(periodTicks==0)이면
// 자식들의 합도 무제한 - 검증 스킵.
bool kValidateChildQuotaAgainstParent(ResourceGroup* parent, ResourceGroup* changingChild,
                                       uint32_t newPeriodTicks, uint32_t newQuotaTicks) {
    if (!parent || parent->cpu.periodTicks == 0) {
        return true;  // 부모 무제한 - 항상 허용
    }
    // 쿼터를 "비율"(quota/period)로 정규화해 비교한다 - 자식마다 다른
    // periodTicks를 가질 수 있으므로 절대값(quotaTicks) 합산은 의미가
    // 없다(예: 부모가 1000틱마다 500틱이면 50%, 자식이 100틱마다
    // 60틱이어도 60%로 부모보다 큼 - 절대값만 보면 60<500이라 잘못
    // 통과시킨다). 고정소수점 스케일은 SP-B26CDBDD §2.1의
    // kVruntimeScale과 같은 이유로 정수 나눗셈 0-버림을 피한다.
    constexpr uint64_t kRatioScale = 1000000;  // ppm 단위
    auto ratioOf = [](uint32_t quota, uint32_t period) -> uint64_t {
        return period == 0 ? 0 : (static_cast<uint64_t>(quota) * kRatioScale) / period;
    };
    uint64_t siblingSumRatio = 0;
    for (auto& child : parent->children) {  // ChunkedList<SharedPtr<ResourceGroup>, 8>
        ResourceGroup* c = child.get();
        if (c == changingChild) {
            continue;  // 변경 대상 자신은 새 값으로 아래에서 따로 더함
        }
        siblingSumRatio += ratioOf(c->cpu.quotaTicks, c->cpu.periodTicks);
    }
    siblingSumRatio += ratioOf(newQuotaTicks, newPeriodTicks);
    const uint64_t parentRatio = ratioOf(parent->cpu.quotaTicks, parent->cpu.periodTicks);
    return siblingSumRatio <= parentRatio;
}
```

**[정정, 2026-09-18, 설계자 opinion]** 이 절 작성 시점엔 동적 그룹
생성이 범위 밖이라 `parent->children`이 항상 비어 있다고 적었으나,
아래 §5-A에서 동적 그룹 생성/삭제가 이번 증분에 포함되도록 정정됐다
- 이 검증 로직이 실제로 실행되는 시나리오가 생긴다.

## 5-A. 동적 그룹 생성/삭제 - `ResourceGroupCreate`/`ResourceGroupDestroy`

**[추가, 2026-09-18, 설계자 opinion("동적 그룹 생성도 착수해야해")]**
§8(원 §5 표기, 아래 번호 유지)이 v1 착수 조건이 아니라고 적었던
것을 정정한다 - 동적 그룹 생성/삭제도 이번 증분에 포함한다. §5의
계층적 쿼터 강제가 실제로 의미를 가지려면(자식이 실제로 존재해야
"자식 합"이 생김) 어차피 이 기능이 선행돼야 하므로, 뒤로 미루는
것보다 함께 진행하는 편이 일관적이다.

`SP-245D130B` §1의 `ResourceGroup` 클래스가 이미 `children`
(`ChunkedList<SharedPtr<ResourceGroup>, 8>`)/`parent`
(`WeakPtr<ResourceGroup>`) 필드를 갖고 있다 - `PN-4190BBD3` 항목1이
"동적 그룹 생성이 아직 없어 자리만 확보(항상 비어 있음)"로 남겨 둔
바로 그 자리다. 새 자료구조는 필요 없고, 아래 두 syscall 핸들러가
그 필드를 실제로 채운다.

```cpp
// resource_group.cpp
// ResourceGroupCreate(parentName: string, name: string) -> error
//   - SP-245D130B §8 표: "이름 지정해 생성, 부모 그룹 지정(생략 시
//     루트 자식)".
// 권한: ResourceGroupJoin과 동일한 모델(SP-245D130B §9-2 확정 -
// "호출자가 이미 그 그룹의 조상 체인 안에 있을 때만 허용") -
// 여기서는 "부모 그룹"의 조상 체인 안에 호출자가 있어야 그 아래
// 자식을 만들 수 있다(새 그룹을 만드는 것도 그 부모 그룹에 대한
// 쓰기 작업이라는 동일 원칙).
ChannelError kResourceGroupCreate(Process& caller, ResourceGroup& parent,
                                   const char* name, uint32_t nameLength) {
    if (!kCallerInAncestorChain(caller, parent)) {  // §9-2와 동일 판정 재사용
        return ChannelError::PermissionDenied;
    }
    for (auto& sibling : parent.children) {  // 이름 유일성 - 같은 부모 아래 중복 금지
        if (kNamesEqual(sibling->name, sibling->nameLength, name, nameLength)) {
            return ChannelError::AlreadyExists;
        }
    }
    SharedPtr<ResourceGroup> child = ResourceGroup::allocate();  // 기존 슬랩 할당+init 관례(§1)
    child->init();
    kCopyName(child->name, name, nameLength);
    child->parent = parent.weakFromThis();
    // CPU 컨트롤(§2)은 기본값 그대로 무제한(periodTicks=0) - 생성 시점에
    // 자동으로 쿼터가 걸리지 않는다(명시적으로 ResourceGroupSetCpuQuota를
    // 따로 호출해야 함, SP-245D130B §3/이 문서 §7과 동일한 "0=무제한
    // 기본값" 원칙).
    parent.children.pushBack(child);  // 부모가 진짜 소유자(SharedPtr)
    return ChannelError::None;
}

// ResourceGroupDestroy(name: string) -> error
//   - SP-245D130B §8 표: "자식/멤버가 없어야 성공(비어있음 강제 -
//     Linux cgroup과 동일)".
ChannelError kResourceGroupDestroy(Process& caller, ResourceGroup& target) {
    SharedPtr<ResourceGroup> parent = target.parent.lock();
    if (!parent) {
        return ChannelError::PermissionDenied;  // 루트 그룹은 삭제 불가
    }
    if (!kCallerInAncestorChain(caller, target)) {
        return ChannelError::PermissionDenied;
    }
    if (!target.children.empty() || !target.memberProcesses.empty()) {
        return ChannelError::NotEmpty;  // Linux cgroup과 동일한 "비어있음 강제"
    }
    parent->children.remove(target);  // SharedPtr 해제 - 자기 소멸
    return ChannelError::None;
}
```

**`kCallerInAncestorChain()`은 `SP-245D130B` §9-2/§3(ResourceGroupJoin
권한 확정)이 쓰는 것과 동일한 헬퍼를 재사용**한다 - 이 문서가 새로
정의하지 않는다(그 문서/이 문서 어느 쪽이 먼저 구현되든 함께 착수하는
단일 증분이므로, 실제 이름/시그니처는 착수 세션이 한 곳에만 정의하고
양쪽에서 재사용).

**이 절이 §5(계층적 쿼터 강제)에 주는 영향**: 동적 그룹 생성이 실제로
존재하게 되므로, §5의 `kValidateChildQuotaAgainstParent()`가 더 이상
"v1 첫 증분에서는 실제로 이 분기를 타는 시나리오가 없다"는 각주 없이
바로 실전에서 동작한다 - §9(검증 계획) 항목4를 "단위 테스트류"가
아니라 **실제 부모-자식 그룹 생성 후 왕복 검증**으로 격상한다.

## 6. `ResourceGroupOf(Task*)` 헬퍼

§4가 참조하는 `kResourceGroupOf(Task*)`는 아직 존재하지 않는 작은
헬퍼다(`SP-B26CDBDD` §5의 인라인 캐스팅 패턴을 재사용):

```cpp
// resource_group.h 또는 scheduler.cpp
ResourceGroup* kResourceGroupOf(Task* task) {
    if (!task->isUserLevel) {
        return nullptr;  // 커널 자체 Task는 그룹 소속 아님(SP-B26CDBDD §3.2와 동일 전제)
    }
    auto* thread = static_cast<UserThread*>(task);
    SharedPtr<Process> proc = thread->process.lock();
    return proc ? proc->group : nullptr;
}
```

## 7. Syscall - `ResourceGroupSetCpuQuota` (RM-48E1E610 번호 예약)

```
ResourceGroupSetCpuQuota(name: string, periodTicks: uint32, quotaTicks: uint32) -> error
// periodTicks==0이면 quotaTicks 무시하고 무제한으로 리셋.
// 권한: SP-245D130B §9-2 확정 그대로(호출자가 대상 그룹의 조상 체인
// 안에 있을 때만) - ResourceGroupJoin과 동일한 검증 함수 재사용.
// 검증: quotaTicks > periodTicks면 즉시 거부(주기보다 많은 실행
// 시간은 무의미). §5의 kValidateChildQuotaAgainstParent()도 통과해야
// 함 - 실패 시 InvalidArgument류로 거부, 그룹 상태는 변경 안 함.
```

`SP-E9B44929`(Group+Call 2단계 인코딩, approved)의 새 체계로 번호를
배정한다 - `ResourceGroupJoin`/`ResourceGroupCreate`/`Destroy`/
`Freeze`/`Thaw`와 같은 syscall 그룹에 속한다(`SP-245D130B` §8이
이미 예약해 둔 그룹, 착수 시 `RM-48E1E610`에 실제 번호 기록).

## 9. 검증 계획

1. 단일 그룹(루트)에 짧은 주기/작은 쿼터를 설정 - 쿼터 소진 후 그
   그룹 소속 Task가 다음 주기까지 `pickNext()`에서 제외되는지, 다른
   그룹(무제한) Task는 영향 없는지 확인.
2. 주기 롤오버 - `periodTicks` 경과 후 `usedTicksInPeriod`가 리셋되고
   다시 스케줄되는지 확인.
3. §4 "보류 목록" 로직 - 스로틀된 Task가 실제로 도로 큐에 삽입되는지
   (사라지지 않는지), vruntime이 보존되는지(재삽입 시 §2.3 굶주림
   방지 보정이 다시 적용되지 않아야 함 - 이미 큐에 있던 값 그대로
   되돌리는 것이지 "새로 큐에 들어가는" 경로가 아님, `SP-B26CDBDD`
   §2.3 조건과 구분 필요).
4. `kValidateChildQuotaAgainstParent()` - §5-A로 동적 그룹 생성이
   이번 증분에 포함되므로, 실제 부모/자식 그룹을 만들어 쿼터 합이
   부모를 넘는 시도가 거부되는지 왕복으로 검증(단위 테스트류가
   아니라 실제 syscall 왕복).
5. `ResourceGroupCreate`/`Destroy`(§5-A) - 이름 중복 생성 거부,
   비어있지 않은 그룹 삭제 거부(`NotEmpty`), 권한 없는 호출자의
   생성/삭제 거부, 삭제된 그룹의 자식 인덱스에서 실제로 제거되는지
   확인.
6. QEMU 4개 표준 시나리오 무회귀(스케줄러 핫패스 변경).
