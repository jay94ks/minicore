# timerfd/signalfd - epoll 호환 타이머/시그널 fd — 설계 제안

설계자 Opinion(`SP-6350DEBB` 대상, 2026-09-26): "signalfd/timerfd를
epoll이 감시하는 것 - 이 프로젝트에 아직 timerfd류 fd도 별도
설계안으로 작성해." - epoll류 설계(`SP-6350DEBB`)가 범위 밖으로
미루려 했던 항목을 분리된 문서로 실제 설계한다.

## 1. 실측 확인한 현재 상태

- **타이머**: `SP-F15B4A63`(지연 실행/타이머 인프라)가 콜백 기반
  타이머를 제공하나, **fd로 노출되지 않는다** - 만료를 알려면 콜백을
  등록해야 하고, epoll처럼 "fd가 준비됐다"로 관찰할 방법이 없다.
- **시그널**: `SP-0666DB3C` §4가 Signal 전달을 이미 설계·구현했다 -
  다만 이건 프로세스에 **비동기적으로 즉시 전달**되는 모델(POSIX
  시그널 핸들러 방식과 유사)이지, "펜딩 시그널을 fd로 읽어오는"
  `signalfd()` 방식이 아니다.
- **`epoll.h`의 fd 종류 분기**(`SP-6350DEBB` §4) - 이 문서가 정의할
  `Kind::Timerfd`/`Kind::Signalfd`를 그 분기에 추가할 자리가 이미
  마련돼 있다.

## 2. 핵심 모델 - 두 fd 종류를 fd 테이블에 새로 추가

```cpp
// minicore/kernel/timerfd.h (신규 파일 제안)
namespace kernel {

struct TimerfdState {
    uint64_t expirationCount = 0;   // 마지막 read() 이후 누적 만료 횟수
    bool periodic = false;
    uint64_t intervalTicks = 0;     // periodic이면 재무장 주기
    // 실제 타이머 콜백 핸들 - SP-F15B4A63의 기존 타이머 인프라 재사용,
    // 콜백이 만료마다 expirationCount++ (여러 번 놓쳐도 POSIX처럼
    // 누적 카운트로 흡수 - timerfd_settime 문서의 표준 동작).
};

}  // namespace kernel

// minicore/kernel/signalfd.h (신규 파일 제안)
namespace kernel {

struct SignalfdState {
    uint32_t watchedSignalMask = 0;   // 이 fd가 관심 있는 시그널 집합
    // 대상 프로세스에 그 시그널이 오면 SP-0666DB3C의 기존 즉시 전달
    // 경로 대신(또는 병행 - §4 참고) 이 fd의 펜딩 큐에 쌓인다.
};

}  // namespace kernel
```

- 둘 다 `Process::FileDescriptor`에 새 `Kind`(`Timerfd`/`Signalfd`)로
  통합된다(`SP-2AAD7C8D` §9.2, `SP-231493CB` §3이 소켓에 쓴 것과
  동일한 패턴 - "새 fd 종류를 기존 fd 테이블에 태그로 추가"라는 이미
  세 번째 반복되는 관례).

## 3. syscall API

새 그룹을 만들지 않고, 그룹6(Event, `SP-2602CAA6`/`SP-6350DEBB`)의
다음 미사용 call 번호(6)부터 이어 붙인다 - "무언가의 상태 변화를
fd로 노출한다"는 이 그룹의 취지와 정합적(RM-23F4B687 §4).

```
TimerfdCreate(periodic: bool) -> fd(int64_t)
TimerfdSetTime(fd, initialTicks: uint64_t, intervalTicks: uint64_t) -> error
SignalfdCreate(signalMask: uint32_t) -> fd(int64_t)
SignalfdSetMask(fd, signalMask: uint32_t) -> error
```

(`Read`는 새 syscall을 만들지 않는다 - 기존 그룹3 `Read`를 재사용,
POSIX `timerfd`/`signalfd`와 동일한 관례. `timerfd`는 8바이트
`expirationCount`를 읽고 0으로 리셋, `signalfd`는 대기 중인 시그널
정보 구조체를 읽는다 - 정확한 구조체 레이아웃은 착수 세션이 POSIX
`signalfd_siginfo` 대조 후 확정, 순수 구현 세부.)

## 4. `Read` 시맨틱 및 준비(ready) 판정 - `SP-6350DEBB` §4 확장

```cpp
bool kIsFdReadable(const FileDescriptor& fd) {
    switch (fd.kind) {
        // ...기존 분기(SP-6350DEBB §4)...
        case FileDescriptor::Kind::Timerfd:
            return static_cast<TimerfdState*>(fd.payload)->expirationCount > 0;
        case FileDescriptor::Kind::Signalfd:
            return static_cast<SignalfdState*>(fd.payload)->hasPending();
    }
}
```

- **`Read`(timerfd)**: `expirationCount`가 0이면 블로킹(v1은 항상
  블로킹 read - `O_NONBLOCK`류는 v1 범위 밖, `SP-231493CB` §7과
  같은 판단), 0보다 크면 그 값을 읽고 0으로 리셋. 만료 발생 시점에
  §1의 타이머 콜백이 `AsyncReactor::submitCompletion()`으로 대기
  중인 리더를 깨운다(기존 배관 재사용, 새 통지 경로 불필요).
- **`Read`(signalfd)**: **시그널 전달 모델과의 상호작용이 이 설계의
  핵심 결정 지점** - `SP-0666DB3C`의 기존 즉시 전달(시그널 핸들러
  방식)과 이 fd 기반 방식이 같은 시그널에 대해 동시에 활성화되면
  어느 쪽이 우선인지 확정해야 한다. **제안(POSIX 관례 그대로)**:
  `SignalfdSetMask`로 지정한 시그널 집합은 그 프로세스의 일반 시그널
  마스크에서도 **블록**돼야 한다(POSIX `sigprocmask`+`signalfd`
  표준 패턴) - 블록된 시그널은 즉시 전달 경로를 타지 않고 이 fd의
  펜딩 큐에만 쌓인다. **이 결정은 `SP-0666DB3C`의 기존 시그널 마스크
  개념(있다면)과의 정합성 확인이 필요** - 착수 전 그 문서에서
  "시그널 블로킹/마스킹" 지원 여부를 먼저 확인할 것(CLAUDE.md
  규칙4 - 확인 안 된 것을 확정으로 적지 않음, 이 문서는 제안만
  한다).

## 5. epoll 통합

`SP-6350DEBB` §4의 fd 종류별 판정 함수 목록에 위 §4의 두 함수를
추가하기만 하면 된다 - 새 통지 배관/새 EpollWatch 필드 불필요,
"완료 통지 지점에서 §4 재판정"(edge 트리거, `SP-6350DEBB` §2-B)
원칙도 그대로 적용된다(타이머 만료 콜백/시그널 도착 지점이 그
"완료 통지 지점"이 된다).

## 6. [갱신, 2026-09-26, 설계자 Opinion] 절대시각 타이머 + 실시간 시그널 - 둘 다 v1 범위로 편입

최초안은 이 두 항목을 범위 밖으로 뒀으나 설계자가 명시적으로
포함하라고 지시했다.

### 6-A. `TFD_TIMER_ABSTIME`(절대시각 타이머)

**[정정]** "벽시계 시각 개념이 얕다"는 최초 판단이 틀렸다 - 이
프로젝트엔 이미 `Rtc`(wall-clock 시각 소스, `RM-32D06563` §12,
`PN-83AE8AE9`)가 있다 - MC146818A CMOS RTC를 읽어 실제 연/월/일/
시/분/초를 얻는 경로가 이미 존재한다.

`TimerfdSetTime`에 절대시각 플래그를 추가한다:

```
TimerfdSetTime(fd, absolute: bool, targetOrIntervalTicks: uint64_t,
               intervalTicks: uint64_t) -> error
```

- `absolute=false`(기존 동작): `targetOrIntervalTicks`는 "지금부터
  몇 틱 후"(§3 원안 그대로).
- `absolute=true`: `targetOrIntervalTicks`는 `Rtc`가 반환하는 형식의
  절대 시각(유닉스 타임스탬프류 - 정확한 인코딩은 착수 세션이
  `Rtc`의 기존 반환 타입에 맞춰 확정, 순수 구현 세부)이다. 설정
  시점에 `Rtc::now()`로 현재 시각을 읽어 그 차이를 스케줄러 틱
  수로 환산(`Timer::tickCount()`가 이미 알려주는 초당 틱 수, 기존
  100Hz 관례 재사용)한 뒤, 이후로는 §3의 상대 틱 방식과 동일하게
  동작한다 - **`Rtc` 재조회 없이 한 번 환산한 틱 카운트로 계속
  간다**(POSIX `timerfd_settime(TFD_TIMER_ABSTIME)`가 시스템 시각이
  나중에 바뀌어도(NTP 조정 등) 이미 걸린 타이머 만료 시각 자체는
  재계산하지 않는 것과 동일한 단순화 - 이 프로젝트는 NTP/시각
  재조정 개념이 아직 없어 이 단순화가 실질적으로 항상 정확하다).

### 6-B. 실시간 시그널(POSIX RT signal, 큐잉 + 다중 인스턴스)

**[정정]** "Signal 번호표(`RM-B5764185`)가 0-31 범위만 다루므로
범위 밖"이라는 최초 판단이 틀렸다 - 설계자가 명시적으로 정정했다:
**"`Minicore Signal 번호표`의 목적은 반드시 존재해야 하는 고정
번호이지, 한계값이 아니다."** 즉 그 표는 POSIX 표준 신호(1-22, 31)가
반드시 그 번호로 존재해야 한다는 걸 보장하는 표일 뿐, 신호 번호
공간 전체의 상한이 아니다 - RT 신호는 그 표가 다루는 범위와 별개로
새 번호 구간을 추가로 예약하면 된다.

**번호 예약**(`RM-B5764185`에 실제로 반영 필요, CLAUDE.md 규칙13):
Linux 관례(`SIGRTMIN`..`SIGRTMAX`)를 따라 **32-63번을 `SIGRT0`..
`SIGRT31`로 예약**한다(32개, 이미 있는 23-30 "미사용" 구간은 그대로
POSIX 표준 번호용 여유로 남기고 건드리지 않음 - RT 신호는 그 표
바깥의 완전히 새 구간).

**큐잉/다중 인스턴스**(표준 신호와의 핵심 차이): 표준 신호는
`Process::pendingSignals`가 신호별로 "펜딩 여부" 비트 하나뿐이라
같은 신호가 여러 번 와도 한 번만 기록된다(`RM-B5764185`가 이미
문서화한 v1 동작). **RT 신호는 이 방식으로는 POSIX 계약을 못
지킨다** - RT 신호는 같은 번호가 여러 번 발생하면 그 횟수만큼
큐에 쌓여 순서대로 전달돼야 한다(+ 각 인스턴스마다 `sigqueue()`류
부가 데이터를 가질 수 있다). 이를 위해:

```cpp
struct RtSignalInstance {
    uint32_t signalNumber = 0;   // 32-63
    uint64_t userData = 0;       // sigqueue()류 부가 데이터(1워드로 축소, v1 단순화)
};
```

`SignalfdState`(§2)가 RT 신호 전용으로 `RtSignalInstance`의 FIFO
큐(고정 용량 - `SP-2602CAA6` §5의 pending 큐 관례, N=8과 같은 수준
재사용)를 별도로 갖는다 - 표준 신호(1-31)는 여전히 비트 방식,
RT 신호(32-63)만 이 큐 방식(**신호 번호로 두 체계를 분기** - 어느
경로를 탈지는 번호 하나로 정적으로 결정됨). `Read`(signalfd)가
표준 신호는 있으면 그대로, RT 신호는 이 큐에서 순서대로 하나씩
꺼내 반환한다. 큐가 가득 차면(POSIX는 이 경우 신호 전달 자체가
실패할 수 있다고 허용) 가장 오래된 것부터 버린다(`SP-2602CAA6`의
기존 pending 큐 정책과 동일 - 새 정책을 또 만들지 않음).

**시그널 발생원(Kill 등)이 RT 신호 번호+userData를 함께 실어
보내는 syscall 확장**도 필요하다 - `KillArgs`(기존, 그룹0)에
`userData: uint64_t` 필드를 추가하거나(표준 신호는 무시) 별도
`SigqueueArgs`류를 신설할지는 착수 세션이 `SP-0666DB3C`의 기존
`KillArgs` 시그니처를 먼저 확인해 정한다(순수 구현 세부).

## 7. 검증 계획(초안)

1. `TimerfdCreate`+`TimerfdSetTime`(1회성) - 지정 시간 후 `Read`가
   `expirationCount=1`을 반환하는지, 그 전에는 블로킹하는지.
2. 주기적 타이머 - 여러 번 만료를 놓친 뒤 `Read`하면 누적 카운트가
   정확한지(POSIX 표준 동작).
3. `SignalfdCreate`+시그널 발생 - `Read`가 올바른 시그널 정보를
   반환하는지, 같은 시그널이 일반 전달 경로로는 안 가는지(§4 마스킹
   확인).
4. epoll 통합 - `EpollCtl(Add, timerfd, Readable)` 후 만료 시
   `EpollWait`이 깨어나는지(레벨+edge 둘 다).
5. **[신규] 절대시각 타이머(§6-A)** - `Rtc::now()`로 현재 시각을
   읽고 그 몇 초 뒤로 `TimerfdSetTime(absolute=true, ...)` 설정 -
   그 시각에 정확히(±1틱) 만료하는지 확인.
6. **[신규] RT 신호 큐잉(§6-B)** - 같은 RT 신호 번호를 연속으로
   3회 발생시킨 뒤 `Read`(signalfd)를 3번 호출 - 3개 인스턴스가
   순서대로(FIFO) 각자의 `userData`와 함께 반환되는지 확인. 표준
   신호(비트 방식)와 달리 "여러 번 발생 = 한 번만 기록"이 되지
   않음을 대조 확인.
7. 표준 5시나리오 무회귀.
