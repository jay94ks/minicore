# 실행 계획: 멀티 프로세스 실행 기반 완성 (ring3 컨텍스트 오염 버그 해결 + 프로세스 생명주기)

## 배경 — 현재 상태 조사 요약

PN-16CA347D("유저랜드 준비, 첫 프로세스 기동") 마일스톤은 완료됐다 -
실제 `minicore/init`이 initrd(CPIO)에서 로드되어 ring3 진입까지
성공했다(커밋 cea71f0). 이어서 PN-AEA74E1B(TSS.RSP0을 코어당
UserThread 하나 전제에서 멀티 UserThread 일반화로 확장)도 완료됐다
(커밋 eb1fe57).

그런데 PN-AEA74E1B 검증 중 **PN-63BCFE45**(그 수정과는 별개인 새
버그)가 발견됐다 - 한 코어에 ring3 UserThread가 **3개 이상** 있으면
실행 컨텍스트가 오염된다(RIP가 절대 도달 불가능한 주소로 튐, CR2도
근거 없는 값). 원인 미상 - 재현 조건만 확인된 상태다.

이 버그가 남아 있는 한 이 프로젝트의 다음 큰 이정표들이 전부 실질적으로
막혀 있다고 봐야 한다:

- QA-26450C3E의 미체크 항목("인터럽트가 올바른 커널 서비스로 라우팅",
  "IPC가 의도한 커널 서비스로 전파") - PN-B3DD3D19가 이걸 다루는데,
  devmgr/fs 등 **여러 유저랜드 커널 서비스가 동시에** 떠 있어야
  검증 가능하다.
- review 상태로 대기 중인 하드웨어/파일시스템 설계 문서(PnP
  SP-9DD4F3EA, AHCI SP-C2670F69, USB SP-E35FD36C, DMA SP-39F18E30,
  VFS SP-7CC5693A) - 전부 실제 드라이버/서비스 프로세스가 실행되는
  환경을 전제로 한다.
- mmap 서브시스템(SP-2AAD7C8D)의 남은 부분(mmap syscall API, VMA
  연동)도 "프로세스가 실제로 여러 개 살아서 매핑을 주고받는" 시나리오
  없이는 검증이 어렵다.

여기에 더해, 프로세스 **종료** 처리 자체가 아직 없다(self-terminate
핸들러 미구현 - PN-71C3D483, onCancel 호출 경로 미연결 - PN-40E976F2,
둘 다 "실행 중이 아닌 Task를 정리하는 메커니즘 자체가 이 프로젝트에
없다"는 같은 근본 공백을 공유). 그리고 이번 조사에서 별도로,
`Process::execImage()`가 ring3 진입 파라미터를 전역 인스턴스 하나에
담아 두는 v1 한계가 실제 멀티프로세스에서 반드시 재현됨을 확인해
PN-D0ED9611로 새로 등록했다.

**이 문서의 목적**: 위 사실들을 종합해, "첫 프로세스 기동" 이후
"실제로 여러 프로세스가 안정적으로 동시 실행"되는 상태까지 가는
경로를 우선순위대로 정리한다.

## 실행 순서

### 1단계 — PN-63BCFE45 근본 원인 규명 및 수정 (최우선, 이후 전부의 선행 조건)

`minicore/kernel/kmain.cpp`에 이미 준비해 둔 임시 진단 코드
(`kRunOneThreadTest`/`kRunThreeThreadTest`, 커밋 전 제거 대상 - 로컬
미커밋 상태)로 이분 탐색을 계속한다:

1. `kRunOneThreadTest`(실제 init + 스핀 스레드 1개 = 총 2 ring3
   Task)부터 먼저 돌려 이 조합이 안전함을 재확인 - 안전하면 "손으로
   만든 스핀 스레드 자체"가 원인이 아니라 "3개 이상"이라는 개수 자체가
   임계값임을 좁힌다.
2. 세 번째 스레드를 `int 0x80` 없이 스핀만 하도록 바꿔서도 재현되는지
   확인 - 트랩 자체가 원인인지, 단순히 "3개 이상 스케줄링"만으로도
   재현되는지 구분한다.
3. `Scheduler::onTick`/`runLoop`에 임시 카운터/로그를 넣어 정확히
   몇 번째 컨텍스트 전환에서 무엇이 잘못되는지 추적한다(단,
   PL-C8648D4D가 실측으로 남긴 교훈 참고 - 진단용 `Serial::write`
   자체가 타이밍을 왜곡시켜 재현율을 바꿀 수 있으므로, 구조적 수정
   이후엔 반드시 로그를 걷어낸 최종 형태로 재검증한다).
4. PN-63BCFE45 문서가 정리해 둔 의심 지점 1~4(Scheduler 큐/
   `inRunQueue`/`gCurrentTask` 3개 이상 경쟁, `Paging::
   createAddressSpace()` 세 번째 호출 시 이상, IDT/GDT/TSS의 암묵적
   "동시 사용자 2개까지" 가정)를 하나씩 배제한다.

**완료 기준**: SMP4/단일 코어 양쪽에서 ring3 UserThread 4개 이상으로
60초+ 스트레스 테스트 무결 통과. 진단 코드는 검증 후 반드시 제거한다
(이미 코드 주석에 "커밋 전 반드시 제거"로 명시돼 있음).

### 2단계 — PN-D0ED9611 (execImage 전역 파라미터 공유 결함 수정)

1단계와 직접적인 선행 관계는 없지만 같은 `process.cpp`/ring3 진입
경로를 다루므로 이어서 처리한다. `gRing3EntryParams` 단일 전역을
없애고 진입 파라미터를 `UserThread` 자신으로 옮긴다.

### 3단계 — 프로세스 종료 처리 인프라 (PN-71C3D483 + PN-40E976F2, 함께 진행)

두 계획이 공유하는 근본 공백부터 푼다 - "실행 중이 아닌(이미 hlt
루프로 빠진) Task를 스케줄러에서 안전하게 떼어내는" 새 API가
필요하다(`Scheduler::retireCurrentTask()`는 "자기 자신만" 전제로
설계돼 재사용 불가). 이 API 설계에 확정되지 않은 세부가 나오면
임의로 정하지 말고 관련 문서(SP-04EE2A18 또는 신규 SP)에 질의로
등록한다. 이어서:

- self-terminate 핸들러(`kSyscallEndpointSelfTerminate`) 구현.
- `Process::destroy()` 호출 전 유저 매핑 전체 해제 - SP-2AAD7C8D
  §3(Maple Tree/VMA 추적)와 자연스럽게 맞물리므로, 이 VMA 추적
  자료구조를 이 단계에서 함께 도입하는 것을 검토한다.
- `AsyncTaskHandler::onCancel`을 프로세스/Task 종료 시퀀스에 실제로
  연결.

### 4단계 — 3단계까지 끝나야 의미를 갖는 검증 항목들

- **PN-0367CDBA** - Channel IPC 다중 accepter/reader/writer 실제
  스트레스 테스트. 임시 `UserThread` 드라이버로 지금도 착수
  가능하지만, 프로세스 모델이 안정화된 뒤 실제 여러 프로세스로
  재검증하는 편이 더 확실하다.
- **PN-B3DD3D19** - 인터럽트/IPC를 유저랜드 커널 서비스로 실제
  라우팅(devmgr/fs 등장의 시작점).
- **PN-268F062B** - 프로세스간 "공개 인터페이스" registry.
- **PN-6D497EB0** - Channel ID를 프로세스 간에 전달하는 메커니즘.

### 5단계 — review 상태로 대기 중인 하드웨어/파일시스템 설계 착수 순서

1~4단계가 "여러 유저 프로세스가 동시에 안정적으로 실행된다"를 실측
으로 증명해야 아래 순서가 실제로 진행 가능해진다:

1. **SP-7CC5693A**(VFS 커널 서브시스템) - `fs` 서비스가 VFS 마운트
   포인트를 실제로 처리하기 시작하는 지점이라 다른 드라이버보다
   먼저 다룬다.
2. **SP-C2670F69**(AHCI)/**SP-E35FD36C**(USB) - 스토리지/입력
   드라이버, VFS가 실제로 뭔가를 마운트할 대상이 필요해지는 시점에
   이어서 진행.
3. **SP-9DD4F3EA**(PnP, 장치 자동 인식/핫플러그) - 개별 드라이버가
   갖춰진 뒤 그 등록/탐지를 일반화.
4. **SP-39F18E30**(DMA 버퍼 관리자) - AHCI/USB 착수 시점에 실제
   DMA 요구사항이 구체화되면 같이 재검토.
5. **SP-2AAD7C8D**(mmap 서브시스템)의 남은 부분(mmap syscall API) -
   3단계에서 도입할 VMA 추적과 연속선상이므로 3단계와 병행 검토.

## 관련 문서/계획

이 계획의 실행 결과는 각 PN 항목이 완료될 때마다 그 계획 자신에
기록하고, 이 문서는 단계가 끝날 때마다 진행 상황 절을 추가해 갱신한다.
