# 실행 계획: 멀티 프로세스 실행 기반 완성 (ring3 컨텍스트 오염 버그 해결 + 프로세스 생명주기)

## 배경 — 현재 상태 조사 요약

PN-16CA347D("유저랜드 준비, 첫 프로세스 기동") 마일스톤은 완료됐다 -
실제 `minicore/init`이 initrd(CPIO)에서 로드되어 ring3 진입까지
성공했다(커밋 cea71f0). 이어서 PN-AEA74E1B(TSS.RSP0을 코어당
UserThread 하나 전제에서 멀티 UserThread 일반화로 확장)도 완료됐다
(커밋 eb1fe57).

그런데 PN-AEA74E1B 검증 중 **PN-63BCFE45**(그 수정과는 별개인 새
버그)가 발견됐다 - 한 코어에 ring3 UserThread가 **3개 이상** 있으면
실행 컨텍스트가 오염된다(RIP가 절대 도달 불가능한 주소로 튐, CR2도
근거 없는 값). 원인 미상 - 재현 조건만 확인된 상태다.

이 버그가 남아 있는 한 이 프로젝트의 다음 큰 이정표들이 전부 실질적으로
막혀 있다고 봐야 한다:

- QA-26450C3E의 미체크 항목("인터럽트가 올바른 커널 서비스로 라우팅",
  "IPC가 의도한 커널 서비스로 전파") - PN-B3DD3D19가 이걸 다루는데,
  devmgr/fs 등 **여러 유저랜드 커널 서비스가 동시에** 떠 있어야
  검증 가능하다.
- review 상태로 대기 중인 하드웨어/파일시스템 설계 문서(PnP
  SP-9DD4F3EA, AHCI SP-C2670F69, USB SP-E35FD36C, DMA SP-39F18E30,
  VFS SP-7CC5693A) - 전부 실제 드라이버/서비스 프로세스가 실행되는
  환경을 전제로 한다.
- mmap 서브시스템(SP-2AAD7C8D)의 남은 부분(mmap syscall API, VMA
  연동)도 "프로세스가 실제로 여러 개 살아서 매핑을 주고받는" 시나리오
  없이는 검증이 어렵다.

여기에 더해, 프로세스 **종료** 처리 자체가 아직 없다(self-terminate
핸들러 미구현 - PN-71C3D483, onCancel 호출 경로 미연결 - PN-40E976F2,
둘 다 "실행 중이 아닌 Task를 정리하는 메커니즘 자체가 이 프로젝트에
없다"는 같은 근본 공백을 공유). 그리고 이번 조사에서 별도로,
`Process::execImage()`가 ring3 진입 파라미터를 전역 인스턴스 하나에
담아 두는 v1 한계가 실제 멀티프로세스에서 반드시 재현됨을 확인해
PN-D0ED9611로 새로 등록했다.

**이 문서의 목적**: 위 사실들을 종합해, "첫 프로세스 기동" 이후
"실제로 여러 프로세스가 안정적으로 동시 실행"되는 상태까지 가는
경로를 우선순위대로 정리한다.

## 실행 순서

### 1단계 — PN-63BCFE45 근본 원인 규명 및 수정 (최우선, 이후 전부의 선행 조건)

**[갱신, 2026-09-15]** 재현 조건이 최초 서술("3개 이상")과 달랐음이
확정됐다 - 실제로는 **"실제 init + 코드/스택이 다른 스레드 1개"
(총 2개 UserThread)만으로 100% 재현**된다(기존 "스핀 스레드 2개"
테스트는 서로 완전히 동일한 코드/스택이라 우연히 증상이 안 보였을
뿐). 이 정정 덕분에 **근본 원인 #1이 확정**됐다 - CR3가
`kContextSwitch`/`iretq` 어디에도 저장·복원되지 않아, UserThread가
첫 ring3 진입 이후 재디스패치될 때 직전에 실행된 다른 UserThread의
주소공간으로 계속 실행되는 버그였다(cr2가 init 자신의 스택 오프셋과
바이트 단위로 일치함을 확인해 증명).

**부분 수정 완료 및 커밋(20eeefd3)** - `Task::userPml4Phys` 필드
추가, `Scheduler::onTick()`에서만 CR3를 복원(`runLoop()`의 idle→Task
디스패치 경로는 부트 스택 위에서 실행될 수 있어 CR3 조작이 안전하지
않음, PN-58501EAA 참고 - 첫 시도에서 Double Fault로 실제 확인).
GRUB/SMP4+init, PVH+init, PVH 무init 3개 시나리오 회귀 없음 확인.

**아직 미해결 - 새 크래시(근본 원인 #2, 가칭)**: 이 수정 이후에도
같은 최소 재현(2 UserThread)이 여전히 크래시한다 - 증상이 Page/Double
Fault에서 **`Scheduler::onTick()` 내부의 Debug 예외(#DB, vector 1)**
로 바뀌었다. `enqueue()` 호출 직후의 평범한 로컬 스택 프레임 읽기
명령에서 발생하며, 그 시점 rflags에 TF(Trap Flag)가 서 있는 것처럼
보이지만 진짜 아키텍처적 원인인지 스택/프레임 손상의 2차 증상인지는
아직 미특정. 자세한 내용/후속 조사 방향은 PN-63BCFE45 "다음에 할 일"
절 참고 - `enqueue()`의 cli/sti 페어링 재검토, TF 비트 설정 지점
추적, Task별 커널 스택 격리/TLB 일관성 확인이 다음 시도 후보다.

**완료 기준**: SMP4/단일 코어 양쪽에서 ring3 UserThread 2개 이상으로
60초+ 스트레스 테스트 무결 통과(원래 "4개 이상"에서 재현 조건 정정에
따라 "2개 이상"으로 하향 - 2개조차 아직 통과 못 함). 진단 코드는
검증 후 반드시 제거한다.

### 2단계 — PN-D0ED9611 (execImage 전역 파라미터 공유 결함 수정)

1단계와 직접적인 선행 관계는 없지만 같은 `process.cpp`/ring3 진입
경로를 다루므로 이어서 처리한다. `gRing3EntryParams` 단일 전역을
없애고 진입 파라미터를 `UserThread` 자신으로 옮긴다.

### 3단계 — 프로세스 종료 처리 인프라 (PN-71C3D483 + PN-40E976F2, 함께 진행)

두 계획이 공유하는 근본 공백부터 푼다 - "실행 중이 아닌(이미 hlt
루프로 빠진) Task를 스케줄러에서 안전하게 떼어내는" 새 API가
필요하다(`Scheduler::retireCurrentTask()`는 "자기 자신만" 전제로
설계돼 재사용 불가). 이 API 설계에 확정되지 않은 세부가 나오면
임의로 정하지 말고 관련 문서(SP-04EE2A18 또는 신규 SP)에 질의로
등록한다. 이어서:

- ~~self-terminate 핸들러(`kSyscallEndpointSelfTerminate`) 구현~~ -
  **완료(2026-09-15, 커밋 ff03f6a+a9b858a)**. `Scheduler::retireTask`/
  `Syscall::submitDetached`/특수 트랩 처리(QU-D96B1DCE 답변)까지 전부
  구현돼 실제 `userland/init`이 `mc::selfTerminate()`로 스스로 종료하는
  end-to-end 왕복이 QEMU로 검증됨. 검증 중 커널 레벨 Task로 디스패치할
  때 CR3가 복원되지 않던 별개의 버그(`gBootPml4Phys` 미복원)도 함께
  발견·수정. PN-71C3D483 항목 3(Process 자원 회수)만 PN-012E8C1A
  (AddressSpaceManager) 완료를 기다리며 남아 있음.
- `Process::destroy()` 호출 전 유저 매핑 전체 해제 - SP-2AAD7C8D
  §3(Maple Tree/VMA 추적)와 자연스럽게 맞물리므로, 이 VMA 추적
  자료구조를 이 단계에서 함께 도입하는 것을 검토한다.
- `AsyncTaskHandler::onCancel`을 프로세스/Task 종료 시퀀스에 실제로
  연결.
- **PN-71E50394**(신규 등록, 2026-09-15) - Signal 전달 인프라 실제
  구현(`Process::pendingSignals`/Kill 체크포인트/syscall API,
  SP-0666DB3C §4). `Kill`의 기본 동작(프로세스 종료)이 실제로
  뭔가를 정리하려면 이 단계의 종료 처리 메커니즘이 선행돼야 하므로
  함께 진행한다.

### 4단계 — 3단계까지 끝나야 의미를 갖는 검증 항목들

- **PN-0367CDBA** - Channel IPC 다중 accepter/reader/writer 실제
  스트레스 테스트. 임시 `UserThread` 드라이버로 지금도 착수
  가능하지만, 프로세스 모델이 안정화된 뒤 실제 여러 프로세스로
  재검증하는 편이 더 확실하다.
- **PN-B3DD3D19** - 인터럽트/IPC를 유저랜드 커널 서비스로 실제
  라우팅(devmgr/fs 등장의 시작점).
- **PN-268F062B** - 프로세스간 "공개 인터페이스" registry.
- **PN-6D497EB0** - Channel ID를 프로세스 간에 전달하는 메커니즘.

### 5단계 — review 상태로 대기 중인 하드웨어/파일시스템 설계 착수 순서

1~4단계가 "여러 유저 프로세스가 동시에 안정적으로 실행된다"를 실측
으로 증명해야 아래 순서가 실제로 진행 가능해진다:

1. **SP-7CC5693A**(VFS 커널 서브시스템) - `fs` 서비스가 VFS 마운트
   포인트를 실제로 처리하기 시작하는 지점이라 다른 드라이버보다
   먼저 다룬다.
2. **SP-C2670F69**(AHCI)/**SP-E35FD36C**(USB) - 스토리지/입력
   드라이버, VFS가 실제로 뭔가를 마운트할 대상이 필요해지는 시점에
   이어서 진행.
3. **SP-9DD4F3EA**(PnP, 장치 자동 인식/핫플러그) - 개별 드라이버가
   갖춰진 뒤 그 등록/탐지를 일반화.
4. **SP-39F18E30**(DMA 버퍼 관리자) - AHCI/USB 착수 시점에 실제
   DMA 요구사항이 구체화되면 같이 재검토.
5. **SP-2AAD7C8D**(mmap 서브시스템)의 남은 부분(mmap syscall API) -
   3단계에서 도입할 VMA 추적과 연속선상이므로 3단계와 병행 검토.

## 진행 상황 갱신 (2026-09-15, 최신화)

**1단계**: **[갱신, 완료]** PN-63BCFE45가 "실제 init + 스레드 1개(총
2 UserThread)"로 근본 원인 #2(#DB/TF)를 다시 재현 시도했으나 4가지
조합(총 ~1만 틱) 전부 재현 실패했고, 그 사이 **SP-83A07867/
PN-40210D5A**(CR3 동기화를 스케줄러의 모든 디스패치 경로로 완전히
통합 - onTick/kTaskStartTrampoline/yieldCurrent·parkCurrent 재개
지점 전부)가 완료(커밋 bd58d99)돼 근본 원인 #1이 다루지 못했던
"아직 발현 안 된 세 번째 공백"까지 구조적으로 막혔다. 설계자가 이
재검증을 근거로 승인해 PN-63BCFE45는 `completed`로 전환됐다 - 1단계
완료.

**2단계(PN-D0ED9611)**: 완료(커밋 47d2544) - `gRing3EntryParams`
전역을 제거하고 `Task::ring3EntryPoint`/`ring3UserStackTop` 필드로
옮겼다.

**3단계**: self-terminate(PN-71C3D483 항목 1+2) 완료에 이어, 그
항목 3(Process 자원 회수)의 선행 조건이던 **PN-012E8C1A**
(KernelAddressSpaceManager/ProcessAddressSpaceManager)와
**PN-38D17292**(Maple Tree 멀티레벨 분할/병합, v1 8개 엔트리 제약
해소)도 완료돼, 이제 PN-71C3D483 항목 3(`ProcessAddressSpaceManager::
unmapAll()` 기반 자원 회수)에 실제로 착수 가능한 상태다 - 다음
자연스러운 착수 대상.

## 진행 상황 갱신 2 (2026-09-15)

**3단계 완료**: PN-71C3D483(self-terminate 항목 1/2/3 전부)이
`completed`로 전환됐다 - `ProcessAddressSpaceManager::
registerFixedRegion()`(신규, findGap 없이 이미 고정된 가상주소를
장부에만 등록)을 `elf::loadIntoAddressSpace()`/`Process::execImage()`
에 배선하고, `Process::destroy()`가 `addressSpace.unmapAll()`을
먼저 호출하도록 완결했다. self-terminate가 이제 커널 스택뿐 아니라
유저 주소공간까지 완전히 회수한다(실측: `freePageCount()` 델타로
등록된 VMA만 정확히 회수됨을 확인).

**새로 발견된 후속 항목**: `Paging::destroyAddressSpace`가 PDPT/PD/PT
중간 테이블 프레임을 회수하지 않는 사전 존재 누수를 PN-2E6CB2D5로
별도 등록(지금은 부팅당 프로세스 1개뿐이라 실질 피해 없음 - 다중
프로세스 반복 생성/종료 워크로드가 생기면 재검토).

**4단계 착수 가능**: 3단계가 끝나 PN-B3DD3D19(인터럽트/IPC 유저랜드
라우팅)의 남은 선행 조건도 전부 해소됐음을 확인해 `scheduled`로
전환했다 - devmgr 실물 없이도 임시 UserThread를 "가짜 devmgr"로 써서
배선 자체는 지금 착수 가능.

## 관련 문서/계획

이 계획의 실행 결과는 각 PN 항목이 완료될 때마다 그 계획 자신에
기록하고, 이 문서는 단계가 끝날 때마다 진행 상황 절을 추가해 갱신한다.
