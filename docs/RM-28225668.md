# Minicore 인터럽트 벡터 목록

설계자 지시(2026-09-16, 메시지) - "[SP-9525C4C0] kLoadBalanceWakeVector의
실제 벡터 번호 하나만 정하기 보다, 할당표 문서를 `Minicore 인터럽트
벡터 목록`으로 정리하는데, 이런 벡터들은(로드 밸런싱이라던지 커널
최적화, 커널 내 인터럽트 전달 등) `0xe0` ~ `0xfd` 범위에서 사용하고
`0xff`는 NMI, `0xfe`는 `Spurious` 벡터로 할당해." RM-7C249618("라이브러리
목록")/RM-C65F7760("VFS 구조")/RM-48E1E610("Syscall 할당표")/RM-B5764185
("Signal 번호표")와 같은 성격의 현황판 - 새 전역 인터럽트 벡터가
설계/구현될 때마다(구현 전 제안 단계에서도, RM-48E1E610과 같은 원칙,
CLAUDE.md 규칙 10 패턴 준용) 이 표에 행을 먼저 추가해 번호가 겹치지
않게 한다.

## 1. 고정 배정 (하드웨어/아키텍처 예약)

| 벡터 | 이름 | 의미 | 비고 |
|---|---|---|---|
| `0xFF` | NMI | Non-Maskable Interrupt | 설계자 지시로 고정 |
| `0xFE` | Spurious | 가짜 인터럽트(APIC) | 설계자 지시로 고정 |

## 2. 커널 내부 IPI/최적화 벡터 (`0xE0` ~ `0xFD`)

로드밸런싱/TLB 샷다운처럼 "커널이 자기 자신에게, 혹은 다른 코어에게
보내는" 저수준 IPI 전용 범위 - 유저랜드로 노출되는 syscall
(`SyscallEndpointId`, RM-48E1E610)이나 디바이스 IRQ(PIC/IOAPIC 라우팅)
와는 별개 네임스페이스다.

| 벡터 | 이름 | 상태 | 근거 |
|---|---|---|---|
| `0xE0` | TLB 샷다운 IPI | **[갱신, 2026-09-16, PN-C7D62610 완료]** `0x25`→`0xE0` 재배선 구현 완료(commit ffc38eb) - SMP4 실측으로 새 벡터 IPI 송수신+ACK 확인 | SP-DE19BB1C §2.2 |
| `0xE1` | `kLoadBalanceWakeVector`(로드밸런싱 idle 코어 기상 IPI) | **[갱신, 2026-09-16, PN-04D6197A]** 구현 완료 - Push/Pull 양쪽 다(`kWakeCoreIfIdle` 호출부 포함) QEMU SMP4 실측 검증 완료 | SP-9525C4C0 §4 |
| `0xE2` | `kForcedMigrationVector`(Running Task 강제 이관 IPI) | **[정정, 2026-09-17, minicore-f8 세션]** 이 표가 "구현 대기"로 남아 있었으나 실제로는 구현 완료 - `scheduler.cpp`에 `requestForcedMigration()`/`kForcedMigrationIsr`/`ForcedMigrationRequest` 전부 존재, `idt.cpp`에 `kForcedMigrationVector` 디스패치도 등록돼 있음을 grep으로 직접 확인. 자동 발동 트리거는 여전히 v1에 없음(수동/진단 API만, QU-FAC822D4 답변) - 이 부분은 원문 그대로 유효 | SP-ECC59BAE §3.1 |
| `0xE3` | `kAsyncDrainVector`(AsyncReactor 하이브리드 (A)+(C) Notification 중 (C) 경로 - 이 코어 자신에게 즉시 드레인 요청) | **[구현+검증 완료, 갱신 2026-09-17]** `AsyncReactor::submitCompletion(task, preemptive=true)`가 발사, `kAsyncDrainIsr`이 `drainOnce()` 반복 호출(commit 5f70565) - (A) 경로는 QEMU 4개 표준 시나리오로 당시 검증 완료. (C) 경로를 막았던 두 버그(PN-57CF48DB - idle 전환 CR3 미동기화 Double Fault, commit 8d4969f; 그 수정으로 드러난 PN-622BA93C - `submitCompletion()`의 코어 라우팅 오류로 인한 connector 무응답, commit c987dbe)가 모두 해결돼, accepter/connector가 서로 다른 코어(SMP4)에서 실제로 핸드셰이크를 완료하는 것까지 실측 확인됨 - 더 이상 보류 항목 없음 | SP-F682B889 §4, PN-FEAAF154 |

| `0xE4` | `kDebugRegSyncVector`(디버그 레지스터 스냅샷 동기화 IPI) | **[뒤늦게 편입, 2026-09-23]** 이 문서가 갱신되지 않은 채 이미 구현/사용 중이었음을 발견 - `debug_session.cpp`의 `kDebugRegSyncVector`가 실제로 이 번호를 쓰고 있었다(`InterruptDelegation::kIsFixedVector`의 하드코딩된 고정 벡터 배제 목록엔 이미 있었음). SCI 벡터를 다음 미사용 번호로 잘못 계산해 이 번호와 충돌시켰다가(`InterruptDelegation::allow()`가 조용히 실패 - 에러 반환값을 제대로 확인하지 않으면 놓치기 쉬운 버그) 실제 QEMU `system_powerdown` 테스트로 발견/수정한 사례 - 이 문서와 `kIsFixedVector` 하드코딩 목록이 동기화돼 있는지 새 벡터를 예약하기 전에 항상 둘 다 확인할 것(RM-F2DAFF66과 같은 "문서 vs 코드 드리프트" 패턴) | SP-9A6D579F |
| `0xE5` | `kAcpiSciVector`(ACPI 전원 버튼 등 SCI) | **[정정, 2026-09-24] 구현은 완료됐으나 현재 부팅 경로에서 비활성화 상태** - `Acpi::resolveIsaIrq(sciInterruptGsi())`로 실측한 극성/트리거(이 프로젝트 QEMU: gsi=9, activeHigh, level)로 `IoApic::setRedirection` + PM1_EN.PWRBTN_EN 세팅, `kernel::InterruptSubscription`(SP-71DA77B3)의 기존 Subscribe/WaitInterrupt 경로 재사용(AHCI와 동일 패턴) - SMP1에서는 QEMU 모니터 `system_powerdown`으로 실제 종료까지 완전 실측 확인됐으나, **GRUB SMP4에서 이 스레드를 스폰하는 것만으로(전원 버튼을 누르지 않아도) 매우 높은 빈도로 PANIC이 재현돼(PN-E4C6AF72/PN-3DDF2797과 근본 원인 공유 가능성)**, `kmain.cpp`의 `kSpawnPowerKernelThreadIfSupported();` 호출 한 줄이 주석 처리돼 있다(함수 자체는 보존) - 원인 규명 전까지 이 벡터는 등록만 돼 있을 뿐 실제로 발동하지 않는다. `Shutdown`/`Reboot` syscall(그룹10)은 이 경로와 무관하게 정상 동작 | SP-0C7A4F3B §1, PN-0B461E6F |

**할당 규칙**: 다음 미사용 번호는 `0xE6`부터 - 새 항목을 추가할 때
이 표의 최댓값 다음 번호를 쓰고, 재사용/건너뛰기 금지(RM-48E1E610과
동일 원칙). **새 번호를 정하기 전에 `interrupt_subscription.cpp`의
`kIsFixedVector()` 하드코딩 목록도 함께 확인한다** - 이 표만 보고
"다음 미사용 번호"를 계산하면 이미 코드에 있지만 이 표에 반영 안 된
고정 벡터와 충돌할 수 있다(위 `0xE4` 사례). 구현이 끝나면 "상태"
칸만 "구현 완료"로 갱신한다.

## 3. 디바이스 IRQ / 기타

아직 이 표로 편입된 항목 없음 - PIC/IOAPIC 라우팅을 다루는 문서가
생기면 이 절에 추가한다(예: PCI 인터럽트 라인 매핑, MSI/MSI-X).
`kAcpiSciVector`(위 §2)는 "디바이스 IRQ"지만 시스템에 유일하고
커널 전용이라 §2에 남겨 뒀다 - 여러 개 생기는 일반 장치 IRQ가
생기면 그때 이 절을 채운다.
